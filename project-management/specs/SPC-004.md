## Summary

Define a reusable, secure, local presentation and feedback utility so an agent
normally supplies structured content rather than constructing a new HTML page
for every complex reply. The contract owns utility rendering and session state
without importing or influencing the consuming product's design architecture.

## Delta against current capability

**ADDED — interactive presentation capability.** A CodeFlow-owned renderer,
declarative document format, local review lifecycle, and `cf-present` skill.

**MODIFIED — CAP-001/CAP-002/CAP-012.** Init/update/customization and manifests
gain the skill and only the project-owned optional configuration warranted by
use; the renderer/catalog ship with CodeFlow rather than as copied frontend
trees.

## Behavior

1. A versioned JSON envelope contains typed blocks; prose-bearing fields contain
   Markdown. The schema rejects malformed documents. An older renderer opening
   a newer schema falls back to an explicit read-only/raw view, never a silent
   partial render.
2. The built-in accessible block catalog covers narrative, bullets, callouts,
   comparisons, decisions/questions, tables, status/evidence, code/diffs,
   trees, diagrams/timelines/flows, media, disclosures/tabs, and structured
   feedback. The skill chooses by information shape; it neither dumps prose nor
   forces visual decoration. A visual block must carry information through
   relationship, sequence, comparison, state, evidence, scale, or actual
   appearance; a text box with decorative styling remains prose and is never
   counted as a visual explanation. A warranted presentation must name the
   question it answers better than ordinary chat and give that governing
   relationship one primary information-bearing form at rest; restyling the
   same answer into panels is a failure, not a successful surface.
3. CodeFlow applies its `cf-design` process to `cf-present` itself: independent
   research, materially different directions when open, representative rendered
   prototypes, Claude-led design judgment, Codex feasibility/fidelity review,
   and an explicit utility `DESIGN_INTENT`. The selected default must be modern,
   elegant, aesthetically coherent, pleasing, functional, responsive, and
   suited to focused explanation/review rather than resembling a generic model
   artifact or dashboard template. Unresolved operator-owned direction is
   brought to the user with the real alternatives and consequences.
4. The renderer supplies a small curated set of utility themes. Every theme has
   coherent light/dark modes, follows system preference by default, supports a
   persisted user override, avoids incorrect-theme flash, and preserves
   contrast, non-colour meaning, diagrams, code, media, controls, and reduced
   motion.
5. An optional project-owned primitive-token file may influence utility colour,
   type, spacing, radius, and approved identity assets through a closed,
   versioned schema. It cannot import CSS, product components, classes,
   frameworks, font executables, or product runtime dependencies.
6. Default language is session-aware, plain, direct, calm explanation that
   preserves exact terms and adapts to the user's evidenced knowledge and tone
   preference. Standard components do not inject canned personality or
   decorative emoji.
7. Sessions have stable UUIDs, document revisions, task/spec/ADR provenance
   when applicable, feedback events with received/delivered/addressed/dismissed
   state, explicit user/agent closure, and bounded history. History is never
   injected into later model context without an explicit resume/look-back.
   Review notes may target exact text, one semantic element, a dragged visual
   area, a whole block, or the whole document. Pending targets remain visibly
   numbered while edited. Element paths and normalized regions are generated
   by the runtime, bounded and validated server-side, and re-anchor only when
   their exact coordinate space remains unchanged; otherwise they remain
   visibly orphaned rather than drifting to a guessed target.
8. Owner-private state uses the platform-appropriate OS state directory keyed
   by canonical project identity, so worktrees share state without writing
   runtime data into `.git` or the worktree. Concurrent updates use an explicit
   locking/append model.
9. Accepted durable decisions are summarized into the canonical task, spec, or
   ADR. Raw feedback and exports remain untracked unless explicitly promoted to
   a user-selected durable path.
10. The local service binds loopback by default, allocates random ports and
   per-session tokens, validates Host/Origin, authenticates every mutation and
   event channel, applies strict CSP/no remote resources, confines real paths,
   isolates untrusted content, and never attaches to the operator's browser
   profile or active view.
11. V1 permits one session-local sandboxed HTML escape block with no network,
    credentials, review-chrome access, or durable execution. It does not ship
    project-tracked executable extensions, a component SDK, SQLite index,
    cloud sharing, or implicit remote serving.

## Interfaces and formats

```text
codeflow present open <document.json>
codeflow present list
codeflow present show <session-id>
codeflow present update <session-id> <document.json>
codeflow present history <session-id>
codeflow present feedback <session-id> [--follow]
codeflow present resolve <session-id> <event-id> --event-version <n> --status addressed|dismissed
codeflow present close <session-id>
codeflow present export <session-id> --out <path>
codeflow present clear [<session-id>] [--older-than <duration>] [--dry-run]
```

- Canonical document and optional utility-token schemas are versioned assets.
- Default closed-session retention is concrete and configurable; implementation
  starts from 30 days, 100 closed sessions, and 500 MiB per project, evicting
  oldest closed state first while preserving active state. A material change to
  those bounds follows the normal plan/spec change path rather than silently
  weakening retention or cleanup behavior during implementation.
- `.codeflow/present/config.toml` and the primitive-token file are project-owned
  and created only when customized. CodeFlow updates never overwrite them.
- The skill contains routing/workflow; conditional references explain blocks,
  language, promotion, retention, and security. Deterministic mechanics remain
  in Rust and renderer assets.
- V1 supports macOS, Linux, native Windows, and WSL2 using their native path,
  permission, process, browser-launch, and state-directory conventions. Cross-
  compilation proves only buildability; each supported runtime needs native or
  explicitly scoped runtime evidence, and an unqualified platform fails closed
  rather than selecting an insecure fallback.

## Edge cases

- Unsupported schema version, malformed Markdown, oversized content, duplicate
  feedback delivery, concurrent writers, stale revision, moved/re-cloned repo,
  interrupted server, abandoned session, and cleanup racing an active session.
- DNS rebinding, forged Host/Origin, token leakage, path traversal, symlink
  escape, imported prompt injection, malicious HTML, remote asset fetch,
  cross-session feedback, and export containing private review chrome/state.
- System theme changes during a session, explicit override precedence, missing
  project tokens, mode-specific contrast/media/diagram failure, and print or
  standalone export fidelity.
- A simple response that should not invoke the skill; a complex response whose
  standard blocks are insufficient; a user-ended session that an agent must not
  reopen without invitation.
- A visually polished but information-poor result made from repeated text cards;
  a dense prose wall with decorative colour; or an unnecessary diagram added
  only to satisfy a visual instruction.
