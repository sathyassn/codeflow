# SPC-016: Record version order, the merge remerge and the policy verdict name

## Summary

This spec pins three requirements of the delivery system whose SPC-013 text is out of date: how `codeflow ci` decides which line's version of a record is older (SPC-013 R-52), how it reads a merge's own changes (SPC-013 R-53), and the name of the policy job's verdict (SPC-013 R-109). TSK-1185 builds the R-52 and R-53 changes. The R-109 name is already on `main` (commit f33ea5e85, 2026-11-06, `.github/workflows/codeflow-policy.yml` line 105), so this spec only records it. SPC-013 holds the earlier text of each. Every other SPC-013 requirement is unchanged and stays in SPC-013.

### Why this spec does not supersede SPC-013

SPC-013 is implemented: its consumers are EPC-020, TSK-229 and TSK-253 (complete) and TSK-124, TSK-125 and TSK-126 (cancelled), so its text is frozen. Superseding it would re-open those completed consumers and every complete EPC-020 task that inherits SPC-013 through its epic, because a completed task may not cite a superseded spec. That is right only when the contract they were built to changes, and here it does not: the EPC-020 work was built correctly to SPC-013, and only these three requirements change. The method says: "An `implemented` spec is frozen, so a later change gets a new spec or an explicit superseding record; do not rewrite history" (`.claude/skills/cf-method/references/project-organization.md`, lines 563 to 565 at eb4d74418). So this spec adds to SPC-013 and does not supersede it. A reader of SPC-013 R-52, R-53 or R-109 takes the text below for any landing judged after TSK-1185 lands.

## Behavior

This section holds the changed requirements. Each item quotes SPC-013's text and the text that replaces it. The rest of each requirement is as SPC-013 states it.

### R-52: which line's version of a record is older

SPC-013 R-52, in the rule for the criteria a reopened task keeps, says:

> a line's version is older only when that line inherited it unchanged: every commit that introduced it there is a proper ancestor of every introduction of the other line's version;

It now reads:

> a line's version is older only when ancestry proves it: every commit that wrote it there, with no parent holding it, is a proper ancestor of every commit that wrote the other line's version, and every merge that kept it from one parent either precedes all those writes or rejected nothing, because its history never held the other version and each parent it kept the version against holds a version written before it, or never held the record, with no name or date read;

### R-53: the paths a merge answers for

SPC-013 R-53 says that a range answers for "the paths each merge in the range changes against the automatic remerge of its parents, conflicted paths included". It now reads:

> the paths each merge in the range changes against the automatic remerge of its parents (`git merge-tree --write-tree`, run in an empty repository that reads only the judged repository's objects, so no merge attribute, config, replacement or commit-graph counts; a merge is clean only when that is conflict-free and its recorded tree is exactly the result), conflicted paths included

### R-109: the policy job's verdict name

SPC-013 R-109's amendment of 2026-11-03 (TSK-336) says "the verdict is named `trusted: commit standards`". It now reads "the verdict is named `commit standards`". Push, schedule and dispatch runs are unchanged: they check only the registry, in their own workflow under the name `registry check`, and create no `trusted:` check.

- SPC-013's consumers are unaffected: their contract is SPC-013, which is unchanged.
