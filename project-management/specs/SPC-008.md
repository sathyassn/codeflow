# SPC-008 — replace-only portal ownership and safe migration

## Summary

Change CAP-015's update contract, not its documentation value. Keep the embedded
offline starter, Markdown authority, layered concept/architecture/technical
browsing, source links, search, supported appearance tokens and public assets.
Offline materialization does not promise offline Node dependency installation.
No tracked pristine runtime copies or automatic three-way source merging.

## Behavior

Fresh setup adopts one portal root. CodeFlow owns its coherent runtime; the
project owns configuration, supported tokens and public assets. Existing
configuration seams are bounded; bespoke runtime/layout changes use explicit
whole-runtime transfer, not an unsupported promise of universal extensions.

Before any portal write, classify affected paths and plan one transaction.
Unchanged managed files may be replaced. Missing managed files are repairable.
Existing bytes equal to the incoming release are accepted. Modified managed
bytes, unknown incoming-path collisions and edited retiring paths stop the
whole portal update before content or state advances. Preserve local edits
and report choices: rehome supported customization, explicitly restore reviewed
managed bytes, or transfer the runtime. Never auto-transfer on a conflict.
Unchanged retiring managed files may be removed. No line merge of lockfiles or
any other runtime source. Report portal outcome separately from general scaffold
changes; the enclosing codeflow update is not a cross-feature transaction.

Fresh adoption may seed absent user configuration. After adoption, missing
project-owned files are reported, not silently recreated. Repeated setup/update
never reclaims project ownership, including newly introduced upstream files.

## Transfer and state

Add only codeflow portal transfer --confirm to the existing portal command;
it operates on the adopted root and requires explicit confirmation.
Transfer covers the complete runtime, not selected files. Repeat transfer is a
clear no-op, never a reset. Update in transferred mode preserves the runtime,
including intentional deletions, and reports upstream reconciliation as
project-owned. No new show, restore, package manager or registry surface.

Adoption schema v2 retains root, starter_version and file hashes. It explicitly
records whole-runtime ownership and a declared generator identity {name,version}.
While managed, provenance follows the installed release and identity is the
managed release's pinned generator. After transfer, starter version/hashes are
frozen transferred-from provenance, not claims about current runtime bytes.
A project may version/rename a genuinely forked generator by updating its
declaration and generator together; unsupported evidence still fails.

Evidence schema remains v1. Validate generator name and version against the
declared identity; managed mode additionally retains the managed-name pin.
Transferred mode must not reject a legitimate declared renamed generator merely
because its name differs from @codeflow/docs-portal. Bound identity lengths and
require nonempty values. Retain closed schema parsing and every existing source,
output, path, size, commit and evidence-structure check. Never execute the
project generator inside the read-only Rust validator. This validates declared
evidence against bytes, not runtime provenance attestation, visual fidelity,
accessibility, browser behavior, quality or security by itself.

The adapter, detached validator, starter manifest, adoption state and generator
declaration must agree for each managed release. A regression test catches a
partially updated release identity. Customized generators must retain the
compatible evidence contract; never weaken validation to make transfer pass.

Transfer is durable, not cryptographically irreversible. Restoring complete
pre-transfer runtime and state from Git is a separate explicit reviewed operation,
with current changes preserved. Setup never does this automatically.

## Migration and recovery

Recover legitimate pending legacy journals before reading/migrating adoption
state. Preserve the lease, bounded staging, state-last publication, hash
comparison, rollback and interrupted-operation recovery. No partial coherent
runtime version may be reported successfully upgraded.

Schema-v1 migration inspects current owned bytes, not merely metadata. Distinguish
absent managed files (repairable), modified managed files (stop/preserve), and
unknown or hash-mismatched baseline entries (stop/preserve). Authenticate each
legacy baseline deletion as a known regular file with bounded reads and a matching
content-addressed hash; never recursively delete unknown or changed content.
Remove authenticated obsolete blobs only in the successful migration transaction.
Empty legacy directory removal is bounded and ownership-checked. Old journals
remain recoverable even though new installs create no baselines.

Reject traversal, unsafe roots, symlinks/reparse escapes, duplicate/unknown state
fields, oversized files and resource exhaustion. Never silently downgrade a
future schema. Failed preflight leaves portal content and adoption state
byte-identical; failed commit rolls back or leaves valid recovery evidence.

## Verification

Exercise fresh/no-portal/unchanged/repeated adoption, drift and identical-incoming
content, missing managed versus project-owned files, collisions, retirement,
transfer and post-transfer additions/deletions, clean and adversarial v1 migration,
legacy journals, race/path failures and transaction-stage fault injection.
Prove v2 never line-merges a lockfile. Test declared generator identity,
legitimate renamed project generators and unchanged evidence failures.

Run green/brownfield distribution and update preservation, manifest/mirror/budget
checks, real portal build plus browser journeys before and after transfer. Native
Claude/Codex trials show appropriate ownership choices, respect for local
edits and honest success limitations. Deterministic tests are not native behavior
evidence; neither substitutes for rendered review. No visual redesign.
