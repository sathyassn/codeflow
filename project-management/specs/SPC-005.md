## Summary

Define a durable repository-documentation portal skill and maintainable starter
that turns authoritative project sources into a layered, navigable, visually
clear guide. The portal is a CodeFlow utility: it may reflect approved project
identity but does not determine or share the consuming product's UI stack.

## Delta against current capability

**ADDED — documentation portal utility.** A `cf-docs-portal` skill, reusable
starter, source/version contract, incremental update workflow, prototype and
evaluation assets, and CodeFlow dogfood portal.

**MODIFIED — CAP-001/CAP-002/CAP-012.** Full-tier scaffold/update/customization
can opt into the portal utility without imposing its frontend dependencies on
projects that do not use it.

## Behavior

1. Before a technical direction is selected, the Claude judgment primary and
   Codex independently research the repository's information needs and a broad
   set of strong modern documentation, product, editorial, and knowledge
   experiences. Linear may be one reference; no single site, generic technical
   writing guide, or remembered pattern becomes the design.
2. The design pass produces several materially distinct prototypes, not palette
   swaps. They are rendered in light and dark modes, reviewed for content
   hierarchy, navigation, comprehension, source traceability, accessibility,
   maintainability, and project fit, then compared by both primary seats. The
   Claude judgment primary leads the final design recommendation; unresolved
   operator-owned direction is brought to the user.
3. CodeFlow applies the `cf-design` process to the documentation utility as a
   CodeFlow product while keeping it separate from consuming-product design.
   The selected common/default experience must be modern, elegant,
   aesthetically coherent, pleasing, functional, and especially strong at
   orientation, comprehension, and progressive exploration; it must not look
   like a generic generated docs template.
4. The selected portal layers concept and purpose, product/capability and
   architecture, then technical/module/file detail. Left/right navigation,
   search, breadcrumbs, cross-links, source links, version context, and
   progressive disclosure are used only where they improve finding and
   comprehension.
5. Prose, bullets, tables, diagrams, architecture maps, screenshots, code, and
   file/module drill-down are selected by information shape. Dense text walls
   and decorative visual dashboards both fail review. A visual must expose
   relationships, sequence, comparison, state, evidence, scale, or actual
   appearance; paragraphs placed in attractive cards are prose, not visuals.
6. Authoritative repository sources remain truth. Generated pages cite or link
   their source, surface conflicts/missing rationale, and never invent history,
   purpose, behavior, or implementation relationships. Incremental updates
   preserve unaffected approved content and identify stale pages.
7. Language follows documented project voice when present and otherwise stays
   plain, precise, neutral, and topic-led. Titles/navigation labels are
   descriptive. Procedures prefer direct imperatives; personal pronouns are
   contextual rather than mechanically banned. Marketing voice, fabricated
   familiarity, cryptic headings, and decorative emoji are absent by default.
8. The portal utility provides curated themes when no approved project utility
   tokens exist. Every theme has coherent light/dark modes, system-following
   default, persisted override, accessible contrast and navigation, reduced
   motion, and correct code/diagram/table/media behavior. Optional project
   influence uses the same narrow primitive-token boundary as cf-present.
9. The portal scaffold is technically coherent, componentized, testable,
   versioned with the repository/doc set, and maintainable without copying
   source prose into a second manual truth. It owns no product components or
   runtime dependencies and shares no visual/component runtime with cf-present.

## Interfaces and formats

- `cf-docs-portal/SKILL.md` owns discovery, research, design settlement,
  generation/update, review, and source-reconciliation workflow.
- Skill assets contain the selected starter and representative fixtures;
  conditional references contain source mapping, information architecture,
  language, theme, update, and verification guidance.
- Deterministic scripts validate source links, version metadata, navigation,
  build output, and stale/orphan pages. V1 does not add a generative CodeFlow
  CLI command merely to wrap model judgment.
- A project chooses an output location and whether generated portal source is
  tracked. CodeFlow and Agent OS dogfood portals remain owned by their actual
  repositories; the public `agent-os-portal` remains a separate repository.

## Edge cases

- A repository with established docs information architecture or visual
  identity; a repo with none; a monorepo with several surfaces; a tiny project
  where a portal is unjustified.
- Conflicting sources, missing ADR rationale, renamed files/modules, version
  skew, broken deep links, orphan pages, source deletion, and generated copy
  that sounds plausible but is not evidenced.
- Prototype selection based on novelty or one admired reference rather than the
  repository's audience and content; copied Linear styling; visually attractive
  but shallow or inaccessible output; text-card grids masquerading as visual
  explanation; one desktop/light screenshot treated as proof.
- Theme or navigation customization that couples the portal to product code;
  utilities influencing the product's design direction in reverse.

## Open questions

The product/utility boundary and prototype-first process are resolved. The
independent Codex lane for TSK-008 provisionally recommends a hybrid information
architecture: a guided orientation and task journey, contextual architecture
explorers only where relationships warrant them, and source-adjacent editorial
explanation. It also proposes Astro Starlight as a static technical baseline,
with a repository-source adapter and disposable generated build model. The
research, alternatives, measurements, risks, and verification limits are
recorded in
`docs/verification/documentation-portal-research-2026-08-01.md`.

These are evidence-backed proposals, not settled requirements. Claude's
independent lane, the cross-model comparison, the exact portal theme and
information architecture, and the framework decision remain open. SPC-005
cannot become `approved` before both primary seats settle those questions and
any experience-changing operator decision is resolved.
