## Summary

Define a durable repository-documentation portal skill and maintainable starter
that turns authoritative project sources into a layered, navigable, visually
clear guide. The portal is a CodeFlow utility: it may reflect approved project
identity but does not determine or share the consuming product's UI stack.

## Delta against current capability

**ADDED — documentation portal utility.** A `cf-docs-portal` skill, reusable
starter, source/version contract, incremental update workflow, prototype and
evaluation assets, and CodeFlow dogfood portal.

**MODIFIED — CAP-001/CAP-002/CAP-012.** Standard/full scaffold, update, and
customization can opt into the portal utility without imposing its frontend
dependencies on projects that do not use it.

## Behavior

1. Before a technical direction is selected, the Claude judgment primary and
   Codex independently research the repository's information needs and a broad
   set of strong modern documentation, product, editorial, and knowledge
   experiences. Linear may be one reference; no single site, generic technical
   writing guide, or remembered pattern becomes the design.
2. The selected common/default experience is a layered field guide, settled
   after independent Claude and Codex research, a rendered three-direction
   comparison, and Claude-led reconciliation. The default Orient entry uses an
   editorial, numbered journey with persistent source context. System material
   uses contextual C4-flavored architecture islands only when a relationship
   benefits from direct exploration. Records use evidence-adjacent reference
   pages for decisions, work, and verification.
3. CodeFlow applies the `cf-design` process to the documentation utility as a
   CodeFlow product while keeping it separate from consuming-product design.
   The selected common/default experience must be modern, elegant,
   aesthetically coherent, pleasing, functional, and especially strong at
   orientation, comprehension, and progressive exploration; it must not look
   like a generic generated docs template.
4. The portal layers concept and purpose, product/capability and architecture,
   then technical/module/file detail. Navigation, Pagefind search, breadcrumbs,
   cross-links, source links, version context, and progressive disclosure are
   used only where they improve finding and comprehension. Architecture
   diagrams have accessible titles/descriptions, labeled directional
   relationships, a legend where needed, and build-time light/dark rendering.
5. Prose, bullets, tables, diagrams, architecture maps, screenshots, code, and
   file/module drill-down are selected by information shape. Dense text walls
   and decorative visual dashboards both fail review. A visual must expose
   relationships, sequence, comparison, state, evidence, scale, or actual
   appearance; paragraphs placed in attractive cards are prose, not visuals.
6. Authoritative repository sources remain truth and are read as bounded blobs
   from one clean, full Git commit. Each generated page records `source_path`,
   `source_sha256`, and `built_from_commit`, shows a pinned-commit source link,
   and displays the repository/release version when defined. V1 uses a
   snapshot-at-commit model and creates no copied historical version trees.
   If current Markdown cannot parse, its stable route contains only a bounded,
   visible, non-searchable current-source error page; ancestor content and
   prior generated output are never republished. Broken links or strict ID
   references, duplicate routes, orphaned pages, missing source/version
   metadata, and unavailable local Git objects fail the build.
   Every publishable Markdown file selected by the committed source-root and
   exclusion configuration has exactly one current page or error stub. Every
   configured input and the adopted runtime must also match committed bytes,
   including edits masked by index flags.
7. Strict `CAP-###`, `ADR-####`, `EPC-###`, `SPC-###`, and `TSK-###` tokens are
   auto-linked with contextual previews. One declared relationship produces
   derived inverse links rather than duplicated relationship truth. ADR views
   expose status, timeline, forward supersede notices, and dated Note,
   Correction, or Update amendments without rewriting the original decision.
   Code excerpts and source claims are extracted from pinned ranges or
   generated metadata; a snippet manifest records path, range, and content
   hash, and drift fails the build. Manually authored plausible code attributed
   to a real source path is prohibited.
8. Language follows documented project voice when present and otherwise stays
   plain, precise, neutral, and topic-led. Titles/navigation labels are
   descriptive. Procedures prefer direct imperatives; personal pronouns are
   contextual rather than mechanically banned. Marketing voice, fabricated
   familiarity, cryptic headings, and decorative emoji are absent by default.
9. The portal utility provides exactly two portal-owned curated utility themes
   through one shared token contract, with one designated default. Each theme
   has coherent light/dark modes, system-following default, a pre-paint
   persisted override, accessible contrast and navigation, reduced motion, and
   correct code/diagram/table/media behavior. Optional project influence uses
   the same narrow one-way primitive-token boundary as cf-present. Portal
   tokens and runtime components are never shared with cf-present or the
   consuming product.
10. The portal scaffold is technically coherent, componentized, testable,
   versioned with the repository/doc set, and maintainable without copying
   source prose into a second manual truth. It owns no product components or
   runtime dependencies and shares no visual/component runtime with cf-present.
11. V1 also produces `llms.txt` and per-page Markdown twins from the same source
    graph. These agent-readable outputs retain source links, provenance,
    version context, and the same staleness and deterministic validation as the
    HTML pages.
12. One authoritative source graph and one portal is the default for both a
    single project and a monorepo. Monorepos retain global orientation and
    shared concepts, then drill down by meaningful surface or owned area using
    multiple source roots and explicit layer paths. A separate portal requires
    a material audience/access, independent release/version, ownership/lifecycle,
    or measured scale boundary. Package count, team count, or sidebar length
    alone does not justify duplicated portals or prose.
    Routes use the semantic layer plus the path relative to the most-specific
    configured source root, so repository folder prefixes do not become reader
    navigation and a source-root move can retain the same route.

## Interfaces and formats

- `cf-docs-portal/SKILL.md` owns discovery, research, design settlement,
  generation/update, review, and source-reconciliation workflow.
- The selected technical baseline is Astro Starlight with Pagefind, exact
  versions, and a committed lockfile. It is an isolated opt-in Node toolchain;
  projects that do not select `cf-docs-portal` receive no Node dependency.
  The adapter boundary permits a future generator without shipping or
  maintaining a second toolchain in V1.
- The skill owns judgment and workflow guidance; a separate embedded portal
  asset bundle owns the selected starter and representative fixtures.
  Conditional skill references cover source mapping, information architecture,
  language, theme, update, and verification guidance.
- Sources are loaded from authoritative paths with schema-validated frontmatter
  aligned with CodeFlow's existing documentation validator. Deterministic
  scripts validate source links and IDs, routes, version/provenance metadata,
  snippet hashes, navigation, build output, and stale/orphan pages, and are
  invocable through `codeflow validate`. The locked implementation branch
  remeasures install, build, and audit behavior. Any temporary dependency
  override records the upstream event that permits its removal. V1 does not add
  a generative CodeFlow CLI command merely to wrap model judgment.
- Generated Markdown twins, copied media, and `llms.txt` use reserved public
  namespaces replaced in full on every publication. Other bounded user-owned
  public files remain outside those namespaces and are preserved.
- A project chooses an output location and whether generated portal source is
  tracked. CodeFlow and Agent OS dogfood portals remain owned by their actual
  repositories; the public `agent-os-portal` remains a separate repository.

## Edge cases

- A repository with established docs information architecture or visual
  identity; a repo with none; a monorepo with several surfaces; a tiny project
  where a portal is unjustified.
- Conflicting sources, missing ADR rationale, renamed files/modules, version
  skew, broken deep links, orphan pages, source deletion, and generated copy
  that sounds plausible but is not evidenced.
- Prototype selection based on novelty or one admired reference rather than the
  repository's audience and content; copied Linear styling; visually attractive
  but shallow or inaccessible output; text-card grids masquerading as visual
  explanation; one desktop/light screenshot treated as proof.
- Theme or navigation customization that couples the portal to product code;
  utilities influencing the product's design direction in reverse.
- A monorepo reduced to a package-folder dump; duplicated shared concepts;
  unjustified per-team portals; or one portal that misleadingly combines
  incompatible access or release/version boundaries.
