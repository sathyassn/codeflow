## Summary

This spec pins the 4.0.0 baseline replacement for its builders: the
installed manifest without a per-file digest, the shipped bases of every
published release carried in the binary, and the tracked sparse pack that
holds what the binary cannot reproduce. TSK-1085 fills and approves it;
TSK-1086 (the retained bases), TSK-1087 (the switch and the migration) and
TSK-247 (the read-only preview) build against its numbered requirements.
The decision of record is ADR-0090.

The settled inputs are the operator's decisions in the workspace
`RELEASE-PLAN.md`: option A, an incompatible manifest and a major release
(2026-10-15); the tracked sparse pack (2026-10-15); every published
release's bases kept in the binary, about 0.6 MB then, with an advisory
2 MB budget whose crossing triggers a review (2026-10-17); the line ships
as 4.0.0 (2026-10-28). The design Codex approved on 2026-10-15
(`design-baseline-05.md`) is not recoverable; this spec re-derives it from
those decisions and the code at `5b1c598f6`. Paths below are under
`crates/codeflow-core/src/` unless stated; line numbers are at that commit,
except where a claim is about a published binary, which is read at the tag
v3.1.1 (`48104f48b`) and marked so.

How to read it: requirements are numbered R-1 onward in the section they
belong to, and "Requirement citations" at the end names the consumer
criterion each one serves. "Edge cases" gives an outcome per case.
"Disclosed choices" lists the decisions this spec takes that a record or a
criterion worded differently, for the batched epic amendment.

## Delta against current capability

Against CAP-002 (`scaffold-update`, `docs/capabilities.md`).

ADDED: bases read from the binary for every published release
(`assets/releases/`); a sparse pack beside the manifest (`.codeflow/bases/`);
a schema probe that refuses a manifest newer than the binary; a one-run
migration of a 3.x project; a read-only preview (`codeflow update --plan`,
TSK-247).

MODIFIED: `.codeflow/manifest.json` moves to schema 2, records no `sha256`
and no top-level `scaffold_version`, and each entry names the version its
base is read at; the drift check and every update decision compare bytes
with the base instead of a hash with the record; the release step adds each
release's bases and the typed repair rules lose their baseline rows.

REMOVED: `.codeflow/.baseline/` in adopting projects and in this repository
(317 files here); the `sha256` field; the manifest's `scaffold_version`
stamp; the interrupted-init distinction `init` drew from a baseline copy.

## Behavior

### Terms

- **Base**: the pristine shipped content a managed file is compared and
  merged against; today the copy under `.codeflow/.baseline/<dest>`
  (`scaffold/state.rs:21`, `:565-602`), whose hash the manifest records
  (`state.rs:500-512`).
- **Retained release**: a published release whose scaffold assets the
  binary carries (R-24 to R-26). Today v2.0.0, v2.1.0, v3.0.0, v3.1.0 and
  v3.1.1; from 4.0.0 on, every release.
- **The pack**: the tracked sparse pack `.codeflow/bases/` (R-8).
- **Published build**: a binary whose version the index names and whose
  current assets equal that release's retained bases; every other binary
  is a **development build** (R-7).
- **Rendered**: an entry's asset after `{{PLACEHOLDER}}` substitution
  (`scaffold/init.rs:395-421`, keys `PROJECT_NAME`, `PROJECT_ONE_LINER`,
  `AREAS`, `STACK`, `TIER`, `SCAFFOLD_VERSION`, `DATE`); for the 312
  entries without `template = true`, rendered equals the asset.

### The manifest

- R-1. Schema 2. `.codeflow/manifest.json` is
  `{"schema_version": 2, "files": {<dest>: {"src", "ownership", "version", "exec"}}}`:
  `src` and `ownership` as today (`state.rs:510-511`), `exec` always
  written (`state.rs:513-514`), and `version`, the plain `MAJOR.MINOR.PATCH`
  the binary that last wrote the entry reports (`opts.binary_version`, as
  `update.rs:426` and `init.rs:250` record today), which names the release
  the base is read at (R-6). Entries stay a `BTreeMap` keyed by `dest`,
  written pretty-printed through `write_record` (`state.rs:558-562`), so
  one entry is one block of six lines in `dest` order, and the file ends
  with exactly one newline (`state.rs:559-560`).
- R-2. Nothing else. No `sha256`, and no top-level `scaffold_version`: the
  project's version pin lives in `.codeflow/project.toml`
  (`ProjectState::scaffold_version`, `state.rs:32`), which `update` and
  `init` keep writing (`update.rs:428`). `scripts/release.py` stops reading
  the manifest as a stamp (`VERSION_STAMP_PATHS`, `release.py:1092-1099`;
  the read at `:1121-1125`), and the manifest is no longer a coupled file of
  a typed repair (R-31).
- R-3. Schema probe. Every reader reads the file beneath the root without
  following a link (`read_beneath_root`, `state.rs:1453-1461`; `doctor`'s
  `read_installed_manifest` leaves `bounded_file::read_regular`,
  `bounded_file.rs:13-24`, which follows one) and first parses
  `schema_version` alone. A
  value above 2 is refused before anything else is read: the message names
  the schema found, the schema this binary reads, the manifest path and the
  project's pin from `project.toml`, with the remedy "install codeflow
  <pin> or newer". A value of 1 selects the migration reader (R-18). A value
  of 2 selects the schema 2 struct. A missing or non-integer value is an
  invalid manifest naming the path. No writer writes a schema it cannot
  read. `doctor` reports the refusal as a failure (R-16); `update`, `init`
  and `decide` return it as an error with nothing written.
- R-4. The 3.x break, as the published parsers make it. Every claim here is
  read at the tag it names with `git show <tag>:<path>`, never at this
  line; a line cite without a tag is at v3.1.1 (`48104f48b`). The parser
  claims hold at every published tag (v2.0.0
  `9b362ba13`, v2.1.0 `16bfbbc03`, v3.0.0 `b9e6097c6`, v3.1.0 `698cc8789`,
  at different lines): `sha256` is required, nothing branches on
  `schema_version`, `update` loads the manifest before its first project
  store, and `init` stores the pin and then loads. The `doctor` claim holds
  at v3.1.0 and v3.1.1 only: at v3.0.0 `check_managed_drift` passes with
  "no readable installed manifest; drift check skipped" when the manifest
  does not parse (v3.0.0 `doctor/mod.rs:2383-2384`), and v2.0.0 and v2.1.0
  have no drift check and no doctor read of the manifest (their `config`
  check, v2.0.0 `doctor/mod.rs:253-291`, only parses every `.codeflow/`
  file as JSON, which a schema 2 manifest is), so those three `doctor`
  binaries pass a 4.0.0 project. A 3.x binary's
  `InstalledFile` requires `sha256` (v3.1.1 `state.rs:498`, no serde
  default) and `load_or_default` deserializes the whole document without
  branching on `schema_version` (v3.1.1 `state.rs:534`). On a schema 2
  manifest with at least one entry it fails with serde's missing-field error
  for `sha256` at the first entry; with an empty `files` map it fails on the
  missing `scaffold_version`. Per command: `update` loads the manifest at
  v3.1.1 `update.rs:308`, before its first write (`state.store` at `:377`),
  and returns "json: missing field `sha256` at line N column M"
  (`scaffold/mod.rs:144-145`), which names the field and not the manifest
  path; no project file is written. `doctor` reads it at v3.1.1
  `doctor/mod.rs:3102` and fails through `input_failure` (`:737`), with
  `Status::Fail` and the manifest path in its message. A repeated `init` on
  the project stores `project.toml` first (v3.1.1 `init.rs:179`), writing
  `scaffold_version` as the 3.x binary's version, then loads the manifest
  (`:182`) and fails on the same field: it lowers the pin by one file write
  and changes nothing else, and the next 4.0.0 `update` raises the pin
  again; the migration guidance names `codeflow update`, never `init`. No
  published binary has a pin check: `check_write_version`
  (`scaffold/version.rs:71` on this line) is absent from every tag and first
  ships in 4.0.0, so a test against a worktree binary shows a pin refusal
  that hides the published behaviour; TSK-1087 AC-5 runs the published
  v3.1.1 binary. At v3.1.0 and v3.1.1 nothing passes silently; at v2.0.0,
  v2.1.0 and v3.0.0 only `doctor` passes, and `update` and `init` fail on
  the field as above. The break is the missing field,
  never a schema number alone, and schema 2 reuses no 3.x field name with a
  new meaning.
- R-5. Line stability. (a) An entry's bytes change only when the shipped
  content of its file changes against the base the entry names, or the
  entry is added or removed. (b) A resync of one managed file changes no
  other entry. (c) The manifest holds no shared stamp and no digest, so a
  resync changes no shared line. (d) The `version` field moves only when
  the shipped text differs from the base the entry names, and then to the
  binary's version: Add, Replace, Force and Merge set it; Adopt keeps it
  when the base at the recorded version equals the rendered text and sets
  it otherwise; the JSON region and policy syncs (R-10, R-12) set it only
  when the rendered shipped text differs from their base; Kept, NoBaseline,
  Conflict and a skipped entry leave the entry untouched; an accepted
  resolution sets it to the pending record's version (R-17). So a run that
  changes file A never rewrites file B's line, whatever version B records,
  while B's shipped text is unchanged. Two stated residuals, both the
  status quo: the closing brace of the last entry gains a comma when a new
  entry sorts after it (the JSON separator), and two pull requests that
  resync the same file with binaries reporting different versions conflict
  on that entry's `version` line, as they do today on `Cargo.toml` and
  `project.toml`.

### The base lookup

- R-6. Order. The base of an entry is (1) the pack entry
  `.codeflow/bases/<dest>` when present, read beneath the root without
  following a link (`read_beneath_root`, `state.rs:1453-1461`); else (2)
  the retained bytes of the entry's `src` at the entry's `version`, when the
  index names that version and the release shipped that `src` (R-26); else
  (3) no base. The pack comes first because a pack entry exists only where
  the binary that wrote it could not promise a retained release reproduces
  the base (R-8), and it is removed as soon as a published build reproduces
  it; a development build of a published version (this repository after a
  release, before the next version bump) would otherwise read the published
  release's bytes for a file it installed from changed assets.
- R-7. Published or development. Once per run, a build is published when
  the index names its own version and the asset of every `[[entry]]` of the
  current `scaffold-manifest.toml` equals its retained bytes at that
  version; otherwise it is a development build. A published build writes no
  pack entry for a non-template file; a development build writes one for
  every file it writes or adopts (R-8). A release binary built from its tag
  is published by construction (R-27).
- R-8. The pack. `.codeflow/bases/<dest>` holds the exact base bytes (the
  text `Baseline::write` stores today: the rendered file, or for a markdown
  or hash region the rendered block, `update.rs:1066`). A pack entry is
  written when: (a) the entry has `template = true` and ownership `managed`
  or `managed-region`, since its rendering depends on project values, the
  date and the version and no release reproduces it (six entries across the
  tiers: `AGENTS.md.tmpl`, `AGENTS.full.md.tmpl`, `AGENTS.minimal.md.tmpl`,
  `CLAUDE.md.tmpl`, `CLAUDE.minimal.md.tmpl`, `rules/worktrees.md`; a
  project at one tier holds three); (b) a development build adds, replaces,
  forces, merges or adopts the file, or syncs a user-owned JSON file (R-12);
  (c) a pending resolution is accepted and the index does not name the
  record's version (R-17); (d) the migration derives a base no retained
  release holds (R-19). A pack entry is removed when a published build
  processes the entry and the retained bytes at the entry's new `version`
  equal the pack's bytes, when the entry is pruned (R-14), or when no
  manifest entry names its `dest` (R-14). A pack entry is never written
  for a user-owned entry that is not JSON (R-13), and never from the live
  file. The pack is written in the same run as the manifest and before it
  (R-20), through the boundary R-22 states.

### Update, by arm and base source

- R-9. Whole managed files. `managed_step` (`update.rs:828-860`) takes the
  base and no recorded hash; "unmodified" means the current bytes equal the
  base. The tests keep their order: absent, then current equals rendered,
  then current equals base, then `--force`, then no base, then rendered
  equals base, then the 3-way merge (`diffy::merge(base, current,
  rendered)`). The outcome per arm and base source:

  | Arm (`update.rs:795-826`) | Condition | Base from the binary | Base from the pack | No base |
  |---|---|---|---|---|
  | Add | file absent | install; `version` := binary; a development build writes the pack entry | same | same |
  | Adopt | current == rendered | record; keep `version` when the base equals rendered, else set it; remove a pack entry the retained bytes reproduce | record; a development build rewrites the pack entry | record with the binary's version; a development build writes the pack entry |
  | Replace | current == base | write rendered; `version` := binary; remove a reproducible pack entry | write rendered; `version` := binary; development build rewrites the pack entry, published build removes it when reproducible | cannot occur: "unmodified" needs a base |
  | Force | modified, `--force` | as Replace, noted "user modifications overwritten (--force)" | as Replace | as Replace, with the base note of NoBaseline |
  | NoBaseline | modified, no base | cannot occur | cannot occur | `<dest>.new` holds the shipped version; the report names the missing base: "no base for <dest>: version <v> is not a retained release and .codeflow/bases/<dest> is absent"; the entry is untouched |
  | Kept | modified, rendered == base | kept, "no upstream change; your modifications stand"; entry untouched | same | cannot occur |
  | Merge | clean 3-way merge | write the merge; `version` := binary; pack as Replace | same | cannot occur |
  | Conflict | conflicting 3-way merge | `<dest>.new` holds the merge with markers; pending record written (R-17); entry untouched | same | cannot occur |

  `Decision` (`update.rs:109-129`) maps as today; `decide` resolves the
  base through R-6 and writes nothing.
- R-10. Managed-region JSON (`.claude/settings.json` and its peers,
  `update.rs:1035-1062`). The previous shipped preset is the base (R-6);
  with none, the 2.1.0 stand-in (`prior_release::settings`,
  `scaffold/prior_release.rs`, TSK-171) is used as today
  (`update.rs:869-879`) and the note says so. The entry's `version` moves
  to the binary's only when the rendered preset differs from the base
  (R-5d); a development build writes the pack entry (R-8b).
- R-11. Managed-region markdown and hash (`AGENTS.md`, `CLAUDE.md`,
  `.gitignore`; `update.rs:1063-1107`). The block is regenerated from the
  rendered template as today; the base is the rendered block, held in the
  pack for the template entries (R-8a) and read from the retained `src` for
  the others. `doctor` compares the live block's bytes with it (R-16).
- R-12. User-owned JSON (`.codeflow/policy.json`, `update.rs:1146-1240`).
  The old shipped default is the base; with none, the 2.1.0 and 3.0.0
  staging stand-ins (`prior_release::policies`, `update.rs:1165-1172`) as
  today, and the note "no shipped-default baseline existed; key sync starts
  from this version" becomes "no shipped default recorded for <dest>; key
  sync starts from this version". New keys, moved defaults, recommended
  values and deprecated keys are computed from that base exactly as today.
  The entry's `version` moves to the binary's only when the rendered
  default differs from the base (R-5d); a development build writes the
  pack entry.
- R-13. User-owned files that are not JSON (`update.rs:1108-1140`). Never
  mutated. A new entry is recorded with the binary's version; the branch
  "missing shipped baseline restored without changing the live file"
  (`update.rs:1124-1133`) is removed, since there is nothing to restore,
  and no pack entry is written even for a template (`docs/product.md.tmpl`
  and the three other user-owned templates: nothing compares them).
- R-14. Orphans (`prune_orphans`, `update.rs:1601-1693`; ADR-0011). An
  orphaned `managed` file is unmodified when its bytes equal its base
  (ADR-0011's "current hash == recorded hash" at
  `docs/decisions/ADR-0011-update-orphan-reconciliation.md:42-45`, restated
  as a byte compare), or the file is gone; then the file and its pack entry
  are removed with the record. A file that is gone is removed from the
  record whether or not a base exists: there is nothing on disk to protect.
  A present file with no base is kept and unmanaged, reported "no longer
  shipped; kept: no base proves it unmodified", never deleted. A modified `managed`, `managed-region` or
  `user-owned` orphan is kept and unmanaged as today; its pack entry goes
  with its record. A pack file whose `dest` no entry names is removed and
  reported. `.codeflow/.baseline/` is no longer touched here. An unsafe
  `dest` (`is_safe_relative_dest`, `update.rs:744-750`) or a linked path
  (`guard_beneath_root`) is skipped and reported, never followed
  (`update.rs:1627-1639`).
- R-15. `init` on an existing file (`init.rs:552-600`). With a record:
  current equals the base and differs from rendered, "newer shipped version
  available, run codeflow update"; current equals rendered, Unchanged;
  otherwise "locally modified". Without a record and with current equal to
  rendered, the file is adopted as managed (recorded with the binary's
  version; a development build writes the pack entry) and, in a fresh
  repository, added to the scaffold commit; the distinction between an
  interrupted earlier init and a pre-existing identical file
  (`init.rs:575-600`, which read the baseline copy) is dropped, because a
  published build writes no per-file evidence and the two outcomes differ
  only in that note. `written` (`init.rs:267-268`) names `.codeflow/bases`
  in place of `.codeflow/.baseline` when the pack has an entry. A
  user-owned entry without a record is recorded as today (`init.rs:555-563`)
  with no baseline write.
- R-16. `doctor --check managed-drift` (`doctor/mod.rs:3499-3560`). For a
  `managed-region` entry the live block's bytes are compared with the base
  block (R-11) and a difference keeps today's warning and remedy. For a
  `managed` entry the live bytes are compared with the base, and a
  difference is one warning listing the files with "codeflow update merges
  your change; `codeflow update --plan` shows the result", never a
  failure. An entry with no base is listed in a warning naming the file and
  the missing base. A manifest that is unreadable or newer than the binary
  (R-3) stays a failure (`Status::Fail` through `input_failure`,
  `doctor/mod.rs:746-760`; a warning exits 0,
  `crates/codeflow-cli/src/cmd/doctor.rs:577-606`). A manifest that is
  absent, or still 3.x and migratable by this binary (R-18, read without
  writes), is a warning naming the path and the remedy, never a pass (today
  absence passes through `read_installed_manifest`, `:3470-3477`). A fresh
  install is ok. `update_leaves`
  (`doctor/mod.rs:1324`) names the base source instead of the baseline path.
- R-17. Pending resolution (TSK-405; `scaffold/update/pending.rs`). The
  record keeps its path `.codeflow/.pending-update/<dest>.json`
  (`pending.rs:20-22`) and holds `from_version` (the entry's `version` when
  the proposal was written), `version` (the proposing binary's version) and
  `shipped` (the shipped text, as today); `old_sha256` and `new_sha256` are
  gone. Reading it (`pending.rs:34-110` restated) refuses, before any write
  and with nothing changed, when `<dest>.new` is still present, when the
  resolved file holds a conflict marker, when the entry's `version` is
  neither `from_version` nor `version`, when the base R-6 resolves for the
  entry equals neither the base at `from_version` nor `shipped`, or when the
  index names `version` and ships `src` with bytes other than `shipped`;
  each with today's remedy text. The record is validated in the preflight
  (R-20 step 1); acceptance sets the entry's `version` to the record's
  `version`, writes the pack entry when the index does not name that version
  (R-8c, with the pack in step 2), stores the manifest (step 4) and removes
  the record after that store (`update.rs:355-369` restated, with no store
  before the main loop); a retry after an interruption accepts either
  state. The base and the record always describe shipped content,
  never the person's file (TSK-405 AC-4): the pack is written only from
  rendered text or a pending record's `shipped`.

### Migration of a 3.x project

- R-18. Trigger and scope. A schema 1 manifest, or a schema 2 manifest with
  `.codeflow/.baseline/` still present (an interrupted earlier run),
  migrates in the same `codeflow update` or `codeflow init` run; `doctor`,
  `decide` and `update --plan` read the same derivation without writing
  (TSK-247 AC-1). One run: the report ends with the manifest rewritten, the
  pack written where R-19 needs it and `.codeflow/.baseline/` removed.
- R-19. Deriving each entry's base. Inputs per entry: the old record (`src`,
  `ownership`, `sha256`, `exec`), S the old manifest's `scaffold_version`
  (`state.rs:521`), B the baseline copy read beneath the root, C the live
  file. (a) B present and `sha256(B)` equals the record: the base is B; the
  `version` is S when the retained bytes of `src` at S equal B, else the
  newest retained release whose `src` equals B, else S with a pack entry
  holding B. (b) B absent and `sha256(C)` equals the record: the live file
  is pristine, so the base is C, resolved as in (a). (c) Otherwise, no
  base: the `version` is S, no pack entry, and the report names the entry
  ("no base for <dest>: the 3.x baseline copy is missing or does not match
  its record"); a present B that does not match its record is reported as
  inconsistent metadata and not trusted. The migration treats an ignored
  (`[scaffold] ignore`) or otherwise skipped entry the same way, so its base
  survives for the day the glob is removed, and touches no live file of its
  own. Every entry's `exec` is kept.
- R-20. Order of writes. (1) Preflight, with nothing written: read every
  input, derive every base (R-19), walk `.codeflow/.baseline/` (R-21) and
  guard every pack path (R-22); a refusal reports and stops here. (2) Write
  the pack entries. (3) The update arms write live files and `.new`
  proposals, reading bases from memory. (4) Write the schema 2 manifest and
  `project.toml`. (5) Remove `.codeflow/.baseline/` (R-21). (6) The report
  lists the removal with its file count and the pack entries written. Every
  file write is atomic (`write_record`, `state.rs:604-684`), so a crash
  leaves each file old or new, never torn. A rerun after an interruption
  converges, by where it stopped: before step 4 the manifest is still schema
  1 and the baseline directory intact, so R-19 re-derives the same bases,
  rewrites identical pack bytes, and the arms judge each live file again: a
  file already at the rendered text is adopted, a file already equal to the
  3-way merge the rerun computes is recorded merged without a second write
  (the merge of the base, that result and the rendered text is that result),
  and a file equal to neither follows the arms as a first run would, writing
  `.new` on a conflict and never clobbering it. After step 4 the schema 2
  manifest is the truth: the rerun removes the baseline directory (step 5)
  and runs its ordinary arms against the pack and the retained bases. After
  step 1 the run reads no base from `.codeflow/.baseline/` again; the
  removal still checks each path's metadata before touching it (R-21).
  TSK-247 AC-4's write preflight is the general one, every update with one
  unwritable destination writes nothing; this step 1 is its migration
  instance, not its definition.
- R-21. Removal boundary. The walk reads every entry with
  `symlink_metadata` and follows no link: `.codeflow/.baseline` itself
  being a link, or any entry that is a link or neither a regular file nor a
  directory, refuses the run in step 1, naming the path and the remedy
  ("remove the link by hand; update removes nothing while it is there").
  Files are removed one by one, then empty directories bottom-up with
  `remove_dir` only, stopping at `.codeflow/.baseline` inclusive; a
  recursive remover is never called. Each unlink and each `remove_dir` runs
  `guard_beneath_root` (`state.rs:1425-1450`) on its path immediately before
  the call, as `remove_beneath_root` does (`state.rs:1475-1482`), so a
  directory swapped for a link between step 1 and step 5 is seen at delete
  time; a link found then stops further removal, is reported with its path,
  and the run exits non-zero. What is left on disk is consistent: the pack,
  the live files and the schema 2 manifest from steps 2 to 4 stay, the
  remaining baseline files stay, and the rerun rule (R-20, after step 4)
  removes them once the link is gone. `remove_file` unlinks one directory
  entry: a baseline name that is a hard link to a file outside the tree
  loses that name only, and the other file keeps its content. Nothing
  outside `.codeflow/.baseline/` is removed. A file under it that no entry
  names is removed too: the tree is engine-generated (ADR-0011) and
  recoverable from version control. Manifest `dest` values never drive the
  removal, so an entry pointing outside the root (absolute, `..` or a prefix
  component, `is_safe_relative_dest` false) cannot direct a delete; it is
  reported Skipped as today (`update.rs:1627-1631`), its base is not
  migrated, nothing is written for it, and the run continues (R-23).
- R-22. Pack write boundary. The pack path is
  `guard_beneath_root(root, ".codeflow/bases/<dest>")` after
  `is_safe_relative_dest(dest)`; a link at the leaf or at any ancestor,
  including `.codeflow` and `.codeflow/bases`, refuses the run before any
  write. Writes go through `write_record` (a private temp file synced and
  renamed, `state.rs:604-684`), which replaces the directory entry and never
  writes through an existing hard link's inode. Nothing is written outside
  `.codeflow/`.
- R-23. A refused path, one rule. A link under `.codeflow/.baseline/`
  found in the preflight, a link on a pack path, or a required input that
  cannot be read stops the run before any write: the report names the
  path, the rule and the remedy, the exit status is non-zero, and the tree
  is byte-identical before and after (TSK-1087 AC-10 hashes it for these
  stop cases). A link found at delete time, after the preflight, follows
  R-21: removal stops there, the exit status is non-zero, and the pack, the
  live files and the schema 2 manifest already written stay, so the tree is
  not byte-identical and AC-10's hash check does not apply to it. An
  escaping `dest`
  (absolute, `..` or a prefix component) is not a stop: it is skipped and
  reported, nothing is read, written, migrated or removed for it, and the
  run continues (R-14, R-21), as `prune_orphans` does today
  (`update.rs:1627-1631`).

### The retained bases in the binary

- R-24. Layout. `assets/releases/index.toml` and `assets/releases/bases.zst`,
  embedded with every other asset through rust-embed
  (`crates/codeflow-cli/src/embedded.rs:9-12`) and read through
  `AssetSource` (`scaffold/assets.rs:14-25`) as `releases/index.toml` and
  `releases/bases.zst`, so a `DirSource` test tree carries its own.
- R-25. Encoding. The index is TOML: `schema_version = 1`,
  `budget_bytes = 2000000`, `stream = "bases.zst"`; one `[[release]]` per
  retained release with `version`, `tag` and `commit`, and a
  `[release.files]` table of `src = "<sha256>"` sorted by `src`; one
  `[[blob]]` per unique content with `sha256` (lowercase hex) and `len`,
  in stream order. Stream order is first-seen order: releases in
  `[[release]]` order, within a release its files in `src` order, and a
  content listed once, where it first appears. The stream is one zstd frame
  (level 19, no dictionary) of the blobs concatenated in that order. A blob
  is the exact bytes of
  `assets/base/<src>` at the release's tag. A release's files are every
  `src` an `[[entry]]` of `assets/base/scaffold-manifest.toml` names at that
  commit (183 files at v3.1.1; the other 16 files under `assets/base/`,
  such as the test-config templates, are not bases). Adding a release
  appends its `[[release]]`, appends the blobs it is the first to carry at
  the end of the stream and rewrites the stream file; no earlier index row
  and no earlier blob's offset changes.
- R-26. Reader. `retained(version, src)` returns the bytes or the distinct
  outcome NotRetained (the index does not name `version`, or that release
  did not ship `src`); never a file from another version. It errors only on
  a corrupt pack (a blob whose `sha256` or `len` disagrees with the stream,
  a stream that does not decode, an index that does not parse), and that
  error names the pack, never a project path. Before it decodes, it sums
  every `len`, refuses an index whose sum exceeds 64,000,000 bytes (about
  nine times today's 7,035,556 raw bytes; the 2 MB budget of R-28 is
  advisory and is not this cap), then decodes with a streaming decoder
  (`zstd::stream::Decoder`, never `decode_all`, which copies into a `Vec`
  with no output cap) with `window_log_max` set so the window is at most
  that cap, into an output buffer of the summed `len`, and refuses a frame
  that yields more or fewer bytes; so a hostile `len` or an expanding frame
  costs at most the summed `len` plus a decoder window of at most the cap,
  128,000,000 bytes in all, before it is rejected.
  In a release build its only inputs are the two embedded assets
  (`embedded.rs:31-33`): no filesystem path is read and no link is
  followed, which is what TSK-1086 AC-3 tests. A debug build and the tests
  read the checkout's `assets/` tree through `AssetSource`
  (`embedded.rs:19-28` uses `std::fs::read`, which follows a link there);
  that tree is the maintainers' checkout, not an adopter's project, and is
  out of AC-3's scope. The index and stream are decoded and verified once
  per process. The reader also answers `releases()` (the versions the index
  names, for reports) and `is_published()` (R-7). The decoder is the `zstd`
  crate on its 0.14 line, the one the lockfile already resolves through
  rust-embed's `compression` feature (`zstd` 0.14.3, `zstd-safe` 8.2.0,
  `zstd-sys` 2.1.2+zstd.1.5.7, `Cargo.lock:2183-2202`), with default
  features, as a direct dependency of the engine; never 0.13, which
  `Cargo.toml:53-62` patches out of the tree for RUSTSEC-2026-0391, 0395 to
  0406 and 0410. `cargo test -p codeflow-core` then builds `zstd-sys`.
- R-27. The release step. The `scripts/release.py` path that prepares a
  release (`sync` with its stamps) adds the release's `[[release]]` and
  blobs and rewrites the stream; `check-state` for a release version
  refuses when the index lacks that version or any retained file differs
  from `assets/base/<src>` at the release commit, naming the version and
  the file. A release is never published with absent bases. The writer is
  TSK-1086's choice (the line's own binary or the `zstd` command line
  tool); the format above is the contract, and the Rust tests decode and
  compare, never re-encode.
- R-28. The budget. The size of `assets/releases/bases.zst` in bytes against
  `budget_bytes` (2,000,000). `check-state` and the retained-bases test
  print the size, and warn, never fail, when it is passed; the crossing is
  a review for the operator (decision of 2026-10-17). TSK-1086 records the
  measured size in its pull request against the numbers below.

## Interfaces and formats

A schema 2 manifest, abridged:

```json
{
  "schema_version": 2,
  "files": {
    ".agents/skills/cf-consult/SKILL.md": {
      "src": "agents/skills/cf-consult/SKILL.md",
      "ownership": "managed",
      "version": "3.1.1",
      "exec": false
    },
    "AGENTS.md": {
      "src": "AGENTS.full.md.tmpl",
      "ownership": "managed-region",
      "version": "4.0.0",
      "exec": false
    }
  }
}
```

The pack: `.codeflow/bases/<dest>`, one regular file per entry, the bytes
of its base; at the full tier of this repository after migration,
`.codeflow/bases/AGENTS.md`, `.codeflow/bases/CLAUDE.md` and
`.codeflow/bases/.codeflow/rules/worktrees.md`, plus every entry a
development build wrote until a published build removes it.

The pending record, `.codeflow/.pending-update/<dest>.json`:

```json
{ "from_version": "3.1.1", "version": "4.0.0", "shipped": "<the shipped text>" }
```

The index, `assets/releases/index.toml`, abridged:

```toml
schema_version = 1
budget_bytes = 2000000
stream = "bases.zst"

[[release]]
version = "3.1.1"
tag = "v3.1.1"
commit = "<the tag's commit>"
[release.files]
"AGENTS.full.md.tmpl" = "<sha256>"
"agents/skills/cf-consult/SKILL.md" = "<sha256>"

[[blob]]
sha256 = "<sha256>"
len = 1234
```

The stream, `assets/releases/bases.zst`: one zstd frame of the blobs in
`[[blob]]` order; a reader decodes it once and slices by the cumulative
`len`.

## Edge cases

| Case | Outcome |
|---|---|
| A recorded `version` that is no retained release (a development build) | The pack is read first (R-6). With a pack entry the arms run as with any base. Without one, a modified `managed` file gets `<dest>.new` and the report names the missing base (R-9 NoBaseline); a JSON region or policy file falls back to the 2.1.0 stand-ins (R-10, R-12); `doctor` warns naming the file (R-16). A file equal to the rendered text is adopted (R-9 Adopt) |
| A rendered template whose render inputs changed since install (the project renamed, a one-liner edited) | The base is the pack entry written at install (R-8a), so the block or file merges and regenerates as today and `doctor` reports no false drift; a pack entry deleted by hand makes the file a no-base case until the next write of that file rewrites the entry |
| A 3.x binary on a 4.0.0 manifest (the published v3.1.1, read at its tag) | `update` fails on the missing `sha256` field before any write, with a message that names the field and not the path; `doctor` fails naming the manifest (at v3.1.0 and v3.1.1; the v2.0.0, v2.1.0 and v3.0.0 doctors pass, R-4); a repeated `init` lowers the pin in `project.toml` and then fails on the same field, writing nothing else; an empty `files` map fails on the missing `scaffold_version` (R-4). At v3.1.0 and v3.1.1 nothing passes; at the three older tags only `doctor` does |
| A manifest newer than the binary (`schema_version` above 2) | Refused by the probe with the schema found, the manifest path and the pin to install (R-3); `doctor` fails (R-16); nothing is written |
| A linked path under `.codeflow/.baseline/` at removal | Found in the preflight walk: the run stops before any write, naming the link and the remedy (R-20, R-21). A link swapped in after the preflight is caught by the guard before that unlink: removal stops there, the pack, live files and manifest already written stay, and the rerun removes the rest once the link is gone (R-21) |
| A baseline entry pointing outside the root (an absolute, `..` or prefixed `dest` in the old manifest) | Reported Skipped and the run continues; its base is not migrated and nothing is read, written or removed for it; the removal walks the real directory, never a `dest`, so nothing outside `.codeflow/.baseline/` is removed (R-14, R-21, R-23) |
| A `<dest>.new` still present when the migration runs | Refused before any write with "resolve <dest>.new and move it over <dest>, then retry" (R-17, `pending.rs:50-58` today) |
| A pack entry equal to the retained bytes at the entry's `version` | Redundant; removed the next time a published build processes the entry (R-8) |
| A pack file whose `dest` no manifest entry names | Removed and reported by `prune_orphans` (R-14) |
| `[scaffold] ignore` matches an entry | Its base migrates to the pack where R-19 needs it; the live file is untouched; removing the glob later resumes management against that base |
| `--force` on a modified file | Force (R-9): the shipped version replaces the file, noted; the pack follows Replace |
| A 2.x project with no `.codeflow/.baseline/` (TSK-171) | R-19 (b) recovers a base for every pristine file from its digest; a modified file has none and gets `.new`; settings and policy use the stand-ins (R-10, R-12) |
| `update --plan` (TSK-247) | Reads the same derivation and bases and writes neither a pack entry nor the manifest; the tree, `.codeflow/manifest.json` and `.codeflow/bases/` hash identically before and after (R-18) |
| An interrupted migration | Before the manifest was written: schema 1 and the baseline directory are intact, so the bases are re-derived, identical pack bytes rewritten, and each live file judged again (adopted, recorded merged without a second write, or handled by the arms as a first run would). After it: the schema 2 manifest is the truth, the baseline directory is removed and the ordinary arms run (R-20) |

layout was displaced because it stands at 68 percent of the budget today

`python3 -I measure.py . v2.0.0 v2.1.0 v3.0.0 v3.1.0 v3.1.1` (add a commit
to include the line; the dictionary keeps insertion order, which is R-25's

```python
import hashlib, subprocess, sys, tomllib
repo, refs = sys.argv[1], sys.argv[2:]
git = lambda *a: subprocess.run(["git", "-C", repo, *a], check=True, stdout=subprocess.PIPE).stdout
zstd = lambda b: len(subprocess.run(["zstd", "-19", "-q", "-c"], input=b, check=True, stdout=subprocess.PIPE).stdout)
unique = {}
for ref in refs:
    manifest = tomllib.loads(git("show", f"{ref}:assets/base/scaffold-manifest.toml").decode())
    tree = {l.split("\t")[1].removeprefix("assets/base/"): l.split()[2]
            for l in git("ls-tree", "-r", ref, "assets/base").decode().splitlines()}
    blobs = [git("cat-file", "blob", tree[s]) for s in sorted({e["src"] for e in manifest["entry"]})]
    for b in blobs:
        unique.setdefault(hashlib.sha256(b).hexdigest(), b)
    print(ref, len(blobs), sum(map(len, blobs)), zstd(b"".join(blobs)))
stream = b"".join(unique.values())  # first-seen order (R-25)
print("unique", len(unique), len(stream), "per blob", sum(zstd(b) for b in unique.values()),
      "solid first-seen", zstd(stream), "solid hash-sorted", zstd(b"".join(unique[k] for k in sorted(unique))))
```

## Disclosed choices

Decisions this spec takes that a record or a criterion worded differently;
each goes to the batched epic amendment with TSK-1085's Closeout.

- The base lookup reads the pack before the retained release (R-6), where
  TSK-1085 AC-2 lists the binary first. The reason is the development
  build of a published version; the outcomes TSK-1087 AC-3 and AC-6 test
  are the same.
- The manifest drops its top-level `scaffold_version` (R-2); the records
  speak only of dropping the digest. `project.toml` keeps the pin, and
  `release.py` loses one coupled stamp.
- The published v3.1.1 `update` fails on the missing field without naming
  the manifest path, and a repeated 3.x `init` lowers the pin before it
  fails (R-4); TSK-1087 AC-5's "a message that names the manifest" holds
  for `doctor` and, for `update`, on the field name.
- `doctor` keeps failing on an unreadable or newer-schema manifest and warns
  on an absent or still-3.x one (R-16); TSK-1087 AC-7's "warn on an
  unreadable manifest instead of passing" reads as the absent case.
- TSK-1087 AC-6's "an unmodified file shall still be replaced" needs a
  base to prove the file unmodified, so it holds through the pack entry a
  development build writes (R-8b); with neither a pack entry nor a retained
  release there is no "unmodified" judgement, only Adopt or NoBaseline.
- Template entries always live in the pack (R-8a) rather than being
  re-rendered: without a stored copy or a digest, whether the render inputs
  changed cannot be decided.
- `init` drops the interrupted-init note (R-15); the identical file is
