# SPC-014: present review contract v2

## Summary

The contract TSK-118 to TSK-122 build against, written by TSK-117 (node A of
the present review parity package, EPC-016 Plan v5.1). A real review found
that a comment cannot target a node or arrow inside a figure, that figures
carry no visible title or explanation, and that no form submits answers to
the agent. This spec pins the formats and rules that fix all three: entity
anchors that survive revisions and are checked by the server, framing the
runtime draws for every figure and table, a `form` block whose answers are
stored against the revision shown and delivered to a waiting agent, and the
surfaces around them (diff, replies, `present check`).

Authoritative design source: workspace
`design/present-parity/proposal-present-parity-v2.md`, v2.1 at workspace
commit `b823cbe`, with the operator decisions of 2026-09-26 (1a, 2a plus c,
3a, 4a). The decisions of record are ADR-0073. Section numbers in brackets,
such as (3.1), point at that proposal. Where this spec and the proposal
differ, this spec governs and says why.

Baseline read: `integration/EPC-016-visual-guide` at `d1c584a60`, where the
`figure` block exists and the `diagram` block is retired. Paths below are
under `crates/codeflow-present/` unless stated.

## Delta against current capability

CAP-016 (interactive presentation review).

ADDED. Document schema v2 with required figure and table framing, the
`form` block and the v2 `decision`; entity targets in `figure` blocks and
through a closed `data-cf-*` vocabulary in `html` stages; the entity
selector on notes with server validation; fuzzy quote re-anchoring and the
changed and orphaned anchor states; the answer ledger with receipts,
amendments and acknowledgment; `feedback --wait`, `--timeout`, `--format
v2`, `responses list`, `ack`, `reply`, `diff`, `check`, `update
--expected-revision` and `--label`; revision context (git commit and
uncommitted digest) and snapshot provenance for code and diff blocks;
threads with replies, reopen and tombstones; `export --include-feedback`.

MODIFIED. The picker resolves to entities instead of climbing to the
enclosing `svg`; the label fallback never yields a bare tag name; the live
session renders the `html` stage title; element notes that lose their
element fall back to a quote or the block instead of orphaning at once; the
drawn-figure gate requires a visible title; the `figure` block's kicker
line becomes "Figure N · title".

REMOVED. The unused `/sandbox/{revision}/{id}` route (TSK-118) and the ADR-0049 and
`docs/architecture/present.md` sentences that say live `html` stages run in
a sandboxed iframe. Nothing a v1 document or a v1 feedback consumer relies
on is removed.

## Behavior

### B1. Anchors (3.1)

A note is anchored by a layered selector: the block id, refined by at most
one of an entity selector, a text selector (W3C TextQuoteSelector `exact`,
`prefix`, `suffix` with the TextPositionSelector `start_utf16`,
`end_utf16`), an element selector (the v1 generated element path) or a
region selector (per-million box), and bound to the revision in its review
envelope. A note with none is a block note. The entity selector is new;
the other three keep their v1 fields.

When a note made on revision R is shown on revision C (C > R), the service
re-anchors it in this order and reports the state it reached:

1. Entity. The block exists in C and has an entity with the same id:
   `entity_anchored` when the block digest is unchanged, else
   `entity_reanchored` with `label_changed` true when the server-resolved
   label differs from the stored one.
2. Quote. The note has quote text (the text selector's `exact`, else the
   excerpt text, else the stored entity or element label). The text
   searched is the block's canonical review text (`document.rs`
   `canonical_review_text`, with v2 references rendered as B5 says), never
   the Markdown source, and the stored `exact`, `prefix` and `suffix` are
   bytes of that text. Review text separators (amended 2026-09-27, TSK-071
   QA defect 8): a block's parts (paragraphs, headings, list items, table
   cells, status labels and details, tree nodes, tab labels, titles and
   captions) are separated by one line break, never leading or trailing, so
   a quote or its context across two parts keeps a separator. Every review
   text root in the page carries this text, and the client maps a selection
   to it ignoring whitespace. A note stored before this change whose quote,
   prefix or suffix crossed two parts no longer matches the exact step and
   re-anchors by the fuzzy step (`changed` true), or goes to step 3 below
   the 0.75 score; a note within one part is unaffected. The exact step is the v1 rule unchanged (`state.rs`
   `reanchor_text`): the quote with its stored prefix before it and suffix
   after it occurs exactly once, and a text note keeps its v1 `reanchored`
   state. A unique quote whose context changed fails that step, goes to the
   fuzzy step and, if it passes, is marked changed. Otherwise the fuzzy step runs
   when the quote is at most 512 UTF-16 units and the block text at most
   65,536; else it goes to step 3. Candidates are the windows of the block
   text that start at offset 0 or after a run of whitespace, end at the end
   of the text or before whitespace or one of `, . ; : ! ?`, and whose
   length is from ceil(0.7 L) to floor(1.3 L) units, L being the quote
   length. Each candidate scores `0.5 * sim(quote, window) + 0.2 *
   sim(prefix, text before) + 0.2 * sim(suffix, text after) + 0.1 *
   position`, where `sim(a, b)` is 1 minus the Levenshtein distance over the
   longer length (1 when both are empty), the text before and after are as
   many units as the stored prefix and suffix, an empty stored prefix or
   suffix scores 1, and position is 1 minus the start shift over the block
   text length (0 when the quote has no stored offset, as for an entity or
   element label). The highest score wins, ties to the lowest start. A score of
   at least 0.75 gives `reanchored` with the new offsets and `changed` true;
   below it, step 3. Lengths and offsets are UTF-16 units, as the v1 text
   selector counts them. Work budget (amended 2026-09-27, TSK-118 review
   round 1): before scoring, the service counts the edit-distance cells the
   candidates need: the quote length times each start's longest window,
   the prefix length times the text before each start (at most the prefix
   length), and the suffix length times the text after each candidate end
   (at most the suffix length; context tables added in review round 2);
   over 32,000,000 it scores nothing and goes to step 3 with the reason that
   the block is too large to search. The result is cached per note and
   revision, and re-anchoring runs outside the session lock.
3. Block. The block still exists: `block_fallback` with the reason (entity
   gone, quote not found, element changed, block too large to search).
4. Document. The block is gone: `orphaned` with the reason; the rail shows
   the note at document level.

A note is never dropped and never re-attached to a different target
without its state saying so: every state after step 1 that is not the
original target is marked changed. On its own revision a note is shown as
anchored. The v1 element and region rules keep their unchanged-digest fast
path and then continue at step 2 instead of orphaning.

### B2. Entities (3.1)

An entity is a review target inside a block, named by an entity id that
matches the figure grammar's id rule, `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`, at
most 64 characters (`figure-grammar.mjs` `KEBAB`), unique within its block. Entity ids are
never derived from draw order, element position or a counter.

- `figure` block. Every item in `wide.draw` or `narrow.draw` that draws a
  state (a mark) and has an `id` is an entity with that id; the same id in
  both compositions is one entity. A text item whose `for` lists ids labels
  those entities. Each drawn state's legend entry is an entity with id
  `legend-<state>`. One rule decides which figures have per-mark entities:
  whether the declaration has a `layout` object, whatever its family or
  binding. A declaration without `layout` draws its marks from `wide.draw`
  and `narrow.draw`, and in a schema v2 document every mark there must carry
  an `id` (the validator refuses one without, because such a mark could only
  be named by position); authored extent and coverage figures are in this
  group. A declaration with `layout` (the derived extent and coverage
  figures) computes its marks on the client, so it exposes only the legend
  entities and the block; its per-mark entities wait for a layout-level key
  contract (Limits).
- `html` stage. Authors name targets with the closed vocabulary below;
  nothing else inside a stage is an entity. Elements without it still take
  element notes (v1 element path) and resolve by the precedence in B3.
- Other blocks have no entities in this contract; they keep text, element,
  region and block notes.

The closed vocabulary, validated in Rust by `safe_html.rs` and refused
outside it (every other `data-cf-*` name, and ids and classes starting with
`cf-`, stay refused as runtime identities):

| Attribute | On | Meaning | Rules |
|---|---|---|---|
| `data-cf-target="<id>"` | any element | An entity. Targets may nest; the innermost wins and "select enclosing" climbs to the next. | id grammar; unique in the block; the reserved value `none` is never an entity id (not in `data-cf-group`, `data-cf-for` or a figure mark id) and excludes the subtree: a gesture inside it resolves to the nearest target ancestor or the block |
| `data-cf-group="<id>"` | a container, usually `g` | An entity selected as one: its descendants are never separate targets. | id grammar; unique in the block (shared id space with targets); no descendant may carry `data-cf-target`, `data-cf-group` or `data-cf-for` |
| `data-cf-label="<text>"` | an element with target or group | The entity's label. | 1 to 120 characters after whitespace collapse; only beside `data-cf-target` or `data-cf-group` |
| `data-cf-for="<id> [<id>...]"` | a label element, usually `text` | This element labels those entities; a gesture on it resolves to the first listed entity. | 1 to 8 ids, each an entity of the same block |

Label resolution. The server is the authority and never needs a DOM:

- `figure` mark: the `text` of every draw item, in the composition named by
  the note's `variant`, whose `for` lists the mark's id, in draw order,
  joined by one space; else the state's `means`; else the id. A legend
  entity: the state's `means`.
- `html` stage entity (from the parsed stage): `data-cf-label`; else the
  text of the elements whose `data-cf-for` lists the entity, joined by one
  space in document order; else `aria-label`; else the entity's own text
  content; else the id.

Whitespace is collapsed and the result cut to 120 characters. It is never a
bare tag name. The runtime writes exactly this label into
`data-cf-entity-label` (the server while scoping a stage, the grammar
module for a figure, from the same rule), and the page sends it back;
`label_mismatch` compares it with the server's own resolution. The runtime renders each entity element with the reserved
attributes `data-cf-entity` (id) and `data-cf-entity-label` (label) so the
page and the server read the same table.

### B3. The resolver (3.1)

One resolver serves hover, click, touch, keyboard and saved anchors. For a
gesture at a point it returns the first that applies:

1. a non-empty text selection inside a block's review text (a text note);
2. a label element with `data-cf-for` (its first entity);
3. the innermost `data-cf-group`, else the innermost entity
   (`data-cf-target` or a figure mark), not inside a `none` subtree;
4. a visible shape or element (the v1 element target list plus `g`, `path`,
   `line`, `polyline`, `polygon`, `rect`, `circle`, `ellipse`, `text`),
   labelled by the nearest ancestor that has a label (B2 order), then by the
   block label;
5. the block;
6. region capture, only when the reviewer asks for it (drag or the region
   key).

It never resolves to runtime chrome, a `defs` subtree, a marker, a `title`
or `desc`, or an element hidden by `display: none`, `visibility: hidden` or
a collapsed ancestor. Thin strokes: a point within 6 CSS pixels of a
`line`, `polyline` or `path` segment of a target counts as a hit, measured
by distance to the segment in screen space, so no hit strokes are needed in
drawn or hand-written SVG. Keyboard: arrow keys move between entities in
document order, `Enter` pins, and `Shift+Enter` ("select enclosing") climbs
to the enclosing entity, then the block. The chip and the rail show the
entity label.

### B4. Server checks on entity anchors (3.1)

On review submit, for each note with an entity selector, the service
accepts it only if all hold, and otherwise refuses the whole review with the
typed error named:

- the envelope revision is the current revision (`stale_revision`, as v1);
- the block exists and has that entity id at that revision
  (`unknown_entity`);
- the selector's `label` equals the label the server resolves by B2
  (`label_mismatch`); the server stores its own label;
- the selector's `block_digest` equals the block's digest (`digest_mismatch`);
- when a `crop_box` is present and the server can compute the entity's
  bounds, the crop lies inside those bounds widened by 8 user units on every
  side, in the user space of the entity's `svg` (`crop_outside_entity`).

The server computes bounds for figure marks from their declared geometry,
and for stage elements that are `rect`, `circle`, `ellipse`, `line`,
`polyline`, `polygon` or `path` (absolute `M L H V C Q Z`), or `g` groups of
those, with no `transform` on the element or an ancestor up to its `svg`.
For any other entity (text only, transformed, HTML element) it cannot, and
it records `crop_check: "unverified"` on the stored note rather than
claiming containment. The PNG crop rule for the page (the crop's pixel
bounds match the entity bounds plus the 6 px stroke padding, within 2 px at
the capture scale, and the crop is not one colour) is a page rule tested in
the browser suite; the server check above is a separate security check.

### B5. Framing (3.2)

Schema v2 makes the runtime draw the framing; authors supply text only.

- `figure` block: the runtime renders "Figure N · title", then the kicker
  as a qualifier when set, the drawing, the legend when the figure draws
  states (always, since states are required), the caption, and one
  `details` disclosure titled "Details" holding the description and the
  table twin. SVG `title` and `desc` stay for assistive technology. The
  declaration fields already carry title, kicker, caption, description,
  states and twin; no block field is added.
- `html` stage: every v2 `html` block is a figure. This departs from the
  proposal's "html stage used as a figure" on purpose: EPC-016 makes the
  figure the default visual form (ADR-0068), and a panel of prose or data
  belongs in a narrative, callout or table block, so one rule keeps the
  numbering and the resolver simple. `title` and `caption` are required; `legend` (1 to 12 entries of `label` and `means`) and
  `description` are optional. The runtime renders "Figure N · title", the
  stage, the legend when given, the caption, and a Details disclosure when
  a description is given. The skill tells authors that a stage whose marks
  encode meaning carries a legend or migrates to a `figure` block.
- `table`: v2 requires `title` and allows `caption`; the runtime renders
  "Table N · title" and the caption.
- Numbering: figures (`figure` and `html`) and tables are numbered
  separately from 1, in document order by a depth-first walk that includes
  blocks inside `disclosure` and `tabs`, collapsed or not.
- References: in a v2 document, `[fig:<block-id>]` in any Markdown field
  renders as a link "Figure N" to that block and `[table:<block-id>]` as
  "Table N". A reference to a missing block or a block of the wrong kind
  is a validation error. v1 documents render these strings literally. The
  server's canonical review text of a v2 block holds the rendered label
  ("Figure 1"), not the reference, and the page's selection text is the
  same, so text offsets agree on both sides.
- The frame's title line, legend, caption and Details are outside the
  block's review text: they are element targets labelled by their text, and
  the canonical review text and block digest rules of v1 are unchanged by
  framing.
- The title is visible text in the live session, history and export. The
  drawn-figure gate (`docs-portal/scripts/browser-verify.mjs` and the
  shared `figureRuleFailures`) fails a figure whose title text is not
  visible in the DOM, so the portal figures meet the same rule.
- The numbering and legend rules are written in the shared
  `figure-grammar.md`, not only in present.

v1 documents keep rendering as today with three additive fixes: figure
parts are selectable (B3), the label fallback of B2, and the live `html`
stage shows its optional title as visible text.

### B6. Forms and answers (3.3)

A `form` block asks the reviewer typed questions. Its fields are a subset
of the MCP elicitation form schema, written as a list so the order is the
order shown:

| `kind` | MCP equivalent | Constraints |
|---|---|---|
| `text` | string | `min_length`, `max_length` (at most 16,384 UTF-16 units), `format` one of `email` (one `@` with a non-empty local part and a domain holding a dot, no whitespace; the page and server share this check), `uri` (an absolute URI with a scheme), `date` and `date-time` (RFC 3339 full-date and date-time), `multiline` (a display hint) |
| `number` | number | `minimum`, `maximum` (finite) |
| `integer` | integer | `minimum`, `maximum` (safe integers) |
| `boolean` | boolean | none |
| `choice` | enum (single) | `options` 2 to 24 of `value` and `label` |
| `choices` | array of enum | `options` 2 to 24; `min_items`, `max_items` |

Each field has `id` (entity id grammar, unique in the form), `label` (1 to
200 characters), optional `description`, and `rationale` one of `none`
(default), `optional`, `required`. The form lists `required` field ids. An
option may be marked `recommended: true` (at most one per field); the page
labels it "Recommended" and never preselects it. No field has a default
value.

Outcomes: `submit` (values, validated), `decline` (no values, an optional
reason of at most 4 KiB: the reviewer chooses not to answer) and `cancel`
(no values: the reviewer dismisses the question for now). All three are
stored and delivered, so the agent is never left waiting on a question the
reviewer has dismissed.

`decision` in v2 is a form: `title`, `markdown`, `options` (2 to 8, as
above, at most one `recommended`) and an optional `rationale` mode
(default `optional`). It renders as a form with one `choice` field whose id
is `choice`. The v1 `decision` with an author-set `status` stays readable;
a v2 `decision` with `status` is refused.

Submission: the page validates before submit. The service validates again
against the form as it is at the revision named in the request (field
kinds, bounds, required, options, rationale, outcome), derives the actor
(`operator`) and the time, and appends the answer atomically. The form
digest is computed only by the server, with the same serialization and hash
as the v1 block digest (`state.rs` `block_digest`); the runtime renders it
on the form as `data-cf-form-digest`, the page echoes it, and a request
whose `form_digest` is not the digest at that revision is refused. The
`payload_digest` of a request is the SHA-256 of its body bytes as
received. Each request carries a
`request_id` (UUID) chosen by the page:

- same `request_id`, same payload digest: the original receipt, nothing
  appended (also when the first response was lost after the append);
- same `request_id`, different payload: refused (`request_id_conflict`),
  nothing appended;
- a correction is a new `request_id` with `amends` naming the original
  answer; it appends an amendment and the original stays readable; an
  amendment always names the original answer, not an earlier amendment.

A request for a revision that is no longer current is refused
(`stale_revision`) with the current revision and whether the form still
exists there and with which digest. The page keeps the draft and asks the
reviewer to confirm it against the current revision; confirming sends a
new request for the current revision.

Page states, shown on the form: editing, submitting, stored (the receipt
arrived; shown as "Stored, waiting for agent" until delivered), delivered,
acknowledged, failed (the request failed; the draft is kept and can be
resent with the same `request_id`), stale (a newer revision exists).

Drafts live in page memory for the life of the page and survive a revision
notice without a reload. No draft, answer, note or reply text is written to
`localStorage`, `sessionStorage`, IndexedDB or cookies; theme preferences
already kept in `localStorage` are unchanged. One exception: an unsent
review draft (its notes, verdict and instruction) may be kept in the tab's
`sessionStorage`, under a key that names the session id, so a reload keeps
the reviewer's work (QA defect 4). It is cleared on submit and on discard,
and dropped when the service reports the session closed; a draft under
another session's key is never shown. While kept, it is readable by the
session's own loopback origin, by this tab and tabs duplicated from it, and
by the browser's session-restore store in the profile, which can bring it
back with a reopened tab. Form answers and replies are never kept there or
in any other browser storage: the agent writes a form's questions, so an
answer must not outlive the page's memory.

Annotating a form (a text selection, a click on a field, an area drag) never
changes a field value, a draft or the store and never submits.

### B7. Authority of answers (3.3, decision 4a)

Answers, notes and replies stay in the private local session store
(`<state root>/present/projects/<project key>/sessions/<id>/`, under
Application Support on macOS), owner-only, and are never written into the
repository. The agent receives each answer with the question title, field
labels and option labels as they were shown, and every v2 event carries
`"untrusted": true`: an answer is evidence of the operator's choice in this
review, never authority to bypass a gate, approve a merge, widen scope or
run a command the agent's own rules would stop. The cf-present skill says
so in its feedback loop.

### B8. The agent loop (3.4)

- `present feedback <id> --wait [--timeout <S>] [--format v1|v2]` blocks
  until at least one event of the chosen format is pending, prints every
  pending one as a JSON line, marks them delivered and exits 0. With no
  `--timeout` it waits without limit; `--timeout S` (1 to 86,400 seconds)
  exits 6 when nothing arrived. When the session closes with nothing
  pending it exits 7. It polls the store every 250 ms and reads no network.
  `--wait` and `--follow` together are a usage error (exit 2).
- In Claude Code the agent runs the wait as a background task inside a
  shell loop that re-arms on exit 6, so only an event (0), a close (7) or
  an error wakes the model, and the agent starts the loop again after each
  turn:
  `while :; do codeflow present feedback "$ID" --wait --timeout 540 --format v2; rc=$?; [ "$rc" -eq 6 ] || exit "$rc"; done`
- `--format v1` (the default) prints only review envelopes, byte-compatible
  with 3.0.0 (C1). When answer, amendment, reopen or tombstone events are
  pending, it prints one line to stderr naming the count and
  `--format v2`, and never delivers them. Under `--wait`, such events do
  not end the wait: the notice is printed once when the wait starts or when
  the first such event arrives, and again on exit if any are pending.
- `--format v2` prints the typed events of I4 for reviews and answers
  together, in sequence order.
- `present responses list <id> [--revision N] [--form <block-id>]
  [--status pending|delivered|acknowledged] [--kind <kind>]` prints v2
  events with their status and never changes delivery state; the filters
  combine with AND.
- `present ack <id> <event-id>` records acknowledgment of a delivered
  event; acknowledging again is a no-op; an unknown or undelivered event
  is refused (exit 2). Delivered and acknowledged are separate states, both
  shown to the reviewer.
- `present reply <id> <event-id> [--note <note-id>] <text>` records the
  agent's reply (at most 16 KiB) on a review, a note or an answer; the
  reviewer sees it in the rail. A reply is agent output and is not
  delivered back to the agent.
- A harness is qualified when the real interactive path (browser, service,
  store, woken session, acknowledgment) is recorded for it. An unqualified
  harness still sees the store work; the reviewer sees "Stored, waiting for
  agent" until something delivers. No background model is started to
  simulate a listener.

### B9. Threads (section 2, threads row)

A review note or an answer is a thread, named by its event id plus, for a
note, its `note_id`. The agent replies (B8). The reviewer can reopen a
thread the agent acknowledged or resolved, which appends a `reopen` event
(with `note_id` for a note thread) that is delivered to the agent. The
reviewer can delete a posted note, which appends a `tombstone` event: the
rail shows "Deleted by the reviewer" in its place and the agent receives the
tombstone. A tombstoned note's body, quote and crop are never shown again
anywhere: not in the rail, `feedback` lines of either format delivered
after the tombstone, `responses list`, `history`, `diff` or `export
--include-feedback`; each shows the tombstone instead. The ledger stays
append-only; nothing is rewritten, so the text remains only in the private
session store until `present clear` removes the session.

### B10. Revisions bound to the repository (3.5)

Each revision written by `open` or `update` inside a git work tree records
its context: the `HEAD` commit, and when the tree has uncommitted changes
the SHA-256 of `git status --porcelain=v1 -z` followed by `git diff
--binary HEAD`; outside a work tree the context is absent. `open` and
`update` take `--label <text>` (1 to 80 characters) for the revision. A v2
document may carry `summary` (1 to 200 characters), which `present list`
shows for the session.

A v2 `code` or `diff` block may carry `source: { "path": "<repo-relative
path>" }`. At `open` and `update` the CLI resolves it inside the work tree
(refusing paths that escape it or are symlinks) and stores in the revision
`snapshots[]`: block id, path, the `HEAD` commit, `digest` (SHA-256 of the
block's shown bytes), `file_digest` (SHA-256 of the working tree file's
bytes at capture), `contains` (true when the shown bytes occur in the
file) and `uncommitted: true` when the file differs from `HEAD`. The
record proves where the snippet came from and whether it matched the file
at capture. The service has no route that serves repository files; the
browser never reads one.

`present diff <id> --from N --to M [--format text|json]` lists every block
of either revision by id as added, removed, changed (digest differs) or
unchanged, in the target's order with removed blocks after, and under each
block the notes and answers of revisions up to M re-anchored to M with
their B1 state. `history` and `diff` show the revision label and context.

### B11. Checking a page before handing it over (3.6)

`present check (<id> [--revision N] | --file <document.json>)
[--screenshot <png>]` validates the document without a browser: schema,
framing (B5), entities and vocabulary (B2), references, and forms (B6).
It prints one JSON line per failure `{ "block_id", "rule", "message" }`
and a final summary line, and exits 0 when there is no failure and 9 when
there is one. With `--screenshot`, when the supported Chromium that the
present runtime already discovers is found, it renders the revision
headless at 1280 by 800 in the default theme and writes the PNG; otherwise
the summary says `"screenshot": "not available"` with the reason, and the
exit status is unchanged.

### B12. Export (section 2, private by default row)

`present export` keeps its share-safe default: no notes, answers, replies
or ledger content. `--include-feedback` adds a read-only appendix with the
notes, answers and replies of the exported revision. Tombstoned notes appear
only as tombstones (B9). The export renders the
framing of B5.

## Interfaces and formats

### I1. Document schema v2

`schema_version: 2`. The v2 reader accepts 1 and 2; a 3.0.0 reader shows
the "Unsupported presentation version" page for 2 (`document.rs`
`parse_document`, `render.rs`). The schema file is
`document-v2.schema.json` in the three schema homes that hold
`document-v1.schema.json` (`assets/base/present/schemas/`,
`.codeflow/schemas/present/` and the managed baseline copy), byte
identical; the v1 file is unchanged. Additions over v1, all others as v1:

```json
{
  "schema_version": 2,
  "title": "…",
  "summary": "optional, 1 to 200 characters",
  "blocks": [
    { "type": "html", "id": "stage-a", "title": "required", "caption": "required",
      "legend": [{ "label": "Solid arrow", "means": "a direct call" }],
      "description": "optional, at most 2,000 characters", "html": "…" },
    { "type": "table", "id": "t1", "title": "required", "caption": "optional",
      "columns": ["…"], "rows": [["…"]] },
    { "type": "code", "id": "c1", "language": "rust", "code": "…",
      "source": { "path": "crates/x/src/lib.rs" } },
    { "type": "form", "id": "store-choice", "title": "Where should answers live?",
      "markdown": "optional prompt",
      "fields": [
        { "id": "home", "label": "Store", "kind": "choice", "rationale": "optional",
          "options": [{ "value": "local", "label": "Private local store", "recommended": true },
                      { "value": "repo", "label": "Committed JSON Lines" }] },
        { "id": "notes", "label": "Anything else", "kind": "text", "format": "multiline", "max_length": 2000 }
      ],
      "required": ["home"] },
    { "type": "decision", "id": "d1", "title": "…", "markdown": "…",
      "options": [{ "value": "a", "label": "Option A", "recommended": true },
                  { "value": "b", "label": "Option B" }],
      "rationale": "optional" }
  ]

```

Limits: at most 32 `form` and v2 `decision` blocks per document, 32 fields
per form, 24 options per field.

### I2. Entity selector on a note

A note (`FeedbackNote`) gains an optional `entity_selector`; a note with it
also carries the `element_selector` of the entity's element so the v1 view
of the note stays well formed (C1). The entity selector, the server label
and `crop_check` are stored on the note inside its review envelope in
`events.jsonl`, like every other selector; one note is never split across
two ledgers. The history schema gains the optional field additively:
`session-history-v2.schema.json` is added in the three schema homes and
`session-history-v1.schema.json` stays byte-identical. The v1 `feedback`
stream serializes the note without the entity selector, server label and
`crop_check`.

```json
"entity_selector": {
  "entity_id": "registry",
  "label": "Registry",
  "block_digest": "<sha256 hex>",
  "variant": "wide",
  "crop_box": { "x": 120.0, "y": 40.0, "width": 180.0, "height": 64.0 }
}
```

`variant` is `wide` or `narrow` for a `figure` block and absent otherwise.
`crop_box` is in the user space of the entity's `svg`, at most three
decimals, and absent for an entity outside an `svg`. The stored note adds
the server's resolved `label` and, whenever B4 could not check containment,
`"crop_check": "unverified"`. The field appears only with that value: on the
stored note, on the history view and on every v2 review line the agent reads;
a note with a `crop_box` and no `crop_check` field had its crop checked. The
v1 stream never carries it.

New anchor states in the note view: `entity_anchored { entity_id }`,
`entity_reanchored { entity_id, label_changed }`, `reanchored { start_utf16,
end_utf16, changed: true }` (existing variant, new field), `block_fallback
{ block_id, reason }`; `orphaned { reason }` is unchanged.

### I3. Review errors

The service answers a refused review or answer with a body
`{ "error": "<code>", "message": "…", "details": { … } }` and the status
in the table after this list. Codes:
`stale_revision` (details `current_revision`, and for answers
`form_present`, `current_form_digest`), `unknown_entity`,
`label_mismatch`, `digest_mismatch`, `crop_outside_entity`,
`request_id_conflict`, `form_digest_mismatch`, `unknown_form`,
`invalid_answer` (details `fields: [{ "field", "code" }]` with codes
`required`, `unknown_field`, `wrong_kind`, `too_short`, `too_long`,
`format`, `below_minimum`, `above_maximum`, `not_integer`,
`unknown_option`, `too_few`, `too_many`, `rationale_required`,
`rationale_not_allowed`), `invalid_amendment` (`amends` names no answer
of this form, or names an amendment), `answer_too_large` (64 KiB request
body), `session_closed`, `store_unavailable` (the session store could not be
locked, read, written or synced, so no receipt was given; a resend with the
same `request_id` is safe: it appends the answer once, or returns the
original receipt if the failed request's line did reach the store).

| Status | Codes | Page behaviour |
|---|---|---|
| 409 | `stale_revision`, `request_id_conflict` | keep the draft or notes; stale asks to confirm against the current revision |
| 410 | `session_closed` | keep the draft read only; nothing can be sent |
| 413 | `answer_too_large` | keep the draft; show the limit |
| 422 | `unknown_entity`, `label_mismatch`, `digest_mismatch`, `crop_outside_entity`, `form_digest_mismatch`, `unknown_form`, `invalid_answer`, `invalid_amendment` | keep the draft or notes; show the field or note errors; a retry with the same body fails the same way |
| 503 | `store_unavailable` | keep the draft; say it was not confirmed as stored and offer to resend with the same `request_id` |

### I4. Answer ledger and v2 events

Answers, amendments, acknowledgments, replies, reopens and tombstones are
appended to `responses.jsonl` in the session directory, beside the v1
`events.jsonl`, which keeps its exact shape. One JSON object per line,
schema `session-responses-v1.schema.json` in the three schema homes:

```json
{ "event": "answer", "sequence": 1, "answer_id": "<uuid>", "request_id": "<uuid>",
  "payload_digest": "<sha256>", "session_id": "<uuid>", "revision": 5,
  "form_id": "store-choice", "form_digest": "<sha256>", "outcome": "submit",
  "values": { "home": "local" }, "rationales": { "home": "…" },
  "question": { "title": "…", "fields": [{ "id": "home", "label": "Store", "kind": "choice",
                "options": [{ "value": "local", "label": "Private local store" }] }] },
  "actor": "operator", "created_at_unix": 1790000000 }
{ "event": "amendment", "…": "as answer", "amends": "<answer uuid>" }
{ "event": "delivered", "sequence": 3, "target": "<event id>", "at_unix": 1790000001 }
{ "event": "acknowledged", "sequence": 4, "target": "<event id>", "at_unix": 1790000002 }
{ "event": "reply", "sequence": 5, "reply_id": "<uuid>", "target": "<event id>", "note_id": "<uuid>", "text": "…", "actor": "agent", "at_unix": 0 }
{ "event": "reopen", "sequence": 6, "reopen_id": "<uuid>", "target": "<event id>", "note_id": "<uuid, for a note thread>", "actor": "operator", "at_unix": 0 }
{ "event": "tombstone", "sequence": 7, "tombstone_id": "<uuid>", "target": "<review event id>", "note_id": "<uuid>", "actor": "operator", "at_unix": 0 }
```

`decline` and `cancel` answers have empty `values` and `rationales`;
`decline` may carry `reason`. Delivery of a review stays in `events.jsonl`
(`delivered`, as v1), so v1 and v2 readers never deliver the same review
twice; delivery of every other v2 event is in `responses.jsonl`.

Append rule: one line per event, written with its newline in one write and
synced before the receipt is returned, under the session lock. On open, a
final line with no newline or that does not parse is a torn append from a
crash: the store truncates it under the lock; its request never got a
receipt, so the page's retry appends it.

v2 feedback line (one per event, `--format v2` and `responses list`):

```json
{ "format": 2, "kind": "review|answer|amendment|reopen|tombstone",
  "event_id": "<uuid>", "session_id": "<uuid>", "revision": 5, "sequence": 1,
  "status": "pending|delivered|acknowledged", "created_at_unix": 0,
  "untrusted": true, "…": "kind fields" }
```

Kind fields: `review` has `verdict`, `instruction` and `notes` with their
`entity_selector`, `crop_check` whenever it is `unverified` (so the agent
never takes an unchecked crop as checked; see I2) and anchor; `answer` and `amendment` have `form_id`,
`outcome`, `values`, `rationales`, `reason`, `question`, and `amends` for an
amendment; `reopen` has `target` and, for a note, `note_id`; `tombstone` has
`target` and `note_id`.
`event_id` is the review's `event_id` or the answer, reopen or tombstone
id.

Receipt returned by `POST /app/api/answers` (HTTP 200):

```json
{ "answer_id": "<uuid>", "request_id": "<uuid>", "sequence": 1, "revision": 5,
  "form_id": "store-choice", "state": "stored", "replayed": false, "stored_at_unix": 0 }
```

New page routes, under the v1 request checks (host, origin, cookie, static
header, content type): `POST /app/api/answers`, `POST
/app/api/threads/reopen`, `POST /app/api/notes/tombstone`. The long poll
gains the kinds `answer_state` and `thread`.

## Edge cases

The fixture index (I7) maps each to a fixture and the task that first makes
it pass.

- A v1 document with an `html` title, rendered by the v2 reader (TSK-118).
- A v2 figure, `html` stage and table, framed and numbered through a
  collapsed disclosure and a tab (TSK-118).
- A v2 `html` stage without a caption, a table without a title, a
  `[fig:missing]` reference, an authored figure mark without an id (refused,
  TSK-118).
- The closed vocabulary: a valid stage; an unknown `data-cf-*` name, a
  duplicate id, `data-cf-for` naming a missing id, a target inside a group
  (refused, TSK-118).
- Entity anchors: valid; forged entity id (`unknown_entity`); crop outside
  the entity (`crop_outside_entity`); client label differing from the
  server label (`label_mismatch`); a transformed entity recorded as
  `unverified` (TSK-118).
- Re-anchoring: same revision; entity kept with a changed label; entity
  removed with the quote found; quote not found (`block_fallback`); block
  removed (`orphaned`) (TSK-118).
- Answers: valid submit, decline and cancel; malformed (`invalid_answer`);
  oversized (`answer_too_large`); stale (`stale_revision`); identical retry
  (original receipt); same request id with a different payload
  (`request_id_conflict`); an amendment; a torn final line (TSK-119).
- Queries by revision, form and status, alone and combined; list then wait
  (TSK-120).
- v1 and v2 feedback lines for the same session, and the stderr notice
  (TSK-120).
- Snapshot provenance for a clean and a dirty file (TSK-121).
- Threads: reopen of a note and of an answer, a tombstone and its absence
  from every later output, export with and without `--include-feedback`
  (TSK-121).

## Limits

- Per-mark entities in a figure whose declaration has a `layout` object
  wait for a layout-level key contract; such a figure exposes legend
  entities and the block (B2). Figures without `layout`, including authored
  extent and coverage figures, have per-mark entities.
- Server containment is checked only where the server can compute geometry
  (B4); other crops are stored as unverified, never as checked.
- Canvas, WebGL and video are not entity targets.
- Remote and phone review, shared databases, rooms, page-side model calls,
  connectors, hosted identity and permission grants are out of scope
  (decisions 1a and 3a).
