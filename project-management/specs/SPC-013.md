# SPC-013: Delivery system for parallel agents

## Summary

This spec pins the behaviour that lets several agents plan, claim, build and
land tracked work on parallel lines without colliding on ids, on status words
or on acceptance evidence. It is the contract the delivery-system tasks
implement and the reference a reviewer tests each task against.

### How to read it

- Rationale lives in the successor ADR to ADR-0046; the plan and its sizes
  live in the epic.
- Requirements are numbered R-1 onward so tasks and reviews can cite them.
  Numbers leave gaps between sections so a revision can insert a
  requirement without renumbering. Requirements added after plan review
  round 1 are numbered R-108 onward and sit in the section they belong
  to; no requirement is renumbered.
- A requirement holds when durable work tracking is on (the existing
  `durable_work_tracking_enabled` switch), unless it says otherwise.
- "Block" and "warn" name the level a plane applies; "never adjustable"
  means an adopter cannot relax the rule once tracking is on.

## Delta against current capability

ADDED: a shared id registry on a protected data branch with an issue
protocol; a hidden `uid` on every record; status verbs with transition rules;
one readiness predicate; an advisory claim command; criterion ids, frozen
criteria and one source-bound acceptance block; total classification of
product PRs; a work-flow model with research inputs, a spike path and
many-to-many spec and epic links; a computed spec state; trusted automation
profiles; `release.backend`; a file-state grader for behavioural evals.

MODIFIED: id allocation moves from the maximum visible in one checkout to the
registry's whole history plus every ref; task, epic and spec status move from
hand edits to verbs judged by one validator; readiness moves from
`status --delivery`'s partial view to the shared predicate; criteria move
from ticked checkboxes to listed criteria with results in the acceptance
block; the anchored preflight runs for tracked work on any branch, not only
`task/` branches; kept brownfield PR templates get an explicit mapping
instead of a failing check; project record templates are read.

REMOVED: `in_progress` as a written status (it stays readable); the ledger's
producerless work-graph event types; the quick standalone record path; the
`off` level for `git.work_records`; the checkbox as the carrier of a
criterion's result on new records.

## Behavior

### Identity

- R-1. Every record carries two identities. `id` is the readable sequential
  id (`EPC-NNN`, `SPC-NNN`, `TSK-NNN`, `ADR-NNNN`) used in filenames, branch
  names and links, as today. `uid` is a UUIDv4 written once into frontmatter
  by `new` and shown in no ordinary view. Legacy `TSK-NNN-NNN` ids stay
  valid and are never renumbered.
- R-2. Two copies with the same `uid` are the same record (a replica). Two
  records with the same `id` and different `uid`s are a collision. The
  validator rejects an edited `uid` on an existing record and a `uid` that
  differs from the registry's binding for that id.
- R-3. Every record created before this spec lands receives a `uid` from
  the seed (R-24) and the backfill (R-25). After the backfill lands on a
  line, no record on that line is exempt from the `uid` checks.
- R-4. The `uid` is an integrity check. It does not replace number
  coordination and does not prove what a record means.

### The registry

- R-5. Each repository that tracks work has one registry: the branch
  `codeflow/registry` on the authority remote, `origin` by default. It holds
  one file per issued id at `ids/<KIND>/<N>.toml` (format in Interfaces).
  Numbers are scoped to their repository.
- R-6. The registry is a data branch with its own profile. It is not in
  `protected_branches`, has no pull-request requirement, skips branch naming
  and the product test gate, and never triggers `ids sync` recursively.
  `codeflow remote protect` applies the data profile to it (no branch
  deletion, no force push) and leaves the rules of `main` unchanged. A
  maintainer creates and seeds the branch once; CI never needs write access
  to it.
- R-7. Allocation reads history. The next number for a kind is one more than
  the greater of: the highest number ever added under `ids/<KIND>/` in the
  registry's history, and the highest id of that kind on any local or
  remote-tracking ref. Deleting or editing a file on the tip never lowers it.
- R-8. The registry only grows. Every commit in a pushed range either adds
  new files under `ids/` and does nothing else, or is a typed restore
  (R-108). Pre-push checks the whole range and git-guard checks the
  command; both block. The registry check (R-109) re-validates the whole
  history and reports any commit that removes or modifies a file outside a
  typed restore.
- R-9. The registry is currently damaged when any path ever added under
  `ids/` is absent from the tip or differs from the content it had when
  first added. The CLI runs this check on the fetched history before every
  issue and refuses to issue while it fails. A commit that caused damage
  that a later restore repaired is historical damage: it stays in history,
  is reported as history by `ids check`, and does not block issue or CI.
- R-108. Typed restore. `ids restore <id>...` writes one commit whose only
  changes re-add or revert the named `ids/` files to the bytes of their
  first addition in history, with the subject `restore: <ids>`. Pre-push,
  git-guard and the registry check accept a commit as a restore only when
  every path it touches was previously added, every path's new content is
  byte-identical to its first addition, and the commit adds nothing else.
  A restore that would bind a number to any other `uid` is refused. Issue
  and CI return to healthy as soon as the tip passes R-9; no other state
  is kept. Restore is a maintainer operation with push rights to the
  registry; CI never runs it.
- R-109. Bootstrap and the registry check. `ids seed` creates the branch as
  an orphan whose root commit adds only `ids/` files; that root commit is
  validated by the same rule as every later commit. The registry branch
  holds no workflow, script or other code, so no job runs from it. The
  registry check is `codeflow ids check` run by the code branch's CI: for
  every pull request, every push of a tracked target, and on a daily
  schedule from the default branch; for a pull request it also applies the
  merge rule of R-14 to the PR's range. The enforcing job runs on
  `pull_request_target`, so its workflow definition comes from the target
  branch and a PR cannot edit, skip or replace the check that judges it; it
  reads the PR head only as git data, never checks out, builds or runs PR
  code, and runs with a read-only token and no secrets. Build and test jobs
  stay on `pull_request`. Its code is the `codeflow` binary the target's
  workflow pins (R-113); a PR cannot select the binary that checks it. The
  check needs no registry write scope. Seeding is idempotent: a rerun on an
  existing branch adds only ids not yet registered and changes nothing.
  (Amended 2026-09-26 after the TSK-100 host proof: under `pull_request` a
  PR that rewrote the check step went green on a damaged registry.)
- R-10. On a host without branch rules, the CLI keeps the last verified tip
  of `origin/codeflow/registry` in untracked local state and refuses to
  issue when the fetched tip does not descend from it. `doctor` reports
  reduced assurance for that repository.
- R-11. Fetches of the registry are never forced. The local
  `codeflow/registry` branch holds pending reservations and is kept apart
  from `origin/codeflow/registry`.

### Issue, merge and admission

- R-12. `new` for an epic, spec, task or ADR issues its id by this protocol,
  in order: fetch `origin/codeflow/registry` (non-forced); compute N by R-7;
  commit `ids/<KIND>/<N>.toml` with a fresh `uid` on top of the fetched tip;
  push that commit to `refs/heads/codeflow/registry`, never forced; then
  write the record with exclusive create, carrying the reserved `uid`.
- R-13. Push outcomes are classified, never collapsed into "taken":
  accepted means reserved; rejected because the tip moved means fetch,
  recompute N and retry, at most five attempts, then stop with the reason;
  a permission, unsupported-operation or transport error is reported as
  that error; an unclear result is resolved by fetching and reading back:
  reserved when the fetched tip reaches a commit (or a replay) that binds N
  to our `uid`; offline means a commit on the local `codeflow/registry`
  under a local lock, reported as "pending, not unique yet".
- R-14. The merge rule: every record added in a PR must be reserved in the
  authority's registry, bound to that record's `uid`, before the PR can
  merge. CI checks the binding against the fetched registry on every run.
  Block; never adjustable.
- R-15. `ids sync` publishes pending reservations. It runs before any online
  write and in pre-push. It replays each pending file on the fetched tip;
  the same `uid` already bound to N counts as reserved; a different `uid`
  bound to N stops sync and names `ids retarget`. In pre-push, sync warns
  and continues when the authority is unreachable or is not the push
  target; it blocks only on a number held by a different `uid`.
- R-16. `ids retarget <id>` renumbers an unmerged record to the next free
  number, rewrites its in-tree links, and records the old id in
  `former_ids`. It refuses a record already landed on a stable target.
- R-17. `ids admit <record path or PR>` reserves the number for a fork or
  hand-written record's `uid`, or, when that number is held, the next free
  number with an instruction to retarget. Only a maintainer with push
  rights to the registry runs it; untrusted PR code never receives write
  credentials. The PR stays red until admitted. An abandoned admission
  leaves a gap; a number is never reissued.
- R-18. `new --resume <id>` completes a crash between reserve and write. It
  writes the record when the reservation's issuer and `uid` match the
  caller's pending state, and refuses otherwise.
- R-19. When a repository with no remote gains an authority, `ids sync`
  merges by file. A clash on a record not yet landed is retargeted. A clash
  on a record already landed on a local stable target stops with an
  explicit authority migration that records the disposition; it never
  renames silently.
- R-20. CI fetches `codeflow/registry` explicitly with its full history, on
  shallow and single-branch checkouts too. Read commands never fetch.
- R-21. `ids check` validates the registry (R-8, R-9) and reconciles it with
  the record inventory on every ref; `doctor` reports the result and any id
  it cannot place.
- R-22. `codeflow remote protect` gains the data profile for the registry
  branch. Applying it to a host is proved end to end before the rest of the
  registry ships: the host proof in TSK-100 exercises the exact arrangement
  of R-109 (orphan data branch, no workflow on it, the check run from the
  code branch's CI) and the journeys named in R-104.

### Claims

- R-23. `work claim <TSK>` runs the readiness predicate in its new-claim
  context (R-40, R-110) and the anchored preflight against the fetched
  target tip, creates
  `task/TSK-NNN-<slug>` from that tip and pushes it. The pushed branch is
  the visible mark of a claim. It is advisory: no document calls it a lock,
  and no command depends on it being exclusive. Two visible branches
  carrying one task's id are reported by `status` as a conflict.

### Seed and backfill

- R-24. `ids seed` reads every id on every ref and in retained history,
  decides which copies are one record by their first introducing commit
  (and, where squash or cherry-pick hides that, by their first landing on a
  stable target), assigns each record one `uid`, writes one registry file
  per id with its provenance (R-111), and reports any id it cannot place.
  It is idempotent: a rerun adds nothing for an id already registered.
  CodeFlow's registry continues at EPC-020, SPC-013, TSK-100 and the next
  ADR number.
- R-111. Legacy ids and provenance in the registry. A legacy
  `TSK-NNN-MMM` id is registered at `ids/TSK/NNN-MMM.toml`; its `id` field
  is the legacy id and its `kind` is `TSK`. Legacy ids never contribute to
  the high-water mark of R-7, and a canonical `TSK-NNN` is a distinct id
  from every legacy `TSK-NNN-MMM`. Every seeded file records `introduced`
  (the first commit that added the record, with the ref it was read from)
  and `landed` (the first commit on a stable target that holds it, or
  `none`); an issued file records `introduced = none` and `landed = none`.
  Identity is the commit sha only: the ref in `introduced` is provenance
  metadata, and an absent value (`none`) matches nothing, so two records
  that are both unlanded are never replicas by `landed`. Seed decides
  replicas from a nonempty matching `introduced` sha or a nonempty matching
  `landed` sha only. When no such match identifies two copies as one
  record (squash or cherry-pick with differing content), seed stops and
  names the ids; the maintainer supplies an explicit mapping with `ids
  seed --map <file>`. Seed writes each mapped copy's introducing sha into
  the registry entry's `mapped` list, with the maintainer and date in
  `mapped_by`, so every later reader, CI and a replayed seed included,
  reproduces the mapping from the registry alone; the verification record
  also cites the map. Seed never infers that two copies are one record
  from a matching number alone. Before a line's backfill, CI judges a
  record without a `uid` against the registry entry: its introducing sha
  equal to `introduced` or to an entry of `mapped`, or its nonempty landing
  sha equal to a nonempty `landed`, means a replica; otherwise a
  collision.
- R-25. `ids backfill` writes the registered `uid` into each existing
  record on the current line whose frontmatter lacks one. It never
  generates a `uid`, never changes an existing one, and refuses a record
  whose id has no registry entry. Each line's backfill lands in that line's
  cleanup PR.

### Recorded and derived facts

- R-26. Recorded facts, written by a person, an agent or a verb: `id`,
  `uid`, title, outcome, criteria with ids, `depends_on`,
  `integration_target`, one epic or a standalone reason, specs,
  `follow_up_of`, `external_refs`, `work_type`; task status among `todo`,
  `blocked`, `complete`, `cancelled`; the Blocker (reason, owner, revisit
  event); the cancellation (reason and where the scope went); the
  acceptance block; epic terminal acts `complete`, `cancelled`, `archived`;
  spec status `draft`, `approved` or `superseded`, with `supersedes` and
  `superseded_by` links; a join's `awaiting_selection` reference (R-43);
  the kind and pin of each dependency edge (R-112).
- R-27. Derived facts, computed by every reader from git and the graph and
  written nowhere: active (a visible branch carrying the task id, on any
  sanctioned prefix, `<prefix>/TSK-NNN-<slug>`, not landed);
  ready (R-40); waiting (`todo` with an unmet dependency, shown apart from
  `blocked`); landed (branch tip is an ancestor of the target, or
  patch-equivalent by `git cherry`); epic progress (counts of its tasks);
  release membership (the changelog and the published baseline); spec
  `implemented` (R-51).
- R-28. `in_progress` stays readable. No verb writes it. `validate` warns
  on an `in_progress` task with no active branch.
- R-29. The ledger's work-graph event types that have no producer are
  retired; no route accepts them.

### Lifecycle and writers

- R-30. Task transitions: `todo` to `blocked` (needs reason, owner and
  revisit event); `blocked` to `todo`; `todo` to `complete` (needs an
  acceptance block that passes R-60); `todo` or `blocked` to `cancelled`
  (needs reason and scope disposition in the Closeout); `complete` to
  `todo` on reopen (needs a reason; the old acceptance block is marked
  superseded and kept). Any other transition is refused.
- R-31. A partial or stacked PR leaves the task `todo`; the last slice
  completes it.
- R-32. Spec lifecycle, the only table:

  | From | To | By | Condition |
  |---|---|---|---|
  | `draft` | `approved` | planning PR on the target | no open question |
  | `approved` | `superseded` | planning PR that adds a new spec revision | the new spec lists `supersedes: [SPC-old]`; the old spec gets `superseded_by: SPC-new` in the same PR; acceptance that cited the old spec's changed criteria is invalidated |
  | `approved` | `implemented` (derived) | no writer | R-51 |

  `approved` never returns to `draft`; a changed contract is a new spec.
  `implemented` is derived and refused as a written value on records
  created after this spec lands; existing records that carry it are read
  as before. `spec status` writes only `approved` and `superseded`.
- R-33. Epic close requires every task terminal, every epic criterion
  verified, every journey criterion verified on the named journey, and
  every consumed spec either implemented in the candidate state or listed
  as still consumed by another open consumer. The candidate state is the
  derived spec state computed with the closing epic counted as `complete`.
  A cancelled child never satisfies the epic's outcome: an epic criterion
  served only by cancelled tasks is unverified. `complete` to `archived`
  needs no further check.
- R-34. The verbs and what they write:

  | Verb | Writes | Checked |
  |---|---|---|
  | `epic new [--integration]`, `spec new`, `task new --epic \| --standalone-reason \| --follow-up-of`, `adr new` | registry file, record with `uid` | R-12; the epic and target resolve on their own line; the record is written on a planning branch of that target |
  | `work next [--epic] [--json]` | nothing | R-40, R-41 |
  | `work claim <TSK>` | task branch, pushed | R-23 |
  | `work start <TSK>` | nothing | today's preflight plus R-42 |
  | `task status <TSK> todo\|blocked\|complete\|cancelled [--reason --owner --revisit]` | status, Blocker, Closeout marks | R-30 |
  | `epic status`, `spec status` | status | R-32, R-33 |
  | `ids seed \| backfill \| sync \| admit \| retarget \| check` | registry, pre-merge renumbering | R-8 to R-25 |

- R-35. The verbs are safe editors, not the only writers. The same core
  validator judges every edit, from a verb, a hand edit or a PR range. A
  verb detects a concurrent edit of the record by content digest and
  replaces the file atomically.
- R-36. `adr new` allocates `ADR-NNNN` through the registry and renders the
  ADR template with `status: proposed`.
- R-37. `new` works at every tier. Project record templates under
  `project-management/templates/` are read and validated before use, with
  the embedded templates as fallback. Shipped templates contain no policy
  character.

### Readiness

- R-40. The core readiness predicate holds for a task when all of these
  hold: status `todo`; no Blocker; no `awaiting_selection` reference
  (R-43); every consumed spec `approved` or derived `implemented`; its
  epic open (or the task standalone); every code dependency accepted and
  present in the execution base; every research or decision dependency
  accepted at its pinned ref (R-112). `work next`, `work claim`, `work
  start`, `status` and CI share this one core and add only the caller
  context of R-110.
- R-110. Caller contexts of the readiness predicate. Three contexts share
  the core of R-40 and differ only in how the caller's own branch and the
  status transition are judged:

  | Context | Callers | Adds to the core |
  |---|---|---|
  | New claim | `work next`, `work claim`, `status` (ready list) | no visible branch carrying the task id on any sanctioned prefix on the fetched remote; the execution base is the fetched target tip |
  | Own task branch | `work start` | the task is the id the checked-out branch carries, `<prefix>/TSK-NNN-<slug>` with any sanctioned prefix (`task/`, `fix/`, `feat/`, `spike/` and the rest of `branch_prefixes`); that branch is not counted as a competing claim; any other visible branch carrying the id is reported as a conflict and does not refuse; the core, status included, is read at the merge-base with the target, and a staged or committed status transition of this task is judged by R-30 and R-60 as in the PR-transition context; a branch that carries no task id has no own-branch context |
  | PR transition | CI on a tracked PR | the task is the PR's `Task: TSK-NNN` line; when the head branch carries a different task id, CI blocks the mismatch; the core is evaluated at the anchored base (the merge-base), not at the head; the head may carry one status transition of R-30 for this task, judged by R-30 and R-60; a second visible branch carrying the id is reported, not refused |

  A task that is `complete` or `cancelled` fails every context. The full
  positive journey (claim, start, build, complete, CI green), the same
  own-branch journey on `fix/`, `feat/` and `spike/` branches carrying the
  task id, a competing-branch negative control and a mismatched-association
  negative control (a PR whose `Task:` line names another task than its
  branch) are proof obligations (R-104).
- R-41. `work next` lists ready tasks first, then waiting and blocked tasks
  with their reasons; includes standalone tasks; excludes tasks with a
  visible branch carrying their id (R-110); and prints the remote tip and fetch time of the
  snapshot it judged from. `--json` returns the same facts.
- R-42. Cross-line dependencies: a predecessor complete on another line is
  accepted there, not available here. For a code dependency, `work start`
  refuses until the accepted change is in this task's execution base by
  merge or by an explicit reviewed port. The execution base is the fetched
  target tip for `work next` and the merge-base of the task branch with
  its target for `work start` and CI. An unfetched line is reported as
  unknown, never as satisfied.
- R-43. Guarded plans: only the selected branch of a decision is written
  into `depends_on`. Until the selection is approved on the target, the
  join task carries `awaiting_selection: <plan or decision path>` in
  frontmatter, is `blocked` with reason "awaiting selection" and that
  reference as its revisit event, and may have an empty `depends_on`. The
  validator requires the referenced path to exist on the target and treats
  the task as a valid record that no context of R-110 can start. A join
  with an empty `depends_on` and no `awaiting_selection` is a root task.
  The approved selection lands by a planning PR that removes
  `awaiting_selection`, writes the selected dependencies and unblocks the
  join; a selection cannot land on a task branch. A cancelled, unselected
  alternative never blocks a join.
- R-112. Dependency edges carry a kind and, for non-code kinds, a pin. An
  entry of `depends_on` is either a bare task id, which is a code
  dependency, or an object `{id: TSK-NNN, kind: research | decision,
  pin: <commit sha>}`. A code dependency is satisfied when the predecessor
  is `complete` and its accepted change is in the execution base (R-42). A
  research or decision dependency is satisfied when the predecessor is
  `complete` and `pin` names a commit that exists on the predecessor's
  target and holds the predecessor's record as `complete`; the planner
  writes the pin when it becomes known, and a research or decision entry
  without a pin is unmet. One predecessor may be a code dependency of one
  consumer and a research dependency of another. The kind is never
  inferred from the predecessor's `work_type`.
- R-44. `status` stops calling a live integration branch removable; it
  reports removable, dirty and unproven entries as local git evidence.
  `orient` prints a task summary from the same predicate.

### Acceptance

- R-50. Criteria on new records are listed lines of the form
  `- AC-n When <condition>, the system shall <behaviour>` with no checkbox.
  Ids are `AC-n`, unique within the record and never renumbered. A task
  criterion that serves an epic criterion ends with
  `(serves EPC-NNN AC-m)`. A journey criterion ends with `(journey)` and
  names the path exercised: fresh init, update, the installed CLI, the
  present runtime, or the release artefact. Legacy records keep their
  checkboxes and are read as before.
- R-51. Spec `implemented` is computed, and this is the only
  cancelled-consumer rule: a spec is implemented when it is `approved`,
  every consumer (each epic or task whose `specs` list names it) is
  terminal, and at least one consumer is `complete`. A spec with no
  consumer, or whose consumers are all `cancelled`, stays `approved` and
  `validate` warns "no delivering consumer". Spec criteria freeze at
  approval and change only by a new spec revision (R-32).
- R-52. Criteria are frozen at planning. A task PR cannot change its
  record's criteria; CI compares the criteria on the task branch with the
  target and blocks on any difference. A change is its own planning PR on
  the target; the task branch then rebases.
- R-53. Journey criterion. When a PR range touches an adopter-facing
  surface (the path set of R-114, created by TSK-104 and extended by
  TSK-106: the scaffold under
  `assets/`, hook sources, shipped templates, managed instructions, the
  CLI command surface, or a runtime adopters run, including the present
  runtime), the PR's task must carry a `(journey)` criterion or serve the
  epic's journey criterion. CI blocks otherwise. Such a range cannot be a
  direct change (R-71). A leaf that serves the epic's journey links the
  shared evidence that actually ran, or states the narrower path it
  verified; it never marks an unrun epic journey as verified.
- R-54. One acceptance block per completion lives in the record's Closeout
  (format in Interfaces). It names the reviewed commit, a recheckable
  review reference, one result line per criterion, the journey result,
  what was not verified, follow-ups or the reason there are none, and the
  verdict.
- R-60. `task status complete` and CI accept the block only when: every
  criterion of the record appears exactly once; every mandatory criterion
  is `verified`, or `waived` with a commit that exists on the target, is
  the planning amendment for that record and that criterion, and is not
  the PR head; the reviewed commit is the PR head, or an ancestor whose
  later diff touches only this record's status and Closeout; and the
  verdict is `approved`. Any other change after the reviewed commit
  invalidates the block. The checker proves structure and binding only and
  says so; it does not prove the evidence is honest, and the review
  reference is recheckable, not authenticated.
- R-61. A reviewer asks two questions and may reject on either: is each
  criterion supported by evidence on this source, and does the result
  achieve the outcome for the affected user. Converge (re-checking each
  criterion against the product when a discovery changes what the work
  can deliver, and again before the PR) is that second question, not a
  separate artefact.
- R-62. A criterion observable only after release records an owner, a
  measurement window and a follow-up task; it is never marked verified at
  build time.

### How work flows

- R-63. Research findings live under `docs/research/`, one file per
  question with its sources. A spec, ADR or epic that draws on them lists
  them in an `inputs` list. A record may cite a research file; a research
  file never carries status.
- R-64. A spike is a task with `work_type: spike` on a `spike/` branch. The
  anchored preflight runs for it. Its PR lands findings (files under
  `docs/research/` and its own record) and never product code; CI blocks a
  spike PR that changes anything else.
- R-65. Spec and epic are many to many, with one owner per link. An epic
  lists the specs it consumes in full or in part in its `specs` list; a
  task lists its own specs and inherits its epic's. A spec keeps no
  consumer list: its consumers are derived by every reader from the
  consumers' `specs` lists, so the two sides can never disagree. One spec
  may be consumed by several epics and one epic may consume several
  specs. An epic with no spec is valid; its own criteria carry acceptance.
  `spec new --for <id>...` accepts several consumers and writes the new
  spec id into each consumer's `specs` list in the same planning change.
- R-66. The standalone test is one rule in one place: a task may stand
  alone when its outcome is one reviewable PR. It records a
  `standalone_reason`, and may list capabilities and specs directly.
  Capabilities may list standalone tasks. A standalone task completed by
  more than one PR is a validator warning at closeout.
- R-67. Today's rules stay: exactly one epic or a standalone reason per
  task; dependencies resolve and are acyclic; specs approved before work
  starts.

### PR classification and light paths

- R-70. Every product PR into a tracked target has exactly one class,
  read from its body and range: tracked (`Task: TSK-NNN`), direct change
  (`Task: none: <reason>`), planning-only (the range touches only records
  under `project-management/` and plans under `docs/plan/`), or a trusted
  automation profile (R-81). An unclassified product PR blocks; never
  adjustable.
- R-71. A direct change is refused when the range touches
  `watched_contract_paths`, `.codeflow/policy.json`, hook sources,
  dependency manifests or lockfiles, the record schema, or an
  adopter-facing surface (the path set of R-114, created by TSK-104 and
  extended by TSK-106).
  Adopters may forbid direct changes entirely; they cannot narrow the
  refused set below this floor.
- R-72. The anchored preflight (the `work start` check) runs once per
  task in two planes: `work start` on any branch that carries a task id on
  a sanctioned prefix (the own-branch context of R-110), and CI for every
  tracked PR whatever its branch prefix. Pre-commit does not repeat it.
  Both planes apply the `git.work_planning` level: `block` by default, or
  `warn`; there is no `off`.
  (Amended 2026-09-27, planning resolution 19: the pre-commit plane is
  retired.)
- R-73. A follow-up is filed with `task new --follow-up-of TSK-NNN "title"`
  on a planning branch of the source task's target; it records
  `follow_up_of` and needs one plan PR with one reviewer.
- R-74. A leaf task is added with `task new --epic EPC-NNN "title"` and one
  reviewer. A new plan version with both review seats is required only
  when an existing node, edge, criterion, owner or safety boundary
  changes.
- R-75. A blocker is recorded on the task branch with
  `task status <TSK> blocked --reason --owner --revisit`; `status` reads
  the branch copy until it lands.
- R-76. Release stabilisation: the release task's criteria are the
  checklist; fix PRs name it with `Task:`; the task stays open until the
  checklist passes.
- R-77. `epic new --integration "title"` creates the epic record and its
  integration branch as today.
- R-78. A record cannot authorise itself: no PR may both add a task record
  and claim `Task:` for that task.

### Enforcement and customisation

- R-80. Each rule names its plane and level, and whether an adopter may
  change it once tracking is on:

  | Every added record reserved with its `uid` before merge; edited `uid` refused | CI | block | no |

  | Standard tier without records sees no record rule | test | pinned | no |

  A rule in the always-blocking row has no level; a rule in the
  never-exempt row keeps whatever level the project configured, and an
  explicit adopter `block` stays effective until its owner changes it.

- R-81. `git.work_records` accepts `block` or `warn` and nothing else.
  `codeflow update` preserves every policy value an adopter set, including
  values equal to a default.
- R-82. A trusted automation profile matches when the actor or app id that
  the workflow passes to `codeflow ci` and the branch pattern both match a
  configured profile. It skips branch naming and commit format, counts as
  its own classification, keeps tests, the secret scan, contract
  assessment and target-side policy, and never changes a policy level. PR
  sections stay evaluated at the configured level (R-80): the profile may
  name the sections its bot body omits and supply their content, and the
  check judges the body with that content; any other missing section
  fails at the configured level. Locally and on fork PRs the actor is
  "unknown": only the pattern match is reported and no exemption or
  supplied content applies.
- R-83. Migration: the new rules apply from a recorded migration baseline
  commit, by transition. A spelling edit to an old complete task warns;
  reopening it, changing its criteria or completing it again applies the
  new rules. A historical exception is bound to the record's exact blob,
  never to its id. Identity, relationship and planning errors are never
  grandfathered.
- R-84. Kept brownfield PR templates have four states, recorded in
  `git.pr_section_mapping`. Diagnosed: `init` or `update`, interactive or
  not, writes a proposed heading mapping, and `doctor` repeats the
  diagnosis on every run; no other check changes and no policy byte is
  overwritten. Accepted: the mapping is recorded and the check runs at its
  configured level against the mapped headings. Refused: the missing
  headings are appended to the template and the configured level applies
  to the shipped headings. Custom: the project sets its own section list in
  policy by a reviewed human change. An interactive `init` or `update`
  asks and records accepted, refused or custom before it reports setup
  complete; only a non-interactive run leaves the diagnosed state. Policy
  is never derived from a template silently.
- R-115. Effective level in the diagnosed state. While the mapping is
  diagnosed, the PR-section check evaluates the shipped headings at the
  effective level. A `pr_sections` value is explicit when the adopter's
  policy file already set it before this `init` or `update` run, whatever
  its value, including a value equal to the shipped default; an explicit
  value stays effective, with no new decision required. The level is
  implicit, and the check runs at `warn`, only when this run creates the
  policy file (a fresh install with no prior policy) and the mapping
  records no operator decision. Explicitness is read from the presence of
  the key in the prior policy file, never by comparing its value with the
  default. An installation whose prior policy provenance cannot be read
  keeps its configured level, and `doctor` reports the unresolved mapping.
  A diagnosed window ends at the
  first accepted, refused or custom decision, and `doctor` names the
  effective level, its origin (`configured`, `shipped default`,
  `diagnosed`) and the pending decision on every run. `codeflow ci` prints
  the effective level and origin of every check it runs. Tests assert the
  effective level and the preserved policy bytes for each state, for a
  first install with no prior policy, for an upgrade of an already
  mismatched repository, and for an upgrade whose policy sets
  `pr_sections` to `block`, equal to the default, which stays `block`.
- R-85. Upgrade order: new binary first, then `codeflow update`. Updated
  hook shims check the binary's capability before dispatch and fall back
  to the previous behaviour with a warning when the binary is older.
- R-113. The binary that enforces CI is chosen by the target. The
  scaffolded workflow installs the `codeflow` version pinned in the
  target-side scaffold state, never the head's, so a PR cannot lower the
  enforcing version while changing a protected surface. The pinned install
  verifies the release asset against the published checksum for that
  exact version and fails closed when the checksum is missing or does not
  match; it never falls back to an unverified download. An upgrade takes
  two pull requests, in order. The first raises only the pinned version;
  the target's binary enforces it, and the candidate binary is tested in a
  separate job. After that pin is on the target, the second carries
  `codeflow update` (new policy keys, schema and templates) and is judged
  by the new binary. A head that adds policy keys or schema the target's
  binary cannot read, while the raised pin has not landed, fails with a
  message that names the two-step order, not a bare unknown-key error.
  This message comes from binaries that implement this rule (3.0.0 on); an
  older binary still reports its own error. Operator decision after plan
  review round 2 (Codex R2-6), matching the upgrade order the 3.0.0
  CHANGELOG documents.
- R-114. One definition of the adopter-facing path set, which R-53 and R-71
  read. TSK-104 creates it, because it classifies PRs first: the current
  `watched_contract_paths` plus the fixed set `assets/`, hook sources,
  shipped templates, managed instruction blocks, the CLI command tree, and
  every runtime adopters run (including `crates/codeflow-present`). TSK-106
  extends it with the release contract paths: `watched_contract_paths`
  extended to the record schema, the CLI flag surface and policy keys.
  TSK-106 owns the behaviour-path set for R-93: every path outside `docs/`,
  `project-management/`, `docs/verification/` and the record templates
  counts as behaviour, and the skill trees count as behaviour because they
  change shipped agent behaviour. Both sets ship as fixtures that the
  journeys of R-104 use.

## Interfaces and formats

Registry file, `ids/<KIND>/<N>.toml`, where `KIND` is `EPC`, `SPC`, `TSK` or
`ADR` and `N` is the part of the id after the kind prefix, as written
(`ids/TSK/100.toml`, `ids/ADR/0068.toml`, legacy `ids/TSK/002-001.toml`):

```toml
id = "TSK-100"
uid = "8f6d0d1c-4a1e-4d2b-9c0e-2b7f2f9f3a11"
kind = "TSK"
title = "Registry proof on a real host"
issuer = "<git user.email at issue, or 'seed', or 'admit:<maintainer>'>"
created = "2026-09-26T10:41:02Z"
target = "integration/EPC-020-delivery-system"
introduced = "none"   # seed: "<sha>@<ref>" of the first commit that added the record
landed = "none"       # seed: "<sha>" of the first commit on a stable target, or "none"
mapped = []           # seed --map: introducing shas of copies mapped to this record
mapped_by = "none"    # seed --map: "<maintainer> <date>", or "none"
```

Every field is required; `target` is the intended integration target at
issue and is informational after that. A file is never edited after it is
added, except by a typed restore (R-108) that returns it to these bytes.
The only commits on the branch are the seed root, issues, admissions and
typed restores.

Record frontmatter gains `uid` (UUIDv4, required after backfill),
`former_ids` (list, written by retarget), `follow_up_of` (one task id),
`work_type` (`spike` among the existing values), `inputs` (list of paths
under `docs/research/`, on specs, ADRs and epics), `standalone_reason` (as
today), `awaiting_selection` (one path, on a join task; R-43), and on specs
`supersedes` (list) and `superseded_by` (one id; R-32). Epics and tasks own
the `specs` list; a spec carries no consumer list (R-65). A `depends_on`
entry is a bare task id (code dependency) or an object
`{id: TSK-NNN, kind: research | decision, pin: <sha>}` (R-112).

Criterion line grammar: `- AC-<n> When <condition>, the system shall
<behaviour>[ (serves EPC-NNN AC-m)][ (journey)]`. A journey criterion's
behaviour names one of: fresh init, update, installed CLI, present runtime,
release artefact.

Acceptance block, a fenced `yaml` block under `## Closeout`:

```yaml
acceptance:
  reviewed: <full commit sha>
  review: <PR review URL, or session:<id>@sha256:<transcript digest>>
  criteria:
    AC-1: verified | <command and result, or file:line>
    AC-2: waived   | <planning commit sha on the target>
    AC-3: failed   | <what failed>
  journey: verified | <path exercised>
  not_verified: <list, or none>
  follow_ups: <TSK-NNN, ...> | none: <reason>
  verdict: approved
```

A superseded block keeps its content under `acceptance_superseded:` with the
reopen reason.

PR body classification line, in the Summary section: `Task: TSK-NNN` or
`Task: none: <reason>`. A planning-only PR needs no line; an automation
profile PR carries none.

Blocker section, required when `status: blocked`:

```
## Blocker
- reason: <text>
- owner: <person or role>
- revisit: <event, such as "TSK-101 lands" or "plan v3 approved">
```

Policy keys added to `git`: `work_records` (`block` | `warn`, default
`block`); `automation_profiles` (list of `{name, actors: [<actor or app
id>], branch_pattern, sections: {<heading>: <content>}}`, where `sections`
supplies content for the PR sections the bot body omits (R-82); default
empty); `pr_section_mapping` (`{state:
diagnosed | accepted | refused | custom, headings: {<required>: <actual>},
decided: <date or none>}`, absent by default; R-84, R-115). Project config
gains `release.backend` (`none` | `external` | `codeflow`, default `none`)
and `work_records_baseline` (the migration baseline commit).
`watched_contract_paths` is extended to the record schema, the CLI flag
surface and policy keys (R-114).

CLI surface added or changed: `ids seed [--map <file>] | backfill | sync |
admit | retarget | restore | check`; `work claim`; `work next --json`;
`task status` with `--reason --owner --revisit`; `task new --follow-up-of`;
`task new --resume`; `epic new --integration`; `adr new`; `spec new --for`
with several ids; `remote protect` with the data profile; `codeflow ci`
with an actor input and an effective-level report (R-115).

Journey names and the adopter-facing surfaces (R-53) are the path set of
R-114, created by TSK-104 and extended by TSK-106.

## Edge cases

- A push whose acknowledgement is lost: after another issuer pushes, our
  reservation commit is an ancestor, not the tip; read-back checks that the
  tip reaches a commit binding N to our `uid` (R-13). A replay may change
  the commit sha and keep the binding.
- A deleted or edited reservation file on the tip: the number is not
  reissued (R-7); issue refuses repository-wide until a typed restore lands
  (R-9, R-108); the original content is recoverable from history. A
  commit that removes many files stops issue in the same way and is
  repaired by one restore naming them all.
- A legacy record before its line's backfill: CI reads the registry file
  by id and judges a record with no `uid` by its `introduced` and `landed`
  provenance (R-111). After the backfill this path is unused.
- A join awaiting selection: a valid record with an empty `depends_on`,
  `awaiting_selection` set and a Blocker; no context of R-110 starts it,
  and a task branch cannot land the selection (R-43).
- Two clones offline take the same number: sync detects the different
  `uid` and retargets the later one; nothing lands with a duplicate.
- Two integration lines add the same number with different `uid`s: the
  merge rule refuses the second at its PR, because N is already bound.
- A fork PR admitted, then the registry moves before merge: the binding is
  to the `uid`, so a later issuer cannot take N; the PR merges.
- A host without branch rules rewinds the registry: issue refuses against
  the last verified tip (R-10); `doctor` reports reduced assurance.
- A join whose alternatives are all cancelled: it stays blocked awaiting
  selection until a reviewed selection or a cancellation of the join.
- A task with a Blocker and an active branch: reported as blocked, not
  active; `work next` shows it under blocked.
- A `Task: none` PR that touches an adopter-facing surface: refused as a
  direct change with the instruction to name the release task or a task.
- A spike PR that changes product code: blocked (R-64).
- A record with `status: implemented` written by hand on a spec created
  after this spec lands: refused; on an older spec: read as before, and
  `validate` warns when it disagrees with the computed state.
- `work next` on a stale clone: the printed snapshot lets the reader judge
  the freshness; a task claimed after that fetch is not excluded.
- `codeflow update` on a repository whose `git.work_records` is `off` from
  an unreleased build: rewritten to `warn` with a notice; every other
  value is preserved.
- A registry push from CI: not permitted; the registry job only reads.
- An abandoned `ids admit`: the number stays reserved to that `uid` and is
  never reissued; the gap is reported by `ids check` as a gap, not damage.
