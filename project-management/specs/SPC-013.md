# SPC-013: Delivery system for parallel agents

## Summary

This spec pins the behaviour that lets several agents plan, claim, build and
land tracked work on parallel lines without colliding on ids, on status words
or on acceptance evidence. It is the contract the delivery-system tasks
implement and the reference a reviewer tests each task against.

### How to read it

- Rationale lives in the successor ADR to ADR-0046, and the delivery
  process this spec serves in ADR-0076; the plan and its sizes live in the
  epic.
- Requirements are numbered R-1 onward so tasks and reviews can cite them.
  Numbers leave gaps between sections so a revision can insert a
  requirement without renumbering. Requirements added after plan review
  round 1 are numbered R-108 onward and sit in the section they belong
  to; no requirement is renumbered.
- A requirement holds when durable work tracking is on (the existing
  `durable_work_tracking_enabled` switch), unless it says otherwise.
- "Block" and "warn" name the level a plane applies; "never adjustable"
  means an adopter cannot relax the rule once tracking is on.

## Delta against current capability

ADDED: a shared id registry on a protected data branch with an issue
protocol; a hidden `uid` on every record; status verbs with transition rules;
one readiness predicate; an advisory claim command; criterion ids, frozen
criteria and one source-bound acceptance block; total classification of
product PRs; a work-flow model with research inputs, a spike path and
many-to-many spec and epic links; a computed spec state; trusted automation
profiles; `release.backend`; a file-state grader for behavioural evals.

MODIFIED: id allocation moves from the maximum visible in one checkout to the
registry's whole history plus every ref; task, epic and spec status move from
hand edits to verbs judged by one validator; readiness moves from
`status --delivery`'s partial view to the shared predicate; criteria move
from ticked checkboxes to listed criteria with results in the acceptance
block; the anchored preflight runs for tracked work on any branch, not only
`task/` branches; kept brownfield PR templates get an explicit mapping
instead of a failing check; project record templates are read.

REMOVED: `in_progress` as a written status (it stays readable); the ledger's
producerless work-graph event types; the quick standalone record path; the
`off` level for `git.work_records`; the checkbox as the carrier of a
criterion's result on new records; the direct-change class `Task: none`
(ADR-0076).

## Behavior

### Identity

- R-1. Every record carries two identities. `id` is the readable sequential
  id (`EPC-NNN`, `SPC-NNN`, `TSK-NNN`, `ADR-NNNN`) used in filenames, branch
  names and links, as today. `uid` is a UUIDv4 written once into frontmatter
  by `new` and shown in no ordinary view. Legacy `TSK-NNN-NNN` ids stay
  valid and are never renumbered.
- R-2. Two copies with the same `uid` are the same record (a replica). Two
  records with the same `id` and different `uid`s are a collision. The
  validator rejects an edited `uid` on an existing record and a `uid` that
  differs from the registry's binding for that id.
- R-3. Every record created before this spec lands receives a `uid` from
  the seed (R-24) and the backfill (R-25). After the backfill lands on a
  line, no record on that line is exempt from the `uid` checks.
- R-4. The `uid` is an integrity check. It does not replace number
  coordination and does not prove what a record means.

### The registry

- R-5. Each repository that tracks work has one registry: the branch
  `codeflow/registry` on the authority remote, `origin` by default. It holds
  one file per issued id at `ids/<KIND>/<N>.toml` (format in Interfaces).
  Numbers are scoped to their repository.
- R-6. The registry is a data branch with its own profile. It is not in
  `protected_branches`, has no pull-request requirement, skips branch naming
  and the product test gate, and never triggers `ids sync` recursively.
  `codeflow remote protect` applies the data profile to it (no branch
  deletion, no force push) and leaves the rules of `main` unchanged. A
  maintainer creates and seeds the branch once; CI never needs write access
  to it.
- R-7. Allocation reads history. The next number for a kind is one more than
  the greater of: the highest number ever added under `ids/<KIND>/` in the
  registry's history, and the highest id of that kind on any local or
  remote-tracking ref. Deleting or editing a file on the tip never lowers it.
- R-8. The registry only grows. Every commit in a pushed range either adds
  new files under `ids/` and does nothing else, or is a typed restore
  (R-108). Pre-push checks the whole range and git-guard checks the
  command; both block. The registry check (R-109) re-validates the whole
  history and reports any commit that removes or modifies a file outside a
  typed restore.
- R-9. The registry is currently damaged when any path ever added under
  `ids/` is absent from the tip or differs from the content it had when
  first added. The CLI runs this check on the fetched history before every
  issue and refuses to issue while it fails. A commit that caused damage
  that a later restore repaired is historical damage: it stays in history,
  is reported as history by `ids check`, and does not block issue or CI.
- R-108. Typed restore. `ids restore <id>...` writes one commit whose only
  changes re-add or revert the named `ids/` files to the bytes of their
  first addition in history, with the subject `restore: <ids>`. Pre-push,
  git-guard and the registry check accept a commit as a restore only when
  every path it touches was previously added, every path's new content is
  byte-identical to its first addition, and the commit adds nothing else.
  A restore that would bind a number to any other `uid` is refused. Issue
  and CI return to healthy as soon as the tip passes R-9; no other state
  is kept. Restore is a maintainer operation with push rights to the
  registry; CI never runs it.
- R-109. Bootstrap and the registry check. `ids seed` creates the branch as
  an orphan whose root commit adds only `ids/` files; that root commit is
  validated by the same rule as every later commit. The registry branch
  holds no workflow, script or other code, so no job runs from it. The
  registry check is `codeflow ids check` run by the code branch's CI: for
  every pull request, every push of a tracked target, and on a daily
  schedule from the default branch; for a pull request it also applies the
  merge rule of R-14 to the PR's range. The enforcing job runs on
  `pull_request_target`, so GitHub takes its workflow definition from the
  default branch and a PR cannot edit, skip or replace the check that
  judges it; the job checks out the PR's base commit, so the target's pin
  and policy apply. It reads the PR head only as git data, never checks
  out, builds or runs PR code, and runs with a read-only token and no
  secrets. Build and test jobs
  stay on `pull_request`. Its code is the `codeflow` binary the target
  pins (R-113); a PR cannot select the binary that checks it. The
  check needs no registry write scope. Seeding is idempotent: a rerun on an
  existing branch adds only ids not yet registered and changes nothing.
  (Amended 2026-09-26 after the TSK-100 host proof: under `pull_request` a
  PR that rewrote the check step went green on a damaged registry.)
  (Amended 2026-09-27, planning resolution 20: GitHub runs a
  `pull_request_target` workflow from the default branch, not the target
  branch, so the job checks out the base commit; TSK-107 review round 2,
  R2-1.)
- R-10. On a host without branch rules, the CLI keeps the last verified tip
  of `origin/codeflow/registry` in untracked local state and refuses to
  issue when the fetched tip does not descend from it. `doctor` reports
  reduced assurance for that repository.
- R-11. Fetches of the registry are never forced. The local
  `codeflow/registry` branch holds pending reservations and is kept apart
  from `origin/codeflow/registry`.

### Issue, merge and admission

- R-12. `new` for an epic, spec, task or ADR issues its id by this protocol,
  in order: fetch `origin/codeflow/registry` (non-forced); compute N by R-7;
  commit `ids/<KIND>/<N>.toml` with a fresh `uid` on top of the fetched tip;
  push that commit to `refs/heads/codeflow/registry`, never forced; then
  write the record with exclusive create, carrying the reserved `uid`.
- R-13. Push outcomes are classified, never collapsed into "taken":
  accepted means reserved; rejected because the tip moved means fetch,
  recompute N and retry, at most five attempts, then stop with the reason;
  a permission, unsupported-operation or transport error is reported as
  that error; an unclear result is resolved by fetching and reading back:
  reserved when the fetched tip reaches a commit (or a replay) that binds N
  to our `uid`; offline means a commit on the local `codeflow/registry`
  under a local lock, reported as "pending, not unique yet".
- R-14. The merge rule: every record added in a PR must be reserved in the
  authority's registry, bound to that record's `uid`, before the PR can
  merge. CI checks the binding against the fetched registry on every run.
  Block; never adjustable.
- R-15. `ids sync` publishes pending reservations. It runs before any online
  write and in pre-push. It replays each pending file on the fetched tip;
  the same `uid` already bound to N counts as reserved; a different `uid`
  bound to N stops sync and names `ids retarget`. In pre-push, sync warns
  and continues when the authority is unreachable or is not the push
  target; it blocks only on a number held by a different `uid`.
- R-16. `ids retarget <id>` renumbers an unmerged record to the next free
  number, rewrites its in-tree links, and records the old id in
  `former_ids`. It refuses a record already landed on a stable target.
- R-17. `ids admit <record path or PR>` reserves the number for a fork or
  hand-written record's `uid`, or, when that number is held, the next free
  number with an instruction to retarget. Only a maintainer with push
  rights to the registry runs it; untrusted PR code never receives write
  credentials. The PR stays red until admitted. An abandoned admission
  leaves a gap; a number is never reissued.
- R-18. `new --resume <id>` completes a crash between reserve and write. It
  writes the record when the reservation's issuer and `uid` match the
  caller's pending state, and refuses otherwise.
- R-19. When a repository with no remote gains an authority, `ids sync`
  merges by file. A clash on a record not yet landed is retargeted. A clash
  on a record already landed on a local stable target stops with an
  explicit authority migration that records the disposition; it never
  renames silently.
- R-20. CI fetches `codeflow/registry` explicitly with its full history, on
  shallow and single-branch checkouts too. Read commands never fetch.
- R-21. `ids check` validates the registry (R-8, R-9) and reconciles it with
  the record inventory on every ref; `doctor` reports the result and any id
  it cannot place.
- R-22. `codeflow remote protect` gains the data profile for the registry
  branch. Applying it to a host is proved end to end before the rest of the
  registry ships: the host proof in TSK-100 exercises the exact arrangement
  of R-109 (orphan data branch, no workflow on it, the check run from the
  code branch's CI) and the journeys named in R-104.

### Claims

- R-23. `work claim <TSK>` runs the readiness predicate in its new-claim
  context (R-40, R-110) and the anchored preflight against the fetched
  target tip, creates
  `task/TSK-NNN-<slug>` from that tip and pushes it. The pushed branch is
  the visible mark of a claim. It is advisory: no document calls it a lock,
  and no command depends on it being exclusive. Two visible branches
  carrying one task's id are reported by `status` as a conflict. With
  `--on TSK-NNN@<sha>` the branch is created from the reviewed pin instead
  of the target tip, after the claim-phase checks of R-42. Run on a branch
  that already holds a new standalone record at HEAD (R-78), `work claim`
  renames that branch to `<prefix>/TSK-NNN-<slug>` and pushes it
  create-only, since the target does not yet hold the record. (Amended
  2026-09-29 by TSK-184, ADR-0076.)

### Seed and backfill

- R-24. `ids seed` reads every id on every ref and in retained history,
  decides which copies are one record by their first introducing commit
  (and, where squash or cherry-pick hides that, by their first landing on a
  stable target), assigns each record one `uid`, writes one registry file
  per id with its provenance (R-111), and reports any id it cannot place.
  It is idempotent: a rerun adds nothing for an id already registered.
  CodeFlow's registry continues at EPC-020, SPC-013, TSK-100 and the next
  ADR number.
- R-111. Legacy ids and provenance in the registry. A legacy
  `TSK-NNN-MMM` id is registered at `ids/TSK/NNN-MMM.toml`; its `id` field
  is the legacy id and its `kind` is `TSK`. Legacy ids never contribute to
  the high-water mark of R-7, and a canonical `TSK-NNN` is a distinct id
  from every legacy `TSK-NNN-MMM`. Every seeded file records `introduced`
  (the first commit that added the record, with the ref it was read from)
  and `landed` (the first commit on a stable target that holds it, or
  `none`); an issued file records `introduced = none` and `landed = none`.
  Identity is the commit sha only: the ref in `introduced` is provenance
  metadata, and an absent value (`none`) matches nothing, so two records
  that are both unlanded are never replicas by `landed`. Seed decides
  replicas from a nonempty matching `introduced` sha or a nonempty matching
  `landed` sha only. When no such match identifies two copies as one
  record (squash or cherry-pick with differing content), seed stops and
  names the ids; the maintainer supplies an explicit mapping with `ids
  seed --map <file>`. Seed writes each mapped copy's introducing sha into
  the registry entry's `mapped` list, with the maintainer and date in
  `mapped_by`, so every later reader, CI and a replayed seed included,
  reproduces the mapping from the registry alone; the verification record
  also cites the map. Seed never infers that two copies are one record
  from a matching number alone. Only live copies decide: while some ref's
  tip holds the id, a copy read only from a line's history, because that
  line later deleted the record or renumbered it to another id, takes no
  part; when no tip holds the id, every copy counts. A live copy's
  introducing commit is the start of its own lifetime, not the first add
  of its id: going back from the tip along the history of the id's record
  paths, the lifetime continues while some record path holds the id, so a
  move under the same id keeps it, and it ends where the id was absent,
  including a removal made by a merge. Across such a gap it continues only
  when the content that returns is identical to the content before (a
  revert, or a round trip through a path that is not a record path). A
  merge result that holds the id at a record path none of its parents
  holds adds the id like any other commit, under the same rule. Seed, the
  reconcile check and the merge rule all use this introduction, so an
  older add of the id that an ended record owns never binds a different
  record. The introduction needs the complete code history: in a shallow
  clone, seed writes nothing and the check fails, both naming
  `git fetch --unshallow`, and no reader takes a shallow boundary commit
  for an introduction. (Amended 2026-09-27: TSK-079, renumbered by hand to
  TSK-084 on the EPC-016 line before the registry existed, left its old
  add in that line's history and stopped the seed with no correct path,
  since a map would have joined two different records; review round 1 of
  the fix found the first-add rule also misnamed and admitted a record
  that reused an ended record's id; review round 2 found that a record
  added by a merge result escaped the rule, and that a shallow clone
  seeded a boundary edit as the introduction.) Before a line's backfill,
  CI judges a
  record without a `uid` against the registry entry: its introducing sha
  equal to `introduced` or to an entry of `mapped`, or its nonempty landing
  sha equal to a nonempty `landed`, means a replica; otherwise a
  collision.
- R-25. `ids backfill` writes the registered `uid` into each existing
  record on the current line whose frontmatter lacks one. It never
  generates a `uid`, never changes an existing one, and refuses a record
  whose id has no registry entry. Each line's backfill lands in that line's
  cleanup PR.

### Recorded and derived facts

- R-26. Recorded facts, written by a person, an agent or a verb: `id`,
  `uid`, title, outcome, criteria with ids, `depends_on`,
  `integration_target`, one epic or a standalone reason, specs,
  `follow_up_of`, `external_refs`, `work_type`; task status among `todo`,
  `blocked`, `complete`, `cancelled`; the Blocker (reason, owner, revisit
  event); the cancellation (reason and where the scope went); the
  acceptance block; epic terminal acts `complete`, `cancelled`, `archived`;
  spec status `draft`, `approved` or `superseded`, with `supersedes` and
  `superseded_by` links; a join's `awaiting_selection` reference (R-43);
  the kind and pin of each dependency edge (R-112).
- R-27. Derived facts, computed by every reader from git and the graph and
  written nowhere: active (a visible branch carrying the task id, on any
  sanctioned prefix, `<prefix>/TSK-NNN-<slug>`, not landed);
  ready (R-40); waiting (`todo` with an unmet dependency, shown apart from
  `blocked`); landed (branch tip is an ancestor of the target, or
  patch-equivalent by `git cherry`); epic progress (counts of its tasks);
  release membership (the changelog and the published baseline); spec
  `implemented` (R-51).
- R-28. `in_progress` stays readable. No verb writes it. `validate` warns
  on an `in_progress` task with no active branch.
- R-29. The ledger's work-graph event types that have no producer are
  retired; no route accepts them.

### Lifecycle and writers

- R-30. Task transitions: `todo` to `blocked` (needs reason, owner and
  revisit event); `blocked` to `todo`; `todo` to `complete` (needs an
  acceptance block that passes R-60); `todo` or `blocked` to `cancelled`
  (needs reason and scope disposition in the Closeout); `complete` to
  `todo` on reopen (needs a reason; the old acceptance block is marked
  superseded and kept). Any other transition is refused. A pull request
  may carry a reopen and a re-completion together (R-119).
- R-31. A partial or stacked PR leaves the task `todo`; the last slice
  completes it.
- R-119. One-PR fix of a complete task. A pull request that names a
  complete task may carry its reopen and its re-completion in one range.
  The range keeps the old active block under `acceptance_superseded:`
  with the reopen reason (R-30), compared with the block on the anchored
  target, and adds a new acceptance block. The anchored preflight (R-72)
  and `work start` accept a complete task whose branch carries that
  reopen as they accept a `todo` task. Every range that reopens and
  completes a task again is judged as a reopen plus a completion and
  bound explicitly, even when the new active block equals the old one.
  R-60 therefore binds the new review to this fix range, without carrying
  an earlier landing's review or a line merge after it, and keeps its
  criteria frozen even when the range changes records only: the own-task
  amendment of R-52 never applies to a range that reopens, and a reopened
  task's criteria change rides in the epic's batched amendment.
  Rejection is deterministic in `task status` and CI, never left to the
  reviewer. A separate reopen PR stays valid, and a range that reopens
  without completing again leaves the task `todo` (R-31). (Added
  2026-09-27, planning resolution 20; binding tightened after plan
  review round 1; the own-task amendment excluded 2026-09-29 by TSK-184.)
- R-32. Spec lifecycle, the only table:

  | From | To | By | Condition |
  |---|---|---|---|
  | `draft` | `approved` | planning PR on the target | no open question |
  | `approved` | `superseded` | planning PR that adds a new spec revision | the new spec lists `supersedes: [SPC-old]`; the old spec gets `superseded_by: SPC-new` in the same PR; acceptance that cited the old spec's changed criteria is invalidated |
  | `approved` | `implemented` (derived) | no writer | R-51 |

  `approved` never returns to `draft`. Until the spec is `implemented`, a
  changed contract is amended in place in a reviewed planning-only change:
  the epic's batched amendment (ADR-0076). A change of meaning gets a dated note naming its planning
  resolution, and the superseded decision stays visible as history; an
  editorial change that keeps the meaning needs no note but still lands in
  a reviewed planning change. That planning change names each consumer
  bound to a changed requirement (one whose criteria or acceptance cite
  it) and its disposition: unaffected, criteria amended in the same change
  (R-52), or reopened (R-30). Once `implemented`, the spec is frozen and a
  changed contract is a new spec. (Amended 2026-09-28, planning
  resolution 25.) `codeflow ci` refuses a change to a spec's text in a
  range that is not planning-only, at the `git.work_records` level; the
  frontmatter fields the commands write are judged by the rules above.
  (Amended 2026-09-28, planning resolution 27.)
  `implemented` is derived and refused as a written value on records
  created after this spec lands; existing records that carry it are read
  as before. `spec status` writes only `approved` and `superseded`.
- R-33. Epic close requires every task terminal, every epic criterion
  verified, every journey criterion verified on the named journey, and
  every consumed spec either implemented in the candidate state or listed
  as still consumed by another open consumer. The candidate state is the
  derived spec state computed with the closing epic counted as `complete`.
  A cancelled child never satisfies the epic's outcome: an epic criterion
  served only by cancelled tasks is unverified until the epic's own
  acceptance block proves it under the rules of a criterion no task serves
  (verified with its evidence, or waived with its planning commit, and the
  journey verified for a journey criterion); a ticked checkbox never proves
  it. The epic's own block, for either kind of criterion, binds as a
  task's does (R-60) in `epic status`, CI and the release judge: its
  reviewed commit exists, only the epic's status and Closeout change after
  it, and a waiver names a planning-only commit that amends that criterion
  of the epic and that the reviewed commit contains. `complete` to
  `archived` needs no further check. (Amended 2026-10-03 by TSK-214,
  sathyassn/codeflow#25: the cancelled-only criterion had no sanctioned
  close, and the own block's review and waivers were never bound. Bound
  consumers: TSK-102 AC-4, criteria amended in the same change.)
- R-34. The verbs and what they write:

  | Verb | Writes | Checked |
  |---|---|---|
  | `epic new [--integration]`, `spec new`, `task new --epic \| --standalone-reason \| --follow-up-of`, `adr new` | registry file, record with `uid` | R-12; the epic and target resolve on their own line; the record is written on a planning branch of that target, except a standalone task's, which may be written on its own task branch (R-78) |
  | `work next [--epic] [--json]` | nothing | R-40, R-41 |
  | `work claim <TSK> [--on TSK-NNN@<sha>]...` | task branch, pushed | R-23, R-42 |
  | `work start <TSK> [--on TSK-NNN@<sha>]...` | nothing | today's preflight plus R-42 |
  | `task status <TSK> todo\|blocked\|complete\|cancelled [--reason --owner --revisit]` | status, Blocker, Closeout marks | R-30 |
  | `epic status`, `spec status` | status | R-32, R-33 |
  | `ids seed \| backfill \| sync \| admit \| retarget \| check` | registry, pre-merge renumbering | R-8 to R-25 |

- R-35. The verbs are safe editors, not the only writers. The same core
  validator judges every edit, from a verb, a hand edit or a PR range. A
  verb detects a concurrent edit of the record by content digest and
  replaces the file atomically.
- R-36. `adr new` allocates `ADR-NNNN` through the registry and renders the
  ADR template with `status: proposed`.
- R-37. `new` works at every tier. Project record templates under
  `project-management/templates/` are read and validated before use, with
  the embedded templates as fallback. Shipped templates contain no policy
  character.

### Readiness

- R-40. The core readiness predicate holds for a task when all of these
  hold: status `todo`; no Blocker; no `awaiting_selection` reference
  (R-43); every consumed spec `approved` or derived `implemented`; its
  epic open (or the task standalone); every code dependency accepted and
  present in the execution base, or, for `work claim` and `work start`
  only, named by a reviewed pin (R-42); every research or decision dependency
  accepted at its pinned ref (R-112). `work next`, `work claim`, `work
  start`, `status` and CI share this one core and add only the caller
  context of R-110.
- R-110. Caller contexts of the readiness predicate. Three contexts share
  the core of R-40 and differ only in how the caller's own branch and the
  status transition are judged:

  | Context | Callers | Adds to the core |
  |---|---|---|
  | New claim | `work next`, `work claim`, `status` (ready list) | no visible branch carrying the task id on any sanctioned prefix on the fetched remote; the execution base is the fetched target tip |
  | Own task branch | `work start` | the task is the id the checked-out branch carries, `<prefix>/TSK-NNN-<slug>` with any sanctioned prefix (`task/`, `fix/`, `feat/`, `spike/` and the rest of `branch_prefixes`); that branch is not counted as a competing claim; any other visible branch carrying the id is reported as a conflict and does not refuse; the core, status included, is read at the merge-base with the target, except for a standalone task whose record is absent there and present at HEAD with `epic_id: null`, a `standalone_reason` and this branch's id (R-78), which is read at HEAD; a staged or committed status transition of this task is judged by R-30 and R-60 as in the PR-transition context; a branch that carries no task id has no own-branch context |
  | PR transition | CI on a tracked PR | the task is the PR's `Task: TSK-NNN` line; when the head branch carries a different task id, CI blocks the mismatch; the core is evaluated at the anchored base (the merge-base), not at the head; the head may carry one status transition of R-30 for this task, judged by R-30 and R-60, or the reopen and re-completion of R-119; a second visible branch carrying the id is reported, not refused; for a standalone task whose record this PR adds (R-78), CI runs the structural checks of the core (identity, target, standalone rationale, approved specs, dependencies, registry) on the record at the reviewed commit and then the acceptance binding at head, and does not apply the start gate (status, Blocker, `awaiting_selection`), so the record may arrive `complete` with a valid acceptance block |

  A task that is `complete` or `cancelled` fails every context, except a
  complete task whose branch or pull request carries the reopen of R-119
  in the own-branch and PR-transition contexts, and the standalone record
  CI admits at completion in the PR-transition context. The status,
  Blocker and `awaiting_selection` terms of the core are the start gate:
  `work start` applies them, and CI admission of a standalone record does
  not. (Amended 2026-09-27, planning resolution 20, to agree with R-119;
  amended 2026-09-29 by TSK-184, ADR-0076, for the standalone one-PR
  task.) The full
  positive journey (claim, start, build, complete, CI green), the same
  own-branch journey on `fix/`, `feat/` and `spike/` branches carrying the
  task id, a competing-branch negative control and a mismatched-association
  negative control (a PR whose `Task:` line names another task than its
  branch) are proof obligations (R-104).
- R-41. `work next` lists ready tasks first, then waiting and blocked tasks
  with their reasons; includes standalone tasks; excludes tasks with a
  visible branch carrying their id (R-110); and prints the remote tip and fetch time of the
  snapshot it judged from. `--json` returns the same facts.
- R-42. Cross-line dependencies: a predecessor complete on another line is
  accepted there, not available here. For a code dependency, `work start`
  refuses until the accepted change is in this task's execution base by
  merge or by an explicit reviewed port. The execution base is the fetched
  target tip for `work next` and the merge-base of the task branch with
  its target for `work start` and CI. An unfetched line is reported as
  unknown, never as satisfied.

  A later task may build on a predecessor's reviewed head before that
  predecessor lands. `work claim` and `work start` accept a code
  dependency whose predecessor is reviewed but not complete only when the
  caller names that head with `--on TSK-NNN@<sha>`, one per such
  dependency. In both verbs every pin must be the commit a review of the
  predecessor names (its PR Reviews row or its acceptance block), lie on
  the predecessor's task branch, and still equal that branch's tip; a
  predecessor advanced after review refuses with "rebase on its new
  reviewed head and recheck". `work claim` checks no ancestry of its own
  HEAD, which cannot contain the predecessor: it checks the prospective
  base before creating anything and creates the task branch from it. The
  base is the one pin, or with several pins the pin that contains every
  other; pins that are not ancestors of one another refuse with "no
  reviewed base contains all pins; land or stack one first", never a
  silent choice. `work start` checks that every pin is an ancestor of the
  actual HEAD. Matching a pin is structural and does not authenticate the
  review's verdict. CI keeps the rule above: when the task lands, each
  code predecessor must be complete in the merge-base, so a stack lands in
  order and no unlanded predecessor is marked complete. (Amended
  2026-09-29 by TSK-184, ADR-0076.)
- R-43. Guarded plans: only the selected branch of a decision is written
  into `depends_on`. Until the selection is approved on the target, the
  join task carries `awaiting_selection: <plan or decision path>` in
  frontmatter, is `blocked` with reason "awaiting selection" and that
  reference as its revisit event, and may have an empty `depends_on`. The
  validator requires the referenced path to exist on the target and treats
  the task as a valid record that no context of R-110 can start. A join
  with an empty `depends_on` and no `awaiting_selection` is a root task.
  The approved selection lands by a planning PR that removes
  `awaiting_selection`, writes the selected dependencies and unblocks the
  join; a selection cannot land on a task branch. A cancelled, unselected
  alternative never blocks a join.
- R-112. Dependency edges carry a kind and, for non-code kinds, a pin. An
  entry of `depends_on` is either a bare task id, which is a code
  dependency, or an object `{id: TSK-NNN, kind: research | decision,
  pin: "<commit sha>"}`. The pin is written quoted. Unquoted, an id that
  YAML resolves to a number, such as digits with no leading zero
  (`70283613`) or an exponent shape in range (`949894e0`), is refused with
  a remedy that says to quote it, never read back; an id YAML keeps as
  text, such as `07028361` or `0123abcd`, reads quoted or not (Amended
  2026-09-28 by TSK-156's planning; wording made precise after its build
  probe). A code dependency is satisfied when the predecessor is
  `complete` and its accepted change is in the execution base (R-42). A
  research or decision dependency is satisfied when the predecessor is
  `complete` and `pin` names a commit that exists on the predecessor's
  target and holds the predecessor's record as `complete`; the planner
  writes the pin when it becomes known, and a research or decision entry
  without a pin is unmet. One predecessor may
  be a code dependency of one consumer and a research dependency of
  another. The kind is never inferred from the predecessor's `work_type`.
- R-44. `status` stops calling a live integration branch removable; it
  reports removable, dirty and unproven entries as local git evidence.
  `orient` prints a task summary from the same predicate.

### Acceptance

- R-50. Criteria on new records are listed lines of the form
  `- AC-n When <condition>, the system shall <behaviour>` with no checkbox.
  Ids are `AC-n`, unique within the record and never renumbered. A task
  criterion that serves an epic criterion ends with
  `(serves EPC-NNN AC-m)`. A journey criterion ends with `(journey)` and
  names the path exercised: fresh init, update, the installed CLI, the
  present runtime, or the release artefact. Legacy records keep their
  checkboxes and are read as before. A tag, `(journey)` or `(after
  release)`, is read where it opens or closes the criterion; a period,
  comma, semicolon or colon after a closing tag does not hide it, and a
  tag inside the text is not a tag. (Amended 2026-09-27 by TSK-155's
  planning: the checker already read an opening tag, and TSK-152 AC-4
  closes with `(journey).`.)
- R-51. Spec `implemented` is computed, and this is the only
  cancelled-consumer rule: a spec is implemented when it is `approved`,
  every consumer (each epic or task whose `specs` list names it) is
  terminal, and at least one consumer is `complete`. A spec with no
  consumer, or whose consumers are all `cancelled`, stays `approved` and
  `validate` warns "no delivering consumer". Spec criteria are settled at
  approval and change only as R-32 states: in place through a planning
  change that names each bound consumer's disposition before the spec is
  implemented, by a new spec after. (Amended 2026-09-28, planning
  resolution 25.)
- R-52. Criteria are settled at planning. A task PR may change its own
  record's criteria: CI computes the change against the target (removed,
  added and changed text) and prints it for the reviewer, who approves it
  with the code; a removed criterion carries a one-line reason in the PR
  body; the completion stays bound to the reviewed commit at head (R-60).
  Every other record's criteria stay frozen: CI compares them with the
  target and blocks on any difference, and another task's criteria change
  by that task's own PR or by the epic's batched amendment. The own-task
  change applies to a task that is not complete at the target; a reopened
  task keeps its criteria (R-119). On a release range (R-120) criteria are
  frozen for every direct change of any class; an amendment reaches a
  release range only brought from a line where a planning PR or the
  task's own reviewed PR landed it (R-120). (Amended 2026-09-29 by
  TSK-184, ADR-0076: the own task's criteria change rides in its PR;
  reconciled with R-119 and R-120, planning resolution 41 of the process
  round.) The epic's batched amendment is a planning amendment that names
  every epic whose records it changes (R-70): it may change the criteria
  of any task of a named epic, and CI reports each change per epic, with
  its delta, for the reviewer. A criteria change to a task complete at
  the target and at the head is flagged, since its acceptance block was
  reviewed against the earlier criteria (R-119). A release range brings an
  amendment's criteria change as a planning landing when that landing
  passes the path rule of R-70. (Amended
  2026-10-03 by TSK-229, ADR-0078, sathyassn/codeflow#49. Bound
  consumers: TSK-105 AC-2 is unaffected, since a task branch still keeps
  every other task's criteria frozen.)
- R-53. Journey criterion. When a PR range touches an adopter-facing
  surface (the path set of R-114, created by TSK-104 and extended by
  TSK-106: the scaffold under
  `assets/`, hook sources, shipped templates, managed instructions, the
  CLI command surface, or a runtime adopters run, including the present
  runtime), the PR's task must carry a `(journey)` criterion or serve the
  epic's journey criterion. CI blocks otherwise. A leaf that serves the epic's journey links the
  shared evidence that actually ran, or states the narrower path it
  verified; it never marks an unrun epic journey as verified.
- R-54. One acceptance block per completion lives in the record's Closeout
  (format in Interfaces). It names the reviewed commit, a recheckable
  review reference, one result line per criterion, the journey result,
  what was not verified, follow-ups or the reason there are none, and the
  verdict.
- R-60. One structural binding rule governs `task status complete` and CI:
  a completion names a reviewed head, and after it only that record's
  status and Closeout change. Every criterion appears exactly once; each
  mandatory criterion is `verified` or `waived`; the verdict is
  `approved`.
  - A waiver names a record-only commit that changed that criterion of
    this record, never the PR head and never a commit that also carries
    code: the planning amendment on the task's target, or, in the task's
    own pull request while the task is not complete on its target (R-52),
    a commit of that range that lies strictly before the reviewed commit
    and changes only this record. The waiver is justified in the
    acceptance block and approved with the code in the same PR. Once the
    PR lands, that commit is on the target, so the line and the release
    judge (R-120) accept the same waiver by the target route; a release
    range and a reopening range have no own-range route. A waiver naming
    an unrelated commit, a commit that changed another record, a commit
    after the reviewed commit, or a commit that did not change the named
    criterion is refused.
  - Direct work binds to the range's head. A reopen and re-completion
    owns its entire range, even when its new active block equals the old
    one: the reviewed commit must be inside that range, after the anchored
    base and at or after its last change outside status and Closeout.
    Compare its archived block and frozen criteria with the anchored
    target. No earlier task landing carries review through a reopened fix.
  - A task pull request that does not reopen its task may merge its
    integration target after the review: each such merge's tree equals
    the clean re-merge of its parents, and the task's own later commits
    change only this record's status and Closeout. A hand-resolved hunk in
    such a merge invalidates the block. Direct work on a release line, a
    completion bound at a head (R-120) and a reopening range never take
    this allowance.
  - A task landing transports the reviewed task onto its line. Its second
    parent is the reviewed head or follows it only by status and Closeout
    changes to that task; its tree is the clean re-merge of its parents.
    A later completion changes planning records only, and only merges or
    planning-only commits follow the landing. Unrelated line work before
    the landing does not enter the reviewed task's segment. A completion
    already made on a task line is judged where its block was introduced.
    This is the landing-merge result of the same binding rule. At a batch
    landing several reviewed heads land together on one candidate; each
    completion stays bound to its own reviewed commit through the commit
    that introduced its block, and a hand-resolved product hunk in one
    task's line merge invalidates that task's block only.
  - Only a release range can carry a brought import. R-120 defines its
    verified source parents and per-path attribution. A brought completion
    retains its source line's binding; every other merge there, including
    a fix PR for the release task, is direct work. Ordinary epic lines,
    stacked lines, shared history and line-to-line syncs keep their own
    task landings and planning amendments. No rule infers a line's parent
    from topology.
  The checker proves structure and binding only and says so. It does not
  prove the evidence is honest; the review reference is recheckable, not
  authenticated. (Amended 2026-09-29 by TSK-184, ADR-0076: the same-PR
  waiver route, the clean line merge after review and the batch landing
  binding; stated as one rule by TSK-140.)
- R-61. The reviewer's two questions, either of which may reject (is
  each criterion supported by evidence on this source; does the result
  achieve the outcome for the affected user), with converging as the
  second question, are stated in `cf-reviewer`, "Procedure", step 3.
  (Moved 2026-09-29 by TSK-184.)
- R-62. A criterion observable only after release records an owner, a
  measurement window and a follow-up task; it is never marked verified at
  build time.
- R-120. Release lines. A release range is judged commit by commit along
  its first-parent path from the merge-base, never by topology or a
  declaration the range itself carries.
  - Scope by name. A release branch is a branch whose name matches
    `git.release_branch_pattern`, read from the policy at the default
    target's remote tip (the fetched destination, never a local ref or the
    pushed graph); when the key is absent there, the default
    `integration/release-*` applies. A range is a release range when its
    head or its target branch name matches: a push to a release branch, a
    pull request into one, and its pull request into the default target.
    No merge-base selects scope, so no rewrite or records-only push rolls
    it back; changing it is a policy change landed on the default target.
    The policy check refuses a pattern that matches the default target or
    an epic line name (`integration/EPC-*`). A name supplies no import
    provenance and never relaxes direct-work checks: an epic line pushed
    under a matching name gets release rules, its own landings are direct
    work, and only merges from verified epic lines are brought. Every other
    range keeps R-52 and R-60. When the default target exists at the
    destination but its tip or policy cannot be read, the check fails
    closed with an error; when the destination has no default target yet,
    the built-in default applies.
  - Release-integration task. The one open task whose record carries
    `role: release-integration` (today TSK-010) owns direct release work
    and closes in the release pull request; it does not select scope. The
    owner is selected as the task open before its completion transition,
    so it may be complete in the judged final head. Its completion binds
    to the head wherever it is made, so `task status complete` on a fix
    branch applies the head binding CI applies into the release branch,
    never a landing merge. The validator refuses
    a second open holder. On a release range with no holder, direct code
    is refused with "no release-integration task to own it"; the release
    rules still apply.
  - Brought changes. On a release range a merge is a brought import only
    when each of its non-first parents lies on the first-parent chain of
    an epic line that passes the epic-line check, read from that line's
    authority ref, or on the default target's first-parent chain, and is
    not reachable only through the release branch's own ref or the pull
    request's head ref, so a range cannot qualify its own merges. A merge
    with any parent that does not qualify (an octopus with one unqualified
    parent, a line rebased or rewritten after the merge so the parent is
    no longer on its chain, a side branch pushed only to the release
    branch, or a branch that is no verified line) is judged wholly as
    direct work; no parent inherits another parent's qualification. The
    rule is the same however the merge arrives: a merge whose non-first
    parents all qualify is an import, judged per path below, whether a
    pull request or a plain merge delivered it, and a pull request into a
    release branch is judged as the merge it would create. Everything else
    that lands on a release branch, the release-integration task's own fix
    pull requests included, is direct work. Within a qualifying merge a
    path is brought only when its tree entry at the merge equals the
    expected import's entry for that path, in existence, object id, mode
    and type: the clean three-way merge result, or the second parent's
    entry when the path conflicts; the same comparison applies to clean
    and conflicted imports, so a mode-only or type-only change is a
    resolution. Equality with the first parent never makes a path brought.
    Any other path is a resolution, a direct change of the merge judged
    against the expected import, not against the first parent: keeping or
    restoring an older record where the import would change it is a
    change, so a restored older completion is bound at the head and a
    restored weaker criterion is refused as frozen, even when the record
    has no first-parent diff.
  - A brought completion retains the source binding defined by R-60. A
    later completion of the same task, brought from the task's own line
    (the one its record targets) and binding where it was introduced
    there, supersedes an earlier brought completion and a completion made
    directly on the release line: the earlier one stops being the
    completion in force and is never accepted. An invalid later
    completion, or one that reaches the release through another line,
    leaves the earlier finding in place. A brought criteria change is
    accepted as that line's and judged again at the merge that landed it
    on the line. A landing merge that reopened the task as it changed its
    criteria is refused as frozen first (R-52). Otherwise the change is
    accepted when that landing merge's range is planning-only by its
    paths, or is the own-task amendment of that record: the merge's
    second-parent range changes the criteria of exactly that record, the
    record is not complete at the merge's first parent, it is complete at
    the merge with an acceptance block whose reviewed commit lies in that
    range (R-60), and the record's tree entry at the merge equals the
    clean re-merge; any other landing merge that changed a criterion is
    refused as frozen. A `uid` a record gains without another change, as
    `ids backfill` writes it, is not a criteria change, and a merge
    resolution may keep a `uid` one side holds but never brings one
    neither side held. Git cannot show whether a
    planning-only landing merge passed that line's pull request check;
    that stays with the host's review and required checks on the line
    (R-80), which are not armed on CodeFlow's own host (AGENTS.md).
  - Release-rule cutoff. This re-judgement applies from a recorded point
    on each epic line. Project config `release_rule_baseline` is a table
    from each line's branch name to one full commit id, its cutoff, read
    from `.codeflow/project.toml` at the default target's advertised tip,
    the same commit and authority as the release pattern; local refs, the
    release branch, the pull request and the pushed graph never supply it,
    and moving a cutoff is a policy change landed on the default target. A
    brought criteria change whose landing merge on its source line is that
    line's cutoff or earlier on the line's verified first-parent chain, as
    the destination advertises it now, is listed as information with the
    task, line, landing, cutoff and governing policy commit: "legacy
    criteria change, landed before the release rule". Commit dates, plain
    ancestry and another line's cutoff never count: a topic landed after
    the cutoff is after it, and a cutoff that is not on the line's chain
    (another line's commit, or rewritten away) covers nothing. A value that
    is not a full commit id, or a key that is not a table, fails closed;
    with no key every landing is judged in full. Only this finding is
    exempt: import qualification, full tree entries, direct criteria
    freezes, resolutions, completion binding and the release-integration
    owner still apply to the same change.
  - Transition tables, a one-time bridge (operator ruling 2026-09-28,
    planning resolution 29). The cutoff table and the records baseline
    table (`release_records_baseline`, TSK-140) exist only to carry a
    project's history from before it adopted R-120; they honour nothing
    after it. Adoption is marked in the tree: `release_rules = 1` in
    `.codeflow/project.toml`, written by `codeflow init` and `update` of
    the release that brings R-120. The adoption commit is the first commit
    on the default target's first-parent chain whose project config
    carries the marker. The marker fixes only that point: R-120 applies
    whether or not a project carries it, so a project without it simply
    has no bridge. It is written once, like a table: once the default
    target's chain carries it, a later commit there that removes it or
    changes its value, a first appearance with another value, or a commit
    in a judged release range that drops it makes every release check
    refuse, naming the commit. The check reads that history in full, from
    the parents each commit records: history it needs that a shallow
    boundary cuts, or a config object the clone lacks, refuses and is
    never read as a project that did not adopt. A local graft file or
    replace ref refuses every release check, naming it, since it would
    change the commits the check walks while the destination holds the
    same ones.
    `scaffold_version` cannot mark it: CodeFlow's own default target
    carried `3.0.0` as a candidate stamp from 2026-08-02, before R-120
    existed. A table is honoured only when all of these hold, read from
    the default target's first-parent history at its advertised tip:
    - Write once. It was added in one commit and never changed after it:
      no edit, no extension, no removal and no re-adding. Any later change
      makes every release check refuse, naming the commit that made it.
    - Before adoption. Its adding commit is the adoption commit or an
      ancestor of it on the chain, and a commit carrying project config
      without the marker precedes the adoption commit on the chain, so a
      project that starts at 3.x can never use a table. Each cutoff's tree
      carries project config without the marker, the cutoff is neither the
      adoption commit nor a descendant of it, and it lies on its line's
      verified first-parent chain. Every entry is checked, whether or not
      a finding uses it.
    - CodeFlow's cutoffs only. Once every entry meets the conditions
      above, each must be one of CodeFlow's approved cutoffs, which the
      judge compiles in: one per epic line, each line's tip on 2026-09-27
      (`docs/verification/release-rule-cutoffs-2026-09-27.md`), the same
      for both tables. A repository meets them only by holding CodeFlow's
      own line history, and then they cover only CodeFlow's own landings
      at or before them, so a consuming project, a fork that keeps
      CodeFlow's root commit included, gains no relief for its own work.
    - No other door. No CLI flag, environment variable or policy key skips
      the rule or a table, `codeflow init` and `update` never write the
      tables, and the documentation describes them only as the 2.x to 3.0
      transition. Each legacy notice is named in the release report.
    When a table fails any condition, every release check refuses and
    names the condition and the commit.
  - Direct changes. On a release range criteria are frozen for every
    direct change of any class and any pushed slice, a records-only
    commit, a pull request that is not an import and any merge resolution
    included: a criteria amendment for any task, the release-integration
    task included, lands on a line through a planning pull request or the
    task's own pull request and is brought (R-52). The freeze follows the record's identity: removing a
    task record, creating one, or putting another `uid` at its path
    changes criteria directly, so a delete and a later re-create cannot
    reset it. A direct commit on the first-parent path whose own
    diff touches only planning records and changes no criterion needs no
    release-integration completion; a merge's resolution never counts as
    such a commit. A direct change to anything else, a fix pull request
    into the release branch included, is integration work: it belongs to
    the release-integration task, whose completion lies inside the release
    pull request and is bound as direct work under R-60 to the release
    head that both primary seats reviewed. A completion of any other task
    made directly on the release line is judged as a task pull request: it
    follows the last change outside planning records and binds to the
    reviewed head, or it moves to its own line.
  - A change that reached a task branch through a faithful merge of the
    task's own integration line is the line's, not the task's. When the
    commits the destination already holds bound a pushed task branch at
    several points, pre-push judges it from the newest one on the task's
    line, the range its pull request into the line is judged on; the base
    is always a commit the destination holds, so nothing new is left out,
    and a change made on the task branch itself, a merge resolution
    included, is still the task's.
  - Pre-push and CI apply this judgement through one shared judge to the
    same committed range and agree on it. Both pass the actual destination
    branch name (pre-push from the pushed remote ref, CI from the pull
    request's head and base) and read the policy from the default target's
    tip at the destination. A new branch is judged by its name like any
    other; a new release branch whose range the destination's tips do not
    resolve is judged from the default target's tip, and refused where
    the destination has no default target yet; a rewrite changes nothing
    about scope, which no merge-base selects; a default target whose tree
    has no policy file fails closed; an object the judge needs and cannot fetch, or a default
    target it cannot resolve, fails closed with an error naming what is
    missing, except the confirmed new-repository case above. `task status
    complete` applies the same judge to one prospective completion (the
    record, the block and the head it would be committed on) and agrees
    with CI on that completion; it gains no range audit, and its refusal
    of a task that is already complete is a status refusal, reported apart
    from any acceptance finding. (Added 2026-09-27, planning resolution
    20; made precise after plan review rounds 2 to 4; scope by branch name
    under the default target's policy after round 6; the own-task
    amendment of R-52 reconciled by TSK-184 on 2026-09-29.)

### How work flows

- R-63. Research findings live under `docs/research/`, one file per
  question with its sources. A spec, ADR or epic that draws on them lists
  them in an `inputs` list. A record may cite a research file; a research
  file never carries status.
- R-64. A spike is a task with `work_type: spike` on a `spike/` branch. The
  anchored preflight runs for it. Its PR lands findings (files under
  `docs/research/` and its own record) and never product code; CI blocks a
  spike PR that changes anything else.
- R-65. Spec and epic are many to many, with one owner per link. An epic
  lists the specs it consumes in full or in part in its `specs` list; a
  task lists its own specs and inherits its epic's. A spec keeps no
  consumer list: its consumers are derived by every reader from the
  consumers' `specs` lists, so the two sides can never disagree. One spec
  may be consumed by several epics and one epic may consume several
  specs. An epic with no spec is valid; its own criteria carry acceptance.
  `spec new --for <id>...` accepts several consumers and writes the new
  spec id into each consumer's `specs` list in the same planning change.
- R-66. The standalone test is one rule in one place: a task may stand
  alone when its outcome is one reviewable PR. It records a
  `standalone_reason`, and may list capabilities and specs directly.
  Capabilities may list standalone tasks. A standalone task completed by
  more than one PR is a validator warning at closeout.
- R-67. Today's rules stay: exactly one epic or a standalone reason per
  task; dependencies resolve and are acyclic; specs approved before work
  starts.

### PR classification and light paths

- R-70. Every product PR into a tracked target has exactly one class,
  read from its body and range: tracked (`Task: TSK-NNN`), epic
  (`Task: EPC-NNN`: a planning-only range for that epic, which touches
  only records under `project-management/` and plans under `docs/plan/`,
  such as its breakdown or its batched amendment, or the PR that brings
  its integration line to `main`), or a trusted automation profile
  (R-81). A PR that names no task and no epic is refused whatever it
  touches; never adjustable. Where durable tracking is inactive, the
  `Task:` line must be present and non-empty and names the harness's
  tracked unit. A malformed, repeated or mismatched `Task:` line is
  refused. (Amended 2026-09-29 by TSK-184, ADR-0076: the direct-change
  class, `Task: none: <reason>`, is removed.)
  A planning amendment names every epic whose records it changes on its
  one `Task:` line, comma separated (`Task: EPC-001, EPC-002`); each epic
  has a record at the head and was not cancelled at the target, the ids
  are distinct, and a task id never takes a list. CI prints the class as a
  planning-only amendment of the named epics. Besides records and plans,
  its range may carry files under `docs/` outside the adopter-facing set
  of R-114 (no hidden folder, and no harness instruction file such as
  `AGENTS.md`, `CLAUDE.md` or `GEMINI.md` or a variant of one, in any
  case) and the root `AGENTS.md` while its managed block,
  markers included, is byte-identical to the target's; any other path,
  `CLAUDE.md`, harness and skill trees, `.codeflow/`, record templates,
  policy, hooks and CI included, leaves the range unclassified, and a
  managed-block change is refused by name. In every folder, records and
  plans included, a hidden path (a `.gitkeep` excepted), a harness
  instruction file, an adopter-facing path matched in any letter case, a
  symbolic link, a submodule entry and a changed name that is not UTF-8
  or holds a backslash stay out, judged from Git's own entries. A range
  that carries a
  doc or `AGENTS.md` is refused when the tree at the target or the head
  holds any symbolic link or submodule, since either could present that
  text at a path the amendment may not write; a range of records and
  plans only is judged as before. The product and watched paths are read
  from the policy at the target. A change to a record of an
  epic the line does not name is refused; a standalone task and a spec
  belong to no epic and are listed, not refused. Without a body (the
  pre-push run) the same path rule applies, the target's `AGENTS.md` read
  from the base, and the pull request judges the named epics. A spec
  approval or supersession still travels in a range of records and plans
  only (R-32). The amendment lands once on its target, normally `main`; an
  integration line takes it by merging that target, and the report flags
  a task record that changed on its line since the line last merged the
  target. (Amended 2026-10-03 by TSK-229, ADR-0078, operator decisions D6

  unaffected, since a planning range that touches a product path still
  blocks.)
- R-71. Removed 2026-09-29 by TSK-184 (ADR-0076). It refused a direct
  change on a floor of surfaces; with the direct class gone, R-70 refuses
  every PR that names no task and no epic, on every surface.
- R-72. The anchored preflight (the `work start` check) runs once per
  task in two planes: `work start` on any branch that carries a task id on
  a sanctioned prefix (the own-branch context of R-110), and CI for every
  tracked PR whatever its branch prefix. Pre-commit does not repeat it.
  Both planes apply the `git.work_planning` level: `block` by default, or
  `warn`; there is no `off`.
  (Amended 2026-09-27, planning resolution 19: the pre-commit plane is
  retired.)
- R-73. A follow-up is filed with `task new --follow-up-of TSK-NNN "title"`
  and records `follow_up_of` and the source's target. A follow-up of an
  epic task is filed on a `plan/` branch of that target and rides in the

  a `plan/` branch, and `task new --follow-up-of` refuses to run on one for
  a standalone source. Its follow-up is a standalone task too (R-78): cut a
  task branch from the target, file the follow-up there, fill in and commit

  `work claim`, which renames that branch to its own `task/TSK-NNN-<slug>`

  pull request.
  (Amended 2026-09-29 by TSK-184, ADR-0076; the standalone source added
  2026-10-03 by TSK-214, sathyassn/codeflow#21; the wording of the

- R-74. A leaf task is added with `task new --epic EPC-NNN "title"` in the

  2026-10-03 by TSK-229, ADR-0078. Bound consumer: TSK-104 AC-6 is

- R-75. A blocker is recorded on the task branch with
  `task status <TSK> blocked --reason --owner --revisit`; `status` reads

- R-76. Release stabilisation: the release task's criteria are the

- R-77. `epic new --integration "title"` creates the epic record and its

- R-78. A record cannot authorise itself: no PR may both add an epic

### Enforcement and customisation

- R-80. Each rule names its plane and level, and whether an adopter may
  change it once tracking is on:

  | Rule | Plane | Default | Adjustable |
  |---|---|---|---|
  | Id grammar, filename equals id, duplicate ids in a tree | validator, CI | block | no |
  | Every added record reserved with its `uid` before merge; edited `uid` refused | CI | block | no |
  | Registry only grows; allocation reads history | pre-push over the range, git-guard, registry CI job | block | no |
  | Every product PR classified | CI | block | no |
  | Anchored preflight for tracked work, any branch (R-72) | `work start`, CI | block | `git.work_planning`: block or warn, never off |
  | Blocked needs reason, owner, revisit; cancelled needs reason and scope; complete needs the acceptance block | validator on the PR range | block | no |
  | Criteria of every record but the PR's own task frozen against the target; the own task's change printed for the reviewer (R-52) | CI | block | no |
  | Acceptance block bound to the reviewed commit | CI | block | `git.work_records`: block or warn |
  | Journey criterion for adopter-facing ranges | CI | block | `git.work_records`: block or warn |

  | A planning amendment changes records only of the epics its `Task:` line names, and keeps `AGENTS.md`'s managed block byte-identical to the target's (R-70, ADR-0078) | CI | block | no |

  | Always blocking, whatever the profile or level: secret scan, protected branches, hook integrity, the registry rules, and a PR that names no task and no epic | all | block | no |
  | Never exempt from evaluation, at the project's configured level: AI attribution, emoji, policy characters, PR sections, release declaration; no automation profile, template state or update changes the level | all | configured level | the level, by a reviewed policy edit |
  | Policy read from the target side; a PR cannot relax its own checks | CI | block | no |
  | Standard tier without records sees no record rule | test | pinned | no |

  A rule in the always-blocking row has no level; a rule in the
  never-exempt row keeps whatever level the project configured, and an
  explicit adopter `block` stays effective until its owner changes it.

  Every warning and note names an existing command, or an edit to a named
  file, that clears it. A plane that runs another plane's check (pre-push
  running `codeflow ci`) prints each finding at its effective level: the
  lower of the finding's own level and the running plane's rule only where
  the finding's rule permits a downgrade; an always-blocking rule and a
  configured block keep their level and stop the operation. Its closing
  line says whether the operation was stopped (TSK-147; added by planning
  resolution 21, bounded after plan review round 4).

- R-81. `git.work_records` accepts `block` or `warn` and nothing else.
  `codeflow update` preserves every policy value an adopter set, including
  values equal to a default.
- R-82. A trusted automation profile matches when the actor or app id that
  the workflow passes to `codeflow ci` and the branch pattern both match a
  configured profile. It skips branch naming and commit format, counts as
  its own classification, keeps tests, the secret scan, contract
  assessment and target-side policy, and never changes a policy level. PR
  sections stay evaluated at the configured level (R-80): the profile may
  name the sections its bot body omits and supply their content, and the
  check judges the body with that content; any other missing section
  fails at the configured level. Locally and on fork PRs the actor is
  "unknown": only the pattern match is reported and no exemption or
  supplied content applies.
- R-83. Migration: the new rules apply from a recorded migration baseline
  commit, by transition. A spelling edit to an old complete task warns;
  reopening it, changing its criteria or completing it again applies the
  new rules. A historical exception is bound to the record's exact blob,
  never to its id. Identity, relationship and planning errors are never
  grandfathered.
- R-84. Kept brownfield PR templates have four states, recorded in
  `git.pr_section_mapping`. Diagnosed: `init` or `update`, interactive or
  not, writes a proposed heading mapping, and `doctor` repeats the
  diagnosis on every run; no other check changes and no policy byte is
  overwritten. Accepted: the mapping is recorded and the check runs at its
  configured level against the mapped headings. Refused: the missing
  headings are appended to the template and the configured level applies
  to the shipped headings. Custom: the project sets its own section list in
  policy by a reviewed human change. An interactive `init` or `update`
  asks and records accepted, refused or custom before it reports setup
  complete; only a non-interactive run leaves the diagnosed state. Policy
  is never derived from a template silently.
- R-115. Effective level in the diagnosed state. While the mapping is
  diagnosed, the PR-section check evaluates the shipped headings at the
  effective level. A `pr_sections` value is explicit when the adopter's
  policy file already set it before this `init` or `update` run, whatever
  its value, including a value equal to the shipped default; an explicit
  value stays effective, with no new decision required. The level is
  implicit, and the check runs at `warn`, only when this run creates the
  policy file (a fresh install with no prior policy) and the mapping
  records no operator decision. Explicitness is read from the presence of
  the key in the prior policy file, never by comparing its value with the
  default. An installation whose prior policy provenance cannot be read
  keeps its configured level, and `doctor` reports the unresolved mapping.
  A diagnosed window ends at the
  first accepted, refused or custom decision, and `doctor` names the
  effective level, its origin (`configured`, `shipped default`,
  `diagnosed`) and the pending decision on every run. `codeflow ci` prints
  the effective level and origin of every check it runs. Tests assert the
  effective level and the preserved policy bytes for each state, for a
  first install with no prior policy, for an upgrade of an already
  mismatched repository, and for an upgrade whose policy sets
  `pr_sections` to `block`, equal to the default, which stays `block`.
- R-85. Upgrade order: new binary first, then `codeflow update`. Updated
  hook shims check the binary's capability before dispatch and fall back
  to the previous behaviour with a warning when the binary is older.
  (Amended 2026-09-27, planning resolution 20: a hook that git fires
  while a `codeflow` command runs that git command dispatches to the
  calling binary, never to another `codeflow` found first on PATH. The
  calling process derives that path from its own runtime identity, sets
  it only in its git child's environment, overwriting any inherited
  value, and never exports it to longer-lived children. The shims quote
  the path exactly, run the capability probe against that same binary,
  and fail the hook when the designated binary is missing or not
  executable, never falling back to PATH or to a no-op. A git command run
  outside a `codeflow` command keeps the PATH lookup and the no-op when
  no binary is found. The value is a dispatch hint, not authentication.)
- R-113. The binary that enforces CI is chosen by the target. The
  scaffolded workflow installs the `codeflow` version pinned in the
  target-side scaffold state, never the head's, so a PR cannot lower the
  enforcing version while changing a protected surface. The pinned install
  verifies the release asset against the published checksum for that
  exact version and fails closed when the checksum is missing or does not
  match; it never falls back to an unverified download. An upgrade takes
  two pull requests, in order. The first raises only the pinned version;
  the target's binary enforces it, and the candidate binary is tested in a
  separate job. After that pin is on the target, the second carries
  `codeflow update` (new policy keys, schema and templates) and is judged
  by the new binary. A head that adds policy keys or schema the target's
  binary cannot read, while the raised pin has not landed, fails with a
  message that names the two-step order, not a bare unknown-key error.
  This message comes from binaries that implement this rule (3.0.0 on); an
  older binary still reports its own error. Operator decision after plan
  review round 2 (Codex R2-6), matching the upgrade order the 3.0.0
  CHANGELOG documents.
- R-114. One definition of the adopter-facing path set, which R-53
  reads. TSK-104 creates it, because it classifies PRs first: the current
  `watched_contract_paths` plus the fixed set `assets/`, hook sources,
  shipped templates, managed instruction blocks, the CLI command tree, and
  every runtime adopters run (including `crates/codeflow-present`). TSK-106
  extends it with the release contract paths: `watched_contract_paths`
  extended to the record schema, the CLI flag surface and policy keys.
  TSK-106 owns the behaviour-path set for R-93: every path outside `docs/`,
  `project-management/`, `docs/verification/` and the record templates
  counts as behaviour, and the skill trees count as behaviour because they
  change shipped agent behaviour. Both sets ship as fixtures that the
  journeys of R-104 use.

## Interfaces and formats

Registry file, `ids/<KIND>/<N>.toml`, where `KIND` is `EPC`, `SPC`, `TSK` or
`ADR` and `N` is the part of the id after the kind prefix, as written
(`ids/TSK/100.toml`, `ids/ADR/0068.toml`, legacy `ids/TSK/002-001.toml`):

```toml
id = "TSK-100"
uid = "8f6d0d1c-4a1e-4d2b-9c0e-2b7f2f9f3a11"
kind = "TSK"
title = "Registry proof on a real host"
issuer = "<git user.email at issue, or 'seed', or 'admit:<maintainer>'>"
created = "2026-09-26T10:41:02Z"
target = "integration/EPC-020-delivery-system"
introduced = "none"   # seed: "<sha>@<ref>" of the first commit that added the record
landed = "none"       # seed: "<sha>" of the first commit on a stable target, or "none"
mapped = []           # seed --map: introducing shas of copies mapped to this record
mapped_by = "none"    # seed --map: "<maintainer> <date>", or "none"
```

Every field is required; `target` is the intended integration target at
issue and is informational after that. A file is never edited after it is
added, except by a typed restore (R-108) that returns it to these bytes.
The only commits on the branch are the seed root, issues, admissions and
typed restores.

Record frontmatter gains `uid` (UUIDv4, required after backfill),
`former_ids` (list, written by retarget), `follow_up_of` (one task id),
`work_type` (`spike` among the existing values), `inputs` (list of paths
under `docs/research/`, on specs, ADRs and epics), `standalone_reason` (as
today), `awaiting_selection` (one path, on a join task; R-43), and on specs
`supersedes` (list) and `superseded_by` (one id; R-32). Epics and tasks own
the `specs` list; a spec carries no consumer list (R-65). A `depends_on`
entry is a bare task id (code dependency) or an object
`{id: TSK-NNN, kind: research | decision, pin: "<sha>"}`, the pin quoted
(R-112).

Criterion line grammar: `- AC-<n> When <condition>, the system shall
<behaviour>[ (serves EPC-NNN AC-m)][ (journey)]`. A journey criterion's
behaviour names one of: fresh init, update, installed CLI, present runtime,
release artefact. A tag may instead open the criterion, and a closing tag
may carry sentence punctuation (R-50).

Acceptance block, a fenced `yaml` block under `## Closeout`:

```yaml
acceptance:
  reviewed: <full commit sha>
  review: <PR review URL, or session:<id>@sha256:<transcript digest>>
  criteria:
    AC-1: verified | <command and result, or file:line>
    AC-2: waived   | <amendment commit sha: on the target, or record-only in this PR before the reviewed commit>
    AC-3: failed   | <what failed>
  journey: verified | <path exercised>
  not_verified: <list, or none>
  follow_ups: <TSK-NNN, ...> | none: <reason>
  verdict: approved
```

A superseded block keeps its content under `acceptance_superseded:` with the
reopen reason.

PR body classification line, in the Summary section: `Task: TSK-NNN` or
`Task: EPC-NNN` where durable tracking is active, a non-empty name of the
harness's tracked unit where it is not. A planning-only PR and the PR
that brings an epic's line to `main` name the epic; an automation profile
PR carries none (R-70).

Blocker section, required when `status: blocked`:

```
## Blocker
- reason: <text>
- owner: <person or role>
- revisit: <event, such as "TSK-101 lands" or "plan v3 approved">
```

Policy keys added to `git`: `work_records` (`block` | `warn`, default
`block`); `automation_profiles` (list of `{name, actors: [<actor or app
id>], branch_pattern, sections: {<heading>: <content>}}`, where `sections`
supplies content for the PR sections the bot body omits (R-82); default

## Edge cases

- A push whose acknowledgement is lost: after another issuer pushes, our
  reservation commit is an ancestor, not the tip; read-back checks that the
  tip reaches a commit binding N to our `uid` (R-13). A replay may change
  the commit sha and keep the binding.
- A deleted or edited reservation file on the tip: the number is not
  reissued (R-7); issue refuses repository-wide until a typed restore lands
  (R-9, R-108); the original content is recoverable from history. A
  commit that removes many files stops issue in the same way and is
  repaired by one restore naming them all.
- A legacy record before its line's backfill: CI reads the registry file
  by id and judges a record with no `uid` by its `introduced` and `landed`
  provenance (R-111). After the backfill this path is unused.
- A join awaiting selection: a valid record with an empty `depends_on`,
  `awaiting_selection` set and a Blocker; no context of R-110 starts it,
  and a task branch cannot land the selection (R-43).
- Two clones offline take the same number: sync detects the different
  `uid` and retargets the later one; nothing lands with a duplicate.
- Two integration lines add the same number with different `uid`s: the
  merge rule refuses the second at its PR, because N is already bound.
- A fork PR admitted, then the registry moves before merge: the binding is
  to the `uid`, so a later issuer cannot take N; the PR merges.
- A host without branch rules rewinds the registry: issue refuses against
  the last verified tip (R-10); `doctor` reports reduced assurance.
- A join whose alternatives are all cancelled: it stays blocked awaiting
  selection until a reviewed selection or a cancellation of the join.
- A task with a Blocker and an active branch: reported as blocked, not
  active; `work next` shows it under blocked.
- A PR with no `Task:` line, or one that names no task and no epic,
  whatever it touches: refused, with the instruction to name its task, or
  its epic for a planning-only range or the PR to `main` (R-70).
- A spike PR that changes product code: blocked (R-64).
- A record with `status: implemented` written by hand on a spec created
  after this spec lands: refused; on an older spec: read as before, and
  `validate` warns when it disagrees with the computed state.
- `work next` on a stale clone: the printed snapshot lets the reader judge
  the freshness; a task claimed after that fetch is not excluded.
- `codeflow update` on a repository whose `git.work_records` is `off` from
  an unreleased build: rewritten to `warn` with a notice; every other
  value is preserved.
- A registry push from CI: not permitted; the registry job only reads.
- An abandoned `ids admit`: the number stays reserved to that `uid` and is
  never reissued; the gap is reported by `ids check` as a gap, not damage.

    builds the cutoffs and the supersession, and its AC-6 reconstruction
    shows exactly these seven as information and no blocking finding from
    the release-line judge. The same reconstruction found two records-rule
    findings that judge a brought change across the whole range instead of
    where it was introduced: SPC-002's approval, landed on EPC-020 by
    planning PR 655, and TSK-069's `uid` backfill, landed by PR 654. They
    would block the real release pull request; TSK-140 owns both (its

    Requirements: R-120, Interfaces.
29. The cutoffs as a one-time bridge (operator ruling, 2026-09-28: option
    A, on three conditions: it is a one-time thing, it has no effect on
    consuming projects, and it leaves no loophole or escape hatch). R-120
    states the rules; TSK-140 builds them for both tables, and the config
    pull request to `main` carries both tables and the adoption marker in
    one commit, after TSK-140 passes review. Threat note, each loophole
    walked against the rules (R1 write once, R2 before adoption, R3 no
    other door):

    | Loophole | Closed by |
    |---|---|
    | Edit a cutoff to a later commit | R1: any change after the adding commit refuses every release check, naming it |
    | Extend the table with a new line | R1, the same |
    | Remove the table and add it again | R1: the re-adding is a second change |
    | Name a cutoff after adoption | R2: the cutoff is the adoption commit or descends from it, or its tree carries the marker |
    | Add the table after adoption | R2: the adding commit must be the adoption commit or before it |
    | Remove the marker to look pre-rule | R1 for the marker (TSK-145 AC-13): removing or changing it on the chain or in a judged range refuses every release check; R2 still fixes adoption at the first marker commit |
    | Use the marker to switch R-120 off | TSK-145 AC-13: the marker never decides whether R-120 applies; a project without it only has no bridge |
    | Hide adoption behind a shallow cut, a missing object, a graft or a replace ref | TSK-145 AC-13: history is read from recorded parents; a cut or missing object refuses, and a graft or replace ref refuses every release check |
    | A cutoff off its line's chain | R2 and R-120: a cutoff not on the line's verified first-parent chain refuses every release check, whether or not a finding uses it |
    | A consuming project, upgraded from 2.x, started at 3.x, or a fork keeping CodeFlow's root commit | R2: an entry that is not one of CodeFlow's approved cutoffs refuses every release check |
    | A fresh 3.x project | R2: no commit with project config but no marker precedes its first marker commit |
    | A line branched from an old base | R2: only landings at or before a recorded cutoff on that line's chain are information; everything after is judged |
    | A flag, variable or policy override | R3: none exists, and a test asserts it |
    | `init` or `update` writing a table | R3: neither writes one; tests assert both |
    | Rewriting the default target's history | Protected-branch rules forbid it (R-80); R1 and R2 read only its first-parent history |

    Consuming projects are unaffected: without a table nothing changes,
    and a table in a consuming project, upgraded from 2.x, started at
    3.x or forked from CodeFlow, refuses every release check unless each
    entry is one of CodeFlow's approved cutoffs, which cover only
    CodeFlow's own history.
    Requirements: R-120.
