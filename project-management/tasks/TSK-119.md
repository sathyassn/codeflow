# TSK-119: present answers stored against revisions

## Description

Node C of the present review parity package (Plan v5). Present has no input
block: `feedback_prompt` is a paragraph, `decision` status is set by the
author, `<form>` is refused and the page policy sets `form-action 'none'`
(proposal section 1). This task adds, to SPC-014, a runtime-owned `form`
block whose answers are validated in the page and on the server and stored
as append-only records bound to the revision shown, in the private local
session store (operator decision 4a), plus a conditional update so a stale
publish returns the current revision (proposal sections 2 and 3.3). Authored
HTML stays script-free.

Boundary with TSK-120 (settled 2026-09-26): this task owns the `form` block
through the "stored" state, including page rendering, drafts, page and
server validation and stale handling. TSK-120 owns delivery to the agent,
the states after "stored" (waiting for agent, delivered, acknowledged,
failed) and the end-to-end browser to agent journey.

## Affected surfaces and interfaces

- `crates/codeflow-present/src/document.rs` and the v2 document schema
  copies (the `form` block and `decision` as a form), `render.rs`,
  `service.rs` (submit endpoint, the page policy for runtime-owned submit),
  `state.rs` (answer records, receipts, amendments, atomic append),
  `limits.rs` (answer size bounds).
- `crates/codeflow-present/web/src/` form rendering, page validation, drafts
  in page memory, the stale-revision confirmation and the submit states up
  to "stored"; `chrome.tsx` where the states show.
- `crates/codeflow-cli/src/cmd/present.rs` for `update --expected-revision N`;
  `crates/codeflow-cli/tests/present_cli.rs`.
- `cf-present` authoring reference for the `form` block, with mirrors and
  hashes; the present rebuild, manifest and checksum. CAP-016.

## Acceptance Criteria

- AC-1 A v2 document can carry a `form` block with the SPC-014 field subset
      (string with length and a small format set, number and integer with
      bounds, boolean, single and multiple choice, a `required` list,
      outcomes submit, decline and cancel, an optional rationale per field);
      a `decision` is a form with one choice and a rationale, and a
      recommended option is labelled and never preselected; evidence: schema
      and render tests on the TSK-117 fixtures (3.3).
- AC-2 The page validates before submit, and the server validates against the
      form digest of the revision shown, derives actor and time, appends
      atomically and returns a receipt keyed by request id; evidence: service
      tests (3.3).
- AC-3 Retries are idempotent: a resubmission with the same request id and the
      same payload succeeds with the original receipt and appends nothing,
      including when the first response was lost after the durable append; the
      same request id with a different payload is refused with a typed error
      and appends nothing; a new request id carrying a correction is an
      amendment, never a retry; evidence: service tests for all three cases,
      the lost-response case dropping the response after the append (3.3;
      Codex R1, plan review round 1).
- AC-4 Malformed and oversized submissions are refused with typed errors and
      leave the store unchanged; a submission against a stale revision keeps
      the draft and asks for confirmation against the current revision;
      evidence: one control per case in service tests and the browser suite
      (4.2 row C).
- AC-5 A crash control: a process killed during an answer append leaves the
      store with the whole answer or none of it, and the session reopens;
      evidence: a crate test that interrupts the append.
- AC-6 Corrections append as amendments; the original answer and each
      amendment stay readable in order; evidence: store tests (4.2 row C).
- AC-7 Drafts live in page memory for the page's life, survive a revision
      notice without a reload, and nothing is written to browser storage;
      evidence: a browser case that inspects storage after drafting (3.3).
- AC-8 `present update --expected-revision N` succeeds when N is current and
      otherwise fails with the current revision in the error; evidence:
      `present_cli` tests (section 2).
- AC-9 The block by gesture matrix that TSK-071 landed gains the `form` block
      and the v2 `decision` form, with text, element and area cells declared
      and justified, the legacy v1 `decision` row kept, and the matrix test
      still naming every variant of the block enum; the real-browser suite
      proves each applicable form cell creates a note; a control proves that
      annotating a form (a text selection, a click on a field, an area drag
      across it) never changes a field value, a draft or the store and never
      submits; evidence: the matrix, its test and the suite output (Codex R2,
      plan review round 1).
- AC-10 v1 documents, v1 sessions and the v1 feedback stream are unchanged;
      evidence: the v1 fixtures pass.
- AC-11 `npm run check`, the browser checks, `cargo test -p codeflow-present`
      and `cargo test -p codeflow-cli --test present_cli` are green and the
      present checksum matches a clean rebuild; evidence: recorded output
      with the head SHA.

## Closeout

A v2 document can ask the reviewer typed questions, and the answers are
stored against the revision shown, append-only, in the private session
store. Evidence is at `a7709c992` on `task/TSK-119-form-answers`; SPC-014
was amended twice on the line first (PR 690 and PR 694), and this task
builds to the amended text; PR 695 converted the criteria to AC-n.

- Form and decision (AC-1): `form.rs` holds the v2 `form` block and the v2
  `decision` as a one-field form; `render.rs` renders them runtime-owned
  (authored HTML stays script-free, `form-action 'none'` is unchanged, the
  page submits by its own fetch). "Recommended" is a label, never a
  preselection; no field has a default. Schemas: `document-v2.schema.json`
  gains the blocks and `session-responses-v1.schema.json` describes the
  `answer` and `amendment` lines, byte identical in the three homes.
- Answers (AC-2 to AC-6): `POST /app/api/answers` under the v1 request
  checks. The page validates first; the server validates against the form
  digest at the named revision (the v1 `block_digest`), derives actor and
  time, and appends one synced line to `responses.jsonl` under the session
  lock before the receipt. Same request id and payload replays the receipt
  (after a successful sync); a different payload is `request_id_conflict`; a
  correction is an amendment naming the original answer. A present `null`
  is `wrong_kind`. Every storage refusal (I/O, a full project, the ledger's
  100,000-line and 64 MiB bounds, a corrupt or unsafe ledger) is 503
  `store_unavailable` with no receipt.
- Record size: the answer record cap is the largest record the form bounds
  allow (1,972,971 bytes; the snapshot holds the title, field ids, labels,
  kinds and option values and labels, charged at 6 bytes a character), so
  every accepted form can be answered, declined and dismissed. Decision:
  the 64 MiB ledger then holds 34 maximum-size answers; a full ledger
  answers the typed 503 that I3 names, and no spec line was added.
- Page (AC-4, AC-7): states editing, submitting, stored ("Stored, waiting
  for agent"), failed (the same request resent), stale (confirm only when
  the question's digest is unchanged), changed (read only; the draft listed
  as text to copy before a reload) and closed (latched; a late receipt
  still reads as stored). Form drafts live in page memory only. Unsent
  review drafts stay in the tab's sessionStorage under amended B6, without
  pictures, and are dropped when the session closes.
- CLI (AC-8): `present update --expected-revision N` exits 8 with
  `{"error":"revision_conflict","expected":N,"current":M}` and writes no
  revision.
- Matrix (AC-9): the annotation matrix gains the `form` block and the v2
  `decision`; the legacy v1 decision row stays; the form control starts
  from a populated draft and proves annotation never changes a value, a
  draft or the store and never submits.
- Verification: property test over generated submission sequences; a crash
  control that aborts a child process mid-append; a hand mutation pass on
  answer validation and the store (48 mutants killed, 0 survived, 1
  equivalent, recorded in the lead's scratchpad `tsk119-mutation.md`);
  cargo-mutants is not installed.
- Harvest: a TSK-118-era worker left 3,010 uncommitted lines for this task
  on a stale base; they are kept in the stash
  `tsk119-partial-answers-core-2026-09-26` (43214df4c) and were reused only
  where they matched the spec.
- Gates (AC-11) at `a7709c992`: `npm run check` reproducible; check:browser,
  check:matrix, check:entities, check:forms pass; `cargo test -p
  codeflow-present` 176 passed; `present_cli` 16 passed, 1 ignored; clippy
  and fmt clean. The Firefox and WebKit chip run failed once in Firefox
  (the composer did not open after Add text) while the load average fell
  from 99, then passed on a rerun at load 9; the web bundle is identical to
  `aa32da0e5`, where it also passed.
- Not verified, and why: a real 410 from the answers route (the service
  stops when the session closes, so the check fulfils the 410); an unsafe
  ledger path beyond sharing the 503 arm with the corrupt-ledger test (a
  test would need a symlinked session file the store refuses to open, and
  it shares that arm); a sync failure on a real disk (the fault is injected;
  a failing disk cannot be made on demand).
- Decision, not a task: if the operator wants B6 absolute again, the
  review draft moves into the loopback service's owner-private session
  store (Fable's durable direction), not back to page memory.
