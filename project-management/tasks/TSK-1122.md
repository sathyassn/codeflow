# TSK-1122: The operator approves the status dashboard design on a clickable prototype with real data before the build starts

## Description

The operator asked on 2026-10-31 (13:15) that the design and layout of the
status dashboard be shown as a clickable prototype with real data, a side
menu, tabs and drill-downs, for approval before the build tasks start; and
that reports be organised by outcomes first, every outcome opening to its
detail (epic, theme, task, evidence). The 4.0.0 status page of 2026-10-31
(`codeflow-400-status.html`, a hand-built page with a sections nav and
eleven sections, the reference look) and the design brief revision 2 are
the inputs; neither has a side menu, tabs or drill-down, and the runtime
cannot yet draw them (TSK-1120). This task is the design pass of
`/cf-design` for the shell and the status document together: one
prototype the operator clicks through, built outside the runtime from the
live board's facts, and the settled `DESIGN_INTENT` the build tasks
(TSK-1120, TSK-1121, TSK-1098) conform to.

Outcome: **the operator has clicked through a prototype of the status
dashboard with real 4.0.0 data (an outcomes-first overview; a side menu
of outcomes, epics, lanes, decisions, evidence and the script; tabs for
aspects inside a view; drill-down from an outcome to its epic, theme,
task and evidence with a breadcrumb and a task context strip; the
operator inputs as form controls; change marks since a previous report),
at desktop and phone width in light and dark, and has approved it or
named the changes, recorded as the `DESIGN_INTENT` the build tasks
conform to; the approved layout contract and registry kinds are written
into TSK-1120's record and the approved view tree into TSK-1098's before
either starts.**

```text
  design brief r2 + 4.0.0 status page + live facts
        |
        v
  clickable prototype (HTML, real data, menu, tabs, drill-down, forms)
        |
        v
  operator walk-through  ->  approved | changes named  ->  DESIGN_INTENT
        |
        v
  TSK-1120 (shell contract)   TSK-1121 (topic, marks)   TSK-1098 (views)
```

Figure: one prototype settles the direction once; the three build tasks
conform to it instead of each deciding the layout.

Decisions, each reversible and disclosed here:

- The starting prototype exists: the coordinator handed the operator a
  first dashboard prototype on 2026-10-31 (the Claude artifact
  https://claude.ai/artifact/F21zCBy6U6qKh87n62tqGH, "Present and Portal
  Redesign" lineage), which the operator is reviewing; this task starts
  from it, carries its content into the committed prototype below and
  folds the operator's first remarks in before the walk-through.
- The prototype is a static HTML page outside the runtime, built from the
  live board's facts gathered the way the 4.0.0 status page gathered them
  (its `gather` and `build` scripts in the design lead's scratchpad, run
  fresh so every number is live at build time with its as-of), using the
  kit tokens and the grammar module's marks so it looks like the runtime
  will; no number is typed by hand. It is a prototype of the design, not
  a report the operator relies on, and says so in its header.
- Outcomes first is the primary structure, not a view option: the
  overview lists the scope's outcomes (the deliverable lines of its epics
  and themes) each with its percent, state and the next step, and every
  outcome opens to its detail in order (the epic, its themes, each
  theme's tasks, each task's context and evidence). Epics, lanes,
  decisions, evidence and the script are side-menu entries that cut
  across the outcomes; a reader who never leaves the outcomes path still
  reaches every fact.
- Approval is the operator's, recorded in this record's Closeout as the
  `DESIGN_INTENT` block of `/cf-design` section 7 with the walk-through
  date and the changes named; a change the operator names is folded into
  the prototype and the records in this task's PR, never deferred to the
  build tasks. The design seat is Claude Fable 5.1 at high, which owns the
  prototype and the intent; the walk-through is the operator's own
  clicking, not a screenshot read.
- This task edits TSK-1120's layout contract and registry text and
  TSK-1098's view tree to the approved design in its own PR (a planning
  amendment naming EPC-022), so the build tasks start from the approved
  shape; it adds no criterion that the approved design does not need.

Non-goals: building the shell (TSK-1120), the topic and marks (TSK-1121)
or the status document (TSK-1098); the portal (TSK-1114); a prototype
kept as a product surface (it is archived with the record and superseded
by the runtime).
