# TSK-241: Operator feedback has one tracker with ids the CLI issues

## Description

The operator's own words (rulings, corrections and preferences given in
chat) have no home in a CodeFlow project, so adopters keep parallel logs and
the same instruction lands in several places in several wordings (issue 75,
filed by an adopter). This task ships one tracker at the full tier: one item
is one file, `project-management/feedback/FB-NNN.md`, written from a new
template with the operator's words verbatim and the agent's reading kept
apart; the id is issued by the shared registry as a new `FB` kind;
`codeflow feedback new | status | list` create, move and list items, and the
status verb moves an item only by its transition table (received, placed,
closed, declined, superseded); `validate --docs` checks the structure;
`codeflow status` shows the open count; `codeflow recall` finds items; and
`project-organization.md` gains an "Operator feedback" subsection, a
conditional read. Effect on adopters: at the full tier `codeflow update`
installs one template and the managed docs changes; the feedback directory
and the `[feedback]` section of the project state file appear only on first
use; standard and minimal tiers change nothing on disk and `feedback new`
refuses there. No record is required of any work, no policy key is added
and the index is never a failing check. An older binary's `ids check` on a
registry that holds an `FB` entry reports it as a repaired-history warning
and does not fail (checked with the 3.0.0 binary). Non-goals: an `acting`
state, a topics file, a required or validated index, a decisions queue, a
cf-reviewer change, and adopting the tracker in the workspace (the
operator's own practice).

Operator decisions (source: operator, chat, 2026-10-04), on the issue 75
design drafted that day:

- An FB record is made only for feedback that sets a standing rule,
  declines or reorders planned work, or spans several units; an ordinary
  request stays in its unit.
- The index is generated on demand: a project opts in by writing it, and a
  stale index is a warning, never a failing check.
- CodeFlow's own repository adopts the tracker. The workspace's adoption is
  the operator's and is not part of this task.

Departures from the design, each checked against `origin/main`:

- `cf-ship/references/pr-evidence.md` is in the per-task reading chain
  (`codeflow doctor --check reading` grows by the bytes added to it), so
  its FB line is written byte-neutral.
- The design says an older binary's `ids check` fails on the new kind; it
  warns (`ids/ledger.rs` records the addition as a violation, which
  `ids/check.rs` reports as a warning while the tip has no damage), so a
  pinned older release keeps passing.
- `feedback status` uses its own transition table and the status verbs'
  digest-checked write; the work lifecycle judge stays for tasks, epics and
  specs, since feedback is not a node of the work graph.
- The template carries `confirmed_by`, which the design's validation names
  but its field list omits.
- The registry file of `FB-001` is `ids/FB/001.toml`, not `ids/FB/1.toml`:
  a registry path carries the number as written, as `ids/TSK/100.toml` does.
- A written index is stale when it differs from the index the items render
  now, not when its file time is older: file times after a clone say
  nothing, and the content check gives no false warning in CI.
- A task pull request may add feedback items. `codeflow ci` refused every
  added record but the task's own, which would have kept an item recorded
  during a task out of that task's pull request; feedback items are exempt
  (`cmd/ci/classification.rs`), since they are not work records and the
  registry merge rule still binds their ids. The design is silent on this.

## Acceptance Criteria

- AC-1 When `codeflow feedback new --topic process --source chat "<summary>"` runs in a full-tier project with a remote, it issues `FB-001` through the registry (`ids/FB/001.toml` on `codeflow/registry`), writes `project-management/feedback/FB-001.md` from the template with `status: received`, and the next call issues `FB-002`; an offline reservation publishes with `ids sync` (`feedback_cli`; `id_registry`).
- AC-2 An unlisted topic is refused with the list; the default list is written to the project state file on first use and kept afterwards (`feedback_cli`).
- AC-3 `feedback status` accepts received to placed with a resolving `--in`, placed to closed with `--evidence`, an open item to declined with `--confirmed-by operator --reason`, and received, placed or closed to superseded with `--by` another existing item; every other transition is refused with the table and nothing is written (`feedback_cli`; unit tests).
- AC-4 `validate --docs` fails on a duplicate uid, an id and path mismatch, an unknown topic, a placed item with no resolving placement, a closed item with an empty Closure, a declined item without the operator's confirmation, a superseded item whose successor does not resolve and an empty Verbatim, and passes a clean set (unit tests in `feedback.rs`; `feedback_cli`).
- AC-5 `feedback list` groups by topic with open items first and `--json` carries every field; `codeflow status` shows the open count only when the directory exists; `codeflow recall` finds an item by a word in its Verbatim (`feedback_cli`; recall unit test).
- AC-6 A present `INDEX.md` that no longer matches the items yields a `validate --docs` warning naming `feedback list --write`; an absent one yields nothing (`feedback_cli`).
- AC-7 A fresh `codeflow init --full` with this branch's build installs the template, carries the "Operator feedback" subsection outside the per-task chain (`codeflow doctor --check reading` within its guideline, the chain unchanged), names FB ids in `pr-evidence.md`, and `codeflow ids check` with the policy workflow's arguments passes on a registry holding an FB entry (`scaffold_test`; `feedback_cli`; the reading check) (journey).
- AC-8 At the standard and minimal tiers, `codeflow feedback new` refuses with the tier reason and writes nothing (`feedback_cli`).
- AC-9 The `CHANGELOG.md` 3.1.0 section carries the change with its release impact, and `docs/cli.md` matches the generated command reference (`scripts/release.py` checks in the quick gate; the command reference test).
- AC-10 A task pull request that adds a feedback item beside its own record is not refused by the record rule of `codeflow ci`, and one that adds another work record still is (`a_task_pr_may_add_feedback_items_but_no_other_record`; a `codeflow ci` run on a fixture branch).
