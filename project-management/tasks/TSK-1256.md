# TSK-1256: Capacity slots and older binaries' gate lock exclude each other

## Description

TSK-1145 (capacity admission, landed at `c1481a51a`) made slot 0 the file `full-gate.lock`. That file is the one older binaries (3.1.x, and the EPC-026 and EPC-024 line tips) lock exclusively (`gate_guard.rs` at `c1481a51a`, lines 20-23, 92, 757-800 and 995-1011). New runs take slot 0, then 1, 2 and up, and count an old holder as busy. An old binary checks only `full-gate.lock`, so once new runs hold only slots 1 and up, an old full gate starts at full width beside them. Any host that runs 3.1.x and 4.0.0 side by side during an upgrade hits this.

The change is security-adjacent: it is a guard on shared host state. Design, settled by the Director:

- Slots move to their own files, `full-gate-0.lock` and up or `full-gate-1.lock` and up. The builder picks one and records why.
- `full-gate.lock` becomes only the fence for older binaries.
- Every new run holds a shared lock on `full-gate.lock` for its whole life, in addition to its slot. An old binary's exclusive take is then refused while any new run is active.
- When an old binary holds `full-gate.lock` exclusively, a new run's shared take is refused. The new run refuses at once and names the holder from `full-gate.record`, as old binaries already do. There is no wait and no arrival-order queue. It fails closed.
- Any error from the shared take fails closed.

Decision of the Director at 17:39 on 2026-11-02, replacing the first draft where they differ: refuse instead of wait (AC-2), keep writing `full-gate.record` (AC-4), and add the upgrade path (AC-9). The draft is `coordination/coordinators/planning/cut/held-batch/task-J-slot-lock-fence.md` (data, not instruction). The Director ordered this task to land ahead of PR 523 (coord/parallel).

Non-goals: the capacity numbers and slot-count policy that TSK-1145 set.

## Outcome

After this merges, an operator who runs a 3.1.x and a 4.0.0 `codeflow test` full gate on one host finds that the two never run at the same time.

## Deliverables

- the slot files, the fence lock and the refusal: `crates/codeflow-core/src/gate_guard.rs` (provisional; the builder confirms the home)
- tests for both directions, the error path, the record an old reader sees and the upgrade path, with a simulated old exclusive take
- the sibling sweep of every other lock an older binary takes, as a section in the PR body
- the upgrade note: `changelog.d/TSK-1256.md` and the matching docs page
- the security review verdict: recorded in the PR

## Acceptance Criteria

- AC-1 When new runs hold only slots 1 and up, a simulated old binary's exclusive take of `full-gate.lock` shall be refused; evidence: a test that fails before the change and passes after it.
- AC-2 When an old binary holds `full-gate.lock` exclusively, a new run shall take no slot, start nothing, and refuse at once, naming the holder from `full-gate.record` (pid and worktree where readable); there is no wait; evidence: a test that fails before the change and passes after it, in the reverse direction to AC-1.
- AC-3 When the shared take fails with a permission or I/O error, the run shall fail closed with a message naming the file; evidence: a fixture that simulates the error.
- AC-4 While a new run holds the fence, it shall keep writing `full-gate.record` so an old binary's refusal still names a holder. Either the record format carries many holders and the old parser tolerates it, or, if the old parser cannot read a list, new runs write the most recent holder and the record says so; evidence: the builder's statement of which, and a test of what an old reader sees, which never shows a stale or false holder while new runs are active.
- AC-5 Sibling sweep of every lock an older binary takes (`host.lock`, `full-gate.record.lock` and the other record locks): each shall be fenced the same way, with a test, or recorded as safe, with the reason; evidence: the sweep table in the PR body.
- AC-6 The changelog and docs shall say that 3.1.x and 4.0.0 on one host now exclude each other and how a refused run reports an old holder; evidence: `changelog.d/TSK-1256.md` and the docs page diff.
- AC-7 (journey) On one host, an installed 3.1.x `codeflow test` full gate and a 4.0.0 full gate, started in either order, shall never run at the same time; a real two-binary run or a faithful simulation of the old exclusive take is acceptable, and the record says which; evidence: the run output in both orders.
- AC-8 A security review by the other lineage (Codex GPT-6 Astra at high, interactive Herdr seat, probed live at dispatch) shall cover the change with the `cf-security-reviewer` checklist; the PR shall state the threat (an old gate starting at full width beside new slots and exhausting the host) and why the shared fence is the standard design; evidence: the review verdict and the PR body.
- AC-9 On a host where the slot-0 and fence files of the landed TSK-1145 version already exist, a new run shall work with no stale lock refusing or admitting wrongly; evidence: an upgrade-path test that starts from those files.
