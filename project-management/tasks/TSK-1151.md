# TSK-1151: Records-only landing candidates use record checks

## Description

Reuse the planning-range classifier to select landing checks from the candidate diff against the integration line tip. Code changes retain the full gate. This standalone delivery targets EPC-022 for 4.0.0. The draft PR awaits operator approval and cross-lineage review arranged by coord/parallel.

Assignment: Codex builder, then a Claude builder seat for the review fixes; coord/parallel owns review and landing.
Design: N/A, bounded CLI classification and existing rule text.
Estimate: Medium (2 to 4 h), based on classifier reuse, a config key, rule text and tests.

## Outcome

CodeFlow and adopting projects can land records-only candidates after record checks without waiting for an unrelated full gate.

## Deliverables

- Shared classification, config and landing evidence: `crates/codeflow-core/` and `crates/codeflow-cli/`.
- Shipped defaults and rules: `assets/base/` and installed `.codeflow/rules/`.
- Regression coverage: crate tests beside the affected implementation.

## Acceptance Criteria

- AC-1 A project declares its record paths in `git.record_paths` at the line tip; the default is empty, and a project with no declaration, a policy that cannot be read or an empty list keeps the full gate. Only regular non-executable Markdown qualifies, whatever the list says. Evidence: tests for each case.
- AC-2 The class decision fails closed. A path outside the list, a JSON or config file read by a check, a rename or copy from a non-record path, a mode change, any submodule added, removed or moved to another commit at any path, an unchanged symlink or submodule on a record path, a protected or release target or an unreadable diff makes the candidate code, which keeps the full gate. A records-only candidate also runs the project's declared record checks (`execution.record_checks`).
- AC-3 `codeflow ci` and the landing record name the class that applied and why, and the landing record names the checks that ran. `codeflow ci` judges the class only at the line's fetched tip: any other base, or no fetched tip, reports code. `execution.record_checks` is read from the tested commit's blob. Evidence: output tests for both classes and a base past a code commit.
- AC-4 Shipped rules (`git-rules` and `worktrees` Bodies of work, and their `assets/` sources) describe the records-only class; CodeFlow's own copies match after `codeflow update`.
- AC-5 Tests show a records-only candidate takes the short path and each AC-2 case takes the full gate, with fail-before and pass-after where behaviour changes. (journey)
- AC-6 The guidance says that several reviewed units ready on one line build one candidate and run one gate, and states the parallel limits: gates in different worktrees run side by side in capacity slots, only a `host_exclusive` target runs alone, and a binary older than the slots refuses new runs while it holds the lock. Evidence: the text diff.
- AC-7 Each required check that fails (`validate --docs`, `ci` on the range, the secret scan, a declared record check, the quick gate) refuses the landing and leaves the line unchanged. Evidence: a test for each.

## Criteria changes

- AC-1 changed: the default is empty, not task, epic and docs Markdown. Reason: tests read Markdown under `docs/` (for example `manifest_consistency.rs` reads ADR-0018 and `coord_store.rs` includes `docs/coordination-ledger.md`) and run only in the essential or full targets, so a default that covered `docs/` would land an edit that fails them, and a binary upgrade alone would weaken an adopter's gate. Coord/ci decided this when TSK-1306 was folded in.
- AC-1 keeps the Markdown-only rule, stricter than TSK-1306's "unless the project lists it". Reason: a data or config file can be read by a check, and a list should not be able to admit one.
- AC-3 changed: adds the reason, the binding to the fetched tip and the blob read. Reason: a supplied base could hide a candidate's code commits, and a hidden worktree edit could shorten the list.
- AC-6 and AC-7 added, carried from TSK-1306 (issue 476, folded here). AC-7 is TSK-1306's AC-2 evidence for the failing checks.
- TSK-1306's lock-order criterion is not carried. Reason: TSK-1256 replaced the exclusive lock with capacity slots, so there is no queue to reorder. Its parallel-limits text is corrected in AC-6 for the same reason.
- Operator approval, 2026-11-03, on PR 486, relayed by the Director: "1 yes, 2 yes". Item 1 accepts AC-2's text as quoted from this branch. Item 2 accepts the record list `"record_paths": ["project-management/tasks/**/*.md", "project-management/epics/**/*.md"]`. The policy edit itself is the operator's and is not in this task's commits.
