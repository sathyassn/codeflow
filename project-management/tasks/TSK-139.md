# TSK-139: qualify each designated catalog seat version natively

## Description

The managed catalog (`current-ensemble.json`, schema 5) designates seat
versions with empty `qualification` arrays, and `codeflow doctor --check
model-bindings` warns "designated version with no full-suite record" for
each of them. This task runs the native `cf-evaluate-model` full suite for
each designated seat version on each harness the catalog names, and adds the
approved result to that version's `qualification` evidence as each one
passes. A version that fails keeps its designation record unchanged and the
failure is reported to the operator; it is never recorded as qualified.

Trigger (amended 2026-09-28): the first release candidate that contains
EPC-018 and these parts of the harness permission work (settings v8, filed
on `integration/EPC-020-delivery-system`): settings unit 1 (the presets and
the recorded harness floors), settings unit 3 (hook commands with
`--contract` and seat readiness), settings unit 5's D1 spike (which settles
the Codex builder profile) and the evaluation fixture route of operator
decision D10. It runs again for each later designation, harness floor change
or permission profile change. A qualification taken earlier would drift at
once: a binding record pins the harness version and settings digests, and
`codeflow doctor --check model-bindings` reports a change in either
(`crates/codeflow-core/src/doctor/mod.rs:672-724`); the evaluation protocol
treats a changed launch envelope as a new cohort
(`cf-evaluate-model/resources/protocol.md:13-16`).

Inputs from TSK-078's identity canary
(`docs/verification/tsk-078-autonomy-catalog.md`): the Claude pinned and
alias launches served the designated ids; the Grok launch requested
`grok-4.7` and its session record named `grok-4.7-build` as the served
model, which is recorded as drift until settled; `gpt-6-astra` and
`gpt-6-sol` were observed at high in the session records of running Codex
review seats (Codex records the requested model, not a served id); and
`gpt-5.6-sol` and `gpt-6-luna` were not observed at all, so they carry
reduced assurance until this task observes them. That canary ran Grok CLI
1.0.34 and read Codex seats running 0.155.1, below the tested floors, so its
sessions are identity evidence only and are never reused as qualification.

Codex permission profiles: under settings decisions D1 and D2 the
`codex-primary` seat launches under two profiles, the reviewer profile
(`--ask-for-approval never` under `cf-guard`) and the builder profile
(`cf-builder` if the D1 spike passes, otherwise full access). Each profile is
qualified separately.

Non-goal: changing designations, seats or duties.

## Acceptance Criteria

- AC-1 For each designated seat version, harness and permission profile the
  seat's duties launch under (for `codex-primary`, the reviewer profile and
  the builder profile as settings unit 5's D1 spike settles it, each
  separately), a native full-suite result whose requested and observed
  model, effort and permission profile match shall be approved, taken on a
  CodeFlow revision that contains the settings units named in the trigger,
  or the version and profile shall be reported not qualified with the
  reason; evidence: the scored result files, with `permission_profile` set
  in each, and `eval_kit.py` validation output.
- AC-2 Each result shall come from a harness at or above the tested floor
  that settings unit 1 records: Grok CLI 1.0.41 and Codex CLI 0.157.1, and
  the Claude Code floor as unit 1 records it; a harness below its floor is
  upgraded first or its rows are reported not run; evidence: the
  `harness_version` in each result and the recorded floors.
- AC-3 Each passing version's catalog entry shall carry its qualification
  record, and `codeflow doctor --check model-bindings` shall no longer warn
  for it; evidence: the doctor output before and after.
- AC-4 `gpt-5.6-sol` (high) and `gpt-6-luna` (medium), unobserved at
  TSK-078, shall be launched natively by pinned id with requested and
  observed model and effort recorded, or stay recorded as unavailable with
  the reason; evidence: the verification record.
- AC-5 The Grok served-id question (`grok-4.7` requested, `grok-4.7-build`
  recorded) shall be settled as a naming of the same version or as drift
  under the ADR-0069 rule; evidence: the vendor record and the decision.
