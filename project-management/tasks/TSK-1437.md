# TSK-1437: A marked epic's line reaches the default branch only when the epic is complete

## Description

Under ADR-0102 a marked epic reaches the default branch once, complete. Today nothing gates a line's pull request into the default branch on the epic's state: the line binding accepts any epic that is not cancelled or archived (`crates/codeflow-core/src/workgraph/work_start.rs:699-724` and `:1279` on `main` at `f8aabc62c`). This task adds the marker to the epic record and a gate in `codeflow ci` that passes a marked epic's line pull request only when the epic is complete, with its proof and whole-epic review on a commit that holds the default branch's tip. An epic without the marker keeps checkpoint pull requests until it closes: those epics, EPC-022 among them, are already in flight, and holding their finished work until a large epic closes would park it on a line.

How the marker is enforced:

- The marker is a field on the epic record, proposed as `main_landing` with the values `whole-epic` and `checkpoint-prs`; an absent field means `checkpoint-prs`, so every epic planned before the release is unmarked. The epic template documents it and `codeflow epic new` can write it; TSK-1443 sets `whole-epic` as the default for new epics after the release.
- `codeflow ci` reads it only from the epic record at the default branch's tip, resolved once per run (the authority rule of ADR-0091), never from the line, the pull request head or the working tree.
- Moved to TSK-1433 on 2026-11-12 by the Director's ruling: the marker read and the field's final name and values. This task uses TSK-1433's read and keeps the template, `codeflow epic new`, the refusal of marker changes off the default branch, and the gate on the line's pull request.
- It is set or cleared only by a planning range into the default branch. A range into any other branch that adds, removes or changes it is refused.
- The planning anchor for a marked epic's criteria is the same default-branch copy, so a line cannot reword its own epic's criteria.

Landing on its target (the line, then `main` with the epic):

- Reachable on the line: the marker and the gate.
- Inert until an epic carries the marker. Records sets `main_landing: whole-epic` on every open epic that has a line (planning landing to `main`), so the gate binds each of them from the first line pull request after that.
- Other lines: nothing else changes. A task that lands alone into `main` is judged as today.

Target: this record targets `main` until EPC-055's line is cut. The line is cut from the default branch tip when this task's first part (the marker field, the template, `codeflow epic new` and the marker refusal) is ready to land; it does not wait for the guard fixes or PR 620. After the cut the record is retargeted to that line and its tasks land on it with no pull request.

Milestone lines (Director's rulings of 2026-11-20): `checkpoint-prs` is for milestone lines only, set explicitly (AC-12), and EPC-022 is the one milestone line named today. Every other epic line is `whole-epic`. EPC-022 reaches `main` in milestone checkpoints until its checkpoint is done; it carries no marker now and is marked after the TSK-1513 sync and its next checkpoint.

The line base of AC-11 (settled 2026-11-20 at the Director's request): the existing claim base does not serve. `codeflow work claim` records its base in the local ref `refs/codeflow/claims/<branch>` (`crates/codeflow-core/src/workgraph/claim_base.rs:175-176` on `main` at `8e1a7b27f8`, called from `work_start.rs:2295`). That holds an exact commit, but for one task branch, and the module calls it "local evidence shared by linked worktrees, not a planning authority" (`claim_base.rs:5`), so a line pull request judged in CI cannot read it. The cut therefore records the base, as AC-11 says.

Waits for TSK-1158's and TSK-1061's work on `main`: their records are on `main`, their work is on the EPC-022 line.

## Outcome

After this merges, a maintainer can mark an epic so that its line reaches the default branch only when every task is complete and its proof and review hold the default branch's tip, while unmarked epics keep their checkpoint pull requests.

## Acceptance Criteria

- AC-1 Before any change, the builder shall record whether epic criteria are frozen after planning as task criteria are (`acceptance.rs:4891-4906` on `main` at `f8aabc62c`), and close the gap if they are not; evidence: a `## Findings` section and a fixture.
- AC-2 For a marked epic, `codeflow ci` shall refuse the line's pull request into the default branch while any task of the epic is todo or blocked, computed from the records; evidence: a one-open-task fixture (issue 770's done-when).
- AC-3 For a marked epic, the line's pull request shall be refused when the epic's criteria differ from the default branch's copy without a recorded amendment; evidence: a fixture (issue 770's done-when).
- AC-4 For a marked epic, the line's pull request shall be refused unless the proof commit contains the default branch's tip and the whole-epic review names that commit, with only the completion record after it; evidence: fixtures for a stale proof and for a later commit.
- AC-5 For a marked epic, the line's pull request shall be refused unless every removed criterion, moved task and cancellation has a reviewed disposition in TSK-1158's waiver form; evidence: fixtures.
- AC-6 A complete marked epic's line pull request shall pass; evidence: a fixture.
- AC-7 An epic that carries no marker shall be judged exactly as today: its pull request into the default branch (a checkpoint of its line) passes or fails by the rules in force before this change; evidence: a fixture that passes before and after the change. (A line is a single delivery unit once marked; an unmarked epic is a legacy epic and keeps its checkpoint pull requests.)

- AC-8 Each planted negative shall be refused naming its cause: a line that sets the marker on its own epic record; a line that removes the marker; a pull request head whose epic copy carries the marker while the default branch's copy does not, which is judged unmarked and the head's change refused; and a default-branch copy that cannot be read, which is refused and never judged unmarked; evidence: one fixture each.
- AC-9 A task that lands alone into `main` shall be judged as today, and a task of a marked epic shall not be offered that route: a pull request from a task branch of a marked epic into `main` is refused naming the epic and its line; evidence: two fixtures.
  - Amended 2026-11-20 (planning amendment). Was: "A task that lands alone into `main` shall be judged as today; evidence: a fixture." Reason: under the operator's ruling of 2026-11-20 a task of an epic with a line reaches `main` only with its line, so a marked epic's task pull request into `main` is refused; text from coord/catalog's criteria note of 2026-11-20 (same file).
- AC-10 The change shall have a cross-lineage review with the `cf-security-reviewer` checklist, with the threat each marker rule closes stated in the pull request; evidence: the review row and its findings. (serves EPC-055 AC-3)
- AC-11 (line cut) A marked epic's line shall be cut from the default branch's tip, and the cut shall record that tip as the line's base in the epic's record or the line's first commit; a line that does not descend from a default-branch commit named in its epic's record is refused as a line pull request; evidence: a fixture for a line cut from the tip and one for a line cut from a stale commit that has no record. Cutting is a planning step done through `codeflow work start` or the epic command, never by hand.
- AC-12 (milestone checkpoint) An epic whose record names itself a milestone (`main_landing: checkpoint-prs`, explicitly set rather than absent) may reach the default branch in checkpoints; each checkpoint pull request shall pass the same close check as a whole epic for the tasks it carries (every carried task complete, proof commit holds the default branch's tip, one cross-lineage review names that commit) and leaves the epic open; evidence: a fixture for a passing checkpoint and one for a checkpoint that carries an open task.
