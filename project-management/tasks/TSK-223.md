# TSK-223: local checks match hosted CI and exec-guard judges only what runs

## Description

Two consumer reports show a local check disagreeing with what it should
judge. Report sathyassn/codeflow#50: the pre-push hook's `codeflow ci` run
classifies a range only when a pull request body is given
(`crates/codeflow-cli/src/cmd/ci.rs` `work_checks`), so it never reaches
the `work.journey_criterion` rule, which needs only the task record and
the range; hosted CI blocks the same range after the pull request opens.
The journey refusal also says a task "has no `(journey)` criterion" when a
criterion carries the tag in the middle of its text, without naming the
rule that the tag must open or close the criterion (R-50). Report
sathyassn/codeflow#52: when a line holds a command exec-guard cannot
resolve, such as a variable as the program, the headless-peer classifier
(`crates/codeflow-core/src/security/headless.rs`) judges the raw text of
the whole line, heredoc bodies and quoted messages included, and flags a
peer name followed by any later marker word, so a review brief or commit
message that only names Codex and the word review is refused as a
headless run. This task builds on TSK-212's pre-push mechanism (the
default-tip policy authority and range) rather than adding a second one.
Non-goals: the policy level of `security.headless_peer_runs` does not
change, every real headless run stays refused, and git-guard's shell
reader (`hooks/git_guard.rs`) is not changed.

## Deliverables

- Bodyless journey check: `crates/codeflow-cli/src/cmd/ci.rs`, `crates/codeflow-cli/src/cmd/ci/classification.rs`
- Journey refusal naming a mid-text tag: `crates/codeflow-core/src/workgraph/acceptance.rs`, `crates/codeflow-core/src/workgraph/record_text.rs`
- Narrower headless fallback: `crates/codeflow-core/src/security/headless.rs`
- Tests: `crates/codeflow-cli/tests/acceptance_journey.rs`, `crates/codeflow-cli/tests/hooks_cli.rs`, unit tests in the files above
- Release note: the pending 3.1.0 entries in `CHANGELOG.md`

## Acceptance Criteria

- AC-1 When a pushed task branch's range changes the adopter-facing path
  set and its task has no journey criterion, the pre-push hook's
  `codeflow ci` run refuses the push on `work.journey_criterion` with the
  same finding that `codeflow ci` reports for that range with the pull
  request body; evidence: a journey test on a fresh `init --full` project
  that pushes a standalone task branch through the installed pre-push
  hook to a local destination and runs `codeflow ci` with the filled
  template over the same range, comparing the journey findings, let
  through by the hook before the change and refused after, with a task
  that has a journey criterion passing both paths. (journey)
- AC-2 When a criterion carries `(journey)` inside its text but neither
  opens nor closes with it, the journey refusal names that criterion and
  says the tag counts only where it opens or closes the criterion;
  evidence: the acceptance_journey tag test asserting the message, failing
  before the change.
- AC-3 When exec-guard cannot fully resolve a line, it judges only what
  the line can run: heredoc bodies and quoted text that only name a peer,
  such as a review brief written with `cat` beside a variable program or
  a commit message naming a model, are let through, and a variable or
  substitution program is judged by its own arguments; evidence: unit
  tests in `headless.rs` for the reported texts and a `hooks_cli` test
  running the reproduction through `codeflow hook exec-guard`, each
  refused before the change and allowed after.
- AC-4 Every headless peer run refused before this change is still
  refused, including `$CMD exec`, `$(printf claude) -p`, an alias, a
  here-string or pipe into a shell, a heredoc script body, a script
  written and then run in the same line, and interpreter code that runs a
  peer; evidence: the existing headless, interpreter and exec-guard unit
  tests unchanged and passing, plus new controls.
- AC-5 The pending 3.1.0 CHANGELOG entries, under their release-impact
  markers, state the journey check on push, the clearer journey message
  and the narrower exec-guard fallback; evidence: the diff and the
  release-impact check.
