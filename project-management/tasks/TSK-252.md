# TSK-252: An after-release epic criterion closes as deferred while its follow-up task serves it

## Description

An epic criterion tagged `(after release)` is observable only after the epic
lands, so its natural follow-up task serves it and can only run later. Epic
close (`epic_criterion_verified` in `crates/codeflow-core/src/workgraph/lifecycle.rs`)
accepted a serving task's result alone once any task served the criterion, so
a valid `deferred` line in the epic's acceptance block was ignored and the
epic could never close (sathyassn/codeflow#106). This task makes the epic
block's valid `deferred` line (owner, window, follow-up) close an after-release
criterion whose serving tasks have not completed, when the line's follow-up is
a serving task that is still open and is listed in `follow_ups`. A complete
serving task's `verified` or `waived` result still wins, and every other
refusal stays. `validate`, `ci` and `epic status complete` share this judgment,
so one change covers them. Non-goal: a follow-up that is a member of the same
epic still blocks close through "every task terminal"; the docs say the
follow-up is filed outside the epic.

## Deliverables

- the fix: `crates/codeflow-core/src/workgraph/lifecycle.rs`, `crates/codeflow-core/src/workgraph/record_text.rs`

- AC-1 When an `(after release)` epic criterion is served by a task that is not complete and the epic's acceptance block defers it with an owner, a window and a `follow-up` that names a serving task which is still open and listed in `follow_ups`, epic close shall accept the criterion. Evidence: a lifecycle regression test that fails before the fix and passes after, run through `set_status` on the epic.
- AC-2 While a complete serving task's `verified` or `waived` result exists, it shall decide the criterion as before, and the epic close shall still refuse an after-release criterion when it is not tagged `(after release)`, when the deferred line names a task that does not serve it while another open task does, when the named follow-up is complete or cancelled, when the deferred line lacks its owner, window or follow-up, or when the follow-up is not listed in `follow_ups`. Evidence: one control test per refusal in `lifecycle_tests.rs`.
- AC-3 (journey) When an epic with an `(after release)` criterion and a `todo` task serving it closes with `codeflow epic status EPC-001 complete --acceptance <block>` carrying the documented `deferred` line, the command shall succeed with the built binary, and the same command shall still refuse for a criterion that is not after-release and for a follow-up that does not serve it. Evidence: the issue's reproduction driven through the Cargo-built `codeflow` binary in a temp repository, which is the CLI test in `classification_cli.rs`, ending in `codeflow ci` on the closed epic.
- AC-4 When a reader looks up how an after-release criterion closes, SPC-013 R-33 and R-62 and the cf-method project-organization reference shall state the rule, and the managed baseline shall match the mirrors. Evidence: `codeflow validate --docs`, `manifest_consistency`, and a byte compare of the `.claude` and `.agents` mirrors.
