# TSK-1318: Windows fence test reads process handles and reports timing

## Description

The hosted Windows test `a_killed_gates_target_tree_ends_before_older_binaries_get_in` failed once at line tip `fe66d4c62` (codeflow-ci run 41763959485, job 126359726029): an older take of `full-gate.lock` succeeded while `tasklist` still listed a process of the killed gate's tree. That reading cannot separate a live process from a dying one or from a recycled process ID, and `tasklist` takes long enough that it acts as a hidden delay in the test. This task replaces the reading with process handles opened before the kill and reports the timing that TSK-1317 needs. It also corrects the three texts that claim more than the code provides (`docs/troubleshooting.md`, two comments in `crates/codeflow-core/src/testing/runner/mod.rs`).

Hosted run 41879206447 (job 126773778322) then showed the gap itself: the killed gate ended 36 ms after the kill, an older take succeeded at 37 ms, and the grandchild and target ended at 43 ms and 53 ms. The Director's ruling of 15:47 on 2026-11-04, relayed by coord/ci, folds the fix into this task. The lock frees only after the gate's whole process tree has ended. On Windows that uses the job object's own report of no active process (`JOB_OBJECT_MSG_ACTIVE_PROCESS_ZERO`, with `ActiveProcesses` as a backstop), never a watcher polling process IDs. On Unix the run's watcher waits until the process group is empty. The test stays strict. TSK-1317's criteria fold into this record in the next EPC-022 planning PR (coord/records).

Non-goals: loosening the test's assertion; the other Windows callers of `still_runs`; Unix targets that are not heavy, whose inherited fence copies already last while any process that kept them runs.

The test may fail more often after this change. That is accurate and is not a reason to rerun until green: a red run is diagnosed from its timing data (Director's ruling of 22:31 on 2026-11-03, relayed by coord/ci).

## Outcome

After this merges, an operator who kills a gate finds that an older CodeFlow gate cannot start until that gate's whole process tree has ended, so two builds cannot share a target folder. coord/ci can read the timing from any hosted Windows run.

## Deliverables

- the handle-based reading and the timing report: `crates/codeflow-cli/tests/test_gate_cli.rs`

## Acceptance Criteria

- AC-1 When the test reads whether the target or its grandchild is alive, it shall use a handle to that process opened before the gate is killed and `WaitForSingleObject(handle, 0)`, so a recycled process ID or a listing delay cannot change the reading, and the assertion that no process of the tree is alive after a successful take shall stay as strict as it was; evidence: the test source and review of its diff.
- AC-2 When the assertion fails, the message shall name each process still alive by role and process ID and give the kill-to-take time and each process's kill-to-end time; when the test passes, the same timing shall appear in the hosted log; evidence: the test source, `.config/nextest.toml` and a hosted Windows job log.
- AC-3 The troubleshooting page, the two `runner/mod.rs` comments and the `gate_guard.rs` module notes shall state the guarantee as built: on Windows a watcher outside the job holds the fence until the job is empty, and a killed watcher lets the fence free with the gate; on Unix a heavy target's watcher keeps the run's locks until its group is empty; evidence: the diff and `guide_altitude_budget`. Changed from "what is guaranteed until TSK-1317 lands", because the Director's 15:47 ruling folds that fix into this task.
- AC-4 (journey) The changed test shall run on the hosted Windows partition, and the PR body shall report its timing and its result, pass or fail; evidence: the hosted job log. This host is macOS, so no local run can stand in for it.
- AC-5 Given a Windows gate that holds a fence, when it starts a target, a watcher process outside the target's job shall hold every fence shared before the target resumes. When the gate ends or signals the watcher's release event, the watcher shall end the job and exit only after the job reports no active process, through `JOB_OBJECT_MSG_ACTIVE_PROCESS_ZERO` on a completion port with `ActiveProcesses` as a backstop, never by polling process IDs. `a_killed_gates_target_tree_ends_before_older_binaries_get_in` shall pass on hosted Windows with its assertion unchanged, its timing showing the take after the last process end; evidence: `runner/job_watch.rs` and the hosted job log (Director's ruling of 15:47 on 2026-11-04).
- AC-6 When the watcher cannot start, cannot copy the job's handle, or cannot hold a fence, the target shall not run and the run shall refuse, naming the fence watcher and the target; evidence: `a_watcher_that_cannot_start_stops_the_target_before_its_command_runs` on hosted Windows.
- AC-7 On Unix, the watcher of a heavy quick target or reserved command shall keep its copies of the run's locks until `kill(-group, 0)` reports `ESRCH`, with a sentinel keeping the group's id reserved while the watcher leaves the group; a fail-before unit test, in which a group member the test leaves as a zombie keeps the fence held until it is reaped, shall pass; evidence: `the_fence_frees_only_after_the_whole_group_has_ended`.
  - Amended 2026-11-04: on Unix, the fence frees when the killed gate's process group is gone, or when every member is positively confirmed to be a zombie; a member that cannot be read counts as alive, which keeps it fail-closed (Director's ruling, 18:5x).
- AC-8 On Windows, `cpu_work_without_output_can_outlast_the_stall_window` shall not be made flaky by shell startup or exit: its CPU work shall run for several one-second stall windows in a process with no `PowerShell` phase, and shall pass. The supervisor's rule shall stay unchanged, so that a target with no job CPU and no output for a full window is reported stalled, and a deterministic test with injected samples shall pin both sides: rising CPU outlasts the window, and a flat window stalls; evidence: `rising_cpu_outlasts_the_window_and_a_flat_window_stalls` and the hosted Windows job log.
  - Amended 2026-11-05: the Director placed this criterion here from PR 607's push run, where the test read `Stalled` in job 127544514574 (run 42103440628, commit 1107c5974) with `cpu_usec` 2312500 and `cpu_state` `Idle`. The target had used CPU, then Windows `PowerShell` stayed alive for at least a second with no CPU while it started or exited. The supervisor needs no change: the default window is 300 s, and at a 1 s window that gap cannot be told apart from an idle target.
- AC-9 `target_repository::earlier_writes_make_the_next_runner_state_unknown` shall not depend on runner speed. When a Git child the guard runs outlives its 3 s bound, the guard's fail-closed refusal shall stay, and the test shall accept that refusal, and only that refusal, for a command it otherwise expects to pass, while at least one such command still passes. The guard's 3 s limit for users shall stay unchanged. A deterministic test with a `git` on `PATH` that sleeps shall show the refusal, which the old exact-pass assertion fails on, and shall show that any other refusal is still a failure; evidence: `a_slow_git_child_is_refused_and_only_that_refusal_is_tolerated` and the hosted Windows job log.
  - Added 2026-11-05: the Director placed this criterion here from PR 607's job 127565744853, where git-guard refused `printf x > notes.txt && git -C . status` with "cannot verify Git configuration: child exceeded 3 seconds" on a busy Windows runner (`hooks_cli/target_repository.rs:4445`), and 111 of 112 tests in the partition passed.
