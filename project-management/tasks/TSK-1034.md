# TSK-1034: A non-trivial project uses its standard framework, in proportion

## Description

The operator's quality asks of 2026-10-27, frameworks (D5); no issue or
task existed. Adopters' agents build non-trivial user-facing surfaces as
hand-written vanilla JavaScript, HTML and CSS (issue #275's evidence:
about 450 plain JS and MJS gate and prototype files in one repository),
and nothing in `cf-stack` or `cf-design` says when a project should use
its type's standard framework instead. CodeFlow's own runtimes point
both ways: the present web is Preact with TypeScript and esbuild, the
docs portal is Astro with Starlight, but the shipped `cf-present` and
`cf-docs-portal` design-system kits are a 1,357-line hand-written
`chrome.js` that works with no build step, and an agent may read that
kit as the model for product code.

Outcome: **`cf-stack` and `cf-design` tell an agent to use the project
type's standard framework (and its component, routing, state and build
tooling) for a non-trivial project instead of hand-written vanilla
JavaScript, HTML and CSS; a proportionality rule says when plain code is
right (a one-page tool, a trivial script, a static page with no
interaction); and the guidance states CodeFlow's position on its own
bounded runtimes such as `cf-present`.**

Rules:

- "Standard framework" is chosen per project type and stack from
  current practice and the project's existing choice; the guidance names
  the decision criteria and examples, not one framework for everyone.
  An existing framework in the project is reused.
- Adopting a new framework in an existing project is a stack decision
  the owner approves (`cf-stack` step 1); the guidance says so.
- The position on CodeFlow's own runtimes says why each is built the way
  it is (for example, a reference kit that must open from a folder with
  no build step) and that it is not a model for product code, or changes
  it where AC-1 finds no such reason. Rebuilding a runtime is out of
  scope and becomes a tracked item if AC-1 recommends it.

Non-goals: the strict typing defaults (TSK-1032, TSK-426); rewriting
adopters' existing surfaces; rebuilding `cf-present` or the docs portal.

## Acceptance Criteria

- AC-1 Before any change, the builder shall research framework choice broadly: current practice across the project types CodeFlow serves (web applications and sites, static documentation, dashboards and internal tools, desktop and mobile, CLIs with a UI, browser extensions; React, Preact, Vue, Svelte, Solid, Angular, Astro, Next and similar, and server-rendered stacks), when plain HTML, CSS and JavaScript or web components remain the better choice, the CodeFlow guidance and runtimes in the survey above, and adjacent concerns (bundle size, accessibility, testing and browser tooling, typed templates, dependency and supply-chain cost); shall record where the guidance applies to projects with no user interface (CLIs, libraries, services, infrastructure and data pipelines, for example their standard CLI, web-service or test frameworks) or why it is limited to user-facing surfaces; and shall record the findings with sources and the chosen scope before any guidance changes; evidence: the note or record section, committed before the first guidance change in the PR.
- AC-2 `cf-stack` and `cf-design` shall tell an agent to use the project type's standard framework for a non-trivial project, with the criteria that make a project non-trivial and the owner approval a new framework needs; evidence: the text diff and a `cf-editorial-review` pass. (serves EPC-022 AC-142)
- AC-3 The guidance shall state the proportionality rule: a one-page tool, a trivial script or a static page with no interaction may stay plain, with the signals that say it has outgrown that; evidence: the text diff. (serves EPC-022 AC-142)
- AC-4 The guidance shall state CodeFlow's position on its own bounded runtimes (`cf-present`, the design-system kits, the docs portal): why each is built as it is and that the kits are not a model for product code, or a recorded change where AC-1 finds no reason; evidence: the text diff and, where a change is recommended, its tracked item. (serves EPC-022 AC-142)
- AC-5 Native instruction qualification under `/cf-evaluate-model` shall include a case where a builder starts a multi-view web surface on the project's framework, and one where a one-page tool stays plain; evidence: the qualification record.
- AC-6 (journey) A fresh `codeflow init --standard` project and a project updated from 3.1.1 shall carry the new text with every pointer resolving; evidence: the journey output.
