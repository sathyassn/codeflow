# TSK-1315: Generated branch names stay readable under a sandbox, and doctor names a refused ref

## Description

A loose ref is a file named after its branch, and a sandbox can refuse to read a file by its name. On 2026-11-03 the Claude Code sandbox refused the loose ref of a generated branch whose title held the word "secret". Git reported the ref as broken, the worktree's HEAD as zeros and all 3732 files as staged additions, and `git fetch --dry-run origin` failed from every worktree with `fatal: bad object`. Outside the sandbox the repository was healthy, and an audit read this as corruption. `work claim` generated that name, and neither `doctor` nor `status` said what had happened. This task changes generated branch names, including `epic new --integration` as the sibling generator, and the `doctor` and `status` reports. ADR file names keep the plain slug, tracked file names stay as they are, and sandbox settings do not change.

## Outcome

After this merges, a person using a sandboxed harness can work on generated branches git can read, and is told that a refused ref is a refused read when one exists.

## Findings

Probed under the sandbox, inside the workspace, on 2026-11-03:

- Any file name holding `secret` or `credentials` is refused, by substring (`secretive`, `my-credentials-x`). As slug words, `credential`, `token`, `password` and `key` stayed readable.
- The cause of the substring match was not found. The rules read in the workspace settings do not explain a refused name with no extension or a `.rs` extension, and the sandbox's full deny list was not visible, so the default list rests on the probe.
- In a clean checkout with a refused tracked file, the installed `status` says `preserve-dirty` with `local changes present`. Keeping the worktree is the safe outcome, so the disposition stays, and only the stated reason changes.
- Considered and rejected: naming `git pack-refs --all` as a remedy. It cleared the failure in a test repository, but a shipped tool should not teach a way to move a ref out of reach of a sandbox's read deny. The report offers only the rename, run outside the sandbox.
- `status` scans refs and reflogs only. One open per tracked file on every run is a real cost, as `status` already took over 120 seconds on this repository under load, and a tracked-file note has low value there. `doctor` scans tracked files as well.

## Acceptance Criteria

- AC-1 When `codeflow work claim` generates a branch name from a title holding a configured word, the name shall leave that word out and the command shall print which words it left out; evidence: `claim_leaves_a_sandbox_denied_word_out_of_the_branch_name_and_says_so` and `claim_says_nothing_when_it_left_nothing_out` in `work_cli.rs`. (journey)
- AC-2 The word list shall be the policy key `git.branch_name_omit_words`, a configurable default that a project can replace or empty, with no harness named in the code path that applies it; evidence: `claim_follows_the_project_word_list`, `branch_name_omit_words_accepts_words_and_rejects_what_a_word_cannot_match`, and the policy reference row that `codeflow validate --docs` checks against the schema.
- AC-3 A test shall reproduce the failed read: a mode 000 loose ref in a test repository makes real git report `bad ref` and a HEAD of zeros, the symptoms probed under the sandbox. A test cannot start the sandbox, and the sandbox gives EPERM where a mode gives EACCES, so the unit tests inject EPERM; evidence: `crates/codeflow-cli/tests/unreadable_ref_report.rs` and the tests in `crates/codeflow-core/src/git/unreadable.rs`.
- AC-4 While a ref file exists that this process is refused, `codeflow doctor --check repo-integrity` and `codeflow status` shall name that ref and say this is not evidence of repository damage, and `doctor` shall name a refused tracked file the same way without asking for a change; evidence: `doctor_and_status_name_a_ref_git_calls_broken_and_never_call_it_damage`, `a_refused_tracked_file_is_named_and_asks_nothing`, and a run of the built binary under the sandbox on a test repository. (journey)
- AC-5 `codeflow status` shall not open every tracked file on a run; when a checkout reads as dirty only because of files this process is refused, it shall keep that worktree and say so instead of `local changes present`; evidence: `the_refs_scan_leaves_tracked_files_alone`, `is_refused_is_true_only_for_a_refused_read`, and the same sandbox run, since a mode of 000 does not make libgit2 report a file as changed. (journey)
