# TSK-1071: Coverage shard drift is reported in CI before a shard overruns

## Description

Source: the Limits section of TSK-1063 (PR 399, branch
`task/TSK-1063-every-windows-test-partition-finishes-well-insid`), after its
Codex review. TSK-1063 gives the Windows partitions a drift check that runs
in the `windows test build` job, where the test list exists before any
partition starts. The Linux coverage shards (`gates-coverage`, two shards,
TSK-270) share the same planner but not that protection. TSK-1063 records:

- the shards keep the rest-shard rule: each shard job builds and runs in one
  job, before any test list exists, so a test the measurements do not know
  runs in the rest shard;
- `scripts/coverage-shards.py drift --list <nextest list json>` exists but is
  run by hand and is not in CI, because no coverage job holds a test list
  before its shard runs;
- the report job's `check` already fails a shard whose test minutes pass 18
  (24 job minutes with 6 of build and setup), but it runs after the shards,
  so it reports an overrun and cannot prevent it;
- the shards sat inside the 24 minute bound in the six line runs TSK-1063
  read (highest 17.6 job minutes), with data that had drifted (about 90
  summed minutes measured against 40 planned) and an uneven split in single
  runs (53.0 against 28.6 summed minutes in run 40839551888).

TSK-1063 asked the coordinator to file this follow-up because none of the
open CI tasks owns this repository's own coverage shards: TSK-384 covers the
shipped managed workflow, and TSK-343 excludes hosted shard changes.

Scope: this repository's own Linux coverage shards, in
`.github/workflows/codeflow-ci.yml`, `scripts/coverage-shards.py` and its
data `scripts/coverage-test-times.json`. Not the managed workflow
`assets/base/ci/codeflow-ci.yml` (TSK-384) and not the Windows partitions
(TSK-1063).

Leads for the investigation, none confirmed. They are options for the
builder to measure, not a chosen design:

- the `windows test build` job (or a Linux equivalent) already lists the
  suite; a drift job on Linux that reads a list before the shards start,
  with the cost of building the list on Linux counted against the 12 minute
  verdict goal of TSK-270;
- tests that exist only on one platform (`cfg(unix)`, `cfg(windows)`) make a
  Windows list a partial answer for the Linux shards, which the check would
  have to account for;
- the drift check run after the shards, in the report job, from the shards'
  own lists, which is cheaper but is not "before a shard overruns"; it
  counts only as a stated fallback if the builder shows the earlier check
  cannot be built;
- a scheduled run of the check, to be weighed against the same limit.

The task ends in one of two states, decided by the investigation (AC-1):
shard drift is detected in CI before a shard can overrun, or the task records
why it cannot be and what the shipped checks do instead. Raising a shard
timeout alone is not a fix.

## Outcome

After this merges, a maintainer is told in CI, before a coverage shard runs long enough to time out, when the shard data no longer covers the suite, or the record states why that cannot be done and which check catches the drift instead.

## Deliverables

- investigation findings with the measured cost of each option: a `## Findings` section in this record
- the CI check, if one can be built: `.github/workflows/codeflow-ci.yml` (a step or job ahead of `gates-coverage`) and `scripts/coverage-shards.py`
- its tests: `scripts/test_windows_partitions.py` (which also runs the planner for the shards) or a sibling test file
- refreshed shard data, only if the check needs it on the current suite: `scripts/coverage-test-times.json`
- the no-check outcome, if it applies: the stated reason in this record and the comment on the coverage jobs in `.github/workflows/codeflow-ci.yml`

## Acceptance Criteria

- AC-1 Before any change, the builder shall record in the Findings, from TSK-1063's merged state and at least five recent hosted runs (run ids named): how many tests the shard data does not cover on the current suite, how far each shard's real time is from its planned estimate, the build and list cost on Linux for each option in the Description, and whether any option gives a test list before a shard starts without lengthening the gates verdict past TSK-270's 12 minute goal; evidence: the Findings section, committed before the first code change.
- AC-2 If AC-1 finds a pre-shard option that holds, CI shall run `coverage-shards.py drift` on a test list before the first coverage shard starts, and shall fail, naming the refresh command, when the data leaves more than the stated share of tests unmeasured, when a shard is planned past its stated bound, or when the filterset passes the command line limit; evidence: a unit test for each condition failing before and passing after, and the check's output on the current data in a hosted run. (serves EPC-022 AC-162)
- AC-3 A planted unmeasured set that would push one shard past its bound shall fail the check in CI before any shard runs, and a run on the current data shall pass; evidence: a unit test with the planted set, and the hosted run of the passing case; for a workflow-level claim, a structural test that the check step exists, runs before `gates-coverage` and is a dependency of the `codeflow gates` verdict, so it cannot be deleted without a failing test. (serves EPC-022 AC-162)
- AC-4 If AC-1 finds that no earlier check can be built within the verdict goal, the record shall state the reason with the measured costs, name the check that catches the drift instead (the report job's 18 test minute `check`, or a cheaper after-the-fact drift report from the shards' own lists), and the workflow comment on the coverage jobs shall say the same; evidence: the Findings and the workflow comment, and for any added after-the-fact report a unit test. (serves EPC-022 AC-162)
- AC-5 Every test shall still run in exactly one shard and the shards' existing checks shall keep their verdicts; evidence: `coverage-shards.py check` on the hosted run of this task's pull request, and TSK-1063's Windows tests passing unchanged. (serves EPC-022 AC-162)
- AC-6 (journey) The hosted run of this task's pull request and of the landing candidate shall each show the check's verdict and the two shards' job times against the 24 minute bound, with run ids and job times recorded; evidence: the run ids and job times in the PR.
