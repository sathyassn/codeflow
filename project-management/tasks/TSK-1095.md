# TSK-1095: codeflow report progress computes percent complete, order, lanes, estimates and issues for any scope

## Description

The operator asked on 2026-10-30 for a command or skill that reports the
status of work properly each time it is asked, in any project that adopts
CodeFlow: what is being worked on with just the right context, the epics
and tasks involved, percent complete at each level (the epic, the task and
the overall scope), the lanes a coordinator runs and the overall across
them, the order work is done in, the expected time to completion for each
item, and the issues for each item. Nothing computes this today:
`codeflow status` prints counts from the working tree with no JSON
(`crates/codeflow-cli/src/cmd/status.rs:7-17`), `work next` prints
readiness (`crates/codeflow-core/src/workgraph/readiness.rs:27-48`), and
`report ceremony` is the only report
(`crates/codeflow-cli/src/cmd/report.rs:17-22`). Every session writes its
own status by hand, with the stale facts the writing rule warns about.

This task is the engine: one read-only command that computes the facts
and prints them as text and JSON. TSK-1098 renders them as a figure-led
`cf-present` document and TSK-1099 is the skill that answers a status
request with them. Shape decided in planning, open to the builder's
investigation (AC-1):

```text
  records (project-management/)      git (refs, worktrees, merges)
        \                                   /
         v                                 v
   scope  ->  stage ladder per task  ->  percent per level
     |          |                          |
     |          v                          v
     |      order (depends_on, ready set, critical path)
     |          |
     v          v
   lanes (ledger lanes when present, else observed) -> per lane and overall
     |
     v
   estimates (adopted forecast, else planned-throughput scenarios, basis named)
     |
     v
   issues per item (blocked, waiting, red or missing check, awaiting operator,
                    stale, deferred result), each with its last check time
```

Figure: the scope selects records, git and the optional forge and ledger
supply facts, and the percent, order, lane, estimate and issue views are
derived from them; nothing is stored.

Decisions, each reversible and disclosed here:

- **Name.** `codeflow report progress`, in the `report` namespace beside
  `ceremony`, `program` (TSK-311) and `away` (TSK-1045); `codeflow status`
  stays the checkout view. The operator confirms the names of the command
  and of TSK-1099's skill at plan approval.
- **Scope.** `--task TSK-NNN`, `--epic EPC-NNN` (repeatable), `--line
  <integration branch>` or the default, every open epic whose home is the
  current target; "overall" is the named scope, so a task report shows the
  task, its epic and that epic's place in the release scope.
- **Stage ladder.** A task's percent is the highest stage it has reached
  on a fixed ladder printed with every report: not started 0, in progress
  (a claim or a task branch with commits) 20, in review (an open pull
  request) 50, reviewed (an approving other-lineage review on the head)
  75, landed on its home target 100; cancelled tasks are excluded from
  every denominator and listed. Stages beyond a task (merged to the
  default branch, released) are reported for the epic and the scope
  apart, never folded into a percent. Criteria verified against criteria
  total is shown beside the stage percent from the acceptance block when
  one exists, never mixed with it. An epic's percent is the mean of its
  open and complete tasks' stage percents, with the count of tasks per
  stage beside it; the scope's percent is the same over its unique tasks,
  never a mean of epic percents. An empty denominator or an unreadable
  record is `unknown`, never 0 or 100.
- **Order.** The topological order of `depends_on` among the scope's open
  tasks, the ready set first (through the readiness core `work next`
  uses, after TSK-1038 never offering landed work), then waiting tasks
  with the predecessor they wait on, then blocked ones with their reason;
  the critical path is the longest chain of open tasks by count, marked.
- **Lanes.** When the coordination ledger has lanes (TSK-439, when
  landed), each lane with its scope, attempt, seat kind and the task's
  percent; otherwise observed lanes: each claimed or started task with its
  worktree, branch, open pull request and head age, labelled `observed`,
  with no seat and no owner invented. A project with no ledger shows
  "lanes: observed only".
- **Estimates.** When the project has adopted `cf-estimate` and a forecast
  record covers the scope, each item's scenario durations come from it,
  bound to the scope and revision it estimated and marked stale when
  criteria changed since. Otherwise three scenarios from the planned
  throughput rule (`cf-method/references/workflow-lifecycle.md` "Planned
  work moves at speed": at least one task per build lane per hour,
  preferably two): favourable at two per lane-hour, planning at one, and
  adverse at one plus one review and landing cycle per batch, over the
  remaining open tasks along the order with the number of lanes observed
  (one when none). Each estimate prints its basis and the time it was
  computed, is a duration and never a calendar commitment, and is never
  extrapolated from an observed slow pace. Usage limits and seat
  availability are not modelled; the issues view names them when the
  ledger records them.
- **Issues.** Per task: blocked (reason, owner, revisit), waiting (the
  predecessor), an open pull request whose required check is red,
  missing or pending (read through the ledger's bounded observer
  `crates/codeflow-core/src/coord/observe.rs`, `unverified` when offline),
  stale (claimed with no commit for longer than the sweep interval
  `[sweep] interval_minutes`, default 30), a deferred acceptance result
  owed (TSK-436), and a follow-up awaiting the operator when the ledger is
  present. Per lane: a seat with no progress since the last tick, from
  ledger evidence only.
- **Fact model.** JSON with `schema_version`, a snapshot time, and every
  field present with `unknown` or `unverified` rather than omitted or
  zero, under the same envelope rules TSK-312 states for `status --json`;
  whichever of TSK-311, TSK-312 and this task lands first names the
  envelope conventions in `docs/cli.md`, and the later ones follow them.
  This task reads records through the existing readiness core and record
  store (`crates/codeflow-core/src/status.rs`, `workgraph/readiness.rs`)
  and never adds a second record reader; home and currency across lines
  stay TSK-311's.

Non-goals: rendering (TSK-1098); the skill and its wiring (TSK-1099);
cross-line home and currency (TSK-311); `status --json` (TSK-312); a
scheduler, daemon or stored report; writing to any record or ledger; a
check or verdict (the report never fails a gate); tracked class and lane
vocabulary (TSK-313, TSK-314, EPC-023).

## Outcome

After this merges, anyone on an adopting project can run one read-only
command and get, for a task, an epic or the whole line, the percent
complete at each level with its basis, the order work is being done in,
the lanes carrying it, an estimate per item with its basis, and the
issues per item, each fact live or marked unverified.

## Deliverables

- the command: `crates/codeflow-cli/src/cmd/report.rs` (`progress` beside `ceremony`), its text renderer and `--json`
- the computation: `crates/codeflow-core/src/progress/` (new: scope, stage ladder, percents, order and critical path, lanes, estimate scenarios, issues), reading records through `crates/codeflow-core/src/status.rs` and `crates/codeflow-core/src/workgraph/readiness.rs`, the forge through `crates/codeflow-core/src/coord/observe.rs`, forecasts through `crates/codeflow-core/src/estimate/`
- the JSON schema: `.codeflow/schemas/progress/report-v1.schema.json`, shipped under `assets/base/`
- tests: unit tests beside the computation and CLI tests in `crates/codeflow-cli/tests/` over fixture repositories (one epic with every stage represented, a cancelled task, an unreadable record, a project with no ledger, an offline forge, a scope with no open task)
- docs: `docs/cli.md` (Remember, the command and the stage ladder), `docs/delivery.md` (where status is read)
- release note: `changelog.d/TSK-1095.md`

## Acceptance Criteria

- AC-1 Before any change, the builder shall investigate broadly and record the findings with sources in this record: (a) what `status`, `work next`, `orient`, `follow list` and `estimate outcomes` already derive and which core functions compute them; (b) how TSK-311 and TSK-312 define the fact model and where this report's envelope must agree; (c) what the acceptance block, the claim metadata and the forge expose for the stage ladder and the issues; (d) how the ledger exposes lanes today and after TSK-439; (e) the `cf-estimate` forecast record shape and how a forecast is bound to a scope; evidence: the record section, committed before the first code change in the PR.
- AC-2 `codeflow report progress` with `--task`, `--epic`, `--line` or no scope shall print, for every task in scope, its stage on the printed ladder and its percent, criteria verified against criteria total when an acceptance block exists, and the per-epic and per-scope percents computed as the Description states, with cancelled tasks excluded and listed and an empty denominator or an unreadable record printed as `unknown`; evidence: CLI tests over a fixture with every stage represented, a cancelled task, an unreadable record and an empty scope. (serves EPC-022 AC-175)
- AC-3 The order view shall list the ready set first, then waiting tasks with their predecessor, then blocked tasks with their reason, in a topological order of `depends_on`, with the critical path marked, agreeing with `work next` on every task's state; evidence: a test that runs both on one fixture and compares states, and a fixture with a diamond and a chain. (serves EPC-022 AC-175)
- AC-4 The lanes view shall show ledger lanes when the ledger records them and observed lanes otherwise, each with its task's percent and the overall across lanes, labelled `observed` with no seat or owner invented, and "lanes: observed only" in a project with no ledger; evidence: tests with a ledger fixture, a no-ledger fixture and two observed lanes. (serves EPC-022 AC-175)
- AC-5 Each item's estimate shall come from an adopted forecast that covers the scope when one exists, marked stale when the scope's criteria changed since, and otherwise from the three planned-throughput scenarios with the lane count observed, each printed as a duration with its basis and computation time and never as a date; a slow observed pace shall never change the basis; evidence: tests with a forecast, a stale forecast, no forecast with one lane and with three lanes, and a fixture whose history is slow with the estimate unchanged. (serves EPC-022 AC-175)
- AC-6 The issues view shall list, per task, blocked, waiting, red or missing or pending required checks, stale claims past the sweep interval, owed deferred results and operator-awaiting follow-ups, and per lane a seat with no progress, each with its last check time, printing every forge fact as `unverified` with the last check time when the observer cannot reach the forge, finishing within the observer's bound, and exiting 0 with completeness reported apart; evidence: tests with the network unreachable, a hung observer, a red check, a stale claim and a deferred result. (serves EPC-022 AC-175)
- AC-7 `--json` shall emit the versioned fact model with `schema_version`, a snapshot time and every field present (`unknown` or `unverified`, never omitted and never zero for missing data), byte-identical across two runs on the same state once the snapshot time is held fixed, validating against the shipped schema; evidence: the schema test and a determinism test with records created in different orders. (serves EPC-022 AC-175)
- AC-8 The command shall write nothing: no record, ledger event, cache or network write, and shall never fetch; evidence: a test that diffs the repository, the coordination home and the network log before and after a run.
- AC-9 (journey) In a scratch project adopted with the installed build, with one epic, four tasks at four stages and two worktrees, `codeflow report progress --epic` shall print the ladder, the percents, the order with the critical path, two observed lanes, three scenario estimates with their bases and the issues with their check times, and `--json` shall validate; evidence: the journey output. (journey)
