# TSK-1095: codeflow status --json gives percent complete, location, order, lanes, windows and issues for any scope

## Description

The operator asked on 2026-10-30 for a command or skill that reports the
status of work properly each time it is asked, in any project that adopts
CodeFlow: what is being worked on with just the right context, the epics
and tasks involved, percent complete at each level (the epic, the task and
the overall scope), the lanes a coordinator runs and the overall across
them, the order work is done in, the expected time to completion for each
item, and the issues for each item. On 2026-10-30 (20:40) the operator
added that timing must read at a glance on a real time axis, and that
work landed on an integration line counts as done while the report makes
clear what is on `main`, what is not, and when it gets there. Nothing
computes this today: `codeflow status` prints counts from the working
tree with no JSON (`crates/codeflow-cli/src/cmd/status.rs:7-17`), `work
next` prints readiness (`crates/codeflow-core/src/workgraph/readiness.rs:27-48`),
and `report ceremony` is the only report
(`crates/codeflow-cli/src/cmd/report.rs:17-22`). Every session writes its
own status by hand, with the stale facts the writing rule warns about.

This task is the engine: it extends `codeflow status`, the command an
adopter already reaches for, with the facts and a JSON form. TSK-1098
renders them as the figure-led `cf-present` document (`--present`) and the
plain-text form (`--md`); TSK-1099 is the `cf-status` skill that answers a
status request with them. TSK-312 (`status --json` on TSK-311's fact
model) is merged into this task on 2026-10-31 and cancelled; every TSK-312
criterion is kept below (AC-2, AC-7 and AC-11). Shape decided in planning,
open to the builder's investigation (AC-1):

```text
  records (project-management/)      git (refs, worktrees, merges)
        \                                   /
         v                                 v
   scope  ->  stage ladder per task  ->  percent per level
     |          |                          |
     |          +-> location: main | line | pull request | branch | none
     |          |         and the path to main with its window
     |          v
     |      order (depends_on, ready set, critical path)
     |          |
     v          v
   lanes (ledger lanes when present, else observed, plus a session file)
     |
     v
   windows: start and expected end per item and per milestone, three
            scenarios, relative to now (adopted forecast when present)
     |
     v
   issues per item (blocked, waiting, red or missing check, awaiting operator,
                    stale, deferred result), each with its last check time
```

Figure: the scope selects records, git and the optional forge, ledger and
session file supply facts, and the percent, location, order, lane, window
and issue views are derived from them; nothing is stored.

Decisions, each reversible and disclosed here:

- **Command and flags.** `codeflow status` keeps its text view unchanged
  with no flag. New: `--json`; the scope flags `--task TSK-NNN`, `--epic
  EPC-NNN` (repeatable) and `--line <integration branch>`, with the
  default scope every open epic whose home is the current target; a scope
  flag with no `--json` prints the progress text view. `--present
  <path>`, `--md` and `--session <file>` are TSK-1098's and TSK-1099's
  surfaces over the same facts; this task defines the `--session` schema
  and merges its facts into the lanes view. "Overall" is the named scope,
  so a task report shows the task, its epic and that epic's place in the
  scope. The coordinator recommended this shape on 2026-10-30 over a new
  `report` verb; the operator confirms the names at plan approval.
- **Stage ladder.** A task's percent is the highest stage it has reached
  on a fixed ladder printed with every report: not started 0, in progress
  (a claim or a task branch with commits) 20, in review (an open pull
  request) 50, reviewed (an approving other-lineage review on the head)
  75, landed on its home target 100; cancelled tasks are excluded from
  every denominator and listed. Criteria verified against criteria total
  is shown beside the stage percent from the acceptance block when one
  exists, never mixed with it. An epic's percent is the mean of its open
  and complete tasks' stage percents, with the count of tasks per stage
  beside it; the scope's percent is the same over its unique tasks, never
  a mean of epic percents. An empty denominator or an unreadable record
  is `unknown`, never 0 or 100.
- **Location and the path to main.** Landed on the integration line is
  done for the task percent, and each task and epic also carries a
  location: `main` (reachable from the trusted remote's default branch),
  `line` (reachable from its integration line only), `pull request` (an
  open pull request into the line or into `main`), `branch` (a task
  branch with commits and no pull request) or `none`. The epic's path to
  `main` is the remaining steps on the landing route the project records
  (land the open units on the line, the line's full gate, the pull
  request to `main`, the operator's merge, release when the project has
  a release step), each with its window from the scenarios, and the
  operator-owned steps marked as such; this is a read of record and git
  state, never a promise.
- **Order.** The topological order of `depends_on` among the scope's open
  tasks, the ready set first (through the readiness core `work next`
  uses, after TSK-1038 never offering landed work), then waiting tasks
  with the predecessor they wait on, then blocked ones with their reason;
  the critical path is the longest chain of open tasks by count, marked.
- **Lanes.** When the coordination ledger has lanes (TSK-439, when
  landed), each lane with its scope, attempt, seat kind and the task's
  percent; otherwise observed lanes: each claimed or started task with its
  worktree, branch, open pull request and head age, labelled `observed`,
  with no seat and no owner invented. A `--session <file>` of
  session-only facts (lane, task, builder, reviewer, seat, verdict in
  flight, blocker, each with its observation time) is validated against a
  shipped schema, merged into the lanes view labelled `session`, and
  never changes a percent or a stage. A project with no ledger and no
  session file shows "lanes: observed only".
- **Windows.** Every open item and every milestone on the path to `main`
  carries a window per scenario: a start (now, or when its predecessors
  end) and an expected end, as durations from the snapshot time, so a
  renderer can place them on one time axis with now marked. When the
  project has adopted `cf-estimate` and a forecast record covers the
  scope, the windows come from it, bound to the scope and revision it
  estimated and marked stale when criteria changed since. Otherwise the
  three scenarios come from the planned throughput rule
  (`cf-method/references/workflow-lifecycle.md` "Planned work moves at
  speed": at least one task per build lane per hour, preferably two):
  favourable at two per lane-hour, planning at one, adverse at one plus
  one review and landing cycle per batch, over the open tasks along the
  order with the number of lanes observed (one when none), and the
  operator-owned steps carrying no duration of their own, marked as
  waiting on the operator. Each window prints its basis and computation
  time, is a duration from now and never a calendar commitment, and is
  never extrapolated from an observed slow pace.
- **Issues.** Per task: blocked (reason, owner, revisit), waiting (the
  predecessor), an open pull request whose required check is red,
  missing or pending (read through the ledger's bounded observer
  `crates/codeflow-core/src/coord/observe.rs`, `unverified` when offline),
  stale (claimed with no commit for longer than the sweep interval
  `[sweep] interval_minutes`, default 30), a deferred acceptance result
  owed (TSK-436), and a follow-up awaiting the operator when the ledger is
  present. Each issue names its unblocker (an agent lane, a CI run, a
  predecessor, the operator) and the window in which it is expected to
  clear when the scenarios give one, so a renderer can draw a blocked
  list and an explicit "needs the operator" set, empty included. Per
  lane: a seat with no progress since the last tick, from ledger or
  session evidence only.
- **Pace and intake.** Over the scope's history the fact model gives,
  per day for the last seven days and in total, the tasks landed on
  their home target and the tasks added to the scope (from record
  creation dates and merge times), with the lane count observed, so a
  reader can see whether intake outruns landing; this is the basis line
  of the planned-throughput windows and is printed with them.
- **Fact model.** JSON with `schema_version`, a snapshot time with its
  zone, and every field present with `unknown` or `unverified` rather
  than omitted or zero, frozen by a schema test; each measure (percents,
  locations, order, lanes, windows, issues, pace) carries an `evidence`
  entry naming its source (records, git, the forge through the observer,
  the ledger, a forecast record, the session file), its check time and
  whether it was checked, so a renderer can draw the evidence matrix.
  TSK-311's `report program` reuses this model for the records it adds
  cross-line home and currency to, and its AC-4's "schema test that
  TSK-312 reuses" reads as this task's schema test. This task reads
  records through the existing readiness core and record store
  (`crates/codeflow-core/src/status.rs`, `workgraph/readiness.rs`) and
  never adds a second record reader.

Non-goals: rendering (TSK-1098); the skill and its wiring (TSK-1099);
cross-line home and currency (TSK-311); a scheduler, daemon or stored
report; writing to any record or ledger; a check or verdict (the report
never fails a gate); tracked class and lane vocabulary (TSK-313, TSK-314,
EPC-023).

## Outcome

After this merges, anyone on an adopting project can run `codeflow status`
with a scope and get, for a task, an epic or the whole line, the percent
complete at each level with its basis, what is on `main` and what is not
with the path to `main`, the order of work, the lanes carrying it, a
window per item and milestone with its basis, and the issues per item,
each fact live or marked unverified, as text and JSON.

## Deliverables

## Acceptance Criteria

- AC-1 Before any change, the builder shall investigate broadly and record the findings with sources in this record: (a) what `status`, `work next`, `orient`, `follow list` and `estimate outcomes` already derive and which core functions compute them; (b) how TSK-311 defines its fact model and where this task's envelope must agree, so `report program` reuses it; (c) what the acceptance block, the claim metadata, git reachability and the forge expose for the stage ladder, the locations and the issues; (d) how the ledger exposes lanes today and after TSK-439; (e) the `cf-estimate` forecast record shape and how a forecast is bound to a scope; (f) the landing route the project records (the integration line, the pull request to `main`, the release step) and how it is read; evidence: the record section, committed before the first code change in the PR.
- AC-2 `codeflow status` with `--task`, `--epic`, `--line` or no scope flag plus `--json` shall give, for every task in scope, its stage on the printed ladder and its percent, criteria verified against criteria total when an acceptance block exists, and the per-epic and per-scope percents computed as the Description states, with cancelled tasks excluded and listed and an empty denominator or an unreadable record given as `unknown`; evidence: CLI tests over a fixture with every stage represented, a cancelled task, an unreadable record and an empty scope. (serves EPC-022 AC-175)
- AC-3 The order view shall list the ready set first, then waiting tasks with their predecessor, then blocked tasks with their reason, in a topological order of `depends_on`, with the critical path marked, agreeing with `work next` on every task's state; evidence: a test that runs both on one fixture and compares states, and a fixture with a diamond and a chain. (serves EPC-022 AC-175)
- AC-4 The lanes view shall show ledger lanes when the ledger records them, observed lanes otherwise, and the facts of a `--session` file validated against its schema and labelled `session`, each with its task's percent and the overall across lanes, with no seat or owner invented, a session fact never changing a percent or a stage, and "lanes: observed only" in a project with no ledger and no session file; evidence: tests with a ledger fixture, a no-ledger fixture, two observed lanes, a valid session file and a malformed one (refused by name). (serves EPC-022 AC-175)
- AC-5 Every open item and every milestone on the path to `main` shall carry a window per scenario (start and expected end as durations from the snapshot time) from an adopted forecast that covers the scope when one exists, marked stale when the scope's criteria changed since, and otherwise from the three planned-throughput scenarios with the lane count observed, operator-owned steps marked as waiting on the operator with no duration of their own, each window printed with its basis and computation time and never as a date; a slow observed pace shall never change the basis; evidence: tests with a forecast, a stale forecast, no forecast with one lane and with three lanes, a chain whose windows start when predecessors end, and a fixture whose history is slow with the windows unchanged. (serves EPC-022 AC-175)
- AC-6 The issues view shall list, per task, blocked, waiting, red or missing or pending required checks, stale claims past the sweep interval, owed deferred results and operator-awaiting follow-ups, and per lane a seat with no progress, each with its last check time, its unblocker (lane, CI run, predecessor or operator) and its expected clearing window when the scenarios give one, with the operator-owned set given explicitly even when empty, printing every forge fact as `unverified` with the last check time when the observer cannot reach the forge, finishing within the observer's bound, and exiting 0 with completeness reported apart; evidence: tests with the network unreachable, a hung observer, a red check, a stale claim, a deferred result and a scope with no operator item. (serves EPC-022 AC-175)
- AC-7 `--json` shall emit the versioned fact model with `schema_version`, a snapshot time with its zone, an `evidence` entry per measure (source, check time, checked or not) and every field present (`unknown` or `unverified`, never omitted and never zero for missing data), byte-identical across two runs on the same state once the snapshot time is held fixed, validating against the shipped schema, with the schema frozen by a test TSK-311 reuses; evidence: the schema test and a determinism test with records created in different orders. (serves EPC-022 AC-175)
- AC-8 The command shall write nothing: no record, ledger event, cache or network write, and shall never fetch; evidence: a test that diffs the repository, the coordination home and the network log before and after a run.
- AC-9 (journey) In a scratch project adopted with the installed build, with one epic, five tasks at five stages across every location and two worktrees, `codeflow status --epic` shall print the ladder, the percents, the locations and the path to `main` with its windows, the order with the critical path, two observed lanes, the three scenario windows with their bases and the issues with their check times, and `--json` shall validate; evidence: the journey output. (journey)
- AC-10 Each task and epic shall carry its location (`main`, `line`, `pull request`, `branch`, `none`) from git reachability against the trusted remote's default branch and the integration line and from open pull requests, and the epic shall carry the remaining steps of its path to `main` from the recorded landing route, each step with its window and the operator-owned steps marked; evidence: tests over a fixture with one task at each location, a line not yet merged to `main`, and a line already merged. (serves EPC-022 AC-175)
- AC-11 The text output of `codeflow status` with no flag shall be unchanged; evidence: the existing status tests unchanged. (serves EPC-022 AC-175)
- AC-12 The pace view shall give, per day for the last seven days and in total, the tasks landed on their home target and the tasks added to the scope, with the observed lane count, from record creation dates and merge times, and the planned-throughput windows shall print this as their basis line; evidence: tests over a fixture with a known history and a fixture with no history (`unknown`, never zero). (serves EPC-022 AC-175)
