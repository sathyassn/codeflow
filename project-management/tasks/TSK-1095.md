# TSK-1095: codeflow status --json gives percent complete, location, order, lanes, windows and issues for any scope

## Description

The operator asked on 2026-10-30 for a command or skill that reports the
status of work properly each time it is asked, in any project that adopts
CodeFlow: what is being worked on with just the right context, the epics
and tasks involved, percent complete at each level (the epic, the task and
the overall scope), the lanes a coordinator runs and the overall across
them, the order work is done in, the expected time to completion for each
item, and the issues for each item. On 2026-10-30 (20:40) the operator
added that timing must read at a glance on a real time axis, and that
work landed on an integration line counts as done while the report makes
clear what is on `main`, what is not, and when it gets there. Nothing
computes this today: `codeflow status` prints counts from the working
tree with no JSON (`crates/codeflow-cli/src/cmd/status.rs:7-17`), `work
next` prints readiness (`crates/codeflow-core/src/workgraph/readiness.rs:27-48`),
and `report ceremony` is the only report
(`crates/codeflow-cli/src/cmd/report.rs:17-22`). Every session writes its
own status by hand, with the stale facts the writing rule warns about.

This task is the engine: it extends `codeflow status`, the command an
adopter already reaches for, with the facts and a JSON form. TSK-1098
renders them as the figure-led `cf-present` document (`--present`) and the
plain-text form (`--md`); TSK-1099 is the `cf-status` skill that answers a
status request with them. TSK-312 (`status --json` on TSK-311's fact
model) is merged into this task on 2026-10-31 and cancelled; every TSK-312
criterion is kept below (AC-2, AC-7 and AC-11). Shape decided in planning,
open to the builder's investigation (AC-1):

```text
  records (project-management/)      git (refs, worktrees, merges)
        \                                   /
         v                                 v
   scope  ->  stage ladder per task  ->  percent per level
     |          |                          |
     |          +-> location: main | line | pull request | branch | none
     |          |         and the path to main with its window
     |          v
     |      order (depends_on, ready set, critical path)
     |          |
     v          v
   lanes (ledger lanes when present, else observed, plus a session file)
     |
     v
   windows: start and expected end per item and per milestone, three
            scenarios, relative to now (adopted forecast when present)
     |
     v
   issues per item (blocked, waiting, red or missing check, awaiting operator,
                    stale, deferred result), each with its last check time
```

Figure: the scope selects records, git and the optional forge, ledger and
session file supply facts, and the percent, location, order, lane, window
and issue views are derived from them; nothing is stored.

Decisions, each reversible and disclosed here:

- **Command and flags.** `codeflow status` keeps its text view unchanged
  with no flag. New: `--json`; the scope flags `--task TSK-NNN`, `--epic
  EPC-NNN` (repeatable) and `--line <integration branch>`, with the
  default scope every open epic whose home is the current target; a scope
  flag with no output flag prints the progress text view. `--json`,
  `--present <path>` (TSK-1098) and `--md` (TSK-1098) are mutually
  exclusive output choices over the same facts; `--session <file>` and
  `--since <previous facts file>` are optional input modifiers: this
  task defines the `--session` schema and merges its facts into the lanes
  view, and reads a previous `--json` output through `--since` to emit
  what changed (landings, new red checks, tasks added, blockers opened or
  cleared, decisions recorded) with their times. "Overall" is the named scope,
  so a task report shows the task, its epic and that epic's place in the
  scope. The coordinator recommended this shape on 2026-10-30 over a new
  `report` verb; the operator confirms the names at plan approval.
- **Stage ladder.** A task's percent is the highest stage it has reached
  on a fixed ladder printed with every report: not started 0, in progress
  (a claim or a task branch with commits) 20, in review (an open pull
  request) 50, reviewed (an approving other-lineage review on the head)
  75, landed on its home target 100; cancelled tasks are excluded from
  every denominator and listed. Criteria verified against criteria total
  is shown beside the stage percent from the acceptance block when one
  exists, never mixed with it, labelled `criteria`, bound to the reviewed
  SHA the block names and marked `stale` when the head has moved since; a
  block or count that is absent is `not recorded`, never `0 of N`. An
  epic's percent is the mean of its open
  and complete tasks' stage percents, with the count of tasks per stage
  beside it; the scope's percent is the same over its unique tasks, never
  a mean of epic percents. An empty denominator or an unreadable record
  is `unknown`, never 0 or 100.
- **Location and the path to main.** Landed on the integration line is
  done for the task percent, and each task and epic also carries a
  location from its own landing evidence: `main` (its landing commit
  reachable from the trusted remote's default branch), `line` (reachable
  from its integration line only), `pull request` (an open pull request
  into the line or into `main`), `branch` (a task branch with commits and
  no pull request) or `none`; a checkpoint merge of the line into `main`
  moves only the tasks whose landing commits it carries, never the epic
  as a whole. A task whose record is on the line but whose work has not
  started is `none` with the note `record on line`, never `line`. A `pull
  request` location carries its substate (`draft`, `open`, `approved at
  <sha>` with the reviewed SHA named and marked `not the head` when the
  head moved); "ready" is never a location, it is the next step's word.
  The open pull requests into `main` are listed with the task state of
  each, so a lead can say "no 4.0.0 pull request into `main` is open; the
  only open one is for a cancelled task" rather than an absolute none.
  Every remote claim is bound to the fetched ref identity it was read
  from (the SHA and the fetch time) and marked `unverified` when that ref
  is older than the sweep interval or could not be fetched. The
  epic's path to `main` is the remaining steps on the landing route the
  project records (land the open units on the line, the line's full gate,
  the pull request to `main`, the operator's merge, release when the
  project has a release step); an agent-owned step carries a window from
  the scenarios; an operator-owned step is two events, ready for the
  operator (a window) and done by the operator (undated, `awaiting the
  operator`), and every step after it is conditional on it and says so.
  The hop to `main` always carries its condition in words and, when the
  scenarios give one, the earliest conditional end under the intake-stops
  scenario ("after the epic is complete on the line, earliest about N
  days if intake stops and capacity holds; then the operator's merge"),
  so "when does it reach `main`" has an answer beyond "no date"; this is
  a read of record and git state, never a promise.
- **Named sets.** The fact model defines each named set once and every
  view reuses it: the landing chain (the open pull requests into the
  line in landing order, with the landed ones and their times), each
  lane's tasks, the path to `main`; a count of a set is the count of
  that one definition.
- **Order.** A topological order of `depends_on` among the scope's open
  tasks, authoritative: a task never precedes its predecessor. Among
  tasks with no dependency between them the state decides the place:
  active first (claimed or started, through the readiness core `work
  next` uses, after TSK-1038 never offering landed work), then ready,
  then waiting with the predecessor waited on, then blocked with the
  reason; so a blocked predecessor sits before its waiting successor,
  and the state is printed on every row. The critical path is the chain
  whose planning-scenario durations sum highest, marked, and the longest
  chain by count is reported apart as the dependency depth, never called
  critical.
- **Lanes.** When the coordination ledger has lanes (TSK-439, when
  landed), each lane with its scope, attempt, seat kind and the task's
  percent; otherwise observed lanes: each claimed or started task with its
  worktree, branch, open pull request and head age, labelled `observed`,
  with no seat and no owner invented. A `--session <file>` of
  session-only facts (lane, task, builder, reviewer, seat, verdict in
  flight, blocker, each with its observation time) is validated against a
  shipped schema, merged into the lanes view labelled `session`, and
  never changes a percent or a stage. A project with no ledger and no
  session file shows "lanes: observed only".
- **Windows.** Every open agent-owned item and every agent-owned step on
  the path to `main` carries one window: the earliest and latest end as
  durations from the snapshot time (the as-of moment), with the planning
  value inside it, and a start that is the as-of moment or its
  predecessors' latest end, so a renderer can place it as a band on one
  time axis with the as-of rule. A blocked item's window is conditional
  on its blocker clearing and says so; an item whose window has no honest
  basis (an unknown predecessor, an undated operator step before it, a
  cancelled or unreadable predecessor) is `not yet estimable` with the
  reason, never a number. When
  the project has adopted `cf-estimate` and a forecast record covers the
  scope, the windows come from it, bound to the scope and revision it
  estimated and marked stale when criteria changed since. Otherwise the
  window comes from the planned throughput rule
  (`cf-method/references/workflow-lifecycle.md` "Planned work moves at
  speed": at least one task per build lane per hour, preferably two):
  earliest at two tasks per lane-hour with one review and landing cycle
  of one hour per unit, planning at one per lane-hour with one review
  cycle and one repair round, latest at one per lane-hour with two review
  rounds and one landing cycle per batch, over the open tasks along the
  order with the number of lanes observed. Every window carries a
  `basis_kind`: `forecast` (an adopted forecast record), `observed` (the
  planned rate over the lanes observed) or `assumed` (no lane observed,
  so one lane is assumed and the window is labelled `assumed one lane`
  wherever it is drawn, never mixed with an observed window). The scope's
  finish is forecast under two named scenarios in one place: intake
  stops (the open tasks at the planning rate) and intake continues at the
  rate observed over the last seven days (which may give no finite
  finish, said in words). Each window prints its basis and computation
  time, is a duration from the as-of moment and never a calendar
  commitment, and the planned-throughput rate is never lowered to an
  observed slow pace.
- **Issues.** Per task: blocked (reason, owner, revisit), waiting (the
  predecessor), an open pull request whose required check is red,
  missing or pending (read through the ledger's bounded observer
  `crates/codeflow-core/src/coord/observe.rs`, `unverified` when offline),
  stale (claimed with no commit for longer than the sweep interval
  `[sweep] interval_minutes`, default 30), a deferred acceptance result
  owed (TSK-436), and a follow-up awaiting the operator when the ledger is
  present. Each issue names its unblocker (an agent lane, a CI run, a
  predecessor, the operator) and the window in which it is expected to
  clear when the scenarios give one, so a renderer can draw a blocked
  list and an explicit "needs the operator" set. The operator set is
  `none owed` only when every source that can name an owed item (records,
  the ledger when present, the away activation's owed items and decisions
  when an activation exists (TSK-1045, read with its own coverage result
  and never written), the forge through the observer, the session file
  when given) was checked at this snapshot; otherwise it is `not
  established` with the unchecked or unreadable source named, never an
  all-clear. Per
  lane: a seat with no progress since the last tick, from ledger or
  session evidence only.
- **Pace and intake.** Over the scope's history the fact model gives,
  per day for the last seven days and in total, the tasks landed on
  their home target, the tasks added to the scope (from record creation
  dates and merge times, each named) and the open count at the end of
  each day, with the lane count observed, so a reader can see whether
  intake outruns landing. Two rates are given and labelled: the scope's
  own observed landing rate, and the planned capacity rate over the lanes
  observed (the planned-throughput rule); the finish forecast names which
  rate each scenario uses, and the intake-stops count names the tasks
  added since the previous snapshot as intake. This is the basis line of
  the windows and is printed with them.
- **Fact model.** JSON with `schema_version`, a snapshot time with its
  zone, and every field present with `unknown` or `unverified` rather
  than omitted or zero, frozen by a schema test; each measure (percents,
  locations, order, lanes, windows, issues, pace) carries an `evidence`
  entry naming its source (records, git, the forge through the observer,
  the ledger, the activation, a forecast record, the session file), its
  check time and whether it was checked, so a renderer can draw the
  evidence matrix. Every forge observation keeps its read time and is
  never overwritten by a later one without its own read time; every time
  in the model carries one zone, the snapshot's, and a check state is the
  value read (`skipped` and `missing` stay so, never rewritten as
  `running`).
  Every snapshot carries the repository identity TSK-311's envelope
  defines, so a `--since` file from another repository is refused even
  when its display ids match. TSK-311's `report program` reuses this
  model for the records it adds cross-line home and currency to, and its AC-4's "schema test that
  TSK-312 reuses" reads as this task's schema test. This task reads
  records through the existing readiness core and record store
  (`crates/codeflow-core/src/status.rs`, `workgraph/readiness.rs`) and
  never adds a second record reader.

- **Report facts the operator asked for on 2026-10-31.** The operator's
  standing requirements for every report (deliverable and overall
  percent; each epic or topic with what it is, done and not done, the
  reasoning and the percent; blockers with a recommended action, why and
  alternatives; operator inputs with context, options, recommendation and
  reasoning; commands that run from any folder) need facts the model did
  not name. The fact model carries, per scope, the `deliverable` (the
  epic's `## Outcome` line, or the task's, `not recorded` when absent)
  beside the percent; per epic, `what_it_is` (its Outcome line), the
  `done` and `not_done` task lists and a `reasoning` line (the stage
  counts and the basis the percent is computed from); `themes` grouping
  an epic's tasks by the record section that introduced them (the
  amendment heading, which is how this repository's epics group asks) or
  by a `theme:` line in the task record when present, `ungrouped`
  otherwise, so a renderer can drill from the epic to a theme to a task;
  per issue, `recommended_action`, `why` and `alternatives` filled from
  the record (the `## Blocker` reason, owner and revisit, the follow-ups,
  a decision note) or from the `--session` file labelled `session`, and
  `not recorded` when neither has them, never invented; per operator
  item, a `decision` with `context`, `options`, `recommendation` and
  `reasoning` from the same sources with the same rule; and per task the
  `context` facts a drill-down needs (outcome line, location, lane, state,
  window, last moved, open pull request). Every command the model cites
  (a check to rerun, a pull request to open, a log to read) carries the
  repository's absolute path or a `git -C <path>` form so a script
  assembled from them runs from any folder; the renderer (TSK-1098)
  assembles the script.

Non-goals: rendering (TSK-1098); the skill and its wiring (TSK-1099);
cross-line home and currency (TSK-311); a scheduler, daemon or stored
report; writing to any record or ledger; a check or verdict (the report
never fails a gate); tracked class and lane vocabulary (TSK-313, TSK-314,
EPC-023).

## Outcome

After this merges, anyone on an adopting project can run `codeflow status`
with a scope and get, for a task, an epic or the whole line, the percent
complete at each level with its basis, what is on `main` and what is not
with the path to `main`, the order of work, the lanes carrying it, a
window per item and milestone with its basis, and the issues per item,
each fact live or marked unverified, as text and JSON.
