# TSK-1051: Printed diagnostics name places, never project values

## Description

CodeFlow prints diagnostics about files a project writes: parser errors,
semantic validation messages, warnings and diagnostic reports. Several of
them print what the project wrote: a parser message quotes a value, a key
or the offending source line, and a validation message repeats the
rejected value. A project file can hold a secret, so these messages can
leak it to a terminal, a CI log or an agent transcript. Outcome: every
such diagnostic names the file and, where the parser or validator gives
one, the line, column and schema names, and never a value, key or line
the project wrote, while each command still refuses, warns or skips as it
does today.

The work starts with an inventory (AC-1), because the set of readers and
sinks is not known: two reviews of this record found sites in all three
crates and in shipped scripts that a list of modules missed. The
inventory decides the build.

Display contract, stated identically in TSK-1029 and TSK-1051: a
diagnostic, report line or export never contains a value, key, heading
or line a project wrote, in its text, its `Debug` form or any error it
wraps. It may name a path, a line and column, a count, and a schema name
or heading CodeFlow defines. A version is shown as `MAJOR.MINOR.PATCH`,
plus a prerelease only in CodeFlow's own release form (`alpha.N`,
`beta.N`, `rc.N`); any other prerelease, and any build metadata, is shown
as `(with a suffix)`, and a value that does not parse as a version is
not shown.

Dependency contract with TSK-1029, at TSK-1029's head
`4a37f6618` (PR 385). Each shared reader and each printer has
exactly one owner; regression tests in this task may still cover shared
consumers.

- TSK-1029 owns everything `codeflow update` and `codeflow update --pin`

  policy load (`hooks/policy.rs` `Policy::load_file`), the remote policy
  read (`remote.rs`), the CI pin checks shared with `codeflow doctor`
  (`scaffold/release_pin.rs`, `doctor/ci_pin.rs`) and the release
  download and `--pin` argument messages. It also owns `ParsePlace` and
  the two helpers in `scaffold/mod.rs`, `toml_error` and `json_error`:
  `ScaffoldError` keeps only a parse place and never a parser error as

  TSK-1029's adversarial helper tests and its canary test over `update`

- TSK-1051 owns every other reader and printer in `codeflow-core`,

commands stay in scope. Non-goal: changing whether a command refuses,
warns or skips.

## Outcome

After this merges, an adopter can show CodeFlow's diagnostics in a terminal, a CI log or an agent transcript without them printing a value, key or line the project wrote.

## Deliverables

- Inventory of input families, readers, commands, sinks and owners, with its search commands and revision: `docs/verification/printed-project-values-inventory-2026-10.md` (provisional name; the docs portal's structure decides the final one)
- Diagnostics that name places only: `crates/codeflow-core/src/`, `crates/codeflow-cli/src/`, `crates/codeflow-present/src/`, and every shipped asset under `assets/` (including `assets/base/` and the docs portal starter under `assets/docs-portal/`, with their mirrors and baselines) where the inventory finds a sink
- Tests per sink, and the scan of AC-5: `crates/codeflow-core/tests/`, `crates/codeflow-cli/tests/`, `crates/codeflow-present/tests/`, and the shipped scripts' own test homes for script sinks
- Public docs that quote or describe a changed message, as the inventory lists them (at least the error and exit-code tables in `docs/cli.md` and the policy rejection paragraph in `docs/adoption.md`)
- Changelog entry: `changelog.d/TSK-1051.md`

## Acceptance Criteria

- AC-1 (investigation) Before any fix, an inventory tied to a named revision of the line shall list every input family CodeFlow reads from a project (at least TOML, JSON, JSONL, YAML, XML including JUnit and Cobertura, LCOV and Istanbul coverage, record front matter, and any other the search finds), every reader of a project-written file, the commands that reach each reader, and every output sink its diagnostics reach (stdout, stderr, written reports, the ledger, and every error chain the CLI prints with its sources and `Debug` forms), across `codeflow-core`, `codeflow-cli`, `codeflow-present` and every shipped asset under `assets/` that reads project files, with one owner for each row: TSK-1029, TSK-1051, or out of scope with a reason. It shall place each site named in the Description and settle each sink of a content-display command separately: only the requested content payload may be out of scope. Evidence: the inventory file with its search commands.
- AC-2 For each reader and sink TSK-1051 owns, the printed diagnostic shall meet the Display contract in the Description: it names the file and, where the parser or validator gives them, the line, column and schema names, and its text, `Debug` form and wrapped errors contain no value, key, heading or source text the project wrote. Evidence: one test per sink that plants a unique value, including the adversarial forms of TSK-1029's helper tests (escaped delimiters, backticks, project-written keys, duplicate keys), failing before the fix and passing after.
- AC-3 Each test of AC-2 shall also assert that the intended diagnostic fired, by its own text, and that the command's outcome (refusal, warning or skip, and exit code) is the same as before the fix. Evidence: the same tests; an absent value alone is not evidence.
- AC-4 A reproducible search over the three crates and every shipped asset that runs, recorded with its commands and revision and rerun on the final head, shall list every place where an error or value read from a project file of any AC-1 family reaches a format string, `to_string()`, an error source or another error wrapper, and give each match a disposition: fixed here, owned by TSK-1029, safe with a reason, or out of scope with a reason. Evidence: the search output and dispositions in the inventory.
- AC-5 New sites shall be caught by a scan test that fails when a parser error type of an AC-1 family is formatted outside the shared helpers, with a reviewed exception list giving a reason per entry; if the investigation shows such a scan cannot be sound, the record and the inventory shall say instead that new sites are caught only by review, and why. Evidence: the scan test failing on a planted direct format, or the recorded reason.
- AC-6 When `codeflow init` runs over a project with existing settings, policy and workflow files, its report shall name paths and schema keys only. Evidence: an init end-to-end test with planted values, failing before and passing after.
- AC-7 (journey) The tests of AC-2 and AC-3 shall run the real binary for every sink a command reaches, and the real script runtime (Node for the docs portal starter, the shell for CI scripts) for every script sink; a library-level test is accepted only for a sink neither reaches, named as such in the inventory.
