# TSK-1051: Printed diagnostics name places, never project values

## Description

CodeFlow prints diagnostics about files a project writes: parser errors,
semantic validation messages, warnings and diagnostic reports. Several of
them print what the project wrote: a parser message quotes a value, a key
or the offending source line, and a validation message repeats the
rejected value. A project file can hold a secret, so these messages can
leak it to a terminal, a CI log or an agent transcript. Outcome: every
such diagnostic names the file and, where the parser or validator gives
one, the line, column and schema names, and never a value, key or line
the project wrote, while each command still refuses, warns or skips as it
does today.

The work starts with an inventory (AC-1), because the set of readers and
sinks is not known: the review of the first draft of this record found
sites in all three crates that a list of modules missed. The inventory
decides the build.

Dependency contract with TSK-1029, at TSK-1029's head
`3cb93af5bd65e92b136e11fcf06c34a28f243bb8` (PR 385). Each shared reader and each printer has
exactly one owner; regression tests in this task may still cover shared
consumers.

- TSK-1029 owns everything `codeflow update` and `codeflow update --pin`
  print and write to the `--diff` export, and the readers they reach:
  the project metadata and state files (`scaffold/state.rs`,
  `registry.rs`), the scaffold version check and its `Unparseable`
  message (`scaffold/version.rs`), pending update records
  (`scaffold/update/pending.rs`), the PR template policy read
  (`scaffold/pr_template.rs`), the workspace policy load
  (`hooks/policy.rs` `Policy::load_file`), the remote policy read
  (`remote.rs`) and the CI pin checks shared with `codeflow doctor`
  (`scaffold/release_pin.rs`, `doctor/ci_pin.rs`). It also owns the two
  location-only helpers in `scaffold/mod.rs`, `toml_error` and
  `json_error`, which print a line and column and no part of the parser's
  message; TSK-1029's adversarial tests (escaped quotes, backticks,
  project-written keys, duplicate keys) are their contract.
- TSK-1051 owns every other reader and printer in `codeflow-core`,
  `codeflow-cli` and `codeflow-present`, including semantic validation
  (such as `hooks/policy_schema.rs`), `codeflow init`'s report, and any
  further format or helper the inventory shows is needed.

Sites the review named, each to be placed in the inventory:
`hooks/policy_schema.rs:1218` (a rejected release branch pattern),
`testing/config/mod.rs:586` (a glob) and `:817` (a schema version),
`doctor/mod.rs:1017` (a hook matcher), `testing/report/junit.rs:317` and
`testing/coverage/cobertura.rs:113` (XML parser text, which names
project-written tags), `codeflow-present/src/config.rs:141` printed at
`codeflow-cli/src/cmd/present.rs:205`, `capability.rs:178`,
`ids/state.rs:59`, `delegate.rs:1681`, `security/policy.rs:63` and
`git/ci.rs:139` (line numbers at the line tip `5f84f30f5`). Shipped
scripts are sinks too: the CI pin installers in `assets/base/ci/` print a
duplicated digest key by name (`fail("lists " key " twice")`) in the
project's CI log.

Out of scope, settled in the inventory with a reason for each: commands
whose purpose is to show content the operator asked for, such as
`codeflow recall`, which prints matching snippets
(`codeflow-cli/src/cmd/recall.rs:122`). Non-goal: changing whether a
command refuses, warns or skips.

## Acceptance Criteria

- AC-1 (investigation) Before any fix, an inventory tied to a named revision of the line shall list every input family CodeFlow reads from a project (at least TOML, JSON, JSONL, YAML, XML including JUnit and Cobertura, LCOV and Istanbul coverage, record front matter, and any other the search finds), every reader of a project-written file, the commands that reach each reader, and every output sink its diagnostics reach (stdout, stderr, written reports, the ledger), across `codeflow-core`, `codeflow-cli`, `codeflow-present` and the shipped scripts under `assets/base/` that read project files, with one owner for each row: TSK-1029, TSK-1051, or out of scope with a reason. It shall place each site named in the Description and settle each content-display command (such as `codeflow recall`). Evidence: the inventory file with its search commands.
- AC-2 For each reader and sink TSK-1051 owns, the printed diagnostic shall name the file and, where the parser or validator gives them, the line, column and schema names, and shall not contain any value, key or source text the project wrote. Evidence: one test per sink that plants a unique value, including the adversarial forms of TSK-1029's helper tests (escaped delimiters, backticks, project-written keys, duplicate keys), failing before the fix and passing after.
- AC-3 Each test of AC-2 shall also assert that the intended diagnostic fired, by its own text, and that the command's outcome (refusal, warning or skip, and exit code) is the same as before the fix. Evidence: the same tests; an absent value alone is not evidence.
- AC-4 A reproducible search over the three crates and the shipped scripts, recorded with its commands and revision and rerun on the final head, shall list every place where an error or value read from a project file of any AC-1 family reaches a format string, `to_string()` or an error wrapper, and give each match a disposition: fixed here, owned by TSK-1029, safe with a reason, or out of scope with a reason. Evidence: the search output and dispositions in the inventory.
- AC-5 New sites shall be caught by a scan test that fails when a parser error type of an AC-1 family is formatted outside the shared helpers, with a reviewed exception list giving a reason per entry; if the investigation shows such a scan cannot be sound, the record and the inventory shall say instead that new sites are caught only by review, and why. Evidence: the scan test failing on a planted direct format, or the recorded reason.
- AC-6 When `codeflow init` runs over a project with existing settings, policy and workflow files, its report shall name paths and schema keys only. Evidence: an init end-to-end test with planted values, failing before and passing after.
- AC-7 (journey) The tests of AC-2 and AC-3 shall run the real binary for every sink a command reaches; a library-level test is accepted only for a sink no command reaches, named as such in the inventory.
