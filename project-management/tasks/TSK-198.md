# TSK-198: Clear the public main secret and dependency scans

## Description

The first main-push run on the public repository failed the two scans the
v3.0.0 release dispatch requires. The full-history secret scan flags the
cf-present `project_key` (a SHA-256 of a project path, not a credential) in
the recorded TSK-115 evidence, and the dependency audit flags `fast-uri`
3.1.6, a development dependency of the docs portal (GHSA-58mr-gqgx-xq4g,
GHSA-qw65-cvwx-89v3, GHSA-hrr3-gc8f-f4qj). This task allowlists exactly
those evidence keys and raises the override to 3.1.8 in the portal and its
starter, with the lockfile, runtime-script and ownership pins that follow.
The record baselines in `.codeflow/project.toml` also named archive commit
ids, which the history filter rewrote, so every pull request here failed the
record checks; they now name the public ids. The release tables
(`release_records_baseline`, `release_rule_baseline`) keep their archive ids:
the release judge treats them as write-once, so public release lines need
their own migration, a follow-up. This pull request is the bootstrap: its
target still names the archive baselines. A public-only clone, as hosted CI
uses, reads them as absent and warns; a clone that shares the archive's
objects finds them and blocks, so this branch is pushed from a public-only
clone. Non-goal: any other dependency or scanner
rule change.

## Acceptance Criteria

- AC-1 When gitleaks scans the full history with `.gitleaks.toml`, it
  reports no leaks; the allowlist names only the two recorded keys, and the
  canary still reports its three novel credentials plus a novel 64-hex key
  planted in each allowed evidence path. Evidence: `gitleaks detect` and
  `scripts/check-gitleaks-allowlist.sh` output, and the main-push secret scan.
- AC-2 When osv-scanner audits the repository's lockfiles, it reports no
  advisory. Evidence: local osv-scanner 2.4.0 output and the main-push
  security review.
- AC-3 The portal and its starter stay byte-identical, and the lockfile,
  runtime-script and ownership pins match the files. Evidence: the portal
  tests and the portal and manifest Rust tests.
- AC-4 When an adopter runs `codeflow init --standard --yes` and
  `codeflow portal setup --path docs-portal` with this build in a new
  repository, the adopted portal pins `fast-uri` 3.1.8 and osv-scanner
  reports no advisory on its lockfile. Evidence: that run, against the
  same run with the binary built from the 3.0.0 release head, which pins
  3.1.6 with three advisories. (journey)
- AC-5 When `codeflow ci` judges a pull request into `main` against a base
  that carries the remapped record baselines, it reports no baseline
  ancestry, workgraph or planning-anchor block. Evidence: `codeflow ci`
  on this branch with the remap commit as base, in a clone of this
  repository, and with the public `main` as base in a public-only clone
  (warnings only), plus the hosted policy check on this pull request.
