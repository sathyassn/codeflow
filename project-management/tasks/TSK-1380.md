# TSK-1380: Idle build output in a project's worktrees is cleaned up by one safe command

## Description

Worktree build output fills the disk. TSK-357 measured one worktree's `target/debug` at 56 GB and about 260 GB across the worktrees of one machine. Today the only safe cleanup is a workspace script, `coordination/scripts/free-idle-targets.sh` (agentic-systems workspace, outside this repository). It is POSIX shell with macOS `df -g`, `lsof` and the host's `hc` and Herdr tools, and it exists only on one machine. The cleanup rule (`assets/base/rules/worktrees.md` "Cleanup") tells every adopter to remove "the worktree's `target/`" when a task lands, but gives no command, so each adopter writes a `rm -rf` of their own.

This task adds that command to `codeflow work`, working the same way on macOS, Linux and Windows. It is a dry run unless asked to apply. It acts only on configured build output folders directly inside the project's own `.worktrees/<name>/`, never follows a link, refuses when it cannot tell whether a worktree has an owner, and reports each folder it removed or skipped, with the bytes and the reason.

What the script does today, so nothing is lost when the workspace retires it: it touches only a real directory named exactly `target` directly inside `<project>/.worktrees/*`; it checks the resolved path is still under `.worktrees`; it skips a worktree that `worktree-in-use.sh` reports in use (cwd of any process by `lsof`, `hc` terminals, Herdr panes, fail closed when `hc` is unreadable); it skips a folder with anything written in the last 90 minutes, but looks only two levels deep; it dry-runs by default and removes with `--apply`; it prints per-folder sizes and a total, then the volume's free space. Known gaps this task closes: the 90-minute check misses a recent write deeper than two levels, the owner check depends on `hc`, nothing covers Windows, the output list is fixed, and nothing is recorded.

Where the command sits: `codeflow work` already holds the durable-work cleanup route `work remove-candidate` (TSK-1308), which reads its settings from the landed policy, refuses on anything it cannot read, and writes a ledger event. This command follows the same pattern. `codeflow status` already classifies worktrees as removable, dirty or unproven (`crates/codeflow-core/src/status.rs:43`); that classification is about whether a worktree can be removed and stays as it is.

Non-goals:

- Removing a worktree, a branch or any ref. `git worktree remove` and `work remove-candidate` keep those, with their merge proofs.
- Anything outside the project's own `.worktrees/`: a `CARGO_TARGET_DIR` elsewhere, `~/.codeflow/gate-runs`, review builds in other folders, global caches, and the worktree folders that other tools manage (`git.worktree_locations` beyond `.worktrees`).
- Running by itself. There is no hook, timer or daemon; a person or session runs the command.
- Host-specific owner probes (`hc`, Herdr, any seat manager). A workspace that wants them wraps this command; the command works without them.
- Retiring `free-idle-targets.sh` and `worktree-in-use.sh`. That is workspace work, done after this lands (AC-16 gives it the mapping).
- Changing the unsupported key `git.clean_regenerable`, which stays accepted and inert.

## Outcome

After this merges, a maintainer or an agent can free the idle build output of the project's worktrees with one command that previews first, removes only rebuildable folders inside `.worktrees/`, and says what it removed and what it left, on macOS, Linux and Windows.

- the command and its removal logic: `crates/codeflow-cli/src/cmd/work.rs` (new `clean-output` subcommand) and a new module under `crates/codeflow-core/src/workgraph/` (provisional; AC-1 decides the module and the platform split)

- guidance: `assets/base/rules/worktrees.md` "Cleanup", its copies `.codeflow/rules/worktrees.md` and `.codeflow/.baseline/.codeflow/rules/worktrees.md`, `docs/cli.md`, `docs/policy-reference.md`, `docs/capabilities.md`, and the generated limits page where it exists
- release note: `changelog.d/TSK-1380.md`
- findings for AC-1: a `## Findings` section in this record

## Acceptance Criteria

- AC-1 Before any change, the builder shall record in `## Findings`, with file:line: each rule of `free-idle-targets.sh` and `worktree-in-use.sh` and where this command meets it; every existing cleanup, inventory and removal route (`work remove-candidate`, `codeflow status` dispositions, `worktrees.md` "Cleanup") and what each leaves to this command; the way to list a process's working directory and open files on macOS, Linux and Windows without `lsof`, `hc` or Herdr, and what each cannot see; and every CodeFlow state that names a worktree and can be live (gate lock, fence and slot holder records from `crates/codeflow-core/src/testing/gate_guard.rs:640`, `codeflow reserve` slots, work claims, delegate records), with how liveness is told. Evidence: the Findings section.
- AC-2 `codeflow work clean-output` shall be a dry run by default that changes nothing on disk, and shall remove only with `--apply`; evidence: a CLI fixture that hashes the whole project tree before and after a bare run and an `--apply` run with nothing eligible, and one that removes an eligible folder only under `--apply`.
- AC-3 The command shall act only on a configured output folder that is a direct child of a linked worktree registered with this repository (as `git worktree list` reports it) and located directly under `<root>/.worktrees/`; the root checkout, a worktree elsewhere (including `.claude/worktrees` and the other `git.worktree_locations` folders), an unregistered folder under `.worktrees/`, and an output folder nested deeper in a worktree shall be left alone; evidence: one fixture per case, each tree byte-identical after `--apply`. When run from a linked worktree, it shall find the same root through the git common directory.
- AC-4 Before any removal the command shall resolve the real paths of `.worktrees`, the worktree and the output folder, shall refuse unless none of the three is a link (symbolic link, Windows junction or other reparse point) and the output folder's real path equals `<real root>/.worktrees/<name>/<output>`, and shall check the folder's identity (device and inode, or volume serial and file index) again immediately before it removes anything and treat a change as a refusal; evidence: fixtures for a linked `.worktrees`, a linked worktree folder, a linked output folder, and an output folder swapped for a link between the check and the removal (through a test seam), each refused with the cause named and the link target untouched.
- AC-5 The command shall never follow a link, at the output folder or at any depth below it. It shall open each directory without following a link (on Unix with `O_NOFOLLOW` and `O_DIRECTORY`, on Windows with a handle opened without following a reparse point), list it through that open handle, and remove each child through the open directory (`unlinkat` or the equivalent, or a handle-relative delete on Windows), never by joining a path string and removing that path. A symbolic link, junction or other reparse point found as a child shall be unlinked as an entry and its target left whole. Evidence: (a) a fixture with a folder outside `.worktrees/` holding a file, linked from inside an output folder by a file link, a directory link and (on Windows) a junction, where the outside folder and file are intact after `--apply`; (b) a swap seam that, after a directory has been listed and before the walk enters it, replaces a child directory with a link to a folder outside `.worktrees/` (a symbolic link on Linux, a junction on Windows), where the walk refuses to enter or removes the link as an entry, reports it, and the outside folder and its files stay whole. Linux and macOS run locally or in CI; Windows runs in the evidence run of AC-12.
- AC-6 The command shall remove only rebuildable build output, never source, records, worktrees, branches or `.git`: a configured folder shall be removed only when git ignores it and no tracked file lies inside it, and a folder that fails either test shall be skipped with that reason; a configured folder name that is a path (a separator, `..`, an absolute path, a glob, a drive prefix), or that is `.git`, `.worktrees` or empty, shall be refused as a setting naming the key. Evidence: fixtures for an ignored folder (removed), an unignored folder, a folder holding one tracked file, and each refused name; the `--help` text of AC-15 states the same limit.
- AC-7 A worktree shall count as owned, and its output folder be skipped with the owner named, when any of these holds: it has uncommitted work (a tracked change, a staged change or an untracked file that git does not ignore); a running process has its working directory, an open file, an open directory or its program image inside the worktree; or a live CodeFlow record names it (each kind AC-1 found, such as a gate lock, fence or slot holder). The owner check shall use no `hc`, Herdr or `lsof`. Evidence: a fixture per kind (a dirty worktree, an untracked file, a child process with its working directory inside, a child holding a file open inside the output folder, a live holder record, a stale holder record that does not count), run on each platform the hosted partitions cover.
- AC-8 The owner check shall fail closed: when the worktree's git state, the process list, a CodeFlow state record or any source AC-1 named cannot be read, is oversized or is malformed, or when the platform offers no scan that covers the current account's processes, that worktree shall be refused with `owner unreadable: <what>`, nothing in it shall be removed, and the command shall exit non-zero; a process of another account that the platform hides by design shall be listed as not checked in the report, never ignored silently. Evidence: a fixture with each source made unreadable through a test seam; and a run with `hc`, `herdr` and `lsof` absent from `PATH` that gives the same skips and removals as a run with them present.
- AC-9 An output folder shall be idle only when no entry anywhere in its tree, at any depth, has a modification time within the threshold; the walk shall not follow links and may stop at the first recent entry; a recent folder shall be skipped with how long ago the newest write was. Evidence: a fixture with the one recent file six levels down (skipped, where the script's two-level check would remove it) and an old tree (removed), under a test clock.
- AC-10 The command shall read three settings from the project's policy, declared in the policy schema with purpose, valid values and notes, and shall read them from the landed policy (the default branch's policy, as `work remove-candidate` does) and never from the worktree being cleaned: `git.build_output_cleanup` (an enum schema kind of `on` and `off`, default `on`; not a Level key, which would accept `warn`, `allow` and `block` that mean nothing here), `git.build_output_dirs` (a list of folder names, default `["target"]`), and `git.build_output_idle_minutes` (a whole number of at least 1, default 90, declared once as an operational `Limit` with its reason and no ceiling, so a project can raise it as far as it wants). A wrong type, a value below the floor, or an invalid folder name shall refuse naming the key; an unreadable landed policy shall refuse the run. The shipped policy file shall not list the keys, so an older binary never meets them. Evidence: tests for each default, an override, each refusal, a branch whose own policy edit does not change what the command removes, `codeflow policy explain` showing the keys, and the limits drift test passing.
- AC-11 When `git.build_output_cleanup` is `off`, the command shall remove nothing even with `--apply`, shall say that the policy turned it off and name the key, and shall exit 0; evidence: a fixture with the key off and an eligible folder that stays whole.
- AC-12 On Windows the command shall remove an output folder whose paths pass 260 characters, shall remove read-only files and folders by clearing the read-only attribute only on entries inside the confirmed output folder and only where removal needs it, and shall leave and report a folder it could not finish (a file in use) with the rest of the work done; evidence: a Windows fixture with a path of more than 260 characters, a read-only file and a read-only folder, passing in the completed `windows tests` partition of a pull request into `main` or of the daily run, named in the pull request that carries it (the placement of ADR-0097 :37 and :70-71 and `docs/releasing.md:224`: a push to the line runs no Windows partition, so a line push is never this evidence; a macOS run does not stand in for it). Until that run exists the Windows fixtures are named as not yet verified in the task's Closeout, never as passed. A removal that fails partway on any platform shall report the folder as failed with the cause, count the bytes already freed, and exit non-zero.
- AC-13 The command shall report each output folder it looked at as one of would remove, removed, skipped, refused or failed, with the worktree, the folder, the bytes, and the reason or the owner named; a total of folders removed and bytes freed (in a dry run, bytes that would be freed); the folders skipped counted by reason; and the volume's free space before and after where the platform can read it. The bytes shall be summed from the entries actually removed, not estimated beforehand, and `--json` shall print the same fields. Evidence: output snapshot tests, and a fixture where the reported bytes equal the sum of the sizes written.
- AC-14 Each removal under `--apply` shall be recorded in the ledger as a `build_output_removed` event carrying the worktree, the folder, the bytes and the time, the way `candidate_removed` records its proof; a failed ledger write shall be reported by name after the removal, with the report printed in full. Evidence: an output and ledger test.
- AC-15 The command shall have help text and docs: `--help` shall state that it is a dry run unless `--apply`, name the scope (build output folders directly in `.worktrees/<name>/` only), name the settings, and say it removes only rebuildable build output and never source, records, worktrees or branches; `docs/cli.md`, `docs/policy-reference.md`, `docs/capabilities.md` and the limits page shall list it and the three keys; the `worktrees.md` "Cleanup" bullet on build output shall name the command, byte-identical in `assets/base/rules`, `.codeflow/rules` and `.codeflow/.baseline`; `changelog.d/TSK-1380.md` shall carry `release-impact minor`. Evidence: the text diff, `codeflow validate --docs`, and the generated-page and byte-identity checks passing.
- AC-16 The pull request shall map each rule of `free-idle-targets.sh` and `worktree-in-use.sh` (AC-1) to the criterion and the fixture that reproduces it, and name the one deliberate difference per rule (the full-depth idle check, the portable owner scan in place of `hc` and Herdr, the setting-driven folder list, the ledger record). The mapping shall also say that the script loops over every project in the workspace while one `codeflow` run covers one repository, so the workspace wrapper keeps the loop, and that `worktree-in-use.sh` stays, because it treats an unreadable `hc` as in use and an idle seat's working directory can be absent from `lsof`; the wrapper runs it first and this command second. Retiring or changing the scripts is the workspace's task and is not done here. Evidence: the mapping table in the pull request body.
- AC-17 (journey) With the installed build, in a scratch project with a bare origin and four linked worktrees under `.worktrees/` (idle and clean; written inside the threshold; dirty; a process with its working directory inside), each with a `target/` of known size, one link out to a folder outside `.worktrees/`, and one worktree whose `target/` holds a tracked file, run from an agent session with the built hooks installed so that a guard refusal would show: the bare run shall list exactly what it would remove and change nothing; `--apply` shall remove only the idle clean worktree's `target/`, report the bytes it named, and leave every other path byte-identical; a second `--apply` shall report nothing to remove. The run shall be made locally on macOS, on Linux in CI, and on Windows in the pull request into `main` or the daily run of AC-12, never a line push. Evidence: the journey output on each platform.
- AC-18 This is a deleting command that reads policy and filesystem state, so it shall have a cross-lineage security review, with the seat's availability checked live, and the pull request shall state the threat each design choice closes: an escape through a link or a swap between check and removal (AC-4, AC-5), a branch editing its own policy to widen the folders (AC-10), a worktree wrongly judged idle or unowned (AC-7 to AC-9), and an over-broad folder name (AC-6). Evidence: the review verdict and the threat list in the pull request.
