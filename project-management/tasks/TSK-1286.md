# TSK-1286: An epic declares the integration line it lands on

## Description

The regroup of 2026-11-03 moves every open task of EPC-022 to a feature epic that lands on the same line, `integration/EPC-022-the-3-2-0-milestone-fixes`. Today the line binds only to the epic its name carries: `epic_line_binding` (`crates/codeflow-core/src/workgraph/work_start.rs:895-938`) refuses a task whose `epic_id` differs from `line_adoption::epic_id(line)` unless it is standalone with a reason, and `epic_line_bound_at` (`work_start.rs:952-998`) binds the line only when a task of that one epic names it. Its callers are `crates/codeflow-cli/src/cmd/ci/context.rs:181-215`, `ci/acceptance.rs:225-250`, `ci/line_tip.rs:195` and `crates/codeflow-core/src/workgraph/status_verb.rs:640`, and `line_adoption::epic_id` is read directly in `ci/context.rs:194`, `:397` and `:445`, `ci/acceptance.rs:208` and `:234`, `ci/line_tip.rs:104` and `workgraph/acceptance.rs:4044`. EPC-023's 4.1.0 tasks have the same problem already.

Design, settled by the Director and the stress test of 2026-11-03:

- An epic record may declare `parent_line: integration/EPC-NNN-<slug>`, the exact name of another epic's line. It is the same field TSK-1011 plans (provisional `parent_line`), not a second one; this task introduces it and its binding, and TSK-1011 later adds adoption inheritance for a child line that has its own branch.
- An epic that declares P's line in `parent_line` and has no line of its own lands its tasks on that line, and the line binds a task of that epic as it binds a task of P.
- The value is read only from the trusted anchor records at the line tip (the anchor `epic_line_bound_at` already reads), never from the pushed head, so a branch cannot rebind itself to a line by editing its own epic record.
- One level only: P names the line's own epic, and a parent that itself declares a parent is refused.

Security relevant: it widens which records a line admits, so the negative cases below are the boundary. Non-goals: adoption inheritance (TSK-1011); retargeting records; any change to how a standalone task binds.

Until this task lands, the tasks the regroup moved can start and be judged on the line only through this task's binding, so it is the first unit of the regroup. The planning pull request sets `parent_line: integration/EPC-022-the-3-2-0-milestone-fixes` on EPC-023, EPC-025 and EPC-027 to EPC-039 so the moves pass once this code lands.

## Outcome

After this merges, a maintainer can run several feature epics on one integration line: a task of an epic that declares `parent_line` binds to that line in `work start`, `codeflow ci` and pre-push, and a branch still cannot rebind itself.

Readers of the epic-line binding, the anchor each reads and where the head's records enter:

- `epic_line_proof` (`crates/codeflow-core/src/workgraph/work_start.rs:726`), reached through `check_epic_line_with_adoptions` (`:670`) and `ci.rs:1452`: reads the target's tip, the line's fetched tip (`line_adoption::fetched_tip`, `line_adoption.rs:339`) and the head. Declarations count only from the first two (`declared_line_tasks`, `work_start.rs:1348`); the head can only refuse.
- `epic_line_binding` (`work_start.rs:955`), called by `judged_declared_target` (`crates/codeflow-cli/src/cmd/ci/context.rs:177-215`) for the protected branch and then the line's tip, so a refusal at either wins: the head enters through the branch's own task record (`declared_work_record_at_revision`) and `head_refusal` (`work_start.rs:1056`).
- `epic_line_bound_at` (`work_start.rs:1197`), called by `ci/line_tip.rs:195`: reads only the line's tip.
- `epic_line_at` (`crates/codeflow-core/src/workgraph/status_verb.rs:642`): reads only the trusted tip given to it.
- Name-only readers of `line_adoption::epic_id`, which read no records: `ci/context.rs:196`, `ci/line_tip.rs:104`, `ci/acceptance.rs:208` and `:234`, `workgraph/acceptance.rs:4044`, `acceptance/receiving_merges.rs:26`.

What review found and what was decided:

- Round 1 (5dcc8d8ce): the head's own declaration was trusted in `epic_line_proof`, and a refusal at one anchor could lose to a binding at another. Decided: declarations bind only from anchors, and a refusal at any anchor wins (fac11e366). The line-name grammar was tightened to need a slug and a valid branch name (`line_adoption.rs:151`).
- Round 2 (fac11e366): a head that changed or deleted a trusted declaration passed, and an owner epic cancelled at the fetched tip did not veto. Decided: both refuse (7b07c2f57, `line_owner_refusal` at `work_start.rs:695`).
- Round 3 (7b07c2f57): the own-task shortcut skipped declaration refusals. Decided: every declaration refusal runs before any binding (a2cc6057b), approved in round 4.
- One level by exact name: the declaring epic names the line, whose name carries the anchor epic (`line_membership`, `work_start.rs:1272`), so a chain through a third epic never binds. A `parent_line` on a task record is refused (`task_parent_line_refusal`, `work_start.rs:1039`).
- Found 2026-11-04 while writing AC-7's docs: nothing refused an anchor epic P that itself declares a `parent_line`, which AC-3 lists. `line_membership` looked P up only to check that it exists, and `bound_in` checked only P's status, so a feature epic's task bound and its line push passed with the 4.0.0 beta (exit 0). Decided: refuse it at each trusted anchor, through `chained_owner` in `bound_in` and `declared_line_tasks` and through `line_membership`, naming the cause. Once the anchor holds a declaring epic's task, the whole line refuses, its own epic's tasks included (the stricter choice, kept after PR 593's security review, F1). `codeflow task status` (`epic_line_at`) now judges through the same `bound_in` (F3). A chained line that holds only its own epic's tasks still binds them, so TSK-1011 can still give a child line its own branch.
- `codeflow work start` reads no epic-line binding, so it starts a task of a declaring epic as it starts one of the anchor epic; the binding applies in `codeflow ci` and pre-push.
