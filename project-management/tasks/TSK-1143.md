# TSK-1143: An adopting project gets a bootstrap epic for its initial capability catalog

## Description

CodeFlow offers every adopting project a bootstrap epic for its initial capability catalog. The operator asked on 2026-11-01 for a comprehensive initial catalog, run as an epic with tasks, for any project that adopts. The mechanism is the builder's choice (a `capability bootstrap` verb, or a step of `init` and `update` that `doctor` points to when the catalog is empty). The outcome is fixed: the adopting project gets a bootstrap epic with one task per stage (inventory, classification, evidence, review), created with that project's own `epic new` and `task new` verbs and referencing the guide (TSK-1144), and finishes with a comprehensive reviewed catalog and `inventory: complete`. It must not create records at a tier where the check is `off` unless asked. Basis: a generator of one epic and four task records from templates, the offer in `init`, `update` and `doctor`, and fixtures at three tiers. Non-goals: the guide text (TSK-1144) and CodeFlow's own run (TSK-1146, TSK-1148).

Design: `coordination/coordinators/capabilities/design-note.md` revision 5 and the operator's comments of 2026-11-01 (about 12:47 EST) in the same folder's `DIRECTION.md`.

## Outcome

After this merges, an adopting project gets a bootstrap epic with its inventory, classification, evidence and review tasks, ready to run, instead of having to invent the process.

## Deliverables

- the offer and the generator: `crates/codeflow-cli/src/cmd/capability.rs` and `crates/codeflow-core/src/capability/bootstrap.rs`
- the epic and task templates: `assets/base/` bootstrap templates and `scaffold-manifest.toml` entries
- the offer in `init`, `update` and `doctor` output
- fixtures at minimal, standard and full tier

## Acceptance Criteria

- AC-1 When the offer runs in a project with tracking and an empty catalog, it shall create one bootstrap epic and four stage tasks (inventory, classification, evidence, review) through the project's own allocation verbs, with `depends_on` edges in that order and each task's criteria stating its stage output; evidence: a fixture project at standard tier. (serves EPC-026 AC-11)
- AC-2 The offer shall also work from each of these entry paths: a populated but incomplete catalog (CodeFlow after the migration: the existing records seed the inventory stage and are not re-created); a fresh standard project with no existing tracking (the offer enables the tracking it needs with the change shown, or, where tracking cannot be enabled, writes the same four stages as a checklist file and says so); and a minimal project after an explicit opt-in (the check key set, or the verb run by request), where it shall create nothing unprompted; evidence: one fixture and test per entry path. (serves EPC-026 AC-11)
- AC-3 The bootstrap epic's final criterion shall require `inventory: complete` in the project's catalog and a recorded review; evidence: the generated epic record in the fixture. (serves EPC-026 AC-11)
- AC-4 (journey) A non-Rust sample project shall run the offer and reach a first valid catalog through the four tasks; evidence: the run's output. (serves EPC-026 AC-11)
  - Amended 2026-11-02: the journey tag moved to open the criterion, where the check counts it; the wording and the serves tag are unchanged.

- AC-5 `init`, `update` and `doctor` shall offer the bootstrap whenever `inventory` is not complete and say how to take it; evidence: one test per command. (serves EPC-026 AC-11)

- AC-6 The offer shall be idempotent and resumable: a rerun after any stage is partly or wholly done shall create no duplicate epic or task and shall continue from the first open stage; evidence: reruns at each stage boundary in a fixture. (serves EPC-026 AC-11)
