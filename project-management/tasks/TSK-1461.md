# TSK-1461: The guards and presets protect the harness's saved shell state

## Description

Supported harnesses keep state that they load into later tool calls: Claude Code saves environment and shell setup that each later command runs first, Codex saves a shell snapshot that each command sources, and the Herdr app keeps launch definitions that decide what a later run starts. An agent command or edit that writes that state changes what every later call runs with, outside any guard's view of the later call. These locations also move with each harness's configuration-folder variable. The guards' startup-file class does not cover them, and the shipped presets and the init and update scaffold do not deny writes to them. Grok documents no saved shell state beyond an environment file the class already covers.

The sweep's first step settled the severity: Claude Code's own protection of its folder applies only in some permission modes and not when its configuration folder is moved, and a stronger deny it ships is behind an undocumented flag, so the guards and presets must provide it. Severity: High.

Overlap: TSK-1456 is this task's base. TSK-1457, TSK-1458 and TSK-1460 judge assignments, arguments and started programs; their rules are not in scope. TSK-284 (todo, EPC-050) protects startup folders; this task adds the harness state locations to the same class. A search of open task criteria on 2026-11-11 found no other owner.

Source: the Director's routing of 2026-11-11 about 12:10 (High, main-first) and his rulings on this task that followed (release impact minor; the dogfood patch as an operator commit). Findings by coord/catalog: workspace build brief `coordination/coordinators/capabilities/briefs/key24-build.md` and the sweep `coordination/coordinators/capabilities/builders/key24-sweep.md` (352a551d). Hook payloads were fed as strings to the installed guard 678d3fa48, an ancestor of `main`; nothing was written to any harness location.

## Outcome

After this merges, on every OS, no agent command or edit can change the state a supported harness loads for later calls without the guards refusing it, wherever the harness's configuration folder is; every shipped preset and the init and update scaffold deny those writes, and `codeflow doctor` reports an install that lacks the denies.

## Deliverables

- a saved-state pass in the guards in `crates/codeflow-core` that compares each write, removal, copy, move, link or extraction target with the harness state locations by file identity, with a readings fallback, read every way a command can name them, including through each harness's configuration-folder variable; the startup-file class itself is unchanged (amended 2026-11-12 by the Director's design ruling (a) for this task; was: "the harness state locations added to the guards' startup-file class in `crates/codeflow-core`, read every way a command can name them, including through each harness's configuration-folder variable")
- the denies in every shipped preset (Claude, Codex) and in the init and update scaffold
- the doctor report for an install lacking the denies, with a printed step that clears it
- tests with fail-before evidence, fed as hook payload strings; nothing under test is executed
- this repository's own install (its Codex profile, and the Claude settings, baselines and manifest `codeflow update` writes) brought to the shipped posture by the operator's script, as operator commits on the task branch
- a changelog fragment, minor, in general terms
- `## Findings`: the first step's answer per harness with sources, each case shown or ruled out with its test, the accepted over-refusals, and the sweep
