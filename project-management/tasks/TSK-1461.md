# TSK-1461: The guards and presets protect the harness's saved shell state

## Description

Supported harnesses keep state that they load into later tool calls: Claude Code saves environment and shell setup that each later command runs first, Codex saves a shell snapshot that each command sources, and the Herdr app keeps launch definitions that decide what a later run starts. An agent command or edit that writes that state changes what every later call runs with, outside any guard's view of the later call. These locations also move with each harness's configuration-folder variable. The guards' startup-file class does not cover them, and the shipped presets and the init and update scaffold do not deny writes to them. Grok documents no saved shell state beyond an environment file the class already covers.

The sweep's first step settled the severity: Claude Code's own protection of its folder applies only in some permission modes and not when its configuration folder is moved, and a stronger deny it ships is behind an undocumented flag, so the guards and presets must provide it. Severity: High.

Overlap: TSK-1456 changes some of the same sources but is not this task's base (see Conflict notes). TSK-1457, TSK-1458 and TSK-1460 judge assignments, arguments and started programs; their rules are not in scope. TSK-284 (todo, EPC-050) protects startup folders; this task adds the harness state locations to the same class. A search of open task criteria on 2026-11-11 found no other owner.

Source: the Director's routing of 2026-11-11 about 12:10 (High, main-first) and his rulings on this task that followed (release impact minor; the dogfood patch as an operator commit). Findings by coord/catalog: workspace build brief `coordination/coordinators/capabilities/briefs/key24-build.md` and the sweep `coordination/coordinators/capabilities/builders/key24-sweep.md` (352a551d). Hook payloads were fed as strings to the installed guard 678d3fa48, an ancestor of `main`; nothing was written to any harness location.

## Outcome

After this merges, on every OS, no agent command or edit can change the state a supported harness loads for later calls without the guards refusing it, wherever the harness's configuration folder is; every shipped preset and the init and update scaffold deny those writes, and `codeflow doctor` reports an install that lacks the denies.

## Deliverables

- a saved-state pass in the guards in `crates/codeflow-core` that compares each write, removal, copy, move, link or extraction target with the harness state locations by file identity, with a readings fallback, read every way a command can name them, including through each harness's configuration-folder variable; the startup-file class itself is unchanged (amended 2026-11-12 by the Director's design ruling (a) for this task; was: "the harness state locations added to the guards' startup-file class in `crates/codeflow-core`, read every way a command can name them, including through each harness's configuration-folder variable")
- the denies in every shipped preset (Claude, Codex) and in the init and update scaffold
- the doctor report for an install lacking the denies, with a printed step that clears it
- tests with fail-before evidence, fed as hook payload strings; nothing under test is executed
- this repository's own install (its Codex profile, and the Claude settings, baselines and manifest `codeflow update` writes) brought to the shipped posture by the operator's script, as operator commits on the task branch
- a changelog fragment, minor, in general terms
- `## Findings`: the first step's answer per harness with sources, each case shown or ruled out with its test, the accepted over-refusals, and the sweep

## Findings

- Harness answers (AC-1, from the workspace sweep `coordination/coordinators/capabilities/builders/key24-sweep.md`, step 1 and step 2; documentation and source only, nothing written to any harness location):
  - Claude Code protects its saved shell state only partly. Its documented protected-path rule covers its configuration folder by name: it prompts in the default and accept-edits modes, denies in the don't-ask mode, leaves the call to the classifier in auto mode and allows the write in bypass mode (Claude Code docs, "Permission modes", sections "Protected paths" and "Skip all checks with bypassPermissions mode"). The rule does not match when the configuration folder is moved to a path without that folder name. For shell commands it checks only redirect and `tee` targets ("Configure permissions"). Settings deny rules hold in every mode ("Permission modes", "Available modes"). The sandbox denies writes into the configuration folder for sandboxed commands only ("Sandboxing", "Protected paths"). The environment file a hook appends to runs before later shell commands ("Hooks", "Persist environment variables"). The installed 2.1.322 binary, read as strings, has a stronger every-mode deny for these folders, but it sits behind a server-side feature flag and is undocumented, so it cannot be relied on. Severity: High.
  - Codex saves a shell snapshot that each later command sources, in a folder under its home folder, which its own variable moves (Codex source `shell_snapshot.rs`; the configuration reference lists the snapshot feature as stable and on by default). Codex documents no protection for that folder; the shipped `cf-guard` and `cf-builder` profiles now keep it read-only.
  - The Herdr app keeps launch templates that decide what a later run starts, under the user configuration folder or its Windows equivalent (from its help text and strings; its source is not available).
  - Grok Build documents no saved shell state or environment file beyond the folder environment file it loads, which the startup-file class already covers (Grok settings and hooks docs).
- Fail-before base (AC-1): the rows ran as payload strings on main's installed 4.0.0 binary (source 678d3fa48, an ancestor of the branch's base), not at f8aabc62c. The branch was rebuilt on a later main after the first workspace build on f8aabc62c, and the released binary is the one adopters run; it has no saved-state pass, so it shows the same gap.

- Residuals (key 24 r1 and r2, 2026-11-12): the build and its reviews found further cases outside this task's scope. They are tracked together as one follow-up task that lands on `main` with its own fix; the follow-up's ID goes into `follow_ups` here once it is reserved.

- Cost scope (key 24 r5, 2026-11-12): a program that changes the files of the folder it runs in refuses only where that folder holds saved shell state. That is the case when a user-level configuration folder resolves inside the project, or when the home, `/etc` or the root is the run folder. A project's own `.claude/` folder never counts. The predicate is the saved-state class's placement reading (at edb186bd9: `saved_state.rs:254-325`, `startup.rs:434-458` and `startup.rs:3422-3460`). Rows fed as payload strings to the branch binary at edb186bd9 (`k24r3/scoperow.sh`, log 108): in a project with its own `.claude/` folder and its own `.claude/session-env` folder, an extraction, an unzip, a `find -exec` and a redirect to a named file all run in both hooks, and a copy into `.claude/` runs; with the home as the run folder, an extraction, an unzip and `git checkout` refuse in git-guard. The operator accepted this cost in decision D5 (2026-11-12 about 10:36), and the Director's ruling of about 13:22 applied it to this reading.
