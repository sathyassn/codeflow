# TSK-178: a spec changes only in a planning change

## Description

SPC-013 R-32 now lets an approved spec be amended in place until it is
`implemented`, through a reviewed planning change (planning resolution
25). Today only review enforces "planning change": no check stops a task
pull request from editing a consumed spec's text. R-52 already stops a
task pull request from changing its own criteria (`work.criteria_frozen`,
`workgraph/acceptance.rs:582`), and `spec status` approval already needs
a planning-only change (`workgraph/lifecycle.rs:1311`). This task adds the
same guard for spec text, so the amendment route in R-32 is checked, not
only reviewed. Fable's review of the TSK-169 planning change proposed it
(finding P3-5).

## The rule

- `codeflow ci` refuses a range that adds, changes or deletes a spec file's
  content unless the range is a planning change. A spec file is a record
  under `project-management/specs/`, including any area file TSK-146
  splits SPC-013 into.
- A planning change is a range whose every path is under
  `project-management/` or `docs/plan/`: the same path set that `spec
  status approved` requires (R-70, `lifecycle.rs:696`). One predicate
  serves both rules.
- Not judged, because other rules own them: the frontmatter fields the
  commands write (`status`, `supersedes` and `superseded_by` by `spec
  status`, `uid` by `ids backfill` and the merge rule).
- Not judged: a verified epic line landing on its target (R-52 treats it
  the same way), and a spec change that TSK-140's rule attributes to a
  brought import on a release range. Their spec changes were judged when
  their planning change landed.
- The finding names the spec, the paths outside the planning set, and the
  route: "change a spec in a planning pull request on the target, then
  rebase".

## Flows checked before filing

None of today's flows edits a spec's text inside a task range:

- `spec new --for` allocates a spec on a `plan/` branch; records are
  allocated only there (`project-organization.md`, "Planning records").
- `spec status` writes only frontmatter, in a planning-only change.
- `task status complete` writes only the task record; `implemented` is
  derived and never written (R-51).
- `codeflow update` writes `project-management/templates/`, never
  `project-management/specs/`.
- `ids backfill` writes only the `uid` field.

Two open tasks do edit SPC-013's text in task ranges: TSK-140 AC-7
restates the binding rule, and TSK-146 splits the spec into area files.
Both land before this rule is armed (TSK-146 follows TSK-140, and this
task depends on TSK-146), so no carve-out is needed. After this task, a
change of that kind lands through a planning pull request.

Known gap, shared with the approval rule: a task branch whose range
touches only planning paths passes. Closing it for both rules is not in
scope.

## Default level

The rule takes the `git.work_records` level (`block` or `warn`, default
`block`), like the acceptance binding it sits beside, so no new policy key
is added. Block, because a spec edited inside a task pull request is the
silent drift R-32's planning route exists to prevent, the fix is one
planning pull request, and no current flow needs the edit. A project that
needs time can set `warn` in a reviewed policy edit, which also softens
the other `work_records` rules; the finding text says so.

Adopter impact: only projects with durable work tracking have specs. After
`codeflow update`, a task or direct pull request that edits a spec's text
fails `codeflow ci`; the spec change moves to a planning pull request.
Specs that no range touches are not judged. This is a behaviour change,
not a break: no command or format changes.

## Acceptance Criteria

- AC-1 When a range changes a spec file's content and touches a path
  outside `project-management/` and `docs/plan/`, `codeflow ci` shall
  report it at the `git.work_records` level, naming the spec, the outside
  paths and the planning route; evidence: `lifecycle_tests.rs` for an
  added, a changed and a deleted spec in a task range.
- AC-2 A planning-only range that changes a spec's text, a range that
  changes only `status`, `supersedes`, `superseded_by` or `uid`, a
  verified epic line landing, and a brought import on a release range
  shall produce no finding; evidence: a test for each.
- AC-3 At `warn` the finding is a warning; at `block` it fails the run;
  evidence: `ci_cli` tests at each level.
- AC-4 (journey) On a fresh full-tier project driven by the built binary:
  a task pull request that edits an approved spec's text fails `codeflow
  ci`; the same edit in a planning pull request passes; `spec status
  approved` and `ids backfill` in their usual ranges pass; evidence: a
  case in `record_lifecycle_journey.rs`.
- AC-5 CAP-010, `project-organization.md`, `docs/adoption.md` and
  `CHANGELOG.md` (one pending Added entry, marked
  `codeflow:release-impact minor`, naming the behaviour change) describe
  the rule; mirrors, baselines and manifest are in sync; evidence:
  `manifest_consistency`, `orchestration_contract`, `codeflow validate
  --docs` and `codeflow ci` clean.
