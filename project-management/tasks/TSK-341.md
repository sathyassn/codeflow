# TSK-341: Stacked claims find and check their reviewed predecessor consistently from any checkout

## Description

Issue: #216. `workgraph/work_start.rs:1592` resolves stacked pins by iterating only `task.depends_on` (`:1622`), and returns those pins at `:1666`. It does not recursively preserve the verified predecessor's own stacked authority. This is related to proposal F by transported provenance, but concerns unlanded reviewed work rather than landed completions.

Outcome: **A claim accepted on a reviewed predecessor chain remains pushable under the same verified pins, or claim refuses the unsupported chain before creating unusable work.**

Source inspection is from the accepted triage at `c5c6f6f671d2bf67a77113c656b3be446fb0bea1`; runtime reproductions remain implementation evidence.

Widened 2026-10-26 for issue #332 (CodeFlow 3.1.1), the converse
disagreement. A completed, unlanded predecessor that merges its target
cleanly to stay current can no longer be claimed on: `review_covers_pin`
(`crates/codeflow-core/src/workgraph/work_start.rs`) refuses any merge
in the span between the reviewed commit and the pin, and
`PinBranches::pin_name` refuses the reviewed pre-merge commit once the
branch has advanced. The predecessor's own push accepts the same
history through its acceptance binding (R-60, a clean re-merge of its
target), so claim and push judge one history two ways. AC-5 makes claim
reuse the push's rule.

## Findings

The bounded behavior is early refusal of a predecessor that itself contains an
unlanded predecessor (AC-3). This keeps claim and push decisions consistent
without treating contained ancestry as review evidence. Land the earlier
predecessor on its declared target, then retry with the next predecessor's
current reviewed head.
Single-predecessor pins remain supported, including a clean re-merge of their
own integration target. Full recursive chain support would need independently
verified evidence for every link and is outside this bounded implementation.

At the assigned base, `PinBranches::read` obtains ids from
`visible_task_ids(root)`, which enumerates checkout record files.
`PinBranches::once` supplies `repo.workdir()`. Branch identification therefore
changes with the checkout and untracked files. Pin lookup must instead read
the target commit's records, falling back to the pinned tree only for a record
the target lacks.

Claim and start use `cmd/work.rs::resolve_pins` and `reviewed_pins` for explicit
pins. Their structural checks subsequently validate dependencies against the
anchored graph. Pre-push reaches `cmd/ci.rs` through the push set; CI and
pre-push both discover predecessor pins through `stacked_pins`. That function
checks only direct dependencies and does not carry the predecessor's own pins.
`review_covers_pin` currently refuses every merge after review, including a
clean re-merge that the predecessor's own acceptance binding permits.

The claiming task's committed head record may supply its own dependency edge
for start. Other graph records remain anchored to the target. Checkout files
provide no dependency or pin authority.
