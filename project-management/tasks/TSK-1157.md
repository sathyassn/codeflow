## Investigation

This is the design of the cancelled local shards (AC-1 to AC-4). It is kept
as history; the Findings measured its first check and cancelled it.

Read for this design: `scripts/coverage-shards.py`, `scripts/windows-partitions.py`,
`scripts/coverage-merge.py`, the `rust-coverage` target in
`.codeflow/test-config.json`, `.config/nextest.toml`, the scheduler in
`crates/codeflow-core/src/testing/runner/mod.rs` (heavy admission and worker
allocation, around lines 425 to 530) and the file list of PR 483 (TSK-1145,
heavy targets sharing the host). Nothing is built yet. Items marked *to prove*
are checked first in the task PR, before the rest is written.

### What the target is today

- `rust-coverage` is one custom command, `cargo llvm-cov nextest --workspace
  --no-fail-fast --fail-under-lines 90 --profile codeflow`, `heavy: true`,
  `workers: 9`, JUnit at `target/nextest/codeflow/junit.xml`.
- The scheduler gives a heavy target its workers and sets `CARGO_BUILD_JOBS`
  and `NEXTEST_TEST_THREADS` to that number. Heavy targets share
  `execution.worker_budget` (9), so coverage already uses the whole budget.
- The floor lives only in that command's `--fail-under-lines`.
  `coverage-merge.py --floor-from` reads it with a regex on the same command,
  so CI and the local target already share one floor declaration.
- CI runs 2 shards (PR 620, TSK-1321, replaces this plan): each runs `cargo llvm-cov nextest
  --no-report -E "$(coverage-shards.py filter N)"`, exports a JSON report,
  and a report job runs `coverage-merge.py` and `coverage-shards.py check`.

### Challenge to the estimate

Sharding on one host adds no threads: the 9 workers are the budget and stay 9.
The planner data holds 87.6 test minutes in total, about 9.7 minutes on 9
threads, against 22.6 measured. So a large part of the target is outside
parallel test execution: the instrumented build, and the serial group (6.4
test minutes, `max-threads = 1`: `test_gate_cli`, `present_cli`, `init_e2e`,
`codeflow-present`, `process_group`). Shards can recover serial and tail time,
not the build. *To prove first:* split one full run's 22.6 minutes into build,
parallel tests and serial tests from the nextest log timestamps. If the
recoverable share is under about 5 minutes, cancel this task with that
measurement as the reason (`codeflow task status` cancelled, with the
numbers), because the saving would not justify a new moving part. The brief's
10 to 14 minute saving is an estimate, not a measurement, and no criterion
promises a time: AC-3 records the wall time whatever it is.

### Design

Declaration. The shard count is the planner's own: `partitions` in
`scripts/coverage-test-times.json` (2 today; PR 620 removes the file). There is no
second count in `.codeflow/test-config.json`. The target's `full` command
keeps its canonical cargo line and gains a wrapper prefix:
`python3 -B scripts/coverage-local.py -- cargo llvm-cov nextest --workspace
--no-fail-fast --fail-under-lines 90 --profile codeflow`. The
`--fail-under-lines N` text that `coverage-merge.py` reads is unchanged.
`scripts/gate-parity.py` (`COVERAGE` at line 41, the derivation at lines 362
to 372) learns that form: it strips the wrapper prefix and `--`, then derives
the hosted shard line from the cargo line exactly as it does today, so
`.github/workflows/codeflow-ci.yml` does not change and a hosted job never
starts a local fan-out. `local_rust_commands` (`gate-parity.py:64-66`) counts a
command as the coverage stand-in only when it starts with `cargo llvm-cov ` and
matches `COVERAGE`; it must match the stripped cargo line, or `SUITE` drops
out of the local set and `rust_parity` fails (`test_the_committed_config_is_at_parity`
requires equality). With the strip, the committed config still owes `SUITE`.
`scripts/test_gate_parity.py` gains cases: the bare cargo form is still
accepted, the wrapped form is accepted and yields the same shard line, and a
wrapper with any other tail fails. `scripts/test_gate_contracts.py:314-315`
pins the bare command byte for byte; the task updates that pin to the wrapped
command and keeps the cargo tail. `docs/releasing.md:580` (the Coverage row)
still names the cargo line as the local full-gate run; the AC-4 note there
says the wrapper is that run, with the same cargo line inside. PR 620 (TSK-1321) also
edits that test file and replaces the shard plan; whichever lands second merges the other in. The scheduler
is not changed (TSK-1145 / PR 483 owns it): the wrapper is an ordinary heavy
custom command that reads the `NEXTEST_TEST_THREADS` and `CARGO_BUILD_JOBS`
the scheduler already sets. The scheduler sets `CODEFLOW_ORACLE_WORKERS=1`
when the command text contains `nextest`, which the wrapped command does, and
the wrapper also sets it to 1 on every shard.

Run. `scripts/coverage-local.py` does, in order:
1. `cargo llvm-cov clean --workspace`, then one build
   (`cargo llvm-cov nextest --workspace --no-run --profile codeflow`), so
   shards do not race on compiling.
2. `coverage-shards.py drift` on the build's test list (the list does not
   exist before the build). A failure stops the target before any shard
   starts. The local target applies only drift's unmeasured-test failures. The
   14 minute plan cap and the 24 job-minute check margin (test minutes plus 6
   setup minutes) belong to the hosted jobs under their 30 minute limit and
   stay on the hosted path: the CLI `plan`, `drift` and `check` defaults in
   `windows-partitions.py` and `coverage-shards.py` are unchanged, so a hosted
   call that passes nothing extra still fails a long plan or shard. The
   wrapper calls the planner's functions directly and passes a local limit
   (none), so it applies the missing, duplicate and wrong-shard rules and
   neither cap.
3. Start the shards. Each shard's argv is `cargo llvm-cov nextest --workspace
   --no-fail-fast --no-report --profile codeflow -E "<filter n>"`, with
   `CODEFLOW_ORACLE_WORKERS=1` and `RUST_TEST_THREADS=1`. With T the
   scheduler's `NEXTEST_TEST_THREADS` and N the planner's shard count, the
   wrapper runs k = min(N, T) shards at once and splits T into k parts of at
   least 1; `NEXTEST_TEST_THREADS` and `CARGO_BUILD_JOBS` take that part. When
   T is below N, the other shards wait their turn in plan order, so every
   planned shard runs and none is dropped; the threads of the shards running
   at once never sum past T.
4. When all shards exit, run one `cargo llvm-cov report --fail-under-lines
   <floor>` and the exactly-once check.

When the scheduler sets no worker count (the wrapper run by hand), it runs
today's full suite: the unfiltered canonical cargo command in one process.
The exactly-once check still runs on that run's test list and report and
requires each listed test once.

Merge. All shards write profiles into one target directory with the pooled
`LLVM_PROFILE_FILE_NAME=codeflow-%4m.profraw` that CI already uses; the LLVM
runtime merges concurrent writers under a file lock. One `report` over that
pool gives the single-process total by construction, so `coverage-merge.py`
and its recomputation are not needed locally (they exist because CI shards run
on separate machines). Alternative considered: a profile directory per shard
plus `coverage-merge.py`; rejected for the extra export step and a second
implementation of the total. *To prove:* the merged total equals the
single-process total on the same tree.

Reports. Concurrent shards must not overwrite `junit.xml`, and the
`journey-gate` target and the exactly-once check read JUnit. *To prove:*
whether nextest takes a per-run JUnit path or store directory from the command
line or the environment. If not, the fallback is a generated tool config file
per shard. The wrapper then writes `target/nextest/codeflow/junit.xml` as the
union of the shard files, so `journey-gate` is unchanged.

Isolation. In CI each shard has its own machine. Locally, the serial group
keeps its tests apart within one process, but two shards could run two
serial-group tests at once. *To prove:* why each serial test is serial (gate
lock, ports, shared state). If any share host state, the wrapper takes the
serial-group tests out of every shard filter (adds the group's exclusion to
each filter) and runs them once in a final single-thread pass with the
group's own filter; each test is still in exactly one place, and the
exactly-once check reads the shards and that pass together as the plan. The
change does not ship
until repeated sharded full runs show no failure that the single run lacks.

### What fails closed

- A shard process that exits nonzero, is killed or times out fails the target
  and names the shard; the other shards are stopped, not waited for.
- The exactly-once check (`coverage-shards.py check` over the shards' test
  lists and JUnit) runs after the shards. A listed test in no shard, in two,
  or outside its planned shard fails the target. A missing shard report is
  "not run", never a pass.
- `drift` runs after the build and before the shards start; too many
  unmeasured tests fails the target before any shard spends time.
- The floor is read from the target's own command text; a missing or
  unparsable `--fail-under-lines` fails the target, as does a report under it.
- Stale profiles are removed first; a report built from no profiles fails.
- If the worker count is not set, run today's full unfiltered suite, with the
  exactly-once check, and say so. The wrapper prints the shard count and
  thread split it used.
- A wrapped command whose tail is not the canonical cargo line fails gate
  parity, so the hosted shard line cannot drift from the local one.

### Hosted disk margin (AC-11 to AC-14)

- None of the eight shard runs above logs `df` or any other disk figure.
  Every shard in them finished, and none logged "No space left on device".
  So the low point cannot be read from past runs.
- This pull request adds the measurement and the check together. A
  background watch records each shard's lowest free disk, and the shard's
  last step fails under 10 GiB or when there is no record. The first run
  after the operator applies the workflow patch is the before measurement
  for AC-11. Freeing (AC-12) follows only if a shard's low point is under the
  margin.
- The margin is 10 GiB, coord/ci's figure. It is not derived from a
  measurement yet. The first run's low points show whether it is right.
- After Grok's security review of 148ea3709 (finding 1), the check also
  fails when the free disk at the end of the job is under the margin, or
  when the record's latest sample is more than 3 intervals old. A record that
  is missing, unreadable or of the wrong type still fails. Without this, a
  record the job could rewrite, or a watch that died after one high sample,
  passed a disk under the margin.
- Accepted limit: a process running as the job's user can still write a
  fresh record above the margin, and it passes while the live disk at the
  end is also above the margin. The live check bounds this to a dip that
  recovered before the report.
