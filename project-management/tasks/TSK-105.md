# TSK-105: acceptance bound to the reviewed commit

## Description

Make a completed task prove its criteria against the result that was
reviewed (design v4 section 5). CI binds the acceptance block to the reviewed
commit, freezes criteria against the target, requires a journey criterion
for adopter-facing ranges, and accepts a waiver only through an amendment
commit on the target. The review skills change with it: cf-reviewer asks
the two questions of section 5.6 and rejects a copied older block,
cf-consult matches, and cf-ship checks the block before shipping. The
parser and the transition rules are TSK-102's.

## Affected surfaces and interfaces

- `codeflow ci` and the scaffolded CI workflow; `task status complete`
  (CAP-003, CAP-010).
- `cf-reviewer`, `cf-consult` and `cf-ship` in `assets/base`, `.claude`,
  `.agents` and the baseline, with manifest hashes and byte budgets.
- Policy: `git.work_records` levels for the binding and the journey rule.
- Shared files this task edits: the CI workflow, the policy schema and
  cf-ship. Ownership follows SPC-013 R-118.

## Acceptance Criteria

- [x] AC-1 When a task becomes complete, `task status complete` and CI shall
      check that every criterion appears once, that mandatory criteria are
      verified or waived, that each waiver names a planning amendment commit
      on the target for that record and criterion, and that the reviewed
      commit is the PR head or an ancestor whose later diff touches only
      this record's status and Closeout; evidence: fixtures for a stale
      block, a waiver without an amendment and a later code change.
      Spec: R-54, R-60.
- [x] AC-2 When a task branch changes its record's criteria, CI shall block
      the pull request; evidence: the criteria-changed fixture.
      Spec: R-52.
- [x] AC-3 When a range touches the adopter-facing path set that TSK-104
      creates and TSK-106 extends (the scaffold, hook sources, shipped
      templates, managed instructions, the CLI command surface, or a
      runtime adopters run, including the present runtime), CI shall
      require a `(journey)` criterion or one serving the epic's journey, and
      a leaf serving the epic journey shall link evidence that ran or state
      its narrower path; evidence: journey-rule fixtures.
      Spec: R-53, R-114.
- [x] AC-4 The checker's output shall state that it proves structure and
      binding, not that evidence is honest, and the review reference shall be
      recheckable; evidence: output snapshot.
      Spec: R-60.
- [x] AC-5 cf-reviewer shall ask whether each criterion is supported on this
      source and whether the result achieves the outcome, may reject naming
      the `AC-n`, and shall refuse a copied older block; cf-consult and
      cf-ship shall match; the skills stay byte identical across mirrors and
      within budget; evidence: skill text, `manifest_consistency` and
      `artifact_budget_contract`.
      Spec: R-61.
- [x] AC-6 `git.work_records` shall set the binding and the journey rule to
      `block` or `warn`; evidence: policy tests.
      Spec: R-80, R-81.
- [x] AC-7 (journey) On a fresh full-tier project with the installed CLI, a
      task completed with a valid block passes and each fault above fails
      for its stated reason; evidence: the section 10 acceptance journeys.
      Spec: R-104.
- [x] AC-8 A criterion observable only after release shall record an
      owner, a measurement window and a follow-up task, and cf-reviewer and
      cf-ship shall never accept it as verified at build time; evidence:
      skill text and a fixture record.
      Spec: R-62.

## Closeout

Implementation is on `task/TSK-105-acceptance-binding`, stacked on
`task/TSK-103-readiness`. Status stays `todo` until the cross-lineage
review; the primary records completion with the acceptance block.

- Delivered outcome: `workgraph::acceptance` binds a completion to the
  reviewed commit (`bind_completion`), freezes criteria on task branches
  (`frozen_criteria`) and states the journey requirement
  (`journey_requirement`); `task status complete` runs the binding before it
  writes (`status_verb::binding`); `codeflow ci` runs it for every range
  (`cmd/ci/acceptance.rs`) and the journey rule with the pull request's
  task (`cmd/ci/classification.rs`); `(after release)` criteria in
  `record_text::after_release_problems`.
- AC-1: `acceptance_cli::a_completion_binds_to_the_reviewed_commit` (an
  unknown reviewed commit, a later code change, a block copied from another
  line, a record change beyond status and Closeout),
  `a_waiver_names_its_amendment_on_the_target` (the amendment passes; an
  unrelated target commit, a branch commit and a ref named like an id
  fail), `task_status_complete_binds_the_block`, and
  `acceptance::tests::only_the_status_line_and_the_closeout_are_outside_review`.
  Every criterion once and mandatory ones verified or waived are the
  TSK-102 structural checks, unchanged.
- AC-2: `acceptance_cli::criteria_are_frozen_on_a_task_branch` (blocks even
  at `warn`; a `plan/` branch changing criteria passes).
- AC-3: `acceptance_cli::an_adopter_facing_range_needs_a_journey` (own
  journey, none, a docs-only control, one serving the epic journey, a
  silent leaf, a leaf naming its narrower path).
- AC-4: the scope note is asserted in CI output and in the verb's refusal
  (`a_completion_binds_to_the_reviewed_commit`,
  `task_status_complete_binds_the_block`, the journey); the reviewed commit
  and a waiver resolve by object id only, never a ref name.
- AC-5: cf-reviewer step 3, cf-consult step 4 and cf-ship step 1 in
  `assets/base`, mirrored to `.claude`, `.agents` and the baseline with the
  manifest hashes; `manifest_consistency` and `artifact_budget_contract`
  pass. cf-reviewer stays within 9.5 KiB; the cf-ship ratchet rises from
  6.5 to 6.75 KiB with a TSK-105 note.
- AC-6: `task_status_complete_binds_the_block` (block refuses, warn
  completes with the warning), `an_adopter_facing_range_needs_a_journey`
  (warn reports without blocking), frozen criteria block at both levels.
- AC-7: `acceptance_journey::a_completion_is_bound_to_the_reviewed_commit_on_a_fresh_project`
  on `init --full` with the built CLI: a valid completion passes the verb
  and CI; a stale block, a waiver without its amendment, a waiver naming
  the head, criteria changed on the branch and a range without a journey
  each fail for their reason.
- AC-8: `acceptance_cli::an_after_release_criterion_is_deferred_never_verified`
  (deferred with owner, window and a listed follow-up passes; verified and
  an unlisted follow-up fail) and the skill text.
- Verification selection: a hand mutation run on the binding checker and
  the verb, 17 mutations, all killed (acceptance_cli plus the unit test).
- Discoveries: `(journey)` is accepted leading or trailing, since the
  records use the leading form; acceptance runs in CI for any range, with
  or without a pull request body; a merge commit that brings the amendment
  onto the target counts as the amendment; existing fixtures gained journey
  criteria and blocks reviewed at the head. The scaffolded CI workflow and
  the policy schema needed no change: `codeflow ci` carries the checks and
  `git.work_records` already existed.
- Not verified: hosted CI, Windows, whether a leaf's evidence link
  resolves (structure only, as R-60 states).
