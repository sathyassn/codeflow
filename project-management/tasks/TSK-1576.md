# TSK-1576: Shipped CI steps refuse a missing or malformed base commit

## Description

Owner: to be assigned by the Director. Staged by coord/records on 2026-11-23, at the Director's direction, from finding K1 of the EPC-057 completion amendment (the Codex confirm of its round k). The Director's ruling of 2026-11-23 on round m moved K1 and its tests out of TSK-1352 into this task, which completes on its own reads.

This is a security fix. Five shipped GitHub steps read a trusted input from the base commit of the change they judge. The base comes from the event, with a fallback. Line numbers are in `assets/base/ci/` at `939d24a15b`.

The defect:

- **Empty pull request base.** When a pull request's event carries no base SHA, these steps take their input from `github.sha`, which on a pull request is the merge of the change's own head:
  - the gate placement (`codeflow-gates.yml:122`, read at `:180-193`);
  - the pinned codeflow version (`:393`, read at `:405`);
  - the gitleaks attribute source and exemptions (`codeflow-ci.yml:337`, used at `:370`, `:404` and `:486`, read at `:512-520`);
  - the security policy, the scanner suppressions and the exception hook (`:972`, read at `:978`, `:1006-1023`, `:1032` and `:1102`).
- **Empty base in the candidate compare.** It reads the index: `git show ":.codeflow/project.toml"` (`codeflow-ci.yml:90`, `:93-94`). The head's pin then compares equal to itself, and the step writes `changed=false` (`:96`).
- **Queue entry with no base.** It hands git the word `unset` (`codeflow-gates.yml:122`, `:393`; `codeflow-ci.yml:972`). That word resolves when the repository holds a branch or tag named `unset` (the mode step tests the value with `git cat-file -e "<value>^{commit}"`, `codeflow-gates.yml:180-181`), so whoever can push such a ref chooses the input. The `gitleaks` step refuses it already (`codeflow-ci.yml:340-342`).
- **Malformed base.** A value that is not a full commit id is handed to git as a revision. The mode step peels it to a commit (`codeflow-gates.yml:180-181`) and reads it (`:182-189`); the install, candidate and audit steps read `<value>:<path>` (`:405`; `codeflow-ci.yml:93`, `:978`), which also works for a tree. The `gitleaks` step checks only that the value is lower-case hex (`:340-342`) and then peels it (`:344`, `:347`). So an abbreviated id, a ref named by a hex string, an annotated tag or a tree can each stand in for the base commit.

Threat closed: a change cannot choose the trusted input that judges it, by its own merge commit, by a ref named `unset` or by a malformed base value.

Why the design is the standard one:

- It fails closed when the trusted input is missing.
- It binds trust to the commit of the branch the change targets, carried by the event, which the change itself cannot alter.
- It checks the value's form, then its object type, before any read:
  - Only a value of the exact width of the checkout's object format (`git rev-parse --show-object-format`), all in lower-case hex, is read as one object id. git can resolve a shorter hex string as an abbreviation, and a string of another width, or of the right width with a non-hex character, as a ref, which is how the malformed cases above can resolve; the test fixtures (AC-3) establish each such case by probe. The lower-case rule matches the policy workflow's check (below) and the `gitleaks` step's (`codeflow-ci.yml:340-342`).
  - `git cat-file -t` must print `commit`. Peeling with `^{commit}`, as the steps do now, accepts an annotated tag that points at a commit.
- The policy workflow already does this: its two `AUTHORITY_SHA` checks, `codeflow-policy.yml:150-152` and `:955-957`, each `grep -Eqx '[0-9a-f]{40}'`, refuse a value that is not a full lower-case SHA-1 commit id (their width is fixed at 40; this task's guard takes the width from the object format), and `:328-330` and `:1009-1011` refuse a fetched base that differs from `BASE_SHA`.

## Outcome

After this lands, the five steps in P33 to P37 take a pull request's or merge queue entry's base commit from the event only, and a pull request or queue entry whose base commit is missing or malformed fails each step that reads that base, naming the base: the mode step only when it places the run (`codeflow-gates.yml:133-160`), and the other four steps whenever they run. A push, scheduled or manual run still reads the run's own commit. Which ref a manual run may read trusted inputs from is outside this task: the Director's ruling of 2026-11-23 files it as its own security task in another epic.
