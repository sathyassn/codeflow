# TSK-141: exec-guard deletion coverage and hooks run by the calling binary

## Description

Three guard and hook defects seen on 2026-09-27, probed at the line tip
`2d3d37176` with the line binary. First, exec-guard's catastrophic floor
refuses `rm -rf /` and `rm -rf ~` but lets the same deletion through when
it is spelled another way: `find / -delete`, `rm -rf /Users/<name>`,
`cd ~ && rm -rf *`, `D=/; rm -rf $D`, `(rm -rf /)`, `{ rm -rf /; }`,
`if true; then rm -rf /; fi`, a `for` loop, `find / -exec rm -rf {} +`
and `ls / | xargs rm -rf` all pass. TSK-112 closed the path forms in
git-guard only. Already refused today and kept by the existing tests in
`security/dangerous.rs`: `rm -rf /*` (`test_rm_rf_root_star`),
`rm -rf --no-preserve-root /` (`test_rm_flag_respellings_blocked`) and
Windows `rmdir /s` and `rd /s` on protected roots
(`test_windows_recursive_delete_protected_roots`). Second, the
headless-run rule of TSK-136 reports `claude --help -p` and
`codex exec --help` as headless runs; at the `block` level that is a
false block. Third, registry seeding from a
checkout whose installed `codeflow` was older than the calling one failed:
the push ran the pre-push hook with the older binary from PATH, which
refused `codeflow/registry` by branch naming. TSK-107 AC-7 does not cover
this: its shim check warns about an older binary and still runs it.

Non-goals: `rmdir` and `unlink` remove one entry, like `rm` without `-r`,
which the floor deliberately allows (ADR-0008), so they are not gaps
against it. The reported `git gc` refusal by the reference-transaction
hook is already fixed on this line (PR 599, `306f9d914`, under TSK-132):
on 2026-09-27 `git gc` and `git pack-refs --all` failed in a hooked clone
with the 2026-09-26 installed binary and passed with the line binary, so
it needs no work here.

## Affected surfaces and interfaces

- exec-guard: `hooks/exec_guard.rs`, `security/dangerous.rs`,
  `security/headless.rs` in `codeflow-core` (CAP-001, CAP-003).
- Hook shims in `assets/base/git-hooks/` and their installed copies; the
  git child environment of the registry push in `ids/issue.rs` and of any
  other git command a codeflow command runs.
- Shared files, per SPC-013 R-118: exec-guard after TSK-136; the hook
  shims after TSK-107, the pre-push shim after TSK-106; allocation and
  registry after TSK-104.

## Acceptance Criteria

- AC-1 When a Bash command reaches a target the catastrophic floor
  protects (the root, a home directory, a system directory) through
  `find ... -delete`, `find ... -exec rm -rf`, `xargs rm -rf`, a literal
  home path such as `/Users/<name>` or `/home/<name>`, a relative path
  after `cd` into such a target, a variable assigned earlier in the same
  command, or inside a subshell, brace group, `if`, `for`, `while` or
  `case` body, exec-guard shall refuse it under
  `security.dangerous_commands` as it refuses the equivalent `rm -rf`,
  and the forms refused today (`rm -rf /*`, `--no-preserve-root`, Windows
  `rmdir /s`) shall stay refused; evidence: exec-guard tests that pair
  each form with its `rm -rf` equivalent, including every gap listed in
  the Description, and the existing `dangerous.rs` tests unchanged,
  except the allowed row `rm -rf /home/user/proj/..`, which asserted this
  gap and moves to the refused tests. Amended 2026-09-28 by the primary:
  that row resolves to the home directory `/home/user`, which this
  criterion refuses, so it cannot stay allowed. Amended again 2026-09-28
  by the primary after the Codex review of round 1, which found these
  forms still passing: the same refusal covers `rsync --delete` and its
  variants (`--del`, `--delete-before`, `--delete-during`,
  `--delete-delay`, `--delete-after`, `--delete-excluded`) with a
  protected destination; the home expressions `${HOME:?}`,
  `${HOME:-...}`, `${HOME:+...}` and `~user`; a relative or globbed path
  that resolves through an existing symlink to a protected target, judged
  by the real path of its longest existing prefix; a `find` rooted at a
  protected target with a deletion action (`-delete`, or `-exec` or
  `-execdir` of a remover), whatever its predicates, and the operands of
  an exec'd remover judged on their own; `xargs` and the remover behind
  transparent wrappers such as `command` and `env`, with here-string
  input; and a variable or working directory any of whose feasible values
  across subshells, branches, loops and `cd -` is protected, since an
  assignment made only in a child or an untaken branch never narrows the
  parent's value. A deletion outside the project that is not under a
  protected target keeps no allowance of its own; `find ~ -name .DS_Store
  -delete` is refused as a find rooted at a home directory.
- AC-2 When a deletion stays inside the project (`rm -rf ./build`,
  `find . -name '*.o' -delete`, a variable that names a project path),
  exec-guard shall allow it; evidence: negative tests. A single-quoted
  `$VAR` is literal text, and a subshell's working directory never
  leaves the parent's. Where the feasible-value rule of AC-1 refuses a
  deletion that would in fact stay in the project, such as a cleanup
  after a loop whose earlier values were protected, the refusal names
  that reason; such refusals are listed in the pull request.
- AC-3 When a `claude`, `codex` or `grok` command line is an effective
  help or version invocation under that CLI's argument grammar,
  exec-guard shall report no headless run; the grammar respects `--`,
  option values, the subcommand position and nested invocations, so
  `claude --help -p` and `codex exec --help` pass while
  `codex exec -- --help`, `claude -p -- --help`, `claude -p -- help`, a
  `help` word given as an option value, and `claude -p hi` still report
  one; evidence: paired exec-guard tests, each exempt form beside the
  same tokens given as prompt or option data, at the `warn` and `block`
  levels, seeded from the Codex plan review probe
  (`followups-help-probe.log`).
- AC-4 When a codeflow command runs git and git fires a CodeFlow hook,
  the hook shall run that same codeflow binary, as SPC-013 R-85 (amended)
  sets: the calling process derives the path from its own runtime
  identity and sets it only in its git child's environment, overwriting
  any inherited value; the shims quote it exactly, run the capability
  probe against it, and fail the hook when it is missing or not
  executable; a git command run outside a codeflow command keeps the PATH
  lookup and R-85 warning; evidence: a `hooks_cli` test in which
  `task new` issues through the registry push with an older stub
  `codeflow` first on PATH (a control fails without the change), and
  negative tests for a poisoned inherited value, another worktree's
  build, a shim launcher on PATH, a path with spaces, a missing
  designated binary, a non-executable file, and a long-lived child that
  must not inherit the value.
- AC-5 (journey) In freshly scaffolded minimal, standard and full-tier
  projects driven by the installed CLI, the Claude, Codex and Grok
  exec-guard wiring shall refuse each AC-1 form, allow the AC-2
  negatives and judge the AC-3 pairs as AC-3 sets, and in the full tier `task new` shall issue with an
  older `codeflow` first on PATH; evidence: `tier_floor_e2e`,
  `codex_hooks` and `id_registry_journey`.
- AC-6 When a `claude`, `codex` or `grok` command runs through a package
  runner (`npx`, `bunx`, `pnpm dlx` or `yarn dlx`, with or without the
  runner's own options), exec-guard shall judge the command it runs as
  it judges the direct invocation: a headless run is reported under
  `security.headless_peer_runs`, and a help or version invocation under
  AC-3's grammar is not; evidence: paired exec-guard tests for each
  runner beside the direct form, at the `warn` and `block` levels. Added
  2026-09-28 by the primary after the Codex review of round 1: the gap
  is inherited from TSK-136, is in the same guard class and ships in
  3.0.0.
