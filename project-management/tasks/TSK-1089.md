# TSK-1089: A topic branch that carries only a line's own commits is judged as the line

## Description

Source: issue #423 (CodeFlow 3.1.1, filed 2026-10-30 by an adopter). No
open task covers it; TSK-433 (complete) gave a line's pull request into
`main` the line treatment of the line's own completions.

An adopter splits an epic line's pull request into `main` into topic pull
requests, each from its own branch carrying a slice of the line's merges.
For the same base, head and flags, `codeflow ci` refuses the topic branch
with `work.acceptance_binding` (the task's reviewed commit is not on the
head's first-parent chain) and passes when `--branch` names the line. The
only difference is the branch name.

The line treatment is keyed on the branch name in several places, read on
the line tip `b7ae7c6a6`:

- `crates/codeflow-cli/src/cmd/ci/classification.rs:236` (a `Task:
  EPC-NNN` body on an `integration/` head becomes `Class::EpicLine`),
  `:259`, `:352`, `:382` and `:639` (the epic-line proof is run only for
  an `integration/` head);
- `crates/codeflow-cli/src/cmd/ci/acceptance.rs:324` (a run without a
  body makes the criteria amendable only for an `integration/` head that
  passes `check_epic_line`);
- `crates/codeflow-cli/src/cmd/ci/context.rs:390`;
- the line bases in `crates/codeflow-core/src/workgraph/acceptance.rs`
  (`:4071`, `:4081`), which mark the judged line only when its name is
  the line.

Rule: a branch gets the line treatment only when its commits show it
carries the line's own judged history: every commit in the range is a
commit of the line, or a merge made on the branch whose result is the
clean re-merge of its parents, each parent being such a line commit or a
commit of the target. A branch name, or an explicit flag naming the
line, only selects which line to check; neither grants the treatment
alone. A picked commit (a new commit with a line commit's patch) is not a
line commit. A branch with any other commit keeps today's judgment.

What counts as the line is fixed by authorities the requester does not
control, separately from the structural epic-line proof, which can take
the epic and the target declaration from the candidate head
(`crates/codeflow-core/src/workgraph/work_start.rs:713`, `:728`) and
does not judge merge commits (`line_adoption.rs:193`):

- the line is the one the target's own records bind to the epic the
  pull request names (`epic_line_binding`, `work_start.rs:883`, read at
  the target tip, never at the head);
- the line's tip is the one the destination advertises for that exact
  ref, resolved once to a commit at the start of the run (the
  remote-tracking ref as fetched for a local run), never a local branch
  or a commit the requester names;
- a commit counts as a line commit only when it is reachable from that
  tip, so it reached the line through the line's own landing route.

How far that tip is judged rests on the hosted protection of lines
(ruleset C, TSK-1080): until a line requires reviewed pull requests on
the host, a requester who can push to the line can place commits on it,
and this task trusts the line no more than `codeflow ci` already does
when `--branch` names it. The task neither widens nor narrows that.

This binds trust, so the review carries the `cf-security-reviewer`
checklist.

Non-goals: changing what the line itself is judged by; the line-to-main
criteria report of TSK-350 AC-9.

## Outcome

After this merges, a maintainer can split an epic line's pull request into `main` into topic pull requests, each carrying only the line's own commits, and `codeflow ci` judges each one as it judges the line.

## Acceptance Criteria

- AC-1 Before any change, the builder shall reproduce the issue's two runs on a fixture of the reporter's shape on the line tip, list every check that keys on an `integration/` branch name (at least the sites in the Description), say for each whether it should follow the commit-based recognition and why, and decide whether an explicit flag naming the line is kept; evidence: a Findings section in this record, committed before the first code change.
- AC-2 When a branch other than the line carries only commits of a line that passes the epic-line proof, plus clean re-merges on the branch, `codeflow ci` shall give it the same verdict and the same binding notes as the same range judged with `--branch` naming the line; evidence: a `ci_cli` fixture of the reporter's shape (a topic branch from `main` carrying a slice of the line's merges, clean), refused before the change with the issue's `work.acceptance_binding` message and passing after. (serves EPC-022 AC-113)
- AC-3 A topic branch with one commit that is not a line commit (a new commit, a picked commit, or a merge whose result differs from the clean re-merge of its parents) shall keep today's judgment; so shall a branch whose commits come from a line that fails the epic-line proof, from a fabricated line (a branch named like the epic's line, or bound to the epic only by records at the head, which passes the structural proof but is not the line the target's records bind), or from a line tip the destination does not advertise (a local branch, or a commit given by flag); and neither the branch name nor the flag alone shall grant the line treatment; evidence: one negative fixture per case, the fabricated-line fixture passing the structural epic-line proof. (serves EPC-022 AC-113)
- AC-4 Every other check AC-1 lists that keys on the line's branch name (branch naming, records, classification) shall give the topic branch of AC-2 the verdict it gives the line, or the record shall state why it differs; evidence: the Findings and a fixture per changed check.
