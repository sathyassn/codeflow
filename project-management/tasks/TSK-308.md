# TSK-308: The acceptance binding counts a landed line adoption

## Description

After a task's landing merge, any non-merge commit on the line's
first-parent chain that changes a non-planning path refuses that task's
acceptance binding (`crates/codeflow-core/src/workgraph/acceptance.rs:1079-1140`,
the message at `:1137`). Since 3.1.0 an epic records a reviewed direct
commit in `line_adoptions` (`crates/codeflow-core/src/workgraph/line_adoption.rs:1-10`),
and the pull request classifier reads it; the binding does not. So an
adopted direct commit, such as an owner's `.gitleaksignore` change on an
epic line, still refuses the binding of every task landed before it
(https://github.com/sathyassn/codeflow/issues/167, part E). This task is the
narrow defect of issue 167; the issue's other parts are the adopter feature
epic's work (design task T1 of the adopter design approved on 2026-10-13).

The binding consumes the verified result of `line_adoption::check_range`,
errors included, so an adoption the line check proves counts like a merge
for that binding, and a forged entry on a branch, an unreadable history or
a changed acceptance block stays refused. `bind_completion`
(`acceptance.rs:341`) also gains a public structured result (the reviewed
commit, the landing merge, the span head and the completion tail), which
the adopter feature epic's carry task reads (design foundation F7). The
adopter's case is declared fixed only after a reproduction with a valid,
landed entry (`triage-codex-01.md`, the issue 167 row). Non-goal: the
record-hygiene checks and guidance of issue 167 parts A to D.

## Deliverables

- the binding reads adoptions, and the structured result: `crates/codeflow-core/src/workgraph/acceptance.rs`, `crates/codeflow-core/src/workgraph/line_adoption.rs`
- tests: the unit tests of `acceptance.rs` and a fixture in `crates/codeflow-cli/tests/acceptance_cli.rs`
- docs: the `line_adoptions` paragraph of `.codeflow/rules/git-rules.md` "Bodies of work" and its shipped source under `assets/base/rules/`, if the binding's behaviour needs a sentence there
- release note: `changelog.d/TSK-308.md`

## Acceptance Criteria

- AC-1 When a direct commit after a task's landing merge is adopted by a
  landed `line_adoptions` entry of the epic, the task's binding shall
  pass; evidence: a CLI fixture with a valid, landed entry, failing before
  the fix and passing after. (serves EPC-022 AC-17)
- AC-2 A direct commit with no landed entry, an entry present only on a
  branch, an entry that names another commit, and an adopted commit that
  also changes the task's acceptance block shall each still refuse the
  binding; evidence: one test per case. (serves EPC-022 AC-17)
- AC-3 When `check_range` cannot read the history or the entries, the
  binding shall refuse with that error, never pass; evidence: a unit test
  with an unreadable entry and one with an overlaid history read through
  TSK-287's guarded reader.
- AC-4 `bind_completion` shall return a public result that names the
  reviewed commit, the landing merge, the span head and the completion
  tail, and the existing callers shall use it without a change of verdict;
  evidence: unit tests of the result and the existing acceptance tests
  unchanged.
- AC-5 (journey) When `codeflow ci` runs with the installed build on a line of the
  adopter's shape (a task landed, then an owner's direct `.gitleaksignore`
  commit recorded in `line_adoptions` by a landed planning PR), the task's
  binding shall pass and the class line shall print the adoption;
  evidence: the journey output on a scratch repository.
