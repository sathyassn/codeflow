# TSK-1004: Import authority tells shared planning merges apart from unpublished imports

## Description

`work.import_authority` can refuse a valid first push of an integration line
as an unpublished import. The ordinary shape: the planning branch is merged
once, at commit P, and both lines branch from P (or both lines hold P because
two merges of the planning branch were byte-identical), then each line
advances on its own. While checking line A, `refuse_unpublished`
(`crates/codeflow-core/src/workgraph/acceptance/imports.rs:286`) walks line
B's local first-parent history through `matching_landing` (`:341`), which
accepts a matching version that is an ancestor of the checked head (`:366`)
as a landing. P is such an ancestor, so a planning record that line A
reached through P is treated as an import from line B, and because line B
is not yet published the push is refused. Divergent tips avoid
`on_home_chain`'s exemption (`:295`). Two distinct merges of the planning
branch, one per line, do not trigger it and are the passing control.
Hosted run 40158545922 hit this through identical same-second merges
(TSK-455 made its test merges distinct); Codex's TSK-455 review (round 3,
thread 01a17228-3903-7d03-be64-a17947d3d9e2) found the shared-P shape
reachable by ordinary branching.

Scope: the import check exempts shared planning provenance, a record version
that both lines carry from the same planning merge and that neither line
has changed since. Every other version keeps today's rule. Non-goal: shared
ancestry alone is never an exemption. A home-only change to a record
(completion, acceptance evidence or criteria) still needs published home
authority even when the other line branched from the commit that landed it,
and nothing changes in what counts as published authority, retired or
deleted home lines included.

Scope addition (2026-10-25, coordinator): the same check refuses a planning
move of a task that was never built. `codeflow ci` for the 3.2.0 line into
`main` reports `TSK-423: ... at c9993bcf3...: the landing changes the task's
declared home`. c9993bcf3 is the merge of PR 292, a reviewed planning PR that
moved the EPC-025 tasks, TSK-423 among them, from the EPC-022 line to their
own line. TSK-423 is `todo` before and after that merge. The merge sits on the
first-parent history of both the EPC-022 line and the EPC-025 line.
`verify_record_home` (`imports.rs`, the "changes the task's declared home"
branch) treats every home change at a landing as a foreign import. The
addition accepts a home change only when the line under check made it itself
through a planning-class merge, with no completion behind the task. The
decision is bound to commit identity and to the record contents at the
landing and its first parent, never to a branch name. Every other home change
keeps today's refusal.

## Deliverables

- The distinction in the import check: `crates/codeflow-core/src/workgraph/acceptance/imports.rs`
- Regression, control and refusal tests: `crates/codeflow-cli/tests/acceptance_cli/imports.rs` and `crates/codeflow-cli/tests/acceptance_journey.rs`
- The planning home-move distinction in `verify_record_home`, in the same file as the first fix, with its refusal tests (AC-5 to AC-9)

## Acceptance Criteria

- AC-1 When two lines both hold one planning merge P that introduced a record, and each has advanced past P without changing that record, a first push of either line shall not be refused by `work.import_authority` for that record, in either push order. Evidence: a test that merges the planning branch once at P, branches both lines from P, advances each, and pushes each line first in turn; it fails before the fix. Two distinct merges of the planning branch, one per line, pass before and after, as a control.
- AC-2 When line B lands an unpublished home-only version of a record (a completion, acceptance evidence or a criteria change) at a merge M, line A branches from M, and then both lines advance independently with that version unchanged, a push of line A shall still be refused for that version with the current unpublished-history message; shared ancestry alone shall not exempt it. Evidence: a paired control test of exactly that shape (A's head past M, so it is not on B's first-parent chain), refused before and after the fix.
- AC-3 When a line's range really imports a record version from another line whose history is unpublished, the existing refusal shall still fire with its current message, and the retired and deleted home paths shall keep their current results. Evidence: the existing refusal and retired-home tests in `crates/codeflow-cli/tests/acceptance_cli/imports.rs` (about lines 711, 781, 890 and 969) stay green unchanged.
- AC-4 (journey) When an adopter runs `a_release_branch_from_two_lines_passes_on_a_fresh_project` with author and committer dates pinned to one second and the original single planning-merge message, both lines shall push. Evidence: `GIT_AUTHOR_DATE=2026-10-25T00:00:00Z GIT_COMMITTER_DATE=2026-10-25T00:00:00Z cargo test -p codeflow-cli --test acceptance_journey`, with a test that keeps the single planning-merge message, output in the PR.

- AC-5 When a landing merge L changes a task's declared home, L is on the first-parent history of the head under check, every path L changes against its first parent is a planning path (judged from the trees, as `non_planning_change` judges them, never from a branch name), and the task record at L and at L's first parent has a status other than complete and no acceptance block (active or superseded), `work.import_authority` shall not refuse the import with "the landing changes the task's declared home". Evidence: a test in which a planning merge moves a `todo` task to a new line, that line is published, and the receiving line's range is checked through `codeflow ci` and the real pre-push entry; it is refused before the fix and passes after.
- AC-6 When a landing changes the declared home of a task that is complete or carries an acceptance block at L or at L's first parent, the import shall still be refused with "the landing changes the task's declared home". Evidence: a test of that shape, refused before and after the fix.
- AC-7 When the landing that changes a task's declared home also changes a path outside the planning class (product code, for example), the import shall still be refused with "the landing changes the task's declared home". Evidence: a test of that shape, refused before and after the fix.
- AC-8 When the landing that changes a task's declared home is not on the first-parent history of the head under check (for example, it exists only on the source line and reaches the head through a merge's second parent), the import shall still be refused with "the landing changes the task's declared home". Evidence: a test of that shape, refused before and after the fix.
- AC-9 (journey) When the operator runs `codeflow ci --base origin/main --head HEAD --branch integration/EPC-022-the-3-2-0-milestone-fixes --into main` on the 3.2.0 checkpoint with this fix, the TSK-423 home-change finding shall be gone, and every existing import refusal test shall still pass. Evidence: that command's output on the checkpoint candidate, run with this branch's binary, in the PR, and the full `crates/codeflow-cli/tests/acceptance_cli` suite green.
