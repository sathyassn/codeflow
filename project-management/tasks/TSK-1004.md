# TSK-1004: Import authority tells shared planning merges apart from unpublished imports

## Description

`work.import_authority` can refuse a valid first push of an integration line
as an unpublished import. The ordinary shape: the planning branch is merged
once, at commit P, and both lines branch from P (or both lines hold P because
two merges of the planning branch were byte-identical), then each line
advances on its own. While checking line A, `refuse_unpublished` (in
`crates/codeflow-core/src/workgraph/acceptance/imports.rs`) walks line B's
local first-parent history through `matching_landing`, which accepts any
matching version that is an ancestor of the checked head as a landing. P is
such an ancestor, so a planning record that line A reached through P is
treated as an import from line B, and because line B is not yet published
the push is refused. Divergent tips avoid `on_home_chain`'s exemption. Two
distinct merges of the planning branch, one per line, do not trigger it and
are the passing control. Hosted run 40158545922 hit this through identical
same-second merges (TSK-455 made its test merges distinct); Codex's TSK-455
review (round 3, thread 01a17228-3903-7d03-be64-a17947d3d9e2) found the
shared-P shape reachable by ordinary branching.

Scope: the import check exempts shared planning provenance, a record version
that both lines carry from the same admissible planning landing and that the
checked line has not changed since. Every other version keeps today's rule.
Non-goal: shared ancestry alone is never an exemption. A home-only change to
a record (completion, acceptance evidence or criteria) still needs published
home authority even when the other line branched from the commit that landed
it, and nothing changes in what counts as published authority, retired or
deleted home lines included.

Scope addition (2026-10-25, coordinator): the same check refuses a planning
move of a task. `codeflow ci` for the 3.2.0 line into `main` reports
`TSK-423: ... at c9993bcf3...: the landing changes the task's declared
home`. c9993bcf3 is the merge of PR 292, a reviewed planning PR that moved
the EPC-025 tasks, TSK-423 among them, from the EPC-022 line to their own
line. TSK-423 is `todo`, with no acceptance block, at both c9993bcf3 and its
first parent. Those two snapshots show it was not complete at either end of
the move; they do not prove that no work on it ever happened. The merge sits
on the first-parent history of both the EPC-022 line and the EPC-025 line,
and its first-parent diff changes seven planning records. The home check in
`verify_record_home` treats every home change at a landing as a foreign
import. The addition accepts a home change only when the line under check
made it itself through an admissible planning landing, with the task in a
permitted state at both ends. The decision is bound to commit identity and
to the record contents at the landing and its first parent, never to a
branch name. Every other home change keeps today's refusal.

### Terms used by the criteria

An **admissible planning landing** is a commit L for which all of these
hold, each read from L and its first parent L1 by commit id. Any tree, diff,
policy, mode or record that cannot be read makes L inadmissible (fail
closed).

1. L is a merge, and `is_clean_remerge` accepts it: its tree is the clean
   merge of its parents, with no hand resolution. `prove_record` keeps this
   check ahead of `verify_record_home`.
2. The diff from L1 to L passes the planning-amendment admissibility check
   that `landing_problem` applies through `range_problem`, with the policy
   read at L1: no hidden folder or file, no harness instruction file (for
   example `project-management/AGENTS.md`), no adopter-facing path in any
   letter case, no symbolic link or submodule on either side, and only plain
   UTF-8 names without a backslash.
3. Every changed name, both the old and the new name of a rename, is a
   record or plan path (`amendment_path` returns `Record`). The docs,
   document indexes and `AGENTS.md` project section that a planning
   amendment may otherwise carry do not qualify here.
4. Every changed entry is a regular, non-executable file (mode `100644`) on
   each side where it exists. An executable-bit change, or any other mode,
   makes L inadmissible.

A task is in a **permitted state** at a commit when exactly one task record
in that tree carries its id or uid (read by identity, as `presence_at`
reads it, so a rename keeps the task and a duplicate or unreadable task
record disqualifies), that record parses with an explicit `status` of
`todo` or `blocked` (a missing, empty or other status disqualifies), and it
holds no acceptance block of any kind: active, superseded or malformed.

Each judgment is made for the exact record version under check, at the
landing that `matching_landing` selects for that version. Nothing is cached
per task or per home, so a task moved twice or moved back is judged at the
landing of the version being imported.

## Deliverables

- The distinction in the import check: `crates/codeflow-core/src/workgraph/acceptance/imports.rs`
- Regression, control and refusal tests: `crates/codeflow-cli/tests/acceptance_cli/imports.rs` and `crates/codeflow-cli/tests/acceptance_journey.rs`
- The planning home-move distinction in `verify_record_home`, in the same file as the first fix, with its refusal tests (AC-5 to AC-9)

## Acceptance Criteria

- AC-1 When two lines both hold one landing P that introduced a task record, P is an admissible planning landing, the task is in a permitted state at P and has no record with its id or uid at P's first parent, and each line has advanced past P without changing that record, a first push of either line shall not be refused by `work.import_authority` for that record, in either push order. Evidence: a test that merges the planning branch once at P, branches both lines from P, advances each, and pushes each line first in turn; it fails before the fix. Two distinct merges of the planning branch, one per line, pass before and after, as a control. Controls, each refused before and after the fix by `refuse_unpublished` with its current message ("exists only on unpublished local history"), and each shown to depend on its check by a run with that check bypassed: the same shared P when it also changes a product path, when it also changes `project-management/AGENTS.md`, when it is an evil merge (a hand-resolved change that neither parent holds), when it sets the executable bit on a record, when it replaces a record with a symbolic link, when it renames a plan file to `docs/` (a path a planning amendment admits but that is no record or plan), when the introduced task has no `status`, and when a second task with a distinct valid id carries the same uid at P (so graph loading, which rejects only duplicate ids, does not refuse it first).
- AC-2 When line B lands an unpublished home-only version of a record (a completion, acceptance evidence or a criteria change) at a merge M, line A branches from M, and then both lines advance independently with that version unchanged, a push of line A shall still be refused for that version with the current unpublished-history message; shared ancestry alone shall not exempt it. Evidence: a paired control test of exactly that shape (A's head past M, so it is not on B's first-parent chain), refused before and after the fix, with a completion case, a criteria-change case and a record introduced already complete.
- AC-3 When a line's range really imports a record version from another line whose history is unpublished, the existing refusal shall still fire with its current message, and the retired and deleted home paths shall keep their current results. Evidence: the existing refusal and retired-home tests in `crates/codeflow-cli/tests/acceptance_cli/imports.rs` (`refuses_unpublished_home` and its four cases, `deleted_home_imports_are_proven_at_the_published_default_landing`, `import_authority_refusals_name_the_import_rule` and `retired_home_rejects_a_non_line_source_chain`) stay green unchanged.
- AC-4 (journey) When an adopter runs `a_release_branch_from_two_lines_passes_on_a_fresh_project` with author and committer dates pinned to one second and the original single planning-merge message, both lines shall push. Evidence: `GIT_AUTHOR_DATE=2026-10-25T00:00:00Z GIT_COMMITTER_DATE=2026-10-25T00:00:00Z cargo test -p codeflow-cli --test acceptance_journey`, with a test that keeps the single planning-merge message, output in the PR. The journey's policy edit moves from the planning branch to the default branch before the lines branch, since a planning landing cannot carry policy.
- AC-5 When a landing L changes a task's declared home, L is on the first-parent history of the head under check, L is an admissible planning landing, and the task is in a permitted state at both L and L's first parent, `work.import_authority` shall not refuse the import with "the landing changes the task's declared home". A status change during the move (for example `todo` to `blocked`) qualifies only when both ends are permitted. Evidence: a test in which a planning merge moves a `todo` task to a new line, that line is published, and the receiving line's range is checked through `codeflow ci` and the real pre-push entry, refused before the fix and passing after; a `todo` to `blocked` move that passes after the fix; a task moved twice by planning merges, and one moved back, each passing after the fix.
- AC-6 When the task is not in a permitted state at L or at L's first parent, the import shall still be refused by `work.import_authority`. Every case below reaches `verify_record_home` and names "the landing changes the task's declared home". Evidence: one test per case, each refused before and after the fix: complete at L; complete at the first parent only (the move removes its acceptance block and status); an acceptance block at the first parent removed during the move; a superseded acceptance block at either end; a malformed acceptance block at the first parent only (a malformed block in the imported version is refused by the existing acceptance-structure checks, with their own diagnostic); a missing `status` at the first parent; and a second task with a distinct valid id that carries the same uid at L, its id sorting after the moved task's so the identity read finds the moved task first (a duplicate id is refused earlier, by graph loading, with "duplicate work id", and is not a case of this criterion).
- AC-7 When the landing that changes a task's declared home is not an admissible planning landing, the import shall still be refused by `work.import_authority`, by the first existing guard the fixture reaches; guard order does not change. Evidence: one test per case, each refused before and after the fix with the diagnostic named here. An evil merge (a hand-resolved change that neither parent holds) is refused by the clean-remerge check in `prove_record`, ahead of `verify_record_home`, with "the home landing contains an unreviewed merge resolution". Each of these reaches `verify_record_home` and names "the landing changes the task's declared home": the landing also changes a product path; `project-management/AGENTS.md`; a hidden file under a planning folder (for example `project-management/.agents/notes.md`); a symbolic link under a planning folder; a rename from a record path to a path outside the planning records; an executable-bit change on a record; a `docs/` file; a direct commit rather than a merge.
- AC-8 When the landing that changes a task's declared home is not on the first-parent history of the head under check (for example, it exists only on the source line and reaches the head through a merge's second parent), the import shall still be refused with "the landing changes the task's declared home". A task moved twice whose later move fails AC-5 is refused at that later landing, whatever the earlier move was. A task created in the landing has no home change at that landing, so this exception never applies to it and today's handling of an introduced record is unchanged. Evidence: a test for the second-parent shape and one for the twice-moved shape, each refused before and after the fix.
- AC-9 (journey) When the operator runs `codeflow ci --base origin/main --head HEAD --branch integration/EPC-022-the-3-2-0-milestone-fixes --into main` on the 3.2.0 checkpoint with this fix, the TSK-423 home-change finding shall be gone. The exception shall suppress only the home-change refusal: publication, record identity, criteria reconciliation, retired-home proofs and the AC-3 refusals all still run. Evidence: that command's output on the checkpoint candidate, run with this branch's binary, in the PR, and the full `crates/codeflow-cli/tests/acceptance_cli` suite green.
