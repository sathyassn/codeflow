# TSK-1346: Guards refuse dispatching a release or creating a release tag through the API

## Description

Source: a guard finding from the Director on 2026-11-05. `docs/releasing.md:8-9` says humans dispatch the publishing workflow and no agent merges, tags or publishes, and the dispatch row (`:46`) asks for a human with write, maintain or admin permission. Every agent here pushes as the operator's account, so GitHub cannot tell an agent from the operator, and nothing on the remote stops an agent's dispatch or its approval of a pending deployment: the `release tags` ruleset holds `update` and `deletion` but no `creation`, and the only environment is `github-pages`, with no required reviewer on release (Director, read live at 13:48).

`.github/workflows/release.yml:41-48` runs on `pull_request` and on `workflow_dispatch` with a `tag` input that defaults to `dry-run`, so the dispatch is the publish step. Only a tag other than `dry-run` sets `publishing` (`:58-60`), and the host job runs only when `publishing` is true (`:269`). A dispatch of the default branch with `tag=dry-run`, or with no tag, builds and does not publish. A dispatch with `--ref` naming another branch runs that branch's workflow file, which a guard cannot read.

Guards judged these strings on installed 3.1.0 and beta 4.0.0 on 2026-11-05; nothing ran:

| Command | Both builds |
|---|---|
| `gh workflow run release.yml`, with or without `-f tag=v9.9.9` or `-R` | passed |
| `gh api -X POST .../actions/workflows/release.yml/dispatches`, `.../dispatches` (repository dispatch) | passed |
| `gh api -X POST .../actions/runs/<id>/pending_deployments` | passed |
| `gh api -X POST .../releases`, `gh api -X POST .../git/refs -f ref=refs/tags/v9.9.9` | passed |
| `curl -X POST https://api.github.com/.../dispatches` | passed |
| `gh release create v9.9.9`, `gh release edit ... --draft=false` | blocked, `security.outward_actions` |
| `git push origin refs/tags/v9.9.9`, `--tags`, `--follow-tags` | blocked, `security.outward_actions` |
| `git push origin v9.9.9` with no such local tag | passed on 3.1.0, blocked on beta |

`security/outward.rs:3341` (`tag_push`) reads tag pushes through the local tag store, which is why a bare name with no local tag differs. The pre-push hook passes tags (`git_hook.rs:3611`, `test_pre_push_tags_ignored`). A wrapped form such as `hc run -- gh workflow run ...` is TSK-1344's.

Non-goals: the release workflow itself, the remote settings (the operator's), and humans' own release steps.

## Outcome

After this merges, an agent session that tries to dispatch a release, approve a pending deployment, or create a release or a release tag through `gh`, the API or `git push` is refused by the guard, and a reader can see which floor holds for the routes a guard cannot judge.

### AC-1: the two research inferences

- An Actions policy actor rule covers every trigger of the file it targets:
  confirmed from the schema. The policies API documents that a repository
  policy's `conditions` "can be empty or contain only `workflow_path`", and
  that `workflow_path` "filters workflows, not events"; events are a
  separate `restrict_action_events` rule. An actor rule therefore cannot be
  limited to the dispatch event of a file that also runs on
  `pull_request`. Source: https://docs.github.com/en/rest/actions/policies
  (read 2026-11-08). How several rules combine is not stated there.
- Whether an App installation token is refused at `pending_deployments`:
  not confirmed. The permissions table lists the endpoint for both user and
  installation access tokens with Deployments write
  (https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps),
  and the endpoint states "Required reviewers with read access to the
  repository contents and deployments can use this endpoint"
  (https://docs.github.com/en/rest/actions/workflow-runs). Reviewers are
  users or teams, so a bot approval is expected to fail, but no page states
  it. A scratch-repository test needs a real API write, which this task
  does not make; the guard refuses the endpoint for every token, so nothing
  here relies on the answer.

### How the guard reads a release workflow and the release tag pattern

- Release workflow: a workflow file under `.github/workflows/` at the
  policy authority (the remote's default branch as last fetched) that runs
  on `workflow_dispatch` or `repository_dispatch` and can publish. It can
  publish when its token can write contents, packages, deployments, pages,
  attestations or an OIDC token; when no permissions are set, so the
  repository default decides; when a job deploys to an environment or
  calls a reusable workflow; or when it reads a secret other than
  `GITHUB_TOKEN`. A file that cannot be read or parsed counts as release.
  In this repository that makes the release and portal workflows release
  workflows, and the CI, registry and daily Windows workflows not.
- Release tag pattern: the guard cannot read an adopter's ruleset, so it
  takes `v*` (this repository's `release tags` ruleset) and a leading digit
  as the release tag shape for every adopter. Any tag the local tag store
  holds, any `refs/tags/` refspec and `--tags` were already refused.

### AC-5: dry runs

A dry run is refused. `release.yml:58-60` sets `publishing` from
`inputs.tag`, and `:269` gates the host job on it, but a dry run still runs
jobs whose token can write contents and calls reusable workflows with write
access. Showing that none of them publishes means evaluating GitHub's
expression language and every job condition at the authority, which the
guard does not do, and the authority's file can change between fetches.
The guard therefore refuses every dispatch of a release workflow and says
so in the refusal.

### AC-6: what still passes

Tested in `ac6_other_dispatches_reads_and_run_queries_still_pass`: dispatch
of a non-release workflow on the default branch, `gh workflow list` and
`view`, `gh run list`, `view` and `watch`, `gh release view` and `list`,
API reads, an issue comment POST, and the `gh pr view` and `gh api` lines
of `coordination/scripts/candidate-hosted-check.sh` as written.
`scripts/proofs/registry-proof/run.sh` passes as the script call the guard
sees. Its line 545, `gh workflow run -R "$REPO" "$WORKFLOW" --ref main`,
typed directly would be refused, because it names a repository other than
the authority's (a disposable proof repository), whose workflows the guard
cannot read. AC-4 and the rule that an unreadable workflow counts as
release require that refusal.

### AC-7: the pre-push hook

The pre-push hook should not refuse release tag pushes, and this change
does not touch it. The hook runs for humans and agents alike and cannot
tell them apart, so a refusal there would stop a human whose release
starts with a tag push, which is common among adopters. Adding it would be
an operator decision through the Director.

### Scope widened on 2026-11-08: re-runs and the sibling sweep

The Director ruled through coord/catalog that a re-run of a release run is
in this task's class and that the sibling routes that start or approve a
release run are fixed here.

**Re-runs (AC-11).** The guard cannot tell a release run from a CI run:
`gh run rerun <id>` and the re-run API routes carry only a run id, the
guard makes no network read (every process spawn under `security/` and
`hooks/` is in a test module), and no local source a requester cannot
forge maps a run id to its workflow. Refusing every re-run would break the
coordination scripts that re-run CI jobs after runner failures
(`coordination/scripts/rerun-commit-standards.sh:39`,
`land-when-green3.sh:48`). The Director chose a check inside the release
workflow: the first step of each publishing job fails when
`GITHUB_RUN_ATTEMPT` is not 1, outside pull request events.

- GitHub's documentation: `github.run_attempt` "begins at 1 for the
  workflow run's first attempt, and increments with each re-run" (Actions
  contexts reference); re-running failed jobs or one job "also re-runs the
  jobs that depend on them" and other jobs "keep their outputs from the
  previous attempt" (Re-running workflows and jobs). The 50 re-run limit
  "includes both full re-runs and re-runs of a subset of jobs".
- Checked read-only on this repository: run 42460109789 was re-run with
  failed jobs; in attempt 2 its re-run jobs ran with `run_attempt` 2, and
  `trusted: release impact`, which passed in attempt 1, kept its first
  start time and did not run again. A gate in its own job is therefore
  skipped by a partial re-run, so the check sits in each publishing job.
- Jobs that get the check: `release.yml` `plan` (it runs `dist host
  --steps=create` when dispatched with a tag), `host` and `announce`;
  `release-plan-authority.yml` `verify` (`gh release create --draft`);
  `portal-pages.yml` `deploy` (the `github-pages` environment).
- CodeFlow installs no release workflow
  (`assets/base/scaffold-manifest.toml:81-82`), so there is no shipped
  template to carry the check or a switch for it; `docs/releasing.md`
  gives adopters the step.
- The workflow files and `release_rerun_contract`, which requires the
  check first in every job with an `environment`, a publishing action or a
  publishing command, land together through
  `coordination/scripts/operator/apply-tsk1346-rerun-check.sh`, so no
  commit holds the test without the workflows it checks.

  dot. A write is refused when the URL cannot be read the way every
  client reads it: a host in a variable, a second `@`, a port that is not
  a number, a dot segment, braces or brackets curl expands, a scheme
  without `//`. A write that sets a Host header, remaps the host
  (`--connect-to`, `--resolve`, `--request-target`) or reads options or
  URLs from a file is refused too. No URL crate is in the workspace; the
  parser is strict instead of permissive, so a spelling two clients read
  differently is refused rather than guessed.
- **B, GraphQL path.** Any path on an API host whose last segment is
  `graphql` is judged as GraphQL for `gh api`, curl, wget, HTTPie and xh,
  and an unreadable body is refused.
- **C, `{owner}/{repo}`.** gh's repository is the one every `-R`,
  `--repo` and `GH_REPO` names; sources that disagree, or that disagree
  with the path, are refused. With none, it is gh's current repository,
  and every GitHub remote must name the authority's repository.
  Placeholders resolve to it. `github_slug` now compares hosts as
  `destination` does, so `evilgithub.com` names no GitHub repository.
- **D, scopes.** `actions` and `administration` write count as
  publishing.
- **E, the re-run contract.** The test reads the step's meaning: its
  first command compares `GITHUB_RUN_ATTEMPT` to 1, the branch exits
  non-zero, and no `if`, `continue-on-error` or `env` undoes it. An
  implied-POST `gh api`, an HTTP write to the API host and a job-level
