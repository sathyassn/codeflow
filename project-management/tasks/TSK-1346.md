# TSK-1346: Guards refuse dispatching a release or creating a release tag through the API

## Description

Source: a guard finding from the Director on 2026-11-05. `docs/releasing.md:8-9` says humans dispatch the publishing workflow and no agent merges, tags or publishes, and the dispatch row (`:46`) asks for a human with write, maintain or admin permission. Every agent here pushes as the operator's account, so GitHub cannot tell an agent from the operator, and nothing on the remote stops an agent's dispatch or its approval of a pending deployment: the `release tags` ruleset holds `update` and `deletion` but no `creation`, and the only environment is `github-pages`, with no required reviewer on release (Director, read live at 13:48).

`.github/workflows/release.yml:41-48` runs on `pull_request` and on `workflow_dispatch` with a `tag` input that defaults to `dry-run`, so the dispatch is the publish step. Only a tag other than `dry-run` sets `publishing` (`:58-60`), and the host job runs only when `publishing` is true (`:259`). A dispatch of the default branch with `tag=dry-run`, or with no tag, builds and does not publish. A dispatch with `--ref` naming another branch runs that branch's workflow file, which a guard cannot read.

Guards judged these strings on installed 3.1.0 and beta 4.0.0 on 2026-11-05; nothing ran:

| Command | Both builds |
|---|---|
| `gh workflow run release.yml`, with or without `-f tag=v9.9.9` or `-R` | passed |
| `gh api -X POST .../actions/workflows/release.yml/dispatches`, `.../dispatches` (repository dispatch) | passed |
| `gh api -X POST .../actions/runs/<id>/pending_deployments` | passed |
| `gh api -X POST .../releases`, `gh api -X POST .../git/refs -f ref=refs/tags/v9.9.9` | passed |
| `curl -X POST https://api.github.com/.../dispatches` | passed |
| `gh release create v9.9.9`, `gh release edit ... --draft=false` | blocked, `security.outward_actions` |
| `git push origin refs/tags/v9.9.9`, `--tags`, `--follow-tags` | blocked, `security.outward_actions` |
| `git push origin v9.9.9` with no such local tag | passed on 3.1.0, blocked on beta |

`security/outward.rs:3341` (`tag_push`) reads tag pushes through the local tag store, which is why a bare name with no local tag differs. The pre-push hook passes tags (`git_hook.rs:3611`, `test_pre_push_tags_ignored`). A wrapped form such as `hc run -- gh workflow run ...` is TSK-1344's.

Non-goals: the release workflow itself, the remote settings (the operator's), and humans' own release steps.

## Outcome

After this merges, an agent session that tries to dispatch a release, approve a pending deployment, or create a release or a release tag through `gh`, the API or `git push` is refused by the guard, and a reader can see which floor holds for the routes a guard cannot judge.

## Acceptance Criteria

- AC-1 Before any product change, the builder shall judge every form in the Description and these against exec-guard and git-guard: `gh api` with an implied POST (`-f`, `-F`, `--input`), `--method` spellings, a numeric workflow id, a workflow display name, `gh workflow run` of another workflow, `git push origin HEAD:refs/tags/v1`, and `git tag` followed by a push in one command; evidence: the table in `## Findings`, with the build it ran on.
- AC-2 exec-guard shall refuse, naming the rule: `gh workflow run` of a release workflow, the workflow dispatch and repository dispatch API calls, a `pending_deployments` approval, a release create or publish through `gh release` or the API, and a tag creation through the API; evidence: tests that fail before the change and pass after it, for each form and spelling in AC-1.
- AC-3 A push that creates or moves a tag matching the release tag pattern shall be refused whether or not the tag exists locally; evidence: tests for the bare name, the full ref, a refspec and `--tags`.
- AC-4 When the guard cannot tell whether a dispatch names a release workflow or whether an API call publishes, including a numeric id, a display name it cannot map, or a `--ref` other than the default branch for a release workflow, it shall refuse; evidence: tests for each.
- AC-5 A dispatch of a release workflow on the default branch with `tag=dry-run` or no tag shall pass only if the builder shows from the workflow at the authority that it cannot publish, as `release.yml:58-60` and `:259` read today; otherwise it shall be refused; evidence: the reasoning in `## Findings` and a test.
- AC-6 Dispatches of other workflows, read-only `gh` and API calls, and `gh run` reads shall still pass, including `coordination/scripts/candidate-hosted-check.sh`'s use and `scripts/proofs/registry-proof/run.sh:545`; evidence: tests.
- AC-7 The builder shall state whether the pre-push hook should refuse a release tag push as a second plane. A change that would stop a human's own release step goes to the Director for the operator before it is built; evidence: the decision in `## Findings`.
- AC-8 `## Findings` and `docs/releasing.md` shall name the routes a guard cannot judge (a script that calls the API, `curl` with a variable URL, a workflow file changed on a branch and dispatched from it) and the floor for each: remote settings such as a `creation` rule on release tags and a required reviewer on a release environment. While agents and the operator share one account, a required reviewer is a floor only together with the guard's `pending_deployments` refusal, since an agent holding that token can approve through the API, and "prevent self-review" would stop the operator approving their own dispatch; it becomes a floor on its own once agents have their own identity, which is with the operator. Any change to those settings goes to the Director for the operator; evidence: the text.
- AC-9 The change shall have a cross-lineage security review with the `cf-security-reviewer` checklist: Grok or Codex when a live probe at dispatch shows usage, else a fresh Claude Opus medium subagent with reduced assurance recorded; evidence: the review row and its findings record.
- AC-10 The pull request shall state the threat this closes and why refusing in the guard and failing closed is the standard design; evidence: the PR body.
