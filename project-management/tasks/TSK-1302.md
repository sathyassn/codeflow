# TSK-1302: A project overrides managed instructions and keeps the overrides through updates

## Description

The operator ruled on 2026-11-03 that a consuming project can replace or extend any managed instruction, a managed skill section, a managed block row or a managed reference file, without editing text that `codeflow update` overwrites. What exists covers part of it: the project-owned section below the managed block in `AGENTS.md`, adopter-owned skills (a skill the project adds itself), the personal model overlay (`~/.codeflow/model-catalog.local.json`, per user, no routes) and `codeflow update`'s three-way merge of edited copies. None of them replaces one managed section or row by name, and none is listed by `doctor`. A sweep of EPC-033 found no customization task to fold this into (TSK-1031, TSK-1032 and TSK-1034 change instruction content, not the override route).

Design direction: a project-owned override file per skill, or override sections the managed text names; the builder chooses after research. Security relevant: an override can change what agents are told about gates and reviews, so the floors in the managed text (the git floor, the non-relaxable command class) stay outside its reach.

## Outcome

After this merges, a project maintainer can replace a managed skill section or managed block row, keep it through `codeflow update`, and see every active override in `codeflow doctor`.

- docs: `docs/customizing.md` (provisional; the builder checks the docs map), and TSK-1296's page links it

## Findings

Read at `4dc4dbf4c` before any change (AC-1). Revised after the Codex design reviews of `6c5d595cb` and `2c0f51214`.

### What already exists

- The project-owned section of `AGENTS.md` adds text below the managed block and survives every update (`crates/codeflow-core/src/scaffold/region.rs:1-13`). It cannot replace one rule or moment row inside the block, so a project can only add a second, possibly contradicting, instruction.
- Adopter-owned skills sit outside the manifest and are never touched by update (`crates/codeflow-core/src/scaffold/update.rs:1-45`). They cannot replace one section of a managed skill.
- `[scaffold] ignore` in `.codeflow/project.toml` (`scaffold/state.rs:142-220`, applied at `update.rs:258-265`) drops a whole file from management, and with it every later upstream fix.
- The three-way merge of a user-modified managed file (`update.rs:845-872`, `999-1008`) keeps a hand edit only while upstream leaves those lines alone; otherwise it writes a `.new` conflict.
- The personal overlay (`crates/codeflow-core/src/model_catalog/inputs.rs:115`) is per user and covers the model catalog only.
- `.codeflow/model-selection.json` is the precedent: a project-owned file that references only names the managed catalog declares, rejects the whole file on any invalid entry, and is checked by `codeflow doctor --check model-bindings`.
- The kernel `assets/base/rule-map.toml` gives every always rule an `id` and every moment row a `key`. Managed skill sections have no stable names.

Limits of the two older routes, which this task keeps and documents but does not change:

- `[scaffold] ignore` gives no floor protection: an ignored file, `git-rules.md` included, can be edited freely and update never restores it. It is not a declared override, so it has no named target and no replacement record.
- A hand edit kept by the three-way merge gives no floor protection either: an edit that removes floor text survives update when upstream does not touch those lines.
- The new doctor `overrides` check lists ignored managed files and user-modified managed files beside the declared overrides, labelled as undeclared customizations with no floor check, so the inventory is complete. Changing what those routes may touch is broader enforcement work and is tracked separately, not built here.

### Chosen design

**1. Override file.** One project-owned file, `.codeflow/overrides.toml`, which update never writes. Each entry names its target by a declared name and gives replacement values. Names and ranges are resolved only from the shipped content of the version being installed (the embedded assets and kernel), never from the installed file, so a marker a project adds locally declares nothing.

- A block row is `rule:<id>` or `moment:<key>`. Its identity is the kernel entry for the project's tier; a contract test asserts each `(kind, name, tier)` is unique.
- A skill section is `<skill>#<section-id>`. The canonical skill identity is the skill's directory name in the manifest; the `.claude/skills/<skill>` and `.agents/skills/<skill>` mirrors are one unit and one override applies to both, keeping them byte-identical.

**2. Classification, deny by default.** Every unit carries a declared class in the shipped text: a `class` field on each `[[rule]]` and `[[moment]]` in `rule-map.toml`, and a `class=` attribute on each `<!-- codeflow:section id=... class=... -->` marker. There are three classes:

- `floor`: states a floor; refused with the floor's name;
- `fixed`: not a text-override target, with a `reason` the kernel records; refused with that reason;
- `overridable`: the only class an override can target. Unclassified units, unmarked skill sections, every rules file, every reference file and every prose block of the kernel are not override targets at all.

**3. Floor list and its coverage contract.** `assets/base/instruction-floors.toml`, embedded like the kernel, holds one entry per floor: its name, the units it covers and its refusal text. Today it has the git floor and the non-relaxable command class. Tests stop the list and the classes drifting apart, and stop a unit being left off:

- every rule and moment in the kernel and every section marker has a class; a missing class fails the build;
- the floor list and the `floor` class are one set: every unit the list names is classed `floor`, and every `floor` unit is named by exactly one floor entry;
- an independent pinned check, not driven by the list, asserts the known floor expressions stay non-overridable: `rule:git`, `rule:authority` (`rule-map.toml:128`), `moment:refusal` (`:589`), `moment:secret` (`:596`), and the precedence line (`:41`);
- a phrase probe fails the build when any `overridable` unit's shipped text contains a listed floor phrase (`non-relaxable`, `git floor`, `[enforced]`, `protected branch`, `--no-verify`, `override env`, `headless`). It is a regression check that supplements explicit classification and review: it catches the listed phrases, not every paraphrase of a floor, so the class on each unit and the review of each classification remain the control;
- the files that state floor text in full carry no section markers, asserted by test: `rules/git-rules.md` (Enforcement, The rules, Protected branches), `rules/workflow-discipline.md` ("Match the gate" at `:265`, "Act within authority" at `:281`) and `cf-model-orchestrator/resources/quality/irreversible.md:15`.

Initial classes for the units Codex named:

| Unit | Class | Reason |
|---|---|---|
| precedence line (`rule-map.toml:41`) | not a unit | prose block; never replaceable |
| `rule:git` | floor (git) | states the git floor |
| `rule:authority` | floor (non-relaxable) | states that approval never unlocks the class |
| `moment:refusal` | floor (git) | forbids `--no-verify`, hook edits and override envs |
| `moment:secret` | floor (git) | points at "Match the gate" for secrets and irreversible steps |
| `moment:standing-rule` | floor (non-relaxable) | relaxing policy, a gate or a review needs explicit approval |
| `rule:forge-identity` | floor (git) | an agent's account never supplies independent merge approval |
| git-rules.md, workflow-discipline.md, irreversible.md | not units | whole files, no markers |
| `rule:review` (all tiers), `moment:review` (all tiers) | fixed | review policy is configured through CodeFlow's review configuration, not instruction text; both `rule:review` variants also state "never headless" (`rule-map.toml:197,204`) |

Review rules: the floor list keeps exactly the two floors AC-3 names, the git floor and the non-relaxable command class (Director's ruling relayed by coord/planning, from the operator's 11-03 decision). The review rows are classed `fixed`, not `floor`. Review policy belongs in CodeFlow's review configuration, not in instruction text. Today that configuration can only add review participants: `standing_reviews` in `.codeflow/model-selection.json` adds an extra-family seat (`crates/codeflow-core/src/model_catalog/authority.rs:211-223`, `241-277`). Turning cross-lineage review off is planned in TSK-1293 AC-10, where a relaxed default is recorded as reduced assurance. Review is never configured by rewriting the review text, so no text override can drop "never headless" or the independence wording, and no third floor is hardcoded. A later decision to make a review row a text-override target is one class change on that row. The phrase probe still blocks an `overridable` class while the row holds "headless", so that change would first have to split out the headless prohibition into a unit classed `floor`. The orchestrator's review instructions are in `cf-model-orchestrator`, which carries no markers in this task, so they are not override targets.

Review floors (AC-3 amended 2026-11-10): review independence, cross-lineage review of a security-sensitive change, and the rule against headless peers are protected by keeping their units `fixed` and adding their phrases to the probe ("self-review", "fresh-context", "other-lineage", "other lineage", "another lineage", "cross-lineage", "headless"). This is the smaller sound change: the floor list keeps its two entries and the refusal path is unchanged. The units that carry these phrases are `rule:review`, `moment:review` and `moment:delegate`, all already `fixed`, and `moment:shape` in the standard and full tiers ("one other-lineage review"), which is reclassed `fixed` with the review reason. The rules files and `cf-model-orchestrator` carry no markers. The contract test fails if any `overridable` unit or section holds one of the phrases.

Adding a floor later is one list entry and the reclassing of its units to `floor`. The table-driven refusal test reads the list, and the set test fails until the list and the classes agree.

**4. Replacement boundaries.** What a target covers:

- A row override replaces fields, never lines: `text` (and optionally `title`) for a rule, `action` for a moment. The renderer builds the line from the kernel with those values, so the bullet or table structure, the pointers (`see`, `MUST OPEN`) and every other row stay shipped. A value must be one line and must not contain `<!--`, `-->` or `codeflow:`; a `|` in a moment action is refused.
- A section override replaces the section body only. The marker line and the heading line stay shipped. The extent runs from the line after the heading to the line before the next heading of the same or higher level, the next section marker, or the end of the file. Nested lower-level headings belong to the section.
- Refused, failing closed with the entry named:
  - a body line that is a heading at the section's level or higher, since it would end the section early and orphan shipped text;
  - any line holding a section marker or a managed-region begin or end marker in either format (`region.rs:18-42` takes the first begin/end pair, so an injected terminator could move the managed block);
  - two entries for one unit.
- Contract tests on shipped content: no duplicate section ids in one skill, no declared section nested inside another declared section, and no `overridable` range that contains a `floor` unit or floor text. An outer section that encloses a protected subsection therefore cannot be declared overridable.
- After applying, every resulting document is re-parsed before any write. The set and order of declared units must equal the shipped set, every `floor` unit must be byte-identical to shipped, the precedence line must be unchanged, and a managed-region file must hold exactly one begin and one end marker with `managed_span` equal to the expected span. Any difference refuses the whole run.

**5. Fail closed, before any write.** Update runs an override preflight at its start, before it writes pending-resolution metadata (`update.rs:330-368`). Any of these refuses the whole update, naming the entry, and writes nothing:

- an unreadable or malformed file;
- a `floor` or `fixed` target;
- an unclassified or unknown name, including a name the new version removed or renamed (the same unknown-target refusal; the message tells the maintainer to retarget or remove the entry);
- an overlap;
- a boundary refusal;
- a failed re-parse.

Doctor runs the same validation against the installed version.

**6. Update-base contract.** The pristine invariant stays: a managed file's recorded `sha256` is the hash of the pristine shipped text `P`, which is the baseline (`update.rs:20-25`). For a file with overrides, update keeps one override record per file, `.codeflow/.baseline/<dest>.overrides.json`, holding:

- the generation number;
- the hash of `P`;
- the applied set `A`, each target with its full replacement values, so the effective text can be rebuilt;
- the hash of the effective baseline `E = apply(P, A)`;
- the hash `W` of the actual written result.

`E` is always the pristine shipped text transformed by the applied overrides, and never includes a hand edit. This is the same rule `update.rs:1001-1008` follows when it records the unmodified rendering, not the merged output, as the baseline. `W` is recorded separately, for recovery and for doctor, and is never used as a merge base.

With `E_old = apply(P_old, A_old)` and `E_new = apply(P_new, A_new)`:

| Case | Detected by | Result |
|---|---|---|
| unchanged | current = `E_old`, `A_new` = `A_old`, `P_new` = `P_old` | nothing to write |
| override edited (B to C) | current = `E_old`, `A_new` differs | write `E_new`; B is the old override, never a hand edit |
| override removed | current = `E_old`, target gone from `A_new` | write `E_new`, which has the shipped text back |
| upstream changed the file | current = `E_old`, `P_new` differs | write `E_new`, with the overrides re-applied to the new shipped text |
| hand edit H on top | current differs from `E_old` | three-way merge with base `E_old`, ours current, theirs `E_new`; a clean merge writes the result and records `E_new` as the base and the merge's hash as `W`; a conflict writes `.new` as today |

A hand edit H survives two updates and stays distinguishable from an override:

| Step | Current file | Recorded base `E` | `W` | Outcome |
|---|---|---|---|---|
| start | `E0` + H | `E0 = apply(P, {B})` | hash(`E0` + H) | doctor: B declared and applied; H listed as an undeclared edit |
| update 1: nothing changed | `E0` + H | `E0` | hash(`E0` + H) | `E_new` = `E0`, so the existing "kept" path applies; H stands |
| update 2: B edited to C | `E2` + H | `E2 = apply(P, {C})` | hash(`E2` + H) | merge(`E0`, `E0` + H, `E2`): C applied, H kept; doctor shows C declared and H still undeclared, because H is the diff between the file and `E2` |
| update 3: override removed | `P` + H | `P` | hash(`P` + H) | merge(`E2`, `E2` + H, `P`): the shipped text is back, H kept |

When H overlaps the overridden section, the merge conflicts and update writes `.new`, as today, so nothing is lost silently. Managed-region files (the `AGENTS.md` block) are rewritten whole by update today, so hand edits inside the block are not kept there now and this task does not change that. Their block is always the shipped block with the declared rows applied, and removing a row override restores the shipped row.

**7. Interruption.** Write order alone is not relied on. Every file whose bytes or override record change in this run gets a journal, `.codeflow/.pending-update/<dest>.overrides.json`, which follows the existing pending-resolution path (`update/pending.rs`). The journal is written atomically (temporary file, then rename) before the destination is touched. It binds three states:

- the old state: the override record and the manifest entry as they were, and the hash of the file before the write;
- the intended rendering: the new generation number, `P_new` (text, as pending resolutions already keep the shipped text), `A_new` and the hash of `E_new`;
- the actual result to be written: the hash `W_new` of the exact bytes, which is `E_new` for a replacement and the merge output for a clean merge that keeps H.

Order: journal, then the destination (atomic rename), then the pristine baseline, the override record and the manifest entry, then the journal is removed. At the next update, before anything else writes, a journal is resolved as below. Doctor only reads it and reports the state.

| State found | Action |
|---|---|
| file hash = `W_new`; every metadata part matches the old or the new generation | roll forward: write the new metadata from the journal, remove the journal, continue |
| file hash = old file hash; every metadata part matches the old generation | nothing landed: remove the journal and recompute |
| anything else: file matches neither, a metadata part matches neither generation, generations disagree, or the journal is unreadable | refuse, naming the file, and overwrite nothing; doctor reports it for a person to resolve |

With no journal, the override record's generation and `P` hash must agree with the manifest entry and the pristine baseline. A mismatch is unverifiable state and refuses in the same way. A clean merge that keeps H is covered because `W_new` is the merge output's hash, never `E_new`'s.

Doctor tells these states apart for each overridden file:

- declared and applied, with the file equal to `E`;
- applied, with the file differing from `E` (undeclared edits on top, shown as their diff);
- a declared set that differs from the applied set (run update);
- an open journal (an interrupted update).

**8. Doctor.** A new `overrides` check lists each declared override with its target, its class, its source line and the shipped text it replaces, its state from points 6 and 7, and the undeclared customizations from "What already exists".

Scope.** This task classes every kernel row, adds section markers to the managed skills its tests need, and documents how more are added. `cf-model-orchestrator` gets markers after TSK-1292 lands, which is editing it now. Replacing a whole reference file is not an override route. The docs name `[scaffold] ignore` as the existing way to stop managing a file, and state that it gives no floor protection, no named target and only the inventory listing above.

### Reason

Deny by default with a declared class on every unit, one floor list tied to those classes by tests, and refusing the whole file before any write is the standard allow-list policy shape. It reuses the whole-file reject the project already trusts in model-selection, and it keeps the pristine-hash invariant that update's correctness rests on.

### Enforcement claim and not covered

Overrides grant no authority and cannot reach a floor unit or the precedence line. Some floor duties are enforced by hooks, guards, CI and remote rules where those planes are configured and active, but installed files do not prove active enforcement, and some floor duties are instruction-only: the shipped git rules name headless task execution as instruction-only (`assets/base/rules/git-rules.md:21-35`). For those, the protection this task adds is that their text is not an override target.

Not covered: an override's replacement text in an `overridable` unit could still contradict a floor stated in another unit. The phrase probe in point 3 checks shipped units, not replacement text, and no general prose-contradiction check is attempted. The floor units and the precedence line ("safety floors and [enforced] rules hold under all") survive every override, which is the disclosed limit of a structural mechanism. Raised for the security review.
