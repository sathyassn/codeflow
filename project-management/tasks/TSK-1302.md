# TSK-1302: A project overrides managed instructions and keeps the overrides through updates

## Description

The operator ruled on 2026-11-03 that a consuming project can replace or extend any managed instruction, a managed skill section, a managed block row or a managed reference file, without editing text that `codeflow update` overwrites. What exists covers part of it: the project-owned section below the managed block in `AGENTS.md`, adopter-owned skills (a skill the project adds itself), the personal model overlay (`~/.codeflow/model-catalog.local.json`, per user, no routes) and `codeflow update`'s three-way merge of edited copies. None of them replaces one managed section or row by name, and none is listed by `doctor`. A sweep of EPC-033 found no customization task to fold this into (TSK-1031, TSK-1032 and TSK-1034 change instruction content, not the override route).

Design direction: a project-owned override file per skill, or override sections the managed text names; the builder chooses after research. Security relevant: an override can change what agents are told about gates and reviews, so the floors in the managed text (the git floor, the non-relaxable command class) stay outside its reach.

## Outcome

After this merges, a project maintainer can replace a managed skill section or managed block row, keep it through `codeflow update`, and see every active override in `codeflow doctor`.

## Deliverables

- the override mechanism: `crates/codeflow-core/src/scaffold/` and the update path, with the managed block and skill templates in `assets/base/` naming what can be overridden
- doctor: a check that lists each override and the managed text it replaces
- docs: `docs/customizing.md` (provisional; the builder checks the docs map), and TSK-1296's page links it
- release note: `changelog.d/TSK-1302.md`

## Acceptance Criteria

- AC-1 Before any change, the builder shall record in a `## Findings` section what the project-owned AGENTS.md section, adopter-owned skills, the personal overlay and the update three-way merge already cover, and the chosen design with its reason; evidence: the Findings.
- AC-2 When a project replaces one managed skill section and one managed block row through the override route, `codeflow update` shall keep both, and `codeflow doctor` shall list both with the managed text each replaces; evidence: a scratch-project test that runs update across two scaffold versions.
- AC-3 An override that targets the git floor or the non-relaxable command class, names a section or row that does not exist, or is unreadable shall be refused or reported naming the override, failing closed; evidence: one test per case.
- AC-4 (journey) In a scratch project with the installed build, a maintainer overrides one skill section and one managed block row, runs `codeflow update`, and doctor lists both; evidence: the journey output.
- AC-5 A changelog entry shall describe the route; evidence: `changelog.d/TSK-1302.md`.

## Findings

Read at `4dc4dbf4c` before any change (AC-1).

What already exists:

- The project-owned section of `AGENTS.md` adds text below the managed block and survives every update (`crates/codeflow-core/src/scaffold/region.rs:1-13`). It cannot replace one rule or moment row inside the block, so a project can only add a second, possibly contradicting, instruction.
- Adopter-owned skills sit outside the manifest and are never touched by update (`crates/codeflow-core/src/scaffold/update.rs:1-45`). They cannot replace one section of a managed skill.
- `[scaffold] ignore` in `.codeflow/project.toml` (`crates/codeflow-core/src/scaffold/state.rs:148-220`) drops a whole file from management, and with it every later upstream fix. It works per file only.
- The three-way merge of a user-modified managed file (`update.rs:5-12`) keeps a hand edit only while upstream leaves those lines alone; otherwise it writes a `.new` conflict. The edit has no name, `doctor` does not list it, and nothing stops an edit that weakens a floor.
- The personal overlay (`crates/codeflow-core/src/model_catalog/inputs.rs:115`) is per user and covers the model catalog only, not instructions.
- `.codeflow/model-selection.json` is the precedent to follow: a project-owned file that may reference only names the managed catalog declares, rejects the whole file on any invalid entry with no partial application or silent fallback, and is checked by `codeflow doctor --check model-bindings`.
- The kernel `assets/base/rule-map.toml` already gives every always rule an `id` and every moment row a `key`. Managed skill sections have no stable names.

Chosen design:

1. One project-owned override file, `.codeflow/overrides.toml`, which update never writes. Each entry names its target by a declared name and carries the replacement text: `rule:<id>` or `moment:<key>` for a managed block row (from the kernel), and `<skill>#<section-id>` for a skill section, where the id is a `<!-- codeflow:section id=... -->` marker on that heading in the managed skill text. Free text, heading wording and line numbers are never accepted as targets.
2. The floors are one declared list, `assets/base/instruction-floors.toml`, embedded in the binary like the kernel. Each entry names a floor (today the git floor and the non-relaxable command class), the units it covers, and its refusal text. The override check reads only this list and checks floors first, so the refusal names the floor. The refusal tests iterate the list, so adding a floor (for example cross-lineage security review, if the operator rules it one) is one entry plus its test row, with no new code path. A contract test fails when a floor names a unit that no longer exists.
3. Fail closed: an unreadable or malformed file, a floor target, a name that does not exist, or two entries for one unit makes `codeflow update` refuse before writing anything, naming the entry, and makes doctor fail. This is the whole-file reject of the model-selection precedent, never partial application.
4. Update renders the shipped text, then swaps each named unit's text. The manifest invariant holds: the recorded hash stays the pristine shipped hash. A file counts as unmodified when it equals the baseline with the overrides applied, so a hand edit is still detected and merged.
5. A new doctor check, `overrides`, lists each active override with its target name and the managed text it replaces.
6. Scope: this task adds section markers to the managed skills its tests need and documents how more are added, so "every instruction changeable" grows marker by marker. `cf-model-orchestrator` gets its markers after TSK-1292 lands, which is editing it now. Replacing a whole reference file stays with `[scaffold] ignore`, and the docs say so.

Reason: an allow-by-declared-name check plus one floor list is the standard policy pattern; it reuses the strict whole-file reject the project already trusts in model-selection, and it keeps the manifest invariant that update's correctness rests on.

Not covered: an override's replacement text could contradict a floor stated in another unit. The floors are still enforced by hooks and guards, and the precedence line in `AGENTS.md` ("safety floors and [enforced] rules hold under all") still stands, but the override text is not scanned. Raised for the security review.

Estimate re-scored at claim: S1 3, S2 1, R 1, sum 5, Hard, 4-6h, unchanged; the floor list is data, not a new shape.
