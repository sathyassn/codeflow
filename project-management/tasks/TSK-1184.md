# TSK-1184: Policy authority refuses when the configured and effective remote identities differ

## Description

With no tracking refs, the policy authority load runs `ls-remote` on the raw configured URL (`crates/codeflow-core/src/hooks/landed_policy.rs:101`, `:153`). The sanitized query (`crates/codeflow-core/src/git/remote_query.rs:196`) leaves out `insteadOf`. If the raw URL advertises an empty repository while an `insteadOf` rewrite names the populated authority, the result is "unestablished", and `landed_policy.rs:273` loads policy from local HEAD. That lets a local change weaken the policy fields read from it (CWE-863). Preconditions: the requester controls the raw endpoint or the configuration, and the tracking namespace is absent.

This task makes the policy authority load compare the configured and the effective remote identities and refuse when they differ, or when either cannot be verified. Source: finding K1 of the TSK-1156 security review (Codex GPT-6 Astra, 2026-11-02 11:27, `coordination/coordinators/parallel/reviews/tsk1156-security-r1.md`), checked against the line tip on 2026-11-02.

Security task, first in the build order of the 2026-11-02 planning PR (Director, 11:30). It changes hook authority and fails closed. Related, not covering it: TSK-327 (the pre-push destination query), TSK-189 and TSK-304 (complete), TSK-1057 (forged plain ref files).

Non-goals: changing which branch is the policy authority (ADR-0091), and restoring arbitrary configured transports to the query.

## Outcome

after this merges, a person is protected from a repository whose raw remote is empty and whose effective remote (through `insteadOf`) is populated, because policy authority refuses with both identities named, and a fresh adopter's first push still works.

## Deliverables

- the identity comparison and the refusal: `crates/codeflow-core/src/hooks/landed_policy.rs`, `crates/codeflow-core/src/git/remote_query.rs`, with the comparison following the fetch guard in `crates/codeflow-core/src/hooks/ref_authority.rs:416`
- tests: the insteadOf fixture, the fail-closed cases, the bootstrap case and one fixture per sibling load path in `crates/codeflow-core/tests/` and `crates/codeflow-cli/tests/`
- the sibling sweep: a table in this record of every policy-authority load path with its verdict
- release note: `changelog.d/TSK-1184.md`

## Acceptance Criteria

- AC-1 When the raw remote is empty and the effective remote, through an `insteadOf` rewrite, is populated, the policy authority load shall refuse and the message shall name both identities; evidence: a fixture that loads local HEAD policy before the change and is refused after it.
- AC-2 When policy authority cannot be verified from the remote, the load shall refuse and never fall back to local HEAD; that covers an identity mismatch, an unreadable effective identity and a failed query; the comparison shall follow the fetch guard (`hooks/ref_authority.rs:416`) and the query shall stay hermetic, with no arbitrary configured transports restored; evidence: one fixture per case and a test that the query environment is unchanged.
- AC-3 Bootstrap shall stay explicit: a repository whose effective remote is verified empty, with matching identities, is the only case where HEAD policy is labelled "unestablished"; "verified empty" means a live, hermetic query of the effective remote URL that returns no refs, never the absence of local tracking refs, and any query error shall refuse (Director, 2026-11-02 11:34); evidence: a test that a fresh adopter's first push still works, and a test that a missing tracking namespace alone does not count as empty.
- AC-4 Every other policy-authority load path shall be listed in this record with a verdict and a test where it can fall back to HEAD; evidence: the sibling sweep table and one test per path that can fall back.
- AC-5 (journey) The installed build in a scratch adopter shall refuse the `insteadOf` case and admit a matching fresh remote; evidence: the journey output.
- AC-6 The cross-lineage security review shall be told to attack the bootstrap carve-out specifically: `insteadOf`, `pushInsteadOf`, an empty fork as the effective remote, and `url.*.insteadOf` set in include files; the PR shall state the threat and why the carve-out is the standard design; evidence: the review brief and verdict, and the PR body.
- AC-7 (added 2026-11-02, the Director, about 14:3x; evidence: the TSK-1156 round-4 builder report, "Harness autonomy gaps", item 3, checked at the EPC-022 tip by a read-only sweep) When the effective remote URL (after `insteadOf`, `pushInsteadOf` and include files are resolved) uses a protocol outside the hermetic allow-list (`SAFE_PROTOCOLS`, `crates/codeflow-core/src/git/remote_query.rs:160`, applied through `GIT_ALLOW_PROTOCOL` at `:257`), the policy authority load shall refuse; the refusal shall name the protocol and the allow-list, shall never retry with a widened list and shall never fall back to local HEAD; evidence: a fixture with an `ext::` effective URL and one with a `git://` effective URL, each refused with that message.
  - Reason for the addition: AC-1 to AC-3 cover `landed_policy.rs:101` and `:153` but not this path, so a legitimate effective remote on any other protocol was refused with no stated message and no test.
- AC-8 (added 2026-11-08, the Director's route after the third delta review of PR 698) For an SSH remote, before `ssh` reads its configuration, the load shall read as text every SSH configuration file `ssh` could read: the system files the `ssh` on `PATH` names, `~/.ssh/config` under both `HOME` and the account's home, and every file an `Include` can name. It shall refuse, naming the file and line and how to proceed, when any word (quotes and backslashes removed, split at `=`, any case) contains `exec`, is `Match`, is `ProxyCommand`, `KnownHostsCommand` or `LocalCommand`, or is `PermitLocalCommand` not followed by `no`; when a quote does not close; and when a file or include is not a readable UTF-8 regular file or passes the depth, file-count or size limit. Over-refusal is accepted. An allow, `accept_ssh_configuration` under `[policy_authority]` in `<account home>/.codeflow/authority/config.toml`, with the home from the password database and neither `HOME` nor `CODEFLOW_HOME` read, is off by default and skips the text check; a file there that is a link, not a regular file, not owned by the account, writable by others or unparsable refuses. Evidence: fail-before and pass-after fixtures for `"Match" exec`, `Ma"tch" exec`, `In"clude"` of a file with `Match exec`, a `HOME` that differs from the account home, a command keyword, a plain `Match`, an unclosed quote and an unreadable include; a real-ssh test that the command never runs; the allow off refusing and on passing the same configuration; an allow selected through `CODEFLOW_HOME` and one selected through `HOME` each refusing; and the agent guards refusing an agent's write of the allow file.
  - Reason for the fail-closed rule: three review rounds found that matching `ssh`'s own parsing (unquoted keywords, then `Match exec` only, then `HOME` expansion) left a way for `ssh -G` to run a command inside the guards. A reader that refuses every class that can run a command does not depend on matching the parser exactly.
  - Reason for accepting over-refusal: a refused adopter has three ways forward (edit the line, fetch the remote once it has its default branch, or the allow), while a missed command runs inside doctor, git-guard and the hooks.
  - Reason for the off-by-default allow: an adopter must be able to accept their own SSH configuration. The allow is read only from the account's own home, so neither a pull request head nor the command the check judges can set it.
  - Reason for the change after the fourth delta review (2026-11-08, the Director): the allow was read from the codeflow home, which `CODEFLOW_HOME` or `HOME` on the judged command selects, so that command could turn the check off; and the user config is a file an agent running as the account can write. The allow moved to the operator-authority directory, which the shipped Claude, Codex and Grok presets and the edit and git guards refuse agents to write, read through the password-database home.
