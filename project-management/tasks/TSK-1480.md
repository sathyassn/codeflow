# TSK-1480: Only an admin creates release tags and integration lines

## Description

Before this task, the repository's forge rules kept `v*` release tags from being moved or deleted and integration lines from being force-pushed or deleted, but no rule stopped anyone with push access from creating either. A workflow token or a write-role pusher could create a release tag or a new `integration/**` line. This task adds two forge rules, each holding only a creation rule with the repository admin role as its one bypass, and changes the release procedure so that the operator creates the `v*` tag at the exact `main` commit before dispatching the release workflow, which then resumes on that tag. The rules are new and separate: they change no existing rule, so the update and deletion protections keep no bypass. The operator applies them with a workspace script, outside this repository. The operator applied the rules before this task's procedure text reached `main`, by the operator's choice; until this task lands, the operator creates each `v*` tag at the exact `main` commit before each release dispatch. Limit: the bypass is the admin role, and agents push as the operator's admin login, so these rules stop workflow tokens and write-role pushers but do not tell an agent from the operator; a separate agent identity is out of scope. Non-goals: `codeflow remote protect` for adopters is unchanged, and line creation stays open there.

Overlaps:

- TSK-1346 AC-8 names a creation rule on the release tag rules as a floor for its docs. This task applies that floor and changes `docs/releasing.md`; whichever of the two lands second aligns the release text.
- TSK-1452 writes its own line rules. This task creates separate rules and reads or changes none of TSK-1452's, so neither task's script can undo the other.

## Outcome

After this merges, only a repository admin can create a release tag or a new integration line, and the operator follows a documented release order that creates the tag at the exact `main` commit before dispatching the release.

## Deliverables

- the two creation rules: repository settings, applied by the operator with a reviewed workspace script (kept in the CodeFlow workspace, outside this repository)
- the release order: `docs/releasing.md`
- the tests that pin a pre-created tag: `scripts/test_release.py`
- the release note: a fragment under `changelog.d/`, if the release-impact check asks for one

## Acceptance Criteria

- AC-1 An operator script in the workspace shall have three modes: a dry run that only reads, an apply mode and a restore mode. It creates two rules, one for `v*` release tags and one for `integration/**` lines, each holding only the creation rule, with the repository admin role as its one bypass actor, always bypassing, and no integration actor. It changes no existing rule. Each rule name must be absent, or held by exactly one rule with the recorded body; anything else refuses. Restore deletes the two. Apply needs an explicit confirmation of the admin role's identity. Its header says it must not be applied before AC-2's text is on `main`. Evidence: the dry-run output and a cross-family review of the script, both in the workspace; the operator applied the reviewed script on 2026-11-12, before AC-2's text reached `main`, by the operator's choice.
- AC-2 `docs/releasing.md` and the release steps shall say the operator creates the `v*` tag at the exact `main` commit before dispatching the release workflow, and that the workflow then resumes on that tag. If the managed release policy states the old order, it changes through the managed-content route. Evidence: the doc diff and `codeflow validate --docs`.
- AC-3 `scripts/test_release.py` shall gain two tests: host state verification reports a resumed tag for a tag at the source with no release; publication verification accepts the requested tag already at the dispatched `main` commit. A tag at another commit stays refused in both. Evidence: the tests, run before and after.
- AC-4 The task shall get one cross-family security review with the `cf-security-reviewer` checklist, the seat probed live at dispatch, covering the script and the docs. The script reaches the Director with its dry-run output before the operator runs it. Evidence: the review row and the Director's acknowledgement.
- AC-5 Public text (record, PR title and body, commit subjects, docs, test names) shall use general words, with no rule identifier and no live-check detail. Evidence: the PR as opened, checked by the reviewer.
