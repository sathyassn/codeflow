# TSK-153: scaffold writes flush the disk once per run

## Description

A standard `codeflow init` takes about 6 s of wall time for about 0.7 s of
CPU on an internal macOS SSD, and adopters feel the same wait on `update`.
A stack sample of a running init put 2,538 of 2,745 samples (92%) in
`__fcntl` under `scaffold::state::write_file`, whose `File::sync_all` is
`fcntl(F_FULLFSYNC)` on macOS. It runs for the temp file and again for the
parent directory, and each installed file passes through `write_file` twice
(its destination and its baseline copy): about four full flushes per file,
about 1,000 for the 255 files of a standard init. A full flush measured
about 13 ms on the same disk against about 2 to 3.5 ms for a plain
`fsync`. The per-file sync arrived with 6b57fe654 ("fix(scaffold): harden
state persistence"). The same path serves `update` (`update.rs`) and the
pull request template edits (`pr_template.rs`). This task keeps the crash
safety that commit added and pays for the full flush once per touched
directory or once per run. Non-goal: changing what init or update writes.

## Affected surfaces and interfaces

- `crates/codeflow-core/src/scaffold/state.rs` (`write_file`,
  `sync_directory`, `write_beneath_root`) and its callers in `init.rs`,
  `update.rs` and `pr_template.rs`.
- Tests in `crates/codeflow-core` and `crates/codeflow-cli/tests/init_e2e.rs`.

## Acceptance Criteria

- AC-1 When a scaffold run writes a managed file, the system shall keep the
  temp-file-and-rename step and make the file's content durable before its
  rename (a plain `fsync` per file is enough for that ordering), so crash
  safety is as strong as today; evidence: the code and AC-4's test.
- AC-2 When init, update or a template edit finishes its writes, the system
  shall issue one full flush per touched directory, or one per run, at the
  end, instead of one per file; evidence: AC-3's test.
- AC-3 A test shall count the sync calls per file and per run for a fresh
  init and an update, and fail when a full flush runs per file again;
  evidence: the test.
- AC-4 When a scaffold run is interrupted between writes, no managed file
  shall be torn or empty: each is either its old content or its new
  content; evidence: a crash-interruption test.
- AC-5 The pull request shall report init and update wall time before and
  after on macOS, as a reported check and not a gate, and state the Linux
  behaviour of the chosen sync calls; evidence: the pull request body.
- AC-6 (journey) A fresh init at every tier and an update from the
  previous scaffold, through the built binary, shall install the same files
  with the same content as before the change; evidence: `init_e2e` and an
  update test.
