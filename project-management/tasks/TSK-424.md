# TSK-424: One exemption register and relaxation report serves every managed check

## Description

Issues #274 (item 2 to 5), #275 (items 4 and 5) and #279 (item 5) each
ask for the same mechanism: a project that relaxes a default check, or
exempts one occurrence from it, records why, who owns it and when it is
revisited, in one format every check reads, and `codeflow ci` reports
the register's health in the pull request evidence. CodeFlow 3.1.1 has
no waiver or exemption concept, so each adopting project invents its
own register, field set and refusal rules.

Outcome: **one exemption register format under `.codeflow/` serves
every managed check this epic adds: each entry carries id, kind, rule,
paths, value where it applies, reason, task id, owner role, date,
expiry and revisit trigger; a check refuses a missing field, a
malformed task id, a past expiry, a head-introduced entry that matches
nothing, a class-wide entry and an inline suppression that cites no
register id, and reports a stale base entry for retirement in that
pull request; admitted debt, admitted once in the pull request that introduces the
check and compared against the previously admitted baseline by stable
occurrence identity, can only shrink; and
`codeflow ci` reports entries, expiring entries, baseline size and its
change in the PR evidence.**

Rules:

- The register (provisional `.codeflow/exemptions.json`) and the
  baseline (provisional `.codeflow/baseline/<check>.json`) are project
  files. What the trusted base governs is the check's own
  configuration and level, so a head can never turn a check off or
  lower it (as the secret-scan exemptions are judged, TSK-292,
  TSK-336). Entries have a lifecycle inside the pull request that needs
  them: an entry introduced or amended at the head is accepted only
  with every required field, is listed in the PR evidence as a new or
  changed exemption for the reviewer, and is never silent; an entry
  retired at the head is accepted when its occurrence is gone at the
  head (the ordinary same-PR repair-and-retirement); a base entry that
  matches nothing at the head is reported as stale and retired in that
  pull request, never refused; a head entry that matches nothing is
  refused. No bypass and no extra planning pull request is needed. A
  setting `max_exemption_days` bounds expiry.
- Admitted debt is separate from exemptions and has its own lifecycle.
  The baseline records stable occurrence identities (path, rule and a
  content hash of the occurrence, never a line number), each naming
  its fix task. The ratchet compares the head's occurrences against the
  previously admitted baseline, the one at the trusted base commit,
  never against a baseline the head edited: a pull request passes only
  when every head occurrence is in the admitted baseline by identity,
  so growth and replacement debt (one admitted occurrence removed, a
  different one added) are refused whatever the head's baseline file
  says; a head may change the baseline only to remove occurrences that
  are gone (shrinking), and any other head edit of the baseline is
  refused. Initial admission needs no extra pull request: `codeflow
  baseline admit <check>` (provisional) writes the first baseline from
  the current occurrences, each with a fix task, inside the pull
  request that first introduces the strict check for that project, and
  `codeflow ci` accepts an admission only when the trusted base holds
  no admitted baseline for that check and prints the admitted
  occurrences in the PR evidence; every later head may only shrink it,
  and widening admitted debt is forbidden by the ratchet (any
  relaxation is a separate operator-authorized policy change, never a
  baseline edit). An occurrence with no fix task is refused at
  admission and at validation.
- A project-wide relaxation of a default (issue #275 item 5, #279 item
  5) is an entry of kind `relaxation` naming the setting and its value,
  with the same required fields; `codeflow ci` lists each one.
- The checks that consume the register are TSK-425, TSK-426 and
  TSK-428; this task ships the reader, the writer, the schema and the
  report, with one consumer stub test.

Non-goals: any one check (the consumers); the secret-scan and
dependency-audit exemption routes that exist today (unchanged).

## Deliverables

- the register and baseline schema and reader: a new `crates/codeflow-core/src/exemptions/` module, with the schema documented in `docs/policy-reference.md`
- the `max_exemption_days` setting: `crates/codeflow-core/src/hooks/policy_schema.rs`
- the admission command: `codeflow baseline admit <check>` in `crates/codeflow-cli/src/cmd/baseline.rs` (new) wired in `crates/codeflow-cli/src/main.rs`, with its CLI help, and the admission evidence (the admitted occurrences with their fix tasks) printed by `codeflow ci` in the PR evidence
- the report: `crates/codeflow-cli/src/cmd/ci.rs` (the PR evidence section) and the pre-push summary
- the review question: the managed review templates in `cf-reviewer` (agent) and `cf-ship/references/pr-evidence.md` in `assets/base/`, `.claude/skills` and `.agents/skills`
- tests: unit tests in `exemptions/` and `crates/codeflow-cli/tests/ci_cli/exemptions.rs` (new)
- release note: `changelog.d/TSK-424.md`

## Acceptance Criteria

- AC-1 A register entry with every field shall be accepted, and an entry with a missing field, a malformed task id, a past expiry, no specific paths and value, an inline suppression citing no register id, or a head-introduced entry that matches no occurrence shall each be refused naming the entry and the field; a base entry that matches nothing at the head shall be reported stale, not refused; evidence: one test per refusal and the stale case. (serves EPC-024 AC-1)
- AC-2 The ratchet shall compare the head's occurrences against the baseline admitted at the trusted base, by stable occurrence identity (path, rule, content hash) with a fix task per occurrence: a head whose occurrences are all admitted shall pass, and growth, replacement debt (an admitted occurrence removed and a different one added) and a baseline occurrence with no fix task shall be refused naming the occurrences, whether or not the head edited the baseline file; a head may only shrink the baseline; initial admission through `codeflow baseline admit` shall be accepted only in a head whose trusted base holds no admitted baseline for that check, inside the pull request that first introduces the check, with the admitted occurrences printed in the PR evidence, and a head that re-admits or widens an existing baseline shall be refused; evidence: tests for growth, replacement, an equal set that passes, a missing fix task, a head that edits the baseline with replacement debt, a head that edits it with growth, a shrink that passes, a first admission alongside the check's introduction, and a second admission refused. (serves EPC-024 AC-1)
- AC-3 `codeflow ci` shall print the register's entry count, entries expiring within `max_exemption_days`, each relaxation, the baseline size and its change against the base, in the PR evidence; evidence: a CLI test reading the output. (serves EPC-024 AC-1)
- AC-4 The check's configuration, level and admitted baseline shall be read from the trusted base commit in CI; exemption entries shall follow their own lifecycle (introduction and amendment accepted only with every field and listed in the PR evidence; retirement accepted when the occurrence is gone; stale base entries reported), with the same-PR repair-and-retirement case passing; evidence: tests with a head that adds, amends and retires exemption entries, including the fix-and-retire case, and a head that tries to lower the level, refused.
- AC-5 The review template shall ask whether a change copies a value that has a home and whether an added exemption is justified; evidence: the template text.
- AC-6 (journey) With the installed build in a scratch adopter project, one exemption with an expiry in the past shall block `codeflow ci`, and the same with a future expiry shall pass with the entry reported; evidence: the journey output.
