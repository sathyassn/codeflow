# TSK-1342: CodeFlow never deletes or moves a branch through a symbolic ref

## Description

Source: the PR 600 F1 confirm review (`coordination/coordinators/parallel/reviews/tsk1308-f1-confirm-37adc82b6.md`, nit 3), which the Director ruled material on 2026-11-05. That nit ran no git experiment. The PR 617 review tested it (`coordination/coordinators/planning/reviews/pr617-records-opus.md`, finding 1), and this record states what it observed.

Which forms follow a link, observed with git 2.53.0 in a scratch repository:

- `git update-ref -d refs/heads/sym` deletes the branch the link points to and leaves the link dangling.
- `git update-ref --no-deref -d refs/heads/sym` removes the link and keeps the target.
- `git branch -D sym` removes the link and keeps the target.

Sites at `a5cd83c69`:

- `crates/codeflow-core/src/ids/issue.rs:888` runs `update-ref -d` on `REGISTRY_REF` (`refs/heads/codeflow/registry`) with no `--no-deref`, and `issue.rs:882` and `:885` call `set_ref`, which runs `update-ref` the same way. The precondition is a symbolic registry ref. The second PR 617 review ran the same git commands in a scratch repository with that ref pointing at `main`: the delete removed `main` despite its old-value check, and the write moved `main` back to an older commit. `drop_pending` itself was not run.
- `rename_standalone_branch` (`crates/codeflow-core/src/workgraph/readiness.rs:2090-2094`) does not follow a link, although it also has no `--no-deref`. Its `old` comes from `repo.head()` (`readiness.rs:1906-1907`), which resolves the chain, so a link to a protected branch is already refused at `readiness.rs:1917-1921`. A link to an unprotected branch deletes that branch by its own name and leaves the link dangling, and `--no-deref` would change nothing. The real command was not run with HEAD on a link.
- TSK-1308 fixes the same class for `codeflow work remove-candidate` in PR 600, open at this writing.

This task fixes the class everywhere CodeFlow deletes a ref or writes one it owns: each site that follows a link either passes `--no-deref` (or the git2 equivalent that removes the named ref only) or refuses a symbolic ref before it deletes. Non-goals: the guards' parsing of a user's own `git branch -D` or `update-ref -d` command lines (the guard plane judges those already), and test fixtures that delete refs to set up a case.

## Outcome

After this merges, an adopter whose repository holds a symbolic branch can run any CodeFlow command that deletes a ref or writes one CodeFlow owns, and the branch the link points to, a protected branch included, is never deleted or moved through the link.

## Deliverables

- the sweep of every ref-deletion site with file:line: this record's `## Findings`
- the fixes: each site the sweep finds following a link, starting with a refusal of a symbolic `REGISTRY_REF` at the top of the registry writers in `crates/codeflow-core/src/ids/issue.rs`; provisional, the sweep decides the rest
- the claim rename's behaviour when HEAD reaches its branch through a link: `crates/codeflow-core/src/workgraph/readiness.rs`
- the per-site symref fixture tests: beside each site's existing tests in `crates/codeflow-core/src/` and `crates/codeflow-cli/tests/`
- the guard against new unguarded deletions: a lint test in `crates/codeflow-core/tests/` (provisional home; the builder may place it with the existing source-scan tests)

- AC-2 Before any code change, the builder shall list every ref-deletion site in product code, scripts and shipped assets (`update-ref -d`, `update-ref --stdin` deletes, `branch -D` or `-d`, `git push --delete`, and git2 reference deletes) and every `update-ref` write on a ref CodeFlow owns, with file:line and one verdict for each: follows a link, passes `--no-deref`, refuses a symbolic ref, or does not follow; evidence: a `## Findings` section committed before the first code change, with the search commands used.
- AC-3 When a ref that CodeFlow deletes or writes is a symbolic ref, each site that follows a link shall act only on the named ref or refuse naming the symbolic ref, and a symbolic `REGISTRY_REF` shall be refused before any registry write or delete, and the branch it points to shall keep its tip; evidence: a symref fixture per such site that fails before the change and passes after it. A site that does not follow a link gets the same fixture as a regression guard, with the reason in `## Findings`.
- AC-4 When HEAD reaches its branch through a link, the claim rename shall refuse naming the link, or the builder shall record in `## Findings` why another behaviour is right; the target's commits shall stay reachable and no link shall be left dangling without that being stated; evidence: a fixture with the link pointing at an unprotected branch.
- AC-5 When a new ref deletion in a form that follows a link is added to product code, scripts or shipped assets without `--no-deref` or a symbolic-ref refusal, a test shall fail naming the file and line, and `git branch -D` shall not trip it; evidence: the lint test, a negative case showing it failing on an unguarded `update-ref -d`, and a case showing `branch -D` passing.
- AC-6 The change shall have a cross-lineage security review that carries the `cf-security-reviewer` checklist: Grok or Codex when a live probe at dispatch shows usage, else a fresh Claude Opus medium subagent with reduced assurance recorded; evidence: the review row in the PR and its findings record.
- AC-7 (journey) With the installed build in a scratch adopter project, each CodeFlow command the sweep names as deleting a ref shall be run where that ref is a symbolic branch pointing at `main`, and `main` shall keep its tip; evidence: the journey output with `git show-ref` before and after.
