# TSK-1174: A pull request summary opens with enough context for anyone to know what it is and why

## Description

Operator direction, 2026-11-01 (relayed by the Director): a pull request
summary must open with just enough context for anyone to know what the PR is
and why it exists, whether or not the change is functional, before any
detail. Today the shipped instruction says the Summary "anchors a reader with
no context in a few lines" (`assets/base/rules/git-rules.md:150`), and
`codeflow ci` checks only the Summary's block shape: one prose paragraph, a
list or table, at most one closing paragraph (`pr_body.rs:1284-1325`,
`summary_problem` at `:1222-1262`). Nothing says what the first paragraph
must hold, and nothing shows a good and a bad one.

Outcome: **after this merges, the shipped PR instructions tell every author,
with one good and one bad example, that the first paragraph of the Summary
states what the PR changes and why, in plain words and before any file name,
identifier or detail; and `codeflow ci` warns, never fails, on the two cases
it can recognize without judging meaning.**

What `codeflow ci` can and cannot enforce (read at line tip, 2026-11-01):

- It cannot judge whether a paragraph states what changes and why. That is
  meaning; a check that guessed would fail closed on prose it cannot read.
  Review and `cf-editorial-review` judge it.
- It can recognize two proxies from the Summary's visible lead text, which
  `summary_blocks` already collects per block (`OpenBlock.text`,
  `pr_body.rs:1056-1066`): a lead under 12 words, and a lead that opens with
  an identifier label (`TSK-NNN`, `EPC-NNN`, `#NNN`, or a path) before any
  words. Both are warnings only. The rule key stays `git.pr_summary`; the
  finding is raised at warn whatever the configured level, and not at all
  when the level is off (`pr_body.rs:1292`). No policy key is added, so the
  policy schema fixtures do not change.

Non-goals: judging meaning mechanically; a new policy key or level; a
change to the block shape rule; any change to the sections other than
Summary.

The good and bad example the three sources carry (identical text, so the
manifest mirror test can hold them together):

```
Bad:  TSK-1013: profile. Adds profile.rs and the reader. See Changes.
Good: Adds an opt-in time-box profile so a project can compare each
      finished task with the hours it was planned for. Without it,
      estimates and results can only be compared as forecasts. Ready for
      review; nothing changes for a project that does not turn it on.
```

The bad one opens with an identifier, names no result, gives no reason and
sends the reader elsewhere. The good one says what changes, why, and where
it stands, in plain words, before any file name.

## Acceptance Criteria

- AC-1 `assets/base/rules/git-rules.md` "PR bodies", the PR body template's Summary comment and `cf-ship` step 6 with `pr-evidence.md` shall each state that the first paragraph says what the PR changes and why, in plain words, before any identifier, file name or detail, and that this holds for a non-functional PR (docs, plan, chore) as much as a functional one; each shall carry the same good and bad example; evidence: the three diffs and the manifest and mirror tests green (`manifest_consistency`). (serves EPC-022 AC-202)
- AC-2 `codeflow ci` shall raise a warning under `git.pr_summary`, level warn whatever the configured level, when the Summary's lead paragraph has fewer than 12 visible words or opens with an identifier label (`TSK-NNN`, `EPC-NNN`, `#NNN` or a path) before any words, naming which case and pointing to the rule; it shall raise nothing when `git.pr_summary` is off, shall never change the exit code, and shall not read or judge the paragraph's meaning; evidence: fixtures that fail before the change (no finding, so the assertion for a finding fails) and pass after, one per case, plus a good-example fixture and the shipped template's own Summary that raise nothing.
- AC-3 The shape check shall be unchanged: every existing `summary_shape` fixture shall give the same result, and any CLI fixture whose short lead now draws the new warning shall be updated to assert the warning, not to hide it; evidence: the existing `pr_body.rs` and `ci_cli.rs` tests green, with the changed fixtures listed in the PR.
- AC-4 (journey) With the installed build, `codeflow ci` on a body whose Summary opens `TSK-123: profile.` shall print the warning and exit 0, and on the good example shall print no summary warning; evidence: the command output.
