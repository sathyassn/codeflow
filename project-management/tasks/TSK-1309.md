# TSK-1309: A reviewed head vouches only for that task's own work

## Description

The line's receiving-merge check (`crates/codeflow-core/src/workgraph/acceptance/receiving_merges.rs:90-103`, reported by coord/ci on 2026-11-03) hides every commit a completed task's reviewed commit contains. A task's merge therefore stops being refused once any later completed task's reviewed commit contains it, although that later review did not review the earlier work. Example: PR 482 (TSK-359) changed `.github/workflows/codeflow-ci.yml`, and its merge 51e6a2dd6 sits inside the bound commits of TSK-1150, 1156, 1246, 1256 and 1268, so the check passes with TSK-359 still `todo`, while PR 560's merge, being the newest, is refused. A reviewed head shall vouch only for the task's own work. Non-goal: changing what a whole-unit review covers. It lands before the pull request from the EPC-022 line to `main` (Director ruling, 2026-11-03), because that pull request relies on this check.

## Outcome

After this merges, the check on a line refuses a landed product change until the task that landed it has its own completion, however many later reviewed heads contain it.

## Deliverables

- The narrowed check: `crates/codeflow-core/src/workgraph/acceptance/receiving_merges.rs`.
- Tests beside that check, and a report of what the corrected check finds on this repository's line.

## Acceptance Criteria

- AC-1 Before any change, the builder shall reproduce the gap with a fixture of two tasks where the later task's reviewed commit contains the earlier task's merge, and shall list each other judge that hides commits by reviewed-commit containment (sibling sweep); evidence: the fixture failing before the change and the list with file:line.
- AC-2 A reviewed commit shall hide only the commits that are the task's own work: commit objects reachable from the reviewed SHA and not from the line at its merge base, excluding what merges of the line brought in, read from the commits and never from a branch name; a commit that came in through a merge of the line shall stay accountable to the task that landed it; evidence: the AC-1 fixture passing, and a fixture where a task's own commits stay hidden.
- AC-3 When the check cannot prove which commits are a task's own, it shall refuse and name the commit (fail closed); evidence: fixtures for an unreadable completion and an ambiguous merge shape.
- AC-4 A landed merge touching only records, or a landed sync that adds no change of its own, shall not be refused by this change; evidence: one allowed fixture for each.
- AC-5 (journey) Before this lands, the builder shall run the corrected check over this repository's EPC-022 line and list every task it finds, and each shall have a completion or a tracked route; evidence: the list in the PR body, including TSK-359. Cross-lineage security review, as this is merge admission.

## Findings

Known limit: a completion of one task can credit another task's chain.

- **Threat:** any completion of task B whose `reviewed:` binds to a commit on task A's chain credits that chain, because nothing ties a record's completion to the chain that carries its task. Known shapes:
  - B branches from A's unlanded head without pinning A as a stacked predecessor, and both land in order. `reviewed_own_commits` walks B's first parents through A's commits.
  - A branch built on A's tip completes B naming that tip and lands through its own merge.
  - A planning commit on the line completes B naming A's tip after A's landing merge (security re-review probe A2).
  - A re-completion of B on a branch cut from the line names A's commit (probe A3).

  In each, A's landing is not refused while A has no completion of its own. This is pre-existing: an active completion admits the same histories, and before this task a reviewed head hid all its ancestry. The archived-review credit does not widen it. The variant where a completion made on A's tip is merged into B's own branch is closed: an archived completion credits only where it was made on the judged chain or on a chain a receiving merge landed (`made_on_own_chain` in `receiving_merges.rs`).
- **Fix:** tie a completion to the chain that carries its task, for example by stopping the walk at the head of a stacked predecessor, read from the commits or a pin. The current stacked-landing rules do not require that pin.
- **Revisit:** when stacked-landing rules change.
