# TSK-173: guard runtime: fail closed, contract and seat readiness

Unit 3 of 5 of the harness permissions work, TSK-171 to TSK-175 (decision record:
`ADR-0075`; design: `docs/verification/permission-presets-design-2026-09-28.md` section 1).

## Description

Units 1 and 2 remove the prompts and move the safety into deny rules and
guard hooks. A guard hook fails open in all three harnesses when it is not
run: only exit 2 blocks, a missing binary exits 127 and the call proceeds, a
timeout proceeds, and Codex skips any hook definition whose hash it has not
trusted. A seat can therefore start with some guards absent and look normal.

This unit makes a guard that runs and fails refuse the call, gates every
hook on a contract version so an older binary refuses too, and makes a host
brief a seat only after each required guard has run in that seat's session
with the hook entries and posture the operator approved. Readiness is a
record of one point in time: the host checks it again before every prompt
and runs a fresh guard-readiness preflight when anything it depends on has changed. It also
writes the delegated seat's native deny of unsandboxed retries and records
the seat settings file's hash, so a primary cannot hand a seat a settings
file it rewrote.

**What readiness shows, by route.** Where the hooks run outside the seat's
sandbox and write receipts where the seat cannot (Claude seats, Codex under
`cf-guard` or `cf-builder`), a receipt shows that the guard ran, for as long
as the sandbox holds. Where the seat can write the receipt location (Grok,
whose hooks run inside its own sandbox and write under `~/.grok`; Codex under
full access), the receipts are **cooperative readiness evidence**: they show
the guards ran for a seat that followed the guard-readiness preflight, and a seat whose guard
was skipped could write them itself. The host labels each route, and this
unit does not claim more.

D8 is decided (workspace `RELEASE-PLAN.md:539`): guard hooks fail closed at
every tier, with `--contract` on every hook, and there is no fail-open
switch. The session-start check reports an outdated binary or project before
work begins and names the exact command; a refusal names the command and
says it is queued for the operator; the agent keeps doing work that needs no
guarded tool and re-checks with `codeflow doctor` once the operator
confirms. The operator's options are to update, to let the agent continue
other work, or to roll back the binary. What stays open is
stated: a hook that times out, an operator-launched primary with hooks
disabled, a hook trust change between guard-readiness preflights, and forged receipts on the
cooperative routes.

## Affected surfaces and interfaces

- Hook commands in `assets/base/settings/*.json`, `assets/base/codex/hooks.json`,
  `assets/base/grok/hooks.json` (the Grok file gains the SessionStart hook,
  identical to Claude's).
- `codeflow hook <name> --contract N` for every hook; `codeflow guard-probe`.
- `crates/codeflow-core/src/delegate.rs` (`delegate init`, `delegate wait`),
  and a readiness record under the CodeFlow state root.
- `codeflow doctor` and the orient digest.
- The primary and delegate skills (D8 guidance, AC-12); the orient digest's
  operator-actions line uses the list format of TSK-175 AC-8.
- The managed `.gitignore` block (`.codeflow/probe/`).

## Acceptance Criteria

- AC-1 Every CodeFlow hook command in the three harnesses shall carry
  `--contract N`, `session-orient` and `session-summary` included, and every
  guard hook shall use the fail-closed form (`docs/verification/evidence/permission-presets/`); with the guard
  exiting 0, 2, 1 and 127, and with a binary that rejects `--contract`, the
  hook shall exit 0, 2, 2, 2 and 2 with a reason on stderr. The reason shall
  name the exact command and say it is queued for the operator: for a
  missing or older binary (127, or a binary that rejects `--contract`), the
  wrapper text that `codeflow update` generates names the minimum binary
  version and the install command for the channel the generating binary
  records, or else the documented install forms (E20 `docs/adoption.md:317-321`);
  for a project older than the binary's supported contract range, the
  binary names `codeflow update` in that root, or reinstalling the last
  binary that supports it. The guards shall
  exit 2 when the policy cannot be loaded, and for a bound path whose
  baseline or binding registry cannot be loaded they shall refuse as TSK-172
  AC-11 states for a lost binding; evidence: hook shell tests,
  `codex_hooks`, and the recorded outcome for Git Bash and for PowerShell on
  Windows, each as supported or unsupported.
- AC-2 (guard-readiness preflight) `codeflow guard-probe --nonce N` shall be recognized by
  git-guard and exec-guard, which each write a receipt (nonce, guard,
  contract, binary version, harness, the payload's `session_id` and `cwd`,
  the posture fields the payload carries or `unknown`, the baseline identity
  evaluated, the binding state of the path, a hash of the hook entries
  that invoke the guard, and the admission tuple the hook observed in its
  own environment, recorded as the value, `absent` or `malformed`) and
  allow the call; the probe process shall write
  only a marker `.codeflow/probe/N.ran` in the worktree and never a receipt;
  edit-guard shall write a receipt for an edit of `.codeflow/probe/N` and
  refuse it. Receipts go under the CodeFlow state root for Claude and Codex,
  and under `~/.grok/codeflow-probe/` for Grok, since Grok hooks share the
  seat's sandbox and have no location the seat cannot write. exec-guard shall
  refuse a shell call that runs `codeflow hook <name>` directly, since only a
  harness invokes a hook; evidence: `hooks_cli` tests.
- AC-3 (acceptance) `delegate wait` shall report a seat ready only when, for
  the launch's nonce: every required guard (Claude: git-guard, exec-guard;
  Codex and Grok: those and edit-guard) has a receipt; all receipts share
  the `session_id` of this launch's SessionStart record; `cwd` is the seat's
  worktree and that worktree is bound (TSK-172 AC-11, AC-13); the contract
  matches the installed binary; the baseline identity is the current one;
  **for each guard, the receipt's hook-entry hash, the hash of the live
  effective entries read once at acceptance from the harness config files
  the seat loads (project and user layer), and the hash of the entries in
  this harness's config file as stored in the current approved identity are
  all equal**; the receipt's harness equals the launched harness and its
  posture equals the posture of the route's role (the design record 1.5): builder
  routes Claude `bypassPermissions`, Codex `never` with full access or
  `cf-builder` per D1, Grok `--always-approve` with `cf-guard-worktree`;
  consult and no-edit review routes Claude `auto`, Codex `never` with
  `cf-guard` (D2), Grok `--permission-mode auto`; for every Grok seat the
  receipt's `cwd` is the seat's own task worktree, the directory its trust
  step named (Grok round 5); a builder posture on a consult or review
  route is a mismatch; with an `unknown` posture compared
  against the launch argv the host recorded and reported as not observed;
  the `.ran` marker exists and no probe file exists; and **every
  receipt's observed admission tuple equals the tuple the host set at
  launch**, where `absent`, `malformed` or different is never ready. Otherwise it shall
  report the route unavailable and name the failed check and its remedy: a
  **not enrolled** repository as "repository not enrolled: the operator runs
  `codeflow update` or `codeflow baseline approve`", a **binding lost** as
  "binding changed: the operator runs `codeflow baseline bind`", and an
  **excluded** child as "excluded repository: no seats; the operator adopts
  it with `codeflow baseline bind`". Each failure shall carry one exclusion
  reason from the design record 1.7 (`guard-missing:<guard>`,
  `hook-entry-mismatch`, `hooks-untrusted`, `posture-mismatch`,
  `harness-mismatch`, `not-enrolled`, `binding-lost`,
  `excluded-repository`, `fixture-only`, `stale`, `contract-mismatch`,
  `pin-missing`, `pin-mismatch`, `pin-unsupported`),
  recorded as a native exclusion of that harness route in that worktree,
  never as a model exclusion. The step shall be called the
  guard-readiness preflight in every message, and the host runs it inside
  the orchestrator's seat preflight, before the identity check. It
  reports; the host skills wait on it (S6: the binary never delivers a
  prompt). Evidence: `delegate_cli` tests for all guards loaded; one Codex
  PreToolUse hook changed or disabled while `session-orient` stays trusted;
  **approved H0, receipts written under H0, the live file edited to H1
  before acceptance, with the same nonce, session, cwd and baseline, refused
  on the live hash**; a receipt from a different harness; a posture that differs
  from the route; all hooks untrusted; hooks disabled; a stale receipt from
  an earlier launch; a probe the model did not run; a legacy repository with
  pre-release hooks; a contract-3 repository with no state; a lost binding;
  an excluded child; a Claude consult in `auto`, a Codex reviewer under
  `cf-guard` and a Grok consult in `--permission-mode auto`, each ready; a
  Grok consult launched with `--always-approve`, `posture-mismatch`; the
  exclusion reason recorded for each failure; a healthy store with the
  admission pin absent in one required hook, `pin-missing`; a pin whose

  after the store is then deleted, that seat's next git mutation refused as

  trusted, `hooks-untrusted` or `guard-missing` whatever its launch line
  carried, since readiness is judged by the loaded hooks' receipts and never
  by assuming one argv saved trust (GUG `18-sandbox.md:57`).
- AC-4 When `delegate init` writes the task-scoped Claude settings, they
