# TSK-239: Estimates learn from outcomes derived from git

## Description

Fixes #77. cf-estimate tells a project to freeze forecasts and learn from outcomes, but nothing produces the outcome timings, so the learning loop never starts and a missing estimate home goes unnoticed. This task adds a read-only `codeflow estimate outcomes` that derives each completed task's timings from git (planned, started, blocked spans, completed, landed), joins them by task id to the planning scenario of the project's frozen forecasts, and prints per-task ratios and, past a printed minimum, the median and range by work type with a contradiction line. The thresholds are report flags with printed defaults, not policy keys or a gate. It reports an adopted estimate home that does not exist. `codeflow status` gains one estimates line only where `.codeflow/estimate.json` exists, and cf-estimate's operating reference gains the derived-outcomes and cold-start recalibration paragraph. Non-goals: no new record key, acceptance-block key, claim commit or doctor check; the command never edits a forecast; no validator over adopter planning documents for session units or summed percentiles, because those live in project documents CodeFlow cannot lint honestly while every duration CodeFlow reads is in seconds and the report prints hours.

## Acceptance Criteria

- AC-1 When `codeflow estimate outcomes --json` runs in a repository whose task record was added by a no-fast-forward planning merge, worked in two commits on its task branch, completed by a commit that writes its acceptance block and landed by a no-fast-forward merge, it reports planned, started, completed and landed as those four commits with their times, and elapsed active equal to completed minus started (`estimate_outcomes_cli`, fixture built in the test).
- AC-2 When the task was blocked and later cleared on its branch, the report lists the span with the blocking and clearing commits and subtracts it from elapsed active (`estimate_outcomes_cli`).
- AC-3 When a forecast's package names the task as its `codeflow_task` source and its planning scenario spans 4 hours over that package's implement, review, verify and rework activities, the report shows the task's ratio; with three such tasks at ratios 0.3, 0.3 and 0.4 it prints the median and the line "outcomes contradict the forecast"; with two it prints "below minimum" and no verdict (`estimate_outcomes_cli`).
- AC-4 When `.codeflow/estimate.json` is adopted and its `root` does not exist, the command reports the missing home and exits 1; without `estimate.json` it still derives timings, exits 0 and says no forecast was joined (`estimate_outcomes_cli`).
- AC-5 The command writes nothing: the working tree and index are unchanged after it runs, and it records nothing in the user registry (`estimate_outcomes_cli`).
- AC-6 `codeflow status` prints an estimates line when `.codeflow/estimate.json` exists, naming a missing home, and prints none when it is absent (`estimate_outcomes_cli`).
- AC-7 When `codeflow init --standard` runs with this branch's build, the installed cf-estimate carries the derived-outcomes paragraph and the cold-start recalibration trigger, `codeflow doctor` reports the reading budgets within their guidelines, and `estimate check` behaves as before (`init_e2e`, `estimate_cli`, `estimate_adoption_e2e`, `artifact_budget_contract`) (journey).
- AC-8 When a task landed by squash or fast-forward, or has no commit before its reviewed one, the report gives `started` as unknown with the reason and no elapsed number (`estimate_outcomes_cli`).
