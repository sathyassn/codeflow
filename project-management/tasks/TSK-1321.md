# TSK-1321: The Windows test plan needs no measurements to stay runnable

## Description

The Windows test plan places tests by the measured times in `scripts/windows-test-times.json`, written by `scripts/windows-partitions.py measure` from the JUnit reports of named green runs. TSK-1319 (PR 587) fixes the filterset overrun that stopped PR 552's Windows proof and refreshes the data once (its AC-6). The data goes stale again as tests are added. On coord/ci's estimate at PR 587's head 425795db8, the filterset limit is reached at about 440 new `codeflow-core` tests, and the 10 percent unmeasured-share check fails at about 595 unmeasured tests, about six days at the recent rate. No open task refreshes the data.

This task makes the refresh routine. A scheduled or triggered job measures from named green runs and reports how close the plan is to each limit, and the refreshed file lands through a normal reviewed pull request before either limit is reached. It builds after TSK-1319 lands, on its script and data; TSK-1319's record is not on the line yet, so its `depends_on` edge is added when it lands. The daily exact-SHA Windows run (TSK-1242) is a natural source of green runs once it exists, but this task does not wait for it. Non-goals: the limit values (TSK-1319 AC-4 keeps them) and the placement rules.

## Outcome

After this merges, the Windows partitions run nextest `hash:M/16` from the one archive with no measured data, so a new or renamed test never makes the plan stale, and the `windows` verdict is computed from the jobs' own results.

## Deliverables

- the refresh job or trigger: `.github/workflows/` and `scripts/windows-partitions.py`
- the tests: `scripts/test_windows_partitions.py`
- the description of the refresh and the headroom report: the script's help and `docs/`, where the Windows plan is described

## Acceptance Criteria

- AC-1 The Windows partitions shall run `cargo nextest run --archive-file ... --partition hash:M/16` from the one archive, with no measured data; `scripts/windows-partitions.py`, `scripts/windows-test-times.json`, the drift check, its limits and the measure and refresh paths shall be removed with their tests and test-config entries; evidence: the diff, and `rg` showing no remaining reader of the removed files.
- AC-2 Every test the archive lists shall run in exactly one partition: the journeys job shall compare the union of the partitions' JUnit reports with the archive listing, and shall name a partition without a report as not finished; evidence: unit tests for a missing test, a duplicate and a missing report, and the hosted run's summary.
- AC-3 The `windows` verdict shall be computed from the Windows jobs' own results, not from a hand-written tuple: it passes only when every job the tier requires succeeded and every skipped job is one the tier declares skipped, and on failure it names each job that is not green with its result; `scripts/ci-reuse.py` shall still refuse a reduced-tier run as full evidence; evidence: tests for a red checks job (named as checks, not as the tier), an undeclared skip, a cancelled partition, and both tiers passing.
- AC-4 A pull request into an integration line shall run the full Windows tier when its range touches `crates/**`, `Cargo.toml`, `Cargo.lock`, `.config/nextest.toml`, `.github/workflows/codeflow-ci.yml` or the scripts the Windows jobs run, and shall also run it when the range or its file list cannot be read (fail closed); any other such pull request runs the reduced tier; pushes, scheduled and manual runs and pull requests into main keep the full tier; evidence: a test per case including the unreadable diff, and one hosted run of each tier.
- AC-5 The tier choice shall be read from the pull request's base and head commits as GitHub gives them, never from a label, title or file in the head that the author controls; evidence: the workflow step and a test that a head-side file cannot select the reduced tier.
- AC-6 `profile.codeflow` in `.config/nextest.toml` shall set `slow-timeout = { period = "120s", terminate-after = 5 }`, so a test running past 10 minutes is ended and reported as a TIMEOUT in its partition's JUnit report while the partition's other results are kept; the bound is at least twice the longest measured test (263 s at 9066afb72, about 450 s on a runner 1.7 times slower); evidence: the config, a local nextest run of a sleeping fixture under a short override that shows TIMEOUT in the report, and the longest test time from the landing run.
- AC-7 (journey) A full Windows run of the line at the landing candidate shall pass with all 16 hash partitions, its slowest partition inside 24 minutes, and a reduced-tier pull request that touches only records shall get a green `windows` verdict; evidence: both run ids and the partition summary.
