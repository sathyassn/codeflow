# TSK-1239: Commit standards admits a pull request when its CI run completes, with no polling

## Description

Source: the CI throughput study of 2026-11-02 (`coordination/coordinators/parallel/throughput/`: RECOMMENDATIONS.md, FINDINGS.md, CHECK-codex.md, CHECK-fable.md), cross-checked by Codex GPT-6 Astra and Claude Fable 5.1, and the operator's priority on CI throughput.

The hosted "commit standards" job waits for the pull request's codeflow-ci run by polling, for up to 35 minutes, while it holds a runner slot (`.github/workflows/codeflow-policy.yml:160-185`, and the admit step of `scripts/ci-reuse.py`). TSK-449's closeout names the runner-slot cost and its revisit trigger (`TSK-449.md:134`). The study recommends replacing the poll with trusted admission that starts when the run completes.

Recurrence 2026-11-05: commit standards refused PR 596 (head bb2ad6ca2, run 41988427754 attempt 1, while gates run 41988427189 was queued) and PR 610 (head 072ac5934, run 41987831703 attempt 1, while gates run 41987831075 was queued; earlier also at draft head bcd0168e7, run 41984732559). Each refusal read "run <gates run> for head <sha> is queued; re-run this check once that run completes", and a manual rerun after the gates run completed was needed. Runs: https://github.com/sathyassn/codeflow/actions/runs/41988427754, https://github.com/sathyassn/codeflow/actions/runs/41988427189, https://github.com/sathyassn/codeflow/actions/runs/41987831703, https://github.com/sathyassn/codeflow/actions/runs/41987831075, https://github.com/sathyassn/codeflow/actions/runs/41984732559.

The existing predicate stays: the newest codeflow-ci run at the exact head, pull request and workflow, with the named verdict jobs succeeded (`scripts/ci-reuse.py:182`). The scaffold shipped to consumers has no such poll; it shares only the cancellation behaviour (`assets/base/ci/codeflow-policy.yml:51`, and it ends at :241), so this task adds no admission mechanism to the scaffold. Non-goals: reuse of hosted verdicts at landing (TSK-359), the cache of the target build (TSK-1240) and any change to the verdict jobs' names.

## Outcome

After this merges, a pull request is admitted by the hosted policy check as soon as its CI run completes, with no runner held while waiting, and a missing, cancelled, failed or wrongly skipped run is still refused.

## Findings

The repository policy workflow builds the trusted target source, fetches PR head only as git data, reads current body into a temp file, runs codeflow ci and ids checks, then invokes ci-reuse.py admit with --wait 2100. admit selects the newest run by run_number, run_attempt and id among exact-head pull_request runs of the named workflow associated with that PR. It requires overall success and named verdict successes. Absent/pending runs sleep in 30-second intervals; other failures refuse immediately. The final PR read compares head, base ref and body digest. Relevant source: .github/workflows/codeflow-policy.yml and scripts/ci-reuse.py admit/admit_main.

TSK-449 closeout line 134 records an upper bound of 35 minutes per ready head. Live sample of the newest 100 completed policy PR runs, inspected via gh api, yielded these long runs (workflow duration includes queuing, so job timestamps are used for runner cost):

- https://github.com/sathyassn/codeflow/actions/runs/41566481011/job/125689179170 : job 02:48:08 to 03:25:42 UTC on 2026-11-03 = 37m34s runner occupancy; admission step 02:50:59 to 03:25:40 = 34m41s, failure.
- https://github.com/sathyassn/codeflow/actions/runs/41565939162/job/125687369553 : job 02:41:38 to 03:19:12 = 37m34s occupancy; admission 02:44:34 to 03:19:09 = 34m35s, failure.

These are the longest workflow-duration samples queried, not an all-history maximum. Hosted success https://github.com/sathyassn/codeflow/actions/runs/40112371841 is TSK-449 prior evidence, not evidence for this task.

Trigger comparison, from https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows :

- workflow_run completed: appropriate automatic completion event, including failed conclusions and reruns. Payload provides run id, attempt, head SHA and PR associations. Workflow must be on default branch; its GITHUB_SHA/ref is default branch, so its ordinary job check alone cannot admit the PR head. PR-controlled workflow execution/results remain untrusted and must be read from authenticated API records, never artifacts or executable payload content.
- workflow_run requested/in_progress: not completion; requested does not fire on reruns. Not sufficient.
- check_run/check_suite completed: GitHub excludes events originating from GitHub Actions to prevent recursion. Not a viable replacement here.
- status: reports commit status activity rather than the completion/attempt identity of this Actions workflow. Insufficient as an authority.
- repository_dispatch/workflow_dispatch: require an explicit dispatcher, add permissions and payload validation, and are not automatic completion notification by themselves. No reason to choose over workflow_run.
- pull_request_target events: needed for current body/readiness/retarget changes but do not signal CI completion. Retain short nonwaiting checks; they cannot alone complete pending admission later.

Body edits do not launch codeflow-ci (its types exclude edited); admission must read current body and repeat final digest check without cancelling any prior run. A rerun retains run id and increments attempt: query latest attempt and recheck identity after jobs, so older completion cannot admit while a newer attempt is pending/failed. Retarget must compare the run-associated base ref with the PR current base and validate current trusted base source; a prior success on a different target cannot admit. A new head rejects a stale completion.

Security boundary for the proposed workflow patch: workflow_run checks attach to default SHA. Explicit exact-head check publication requires narrowly scoped checks:write on trusted code, or an alternative dispatch mechanism that preserves correct check identity. Keep the existing required context and avoid an earlier failed duplicate check masking the later successful verdict. Do not silently broaden the token or claim this point is already settled.

## Publisher decision and local implementation

The operator directed this session to apply the settled decision in
`/private/tmp/claude/p4f-1239-publisher.md` on 2026-11-03. The decision permits
only the separate publisher to hold contents:read and checks:write. The workflow
default is permissions:{}, and build and validation tokens remain read-only.
The repository workflow was editable; no guard refusal occurred, so no
operator application patch is needed.

| Part | Threat closed | Local implementation |
|---|---|---|
| Default-branch scripts | PR code acquiring the check-writing token | Both helper scripts come from github.workflow_sha; the publisher checks out only that trusted commit, with persisted credentials disabled. |
| Read-only validation | A build or PR body gaining write authority | The build checks out the current target SHA and fetches the PR head only as git data. The body is a temp file; only its digest crosses the job boundary. |
| Exact-head publisher | A success on another PR, head, target or attempt admitting this PR | The publisher independently reads public API records, matches the event identity and newest attempt, and repeats current PR and run reads before its write. |
| Check initialization | An initial metadata-read error preserving an older success | The publisher creates a failing check at the native event head before API reads. It can promote only that newly returned id after current API proof. |
| No artifacts | A PR artifact supplying executable code or a fabricated verdict | No artifact is downloaded or interpreted; the API supplies run and attempt job records. |
| Per-PR queue | A body edit cancelling or replacing a check | PR and completion events share a non-cancelling queue:max group. No polling step remains. |

This follows GitHub's split between unprivileged work and a trusted completion
workflow. Here the publisher reads public metadata without authentication so
its write token needs no Actions or pull-request read scope. Public API rate
limits can refuse admission; they never grant success. The writer makes no
blind retry of a POST with an uncertain outcome.

The consumer scaffold gains no admission mechanism, as AC-5 requires. Its
only change is the empty workflow-level permission default; its existing
policy job retains explicit read permissions. The baseline and manifest hash
follow. This shipped template change has patch release impact; the repository
admission mechanism itself does not ship to consumers.

## Design conflict

A native job concludes when its runner ends, so `trusted: commit standards` cannot stay unfinished without holding a runner. The check must be written through the Checks API and concluded on CI completion. ADR-0091 assigns that to Mode A: a dedicated App creates `authority: commit standards` in progress and concludes it (TSK-1177, TSK-1348, both todo). In Mode B, TSK-1177 AC-1 makes the native job fail closed on any other check run of a trusted name, so a `GITHUB_TOKEN` publisher under that name, which this branch's 2026-11-03 publisher decision used, contradicts the recorded design.
