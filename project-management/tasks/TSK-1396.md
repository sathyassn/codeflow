# TSK-1396: Projects choose whether branches must be up to date, or use a merge queue

## Description

ADR-0081 made "require branches to be up to date before merging" part of the
protection CodeFlow ships. At the line's b85d30681, `codeflow remote protect`
always writes strict required checks (`crates/codeflow-core/src/remote.rs:358`,
`:369`), and `codeflow doctor --check remote-perimeter` warns whenever the
live rules are not strict (`crates/codeflow-core/src/doctor/remote_perimeter.rs:599`,
`:641`, `:871`). No policy key lets a project choose otherwise
(`crates/codeflow-core/src/hooks/policy_schema.rs` has none), so a project
that turns the setting off on its host gets a doctor warning that never
clears. No shipped workflow triggers on `merge_group`, and ADR-0091 says merge
queues are not covered until it is wired (`ADR-0091` line 224).

The operator's direction (relayed by the Director, 2026-11-08): the strict
rule stays on by default, projects can opt out, and a merge queue is the
alternative where the host offers one. This task adds the policy key, makes
`remote protect` and doctor honour it, wires `merge_group` into the shipped
CI and policy workflows, and records the decision in an ADR that amends
ADR-0081. Non-goals: changing this repository's own `main` rules, which stay
the operator's, and merge queues on hosts other than GitHub beyond a refusal
with the reason.

## Outcome

After this merges, a project can keep the strict up-to-date rule, turn it
off with a stated reason and no standing doctor warning, or use a merge
queue where its host supports one, with CodeFlow's checks reporting for
queue entries.

## Acceptance Criteria

- AC-1 A policy key (for example `git.require_up_to_date`) shall take `true` (the default, also when absent), `false` or `merge_queue`; `codeflow remote protect` and `codeflow doctor --check remote-perimeter` shall honour it, and with `false` or `merge_queue` doctor shall not warn that the rules are not strict and shall say why. Only the committed value relaxes the rule: a working-tree value that differs from HEAD, and any environment value, shall be ignored or refused, never used to relax it; evidence: schema and policy unit tests, remote protect tests for each value, doctor tests for each value with strict and non-strict live rules, and a test with the working tree set to `false` while HEAD has the key absent or `true`, in which remote protect still writes strict checks and doctor still warns.
- AC-2 The shipped CI and policy workflows, and this repository's copies, shall run every required job for a merge-queue entry, never skipped: the policy job still judges only from the default-branch authority with the queue commit treated as data, the installed release stays the base pin and never comes from the queue commit, and each workflow's concurrency key tells queue entries apart; evidence: workflow template tests for each of those properties on a `merge_group` event, and a hosted queue run where the host supports one, else that run named as not verified.
- AC-3 With `merge_queue`, `codeflow remote protect` shall add the host's merge-queue rule where the host and plan support it, and otherwise refuse with the reason (for example a user-owned GitHub repository); evidence: remote protect tests for a supported host and for each refusal.
- AC-4 The docs shall state the cost of each setting and that a merge queue on GitHub needs an organization-owned repository; evidence: the `docs/policy-reference.md` and adopter docs diff.
- AC-5 An ADR shall amend ADR-0081 with the opt-out and the merge-queue route; evidence: the new ADR and ADR-0081's amended status line.
- AC-6 (journey) With the installed build of this change in a scratch project whose HEAD commits `git.require_up_to_date: "merge_queue"`, `codeflow update` shall install CI and policy workflows that run for a `merge_group` event, and the installed policy workflow shall carry the separate `trusted: merge queue admission` job, judged from git data only, which `codeflow remote protect` requires only together with the merge queue rule; `codeflow doctor --check remote-perimeter` shall name the merge-queue choice; evidence: the scratch-project outputs and the installed workflow diff, with the host-side queue run named as not verified where the host has no queue. ## Findings

Built first on the EPC-022 line (branch tip `cc04d38542`, from
`5405cdb1b8`), then ported onto `main` at `5565469053` for EPC-057 on
branch `task/TSK-1352-TSK-1396-workflows-once-per-epic-and-merge-queue`,
which TSK-1352 continues. ADR-0100 keeps the number and uid the registry
issued for this decision on 2026-11-08.

Before this change `remote protect` always wrote strict checks and doctor
warned whenever the live rules were not strict, with no policy key to
choose otherwise.

- **AC-1, the policy key.** `git.require_up_to_date` reads `true`, `false`
  or `"merge_queue"`, strict by default and when absent (`UpToDate` in
  `crates/codeflow-core/src/hooks/policy.rs`, its entry in
  `policy_schema.rs`). Both commands take the value from
  `up_to_date_choice` in `crates/codeflow-core/src/remote.rs`, which
  honours a relaxing value only from the default branch's remote-tracking
  ref; a working-copy value, a local branch, a repository without a remote
  and the environment never relax the rule. Tests:
  `only_the_committed_value_relaxes_the_rule`,
  `a_local_commit_or_no_remote_never_relaxes`,
  `doctor_honours_each_committed_value`,
  `a_working_copy_value_never_quiets_doctor`, and the CLI test
  `a_working_copy_or_environment_value_never_relaxes_the_plan`.
- **AC-2, the workflows.** The shipped CI and policy templates trigger on
  `merge_group`. The policy jobs judge from `merge_group.base_sha`, which
  must be on the default branch, and fetch the queue commit as data. Each
  queue entry has its own concurrency group in the policy workflow. Tests:
  `crates/codeflow-core/tests/merge_group_workflows.rs`, which judges the
  shipped templates always and the installed baseline and this
  repository's copies once they trigger on `merge_group`.
- **AC-3, the queue rule and its refusals.** `merge_queue_rule` and the
  refusals (`queue_refused_offline`: a provider without an adapter,
  `--check-app`; `RepoInfo::queue_refused`: a user-owned or unknown owner;
  `queue_admission_missing`: a default-branch policy workflow without the
  admission job). A refused queue, or one the host refuses on write, keeps
  the strict rule. Tests: `a_queue_is_refused_with_the_reason`,
  `a_host_refusal_writes_the_strict_rule_instead`,
  `the_admission_check_is_required_only_with_the_queue_rule`,
  `a_queue_waits_for_the_admission_check`,
  `the_dry_run_names_the_fallback`.
- **AC-4, the docs.** `docs/policy-reference.md` and `docs/adoption.md`
  state the cost of each value and that GitHub's merge queue needs an
  organization-owned repository.
- **AC-5, the ADR.** ADR-0100 amends ADR-0081, and ADR-0081's status line
  names the amendment.

### Port onto main

Main had moved on since the line build: it has none of EPC-022's line
features (adopt, scope, prepared writes), names the verdict `commit
standards` without a prefix with an explicit `TRUSTED_VERDICTS` list
(TSK-1368), and has the `authority` job, the producer refusal step and a
token-carrying private fetch (TSK-1177, TSK-1175). Each conflict was
resolved to main's code plus this task's intent:

- `remote.rs`: the queue fallback lives in `apply_owned`, split into
  `owned_body` and `send_owned`, since main has no prepared-write path;
  `owned_rulesets` returns a result per ruleset as main's `apply` reads
  it; no adopt or scope code was carried.
- `trusted: merge queue admission` joins `TRUSTED_VERDICTS`, so the
  rulesets, doctor and the refusal step treat it by the list, and
  `planned_checks` holds it out of B and C except beside the queue rule.
- The policy template keeps main's verdict job, authority job and token
  fetch. The admission job takes main's verdict-job shape: no credential
  left in the checkout, the token fetch, the producer refusal and a last
  read of the head and base branch (no body), each followed by the
  checkout assertion. The authority job also needs it and, in Mode A,
  concludes `authority: merge queue admission`, which no ruleset requires.
- The producer refusal reads the event: on `merge_group` a check run
  counts only when a `merge_group` run of the policy workflow's path made
  it, and on a pull request only a `pull_request_target` run; any other
  event fails the step. The authority job's copy keeps the pull request
  head, since it never runs for a queue entry.
- Tests follow: `merge_group_workflows` still forbids any queue-state
  read in the admission job and any host read or token in its judging
  step, but no longer forbids the token fetch, refusal and last read the
  verdict-job shape adds; `authority_job` expects the queue form of the
  refusal only in a copy that triggers on `merge_group`, and gains
  `a_check_run_counts_only_from_the_runs_own_event`.
- `scripts/gate-parity.py` keeps main's release condition and adds the
  queue form; docs keep main's doctor count and wording, with the queue
  sentences added.

For the acceptance: `manifest_consistency` and
`authority_job::the_baseline_is_the_template` fail until an operator
resync writes the shipped workflows into `.codeflow/.baseline/` and the
manifest, which workers may not write; this repository's own
`.github/workflows/` copies take a second operator patch.

Not verified:
- a hosted merge queue run, because this repository is user-owned and
  GitHub offers it no merge queue;
- the tests above after the resync;
- AC-6, the scratch-project journey, owed on the installed build.
