# TSK-329: The model evaluation gate target waits for the binary it runs

## Description

The `model-eval-kit` gate target can start before the binary it runs exists,
and its result then depends on scheduling. In the full gate on candidate
dd1188c5e (batch 2, gate run 7ba19750-cf8d-4043-a25e-a89ff2299411 under
`/Users/sathya/.codeflow/gate-runs/7a134ea9c2ea8c39/`), `model-eval-kit`
failed with a `FileNotFoundError` for `target/release/codeflow` in
`test_closeout_inventory_matches_real_local_worktrees`
(`evals/model-artifacts/test_eval_kit.py:8513`, calling
`eval_kit.configure_closeout_inventory`, which runs the binary at
`assets/base/agents/skills/cf-evaluate-model/scripts/eval_kit.py:3043`).
`release-automation` passed in the same run. The test builds the path from
`CARGO_TARGET_DIR` or `target`, plus `release/codeflow`
(`test_eval_kit.py:8509`). `.codeflow/test-config.json` declares
`model-eval-kit` with no `requires`, and it runs in both the essential and
the full mode (`.codeflow/test-config.json:282`), so nothing orders it after
a producer of that binary in either mode. It passed in batch 1 and in a
targeted rerun only because a binary was already there.

No target in the gate is shown to build `target/release/codeflow`. The
archived run gives `release-automation` the debug binary
(`CODEFLOW_BIN` ending in `target/debug/codeflow`, from the declared
`codeflow-bin` target, `.codeflow/test-config.json:114`;
`scripts/test_release.py:33` and its fallback build at `:39` to `:51`), so
the pass of `release-automation` proves neither that the release binary
existed nor an ordering. The release-profile test targets are full-only
(`read-benchmark` at `:460`, `prose-exhaustive` at `:476`), and
`present-binary-delta` builds under its own `target/binary-delta-*`
directory. The inventory test states no release-profile requirement. The
builder chooses the producer path and records why:

- use the existing `codeflow-bin` contract, which the archived manifest
  already supplies to `model-eval-kit` as `CODEFLOW_BIN`, add
  `codeflow-bin` to the target's `requires`, and have the test take its
  binary from `CODEFLOW_BIN` before any path under `target/`; or
- if a release-profile binary is necessary, say why, and name an explicit
  producer target, declared in `requires`, that is available in both modes.
  A test that builds its own binary is not an option, because the producer
  must be a declared prerequisite that runs before the consumer.

Adding `requires: [release-automation]` is not a repair, because that target
does not build the release binary.

The outcome is that `model-eval-kit` succeeds in each supported gate mode,
with only its declared prerequisites, from an empty artifact directory,
whatever order the scheduler picks. Non-goals: changing what the evaluation
kit tests, or switching the gate to serial execution.

## Acceptance Criteria

- AC-1 The task shall state the declared producer target of the binary
  that `model-eval-kit` runs and how the test resolves that binary, shall
  show that the producer is declared for both the essential and the full
  mode, and shall not rely
  on `release-automation` or any other target that does not produce it;
  evidence: the diff, and a sentence per mode naming the producer.
  (serves EPC-022 AC-26)
- AC-2 In each supported gate mode (essential and full), `model-eval-kit`
  shall succeed with its declared prerequisites from an isolated empty
  artifact directory (a fresh `CARGO_TARGET_DIR` that holds no
  `release/codeflow` and no `debug/codeflow`); evidence: one bounded run
  of the target with its prerequisites per mode, showing the producer ran
  first and the target passed. A run that passes only because a binary was
  already present does not count. (serves EPC-022 AC-26)
- AC-3 A deterministic check shall fail when a gate target runs a binary
  under `target/` that none of its declared prerequisites produces, and it
  shall fail on the current `model-eval-kit` configuration; evidence: the
  check failing before the change and passing after. (serves EPC-022 AC-26)
- AC-4 When `model-eval-kit` is run directly outside the gate with no
  binary present, it shall fail with a message that names the missing
  prerequisite and how to produce it, and not with `FileNotFoundError`;
  evidence: a test of that direct invocation. This criterion is the only
  place a missing-binary failure is accepted; it does not stand in for AC-2.
- AC-5 With the binary absent at the start, a bounded run of
  `model-eval-kit` and its prerequisites that requests the consumer first,
  or delays the producer's eligibility, shall still run the producer before
  the consumer and pass, in each mode, with dependency enforcement kept and
  no execution of the consumer before a declared prerequisite (journey);
  evidence: the run's schedule log for each mode, with the forcing method
  stated. No whole-workspace gate is needed per variation; the landing
  candidate's own full gate is the final proof. (serves EPC-022 AC-26)
