# TSK-1320: A reviewed completion survives a landed planning move of its epic

## Description

`work.acceptance_binding` refuses a reviewed task once its branch merges a line where a landed planning PR changed only the task's epic. The check compares the record's reviewed part at the reviewed commit with the record at the head (`crates/codeflow-core/src/workgraph/acceptance.rs:1418-1436`, `reviewed_part`), so any later change outside status and Closeout reads as unreviewed work. The regroup commit cc62e9381 changed `epic_id` in 221 task records and nothing else in most of them. Since then PRs 523 (TSK-1101), 535 (TSK-1255) and 525 (TSK-1162) refuse after merging line tip 9c5f665cf locally (the refused pushes are recorded in coord/capabilities' stream3 rework note), and each needs a fresh whole-unit review only because of that edit. PR 518 (TSK-1039) also refuses, but its record has reshuffled blocks and an unlanded amendment, so it must keep refusing.

This task admits that one shape and keeps every other change refused. The admitted edit is a change to `epic_id`, and lines added outside the front matter, the acceptance criteria, the acceptance block, the Deliverables and the Closeout. It is admitted only where the chain from the reviewed commit to the head stacks (clean re-merges of a target tip and own commits that change only status and Closeout, `acceptance.rs:1430`), so every change to the reviewed part came from the merged target commits; the refusal and the fixture name the first-parent commit of the target that changed the record, read from the target's contents. The regroup's edit, cc62e9381, reached the line through merge 5b42362db (PR 562). The task's landing line must be the same before and after: its `integration_target`, and the line its new epic declares (`parent_line`). The check reads `parent_line` from the epic record at the target itself; the field's parsing landed with TSK-1286's product change in PR 572 (`crates/codeflow-core/src/workgraph/lifecycle.rs:56-58`), so this task needs no further code from TSK-1286. Non-goals: TSK-1316 (a planning merge that carries a completed record into another line's check), and record edits a task branch makes itself, which stay reviewed content.

Threat kept closed: a builder or a branch moving a reviewed task, or changing what its completion attests, without a fresh review. Admission depends only on one commit on the first-parent line of a trusted target tip; the check proves where that commit is, not that a reviewed planning PR made it. On a task PR the trusted tip is the base the run pins. On an amendable range (a line PR into `main`, a push to the line, a root-branch range or a planning amendment) the range head is also trusted for a task whose `integration_target` is the judged branch, so that head is the move's authority there: at a line PR into `main` the operator reviews and merges it. Cost of not fixing: a fresh whole-unit review for every reviewed, unlanded task that the regroup touched, and the same again after any later planning move of epics.

## Outcome

After this merges, a builder whose reviewed task was moved to another epic by a landed planning PR can merge the line and keep the completion, without a fresh review, while every change to what the completion attests still refuses.

## Deliverables

- the binding change and its fixtures: `crates/codeflow-core/src/workgraph/acceptance.rs` and its tests
- the rule text: SPC-013 R-60 and `docs/capabilities.md` CAP-010, where they describe what a reviewed record may change

## Findings

Research, 2026-11-04, at line tip cf8f5e1e2.

- Where it refuses: `reviewed_span_problem` (`acceptance.rs:1427-1436`). When the chain from the reviewed commit to the head stacks (`Stacked::Clean`), it compares `reviewed_part` at the reviewed commit with the completed record and refuses on any difference. A clean re-merge of the line after review that brings the regroup's edit therefore refuses.
- The regroup's shape, read from cc62e9381 for TSK-1101, TSK-1162, TSK-1255 and TSK-1039: the `epic_id:` front matter line changes from EPC-022 to a feature epic, and one `- Regrouped 2026-11-03 ...` bullet is added at the end of the Execution contract section. Nothing else changes. The edit reached the line's first-parent chain at merge 5b42362db (PR 562); its first parent cf9a0c9ea holds the old record. EPC-027 and EPC-034 declare `parent_line: integration/EPC-022-the-3-2-0-milestone-fixes` at the line tip.
- The epic facts reader exists: `work_start::epic_record_at_revision` reads an epic record at a revision, and `work_start::line_membership` decides whether an epic's tasks land on a line (the line's own epic, or one hop through `parent_line`). The change reuses both.

Design.

- Only inside `Stacked::Clean`, so the task branch's own commits after review still change only status and Closeout, and every merge is a clean re-merge of a run target tip (the existing rule).
- The record difference must have the admitted shape, compared as parsed and by bytes: front matter lines byte-equal except the single `epic_id:` line, and the parsed front matter equal without `epic_id`; the old body a subsequence of the new body, with each matched line keeping its parsed line kind; every added line plain text (not a heading, fence, HTML block or comment) and outside the Acceptance Criteria and Deliverables sections; those two sections byte-equal and the parsed criteria equal. Both epics must be named; null or missing refuses.
- Provenance: walk the first-parent chain of each run target tip (`StackingTips`), back to the first commit the reviewed commit already contains, and collect each commit the head contains whose record differs from its first parent's. Exactly one such commit must exist. Its own edit must have the admitted shape with status, Closeout and acceptance blocks unchanged, the same old and new epic, and it must add every line the head's record added.
- Landing line: the task's `integration_target` is unchanged (front matter equality), and at that target tip the new epic is the line's own epic or declares it as `parent_line`, read with `line_membership`. Any read error refuses.
- A refusal keeps the existing message start and adds the commit that changed the record, or says no target commit did, and the part that changed.

Why this is the standard fail-closed design: trust is bound to identities a requester cannot forge, the exact commits on the first-parent chain of the tips the run is judged against and the parsed parts of the record at those commits. It never reads a branch name, PR title, commit message or date. Every unreadable commit, blob, record or epic, every ambiguous edit (more than one target commit) and every shape outside the one admitted edit refuses, so the change narrows a refusal only for an edit already on the first-parent line of a trusted target tip; where that tip is an amendable range's own head, that head is the authority, as the Description states.
