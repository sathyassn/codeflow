# TSK-298: The project's records are read by a YAML parser written in safe Rust

## Description

CodeFlow reads and writes the YAML front matter of every record, the id
registry and other project files through `serde_yaml_ng` 0.10 (the workspace
dependency `serde_yaml`, `Cargo.toml:22`, used by `codeflow-core` and
`codeflow-cli`). That crate is built on `unsafe-libyaml`, whose repository is
archived; OSV lists it as unmaintained (RUSTSEC-2024-0449) with no fixed
version. TSK-297 keeps the dependency audit passing with a suppression that
expires on 2026-12-31. This task removes the cause: the project's records are
read and written by a maintained YAML parser written in safe Rust, and
`serde_yaml_ng` and `unsafe-libyaml` leave `Cargo.lock`. The task first
compares the candidate parsers on the three things the records need: no
`unsafe`-based C port in the dependency tree, a maintained release line, and
the same parsed values and the same written bytes as today for every record,
template and registry file in this repository and in the scaffold. The
suppression added by TSK-297 is removed here. Non-goals: changing the record
format, the front matter keys or the records' comments and key order.

The change touches the record reader and writer (`workgraph/record_text.rs`,
`workgraph/store.rs`, `workgraph/allocate.rs`, `models/`), `validate/`,
`scaffold/update.rs` and `hooks/landed_policy.rs`, so it is a hotspot with
most of this epic's tasks. It lands after the other code tasks on the line
that touch those files, to limit conflicts; this is a priority, not an edge.

## Deliverables

- the chosen parser, with the comparison and its decision: `docs/decisions/` (an ADR, because it adds a dependency)
- the migrated readers and writers: `crates/codeflow-core/src/`, `crates/codeflow-cli/src/`, and the workspace dependency in `Cargo.toml` and `Cargo.lock`
- the equivalence tests over every record, template and registry file: `crates/codeflow-core/tests/`
- the removed suppression: `osv-scanner.toml`
- release note: `changelog.d/TSK-298.md`

## Acceptance Criteria

- AC-1 `Cargo.lock` shall hold neither `serde_yaml_ng` nor `unsafe-libyaml`, and the chosen parser and every crate it adds shall be written in safe Rust and have a release in the 12 months before the decision. Evidence: `Cargo.lock`, `cargo tree`, and the ADR's comparison. (serves EPC-022 AC-13)
- AC-2 When the migrated build parses every record, template, registry and front matter file in this repository and in the scaffold, it shall produce the same values as the 3.1.1 build. Evidence: a test that runs both parsers over the files and compares, kept as a fixture of the parsed values.
- AC-3 When the migrated build writes a record, the id registry or any other YAML it writes today (a status change, an allocation, a follow-up, a manifest entry), it shall write the same bytes as the 3.1.1 build for the same input, comments and key order included. Evidence: golden tests for each writer.
- AC-4 When a file holds malformed YAML, a duplicate key, deep nesting, an alias expansion or a very large scalar, the build shall refuse it with an error that names the file, within a bounded time and without a crash, as the 3.1.1 build does or more strictly. Evidence: one test per class.
- AC-5 The `osv-scanner.toml` entry for `RUSTSEC-2024-0449` shall be removed, and the dependency audit shall pass without it. Evidence: osv-scanner 2.4.0 on the tree, exit 0.
- AC-6 (journey) When a project created with 3.1.1 runs `codeflow validate --docs`, `task new`, `task status`, `work claim`, `work start` and `ci` with the migrated build, each shall give the same result and the same written files as the 3.1.1 build. Evidence: a scratch project run through both binaries, with the outputs and the tree diffed. (serves EPC-022 AC-13)
