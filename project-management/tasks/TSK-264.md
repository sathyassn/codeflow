# TSK-264: Each pull request carries its changelog entry in its own fragment

## Description

Pending changelog entries move out of the one shared pending section of
`CHANGELOG.md` into one fragment file per pull request under `changelog.d/`
(issue 119, design revision 3). Today every work PR inserts into the same
region of that section, so each landing forces a hand-resolved main merge, an
`Unclean` acceptance stack and a fresh review on every other open PR. Two PRs
that each add a fragment merge cleanly in git and libgit2, so the main merge
each owes after a landing stays a clean re-merge.

`scripts/release.py` gets one reader, `pending_text`, that composes the
fragments into the pending section for every check (`check-pr`,
`check-state`, `preflight`, `sync`, the publishability check). A tree holds
pending entries in one carrier: fragments, or one written pending section.
`sync` stamps from the fragments and never writes the section. A new,
reviewed `assemble` step writes the section and removes the fragments
before publication, and `release-notes` refuses a source that still holds a
fragment. Typed repairs accept fragment paths. `scripts/changelog_split.py`
moves today's pending section into fragments and lets each open PR move its
own entries at the main merge it already owes.

Non-goals: the manifest digests (PR 125, TSK-258), the reopen rule, branch
protection, and any merge driver. No workflow command line changes. The
shipped release-policy guidance and the pull request template stay as they
are: adopters do not run this calculator, and both are managed files whose
hashes PR 125 removes, so this unit leaves `.codeflow/manifest.json` alone.

- AC-1 When two branches each add a distinct fragment, the merge shall be conflict-free and `check-state --structural` on the result shall list both entries and the bumped target; evidence: `git merge-tree --write-tree` exit 0 on two scratch branches and the JSON naming both labels and the version (journey record), plus `FragmentTests` (journey)
- AC-2 When a PR adds one `minor` fragment, `check-pr` shall accept `Impact: minor` and refuse `patch`; when a PR edits a carried entry, it shall assess the edit at the entry's impact; when a PR removes a fragment, it shall require `Withdrawal`; evidence: `FragmentTests`, the fragment variants of `PullRequestTests` and `EntryEditTests`, and the duplicate-label case of `FragmentValidationTests`
- AC-3 If a tree holds two fragments with one label, a `##` or `#` heading, an unknown kind, an entry without a heading, a bad name, a non-`.md` file or a `legacy-group=` marker, then `pending_text` shall refuse naming the file, and `check-pr`, `check-state` and `preflight` shall fail with that message; evidence: `FragmentValidationTests`, one test per rule and each caller asserted once
- AC-4 If a tree holds a fragment and a written pending section, then `check-state` and `check-pr` shall fail naming the fragments and `assemble`; evidence: `FragmentCarrierTests`
- AC-5 When `sync` runs on a fragments-only worktree, it shall stamp the fragment target and write no section; when a written section's body differs from the composed text, it shall refuse; when it matches, it shall stamp; evidence: `FragmentSyncTests`, three tests, which fail on the unchanged `release.py` (the baseline downgrade)
- AC-6 When `assemble` runs, it shall write the section byte-identical to `pending_text`, remove the fragments, be a no-op without fragments, and its PR shall pass `check-pr` with `Impact: none`; evidence: `FragmentPublicationTests` and the journey's assemble step
- AC-7 If a fragment exists at the source ref, then `release-notes` shall fail naming it; evidence: `FragmentPublicationTests` and the journey's negative step
- AC-8 When a typed repair removes one whole fragment, `check-pr` shall accept it as a withdrawal; when it edits a fragment's bytes or impact, it shall refuse; fragment paths shall be exempt from the stamp loop; evidence: `FragmentRepairTests`
- AC-9 While behaviour paths change with no fragment added or edited and no `Impact: none`, the preflight shall warn; with a fragment or `Impact: none` it shall be silent; evidence: `FragmentPreflightTests`
- AC-10 When the migration's fragments are assembled in a scratch worktree, the result shall differ from the parent's `CHANGELOG.md` only in the heading; evidence: the `git diff` output recorded in the PR
- AC-11 When the pull request head, which contains `main`, is checked, `CHANGELOG.md` shall carry no pending section and the `release state` job's command (`python3 scripts/release.py check-state --ref <head>`) shall pass; evidence: its output at the head, and the same job on `main` after the merge
- AC-12 When a branch that added a fragment merges a `main` that landed another fragment, `read_merge` shall report `Clean`; evidence: `acceptance.rs` test `two_fragment_branches_merge_as_their_clean_re_merge` and the journey's merge (journey)
