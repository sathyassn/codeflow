# TSK-1280: Every test runs offline, and none resolves a network host

## Description

Codex seats cannot run the quick gate. Their sandbox blocks a test's DNS lookup of `example.invalid`, and the harness ends the exec (the Director, 06:2x on 2026-11-03, via coord/parallel). The message, seen on three seats (TSK-1256, TSK-1240, TSK-450): `write_stdin failed: Unified exec process failed: Network access to "example.invalid" was blocked: local/private network addresses are blocked by the sandbox policy`.

It happened inside the quick target `contract-scans`, which runs codeflow-core's integration tests (`scripts/contract-scans.py`). The log is `codeflow/.worktrees/tsk-1256/target/task-evidence/scan-fix-quick-own-binary.log`. Outside the sandbox the lookup gets NXDOMAIN and the test passes, so nothing depends on the network: it is a hermeticity defect, and adopters who run tests in a sandbox hit it too.

Likely source, not yet confirmed: `crates/codeflow-core/tests/content_rules.rs:569`, `only_the_recorded_default_branch_judges_and_none_is_guessed`, which sets origin to `https://example.invalid/adopter.git` with no `origin/HEAD`, so the code under test may query the remote. Other `example.invalid` uses in that suite are emails or plain strings. AC-1 confirms or replaces this lead.

Owner: coord/planning (builder to be staffed). Adopter-facing: if production code makes a network call during a local policy judgment, adopters get that call too.

## Outcome

After this merges, a maintainer or adopter can run the quick and full gates in a sandbox with network denied, and no test resolves a network host.

## Deliverables

- the list of network-resolving tests and their call sites: this record's Closeout
- the hermetic tests, and any production fix for a network query in a local judgment: `crates/codeflow-core/` and the other crates the builder confirms
- the gate check that keeps it offline: the test configuration and its script, which the builder confirms
- the release note: `changelog.d/TSK-1280.md`

## Acceptance Criteria

- AC-1 Every test in the quick and full gates that makes a network lookup shall be identified. The suites shall be run with network denied (the Codex cf-builder sandbox, or an equivalent deny), and the tests and their call sites recorded. Evidence: the network-denied run is the fail-before evidence, with the message above and the log path.
- AC-2 Each such test shall become hermetic, through an injected resolver, a local path or `file://` remote, or a loopback-only check. A test shall never be skipped under a sandbox and what it asserts shall never be weakened. If production code queries a remote where the test expected none (for example the default-branch lookup), the record shall say whether that production behavior is intended; if it is not, it shall be fixed here, and adopters get no network call from a local policy judgment. Evidence: the diff per test and the record's statement on production behavior.
- AC-3 A gate check shall keep it that way: the quick and full suites shall run green with network denied on at least one platform in CI or locally, and a new network lookup in a test shall fail that check. Evidence: the green run and a run with a planted lookup that fails.
- AC-4 A changelog entry shall describe the change. Evidence: `changelog.d/TSK-1280.md`.
