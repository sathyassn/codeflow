# TSK-1124: A sync that takes a main task's record unchanged is not a change the line makes

## Description

Source: issue #456 (CodeFlow 3.1.1, by an adopter), read on the line tip
`79eec1783` after a diagnosis found no open task that covers it. TSK-1066
makes a clean sync pass and a hand-edited sync block; neither says what
`ci --branch <line>` does with a `main` task the line has never held and
that `main` reopened.

A sync merges `main` into an integration line. `main` holds a task
(TSK-739 in the issue) that the line has never held. On `main` it was
completed, reopened with one added criterion, and completed again. The
merge carries `main`'s record unchanged: the blob is the same on the
merge and on `main`'s tip. `codeflow ci --branch <line> --base <line tip>
--head <sync merge>` blocks it twice with `work.acceptance_binding`:

- "`refs/remotes/origin/main` (commit ...) records a completion of this
  task, but it is not the target this run is judged against, so its
  criteria stay as they were; a reopened task keeps its criteria once a
  completion of it has landed";
- "a reopened task keeps its criteria as the anchored target has them;
  change them in the epic's batched amendment, a planning pull request
  on the target".

The pre-push check on the same push passed: it judges from `main`'s tip,
where the record is current. In the issue's table the task is absent at
the line tip, complete (after the reopen and an added criterion) at
`main`'s tip, and the same blob at the sync merge.

Sites, read on the line tip. Both quoted findings come from the
binding of T's completion, `bind_completion_with_amendment`, under
`work.acceptance_binding`:

- The first sentence: `recovered_completion` (`acceptance.rs:2124`)
  finds main's earlier completion, because `reopened_in_range`
  (`lifecycle.rs:2388-2416`) sees main's reopen commit in the sync's
  range. `judge_reopened` (`acceptance.rs:2257`, tips at
  `:2308-2342`) does not count the default-branch tip as a criteria
  base, so the landing is
  `Landing::Unjudged` (text at `landing.rs:128-130`), and the refusal at
  `acceptance.rs:2176-2179` is pushed under `work.acceptance_binding` at
  `acceptance.rs:657`. That refusal keeps the earlier criteria.
- The second sentence: `reopen_problems` (`lifecycle.rs:1190`) compares
  those kept criteria with the recompleted record and returns
  `REOPENED_CRITERIA` (`acceptance.rs:3679`), pushed under
  `work.acceptance_binding` at `acceptance.rs:658-663`.
- The same text is also raised as `work.criteria_frozen` by
  `reopened_criteria` (`acceptance.rs:3656-3666`), but only when the
  line's base, or its history through `RecordStore::recovered`, holds
  an older complete record of T (`acceptance.rs:3768-3786`). A line that
  never held T gets `Ok(None)` there and raises nothing. A line that
  synced main's first completion earlier does hold it, so that shape
  can raise `work.criteria_frozen` as well.

Pre-push passes the default-branch tip as `--policy-from` (`ci.rs:108-113`,
`ci.rs:429-447`), which makes that tip a judged criteria base, so
neither finding fires there; AC-1 confirms this.

Design (Fable reviews it before the build; it replaces the first
design, a byte comparison with the default-branch tip, for the reason
Findings gives): a record whose exact contents the range imports from a
verified home landing (`acceptance::imported_records`: the source is a
default target or verified epic line, holds the record on its
first-parent chain, and shares that landing with the head) carries
criteria its home already judged. Two places still judge it against the
line's own copy:

- The introduction trace (`landing.rs` `trace`) counts a sync merge as
  introducing the version it carries whenever the line's parent held no
  record of the task. The fix: a commit introduces a version only when no
  parent holds it, a parent holds another version, or it has no parent.
- The records range check (`lifecycle.rs` `judge_change`) compares the
  line's base record with the head record and raises
  `REOPENED_CRITERIA`. The fix: for an imported record, and only for it,
  that one comparison is skipped.

The authority binds to the import proof, never to a name, flag or
remote-tracking ref. A record the head changes by even one byte is not
imported and is judged as the line's change. Every other check still
applies, including the status steps a sync carries, which stay judged one
by one as TSK-1036 AC-7 requires, and the record's binding, review and
landing.

The issue's related report (a completed task's own branch cannot push its
completion, `work.stable_planning_anchor`) is the family of #454 and is
not part of this task. TSK-350 AC-13 covers the `work.criteria_frozen`
shape of #454; the refusal to start from a complete record is still
uncovered, and the builder names what it needs in Findings for the
primary (AC-1).

Non-goals: the sync-merge hand-edit check (TSK-1066), the status steps a
sync carries (TSK-1036), the #454 pre-push family.

## Findings

Investigated on the line tip `92149edc8` with the fixtures in
`crates/codeflow-cli/tests/acceptance_cli/main_reopens.rs`. Each shape
runs in three forms: `ci --branch <line>`, the pre-push form
(`--policy-from` and `--commits-from` at `main`'s tip) and the pull
request form of a task branch that merged `main` (`--into <line>`).
On `main`, TSK-001 is completed in its pull request and then reopened,
amended with a third criterion, fixed and completed again, each through
its own pull request that passes `codeflow ci` on `main`.

| Shape | Before the change | After |
|---|---|---|
| Never held: planned on `main` after the cut (issue #456) | passes, all forms | passes |
| Synced first: the line merged `main`'s first completion | blocks, all forms | passes |
| Held at the cut: planned before the line was cut | passes, all forms | passes |
| Relabeled in its pull request: as held at the cut, completed, relabeled and completed again in one pull request (issue #464's history) | passes, all forms | passes |

- **Issue #456 already passes on the line.** Neither quoted
  `work.acceptance_binding` sentence fires for the never-held shape in
  any form. The import proof already skips an imported record in the
  acceptance binding and the `work.criteria_frozen` check. I did not
  bisect which landing fixed it.
- **Issue #464 already passes on the line** in both shapes that model
  its history. Its adopter repository was not available, so its exact
  history is modeled, not replayed.
- **The synced-first shape still blocks, and the same way in all three
  forms**, so pre-push and `ci --branch` do not read different
  authorities here. The two findings are:
  - `work.import_authority`: "accepted criteria cannot be resolved: the
    judged points hold different versions of this task, and none of them
    is newer than the others". The cause is `trace` in `landing.rs`. The
    line's first sync merge held version A while its line parent held no
    record, so it counted as an introduction of A. That merge is not in
    `main`'s history, so A and `main`'s re-completed version B could not
    be ordered.
  - `work.records`: "a reopened task keeps its criteria as the anchored
    target has them". The cause is `judge_change` in `lifecycle.rs`,
    whose `transition_problems` and `reopen_problems` compare the line's
    base record (A) with the head's (B) and return `REOPENED_CRITERIA`.
- **The first design is replaced.** A byte comparison with the
  default-branch tip would bind to whichever commit a ref names at the
  run. The import proof already binds an imported record to a verified
  home landing on the source's first-parent chain, and it is what the
  acceptance binding uses for the never-held shape, so the fix reuses it.
- **Status steps are unchanged.** `judge_change` still applies every
  transition and reopen problem except `REOPENED_CRITERIA` for an
  imported record, and the status steps a sync carries are judged as
  before (TSK-1036).
- **The record-only route of the 05:55 comment on #464 stays refused,
  correctly.** A line commit that writes `main`'s record blob is not a
  merge of `main`, so the record is not imported. It blocks with "reviewed
  commit ... is not the head or an ancestor of it" and "the archived
  acceptance block reviewed at ... is not a completion this range made",
  because the reviewed code is not in the head. With the sync passing,
  the sync is the route, and this record-only copy is kept as a negative
  fixture (AC-5).
- **What the #454 family needs, for the primary to file.** Both reports
  are pre-push on a task branch whose task targets a line. Neither is
  covered by this task, and only TSK-350 AC-13 (`work.criteria_frozen`)
  touches it.
  - `push_set.rs` `judged_by` takes the destination's default branch as
    the authority whatever the pushed record's `integration_target`
    says. A task that a line's planning amendment moved off `main` then
    meets two unordered versions (#454).
  - Pushing an already landed completion to the task's own branch runs
    with `--base` equal to `--head`, an empty range, so the record is
    judged as a start and refused by `work.stable_planning_anchor`
    ("cannot start from status 'complete'", #456's related report).
  - Need: judge a task branch's push against the line its record targets
    when the destination advertises that line, and treat an empty range
    whose head the line already contains as no change. Not run here; read
    from the issues and the source.

## Outcome

After this merges, a maintainer who syncs `main` into an integration line passes `codeflow ci --branch <line>` when `main` reopened and recompleted a task the line has never held, and a sync that edits that record by even one byte still blocks.
