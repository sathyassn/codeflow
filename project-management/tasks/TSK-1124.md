# TSK-1124: A sync that takes a main task's record unchanged is not a change the line makes

## Description

Source: issue #456 (CodeFlow 3.1.1, by an adopter), read on the line tip
`79eec1783` after a diagnosis found no open task that covers it. TSK-1066
makes a clean sync pass and a hand-edited sync block; neither says what
`ci --branch <line>` does with a `main` task the line has never held and
that `main` reopened.

A sync merges `main` into an integration line. `main` holds a task
(TSK-739 in the issue) that the line has never held. On `main` it was
completed, reopened with one added criterion, and completed again. The
merge carries `main`'s record unchanged: the blob is the same on the
merge and on `main`'s tip. `codeflow ci --branch <line> --base <line tip>
--head <sync merge>` blocks it twice with `work.acceptance_binding`:

- "`refs/remotes/origin/main` (commit ...) records a completion of this
  task, but it is not the target this run is judged against, so its
  criteria stay as they were; a reopened task keeps its criteria once a
  completion of it has landed";
- "a reopened task keeps its criteria as the anchored target has them;
  change them in the epic's batched amendment, a planning pull request
  on the target".

The pre-push check on the same push passed: it judges from `main`'s tip,
where the record is current. In the issue's table the task is absent at
the line tip, complete (after the reopen and an added criterion) at
`main`'s tip, and the same blob at the sync merge.

Sites, read on the line tip:

- `crates/codeflow-core/src/workgraph/landing.rs:129`
  (`TaskJudgement::landing_unknown`, the `Landing::Unjudged` text) and
  `crates/codeflow-core/src/workgraph/acceptance.rs:2177` (the refusal it
  feeds when the criteria differ from the authority).
- `acceptance.rs:3656` `reopened_criteria`, `:3699` `reopened_ids` and
  `reopened_judged` (below them): a task the base no longer holds is
  judged against the newest version in its history
  (`RecordStore::recovered`), and a recompleted record whose criteria
  signature differs from that version counts as a reopen with changed
  criteria. For a sync, that version is `main`'s own earlier completion,
  so `main`'s reopen is read as the line's.
- `acceptance.rs:3679` `REOPENED_CRITERIA`, the second message.

Design (Fable reviews it before the build): a record that the head holds
byte for byte as the default branch tip holds it is `main`'s own
content, whose history `main` already judged. `ci --branch <line>` shall
judge it as `main`'s content, as the pre-push check does, or skip a
record whose blob at `--head` equals the default branch tip's blob. The
choice binds to the default-branch commit and to blob equality, never to
a name or a flag, and a record that differs from `main`'s tip at the
head, by even one byte, is judged as the line's change.

The issue's related report (a completed task's own branch cannot push its
completion, `work.stable_planning_anchor`) is the family of #454 and is
not part of this task: no open task covers #454 either, and the builder
names what it needs in Findings for the primary (AC-1).

Non-goals: the sync-merge hand-edit check (TSK-1066), the status steps a
sync carries (TSK-1036), the #454 pre-push family.

## Outcome

After this merges, a maintainer who syncs `main` into an integration line passes `codeflow ci --branch <line>` when `main` reopened and recompleted a task the line has never held, and a sync that edits that record by even one byte still blocks.

## Acceptance Criteria

- AC-1 Before any change, the builder shall record in this record which code path raises each of the issue's two findings for the fixture, whether pre-push and `ci --branch` read different criteria authorities and why, which of the two designs (judge the record as `main`'s content, or skip a record whose blob equals the default branch tip's) the code supports, and what the #454 family needs, for the primary to file; evidence: the Findings section, committed before the first code change.
- AC-2 Given a line that never held task T, a `main` that completed T, reopened it with one added criterion and completed it again, and a sync merge carrying `main`'s record unchanged (the same blob as `main`'s tip), `codeflow ci --branch <line> --base <line tip> --head <sync merge>` shall raise no `work.acceptance_binding` finding for T; evidence: a CLI fixture of the issue's table, blocking before the change with both quoted messages and passing after. (serves EPC-022 AC-198)
- AC-3 The same sync shall get the same verdict through the pre-push check and through `codeflow ci` in the pull request form; evidence: the fixture through each form, passing in all three after the change. (serves EPC-022 AC-198)
- AC-4 A sync that edits T's record, criteria or acceptance block by even one byte against `main`'s tip shall still block, naming T and the merge, and a line that reopens and changes the criteria of a task it holds shall still be refused; evidence: negative fixtures for a one-byte edit, a criterion added in the merge and a line-side reopen, passing before and after.
- AC-5 When the default branch tip cannot be read at the run, or the record's blob cannot be compared, the sync shall be refused with the cause, never accepted; evidence: a fixture with the remote-tracking ref missing, refused before and after.
- AC-6 (journey) With the built binary in a scratch repository, the AC-2 sync shall pass in the three forms and the AC-4 one-byte edit shall block; evidence: the journey output.
