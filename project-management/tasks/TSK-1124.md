# TSK-1124: A sync that takes a main task's record unchanged is not a change the line makes

## Description

Source: issue #456 (CodeFlow 3.1.1, by an adopter), read on the line tip
`79eec1783` after a diagnosis found no open task that covers it. TSK-1066
makes a clean sync pass and a hand-edited sync block; neither says what
`ci --branch <line>` does with a `main` task the line has never held and
that `main` reopened.

A sync merges `main` into an integration line. `main` holds a task
(TSK-739 in the issue) that the line has never held. On `main` it was
completed, reopened with one added criterion, and completed again. The
merge carries `main`'s record unchanged: the blob is the same on the
merge and on `main`'s tip. `codeflow ci --branch <line> --base <line tip>
--head <sync merge>` blocks it twice with `work.acceptance_binding`:

- "`refs/remotes/origin/main` (commit ...) records a completion of this
  task, but it is not the target this run is judged against, so its
  criteria stay as they were; a reopened task keeps its criteria once a
  completion of it has landed";
- "a reopened task keeps its criteria as the anchored target has them;
  change them in the epic's batched amendment, a planning pull request
  on the target".

The pre-push check on the same push passed: it judges from `main`'s tip,
where the record is current. In the issue's table the task is absent at
the line tip, complete (after the reopen and an added criterion) at
`main`'s tip, and the same blob at the sync merge.

Sites, read on the line tip. Both quoted findings come from the
binding of T's completion, `bind_completion_with_amendment`, under
`work.acceptance_binding`:

- The first sentence: `recovered_completion` (`acceptance.rs:2124`)
  finds main's earlier completion, because `reopened_in_range`
  (`lifecycle.rs:2388-2416`) sees main's reopen commit in the sync's
  range. `judge_reopened` (`acceptance.rs:2257`, tips at
  `:2308-2342`) does not count the default-branch tip as a criteria
  base, so the landing is
  `Landing::Unjudged` (text at `landing.rs:128-130`), and the refusal at
  `acceptance.rs:2176-2179` is pushed under `work.acceptance_binding` at
  `acceptance.rs:657`. That refusal keeps the earlier criteria.
- The second sentence: `reopen_problems` (`lifecycle.rs:1190`) compares
  those kept criteria with the recompleted record and returns
  `REOPENED_CRITERIA` (`acceptance.rs:3679`), pushed under
  `work.acceptance_binding` at `acceptance.rs:658-663`.
- The same text is also raised as `work.criteria_frozen` by
  `reopened_criteria` (`acceptance.rs:3656-3666`), but only when the
  line's base, or its history through `RecordStore::recovered`, holds
  an older complete record of T (`acceptance.rs:3768-3786`). A line that
  never held T gets `Ok(None)` there and raises nothing. A line that
  synced main's first completion earlier does hold it, so that shape
  can raise `work.criteria_frozen` as well.

Pre-push passes the default-branch tip as `--policy-from` (`ci.rs:108-113`,
`ci.rs:429-447`), which makes that tip a judged criteria base, so
neither finding fires there; AC-1 confirms this.

Design (Fable reviews it before the build): a record that the head holds
byte for byte as the default branch tip holds it is `main`'s own
content, whose criteria `main` already judged. For that record,
`ci --branch <line>` shall take the default-branch tip as its criteria
authority, as the pre-push check does. The choice binds to the
default-branch commit and to blob equality, never to a name or a flag,
and a record that differs from `main`'s tip at the head, by even one
byte, is judged as the line's change.

Blob equality changes only the criteria authority for these two
acceptance findings. It exempts nothing else: the status steps a sync
carries stay judged one by one as TSK-1036 AC-7 requires (no
remote-tracking ref or default-branch tip exempts a step), and the
record is still bound and checked for its review and landing.

The issue's related report (a completed task's own branch cannot push its
completion, `work.stable_planning_anchor`) is the family of #454 and is
not part of this task: no open task covers #454 either, and the builder
names what it needs in Findings for the primary (AC-1).

Non-goals: the sync-merge hand-edit check (TSK-1066), the status steps a
sync carries (TSK-1036), the #454 pre-push family.

## Outcome

After this merges, a maintainer who syncs `main` into an integration line passes `codeflow ci --branch <line>` when `main` reopened and recompleted a task the line has never held, and a sync that edits that record by even one byte still blocks.

## Acceptance Criteria

- AC-1 Before any change, the builder shall record in this record which code path raises each of the issue's two findings for the fixture, whether pre-push and `ci --branch` read different criteria authorities and why, where the design adds the default-branch tip as the criteria authority for a record whose blob equals the tip's, and that status-step judgment is unchanged, and what the #454 family needs, for the primary to file; evidence: the Findings section, committed before the first code change.
- AC-2 Given a line that never held task T, a `main` that completed T, reopened it with one added criterion and completed it again, and a sync merge carrying `main`'s record unchanged (the same blob as `main`'s tip), `codeflow ci --branch <line> --base <line tip> --head <sync merge>` shall raise neither a `work.acceptance_binding` nor a `work.criteria_frozen` finding for T; the same holds for a line that synced `main`'s first completion of T before the reopen; evidence: a CLI fixture of the issue's table, blocking before the change with both quoted sentences under `work.acceptance_binding`, and a fixture of the earlier-sync shape, blocking before the change with the rule and message AC-1 records; both pass after. (serves EPC-022 AC-198)
- AC-3 The same sync shall get the same verdict through the pre-push check and through `codeflow ci` in the pull request form; evidence: the fixture through each form, passing in all three after the change. (serves EPC-022 AC-198)
- AC-4 A sync that edits T's record, criteria or acceptance block by even one byte against `main`'s tip shall still block, naming T and the merge, and a line that reopens and changes the criteria of a task it holds shall still be refused; evidence: negative fixtures for a one-byte edit, a criterion added in the merge and a line-side reopen, passing before and after.
- AC-5 When no tip of the default branch can be read at the run, or the record's blob at the tip cannot be read or compared, the sync shall be refused with the cause, never accepted; evidence: a fixture that deletes `origin/HEAD`, `main` and `master` (local, remote-tracking and any configured upstream), refused before and after with the "no default target is found here" cause (`acceptance.rs:2496-2500`); a fixture whose task names a target that does not resolve, refused before and after with the "does not resolve here" cause (`acceptance.rs:2296`); and a fixture whose tip record blob is missing from the object store, refused after the change with a cause that names the unreadable blob.
- AC-6 (journey) With the built binary in a scratch repository, the AC-2 sync shall pass in the three forms and the AC-4 one-byte edit shall block; evidence: the journey output.
