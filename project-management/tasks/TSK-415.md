# TSK-415: The sed judge reads quoted delimiters and judges only sed's own writes

## Description

Issue #258, two cases on CodeFlow 3.1.1 (`48104f48b`), which already
holds TSK-290's sed reader (`crates/codeflow-core/src/security/sed_script.rs`):

- `sed -i '' 's#b#c#' "$TMPDIR/sedprobe.md"` is refused under
  `git.hook_integrity` as editing "repository enforcement files", while
  the same edit with `/` as the delimiter passes. The scratch file is
  outside any repository. The likely cause, not confirmed in source, is
  that `#` inside the quoted expression is read as a comment start,
  leaving the `sed -i` target unresolved and the rule failing closed.
- `sed -n "/## Closeout/,$ p" <record>; rg -n "..." DOC-INDEX.md; rg -n "mode|quick" .codeflow/project.toml`,
  a read-only line, is refused with "`sed` takes a word the shell fills
  in, and the command line names the enforcement path
  `.codeflow/project.toml`" (`crates/codeflow-core/src/hooks/git_guard.rs:4462`).
  The `$` is a sed address followed by a space, which the shell does not
  expand, and the enforcement path is an operand of a separate `rg`
  read. The check combines "some sed word is unresolved" with "an
  enforcement path appears anywhere on the line".

Outcome: **git-guard refuses `sed` under `git.hook_integrity` only when a
path sed itself could write (an `-i` target, or a `w` or `W` command or
flag) resolves to a hook, policy or settings path; a quoted `#` or a `$`
that the shell does not expand is part of the argument, and a path named
by another command on the line never counts against sed.**

Rules:

- The shell word reader keeps a `#` that is inside quotes, or not at the
  start of a word, as text; a `$` followed by a space, a quote or the
  end of the word is text, not an expansion.
- The unresolved-sed check judges only the words sed could write: the
  `-i` operands and the targets of `w`, `W` and the `s///w` flag,
  resolved by TSK-290's reader. A word the shell fills in among those
  stays refused where an enforcement file is reachable (TSK-406's rule).
  Another command's operands on the same line are judged by that
  command's judge alone.
- The second case's `sed -n` with no `-i` and no `w` is a read and
  passes.

Non-goals: `sed` forms TSK-290 marks unproven (they stay refused), and
the shell segmenter defects TSK-417 owns (newlines and braces inside
quotes, variable `tee` paths).

Added by the EPC-022 amendment of 2026-10-22 under the operator's release
rule of 2026-10-18 (a defect that blocks work belongs in 3.2.0).

Widened 2026-10-26 for the comment of 2026-10-26 on issue #342, the same
delimiter family as #258. `cd <worktree> && sed -i '' 's|...|...|' tests/test_person_apply.py && ...`,
a `|`-delimited program holding `(`, `"`, `\\r\\n`, `[ ]` and a
` # ` comment in the replacement Python text, is refused under
`git.hook_integrity` although its only target is an ordinary test file.
Rechecked on 2026-10-26 with the line's binary at `0f08dd7f8`: still
refused, now as "`sed -i` edits the integrity path `cannot inspect every
glob path: more than 4096 entries`" (3.1.0 named "repository enforcement
files"). Narrowed on the same binary: `sed -i '' 's|(a)|x|' tests/x.py`
and `sed -i '' 's|a # c|b|' tests/x.py` are refused with or without the
`cd`, while `s/a # c/b/`, `s|a|b|`, `s|"a"|x|` and `s|a\[200\]|b|` pass.
So a `|`-delimited program loses its target when it holds `(` or ` # `,
and the leftover text is read as a path glob. AC-7 owns it.
