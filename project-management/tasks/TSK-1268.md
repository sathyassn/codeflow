# TSK-1268: Ready pull requests land together on one batch candidate per line

## Description

CodeFlow's instructions and this repository's release check made landings on an integration line happen one pull request at a time. This task makes ready pull requests land together. When a line lands, every pull request reviewed and ready at that moment goes onto one candidate, in dependency order, with one full gate and one hosted run. Each line has one candidate at a time, lines land in parallel, and a pull request that becomes ready later joins the next candidate. It removes process and adds none. The wording matches the workspace rule "Landings batch; they are never one PR at a time" (workspace commit fefa7a0).

The enforcement was a hosted refusal, not a GitHub setting. Ruleset 25435656 ("Integration hosted gates", on `refs/heads/integration/**`) requires `release impact`, and its `strict_required_status_checks_policy` is `false`, so GitHub does not require an up-to-date branch. The `release impact` job (`.github/workflows/codeflow-release.yml:28-58`, run on `opened, synchronize, reopened, edited`) calls `scripts/release.py check-pr`. At the line tip, `scripts/release.py:1270-1271` refused any pull request whose event base was not the current target tip, or whose head did not contain that base: "PR base is stale relative to current target; refresh and recompute". So once one pull request landed, each other ready pull request failed on its next run (a body edit counts) until it merged the new tip in. Hosted runs 41562952216, 41562355552 and 41560128031, and PR 480, failed this way.

The fix judges such a head against the current tip and the exact merge it would produce, and keeps the stale refusal where the verdict could be wrong (AC-5).

Interaction with TSK-336 and TSK-1264: today `release impact` runs the pull request merge commit's own `scripts/release.py`, so this fix works on line pull requests once it lands. After TSK-336 moves the verdict to the default branch's code, the fix applies only once it reaches main, so it has to be on main before TSK-1264 removes the head-built job. EPC-022's main-merge must-haves carry this order; that note is maintained on its planning branch by the session that owns it.

Non-goals: no ruleset change, since none is needed (`strict` is already `false`); no change to the workspace `AGENTS.md`, which is maintained separately.

## Outcome

After this merges, the primary can land every reviewed, ready pull request on a line in one candidate, without refreshing each one after the others land.
