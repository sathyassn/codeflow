## Acceptance Criteria

- AC-1 `Cargo.lock` shall hold neither `serde_yaml_ng` nor `unsafe-libyaml`, and the chosen parser and every crate it adds shall be written in safe Rust and have a release in the 12 months before the decision. Evidence: `Cargo.lock`, `cargo tree`, and the ADR's comparison. (serves EPC-023 AC-15)
- AC-2 When the migrated build parses every record, template, registry and front matter file in this repository and in the scaffold, it shall produce the same values as the 3.1.1 build. Evidence: a test that runs both parsers over the files and compares, kept as a fixture of the parsed values.
- AC-3 When the migrated build writes a record, the id registry or any other YAML it writes today (a status change, an allocation, a follow-up, a manifest entry), it shall write the same bytes as the 3.1.1 build for the same input, comments and key order included. Evidence: golden tests for each writer.
- AC-4 When a file holds malformed YAML, a duplicate key, deep nesting, an alias expansion or a very large scalar, the build shall refuse it with an error that names the file, within a bounded time and without a crash, as the 3.1.1 build does or more strictly. Evidence: one test per class.
- AC-5 The `osv-scanner.toml` entry for `RUSTSEC-2024-0449` shall be removed, and the dependency audit shall pass without it. Evidence: osv-scanner 2.4.0 on the tree, exit 0.
- AC-6 (journey) When a project created with 3.1.1 runs `codeflow validate --docs`, `task new`, `task status`, `work claim`, `work start` and `ci` with the migrated build, each shall give the same result and the same written files as the 3.1.1 build. Evidence: a scratch project run through both binaries, with the outputs and the tree diffed. (serves EPC-023 AC-15)
