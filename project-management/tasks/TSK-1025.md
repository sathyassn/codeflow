# TSK-1025: A standalone task files its own follow-up record in its pull request

## Description

Issue #354, item 1 (CodeFlow 3.1.1, an adopter's standalone task
TSK-643). The task's pull request carried its own record and a new
follow-up task record that its AC-6 waiver names, and `codeflow ci`
refused it under `work.classification`: "a task PR may add only its own
standalone task record". Removing the follow-up record after completion
then forced a reopen, which led to the issue's other two items. Those are
placed elsewhere: the waiver refused after a reopen is TSK-340 AC-7, and
`work.criteria_frozen` counting the task's own remote branch is TSK-350
AC-5.

Read on the line tip `7172229aa`:

- the refusal: `crates/codeflow-cli/src/cmd/ci/classification.rs:1055-1066`
  refuses any added record that is not the PR task's own, and any second
  added record;
- the documented route: `docs/cli.md:118` (`--follow-up-of`) says a
  standalone task's follow-up is "a standalone task, filed on a task
  branch cut from the target, with its record filled in and committed,
  then claimed with `work claim`". That is the follow-up's own task pull
  request, which carries its code, so the record reaches the target only
  when the follow-up's work lands, after the source task that names it;
- the issue says `work claim` needs the predecessor complete on the
  target. Not confirmed: `task new --follow-up-of` writes only
  `follow_up_of` and no `depends_on` edge
  (`crates/codeflow-core/src/workgraph/light_paths.rs:200`), so a claim
  is held back only when someone adds that edge by hand.

Outcome: **a standalone task can file the follow-up its own acceptance
names in the same pull request, and the docs give one route that works
before the source task lands.**

Design: a standalone task pull request may add, besides its own record,
only the follow-up records its own acceptance block names in
`follow_ups`: new standalone tasks whose `follow_up_of` is the pull
request's task, at status `todo`, with no product path of their own. Every other
added record stays refused, as does a follow-up record that is complete,
names another source, belongs to an epic, or is changed by a later commit
in a way that would bind work to it. The alternative, docs only (file the
follow-up first in a records-only pull request), keeps classification
unchanged but adds one pull request and one merge cycle per follow-up,
which is the cost the issue reports; the bounded allowance is chosen
because the added record carries no work and is reviewed with the source
task that names it.

## Acceptance Criteria

- AC-1 When a standalone task's pull request adds its own record and new standalone task records at `todo` whose `follow_up_of` names that task and which its acceptance block names in `follow_ups`, `codeflow ci` and the pre-push hook shall classify it as that task's pull request with no `work.classification` finding; evidence: a ci_cli fixture of the issue's shape, failing before the change with the quoted message. (serves EPC-022 AC-133)
- AC-2 An added record that its source's acceptance does not name in `follow_ups` (including a valid `todo` follow-up of this task that the acceptance omits), or that names another source, is not at `todo`, belongs to an epic, has no `follow_up_of`, or comes with a product path outside the source task's own change, shall keep today's refusal; evidence: one negative fixture per case, the unnamed follow-up among them.
- AC-3 The `--follow-up-of` help, `docs/cli.md` and the lifecycle guidance shall state one route for a standalone task's follow-up that works before the source lands, and the follow-up filed that way shall pass `work claim` once the source task lands; evidence: the doc diff and a CLI test of the claim.
- AC-4 (journey) With the installed build in a scratch adopter project, a standalone task shall add its follow-up record in its own pull request, complete with a waiver naming the follow-up, and pass `codeflow ci` without a reopen; evidence: the journey output.
