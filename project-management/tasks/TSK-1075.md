# TSK-1075: Two clones never build one task through branches named from different titles

## Description

Source: the session system design, revision 12 change log ("cross-clone
arbitration stays tracked for the title-slug case only") and Codex
review r8-01. In 4.0.0 an away claim follows the cooperative claim
contract (TSK-1045 AC-14): one create-only push of a claim commit, an
unclear result settled by `ls-remote` of that branch, and one clone's
lock serialising its own claims. The existing claim refuses a visible
branch carrying the task id (`claim_on` in `readiness.rs`).

The case that remains: the branch name carries a slug of the task's
title (the same function), so two clones that read different titles for one
task create two different branches, and each clone's `ls-remote` of its
own branch shows its own claim. The refusal by task id closes this only
when the other branch is already visible, which leaves the seconds
between the remote listing and the push.

## Outcome

After this merges, two clones coordinating one body of work never both
build one task: a claim is arbitrated by task id at the forge, whatever
title each clone read.

## Acceptance Criteria

- AC-1 Before any change, the builder shall record with sources: every reader that derives a branch name from a task title, the options for arbitrating by task id (a claim ref keyed by task id such as `refs/codeflow/claims/<task id>`, or a branch name without the slug), how GitHub and a bare remote treat each, and how the shipped hooks and guards judge each; evidence: the Findings section, committed before the first change.
- AC-2 Two clones that read different titles for one task shall produce at most one claim, by a create-only operation keyed by the task id; evidence: a test with renamed titles in each clone (one claim, one refusal) and two simultaneous claims (one wins).
- AC-3 A lost reply on the arbitration step shall be settled by reading the task-id key under TSK-1045's claim contract, never retried past its attempts; evidence: tests for our value, an absent key and another clone's value.
- AC-4 Where the chosen key needs a new ref namespace, the enforcement planes shall allow only its create and delete forms, reviewed cross-lineage; evidence: hook and guard tests and the security review record.
- AC-5 Stale keys shall be removed only with merge or cancellation proof for their task; evidence: tests for a landed task (removed), an open task (kept) and an unreadable task (kept).
