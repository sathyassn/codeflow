# TSK-214: standalone follow-ups land and cancelled-only epic criteria close

## Description

Two consumer reports name dead ends in the work-record lifecycle, where a
project had to invent ceremony to close work. sathyassn/codeflow#21: a
follow-up of a standalone task cannot land, because `task new
--follow-up-of` runs only on a `plan/` branch, a planning PR must name an
epic, and `Task: TSK-NNN` on that branch fails
`work.stable_planning_anchor`. sathyassn/codeflow#25: an epic criterion
served only by cancelled tasks cannot close, because epic close never
reads the epic's own acceptance block for it, although it does for a
criterion no task serves. The fix follows ADR-0076: a follow-up of a
standalone task is itself a standalone task whose record lands with its
work on its own task branch, and a criterion whose every serving task is
cancelled is proven by the epic's own block under the rules of an unserved
criterion, so cancelling a task never proves a criterion. That block, for
unserved criteria too, now binds to its reviewed commit and its waivers to
real planning amendments, as a task's block does; before, any commit-shaped
value passed. SPC-013 R-33 and
R-73 state the old rules; their amendment rides in EPC-020's batched
amendment on a `plan/` branch, as R-32 requires. Non-goal: a follow-up of
an epic task, which still rides in the epic's batched amendment.

## Acceptance Criteria

- AC-1 (journey) When `codeflow task new --follow-up-of` names a
  standalone source off a `plan/` branch, the system shall write a
  standalone follow-up record (`epic_id: null`, a `standalone_reason`,
  `follow_up_of` and the source's target) that `work claim` moves to its
  own task branch, and `codeflow ci` shall classify the PR naming it as
  tracked and pass with the record, code and acceptance in one range; on a
  `plan/` branch it shall refuse and name the task-branch route, and a
  follow-up of an epic task shall still be refused off a `plan/` branch;
  evidence: a journey in `light_paths_journey.rs` that fails before the
  change and passes after.
- AC-2 When an epic criterion is served only by cancelled tasks, epic
  close shall accept it only from the epic's own active acceptance block
  under the rules of an unserved criterion (verified with evidence, or
  waived with its planning commit, and the journey verified for a journey
  criterion), and refuse it without that block or with a ticked checkbox
  alone; a criterion with a live serving task stays judged by its tasks.
  For unserved and cancelled-only criteria alike, the own block shall bind
  as a task's does in the status verb, CI and the release-line judge: its
  reviewed commit exists and only the epic record's status and Closeout
  changed after it, and each waiver names a planning-only amendment of
  that criterion of the epic that the reviewed commit contains, and a
  binding failure shall print the epic's repair route (correct the block,
  rerun `epic status` for an open epic, replace the Closeout block of a
  completed one; never a task reopen); evidence: lifecycle, release-line
  and `classification_cli` tests (verb, hand edit and CI, valid and
  invalid waivers, a live-task control) and
  `remedy_clearing::clears_epic_acceptance_binding`, which follows the
  printed steps, each failing before the change and passing after.
- AC-3 The `--follow-up-of` help, `docs/cli.md`, CAP-010 and the cf-method
  project-organization reference state the standalone follow-up route and
  the cancelled-only criterion rule, with every mirror and baseline copy
  matching; evidence: the diff, `manifest_consistency` and
  `repository_update_noop`.
- AC-4 The pending 3.1.0 CHANGELOG entry, under its release-impact marker,
  states both fixes and who they affect; evidence: the diff and the
  release-impact check.
