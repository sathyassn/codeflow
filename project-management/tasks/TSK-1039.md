# TSK-1039: The pre-push gate narrows from a base the push itself proves

## Description

Issue #371 (CodeFlow 3.1.1, `48104f48b`, opened 2026-10-28 01:16Z). With
targets that declare `narrow` paths and a complete green full run
recorded at the merge base, the pre-push hook runs every quick target on
every push, each with the reason "no proven comparison base"; the same
happens on a follow-up push with a green run at the branch's remote tip.
`codeflow test --mode quick --since main` on the same fixture does
narrow, so green-run storage and the config digest work and only the hook
path never supplies a base. At 3.1.1 the shim reaches
`run_gate_exact(root, "quick")` with default options (the issue cites
`git_hook.rs:1278`, `gate.rs:152-153`), and the selector returns "no
proven comparison base" when `since` is absent (`delivery.rs:234-235`).
In the reporting repository every push runs about 550 to 580 seconds,
over the 60-second push budget, and the adopter is building its own
selection map as a workaround.

On the 3.2.0 line, TSK-352 (complete) added a default base for quick and
essential runs: `comparison_base` in
`crates/codeflow-core/src/testing/delivery.rs:388-420` takes an explicit
`--since`, else the merge base of `HEAD` with the declared integration
target of the task the branch carries. It returns "no comparison base"
for a branch with no task (`:413`), a detached head (`:405`) or a task
with no declared target (`:416`), and it never uses the push's own old
remote tip. Planning did not confirm whether the line's pre-push path
reaches this selector or still runs `run_gate_exact` with no options;
AC-1 runs the issue's cases on the line tip to settle it.

Outcome: **the pre-push gate derives a comparison base from the push
itself (the remote's old tip for an update, the merge base with the
push's target for a new branch, or the task's declared line where the
branch carries a task) and narrows when a green run exists at that base,
falling back to every target, with its reason, when no base is proven.**

Rules:

- The base is evidence identity, so it is an exact commit, never a
  mutable branch name; an unproven base runs everything and names why
  (TSK-352's decision).
- Unknown, renamed and deleted paths still select every target.
- The push's old tip counts only when a complete green run is recorded
  at it with the same config digest, as TSK-352's `green_base` requires.

Non-goals: result reuse (TSK-355); the push budget itself.

## Deliverables

- the base derivation: `crates/codeflow-core/src/testing/delivery.rs` (`comparison_base`) and the pre-push path in `crates/codeflow-core/src/hooks/git_hook.rs` and `crates/codeflow-cli/src/cmd/push_set.rs`
- tests: the issue's eight cases as hook tests through a real `git push` to a local bare remote, in `crates/codeflow-cli/tests/`, each failing before the change where the line still fails it
- docs: `docs/test-gate.md` (how a push picks its base)
- release note: `changelog.d/TSK-1039.md`

## Acceptance Criteria

- AC-1 Before any change, the builder shall investigate broadly: run the issue's eight cases (it offers its fixture script) on the line tip and at 3.1.1; trace which selector the line's pre-push uses and with what options; list every caller of the gate (pre-push, `codeflow test`, integrate, CI) and the base each derives; check adjacent cases (a force push, a push of several refs, a push to a new remote, a branch with no task such as `plan/` or `chore/`, a shallow clone); and record the findings and the chosen scope in this record before any change; evidence: the record section, committed before the first code change in the PR.
- AC-2 On an update push whose old remote tip has a complete green run with the same config digest, the pre-push gate shall narrow to the targets the changed paths select; evidence: a hook test through a real push, failing before the change where the line fails it. (serves EPC-022 AC-146)
- AC-3 On a new branch, the pre-push gate shall use the merge base with the push's target, or the carried task's declared line, and narrow when a green run exists there, for a branch with or without a task; evidence: hook tests for both. (serves EPC-022 AC-146)
- AC-4 With no proven base, an unknown, renamed or deleted path, or a config digest that differs, every target shall run and the reason shall be printed; evidence: hook tests per case.
- AC-5 (journey) With the built binary in a scratch adopter with three narrow targets and a local bare remote, a one-path change pushed after a green run shall run exactly its target; evidence: the journey output.
