# TSK-1478: A planning landing may carry decision documents alongside task records

## Description

A planning pull request already admits records, plans, other files under
`docs/` (ADRs under `docs/decisions/` included), exact declared document
indexes and the project-owned part of root `AGENTS.md` (`amendment_path`,
`crates/codeflow-core/src/workgraph/classify.rs:348-377`). The import side is
narrower. `admissible_planning_landing`
(`crates/codeflow-core/src/workgraph/acceptance/imports.rs:377-420`), built by
TSK-1004, accepts a landing only when every changed name is a record or plan.
It decides two import questions: shared planning provenance for an
introduced task record (`is_shared_planning`, `imports.rs:320-366`) and a
planning move of a task's home (`is_planning_move`, `imports.rs:430-441`). A
planning landing that carries an ADR next to its records therefore passes as
a planning pull request, but a line that takes it loses both answers, and the
import is judged under `work.import_authority` as an unpublished import or a
home change.

Change: `admissible_planning_landing` also admits a decision document, a
regular, non-executable (`100644`) file whose path is an ADR in the record
layout compiled into the binary, `docs/decisions/ADR-NNNN[-slug].md`, one
level deep with four or more digits, as `record_id_from_path` reads it
(`crates/codeflow-core/src/ids/entry.rs:170-198`). No policy value or file the
range can change defines that layout. Every other condition stays: two
parents, a clean remerge, the planning range check, regular files and both
sides of a rename. Every other path still makes the landing inadmissible:
other `docs/` files, `docs/decisions/README.md` and `template.md`, document
indexes, `AGENTS.md`, instructions, hooks, policy and CI. This follows the
operator's decision of 2026-11-12: a planning pull request may carry decision
documents, never instructions, hooks, policy or CI.

Non-goal: this task does not change the planning range check, and it keeps
the existing admission of the project-owned part of root `AGENTS.md` in a
planning pull request (`classify.rs:349-351`). Whether to remove that
admission is a separate public-behaviour question for the operator.

Overlap: EPC-056 (planning derives the epic graph and states what each
landing leaves on `main`) is the nearest epic; its outcome is the epic graph
and landing answers, so this admission change stays standalone. Open tasks
TSK-1185 (import ordering of superseding record versions) and TSK-421 (line
sync, carry and close) do not cover it. TSK-1004, which built the check, is
complete. Issue 83 reported the pull-request side, which ADR-0078 since
widened; this task covers the import side.

## Outcome

After this merges, a team can land a planning pull request that carries its
ADRs next to its task records, and the lines that take it keep shared
planning provenance and planning moves.

## Acceptance Criteria

- AC-1 `admissible_planning_landing` shall admit a planning landing whose changes are task records, plans and decision documents only, where a decision document is recognised only by the ADR record layout compiled into the binary (`docs/decisions/ADR-NNNN[-slug].md`, as `record_id_from_path` reads it), never by a policy value or a file the range can change. Evidence: a test with a clean planning merge that adds a task record and an ADR, refused before the change by `work.import_authority` on a line that takes it, and passing after, for both shared provenance and a planning move.
- AC-2 Any other path shall still make the landing inadmissible, and anything the check cannot read shall still refuse (fail closed). Evidence: controls refused before and after, each shown to depend on its check: an ADR-shaped name in a nested folder, `docs/decisions/README.md`, `docs/decisions/template.md`, another `docs/` file, a declared document index, root `AGENTS.md`, a harness instruction file, a hook, the policy file, a CI workflow, an ADR with the executable bit, an ADR as a symbolic link, a rename from an ADR path to a non-ADR path, an evil merge carrying an ADR, and a policy that declares an extra decision folder.
- AC-3 The decision-document admission shall not widen the instructions admission in any way: the managed block of root `AGENTS.md`, rules, skills, hooks, policy and CI stay refused, both by the planning range check and by `admissible_planning_landing`. Evidence: a must-refuse test row for each (an edit inside the managed block, a file under `.codeflow/rules/`, a skill file, a hook, the policy file, a CI workflow), each carried next to an ADR, refused before and after.
- AC-4 The docs that describe planning landings shall state that a planning landing counts as shared planning provenance or a planning move only when it carries records, plans and decision documents (ADRs), and nothing else: `docs/policy-reference.md` "Planning amendment paths", the pull request class row in `docs/capabilities.md`, and any other page the builder finds. Evidence: the doc diff and `codeflow validate --docs`.
- AC-5 The change shall get one cross-family security review with the `cf-security-reviewer` checklist, and the pull request shall state the threat the admission rule guards against (a planning landing that carries instructions, hooks, policy or CI) and why a path rule compiled into the binary is the fail-closed design. Evidence: the review row.
- AC-6 With the built binary, a scratch repository whose line takes a planning landing carrying a task record and an ADR shall pass the import check, and one whose planning landing carries an ADR plus a hook shall be refused. Evidence: both outputs. (journey)
