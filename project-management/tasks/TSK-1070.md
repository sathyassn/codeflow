# TSK-1070: The Claude settings show effort, pull request, usage and worktree, and support bypass mode set outside the repository

## Description

Source: issue 402 ("Richer default status line: effort, PR state and usage
in managed settings"), which asks the scaffold to adopt a richer
`statusLine`, or to state that projects own it. The operator decided on
2026-10-29 (13:2x) to adopt it as recommended. Issue 351 and TSK-1028
(complete) are the history: TSK-1028 made the shipped line the `jq` line of
issue 351's comment (model name and id, version, output style, folder,
branch, context use) with a folder-and-branch fallback when `jq` is absent,
and left effort to each person. That leaves a contributor no view of the
effort their session runs at, of the pull request their branch has, of how
much of their plan's usage windows is spent, or of whether they are in a
linked worktree.

This task adds four fields to the shipped line. Each is printed only when
Claude Code's status JSON supplies it, and the line prints nothing for a
field that is absent: no placeholder, no `null` and no stray separator. The
field names were checked against https://code.claude.com/docs/en/statusline.md
on 2026-10-29 and match the issue exactly:

| Shown | Field in the status JSON | Documented as absent when |
|---|---|---|
| effort beside the model | `effort.level` (`low`, `medium`, `high`, `xhigh`, `max`) | the current model does not support the effort parameter |
| the open pull request and its review state | `pr.number`, `pr.review_state` (`approved`, `pending`, `changes_requested`, `draft`) | no open PR is found for the branch, or it merged or closed; `review_state` may be absent while `pr` is present |
| plan usage | `rate_limits.five_hour.used_percentage`, `rate_limits.seven_day.used_percentage` (0 to 100) | the user is not a claude.ai Pro or Max subscriber, before the first API response, or a window has passed its `resets_at`; each window can be absent alone |
| linked worktree | `workspace.git_worktree` (the worktree name) | the directory is the main working tree |

Constraints from the issue and from TSK-1028 that hold here:

- A plugin or mod cannot provide `statusLine`, so the managed
  `.claude/settings.json` presets remain the only shared route.
- A committed `statusLine` replaces a contributor's own. The opt-out is the
  contributor's `.claude/settings.local.json`. TSK-1028 wrote this into
  `docs/harness-posture.md` ("Shared and personal settings") and
  `cf-customize/references/personal-settings.md`; this task keeps both true
  and lists the new fields there.
- `codeflow update` replaces a `statusLine` that is exactly a value
  CodeFlow shipped, proved by the recorded baseline, and keeps and reports a
  line the project changed (TSK-1028 AC-4). The new line is a new shipped
  value, so a project still holding TSK-1028's line, or the older
  branch-only line, moves to it by the same rule. No new update mechanism is
  needed.
- Without `jq` the line prints the folder and branch and "jq not found" and
  exits 0 (TSK-1028 AC-2). The new fields need `jq` and are not part of the
  fallback.

Non-goals: no call to `gh` or the network for the pull request (only what
Claude Code puts on stdin), no `refreshInterval` or other `statusLine` key,
no change to the effort opt-in (TSK-1028 AC-3), no change to a project's own
line, and no change to the Codex configuration. The builder picks the exact
layout and may reuse the context bands (green below 50, yellow below 80, red
from 80) for the usage percentages; if so, the PR says so. TSK-1028 allowed a
managed script in place of the inline command; that choice stays the
builder's, with the same update rule.

Dependency: TSK-1028 is complete and its code is on this line, so there is
no edge. TSK-1028's criteria stay as they are.

## Scope widened (2026-10-31)

The operator asked on 2026-10-31 for every Claude settings change to land as
one task for CodeFlow and the consuming projects: this status line, the
compaction point TSK-1029 shipped (kept at 35 percent of the 1M window,
already consistent in every preset and this repository's file), and the
bypass permission mode of issue 451. Claude Code ignores
`bypassPermissions` in a project settings file since v2.1.257 and starts the
session in Manual mode, so the shipped `bypass-sandboxed.json` key did
nothing, and a project mode value outranks the user file. ADR-0093 records
the decision. The scope change is a safety and interface change to the same
files, so it is recorded here instead of a second task.

## Operator decisions (2026-10-31)

- Status line: the inline command with model (id) and effort, version,
  style, folder (branch) and worktree, pull request, context and the two
  usage windows, each optional field only when Claude Code supplies it;
  every preset carries it.
- Compaction stays at 35 percent (TSK-1029).
- Bypass: no preset or CodeFlow's own file sets `defaultMode`. The
  operator decided on 2026-10-31 (option A, after the sandbox exemptions
  research section 8) that the binding settings live in a CodeFlow-owned
  session file, `~/.codeflow/claude/session.json`, loaded with
  `claude --settings`: bypass mode on the person's yes, the sandbox on with
  no unsandboxed retry, `strictAllowlist` with the host list, the
  exclusions and the shipped deny and ask rules. `codeflow claude-session
  --install`, which `codeflow init` offers after the bypass answer, writes
  it and a `claude` shell function that loads it inside CodeFlow projects,
  and adds the line that sources the function to `~/.zshrc` or `~/.bashrc`
  only on the person's yes. A session started without it is warned at
  session start. The person's `~/.claude/settings.json` gets only optional
  per-item additions, each on its own yes, with a backup and a record.
- Permissions in every preset and this repository's file:
  `sandbox.allowUnsandboxedCommands: false` with the host-state commands in
  `sandbox.excludedCommands` (the `gh` subcommands CodeFlow uses and
  `git push *`; `herdr` and the Codex plugin at user scope, after the
  sandbox exemptions research and issue 452); Read and sandbox
  denies on the token stores of `gh`, git, Docker, gcloud, Azure, npm and
  the macOS keychains; the `secret` and `credentials` name rules narrowed
  to exact names and data-file extensions, so source files such as
  `secret_scan.rs` are readable in the sandbox.
- Network (second decision that day): `sandbox.network.allowedDomains`
  lists the development hosts instead of `*`; private-range denies and
  local binding stay; the project's own hosts survive `codeflow update`.
- CodeFlow's own `.claude/settings.json` takes these through this branch's
  `codeflow update`.

## Outcome

After this merges, a contributor on a CodeFlow project sees their session's effort, the open pull request and its review state, their 5-hour and 7-day usage, and the linked worktree in the shipped status line whenever Claude Code reports them, and a project on an earlier shipped line moves to this one on `codeflow update`. An operator can run Claude Code in bypass mode as a documented choice, set at launch or in CodeFlow's own session file that a plain `claude` loads inside CodeFlow projects, with no shipped project key that silently does nothing, every file outside the repository written only on their yes, and with the guards, deny rules and a stricter sandbox (no rerun outside it, token stores denied, development hosts only) still in force and proven by a live canary.
