# TSK-1070: The status line shows effort, pull request, usage and worktree when Claude Code supplies them

## Description

Source: issue 402 ("Richer default status line: effort, PR state and usage
in managed settings"), which asks the scaffold to adopt a richer
`statusLine`, or to state that projects own it. The operator decided on
2026-10-29 (13:2x) to adopt it as recommended. Issue 351 and TSK-1028
(complete) are the history: TSK-1028 made the shipped line the `jq` line of
issue 351's comment (model name and id, version, output style, folder,
branch, context use) with a folder-and-branch fallback when `jq` is absent,
and left effort to each person. That leaves a contributor no view of the
effort their session runs at, of the pull request their branch has, of how
much of their plan's usage windows is spent, or of whether they are in a
linked worktree.

This task adds four fields to the shipped line. Each is printed only when
Claude Code's status JSON supplies it, and the line prints nothing for a
field that is absent: no placeholder, no `null` and no stray separator. The
field names were checked against https://code.claude.com/docs/en/statusline.md
on 2026-10-29 and match the issue exactly:

| Shown | Field in the status JSON | Documented as absent when |
|---|---|---|
| effort beside the model | `effort.level` (`low`, `medium`, `high`, `xhigh`, `max`) | the current model does not support the effort parameter |
| the open pull request and its review state | `pr.number`, `pr.review_state` (`approved`, `pending`, `changes_requested`, `draft`) | no open PR is found for the branch, or it merged or closed; `review_state` may be absent while `pr` is present |
| plan usage | `rate_limits.five_hour.used_percentage`, `rate_limits.seven_day.used_percentage` (0 to 100) | the user is not a claude.ai Pro or Max subscriber, before the first API response, or a window has passed its `resets_at`; each window can be absent alone |
| linked worktree | `workspace.git_worktree` (the worktree name) | the directory is the main working tree |

Constraints from the issue and from TSK-1028 that hold here:

- A plugin or mod cannot provide `statusLine`, so the managed
  `.claude/settings.json` presets remain the only shared route.
- A committed `statusLine` replaces a contributor's own. The opt-out is the
  contributor's `.claude/settings.local.json`. TSK-1028 wrote this into
  `docs/harness-posture.md` ("Shared and personal settings") and
  `cf-customize/references/personal-settings.md`; this task keeps both true
  and lists the new fields there.
- `codeflow update` replaces a `statusLine` that is exactly a value
  CodeFlow shipped, proved by the recorded baseline, and keeps and reports a
  line the project changed (TSK-1028 AC-4). The new line is a new shipped
  value, so a project still holding TSK-1028's line, or the older
  branch-only line, moves to it by the same rule. No new update mechanism is
  needed.
- Without `jq` the line prints the folder and branch and "jq not found" and
  exits 0 (TSK-1028 AC-2). The new fields need `jq` and are not part of the
  fallback.

Non-goals: no call to `gh` or the network for the pull request (only what
Claude Code puts on stdin), no `refreshInterval` or other `statusLine` key,
no change to the effort opt-in (TSK-1028 AC-3), no change to a project's own
line, and no change to the Codex configuration. The builder picks the exact
layout and may reuse the context bands (green below 50, yellow below 80, red
from 80) for the usage percentages; if so, the PR says so. TSK-1028 allowed a
managed script in place of the inline command; that choice stays the
builder's, with the same update rule.

Dependency: TSK-1028 is complete and its code is on this line, so there is
no edge. TSK-1028's criteria stay as they are.

## Outcome

After this merges, a contributor on a CodeFlow project sees their session's effort, the open pull request and its review state, their 5-hour and 7-day usage, and the linked worktree in the shipped status line whenever Claude Code reports them, and a project on an earlier shipped line moves to this one on `codeflow update`.

## Acceptance Criteria

Verdicts below are for the line run through `/bin/sh` on sample status JSON, as TSK-1028's status line tests do.

- AC-1 Before any change, the builder shall record in the PR the field names this task reads, checked against https://code.claude.com/docs/en/statusline.md on the day of the check, and the Claude Code version the live journey (AC-10) ran on; a name that differs from the table in the Description is used as documented and the difference is stated; evidence: the PR section naming each field, its documented type and its documented absence.
- AC-2 Given status JSON that supplies `effort.level`, the shipped line shall print the effort beside the model, and print no effort text when `effort` is absent; evidence: a preset test over every preset with the field present at each of the five documented levels and absent, failing before the change and passing after. (serves EPC-022 AC-161)
- AC-3 Given `pr.number` and `pr.review_state`, the line shall print the number and the review state; given `pr.number` alone it shall print the number alone; given neither it shall print nothing for the pull request; evidence: a preset test for the four documented states, the number-only case and the absent case, each sample also asserting AC-6's separator rule (no `null`, empty brackets or doubled separator), failing before and passing after. (serves EPC-022 AC-161)
- AC-4 Given `rate_limits.five_hour.used_percentage` and `rate_limits.seven_day.used_percentage`, the line shall print each present percentage with its window, print one window when only one is present, and print nothing for usage when `rate_limits` is absent; evidence: a preset test for both windows, each alone, none, a fractional value (such as 23.5), 100, and a present value of 0 (printed, not treated as absent), each sample also asserting AC-6's separator rule (no `null`, empty brackets or doubled separator), failing before and passing after. (serves EPC-022 AC-161)
- AC-5 Given `workspace.git_worktree`, the line shall print the worktree name, and print nothing for it when the field is absent; evidence: a preset test with the field present and absent, failing before and passing after. (serves EPC-022 AC-161)
- AC-6 The existing fields shall print as before: with none of the four new fields in the status JSON the line prints the same text as TSK-1028's line, and for any combination of present and absent new fields it prints no `null`, empty brackets or doubled separator; a path with backslashes prints literally; evidence: TSK-1028's status line tests passing unchanged, plus one test over all sixteen combinations of the four field groups (effort, pull request, usage, worktree) each present or absent. The sixteen cover the groups, not the cases inside one: the pull request states of AC-3 and the usage windows of AC-4 are tested there, and each of their samples asserts the same rule (no `null`, empty brackets or doubled separator). (serves EPC-022 AC-161)
- AC-7 With `jq` absent from `PATH`, the line shall still print the folder and branch with "jq not found" and exit 0, whatever fields the status JSON carries; evidence: TSK-1028's no-`jq` test, extended to a status JSON that carries all four new fields, passing before and after. (serves EPC-022 AC-161)
- AC-8 `codeflow update` shall replace a `statusLine` that is exactly a value CodeFlow shipped, TSK-1028's line and the older branch-only line included, with the new line, and keep and report a line the project changed, by TSK-1028 AC-4's rule; evidence: settings-merge tests for a project at TSK-1028's line (moves; fails before the change), at the older line (moves), at a changed line (stays and is reported) and with the key deleted (stays unset), and `codeflow update` run on a scratch project at each. (serves EPC-022 AC-161)
- AC-9 The docs shall state that a committed `statusLine` replaces a contributor's own, that the opt-out is `.claude/settings.local.json`, and which fields the shipped line shows and when each is absent; the managed text and the `.claude/skills` and `.agents/skills` copies shall match, and the replacement claim shall agree with the Claude Code settings precedence cited there; evidence: the doc diff and the skill mirror check. (serves EPC-022 AC-161)
- AC-10 (journey) In a live Claude Code session in a scratch project updated by this branch, inside a linked worktree on a branch with an open pull request, the status line shall show the effort (and its change after `/effort`), the pull request, the worktree and, on a subscription plan, the usage; and a contributor's own line in `.claude/settings.local.json` shall replace it; evidence: pane captures of the status line in each state, and a statement of any field the session could not supply (for example usage on a login that is not a subscription). (serves EPC-022 AC-161)
