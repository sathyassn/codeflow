# TSK-104: work classification for every product pull request and the light paths

## Description

Today the anchored preflight runs only on `task/` branches, and a pull
request can carry product changes with no work association. This task
classifies every product pull request as tracked (`Task: TSK-NNN`), direct
change (`Task: none: <reason>`), planning-only (records and plans only), or
a trusted automation profile, and blocks an unclassified one; runs the
preflight for tracked work on any branch; refuses direct changes on the
protected surfaces of design v4 section 7; and adds the light paths of
section 8: `task new --follow-up-of`, `epic new --integration`, and
`adr new` with the ADR template defaulting to `proposed`. It also carries
the spike path of section 3.1 row 1. The automation profiles themselves
(trusted actor, skipped checks) are TSK-107's; this task gives them a
classification slot.

## Affected surfaces and interfaces

- `codeflow ci` PR-body checks and the scaffolded CI workflow; pre-commit
  preflight (CAP-003).
- `task new`, `epic new`, new `adr new`; `docs/decisions/template.md` and its
  scaffold copy (CAP-010).
- Shared files this task edits: the CI workflow, the hooks and the ADR
  template. Ownership follows SPC-013 R-118.

## Acceptance Criteria

- [ ] AC-1 When a product pull request carries none of the four
      classifications, CI shall block it; a planning-only pull request that
      touches product paths shall block; evidence: CI fixtures per class.
      Spec: R-70.
- [ ] AC-2 When a pull request from any branch names `Task: TSK-NNN`, the
      anchored preflight shall run in the CLI, pre-commit and CI, including a
      `fix/` pull request that names a task; evidence: preflight tests on
      `fix/`, `feat/` and `task/` branches.
      Spec: R-72, R-76.
- [ ] AC-3 When `Task: none: <reason>` touches watched contract paths,
      policy, hooks, dependency manifests or lockfiles, the record schema,
      or the adopter-facing path set that TSK-106 owns, CI shall block; a
      project may forbid direct changes entirely but cannot narrow the
      refused set; evidence: CI fixtures per surface.
      Spec: R-71, R-114.
- [ ] AC-4 `task new --follow-up-of TSK-NNN` shall record `follow_up_of` and
      write the record on a planning branch of the source's target;
      `epic new --integration` shall create the epic's integration branch;
      `adr new` shall issue the next ADR number through the registry and
      write the template with `status: proposed`; evidence: command tests.
      Spec: R-36, R-73, R-77.
- [ ] AC-5 A task with `work_type: spike` on a `spike/` branch shall pass the
      preflight and land its findings under the rule SPC-013 settles
      (design v4 section 3.1 row 1); evidence: spike journey.
      Spec: R-64.
- [ ] AC-6 (journey) On a fresh project with the installed CLI, a follow-up,
      a leaf task, a small fix with `Task: none`, and a new ADR shall each
      take one command and at most one ordinary pull request; evidence: the
      section 10 journeys for classification and light paths.
      Spec: R-74, R-104.
- [ ] AC-7 When one pull request both adds a task record and names that
      task in `Task:`, CI shall block it; evidence: CI fixture.
      Spec: R-78.
