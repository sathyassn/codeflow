# TSK-104: work classification for every product pull request and the light paths

## Description

Today the anchored preflight runs only on `task/` branches, and a pull
request can carry product changes with no work association. This task
classifies every product pull request as tracked (`Task: TSK-NNN`), direct
change (`Task: none: <reason>`), planning-only (records and plans only), or
a trusted automation profile, and blocks an unclassified one; runs the
preflight for tracked work on any branch; refuses direct changes on the
protected surfaces of design v4 section 7; and adds the light paths of
section 8: `task new --follow-up-of`, `epic new --integration`, and
`adr new` with the ADR template defaulting to `proposed`. It also carries
the spike path of section 3.1 row 1. The automation profiles themselves
(trusted actor, the skipped branch and commit checks, supplied PR
sections) are TSK-107's; this task gives them a
classification slot.

## Affected surfaces and interfaces

- `codeflow ci` PR-body checks and the scaffolded CI workflow; pre-commit
  preflight (CAP-003).
- `task new`, `epic new`, new `adr new`; `docs/decisions/template.md` and its
  scaffold copy (CAP-010).
- The adopter-facing path-set definition of SPC-013 R-114, created here
  and extended by TSK-106.
- Shared files this task edits: the CI workflow, the hooks and the ADR
  template. Ownership follows SPC-013 R-118.

- Interpretations and deviations, for review:
  - Operator direction 2026-09-26: the planning check runs once at
    `work start` and in CI; the per-commit pre-commit preflight is retired.
    Planning amendment in this pull request, ruled 2026-09-27: AC-2 no
    longer names pre-commit.
  - Operator direction 2026-09-27: the product paths are project-owned
    (`git.product_paths`, stack default at init, added once by update).
    CodeFlow names `assets/**` and `crates/**` in its own policy, which
    covers the fixed set of R-114; CI workflow files join the floor, per
    the rule that such changes never go direct.
  - Two classes added beyond R-70, accepted 2026-09-27. A pull request
    without a `Task:` line is tracked when its branch carries the task id,
    because the branch already names the task and the anchored preflight
    runs on it, so a second declaration adds nothing. An `integration/`
    head is an epic landing, because the line's tasks were each classified
    when they landed on it. `plan/` and `integration/` never carry a task
    id.
  - Breaking, ruled 2026-09-27: a required `Task:` line can block an
    existing adopter's pull request, so the change is released as major.
    The shipped pull request template now carries the line with a hint.
    No policy key turns classification off; `git.direct_changes` only
    allows or forbids direct changes.
  - ADR numbers come from the highest visible ADR plus one;
    `light_paths::next_adr_id` is the touch point for the TSK-101 registry
    (accepted 2026-09-27; TSK-101 wires it when it rebases).
  - The automation class is a slot: CI passes no profile until TSK-107.
  - Review round 1 (Codex, 2026-09-27) fixes. Classification reads the
    range as one tree diff from the merge-base (`git diff -z --name-status
    --no-renames`), so merge resolutions, deletions and both sides of a
    rename count, and an enumeration failure blocks. Tracking is on when it
    is on at the target or at the head. A branch carrying a task id, or a
    `spike/` branch, cannot take `Task: none`.
  - Epic line binding: the ruling asked for the epic from the target's
    records, but an epic planned on its own line (EPC-020 is not on
    `origin/main`) has no record there, so the check reads the target's
    records first and the line's otherwise (accepted 2026-09-27). The
    target's records are read at its current tip, so an epic cancelled on
    the target after the line forked blocks (review round 2, R2-1); the
    merge-base only bounds the range and the first-parent walk. A line needs a name
    `integration/EPC-NNN-<slug>`, an epic record that is not cancelled, a
    task of that epic targeting this exact line, the project's default
    target as destination, and only merge commits on its first-parent
    history. Residual: the records and the merges on the line are the
    head's own, so a crafted line with a fake epic and a merged side branch
    would pass; closing that needs the epic record anchored on the target
    before the line is cut, a planning-flow decision.
  - `work_records::dispatch` (TSK-102) still reads activation from the
    head; classification now blocks the bypass, so it was not changed here.
- Not verified: CI on a hosted runner, the push in `epic new --integration`
