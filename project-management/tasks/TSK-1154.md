# TSK-1154: A landing candidate accepts a task's own criteria change that its pull request already judged

## Description

Source: issue #488 (CodeFlow 3.1.1, by an adopter), read at commit
`4880597073` (the step 4 planning branch head) after a search found no open task
that covers it. `cf-plan` says a task's own criteria change rides in its own
PR. A task that rewrites one of its own criteria on its task branch, gets
that reviewed and lands it on its integration line still fails `codeflow ci`
on the landing range with `work.criteria_frozen`. The only way through is a
separate records-only epic amendment that copies the criterion byte for byte
onto the line first. The adopter paid that cost twice in one day (an extra
branch, review, push and CI run each time).

Why no open task covers it:

- TSK-350 AC-6 (issue #380) gives the task's own PR range, judged with
  `--into <line>` and in pre-push, a bounded exception for the task's own
  criteria change. Its range is the task branch's. A landing candidate is a
  different range: base is the line tip, head is the tip plus a no-ff merge of
  the task head, on a branch that is neither the task's nor an `integration/`
  head. Criteria classification gives such a head no own-task identity: with
  no class it takes the `integration/` or amendment path, and otherwise
  `Criteria::Frozen`
  (`crates/codeflow-cli/src/cmd/ci/acceptance.rs:290-345`, with
  `task_criteria` at `crates/codeflow-core/src/workgraph/acceptance.rs:4394`).
  TSK-350 AC-1 resolves the task from the judged head, but only for a task
  branch name. This task is the landing half of the same outcome, so it
  depends on TSK-350 and reuses its rule rather than writing a second one.
- TSK-1129 (PR 478) lets a task's completion waive a criterion by naming an
  amendment in its own range; it does not change which range may change a
  criterion. TSK-1124 and TSK-1152 change `work.acceptance_binding` for a
  `main` sync and `work.criteria_frozen` for a carried cancellation. None
  admits an own-criteria change in a landing candidate.

Design. A range whose destination is a confirmed integration line (decided
from the destination the run is given and the trusted-line binding
`epic_line_binding`, `crates/codeflow-core/src/workgraph/work_start.rs:883`,
never from the head's branch name) judges each no-ff merge it holds as that
task's own range: base is the merge's first parent, head is its second
parent. A task's own criteria change brought in by such a merge is accepted
exactly when TSK-350 AC-6 accepts the same change in the task's own PR range
at that second parent. Everything the merge does beyond that stays judged as
today. Fail closed, and bind to base-branch content and exact SHAs. The trusted
line tip is the one the destination advertises for that exact ref, resolved
once to a commit at the start of the run (the remote-tracking ref as fetched
for a local run), never a local branch, a requester-supplied anchor or a
commit the head names, as TSK-1089 fixes it
(`project-management/tasks/TSK-1089.md:60-74`). With no `--into`, as in the
issue's invocation, the line is the one fetched `integration/EPC-*` ref
whose tip is exactly the base commit; none found means the range is not a
line landing and keeps today's verdict, and two or more refuse. The checked
range starts at that pinned tip: a supplied `--base` that is not the tip
does not shorten it, so the whole tip-to-head range is judged, or the run
refuses with the cause. The line
and the epic come from the trusted records at that tip, the task's
declared target is read at the line tip and at the second parent, and a
criteria change that no exact parent pair explains is refused. The PR body
reason line TSK-350 reads for the task's own PR is not read at landing
(a landing candidate has no body to trust); the dated amendment note inside
each changed criterion, which `cf-plan` already requires, is the record that
travels with the content.

Main batch (AC-16). A batch pull request into `main` whose members each
declare `main` as their integration target is the same per-member judgment
with a different anchor and binding. The trusted tip is the `main` commit the
pull request's base gives (on a local run, the fetched `origin/main`), never
a fetched epic line. A hosted pull request run sets `merge_landing`
(`crates/codeflow-cli/src/cmd/ci.rs:790`), which skips the line-tip check, and
classifies the whole range from one body's `Task:` line
(`classification::dispatch`, `ci.rs:1179`), so the run itself has to apply
the member judgment. The member binding to `main` is new: today's
`task_line_binding` (`crates/codeflow-core/src/workgraph/work_start.rs:1571`)
resolves an epic from the line name first and refuses `main`
(`crates/codeflow-core/src/workgraph/line_adoption.rs:195-208`), and the
epic-line binding of its other callers does not change. Each task member
binds as a one-task pull request into `main` does, through its own record's
acceptance block: the member head equals the reviewed commit or descends
from it as that binding accepts (a non-merge after it changes only the
record's status and Closeout; a merge is a clean re-merge of `main`'s
first-parent line), judged with the base's policy and binary and no forge
lookup, so the trust model is a
one-task pull request's. A filing member, which only adds new records, is
judged by the record rules of a one-pull-request filing into `main`; any
other records-only member goes to `main` on its own. A member's criteria are judged from the
trees at its two parents alone, never from pull request text, a branch name
or another side channel, and no existing criterion may change in such a
batch, the bound task's own included, because TSK-350 AC-6 covers only a
confirmed line. Records match across the two trees by id and uid, never by
path; an id or uid on two records in one tree, or a record matching two
records in the other, refuses; and criteria are compared on every matched
pair, so a record deleted and added back, renamed or split is still judged
against its first-parent criteria.

Decision owner: the operator approved TSK-350 AC-6 (the criteria-authority
exception with its binding) on 2026-10-28, and that approval is now recorded
in TSK-350's record. This task applies that approved check at the task's own
merge in the line landing and moves no other criteria boundary. If AC-1's
findings show the landing range needs a different authority than AC-6's, the
change goes back as a planning amendment first.

Non-goals: no change to the TSK-350 PR-range verdicts; no acceptance of
another task's criteria change; no change to the reopen freeze or to the
completion binding.

## Outcome

After this merges, a maintainer can land a reviewed task whose own criteria
changed in its PR through a landing candidate that `codeflow ci` accepts, with
no separate amendment branch.
The same per-member judgment admits a clean batch pull request into `main`
whose members each target `main` (AC-16), so a cut to `main` can be one
batch pull request.

A filing member, a records-only member whose diff from its first parent only adds new record files and changes or removes no existing file, is admitted on the terms of a one-pull-request filing into `main`: it has no acceptance block either, and `codeflow ci` applies to that member's own diff exactly the record rules it applies to such a filing, with the base's policy and binary. Records are matched across the two trees by id and uid, never by path. An id or uid that occurs on more than one record in either tree refuses the member, and so does a record in one tree whose id and uid match two different records in the other. A record matches the record in the other tree that shares its id or its uid; a missing uid matches nothing. Criteria are compared on every matched pair, so a changed criterion is a change whether the pair matched by id, by uid or by both, and a first-parent record with no match in the second parent is a change. An added record is a second-parent record whose id and uid are both absent from the first parent. An unreadable task record in either tree refuses the member.
