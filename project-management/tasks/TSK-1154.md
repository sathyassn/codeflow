# TSK-1154: A landing candidate accepts a task's own criteria change that its pull request already judged

## Description

Source: issue #488 (CodeFlow 3.1.1, by an adopter), read at commit
`4880597073` (the step 4 planning branch head) after a search found no open task
that covers it. `cf-plan` says a task's own criteria change rides in its own
PR. A task that rewrites one of its own criteria on its task branch, gets
that reviewed and lands it on its integration line still fails `codeflow ci`
on the landing range with `work.criteria_frozen`. The only way through is a
separate records-only epic amendment that copies the criterion byte for byte
onto the line first. The adopter paid that cost twice in one day (an extra
branch, review, push and CI run each time).

Why no open task covers it:

- TSK-350 AC-6 (issue #380) gives the task's own PR range, judged with
  `--into <line>` and in pre-push, a bounded exception for the task's own
  criteria change. Its range is the task branch's. A landing candidate is a
  different range: base is the line tip, head is the tip plus a no-ff merge of
  the task head, on a branch that is neither the task's nor an `integration/`
  head. Criteria classification gives such a head no own-task identity: with
  no class it takes the `integration/` or amendment path, and otherwise
  `Criteria::Frozen`
  (`crates/codeflow-cli/src/cmd/ci/acceptance.rs:290-345`, with
  `task_criteria` at `crates/codeflow-core/src/workgraph/acceptance.rs:4394`).
  TSK-350 AC-1 resolves the task from the judged head, but only for a task
  branch name. This task is the landing half of the same outcome, so it
  depends on TSK-350 and reuses its rule rather than writing a second one.
- TSK-1129 (PR 478) lets a task's completion waive a criterion by naming an
  amendment in its own range; it does not change which range may change a
  criterion. TSK-1124 and TSK-1152 change `work.acceptance_binding` for a
  `main` sync and `work.criteria_frozen` for a carried cancellation. None
  admits an own-criteria change in a landing candidate.

Design. A range whose destination is a confirmed integration line (decided
from the destination the run is given and the trusted-line binding
`epic_line_binding`, `crates/codeflow-core/src/workgraph/work_start.rs:883`,
never from the head's branch name) judges each no-ff merge it holds as that
task's own range: base is the merge's first parent, head is its second
parent. A task's own criteria change brought in by such a merge is accepted
exactly when TSK-350 AC-6 accepts the same change in the task's own PR range
at that second parent. Everything the merge does beyond that stays judged as
today. Fail closed, and bind to base-branch content and exact SHAs: the line
and the epic come from the trusted records at the line tip, the task's
declared target is read at the line tip and at the second parent, and a
criteria change that no exact parent pair explains is refused. The PR body
reason line TSK-350 reads for the task's own PR is not read at landing
(a landing candidate has no body to trust); the dated amendment note inside
each changed criterion, which `cf-plan` already requires, is the record that
travels with the content.

Decision owner: TSK-350 Closeout records the operator's approval of the
criteria-authority exception (AC-6). This task extends the same exception
to the landing range and writes no code until that approval is recorded or
the operator confirms the extension in a planning amendment. If AC-1's
findings show the landing range needs a different authority than AC-6's, the
change goes back as a planning amendment first.

Non-goals: no change to the TSK-350 PR-range verdicts; no acceptance of
another task's criteria change; no change to the reopen freeze or to the
completion binding.

## Outcome

After this merges, a maintainer can land a reviewed task whose own criteria
changed in its PR through a landing candidate that `codeflow ci` accepts, with
no separate amendment branch.

## Acceptance Criteria

- AC-1 Before any change, the builder shall reproduce issue #488's four steps on the line tip, record which code raises `work.criteria_frozen` for the candidate and why TSK-350 AC-6 does not reach it, state how the candidate's merges are judged today, name every authority the rule reads (line tip records, second-parent records, policy source), and confirm the operator's approval of the criteria-authority exception is recorded; evidence: a Findings section in this record, committed before the first code change.
- AC-2 Given a line tip with task T todo at AC-4 text A, a task head that rewrites AC-4 to text B with a dated amendment note and adds T's completion, and a candidate that is the tip plus a no-ff merge of that head, `codeflow ci --base <tip> --head <candidate>` shall raise no `work.criteria_frozen` finding and shall print a note naming T AC-4; evidence: a CLI fixture of the issue's repro, failing before the change with `work.criteria_frozen` for T AC-4 and passing after. (serves EPC-022 AC-47)
- AC-3 The same task head shall get the same verdict through the task's own PR range (`--into <line>`), through the landing candidate in `codeflow ci`, and through a real push of the candidate to the line; evidence: the AC-2 fixture through each form, passing in all three after the change.
- AC-4 `codeflow ci` shall still refuse each of these for the landing candidate, naming the cause: (a) a change to another task's criteria in the merge; (b) a criteria change made by a non-merge commit on the candidate; (c) a merge whose result differs from the clean merge of its parents in a criterion; (d) a task whose record does not declare the line as its target at the line tip and at the second parent, or whose epic fails the trusted-line binding (missing, cancelled or archived); (e) a task that already has a completion on the line or on the default target (the reopen freeze); (f) a changed criterion with no dated amendment note; (g) any change to an epic record's criteria; and (h) history that cannot be read, a shallow history or a missing object; evidence: one fixture per refusal (eight), each refused before and after the change for the stated reason, except AC-2's shape.
- AC-5 The rule shall bind to exact commits and trusted records: a head branch named like a task or like `integration/...` on a destination that is not a confirmed line, a second parent that is not reachable from the candidate through a merge, and a task identity taken only from the checkout or a flag shall each grant nothing; evidence: one fixture per case, each refused after the change.
- AC-6 The refusal remedy and `docs/delivery.md` shall say where a task's own criteria change lands (its own PR, then its landing candidate) and shall not send an adopter to a batched amendment for a change this rule accepts; evidence: a remedy text test and the `docs/delivery.md` diff.
- AC-7 (journey) With the built binary in a scratch full-tier repository with one integration line, the issue's four steps shall pass `codeflow ci` on the candidate, and the AC-4 (a) variant shall be refused; evidence: both runs, quoted in the PR body. (serves EPC-022 AC-47)
