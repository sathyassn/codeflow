# TSK-1416: The strict text rule accepts a variable whose value the same line spells literally

## Description

Under the default `security.text_guard: strict`, exec-guard refuses any run-time word it cannot resolve. That includes a loop variable or a variable assigned a literal value earlier on the same line, even when the command that uses it only reads. Agents hit this refusal many times a day on ordinary read-only lines, such as a loop over a fixed list of pull request numbers or a branch name set once and then used in an API path. The refusal is correct as the rule is written today (TSK-1073 AC-7, AC-21, AC-23, AC-34, AC-35 and AC-37 require it), and the relaxed policy route needs a remote default branch, which some checkouts do not have.

This task narrows the strict rule for one class only. A variable counts as resolved under strict when the same line gives it a literal value, in a `for` header over literal words or in a `NAME=<literal>;` assignment, and no command runs between that definition and the use. A pipeline element counts as a command in between. The value is then judged exactly as if the literal were written in place of the variable, by every rule that would judge the literal.

The narrowing never reaches a write target or an interpreter operand that the literal would make an enforcement path, and it never resolves a value the shell could change before the use. Every other run-time word keeps today's strict refusal.

Non-goals: the relaxed policy mode; directory changes, which stay an unknown directory as TSK-397 decides; any resolution wider than TSK-1073 AC-7's scoping rules; and the other refusal classes in the 2026-11-10 classification, which are owned by TSK-1073 and TSK-1408.

## Outcome

After this merges, an agent working under the strict default can run a read-only command over a loop of literal values, or with a variable it set to a literal on the same line, without a refusal. Every form the strict rule refuses today for a reason other than "the value is unknown" stays refused.

## Acceptance Criteria

- AC-1 Before any code change, the builder shall record in `## Findings` the strict rule's current path for a run-time word (where a word becomes tainted, where the first tainted word is refused, and which TSK-1073 criteria pin each refusal), and the list of refusal reasons that must survive this change; evidence: the Findings section committed before the first code change.
- AC-2 Under the strict default, exec-guard shall allow a read-only command that uses a loop variable from a `for` header over literal words, and a read-only command that uses a variable assigned a literal by `NAME=<literal>;` with no command between the definition and the use; evidence: one guard test per form, each failing on the base binary and passing after.
- AC-3 Under the strict default, each of these shall stay refused under `security.text_guard`: a variable with no assignment on the line, a value from a command substitution, a value containing a glob, a definition with any command between it and the use (a pipeline element included), and a line where a trap or an alias could run code before the use; evidence: one guard test per class, each refused on the base binary and after.
- AC-4 A value accepted under AC-2 shall be judged by every other rule as if the literal were written in place of the variable, so a literal that names an enforcement path, a protected path or a write target gets the same verdict as the written literal; evidence: tests that pair each such literal written in place with the same literal given through a variable, with equal verdicts, including at least one interpreter operand and one write target.
- AC-5 TSK-1073 AC-21 and AC-23 shall hold unchanged: their lines still get from exec-guard the strict refusal of the run-time operand, and the relaxed and git-guard verdicts those criteria name; evidence: TSK-1073's tests for AC-21 and AC-23 passing unchanged, with no edit to their assertions.
- AC-6 A replay of TSK-397's corpus (`crates/codeflow-cli/tests/text_guard_invariant.rs`, as TSK-1073 AC-8 extends it) against the base binary and the new binary shall show only refusals that move from refused to allowed under AC-2's class, and no allowed line that becomes refused; evidence: the replay output in the pull request body, with each changed line classed.
- AC-7 (journey) On the installed candidate in a scratch checkout under the strict default, an agent session shall run one accepted form of each kind and have one control of each AC-3 class refused, with the refusal message naming `security.text_guard`; evidence: the session's guard output pasted in the pull request body.
