# TSK-1275: Each guard call finishes quickly on a loaded host without changing what it refuses

## Description

Every Bash call in every session runs `codeflow hook exec-guard`, so its wall time is paid on every command, by this project and by adopters. On a loaded host three `exec-guard --contract 3` processes were seen running for 2, 18 and 27 seconds at 43 to 53% CPU. TSK-1258 bounds the glob matcher and stops a full cache recompiling; its stack sample put 229 of 283 samples in `regex::Regex::new` under `pattern::matches_extended_glob`, reached from `secret_path_spelling` via `real_secret_path`. Builds on TSK-1258; depends_on is added when TSK-1258's record lands on EPC-022. This task measures a baseline for each guard call, sets a latency target, and removes the remaining cost beyond TSK-1258 without changing what any guard refuses. Non-goal: relaxing, skipping or caching away a refusal to gain speed.

## Baseline

Measured 2026-11-03 at line tip d2752c69d, on the worktree's own builds. Each cell is 10 runs per hook, input and priority (normal, and under `nice -n 10`), on one host that other sessions were loading. Inputs: `ls`, `git status`, a 7-stage pipe, `cat secrets/prod/api.key` (refused, exit 2) and a heredoc. Raw rows with load and idle are in the task worktree's `.state/guard-latency-*.json`.

| Build and hook | Median range over inputs | Worst single run | Host during the block |
|---|---|---|---|
| release, exec-guard | 136 to 202 ms | 597 ms (first run of the first cell), otherwise 239 ms | load 14 to 21, idle 35 to 74% |
| release, git-guard | 137 to 232 ms | 250 ms | load 9 to 14, idle 49 to 83% |
| debug, exec-guard | 182 to 267 ms | 298 ms | load about 13 |
| debug, git-guard | 190 to 352 ms | 571 ms | load about 13 |
| debug at the TSK-1258 worktree (exec-guard only; build was dirty) | 194 to 270 ms | 379 ms | load about 13 |

Where the time goes (one `sample` of a release `exec-guard` for `ls`):

- Every call spends about 113 of its roughly 123 busy milliseconds before it reads stdin, in `project_root` > `RepoInfo::discover` > `checked_registration` > `read_registration` > `open_checkout` > `git2::Repository::open`.
- Most of that is libgit2 parsing the shared `.git/config` (18 KB, 171 sections), loaded more than once. The file holds no worktree entries (those live under `.git/worktrees/`); it is mostly 168 `[branch]` sections, 94 of them for branches that no longer exist locally. Pruning them is separate cleanup work that the Director routes, not part of this task.
- Work after stdin is read, which includes the judgement, is under 10 samples for `ls`.
- No regex compile showed for `ls`. The `secret_path` input was not sampled, so the TSK-1258 regex cost is not re-measured here.
- Consequence: the floor is about 135 ms even for `ls`, above the AC-2 median target of 100 ms, so the fix must cut the repository open, not only the glob cache.

## Design direction

Guards are security code, so secure defaults apply.

- Cheapen the repository open; do not skip it by command class. Open the repository lazily, only when a rule needs repository state, or cache the parsed result keyed by the identity of the repository's `config` file (device, inode, size and modification time). When the guard cannot be sure a cached value is current, it reopens (fail closed).
- A skip list of commands that need no repository decides trust from text the requester controls. It is out of scope unless the first option cannot reach the target, and then it needs its own security design and a cross-lineage review before it is built.
- Measure the median and p95 before and after, on this repository and on a small fixture repository, and record both in the PR.
- The fix meets the target on its own, however large the repository's config file is. An adopter's config grows the same way (VS Code, for example, writes `vscode-merge-base` sections), so the fix never relies on pruning branch sections.
- The worst case is measured next to the small fixture: this repository's config (168 `[branch]` sections, 18 KB) or a fixture of that size.

## Outcome

After this merges, every session on a loaded host pays a bounded, measured cost per guard call, and the guards refuse exactly what they refused before.

## Acceptance Criteria

- AC-1 The baseline is recorded for 5 or 6 representative hook inputs (a plain `ls`, a `git status`, a long piped command, a command naming a path under a secrets-like directory, a heredoc), each timed 10 times at normal priority and 10 times under nice 10, on the release build and on the debug build seats use, with median, max, host load and idle, and a profile of the slowest input naming where the time goes (regex compile, policy load, filesystem walks or git calls). Evidence: the saved raw numbers and the profile.
- AC-2 The target is a median under 100 ms, a p95 under 250 ms and a max under 500 ms per guard call on the release build under the same load, because a call that costs more than a few perceived frames or a half second is felt on every command. It is measured with the AC-1 method on a small fixture repository and on the worst case (a config of this repository's size, 168 branch sections and 18 KB, either this repository or a fixture), before and after, with the target met on both without pruning any branch section, and every set is recorded in the PR. When the baseline shows another figure is realistic, the PR states the figure and the reason. Evidence: the same inputs and method, timings at the base and at the head on both repositories.
- AC-3 Fail-closed behavior is unchanged. Every existing guard refusal test passes, and a differential run over the AC-1 inputs and the refusal test corpus shows no input that refuses at the base is allowed at the head. Evidence: `cargo test -p codeflow-core` guard and hook tests, and the differential result.
- AC-4 A sibling sweep covers git-guard and the other hooks on the same path (policy load, glob compile, repository lookup, filesystem walks) and records each as fixed or not affected with a reason. Evidence: the sweep table in the PR body.
- AC-5 A changelog entry states the latency change. Evidence: `CHANGELOG.md` diff.
- AC-7 The hooks_cli test `shell_expansion_chains_have_bounded_guard_time` keeps its purpose, proving guard time grows linearly with chain length and not worse, and its measurement holds under load. It failed a coverage rerun on a 9-worker host: the `eval` chain at N=80 took 10.8035 s against a bound of 10.7941 s (6 times the N=20 control of 1.4657 s, plus 2 s), 9 ms over, while the same tree passed in the full gate. The control and chain runs interleave, each size takes the median of repeated runs, and the test compares growth ratios, not one wall-clock ratio. The bound is not loosened to a constant that would hide a real superlinear regression. Evidence: the test passes 20 of 20 repeated runs under coverage at jobs=9, with the run count and the observed ratios recorded; a test or recorded check shows a quadratic chain still fails the bound; the failure reproduces before the fix and passes after, where that is reproducible. The failing log is `c3a-journey.txt` (sha256 prefix 597f54cc).
- AC-6 A cached repository state is used only when the identity of the repository's `config` file (device, inode, size and modification time) matches the identity recorded with it, and a mismatch or an unreadable identity reopens the repository. Evidence: a test that edits the config between two guard calls and sees the second call use the new content, and a test that an unreadable identity reopens.
