# TSK-1275: Each guard call finishes quickly on a loaded host without changing what it refuses

## Description

Every Bash call in every session runs `codeflow hook exec-guard`, so its wall time is paid on every command, by this project and by adopters. On a loaded host three `exec-guard --contract 3` processes were seen running for 2, 18 and 27 seconds at 43 to 53% CPU. TSK-1258 bounds the glob matcher and stops a full cache recompiling; its stack sample put 229 of 283 samples in `regex::Regex::new` under `pattern::matches_extended_glob`, reached from `secret_path_spelling` via `real_secret_path`. Builds on TSK-1258, which is complete on `main`. This task measures a baseline for each guard call, sets a latency target, and removes the remaining cost beyond TSK-1258 without changing what any guard refuses. Non-goal: relaxing, skipping or caching away a refusal to gain speed.

Target moved to `main` on 2026-11-12 (the Director's ruling of 2026-11-11, 22:52 EST, under the epic delivery plan (ADR-0102, proposed): the EPC-022 line takes no new work, and a task still `todo` with no pull request into the line moves to `main`). Until then this record existed only on its task branch (`task/TSK-1275-each-guard-call-finishes-quickly-on-a-loaded-hos` at 4127af9fc), whose design, baseline and measurement commits stay there for the builder. The TSK-1258 edge, deferred until TSK-1258's record landed, is added now that it is complete on `main`. Owner: coord/catalog, which adds the readings of 2026-11-11 as evidence.

## Baseline

Measured 2026-11-03 at line tip d2752c69d, on the worktree's own builds. Each cell is 10 runs per hook, input and priority (normal, and under `nice -n 10`), on one host that other sessions were loading. Inputs: `ls`, `git status`, a 7-stage pipe, `cat secrets/prod/api.key` (refused, exit 2) and a heredoc. Raw rows with load and idle are in the task worktree's `.state/guard-latency-*.json`.

| Build and hook | Median range over inputs | Worst single run | Host during the block |
|---|---|---|---|
| release, exec-guard | 136 to 202 ms | 597 ms (first run of the first cell), otherwise 239 ms | load 14 to 21, idle 35 to 74% |
| release, git-guard | 137 to 232 ms | 250 ms | load 9 to 14, idle 49 to 83% |
| debug, exec-guard | 182 to 267 ms | 298 ms | load about 13 |
| debug, git-guard | 190 to 352 ms | 571 ms | load about 13 |
| debug at the TSK-1258 worktree (exec-guard only; build was dirty) | 194 to 270 ms | 379 ms | load about 13 |

Where the time goes (one `sample` of a release `exec-guard` for `ls`):

- Every call spends about 113 of its roughly 123 busy milliseconds before it reads stdin, in `project_root` > `RepoInfo::discover` > `checked_registration` > `read_registration` > `open_checkout` > `git2::Repository::open`.
- The registration loop in `RepoInfo::discover` (`repo.rs:120`) validates every registered worktree before policy selection, and each present registration opens its checkout, so each open loads configuration. This repository registers about 90 worktrees, which is the amplification; an adopter with two worktrees pays about two. The sample shows 94 samples under `checked_registration` and 68 under the registration's open, which supports repeated opens as a substantial cost. It does not give an exact open count or isolate configuration parsing as the whole cost, so both are measured in the work (AC-2). The shared `.git/config` (18 KB, 171 sections) is what each open parses. The file holds no worktree entries (those live under `.git/worktrees/`); it is mostly 168 `[branch]` sections, 94 of them for branches that no longer exist locally. Pruning them is separate cleanup work that the Director routes, not part of this task.
- Work after stdin is read, which includes the judgement, is under 10 samples for `ls`.
- No regex compile showed for `ls`. The `secret_path` input was not sampled, so the TSK-1258 regex cost is not re-measured here.
- Consequence: the floor is about 135 ms even for `ls` on this repository, above the AC-2 median target of 100 ms, so the fix must cut the cost of the registration loop, not only the glob cache.

- The p95 column is the second largest of 10 runs.
- Opens per call equal the sibling count plus a fixed 6 (exec-guard) or 10 (git-guard); config size does not change the count.
- Each sibling is opened once (`repo.rs:1029`). The repeats are discovery (`repo.rs:238`, `repo.rs:244`: 3 each for exec-guard, 5 each for git-guard). Removing the repeats saves 4 (exec-guard) or 8 (git-guard) opens, about 4% at 90 worktrees, so it is a small sound gain alone.
- Time grows with siblings times config size: at 90 worktrees the 18 KB config adds about 77 ms over the small one. The remaining gain has to come from the per-sibling check, within the equivalence table.
- Cleanup input (the operator owns any prune): at 91 registered worktrees the registration loop is 92 of 99 opens; about 30 would cost about a third as many.
- Inside the Claude Bash sandbox, one guard call at the codeflow root took 1.5 to 1.7 s on 2026-11-12, against 257 to 362 ms outside it, because the sandbox checks every file operation (coord/catalog, workspace `coordination/coordinators/capabilities/notes/tsk1275-state-2026-11-12.md`). AC-8 makes the file-operation count and the sandboxed cost part of the target.

## Design direction

Guards are security code, so secure defaults apply.

Revised after the Codex plan challenge at c38aa083e (three major findings, all accepted).

- **No reuse between calls.** A successful validation is never carried from one guard call to the next. No unforgeable on-disk key exists: a device, inode, size and modification time tuple survives a same-length edit with a restored time, and includes, `config.worktree`, registration pointers and ownership change without touching the config file. A stored verdict with a content hash beside it does not authenticate the verdict, and a protected signer is disproportionate. Memoizing inside one invocation stays, as `RepoFactsScope` (`edit_guard.rs:988`) already does, including cached registration errors.
- **Sibling worktrees are still validated.** Skipping them is not equivalent: discovery validates them before policy selection, and `checkout_roots` and `protected_paths` (`edit_guard.rs:782`) protect sibling enforcement files, markers and absent registered checkout locations. A skip list of commands that need no repository decides trust from text the requester controls and is out of scope.
- **Replace an open only where the rejection is proven the same.** Before any call to `Repository::open` is replaced, a table in the PR lists each thing the open checks and says whether it stays per checkout, is safely shared across siblings, or keeps a full open. The rows, from the challenge (libgit2 1.9.6, `repository.c:1107`): marker parsing and path resolution; repository structure (HEAD present, common directory, objects and refs); linked-worktree classification; configuration loading (local, enabled `config.worktree`, global and system, includes evaluated per sibling); repository format, extensions and `core.bare`; grafts and shallow files; ownership with `safe.directory`. Anything not proven equal keeps a full open. Rejection behavior is the same before and after.
- **Candidates, in order of preference.** (1) Remove opens that repeat inside one invocation (for example the second open of the common directory) after counting the opens per call. (2) Share only the checks the table proves shared. Parallel validation was considered and dropped: `RepoFactsScope` is thread-local (`edit_guard.rs:958`), so worker threads would not populate the caller's facts, later protection checks would reopen the registrations, the validate-once test (`repo.rs:1409`) would break and the saving would be lost; it would also add threads on a loaded host.
- **Race and forgery contract.** Keep the two-way pointer checks, the physical common-directory identity, valid directory-marker aliases and proven-absence handling. A permission error, a dangling link or ambiguous metadata is never treated as absent. Reads are bounded and special files are rejected without blocking. The PR states how a replacement during validation is detected; neither the current sequence nor a filesystem read gives an atomic snapshot, so the design names what is rechecked. libgit2's registration listing filters entries, so no claim is made about every odd entry.
- **Honest outcome.** If equivalence leaves the saving too small to reach the target, the PR says so with numbers and states the smaller sound gain. A smaller sound gain is better than a fast unsound one.
- **Do not rely on pruning.** The fix meets the target on its own, without pruning, on every cell of the measured matrix (worktree count by config size); the honest-outcome clause governs any cell it cannot reach. An adopter's config grows the same way (VS Code writes `vscode-merge-base` sections).

### Per-check equivalence table for a sibling open

Source: libgit2 1.9.6 `git_repository_open_ext` (`repository.c:1107`) as `Repository::open` calls it through `open_checkout` (`repo.rs:1029`). Cost split from the measurements above: parsing configuration (the 18 KB local config alone adds about 0.8 ms per open in the debug fixtures, the global and system files are read on every open) is the larger part; the structural and ownership checks are stat calls.

| Check libgit2 makes on open | Inputs | Decision for a sibling |
|---|---|---|
| Find the repository (`find_repo`): gitfile parse, relative paths, HEAD, objects and refs present | the sibling's marker, admin directory, common directory | Per checkout. Today's `read_registration` already checks the pointers both ways and the common directory identity. A replacement must repeat the HEAD, objects and refs presence checks and the gitfile syntax, or keep the open. |
| Linked-worktree classification (`repo_is_worktree`, `repository.c:1084`) | gitdir differs from commondir; `gitdir` file exists | Per checkout, two stats. Safe to do directly. |
| Load configuration (`obtain_config_and_set_oid_type`): local, `config.worktree` when `extensions.worktreeConfig` is on, global, system, XDG, includes with conditions | the common config, the sibling's admin directory (its `config.worktree`), the sibling's own gitdir for `includeIf gitdir:` and `onbranch:` | Shared only when the common config has no `include`, `includeIf` or `extensions.worktreeConfig` key and the sibling's admin directory has no `config.worktree`; then every sibling of one physical common directory sees the same files, and one full open of any of them in this invocation has shown libgit2 accepts them. Otherwise per checkout, full open. |
| Format and extensions, object format, `core.bare` (`load_config_data`) | values from the configuration above | Shared under the same condition as configuration loading, since the values are the same. |
| Work directory (`load_workdir`) | the sibling's `gitdir` link and `core.worktree` | Per checkout. Already validated two ways by `read_registration`; `core.worktree` present means full open. |
| Grafts and shallow (`load_grafts`, `repository.c:877`) | `info/grafts` and `shallow` under the common directory | Shared through the common directory, so covered only by a full open of a sibling of the same physical common directory in this invocation (see the gate below). |
| Ownership (`validate_ownership`, `repository.c:668`) | owner of the work directory, the gitfile and the gitdir, then `safe.directory` in global configuration when an owner differs | Per checkout. A direct check can only accept the case where all three paths are owned by the current user; any other owner, any error, or a non-Unix host keeps the full open, so `safe.directory` and sudo handling stay libgit2's. |
| Namespace (`repo_load_namespace`) | `GIT_NAMESPACE`, only with the from-env flag | Not used by `Repository::open`; no action. |

The gate. The first sibling of each physical common directory (the canonical directory its `commondir` file resolves to, which must also be the parent of its registration directory) always takes the full open. Only after that open succeeds, and only if the sibling's own facts hold, is the common directory marked proven for the rest of this invocation. Later siblings of the same common directory skip the open when their own facts hold. The current checkout's open is not relied on: a registration directory can be reached through a symlinked `worktrees` directory, so its common directory need not be the one the current checkout opened. The mark lives in `PROVEN_COMMON`, which exists only inside a `RepoFactsScope` and is dropped with it; outside a scope every sibling is opened.

Why a skipped open cannot miss a rejection, row by row (p3R finding 1):

| Rejection the open can make | Why the skip cannot miss it |
|---|---|
| Repository format version and extensions, object format | They are read from the common config. The gate's full open of a sibling of the same physical common directory accepted that file; the skipping sibling reads the same file and only qualifies when the file has no `include`, `worktree` or `bare` word. |
| `core.bare` and `core.worktree` | Any config containing `bare` or `worktree` keeps the full open, and so does a sibling with a `config.worktree` file. The work directory of a skipped sibling is the parent of its marker, which the two-way gitfile and registration checks have proven. |
| Shallow and grafts | Files under the common directory, one set per physical common directory; the gate's full open loaded them. A change between the two opens inside one invocation is the same race the invocation-local memoization already accepts. |
| Conditional includes (`includeIf gitdir:` and `onbranch:` differ per sibling) | Any `include` word in the common, global, XDG or system file keeps the full open, so no skipped sibling has an include whose condition could differ. |
| `config.worktree` and `extensions.worktreeConfig` | A present `config.worktree` in the sibling's registration directory keeps the full open; the word `worktree` in any shared config does too. |
| Ownership and `safe.directory` | The skip needs the effective user to own the work directory, the gitfile and the registration directory. Any other owner, any stat error or a non-Unix host keeps the full open, so `safe.directory` and elevated-user handling stay libgit2's. |
| Marker syntax, relative paths, directory markers, path-length failures | Only an exact `gitdir: <absolute path>` regular gitfile qualifies; a relative target, a directory marker, a symlink or any parse doubt keeps the full open. |
| Repository structure (HEAD, objects, refs, `commondir`) | Each is stated by a no-follow stat or a bounded read of a regular file or directory; a symlink or special file keeps the full open. |
| Linked-worktree classification and common directory identity | The `gitdir` and `commondir` regular files exist, `commondir` resolves to the physical parent of the registration directory, and the same path comparison `read_registration` makes today passes. |
| A rejection the table does not list | Not skipped: every condition above is required, and any failure runs today's open and returns today's error text. |

What the table allows. A sibling skips its open only when every row's condition holds; each failed condition keeps today's full open and its error text. The shared rows are decided once per invocation from the common config's bytes and are never carried to the next call (AC-6). What the table does not allow: skipping a sibling, trusting pointer files alone, or any cross-call reuse.

Finding from the build (phase timers, debug build, 90 worktrees, 18 KB config): a skipped sibling open cut `Repository::open` calls from 95 to 7 per call but did not cut the time. The 90-sibling loop stayed at 150 to 190 ms, of which 0.5 to 3 ms per sibling is in `registered_marker`. Cause: on macOS `normalize_case` (`edit_guard.rs`) lists the whole parent directory for every resolved path component, so 90 siblings under one `.worktrees/` directory cost a quadratic number of entry comparisons, each with Unicode folding. Path-prefix results were already kept per invocation (`resolved_component`); the listing was not. The change keeps one listing per parent directory inside `RepoFactsScope`, folds each entry name once, and re-reads the directory once if the kept listing does not yield the entry, so a stale listing can only cost time. One invocation's resolution was never atomic (each component is a separate filesystem call), so the kept listing adds no new race; nothing is kept between calls. The listing must now complete before a match is used, where the old loop stopped at the first match, so a directory entry that cannot be read refuses in one more case (fail closed). The sibling open skip is kept only if it still pays after this change; otherwise it is dropped and this table stays as the record of why.

Open question for the build to answer with numbers: after the conditions, how much of the 1.1 to 1.9 ms per sibling is configuration parsing (removed) and how much is the remaining structural work (kept). If the saving at 90 worktrees and an 18 KB config does not reach the AC-2 target, the PR states the smaller sound gain.

## Acceptance Criteria

- AC-1 The baseline is recorded for 5 or 6 representative hook inputs (a plain `ls`, a `git status`, a long piped command, a command naming a path under a secrets-like directory, a heredoc), each timed 10 times at normal priority and 10 times under nice 10, on the release build and on the debug build seats use, with median, max, host load and idle, and a profile of the slowest input naming where the time goes (regex compile, policy load, filesystem walks or git calls). Evidence: the saved raw numbers and the profile.
- AC-2 The target is a median under 100 ms, a p95 under 250 ms and a max under 500 ms per guard call on the release build under the same load, because a call that costs more than a few perceived frames or a half second is felt on every command. It is measured with the AC-1 method on a matrix that varies the number of registered worktrees (for example 2, 30 and 90) together with config size (a small config and one of this repository's size, 168 branch sections and 18 KB), using this repository and fixtures, before and after, with the target met on every cell without pruning any branch section, and every set is recorded in the PR with the p95 as well as the median. The PR also records the number of repository opens per call before and after. When the baseline shows another figure is realistic, the PR states the figure and the reason. Evidence: the same inputs and method, timings at the base and at the head on both repositories.
- AC-3 Fail-closed behavior is unchanged. Every existing guard refusal test passes, and a differential run between pinned base and head binaries compares exit decisions and refusal causes, and keeps the allowed controls and recovery commands. The corpus includes the codeflow-cli hooks_cli tests and their fixtures (for example `checkout_identity_main_checks_each_registration`, `checkout_identity.rs:196`) and crosses main, linked and retargeted invocation with: existing refusal and recovery fixtures, including writes to sibling protection files; conflicting pointers, foreign common directories, symlink aliases and loops, native relative paths and non-UTF-8 names; sibling-specific `config.worktree`, conditional includes, ownership exceptions, malformed graft and shallow files, unreadable and special files; same-identity config changes, included-file-only changes and registration changes between calls; and replacement during validation and after an invocation-local entry is populated. The per-check equivalence table of the design direction accompanies it, since a finite corpus supports the invariant and does not prove it. Evidence: `cargo test -p codeflow-core` and `-p codeflow-cli` guard and hook tests, the differential result, and the table.
- AC-4 A sibling sweep covers git-guard and the other hooks on the same path (policy load, glob compile, repository lookup, filesystem walks) and records each as fixed or not affected with a reason. Evidence: the sweep table in the PR body.
- AC-5 A changelog entry states the latency change. Evidence: `CHANGELOG.md` diff.
- AC-7 The hooks_cli test `shell_expansion_chains_have_bounded_guard_time` keeps its purpose, proving guard time grows linearly with chain length and not worse, and its measurement holds under load. It failed a coverage rerun on a 9-worker host: the `eval` chain at N=80 took 10.8035 s against a bound of 10.7941 s (6 times the N=20 control of 1.4657 s, plus 2 s), 9 ms over, while the same tree passed in the full gate. The control and chain runs interleave, each size takes the median of repeated runs, and the test compares growth ratios, not one wall-clock ratio. The bound is not loosened to a constant that would hide a real superlinear regression. Evidence: the test passes 20 of 20 repeated runs under coverage at jobs=9, with the run count and the observed ratios recorded; a test or recorded check shows a quadratic chain still fails the bound; the failure reproduces before the fix and passes after, where that is reproducible. The failing log is `c3a-journey.txt` (sha256 prefix 597f54cc).
- AC-6 No successful validation or repository state is reused between guard calls; reuse is limited to one invocation, and a cached registration error stays cached only for that invocation. Evidence: a test that changes the config (same length with a restored modification time), an included file, a `config.worktree` and a registration between two calls and sees the second call judge the new state, and a test that a replacement during validation is detected or refused as the design states.
- AC-8 For each supported harness (Claude, Codex and Grok), the PR shall state whether that harness runs the guard hooks inside its sandbox, established from the harness's documentation or an observed run. The PR shall also count the file operations of one guard call at each AC-2 matrix cell, before and after, and state a sandboxed-cost target with its basis. Evidence: the per-harness table with its source, the counts, and sandboxed timings beside the AC-2 figures.
