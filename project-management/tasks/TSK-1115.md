# TSK-1115: Python runs under the gate resolve only from the lock

## Description

Issue #275's comment of 2026-10-29 reports what two adopting repositories
built because CodeFlow has no equivalent (lessons 8 and 9, custom parts 2
and 5): a locked-environment launcher and inline-script admission. Strict
results differ between machines and CI unless every Python run under the
gate resolves from one lock; and PEP 723 `# /// script` blocks let
`uv run --script` resolve packages outside the lock, through `[tool]`
tables (index, source, override, constraint and dependency-metadata keys)
or unpinned packages. TSK-426's Description lists "a locked tool
environment" for Python and no criterion defines it.

This task ships the launcher contract with `cf-stack` for Python and the
admission rule in the gate: `prepare` is the only network step
(`uv sync --locked --no-build --no-cache` with an environment allowlist,
refusing index and source overrides); `run` works offline and checks an
identity stamp (lock, manifests, Python and uv identity), failing with the
prepare command when the stamp is stale; the strict targets call prepare
then run; the trusted admission job uses the authority's launcher; and a
tracked Python file whose inline metadata holds any `[tool]` table or a
package not exactly pinned, registered and present in the root lock is
refused, with exemptions only through TSK-424's register. Other languages
get the contract as documentation where the adopter's tool has a locked
mode (`npm ci`, `cargo --locked`); the shipped launcher is Python's.

## Outcome

After this merges, an adopter's Python checks under the gate resolve packages only from the lock, on every machine and in CI, and an inline script cannot pull a package the lock does not hold.

## Deliverables

- the launcher: `assets/base/testing/launcher/cf-python-env.py` (standard library only; `prepare` and `run`), its `cf-stack` setup in `assets/base/skills/cf-stack/SKILL.md` and the Python profile resources, both mirrors byte-identical
- the inline-metadata admission check: `crates/codeflow-core/src/gate/inline_metadata.rs` (new) wired into the strict Python target of `.codeflow/test-config.json` templates
- the authority-side use: the trusted verdict job reads the launcher and lock from the authority (TSK-336, TSK-1103); `docs/test-gate.md` and `docs/policy-reference.md`
- CodeFlow's own `scripts/` and vendored Python under the contract, or admitted rows in the TSK-424 register with fix tasks
- tests: launcher tests (stale stamp, network refused in run, override refused), admission fixtures (a `[tool]` table, an unpinned package, a pinned package absent from the lock, a clean block), the `cf-stack` fixture run
