# TSK-367: A bounded mutation campaign proves the enforcement tests catch weakened checks

## Description

Source: both test integrity audits of 2026-10-17 at
`eaf2ed04e932186cdd26dc4a7e5740cc553acee3`. Line coverage of the
enforcement modules is high (for example `hooks/git_guard.rs` 95.89,
`hooks/policy.rs` 99.30 and `workgraph/acceptance.rs` 94.06 percent in run
`8b201fe4-2175-47a7-b3b8-1ac6961dfc71`), but coverage counts execution, not
whether a test fails when a check is weakened. No mutation run exists.

Each audit named ten probes, sites where a weakened check would most
likely survive. Merged and deduplicated, with the task that owns a fix

Outcome: a first, bounded mutation campaign over the enforcement code
(hooks, guards, policy, acceptance binding, ids, CI judgement and secret
scanning) records killed, surviving, equivalent and unexercised mutants
against one exact revision, and every surviving material mutant gets a
regression that fails before its repair and passes after.

The tool is chosen inside the task: `cargo-mutants` or an equivalent,
after checking its maintenance (recent releases, open security advisories)
and its safety (it runs copies of the code under test; it runs inside the
sandbox on a scratch copy, never on the shared checkout, never with
credentials in its environment). Installing it follows the operator's
normal tool-adoption decision.

This task does not add a standing gate. Whether mutation testing becomes a
recurring gate, and on which paths, is the operator's decision after this
campaign, taken on its measured run time and findings.

Product surface: this repository's tests; product code changes only where
a surviving mutant shows a real defect, each named in the pull request.

## Deliverables

- the campaign record: tool, version, configuration, exact revision, modules, mutant counts by outcome, run time and machine, per-probe result (provisional home `docs/verification/mutation-campaign-2026-10.md`; the builder confirms)
- regressions: tests beside the code they protect, one per surviving material mutant
- the configuration used, if kept for a rerun: provisional `.cargo/mutants.toml`
- the decision input for the operator: measured cost and findings, in the record and the pull request

## Acceptance Criteria

- AC-1 The campaign shall run over `crates/codeflow-core/src/hooks/`,
  `src/security/`, `src/workgraph/acceptance.rs`, the ids registry code,
  `crates/codeflow-cli/src/cmd/ci/` and the secret scan, at one recorded
  revision, and record each mutant's outcome and the total run time;
  evidence: the campaign record and the tool's output. (serves EPC-023 AC-24)
- AC-2 Every probe in the table above shall have a recorded result:
  killed with the killing test, fixed by its owning task with that task's
  regression, or surviving with a new regression from this task;
  evidence: the per-probe table in the record.
- AC-3 Each surviving mutant judged material shall get a regression that
  fails on the mutant and passes on the repaired code, and each surviving
  mutant judged equivalent or immaterial shall carry a one-line reason;
  evidence: the fail-before and pass-after runs. (serves EPC-023 AC-24)
- AC-4 The record shall state the tool's maintenance and safety check and
  that the run used a scratch copy without credentials; evidence: the
  record and the tool version.
- AC-5 The record and the pull request shall state that a standing
  mutation gate is the operator's decision, with the measured cost per run
  and per changed file; evidence: the text and the campaign run. (journey)
