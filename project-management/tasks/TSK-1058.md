# TSK-1058: The Monitor tool is judged like every other shell tool

## Description

This is a planning draft accepted from the TSK-397 design note, revision 4.1, Part C (pull request 331), where it is unit U5 (`Monitor` matcher). The note called the unit 3.3.0; the release is 4.1.0. Part C is accepted as planning drafts only: the criteria below are drafts, and this unit takes its own whole-unit review when it is built. Part C decisions (i) to (v) apply: (i) explicit non-secret enforcement-file arguments are allowed on a qualified host under attested `W-enforcement`, and the secret-read classes override, never a file name; (ii) a patch update invalidates a record, because exact executable digests bind it and a changed binary is `Unknown` until the operator re-runs the ceremony; (iii) managed settings are a design requirement for qualification, not a vendor fact; (iv) no exclusion matcher ever, so a non-empty `excludedCommands` disqualifies and route A+ is dropped; (v) the ceremony runs through the Bash tool, never the `!` prompt, and its evidence is receipts, not operator attention.

Every tool that runs shell text must be judged by the guards. The `Monitor` tool runs shell text, so it must be judged like `Bash`. This unit confirms the tool's input shape and makes the guard matcher cover it in the three presets; whether any preset leaves it unjudged today is the first thing AC-1 establishes.

Edges: none.

## Outcome

after this merges, an operator can rely on git-guard refusing a command given to the `Monitor` tool in the same way as one given to `Bash`.
