# TSK-405: A resolved update conflict does not come back on the next update

## Description

Issue: #74, its comment of 2026-10-13 only. When `codeflow update` hits a conflict in a managed file the project customised, it writes `<file>.new` and a report note, but keeps the old shipped baseline and manifest hash (`crates/codeflow-core/src/scaffold/update.rs:818`, the `ManagedStep::Conflict` arm; the clean-merge arm at `:809` records the new shipped hash and baseline). After a person resolves the `.new` and replaces the file, the next update merges against the old base, sees the previous release's upstream changes as project changes and conflicts again on the same hunks. The adopter's workaround is to re-resolve the same conflict on every update; a project that customises its CI workflow hits it every release.

The Codex review of PR 249 reproduced it with this worktree's binary (`target/review-PR249-update-conflict-02.txt` in the planning worktree): after a simulated resolution the second update exits 2 and recreates the same conflict. In a control, setting only the existing baseline and manifest hash to the pristine candidate, with the person's file kept, made the next update exit 0 and keep the project's change, with no format change.

Outcome: **a person's accepted resolution of an update conflict is recorded against the correct shipped base, so the same conflict does not return on the next update and later upstream changes still merge.**

Invariant: the baseline and manifest hash keep describing shipped content, never the person's merged file. The existing formats stay. The baseline replacement and `codeflow update --plan` stay in 4.0.0 and carry this regression test forward.

The builder chooses how the resolution is recorded (for example, the conflict arm writes the new shipped baseline beside the `.new` and records the resolution as pending, and the next update accepts it only when the `.new` is gone and the file holds no conflict markers; or an explicit resolve step) and records why. Whatever the route, an unresolved or mismatched resolution is never accepted silently.

Added by the EPC-022 amendment of 2026-10-18 after the second Codex review of PR 249 (`target/review-PR249-codex-02.md`, R10), under the operator's rule that every defect that forces an adopter workaround belongs in 3.2.0.

## Acceptance Criteria

- AC-1 When a managed file conflicts, a person resolves the `.new` keeping a project change and replaces the file, and `codeflow update` runs again on the same release, the update shall report the file as kept (user-modified) with no conflict and no `.new`; evidence: the review's reproduction as a test, failing before the change. (serves EPC-022 AC-95)
- AC-2 After that resolution, an update to a later release that changes another part of the same file shall merge cleanly and keep the project change, and one that changes the same hunk shall conflict again against the new base only; evidence: a three-release test.
- AC-3 A `.new` still present, a resolved file that still holds conflict markers, or a baseline or manifest hash that matches neither the old nor the new shipped content shall never be accepted silently: the update shall report it and change nothing; evidence: negative tests per case.
- AC-4 The baseline and manifest hash shall always equal the shipped content of the release they name, never the person's file; evidence: assertions in every test above.
- AC-5 (journey) With the installed build, a scratch project customised at 3.1.1, updated to the candidate with a conflict, resolved by hand and updated again shall keep its customisation with no repeated conflict; evidence: the journey output.
