# TSK-142: local full gate parity on one machine

## Description

On 2026-09-27 the local full gate on the EPC-020 line could not go green
in one run on one machine. `docs-portal` needs Node 24.18.0 (its
`.node-version`) and `cf-present-qualification` needs the official Node
26.4.0 (its `package.json` engines; Homebrew's 26 fails on zlib), and CI
pins each per job while the local gate runs both under one PATH. The
present real-browser check uses `target/debug/codeflow` and ignores
`CARGO_TARGET_DIR`, although `real-browser-check.mjs` honours
`CF_PRESENT_CODEFLOW`, which the gate command does not pass. On Windows,
a killed gate leaves its target processes running and frees the machine
lock, because only Unix tracks the target's process group. A readiness
test failed intermittently. This task makes one `codeflow test --mode
full` invocation reproduce CI on one machine.

Non-goals: the figure-gate test that exceeds 900 s stays with TSK-118,
whose AC-8 names that test as its evidence; the 120 s present handoff
expiry is by design (ADR-0049, planning resolution 20).

## Affected surfaces and interfaces

- `.codeflow/test-config.json` (the `docs-portal` and
  `cf-present-qualification` targets), `scripts/gate-parity.py`, a Node
  version file for the present web package.
- `crates/codeflow-core/src/testing/runner/` and `testing/gate_guard.rs`

- The readiness test named in the Closeout, under
  `workgraph/readiness.rs` or `readiness_journey`.
- Shared files, per SPC-013 R-118: the local gate row (owner TSK-134).

## Acceptance Criteria

- AC-1 When the local full gate runs `docs-portal` and
  `cf-present-qualification` in one invocation, each target shall run on
  the Node version its CI job pins, read from a version file per target,
  and a missing version shall fail that target with a message naming the
  version; evidence: `gate-parity` asserting that the local and CI pins
  agree, and a full gate log on one machine with both targets green.
- AC-2 When the gate runs the present real-browser check, it shall use
  the `codeflow` binary the gate built, wherever `CARGO_TARGET_DIR`
  points; evidence: a gate run with `CARGO_TARGET_DIR` outside the
  worktree in which the check passes, and a `gate-parity` check on the
  target command.
- AC-3 When a full gate is killed on Windows, its running targets shall
  end with it, so the machine lock never frees while a target of the
  killed gate runs; evidence: a runner test on the Windows CI job that
  kills the gate process and finds the target tree gone.
- AC-4 When the readiness test that failed intermittently on 2026-09-27
  runs, it shall pass on every run, with its cause removed rather than
  retried; evidence: the test's name and cause in the Closeout and a log
  of 50 consecutive passing runs under the gate's parallel load.
- AC-5 (journey) In a freshly scaffolded project driven by the installed
  CLI, when a `codeflow test --mode full` is killed during a long target,
  no second full gate shall run beside that target: on Windows the target
  ends with the gate, on Unix the lock stays held until the target's
  process group exits (TSK-134), and the next full gate then takes the
  lock; evidence: a `test_gate_cli` case run on the Windows and Linux CI
  jobs.
