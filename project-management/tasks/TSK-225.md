# TSK-225: Managed CI runs a project setup step, checks a pinned release digest and scans only a change's own commits

## Description

Three defects in the managed CI templates, reported by an adopter for 3.0.0
in sathyassn/codeflow issues 46, 47 and 48, fixed together for 3.1.0 in the
shipped templates under `assets/base/ci/` and the code that installs and
checks them. Non-goal: editing CodeFlow's own live workflows, which agents
may not do; the gitleaks step patch for them is handed to the operator.

Issue 81, found in these files during the work, is fixed here too: the
managed security review read its enforcement levels from the pull request's
own checkout and fell back to `warn`, so a pull request could lower its own
gate. The fix and its sibling sweep (every template, every managed job and
the setup hook) read every enforcement level and exemption from the trusted
commit and fail closed when they cannot be read.

- **Project setup (46).** The gates job runs `codeflow test --strict` on the
  runner's default toolchain, so a project that needs its own toolchain
  either forks the managed file or runs the gate twice. The managed job and
  the shared pinned run of the GitLab, Bitbucket and generic templates now
  source a project-owned `.codeflow/ci-setup.sh`, when the change holds one,
  after installing codeflow and before the test gate. `codeflow update` never
  writes it, and doctor reports it.
- **Pinned release digest (47).** Every installer trusts the release's own
  `sha256.sum`, which anyone who can replace a release asset can replace too.
  A `[scaffold_sha256]` table in the project state file now records the
  reviewed archive digest per release triple with the version it belongs to.
  When the pin commit holds the table, the installers require it to match
  (a stale version, a missing triple or a different digest fails closed) and
  still check `sha256.sum`. `codeflow update --pin <version>` writes the
  version and the table from a release whose archives it downloads and
  checks. A project that never pinned a digest keeps the `sha256.sum` check
  with a visible warning, because requiring the table when it is absent
  would leave a fresh `codeflow init` and the first upgrade pull request
  unable to pass: the base they are judged by has no table yet.
- **Secret scan scope (48).** The scan read the whole history of HEAD, so a
  finding already in the base, or on any branch merged into it, failed every
  pull request. A pull request now scans only the commits it brings
  (base..HEAD) and a push the pushed range; a weekly schedule, a manual run,
  a push that creates the branch and a push whose previous tip is gone scan
  the full history. Exemptions are still read only from the trusted commit
  (TSK-210).

## Acceptance Criteria

- AC-1 When the change holds `.codeflow/ci-setup.sh`, the managed GitHub gates job and the shared pinned run of the GitLab, Bitbucket and generic templates source it under `set -eu` after installing codeflow and before `codeflow test --strict`, so what it exports reaches the test gate and a failing hook fails the run; without the file they run the test gate as before (tests that execute the shipped scripts, failing before the change).
- AC-2 `codeflow update` never writes, rewrites or removes `.codeflow/ci-setup.sh`, and `codeflow doctor --check ci-perimeter` reports whether the hook is present, whether the CI file runs it, and its first command (an update round-trip test and doctor unit tests).
- AC-3 When the project state file at the pin commit holds a `[scaffold_sha256]` table, every shipped installer (gates, candidate, the enforcing policy job and the shared pinned run) requires its `version` to equal `scaffold_version` and its entry for the runner's triple to equal the downloaded archive's SHA-256, and still checks `sha256.sum`; a stale version, a missing entry or a different digest fails closed and installs nothing, including when the release's `sha256.sum` was replaced to match a replaced archive (install tests over a local `file://` release, failing before the change).
- AC-4 When no `[scaffold_sha256]` table is pinned, and the state holds nothing the installers refuse as possibly hiding one (an escaped table name or key, a multi-line string, a line starting with a character that is not printable ASCII, a control character, a name outside printable ASCII, a carriage return inside a line, another form of the table), the installers verify against `sha256.sum` as before and say that no reviewed digest is pinned (a warning annotation on GitHub, a note on stderr elsewhere) (install tests).
- AC-5 `codeflow update --pin <version>` downloads that release's `sha256.sum` and its three archives and refuses a malformed version, a lowered pin, a missing listing, an archive that does not match its listing, or a state whose own lines the installers would still refuse (naming the line, writing nothing); on success it writes only `scaffold_version` and the `[scaffold_sha256]` table in the project state file, keeping every other key and file, with the whole state written in a form the installers read (strings that need escapes on one line, arrays whose elements could read as keys on their key's line) (CLI tests over a `file://` release, one running the pinned state through the shipped installer).
- AC-6 `codeflow doctor --check ci-perimeter` recognizes the new installers, names the verification mode (pinned digest and `sha256.sum`, or `sha256.sum` only), and warns, with a remedy that `codeflow update --pin <version>` clears, when the checkout's table names another version or lacks a triple, and names the line to rewrite when the installers refuse the state (doctor unit tests; remedy clearing tests).
- AC-7 On a pull request the managed secret scan reads only the commits HEAD holds and the base does not, so a finding already in the base's history does not fail it while a leak the pull request adds still does; on a push it reads the pushed range; a scheduled or manual run, a push that creates the branch and a push whose previous tip is not in the checkout read the full history of HEAD; the step prints which mode ran and its range, and exemptions are still read only from the trusted commit (cases in `scripts/check-scaffold-gitleaks.sh` that fail on the previous template).
- AC-8 The managed CI workflow runs on a weekly schedule and on manual dispatch for that full-history scan, and its gates job does not run on the schedule (template tests).
- AC-9 The CI README, `docs/adoption.md`, `docs/capabilities.md`, the template header comments, the upgrade-order remedy and the CHANGELOG 3.1.0 entries with release-impact markers describe the three changes; `manifest_consistency` (once the AC-10 patch is applied), `init_e2e`, the scaffold tests and `codeflow validate --docs` pass (suite runs).
- AC-10 The patch that brings CodeFlow's own `.github/workflows/codeflow-ci.yml` gitleaks step in line with the template is written for the operator, since agents may not edit live workflows, and the hand-back says that until it is applied the harness's own-workflow check, the installed-manifest check in `manifest_consistency` and `repository_update_noop` stay red, and pass with it (review; the three checks run on a copy with the patch applied).
- AC-11 (journey) In a freshly scaffolded project driven by this build, `codeflow doctor --check ci-perimeter` reports `sha256.sum` only and no setup hook; after adding `.codeflow/ci-setup.sh` and running `codeflow update` the hook is unchanged and doctor names it; `codeflow update --pin <version>` against a local release writes only the pin and the table, after which doctor reports the pinned digests; a lower `--pin` is refused with a nonzero exit (the journey run with its observed output).
- AC-12 (issue 81) The managed `security review` job reads `git.security_review`, `git.dep_audit` and every `osv-scanner.toml` from the trusted commit (the pull request's base SHA, or the pushed commit), so a pull request that turns both keys off, deletes them or adds its own suppression is judged by the base, and osv-scanner runs with `--no-ignore` so a `.gitignore` the change edits cannot hide a lockfile; the audit's verdict follows osv-scanner's exit status, so a file path in its output cannot turn an advisory into a pass and a lockfile it cannot read is a scan error, and the scanner is downloaded outside the checkout so a link the change commits cannot redirect the write; a missing policy file at that commit, a missing or unreadable key, or a value other than `block`, `warn` or `off` fails the job (a test that runs the shipped step against a two-commit repository, failing on main).
- AC-13 (issue 81) The project setup hook cannot skip the test gate by accident in any template: a `codeflow` function, a `PATH` entry or `set +e` in it leaves the real gate running, and an `exit` in it, even `exit 0`, fails the run (the hook tests for the GitHub step and the shared run, failing on main). The hook shares the gate's shell, so it is not a boundary against a hook written to defeat the gate; like the CI file a change can edit, it is reviewed, and `codeflow ci` in the trusted policy job names a change that adds, edits or removes it (a CLI test), and the CI README says so.
- AC-14 (issue 81) `codeflow ci` names a change that lowers or removes `git.security_review` or `git.dep_audit` relative to the policy that judges it, deleting the whole policy file included, and says nothing when the change raises them or leaves them alone (a CLI test, failing on main); the CHANGELOG, the CI README and the adoption guide state the change and what an adopter does (missing keys land before the 3.1.0 workflow; a first adoption and a suppression under `block` have a named path), and the operator patch `target/scratchpad/live-codeflow-ci-81.patch` brings CodeFlow's own security review step, the baseline and the manifest in line (`manifest_consistency` passes once it is applied).
