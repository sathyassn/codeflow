# TSK-1253: Tests that wait on a fake remote or child process tolerate a loaded runner

## Description

Source: hosted run 41523922494, attempt 1, partition 4, on PR 526.

On hosted Windows, `codeflow-cli::policy_authority_journey` test `asking_the_remote_sends_no_stored_http_credentials` (`crates/codeflow-cli/tests/policy_authority_journey.rs:369`) timed out at a 10 second fake-remote wait. It passed on rerun. The red shard also failed commit standards, which reuses the run, and it stalled a records-only pull request's landing chain. The cause class is a fixed wall-clock wait on a loaded runner. The test file has no 10 second constant: it calls `challenging_server()` (`:324`) and `Adopter::doctor()` (`:112`), so the wait sits either in the product's remote query timeout that `doctor` uses or in a shared helper. Find it first.

No open task owns this test. TSK-1077 introduced the journey (its AC-8) and is complete. TSK-1005's flaky-test register is related: a quarantine entry used meanwhile follows its register rules.

Narrowed 2026-11-02 (the Director, 18:3x; source `coordination/coordinators/planning/cut/held-batch/task-G-remote-wait-flake.md`, "Narrowed"): a second slow test, `security::interpreter::tests::interpreter_large_glob_requires_a_safe_prefix` (`interpreter.rs:4643`), ran for more than 53 minutes inside the glob matcher in a full lib run, and 6.5 s alone. TSK-1258 owns its reproduction, the cause and the matcher bound, as a security task. This task keeps only making that test hermetic, so it no longer depends on the shared state TSK-1258 shows (not a working-directory race, which TSK-1258 found false). It depends on TSK-1258's finding, and one builder takes both, TSK-1258 first.

## Outcome

After this merges, the fake-remote tests wait on events, not on a fixed wall-clock bound, and a loaded runner no longer reddens them.

## Deliverables

- the event-based wait in the failing test or its helper: `crates/codeflow-cli/tests/`
- the sibling sweep of fixed short waits, each fixed or recorded with a reason

Issue 647, `an_unknown_repository_identity_never_matches_a_link`
(`crates/codeflow-cli/tests/follow_cli.rs`):

- The test forces a timeout with `Limits { git: Duration::ZERO }`.
  `observe::within` spawned the work and then called `recv_timeout(ZERO)`,
  which still returns an answer already in the channel. If the caller lost
  the processor between the two, the quick identity read finished first and
  the answer was `Known`, the hosted failure. A loaded runner makes this
  more likely, so it belongs to this class.
- The fix is in product code, `within` in `crates/codeflow-core/src/coord/observe.rs`:
  a zero limit gives the work no time, so it is not started and the answer
  is unknown. No test-only change can force this read to stall on every
  host: the read is in-process `git2`, with no command to replace. Product
  behaviour does not change: every product limit is a nonzero constant, and
  this test was the only caller passing zero.
- `a_zero_limit_is_unknown_however_fast_the_work` holds the rule in the
  unit tests of `observe.rs`.
