# TSK-1094: Qualification runner accepts the shipped Claude status line

## Description

The native qualification runner (`evals/qualification/runner.py`) refuses
every Claude trial whose fixture was scaffolded from the 3.2.0 line. The
fixture's Claude settings carry CodeFlow's shipped status line, which Claude
Code draws under the editor as
`Opus 5.5 (claude-opus-5-5) | v2.1.314 | default | repository (task/...) | ctx:0k/1000k (0%)`.
The ready check `editor()` accepts only Claude Code's own branch row there,
so it reports "seat did not become ready" and no trial runs. This blocks the
AC-4 qualification of TSK-1030 to TSK-1033.

The fix teaches `editor()` the shipped status line row, matched strictly
against the format the `statusLine` command in
`assets/base/settings/*.json` prints: the model id must equal the requested
`--model`, the folder must be the fixture's repository folder and the branch
must be the fixture record's branch. A row Claude Code cut with `…` in a
narrow pane is accepted only when the cut falls after the branch. Every
other row under the editor still refuses. Non-goal: fixtures keep their
status line, so trials see what adopters see.

A live trial (TSK-1033, trial 3) then showed that with input in the editor
Claude Code can add a third row under the mode row, the transient editor
hint `ctrl+g to edit in Nvim`, which the two-row check refused. The rows
under the editor are now modelled as the known sets Claude Code shows in
each frame (`footer_rows`): ready and pending input, with the status line
or the branch row, in any mode, with the hint only when the editor holds
input.

## Outcome

After this merges, the qualification operator can run Claude trials on
fixtures scaffolded from the 3.2.0 line, which ship the status line, and
the runner still refuses any frame it cannot tie to the fixture.
