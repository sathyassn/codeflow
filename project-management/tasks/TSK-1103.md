# TSK-1103: A project check runs from the trusted base before any candidate code

## Description

Issue #437 (2026-10-30): the managed `codeflow-ci.yml` runs the gate from
the pull request's merge checkout, so a project check that decides how the
candidate is judged runs the candidate's own copy, and the candidate can
skip, replace or widen it. Confirmed on the line at `0ce66e072`: the gates
job checks out the merge ref (`assets/base/ci/codeflow-ci.yml:52-54`),
picks `essential` or `full` from the head's `.codeflow/test-config.json`
(`:176`), sources the head's `.codeflow/ci-setup.sh` (`:189-191`) and runs
`codeflow test` on the head's config (`:196`); the setup hook is documented
as not a security boundary (`assets/base/ci/README.md:273-282`) and
`codeflow ci` only notes a change to it (`ci.rs:2124-2153`). The only
base-read input today is the pin (`codeflow-ci.yml:58`, `:70`).
`codeflow-policy.yml` checks out the base SHA (`:71`), fetches the head as
data (`:183-193`) and runs the fixed `codeflow ci` (`:229`), with no project
slot. Existing work covers the pieces, not the slot: TSK-1020 (complete)
added `codeflow test --config`; TSK-1001 AC-18 takes this repository's own
gate from the base config; TSK-336 makes the default branch the only
authority for the hosted verdict jobs and refuses a head that changes
`codeflow-ci.yml` (AC-14); TSK-1077 is local hook policy; TSK-294 reads one
project hook from the trusted commit for the dependency audit only.

This task adds the general slot: a project-owned declaration of checks that
the managed CI runs from the trusted commit's copies before any candidate
code, with the base, head and merge commits and the head repository as
arguments, failing the required check on the script's exit status. The
declaration lives in a project-owned file `codeflow update` never writes.
The home is the trusted verdict job of TSK-336 (`pull_request_target`,
default-branch files, the head as git data only), because a `pull_request`
workflow runs the head's own copy and could drop the step. Non-goal: a
project check that needs candidate code or a toolchain stays in the gates
job and outside this task; `codeflow test` is unchanged.

Criteria changes (2026-11-02, issue 510 folded in; dated note in PR 497's convention):

- Issue 510 has the same root cause as issue 437 and is added to `external_refs`. Its shape, a project check that reads its checker with a base-SHA `git show` before the setup hook, becomes a second fixture of AC-1.

- Security: this is already a CI-admission task; its cross-lineage review (Execution contract) carries the `cf-security-reviewer` checklist, the same as TSK-1187.

After this merges, an adopter can declare a project check that the managed CI runs from the trusted base before any candidate code, and a pull request cannot skip, replace or weaken it.

## Findings (AC-7, AC-14)

Researched 2026-11-07 on the line tip `c35cf003f`, before any code change.

How hosted CI runs trusted code against an untrusted candidate:

- GitHub. `pull_request_target` "runs in the context of the default branch
  of the base repository", with `GITHUB_SHA` the "last commit on default
  branch" and `GITHUB_REF` the default branch, and GitHub warns that running
  untrusted code on it "may lead to security vulnerabilities" (GitHub Docs,
  "Events that trigger workflows", pull_request_target, read 2026-11-07).
  `codeflow-policy.yml` already relies on this: it refuses any other ref
  (`assets/base/ci/codeflow-policy.yml:85-98`), checks out `github.sha`
  (`:102-105`), fetches base and head only as refs (`:238-253`) and asserts
  the checkout after every step. A `pull_request` workflow runs the merge
  ref's own copy of the file (`codeflow-ci.yml:26-27`, `:53-55`), so a head
  can drop any step there; that is AC-9's reason. The job token is
  `contents: read` plus `pull-requests: read` (`codeflow-policy.yml:77-79`).
- The test merge commit. GitHub computes `mergeable` in the background and
  `merge_commit_sha` names a test merge only when the pull request merges
  cleanly (REST "Get a pull request"; secondary mirrors read 2026-11-07), so
  a conflicting pull request has no merge commit, and the one it has can be
  computed against an older base. The merge argument is therefore optional:
  the step passes it only when the fetched `refs/pull/<n>/merge` has the
  resolved base tip and the head as its parents, and an empty string
  otherwise.
- GitLab. Merge request pipelines "run on the contents of the source branch
  only and ignore the content of the target branch", and a fork's pipeline
  "uses the fork project's CI/CD configuration" (GitLab Docs, "Merge request
  pipelines", read 2026-11-07). The only project-proof placement is a
  pipeline execution policy, whose jobs a project's `.gitlab-ci.yml` "cannot
  override" (GitLab Docs, "Pipeline execution policies"; a paid tier).
- Bitbucket. Pull request pipelines read `bitbucket-pipelines.yml` from the
  source commit (the shipped template's own notes,
  `assets/base/ci/bitbucket-pipelines.yml:17-48`); Atlassian's trigger page
  does not state it, so this is not confirmed from a primary source. Neither
  Bitbucket nor the generic wrapper has a trusted-base workflow.
- So the GitLab, Bitbucket and generic templates can run the declared checks
  from the target commit's copies, which holds against a head that edits the
  check, the boundary file or the declaration, but not against one that edits
  the pipeline file itself. The README states that limit and names the
  GitLab pipeline execution policy as the route to a boundary.

What adopters put in such checks: a module boundary (no import across a
listed edge), a debt register that may only shrink, generated files that must
match their source, an owners file that must cover every new path (the
reporter's shape in issue 437), and issue 510's shape, a checker read with a
base-SHA `git show`. All read the head as git data and need no toolchain
beyond the runner's shell, Python or Node; a check that needs the candidate
built stays in the gates job (the Description's non-goal).

Every project-owned input the managed CI reads today:

| Input | Read by | From | `codeflow ci` note |
|---|---|---|---|
| `.codeflow/project.toml` pin | install steps | base (`codeflow-ci.yml:59`), authority (`codeflow-policy.yml:119`) | pin rules |
| `.codeflow/policy.json` | gates (`validate --docs`), policy job, security review | head checkout, authority, base (`codeflow-ci.yml:1004`) | `CI_SECURITY_LEVEL_LOWERED` |
| `.codeflow/test-config.json` | gates mode choice and `codeflow test` | head checkout (`codeflow-ci.yml:177`, `:196`) | none |
| `.codeflow/ci-setup.sh` | gates job, sourced | head checkout (`codeflow-ci.yml:190-192`) | `CI_SETUP_HOOK_CHANGED` (`ci.rs:2104-2137`) |
| `.codeflow/audit-exceptions.sh` and the register it reads | security review | trusted commit export (`codeflow-ci.yml:1055-1070`, `:1108-1125`) | none |
| `osv-scanner.toml`, `.gitleaksignore` | audit, secret scan | trusted commit | none |

TSK-294's hook runs from a `git archive` of the trusted commit outside the
checkout with `CODEFLOW_TRUSTED_SHA` and `CODEFLOW_TRUSTED_ROOT`; this task
reuses that shape. TSK-1178 AC-1 (from TSK-336 AC-14) makes admission accept
only verdicts produced by the default branch's code at the authority SHA;
the base checks live in that same authority job, so they need no separate
admission. The register the audit hook reads is the project's own choice,
so codeflow cannot know it; the declaration names it
(`audit_exception_inputs`) so the note can watch it.

The note shape (AC-5, AC-10, AC-14): the setup-hook note compares blob ids
at base and head (`ci.rs:2114-2137`) and prints one `note` line with a remedy
code; a head tree it cannot read is named, never read as a removal
(`ci.rs:3541-3558`). Remedy codes are `Step` entries in
`crates/codeflow-core/src/remedy.rs:592-600`, each with a
`remedy_clearing` row. Adjacent cases: a rename is a removal at the old path
and an addition at the new one, and both are named; a change from a file to
a symbolic link with the same text keeps the blob id, so the comparison
includes the file mode; several changed inputs print one note per changed
path, each naming the path and what reads it, so each remedy names the one
file it restores (amended at build: one note per kind would need a remedy
naming several files).

Adjacent concerns:

- Timeouts. The verdict job has `timeout-minutes: 20`; a check declares
  `timeout_seconds` (default 300, at most 900) and the step kills the
  check's whole process group at that time and fails naming it.
- Interpreters. `ubuntu-24.04` carries bash, sh, python3, node and perl; the
  declaration names a bare interpreter, resolved on PATH, and a missing one
  fails the check.
- Forks. `pull_request_target` runs for fork pull requests with the base
  repository's token; the head is fetched as data from `refs/pull/<n>/head`
  and never checked out, and the head repository is passed as text.
- The token. The script's environment is cleared to a fixed set of
  variables, and its git directory is a fresh one that borrows the
  repository's objects (`objects/info/alternates`) and carries only the four
  named refs, so the checkout's persisted credentials are not in its config.
- Re-runs. A re-run keeps the original event's `GITHUB_SHA`, so it judges
  with the declaration the default branch had then; a new event judges with
  the current one.
- The base race (AC-15). `pull_request.base.sha` is the base when the event
  fired; a base that moved since is not seen. Each job now resolves the base
  ref's tip once and judges `merge-base(head, tip)..head`. A base that moves
  after the verdict still needs strict up-to-date checks or a merge queue.

Chosen scope: a declaration `.codeflow/base-checks.json` (schema shipped to
`.codeflow/schemas/base-checks.schema.json`, never written by update); a
`codeflow ci base-checks` subcommand that runs it from a trusted commit; the
step in the `codeflow-policy.yml` verdict job and in the shared pinned run
of the GitLab, Bitbucket and generic templates; the base-tip resolution in
both GitHub workflows; the gates job's base read of `test-config.json` and
`policy.json`; two `codeflow ci` notes; the doctor lines; the docs.

Gates job trust, 2026-11-07, after the second review of the setup hook:

- The runner user can change anything the job later trusts. GitHub's
  hosted runners docs, "Administrative privileges": "The Linux and macOS
  virtual machines both run using passwordless `sudo`."
  (https://docs.github.com/en/actions/reference/runners/github-hosted-runners)
  So code that runs earlier in a job can replace any binary, interpreter
  or file a later step of that job reads; no filter on what one step
  passes to the next closes that.
- Which job is trusted. `codeflow-ci.yml` runs on `pull_request`, whose
  `GITHUB_SHA` is the "Last merge commit on the `GITHUB_REF` branch" and
  whose ref is "PR merge branch `refs/pull/PULL_REQUEST_NUMBER/merge`"; it
  runs the change's own workflow file, hook and tests. `codeflow-policy.yml`
  runs on `pull_request_target`, which "runs in the context of the default
  branch of the base repository rather than in the context of the merge
  commit" (https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows);
  its verdict job checks out the default branch and reads the head as data.
  Only that job is trusted. Making the gates verdict itself come from the
  default branch's workflow is TSK-1178 AC-1 (todo).
- What the verdict job does today when these files change, at
  `19e7203ed`: `codeflow ci` prints a note for `.codeflow/ci-setup.sh`
  (`CI_SETUP_HOOK_CHANGED`, `crates/codeflow-cli/src/cmd/ci.rs:2124-2157`)
  and for a lowered `git.security_review` or `git.dep_audit` in
  `.codeflow/policy.json` (`CI_SECURITY_LEVEL_LOWERED`, `ci.rs:2111`); every
  such note leaves the verdict unchanged. It names no other
  `.codeflow/policy.json` edit and no `.codeflow/test-config.json` edit. A
  change to a managed workflow is a warning that "never blocks: the
  operator's own update of the policy workflow passes through it"
  (`crates/codeflow-cli/src/cmd/ci/workflow_change.rs:1-8`). No route in
  `codeflow ci` admits a change to a guarded file past a blocking verdict:
  the only change-specific admission is the secret-scan exemption's task
  admission (`work_start.rs:2552-2577`).
- The verdict job can see the three files (base and head are fetched as
  data) and `codeflow ci` can block on them. A blocking rule would refuse
  every pull request that edits them, including an ordinary new test
  target, with no admission route; that is a choice for the operator.
