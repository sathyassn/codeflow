# TSK-1103: A project check runs from the trusted base before any candidate code

## Description

Issue #437 (2026-10-30): the managed `codeflow-ci.yml` runs the gate from
the pull request's merge checkout, so a project check that decides how the
candidate is judged runs the candidate's own copy, and the candidate can
skip, replace or widen it. Confirmed on the line at `0ce66e072`: the gates
job checks out the merge ref (`assets/base/ci/codeflow-ci.yml:52-54`),
picks `essential` or `full` from the head's `.codeflow/test-config.json`
(`:176`), sources the head's `.codeflow/ci-setup.sh` (`:189-191`) and runs
`codeflow test` on the head's config (`:196`); the setup hook is documented
as not a security boundary (`assets/base/ci/README.md:273-282`) and
`codeflow ci` only notes a change to it (`ci.rs:2124-2153`). The only
base-read input today is the pin (`codeflow-ci.yml:58`, `:70`).
`codeflow-policy.yml` checks out the base SHA (`:71`), fetches the head as
data (`:183-193`) and runs the fixed `codeflow ci` (`:229`), with no project
slot. Existing work covers the pieces, not the slot: TSK-1020 (complete)
added `codeflow test --config`; TSK-1001 AC-18 takes this repository's own
gate from the base config; TSK-336 makes the default branch the only
authority for the hosted verdict jobs and refuses a head that changes
`codeflow-ci.yml` (AC-14); TSK-1077 is local hook policy; TSK-294 reads one
project hook from the trusted commit for the dependency audit only.

This task adds the general slot: a project-owned declaration of checks that
the managed CI runs from the trusted commit's copies before any candidate
code, with the base, head and merge commits and the head repository as
arguments, failing the required check on the script's exit status. The
declaration lives in a project-owned file `codeflow update` never writes.
The home is the trusted verdict job of TSK-336 (`pull_request_target`,
default-branch files, the head as git data only), because a `pull_request`
workflow runs the head's own copy and could drop the step. Non-goal: a
project check that needs candidate code or a toolchain stays in the gates
job and outside this task; `codeflow test` is unchanged.

## Outcome

After this merges, an adopter can declare a project check that the managed CI runs from the trusted base before any candidate code, and a pull request cannot skip, replace or weaken it.

## Deliverables

- the declaration format and its reader: `crates/codeflow-core/src/ci/` (new module, provisional name `base_checks.rs`) and the schema under `.codeflow/schemas/`
- the managed step in the trusted verdict job: `assets/base/ci/codeflow-policy.yml` (TSK-336 owns the job; this task adds the step), and the same step in the GitLab, Bitbucket and generic templates under `assets/base/ci/`
- the `codeflow ci` warn-tier note and remedy: `crates/codeflow-cli/src/cmd/ci.rs`, `crates/codeflow-core/src/remedy.rs`
- the `codeflow doctor --check ci-perimeter` report lines: `crates/codeflow-cli/src/cmd/doctor/`
- docs: `assets/base/ci/README.md`, `docs/adoption.md` (the CI section), `docs/capabilities.md` (CAP-003), `docs/policy-reference.md`
- tests: `crates/codeflow-cli/tests/ci_cli/` (declaration, fail-closed and trust fixtures), the scaffold template tests, a 3-way `codeflow update` fixture
- the reply on issue #437 naming this task (drafted in the coordinator's scratchpad as `issue437-reply.md`)

## Acceptance Criteria

- AC-7 Before any change, the builder shall research base-run project checks broadly: how hosted CI systems run trusted code against untrusted candidates (`pull_request_target` and base checkouts on GitHub, protected variables and trusted runners on GitLab, Bitbucket pipes), what adopters put in such checks (boundary files, debt registers, generated-file checks, ownership rules), every managed CI file and every project-owned input it reads today, TSK-336 AC-14's admission design and TSK-294's trusted-commit hook, and adjacent concerns (timeouts, interpreters available on the runner, forks, the merge commit not existing for a conflicting pull request, re-runs); and shall record the findings with sources and the chosen scope before anything else changes; evidence: the Findings section, committed before the first code change in the PR. Listed first because it runs first (the operator's rule of 2026-10-27).
- AC-1 When the trusted commit's declaration names a check, the managed CI shall run that check from the trusted commit's copies of the script and its listed inputs, with the base, head and merge commits and the head repository as arguments, and a head that edits the boundary file, the script, `.codeflow/ci-setup.sh` or the declaration shall still get the base's decision; evidence: the reporter's reproduction as a fixture, failing before the change and passing after. (serves EPC-022 AC-181)
- AC-2 The step shall fail closed: a declared script that is missing, unreadable, a symbolic link or gitlink, not executable by its stated interpreter, or past its timeout shall fail the required check naming the declaration and the path, and a declaration that cannot be parsed shall fail; evidence: one fixture per case. (serves EPC-022 AC-181)
- AC-3 Trust shall be bound to the trusted SHA resolved once at job start (the default branch, per TSK-1077 and TSK-336), never to a head file or a name the requester controls, and a pull request into an integration line shall be judged by the default branch's copies; evidence: a fixture where the line's base carries a differing declaration and the default branch's copy decides, and the threat statement in the PR body. (serves EPC-022 AC-181)
- AC-4 The declaration shall survive `codeflow update` unchanged (a 3-way merge fixture), the managed GitHub workflow and the GitLab, Bitbucket and generic templates shall carry the same step, and `codeflow doctor --check ci-perimeter` shall report the declared checks and a managed workflow that does not run them; evidence: the update fixture, the template tests and the doctor output.
- AC-5 `codeflow ci` shall print a warn-tier note with its own remedy when a range edits a declared script, one of its inputs or the declaration, as `ci.rs:2124` does for the setup hook, and the verdict shall be unchanged; evidence: a CLI test and a `remedy_clearing` run.
- AC-6 `assets/base/ci/README.md`, `docs/adoption.md` and `docs/capabilities.md` shall state the boundary (what runs from the base), its limit (no candidate code or toolchain) and the route for a check that needs them; evidence: the doc diff and `codeflow validate --docs`.
- AC-8 (journey) With the installed build in a scratch adopter on a scratch GitHub repository, a declared check that reads a boundary file shall pass a clean pull request, fail one that adds a file the boundary forbids, and fail the same pull request when its head rewrites the check to always pass; evidence: the three run links.
