When a line takes `main`, the push of that sync runs `codeflow ci` over every commit the sync brings in. Two costs in that run are this task's:

- The per-record range walk. On `main` at `ad5971c8d`, each judged record builds its own walker (`crates/codeflow-core/src/workgraph/status_steps.rs:140-143`) and walks the whole range (`:471-505`), so the walk cost grows with records judged times commits in range. A macOS `sample` of the EPC-025 sync (merge `83b9420d8`, 2,836 commits from `main`) on a release build of `main` put 2,460 of 2,463 samples under `lifecycle::judge_pull_request_shaped`, then `judge_range_against`, `range_steps`, `status_steps::judge` and `Walker::range` (coord/parallel, 2026-11-14). TSK-1499's AC-8 removes the per-commit graph file open inside each walk; this task's AC-2 makes one walk serve every judged record.
- The id-registry check's git children. In coord/records' EPC-022 proof of 2026-11-15 (pid 16769, 60 records added under `project-management` and `docs/decisions` against the merge base `f77a0aead`), `ids::check::merge_rule` (`crates/codeflow-core/src/ids/check.rs:252-344` on `main` at `a33b9296a`) ran its uniqueness scan (`:435-490`), which calls `ids::inventory::copies_at` (`inventory.rs:67-94`) once for each distinct code ref tip (`check.rs:466-472`). Each call starts `ls-tree` in `ids::git::Git::tree` (`git.rs:309-341`) and `cat-file --batch` in `Git::blobs` (`git.rs:256-302`). When sampled, the proof had run 2 h 07 min (19:18 CPU) with no verdict, and 1447 of 1493 samples were waiting on those children. `codeflow ids check` reads every ref the same way (`check.rs:126`, `inventory::on_every_ref` at `inventory.rs:101-119`); uncapped in a scratch mirror with 600 branch refs and 474 distinct tips, it took 1959 s and exited 0 on binary `ad5971c8d` (coord/records, 2026-11-16).

Predecessor: TSK-1306 bounded `codeflow ci` for a records-only head and a 95-commit landing candidate. It is complete on the EPC-022 line, not on `main`. ## Outcome

On a line's main sync, every judged record shares one walk of the range, and the id-registry check and `codeflow ids check` list and read the code refs' records with a fixed number of git children, so a judgment walks the range once however many records it judges, the number of git children started to list and read the code refs' records is the same however many distinct tips there are, and no record blob is read twice in one run; the findings, order and exit code stay the same. With TSK-1499's bounded graph check and reopen walk, a line's main sync of a few thousand commits gets its verdict within the bound AC-1 states.

## Acceptance Criteria

- AC-1 On the release binary and an idle host, `codeflow ci` shall judge a main sync of a few thousand commits into a line in bounded time: the bound is a wall time per form that the pull request states as a number the builder confirms from the measurement, no more than the 60 s default push budget of TSK-1306's AC-4, so that it needs no setting. It is measured in the pre-push and pull request forms on three ranges: the EPC-025 sync (`83b9420d8`, base `6eb4a9ebb`, 2,836 commits from `main`), the EPC-026 sync (tree `4a1ee2d72`, base `3ad11d9ef`) and the EPC-022 sync fixture `f77a0aead..3c8b6cfd2` (693 commits). `3c8b6cfd2` is a simulated merge of `main` at `f77a0aead` into `97a6c9066` with `main`'s side taken on conflicts, tree `5d460bf99`; it is held in coord/records' clone, and the builder rebuilds that merge and checks the tree where it is absent. Evidence: wall times before and after on all three ranges, where "before" is the pull request's base, which holds TSK-1306's two commits (AC-6), and the pull request also gives the time on `main` at `ad5971c8d`, without them, so it shows what those commits already bound and what this change adds.
- AC-2 The range shall be walked once per judgment and that walk shared by every judged record, and the commit-graph identity check shall run a bounded number of times per judgment, never once per commit per record. Bound: exactly one walk per judgment, and a graph-check count that is the same for a 50-commit and a 500-commit range and for one record and five. Measured on a unit fixture with at least three records, merges and a commit-graph chain, built at both sizes, and in a profile of the EPC-022 sync fixture (AC-1). Evidence: the counting test on the fixture, and the profile with file:line in the pull request.
- AC-6 The change shall build on TSK-1306's commits `607227827` (one commit index shared by every walk) and `4e38b9de4` (each judged history walked once per run) as they are on `main`, and shall not re-make them. Bound: `git merge-base --is-ancestor` exits 0 for each commit against the pull request's base. Measured on that base. Evidence: both commands and their exit codes in the pull request, and the pull request body names which of the profiled costs those commits remove and which this change removes.
- AC-9 (Added 2026-11-15 (coord/records), Director ruling: the id-registry check's per-commit git spawn, found in the EPC-022 proof. On `main` at `a33b9296a` the children are started once per distinct code ref tip, not once per commit: `crates/codeflow-core/src/ids/check.rs:466-472`.) The id-registry check shall not start git children once per code ref tip. Its uniqueness scan (`ids::check::merge_rule`, `check.rs:435-490`) and `codeflow ids check` (`check.rs:126`, `inventory::on_every_ref`) shall list and read the records of every distinct code ref tip with a fixed number of git children, or in process, instead of one `ls-tree` child (`ids::git::Git::tree`, `git.rs:309-341`) and up to one `cat-file --batch` child (`Git::blobs`, `git.rs:256-302`) per tip through `ids::inventory::copies_at` or, on the EPC-022 line, `copies_with`. Reading each record blob once across tips is TSK-1306's commit `607227827`, which this change keeps and does not re-make (AC-6). The findings shall not change: the same `uniqueness:` blocks in the same order with the same exit code, and a missing record blob still refuses with today's `requested blob <id> is missing` message (`git.rs:286-289`). Bound: the number of git children started to list and read the code refs' records is the same with 5 and with 50 distinct code ref tips, and no record blob is read twice in one run. Evidence: (a) a test that counts those git children and blob reads in `merge_rule` and in `codeflow ids check` on a fixture whose range adds records, built with 5 and with 50 distinct code ref tips that hold the record tree, failing on the pull request's base (at least one child per distinct tip) and passing on the head (the same count at both sizes); (b) wall time and a macOS `sample` for the pull request form of `codeflow ci` on the EPC-022 sync fixture (AC-1; 693 commits, 60 records added against the merge base), in a clone with at least as many distinct code ref tips as coord/records' clone held on 2026-11-15 (474 tips across 600 branch refs), on `main` at `ad5971c8d`, on the pull request's base and on the head, where the EPC-022 proof (pid 16769) had run 2 h 07 min (19:18 CPU) with no verdict when sampled, with 1447 of 1493 samples waiting on git children under `copies_at`; the head finishes the id-registry check within the bound stated under AC-1, with `Git::blobs` and `Git::tree` no longer the dominant frames; (c) the same `uniqueness:` findings, order and exit code on that range before and after, and a test with a missing record blob on one ref, refused before and after with the same text.
