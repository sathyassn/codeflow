# TSK-335: Secret-path spellings receive the same verdict

## Description

Issue: #180. This is related to proposal A by security boundary, but its root is the matcher, not a missing store entry. It deserves separate regression evidence.

`security/interpreter.rs:101` passes the raw word into `matches_extended_glob` at `:132`. `security/pattern.rs:19` turns `**` into `.*` but keeps the following slash. Thus `**/id_rsa*` becomes a pattern requiring a slash, and cannot match bare `id_rsa`. The relevant deny is in `security/actions.json:636`. This is a source-level explanation of the reported difference, not just the issue author's hypothesis.

The `.env` and source-name cases are a separate explicit limitation: `interpreter.rs:123` skips entire groups with carve-outs (`actions.json:580`, `:615`). Adding `./` alone would not fix those. PR 187's `interpreter.rs:105` retains the same secret-path routine and its `carveouts.is_empty()` condition.

Outcome: **A hard-denied secret path receives the same shell verdict when spelled bare, relative or absolute.**

Source inspection is from the accepted triage at `c5c6f6f671d2bf67a77113c656b3be446fb0bea1`; runtime reproductions remain implementation evidence.
