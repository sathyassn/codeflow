# TSK-1313: A newer line push cancels the older push run on that line

## Description

The operator asked on 2026-11-03: "A newer line push cancels the older push run - wasn't this already considered? anyways make sure its considered and tasked". `codeflow-ci.yml:30-32` cancels only `pull_request` runs and groups by ref, so a superseded line push runs to the end, and a dispatch on a line shares a group with that line's pushes. A superseded line commit's verdict is required nowhere (hosted CI savings analysis of 2026-11-03). This is a root task so it can land early; TSK-1026 keeps its pull request design and points here. Non-goal: anything on `main`.

## Outcome

After this merges, a newer push to an integration line cancels the older push run on that line, so a maintainer pays for the newest tip's run only.

## Deliverables

- the concurrency settings: `.github/workflows/codeflow-ci.yml`, by operator script if the guard lists the file
- the test: the workflow's scaffold or gate-parity test; AC-3 names it

## Findings

- AC-4, before: four superseded line push runs burned 1, 3, 164 and 0 job-minutes on 2026-11-03, 168 in total, as the Description's savings analysis records.
- AC-4, after: not measured yet. The change has no hosted run on a line until it lands; the first superseded line push after landing gives this number, recorded under TSK-1273.
- AC-5: no doc needs a change. No doc describes this workflow's cancellation; the cancellation text in `assets/base/ci/README.md` covers `codeflow-policy.yml`. `assets/base/ci/codeflow-ci.yml` and its baseline copy have no `concurrency` block and no integration push trigger, so adopters get no change. The recovery AC-7 names is already the project rule for a cancelled run: AGENTS.md "Landings batch" says cancelled is not green and to start or rerun the run.
- AC-6: a rerun keeps its original ref and SHA, so a rerun of an old push in the line's group would cancel the newest run, and `cancel-in-progress: false` alone would still let it replace a pending one. The group therefore moves a push rerun to `codeflow-ci-push-rerun-<run id>-<attempt>`, and the cancel expression requires `run_attempt == 1`. GitHub's `run_attempt` is a string and `==` with a number compares as numbers.
- AC-6, not observed: the rule assumes GitHub evaluates the workflow-level group again on each attempt, with `github.run_attempt` set to the new attempt. The test models this; no hosted run has shown it. If the assumption is wrong, a rerun of an old line push stays in the line's group and cancels the newest tip's run, which then shows as a failure. It will be observed at the first rerun of a line push after landing: the rerun should run alone and leave the newest tip's run untouched.
- AC-7: top-level concurrency is decided before any step runs, so no step can stop a late older run from cancelling the newest one. The workflow comment states the limit and the recovery.
- AC-7, how a cancelled run shows: the `codeflow gates` and `windows` verdict jobs run with `if: always()` (`.github/workflows/codeflow-ci.yml:719` and `:1110`), so a push run cancelled by a newer push still runs both and they conclude failure, not cancelled. In the out-of-order case that failure lands on the newest tip, which is also the head of the line's pull request to `main`. It is a false red, never a false green: rerun the newest tip's run to clear it.
- AC-8: no function available to a top-level concurrency group can keep case, so the workflow cannot prevent the collision. It is prevented by how lines are named and checked:
  - `codeflow epic new --integration` names a line `integration/EPC-NNN-<slug>`, and the slug is lower-case (`crates/codeflow-core/src/workgraph/light_paths.rs`, `slug_words`), so two lines it makes never differ only in case.
  - `scripts/test_gate_contracts.py` refuses records whose `integration_target` or `parent_line` values form a case pair.
  - Read live 2026-11-05 15:39 EST: the remote has five integration lines and no case pair. The "Integration hosted gates" ruleset (id 25435656) has only required status checks, non-fast-forward and deletion rules, so nothing on the remote refuses a hand-made twin. That needs push access to this repository, and its effect is a cancelled run whose verdicts show as a failure (see AC-7), or a replaced pending run with no verdict, never a false green; the recovery is to rerun the newest tip's run. A branch-name ruleset that refuses a twin is a repository setting, the operator's step, and is not part of this task.
