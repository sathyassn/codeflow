# TSK-1084: The guard test fixtures ignore the host's Git configuration

## Description

Source: the hosted failure of PR 346 (TSK-1002) at `92e7b5029`,
triaged 2026-10-30 and corrected in the planning review the same day.

Hosted run 41026268442 failed one test,
`target_repository::tsk1002_review17_fd_values_help_programs_carets_and_backups`,
on Linux (coverage shard 2 of 2) and Windows (tests partition 5 of 12),
while it passed on the builder's macOS host. The test expects
`git log ^main HEAD` to be refused because a leading `^` handed to a
Git call that runs a configured program must be quoted. The refusal
needs a program to judge: the runner reader judges `core.pager` for a
paging verb (`crates/codeflow-core/src/hooks/git_guard/runners/catalog.rs:106`,
`runners.rs:634-641`) and runs its pattern check only when a runner or
configured command exists (`runners.rs:2248-2257`). `credential.helper`
is judged only for remote verbs (`catalog.rs:115`), so it cannot decide
a `git log` verdict. The fixture configured no pager, so on the hosted
runners the line was allowed. TSK-1002 then pinned `core.pager` in that
fixture (`c201cc0b3`,
`crates/codeflow-cli/tests/hooks_cli/target_repository.rs:1700-1706`),
which supplies the program the test needs.

The guard runs through `isolated_codeflow`, which sets
`GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` to `/dev/null`
(`crates/codeflow-cli/tests/hooks_cli.rs:57-68`), and the guard's
configuration reader shells to `git` with that environment
(`crates/codeflow-core/src/security/git_config.rs:142-149`). Why the
macOS host still saw a pager before the pin is not known: a remaining
leak (a configuration file Git reads outside those two variables, a
test that builds its own command, or the fixtures' own `git` setup
calls) or a difference in the fixture itself. A guard verdict that
depends on the host makes the suite pass on one runner and fail on
another, and can hide a real change in a verdict.

Non-goals: changing any guard verdict; the guard's own reading of a
user's real configuration, which is product behaviour.

## Outcome

After this merges, a maintainer gets the same `hooks_cli` verdicts on macOS, Linux and Windows whatever Git configuration the host has.

## Findings

Measured 2026-10-30 on the builder's macOS host (Git 2.53.0 from Homebrew)
at the line tip `461827479`, which is `92e7b5029` plus the TSK-1002 pin
and later merges. The test, its guard and its Git calls are unchanged by
those merges, so the unpinned test was reproduced by commenting out the
one pin line (`target_repository.rs:1706`) and running the built test
binary under controlled environments (`env -i PATH HOME TMPDIR` plus the
named variable).

### Why the review 17 test passed on macOS without the pin

The cause is an inherited environment variable, not Git configuration.
The runner reader judges the pager program from two places: the
`core.pager` setting and the `PAGER` and `GIT_PAGER` variables of the
guard's own process (`runners.rs:663-684`, which falls back to
`std::env::var` when the line did not assign the variable). This host
exports `PAGER=less` (`env | grep PAGER`), so `git log ^main HEAD` always
had a program to judge. Hosted runners export no `PAGER`.

| Run of the unpinned test | Result |
|---|---|
| host environment as is | pass (refused, as the test expects) |
| host environment without `PAGER` | fail (line allowed) |
| `env -i` (hosted-like) | fail (line allowed) |
| `env -i` plus `PAGER=less` | pass |
| `env -i` plus `GIT_PAGER=less` | pass |
| `env -i` plus `EDITOR=nvim VISUAL=nvim` | fail (`git log` runs no editor) |

The host's Git configuration is not involved: `git config --system --list
--show-origin` shows only `credential.helper=osxkeychain` from
`/opt/homebrew/etc/gitconfig`, and `git config --global --list
--name-only` shows no `core.pager`. The pin comment at
`target_repository.rs:1700-1705` names the system `credential.helper` as
the host difference; that was the wrong cause (`credential.helper` is
judged only for remote verbs, `catalog.rs:115`).

### Every path by which a `hooks_cli` run reads host state

| Path | Leak? | Evidence |
|---|---|---|
| Guard reads `PAGER`, `GIT_PAGER`, `EDITOR`, `VISUAL`, `GIT_EDITOR`, `GIT_SEQUENCE_EDITOR`, `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_PROXY_COMMAND`, `GIT_EXTERNAL_DIFF`, `GIT_DIFFTOOL_EXTCMD`, `GIT_ASKPASS`, `SSH_ASKPASS` from its process environment | Yes | `runners.rs:663-684`, `catalog.rs:162-174`; table above. `isolated_codeflow` (`hooks_cli.rs:57-68`) removes none of them |
| Inherited `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n`, `GIT_CONFIG_VALUE_n`, `GIT_CONFIG_PARAMETERS` reach the guard's `git config --list` and every fixture `git` call | No under `cargo test` | `.cargo/config.toml` forces all of them (`force = true`) to the repository's maintenance-off settings (TSK-245), so a cargo-run test sees the same values whatever the shell exports; `git_config.rs:142-149` passes them on. A test binary started directly inherits the shell's values instead. The isolation keeps them, and `git_spawn_contract` reviews each site that could replace them |
| Inherited agent-session markers (`CLAUDECODE`, `CODEX_SESSION_ID`, `CODEX_THREAD_ID`, `CODEX_CI`, `GROK_SESSION_ID`) | No under `cargo test` | `.cargo/config.toml` forces them empty. A test binary started directly inside a Claude Code session inherits `CLAUDECODE`, a hook then judges its actor an agent (`root_checkout.rs:54-60`), and 15 `hooks_cli` tests fail on the root-checkout commit rule (for example `pre_commit_passes_clean_feature_branch`); that is a runner artifact and is not changed here |
| Other inherited `GIT_*` variables (`GIT_AUTHOR_*`, `GIT_COMMITTER_*`, `GIT_TEMPLATE_DIR`, `GIT_EXEC_PATH`, `GIT_SSH_COMMAND`) | Yes | `runners.rs:1031`, `1513` read two of them; the fixtures never remove them |
| System and global files through `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_GLOBAL` | No for `isolated_codeflow`, `git()` (`hooks_cli.rs:106-111`), `git_out`, `target_repository.rs:12-18` and the direct calls that set both to `/dev/null` | the two lines at each site |
| Fixture `git` calls with no isolation at all | Yes | `hooks_cli.rs:3803` (`rev-parse`), `5396` (`rev`), `5418` (`push_url`), `6455` (`cat-file`), `9040` (`rev-parse`) read the host's system and global files |
| `HOME` and `XDG_CONFIG_HOME` | Yes for the guard, no for Git | Git skips both files once `GIT_CONFIG_GLOBAL` is set (Git 2.32 and later), but the guard's config-file checks read `$HOME/.gitconfig`, `$HOME/.config/git/config` and `$XDG_CONFIG_HOME/git/config` (`runners.rs:1597-1615`) and the real user home (`line_home.rs:267-271`); `isolated_codeflow` sets neither |
| Tests that build their own command | Mixed | `hooks_cli.rs:1130` copies `codeflow()`'s environment (isolated); `7214`, `7377` and `7519` set the two config files but keep every other inherited variable; `9953` is isolated; `7863` runs `--help` only and reads no Git state |
| The fixtures' setup `git` calls | Yes, as the rows above | `git()` removes only `GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE` |
| Hooks installed in fixture repositories | Follows the calling `git` call | a hook inherits the environment of the `git` process that ran it |

The fix is one shared helper that removes every inherited `GIT_*`
variable except the forced maintenance settings, and the non-`GIT_`
program variables the guard reads, points the system and global files at
`/dev/null`, and gives the run an empty home; the helpers and the direct
calls use it instead of repeating the two lines. The fixture crate's clone
builder can set a variable but not remove one, so clones set only the two
files and the home. `git_spawn_contract` lists the helper's environment
calls in `git_environment_allowlist.tsv`.
