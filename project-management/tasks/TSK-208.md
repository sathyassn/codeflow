# TSK-208: a release never hosts a dirty build

## Description

A consuming project reported (sathyassn/codeflow#14) that the 3.0.0
release binary prints `dirty=true`, so it cannot be reproduced exactly from
the tag. TSK-203 fixed the cause for 3.1.0: the release job wrote
`dist-manifest.json` into the checkout before building, and that path is
now ignored. The reporter also asked that a release fail when a build
reports `dirty=true`; nothing checks that today, so the next untracked
file a release step writes would ship a dirty binary again. This task
makes the release refuse to host any archive whose binary does not carry
`<version> source=<release commit> dirty=false`: `release-main-recheck`, the
custom job cargo-dist runs after the platform builds and before hosting,
checks every archive, in dry runs too. Each binary embeds that line as a
literal (`codeflow --version`), so the check reads the bytes and needs no
runner per platform. Non-goal: rebuilding 3.0.0.

## Acceptance Criteria

- AC-1 When `release.py verify-clean-builds` reads a directory of release
  archives (`.tar.xz` and `.zip`), it passes only when every archive holds
  a `codeflow` binary carrying `<version> source=<release commit>
  dirty=false`, and refuses, naming the archive, a dirty build, a build
  from another commit or version, an archive with no binary, and a
  directory with no archive; evidence: `scripts/test_release.py` cases for
  each, against archives built in the test.
- AC-2 `release-main-recheck` downloads every `artifacts-build-local-*`
  artifact and runs that check on the release commit before cargo-dist's
  host job, also on a dry run, so a dirty build blocks hosting; evidence:
  `release_contract` pinning the step and its place, and the dry-run
  release dispatch of the next candidate. (journey)
- AC-3 `docs/releasing.md` names the check among the publication guards;
  evidence: the doc diff.
