# TSK-1062: The Windows killed-gate test waits on a signal, not a fixed deadline

## Description

Source: the line's own push run at `dc9ec266d` (run 40750765706, job
"windows tests (12 of 12)", job id 123053893714). The test
`codeflow-core testing::runner::tests::a_killed_gate_ends_its_target_tree_on_windows`
failed as `FAIL + LEAK [61.585s]`, panicking at
`crates/codeflow-core/src/testing/runner/mod.rs:1960` with "the target
recorded its pid". The same test passed on the line's earlier run at
`e937da4ee`. Nine other tests in the same shard were reported slow
(over 60 seconds), so the runner was loaded.

The test (TSK-142 AC-3) spawns its own test binary as a gate
(`windows_gate_helper`, `:1905`), whose target runs `cmd.exe`, then
`powershell`, which writes its pid to `pid.txt`. The test polls for that
file 1,200 times at 50 ms (`:1950-1960`), a fixed 60-second deadline,
then kills the gate and checks the tree ended. Three things are not
known from the log, and each could produce the same panic:

- the helper's start, the gate's start and PowerShell's start were
  slower than 60 seconds on a loaded runner;
- the helper or its target failed early, which the test cannot see: the
  helper's stdout and stderr go to null and `run_target`'s result is
  discarded (`let _ =`, `:1913`);
- the pid file was written in a form the parse rejects.

The `LEAK` verdict also shows a second defect: when the wait panics,
the spawned gate and its target tree are left running, because the kill
happens only after the wait succeeds.

The fix: the test passes or fails for a stated cause on a slow runner,
never on an arbitrary deadline alone, and it never leaves its gate
running. Raising the deadline alone is not a fix.

Non-goals: changing what TSK-142 AC-3 proves (a killed gate ends its
target tree); the Windows partition balance (shard 5 of 12 hit the
30-minute limit on the first attempt of PR 392's run 40775926015), which is a separate
outcome.

## Outcome

After this merges, a maintainer reading a Windows run can trust that a failure of the killed-gate test names its cause, and that the test leaves no process behind.

## Findings

Recorded before any code change (AC-1).

### The failing run

Run 40750765706, job "windows tests (12 of 12)" (123053893714), read from the job log:

- The test started at about 19:44:21 and was reported `SLOW [> 60.000s]` at 19:45:21, then `FAIL + LEAK [61.585s]` at 19:45:23. It panicked at `runner/mod.rs:1960` with "the target recorded its pid". 61.585 s is the 60 s poll (1,200 x 50 ms) plus about 1.5 s of start and teardown.
- The shard ran 218 tests in 683 s with 10 reported slow. While the test waited, `scaffold_test` tests in the same shard took 14.8 s, 17.7 s and 19.8 s for work that takes seconds elsewhere, so the runner was heavily loaded.
- The log holds nothing from the helper: the test sent its stdout and stderr to null.

### The test and helper (read at `461827479`)

- The helper (`windows_gate_helper`) is this test binary run as the gate. It runs one target (`cmd.exe` then `powershell`), which writes `pid.txt` and sleeps 120 s. The helper discards `run_target`'s result (`let _ =`), so a failed start leaves no trace.
- The test polls `pid.txt` 1,200 times at 50 ms and never checks whether the gate is still running. It kills the gate only after the poll succeeds, so a panic in the poll leaves the gate and its target running. That is the `LEAK` verdict.

### Which cause

The three causes in the Description cannot be told apart from this log, and none is settled (AC-1 was amended for this):

| Cause | Fits the log | Against it |
|---|---|---|
| Start of the helper, the gate or PowerShell slower than 60 s on a loaded runner | the load above; 9 other slow tests | the same test passed at `e937da4ee`; no start time was recorded |
| The helper or its target failed early | the helper's output went to null and its result was discarded, so an early failure looks the same | nothing in the log shows one |
| `pid.txt` written in a form the parse rejects | none | the same command writes a parseable file on every green run, and the CLI journey reads the same file the same way; `Set-Content` of a number writes ASCII digits and a line break, which `trim` removes |

A reproduction was not possible: there is no Windows host or runner available to this build session, and a hosted rerun of the same job cannot be forced to be loaded the same way. The fix therefore makes the next failure name its cause instead of guessing this one: the test watches the helper's exit, keeps the helper's output, and ends with what was and was not observed.

What would settle the cause: a hosted Windows failure of this test under the new wait. Its message gives the helper's exit status and output (an early helper failure), the pid file's state and text (a rejected form), or the 60 second bound with the helper still running (a slow start). A repeat run of the hosted Windows partition under load would also do.

Fixed-deadline waits on a child's file or state, in `testing/runner` and the gate-lock tests, and the CLI gate journeys that drive the same child:

| Test | Wait | Runs on | Decision |
|---|---|---|---|

| `doctor/mod.rs` probe timeout | child exit with a stated timeout error | all | Not changed: it already ends in a named timeout result |

### The bound that remains (AC-3)

The pid wait keeps its 60 s bound, not raised. Measured start times from a loaded runner do not exist: the only data point is the failing run, which shows the start took over 60 s or never happened. The hosted nextest runs show a passing test's output nowhere, so a printed start time would not be visible either. The bound is therefore kept as the failing run's own limit and is justified only as a backstop: the test now ends earlier whenever the helper exits, and when the bound is reached the failure says the helper was still running, shows what `pid.txt` held and what the helper wrote, and says it cannot tell a slow helper start, a slow target start and a slow PowerShell start apart. A later change of the bound needs a measured start time, which that message supplies the first time the bound is reached.
