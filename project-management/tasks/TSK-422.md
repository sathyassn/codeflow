# TSK-422: The coordination ledger is a clone-local event log with a follow command

## Description

Issue #272, items 2 and 4 and the comment of 2026-10-21, under
ADR-0086 as the operator decided on 2026-10-22. An orchestrating
session owns a "task ledger" that CodeFlow gives no shape, no closure
rule and no place in the session loop; in an adopting project a
hand-written ledger stopped after nine days, handed-over items went
quiet, a merge of lane stocktakes produced about 940 items mostly
duplicating tracked work, and a deleted lane lost what only its
conversation held.

Outcome: **the follow-up ledger lives in the clone's common git
directory (`.git/codeflow/coord/`) as JSON Lines events appended under
a lock and validated against a schema, with a folded current view;
`codeflow follow add|update|close|list|adopt` keeps open commitments as items
`FU-NNN` whose holder is `coordinator` or a lane id, any session adds items,
only the holder closes one and only on proof, an item lists what it
waits on and CodeFlow derives when it is due, a merged pull request or
a completed task closes its linked items with that proof, `add` refuses
a duplicate of an open record and a cycle among items, and
`codeflow work status` lists per task the worktrees with uncommitted
changes, unpushed commits and commits on no branch.**

Decided by ADR-0086 (the operator, 2026-10-22), applied here:

- **Location A**: clone-local, in the common git directory, where
  CodeFlow's ledger JSONL, locks and registry state already live;
  shared by every worktree; untracked; never in history. `follow list`
  gives a table or Markdown view; an opt-in `follow snapshot` writes a
  tracked copy under `project-management/` for a project that wants
  history. CodeFlow owns the schema, CLI, hooks and rules; the project
  owns the entries.
- **One ledger per project (per clone).** Any orchestrating model or
  session reads the same list; the holder tells them apart.
- **Three logs, each with one job,** under `.git/codeflow/coord/`:
  `items.jsonl` (follow-up item events), `lanes.jsonl` (lane and seat
  events, TSK-439) and `roles.jsonl` (coordinator events, TSK-439);
  `status/` holds one overwritten heartbeat file per holder
  (`coordinator.json`, `LN-NNN.json`), never logged; `counters.json`
  (next FU and LN numbers, written under the lock), `coord.lock` (one
  writer at a time) and `archive/` (closed history, compacted by month)
  sit alongside. The logs refer to each other only by id.
- **The envelope on every event line**, field names in full:
  `schema_version`, `event` (from the closed list for that log),
  `subject_id`, `sequence` (rises by one per log, assigned under the
  lock; order is by sequence, never by clock), `recorded_at` (UTC, for
  people), `recorded_by` (role required, `coordinator` or a lane id;
  harness, model and session id when known) and optional `comment`
  (scanned for secrets like commit text). Each line is checked against
  the schema; the current state is folded from the events in order;
  `list` prints a table or `--md` Markdown, never the source.
- **A follow-up item is a full record** that stands on its own for a
  cold reader. Required: `title`, `description`, `done_when`, `source`
  (operator, coordinator, a lane id, a review, an issue, outside),
  `holder` (coordinator, a lane id or operator), and `links` or
  `no_link_reason`. Optional: `source_reference`, `waits_on`,
  `next_check` (derived when absent), `needs_operator`, `priority`
  (low, normal, high, blocking).
- **Item events**: `item_added` (the full item), `item_updated` (at
  least one changed field, never `source`), `item_checked` (result
  `still_waiting` or `now_due`), `item_handed_over` (new holder),
  `item_closed` (proof `{kind, reference}`, kind one of
  `merged_pull_request`, `commit`, `task_completed`, `ruling`,
  `operator_answer`), `item_dropped` (reason; only by its holder or the
  coordinator) and `item_reopened` (reason, for example a reverted
  proof).
- **Reading order at session start**: `roles.jsonl`, then
  `items.jsonl`, then `lanes.jsonl`, then `status/`.
- **Name.** The system is the coordination ledger, recommended and
  pending the operator; its parts are follow-up items (`FU-NNN`,
  `codeflow follow`) and lanes (`LN-NNN`, `codeflow lane`); the lead
  role is the coordinator.
- **An aid, not a control.** The ledger never blocks git, records, CI
  or landing; a missing or damaged ledger only warns. Coupling is one
  way: the ledger may name task, epic and ADR ids and reads their
  state for auto-close and readiness, but never writes a record;
  records, pull request bodies and `codeflow ci` never cite FU or LN
  ids and never read the ledger, which is clone-local and absent in
  CI. When an item becomes real work it becomes a task through normal
  planning, citing the real origin (issue, pull request or review),
  and the item links to the task.
- **Item identity**: `FU-NNN`, allocated per project, rising, never
  reused. An item moves through open, waiting, due, closed (proof) and
  dropped (reason, by the holder), and a closed item can be reopened
  when its proof is reverted.
- **Dependencies**: `waits_on` names a task (due when it changes
  state), a pull request (merges, closes or its checks finish), a lane
  (reports, goes idle or its seat goes stale), another row (closes),
  the operator (answers; listed under "needs you" in every status), an
  outside event (a stated time, then checked by hand) or a time. Items
  point at tasks and never copy the task graph; a cycle among items is
  refused at `add`.
- **Auto-close**: a merged pull request or a completed task closes its
  linked items with that proof, derived by `list` from the records and
  the remote.
- **Fields**: id, what, source, holder (`coordinator` or `LN-NNN-<slug>`, from
  TSK-439), a CodeFlow id (task, epic criterion, decision) or a reason
  why none exists yet, waits on, next check, the running seat,
  worktree and head while work runs, and closure proof.
- **Closure on proof**: a merged pull request or commit, a recorded
  ruling, or the operator's answer quoted with its date; "handed to a
  lane" never closes an item; an item linked to a task closes when that
  task closes, with the task's proof, derived by `list`.
- **Dedupe**: `add` compares the subject with open tasks, epic criteria
  and open items and refuses a match until the author links the id or
  rejects it with a reason.
- **Recoverable lane state**: `work status` reads git for each task's
  worktrees (uncommitted changes, unpushed commits, commits on no
  branch).

Non-goals: lane records and heartbeat (TSK-439); the hooks that
surface items (TSK-440); the rules (TSK-423). The holder value `coordinator`
works before TSK-439 lands; lane ids are validated once it does.

## Acceptance Criteria

- AC-1 `codeflow follow add` from any session shall allocate `FU-NNN` (rising, never reused) and append a schema-valid `item_added` event carrying the full item (title, description, done_when, source, holder, links or no_link_reason, and the optional fields), `update`, `check` and `hand-over` shall append `item_updated` (never changing `source`), `item_checked` and `item_handed_over`, `close` shall append `item_closed` only from the item's holder and only with a proof of a listed kind, refusing "handed to a lane", `drop` shall need a reason from the holder or the coordinator, `reopen` shall append `item_reopened` with a reason, a malformed event or envelope shall be refused, and `list` shall show the folded state (open, waiting, due, closed, dropped) as a table and as Markdown; evidence: CLI tests, including a close by a non-holder and a cold-reader check that an item renders without its conversation. (serves EPC-025 AC-1)
- AC-2 `add` with a subject that matches an open task, an epic criterion or an open row shall refuse naming the match until the author links the id or rejects it with a reason, and `add` or `update` that would make a cycle among items shall be refused naming it; evidence: CLI tests over fixture records. (serves EPC-025 AC-1)
- AC-7 An item shall become due when what it waits on changes state (a task claimed, complete or blocked; a pull request merged, closed or its checks finished; a lane reporting, idle or with a stale seat; another row closed; a stated time passed), an item waiting on the operator shall list under "needs you", and a merged pull request or a completed task shall close its linked items with that proof; evidence: one test per wait kind and the auto-close test. (serves EPC-025 AC-1)
- AC-3 The store shall live under `.git/codeflow/coord/`, be readable and writable from every worktree of the clone, never appear in `git status` or history unless `snapshot` is used, and two sessions appending at once shall never corrupt it; evidence: a two-worktree test, `git status` and a concurrent-append test. (serves EPC-025 AC-1)
- AC-4 `codeflow work status` shall list, per task, each worktree with uncommitted changes, unpushed commits and commits on no branch, read from git; evidence: a CLI test over a fixture with one of each. (serves EPC-025 AC-1)
- AC-5 The guards shall keep allowing CodeFlow's own writes under `.git/codeflow/coord/` and refuse an agent's direct edit of the store, under TSK-379's reach rule; evidence: guard tests for both.
- AC-8 The ledger shall be an aid and never a control: `codeflow ci`, pre-push, `task status`, `work claim`, `work start` and `codeflow integrate` shall give the same verdict with the ledger present, absent or damaged, a damaged ledger shall only warn, the ledger shall never write a record, and `codeflow validate --docs` shall flag a task, epic or ADR record and `codeflow ci` a pull request body that cites an FU or LN id; evidence: a fixture run of each command with the store absent and with a corrupted log, a code search for writes under `project-management/` from the follow module, and validate and ci tests with a planted FU id. (serves EPC-025 AC-1)
- AC-6 (journey) With the installed build in a scratch adopter project with two worktrees, a session in each shall add items, link one to a task, close one on a commit and be refused closing the other's, and `follow list --markdown` from either worktree shall show the same folded state; evidence: the journey output.
