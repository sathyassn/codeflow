# TSK-422: An orchestrator's follow-up ledger is a command whose rows close on proof

## Description

Issue #272, proposal items 2 to 4 and the comment of 2026-10-21. An
orchestrating session owns a "task ledger"
(`cf-model-orchestrator/SKILL.md:63`) that CodeFlow gives no shape, no
closure rule and no place in the session loop. In an adopting project
with six lanes, a hand-written ledger stopped being updated after nine
days, items the operator handed over went quiet, and status was
assembled from memory. Merging the lanes' stocktakes by hand produced
about 940 rows, most of them work already tracked as tasks or criteria
in other words. A half-hourly sweep scheduled inside the coordinator
session was lost with the session; a deleted lane recovered only what
its own tracker file held, losing uncommitted edits, running seats and
in-flight reviews.

Outcome: **a project-level follow-up ledger, kept locally in the
clone's common git directory and shared by every worktree, session and
orchestrating model of that clone, keeps the open commitments as
structured rows with a fixed schema; any session adds rows, only a
row's holder closes it, on proof; `add` refuses a row that duplicates
an open CodeFlow record until it is linked or the match is rejected;
`codeflow orient` and the SessionStart digest print the open, overdue
and operator-owned rows for the current holder; and `codeflow work
status` lists, per task, the worktrees with uncommitted changes,
unpushed commits and commits on no branch.**

The operator shaped this on 2026-10-22: the ledger is project level,
works for any model that orchestrates, and stays local. It changes
where CodeFlow keeps working state and partly supersedes ADR-0076's
"plan in the harness's task tools", which are session-scoped and
vendor-specific, so this task drafts a new ADR (allocated with
`codeflow adr new`) that records the decisions below as proposals the
operator may still adjust. Two design questions stay open for the
operator to confirm, with the proposed answers: one ledger per project
(per clone), not per host; and any session, host or lane, may add rows.

Decisions proposed here, for the ADR:

- **Location.** Untracked, in the clone's common git directory
  (provisional `.git/codeflow/follow/`, resolved through `git
  rev-parse --git-common-dir`), so it is shared by every worktree of
  the clone, survives sessions and never enters history. Durable
  outcomes still go to tasks, ADRs and records, and each row links
  them.
- **One ledger per project (per clone), not per host,** so any
  orchestrating model or session reads the same list; the holder field
  tells sessions apart.
- **Command** (provisional `codeflow follow add|update|close|list`)
  with the fields #272 and its comment state: id, what, source,
  holder, a CodeFlow id (task, epic criterion, decision) or a reason
  why none exists yet, waits on, next check, the running seat,
  worktree and head while work runs, and closure proof.
- **Who adds and who closes.** Any session, host or lane, may add
  rows. Each row names its holder, and only the holder closes it, with
  a proof: a merged pull request or a commit, a recorded ruling, or the
  operator's answer quoted with its date; "handed to a lane" never
  closes a row. A row linked to a task closes when that task closes,
  with the task's proof, which `list` derives from the records.
- **Dedupe.** `add` compares the subject with open tasks, epic criteria
  and open rows and refuses a match until the author passes the id to
  link or a reason to reject it.
- **Surfacing.** `orient` and the SessionStart digest print the open,
  overdue and operator-owned rows for the current holder, so the check
  survives any one session; an optional hook or `codeflow ci` advisory
  (`codeflow hook follow-check`, wired only when a project opts in)
  flags a status turn that mentions an operator ask but adds no row,
  and rows with no next check.
- **Recoverable lane state.** `work status` lists per task the
  worktrees with uncommitted changes, unpushed commits and commits on
  no branch, read from git, so a restarted session sees what it would
  otherwise lose.
- The managed-block rule and the `cf-model-orchestrator` rule that
  require the ledger are TSK-423's, so each is one reviewable pull
  request; the ADR lands with this task.

Non-goals: the managed rule and the orchestrator skill's use of the
ledger (TSK-423); tracking a snapshot in git (a project may add it);
the operator feedback tracker (#75).

Added by the EPC-022 amendment of 2026-10-22 under the operator's
decision of that day (project-management changes go in 3.2.0).

## Acceptance Criteria

- AC-1 `codeflow follow add` from any session shall write a row with every schema field (a CodeFlow id or a reason why none exists), `update` shall change holder, waits-on, next check and the running seat, worktree and head, and `close` shall be accepted only from the row's holder and only with a proof (a merged pull request, a commit, a recorded ruling or a quoted operator answer), refusing "handed to a lane"; evidence: CLI tests, including a close by a non-holder. (serves EPC-022 AC-111)
- AC-2 `add` with a subject that matches an open task, an epic criterion or an open row shall refuse naming the match until the author links the id or rejects it with a reason, and a row linked to a task shall show as closed with that task's proof once the task is terminal; evidence: CLI tests over fixture records. (serves EPC-022 AC-111)
- AC-3 `codeflow orient` and the SessionStart digest shall print, for the current holder, the open count, each row whose next check is past and each row whose holder is the operator, from any worktree of the clone, and shall print nothing when no ledger exists; evidence: CLI tests from two worktrees and the digest output. (serves EPC-022 AC-111)
- AC-4 `codeflow work status` shall list, per task, each worktree with uncommitted changes, unpushed commits and commits on no branch, read from git; evidence: a CLI test over a fixture with one of each. (serves EPC-022 AC-111)
- AC-5 The ledger shall live under the clone's common git directory, shared by every worktree and absent from `git status` and history, and the advisory hook or `ci` advisory shall be off unless a project wires it and shall then flag a status turn with an operator ask and no row and a row with no next check; evidence: a two-worktree test, `git status` and the advisory tests.
- AC-7 The ADR shall record the location, the per-clone scope, who adds and who closes rows, and the part of ADR-0076 it supersedes, as proposals the operator confirms, and `codeflow validate --docs` shall pass; evidence: the ADR and the validate output.
- AC-6 (journey) With the installed build in a scratch adopter project, a session shall add three rows, link one to a task, close one on a commit, and a new session's SessionStart digest shall show the two open rows with one overdue; evidence: the journey output.
