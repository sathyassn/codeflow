# TSK-1514: The docs portal lease test waits for a complete ready file and never leaves its coordinator running

## Description

The docs-portal adapter test "a live writer blocks a lease whose coordinator was killed until it exits" can fail under host load and then hold the whole test run open. The defect is in its helper `startLeaseCoordinator` (`docs-portal/tests/adapter.test.mjs:1344-1366` on `main` at `a33b9296a`; the test is at `:1402`). The coordinator child writes `.coordinator-ready` with a plain `writeFileSync` (`:1356`). The parent's `waitUntil` returns as soon as the file can be opened (`:1362`), and the parent then parses a second read with `JSON.parse` (`:1363`), so it can read a file the child has created but not finished writing. The child then ends in `await new Promise(() => {})` (`:1358`) and keeps an interval running (`:1357`); when the parent throws before it returns the `kill` handle (`:1365`), nothing kills it. The writer child it starts (`:1353`) is also left running, because its pid is only known from the ready file.

Seen at TSK-361's head `224735f61`, at host load about 296 (load figure from the Director's ruling; it is not in the saved logs). The file is shifted by 29 lines there, so the log names `adapter.test.mjs:1431` for the test and `:1392` for the parse:

```
✖ a live writer blocks a lease whose coordinator was killed until it exits (1717.892ms)
  SyntaxError: Unexpected end of JSON input
      at JSON.parse (<anonymous>)
      at startLeaseCoordinator (file:///…/codeflow/.worktrees/tsk-361/docs-portal/tests/adapter.test.mjs:1392:22)
```

Its `lease-coordinator.mjs` child then sat at 0% CPU and held the file pending for 26 minutes, until the run was stopped (exit 143); the file-level line reads `adapter.test.mjs (1853282.235125ms)`, "Promise resolution is still pending but the event loop has already resolved". The same test passed 1 of 1 when run alone. Evidence (workspace repository): `coordination/coordinators/parallel/notes/build-cicd-TSK-361-report.md`, "Runs after the lift", and `coordination/coordinators/parallel/notes/tsk361-lift-logs/ac11-docs-portal.log` (lines 173 to 184) and `ac11-probe-live-writer.log`.

A second lease test in the same file has the same two faults: "the check workflow's test workers keep the lease held after the runner is killed" (`:1588` on `main` at `ec8d5c1ab`, same blob `344dca256`; `:1617` at TSK-361's head `224735f61`). It spawns `scripts/workflow.mjs check` (`:1597`), waits only for the worker's `worker-tick` file (`:1599`), and then reads the owner record and takes `record.owner.writers[0]` as the runner (`:1601-1603`). `workflow.mjs` records the runner's pid only after it has spawned it (`recordWriter`, `docs-portal/scripts/workflow.mjs:65`), so on a loaded host the test can read the record before the runner is in it and get `undefined`. The test kills the coordinator and the runner only on the passing path (`:1604`, `:1606`); its `finally` (`:1615-1618`) kills only the worker, and only once its pid has been read (`:1600`). A throw before `:1604` leaves the coordinator and the runner running, and a throw before `:1600` leaves a started worker running too, since its pid is not yet known.

The lease writer in `docs-portal/scripts/publication.mjs` is not the cause, and readers never see a partial lease. The first owner file is written and synced in a private candidate folder (`writeDurableJson` with `exclusive: true`, `:45`, branch `:884-889`) and only then linked onto the claim (`:48`). Later updates (`:116`) write a temporary file, sync it and rename it into place (`:891-899`).

The test file is a managed starter file, and `assets/docs-portal/starter/tests/adapter.test.mjs` holds the same bytes (blob `344dca256` for both on `main` at `a33b9296a`, and the same blob on the EPC-022 line at `7749102cd`). `portal_dogfood_runtime_matches_the_shipped_starter` (`crates/codeflow-core/tests/manifest_consistency.rs:1030`) requires the two copies to stay byte-identical, so the fix goes into both.

Why this task exists, and why it targets the EPC-022 line:

- The same bytes are on `main`, so every gate run of the docs-portal target on `main`, and on each line that takes `main`, can hit it.
- It makes a gate intermittently red, and it can hold a run for 26 minutes with a live child process.
- No open record covers it. Searched on `main` at `a33b9296a` and on the EPC-022 line at `7749102cd` for "coordinator-ready", "startLeaseCoordinator", "Unexpected end of JSON input" and "lease test" under `project-management/`: four hits (TSK-279, TSK-332, TSK-405, TSK-1263), all complete and none about this test or its ready file.
- Its epic EPC-047 lands on the EPC-022 line (its `parent_line`), so the fix lands there with TSK-1511 and reaches `main` when the line does. Amended 2026-11-16: the record first targeted `main`, on the ground that a test-only fix there reaches `main` sooner than TSK-361's line does.

Non-goals: changing the lease writer or anything else in `publication.mjs`, or the writer recording in `workflow.mjs`; the other child scripts in this test file other than the check-workflow lease test above, which AC-5 covers, since they already kill their child in a `finally` (for example `:1921-1922`, `:1983-1986`, `:2187-2188`); the docs-portal target's timeout, which TSK-1511 covers.

## Outcome

After this merges, a CodeFlow maintainer running the docs-portal gate on a loaded host gets a real verdict from the lease tests, and no lease test leaves a child process running that holds the run open.

## Acceptance Criteria

- AC-1 The coordinator child shall write `.coordinator-ready` atomically: it writes the JSON to a temporary file in the same folder and renames it to `.coordinator-ready`, so the parent never sees a partly written ready file. Evidence: the file:line of the write at the final head, in both copies.
- AC-2 The parent shall also tolerate a partial or empty read: when `.coordinator-ready` exists but does not parse as the expected JSON, the parent shall read it again until it parses or a stated bound passes, and on that bound shall fail with a message that names the ready file, not with a bare `SyntaxError`. The pull request states the bound (for example the 5 s default of `waitUntil`, `:3388`). AC-1 and AC-2 are both required; either one alone does not meet this task. Evidence: the file:line of the read at the final head, in both copies.
- AC-3 The test shall kill the coordinator child, and the writer child when one was started, in a `finally` on every path: a normal pass, a failed assertion, a thrown parse or a timeout in `startLeaseCoordinator`, and a failure in either calling test (`:1388`, `:1402`). Evidence: the file:line of each `finally` at the final head, in both copies.
- AC-4 Evidence for AC-1 to AC-3, named in the pull request with each run's result line:
  - (a) the quoted assertion from the failing run above (`SyntaxError: Unexpected end of JSON input` at `startLeaseCoordinator`), as the reason for the change;
  - (b) a test case that forces a partial ready file (for example a coordinator script that first writes part of the JSON, waits, then writes the rest), which fails on the pull request's base with `Unexpected end of JSON input` and passes on the head;
  - (c) a check that no child process survives the failing path: after the forced failure, the coordinator's pid and the writer's pid are no longer alive (`process.kill(pid, 0)` throws), and the test file's run exits by itself instead of staying pending;
  - (d) `portal_dogfood_runtime_matches_the_shipped_starter` passes at the head, and `git diff --no-index` of the two copies is empty;
  - (e) the docs-portal target's adapter tests pass at the head, once alone and once on a loaded host.
- AC-5 The check-workflow lease test ("the check workflow's test workers keep the lease held after the runner is killed", `:1588`) shall read recorded state only after it is written, and shall leave no child running:
  - (a) when it reads the runner's pid from the owner record, the test shall first wait, within a stated bound, until `owner.writers` names a live pid, and on that bound shall fail with a message that names the owner record, not with a `TypeError` or a kill of `undefined`; the same applies to any other read in the test of a file or record field that a child writes after the test starts it;
  - (b) the test shall kill the coordinator, the runner and the worker, each once its pid is known, in a `finally` on every path: a normal pass, a failed assertion, a thrown read and a timeout.
  Evidence: the file:line of the wait and of the `finally` at the final head, in both copies; a forced case in which the owner record names no writer until after the worker starts (for example a delay before `recordWriter` in a test copy), which fails on the pull request's base and passes on the head, with each run's result line; after the forced failure, the coordinator's, the runner's and the worker's pids are no longer alive (`process.kill(pid, 0)` throws) and the test file's run exits by itself. AC-4 (d) and (e) cover this test too.
