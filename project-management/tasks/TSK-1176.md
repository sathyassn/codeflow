# TSK-1176: Secret scanning cannot be replaced or evaded by the pull request

## Description

Issues #279 and the PR 231 follow-ups (SEC-03, SEC-06, SEC-07). Split from TSK-336 on 2026-11-01. The whole-PR review of PR 479 graded TSK-336 Very Hard (9: S2 2, S6 1, S7 1, C 2, X 1, R 2), and a Very Hard task is split before claim. TSK-336 keeps the foundation (the default branch's code judges every pull request); this task takes one outcome with the criteria that prove it, moved and not copied, each marked with its old number. The five pieces are TSK-336, TSK-1175, TSK-1176, TSK-1177 and TSK-1178.

A pull request's secret scan runs the head's own copy of the workflow, so the head can change the scan that judges it; SEC-03 asks that the scan, like the policy verdict, come from trusted authority. SEC-06 (a replace ref hides a planted secret) and SEC-07 (an octopus merge's additions are not read) are scan-reading gaps in the same job. SEC-05 (low: legacy-fingerprint advice still covers a clean two-parent merge amended to add content) is advice only and suppresses no finding; disposition: tracked once here, revisit when this task edits the legacy-fingerprint advice (moved from TSK-336, where the revisit event was the same edit), where the fix is to require a remerge CONFLICT header naming the path. The scan job lives in the trusted verdict workflow that TSK-336 sets up, hence the edge.

Files shared by the five pieces (`codeflow-ci.yml`, `codeflow-policy.yml`, their installed copies and baselines, `ci.rs`): one writer at a time, as TSK-336's contract says; the Coordinator orders the writers. File sharing adds no scheduling dependency.

Outcome: **the `trusted: secret scan` verdict runs the authority's scan logic over the range as data, finds a secret introduced by any commit (a replaced object or an octopus merge included), and no head-run `secret scan` job exists.**

Non-goals: the other verdict jobs (TSK-336); who creates the authority check (TSK-1177).

### The trusted gitleaks allowlist canary

Folded in 2026-11-05 by the records follow-up after PR 617, from TSK-1163 and TSK-1166 of the unpushed plan `plan/epc-022-hosted-ci-scope` (workspace backup `coordination/backups/plan-epc-022-hosted-ci-scope-8c3a3e853.patch`). That plan was never pushed, so neither task exists on the line. The canary is a security floor: the operator decided on 2026-11-02 (hosted CI scope page, row "canary", confirmed 01:19Z) to keep it and make it a trusted required check.

The secret scan reads the trusted base's `.gitleaks.toml`, so a pull request that only widens the allowlist passes the scan, and after it merges the widened file is the trusted config. The canary (TSK-198) plants novel credentials and fails when the config no longer reports them. At line tip `1107c5974` it protects nothing:

- it is a job inside `codeflow-ci.yml` (`gitleaks-canary`, `.github/workflows/codeflow-ci.yml:1751-1767`) that runs the pull request's own `scripts/check-gitleaks-allowlist.sh` from the `pull_request` checkout, so the pull request that widens the allowlist can also edit the script that judges it; the script copies the config from the checkout it runs in (`scripts/check-gitleaks-allowlist.sh:10` and `:44`);
- no ruleset requires it. Read live at 20:39Z on 2026-11-05: "Integration hosted gates" requires `codeflow gates`, `windows`, `commit standards` and `release impact`; "main required checks" adds `secret scan` and `security review`; every entry has integration id 15368 (GitHub Actions).

Threat closed: a pull request that widens the secret-scan allowlist, or edits the canary script, becomes trusted config without any required check failing.

Design (AC-11 confirms it):

- A separate job in `.github/workflows/codeflow-policy.yml`, which runs on `pull_request_target`, so GitHub takes the workflow from the default branch. It checks out the default branch's authority at `GITHUB_SHA`, as `trusted: commit standards` does (`codeflow-policy.yml:7-8`, `:89-91`), runs the authority's copy of the script with the pinned, checksummed gitleaks, and fetches the pull request's base and head only as git data.
- The authority, never the base. For a pull request into a line the base is the line tip, which agents change by merging, so a canary that ran the base's script falls to two pull requests: the first makes the script always pass, keeps `.gitleaks.toml` unchanged and lands; the second widens the allowlist and is judged by the weakened script. A line merge does not change the default branch, so the authority's script still fails the second. Corrected 2026-11-05 after the review of PR 629 (F1): the plan and this record's first text said the base commit's script.
- The pull request's `.gitleaks.toml` is read as data only: the head is fetched into a private ref and `git show <head>:.gitleaks.toml` writes it to a temporary file. The script gains a config-path argument.
- It stays a separate job, never a step of another verdict job: steps share their job's token, and the canary, which parses pull request content, holds only `contents: read`.
- On the line, the policy workflow runs only on `pull_request_target`, and pushes create no check under a `trusted:` name (`codeflow-policy.yml:27-30`). Line and `main` tips stay judged on push and schedule by the `codeflow-ci.yml` job, renamed so that no job a pull request can edit carries the trusted check's name (provisional: `gitleaks allowlist canary (advisory)`), with a comment that names the trusted job. TSK-359 AC-4 and TSK-1026 AC-3 list it among the jobs that run on every push and are never reused; that stays true.
- A ruleset entry names a check by its context and the GitHub Actions app id. That identifies the app, not the workflow file, and a pull request can add a job of any name to `codeflow-ci.yml`. AC-11 settles how GitHub resolves such a pair. If the ruleset cannot tell them apart, the merge admission binds the result instead: the trusted `commit standards` job reads the canary's result only from a run of the default branch's `codeflow-policy.yml` on `pull_request_target` at the exact head and merge commit.

`pull_request_target` hazards the job avoids, each checked by the security review:

- no checkout, build, install or execution of pull request code: the head is fetched as git objects, and only one blob is read, as data;
- `contents: read` and nothing else, set on the job, and no secret;
- no pull request text (title, body, branch name, file content) reaches a `run:` script through `${{ }}`; values reach the shell only through `env:`;
- the untrusted config cannot reach outside the temporary directory: an `[extend]` path or any other file reference is refused or resolved inside it, and a missing or unparseable config fails the check;
- the job follows the policy workflow's concurrency rule from TSK-1040, so a body edit or other same-head event never cancels the run that judges a pushed head; hence the edge on TSK-1040.

The job can first run on this repository only after the line's pull request to `main` merges, because `pull_request_target` runs `main`'s copy. Requiring the check before then would block every pull request. So the hosted adversarial proof and the operator's ruleset step are TSK-1270 AC-6 to AC-8, which run after that merge. The operator ruled out scratch repositories for the trusted verdict's hosted proofs (Director, 22:35 on 2026-11-02, EPC-022's TSK-1270 row), after the plan was written, so the plan's scratch-repository evidence moves there too.

### One verdict per head commit

Folded in 2026-11-05 from `coordination/coordinators/parallel/reviews/tsk1177-head-fc1a9acb1.md` F2 in the workspace repository, which predates TSK-1177 and is tracked once here, where the review said to revisit it. A verdict is bound to the head commit, not to the pull request: the refusal accepts any `pull_request_target` run of the policy workflow, and the authority job keys its checks only on `head_sha`. With two open pull requests from one head, one into the default branch whose body fails its verdict (an under-declared release impact, for example) and one whose body passes, an agent edits the passing one's body, its verdict becomes the latest check on the commit, and the failing one merges. A pull request into a line with the same head does the same for one into the default branch. The commits are the same, so the effect is limited to body and base-dependent verdicts: pull request body standards and the declared release impact.

Threat closed: a pull request merges on a verdict that another pull request earned on the same commit.

## Outcome

after this merges, a pull request cannot replace, weaken or evade the secret scan that judges it, and a secret introduced by any commit is found. A pull request that widens the secret-scan allowlist fails a canary that runs only trusted code, and a verdict another pull request earned on the same head commit admits no other pull request.

## Findings

Security review at `345f8da876b8419b48e457df70973e38123bbd2a` (same-family
Opus subagent; Codex and Grok were at their limits, so reduced assurance).
The hosted path was found sound. Two material findings sat in the local
dependency audit of `codeflow scan`; both are fixed in this pull request.

- **F1, material, fixed: the audit could write outside its folder.**
  `export` and `base_suppressions` in `crates/codeflow-core/src/hooks/osv.rs`
  joined each path `git ls-tree` lists onto the temp folder. A crafted tree
  with entries named `..` lists `../../pwned.txt`, so a range could write
  any bytes anywhere the user can write. Now every git-listed path goes
  through `Scratch` (`hooks/gitleaks/range.rs`): each `/` component must be
  one plain name (no empty, `.`, `..`, root or drive prefix; on Windows no
  `\`, `:` or trailing dot or space), and each folder written into must
  resolve inside the scratch root. Anything else refuses the audit. This is
  the standard per-component check archive extractors use against path
  traversal. Fail before: with the check disabled,
  `a_tree_entry_named_dot_dot_is_refused_and_nothing_is_written_outside`
  gets `Ok(())` and the file is written outside. Pass after, with
  `a_scratch_folder_takes_only_plain_relative_paths`.
- **F2, material, fixed: a range could ship its own suppression on a
  case-insensitive disk.** The export skipped only the exact name
  `osv-scanner.toml`, so on macOS or Windows a head `OSV-Scanner.toml` was
  read by osv-scanner as the suppression file. The export now leaves out,
  at every folder level, each name that may open as `osv-scanner.toml`:
  compared after Unicode lower- then upper-casing (so `ſ` counts as `s`)
  and after trimming the trailing dots and spaces Windows drops. Base
  copies are still placed only under the exact name, as the Linux hosted
  audit reads them. Fail before: `a_head_suppression_in_another_case_is_never_exported`
  lists `OSV-Scanner.toml`, `sub/osv-SCANNER.TOML` and two other spellings
  in the exported tree. Pass after.
- **Sibling sweep.** Every place the scan code writes a git-listed path:
  osv `export` (head tree and the base export for the exception hook),
  `base_suppressions`, and the gitleaks range scan's copy of extended
  configuration files (`write_inputs`), all now through `Scratch`. Config
  names elsewhere: the gitleaks scan reads `.gitleaksignore`, its
  configuration and `.gitattributes` from the base by exact path through
  `git cat-file` and passes them to gitleaks explicitly, and its source
  folder holds only a `.git` file, so no head file can stand in for them.
  The hosted steps run on Linux, which is case-sensitive, and are unchanged.
- **Found by the quick gate, fixed:** `export` piped `git cat-file
  --batch` stdin itself, which the `stdin_pipe_rule` contract refuses
  outside `git/stdin.rs`. Earlier quick runs timed out before this test
  reported. It now uses `spawn_with_input`, which writes from its own
  thread and reports a write error. The same run showed the remote lint
  (`test_remotes_contract`) flagging osv.rs's `RELEASES` constant, the
  osv-scanner release page; it now has an allowance entry beside the
  gitleaks one, with the reason. A later quick run showed the
  `remedy_clearing` coverage test missing the `SCAN_TOOLS_UNAVAILABLE`
