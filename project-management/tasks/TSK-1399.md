# TSK-1399: The pr merge guard reads the base of the repository the command names

## Description

git-guard allows `gh pr merge` only when a lookup proves the pull
request's base is not protected; any doubt refuses under
`git.pr_merge_to_protected` (`check_gh_pr_merge`,
`crates/codeflow-core/src/hooks/git_guard.rs:12229`, at the line's
d8274e43e). The lookup (`gh_pr_base` and `gh_pr_base_blocking`,
`crates/codeflow-cli/src/cmd/hook.rs:855` and `:867`) runs
`gh pr view <n> --json baseRefName` in the hook process's own working
folder. It receives only the target (`PrBaseLookup`, `git_guard.rs:37`),
so the command's repository flag, its `GH_REPO` and its working folder
never reach gh.

Found on 2026-11-09 (read-only diagnosis by coord/ci): from the
agentic-systems workspace root, which has no git remote and is where
sessions start,
`gh pr merge 736 --repo sathyassn/codeflow --merge --match-head-commit <sha>`
into the unprotected line `integration/EPC-022-the-3-2-0-milestone-fixes`
was refused, because gh answered "no git remotes found". The same payload
with the hook process in the codeflow root was allowed. A leading
`cd <repo> &&` does not help, because the hook runs before the command.

Two more defects sit in the same parse, found while filing this record
(installed 3.1.0 at 698cc8789; the code is unchanged at d8274e43e):

- `pr_merge_target` (`git_guard.rs:12281`) does not know the repository
  flag takes a value (`GH_PR_MERGE_VALUE_FLAGS`, `:12268`), so with the
  flag before the number it reads the repository name as the target and
  refuses a merge it should allow.
- `check_gh` (`git_guard.rs:12149-12160`) judges a merge only when `merge`
  is the word right after `pr`. gh also accepts its repository flag
  between `pr` and the subcommand, and that form skips the merge check
  entirely, the `--delete-branch` refusal included. This is a fail-open
  gap. This record and the task's pull request describe it in class words
  only; the exact forms go in the task's tests.

The task makes the guard resolve the repository the same way gh does, run
the lookup against it, and find the merge subcommand wherever gh accepts
it. Non-goals: help forms (TSK-1073 AC-40, was TSK-1024 AC-10); the
server-side landing modes, the administrator override and
enforcement-changing pull requests (TSK-1398 AC-4); gh aliases.

```text
gh pr merge <target> [flags]
        |
        v
repository, in gh's own order:
  1. --repo / --repo= / -R           (a URL target names its own repository)
  2. GH_REPO: inline in the command, else the hook's environment
  3. the folder's remote: the command's cd target, else the hook's folder
        |
        v
gh pr view <target> --repo <resolved>  (or run in the resolved folder)
        |
        v
base unprotected -> allow; protected, unreadable, timed out,
unresolvable or contradictory -> refuse (git.pr_merge_to_protected)
```

### Decided: the repository flag needs no head match

The repository flag and `GH_REPO` are requester text. They decide only
which repository the base is read from. Because the guard resolves the
repository in gh's own order, the guard and gh read the same repository
for the same command. A false `--repo` therefore points both at the same
pull request: the base the guard judges is the base gh merges into. No
head match against `--match-head-commit` is needed to make the base read
sound. `--match-head-commit` stays good practice and this task does not
require it. Decided by the Director on 2026-11-09, relayed by coord/ci.

## Outcome

After this merges, an agent session can merge a pull request into an
unprotected base with `gh pr merge N --repo owner/repo` from any folder,
the workspace root included, and every form gh accepts for naming the
repository is judged against the base of that repository.

## Acceptance Criteria

- AC-1 When `gh pr merge` names a repository with `--repo O/R`, `--repo=O/R` or `-R O/R`, git-guard shall read the pull request's base from that repository whatever the hook's working folder, and shall not read the flag's value as the merge target; a target given as a pull request URL shall be read from the repository the URL names, as gh does. Evidence: git-guard unit tests with a fixed lookup that records the repository it was asked for, one per flag form and flag position, failing before at d8274e43e and passing after.
- AC-2 With no repository flag, git-guard shall take the repository in gh's order: a `GH_REPO` the command sets inline (an assignment prefix or another form the guard's shell model already reads), else `GH_REPO` in the hook's environment, else the remote of the folder the command runs in (its `cd` target as the shell model resolves it), else the hook's own folder. Where gh's order settles a conflict the guard shall follow gh, so a flag beats `GH_REPO` and an inline value beats the hook's environment. Evidence: unit tests per source and for each precedence pair.
- AC-3 git-guard shall keep refusing under `git.pr_merge_to_protected` when no source names a readable repository, when a `GH_REPO` is set in a form the guard cannot read, when the sources disagree where gh's order would not settle it (for example two different inline `GH_REPO` values, or an inline value the guard cannot parse), when the command's working folder cannot be resolved, or when the lookup fails or times out. A protected base shall be refused through every source, and `--delete-branch` shall stay refused whatever the base and the flags. Evidence: the negative fixtures in AC-4, failing closed before and after.
- AC-4 The builder shall cover each case as a fixture: `--repo O/R`; `--repo=O/R`; `-R O/R`; inline `GH_REPO`; hook-environment `GH_REPO`; an unreadable `GH_REPO`; a flag and `GH_REPO` naming different repositories (the flag wins, as in gh); a `cd` target with a remote; no source at all (refused); a protected base through each source (refused); a flag naming a different repository whose pull request with that number has a protected base (refused); a repository flag value placed after `--` (not read as the flag). Evidence: the fixtures in the git-guard unit tests, each named for its case.
- AC-5 git-guard shall find the `merge` subcommand of `gh pr` in every position gh accepts, the repository flag before the subcommand included, so that every such form gets the same judgement as the plain form, the `--delete-branch` refusal included. Evidence: unit tests for each accepted placement, failing before at d8274e43e (allowed) and passing after (judged); a form the guard cannot place is refused.
- AC-6 The lookup shall pass the resolved repository to gh as `--repo`, or run gh in the resolved folder, under the existing bounded timeout (`GUARD_PR_LOOKUP_SECS`), and shall return no base on any failure. Evidence: a CLI test with a stub `gh` that records its arguments and working folder, and a timeout test.
- AC-7 (journey) From a folder with no git remote, `gh pr merge N --repo owner/repo` into an unprotected base shall be allowed and into `main` refused, judged by the worktree's built binary through the installed hook path; evidence: the hook payload runs and their output in the pull request body, with the same payloads refused at d8274e43e for the unprotected case.
- AC-8 The pull request shall state, in class words, the threats closed (a guard that judged the wrong repository's base, and a subcommand placement that skipped the merge check) and why the design is the standard one; evidence: the pull request body.
