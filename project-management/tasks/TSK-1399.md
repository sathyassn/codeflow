# TSK-1399: The pr merge guard reads the base of the repository the command names

## Description

git-guard allows `gh pr merge` only when a lookup proves the pull
request's base is not protected; any doubt refuses under
`git.pr_merge_to_protected` (`check_gh_pr_merge`,
`crates/codeflow-core/src/hooks/git_guard.rs:12229`, at the line's
d8274e43e). The lookup (`gh_pr_base` and `gh_pr_base_blocking`,
`crates/codeflow-cli/src/cmd/hook.rs:855` and `:867`) runs
`gh pr view <n> --json baseRefName` in the hook process's own working
folder. It receives only the target (`PrBaseLookup`, `git_guard.rs:37`),
so the command's repository flag, its `GH_REPO` and its working folder
never reach gh.

Found on 2026-11-09 (read-only diagnosis by coord/ci): from the
agentic-systems workspace root, which has no git remote and is where
sessions start,
`gh pr merge 736 --repo sathyassn/codeflow --merge --match-head-commit <sha>`
into the unprotected line `integration/EPC-022-the-3-2-0-milestone-fixes`
was refused, because gh answered "no git remotes found". The same payload
with the hook process in the codeflow root was allowed. A leading
`cd <repo> &&` does not help, because the hook runs before the command.

Two more defects sit in the same parse, found while filing this record
(installed 3.1.0 at 698cc8789; the code is unchanged at d8274e43e):

- `pr_merge_target` (`git_guard.rs:12281`) does not know the repository
  flag takes a value (`GH_PR_MERGE_VALUE_FLAGS`, `:12268`), so with the
  flag before the number it reads the repository name as the target and
  refuses a merge it should allow.
- `check_gh` (`git_guard.rs:12149-12160`) judges a merge only when `merge`
  is the word right after `pr`. gh also accepts its repository flag
  between `pr` and the subcommand, and that form skips the merge check
  entirely, the `--delete-branch` refusal included. This is a fail-open
  gap. This record and the task's pull request describe it in class words
  only; the exact forms go in the task's tests.

The task makes the guard ask gh itself which base the merge would use,
with the same inputs the merge will use, and find the merge subcommand
wherever gh accepts it. Non-goals: help forms (TSK-1073 AC-40, was
TSK-1024 AC-10); the extra refusals TSK-1398 AC-4 adds for the
server-side landing modes and enforcement-changing pull requests, which
stay with TSK-1398. The server-side landing modes are not exempt from
this task: every form that uses them still falls under the
protected-base check, as AC-12 requires. The administrator override is
not left to TSK-1398: AC-12 refuses every override form outright in this
task, with no dependency. gh aliases are in scope too: AC-12 resolves an
alias and judges its expansion, or refuses it.

```text
gh [env] pr [repo flags] merge [selector] [repo flags] [other flags]
        |
        v
guard reads: the gh executable, the selector, every repository flag
(pflag rules), the command's inline environment, the command's folder
        |  any of these unreadable or not reproducible -> refuse
        v
<same gh> pr view <selector> <repo flags as given> --json baseRefName,number,url
  argv only, in the command's folder, with the command's inline
  environment, non-interactive, under GUARD_PR_LOOKUP_SECS
        |  timeout, non-zero exit, bad JSON, no base,
        |  or number/url not matching the selector -> refuse
        v
base protected -> refuse (git.pr_merge_to_protected)
base unprotected -> allow only if an effective forge rule is
  established to bind this credential on every branch the target's
  policy protects; an exemption or an unreadable rule -> refuse
--delete-branch -> refuse always
administrator override (--admin, alias, API bypass) -> refuse always
```

### Decided: the guard asks gh the same question the merge asks

The guard does not re-implement how gh chooses a repository and a pull
request. gh's own resolution has more steps than a flag, `GH_REPO` and a
remote:

- a pull request URL selector outranks `--repo` and `GH_REPO`;
- an unqualified `OWNER/REPO` takes its host from `GH_HOST`, else the
  config's default host;
- with no flag and no `GH_REPO`, gh uses the `gh repo set-default`
  resolution, else the remotes in the order `upstream`, `github`,
  `origin`;
- an empty selector is the current branch's pull request in the folder
  gh runs in.

A copy of that order in the guard would drift from gh. So the lookup runs
the same gh executable with the command's selector and repository flags
as given, in the folder the command will run in, with the command's
inline environment applied. The match covers exactly those inputs: the
executable, the selector, the repository flags, the folder and the
inline variables. Given them, gh resolves the repository, host,
set-default remote and current branch for the lookup as it will for the
merge. Anything else that can change gh's resolution, such as shell
state the hook cannot see, is the environment residual below. Within
the match, the repository flag and `GH_REPO` are requester text, but a
false value points the lookup and the merge at the same pull request,
so no head match is needed; `--match-head-commit` stays a practice and
this task does not require it. Director's direction of 2026-11-09, relayed by
coord/ci, after Grok's review of the first record.

### Threats and residuals

- Closed: a guard that judged a different pull request's base than the
  one gh merges (AC-1 to AC-4, AC-6, AC-9), and a subcommand placement that skipped
  the merge check (AC-5).
- Closed: a base judged by the session repository's policy instead of
  the target's (AC-11), and gh forms that merge or change a ref without
  being judged (AC-12).
- Closed: a gh alias that expands to a merge or ref change, which
  `check_gh` never saw as one (AC-12).
- Closed: an administrator-override merge that passes the check while
  the base reads unprotected and, after a retarget, lands on a protected
  base by bypassing the forge's rulesets. A head pin cannot pin the
  base, so AC-12 refuses every override form outright, whatever base the
  lookup returns.
- Closed: a plain merge, with no override flag, by a credential the
  forge rules exempt (classic protection with `enforce_admins` off, or
  a bypass actor that covers it), which passes the check on an
  unprotected base and lands on a protected base after a retarget with
  the same head. AC-12 allows a merge only when a forge rule is
  established at check time to bind the credential on every protected
  base, and refuses otherwise.
- Residual, time of check: the base can be retargeted between the
  lookup and the merge, and `--match-head-commit` pins the head, not
  the base. This task claims only what AC-12 establishes: every branch
  the target's policy protects has a forge rule that requires a pull
  request and exempts this credential by no bypass actor and no
  administrator exemption, so a retargeted merge there must still pass
  that rule. The forge can still accept a merge that meets the rule's
  own requirements, such as passing required checks, while the target's
  policy forbids it; this task does not claim to close that case.
- Residual, environment: the hook sees the command line and its own
  environment, not the shell the command will run in. In a harness
  where shell state persists, a variable exported earlier or set by a
  profile can change what gh resolves without the hook knowing. The
  forge's rules are the backstop only as far as AC-12 establishes, as
  above. This task does not claim to close it.
- The lookup runs gh, and gh runs git, in the command's folder before
  the guard's verdict. AC-6 requires the traced command list, the
  program-valued configuration each command can run, and a local
  fixture showing both that no such program runs and that the
  repository and pull request gh resolves stay the same.

## Outcome

After this merges, an agent session can merge a pull request into an
unprotected base with `gh pr merge N --repo owner/repo` from any folder,
the workspace root included, where the forge rules bind its credential
as AC-12 requires, and every form gh accepts for naming the repository
is judged against the base of that repository.

## Acceptance Criteria

- AC-1 git-guard shall read the command's repository flags as pflag reads them: `--repo O/R`, `--repo=O/R`, `-R O/R`, `-R=O/R` (one `=` stripped), `-RO/R`, before or after `merge`, with the last of repeated flags winning, and shall not take a flag's value as the selector. It shall pass the selector and every repository flag to the lookup exactly as given, as separate arguments, never through a shell string, so gh applies its own last-flag rule. A selector or repository flag it cannot parse (a missing or empty value included) shall be refused. Evidence: git-guard unit tests per spelling, placement and repetition, each with a fixed lookup that records the arguments it was given, failing before at d8274e43e and passing after.
- AC-2 The lookup shall run `gh pr view` with the command's selector (a number, a branch, a URL or none) and its repository flags, `--json baseRefName,number,url`, in the folder the command will run in as the shell model resolves it (its `cd` target, else the hook's folder), with every variable the command sets inline for gh applied (an assignment prefix or another form the shell model already reads; the last assignment of a repeated name wins, as in the shell). Evidence: unit tests whose fixed lookup records the selector, flags, folder and environment it was given, one per case in AC-4.
- AC-3 git-guard shall keep refusing under `git.pr_merge_to_protected` when the command sets a variable for gh whose value the guard cannot reproduce, when the command's folder cannot be resolved, when the selector or a repository flag cannot be parsed, or when the lookup cannot run as AC-6 requires. A protected base shall be refused through every input. Evidence: the negative fixtures in AC-4; the cross-repository fixture (a flag naming a repository whose pull request with that number has a protected base, while the hook folder's own pull request has an unprotected one) is allowed before at d8274e43e and refused after, and its lookup record shows the other repository.
- AC-4 The builder shall cover each case as a fixture, each named for its case and recording what the lookup was given: each spelling and placement in AC-1; two `--repo` flags (both passed through, in order); a URL selector together with a different `--repo` and `GH_REPO` (passed through unchanged, so gh's URL rule decides); inline `GH_HOST` with an unqualified `--repo`; inline `GH_REPO`, and two inline `GH_REPO` values (the last applied); `GH_REPO` in the hook's environment; a folder with `upstream` and `origin` remotes and no flag, and a `set-default` resolution (the lookup runs in that folder); an empty selector after a `cd` (the lookup runs in the `cd` folder); the field command, from a hook folder with no remote, a `cd` to a repository, a number selector and no repository flag (the lookup record shows the `cd` folder; refused before at d8274e43e, allowed after when that repository's base is unprotected); `GH_CONFIG_DIR` set inline (recorded on the lookup); a variable whose value the guard cannot read (refused); an unresolvable folder (refused); an unparseable flag (refused); each AC-6 answer failure (refused); each AC-9 executable case (refused); a protected base through each input (refused); the cross-repository case of AC-3; a repository flag value after `--` (not read as the flag). The URL-against-`GH_REPO` fixture and the two-remote fixture fail before at d8274e43e by being allowed when the hook folder's pull request is unprotected. Evidence: the fixtures in the git-guard unit tests.
- AC-5 git-guard shall find the `merge` subcommand of `gh pr` in every position gh accepts, the repository flag before the subcommand included, so that every such form gets the same judgement as the plain form. `--delete-branch` shall stay refused whatever the base, and the refusal and the `core.bare` protection it exists for shall judge from the same resolved lookup as the base check: any part of them that reads the pull request or its branches uses that one answer, never a second resolution. Evidence: unit tests for each accepted placement, failing before at d8274e43e (allowed) and passing after (judged); `--delete-branch` with each input form and with a failed lookup, refused; a form the guard cannot place is refused.
- AC-6 The lookup shall run non-interactively (no prompt, no terminal input) under the existing bounded timeout (`GUARD_PR_LOOKUP_SECS`), and git-guard shall refuse on a timeout, a non-zero exit, an answer that is not valid JSON, an answer without the base, or a returned number or url that does not match the selector (a number selector must equal the returned number; a URL selector must name the same host, repository and number as the returned url). Because the lookup runs gh, and so git, in the command's folder before the verdict: (a) `## Findings` shall list, in class words, every git command the lookup's gh runs in the command's folder for a number, a branch, a URL and an empty selector, taken from a trace of the same gh the AC-7 journey runs, commands only some selectors reach included; the number, branch and empty selector traces shall have no repository flag and no URL selector, so gh reads the folder's remotes and the set-default key, and a trace that only uses a repository flag does not satisfy (a); (b) for each listed command, `## Findings` shall name which program-valued configuration it can run, by class: a filesystem monitor, an ssh command, a credential helper, a hook, and included configuration that sets any of those; (c) a local fixture, which can be re-run offline and in a fork, shall run the same gh binary as the AC-7 journey, with that gh running real git: the command's folder is a local repository with a local bare remote, and the base, number and url come from a gh host pointed at a fixture server or another local substitute that returns those three fields; a pull request on the public forge does not satisfy (c), and a separate live run may be recorded but is not this evidence. The fixture shall run a number, a branch and an empty selector with no repository flag and no URL selector. The folder's configuration shall name a program for every class in (b), a class the table calls unreachable included, with one marker file per class. For each selector: no marker shall show a run, in every case, and each named program writes its own marker when it runs; when the lookup returns a base, number and url, they shall match a second lookup that still reads the remote URLs and the set-default resolution; a refusal counts only if no marker shows a run, and never excuses a program that ran; a prevention that changes which repository or pull request is resolved shall refuse rather than return that answer, and a refusal with no marker showing a run satisfies this criterion. Evidence: a CLI test with a stub `gh` that records its arguments, folder and environment and returns each failing answer; a timeout test; the traced list and the class table in `## Findings`; the local fixture in (c), with its marker files.
- AC-7 (journey) From a folder with no git remote, `gh pr merge N --repo owner/repo` into an unprotected base shall be allowed and into `main` refused, judged by the worktree's built binary through the installed hook path with the real gh; evidence: the hook payload runs and their output in the pull request body, with the same unprotected payload refused at d8274e43e.
- AC-8 The pull request shall state, in class words, the threats closed and the two residuals in "Threats and residuals" (the time-of-check gap, with `--match-head-commit` and the forge's rulesets as the backstop, and the shell environment the hook cannot see), and why asking gh itself is the standard design; evidence: the pull request body.
- AC-9 The lookup shall run the same gh executable the command would run, resolved from `PATH` as the hook sees it. git-guard shall refuse when the command names gh by a path, changes `PATH` inline, or the guard cannot resolve the same executable. Evidence: unit tests for a path-named gh, an inline `PATH` change and an unresolvable gh, each refused, and a plain `gh` as the control.
- AC-10 git-guard shall refuse a base found protected and a base it could not confirm with different messages under `git.pr_merge_to_protected`. The protected message shall name the base; the unconfirmed message shall name its cause (a lookup failure, a timeout, no remote, an answer it cannot parse). Each message shall name the sanctioned path for its case. Today one message covers both (`git_guard.rs:12258-12263` at 4dc4dbf4c). Evidence: git-guard unit tests asserting the protected message and the unconfirmed message for each cause, and the `git.pr_merge_to_protected` row in `docs/policy-reference.md` naming both.
- AC-11 git-guard shall judge the base by the trusted landed policy of the host and repository the lookup resolves, never by the session repository's policy, for every repository selector: `--repo` and `-R`, a URL selector, `GH_REPO`, and gh's repository defaults (the routes AC-4 exercises). It shall refuse under `git.pr_merge_to_protected` when that policy cannot be read or verified. Today the session repository's landed policy judges every target (`crates/codeflow-cli/src/cmd/hook.rs:402-432` at 4dc4dbf4c). The builder shall record in `## Findings`, with its reasoning, how the target's landed policy is read and verified. Evidence: that record in `## Findings`; a test where the base is protected only by the target's policy and is refused; a test where a provably unprotected base, run from a folder with no remote, is allowed; a test per selector route that the policy read is the resolved repository's; a test where the target's policy cannot be read or verified, refused.
- AC-12 git-guard shall resolve and judge every gh form that can merge a pull request or change a ref on the forge by the same rules as `gh pr merge` (AC-1 to AC-6, AC-9 to AC-11), and shall refuse a form it cannot resolve and judge safely. These forms include: `gh api` REST calls to pull request merge and git ref endpoints (`check_gh`, `git_guard.rs:12149-12160` at 4dc4dbf4c, skips `gh api` entirely today); GraphQL mutations that merge or change a ref, such as `mergePullRequest` and `updateRef`; auto-merge and merge-queue enrollment, such as `gh pr merge --auto` and `enablePullRequestAutoMerge`; the administrator override; and a gh alias. git-guard shall refuse every administrator-override merge form outright, whatever base the lookup returns, because a head pin cannot pin the base and an override defeats the forge's rulesets: `gh pr merge --admin` in every spelling and placement gh accepts, an alias that expands to it, and REST or GraphQL requests that ask to bypass branch protection or rulesets, such as a merge request that asks for a bypass or a `mergePullRequest` mutation with a bypass input. For an alias, git-guard shall resolve it against gh's own alias configuration, read the same fail-closed way, and judge the expansion by the same rules; it shall refuse when it cannot read that configuration or resolve the alias, and shall refuse an alias whose expansion is a shell alias (`!`-prefixed), whose effect it cannot judge. As a secure default the Director set on 2026-11-10, which the operator can overrule, git-guard shall allow a `gh pr merge` or an API merge (REST or GraphQL) into an unprotected base only when an effective forge rule is established at check time to bind the merge's credential on every branch the target's landed policy protects: no bypass actor covers that credential, classic protection has `enforce_admins` on, and the rule requires a pull request to update the branch. git-guard shall read those rules with the same bounded, fail-closed gh lookup as the base, and shall refuse when it cannot establish them (an unreadable rule set, a timeout, a lookup the credential's token cannot make) or finds an exemption. The refusal message shall name the cause, the forge setting to change and the sanctioned path. These refusals fall under `git.pr_merge_to_protected`, whose configured level is the adopter's relief. The pull request shall record a sweep table of every gh form the guard judges by a looked-up or resolved target, or that can merge or change a ref, in class words, naming how each is judged; a row may say "left as is", with its reason, only for a form that cannot merge or change a ref. Evidence: the sweep table in the pull request body; for each merge-capable or ref-mutating form, a test that a protected base or ref is refused and a test that a form the guard cannot resolve and judge is refused; for aliases, a test that an alias expanding to `pr merge` on a protected base is refused, a test that an alias the guard cannot resolve is refused, with unreadable alias configuration as one of those cases, a test that a shell alias is refused, and a test that an alias expanding to a read-only verb is allowed; for the administrator override, a refusal test for each spelling and placement of `--admin`, for an alias that expands to it and for each REST or GraphQL bypass form, including one where the base reads unprotected at check time; for the forge rules, a regression test where a plain API merge by a credential with bypass rights, with the head unchanged after a retarget, is refused, an allowed control where the rule binds the credential, and refusal tests for classic protection with `enforce_admins` off, a bypass actor that covers the credential, an unreadable rule set and a timeout.
