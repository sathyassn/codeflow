# TSK-1152: A status change rides in a PR that is already landing

## Description

Operator direction, 2026-11-01 about 14:22 EST: epic and task status updates are marked along with the work that completes them, and no PR is raised only to mark a record done or cancelled, so time, money and CI minutes are not wasted. A task's completion already rides in its own PR. Three places force a status-only PR today: `outside_own_record` in `crates/codeflow-core/src/workgraph/acceptance.rs` (`:3249`) refuses any change to another task's record in a task PR; `task_record_additions` in `crates/codeflow-cli/src/cmd/ci/classification.rs` (`:1020`) lets a task PR add only its own record; and the cancellation route for an unlanded standalone task goes through its own `plan/` PR (`amendment.rs:337`, `classification.rs:703`, `project-organization.md:335-344`, `docs/troubleshooting.md:174`).

The change: a task PR may carry the `todo` or `blocked` to `cancelled` change of another task, and the cancelled record of an abandoned standalone task, when the carrying task's own reviewed record names it. The epic close PR carries the epic's `complete` status with its outcome record; an epic cancellation, a supersession and a follow-up status change ride in an open planning PR or the task PR that settles them. The skills, docs, templates and managed rules say so, and the `plan/` cancellation code path stays accepted for records already filed that way but is no longer recommended; with no carrier landing, the cancellation waits on the abandoned branch for the next PR that touches that work. Research and the full place list (25 rows): `coordination/coordinators/planning/status-rides.md` in the agentic-systems workspace.

Non-goals: no change to the transition table or to completion binding; a task PR still never completes another task or any epic. TSK-1036 AC-4 refuses a head "that changes another record's status"; this task narrows that refusal for the named, status-only cancellation and no other case, and its builder updates the TSK-1036 test fixtures that assert the broader refusal.

## Outcome

After this merges, an agent or maintainer can cancel or supersede a task in the PR that settles the work, and `codeflow ci` accepts it; no guidance sends them to a PR opened only to change a status.

## Acceptance Criteria

- AC-1 When a task PR's own record names another task with the new `cancels` key, and that task is `todo` or `blocked` on the target, `codeflow ci` shall accept the PR carrying that task's change to `cancelled` (status plus the `- cancelled:` and `- scope:` Closeout lines) with no `work.criteria_frozen` finding; evidence: a `codeflow ci` CLI fixture over a carrier and carried record that passes, failing before the change.
- AC-2 `codeflow ci` shall still refuse each of these with a message that names the carrying routes: (a) a change to a record the key does not name; (b) any change beyond status and the two Closeout lines the verb writes (criteria, `depends_on`, body, and existing Closeout content); (c) a transition the lifecycle judge refuses; (d) a cancellation without reason or scope; (e) a carried completion of another task; (f) any epic record change in a task PR; (g) a named record that is not `todo` or `blocked` on the target, including a `complete` record and an already `cancelled` one whose Closeout is edited; (h) a rename or identity substitution (id, uid or path) accompanying the cancellation; (i) a key given only in the PR body; and (j) `cancels` added or changed after the carrier's reviewed commit, which invalidates the carrier's existing acceptance binding; evidence: one fixture per refusal (ten), each failing for the stated reason, and the TSK-1036 refusal fixtures updated only where they assert the broader refusal.
- AC-3 When a task PR adds the cancelled standalone record of the task it replaces, named by `cancels`, with both Closeout lines and absent from the merge-base, `task_record_additions` shall accept it, and an added record not so named shall stay refused; evidence: `classification.rs` tests for both.
- AC-4 The `plan/` cancellation code path (`cancelled_standalone`, `cancellation_entry`, `cancellation_push_check`) shall keep accepting a range of that one record with `Task: TSK-NNN`, for compatibility with records already filed that way, but no skill, rule, doc or remedy shall recommend opening such a PR. When no PR is landing that could carry a cancellation, the guidance shall say the cancellation waits: the cancelled record stays on the abandoned task's branch (the branch and worktree are kept) and rides in the next PR that touches that work, and no PR is opened for it alone; the refusal and remedy texts shall name the carrying routes only; evidence: the existing `cancelled_standalone` tests unchanged, a test on the message text, and the AC-5 search.
- AC-5 The rule shall be stated in each place of the Deliverables, with a row-by-row disposition of the 25 rows of `status-rides.md` section 4 in the PR body (done, or not applicable with the reason; row 25, the coordination files, belongs to the Coordinator, and rows 18 and 21 are inspected and either changed or marked not applicable), including the frozen-criteria remedy at `crates/codeflow-cli/src/cmd/ci/acceptance.rs:418` and the doc comments of `cancellation_entry` and `cancellation_push_check`; no text shall send a cancellation to its own `plan/` PR; evidence: the disposition table, `rg -n "own .plan/. pull request|through a .plan/. pull request|cancel.*plan/" assets docs .claude .agents` returning no recommendation, and `codeflow validate --docs` green.
- AC-6 The epic close text (`cf-ship`, `project-organization.md`, `docs/delivery.md`) shall state that the epic's `complete` status is written in the epic close PR with its outcome record, that an epic cancellation rides in an open planning PR, and that no document shows a status-only PR; evidence: the AC-5 search and the `docs/delivery.md` diff.
- AC-7 The managed sources, both skill mirrors, the manifest, the rule-map output and this repository's managed block shall agree; evidence: `cargo test -p codeflow-core --test manifest_consistency` and a clean `codeflow update` check.
- AC-8 (journey) With the built binary in a scratch full-tier repository, a task PR that names a second task in `cancels` shall pass `codeflow ci` at its head, and the same PR with the key removed shall be refused; evidence: both `codeflow ci` runs, quoted in the PR body.
