# TSK-362: Every capability promise resolves to a test, a native record or a declared gap

## Description

Source: the two test integrity audits of 2026-10-17 at
`eaf2ed04e932186cdd26dc4a7e5740cc553acee3`.

`codeflow validate --docs` requires a shipped capability's `verified_by`
list to be non-empty (`crates/codeflow-core/src/validate/docs.rs:423`) and
nothing more; `docs/capabilities.md:16` says the tags are not resolved. By
hand, every tag resolves, but one names a source file (CAP-010,
`codeflow-core src/model_qualification.rs`) and one names a test that
passes without running in CI (CAP-013, `live_eval_pack.rs`). CAP-008's
entry does not say that its GitHub boundary is a stubbed `gh`
(`crates/codeflow-core/src/remote.rs`, `GithubProvider::run_gh`).

The journey map (`crates/codeflow-cli/tests/journey_gate.toml`, 42
entries) is stricter but has two gaps. A pending entry is refused only when
its task is `complete` (`crates/codeflow-cli/tests/journey_gate.rs`, the
pending check near line 196), so "the live pack graded with zero, one and
two available primaries" stays pending on TSK-116, which is cancelled and
superseded by TSK-194, and the gate never demands it. And 13 of 42 entries
name one test as both control and fault; the map check does not require
them to differ.

Moved to EPC-026 on 2026-11-01 and narrowed by its planning pull request: this task keeps the typing and resolution of `verified_by` on the new records (AC-1 to AC-4 below). The journey map rules of the old AC-3, AC-4 and AC-5 are TSK-1142 in EPC-023 and keep every obligation.

Outcome: every capability promise names the kind of proof it needs and
resolves to an existing test identity, a named native verification record,
or a declared gap, and a green gate cannot be read as "every capability and
journey proven" when one is not.

Non-goals: running native qualification (TSK-368) and writing the missing
tests themselves, beyond what a resolved tag needs. Product surface:
`validate --docs` is adopter-facing engine (adopters keep their own
registry); the registry and journey map are this repository's.

## Deliverables

- tag resolution: `crates/codeflow-core/src/validate/docs.rs` (resolve each `verified_by` entry to a test identity, a verification record under `docs/verification/`, or a declared gap with its kind)
- the registry: every entry in `docs/capabilities.md` (17 capabilities), each tag typed as engine, CLI, hosted, native or gap, and CAP-008's stubbed GitHub boundary disclosed
- docs: the `verified_by` format in `docs/capabilities.md` and the validate reference
- release note: `changelog.d/TSK-362.md`

## Acceptance Criteria

- AC-1 When `validate --docs` reads a `verified_by` entry that names no
  existing test identity, verification record or declared gap, it shall
  refuse naming the capability and the entry, and a source file named as
  evidence shall be refused; evidence: tests with a fabricated tag, a
  renamed test, a source file and each valid kind. (serves EPC-026 AC-9)
- AC-2 All 17 capabilities shall validate under the new rule, with each
  native or hosted promise either pointing at a current record or declared
  as a gap, and CAP-008 stating that tests stub the GitHub boundary;
  evidence: `codeflow validate --docs` on the change and the registry diff.
  (serves EPC-026 AC-9)
- AC-3 `verified_by` shall be typed (`test:`, `journey:`, `record:`, `gap:`) on the new records and resolved against the test tree or a `docs/verification/` record; a `shipped` record whose only evidence is `gap:` shall carry `stage: unassessed`; evidence: a fixture per kind. (serves EPC-026 AC-9)
- AC-4 (journey) With the installed build, adding a fabricated tag shall make `validate --docs` fail and restoring it shall pass; evidence: both runs. (serves EPC-026 AC-9)
