# TSK-181: Windows full gate target guarding and Node launcher form

## Description

Grok's review of TSK-142 (PR 742, head `ee35fbf74`) approved it with two
Windows findings at P2, filed here as one follow-up. F1: when the runner
cannot place a target in its kill-on-close job object
(`AdoptError::Unguarded`), it prints a warning and lets the target run
(`crates/codeflow-core/src/testing/runner/mod.rs:411-416`), and
`TargetJob::adopt` resumes the target before it reports the failure
(`target_job.rs:50-53`). If that gate is then killed, the OS frees the
gate lock while the target still runs, which is the failure TSK-142 AC-3
exists to prevent. F2: the two Node targets (`.codeflow/test-config.json`,
`cf-present-qualification` and `docs-portal`) pass their chain to
`scripts/with-node.py` as one single-quoted POSIX string. On Windows the
gate's Auto shell is `cmd.exe /D /S /C` (`runner/mod.rs:512-515`,
`:542-547`), which does not treat single quotes as quotes, so it splits
the line at the first `&&` before the launcher can select a version. The
target fails closed: it never runs on the pinned Node, and it never runs
silently on PATH Node. This task makes an unguarded target fail instead of
run, and gives the Node launcher a form `cmd.exe` passes whole, with
`gate-parity` requiring that form. Non-goal: adding a full-gate run to the
Windows CI job.

## Acceptance Criteria

- AC-1 (serves EPC-020 AC-10) When the runner cannot create, configure or
  join the job object for a Windows target, it shall end that target while
  it is still suspended, so the target's command never runs, and report
  the target failed with a
  message naming the target and the OS error; it shall never warn and let
  the target run outside a job, so the gate lock never frees while a target
  of a killed gate runs. Evidence on this Mac: a platform-neutral unit test
  of the runner's decision for each adopt outcome (joined, job failed,
  resume failed) that requires a job failure to end the child and fail the
  target, and `cargo clippy --workspace --all-targets --target
  x86_64-pc-windows-msvc -- -D warnings` clean. Evidence that needs a real
  Windows runner: a `cfg(windows)` runner test on the Windows CI job that
  forces the job step to fail through a test seam and finds the target
  reported failed, its process gone, and no marker file written by its
  command; and `a_killed_gate_ends_its_target_tree_on_windows` still
  passing there.
- AC-2 When the full gate runs a Node target on Windows, where the Auto
  shell is `cmd.exe /D /S /C`, the whole target command shall reach
  `scripts/with-node.py` unsplit, and the launcher shall run the inner
  chain on the Node version its version file pins in a shell that accepts
  that chain's syntax (the present chain uses POSIX `$(...)` and
  `${...}`); a missing version shall still fail naming the version and
  the file. Evidence on this Mac: a unit test that splits each Node target
  command of `.codeflow/test-config.json` the way `cmd.exe` does (at
  unquoted `&`, `&&`, `|` and `||` outside double quotes, with `^` as the
  escape) and finds the launcher call and its whole inner chain in one
  segment; and `scripts/test_with_node.py` cases for the Windows branch
  that run on any platform (the shell and arguments it builds). Evidence
  that needs a real Windows runner: on the Windows CI job, which installs
  Node 24.18.0, the `docs-portal` target's configured full-mode command
  run through `cmd.exe /D /S /C` logs `with-node: Node 24.18.0` and exits
  0. The present target is not run on Windows; its evidence is the split
  test above.
- AC-3 When a full-mode target runs Node through the launcher in a form
  `cmd.exe` would split, such as today's single-quoted chain,
  `scripts/gate-parity.py` shall report drift naming the target and the
  required form, and it shall accept the new form. Evidence:
  `scripts/test_gate_parity.py` cases for the old form refused and the new
  form accepted, and `python3 -B scripts/gate-parity.py` OK on this
  repository's config.
