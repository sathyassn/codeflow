# TSK-1082: A guard that does not answer in time blocks the tool call where the harness allows it

## Description

Found live on 2026-10-29: a Grok Build 1.0.70 seat logged `pre_tool_use hook
(project/settings) failed, ignored: timed out after 5000ms` and ran the tool
call. CodeFlow's in-session guards (`codeflow hook git-guard`, `exec-guard`,
`edit-guard`) fail open when a harness kills them on a timeout, because the
`|| { …; exit 2; }` wrapper in the hook command never runs on a kill.

What each harness does on a `PreToolUse` command hook timeout, from its
source or documentation:

| Harness | On timeout, crash or other exit | Blocking option | Timeout default |
|---|---|---|---|
| Claude Code 2.1.312 | lets the call through | `"onFailure": "block"`, from 2.1.295 | 600 s |
| Codex 0.166.0 | lets the call through (`codex-rs/hooks/src/events/pre_tool_use.rs:211-217`, tag `rust-v0.166.0`) | none (`protocol/src/hooks.rs:150-185`) | 600 s |
| Grok 1.0.70 | lets the call through (`~/.grok/docs/user-guide/10-hooks.md:299`) | none | 5 s |

Only exit 2 with a reason on stderr, or a deny answer, blocks in all three.
Grok also reads the guard entries in `.claude/settings.json`, which carried
no `timeout`, so Grok gave them its 5 second default.

A reproduction on this line found a real stall: a FIFO named by a git
configuration include blocks libgit2 discovery inside `git-guard` and
`exec-guard`, and both waited until killed (TSK-283's follow-up F3).

The change, secure by default:

- each guard arms its own deadline before it reads its payload and refuses
  with exit 2 and a reason after 20 seconds without a decision, which blocks
  in every harness;
- every shipped guard entry carries `"timeout": 30` in the Claude presets,
  `.grok/hooks/codeflow.json` and `.codex/hooks.json`, and the Claude
  entries carry `"onFailure": "block"`;
- `codeflow update` gives an existing Claude guard entry the shipped fields
  (a codeflow-owned hook entry takes the shipped object), and moves the Grok
  and Codex files by its 3-way merge;
- `codeflow doctor --check guard-timeouts` warns about a guard entry in any
  file a harness reads that lacks the shipped timeout or, in Claude settings,
  `"onFailure": "block"`, and states the residual below.

Residual, stated in `docs/policy-reference.md`, ADR-0075 and the doctor
output: Codex and Grok have no fail-closed setting, so a guard process that
does not start, or is starved past 30 seconds, fails open there. Claude blocks
it through `onFailure`.

Not in scope: bounding libgit2 discovery itself (the guard's deadline now
bounds its effect), Codex or Grok harness changes, and the workspace root's
own settings, which take the change through `codeflow update` after release.

## Outcome

After this merges, a person running Claude Code, Codex or Grok with CodeFlow's guards can rely on a guard that stalls inside its own process blocking the tool call, and on Claude blocking any guard failure; doctor tells them when a guard entry lacks the fields and what still fails open in Codex and Grok.

## Acceptance Criteria

- AC-1 When a guard has reached no decision 20 seconds after it starts, it shall exit 2 with a reason on stderr that names `codeflow doctor --check git-config-includes`; evidence: `a_guard_stalled_on_a_fifo_include_refuses_at_its_deadline` in `hooks_cli.rs`, failing before the change (git-guard still ran after 30 s) and passing after. (journey)
- AC-2 On an ordinary call each guard shall decide well inside its deadline and the hook timeout; evidence: `each_guard_decides_well_inside_its_deadline` in `hooks_cli.rs` (under half the deadline) and the unit test that the deadline sits at least 5 s inside the timeout.
- AC-3 Every shipped guard entry shall carry `"timeout": 30`, the same in the Claude, Grok and Codex files, and every Claude guard entry, and no other Claude hook entry, shall carry `"onFailure": "block"`; evidence: `every_shipped_guard_entry_carries_the_shared_bounds` in `guard_timeouts.rs`.
- AC-4 When a project's Claude guard entries lack the shipped fields, `codeflow update` shall give them the shipped fields, keep the project's own hooks, report each change and change nothing on a second run; evidence: `update_gives_the_guards_the_shipped_timeout_and_failure_handling` in `settings_merge.rs`, failing before the merge change and passing after.
- AC-5 Doctor shall warn, naming the file and guard, for a guard entry with no `timeout`, another timeout, or (Claude settings) no `"onFailure": "block"`, in `.claude/settings.json`, `.claude/settings.local.json`, `.grok/hooks/*.json` and `.codex/hooks.json`, shall fail on a hook file it cannot parse, and shall state the Codex and Grok residual; evidence: the unit tests in `guard_timeouts.rs`, one per case.
- AC-6 The warning's printed step shall clear it on a project installed with the earlier entries; evidence: `clears_doctor_guard_timeouts` in `remedy_clearing/main.rs`. (journey)
- AC-7 This repository's own harness files shall carry the shipped entries, written by `codeflow update`; evidence: `codex_hooks.rs` dogfood tests and `codeflow doctor --check guard-timeouts` passing in the worktree.
- AC-8 The docs shall state the design and the residual; evidence: `docs/policy-reference.md`, ADR-0075's residual line, `docs/troubleshooting.md` and the changelog fragment.
