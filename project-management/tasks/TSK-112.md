# TSK-112: git-guard judges a git command by the repository it targets

## Description

git-guard judges a git command reached through `cd <path>`, `git -C <path>`
or a path held in a shell variable against the session repository instead
of the repository the command targets, so it blocks allowed work. Observed
case (Fable's Plan v3 review, finding N11): a commit in a scratch repository
through `-C` was blocked as a commit on `main`. Design v4 records this as a
small standalone task: judge `cd` and `$VAR` paths by their target. Non-goal:
any relaxation of a guard rule for the session repository.

## Affected surfaces and interfaces

- git-guard in `crates/codeflow-core/src/hooks/` and its tests (CAP-003).
- Every harness that wires git-guard (Claude, Codex, Grok hooks).

## Acceptance Criteria

- [x] AC-1 When a git command reaches another repository through `cd <path>`
      or `git -C <path>`, git-guard shall judge the branch and protection
      rules of that repository; the observed `-C` false block shall pass;
      evidence: a regression test reproducing the observed case.
      Result: `test_tsk112_relative_dash_c_after_cd` and
      `test_tsk112_target_only_protected_pattern_blocks` (both fail on the
      3.0.0 guard), and `test_tsk112_read_target_reads_branch_and_whose_policy`
      on real repositories. With the operator's stricter reading, a repository
      without a policy keeps the default protection of `main` and `master`
      (`test_tsk112_repo_without_policy_keeps_default_protection`).
- [x] AC-2 When the path is held in a shell variable, git-guard shall judge
      the repository it resolves to where it can resolve it; evidence:
      tests for a resolvable variable.
      Result: `test_tsk112_variable_path_judged_by_its_target` (`R=…;`,
      `&&`, `export`, `${R}`, a variable built from another, `cd "$R"`).
- [x] AC-3 A command that targets a protected branch through `cd`, `-C` or a
      variable shall still be blocked. git-guard grants a resolved-target
      verdict only when every path the shell could take is modeled; when it
      cannot prove the target (an unset or escaped variable, a subshell, a
      `cd` that can fail before `;`, an unmodeled launcher environment), a
      mutation shall block, from any session branch, with a message that
      names what could not be resolved and says how to make it resolvable
      (a literal path, or `cd <path> &&` first), never a claim that the
      target is safe (SPC-013 planning resolution 13, tightened by the
      review round 1 decision B1); evidence: negative tests, including an
      unresolvable variable from an unprotected session, asserting the
      output text.
      Result: `test_tsk112_unresolved_target_blocks_and_says_how_to_resolve`
      (sessions `main` and `feat/s`, message, remedy and note);
      `test_tsk112_failing_cd_keeps_the_old_directory`,
      `test_tsk112_escaped_dollar_is_not_expanded`,
      `test_tsk112_launcher_environment_is_modeled`,
      `test_tsk112_nested_moves_are_unresolved` and
      `test_tsk112_uncertain_moves_never_loosen_the_verdict`;
      `test_tsk112_dash_c_with_git_dir_judges_the_git_dir` closes the
      `-C` plus `--git-dir` wrong allow. On real repositories,
      `git_guard_blocks_targets_it_cannot_prove` reproduces the review's
      probe table.
- [x] AC-4 (journey) With the installed CLI's hooks in a Claude Code session,
      a commit in a scratch repository through `-C` shall pass and a commit
      on the session repository's `main` shall be blocked; evidence: session
      transcript or hook test driven by the harness payload.
      Result: `git_guard_judges_the_repository_a_command_targets` in
      `crates/codeflow-cli/tests/hooks_cli.rs` runs the built binary on a
      Claude Code `PreToolUse` payload against real repositories: `-C` into
      a scratch repository on `feat/x` exits 0, a commit on the session's
      `main` exits 2, an unresolved variable exits 2 with the disclosure.

## Closeout

- Shipped: target resolution in `hooks/git_target.rs` and `judge_target`
  in `hooks/git_guard.rs`; the CLI resolver reads the target's branch and
  effective policy (`git_guard::read_target`). A flat line (simple
  commands joined by `;`, `&&` or newlines; a `$(…)` inside a word is
  allowed) is modeled: the working directory is a set of candidates, a
  `cd` proves its move only across `&&`, and every candidate is judged by
  its own branch and policy. Anything unmodeled leaves the target
  unresolved, and a mutation then blocks as if on a protected branch.
- Review round 1 (Codex, changes requested): T112-1 escaped `$`, T112-2
  `env` launcher environment, T112-3 failing `cd` before `;`, T112-4
  unresolved targets now block (decision B1). All fixed, with unit and
  real-repository regressions.
- Review round 2 (Codex, changes requested): R2-1 a location or
  assignment built from `$(…)` or backticks was read as known; the splitter
  now leaves a placeholder that is never expanded. R2-2 a newline or comment
  after `&&` lost the proven move; it now continues the and-list. Also
  closed: `pushd`, a negated `cd` and an assignment whose redirection can
  fail are no longer modeled. Evidence: `test_tsk112_substituted_locations_are_unresolved`,
  `test_tsk112_and_list_continues_across_newlines`,
  `test_tsk112_unmodeled_moves_stay_unknown`, and both substitution forms
  on real repositories in `git_guard_blocks_targets_it_cannot_prove`.
- Review round 3 (Codex, changes requested): R3-1 a substitution before
  the subcommand hid it (`git $(printf '') commit`). A substitution at or
  before the subcommand, in a global option, in the program name, unquoted
  in a judged subcommand, or outside a quoted message value now makes the
  command unclassifiable, and it blocks (see round 4 for the rule chosen).
  Boundary (confirmed by the primary): after the subcommand, the rule
  applies only to the subcommands the guard judges (commit, merge,
  cherry-pick, rebase, reset, branch, config, update-ref, symbolic-ref,
  fast-import, push, checkout, switch). A read-only command such as
  `git show "$(…)"` or `git log "$(…)"..HEAD` passes, since its arguments
  cannot turn it into a mutation.
  Evidence: `test_tsk112_substitution_before_the_subcommand_blocks`, the
  property test `test_tsk112_no_placeholder_before_the_subcommand_allows`
  (over 200 insertions and attachments), and the four probes on real
  repositories in `git_guard_blocks_targets_it_cannot_prove`.
- Review round 4 (Codex, changes requested): R4-1 the unclassifiable
  branch returned early, so with `git.local_ref_protection` off or warn a
  known `git commit` on a `commit_to_protected: block` main passed once a
  substitution was added outside its message. Classification uncertainty
  now adds its own verdict and the judgment continues: target resolution,
  the protected-commit check and every other rule still run, and the result
  is the strictest of them. The uncertainty verdict itself takes the
  strictest level among the rules the unknown part could break (all branch
  rules when the subcommand is unknown, else the subcommand's own rules),
  judged under each candidate target's policy. For commit, merge,
  cherry-pick, rebase and reset, which act on the branch they run on,
  unknown arguments matter only on a protected target. Evidence:
  `test_tsk112_uncertainty_keeps_the_protected_commit_check` (both forms,
  `local_ref_protection` off, warn and block, literal, default-policy and
  feature-branch controls) and `git_guard_uncertainty_keeps_the_protected_commit_check`
  on real repositories.
- Behavior change to note: a `cd` inside a subshell or a `bash -c`
  string (`(cd x && git commit)`) is not modeled, so a commit there now
  blocks until written as `cd x && git commit` or `git -C x commit`.
- Verification: manual targeted mutation runs (round 1: six mutants;
  round 2: six mutants on the `;` candidate rule, escaped `$`, launcher
  environment, the protected-branch assumption, pipes and nested moves);
  all caught. `cargo-mutants` is not installed here, so no tool run.
- Integration: rebased on `integration/EPC-020-delivery-system` per PR 558.
- Not done: the pack-refs false block in the reference-transaction hook.
  git 2.53 sends a loose-ref prune as `oid 0` lines, the same form as
  `git update-ref -d <ref> <oid>`, so a per-line exemption would open a
  delete path. A fix needs a process-level discriminator; it is a separate
  task.
- Not done, predates this task (Codex round 4): an unjudged subcommand name
  can be a git alias for a judged one (`git -c alias.x=commit x`, an
  `include.path` alias, or one in local config), and it is not judged. A
  fix needs a known read-only list or alias resolution; it is a separate
  task.
