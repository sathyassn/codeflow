# TSK-337: The prescribed Codex lane starts with its intended permissions

## Description

Issue: #213. `assets/base/agents/skills/cf-model-orchestrator/resources/routing/transport.md:57` selects `cf-builder` through `-c default_permissions`, while the profile is defined in project config (`assets/base/codex/config.toml:72`, `:228`). The issue reports that Codex 0.163.0 performs an earlier global-only configuration load. The integration line contains no accommodation for that load order.

The current consult row already omits the override and relies on the project's default. The verified repository claim is therefore narrower than “all managed launches pass the bad flag”: the builder row does, and explicitly selecting either project profile has the reported failure. The upstream regression and native startup results were not independently reproduced here.

Outcome: **Each prescribed Codex launch reaches an authenticated prompt with the intended effective guard or builder permissions on the supported CLI release.**

Source inspection is from the accepted triage at `c5c6f6f671d2bf67a77113c656b3be446fb0bea1`; runtime reproductions remain implementation evidence.

Widened 2026-10-22 by the EPC-022 amendment of that day for issue #254:
a Codex builder seat launched as the launch table says cannot run the
full gate (`gate lock unavailable: Operation not permitted`, lock
`~/.codeflow/locks/full-gate.lock`), because `[permissions.cf-builder]`
extends `cf-guard` and adds writes only under `:workspace_roots`
(`assets/base/codex/config.toml:228-231`); issue #24 gave the Claude
sandbox preset both folders in 3.1.0 and the Codex profiles never got
them. AC-5 and AC-6 add the grants and the doctor report to this task's
outcome, which is already the builder seat's intended permissions.

## Acceptance Criteria

- AC-1 Reproduce with a clean synthetic user configuration and the managed project config; distinguish startup config failure from authentication failure.
- AC-2 Select a launch/configuration route that survives both global bootstrap and project loading. Prove workspace/common-git write scope, credential denies and network posture at the resulting session, with no fallback to unrestricted permissions.
- AC-3 Update every managed launch instruction and customization/preflight check consistently. If user-level installation is necessary, make the exact operator-applied change reviewable and avoid silently changing unrelated profiles.
- AC-4 (journey) Native guard and builder launches, including a linked worktree, reach the prompt and pass permission canaries. Unsupported releases fail with the actual cause and a qualified recovery.
- AC-5 The `cf-builder` profile shall grant writes under `~/.codeflow/locks`, so a builder seat launched as the managed launch table says runs `codeflow reserve` and quick-mode heavy targets under the shared lock; full gates and their evidence stay with the primary, and `~/.codeflow/gate-runs` stays unwritable to builder and review seats, with the decision stated in the profile comment; evidence: a native builder seat running `codeflow reserve` and a quick-mode heavy target under the lock, a review seat refused, and the issue's `gate lock unavailable` refusal reproduced before the change. Amended on 2026-10-27 from a `~/.codeflow/gate-runs` grant and a full gate: the gate copies run artifacts into that folder following links and trusts its run records without authenticating them, so a seat that could write it could plant evidence a later gate trusts; those two gate defects are tracked as a separate security task. (serves EPC-022 AC-34)
- AC-6 `codeflow doctor --check permissions` shall report the Codex profiles' grants on the lock and gate-run directories, as it does for the Claude preset; evidence: the doctor output on a profile with and without the grants. (serves EPC-022 AC-34)
