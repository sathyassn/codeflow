# TSK-1236: run.json records when a gate asked for the lock, when it got it and who held it

## Description

Source: the CI throughput study of 2026-11-02 (`coordination/coordinators/parallel/throughput/`: RECOMMENDATIONS.md, FINDINGS.md, CHECK-codex.md, CHECK-fable.md), cross-checked by Codex GPT-6 Astra and Claude Fable 5.1, and the operator's priority on CI throughput.

Issue [#513](https://github.com/sathyassn/codeflow/issues/513) (CodeFlow 3.1.1): `codeflow test` records each full gate's targets and durations in `run.json`, but not how long the run waited for the machine-wide gate lock or who held it, so a project cannot measure what the lock costs. In the reporting repository, half of consecutive full gates started within 2 minutes of the previous one ending, which suggests a standing queue.

The ask is to record the wait (request time, grant time, seconds waited) and the holder (pid, worktree, mode) in `run.json` and in the refusal message when a gate waits for or is refused the lock. The issue also asks for a read-only command that lists the current holder and recent waits; that command is not part of this task and may follow it.

TSK-1145 (PR 483) replaces the single lock with capacity slots. Its record is not on this line yet, so `depends_on` cannot name it; the edge `TSK-1145 -> TSK-1236` is pending and is added by a later amendment after TSK-1145 lands, because the wait and the holder are recorded against whatever lock model is current.

## Outcome

After this merges, a project can read from `run.json` how long each full gate waited for the lock and which run held it.

## Deliverables

- the wait and holder fields and the refusal text: `crates/codeflow-core/src/testing/` (the lock) and the run record
- the `run.json` schema and its version rules
- tests: a gate that waits for a held lock, and one that is refused
- docs: `docs/cli.md` where `run.json` is described

## Acceptance Criteria

- AC-1 Before any change, the builder shall record in the Findings how the lock is taken and released today, what a refusal prints, and whether TSK-1145 has landed on the line (and so whether the holder is one run or a set of slots); evidence: a `## Findings` section, committed before the first code change.
- AC-2 When a full gate waits for the lock, `run.json` shall record the time it asked, the time it got the lock, the seconds waited, and the holder at the time it asked (pid, worktree, mode); evidence: a test with a held lock and a released one. (serves EPC-022 AC-234)
- AC-3 When a gate is refused the lock, its message and `run.json` shall name the holder and the time it asked; evidence: a test of the refusal.
- AC-4 A gate that gets the lock at once shall record a wait of zero and its holder as none, and the schema version rules of `run.json` shall hold; evidence: the schema test.
- AC-5 In a scratch project with the installed build, two full gates started together shall leave a `run.json` for the second that shows its wait and the first's holder identity; evidence: the journey output. (journey)
