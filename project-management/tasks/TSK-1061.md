# TSK-1061: A planning amendment reports epic criteria it adds, removes or rewords

## Description

Source: Codex review 03 of PR 390 (GPT-6 Astra, session
`01a18401-c6f9-71c2-a4a6-4b5b0d81c8b4`,
`target/review-TSK-1002-followups-codex-03.md` in the
`plan-tsk1002-followups` worktree), confirmed by reading the code at
PR 390's head `e91633a3e`.

`codeflow ci` prints one `work.planning_amendment` note per changed
record so the reviewer of a planning amendment sees what it changes;
ADR-0076 says the criteria delta is computed by CI, never declared by the
author. `changes()` in `crates/codeflow-core/src/workgraph/amendment.rs`
compares criteria only when the record is a task (`:256`,
`after.kind == RecordKind::Task`). An epic whose criteria change is
reported as "changed, with no status or criteria change" (`:275`).

Observed on PR 390 itself: its range adds EPC-022 AC-152 and AC-153 and
adds a superseding amendment note under AC-86, and `codeflow ci --into`
the line printed "EPC-022: EPC-022 changed, with no status or criteria
change" at `22c503e55` and at `e91633a3e`.

This is a reporting defect, not an admission bypass: the planning class
and every refusal stay as they are. Its cost is that the human reviewer,
who by the note's own text "confirms each change before it lands", is
told an epic's criteria did not change when they did.

The remedy: compare an epic's criteria the way a task's are compared,
with the existing `criteria_delta` (`workgraph/acceptance.rs:3529`), so an
added, removed or reworded epic criterion, and an amendment note added
under one, is printed. The R-119 completion flags stay task-only, since
an epic's completion is judged elsewhere.

Non-goals: changing what the planning class admits or refuses; changing
task criteria reporting beyond keeping it as it is.

## Outcome

After this merges, a reviewer of a planning amendment can see every epic criterion it adds, removes or rewords in `codeflow ci`'s output, instead of a note saying the criteria did not change.

## Deliverables

- epic criteria in the amendment report: `crates/codeflow-core/src/workgraph/amendment.rs` (`changes()`)
- tests for an added, a removed and a reworded epic criterion, an added amendment note, and an unchanged epic: `crates/codeflow-cli/tests/planning_amendment.rs` and unit tests beside `amendment.rs`
- the report's description, if it names what is compared: `docs/cli.md` (the `work.planning_amendment` paragraph)
- investigation findings: a `## Findings` section in this record
- release note: `changelog.d/TSK-1061.md`

## Acceptance Criteria

- AC-1 Before any change, the builder shall investigate and record in this record: how epic and spec criteria are parsed into `RecordView.criteria` (amendment notes under a criterion included, per EPC-022 AC-78), every other place in `amendment.rs` and the planning-class code that branches on `RecordKind::Task` and whether an epic or spec change is reported there, and whether a spec's requirements need the same report; evidence: the record section, committed before the first code change.
- AC-2 When a planning amendment adds, removes or rewords an epic criterion, `codeflow ci` shall print a `work.planning_amendment` note naming each such criterion with the `criteria_delta` wording (added, removed with the reason request, changed from and to, or tags changed); evidence: one test per kind, each printing "no status or criteria change" before the fix.
- AC-3 When an amendment adds a dated amendment note under an epic criterion, the note shall be reported as a change to that criterion; evidence: a test with the AC-86 sub-bullet form of PR 390, failing before the fix.
- AC-4 An epic whose criteria and status are unchanged shall still print "changed, with no status or criteria change", task criteria reporting and the R-119 flags shall be unchanged, and the planning class shall admit and refuse exactly what it did before; evidence: the existing `planning_amendment` tests passing unchanged, plus a test of an epic changed only outside its criteria.
- AC-5 (journey) With the built binary, `codeflow ci --pr-body-file <body> --into integration/EPC-022-the-3-2-0-milestone-fixes` over PR 390's range (`dc9ec266d..e91633a3e`) shall print the EPC-022 delta for AC-152, AC-153 and AC-86; evidence: the command output before and after.
