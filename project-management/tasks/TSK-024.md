# TSK-024 — guide project organization and authority

## Description

Improve existing method/customize/plan guidance rather than importing a second
organization framework. New projects reason from accepted boundaries and
lifetime; existing projects retain credible native layouts and authorities.
Use a concise optional worked example, not a mandatory source skeleton.

## Affected surfaces and interfaces

Canonical skill/reference assets, relevant PM templates, onboarding guidance,
eval resources, harness mirrors and their manifest/baselines. TSK-023 owns Rust
activation changes. Shared knowledge is linked, not copied everywhere.

## Acceptance Criteria

- [ ] Guidance distinguishes greenfield/brownfield, native build units from
  runtime/release boundaries and real data/trust ownership from folders.
- [ ] Existing sources/authorities need no cosmetic migration; onboarding states
  actual cwd, tier, ownership/conflict and fixed-document limitations.
- [ ] Living requirements and frozen SPC inputs remain distinct; EPC/TSK IDs,
  relationships, paths and enabled planning-anchor gates remain unchanged.
- [ ] Templates name material affected boundaries and responsible primary versus
  executor/reviewer without duplicate doctrine or authoritative task rosters.
- [ ] Paired behavioral cases validate and use decision-based rubrics; active
  full-tier external-authority tension is not hidden.
- [ ] Manifest/mirror/baseline consistency passes for this task's authored assets;
  native Claude reviews the instruction diff before integration.

native Claude primary/high cross-lineage review. This task owns distribution
