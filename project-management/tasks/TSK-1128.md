# TSK-1128: A quick test run inside a reserve uses the reserved heavy-work lock

## Description

`codeflow reserve -- codeflow test --mode quick` takes the shared heavy-work
lock, then the nested quick run refuses its own heavy targets
(`repository-update-noop`, `contract-scans`, `rust-clippy`) as "another heavy
gate" and exits 1: the child cannot tell that its own parent holds the lock.
Run directly, a quick run refuses heavy targets at once whenever another
worktree holds the lock, because this repository sets
`execution.heavy_wait_seconds` to 0. With seven builder lanes no builder
could produce the quick evidence AGENTS.md asks for before a push, and
builders fell back to retry loops, one of which held the lock for about six
hours. A reserve that waited 1800 seconds was also refused while the lock
passed to a later waiter: waiters were not served in arrival order.

This task lets a quick run nested under `codeflow reserve` run its heavy
targets under the parent's lock, lets a direct quick run wait a bounded
time, and serves waiters in arrival order. Inheritance is bound to possession of the parent's locked open file
description, passed as a descriptor by `codeflow reserve` and verified with
the OS lock; an environment value alone grants nothing, and any check that
fails falls back to ordinary admission. Full and essential gates keep taking
the lock themselves and are unchanged. Non-goals: inheritance on Windows
(byte-range locks there belong to the handle that took them, so a nested
quick run keeps today's refusal or bounded wait), and changing the shipped
scaffold default of `heavy_wait_seconds`.

## Outcome

After this merges, a builder can run `codeflow reserve -- codeflow test
--mode quick`, or `codeflow test --mode quick --wait-seconds N`, and get
quick evidence while other worktrees gate, without two heavy gates ever
running at once.

## Deliverables

- Lock inheritance and its checks: `crates/codeflow-core/src/testing/gate_guard.rs`
- Descriptor hand-off from reserve: `crates/codeflow-core/src/testing/runner/`, `crates/codeflow-cli/src/cmd/reserve.rs`, `crates/codeflow-cli/src/main.rs`
- `codeflow test --wait-seconds`: `crates/codeflow-cli/src/cmd/test.rs`, `crates/codeflow-core/src/testing/`
- This repository's bounded wait: `.codeflow/test-config.json`
- Tests: `crates/codeflow-cli/tests/test_gate_cli.rs` and unit tests in `gate_guard.rs`
- Docs: `docs/cli.md`, `docs/troubleshooting.md`

## Acceptance Criteria

- AC-1 When `codeflow reserve` runs `codeflow test --mode quick` on Unix, the quick run's heavy targets run under the reserve's lock and the run passes; a test fails before the change and passes after. (journey)
- AC-2 Inheritance is granted only to a process that holds a descriptor of the parent's locked open file description, checked against the lock path's file identity and the OS lock (a fresh open is refused, the inherited descriptor locks); an environment value naming a descriptor the process opened itself, or naming any other file, grants nothing and falls back to ordinary admission; a test shows a forged value is refused while another gate holds the lock.
- AC-3 Inherited descriptors are close-on-exec in the receiving `codeflow` process, so targets and their daemons never keep the lock after the run; `codeflow reserve` hands descriptors only to a command that is the same executable file as the running `codeflow` (device and inode after resolving links), so a program merely named `codeflow`, by path or on `PATH`, gets no descriptor and no hand-over value, and a test shows its unlock attempt cannot free the reserve's lock.
- AC-4 When another gate holds the lock, `codeflow test --mode quick --wait-seconds N` waits up to N seconds for heavy targets and then refuses as before; the flag overrides `execution.heavy_wait_seconds`; this repository's config sets a bounded default wait; a test fails before and passes after.
- AC-5 No change lets two heavy gates run at once: a second, unrelated heavy gate still refuses while a nested quick run holds the inherited lock, and a full or essential gate under `codeflow reserve` still refuses; a nested run adds its targets' process groups to the holder's record and leaves live ones there when it ends, so a target that survives a killed nested run keeps the next gate refused until it exits; tests cover the first and the surviving target.
- AC-6 Full and essential behaviour is unchanged: they take the lock themselves and never inherit; existing gate-lock tests pass.
- AC-7 Waiting quick runs and reserves take the lock in arrival order: each waiter queues a ticket beside the lock, a caller is refused while an earlier live ticket is queued, tickets of exited processes or past their deadline are dropped (on Windows through a process query), equal arrivals are ordered by process id, an unreadable queue refuses (fail closed), and a malformed ticket refuses once and is moved aside; a test shows an earlier waiter gets the lock before a later one. (journey)
