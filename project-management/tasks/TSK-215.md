# TSK-215: Grok sessions run the CodeFlow guards

## Description

Issue 29: Grok Build 1.0.46 reads `$name` and `${...}` in a hook command
as its own environment-variable template. CodeFlow's hook commands carry
an inline shell probe full of shell variables (`codeflow_ok`,
`codeflow_rc`, `${TMPDIR:-/tmp}`), so Grok finds them unset, skips every
hook and runs the tool anyway: git-guard, exec-guard, edit-guard and
session-orient never run in a Grok session, and `codeflow doctor` reports
only folder trust. The commands come from `assets/base/grok/hooks.json`
and the Claude settings presets, which Grok also reads; the Codex hooks
carry the same probe.

The change makes every shipped hook command free of `$`, keeps exit 2
(block) with a reason whenever the hook fails, and gives doctor a check
that names template tokens Grok would skip and judges a canary payload
with the shipped Grok shell guard's handler in its own process,
executing nothing. Non-goal: driving a live Grok session from doctor,
which would need a model run.

## Acceptance Criteria

- AC-1 When `codeflow init` or `codeflow update` writes the Grok hooks
  file, a Claude settings preset or the Codex hooks file, no hook command
  contains a `$`; evidence: a regression test over the shipped assets that
  fails on the 3.0.0 assets and passes after, and the repository's own
  installed copies and baselines.
- AC-2 When a hook command runs under a POSIX shell, it exits 0 when the
  binary allows, and exits 2 with a nonempty reason on stderr when the
  binary refuses by policy (the guard's message first), is missing (the
  installer and `codeflow update` named), predates hook contract 3 (the
  binary's own error) or fails silently, with no second call to the
  binary; evidence: the wrapper tests in `refusal_journey`. Changed in
  review: Codex lets a call through on exit 2 with an empty stderr, so
  "the guard's message only" became "first", with a closing line.
- AC-3 When `codeflow doctor` runs in a project with Grok project hooks,
  the grok check warns, naming the file, when a CodeFlow hook command
  Grok loads contains a `$`, and otherwise, when the shipped exec-guard
  handler (command, timeout and environment) is bound where Grok's shell
  tool hits it (matched as Grok matches, command handler checked), judges
  a fixed canary dangerous command with the handler
  `codeflow hook exec-guard --contract 3` runs, in doctor's own process
  under the catastrophic-command floor alone, reading no policy,
  repository, working directory or environment, recording no refusal and
  executing nothing, and reports whether it refused with exit 2, a reason
  and Grok's deny answer; a customised handler is reported unverified, a
  `codeflow` found on PATH is reported, and neither is run; the update
  step is offered only where update's own steps rewrite the file or
  propose a `.new` merge that repairs it, any other file gets the hand
  edit with the reason update leaves it, and both steps are given when
  both kinds of file are stale; a missing shell guard gets the update
  step only where update would bind the shipped guard again, and
  otherwise the hand edit quoting the shipped guard group; evidence:
  doctor unit tests and runs against the built binary. The canary does not exercise a shell, the
  command-line parsing, the `codeflow` on PATH or Grok's own hook call;
  AC-4 covers a live session. Changed in review: running the configured
  command executed repository shell text (round 1); a `codeflow` on PATH
  or a handler environment could be repository-controlled (round 2); a
  re-executed binary path could be swapped (round 3); a scratch folder
  inside a repository let that repository's policy decide the canary and
  receive its refusal record, and update skips symlinks and keeps
  unchanged-upstream edits (round 4); a missing guard was always sent to
  update, and stale files of both kinds got only the update step
  (round 5).
- AC-4 When an agent in a live Grok session in a scratch repository runs
  `git commit` on `main`, the guard refuses it; evidence: the session's
  hook lines, or recorded as not run when no Grok session is available.
  (journey)
- AC-6 When Grok sends a `PreToolUse` payload with each field under both
  spellings, as Grok 1.0.46 does, the guards read it (equal spellings are
  one field; spellings that disagree stay an unreadable payload), and a
  refusal of a Grok call also returns Grok's deny decision on stdout with
  the whole refusal, while Claude and Codex payloads get nothing on
  stdout; evidence: payload unit tests, the Grok wiring test with the
  captured payload shape, and the live session of AC-4. Added during the
  build: the live check of AC-4 found the hooks running but allowing.
- AC-5 The enforcement-planes page, the Grok host resource and the
  pending 3.1.0 CHANGELOG entry under its release-impact marker describe
  the new wrapper and the doctor check; every mirror and baseline copy
  matches; evidence: the diff, `manifest_consistency` and
  `repository_update_noop`. The migration note and doctor's remedy cover
  an edited hook file (update writes a `.new` merge to resolve) and
  `.claude/settings.local.json` (a hand edit); evidence: the
  `remedy_clearing` tests for both. Extended in review.
