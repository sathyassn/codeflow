# TSK-302: The exec guard judges the paths an interpreter is given

## Description

exec-guard refuses an interpreter call whose inline code names an
enforcement path, but it never reads the interpreter's arguments
(https://github.com/sathyassn/codeflow/issues/173). At v3.1.1,
`crates/codeflow-core/src/security/interpreter.rs:47` scans only the code
bodies that `outward::interpreter_bodies` returns, and `record_interpreter`
(`crates/codeflow-core/src/security/outward.rs:294`) keeps `-c` and `-e`
code and a stdin count and drops every other argument. So
`python3 - "<repo>/.claude/settings.json"` with a heredoc that writes
`sys.argv[1]` is allowed, and it can switch off the guard hooks wired in
that file. This task carries each interpreter's arguments, with the
directory the command runs in and whether `xargs` or `find -exec` supplies
more of them, into the same judgment the code words get: the
always-blocking authority check and the `git.hook_integrity` enforcement
path check. An argument the guard cannot read is judged by the rule
git-guard already applies to writer operands. Non-goal: a program that
builds a path internally stays past the guard, and the OS sandbox stays
the backstop. TSK-299's `sort -o`, `curl -o` and `wget -O` gaps in
git-guard are reproduced here and reported, not fixed.

## Acceptance Criteria

- AC-1 When `python`, `python3`, `node`, `nodejs`, `perl` or `ruby` is
  given an argument that names an enforcement path, exec-guard shall refuse
  it under `git.hook_integrity`: a literal path, a path in a linked
  worktree, an argument after inline code, an argument after stdin `-` and
  a script's argument; evidence: a refusal test per form in
  `security/interpreter.rs`.
- AC-2 When the interpreter runs under `env`, `env -S`, `command`, a shell
  `-c` string, `xargs` or `find -exec`, or after a `cd`, and the wrapper's
  words, its input or a `find` start that reaches an enforcement file
  supplies the path, exec-guard shall refuse it; evidence: a refusal test
  per wrapper.
- AC-3 An interpreter argument that names policy authority metadata (the
  repository's Git config or remote-tracking refs) shall refuse whatever
  the `git.hook_integrity` level; evidence: a test with the level off.
- AC-4 When an argument holds a value the guard cannot read, exec-guard
  shall refuse it when its spelled part could name an enforcement path or
  the line names one, the issue's `W=<repo>; python3 -
  "$W/.claude/settings.json"` included, and the refusal shall name the
  rule and the sanctioned route; an unreadable argument on a line that names
  no enforcement path stays allowed; evidence: refusal, allow and message
  tests.
- AC-5 Ordinary data and output file arguments outside enforcement paths,
  reading an enforcement file with a reader or on the interpreter's stdin,
  and quoted documentation text that only contains shell examples shall
  stay allowed; evidence: allow tests.
- AC-6 When the built `codeflow hook exec-guard --contract 3` judges issue
  173's interpreter cases in a fresh project with a linked worktree, it
  shall refuse each of them and allow the controls; evidence: a CLI journey
  in `crates/codeflow-cli/tests/hooks_cli.rs` (journey)
- AC-7 The `git.hook_integrity` row of `docs/policy-reference.md` shall
  state the interpreter argument rule and its limit, and
  `changelog.d/TSK-302.md` shall carry the 3.2.0 entry; evidence:
  `codeflow validate --docs` and the release check.
