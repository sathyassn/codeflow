# TSK-1085: The baseline replacement design is recorded and reviewed

## Description

Source: the operator's decisions on the 4.0.0 baseline replacement, recorded
in the workspace `RELEASE-PLAN.md` on 2026-10-15 and 2026-10-17, and the
version decision of 2026-10-28 that brings the replacement into this
release (EPC-022, Version relabel amendment).

The design Codex approved after five rounds on 2026-10-15 lived only in a
worktree's build output (`.worktrees/baseline-design/target/design-baseline-05.md`),
which has since been removed; no copy exists on disk, in any ref or in a
pull request (searched 2026-10-30). What survives is the operator's three
decisions:

| Decision | Date | Content |
|---|---|---|
| Option A | 2026-10-15 | An incompatible manifest and a major release, shipped as 4.0.0 |
| Sparse pack | 2026-10-15 | A tracked sparse pack is accepted beside the manifest |
| Retention | 2026-10-17 | The binary keeps the shipped bases of every published release (about 0.6 MB then), with an advisory 2 MB budget whose crossing triggers a review |

Today a project carries a pristine copy of every installed managed file
under `.codeflow/.baseline/` (317 files, about 7 MB in this repository)
and a `sha256` per file in `.codeflow/manifest.json`
(`crates/codeflow-core/src/scaffold/state.rs:500-516`). Both change on
every release and make unrelated pull requests conflict (issue 119).
The replacement moves the shipped bases into the binary, drops the digest,
and keeps in the repository only what the binary cannot reproduce.

This task re-establishes that design as durable records before anything is
built: an accepted decision record and the approved spec `SPC-015`, which
TSK-1086, TSK-1087 and TSK-247 cite by numbered requirement. It changes no
code. Non-goals: the changelog portion of issue 119 (landed as
ADR-0082, fragments under `changelog.d/`) and the update preview itself
(TSK-247).

## Outcome

After this merges, the builders of TSK-1086, TSK-1087 and TSK-247 can build
against one approved, cross-lineage reviewed statement of the manifest
schema, the base lookup, the sparse pack and the 3.x migration, instead of
reconstructing a lost design each.

## Deliverables

- the decision record: a new ADR under `docs/decisions/`, allocated with `codeflow adr new`, status accepted, listed in `docs/decisions/README.md`
- the spec: `project-management/specs/SPC-015.md`, filled and approved (`codeflow spec status SPC-015 approved`), its requirements numbered
- the size measurement and its command: in `SPC-015`
- the consumers' criteria check: a note in this record's Closeout naming any TSK-1086, TSK-1087 or TSK-247 criterion the approved spec makes stale, for the batched epic amendment

## Acceptance Criteria

- AC-1 The ADR shall record the three operator decisions with their dates and their source (`RELEASE-PLAN.md`), the alternatives they displaced (keeping `.codeflow/.baseline/` and the per-file digest; TSK-258's digest-free schema 2 that kept the baseline directory, an intervening format) and the consequences for adopters (a 3.x binary cannot read a 4.0.0 project; one migration step); evidence: the ADR with status accepted and its README row.
- AC-2 `SPC-015` shall pin, as numbered requirements: the manifest schema (fields per entry, the `scaffold_version` the base is read at, the refusal rule for a schema newer than the binary's, and the 3.x break pinned to the published parser: `InstalledFile.sha256` is a required string and `load_or_default` never reads `schema_version` (`crates/codeflow-core/src/scaffold/state.rs:512`, `:548-550`), so the new schema omits `sha256` and a 3.x binary fails on serde's missing-field error, never on a schema number alone); manifest line stability (an entry a resync does not change keeps its bytes, a resync of one managed file changes no other entry's line, and no shared stamp or digest changes on a resync, so two pull requests that change different files never touch the same manifest line, the failure issue 119 reports); the base lookup order (the binary's retained release at the recorded version, then the sparse pack, then no base); what the sparse pack holds, where it lives, and when an entry is written and removed (rendered copies the binary cannot reproduce from the project's render inputs, bases of unpublished builds, accepted conflict resolutions from TSK-405); the layout and encoding of the retained bases in the binary and how a release adds its own; the outcome of every `ManagedStep` arm (`crates/codeflow-core/src/scaffold/update.rs:795-860`), `prune_orphans`, `init`'s recorded-file judgement and `doctor --check managed-drift` with each base source; and the migration of a 3.x project (schema 1 manifest plus `.codeflow/.baseline/`) in one `codeflow update`; evidence: the spec, each requirement numbered and cited by at least one TSK-1086, TSK-1087 or TSK-247 criterion or named as uncited with a reason.
- AC-3 `SPC-015` shall state the compressed size of the retained bases for v2.0.0, v2.1.0, v3.0.0, v3.1.0, v3.1.1 and the current line against the 2 MB advisory budget, with the command that measured it; evidence: the numbers and the command in the spec, reproducible on the line.
- AC-4 `SPC-015` shall name each invariant of landed work and how the design keeps it: TSK-405 (a person's resolution is recorded against shipped content and does not return), TSK-401 (a person's additions to enforcement files survive), TSK-225 (`update --pin` and `[scaffold_sha256]`), ADR-0011 (orphan reconciliation, whose unmodified test is a hash compare at `docs/decisions/ADR-0011-update-orphan-reconciliation.md:42-45` and is restated as a byte compare against the base), the release repair rules for coupled files and baselines in `docs/releasing.md` ("Typed repair rule" table) and `scripts/release.py`, and the eval kit scrub in `eval_kit.py`; evidence: a table in the spec with one row each.
- AC-5 The design shall be reviewed by the other lineage in one read-only pass over the ADR and the spec, every material finding resolved before approval; evidence: the pull request's Reviews row with the reviewed commit, and `open_questions: []` in the spec.
- AC-6 `codeflow validate --docs` shall be clean on the branch with the spec approved; evidence: the command output in the pull request.
- AC-7 `SPC-015` shall pin, as numbered requirements, the write and removal boundary and its edge cases: removing `.codeflow/.baseline/` and writing the sparse pack follow no link, remove nothing outside `.codeflow/.baseline/`, write nothing outside `.codeflow/`, and a refused path is reported and stops the run before any write; and the "Edge cases" section shall state the outcome for each case it lists (a recorded version that is no retained release, a rendered template whose render inputs changed, a 3.x binary on a 4.0.0 manifest, a manifest newer than the binary, a linked path under `.codeflow/.baseline/` at removal, a baseline entry pointing outside the root); evidence: the requirements, each cited by the TSK-1087 criterion that owns its row: AC-10 the removal and pack-write boundary and the two path cases (a linked path under `.codeflow/.baseline/`, an entry pointing outside the root); AC-5 the 3.x binary on a 4.0.0 manifest and the newer schema; AC-6 the recorded version that is no retained release; AC-3 the rendered template whose render inputs changed, as the sparse-pack base source.

  `scaffold_version` (`SPC-015` R-2); `release.py` loses that coupled stamp,

- TSK-1086 AC-1 and AC-4: the retained files are the entry `src` files of
  each release's `scaffold-manifest.toml` (183 at v3.1.1), not all of
  `assets/base` (199); the fixture comparison and `check-state` read that
  set (`SPC-015` R-25, R-27).
- TSK-247: no criterion made stale. AC-1 cites R-6 to R-8 and R-18. AC-4
