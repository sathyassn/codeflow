# TSK-397: The exec guard adds a strict rule where the sandbox is absent or loosened

## Description

Source: PR 239 (TSK-373) final confirm, 2026-10-18. `cd src && python3 tool.py ..` from the checkout root is refused, because the guard's directory set keeps the starting directory after a `cd` (`crates/codeflow-core/src/security/outward.rs`, `DirSet::change`).

History of the outcome:

- 2026-10-25 (operator): narrowing after `cd` cannot be made sound against shell state the guard cannot see, so `cd src && python3 tool.py ..` stays refused. The PR 331 reviews found 14 text-bypass classes.
- 2026-10-27 (operator, option D): every stop in launcher traversal keeps its words judged, with a non-executing allowlist.
- 2026-10-28 (operator, narrowed option (c)): the allowlist and its shadowing analysis are removed. The text guard has two outcomes, selected from the harness configuration the host can read. The specification is design note D revision 4.1, Part A (`target/tsk-397-design-D.md` in the TSK-397 worktree; checks: Codex 01 to 03, Fable 01 to 04).

The two outcomes:

- **Baseline** is the line's rule unchanged. It applies only when the guard attests the configuration the call's harness runs under: the payload identifies one harness, every layer that harness reads is read, and each layer's containment settings equal the shipped preset or a narrower form the guard lists. That is a reading of files, not proof that a sandbox contains the call.
- **Tightened** adds the strict branch, PR 331's rule with every name-based exemption removed. It applies to anything not attested (unreadable, unknown, ambiguous or customised), on native Windows under Claude Code or Grok Build, on a recognised unsandboxed retry (`dangerouslyDisableSandbox`), and when the policy of the call's repository or of the Claude session's project sets `security.text_guard: strict` or cannot be read.

What is attested (revised after Codex 17 and Fable 02, which with rounds 15 and 16 each found a loosening the earlier trigger list lacked; an enumeration over formats CodeFlow does not own cannot be made sound, so it was inverted):

- Claude Code: the session project (`CLAUDE_PROJECT_DIR`, required), its repository root and a linked worktree's main checkout (found through Git's worktree metadata), each with shared and local settings, plus the user and managed settings. In every layer, `sandbox` and `permissions` may hold only listed keys, each with the shipped value or a narrower one; the layers together enable a fail-closed sandbox, carry the floor and deny the shipped credential variables. Managed preferences and a cached server-managed file tighten when present.
- Codex: the user configuration, profile files beside it, and the project configuration when the user configuration trusts the project. Every top-level key must be known; containment keys hold shipped values; a shipped permission profile may only add denies or narrow an access. System and managed files tighten when present.
- Grok Build: `GROK_SANDBOX` or the user configuration's `[sandbox] profile` selects a shipped profile, whose definition in the user and project profile files equals the shipped one or narrows it.

Doctor and the hook decide through the same function (`sandbox_state::reasons`). The cost is over-refusal: a customisation that loosens nothing, beyond a listed narrower form, still selects the strict rule, and doctor names the change.

The tightened outcome keeps every baseline finding. Neither outcome allows what the line refuses, except the H-3 class below, which the baseline allows and the tightened outcome refuses. A replay of the historical corpus is the test.

Hardening in both outcomes:

- a NUL byte refuses (H-1);
- the headless `xargs` reader no longer guesses a bare optional-value option or a BSD option (H-2);
- a line made only of bare `cd`, `pushd` and `popd` builtins no longer takes the startup write judgement (H-3, issue 342);
- the enforcement paths are explicit `sandbox.filesystem.denyWrite` entries in the presets (H-4);
- `~/.codeflow/authority/` is a protected directory, reserved for the 4.1.0 qualification records (H-5).

`codeflow doctor --check sandbox` names the outcome a host gets and why (H-6). Non-goals for 3.2.0: qualification, receipts, capability relaxation and the other Part C units, which are planned for 4.1.0.

Limits (design D, A6), each as it is on the line today unless noted:

- An unread program (a script file, code the guard does not read) can write an enforcement file or read a secret wherever no kernel deny holds. The strict branch narrows the text-visible paths and contains nothing.
- An unsandboxed retry the harness does not mark follows the baseline today: a Codex seat (no field), or a Claude version that does not send the field. Failing closed there is tracked as TSK-1052 (EPC-022, filed by PR 390).
- Launch flags are not read and can get the baseline today: `--settings`, `--sandbox`, `-c` and `--profile`, including a Codex launch with `--sandbox danger-full-access` or the bypass flag; so are server-managed settings that are not cached on disk. Failing closed there is tracked as TSK-1052.
- Claude Code top-level keys outside `sandbox` and `permissions`, such as `env`, are not attested; they configure no documented containment.
- Doctor's state-root check reads Claude write grants only; Codex and Grok grants are not computed, and doctor does not claim the state root is unwritable.
- An `awk` inline program that writes an enforcement path passes the exec guard (git-guard refuses it); it is the unread-program residual above, to be tracked once.
- Debug builds of the hook honour `CODEFLOW_TEST_CLAUDE_MANAGED_DIR` from the hook environment, so an operator running a debug hook binary should know that variable moves the managed settings layer; release builds ignore it.
- The `Monitor` tool is outside the hook matcher (4.1.0, TSK-1058).
- Policy authority under `refs/remotes/origin/*` and `packed-refs` is writable by a direct file write (4.1.0, TSK-1057).
- In a linked worktree, protection of the shared `.git`'s `hooks`, `config` and `config.worktree` is unverified (4.1.0, TSK-1054).
- Codex nested secret files and `.envrc`, and Grok's launch-time globs, are recorded gaps of those profiles.
- A non-empty `excludedCommands`, or any other unattested customisation, tightens the whole session. That is a cost, not a gap.

Follow-ups (for the closeout `follow_ups`): the Part C units of design D, planned for 4.1.0 in EPC-023 by PR 391. They are TSK-1054 (qualification record), TSK-1055 (capability relaxation), TSK-1056 (administrator policy), TSK-1057 (authenticated policy authority), TSK-1058 (`Monitor` matcher), TSK-1059 (trusted host-state operations) and TSK-1060 (Codex managed requirements). Failing closed in the unknown-containment cases is tracked as TSK-1052 (EPC-022).

Criteria changes in this amendment (2026-10-28):

- Changed AC-1: it keeps both refusals and now states them for both outcomes. Reason: the outcome now has two text rules, and the refusal holds in each.
- Replaced AC-2: the per-bypass-line refusal list of option D, with its non-executing allowlist rule, is removed. Reason: the operator chose narrowed option (c), which removes every name-based exemption. The strict branch refuses every listed bypass line in the tightened outcome. The baseline keeps the line's rule, so the bypass lines stay text-bypassable there, as A6 states. The new AC-2 is the invariant that no line refusal is lost.
- Replaced AC-3: the installed-build journey of `cd src && python3 tool.py ../.claude/settings.json` is covered by the new AC-1 in both outcomes. The new AC-3 pins retry recognition, which this outcome adds.
- Added AC-4 to AC-8, for the triggers, doctor, measurement, policy key and hardening of design D Part A.
- Changed AC-2 after the Codex 16 and Fable 01 reviews: the exception is the H-3 class, checked by a predicate, where it was four listed rows. Reason: the exception is a class, and a row list would let a widened predicate pass unnoticed. The corpus gains the review's three class rows.
- Changed AC-4 after the same reviews: an absent Codex or Grok configuration tightens a call identified as that harness. Reason: without it the shipped profile is not in force, and the call cannot be shown contained.
- Changed AC-5: doctor prints one text-rule line per harness, decided by the hook's function. Reason: one host line could disagree with what the hook decides for a given harness.
- Changed AC-4 after Codex 17 and Fable 02: the per-trigger fixtures become attestation fixtures (each customised, unknown or unreadable form tightens; each listed narrower form stays the baseline), and an unidentified payload tightens. Reason: the trigger list could not be made sound; the union rule let a payload of no single harness reach the baseline.
- Changed AC-5 after the same reviews: a harness the project does not configure is a note, and doctor no longer claims the state root unwritable. Reason: its write set left out grants it cannot compute.
- Changed AC-7 after the same reviews: a Claude call also reads the session project's policy, failing closed. Reason: `strict` set in the session's project was lost when the call ran in another repository.

First added to EPC-023 (4.1.0) on 2026-10-18; moved to EPC-022 (3.2.0) the same day after the Codex review of PR 249, under the operator's rule that every security gap and every defect that forces an adopter workaround or blocks work belongs in 3.2.0.

## Outcome

After this merges, an adopter's agent sessions are judged by the line's text rule wherever the guard attests the harness configuration as the shipped preset or a narrower form, and by an added strict rule everywhere else. No command the line refuses is allowed, except a line made only of bare `cd`, `pushd` and `popd` builtins, which writes nothing. The change is breaking (4.0.0): a tightened host repairs it with `codeflow doctor --check sandbox`.

## Acceptance Criteria

- AC-1 `cd src && python3 tool.py ..` and `cd src && python3 tool.py ../.claude/settings.json` from the checkout root shall refuse in both outcomes; the origin case stays refused until the 4.1.0 qualification design; evidence: guard tests under both outcomes. (serves EPC-022 AC-86)
- AC-2 (journey) No row of the historical corpus that the line binary at `5f2fe3827` refuses shall be allowed in either outcome. The corpus is the Codex and security round probes as the round 15 replay assembled them, the 49-line everyday sample and the two shell review fixtures. A row may become stricter. Each row keeps its original operation. Every judgement shall exit 0 or 2. The one reasoned exception is the H-3 class: a line made only of bare `cd`, `pushd` and `popd` builtins with literal or plain `"$NAME"` arguments, joined by `&&`, `;` or newlines, may be allowed in the baseline and shall be refused in the tightened outcome; evidence: `text_guard_invariant.rs` at the head, which states the class as its own predicate and drives the built binary through `codeflow hook exec-guard` with a Claude payload from a session in a fixture checkout carrying the shipped preset, with the line column and the line binary's version and digest beside the corpus.
- AC-3 A payload with `dangerouslyDisableSandbox: true` shall be judged under the strict branch (the recorded Claude Code 2.1.312 payload as fixture). A payload without the field shall be judged by the host's outcome. The release note and doctor shall state that an unmarked retry follows the baseline; evidence: state tests, the replay's tightened column, the doctor message test. The installed-build journey runs at epic close.
- AC-4 The shipped configuration of each harness, as an adopter following the docs has it, shall select the baseline on macOS and Linux and the tightened outcome on native Windows under Claude Code and Grok Build. Each customised containment setting beyond a listed narrower form, each unknown setting, and each malformed, non-regular, oversized or unreadable layer, in every layer the harness reads, shall tighten, and each listed narrower form shall keep the baseline. A payload that identifies no single harness shall tighten. A non-empty `excludedCommands` shall tighten without any matching; evidence: `sandbox_state` attestation tests and the round 17 probe.
- AC-5 Doctor shall print one text-rule line per harness, decided by the function the hook uses, naming each reason; it shall note the shipped configuration and a harness the project does not configure, and fail when a configured harness is not attested, on an unreadable policy, and when the project, the temporary directory or a Claude write grant of any layer reaches the CodeFlow state root. It shall not claim the state root is unwritable. `codeflow update` shall deliver H-4 and H-5 to the presets and profiles. The commands H-5 names shall run unchanged; evidence: doctor and preset tests, the existing CLI tests of those commands.
- AC-6 The 49-line everyday sample shall be judged by the built binary in both outcomes, with the per-line results recorded in the replay file at the head; no count is a criterion; evidence: the replay file.
- AC-7 `security.text_guard` shall accept `auto` and `strict`. `strict` shall add the strict rule on every host. Where policy sources disagree, `strict` shall win. A Claude call shall also read the session project's policy, and tighten when it sets `strict` or cannot be read. No value shall select the baseline on a tightened host; evidence: policy schema, landed-policy merge, state tests and the round 17 probe.
- AC-8 The hardening items shall hold in both outcomes: a command holding a NUL byte refuses (H-1); a bare GNU optional-value `xargs` option or an unmodelled one never hides a headless peer run (H-2); and `cd ~ && cd "$p"` and `cd / && pushd "$p"` pass the startup check while every other line keeps the write judgement (H-3); evidence: guard, headless and startup tests.
