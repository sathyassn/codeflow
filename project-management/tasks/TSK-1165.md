# TSK-1165: A newer push to an integration line cancels the older run of that line

## Description

Operator decision, 2026-11-02 (hosted CI scope page, confirmed 01:19Z,
row "superseded": cancel superseded line push runs).

This repository's `.github/workflows/codeflow-ci.yml` puts every run in
the group `${{ github.workflow }}-${{ github.ref }}` and sets
`cancel-in-progress` only for `pull_request` events (`:30-32`). When a
second landing reaches an integration line while the first landing's push
run is still going, both full runs finish: about 214 job minutes for the
superseded one (`ci-inventory.md`, run 41355478049), and its jobs hold
runner slots the newest tip waits for.

TSK-1026 does not cover this. It changes the shipped template
`assets/base/ci/codeflow-ci.yml` and states that push runs are never
cancelled there. This task changes only this repository's workflow.

Outcome: **when a newer tip of an integration line is pushed, the run for
the older tip of that line is cancelled and the newest tip runs to its
full verdict; pushes to `main` are never cancelled; pull request runs
behave as today.** This holds for first attempts that start in push order.
GitHub does not promise that order, so a late-starting older run can cancel
the newest run; rerunning the newest tip's run recovers it. A push rerun
never cancels a newer run (clarified 2026-11-02 after review).

Why a cancelled run on a superseded tip loses nothing: the line rule
"Hosted green before the next landing" (`AGENTS.md`) counts only the
current tip's verdicts. A cancelled run is not green, and a green verdict
for an earlier tip is stale, so the older tip's run could never be
evidence for the next landing once a newer tip exists. One cost: when the
newest tip's run fails, the failure is not yet attributed to one of the
landings it carries; the primary diagnoses it as the "Navigate blockers"
row says, and may dispatch a run on the older tip's commit.

Inputs the builder reads first:

- TSK-1040's research (the research edge below): by default a group keeps
  one running and one pending run, a newer run replaces the pending one,
  and `cancel-in-progress: true` also cancels the running one; `queue:
  max` keeps every pending run. Here replacing a pending older line push
  is wanted, so the default single-slot queue suits line pushes.
- Schedule and dispatch runs on an integration ref share the push's group
  today; with cancellation on, a line push would cancel a dispatched run.
  They need a group of their own run, as `codeflow-policy.yml` gives its
  push, schedule and dispatch runs (`:56-57`).
- TSK-359 reuse: `scripts/ci-reuse.py` takes a verdict only from a
  `pull_request` run (`:154`, `:192`) and refuses a cancelled or partial
  run (TSK-359 AC-3), so a cancelled push run is never a reuse source. A
  newest-tip push that reuses its pull request's verdict finishes in
  minutes, so it is rarely the one cancelled; if it is, the newer tip's
  run decides. This task changes no reuse condition.

Non-goals: the shipped template (TSK-1026), `codeflow-policy.yml`
(TSK-1040), and the pull request cancellation rule.

## Research and design (AC-1)

Checked 2026-11-02 before any change, against GitHub's "Control the concurrency
of workflows and jobs" page (docs.github.com, Actions, using-jobs/using-concurrency),
the required status checks troubleshooting page, and TSK-1040's recorded
research at `61d221f4f`.

Findings:

- TSK-1040's semantics hold. A group allows one running and one pending run.
  A new run replaces the pending one, and `cancel-in-progress: true` also
  cancels the running one. `queue: max` and `cancel-in-progress: true` are
  not allowed together. A group name may be any string or expression using
  the `github`, `inputs` and `vars` contexts, among others.
- A cancelled check does not satisfy a required check. GitHub lists
  `success`, `skipped` and `neutral` as passing. A cancelled run is not on
  that list, and the pages do not say more. This matches the line rule
  "Hosted green before the next landing" in `AGENTS.md`, which counts
  cancelled as not green and counts only the current tip.
- Today `codeflow-ci.yml` uses one group per workflow and ref and cancels
  only for `pull_request`. A main, schedule or dispatch run is therefore not
  cancelled while running, but a newer run in the same ref group still
  replaces a pending one. Per-run groups remove that replacement, which AC-3
  requires ("never cancelled and never cancel another run").

Chosen expression (the top-level `concurrency` block only):

```yaml
concurrency:
  group: ${{ (github.event_name == 'pull_request' || (github.event_name == 'push' && startsWith(github.ref, 'refs/heads/integration/') && github.run_attempt == 1)) && format('{0}-{1}', github.workflow, github.ref) || format('{0}-run-{1}-{2}', github.workflow, github.run_id, github.run_attempt) }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' || (github.event_name == 'push' && startsWith(github.ref, 'refs/heads/integration/') && github.run_attempt == 1) }}
```

(Revised after review round 1; the first draft had no `run_attempt` term.)

- `pull_request`: the same group as today and the same cancellation, a
  rerun included. This task does not change it.
- first-attempt push to `integration/**`: one group per line, so a newer
  push cancels the older running or pending run of that line.
- a rerun of a push (`run_attempt` above 1): a group of its own and no
  cancel. Both are needed: `cancel-in-progress: false` alone would still
  let a rerun sitting in the line group replace the pending run there.
- push to `main` or `master`, schedule, dispatch (an integration ref
  included): a group of the run's own id and attempt, so nothing cancels it
  and it cancels nothing.
- The expression is parenthesised because `&&` binds tighter than `||`. The
  group string is non-empty, so `cond && group || other` selects correctly.

Interactions: TSK-359's reuse reads only `pull_request` runs and refuses
cancelled ones, so a cancelled push run is never a reuse source and no reuse
condition changes. When the newest tip's run fails, the failure is not yet
attributed to one landing; the primary diagnoses it.

Limits found in review round 1 (2026-11-02), with the chosen handling:

- Case. GitHub compares concurrency group names without regard to case
  (GitHub's concurrency page, which the review cites), so the lines
  `integration/EPC-022-x` and `integration/epc-022-x` would share a group, and
  a push to one would cancel the other's run. No workflow expression can fold
  or encode case: the available functions are `format`, `join`, `contains`,
  `startsWith`, `endsWith`, `toJSON`, `fromJSON` and `hashFiles`, and the
  string ones compare without regard to case. Sound remedies therefore sit
  outside the expression. Choice: keep the group on the literal ref and make
  the case-twin pair impossible by a repository rule, an operator step: a
  ruleset "restrict branch names" with a case-sensitive pattern such as
  `^integration/EPC-[0-9]+-[a-z0-9-]+$`, under which no two allowed names
  differ only in case. Until it is set, a twin needs push permission on this
  repository, and its effect is a cancelled run (never a false green) that a
  rerun recovers. The workflow comment states the limit, and a test checks
  that the integration lines the project's records name hold no such pair.
  Not verified: the live rulesets and branch-creation permissions; `gh` could
  not be read from this sandbox.
- Out-of-order first attempts. GitHub does not promise that runs start in
  push order, so an older tip's run that starts late can cancel the newest
  tip's run. The workflow cannot prevent this. Reading the branch tip needs
  only contents read, so freshness is readable, but the decision runs too
  late: top-level concurrency cancels a run before any of its steps starts,
  and a step cannot rescue a run that is already cancelled. A design that
  explicitly cancels other runs from a step would need `actions: write`,
  which the workflow does not hold. Recovery: rerun the newest tip's run,
  which has its own group, so nothing cancels it. The unconditional claim that the newest
  tip gets its verdicts is removed from this record's Outcome and AC-2, and
  from the workflow comment. EPC-022 AC-202 carries the same claim and needs
  the same clarification, which is the Director's planning edit.
- Push reruns. A rerun keeps the original ref and SHA, so a rerun of an old
  push would sit in the line group and cancel the newest run. Push reruns
  now use a group of their own and do not cancel. Pull request reruns keep
  today's rule.
- The test models a subset of GitHub's expression rules (documented in the
  test): string equality and `startsWith` ignore case. It checks names, not
  syntax, so it refuses a name outside its set but would accept arithmetic;
  it is not a validator of the workflow's expression grammar.

Not exercised locally: AC-2's two hosted pushes to a scratch line need the
workflow applied and a push, which this builder may not do.
