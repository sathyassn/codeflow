# TSK-378: The guards judge every script interpreter the way they judge python and node

## Description

Source: the security review of PR 239 (TSK-373) on 2026-10-18, marked "must fix before 3.2.0 ships". Severity high. It is unreleased TSK-302 work, so 3.2.0 would otherwise ship the gap.

The interpreter family list (`crates/codeflow-core/src/security/outward.rs:1220-1236`, `interpreter_family`) knows only `python`, `node`, `nodejs`, `perl` and `ruby`. A script run through another launcher passes both guards with an enforcement path as its argument:

- `deno run -A tool.ts .claude/settings.json`
- `bun tool.ts .claude/settings.json`
- `npx tsx tool.ts .claude/settings.json`
- `uv run tool.py .worktrees/w/.git`

`uv run python tool.py ...` is already refused, because the guard reaches `python`. The fix either adds these families (`deno`, `bun`, `tsx` and `ts-node` through `npx` and `pnpm dlx`, `uv run` and `uvx` with a script operand), or treats an unknown program followed by a script-like operand as an interpreter. The builder chooses and records the reason; the outcome is the same either way.

Outcome: **a script run through deno, bun, tsx or uv gets the same verdict as the same script run through python or node.**

Non-goal: modelling what each runtime's script does; the guard judges the operands, as it does for python and node.

Added by the EPC-022 amendment of 2026-10-18 under the operator's release decision of that day (workspace `RELEASE-PLAN.md`, 2026-10-18 operator decision).

Widened on 2026-10-20 (EPC-022 amendment) by the primary under the
operator's rule that every security gap belongs in 3.2.0, with finding P-2
of the `cf-security-reviewer` round 1 review of PR 264 (TSK-380) at
`c03b082dc`, severity high, likely, pre-existing on base and head
(`.worktrees/tsk-380/target/review-TSK-380-security-01.md`). GNU
`parallel` runs the Perl inside a `{= perl =}` replacement string for
each input, so a template word is interpreter code the guards never
judge: `parallel foo '{= system("touch ".$ENV{HOME}."/.zs"."hrc") =}' ::: x`
passes exec-guard on both binaries, and the same shape can name an
enforcement path in a `system` or `open` call the template builds at run
time. Today the guards read the commands `parallel` builds from its
template and `:::` inputs (`docs/policy-reference.md`, the closed rule;
`crates/codeflow-core/src/hooks/git_guard.rs:4980`, `parallel_violation`,
and `crates/codeflow-core/src/security/unresolved.rs:872`), and a template
word in braces is read as a replacement string, never as Perl. The
widening: a `{= ... =}` replacement string (a `--rpl` defined
replacement string holding Perl, and the `--plus` forms, included) is
judged as `perl -e` code in addition to every check the line already
gets: no existing refusal is removed, and no line refused today is
allowed. So exec-guard, which judges `perl -e 'open(F, ">",
".claude/settings.json")'` as `git.hook_integrity` and `perl -e
'system("touch $ENV{HOME}/.zshrc")'` as `security.shell_startup` today,
refuses the same text inside a replacement string for the same reason;
git-guard keeps every refusal it gives those lines today (it names
`.claude/settings.json` on the line, and reads a `{= =}` string as a
glob it will not inspect past 4096 entries), and `perl -e` verdicts
stay as they are on both hooks. Grok 4.7's round 3 review of PR 268
judged every line on the tree at `d55b752ad`
(`target/review-PR268-grok-03.md`, the seven-row table) and is the base
for the evidence below. Before the Perl judgment can be the verdict the
test sees, the deletion reader has to model `--plus` and `--rpl` as
input options (`crates/codeflow-core/src/security/deletion.rs:4404`,
`input_options_unproven`, from `judge_parallel` at `:4430`), which today
refuse any `parallel --plus` or `--rpl` line on exec-guard as an
unmodelled option under `security.dangerous_commands`. A replacement
string the guard cannot read refuses as cannot-verify, naming it, on a
line that names a protected path or where one is reachable. The P-2 line itself builds its path from
pieces at run time (`$ENV{HOME}."/.zs"."hrc"`) and names no protected
target on the line: that is the existing piece-assembly residual
(`docs/policy-reference.md`, "Every harness": a path assembled by a
program from pieces is kept as an allowed regression; the operator
decision of 2026-10-15), which `perl -e` of the same text is allowed
under today, and this widening does not narrow it: the P-2 parallel line
stays allowed on exec-guard and stays refused by git-guard's current
glob reading of the `{= =}` string, and `perl -e` of the piece text
stays allowed on both hooks. What the widening closes is that the replacement
string was not judged at all. `parallel` was not installed on the
reviewer's host, so the behaviour was read from the GNU parallel manual
and its `{= =}` documentation, and the builder confirms it with GNU
parallel in a scratch fixture before the tests are written.

## Acceptance Criteria

- AC-1 When a command runs a script through `deno run`, `bun`, `bun run`, `npx tsx`, `npx ts-node`, `pnpm dlx tsx`, `uv run <script>` or `uvx`, and an argument reaches an enforcement path, exec-guard and git-guard shall refuse it as they refuse `python3 tool.py <path>`; evidence: one guard test per launcher, each failing before the change. (serves EPC-022 AC-74)
- AC-2 The same launchers with an ordinary argument (`deno run tool.ts src/`, `bun test`, `uv run pytest`) shall pass; evidence: guard tests.
- AC-3 Version suffixes, `.exe` names and options before the script (`deno run --allow-read tool.ts`, `uv run --with x tool.py`) shall get the same verdict as the plain form; evidence: tests per form.
- AC-4 `docs/policy-reference.md` shall list the recognised launchers and say how an unknown launcher is judged; evidence: the doc text.
- AC-5 (journey) With the installed build, an agent session running each launcher form with `.claude/settings.json` as an argument, and the refused `parallel` lines of AC-6, shall be refused, and the ordinary forms shall run; evidence: the journey output.
- AC-6 (added 2026-10-20 from P-2 of the PR 264 security review) When a `parallel` template holds a `{= perl =}` replacement string, or a `--rpl` definition holds Perl, the string shall be judged as `perl -e` code in addition to every check the line already gets, so the Perl judgment removes no existing refusal and allows no line refused today; the one line this task changes from refuse to allow is `parallel --plus echo '{/.}' ::: a.txt`, refused on exec-guard today only for the unmodelled `--plus` option, which the deletion reader models: exec-guard shall refuse `parallel foo '{= open(F, ">", ".claude/settings.json") =}' ::: x` as a write of `.claude/settings.json` (`git.hook_integrity`; allowed today, so this case fails before the change) and `parallel --rpl '{w} open(F, ">", ".claude/settings.json")' foo '{w}' ::: x` for that same settings write (today it refuses under `security.dangerous_commands` for the unmodelled `--rpl` option, so the reason changes once `--rpl` is modelled), and shall keep refusing `parallel foo '{= system("touch $ENV{HOME}/.zshrc") =}' ::: x` as `security.shell_startup`; git-guard shall keep its current refusals of those four lines (the three `parallel` lines above and the P-2 line), unchanged (`git.hook_integrity`: the line names `.claude/settings.json`, or the `{= =}` string is read as a glob it will not inspect); the P-2 line `parallel foo '{= system("touch ".$ENV{HOME}."/.zs"."hrc") =}' ::: x` shall stay the piece-assembly residual on exec-guard (allow) and stay refused by git-guard's current glob reading; the `perl -e` verdicts of the three texts shall be unchanged on both hooks (exec-guard refuses the `open` and `$ENV{HOME}/.zshrc` texts and allows the piece text; git-guard allows all three); a replacement string the guard cannot read (a non-literal it does not resolve) shall be refused as cannot-verify naming it on a line that names a protected path or where one is reachable; and `parallel echo '{= s/\.txt$// =}' ::: a.txt b.txt`, `parallel --plus echo '{/.}' ::: a.txt` (refused today on exec-guard for the unmodelled `--plus` option, so it fails before the change) and `parallel gzip {} ::: *.log` shall pass on both hooks; evidence: Grok's round 3 seven-row table in `target/review-PR268-grok-03.md` as the base verdicts, one guard test per line and hook asserting the stated verdict and its reason, the `open` refusal and the `--plus` pass failing before the change, and the builder's note of the GNU parallel version that confirmed the replacement-string behaviour. (serves EPC-022 AC-74)
