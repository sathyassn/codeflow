# TSK-1285: A hook binary older than the repository says it is too old

## Description

A hook binary older than the repository it guards reads the repository's newer records and test config as user errors. On 2026-11-03 the installed codeflow 3.1.0 pre-push hook, run on a plain task-branch push to the 4.0.0 line (TSK-1039's branch at 46ac87541, fed on stdin, nothing pushed), refused with `git.test_gate_on_push`:

- "invalid test config ... targets[1].heavy: unknown field"
- `codeflow ci` work.acceptance_binding, work.criteria_frozen, work.valid_graph
- `codeflow validate --docs` failed

Each message tells the user to "fix the findings above", but nothing is wrong with the repository. The binary is too old. The same push passes with a binary built from the line first on PATH. Log: `/private/tmp/claude/prepush-310-repro.log` (copy it into the PR's evidence). The operator hit this on a TSK-1241 push.

A second case, on 2026-11-03 at 11:2x: the push of `plan/regroup-feature-epics` was refused by the installed codeflow 3.1.0 pre-push hook with "push set could not load test-config.json: ... targets[1].heavy: unknown field". The same push went through with the 4.0.0 worktree binary (`.worktrees/tsk-1085/target/debug`) first on PATH, without `CODEFLOW_HOOK_BINARY`. The beta install after the c3b2 landing fixes this host; this task fixes the message for every adopter whose binary lags.

## Outcome

After this merges, a person whose hook or CLI binary is older than the repository's records is told the binary is too old, which version the repository needs and how to upgrade, instead of being asked to fix findings that are not there; the refusal still fails closed.

## Deliverables

- the investigation and the chosen detection signal: this record's `## Findings` section
- the too-old refusal for each reader: the test config, record, policy and ledger readers under `crates/codeflow-core/src/` that the Findings name

`coord/transition.rs` already says "newer than this build reads; upgrade codeflow"; that is the wording to match.

### Markers the repository already carries

- `scaffold_version` in `.codeflow/project.toml`: the CI pin (`doctor/ci_pin.rs`), written by `init` and `update`, compared by `version_skew_warning`.
- `scaffold_version` in `.codeflow/manifest.json`: the same value as an update stamp.
- `schema_version` in each config file. These do not move when a field is added: `heavy` arrived with the test config still at `1.0`. They cannot be the signal.

### Chosen signal

- **Signal:** the pin in `.codeflow/project.toml` is newer than the running binary, by `scaffold::version::is_older`.
- **It fires only after a reader has failed.** A pin newer than the binary is not itself a refusal. The upgrade route is two pull requests, and the first raises only the pin while the older target binary judges it (`doctor/ci_pin.rs`), so a blanket refusal would break upgrades.
- **Records have no field to detect,** so in `codeflow ci` every blocking `work.*` finding collapses into the one refusal when the pin is newer. `git.*` and other findings are still printed: those rules read the commit and the judged policy, not the newer records.
- **`codeflow ci` reads the pin at the judging authority's commit, never at the head.** The head is the requester's text, so a raised pin there cannot hide findings. With no authority there is no trusted marker, so the no-marker line applies.
- **The push reads the pin at the destination default branch's tip,** the commit that judges the push.
- **Local readers read the working tree's pin,** the same tree those readers are refusing. So does `codeflow ci`'s first policy check, which runs before any authority is known: it stops the run either way, so a raised pin changes only the wording.
- **No marker:** a missing, unreadable or unparseable pin keeps today's refusal and adds one line saying the binary may be older, with the check to run (AC-3).
- **Fail closed:** the refusal replaces text only. Every path keeps its non-zero exit, and `codeflow ci` adds a blocking finding in place of the blocking findings it removes.

### Who sees the message (AC-6)

The message reaches users from the first release that carries this change. A binary already installed cannot print text it does not contain, so a 3.x binary on a 4.0.0 repository keeps its per-field refusal, which stays fail-closed, and the 3.x to 4.0.0 upgrade path stays in the release notes.

### Limits

- `codeflow doctor` and the session guards also read the policy; they are outside "a push or commit" and keep their own reports.
- `codeflow ci` reads the project state strictly at the head first (`adopter::check_head_config`). A state with no `scaffold_version` line refuses there with exit 2 and keeps that report, so in `codeflow ci` the no-marker line covers a pin it cannot compare or an authority with no state file.
- `codeflow validate --since` judges transitions and keeps its own report.
- AC-5's fixture raises the pin together with a policy key from that later release, and its passing push has neither. The pin alone cannot flip a push: AC-2 requires a reader to have failed, and the policy's own `schema_version` is inert (`policy_schema.rs`). A separate test shows a newer pin with everything readable still pushes.
- When the pin is newer, a genuine `work.*` or policy mistake is hidden until the binary is upgraded. This binary cannot tell the two apart, and the refusal stands either way.
