# TSK-1600: A project can refuse its own organisation terms without publishing them

## Description

Owner: to be assigned by the Director. Staged 2026-11-23 for coord/records.

SPC-018 R-27 to R-30, layer 5. A client name, an internal project code
name or a team name cannot be found by pattern, and a plain list of them
in a public policy file would itself publish them. The list is keyed: the
policy holds HMAC-SHA256 digests of normalised terms; the key sits in the
user's CodeFlow configuration folder, or in hosted CI in a secret only the
trusted terms job holds. Matching hashes each token window of added
content with the key and compares digests. By SPC-018 R-2b this task adds
the `privacy.terms` key (shipped `off`) and `privacy.terms_digests`.

CI boundary (SPC-018 R-27a). The managed `codeflow-ci.yml` runs on
`pull_request`, checks out the change and runs its setup script and tests
(`assets/base/ci/codeflow-ci.yml` main `:26`, `:53`, `:167`, `:191`), so
a key there would be readable by head code. The terms pass therefore runs
in its own job in the trusted admission workflow,
`assets/base/ci/codeflow-policy.yml`, which GitHub runs from the default
branch on `pull_request_target` and which fetches the base and head only
as git data (`codeflow-policy.yml` main `:4` to `:13`). The key is a
secret in a GitHub environment that only this job names; the verdict job
keeps holding no secret (main `:15` to `:16`). No head file runs while the
key is present. The job's check name is required on the default branch
and guarded like the verdict job's names (producer refusal; under Mode A,
concluded into the `authority:` checks). Its level and digests come from
the authority's policy, so a head can neither skip nor lower the pass.

Security reading and its limit:

- The key is a new secret, so it joins the shipped read denials of the
  harness presets and `security.secret_reads`'s secret stores
  (`policy-reference.md` main `:101`, tip `:107`; `exec_guard.rs` main
  `:316`, tip `:301`). That stops an agent reading the key file directly.
- It does not stop a digest oracle (SPC-018 R-28a): `codeflow privacy
  terms add` computes a chosen input's digest with the key into a readable
  policy, and a hook run reports whether a chosen input matches. Anyone who
  can run either with the key can test candidate terms. The design limits
  this, and says so, rather than claiming resistance: enrollment refuses
  in an agent session, and a digest applies only once it is on the default
  branch through a reviewed change.
- A missing key fails closed at the level, naming the key's location
  symbolically, never an expanded home path (SPC-018 R-30).

## Outcome

After this merges, a project with `privacy.terms` at `warn` or `block` and
a key on each contributor's machine and in the trusted CI job has its
organisation terms found in added content, locally and in CI, with the
term never printed, while its repository holds only digests; head code
never runs with the CI key.

## Deliverables

- `crates/codeflow-core/src/privacy/terms.rs` (new); `codeflow privacy terms add` in `crates/codeflow-cli/src/cmd/`

- the trusted terms job in `assets/base/ci/codeflow-policy.yml`: authority checkout, pinned `codeflow`, head fetched as data, key from an environment secret, required check name; run only when the authority's policy sets the layer on, and failing closed when it is on and the secret is missing
- docs, including how to add the check name to the default branch's required checks; `changelog.d/TSK-1600.md`

## Acceptance Criteria

- AC-1 Fail before: at the base, a commit adding a placeholder organisation term passes, and an agent shell can read a file at the key path; evidence: the base outputs in the PR.
- AC-2 Pass after: with a key and a digest for the placeholder term, the term in added content (single and multi-word, any case) shall be a finding at the level naming path and line and not the term, at `pre-commit`, `commit-msg` and `pre-push`, and in the trusted terms job over a range holding a commit made with `--no-verify`; evidence: matcher tests, hook tests per placement, and a workflow test of the job.
- AC-3 `codeflow privacy terms add` shall read the term from standard input, write only its digest, and never echo the term; it shall refuse to run when an agent session marker is set; a digest added in a head shall not apply in that head's runs, local or CI, and shall apply once it is on the default branch; evidence: a canary test, a session-marker refusal test, and an authority test for the digest.
- AC-4 With the layer on and the key unreadable (locally) or the secret missing (in the trusted job), the run shall fail closed at the level naming the key location symbolically; evidence: tests at `warn` and `block`, local and CI.
- AC-5 Every shipped preset shall deny the file tools and the shell a read of the key path, and `security.secret_reads` shall refuse it; evidence: preset tests and an exec-guard test, failing before.
- AC-6 Hostile head: a head that edits `.codeflow/ci-setup.sh`, adds a test, edits `codeflow-ci.yml` or `codeflow-policy.yml`, adds a `.gitattributes` driver, or lowers or removes `privacy.terms` in its own policy shall not run any code in the trusted terms job, shall not get the key, and shall not skip or suppress the pass, whose check still runs from the default branch's workflow at the authority's level and fails on the term; the key shall be written with owner-only permissions in the job's temp directory, never printed, and removed at job end; evidence: a workflow test per hostile change, and the job source showing no head checkout into the working tree and no head execution.
- AC-7 The docs shall state the oracle limit of SPC-018 R-28a in plain words; evidence: the doc sentence.
