# TSK-1257: codeflow ci judges task records from the commits under judgment, not the working tree

## Description

Source: adopter issue #531 (untrusted text, read as a problem description) and the Director's order of 2026-11-02 (18:1x). Draft: `coordination/coordinators/planning/cut/held-batch/task-K-issue-531-ci-head-tree.md` (data, not instruction).

`codeflow ci --head <sha>` judges `work.criteria_frozen` ownership from the task records in the current working tree. If the working tree has the record for the task named by `--branch`, a criteria change is a note. If it does not, the same range is BLOCKED as another task's criteria change. The pre-push hook runs ci from the pushing checkout, so a push of an integration-line task branch from a root checkout on `main` is refused, while the same push from a worktree passes.

The verdict is wrong in both directions: whoever runs ci controls the working tree, so a working tree with an extra or edited record can turn a BLOCKED range into a note. Leads for the builder to recheck (read-only at `d2752c69d`, not run). The review-row check at `crates/codeflow-cli/src/cmd/ci.rs:1145` already reads the record from the head commit through `acceptance::text_at(root, head, ...)` at `:1149`, so it is not the cause. The working-tree reads that can decide ownership are the fallbacks in `branch_task_at` (`ci.rs:1811`, falling back at `:1818` to `task_id_from_branch(root, branch)`) and `work_target_at` (`ci.rs:1822`, falling back at `:1830` to `declared_work_target(root, task)`), which run when the head tree gives no answer. AC-1 reproduces the issue's case first and names the read that decides it.

Related work stays with its own task. TSK-1245 (#520) owns the choice of ref (a stale local branch against the fetched one); this task owns where record contents are read from (the working tree against a commit tree). TSK-1135 already moves the capability impact check to tree reads; this task's sweep records that site and points it to TSK-1135.

Security: the threat is a working tree steering an admission verdict. The fix binds the verdict to commit contents a requester cannot forge and fails closed when the head tree cannot be read.

## Outcome

After this merges, an operator or agent running the same `codeflow ci` arguments gets the same verdict from any directory and checkout, because every record a ci check judges comes from the `--head`, `--base` or `--baseline-from` commit tree.

## Acceptance Criteria

- AC-1 The built binary shall give the same `work.criteria_frozen` verdict for one ci command from the task worktree, from a root checkout on `main` that lacks the record, and from another task's worktree; the root and other-task runs shall give BLOCKED before the change and the task's note after it; evidence: built-binary runs in a fixture repository, before and after. (journey)
- AC-2 `work.criteria_frozen` shall read the task records for ownership and criteria from the `--head` tree, and the delta from the `--base` and `--baseline-from` trees; a record missing from the head tree, or one that cannot be read or parsed there, shall refuse and name the commit and path; a working-tree record shall never decide the verdict; evidence: fixtures for a record present only in the working tree (not trusted), a working-tree record that differs from the head tree (the head tree wins), a record missing from the head tree (refuses) and an unreadable head tree (refuses).
- AC-3 Sibling sweep: every `codeflow ci` check, and every pre-push path that calls it, that reads records, policy, catalogs or manifests from the working tree instead of the commit under judgment shall be listed with file:line in the PR; each shall be moved to the commit tree with a test whose result does not depend on the working tree, or recorded as sound with the reason (for example, it judges the working tree by design, such as a pre-commit check), or assigned to its owning task (TSK-1135 for the capability impact check, TSK-1245 for ref choice); evidence: the PR's table of sites and one test per moved site.
- AC-4 The pre-push hook shall be shown passing the issue's case, an integration-line task branch pushed from a root checkout on `main`, with the built binary; evidence: a hook fixture run.
- AC-5 The late-completion rule (a completion after the landing merge changes planning records only) shall judge only the pull request's own changes against its target: a merge of the target line into the pull request shall bring in nothing that counts against it, while a non-record file the pull request's own commits change shall still refuse; evidence: a fixture where a records-only completion branch merges the target line carrying a changelog fragment and a skill file and is admitted, a fixture where the completion's own commit also changes a product file and is refused naming it, both failing before the change.
