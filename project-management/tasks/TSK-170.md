# TSK-170: unresolved conflict markers refused before commit

## Description

In EPC-016's TSK-120 review round 4, a merge left four sets of conflict
markers in `.codeflow/manifest.json` and they were committed. The
pre-commit hook and `codeflow validate --docs` accepted the commit; only
`codeflow doctor` refused it, because its config check parses the JSON
files under `.codeflow/` (`doctor/mod.rs:506`). No CodeFlow check looks
for markers in any other file, so the same slip in a Markdown, YAML or
source file lands silently. The pre-commit hook today checks
protected-branch commits and staged secrets only
(`hooks/git_hook.rs:43-70`).

This task adds one check, shared by the pre-commit hook and `codeflow ci`,
that refuses unresolved conflict markers in the lines a change adds to a
text file, under a new policy key.

Non-goals, and where each gap is caught (git behaviour checked on git
2.53.0):

- No whole-file sweep of existing content: only added lines are judged,
  as for the secret scan and the dash check.
- No git-guard or pre-merge-commit rule. Git runs pre-commit when a
  conflicted merge is concluded with `git commit` or
  `git merge --continue`.
- `git rebase --continue` runs no pre-commit hook, so a marker left while
  resolving a rebase is committed locally; `codeflow ci` over the range
  catches it.
- A clean merge of a branch that already holds a marker runs
  pre-merge-commit, which has no content check; as for the secret scan,
  `codeflow ci` over the range catches it.
- No change to `doctor`.

## The check

- A marker is a line that starts with `<<<<<<<`, `>>>>>>>` or `|||||||`
  (diff3) followed by a space or the line end, or a line that is exactly
  `=======`. Each length is the path's `conflict-marker-size`, 7 unless
  `.gitattributes` sets it, the rule `git diff --check` and git's merge
  use.
- `<<<<<<<`, `>>>>>>>` and `|||||||` lines are findings on their own. A
  `=======` line is a finding only between an opening and a closing
  marker in the same file, so a Markdown setext heading underline is
  never one. The order is judged across hunks, over all the lines the
  change adds to that file: an opening in one hunk and its separator in
  a later one is the usual shape of a leftover conflict.
- The size comes from `.gitattributes` as the change will commit it: the
  pre-commit hook reads the staged `.gitattributes` (the semantics of
  `git check-attr --cached`), and `codeflow ci` reads it at the head. A
  commit that adds a fixture and its attribute together passes on both
  planes.
- The way through for a file that legitimately holds markers (a fixture,
  a document about git) is git's own: set `conflict-marker-size` for its
  path in `.gitattributes` to a length its markers do not have. That is
  smaller than a new path allowlist and sound, because git's merge then
  writes longer markers in that file too, so a real conflict there is
  still caught. No allowlist key is added.
- Binary files and deletions are skipped.

## Default level

`git.conflict_markers` defaults to `block`. A committed marker has no
legitimate use once the attribute route exists; it is invisible in prose,
breaks JSON and YAML parsing silently (the TSK-120 case), and costs
seconds to fix before the commit and a repair PR after. The matcher's
structure rule keeps false positives near zero, and a team can set
`warn` or `off` in a reviewed policy edit. Bootstrap grace suspends it
like the other git rules. For adopters it is a behaviour change, not a
break: `codeflow update` adds the key at `block` and reports it, and only
commits that add unresolved markers are refused.

## Acceptance Criteria

- AC-1 When a staged change adds a line that is an opening, closing or
  diff3 base marker, or a separator between an opening and a closing
  marker, to a text file, the pre-commit hook shall report it under
  `git.conflict_markers` naming the file, line and marker, with the
  remedy "resolve the conflict and restage, or set conflict-marker-size
  for the path in .gitattributes"; at `warn` it warns and at `off` it is
  silent; evidence: unit tests in `conflict_markers.rs` for each marker
  kind, with and without a trailing label, and `git_hook.rs` tests at
  each level.
- AC-2 A `=======` line outside an opening and closing marker, a marker
  that does not start its line, a marker longer or shorter than the
  path's size, a binary file and a deletion shall produce no finding;
  evidence: unit tests for each, including a Markdown setext heading.
- AC-3 A path whose `.gitattributes` sets `conflict-marker-size` shall be
  judged at that size: 7-character markers there are no finding and
  markers of the set size are; the pre-commit hook reads the staged
  `.gitattributes`, so a fixture and its attribute staged together
  commit; evidence: unit tests with the attribute set and unset, and a
  hook test that stages both in one commit.
- AC-4 `codeflow ci` shall run the same matcher over the added lines of
  its range in every text path, with the same level, messages and
  attribute rule, and name `conflict-markers` among the checks it ran;
  evidence: a `ci_cli` test with one finding per case of AC-1 and AC-3
  and a parity test that feeds one staged diff to both planes and
  compares the findings.
- AC-5 The policy carries `git.conflict_markers` (default `block`) in
  `assets/base/policy.json`, the parser, the schema and this
  repository's policy; bootstrap grace sets it off; `codeflow update`
  adds it to an existing policy and reports it; evidence: policy and
  schema tests and an update test.
- AC-6 (journey) On a fresh `codeflow init` project driven by the built
  binary through its installed hooks: a conflicted merge concluded with
  `git commit` while a file still holds markers is refused; after the
  markers are resolved the commit passes; a Markdown file with a
  `=======` underline and a fixture holding 7-character markers under a
  `conflict-marker-size=32` path both commit; `codeflow ci` over the
  range reports the refused case and passes the others; a conflict
  resolved with markers left during `git rebase --continue` commits
  locally and `codeflow ci` over the range refuses it; evidence: an
  end-to-end test in `hooks_cli.rs`.
- AC-7 This task's own range passes its check: fixtures in its tests are
  built so no added line is a marker at the default size, or live under
  a path with the attribute set; evidence: `codeflow ci` over the task
  range, clean.
- AC-8 `git-rules.md` lists the check on the pre-commit plane, CAP-003
  names it and its tests, `docs/adoption.md` names the key `update`
  adds, and `CHANGELOG.md` carries one pending Added entry, marked
  `codeflow:release-impact minor`, naming the default `block` as a
  behaviour change and the `.gitattributes` route; mirrors, baseline and
  manifest are in sync. An example in these texts never shows a real
  marker line at the start of a line, since that would trip the check on
  this task's own range: describe the marker in words, indent it, or set
  the attribute; evidence: `manifest_consistency`, `init_e2e`,
  `codeflow validate --docs` and `codeflow ci` clean (serves EPC-020
  AC-14).
