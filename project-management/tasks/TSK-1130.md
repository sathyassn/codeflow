# TSK-1130: git-guard judges a hooks path inherited from the environment once the policy authority resolves

## Description

Once the policy authority resolves, git-guard refuses a `core.hooksPath`
injected through `GIT_CONFIG_*` only when the assignment is written in the
command itself. `git_config_env_sets_hooks_path`
(`crates/codeflow-core/src/hooks/git_guard.rs:1442-1448`, called at
`:1104-1109`) reads `GIT_CONFIG_KEY_*` and `GIT_CONFIG_PARAMETERS` from
`leading_env_assignments` (`:1409-1440`), which collects prefixes and
`env`, `export`, `declare` and `command` arguments of that command. It never
sees the process environment the hook itself inherited.

Grok round 03 on PR 467 (`/private/tmp/pr467-gk-03.md`) confirmed the trigger
with Git 2.53.0: the process environment holds `GIT_CONFIG_COUNT=1`,
`GIT_CONFIG_KEY_0=core.hooksPath` and `GIT_CONFIG_VALUE_0=<dir>`, the
repository config names a hooks directory without `post-index-change`, and
`git status`, which rewrites the index, runs the hook in `<dir>`. A resolved
`git status` whose text carries no assignment passes. TSK-1104 closed the same
gap for the unresolved window only (`ref_authority.rs`,
`no_index_change_hook`), and left the resolved verdicts unchanged on purpose.

Exec-guard judges git commands through the same check, so the fix must cover
both guards. The fix reads the effective configuration Git lists for the call
(`security::git_config::read`, which keeps the process environment) and judges
the hooks path it reports, in addition to the command-line forms already
judged. Non-goals: no change to which hook-skip variables are refused; the
unresolved-window rule of TSK-1104 changes only for a hooks path that is not
the repository's own, because that window shares the reader (amended after
Codex security round 01 on PR 474).

## Outcome

After this merges, an agent whose session inherits a `core.hooksPath` through
`GIT_CONFIG_COUNT` or `GIT_CONFIG_PARAMETERS` is refused by git-guard and
exec-guard when a git command would run a hook from that path, the same as
when the command writes the assignment itself.

## Deliverables

- the effective-configuration hooks-path check in the resolved path: `crates/codeflow-core/src/hooks/git_guard.rs`, with exec-guard covered through the same check
- the journey tests with an inherited environment and with environment-selected files: `crates/codeflow-cli/tests/hooks_cli/target_repository.rs` (`refusal_journey` holds only the changed older TSK-1104 control)
- the policy text for the rule: `docs/policy-reference.md`
- the changelog fragment: `changelog.d/TSK-1130.md`

## Acceptance Criteria

- AC-1 When the process environment carries `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n=core.hooksPath` and `GIT_CONFIG_VALUE_n` (or `GIT_CONFIG_PARAMETERS` naming it), and the policy authority is resolved, git-guard and exec-guard shall refuse a git command that would run a hook from that path. Evidence: a unit test per spelling, and the Grok round 03 trigger reproduced, failing before the change and passing after.
- AC-2 When the effective configuration cannot be read, or the hooks path it names cannot be resolved with certainty, the check shall refuse (fail closed). Evidence: a test with an unreadable configuration and one with an unsupported path spelling.
- AC-3 (amended after Codex security round 01 on PR 474: the inherited environment can select a global or system file, and a directory can gain a hook after the check, so neither the file scope nor the directory contents can decide) A call with no `core.hooksPath`, and a call whose value in force comes from the repository's own `local` or `worktree` configuration, shall keep their present verdicts; a value from the command, global or system scope shall refuse whatever its directory holds. Evidence: tests for each scope, for explicit global and system files, home and XDG directories, direct and conditional includes, and a repository value that makes an injected one ineffective.
- AC-4 (journey) (amended with AC-3) With the installed build in a scratch adopter whose process environment carries the three variables, or selects a global, system, home, XDG or included file that sets `core.hooksPath`, `git status` through git-guard and exec-guard, from the root and a linked worktree, shall exit 2 naming the hooks path, whether the directory holds a hook or is empty. With a repository-owned `core.hooksPath` the same environment shall exit 0 and the injected hook shall not run. Evidence: the journey output with each hook's exit code, and a control showing the injected hook runs when the repository sets no value.
- AC-5 (added after Codex security round 01 and the coordinator's sweep of the same class: the caller chooses which configuration counts as repository-owned when it moves the repository) When the process environment sets `GIT_DIR`, `GIT_COMMON_DIR` or `GIT_WORK_TREE` so that Git's repository location differs from the one found without them, git-guard and exec-guard shall refuse git, from a root checkout and a linked worktree; a variable naming the repository Git finds anyway, and no variable, keep their verdicts. Evidence: a journey per variable in both guards, failing before and passing after, and a unit test.
