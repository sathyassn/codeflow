# TSK-333: Version pins compare with one parser everywhere

## Description

TSK-309 (PR https://github.com/sathyassn/codeflow/pull/207, not yet landed)
replaces the loose version parse in
`crates/codeflow-core/src/scaffold/version.rs` with a strict one that
returns nothing for a version that is not `MAJOR.MINOR.PATCH` with an
optional prerelease and build, and guards init and update with it
(`check_write_version`). Its review (finding N2, tracked on PR 207) found
that two other paths still differ:

- `is_older` now falls back to plain string order when either side does not
  parse, where the line's version (`version.rs:9` to `:31`) read missing or
  non-numeric parts as 0. A hand-edited pin such as `3.10` or `10.0`
  therefore compares differently after TSK-309 in the two other callers:
  `update --pin` refusing a lower pin
  (`crates/codeflow-core/src/scaffold/release_pin.rs:418`) and doctor's
  lowered-pin warning (`crates/codeflow-core/src/doctor/ci_pin.rs:258`).
  For example, `"10.0" < "9.0"` as strings.
- `pin_release` (`release_pin.rs:397`) accepts any value that passes the
  looser `is_version` (`release_pin.rs:342`, checked at `:403`) and writes
  it to `scaffold_version` (`:463`). So `update --pin` can write a pin that
  TSK-309's guard then refuses for every later `init` and `update` as not
  parseable.

The outcome is that every comparison of versions and every writer of a pin
uses the one parser TSK-309 adds, and no caller compares an unparseable
version as a string: `pin_release` refuses a version the parser rejects
before it fetches or writes anything; the lower-pin check and doctor's
pin comparison report an unparseable pin by name instead of comparing it;
the skew warning (`version.rs:38`) stays quiet or names the unparseable
pin, the builder chooses which and records why. The comparison API makes
the unparseable case explicit (for example a result the caller must
handle) so a new caller cannot reintroduce a string order.

Non-goals: version handling in `scripts/release.py`, the installers'
format check (the strict form is a subset of what they read, so they keep
accepting every pin this task allows), and TSK-309's own criteria.

## Deliverables

- the shared comparison: `crates/codeflow-core/src/scaffold/version.rs`
- its callers: `crates/codeflow-core/src/scaffold/release_pin.rs` (`pin_release` and the lower-pin check) and `crates/codeflow-core/src/doctor/ci_pin.rs`
- tests: unit tests in those files and a CLI test of `codeflow update --pin` in `crates/codeflow-core/tests/scaffold_test.rs` or `crates/codeflow-cli/tests/` (the builder confirms)
- docs: the `update --pin` and doctor `ci-pin` entries in `docs/cli.md` and `docs/troubleshooting.md` where they describe accepted versions
- release note: `changelog.d/TSK-333.md`

## Acceptance Criteria

- AC-1 Every comparison of two versions in `crates/` shall go through the
  one parser TSK-309 adds, and no code path shall order versions as
  strings; evidence: the diff, a search for other comparisons recorded in
  the PR, and a test that two-part and suffixed pins (`3.10`, `10.0`,
  `3.2.0x`) are never ordered as strings. (serves EPC-022 AC-30)
- AC-2 When `codeflow update --pin <version>` is given a version the parser
  rejects, it shall refuse before any download or write, naming the value,
  and leave every project byte unchanged; evidence: a CLI test that
  compares the bytes. (serves EPC-022 AC-30)
- AC-3 When the pinned `scaffold_version` does not parse, the lower-pin
  check of `update --pin` and doctor's `ci-pin` check shall report the
  unparseable pin by name and never compare it; evidence: a test per
  caller. (serves EPC-022 AC-30)
- AC-4 Versions that both parse shall compare exactly as TSK-309's parser
  orders them, so a lower parseable pin is still refused and a lowered pin
  still warned; evidence: the existing release-pin and ci-pin tests
  passing unchanged, plus a prerelease and a build-metadata case.
- AC-5 The skew warning shall not print a false "behind" message for an
  unparseable pin; evidence: a test of `version_skew_warning` with an
  unparseable pin, matching the behaviour the task records.
- AC-6 (journey) With the installed build of this change in a scratch
  project, `codeflow update --pin 3.2` shall refuse with the value named
  as unparseable, not with a download error, and leave `git status`
  clean, and `codeflow doctor` on a project whose pin was
  hand-edited to `10.0` shall name the pin as unparseable; evidence: both
  outputs.
