# TSK-149: a ceremony report with a recorded baseline

## Description

Ceremony is the process cost that does not change the product: extra
pull requests per logical change, extra review rounds, and refusals an
agent hits on its own pushes. Nothing measures it today, so a change that
adds ceremony is not seen and one that removes it cannot show the gain.
Counted during planning over pull requests 568 to 644 (77 pull requests:
28 plan, 26 task, 20 fix, 3 docs), 20 of them only moved a record's status
or ownership (576, 579, 591, 594, 597, 602, 609, 612, 614, 616, 618, 619,
623, 627, 628, 630, 633, 639, 640, 641). Refusals were never recorded, so
their baseline is unknown.

This task adds a read-only report that shows, over a window of pull
requests or dates, pull requests per logical change, review rounds per
pull request, and refusals hit by the project's own pushes, with the
baseline above recorded and a check run before a release.

## Affected surfaces and interfaces

- A new read-only command, `codeflow report ceremony`: SPC-013 R-103's
  one host-backed read, printing `unknown` when the host call fails;
  `codeflow status` and the work reads stay offline.
- The existing JSONL ledger (`crates/codeflow-core/src/ledger/`): a new
  event for a refusal by a git hook or session guard, written locally when
  the refusal happens.
- `cmd/git_hook.rs` and the guards, only to append that event.
- A baseline record under `docs/verification/` for pull requests 568 to
  644.
- Shared files, per SPC-013 R-118: pre-push, hook rendering and dispatch
  (the event append), the ledger, and the release docs row
  (`docs/releasing.md`).

## Acceptance Criteria

- AC-1 When `codeflow report ceremony` runs over a window, it shall print
  pull requests per logical change (a task or planning change counted
  once across its pull requests, with record-status-only pull requests
  shown as their own row), review rounds per pull request, and refusals
  hit by own pushes; evidence: `report_cli` tests on a fixture history
  with known counts.
- AC-2 When the host is not reachable, or its review data is not
  available, the report shall print `unknown` for review rounds and never
  estimate them; record-derived counts shall still print; `codeflow
  status` and the work reads shall make no network call; evidence: a test
  with the host call failing, and the existing no-network test of the
  read commands.
- AC-3 When a git hook or session guard refuses an operation, it shall
  append one ledger event naming the rule, the plane and the effective
  level, with no command text or secret, and a refusal at warn shall not
  be counted as a refusal; evidence: `hooks_cli` tests for a blocked push,
  a warned push and a blocked guard call, reading the ledger.
- AC-4 The baseline for pull requests 568 to 644 shall be recorded with
  the command that reproduces it, and the report over that window shall
  match it; evidence: the baseline file and the report output in the pull
  request.
- AC-5 Before a release, the release checklist shall run the report over
  the release's window and compare it with the baseline, as information
  that never blocks; evidence: the checklist step in `docs/releasing.md`
  and its output on the release candidate.
- AC-6 (journey) In a freshly scaffolded standard-tier project driven by
  the installed CLI, a refused push followed by `codeflow report ceremony`
  shall show that refusal, and a warned push shall not; evidence: a
  journey test in `hooks_cli` or `init_e2e`.
