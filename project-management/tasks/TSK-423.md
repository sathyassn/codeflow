# TSK-423: The managed rule and orchestrator skill require the follow-up ledger

## Description

Issue #272, proposal item 1 and its acceptance. With the ledger command
in place (TSK-422), nothing yet tells a host session to use it:
`workflow-discipline.md` "Sessions and state" says to externalize state
but names no home for open commitments and no closure rule, and
`cf-model-orchestrator` names a task ledger with no shape.

Outcome: **the managed block, `workflow-discipline.md` and
`cf-model-orchestrator` say that the host logs every operator-handed
item and every unsettled or untasked item at once in the follow-up
ledger, with its fields, closes a row only on proof, reads the ledger at
session start, after compaction and before every status reply, and
builds status from it; and a fresh-context qualification shows a host
reporting three handed-over items, one stalled, without being asked.**

Rules the guidance states:

- The ledger is `codeflow follow` (TSK-422); its rows carry what,
  source, holder, task id or `needs task`, waits on and next check.
- A row closes only on proof (a merged pull request or commit, a
  recorded ruling, the operator's answer), never on "handed to a lane".
- The host reads the ledger at session start (the digest shows it),
  after compaction and before every status reply, and a status reply
  names each open row by its outcome, as the writing rule orders.
- The managed map's "report status or hand off" row (which TSK-387
  extends with the live-state and stuck-lane checks) names the ledger;
  the "start a session, or resume after compaction" row reads it.

Non-goals: the command (TSK-422); a per-host file; a mandatory hook.

Added by the EPC-022 amendment of 2026-10-22 under the operator's
decision of that day (project-management changes go in 3.2.0).
