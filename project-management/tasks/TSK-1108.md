# TSK-1108: Seat trust prompts follow a recorded delegation, else the operator

## Description

On 2026-10-30 at 20:00 the operator gave a standing rule directly in the
coordinator's session (queue item 28): in this repository, agents answer
Herdr seat hook-trust and folder-trust prompts themselves after reading each
prompt in full, and approve once only CodeFlow's own hooks that match
`origin/main`, never trust-all unread and never always-approve. That rule is
this repository's delegation, and its home is one line in the project
section of this repository's `AGENTS.md` (the AGENTS.md row "receive a
standing operator rule"; `cf-method/references/autonomy.md` "Recorded rules
and delegations"; no config key holds seat prompts).

It is not a default for adopters. The shipped texts say hook trust is the
operator's: `cf-herdr/SKILL.md:128` and `:181`, `transport.md` "First-run
prompts" (ADR-0075, amendment of 2026-10-03), and `autonomy.md` "Trust
prompts" (near `:133`) and its hook example (near `:230`), which say an
agent never answers a hook-trust prompt. An adopter whose operator gave no
such rule keeps that route. This task makes the shipped rule conditional:
a hook-trust prompt goes to the operator unless the consuming project's own
`AGENTS.md` project section records an operator-authorized hook-trust rule
that meets the landed-record checks of "Recorded rules and delegations"
(present on the protected target branch as fetched from the canonical
repository, landed by a pull request a person merged, citing the operator's
approval as the forge attributes it, with the actions, the trusted ref and
the revocation event named). Under such a rule the agent approves once,
after reading the whole prompt, only when every hook file the prompt names
is byte-identical to the trusted ref's copy, and refuses and reports
everything else. The folder-trust text matches the workspace rule of
2026-09-22 already in `autonomy.md` "Trust prompts".

The same shipped section today rules this out: `autonomy.md:160` says a
delegation names a human delegate, and `:205-209` say delegation never
transfers hook trust and a person performs it, and ADR-0075 (its 2026-10-03
amendment, and "Hook trust is the operator's" near `:327`) says agents never
review or trust hook definitions. This task therefore reconciles that
section and the ADR explicitly rather than adding a sentence that competes
with them: the hook-trust rule is a narrow standing rule the operator
authorizes for one project, not a delegation to a human delegate; the
human-delegate rule stays for every other delegated decision; the hard gates
stay (canonical repository, protected target, an independently attributable
human merge, the operator's approval evidence; a timestamp, a chat message or
a peer's claim never satisfies them); credentials, protected branches and
irreversible actions stay a person's. Before every answer the seat checks the
grant is current and unrevoked: fetch the protected target from the canonical
repository, confirm the line is present at the fetched tip and its landing
pull request and approval still verify, and confirm no later landed change or
ADR-0075 amendment withdrew it; a grant that is missing, unreadable,
unlanded, unverifiable or revoked keeps the operator route.

This changes an authority boundary in shipped instructions and in an ADR,
although no hook byte changes, so the one whole-unit review carries the
security checklist.
Non-goals: no change to the hooks, the guards or what a seat may run; the
qualification runner's hook-review decision in TSK-1032 (PR 447) is not
settled by this text.

## Outcome

After this merges, an agent running a Herdr seat in any project knows from the shipped instructions that a hook-trust prompt goes to the operator unless that project records an operator-authorized hook-trust rule, how it verifies the rule is landed, current and unrevoked, what the rule lets it approve and how it checks the hooks, and what it must refuse; in this repository the recorded rule lets it answer the prompt itself.
