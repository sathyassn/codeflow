# TSK-220: Merging the moved target into a reviewed task keeps its acceptance

## Description

A reviewed, completed task pull request must contain the current target for
the release-impact check, so after every merge to `main` it merges `main`
in. In a clone whose local `main` is strictly behind `origin/main`, such as
a root checkout that is never pulled, `codeflow ci` and the pre-push hook
then refused the completion under `work.acceptance_binding`: the binding
read the task's target from the stale local branch, so the merge's second
parent was not on that line and the merge counted as unreviewed work.

The fix judges a merge after the review against the target tips of the run,
never a local branch, its upstream configuration or a remote-tracking ref:
the base `codeflow ci` is given (the pull request's base in hosted CI), the
pre-push hook's candidate authority (the destination default branch's
advertised tip), and for a planning or line range its own line, only for
the tasks whose target is that line. A merge
stacks only when its second parent is on such a tip's first-parent line and
its recorded result equals the conflict-free automatic merge of its parents.
Anything else stops the walk and refuses, naming the commit, even when the
net change cancels out; a history overlay (grafts, replace refs) or a
shallow cut on the walked chain also refuses. The status verb, which has no
run base, previews the rule against the task's target as `work start`
anchors it. A task completed, reopened and completed again inside its own
unmerged pull request may change its own criteria while no record with its
id or uid is on the anchored target, under any path and file name the
record reader accepts (TSK-213's refusal); when the target cannot be read,
it keeps the criteria it was completed with.

Non-goals: the release-impact check's stale-base rule stays as it is, and a
reopening range, direct release-line work and a landed head still never
stack a merge (SPC-013 R-60, R-119, R-120).

## Acceptance Criteria

- AC-1 When a completed task branch merges its moved target cleanly after the reviewed commit, and the local target branch is strictly behind its upstream, `codeflow ci` against the published base and `codeflow task status complete` keep the binding; evidence: `acceptance_cli a_clean_merge_of_the_moved_target_keeps_the_binding`, which fails on the unfixed source and passes after.
- AC-2 When the commit after the review is a merge of the target with a hand edit, a conflicted merge resolved by hand, a regular commit beyond the record's status and Closeout, or a merge of an unrelated branch, `codeflow ci` still refuses under `work.acceptance_binding` and names that commit; evidence: `acceptance_cli anything_but_a_clean_target_merge_still_blocks_and_names_the_commit`.
- AC-3 When a task into an integration line merges the moved line after its review while the local line branch is behind `origin`'s, the binding holds, and the existing line, landing, reopen and release-line binding tests stay green; evidence: `acceptance_cli a_task_into_a_moved_integration_line_keeps_the_binding` and the `acceptance_cli`, `acceptance_journey` and `release_line_cli` targets.
- AC-4 (journey) When PR 35's head (8fb08e415) takes `origin/main` by a clean merge in a scratch worktree of a clone whose local `main` lags, `codeflow ci --base origin/main` with this build passes the binding where the 3.0.0 binary refuses it; evidence: both runs pasted in the pull request, the merge never pushed.
- AC-5 CAP-010, the delivery table, the cf-ship skill (every mirror and baseline copy) and the pending 3.1.0 CHANGELOG entry describe the rule, including that a merge's recorded result must equal the conflict-free automatic merge of its parents; evidence: the diff, `manifest_consistency` and `codeflow validate --docs`.
- AC-6 When the run's base is the published target, a merge of an unpublished commit refuses whether the local `main` tracks another remote that holds it or `origin/main` is forged to it, and a graft that puts it on the target's first-parent line refuses as a history overlay; and the pre-push hook's candidate authority (`--policy-from`) carries a target merge its range base does not reach; evidence: `acceptance_cli local_refs_and_overlays_never_make_a_merge_the_target`, which passes `codeflow ci` at 173c5422b and refuses after, and `acceptance_cli the_pre_push_candidate_authority_carries_a_target_merge`.
- AC-7 When the walk after the review stops, at a merge of more than two parents or an unreviewed change later removed, `codeflow ci` refuses and names the commit even though the net change is empty; evidence: `acceptance_cli a_stopped_stack_refuses_even_when_the_change_nets_out`.
- AC-8 When a task is completed, reopened, given a new criterion and completed again inside one unmerged branch, and its record is not on the target, `codeflow task status complete` and the binding accept it; when the record is on the target, the verb still refuses the criteria change; evidence: `acceptance_cli an_unlanded_task_may_change_its_criteria_when_reopened_in_its_range` and TSK-213's head `fbe18e185` reproduced in a scratch worktree.
- AC-9 When a task that targets `main` merges a landed integration line carrying a change the review never covered, the line's pull request into `main` refuses under `work.acceptance_binding`, while a task that targets that line still stacks the same merge; evidence: `acceptance_cli a_line_carries_merges_only_for_the_tasks_that_target_it`, which passes `codeflow ci` at d3d92a000 and refuses after.
- AC-10 When a landed task's record moves from the flat `tasks/` folder into its epic's `tasks/` folder and the task is reopened with changed criteria, the status verb refuses and `codeflow ci` blocks, because the record is found on the target by id or uid in every layout; evidence: `acceptance_cli a_moved_landed_record_keeps_its_criteria`, whose verb exits 0 at d3d92a000 and refuses after.
- AC-11 When a landed record without a `uid` sits at `project-management/tasks/TSK-001.MD` and the task is reopened in its own pull request with a changed criterion, kept at that path or moved into its epic's folder, `codeflow ci` blocks, because presence on the target is decided by the work-record reader and the parsed id; evidence: `acceptance_cli a_landed_record_with_an_uppercase_extension_keeps_its_criteria`, which passes `codeflow ci` at df8e476fb and refuses after.
