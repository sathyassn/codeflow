# TSK-300: assemble the 3.1.1 patch release

## Description

CodeFlow 3.1.1 is a patch for the critical open issues (153, 147 and 148), the
Linux CI speed-up and the dependency audit suppression (workspace
`RELEASE-PLAN.md`, "Patch 3.1.1, decided 2026-10-12"). This task writes the
release source on the final `main`: it runs `release.py assemble`, which
composes the pending fragments into one `## [3.1.1]` section and removes
them, and it adds an "Upgrading from 3.1.0" note with the four items the
operator chose for the notes. It runs last, after every 3.1.1 pull request
has landed, so no fragment can arrive beside the written section. Non-goal:
publication. The dry run, the `v3.1.1` dispatch and the tag stay with the
operator.

## Deliverables

- The assembled 3.1.1 section and its upgrade note: `CHANGELOG.md`
- The removed fragments: `changelog.d/`
- Full-gate and release-check evidence: this task's pull request

## Acceptance Criteria

- AC-1 When `python3 scripts/release.py assemble --repository sathyassn/codeflow` runs on a tree that holds every 3.1.1 change, `CHANGELOG.md` shall hold one `## [3.1.1]` section above `## [3.1.0]`, `changelog.d/` shall hold no fragment, and `release.py check-state` shall report version 3.1.1 with impact `patch`; evidence: the command output on the candidate.
- AC-2 Every entry in the 3.1.1 section shall keep the label, impact marker and bytes it had in its fragment; evidence: a comparison of each fragment against the assembled section, and `release.py check-pr` on the pull request.
- AC-3 The 3.1.1 section shall open with an "Upgrading from 3.1.0" note covering the binary swap on macOS, running `codeflow ci` by hand (issues 130 and 141), the credential route for CodeFlow's own pushes (issue 151) and the `.gitleaksignore` route (issue 139); evidence: the reviewed text, with each command checked against the 3.1.1 binary or the issue it cites.
- AC-4 When the full gate runs on the exact candidate, every target shall pass; evidence: `codeflow test` in full mode on the candidate commit.
- AC-5 When the release notes are rendered from the candidate for `v3.1.1`, they shall render the 3.1.1 section with no fragment refusal, and read correctly for a new user and for a user upgrading from 3.1.0; evidence: `release.py release-notes --tag v3.1.1` output and the two reads recorded in the pull request (journey)
