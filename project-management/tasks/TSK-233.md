# TSK-233: exec-guard semicolon launcher check needs a word boundary

## Description

Issue 66: exec-guard's privilege check refuses any line containing a
semicolon, a space and a launcher name (`su`, `sudo`, `doas`, `pkexec`,
`runuser`) as a raw substring, so prose such as "supersedes", "summary" or
"such as" after a semicolon in a heredoc, an `echo` or a grep pattern is
blocked. The check in `crates/codeflow-core/src/security/privilege.rs`
(`check_priv_chaining`) now also requires the launcher name to end at a word
boundary: whitespace, the end of the line, a control character, or a shell
metacharacter or expansion starter. It is deliberately conservative: it still
reads no quoting, heredoc or other text structure (the data-stripping
approach of PR 56 was withdrawn because it leaked), so every launch refused
before is refused with the same rule and reason, a launcher inside a quoted
string included. The only changed verdicts are words that merely start with a
launcher name. Non-goals: parsing simple commands, changing the `&&`, `||`
and pipe checks, or catching the `;su` form without a space, which the check
never covered. The issue's literal `grep -n '; su' file.txt` still blocks,
because a quote right after the launcher name is a boundary (`su''` is a
launch); `grep -n '; supersedes' file.txt` passes.

## Acceptance Criteria

- AC-1 When a command line holds a semicolon, a space and a word that only starts with a launcher name ("supersedes", "summary", "such as", "subtotal", "doasync", "sudoku" and the like), `security.privilege_escalation` no longer refuses it, including the issue's printf, heredoc and quoted-pattern forms (`test_semicolon_before_a_word_that_starts_with_a_launcher_name_is_allowed`, which fails on the unfixed check and passes after).
- AC-2 When the launcher name after a semicolon ends at a word boundary (end of line, whitespace, a tab, a shell metacharacter or an expansion starter), every launcher in the list is still refused with the same rule, reason and pattern as 3.0.0 (`test_semicolon_launchers_still_refuse_at_every_word_boundary`, `test_semicolon_refusal_reason_is_unchanged`), and a corpus of real launches across the launcher list, separators, heads and tails gets identical verdicts from the installed 3.0.0 hook and this branch's hook, the only changed verdicts being prefix words.
- AC-3 On the real `codeflow hook exec-guard`, the issue's heredoc is allowed and `true; su -` is still refused with `security.privilege_escalation` (`exec_guard_semicolon_launcher_check_stops_at_the_launcher_word`, `installed_minimal_hooks_refuse_each_family_and_allow_real_ordinary_work`) (journey).
