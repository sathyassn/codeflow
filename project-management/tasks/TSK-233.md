# TSK-233: exec-guard semicolon launcher check needs a word boundary

## Description

Issue 66: exec-guard's privilege check refuses any line containing a
semicolon, a space and a launcher name (`su`, `sudo`, `doas`, `pkexec`,
`runuser`) as a raw substring, so prose such as "supersedes", "summary" or
"such as" after a semicolon in a heredoc, an `echo` or a grep pattern is
blocked. The check in `crates/codeflow-core/src/security/privilege.rs`
(`check_priv_chaining`) now lets the name pass only when a letter, digit,
underscore or hyphen continues it into a longer word (`supersedes`,
`doasync`, `su-like`). Whitespace, the end of the line and every other
character after the name still refuse, because a shell can reach the launcher
through quotes, globs and expansions (`su''`, `su??`, `su[d]o`, `su@(do)`,
`su$IFS`), and the variants `sudoedit`, `sudoreplay`, `sudo-rs` and `su-exec`
still refuse. It is deliberately conservative: it still reads no quoting,
heredoc or other text structure (the data-stripping approach of PR 56 was
withdrawn because it leaked), so every launch refused before is refused with
the same rule and reason, a launcher inside a quoted string included. The only
changed verdicts are words that continue the name into a longer word.
Non-goals: parsing simple commands, changing the `&&`, `||` and pipe checks,
or the `;su` form without a space, which this check never covered and other
checks still refuse. The issue's literal `grep -n '; su' file.txt` still
blocks, because a quote right after the launcher name cannot be told from
`su''` without reading quotes; `grep -n '; supersedes' file.txt` passes.

## Acceptance Criteria

- AC-1 When a command line holds a semicolon, a space and a word that continues a launcher name into a longer word ("supersedes", "summary", "such as", "subtotal", "doasync", "sudoku" and the like), `security.privilege_escalation` no longer refuses it, including the issue's printf, heredoc and quoted-pattern forms (`test_semicolon_before_a_word_that_starts_with_a_launcher_name_is_allowed`, which fails on the unfixed check and passes after).
- AC-2 When the launcher name after a semicolon is followed by anything but a letter, digit, underscore or hyphen (end of line, whitespace, a tab, a quote, a glob or expansion character, punctuation), or is a launcher variant, every launcher in the list is still refused with the same rule, reason and pattern as 3.0.0 (`test_semicolon_launchers_still_refuse_at_every_word_boundary`, `test_semicolon_launcher_variants_still_refuse`, `test_semicolon_refusal_reason_is_unchanged`), and a corpus of real launches across the launcher list, separators, heads and tails gets identical verdicts from the base build without this change, and from the installed 3.0.0 hook except for a difference already on `origin/main`, the only changed verdicts being words that continue the name.
- AC-3 On the real `codeflow hook exec-guard`, the issue's heredoc is allowed and `true; su -` is still refused with `security.privilege_escalation` (`exec_guard_semicolon_launcher_check_stops_at_the_launcher_word`, `installed_minimal_hooks_refuse_each_family_and_allow_real_ordinary_work`) (journey).
