# TSK-102: work record lifecycle with status verbs and transition rules

## Description

Give every recorded fact one writer path and one judge (design v4 sections 3,
4, 5.1 and 7). Add the status verbs `task status`, `epic status` and
`spec status`; put the transition rules in the core validator so a hand edit
is judged exactly like a verb; require a `## Blocker` for blocked tasks and
a Closeout for cancelled ones; list new criteria with ids and no checkbox;
parse the acceptance block; apply the rules from a recorded migration
baseline; add `git.work_records` (`block` or `warn`, never `off`); and
retire the ledger's work-graph event types that have no producer
(`crates/codeflow-core/src/ledger/routing.rs:26-36`). Writes detect a
concurrent edit by digest and replace atomically. Non-goal: the CI binding of
the acceptance block to the reviewed commit (TSK-105) and derived views
(TSK-103).

## Affected surfaces and interfaces

- Record schema and validator: `crates/codeflow-core/src/validate/`,
  `crates/codeflow-core/src/workgraph/store.rs` (CAP-010).
- New CLI verbs; the ledger routing table.
- Policy schema: `git.work_records`. Record templates: criteria without
  checkboxes. Ownership of these shared files follows SPC-013
  R-118.

## Acceptance Criteria

- [ ] AC-1 When `task status TSK-NNN todo|blocked|complete|cancelled`,
      `epic status` or `spec status` runs, it shall write only the status and
      the sections its transition needs, and the validator shall give the
      same verdict for the same change made by hand; evidence: verb tests
      paired with hand-edit fixtures.
      Spec: R-34, R-35.
- [ ] AC-2 When a task is `blocked` without a Blocker naming reason, owner and
      revisit event, `cancelled` without a Closeout reason and scope
      disposition, or `complete` without an acceptance block, the validator
      shall fail on the pull request range; evidence: one failing fixture per
      missing element.
      Spec: R-26, R-30, R-80.
- [ ] AC-3 Reopening `complete` to `todo` shall need a reason and mark the old
      acceptance block superseded; a partial or stacked pull request shall
      leave the task open; evidence: transition tests.
      Spec: R-30, R-31.
- [ ] AC-4 Epic close shall need every task terminal, every epic criterion
      verified, journey criteria verified on the journey, and every consumed
      spec implemented in the candidate state (computed with the closing
      epic counted as complete) or listed as still consumed by another open
      consumer; an epic criterion served only by cancelled tasks is
      unverified; evidence: close-rule tests, including a spec whose last
      consumer is the closing epic.
      Spec: R-33.
- [ ] AC-5 `spec status` shall write only `approved` and `superseded`: draft
      to approved by a planning PR with no open question; approved to
      superseded only in a planning PR that adds a new spec listing
      `supersedes` and sets `superseded_by` on the old one, invalidating
      acceptance that cited the changed criteria; approved never returns to
      draft. `implemented` shall be computed (approved, every consumer
      terminal, at least one complete), a spec with no consumer or only
      cancelled consumers stays approved with the warning "no delivering
      consumer", and a hand-written `implemented` on a new spec is refused;
      evidence: tests for one final consumer, mixed complete and cancelled
      consumers, a superseding revision and a refused hand-written value.
      Spec: R-26, R-32, R-51, R-104.
- [ ] AC-6 New records shall list criteria as `- AC-n ...` without a
      checkbox, legacy checkbox records shall read as before, and the
      acceptance block parser shall accept the section 5.4 structure and
      reject malformed blocks without panicking; evidence: parser tests.
      Spec: R-50, R-54.
- [ ] AC-7 The rules shall apply from a recorded migration baseline and by
      transition: a spelling edit to an old complete task warns; reopening,
      changing criteria or completing again applies the new rules; a
      historical exception binds to the exact blob; identity, relationship
      and planning errors are never grandfathered; evidence: baseline tests.
      Spec: R-83.
- [ ] AC-8 `git.work_records` shall accept `block` or `warn` and refuse
      `off`; every existing adopter policy value, default-equal ones
      included, shall be preserved on update; a standard-tier project without
      records shall see no record rule; evidence: policy and update tests.
      Spec: R-80, R-81.
- [ ] AC-9 `validate` shall warn on stale words: a planning epic with
      complete tasks, `in_progress` with no active branch, an approved spec
      whose consumers are all accepted; no verb writes `in_progress`;
      evidence: warning fixtures.
      Spec: R-28, R-80.
- [ ] AC-10 The ledger work-graph event types with no producer shall be
      removed; evidence: the routing table and its tests.
      Spec: R-29.
- [ ] AC-11 (journey) On a fresh `codeflow init --full` project with the
      installed CLI, every section 4 transition, including partial and
      stacked pull requests, cancel and reopen, shall run through the verbs
      and through a hand edit with the same verdict; evidence: the section 10
      transition journeys.
      Spec: R-104.

## Execution contract

- Plan: Plan v6, from design v4 section 12. Size: large.
- Seats: responsible primary, executor and cross-lineage reviewer are
  assigned at dispatch under
  `cf-model-orchestrator/resources/capability-routing.md`; Plan v6 does not
  name them.
- Integration: `task/TSK-102-<slug>` from
  `integration/EPC-020-delivery-system` after `codeflow work start` passes,
  which needs SPC-013 approved and every predecessor complete.
- Verification selection: a targeted mutation run on the transition rules
  (state-transition logic whose wrong verdict is invisible in examples), and
  property tests for the acceptance block parser (untrusted input with a
  no-panic contract and a stable round-trip oracle).
- Recovery: records are Git-tracked text; a wrong transition is reverted by
  a reviewed edit.
- Closeout contract: capture bounded in-node discoveries only when they are
  review-relevant. A material graph, scope, interface, ownership, acceptance
  or safety change stops work and returns to both primary seats as Plan v7
  before implementation continues. Closeout cannot approve a deviation after
  the fact.
