# TSK-1433: A task's review is bound to the commit that lands, with no pull request

## Description

A task of a marked epic lands on its line with no pull request (ADR-0102), so its review must be checked from its record alone. Today, with no pull request body, part of the review check returns no finding (`crates/codeflow-cli/src/cmd/ci.rs:1145-1150` on `main` at `f8aabc62c`), and nothing ties the record's approving review to the commit the landing merge carries or to a reviewer of another lineage. This task makes `codeflow ci` refuse such a landing, on pre-push and later on the epic's pull request, with one verdict for both. Non-goal: changing how ranges on the pull request route are judged.

Landing on its target (`main`, alone, early):

- Reachable: the stricter check on a landing with no pull request.
- Inert: ranges on the pull request route are judged as today.
- Other lines: nothing.

Widened 2026-11-12 by the Director's ruling (relayed by coord/ci, about 02:00 EST), because the check as first planned ran on every epic line and read the builder's lineage from the plan:

- Scope: the check runs only on the line of an epic whose record carries the marker `whole-epic`, and is inert on every other line, so an unmarked line such as EPC-022's, or an adopter's, is judged as today. `codeflow ci` reads the marker once per run, only from the epic record at the default branch's tip (the authority rule of ADR-0091), never from the line, the pull request head or the working tree. A marker the run cannot read, or one with an unknown value, refuses with a message naming the field and the values it accepts.
- This task owns the marker read and the field's name and values. TSK-1437 proposed `main_landing` with the values `whole-epic` and `checkpoint-prs`, an absent field meaning `checkpoint-prs`; the builder uses that unless it finds it unclear and says which it chose. TSK-1437 keeps the template, `codeflow epic new`, the refusal of marker changes off the default branch and the gate on the line's pull request.
- Builder lineage: the record's `- Builder:` line is the plan and often names a fallback, so it cannot show who built. The acceptance block gains one additive field naming the lineage that built, with exactly one value (proposed `built_by`; the operator confirms the name). Absent on an unmarked epic, nothing changes. On a marked epic's line, a missing, empty or multi-valued field refuses. The check compares it with the reviewer named first in `review`, and no longer reads the `- Builder:` line.
- Reduced assurance: on a marked line, a reviewer of the builder's family passes only when the completion carries the recorded reduced-assurance statement (other families probed live and unavailable), in the form the rules and existing completions use.
- Limit: both values are written by the agents under review, so the check catches mistakes and drift, not a forged claim, and no doc calls it proof of independence. An unforgeable source of the builder's identity is a follow-up, filed as its own task if the builder names one.

## Outcome

After this merges, a maintainer can rely on `codeflow ci` to refuse a task landing with no pull request on a marked epic's line unless the task's record names an approving review by another lineage at the commit that lands, while every unmarked line is judged as before.

## Acceptance Criteria

- AC-1 Before any change, the builder shall record which paths with no pull request body already check the approved verdict (`ci.rs:1099-1112` and `record_text.rs:1706-1709` on `main` at `f8aabc62c`) and what is missing; evidence: a `## Findings` section with file:line.
- AC-2 When a landing with no pull request merges a task whose acceptance block names the merged commit and an approving reviewer of another lineage, `codeflow ci` shall pass it; evidence: a fixture.
- AC-3 `codeflow ci` shall refuse a landing with no pull request, naming the cause, when the record has no review row, when the review names another commit, when the reviewer is of the lineage the record names for the builder, and when the verdict does not approve; evidence: one fixture each.
- AC-4 `codeflow ci` shall give the same verdict for the same landing on pre-push and on the range of the epic's pull request into the default branch; evidence: one fixture run in both forms. (serves EPC-055 AC-1)
- AC-5 The change shall have a cross-lineage review with the `cf-security-reviewer` checklist, since it changes which landings are admitted; evidence: the review row and its findings. (serves EPC-055 AC-3)
- AC-6 (added 2026-11-12) The check shall run only on the line of an epic whose record at the default branch's tip carries the marker `whole-epic`, read once per run and never from the line, the pull request head or the working tree; on any other line `codeflow ci` shall judge a landing exactly as before this change, and a marker that cannot be read or has an unknown value shall refuse, naming the field and its accepted values; evidence: an unmarked line shaped like EPC-022 refused before and judged as today after, a marked line running the check, and a malformed or unreadable marker refusing.
- AC-7 (added 2026-11-12) On a marked epic's line, the check shall read the builder's lineage from one field of the acceptance block, compare it with the reviewer named first in `review`, and no longer read the `- Builder:` line; a missing, empty or multi-valued field shall refuse, and the field absent on an unmarked epic shall change nothing; evidence: a Codex build reviewed by Claude, recorded with a two-family `- Builder:` line, refused before and passing after, and one fixture each for a missing, empty and multi-valued field.
- AC-8 (added 2026-11-12) On a marked epic's line, a reviewer of the builder's family shall pass only when the completion carries the recorded reduced-assurance statement, and refuse without it; evidence: one fixture each.
- AC-9 (added 2026-11-12) The record's `## Findings`, the module doc and the pull request shall state that both values are written by the agents under review, so the check catches mistakes and drift, not a forged claim, and none shall call it proof of independence; the pull request shall list the field's name and the reduced-assurance form under open operator decisions; evidence: the diff and the body.
