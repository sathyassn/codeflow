# TSK-1433: A task's review is bound to the commit that lands, with no pull request

## Description

A task of a marked epic lands on its line with no pull request (ADR-0102), so its review must be checked from its record alone. Today, with no pull request body, part of the review check returns no finding (`crates/codeflow-cli/src/cmd/ci.rs:1145-1150` on `main` at `f8aabc62c`), and nothing ties the record's approving review to the commit the landing merge carries or to a reviewer of another lineage. This task makes `codeflow ci` refuse such a landing, on pre-push and later on the epic's pull request, with one verdict for both. Non-goal: changing how ranges on the pull request route are judged.

Landing on its target (`main`, alone, early):

- Reachable: the stricter check on a landing with no pull request.
- Inert: ranges on the pull request route are judged as today.
- Other lines: nothing.

Widened 2026-11-12 by the Director's ruling (relayed by coord/ci, about 02:00 EST), because the check as first planned ran on every epic line and read the builder's lineage from the plan:

- Scope: the check runs only on the line of an epic whose record carries the marker `whole-epic`, and is inert on every other line, so an unmarked line such as EPC-022's, or an adopter's, is judged as today. `codeflow ci` reads the marker once per run, only from the epic record at the default branch's tip (the authority rule of ADR-0091), never from the line, the pull request head or the working tree. A marker the run cannot read, or one with an unknown value, refuses with a message naming the field and the values it accepts.
- This task owns the marker read and the field's name and values. TSK-1437 proposed `main_landing` with the values `whole-epic` and `checkpoint-prs`, an absent field meaning `checkpoint-prs`; the builder uses that unless it finds it unclear and says which it chose. TSK-1437 keeps the template, `codeflow epic new`, the refusal of marker changes off the default branch and the gate on the line's pull request.
- Builder lineage: the record's `- Builder:` line is the plan and often names a fallback, so it cannot show who built. The acceptance block gains one additive field naming the lineage that built, with exactly one value (proposed `built_by`; the operator confirms the name). Absent on an unmarked epic, nothing changes. On a marked epic's line, a missing, empty or multi-valued field refuses. The check compares it with the reviewer named first in `review`, and no longer reads the `- Builder:` line.
- Reduced assurance: on a marked line, a reviewer of the builder's family passes only when the completion carries the recorded reduced-assurance statement (other families probed live and unavailable), in the form the rules and existing completions use.
- Limit: both values are written by the agents under review, so the check catches mistakes and drift, not a forged claim, and no doc calls it proof of independence. An unforgeable source of the builder's identity is a follow-up, filed as its own task if the builder names one.

## Outcome

After this merges, a maintainer can rely on `codeflow ci` to refuse a task landing with no pull request on a marked epic's line unless the task's record names an approving review by another lineage at the commit that lands, while every unmarked line is judged as before.

## Findings

Recorded before any change, on `main` at `63061d210`. `ci.rs`, `record_text.rs` and `acceptance.rs` are byte-identical to `f8aabc62c`, so the line numbers below are the record's.

A landing with no pull request reaches `codeflow ci` in two forms: the line's push, with no pull request body (the pre-push hand-off), and the epic's pull request from the line into `main`. A probe fixture landed a completed task on an epic line and ran both forms for each cause. The results:

| Cause | Line push | Epic PR | What refuses it |
|---|---|---|---|
| A valid completion, reviewed by another lineage | passes | passes | nothing |
| No review row: the task merged with no completion | refused | refused | the receiving-line rule, for product paths only |
| A review of another commit | refused | refused | the completion binding |
| A reviewer of the builder's lineage | passes | passes | nothing |
| A verdict that does not approve | refused | refused | the records rule |

What already checks a completion with no pull request body:

- `crates/codeflow-cli/src/cmd/ci.rs:1099-1111` runs `acceptance::dispatch` for every tracked range, with or without a body; `:1103` marks the pre-push hand-off. It binds each completion the range introduces (`crates/codeflow-core/src/workgraph/acceptance.rs:4254-4361`, calling `bind_completion_with_amendment` at `:4329`). `binding_source` (`acceptance.rs:1312-1366`) and `reviewed_span_problem` (`:1385`) require the block's `reviewed` commit to be the landed source head or its ancestor, with only the record's status and Closeout after it. A review of another commit is therefore refused in both forms.
- The approved verdict: `crates/codeflow-core/src/workgraph/record_text.rs:1706-1711` refuses any verdict other than `approved`. It is reached through `completion_problems` (`crates/codeflow-core/src/workgraph/lifecycle.rs:1372-1387`) and reported under `work.records` in both forms.
- No review row: `crates/codeflow-core/src/workgraph/acceptance/receiving_merges.rs:17-109` refuses adopter-facing paths that a merge brings onto an epic line outside every reviewed task head. A task merged with no completion is refused for its product paths. Work outside product paths passes, and the message does not name the missing review.
- An empty `review` field: the block parser refuses it (`record_text.rs:1477-1478`).

What is missing:

- Nothing reads who reviewed. Without a body, `tracked_review` returns at `ci.rs:1148-1150` (only a task pull request's class has a review task), so `review_row_check` (`ci.rs:1168-1233`) never runs. That function is also the only code that derives a reviewer seat from the block (`ci.rs:1201-1206`), and it uses the seat only to print the row.
- Nothing reads the builder. A completion reviewed by the builder's own lineage passes both forms.
- The shipped task template has no `## Execution contract` (`assets/base/pm/task.md.tmpl`, sections at lines 18, 26, 34, 67 and 84), so an adopter's record names no builder unless planning adds the line.

What this task adds: one check, read from the completion alone. It is built in the batch the Director ruled on 2026-11-12.

- Where it runs: only on the line of an epic whose record sets `main_landing: whole-epic` (the field and values TSK-1437 proposed; an absent field means `checkpoint-prs`). The marker is read once per run, at the first completion it governs, from the epic record at the default branch's commit. That commit is the one `--policy-from` names, which the pre-push hook and the hosted workflow set to the default branch's tip, else the default branch this clone resolves. The line, the pull request head and the working tree are never read for it. A marker the run cannot read, or one with another value, refuses with the field and the values it accepts. A line push whose clone cannot resolve the default branch, for example when `origin/HEAD` names a branch the clone has not fetched, is refused on any epic line, marked or not; fetch the default branch first. Every other line, an unmarked line included (EPC-022's shape), a task pull request and a push of its branch are judged as before.
- What it compares: two optional acceptance-block keys. `built_by` names the one lineage that built the task, as a lineage id of the model catalog built into the binary (`claude`, `codex` or `grok`). The reviewer is the `review` field's text before its first comma or semicolon. On a marked line a missing `built_by`, or one that is not exactly one lineage id, refuses; an empty one is refused by the block parser, as every empty key is. A reviewer of another lineage passes. A reviewer of the same lineage passes only with `reduced_assurance` in a fixed form: items separated by `;`, each exactly `<lineage id> probed unavailable` (the id exact, as `built_by` is) with no other word, with exactly one item for each other lineage and none for the builder's, for example `codex probed unavailable; grok probed unavailable`. Any other value refuses, naming the field, the form and the offending item. The value is still written by the agents under review: the form makes a careless, mistaken or contradicted statement refuse, such as one that only names the other lineages, leaves out the probe or adds `not probed`, but it requires the assertion and does not show that the probe took place. The plan's `- Builder:` line is not read: it is the plan, and it often names a fallback.
- No fixed form for the reduced-assurance statement existed. The rules (`.codeflow/rules/workflow-discipline.md:132-143` and `:300-309`) require it recorded, and completions write it as free text in `review`, so the key and its rule are new.
- What it is and is not: both keys are written by the agents under review, so the check catches a mistake or drift in what a completion says about its builder and reviewer. It does not catch a forged claim and is no proof of an independent review. It reads only the completion in the tree, never a verdict file or the path `review` cites. Checking a completion against its verdict file is the adopter's own landing process.
- An unforgeable source would be the commit author or committer identity the harness sets for each seat, or a seat record signed by the harness. Neither exists today. TSK-1469 is that follow-up ("A whole-epic line judges builder lineage from a source the builder cannot write"); it goes in this task's `follow_ups` when the task completes, and it is revisited when TSK-1433 lands on `main`.
