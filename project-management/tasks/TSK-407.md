# TSK-407: A link created earlier on a command line is refused like an existing link

## Description

Source: the security review of PR 239 (TSK-373) on 2026-10-18, severity medium, shipped in both guards. A link that already exists is followed and refuses, but a link created earlier on the same command line is not seen, because the guards judge the line before it runs and the link is not on disk yet. Reproduced on the line at `236e9d08b` with that tree's built hooks, the commands judged and never run: git-guard and exec-guard both allow `ln -s .claude/settings.json s2 && python3 tool.py s2`, `ln -s .claude/settings.json s2 && cp x s2` and `ln -s .claude/settings.json s2 && printf x > s2`, while exec-guard refuses `python3 tool.py .claude/settings.json`.

Decision: the residual is refused, not accepted. A link created earlier on the same line is part of the shell grammar the guards model (operator decision of 2026-10-15 on TSK-302's scope), so it is judged like an existing link. Decided by the primary on 2026-10-18 under the operator's direction of that day to decide from evidence (workspace `RELEASE-PLAN.md`, "Settled under it the same day", item 2).

Outcome: **a writer or interpreter that names a link created, or possibly created, earlier on the same command line gets the verdict it would get if the link already existed, and a link whose target the guard cannot resolve is refused.**

Rule: the guards model the filesystem state that earlier commands on the line produce, and resolve every later word through it.

- **Link-creating commands read:** `ln` (symbolic or hard, with `-s`, `-f`, `-n`, `-T` and `-t <dir>`), `link`, and `cp -s`, `cp -l`, `cp --symbolic-link` and `cp --link`.
- **Names and targets:** a link's name and target are resolved through TSK-406's expansion resolver (assignments, static substitutions, `PWD` and `HOME` as command-position state), so `L=l; ln -s .worktrees/<w> "$L"` creates `l`. This task owns expanded link names and targets and their propagation to later writers and interpreters; it reuses TSK-406's resolver and carries no second one.
- **Where the link lands:** a relative link name resolves from the command's working directory, never from an assigned `PWD` parameter (TSK-406 keeps the two apart): after `PWD=/private/tmp`, `ln -s .claude d` still creates `d` in the checkout. For the last operand, a real directory and a symbolic link to a directory are treated differently. A real directory receives the link inside it under the target's base name, with or without `-n` (`ln -sn ../.claude docs` creates `docs/.claude`, whose target resolves to `.claude`). A symbolic link to a directory is followed the same way without `-n` (`ln -s docs a && ln -sf ../.claude a` creates `docs/.claude`); with `-n` it is treated as a plain name, so `-f` replaces it (`ln -s docs a && ln -sfn .claude a` makes `a` point at `.claude`) and without `-f` the command fails. `-T` never treats the operand as a directory: it replaces a file or symbolic link with `-f`, and against a real directory the command fails, because a directory cannot be replaced by a link. A link command can fail after creating some of its links: with several targets each operand is linked in turn, and a later operand's failure does not remove the links already made (`ln -s ../.claude ../src docs`, with `docs/src` present, creates `docs/.claude` and then fails). So the guard keeps every possible filesystem effect of a link command, including the links of the operands that succeed when the command as a whole fails, for every later word reached through `&&`, `||`, `;`, a newline or any other separator. Only a failure known to happen before any change creates nothing (a single-target `-T` against a real directory, a destination directory that does not exist); where the guard cannot tell, it keeps all the possible states. The same holds for `ln -t <dir>`, `cp -s` and `cp -l` with several sources. `-t <dir>` places each target in `<dir>`.
- **What a symbolic link points at:** its target text is kept as written and resolved when a later word consumes it, relative to the link's own parent directory, not the command's directory (`ln -s ../.claude docs/l` points at `.claude`). Resolution walks component by component through the line's links and the disk, as the existing walk does for links on disk (`crates/codeflow-core/src/hooks/edit_guard.rs:490-513`). So a chain resolves through links created after the first one (`ln -s a b && ln -s .claude a`, then `b/settings.json` is `.claude/settings.json`). A hard link, `cp -l` or `link`, names the file its source resolves to when it is created.
- **Verdict:** a later writer or interpreter word that resolves to an enforcement path or a checkout root refuses with the rule the target itself gets: git-guard owns shell writers (redirects, `tee`, copy and move destinations, in-place editors, `rm`), exec-guard owns interpreter arguments and code. A word whose resolution meets a cycle, more links than the OS follows, an unresolved expansion or glob in a link's name or target, or a path under a link the guard cannot read refuses as cannot-verify. A word that resolves to an ordinary path keeps its ordinary verdict, so `ln -s src/app.py app.py && python3 app.py` passes.
- **Order:** "later" covers every list and pipeline separator (`&&`, `||`, `;`, `|`, `&`, newline), subshells, brace groups and command substitutions. Where a link may or may not exist (a link command on an `||` branch), every reachable state is judged. Filesystem changes made inside a subshell, brace group or command substitution persist for every later command; only the working directory and shell parameters are scoped, as TSK-406 defines.

The startup-file judgment already reads `ln` and `cp -s` or `cp -l` as link-creating commands (`crates/codeflow-core/src/security/startup.rs:2848-2867`, `copy_judgment`); this task reads the same commands for enforcement paths and checkout roots and carries the resulting state to the later words on the line.

The partial-failure behaviour was established by the Codex review of PR 255, round 3, with `/bin/ln` and GNU `ln` on a harmless temporary fixture (both returned 1 and left the first link in place); the hook verdicts below are judged strings, and no exploit was executed. Reproduced on the line at `236e9d08b` (Codex review of PR 255, rounds 1 and 3, and the drafter), payload cwd the main checkout, the commands judged and never run, both guards allowing each case through `cp -s` and the named owning guard allowing each partial-failure case (judged by Codex round 3; the `docs/src` condition held only in its native fixture, not in the checkout the hooks judged): `L=l; ln -s .worktrees/<w> "$L" && python3 tool.py l`; `ln -s a b && ln -s .claude a && printf x > b/settings.json`; `ln -s ../.claude docs/l && printf x > docs/l/settings.json`; `ln -s docs a && ln -sf ../.claude a && printf x > a/.claude/settings.json`; `ln -s docs a && ln -sfn .claude a && printf x > a/settings.json`; `ln -s .claude a && cp -s a b && printf x > b/settings.json`; `ln -s ../.claude ../src docs || printf x > docs/.claude/settings.json` and the same line with `;` (git-guard), and `ln -s ../.claude ../src docs || python3 tool.py docs/.claude/settings.json` (exec-guard). The ordinary controls `ln -s src/app.py app.py && python3 app.py`, `L=l; ln -s src/main.rs "$L" && python3 tool.py l`, `ln -s a b && ln -s src a && printf x > b/new.txt` and `ln -s ../src docs/l && printf x > docs/l/new.txt` pass today and must keep passing.

Non-goal: a link created by interpreter code (`os.symlink`, `fs.symlinkSync`) is runtime-built and stays the stated residual of the 2026-10-15 decision; the OS sandbox and the permission preset are the backstop. A link name or target written with a shell expansion is not that residual: it is in this task's scope.

Added by the second EPC-022 amendment of 2026-10-18.

## Acceptance Criteria

- AC-1 When a line runs `ln -s <enforcement path> <link>` before a writer or interpreter that names `<link>`, the guards shall refuse it as they refuse the enforcement path itself: `ln -s .claude/settings.json s2 && python3 tool.py s2`, `... && cp x s2`, `... && printf x > s2`, `... && tee s2`, `... && sed -i s/a/b/ s2`; evidence: one guard test per writer and per interpreter route, each failing before the change. (serves EPC-022 AC-97)
- AC-2 The same refusal shall hold for a hard link (`ln .claude/settings.json h`), `cp -s`, `cp -l`, `link`, `ln -sfn`, `ln -t <dir>`, a link to a directory followed by a write under it (`ln -s .claude d && printf x > d/settings.json`), a link to a checkout root followed by `rm -rf` through it (`ln -s .worktrees/<w> l && rm -rf l/`), each separator (`;`, `||`, `|`, `&`, a newline, a subshell and a brace group), and resolution through the line's state: a chain created in reverse order (`ln -s a b && ln -s .claude a && printf x > b/settings.json`), a target relative to the link's parent (`ln -s ../.claude docs/l && printf x > docs/l/settings.json`), a directory operand (`ln -s docs a && ln -sf ../.claude a && printf x > a/.claude/settings.json`), a replacement (`ln -s docs a && ln -sfn .claude a && printf x > a/settings.json`), `cp -s` of a line-made link (`ln -s .claude a && cp -s a b && printf x > b/settings.json`), `-n` with a real directory operand (`ln -sn ../.claude docs && printf x > docs/.claude/settings.json`, with `docs` an existing directory and `docs/.claude` absent) a link made after an assigned `PWD` (`PWD=/private/tmp; ln -s .claude d && printf x > d/settings.json`), and a link left by a failed multi-target command (`ln -s ../.claude ../src docs || printf x > docs/.claude/settings.json`, the same with `;`, and `ln -s ../.claude ../src docs || python3 tool.py docs/.claude/settings.json`, with `docs` and `docs/src` present and `docs/.claude` absent); writers by git-guard, interpreters by exec-guard; evidence: guard tests per form, the ten resolution cases failing before the change. (serves EPC-022 AC-97)
- AC-3 A later word whose resolution meets an unresolved link name or target (an unset or externally set variable, a non-static substitution, a glob), a cycle (`ln -s a b && ln -s b a && printf x > a/f`), more links than the OS follows, or a path under a link the guard cannot read shall be refused as cannot-verify with a message naming the link; evidence: guard tests per case. (serves EPC-022 AC-97)
- AC-4 Ordinary uses shall keep passing: `ln -s src/app.py app.py && python3 app.py`, `ln -sf build/out latest && cat latest/log.txt`, `ln -s ../shared lib && printf x > lib/a.txt` where `../shared` holds no enforcement path or checkout, the ordinary chain `ln -s a b && ln -s src a && printf x > b/new.txt`, the ordinary parent-relative target `ln -s ../src docs/l && printf x > docs/l/new.txt`, the expanded-name control `L=l; ln -s src/main.rs "$L" && python3 tool.py l`, `-n` into a real directory with an ordinary target (`ln -sn ../src docs && printf x > docs/src/new.txt`, `docs/src` absent), a `-T` command that fails against a real directory (`ln -sfT ../.claude docs; printf x > docs/new.txt`), a failed multi-target command with an ordinary surviving link (`ln -s ../lib ../src docs || printf x > docs/lib/new.txt`, with `docs/src` present and `lib` holding no enforcement path or checkout), an ordinary link after an assigned `PWD` (`PWD=/private/tmp; ln -s src d && printf x > d/new.txt`), and a link created with no later writer or interpreter; an existing link to an enforcement path shall keep refusing; evidence: guard tests.
- AC-5 `docs/policy-reference.md` shall state the same-line link rule, the link-creating commands it reads, and the runtime-built link residual with its sandbox backstop; evidence: the doc text.
- AC-6 (journey) With the installed build, an agent session in a scratch adopter project shall be refused each planted line of AC-1 to AC-3 and AC-7 and shall run the ordinary forms of AC-4; evidence: the journey output.
- AC-7 A link whose name or target is written with a shell expansion shall be judged through TSK-406's resolver and carried to later words: `L=l; ln -s .worktrees/<w> "$L" && python3 tool.py l` shall be refused by exec-guard and `T=.claude; ln -s "$T" d && printf x > d/settings.json` by git-guard; `ln -s .claude "$(printf %s d)" && printf x > d/settings.json`, which git-guard already refuses because `ln` names `.claude`, keeps refusing; `L=l; ln -s src/main.rs "$L" && python3 tool.py l` passes; evidence: guard tests, the first two refusals failing before the change and the static-substitution name as a preservation case. (serves EPC-022 AC-97)
