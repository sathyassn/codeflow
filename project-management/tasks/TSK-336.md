# TSK-336: Hosted policy verdicts have trusted authority and limited credential exposure

## Description

Issues: #204 and #202. These share the hosted workflow trust boundary, although credential persistence and check-name reuse are separate mechanisms. One workflow-hardening unit can cover both.

`assets/base/ci/codeflow-policy.yml:57` fixes the job name to `commit standards`; `:71` checks out the PR base SHA; `:74` installs the target-pinned binary. `:219` runs CI only on PR events while `:238` runs the registry check under the same job name on other events. No inspected step classifies the base's protection before selecting the required name. Current automation profiles come from the judging policy in `crates/codeflow-cli/src/cmd/ci.rs:1687`; the older `target_profiles` function named by the issue is not present in `ci/adopter.rs` at this revision.

The five shipped checkout steps lack `persist-credentials: false`: `codeflow-ci.yml:49`, `:197`, `:333`, `:795` and `codeflow-policy.yml:69`. Workflow permissions are read-only (`codeflow-ci.yml:36`, `codeflow-policy.yml:62`). This constrains the token's impact but does not justify handing it to later code.

Also owned here: SEC-03 from the confirm review of PR 231 (TSK-292) on 2026-10-18. A pull request's secret scan runs the head's own copy of the workflow, so the head can change the scan that judges it. It shares this task's workflow trust boundary: the scan, like the policy verdict, must come from trusted authority (AC-1). Named here by the amendment of 2026-10-18 so its owner is findable.

Outcome: **Only a fully checked range judged by trusted authority can produce the required policy verdict, and later repository code receives no persisted checkout token.**

Source inspection is from the accepted triage at `c5c6f6f671d2bf67a77113c656b3be446fb0bea1`; runtime reproductions remain implementation evidence.

## Acceptance Criteria

- AC-1 Establish authority from the default branch's trusted configuration. Protected integration/release targets remain usable. An unprotected target, a lookalike nested branch, or an unverifiable base cannot emit an authoritative success under the required name.
- AC-2 Push/dispatch jobs that run only registry checks use a distinct check name or run the full required policy contract. A protected ref alone is insufficient to make an ids-only run equivalent to commit standards.
- AC-3 In a fixture repository, test a malformed head against main, a weak unprotected target, retargeting, dispatch, and a protected integration target. Query main's actual merge/check state. Record whether the pre-fix check-name collision can satisfy the requirement; do not infer that from the visible green job alone.
- AC-4 Every shipped checkout disables credential persistence. Later private-repository fetches still work through an explicitly scoped authentication mechanism that is not left available to repository code.
- AC-5 (journey) A fresh and an updated adopter run the resulting workflows. Template tests cover every checkout and event class, and hosted evidence proves both valid integration PRs and the negative cases.
