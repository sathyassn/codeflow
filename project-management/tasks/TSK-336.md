# TSK-336: Policy and release verdicts run only the default branch's code

## Description

Issues: #204 and #202. These share the hosted workflow trust boundary, although credential persistence and check-name reuse are separate mechanisms. One workflow-hardening unit can cover both.

`assets/base/ci/codeflow-policy.yml:57` fixes the job name to `commit standards`; `:71` checks out the PR base SHA; `:74` installs the target-pinned binary. `:219` runs CI only on PR events while `:238` runs the registry check under the same job name on other events. No inspected step classifies the base's protection before selecting the required name. Current automation profiles come from the judging policy in `crates/codeflow-cli/src/cmd/ci.rs:1687`; the older `target_profiles` function named by the issue is not present in `ci/adopter.rs` at this revision.

The five shipped checkout steps lack `persist-credentials: false`: `codeflow-ci.yml:49`, `:197`, `:333`, `:795` and `codeflow-policy.yml:69`. Workflow permissions are read-only (`codeflow-ci.yml:36`, `codeflow-policy.yml:62`). This constrains the token's impact but does not justify handing it to later code.

Also owned here: SEC-03 from the confirm review of PR 231 (TSK-292) on 2026-10-18. A pull request's secret scan runs the head's own copy of the workflow, so the head can change the scan that judges it. It shares this task's workflow trust boundary: the scan, like the policy verdict, must come from trusted authority (AC-1). Named here by the amendment of 2026-10-18, with acceptance in AC-6. The same amendment gives this task SEC-06 (AC-7) and SEC-07 (AC-8) from the PR 231 follow-ups. SEC-05 (low: legacy-fingerprint advice still covers a clean two-parent merge amended to add content) is advice only and suppresses no finding; disposition: tracked once here, revisit when this task edits the legacy-fingerprint advice, where the fix is to require a remerge CONFLICT header naming the path.

Outcome: **Only a fully checked range judged by trusted authority can produce the required policy verdict, and later repository code receives no persisted checkout token.**

Source inspection is from the accepted triage at `c5c6f6f671d2bf67a77113c656b3be446fb0bea1`; runtime reproductions remain implementation evidence.

The design in short:

- Verdict jobs in the policy workflow (`pull_request_target`, the default
  branch's file) run for every pull request whatever its target, never
  reference the environment, and are named `trusted: commit standards`,
  `trusted: secret scan` and, in this repository, `trusted: release
  impact`. The head-run `secret scan` job and this repository's head-built
  `release impact` job are removed in the same change, and registry-only
  runs get their own name, so the old names have no producer.
- One authority job, only for `pull_request_target` into the default
  branch, is the only job that references `environment:
  codeflow-authority`; it mints an App installation token inside the one
  step that creates the `authority: commit standards`, `authority: secret
  scan` and `authority: release impact` check runs on the head SHA.
  Ruleset B (TSK-1080) pins those names to the App's id. Without the App
  (Mode B, the floor), the final step lists check runs and statuses of the
  trusted names and fails closed.
- Pull requests into lines get no App check; ruleset C (TSK-1080, strict)
  requires the `trusted:` names pinned to 15368.
- Enablement order: this task reaches `main` through the line's reviewed
  pull request under today's rules; from that merge until the operator
  runs `remote protect` and retires rulesets 24379074 and 25435656, every
  pull request into `main` and the lines is unmergeable (fail closed, by
  design). The operator's Mode A steps are listed in TSK-1080.

both names are also required directly and pinned only to the Actions

adds refusals there. The design above still has the trusted and
authority verdicts call `admit`, so it does not close this alone.

AC-14 closes it with the standard split between trusted CI definition
and untrusted code under test. The gates verdict that admission reads
comes from the default branch's `codeflow-ci.yml` at the authority SHA
(AC-1), with the scripts and configuration that decide which tests run
and how a job concludes (the set AC-13's Findings names, such as the
partition and reuse scripts) read from that SHA too. The head's code,
Rust and scaffold included, is the candidate those jobs build and test,
as `codeflow-ci.yml:110-127` builds it today, so an ordinary product
change is still admitted. The run gets a read-only token and no secret
or environment, since it executes head code. A head's own copy of the
workflow or of those inputs never decides admission, and neither does a
line's copy: equality with an integration base is not authority. A pull
request that changes the workflow or those inputs is judged by the
default branch's copy and reaches `main` by the operator's merge (Mode
A), as AC-11 already states for the policy workflow.
