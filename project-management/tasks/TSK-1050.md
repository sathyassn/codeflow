# TSK-1050: The guard opens each repository once per hook call

## Description

Exec-guard judges every literal word of interpreter code from every
directory the line may run in, and each judgement asks which repositories
own the target (`target_roots` in `crates/codeflow-core/src/hooks/repo.rs`).
That lookup is cached per target, but every new target opens the owning
repository again through `repo::open` (git2 discovery plus the registration
cross-checks), although the owner is the same checkout every time. A line of
nested shells (`bash <<< ...`, `bash <(...)`, `... | bash`, `source <(...)`)
therefore opens the session's repository once per word and directory: about
18 opens per word on the process-substitution route. This made the hosted
test `shell_expansion_chains_have_bounded_guard_time` fail four times since
2026-10-27 (runs 40502828576, 40514843291, 40656684463, 40661610177), always
on the process route at N=80. This task keeps each owner's successful
reading for the `RepoFactsScope` that one guard evaluation already uses,
and reuses it only where it cannot weaken a verdict. A target the owner
could enforce through always opens the owner again, so a broken owner
still refuses it. A failed open is never kept, so a mended owner is seen.
A kept reading may keep an owner in a target's list but never remove one
as a duplicate; when it would, every owner is read again. Every caller
refuses if any owner protects the target, so an owner kept in the list can
only add a refusal. It also reads once per line, for one guard
evaluation, whether a line names `RIPGREP_CONFIG_PATH` in git-guard
(`preprocessor_write_violation` and `line_without_patterns`), which read
the whole line again for every segment; PR 346 fixes the same pattern on
its own paths. Non-goals: the secret-glob regex cache (PR 346, TSK-1002),
the per-segment ripgrep configuration reads on the exec-guard paths PR 346
changes, and any change to the timing test's bound.

## Outcome

After this merges, agents and CI runs can have exec-guard judge long lines
of nested shells with one repository open per owner for ordinary words,
instead of one per word and directory: the process-substitution route takes
about 30% less time in a release build (3.81 s to 2.63 s at 160 chained
shells), and the other routes change little. The guard-time test's flake is
not removed by this task alone: it also needs the regex cache in PR 346
(TSK-1002), which is most of that test's cost in debug and coverage
builds.

## Deliverables

- the per-root open cache and its scope wiring: `crates/codeflow-core/src/hooks/repo.rs`, `crates/codeflow-core/src/hooks/edit_guard.rs`
- the open-count and fail-closed tests: `crates/codeflow-core/src/hooks/repo.rs`
- the per-line ripgrep configuration memo and its read-count test: `crates/codeflow-core/src/hooks/git_guard.rs`
- the verdict and timing comparison scripts: `scripts/proofs/guard-repo-opens/`
- the release note: `changelog.d/TSK-1050.md`

## Acceptance Criteria

- AC-1 Before the fix is made, the slow exec-guard routes shall be investigated and recorded: the hosted failures of the guard-time test, the code paths that dominate exec-guard time on nested-shell lines, which of them this task owns and which open work already covers. Evidence: the PR body's investigation section, with the profile, the hosted runs and the open PRs named.
- AC-2 When one guard evaluation looks up the owners of many ordinary targets in one repository, the system shall open each discovered owner once per `RepoFactsScope`, shall open it again in a new scope, and shall not keep a reading outside a scope; two distinct owners shall each keep their own reading. Evidence: a build-count test like `PROTECTED_BUILDS` that fails before the change and passes after, and a two-owner test.
- AC-3 When an owner cannot be opened, or breaks or is mended during the scope, every lookup of a target the owner could enforce through shall return what a fresh reading returns, a failed open shall not be kept, and no kept reading shall remove an owner from a target's list; with stable repositories every guard verdict shall be unchanged. Evidence: tests that break and mend an owner mid-scope in both lookup orders with unseen targets, that replace a linked worktree mid-scope, and that read a broken owner for unseen targets, each failing at 76dbd6b41; the `hooks_cli` guard suites and the core `security` and `hooks` tests passing.
- AC-4 When exec-guard judges the nested-shell routes (here-string, process substitution, pipe, source) at N=20, 40, 80 and 160, the time before and after the change shall be recorded for debug and release builds, with the guard-time test's own output. Evidence: the PR body's timing table, bound to each binary's `codeflow --version` identity and sha256, from clean builds of the line tip and the final head, with `scripts/proofs/guard-repo-opens/timing.py`.
- AC-5 When the change is released, the changelog shall carry a patch-impact entry that says the guard opens each repository once per hook call and that no verdict changes. Evidence: `changelog.d/TSK-1050.md`.
- AC-6 When the real hooks `codeflow hook exec-guard` and `codeflow hook git-guard` judge allowed and refused commands with a JSON payload, as a harness runs them, including nested-shell lines and enforcement, worktree and secret paths, the fixed binary shall give the same exit code and message as the line tip's binary. Evidence: `scripts/proofs/guard-repo-opens/verdicts.py` run on clean builds of the line tip and the final head, with both binaries' identities and the per-case verdicts attached to the PR. (journey)
- AC-7 When git-guard judges a line of many segments, it shall read whether the line names `RIPGREP_CONFIG_PATH` once per line text for one guard evaluation, not once per segment, with the same verdicts. Evidence: a read-count test of a 40-segment line that fails before the change (40 reads) and passes after (1 read).
