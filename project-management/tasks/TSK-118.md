# TSK-118: present entity targets and figure framing

## Description

Node B of the present review parity package (Plan v5). Today the picker
admits `svg` but not its parts, hover and capture climb to the enclosing
`svg`, an unlabelled shape shows its tag name, authors cannot name targets,
and an element note orphans whenever its block digest changes (proposal
section 1). Figures carry no required visible title or explanation. This
task builds, to SPC-014: one resolver for hover, click, keyboard, touch and
saved anchors that resolves to semantic entities; entity ids from figure
declarations and from the closed vocabulary in hand-written `html` stage
SVG; anchors bound to the revision and validated by the server; the
re-anchor order with changed and orphaned states; and runtime-owned framing
for the `figure` block, the `html` stage used as a figure, and the table
(proposal sections 3.1, 3.2 and 3.7). From TSK-071 it takes the figure and
`html` stage element cells of the annotation matrix, QA defect 5 in its
figure form, and the figure-part clicks of QA defect 6; defect 6's
code-line, diff-line and diff-whitespace cases stay with TSK-071. Inputs,
durable in the workspace `design/present-parity/inputs/` (workspace commit
`73faec2`): the QA report `present-qa-report.md`, its matrix
`block-gesture-matrix.tsv`, and the operator's delivery review document
`delivery-review-document.json` with its build script
`delivery-review-build.py`. Non-goals: forms and answers (TSK-119), delivery
(TSK-120), replies and diff (TSK-121).

## Acceptance Criteria

- [ ] Given a committed fixture built from `delivery-review-document.json`
      (the operator's delivery-system document: six `html` stages at
      revision 5, one with a hand-written figcaption) with one stage
      migrated to a `figure` block, when the
      real-browser suite targets a rectangle, a thin arrow, a label inside a
      group and a node's sibling label (`data-cf-for`), each selects the
      intended entity by mouse, keyboard (including "select enclosing") and
      touch, in light and dark, and the chip and rail show the entity label;
      evidence: the suite output per target, gesture and theme (proposal
      4.2 row B, 3.1).
- [ ] The resolver follows SPC-014's precedence (selected text, `data-cf-for`
      label, innermost semantic group, visible shape, block, region on
      request), excludes chrome, `defs` and markers, and pads thin strokes
      by distance to the segment so neither drawn nor hand-written SVG needs
      hit strokes; evidence: selection browser cases per rule.
- [ ] Entity ids are stable across regeneration: a declaration re-emitted in
      a different draw order yields the same ids, and hand-written SVG uses
      only the closed vocabulary, which Rust validates and refuses outside
      it; evidence: crate tests and a property test over declaration order.
- [ ] When an entity anchor is submitted, the service accepts it only if the
      entity id exists in that block at that revision, stores the label the
      server resolved (a differing client label is refused) and the crop
      lies inside the entity bounds within the SPC-014 tolerance; a forged
      entity id and a crop outside the entity are refused with typed errors;
      evidence: service tests on the TSK-117 fixtures (3.1).
- [ ] Every element note on a figure entity carries a PNG crop whose pixel
      bounds match the selected entity's bounds, widened only by the
      thin-stroke padding SPC-014 defines, at the capture scale within 2 px,
      and whose content is not a single colour; this is the crop rule TSK-071
      applies to the other blocks; evidence: the suite asserts the returned
      PNG for each migrated element cell, including a scale conversion case,
      with wrong-size and blank-crop negative controls; the server's
      containment check above stays a separate security check (Codex R3, plan
      review round 1).
- [ ] When `present update` produces a new revision, notes re-anchor by
      entity id, then quote, then block, then document, and a note that
      moved or lost its target is shown changed or orphaned, never dropped
      or silently re-attached; evidence: re-anchor and orphan controls in
      crate tests and the suite (section 2 last row, 3.1).
- [ ] Every figure shows its title as "Figure N · title" (a kicker is an
      optional qualifier after it), a caption with the takeaway, a legend
      when marks encode meaning and one Details disclosure holding the
      description and the data-table twin; an `html` stage used as a figure
      gets the same runtime framing; a v2 table requires a title and allows
      a caption; numbering follows document order through nested, collapsed
      and tabbed blocks and `[fig:<id>]` resolves; the title is visible in
      the live session, history and export; evidence: render tests, browser
      cases in live, history and export (3.2).
- [ ] The drawn-figure gate fails a figure whose title text is not visible
      in the DOM, with a failing fixture a compliant page cannot mask;
      evidence: the gate test (3.2).
- [ ] The Rust reconstruction and the shared figure module stay byte-equal
      after the framing and entity changes: the paired rendered fixtures are
      regenerated from the module and pass both the module's tests and the
      reconstruction's tests, their starter copies and pristine hashes match,
      and `validate --portal` passes on both guides at the task head; a
      tampered title and a tampered entity output in a rendered companion each
      fail `validate --portal`, so updating the pins cannot weaken the
      canonical comparison; evidence: the JS and Rust parity tests, the two
      tamper controls and the `validate --portal` output for both guides
      (Codex R4, plan review round 1).
- [ ] This task rebases on whatever TSK-061 and TSK-063 have landed before
      it lands, and every figure they authored passes the visible-title
      rule on the rebased head; one that fails returns to its owning task
      or is fixed here with its owner's agreement; evidence: the portal
      `browser:verify` run on the rebased head for both guides.
- [ ] A v1 document renders as before and a v1 session stays readable, per
      the SPC-014 compatibility table; evidence: the v1 fixtures pass.
- [ ] QA defect 5 (in its figure form, since TSK-087 removed the Mermaid
      block) and the figure-part clicks of defect 6
      (`present-qa-report.md`, 2026-09-22) are fixed with a reproducing
      fixture each, or dispositioned with a reason in the closeout;
      evidence: the defect table with fixture names.
- [ ] `npm run check`, the browser checks, `cargo test -p codeflow-present`
      and `cargo test -p codeflow-cli --test present_cli` are green, the
      present checksum matches a clean rebuild, the skill mirrors and hashes
      pass the manifest test; the design primary reviews the framing and
      targeting rendered in three skins, two modes and two widths; evidence:
      recorded output with the head SHA and the review record.
