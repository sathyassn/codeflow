# TSK-171: permission presets from one action table

Unit 1 of 5 of the harness permissions work, TSK-171 to TSK-175 (decision record:
`ADR-0075`; design: `docs/verification/permission-presets-design-2026-09-28.md`). TSK-172 reads
this unit's policy keys and merges after it; the two can be drafted and
reviewed in parallel and ship in the same release as separate pull requests.
TSK-175's D1 spike uses this unit's `cf-builder` profile.

## Description

The shipped Claude preset carries 161 ask rules. Ask rules prompt in every
Claude mode, including the production modes ADR-0055 sets, so delegated and
primary sessions stall. The Codex and Grok presets carry their own
hand-written lists, which drift from Claude's.

This unit replaces the ask rules with deny rules generated from one action
table, for all three harnesses, and teaches `codeflow update` to carry the
change to existing adopters without losing their own choices. After it,
agent sessions meet no prompt except Claude's critical-path countdown:
publishing, releases, tag pushes, gists, privilege launchers, account and
credential commands, keychain reads and user-level persistence are refused;
the operator performs them. The guards that catch spellings the text rules
cannot express are TSK-172.

Non-goals: the guard checks (TSK-172); hook wiring and fail-closed commands
(TSK-173); the unsandboxed retry (TSK-174); launch postures (TSK-175); the
operator's user settings, which are never written.

## Acceptance Criteria

- AC-1 No shipped Claude preset shall carry an `ask` array, and no deny rule
  shall match `rm -rf /tmp/x`, `rm -rf ~/scratch/x`, `gh release view v1`,
  `gh secret list`, `crontab -l`, `git branch -d topic`, `cargo test`, `npm
  run build`, `gh pr create --draft`, `cargo +nightly test --features
  publish` or `npm --prefix x run publish-docs`; evidence: `settings_presets`
  tests with the documented matcher.
- AC-2 Every shipped Claude preset shall deny each family of the action
  table, including `gh auth switch`, `gh auth login` and `gh auth setup-git`;
  carry an `Edit(...)` deny for each enforcement path; list the `!`
  carve-outs after the read denies they narrow; and carry no `Write(...)`
  path rule; evidence: tests per family and an order test.
- AC-3 The read denies shall leave `~/.claude/projects/<p>/memory/**`,
  `.env.example` and a file named `secret_scan.rs` readable by the file tools
  and keep transcripts, `.env` and `*.pem` denied; the sandbox shall deny the
  listed credential variables and stores; evidence: tests. Whether the
  sandbox honors the carve-outs for a shell `cat` is recorded by TSK-175.
- AC-4 When a Claude permission pattern from the preset is read with Grok's
  matching (prefix without word boundary, or glob), it shall not refuse any
  AC-1 command; evidence: a Grok-semantics matcher test.
- AC-5 The Claude arrays, the delegate fragment and the Codex rules shall be
  generated from the one table; a test shall fail when a family has no entry
  and no stated reason for a harness; every Codex `match` and `not_match`
  example shall pass `codex execpolicy check`; every shipped JSON and TOML
  asset shall parse; the Grok `cf-guard-worktree` profile's `deny` and
  `read_only` lists shall equal `cf-guard`'s plus its two additions;
  evidence: parity test, check output, parse test.
- AC-6 The manifest shall list `.codex/rules/codeflow.rules` and
  `.grok/sandbox.toml` in the minimal tier array; `.grok/sandbox.toml` shall
  be installed only when absent; evidence: a manifest assertion and scaffold
  tests.
- AC-7 (journey) When `codeflow update` runs, it shall merge permission
  arrays three ways against the prior baseline (an entry retired from the
  preset is removed, an entry the adopter removed stays removed and is
  reported, an adopter-only entry stays, a new entry is added), and it shall
  move a policy scalar equal to the prior shipped baseline to the new
  default and report it, keeping a value that differs; a second run shall
  change nothing; an adopter's own deny entry, command or file read, shall
  still take effect after the update, with and without a prior baseline;
  evidence: the `permission_presets_update` merge tests from representative
  2.x baselines, an absent baseline, an adopter who removed the `sudo` deny
  and set `privilege_escalation: warn`, and an adopter at the old
  `headless_peer_runs: warn` default; `repository_update_noop`; and the
  upgrade journey through the installed CLI below.

  Setup: three projects made by `codeflow init --minimal`, each planted
  with the 2.1.0 fixtures of the unit suite
  (`crates/codeflow-core/tests/fixtures/presets-2.1.0/`: the Claude preset
  and the policy) as the project files and their `.codeflow/.baseline/`
  copies. The ordinary project adds nothing. The two adopter projects add
  the adopter's own denies `Bash(terraform apply *)`,
  `Read(**/.env.example)` and `Read(**/team-secret.py)`, which overlap the
  shipped carve-outs; one keeps the settings baseline and one has it
  deleted. `codeflow update` then runs twice in each.

  Effective rules are judged on the updated settings: commands by the AC-1
  matcher, and file reads by Claude's documented semantics for ordered
  `Read` denies and `!` carve-outs, as the AC-3 tests evaluate them. The
  presence of an entry in an array is not evidence of effect. After each
  update:
  - with a baseline, every shipped `ask` entry is retired, and
    `security.privilege_escalation` moves from the 2.1.0 `warn` to `block`;
    the retired entries and the moved default are reported;
  - in every project, every deny of the new preset is present;
  - in both adopter projects, `terraform apply -auto-approve` is refused
    and reading `.env.example` and `team-secret.py` is denied;
  - in the ordinary project, reading `.env.secret.py` and
    `.env.credentials.ts` is denied, and `secret_scan.rs` and
    `.env.example` stay readable;
  - the second `codeflow update` changes no file, and `codeflow validate`
    is clean.
- AC-8 The release note skeleton shall name the order (upgrade the binary,
  then `codeflow update`), the refused actions and the relief for each
  (remove the deny entry from the project file, or set the policy level;
  both kept by update; a local ask rule cannot restore a denied action), and
  that route D9 A narrows credential exposure only on a host that carries the
  agent token alone, and the operator's login stays on this host for setup
  and workflow pushes, so the token narrows what agents use by default and
  does not stop a deliberate read of a stored login outside the refused
  forms; that agent sessions replace `git pull` with `git fetch`
  then a checked `git merge --ff-only` or `git rebase`, while a human
  terminal is unaffected; that `codeflow update`, `init` or the first
  `baseline approve` binds the root, with a binding-only confirmation for an
  identity already approved on the machine; and that an outer workspace
  takes one `codeflow baseline bind --inventory` for its nested
  repositories; and that a local landing that changes an enforcement path
  waits for the operator's `codeflow baseline approve --merge <source>
  --into <target>`, bound to the source and target commits and the method,
  while an agent's `gh pr merge` passes only immediately and only when no
  commit on the pull request changes an enforcement path, auto-merge and
  merge queues being the operator's; and the D7 to D9 changes as decided on
  2026-09-28: seats briefed only through `herdr agent prompt`, folder
  trust granted at launch, Escape the only key, `/compact`, `/clear` and
  `/new` the only slash commands; guard hooks that fail closed at every
  tier with no fail-open switch, a session-start line naming the outdated
  side and its exact command, and the options (update, continue other work,
  roll back the binary); agents on their own fine-grained token in
  `GH_TOKEN`, workflow pushes queued for the operator; and the
  operator-actions list, where it lives and where it is shown; evidence:
  the note.
- AC-9 (Codex profile assets, before TSK-175's D1 spike) The shipped
  `.codex/config.toml` shall keep `default_permissions = "cf-guard"` with the
  network proxy on, the secret denies of `docs/verification/evidence/permission-presets/codex/config.toml` and
  the enforcement-plane `read` entries, and shall define `cf-builder`
  (extends `cf-guard`, `.git` write with `.git/hooks` and `.git/config`
  read, local binding on) without selecting it; `codeflow update` shall carry
  the change to an adopter's copy through the managed three-way merge and
  keep the adopter's own keys; the tested floor for permission profiles and
  the proxy shall be recorded as Codex 0.157.1, the version they were
  qualified on (the design record, revision 4, section 9; kept with the review record), with earlier versions marked
  unqualified rather than unsupported; evidence: a parse test, merge tests,
  and a recorded launch of the tested Codex version selecting each profile
  (`-c default_permissions="cf-builder"` for the builder) without a config
  error. Whether `cf-builder` works end to end is TSK-175's D1 spike, not this
  criterion.
