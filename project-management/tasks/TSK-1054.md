# TSK-1054: A qualification record attests what a host can contain

## Description

This is a planning draft accepted from the TSK-397 design note, revision 4.1, Part C (pull request 331), where it is unit U1 (qualification record and ceremony). The note called the unit 3.3.0; the release is 4.1.0. Part C is accepted as planning drafts only: the criteria below are drafts, and this unit takes its own whole-unit review when it is built. Part C decisions (i) to (v) apply: (i) explicit non-secret enforcement-file arguments are allowed on a qualified host under attested `W-enforcement`, and the secret-read classes override, never a file name; (ii) a patch update invalidates a record, because exact executable digests bind it and a changed binary is `Unknown` until the operator re-runs the ceremony; (iii) managed settings are a design requirement for qualification, not a vendor fact; (iv) no exclusion matcher ever, so a non-empty `excludedCommands` disqualifies and route A+ is dropped; (v) the ceremony runs through the Bash tool, never the `!` prompt, and its evidence is receipts, not operator attention.

An administrator-protected record, written only by `sudo codeflow doctor --qualify --confirm`, attests which capabilities one execution context has. It is the evidence that lets later units (TSK-1055) relax a text rule, because the record says what the host contains. The record is root-owned and lives in the managed-settings location pattern for each platform: `/Library/Application Support/CodeFlow/qualification/`, `/etc/codeflow/qualification/` and `%ProgramData%\CodeFlow\qualification\`.

Edges: this unit depends on three tasks. TSK-397: its H-5 change denies `~/.codeflow/authority/` in 3.2.0 and so protects the receipts that criterion AC-2 writes there. TSK-1056 (U3): qualification is sound only under the independently enforced managed policy that unit pins, and its doctor check (AC-2 there) refuses the ceremony without the managed file. TSK-1060 (U7): the design note requires the Codex requirements file to have landed before any Codex record is attested. Each is an edge because a prerequisite of one criterion still decides whether the whole task can be accepted; the work may start early from a predecessor's exact reviewed head. AC-5 stays as the behavioral check that the Codex evidence is consumed. TSK-1052 (writes followed by a run of the written file, refused where containment is unknown) and TSK-1053 (runner grammars) are planned in PR 390. A qualification record can only add attested capabilities to them, never remove a refusal they make where containment is unknown.

Non-goals: a containment fallback when `W-common-git` is unattested; a ceremony route through the `!` prompt; a Grok route.

## Outcome

after this merges, an administrator can run one ceremony that records which capabilities a Claude Code host has, and every later relaxation can read that record instead of trusting a claim.

## Acceptance Criteria

- AC-1 When a record is read, its binding digest shall cover the harness and exact executable digests (the harness entry file and `codeflow` by `current_exe`), the platform and backend, the canonical session roots and common git dir, every readable settings layer, the harness process argv read through the hook's parent chain (terminal launch only until verified per launcher; unreadable is `Unknown`) and the qualification-policy schema version, and any mismatch, a patch update included, shall read as `Unknown`; evidence: unit tests that change each input in turn.
- AC-2 The ceremony shall run through the Bash tool driven by the session at the operator's request, never the `!` prompt, which is unsandboxed and excluded. `--confirm` shall attest a capability only on authenticated evidence, written through a trusted execution identity (the harness-run guard, never the session's own writes) under `~/.codeflow/authority/receipts/`, that the intended protected operation reached the sandbox: a receipt bound to the ceremony id, a fresh nonce for the probe and the exact executable digests, recording the command text as executed, the resolved executable path and digest, and the sandbox outcome (the operation ran and was denied by the sandbox), not the guard's judgement of the text alone; with a changed positive control, and readable and writable controls outside the sandbox showing that the denial is the sandbox's and not a permission error. A guard refusal, a cancelled or timed-out command, a substituted or shadowed executable (the command resolved to another path or digest than expected), a replayed receipt (an earlier ceremony id or nonce) and missing execution evidence shall each leave the capability unattested, as shall an unread secret nonce; evidence: a ceremony journey on a scratch host and one negative test for each of these six cases.
- AC-3 From a linked-worktree session, writes to the resolved canonical `<common>/hooks`, `<common>/config` and `<common>/worktrees/*/config.worktree` shall be denied by absolute entries generated into the main checkout's `.claude/settings.local.json` (merged, never overwritten, by an operator-run `codeflow update`), with a positive control; otherwise `W-common-git` shall be unattested and no containment fallback shall exist; evidence: a linked-worktree journey and a merge-not-overwrite test. (the design note's AC-7)
- AC-4 A valid record shall yield `Unknown` after each of: a changed settings layer, a `--settings` or `--add-dir` launch, a different project or common dir, a replaced binary, and a forged record under the state root or with the hook's uid; evidence: one test per case. (the design note's AC-8)
- AC-5 Codex qualification shall need its hook execution context verified and TSK-1060 (U7) landed with the requirements file shown effective in the seat's launch, and Grok shall have no route, because its hooks run inside the sandbox and its receipts would be agent-writable; evidence: a test that a Codex record is `Unknown` without the effective-requirements evidence TSK-1060 produces, and the Grok refusal.
- AC-6 The `--harness` flag shall land with the Codex re-trust transition and a dispatch gate: the relay shall send a probe and shall refuse a brief until the seat's receipt exists; evidence: a relay journey with and without the receipt.
- AC-7 The task shall begin with an investigation note, kept with its evidence, stating how the qualification record composes with TSK-1052 and TSK-1053: for a fresh record (every binding input matches), a stale record (any binding input changed, a patch update included) and a rejected record (forged, malformed, wrong owner or wrong repository), the refusals those tasks make where containment is unknown shall stay in force, and only a fresh record may add attested capabilities; evidence: the note and one test per record state against a TSK-1052 case and a TSK-1053 case.
