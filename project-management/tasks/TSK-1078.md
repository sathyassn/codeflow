# TSK-1078: Local git hooks judge at the landed policy level

## Description

Source: the content policy design for issue #279, revision 5, unit U3,
closing finding D-1 (Grok's design, item 4.4), which no task owned.

The pre-commit secret scan and conflict-marker check take their level
from the uncommitted working-copy policy:

- `crates/codeflow-cli/src/cmd/git_hook.rs:116` loads
  `Policy::load_effective(&root)`, which reads
  `<root>/.codeflow/policy.json`
  (`crates/codeflow-core/src/hooks/policy.rs:872-874`, `:944-945`);
- core `crates/codeflow-core/src/hooks/git_hook.rs:159` and `:163` skip
  the scan and the marker check when `is_active` is false, and `is_active`
  is `Block | Warn` (`policy.rs:62-64`), so `allow` skips as `off` does;
- the path gate already composes with the landed policy (`:145`;
  `landed_policy.rs:629-638`), and bootstrap grace keeps the scan on
  (`policy.rs:991-1022`); the commit-msg stage validates the file but a
  valid `off` passes.

An uncommitted `off` or `allow` therefore lets a content secret be
committed with pre-commit silent. Who can write the file: in a Claude
session `Edit(/.codeflow/policy.json)` is in `permissions.deny`, but
Claude's file tools run no edit-guard (`docs/policy-reference.md:1153`);
Codex and Grok run `codeflow hook edit-guard` (`.codex/hooks.json:14`,
`.grok/hooks/codeflow.json:14`); outside a session nothing does. This task
makes the edit harmless rather than blocking it: the landed level is the
floor and the worktree may only raise it.

The same load serves every classic hook the binary runs (pre-commit,
commit-msg, pre-merge-commit and pre-push; `crates/codeflow-cli/src/cmd/git_hook.rs:111`
at the line's 96a01e17e), so a committed policy that is stale, as on an
out-of-date local protected branch, or edited on the branch also sets
what those hooks apply. AC-7, added 2026-11-08 by the Director's ruling
on TSK-1398, extends the landed floor to every level and list those four
hooks apply, each in its strict direction, and AC-8 does the same for `codeflow ci`'s range choice,
which reads the same file (`crates/codeflow-cli/src/cmd/ci.rs:418`, `:445`).
TSK-1398 records that until both land, agents cannot drop the in-session
sync of a protected branch.

Non-goals: the path gate (already landed-composed); the hosted scan
(TSK-336).

## Outcome

After this merges, an operator can rely on pre-commit, commit-msg, pre-merge-commit, pre-push and `codeflow ci`'s range choice judging at least as strictly as the default branch's policy, whatever the uncommitted, stale or branch-edited policy file says.

Pre-merge-commit did not scan content at this base: core
`hooks/git_hook.rs:955-991` only checked protected merges and root checkout,
and `assets/base/git-hooks/pre-merge-commit` dispatches only that stage.
The scan was added in this unit (see below).

`Policy::load_effective` (`policy.rs:1185`) applies bootstrap grace via
`suspend_for_bootstrap` (`:1233`); composition must preserve that window
after composing, while retaining the secret scan. No remote query is needed
when a local authority is available; an authority read failure must refuse.
Unordered values keep the landed value rather than pretending to order
patterns or branch identities.

Composition also preserves the implicit footer allowances of
`GitPolicy::allowed_footer_tokens` (`policy.rs:934` on the base). A removed
ticket key cannot survive as an unchecked generic footer. Narrowing keys
must refuse if it removes validation of a landed pattern or required ticket
footer. A new required footer must not admit a token outside an active
landed body rule's allowances. These cases have composition tests.

The baseline hook matrix failed all eight tests before composition; the
range-selection matrix failed all three tests before its branch-list
composition. After the change, all eight hook tests, all three range tests
and all twelve composition tests passed. The range fixtures also show that
an added prefix would admit a task's declared target before checking that
the composed prefixes exclude it.

The pre-merge-commit half of AC-1 is now covered: `pre_merge_commit` calls
the same `scan_staged_content` as pre-commit, at the composed levels
(`crates/codeflow-core/src/hooks/git_hook.rs:1003`).
`landed_floor_content_scans_survive_lowered_checkout`
(`crates/codeflow-cli/tests/hooks_cli/landed_floor.rs:313`) requires both
hooks to refuse a secret and marker text with the checkout at `off` and
`allow`, and `landed_floor_real_merge_journey_refuses_content_and_keeps_head`
(`landed_floor.rs:126`) drives a real `git merge --no-ff` through the
installed hook. AC-5 is covered by
`landed_floor_real_commit_journey_refuses_content_and_keeps_head`
(`landed_floor.rs:91`): on a scratch adopter set up by `codeflow init
--minimal --yes`, it plants a content secret, lowers the worktree policy to
`off` and `allow`, commits through the installed hook with the test binary
first on `PATH`, and requires a pre-commit secret refusal with HEAD
unchanged.

Adopter-visible change: in a clone with a remote but no recorded remote
default branch (`refs/remotes/origin/HEAD`), commit-msg, pre-merge-commit,
pre-push and registry pushes (`ids seed`, `task new`) now refuse until the operator runs
`git remote set-head origin --auto`, and the refusal names that command.
Before, only the pre-commit path gate refused there. The
test fixtures that lacked a remote default branch now record it, as a clone
does (`set_remote_head` in `crates/codeflow-cli/tests/hooks_cli.rs`, and
`git remote set-head origin main` in the acceptance_cli push fixtures); no
assertion on a refusal was weakened.

`codeflow ci` range floor (Director ruling, Option A): `range_policy` reads
the floor at the commit the run already pins, in this order:
`--policy-from`, `--base`, `--into` (by exact ref), then the base the CI
event names, then `CODEFLOW_DEFAULT_BRANCH` (`pinned_floor` in `crates/codeflow-cli/src/cmd/ci.rs`). It
uses the landed policy at the remote's default branch only when nothing is
pinned. A hosted `actions/checkout` with fetch-depth 0 has no
`refs/remotes/origin/HEAD`, so without this every hosted run would have
stopped at the range choice. The pin grants no new trust: the range is
already judged by the policy at that same base (`judging_policy`). The
pinned read applies no operator policy baseline (TSK-1057), as the judging
read at the base does not either.

Merge regression found and fixed after merging the EPC-022 line at
9168e8fe7d: TSK-1351 made a `git.candidate_prefix` name an allowed branch
name at pre-push, so a checkout `candidate_prefix` could widen naming. The
hook floor now keeps the landed `candidate_prefix` and
`candidate_search_depth` (`compose_git` in
`crates/codeflow-core/src/hooks/landed_policy.rs`), with a composition test
and a pre-push test that failed before and pass after.

Whole-unit review (Codex, CHANGES at `917bc3dc4d`) showed that independent
level maxima and a unioned protected list do not keep every landed decision,
so "a checkout can only tighten" was not proven. Three cases and their fixes:

- F1: a protected branch added by the checkout granted CI target authority
  (declared-target eligibility and the range base). Grants now read the
  landed list through `GitPolicy::trusted_protected_branches`, set by
  `compose_git` and by `range_policy`; the union stays for prohibitions.
  Push-set range bounds, the push declared target and the root-branch default
  read the same list.
- F2: protection selects the force-push level and exempts a branch from
  naming, so adding a branch to the list could remove a landed block. The
  pre-push force-push level is the stricter of the two classifications, and
  only the landed classification exempts a branch from naming.
- F3: raising `commit_ticket_required` to `warn` turned a block on a
  malformed ticket reference into a warning. A malformed reference blocks at
  every requirement level. The same dependency existed for a merge with its
  own subject under `commit_ticket_merges`; the stricter finding stands.

The claim that holds is narrower: a checkout cannot lower a level, drop a
landed list entry or raise a limit, and every decision that depends on another
field is judged under the landed value and the composed value with the
stricter result standing. Fields judged without such a dependency are listed
in the fix round's report. Tests that failed
before the fix and pass after: `landed_floor_pre_push_added_protection_*`,
`landed_floor_malformed_ticket_blocks_when_the_checkout_requires_a_ticket`,
`landed_floor_merge_ticket_rule_does_not_lower_the_landed_ticket_block`,
`test_ticket_malformed_present_blocks_at_every_required_level` and
`a_protected_line_the_checkout_adds_is_not_a_declared_target`.
