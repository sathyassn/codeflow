# TSK-1129: A task waiver accepts its own planning amendment that also updates the plan

## Description

Context: EPC-022. Source: issue #465. A task waiver
(`AC-N: waived | <amendment SHA>`) names a planning amendment of the
criterion. In the task's own pull request it may name an amendment in its
own range, and that amendment had to change only the task's record
(`waiver_problem` in `crates/codeflow-core/src/workgraph/acceptance.rs`).
The epic's waiver rule, and a task waiver that names an amendment on its
target, accept a planning-only commit that amends the criterion. So one
decision that narrows a criterion and updates the epic plan, as the plan
rule asks, had to be split into a record-only commit and a plan commit.

This task gives the own-range route the same test as the target route:
planning records only, and it must amend this criterion of this record.
A refusal of a commit off the target still names what "on the target" means
and the planning route (TSK-340 AC-7). Non-goals: the target route, the
landed-reopen rule and the ordering rules (after the range's merge-base,
strictly before `reviewed`) are unchanged.

## Outcome

After this merges, a builder can waive a criterion in a task's own pull
request by naming one amendment commit that changes the criterion and the
epic plan together.

## Findings

Probed on the line at `11a34926d` with the tests in `planning_amendment.rs`
before any code change:

- Fails: an amendment in the task's own range that amends the criterion
  and updates the epic plan is refused with "must change only this task's
  record to count as an amendment in its own range".
- Already passes: on the target, an epic amendment that also changes the
  epic record, the epic plan and another task's record waives the criterion
  it amends, named by its commit or by its landing merge. The issue's
  refusal text ("is not on the target or a record-only amendment") is the
  off-target message, so the issue's run did not pin the target that held
  the amendment; on this line, with the pull request's base pinned, it is
  accepted.
- Already passes: a criterion the amendment removes leaves the record; the
  completion has no row for it and needs no waiver. A `waived` row for a
  removed criterion is refused by `work.records` ("acceptance block lists
  AC-1, which the record does not have"), which is correct.
- Sibling sweep: the target route and the epic waiver rule already use the
  planning-only test (`non_planning_change`, then the criterion check);
  `task status` shares `waiver_problem`, so one change covers CI and the
  verb.
- Found while building, from `an_unrecorded_integration_line_earns_no_authority`
  (TSK-340): when a task declares a target that does not qualify (an
  unrecorded `integration/` name), `task status` anchors the range at the
  default target, so commits made on that unrecorded line counted as the
  task's own range. The record-only rule refused a batched amendment there
  only as a side effect; a record-only amendment made on that line was
  accepted as an own-range waiver. CI is not affected: it pins the pull
  request's base.
- Codex review round 01 (SEC-01): the first fix narrowed the own range to
  the merge-base with that line's ref, which a requester can rewind, delete
  or leave unfetched to restore the broad range. No ref naming an
  unqualified line can mark which commits are the task's own, so such a
  task now has no own range in the verb (`qualify` in
  `crates/codeflow-core/src/workgraph/status_verb.rs`). Pinning the line
  with `--base` and `--into` makes it the target, whose merge-base is the
  boundary; the two TSK-340 journeys whose line `main` never records now
  pin it.
- Codex review round 01 (SEC-02): the planning-only test was a directory
  prefix (`is_planning_path`), so `docs/plan/AGENTS.md`, a hidden file under
  `docs/plan/` or an adopter-facing path there passed it; on the target
  route this was already so on the line. Both task waiver routes and the
  epic waiver now admit a path only when `classify::amendment_path` reads it
  as a planning record under the policy at each pinned target (the reviewed
  commit for an epic's own waiver), and refuse when that policy cannot be
  read. The other `non_planning_change` callers (completion commits and
  release landings) are not waivers and keep their test.
- A criterion the task's own pull request removes needs no waiver row;
  `work.criteria_removal` asks the pull request body for the reason, as
  before.

## Acceptance Criteria

- AC-1 Before any change, this record shall state which parts of issue #465 fail on the line and which already pass; evidence: the Findings section, committed before the first code change.
- AC-2 (journey) When a task pull request's waiver names an amendment in its own range that amends this task's criterion and also updates the epic plan, `codeflow ci` shall accept it; evidence: `an_own_range_waiver_may_update_the_plan_beside_the_record` through `codeflow ci` in a scratch repository, failing before the change and passing after.
- AC-3 Both waiver routes shall refuse an amendment that changes a path other than a planning record (product code, the policy file, and beneath `docs/plan/` a harness instruction file, a hidden file or an adopter-facing path) or does not amend this criterion, and each such refusal off the target shall still name what "on the target" means and the planning route; evidence: `a_task_waiver_refuses_a_mixed_or_unrelated_amendment` on both routes, and `a_waiver_survives_the_reopen_that_removes_a_follow_up_record` with its refusal of the filing commit.
- AC-4 The target route shall keep accepting an epic amendment that also changes the epic record, the epic plan and another task's record, and a removed criterion shall need no waiver; evidence: `a_task_waiver_names_an_epic_amendment_on_the_target`, passing before and after.

- AC-6 When a task declares a target that does not qualify and is not pinned, `task status` shall give it no own range, so an amendment made on that line, batched or of the record alone, is refused as a waiver whatever its ref now points at or whether it exists, and an amendment on the task's own branch is accepted only once `--base` and `--into` pin the line; evidence: `an_unrecorded_integration_line_earns_no_authority` with its record-only, rewound-line and deleted-line cases, `an_unrecorded_line_needs_pins_for_an_own_range_waiver`, and the `acceptance_journey` sequence tests.
