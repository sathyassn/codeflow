# TSK-009 — build and qualify the documentation portal utility

## Description

Implement the approved `cf-docs-portal` skill, starter, source/update contract,
utility themes, and deterministic validators; then dogfood the result against
CodeFlow. Preserve the selected direction while keeping project source truth
and product/utility technical boundaries explicit.

## Affected surfaces and interfaces

- `cf-docs-portal` skill/references/assets/scripts, manifests/mirrors,
  documentation/capability/architecture/release surfaces, CodeFlow dogfood
  portal source and build evidence; approved SPC-005.

## Acceptance Criteria

- [ ] The skill builds and incrementally updates the approved layered portal
      from authoritative repository sources with source/version links and
      explicit stale/conflict handling.
- [ ] The starter is componentized, maintainable, responsive, accessible, and
      isolated from consuming-product and cf-present frontend/runtime code.
- [ ] Curated utility themes and light/dark modes satisfy the approved direction
      and optional primitive-token boundary without generic template slop;
      both themes are rendered in light and dark, follow the system before
      paint, persist an explicit preference, and show no incorrect-mode flash.
- [ ] Language remains source-grounded and audience-fit; descriptive titles,
      direct procedures, exact terms, appropriate visuals/bullets/prose, and
      contextual editorial review are demonstrated on real CodeFlow content.
- [ ] Deterministic validators prove source and snippet hashes, stale-page
      exclusion, strict ID linking and derived inverse links, provenance and
      version metadata, routes/navigation, `llms.txt` and Markdown twins, and
      fail-closed behavior for broken, conflicting, duplicate, orphaned, or
      missing inputs; they run through the approved `codeflow validate`
      boundary.
- [ ] The exact-pinned Starlight/Pagefind toolchain has a committed lockfile,
      clean locked install/build/audit evidence, and a bounded upgrade rehearsal;
      non-adopters, consuming-product code, and cf-present receive no portal
      dependency, token, component, runtime, or generated-content coupling.
- [ ] The concise mirrored skill and single embedded starter stay within
      explicit byte budgets. Release evidence records the starter's compressed
      and unpacked size plus the measured CodeFlow binary-size delta, and no
      portal workspace or lockfile is materialized before explicit adoption.
- [ ] Isolated real-browser journeys cover Orient → System → Records, search,
      strict-ID previews, source links, both themes and modes, responsive
      behavior, runtime/network errors, reviewable screenshot evidence,
      deterministic layout regression checks, and no-flash
      persistence across Chromium, Firefox, and WebKit where the supported
      host can run them. Accessibility evidence targets WCAG 2.2 AA, including
      real keyboard paths, accessibility-tree structure, measured contrast via
      axe, focus not obscured (SC 2.4.11), and minimum target size (SC 2.5.8).
      Actual assistive-technology sessions and perceptual pixel baselines are
      reported separately when warranted, never inferred from structural tests.
      Browser profile/context, ports, test data, output/traces, services, and
      retained failure evidence are task-owned and teardown is verified;
      unavailable native/platform evidence is reported, never inferred.
- [ ] Clean init/update canaries and empty, tiny, and monorepo fixtures prove
      opt-in installation, incremental reconciliation, agent-readable outputs,
      one authoritative graph with global-to-area drill-down, justified split
      criteria, product/cf-present isolation, and honest refusal when a portal
      is not warranted.
- [ ] Fable and Codex independently review the integrated code, portal design,
      generated content, tests, and diff size; no material finding remains.

error pages, and hardens source, media, relationship, and publication evidence.
