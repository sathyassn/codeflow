# TSK-244: Record writes refuse a symbolic link at any path component

## Description

Issue 94: the commands that create and change work records write through a
symbolic link anywhere above the record. A branch that commits
`project-management`, a kind folder (`epics`, `tasks`, `specs`), `docs` or
`docs/decisions` as a link to a path outside the checkout makes
`codeflow epic new`, `task new`, `spec new`, `adr new`, `task status` and
their siblings write a record, create folders or delete a file where the
link points (CWE-59). The class is a record write that resolves its path
without refusing a link in an intermediate component: `create_dir_all`,
`fs::write` and `remove_file` follow a link at any ancestor, `create_new`
refuses only a leaf link, and `file_lock::atomic_write` writes its
`<record>.tmp` through a link at that name.

This task routes every record write, delete and directory creation under
`project-management/` and `docs/` through one shared helper,
`crate::contained`, promoted from the portal's descriptor-anchored
transaction I/O: each component from the repository root is opened without
following a link, junction or other reparse point, and the operation is
refused when one is found. The portal keeps a thin wrapper over the same
helper. For a project without links, the visible changes are that a
replaced record keeps its Unix permission bits and is synced with its
folder, and that `ids retarget` refuses a file already at the new number
before it changes anything. Non-goals: what the listing reads (it already
skips a linked record or kind folder), the scaffold's lexical guard
(`guard_beneath_root`, which already refuses a pre-planted link), and
writes outside record paths, which the report lists. PR 93's feedback
tracker can adopt the helper later.

## Acceptance Criteria

- AC-1 When `project-management`, a kind folder or `docs` or `docs/decisions` is a symbolic link, `codeflow epic new`, `task new`, `spec new` and `adr new` refuse with a message naming the linked component and write, create or delete nothing where it points (`record_creation_refuses_a_link_above_the_record`, `adr_creation_refuses_a_link_above_the_record`, the CLI journey `record_link_refusal`) (journey).
- AC-2 When the records sit under a linked `project-management`, `codeflow task status` refuses and leaves the record where the link points unchanged, and `codeflow status` and the orient digest create no folder there and say why the work summary is missing (the CLI journey `record_link_refusal`; `markdown_store_refuses_a_linked_project_management`) (journey).
- AC-3 When `codeflow ids backfill` or `ids retarget` meets a linked record root or a tracked link under `docs/`, it writes and deletes nothing through the link (`backfill_never_writes_through_a_linked_record_root`, `retarget_never_writes_through_a_tracked_link`).
- AC-4 Every record write, delete and directory creation the record commands make goes through `crate::contained`, which opens each component from the repository root without following a link, junction or reparse point, creates missing folders through the same walk, creates a record exclusively for the creating verbs (`MarkdownStore`'s create still replaces), replaces a record atomically while keeping its Unix permission bits, and names the linked component in its refusal; the portal uses the same helper (`contained` unit tests on Unix; the Windows junction test in CI).
- AC-5 An operation that wrote through the old `<record>.tmp` name leaves a link planted there alone and succeeds (`spec_linking_never_writes_through_a_planted_temporary_name`, `follow_up_never_writes_through_a_planted_temporary_name`).
- AC-6 When linking a new spec to its consumers fails part way, every consumer already touched, including the one whose write failed after its rename, is restored and the new spec is removed; a consumer named twice is linked once (`spec_linking_failure_restores_every_consumer`). When `ids retarget` finds a file at the new number, it refuses before changing any file in the tree (`retarget_refuses_an_existing_destination_before_changing_anything`).
