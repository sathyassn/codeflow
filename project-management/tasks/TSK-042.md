# TSK-042: verify portal composition per source

## Description

Today's browser verification samples the portal, so a single well-composed page
can carry a build in which most eligible sources are still re-rendered
Markdown. This task turns browser-verify into a per-source coverage gate:
after the TSK-050 page classes, the TSK-051 adapter shape and the TSK-052
guide pages settle, every eligible source must show what its page class
requires: every explanatory page the altitude trio with a figure in Concept,
the record pointer page its folder table, and no per-record page at all in a
build whose configuration turns records off. A page that is Markdown under the
shell fails and is named,
and fixtures must prove the gate cannot be masked. The two holes
under the gate, the empty Pagefind entry and the cleanliness exemption, moved to
TSK-048 on 2026-09-20 so they land before the composed views.
Non-goal: no page content is authored here and no page class is invented. The
gate enforces the doctrine and the sources as they already stand, and it lands
only after TSK-050, TSK-051 and TSK-052 conform.

`docs-portal/scripts/browser-verify.mjs`, `docs-portal/scripts/git-snapshot.mjs`,

### What the gate does now

`docs-portal/scripts/page-classes.mjs` is the one declared source of the class
rules. It names the altitude panels, the Concept carriers, the record pointer
columns and, per class, the requirements a page must meet with the text each
failure prints. `browser-verify.mjs` classifies every page in the commit-bound
evidence before a browser starts: every non-stale source-backed page is
explanatory, the generated pointer page is its own class. It then visits each
eligible route once, reads one structural observation from the rendered
document, and reports every unmet requirement in a single failure naming the
offending source. A route the run never observes fails as a missing
observation, so coverage cannot be sampled. The path heuristic
`architectureShapedLayers` is gone and `discoverSurfaceRoutes` no longer
carries the sampled route lists that fed it.

### Why `browser:verify` is still red

`assertSemantics` requires a navigation landmark at the site root. The splash
landing renders none: measured live, the landing has main 1, h1 1, navigation
0, while `orient/product` has main 1, h1 1, navigation 2. The check and every
input that builds the landing, `adapter.mjs`, `src/`, `public/` and
`portal.config.json`, are byte-identical to `807679560`, so the failure
predates this task and reproduces on the integration head without it. All
three engines fail the same way, before any composition, swatch or altitude
check runs.

Nothing in the doctrine says whether the landing carries a navigation landmark,
so this is a project decision, not a mechanical fix, and the check was not
weakened to go green. Two ways out, both one edit:

1. Give the landing a navigation landmark. The landing markup comes from
   `renderIndex` in `adapter.mjs`, which TSK-051 owns, and the reading-path
   figure is already the landing's navigation.
2. Scope the requirement: assert the navigation landmark on a guide page,
   where the portal's navigation actually is, and assert the landing's own
   navigability through its reading-path figure links.

The recommendation is 1: the landing is the portal's entry point, its body is a
list of links, and a landmark makes that reachable to a screen reader without
changing what the gate asserts.

### Open decisions

The class rules treat every source-backed page as explanatory. The doctrine
exempts a reference page that only looks something up, but no source declares
which pages those are, and inventing a page class is a non-goal here. If the
epic wants that exemption it needs a declared marker and an owner. Nothing in
the guide needs it today: all 15 sources carry their class.
