# TSK-042: verify portal composition per source

## Description

Today's browser verification samples the portal, so a single well-composed page
can carry a build in which most eligible sources are still re-rendered
Markdown. This task turns browser-verify into a per-source coverage gate:
after the TSK-050 page classes, the TSK-051 adapter shape and the TSK-052
guide pages settle, every eligible source must show what its page class
requires: every explanatory page the altitude trio with a figure in Concept,
the record pointer page its folder table, and no per-record page at all in a
build whose configuration turns records off. A page that is Markdown under the
shell fails and is named,
and fixtures must prove the gate cannot be masked. The two holes
under the gate, the empty Pagefind entry and the cleanliness exemption, moved to
TSK-048 on 2026-09-20 so they land before the composed views.
Non-goal: no page content is authored here and no page class is invented. The
gate enforces the doctrine and the sources as they already stand, and it lands
only after TSK-050, TSK-051 and TSK-052 conform.

### What the gate does now

`docs-portal/scripts/page-classes.mjs` is the one declared source of the class
rules. It names the altitude panels, the Concept carriers, the record pointer
columns and, per class, the requirements a page must meet with the text each
failure prints. `browser-verify.mjs` classifies every page in the commit-bound
evidence before a browser starts: every non-stale source-backed page is
explanatory, the generated pointer page is its own class. It then visits each
eligible route once, reads one structural observation from the rendered
document, and reports every unmet requirement in a single failure naming the
offending source. A route the run never observes fails as a missing
observation, so coverage cannot be sampled. The path heuristic
`architectureShapedLayers` is gone and `discoverSurfaceRoutes` no longer
carries the sampled route lists that fed it.

### The landing navigation landmark, fixed here

`assertSemantics` requires a navigation landmark at the site root and the
splash landing rendered none: measured live, main 1, h1 1, navigation 0, while
`orient/product` measured main 1, h1 1, navigation 2. The check and every input
that builds the landing were byte-identical to `807679560`, so the defect
predated this task and reproduced on the integration head without it. It is
fixed here rather than deferred because the gate this task ships is the first
check that reaches it: it stopped all three engines before any composition,
swatch or altitude check could run.

The fix is semantics only. `readingPathFigure` in `adapter.mjs` wraps the
reading-path figure in `<nav class="portal-reading-path-nav" aria-label="Reading
path">`. The landing shows what it showed before: every portal rule for that
figure is a descendant selector, so no rule changes which element it matches.
The landing has no sidebar, so this figure is the whole of its navigation and
now carries the landmark and the name that says so. Measured after the fix, the
landing reports navigation 1, and all three engines pass `assertSemantics`.

### The strict-ID preview repair

`assertStrictIdPreview` hovers the first strict-ID trigger on the page it
picks, and it assumed that trigger was visible on load. That stopped being true
when TSK-052 composed the guide pages into trios: a cited id now sits in a
panel the tablist shuts. Measured on the built portal, the selected route
`system/architecture` carried one trigger, `CAP-017` to `/orient/capabilities/`,
inside the `technical` panel with `hidden` set, `display: none` and zero client
rects, while `concept` was the selected tab, so all three engines timed out on
the hover.

`revealAltitudePanel` now reaches it the way a reader does: it finds the panel
containing the trigger, clicks that panel's tab, and waits for the tab to report
`aria-selected="true"` and the panel to be visible. A trigger outside every
panel keeps the previous path untouched, and the hover, keyboard, touch and
escape sequence after it is unchanged. Its unit case builds a real portal,
cites `CAP-001` inside a Technical panel, loads the built page with the real
`portal-tabs.js`, and asserts the trigger starts hidden, that the helper returns
`portal-panel-technical` and makes it visible, that a second call on an open
panel is a no-op, and that an element outside every panel returns null.

### The theme matrix now sets the theme the way the page does

`assertThemeMatrix` used to write `data-theme` straight onto the root while the
page's own appearance owner still held the preference the earlier checks had
stored, so the attribute and the stored preference could disagree during a scan.
It now drives the Display control where the page exposes it, writes the same
`starlight-theme` and `cf-portal-skin` preferences that control writes where it
does not, and waits, with no sleep, until the root resolves the mode's own
`--cf-text-muted` before scanning. `applyDisplayState` is exported, and a case
in `tests/composition-browser.test.mjs` holds both paths to one postcondition:
the stored preference and the root attribute agree. The matrix also hands the
page back with the display keys cleared and the light appearance restored.

### The reduced motion repaint defect, fixed here

With that disagreement gone, webkit still failed `assertA11y` from
`assertThemeMatrix`: `color-contrast` 2.3:1, foreground `#4d555d` on background
`#161a1e`, on the landing's first and third paragraphs. `#4d555d` is the light
`--cf-text-muted` and `#161a1e` is the dark surface, so the report described a
page in two states at once.

Measured against the built portal over a loopback server, in webkit, with the
gate's own context options, switching appearance the way a reader does:

| Condition | Paragraph colour after the switch to dark |
|---|---|
| `reducedMotion: reduce`, switched through the Display control | `rgb(77, 85, 93)`, the light value, with the root token at `#a8b0b8` |
| the same, plus `transition-duration: 0s !important` | `rgb(168, 176, 184)`, correct |
| the same, plus `transition: none !important` | `rgb(168, 176, 184)`, correct |
| no reduced motion, everything else identical | `rgb(168, 176, 184)`, correct |
| a persistent context alone, or touch alone | correct |

The cause was `docs-portal/src/styles/portal.css`: under
`prefers-reduced-motion: reduce` every element took
`transition-duration: 0.01ms !important`, and with `transition-property: all` in
force a theme change started a colour transition on every element. webkit never
advances a transition that short, so each element kept its pre switch colour
until a reload while the root's custom properties already held the new values. A
full page screenshot in that state showed the portal painted light under
`data-theme="dark"`.

That was reader facing, not a test artefact: a Safari reader with Reduce Motion
enabled could not change appearance, palette, typeface or scale without
reloading. chromium and firefox were unaffected, which is why only webkit was
red. The gate this task ships is the first check that reaches it.

The block now ends those transitions at once, `transition-duration: 0s
!important`, which keeps the rule's shape and its intent. The starter mirror
carries the same byte, and the pristine hashes were refreshed.
