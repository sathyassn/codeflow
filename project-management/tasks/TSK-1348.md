# TSK-1348: One setup command creates the authority and agent GitHub Apps

## Description

Mode A (TSK-1177) needs a GitHub App whose installation token creates the `authority:` check runs, an environment `codeflow-authority` restricted to the default branch, and the App's key and id stored in that environment. TSK-1080 (complete) documents this as a seven-step web procedure for the operator. The GitHub setup research of 2026-11-05 (`coordination/coordinators/planning/briefs/github-setup-research.md`, workspace commit d6cd9f99) found that only two steps need a browser: registering an App from a manifest page and installing it. Everything else has a documented REST endpoint, and nearly every write needs Administration write on the repository, so it runs under the administrator's own login and never under an agent's token.

The operator decided on 2026-11-05 that agents get their own GitHub identity through a GitHub App installation, created by the same setup command as the authority App. The agent App has Contents and Pull requests write, and no Administration, Workflows, Environments or Deployments permission. Pull requests and merges it makes show the App's bot name (`<slug>[bot]`), and a merge commit GitHub makes when the agent App merges names `<slug>[bot]` as its author: the operator accepted the bot name on merge commits in the same decision (route (c) of the research's attribution question). Commits the agents make keep the human author, and nothing adds AI attribution: `git.ai_attribution` is unchanged, and the command adds no trailer or co-author. The operator decided on 2026-11-06 that the agent App is the committer of a commit an agent session makes: the session sets `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL` to the values `codeflow remote agent-token --committer` prints, delivered through project harness settings. The agent App is optional for every project and developer, and nothing requires it.

Design change 2026-11-07 (issue 696, Director from the adopter's settled design): agent pull requests show the developer as author through a third, optional App, the PR App, and never through a user token of the agent App. A GitHub App user access token carries the permissions both the App and the user have, and neither the device flow nor a refresh can narrow its permissions (`## Findings`), so a user token from the agent App, which holds Contents write, would let an administrator's agent merge or push, possibly under the administrator's ruleset bypass. The PR App holds Pull requests write, Contents read and Metadata read only, so GitHub refuses a merge or a push made with its token for every user. Where a project has the agent App, its installation token covers pushes, reads and the git credential helper; where it does not, agents use the developer's own git credentials. Each App is optional (AC-16, AC-20).

This task is TSK-1080's docs follow-up (its operator steps 1 to 5 and 7) plus the command that makes those steps two clicks. Non-goals: the authority job and Mode B (TSK-1177); ruleset writing (`codeflow remote protect`, TSK-1080); the release environment and its actor rule (TSK-1346); the Actions event policy (TSK-1347).

Recovery: the command writes host state (an App, an environment, a secret, a variable). Every write it makes is listed in its output with the command or endpoint that undoes it; the App is deleted from the account's App settings, which is a web step.

## Outcome

After this merges, a repository administrator can set up CodeFlow's authority App, its environment and secrets, and, optionally, a separate agent App with narrowed rights, with one command and two clicks per App; where the agent App is used, agents push and act on GitHub under its identity while commits keep the human author. A project that wants agent pull requests to show the developer as author adds the optional PR App in the same run, with one more click, and its token can open and edit pull requests but cannot merge or push. Either App works without the other, and a project with neither has its agents act with the developer's own login and git credentials.

### AC-8: where the agent App's key is kept, and why

- **Store:** the operating system's credential store. On macOS it is a login
  keychain item, service `codeflow-agent-app`, account `owner/name`, written
  through `/usr/bin/security -i` with the value as hex on standard input, so
  no process argument list carries it. On Linux it is a Secret Service entry
  written by `secret-tool store`, which reads the value from standard input.
  Windows has no supported store yet, so the command refuses the agent App
  there before creating it (`--no-agent` sets up the authority App alone).
- **No file at all.** The setup sends the authority key to `gh secret set` on
  standard input and the agent key to the store on standard input.
  `agent-token` signs with `openssl dgst -sha256 -sign /dev/stdin` (checked
  with OpenSSL 3.6.3 and the system LibreSSL 3.3.6 on 2026-11-05, both
  giving a 256-byte signature) and sends the App's token to GitHub with
  `curl -H @-` (checked: curl 8.7.1 sent a header read from standard
  input). Only the signing input, which is not secret, is written, in a
  private temporary folder removed on every exit path. This is stronger
  than AC-8's allowance of a temporary key file.
- **What the custody rests on.** Any process of the same user that can reach
  the keychain or the Secret Service can read the entry; on macOS an item
  the `security` tool created is expected to be readable by `security
  find-generic-password -w` without a prompt (not verified here: an agent
  may not read a credential store). So the key stays out of an agent session's reach only while the
  session's sandbox denies the credential store and only `codeflow remote
  agent-token` runs outside it. An unsandboxed agent shell could read it.
  The operator step's part E5 checks this on this host; if the sandbox does
  not deny the keychain, AC-8 does not hold here, and the options are a
  keychain access list that trusts only the `codeflow` binary (which needs
  the Security framework called from the binary, not the `security` tool),
  or a guard rule refusing `security find-generic-password -s
  codeflow-agent-app`. Neither is built here.

### AC-3 against ADR-0091's agent principal

ADR-0091 "Agent principal (decision 1)" gives the agent Contents and Pull

Design choices that follow, as they apply to the PR App:

- **The device flow click.** The manifest cannot turn the device flow on, so
  `setup-apps` names the click on the PR App's settings page, and
  `pr-login` names the page again on `device_flow_disabled`.
- **A refused refresh.** The pages name no error code for it, so any OAuth
  error GitHub returns to a refresh is read as a refused authorization and
  gives the one message naming `pr-login`. A transport failure or an HTTP
  status that is not an OAuth answer names its cause instead.
- **Rotation.** The old refresh token stops working once used, so the new one
  is stored before the access token is printed, a failed store says the
  developer must authorize again, and a file lock lets one refresh run at a
  time, so two sessions never spend the same refresh token.
- **Store.** The entry is kept under its own service (proposed
  `codeflow-pr-user`), account `owner/name`, apart from the agent App's key
  (`codeflow-agent-app`), and is replaced in place on each refresh
  (`security add-generic-password -U`, or `secret-tool store`, which
  replaces an entry with the same attributes).
- **Revocation.** A cached access token is checked before it is printed; a
  401 leads to a refresh, which a revoked authorization refuses. The login
  GitHub answers is the author the developer's pull requests show.

- **No key and no secret kept.** GitHub issues a key, a client secret and a
  webhook secret for every manifest App, and an App always keeps one key, so
  "no private key, no client secret" means CodeFlow discards all three at
  conversion and the PR App is used only

  replaced on the App's page but not removed.
- **The grant check is the permission control.** Since a user token cannot
  be narrowed by permission and one token reaches every installation of the

  before each print and refuses on any difference (AC-18), comparing ids
  GitHub returns (App id, client id, repository id) with those recorded at

  token already printed. Whether a refreshed token keeps a `repository_id`
  restriction is undocumented, so the check reads the repository list
  rather than relying on that parameter.
- **Reviews.** Pull requests write lets the token approve or dismiss
  reviews, and the pull request's author cannot approve their own pull
  request, but an agent could approve another developer's. By operator
  decision the guard rule (AC-19) is variant A: it refuses every approval
  and dismissal it can parse in a guarded session, whatever token is
  visible, and GitHub still accepts these calls from outside the guard.
- **Bypass.** The rulesets page does not say how a bypass applies to a user
  token, so the design does not rely on rulesets to stop the PR App's token.
  The merge endpoint needs Contents write, which the token cannot hold
  because it has only what both the user and the App have. The pages read
  do not describe a git push with a user token, so the push refusal rests on
  the same intersection and is first observed in AC-7's journey.
