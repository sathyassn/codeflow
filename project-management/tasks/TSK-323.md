# TSK-323: Ignored and oversized files are judged by the default branch's size and ignore rules

## Description

The second step of https://github.com/sathyassn/codeflow/issues/174, on
TSK-322's path gate: a file the project's own ignore rules exclude, or a
file over a size limit, can still be committed. This task adds two keys,
read at the policy authority, the default branch at one SHA (TSK-1077),
never the working tree or a pull request's base:

- `git.ignored_files` (`{level, allow: [{path, reason}]}`, default level
  `warn`): the authority's `.gitignore` files through a gitignore matcher;
  a tracked file is still tested; a `.gitignore` edit in the range admits
  nothing.
- `git.max_file_bytes` (`{limit, except_under}`): on by default; a new or
  changed file larger than 1 MiB warns; in a new scaffold, a new or
  changed file larger than 10 MiB is refused; an updated project gets
  report lines only, for both thresholds, until it opts in; an explicit
  `limit` or `except_under` in the authority's policy replaces the
  default.

Both honour TSK-322's built-in exemption and its normalization. The matcher
needs the `ignore` crate or an equivalent, a new dependency, so a tier-3
decision is recorded before any code (`Cargo.toml:36` holds
`unicode-normalization`; `ignore` is not yet a dependency). Non-goal: a
type rule beyond the name patterns TSK-322 already gives.

A refused file has three admission routes: (1) Git LFS, since the gate
sizes the blob git holds, which for an LFS-tracked path is the pointer,
so it passes with no policy change; (2) a `limit` or `except_under`
change in the policy on `main` through a reviewed pull request; (3) from
4.2.0, a per-path `admitted` row in TSK-424's register. A single-file
exception does not exist in 4.0.0 beyond naming the file's directory
under `except_under`. Legitimate large cases (model weights, datasets and
fixtures, media, vendored binaries, installers) belong in Git LFS, or in
a release asset or package registry the repository references by digest.

Amended 2026-10-29 by the content policy amendment (issue #279, design
revision 5, decision 8, taken by the operator that day with the
admission routes stated). Until then this record said both keys were off
by default and read at the base revision, with `ignored_files` at level
`off`. Reasons for the change: two keys that are off protect nobody on
the day they ship (decision 8 (b)), and the default branch is the only
policy authority (TSK-1077, decision 5). This task stays a feature on this
line by the operator's placement of 2026-10-18 and is not relabelled.

## Outcome

After this merges, an adopter is warned about ignored files and files larger than 1 MiB, and a new scaffold refuses files larger than 10 MiB with the routes to admit them, all judged by the default branch's policy.

## Findings

Recorded on the task's base, `integration/EPC-022-the-3-2-0-milestone-fixes`
at `606f91960`, before any code change.

- **How each key is read today.** Neither `git.ignored_files` nor
  `git.max_file_bytes` exists: the schema holds 74 keys
  (`crates/codeflow-core/src/hooks/policy_schema.rs`, `SCHEMA`), and a
  policy naming either is refused as an unknown key (`validate_leaf`). No
  rule judges a file's size or the ignore rules anywhere in the binary.
  TSK-322's path gate reads its own keys two ways:
  - pre-commit (`crates/codeflow-core/src/hooks/git_hook.rs:145-157`)
    calls `landed_policy::staged_paths` (`landed_policy.rs:629-639`): the
    landed policy composed with the working copy, which may add denials
    only. The landed policy (`load_raw`, `landed_policy.rs:33-143`) is the
    default branch's tracking ref (`refs/remotes/<remote>/HEAD`, else
    `main` and `master`), then a declared integration line on top, which
    supplies path exceptions (`over_target`) and stricter levels
    (`stricter_levels`, `:425-474`, which copies only level keys from the
    line). Keys of any other kind keep the default branch's value. Before
    the first fetch the source is `HEAD`, and with no commit the working
    copy.
  - `codeflow ci` (`crates/codeflow-cli/src/cmd/ci.rs:426-464`,
    `judging_policy` at `:1971-2034`) reads `.codeflow/policy.json` at one
    commit: `--policy-from` (the target tip pre-push names), else the
    range's base, else the working copy when no base resolves. The path
    gate (`:551-578`) judges every commit the range introduces with it.
  - Both `staged` and `range` return early when `git.path_policy` is
    inactive (`path_policy.rs:384-386`, `:415-417`), and every judged entry
    comes from the index or the commit trees (`check_diff`, `:352-376`),
    never the working tree. Gate inputs, every `.gitignore` included, are
    exempt from the name and prefix rules (`exempt`, `:234-249`).
- **How an LFS-tracked path appears to the gate.** The gate reads the blob
  id git records for the path (`file.id()` in `check_diff`; the index
  entry's id for merges). For a path `.gitattributes` gives `filter=lfs`,
  git runs the clean filter on `git add` and records its output, the
  pointer text (`version`, `oid sha256:...`, `size N`, about 130 bytes),
  as the blob. A size rule that reads the recorded blob's size therefore
  sees the pointer, whatever the payload. Where the filter is not
  configured (no `git lfs install`), git records the payload itself, and
  the rule sees its real size. `git-lfs` is not installed on this host, so
  the fixture runs git's own filter mechanism with a clean command that
  writes the pointer format.
- **How `codeflow update` reports a new default.** A user-owned
  `policy.json` gains only keys the shipped template carries
  (`crates/codeflow-core/src/scaffold/update.rs:15-19`), and a new key
  never enters the template in the release that introduces it
  (`policy_schema.rs:15-56`; `docs/policy-reference.md` "Where a new key
  goes"; `crates/codeflow-core/tests/policy_key_placement.rs`). So
  `update` cannot write either key. Non-file findings go to the report's
  notes (`scaffold/report.rs:76-77`), as the outcome marker and work
  records baseline notes do (`update.rs:433-438`). Project kind is
  recorded in `.codeflow/project.toml` by adoption markers that `init`
  writes and `update` never rewrites: `release_rules`
  (`scaffold/state.rs:47-52`, `init.rs:186-192`, `update.rs:431`) and
  `outcome_present_uids` (TSK-435). `ProjectState` does not deny unknown
  keys, so an older binary reads a project file that carries a new marker.
- **Which shipped scaffolds carry an explicit setting.** None.
  `assets/base/policy.json` and this repository's `.codeflow/policy.json`
  carry neither key and no size limit. The shipped `assets/base/gitignore`
  is the only ignore input a new scaffold has (secret names such as
  `*credentials*`, `.DS_Store`, `.worktrees/`, local settings). This
  repository tracks no ignored file (`git ls-files -ci --exclude-standard`
  prints nothing) and its largest tracked blob is 884,357 bytes
  (`crates/codeflow-core/src/hooks/git_guard.rs`), under 1 MiB.
- **The dependency.** `Cargo.lock` holds no `ignore` crate; `globset`
  0.4.19, which `ignore` builds on, is already a dependency
  (`Cargo.toml:26`).
