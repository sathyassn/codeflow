# TSK-1386: The shell guards protect home enforcement paths for every writer and spelling

## Description

The edit guard treats the home enforcement paths as protected: the `~/` entries of the Claude edit denies (`actions::table().claude_edit_denies`, read by `enforcement_patterns` in `crates/codeflow-core/src/hooks/edit_guard.rs:315`), such as `~/.codeflow/authority/`, the home harness settings and hooks, and the Codex and Grok config. It resolves symlinks and fails when the home cannot be read (`enforcement_path`, `edit_guard.rs:198`). The two shell guards do not apply that set to a shell write: git-guard's `word_could_name_spelled` returns no match for a word starting with `/` or `~` (`crates/codeflow-core/src/hooks/git_guard.rs:3606-3608`), and `token_integrity_path_literal` then checks only repository authority, repository enforcement and `integrity_target` (`git_guard.rs:2537-2548`). Found during PR 698 (TSK-1184) and reproduced on 2026-11-08 with the 4.0.0 beta built at `678d3fa48`, judging payloads only:

| Command | git-guard | exec-guard |
|---|---|---|
| `printf x > <home>/.codex/config.toml` | allowed | allowed |
| `printf x > ~/.codex/config.toml` | allowed | refused by `security.text_guard` only |
| `printf x > $HOME/.codex/config.toml` | allowed | refused by `security.text_guard` only |
| `printf x \| tee <home>/.codeflow/authority/config.toml` | allowed | allowed |

So for a Bash write, the home enforcement paths rest on the harness sandbox alone, and a `~` spelling rests on the generic strict text rule, which a policy may set to `relaxed`. This task makes both shell guards judge a write to a home enforcement path as an enforcement write, for every shell writer and every spelling of the path. The rule is the authority floor, so it is the same for adopters and has no configurable relaxation.

Related records, not redone here: TSK-378 and TSK-413 judge writes and git calls made by interpreter programs; TSK-407 refuses links created earlier on a command line. This task states the shell writer boundary for the home paths; where one of those tasks lands first, this task reuses its resolver. TSK-397 (complete) added the strict text rule this task stops relying on for these paths.

Non-goals: reads of these paths; repository enforcement paths, which the guards already judge; the sandbox profile.

## Outcome

After this merges, an operator can rely on git-guard and exec-guard to refuse a shell write to `~/.codeflow/authority/`, the home harness settings and hooks, or the Codex and Grok config, however the path is spelled, with or without the harness sandbox.

## Deliverables

- the shared home enforcement check for shell writers: `crates/codeflow-core/src/hooks/` (the module is named in the PR; it reuses `edit_guard::enforcement_path` or the set it reads)
- git-guard and exec-guard wiring: `crates/codeflow-core/src/hooks/git_guard.rs`, `crates/codeflow-core/src/hooks/exec_guard.rs` (or their modules)
- tests: the guards' existing test modules, judging payloads only
- release note: `changelog.d/TSK-1386.md`

## Acceptance Criteria

- AC-1 When a Bash command writes to, creates, removes or changes the mode or owner of a home enforcement path, git-guard and exec-guard shall each refuse it and name the path and the rule, for every writer the guards already judge: each entry of the shared writer table `WRITERS` (`crates/codeflow-core/src/security/unresolved.rs:39`, read through `judge_writer`, which today includes `cp`, `mv`, `ditto`, `dd`, `install`, `ln`, `tee`, `touch`, `truncate`, `mkdir`, `mktemp`, `rm`, `rmdir`, `unlink`, `chmod`, `chown`, `chgrp`, `shred`, `rsync`, `scp`, `tar`, `bsdtar`, `gtar`, `unzip`, `zip`, `curl`, `wget`, `patch`, `trash` and `trash-put`), every redirection (`>`, `>>`, `>|`, `&>`, a numbered fd), `sed -i`, and `sed`'s `w` and `W` commands with or without `-i`. The home enforcement paths are the `~/` entries of the set the edit guard reads, so a path added there is covered here with no second list. Interpreter programs stay with TSK-378 and TSK-413. Evidence: a table test per guard over every writer form, each failing before the change where it was allowed, judged payloads only, and a test that fails when a `WRITERS` entry has no home-path case.
- AC-2 The refusal shall hold for every spelling of the path: absolute, `~`, `$HOME`, `${HOME}`, `"$HOME"`, a relative path from a `cd` into the home, a brace or quote split, and a symlink whose real destination is a home enforcement path (a link in the repository to `~/.codex`, or `~/.codex` itself a link). Evidence: a test per spelling under both guards, failing before the change where it was allowed, and one with `security.text_guard` set to `relaxed`, so the refusal no longer depends on the strict text rule.
- AC-3 When the guard cannot resolve the home, a symlink, or a writer's target (an unknown variable, a command substitution `$(...)` or backticks, an unreadable directory, an unmodelled writer option that names a target), it shall refuse with a message saying it could not resolve the target, and never allow. This holds with `security.text_guard` set to `relaxed`, so it does not rest on the strict text rule. Evidence: a test per case under both guards with `text_guard` relaxed, including `printf x > "$(printf %s <home>/.codex/config.toml)"`.
- AC-4 The refusal shall have no configurable relaxation: no policy key, profile, environment variable or `security.text_guard` value shall allow a write to a home enforcement path, and `codeflow doctor` shall not report it as relaxable. Ordinary writes shall be unchanged: a write to `notes.md`, to `$TMPDIR`, to the session scratchpad and to `~/.codeflow/locks/` shall pass as today. Evidence: tests under each policy value, the ordinary-write cases, and the policy schema showing no new key.
- AC-5 (journey) With the built binary, the four commands in the Description's table shall be refused by both guards, and `printf x > notes.md` allowed, run as hook payloads in one session. Evidence: the payload log with each verdict, at the base and at the head, judged only, never executed.
- AC-6 The pull request shall have a cross-family security review using the `cf-security-reviewer` checklist, with Grok as the default seat, covering each writer form and spelling and the fail-closed paths. Evidence: the review file named in the PR body.
