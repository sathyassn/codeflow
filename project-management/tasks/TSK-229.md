# TSK-229: One planning amendment names several epics and carries its instruction text

## Description

One reviewed plan change could not land as one pull request: a `Task:` line
named one epic, and `AGENTS.md` left a planning range unclassified, so every
other task's criteria change was refused as frozen (sathyassn/codeflow#49).
This task lets one planning amendment name several epics on its `Task:`
line (`Task: EPC-002, EPC-003`) and carry docs and the project section of
`AGENTS.md` while the managed block stays byte-identical to the target's.
`codeflow ci` reports each change per named epic and refuses a change to an
epic the line does not name; the pre-push run applies the same path rule
with the target's `AGENTS.md` read from the base. The amendment lands on
`main` and lines take it by merging `main`. Operator decisions D6 to D9 of
2026-10-03; design: issue 49, recommendation B.

Non-goals: no policy key, no plan record kind, no change to a task pull
request's own-criteria rule or to the reopen rule (SPC-013 R-119); a spec
approval still travels in a range of records and plans only (R-32).

## Deliverables

- Classification of a multi-epic `Task:` line and the planning path set: `crates/codeflow-cli/src/cmd/ci/classification.rs`, `crates/codeflow-core/src/workgraph/classify.rs`, `crates/codeflow-core/src/scaffold/region.rs`
- Criteria and the pre-push planning test: `crates/codeflow-cli/src/cmd/ci/acceptance.rs`
- The per-epic report and the epic scope: `crates/codeflow-core/src/workgraph/amendment.rs`, `crates/codeflow-core/src/workgraph/acceptance.rs`, `crates/codeflow-core/src/remedy.rs`

- Requirements: SPC-013 R-52, R-70, R-73, R-74 and R-80 in `project-management/specs/SPC-013.md`

## Acceptance Criteria

- AC-1 When a `plan/` pull request names `Task: EPC-001, EPC-002` and changes the criteria of a task in each epic, `codeflow ci` shall pass, print the class as a planning-only amendment of both epics, and print one `work.planning_amendment` note per task with its criteria delta; evidence: `planning_amendment one_amendment_changes_criteria_in_two_epics`, whose fixture the 3.0.0 binary refuses.
- AC-2 When the same pull request also changes `AGENTS.md` below its managed block, `docs/plan/plan.md` and `docs/reading.md`, `codeflow ci` shall pass; when one byte inside the managed block changes, it shall block under `work.classification` naming the managed block; evidence: `planning_amendment an_amendment_carries_its_instruction_text_but_not_the_managed_block`.
- AC-3 When the same branch runs through the pre-push check with no body, the verdicts of AC-1 and AC-2 shall hold; evidence: the `ci_push` cases of the AC-1 and AC-2 tests.
- AC-4 When a planning pull request changes `src/lib.rs`, `CLAUDE.md`, `.claude/settings.json` or `.codeflow/policy.json`, `codeflow ci` shall still refuse it; evidence: `planning_amendment a_planning_amendment_still_refuses_product_and_enforcement_paths` and the classify unit tests.
- AC-5 When a task pull request changes its own and another task's criteria, `codeflow ci` shall print its own delta and refuse the other as frozen, a reopened task shall keep its criteria inside an amendment, and the existing `acceptance_cli` and `ci_cli` suites shall pass unchanged; evidence: `planning_amendment a_task_pull_request_keeps_other_criteria_frozen` and the unchanged suites.
- AC-6 (journey) When an amendment adding a line task lands on `main`, `work start` for that task on the line shall refuse and its pull request shall name the merge-planning remedy until the line merges `main`; then `work start` shall pass and the anchored record shall carry the amended criteria; before landing, `codeflow ci` shall flag a record newer on the line; evidence: `planning_amendment a_line_takes_the_amendment_by_merging_main`.
- AC-7 When a planning pull request naming `EPC-001` changes a task of `EPC-002`, `codeflow ci` shall refuse it and name the task and its epic, while a standalone task's record is listed and not refused; evidence: `planning_amendment an_amendment_names_every_epic_it_changes`.
- AC-8 When CodeFlow 3.0.0 reads `Task: EPC-001, EPC-002`, it refuses the line as malformed, and the CHANGELOG 3.1.0 entry carries the migration note; a list of task ids stays malformed in 3.1.0; evidence: the 3.0.0 binary run on the AC-1 fixture, `planning_amendment a_task_line_list_takes_only_distinct_epics` and the CHANGELOG diff.
