# TSK-1155: codeflow ci refuses a direct commit on an integration line before the gate runs

## Description

Source: issue #489 (CodeFlow 3.1.1, by an adopter), read at commit
`4880597073` (the step 4 planning branch head) after a search found no open
task that covers it. A landing candidate for an integration line held one
commit made directly on it (a task's completion record) after a no-ff task
merge. `codeflow ci --base <line tip> --head <candidate>` and the full gate
passed; the pre-push hook then refused the push with `work.epic_line`. The
gate (about 12 minutes there) had run on a candidate that could never land,
and the candidate and the next two queued landings were rebuilt.

Cause, read on the tip above:

- The rule is raised only by the pre-push hook: `epic_line_push`
  (`crates/codeflow-core/src/hooks/git_hook.rs:1302`) calls
  `line_adoption::check_range` over the pushed range and emits
  `work.epic_line` (`:1396`). Nothing in `codeflow ci` emits that rule id.
- `codeflow ci` runs `check_epic_line_with_adoptions` only when the head's
  branch name starts with `integration/`
  (`crates/codeflow-cli/src/cmd/ci/classification.rs:639`), and that
  judges the line's range into the default target. A candidate named
  otherwise, with the line tip as base, reaches no epic-line check.
- The hook's own doc comment says a range it cannot read is a note because
  "CI stays the hard line (charter D19)" (`git_hook.rs:1293-1301`). CI does
  not hold that line for this rule today, so the hook is the only check.

Overlap checked, none found: TSK-1151 (records-only landing candidates, PR
486, coord/parallel) changes which checks a candidate's class selects
(`classification.rs`), not the epic-line rule; TSK-1089 keys line treatment
on a branch's commits for a line-to-main range, not a range onto the line;
TSK-433 and TSK-248 are complete; TSK-402 judges a carry merge onto another
line and must keep passing here (a merge is not a direct commit). The nearest
region is coord/parallel's: this task lands in `codeflow ci`'s candidate
classification beside TSK-1151, so the two are one writer at a time, and the
candidate-checking route is the parallel lane's to use.

Design. `codeflow ci` judges a range whose destination is a confirmed
integration line with the same `line_adoption::check_range` the hook runs,
and reports the same `work.epic_line` finding with the same remedy. The
destination comes from the run's inputs, never from the head's branch
name:

- With `--into <line>` (or the pre-push destination), the line is that ref.
- With no `--into`, as in the issue's invocation, the line is the one
  `integration/EPC-*` remote-tracking ref (as fetched) whose tip is exactly
  the base commit. Zero such refs means the range is not a landing on a line:
  ordinary behaviour, with a note that no line destination was found. Two or
  more refuse, naming them.
- The line is bound by `epic_line_binding`
  (`crates/codeflow-core/src/workgraph/work_start.rs:883`) read at the
  trusted tip, never at the head, as TSK-1089 does
  (`project-management/tasks/TSK-1089.md:60-74`). The trusted tip is the one
  the destination advertises for that exact ref, resolved once to a commit at
  the start of the run (the remote-tracking ref as fetched for a local run),
  never a local branch, a requester-supplied anchor or a commit the head
  names. A line whose authority cannot be established refuses.
- The checked range starts at that pinned tip, as the hook's range does
  (`git_hook.rs:1361-1369`). A supplied `--base` that is not the tip does
  not shorten it: the whole tip-to-head range is judged, or the run refuses
  with the cause. `check_range` excludes history through the base it is
  given (`line_adoption.rs:185`), so without this a base placed after a
  direct commit would hide it.

A destination confirmed to be something else, such as `main`, keeps ordinary
behaviour: this rule adds nothing there. Fail closed for an intended line: a
binding that cannot be established, an ambiguous destination, history that
cannot be read, and malformed adoption entries each refuse in `codeflow ci`
with the cause, since CI is the hard line. The adoption entries are the ones
`check_range` already reads (landed at the target or in the line's history);
the head alone cannot adopt its own direct commit.

Non-goals: the hook keeps its note for an unreadable range (charter D19);
no change to which direct commits an adoption entry may excuse.

## Outcome

After this merges, a maintainer sees a direct commit on a landing candidate
in `codeflow ci` before the full gate runs, so the candidate is rebuilt
without a wasted gate.

## Findings

Recorded 2026-11-01 before the first code change (AC-1), on the line tip
`bee344658` merged into the reviewed planning SHA `9c486dbdf`.

**Reproduction.** The fixture
`a_candidate_with_a_direct_commit_is_refused_as_the_hook_refuses_it`
(`crates/codeflow-cli/tests/ci_cli/line_tip.rs`) builds issue #489's four
steps: a line published at tip T, a candidate C of T, a no-ff merge and one
plain commit, `codeflow ci --base T --head C`, then the pre-push hook for C
onto the line. On the unchanged code `codeflow ci` exits 0 with no finding
(the fixture fails at its first assertion: exit `Some(0)`, expected
`Some(1)`); the hook refuses the same push with `work.epic_line`
(`epic_line_push`, `crates/codeflow-core/src/hooks/git_hook.rs:1302`).
Nothing in `codeflow ci` raises that rule. Its only epic-line work is the
proof for an `integration/`-named head (`classification.rs:639`, and
`verified_epic_line` in `ci.rs`), which judges a line's range into its
target.

**The destination rule changes.** The planned rule judged every range whose
destination is a line, with `--into <line>` naming it. Three callers name a
line as the destination for a task head: the hosted pull request job
(`GITHUB_BASE_REF`), the pre-push hook's hand-off (`--into=<declared
target>`, `push_set.rs`) and a bare run on a task branch (its declared
target). A task head lands by a no-ff merge whose first parent is the line
tip, so its own commits never sit on the line's first-parent history;
judging those heads as the line's next tip would refuse every task pull
request. In the code, `--into` without the hook's hand-off already marks a
pull request landing check (`pr_context` in `ci.rs`). So the check decides
by how the head reaches the line, from the run's context, never from the
head's branch name (coordinator direction, 16:55):

- A pull request body or event, or `--into`: the head lands by merge and is
  not a line tip. Not judged.
- A push hand-off (`--pushed-ref`, which the hook now always passes, or
  `--advertisement-stdin`): the hook judges a push to a line itself. Not
  judged.
- `--line-tip <LINE>`: the head is that line's next tip. Judged.
- Otherwise, a base that is the fetched tip of exactly one
  `integration/EPC-*` line: the run cannot tell a landing candidate from a
  pull request head, so the head is judged as that line's next tip and a
  direct commit refuses with a remedy naming both routes (`--line-tip` for a
  candidate; `--into` or the body for a pull request head). Two lines at the
  base refuse; none means no line destination, and a status line says so.

The coordinator asked that a run which cannot tell which applies refuse. The
first build made that case a warning instead, because five existing tests
run a bare `codeflow ci` on a task or planning branch whose base is its
line's tip (`acceptance_cli`
`imports::deleted_home_imports_are_proven_at_the_published_default_landing`
and four `ci_cli` `range_context` tests), and `ci-generic.sh` runs that
shape outside a pull request event. The cross-lineage review (Codex,
2026-11-01) found the warning contradicts AC-4, and the coordinator's
ruling stands: the case refuses. The cost: a bare `codeflow ci` on a task
branch whose line is fetched now refuses its own commits until the run
names its role (`--into <LINE>`), and a `ci-generic.sh` run outside a
pull request event needs `CODEFLOW_PR_BODY`; its header says so. The four
`range_context` tests keep judging base selection and assert that the role
refusal is their only finding; the imports test passes `--into`.

A new line is cut from `main`, so its tip is often `main`'s tip as well.
A base at that commit cannot say whether the head lands on `main` or
becomes the line's next tip, and no fact the requester cannot forge tells
them apart. Decision by coord/planning, 2026-11-01 21:01: that run is
ambiguous and refuses, as the recorded design and the operator's
secure-by-default rule (2026-10-24: fail closed when a check cannot be
sure) both require; the refusal names the role flag the run needs
(`--into main` for a change into the default target). A build that read
such a base as `main` was reverted before landing. `release_line_cli`'s
release push runs pass the push hand-off (`--pushed-ref`) and its planning
pull request run passes `--into`
(`a_bare_run_at_a_fresh_line_and_main_refuses_naming_the_role`,
`the_same_run_into_main_passes_with_its_role`). A head that is its base adds
no commit, so it is not judged however it lands; the two commit ids decide
that, not a name.

A head named like a task and offered as a line tip is therefore refused
(AC-5); the same head as a pull request head is not a line tip.

**Authorities the check reads.**

- The line's trusted tip: `refs/remotes/origin/<line>`, resolved once to a
  commit (`line_adoption::fetched_tip`). A local branch, a supplied base and
  anything the head names are never the tip. No fetched tip refuses.
- The line's binding: `epic_line_bound_at` (split from `epic_line_binding`
  in `work_start.rs`) at that tip: the epic exists there, not cancelled or
  archived, and a task of that epic there names this line. Records only in
  the head do not bind.
- The range: always from the pinned tip to the head
  (`line_adoption::check_range`), whatever `--base` says; a head that does
  not contain the tip refuses.
- Tracking: `durable_work_tracking_enabled_at` at the head, the line tip and
  the default target; on at any one turns the check on, and an unreadable
  state refuses.
- Adoption entries: the ones `check_range` reads (at the head, and landed at
  the default target from `default_work_target_ref` or first arrived on the
  line by a merge). A malformed head entry refuses, even with no direct
  commit.
