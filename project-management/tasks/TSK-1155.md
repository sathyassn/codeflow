# TSK-1155: codeflow ci refuses a direct commit on an integration line before the gate runs

## Description

Source: issue #489 (CodeFlow 3.1.1, by an adopter), read at commit
`4880597073` (the step 4 planning branch head) after a search found no open
task that covers it. A landing candidate for an integration line held one
commit made directly on it (a task's completion record) after a no-ff task
merge. `codeflow ci --base <line tip> --head <candidate>` and the full gate
passed; the pre-push hook then refused the push with `work.epic_line`. The
gate (about 12 minutes there) had run on a candidate that could never land,
and the candidate and the next two queued landings were rebuilt.

Cause, read on the tip above:

- The rule is raised only by the pre-push hook: `epic_line_push`
  (`crates/codeflow-core/src/hooks/git_hook.rs:1302`) calls
  `line_adoption::check_range` over the pushed range and emits
  `work.epic_line` (`:1396`). Nothing in `codeflow ci` emits that rule id.
- `codeflow ci` runs `check_epic_line_with_adoptions` only when the head's
  branch name starts with `integration/`
  (`crates/codeflow-cli/src/cmd/ci/classification.rs:639`), and that
  judges the line's range into the default target. A candidate named
  otherwise, with the line tip as base, reaches no epic-line check.
- The hook's own doc comment says a range it cannot read is a note because
  "CI stays the hard line (charter D19)" (`git_hook.rs:1293-1301`). CI does
  not hold that line for this rule today, so the hook is the only check.

Overlap checked, none found: TSK-1151 (records-only landing candidates, PR
486, coord/parallel) changes which checks a candidate's class selects
(`classification.rs`), not the epic-line rule; TSK-1089 keys line treatment
on a branch's commits for a line-to-main range, not a range onto the line;
TSK-433 and TSK-248 are complete; TSK-402 judges a carry merge onto another
line and must keep passing here (a merge is not a direct commit). The nearest
region is coord/parallel's: this task lands in `codeflow ci`'s candidate
classification beside TSK-1151, so the two are one writer at a time, and the
candidate-checking route is the parallel lane's to use.

Design. `codeflow ci` judges a range whose destination is a confirmed
integration line with the same `line_adoption::check_range` the hook runs,
and reports the same `work.epic_line` finding with the same remedy. The
destination comes from the run's inputs, never from the head's branch
name:

- With `--into <line>` (or the pre-push destination), the line is that ref.
- With no `--into`, as in the issue's invocation, the line is the one
  `integration/EPC-*` remote-tracking ref (as fetched) whose tip is exactly
  the base commit. Zero such refs means the range is not a landing on a line:
  ordinary behaviour, with a note that no line destination was found. Two or
  more refuse, naming them.
- The line is bound by `epic_line_binding`
  (`crates/codeflow-core/src/workgraph/work_start.rs:883`) read at the
  trusted tip, never at the head, as TSK-1089 does
  (`project-management/tasks/TSK-1089.md:60-74`). The trusted tip is the one
  the destination advertises for that exact ref, resolved once to a commit at
  the start of the run (the remote-tracking ref as fetched for a local run),
  never a local branch, a requester-supplied anchor or a commit the head
  names. A line whose authority cannot be established refuses.

A destination confirmed to be something else, such as `main`, keeps ordinary
behaviour: this rule adds nothing there. Fail closed for an intended line: a
binding that cannot be established, an ambiguous destination, history that
cannot be read, and malformed adoption entries each refuse in `codeflow ci`
with the cause, since CI is the hard line. The adoption entries are the ones
`check_range` already reads (landed at the target or in the line's history);
the head alone cannot adopt its own direct commit.

Non-goals: the hook keeps its note for an unreadable range (charter D19);
no change to which direct commits an adoption entry may excuse.

## Outcome

After this merges, a maintainer sees a direct commit on a landing candidate
in `codeflow ci` before the full gate runs, so the candidate is rebuilt
without a wasted gate.

## Deliverables

- the CI epic-line check: `crates/codeflow-cli/src/cmd/ci/classification.rs` (and the range's destination in `crates/codeflow-cli/src/cmd/ci/context.rs`), reusing `crates/codeflow-core/src/workgraph/line_adoption.rs`
- tests: `crates/codeflow-cli/tests/ci_cli/` (a CLI fixture per case) and the existing hook journey test as the control
- docs: `docs/cli.md` (the `--into` destination and the finding) and the landing text in `git-rules.md` "Bodies of work" (managed source and this repository's copy) where it names where the rule is checked
- release note: `changelog.d/TSK-1155.md`

## Acceptance Criteria

- AC-1 Before any change, the builder shall reproduce issue #489's four steps on the line tip, record that `codeflow ci` reports nothing while the hook refuses, confirm the Description's destination rule (explicit `--into`, else the base commit being the tip of exactly one fetched `integration/EPC-*` ref) against the code or record why it changes, and name every authority the check reads and where each trusted tip comes from; evidence: a Findings section in this record, committed before the first code change.
- AC-2 When a range's destination is a confirmed integration line and the range holds a commit made directly on it that no landed `line_adoptions` entry names, `codeflow ci` shall raise `work.epic_line` with the pre-push hook's message and remedy, naming the commit; evidence: a CLI fixture of the issue's repro (tip, a no-ff task merge, one plain commit), failing before the change with no finding and passing after.
- AC-3 The same candidate shall get the same verdict through `codeflow ci` and through the pre-push hook, for a refused range and for a clean one (a candidate of merges only, and a direct commit that an adopted entry names); evidence: the fixture through both forms, each agreeing, and the existing hook test unchanged.
- AC-4 `codeflow ci` shall refuse, naming the cause, and never skip: (a) an intended line (named by `--into`, or found from the base) whose binding cannot be established at the trusted tip, or that two lines claim, including a fabricated local line ref, a requester-supplied anchor and binding records that exist only in the head; (b) history or adoption entries that cannot be read; (c) a malformed adoption entry in the head; (d) a head that deletes the epic's records to switch the check off (tracking judged at the head or the target, as the hook does); and (e) an adoption entry that exists only in the head's own commit and has not landed; evidence: one fixture per case (five), each refused after the change.
- AC-5 A head branch named `integration/...` or like a task on a destination confirmed to be something else (such as `main`, or no line found) shall grant or remove nothing: the check follows the destination only, so this rule neither fires nor is skipped by the head's name; evidence: fixtures for both names, one on a confirmed line with a direct commit refused, and one on `main` where this rule raises nothing and the ordinary verdict is unchanged.
- AC-6 `docs/cli.md` and the landing text in `git-rules.md` shall state that `codeflow ci` checks a direct commit on a line before the gate, name how the destination is given, and match the managed copy; evidence: the doc diff and `codeflow validate --docs` green.
- AC-7 (journey) With the built binary in a scratch full-tier repository with one integration line, the issue's four steps shall be refused by `codeflow ci` before any gate and the repaired candidate (the task's completion made on the task branch and merged) shall pass; evidence: both runs, quoted in the PR body.
