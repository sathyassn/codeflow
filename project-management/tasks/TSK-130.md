# TSK-130: guidance retention evals across compaction

## Description

Nothing measures whether the agent still follows the rules deep into a
session or after compaction, and cf-evaluate-model treats a reused session
as contamination. This task adds a declared scripted multi-turn case kind to
the protocol (the fixture supplies a turn script, only the probe turn is
graded) and a guidance-retention pack for the three hard cases: estimate
volunteered in a plan, outcome-first status, and spontaneous cf-present,
each with a paired negative. It runs against a freshly scaffolded fixture
project, since that is what adopters get, in a fresh arm and an after-
compaction arm. The full five-arm matrix is out of scope. Source: research
map "Evaluation that proves it"; Fable challenge F3.

## Affected surfaces and interfaces

- `cf-evaluate-model` protocol text, `resources/packs.json` and
  `resources/fixtures.json` (append-only), all mirrors and the manifest.
- Fixture settings for cheap auto-compaction
  (`CLAUDE_CODE_AUTO_COMPACT_WINDOW`), inside disposable fixtures only.

- Kind: a case with a `session` block of kind `scripted-multi-turn` takes
  its warm-up turns from the fixture's `script`, its probe from the case
  `prompt`, and is graded on the probe turn only. Each arm is its own case
  (`-fresh`, `-after-compaction`), so results, scoring and comparison keep
  the existing trial shape; the validator requires both arms of a probe to
  match in everything but the arm.
- Arms: fresh sends the probe as turn 1 with no warm-up and no window.
  After-compaction sends 11 warm-up turns (rebuild a generated support
  archive, then read ten 44 KB weeks of it) with
  `CLAUDE_CODE_AUTO_COMPACT_WINDOW=100000` in the fixture's
  `.claude/settings.local.json`, which the scaffold's gitignore keeps out of
  fixture history. The variable's range (100,000 to 1,000,000, a plain
  integer) is from the Claude Code environment-variable reference, and the
  name is present in the installed 2.1.283 binary. Both arms are
  Claude-host cases.
- Pack: `guidance-retention`, three hard probes (a landing time asked for in
  a plan, "Where do we stand?", a cross-repository release explanation) and
  three paired negatives (a feature list, a ticket number, one command), on
  three standard-tier fixtures. Two new hard requirements, `CF-EST-005` and
  `CF-OUT-006`, are owned by the map and the rule references; the
  explanation cases use `CF-PRES-001` and `CF-OUT-003`. Probes never name
  the rule. The status and explanation probes also trigger TSK-128's prompt
  reminder (122 and 152 bytes); the estimate probe does not, so it tests
  the map and the compaction block alone.
- Harness: the materializer refuses a scripted case when the fresh scaffold
  lacks the rule map or the re-injection hooks, writes no `TASK.md`, and
  keeps the turn plan in the evaluator-side trial record. `check-session`
  checks a Claude Code transcript (one session, typed turns exactly the
  plan, no compaction in the fresh arm, automatic compaction inside the
  warm-up followed by the `SessionStart:compact` hook in the other), names
  the validity flag of any failure, extracts the probe turn with its digest
  and runs the case's detectors. `retention-report` recomputes statuses and
  applies AC-5's bar.
- Review round 1 (Codex at f91d9fdc5, changes requested; Fable at
  f91d9fdc5, changes requested). Each counterexample is a test that failed
  before the fix (13 failures, `test_retention_pack.py`):
  - R130-1: `retention-report` requires original trials 1 to 3 (1 for a
    negative); a retry takes the next number and adds to the tally, so an
    original failure stays; one native session (trace or session evidence
    reference) counts once; trial numbers are positive integers.
  - R130-2 and Fable 4: `check-session` refuses a record whose plan is not
    the case's own plan by `session_digest`, which `materialize` now writes;
    a completed scored trial carries its `check-session` output, cited by a
    session evidence digest and keeping every flag the check raised.
  - R130-3: every message needs one native session id and a `uuid`; a reply
    belongs to the typed turn it descends from by `parentUuid` (a compact
    boundary's `logicalParentUuid`), each turn must finish before the next,
    and the probe needs its own finished reply.
  - R130-4: each automatic compaction needs its own re-injection hook
    record before the next compaction or the probe; the message says "no
    record of" rather than claiming the hook never ran (Fable 3).
  - Fable 1: the explanation probe needs cf-present opened or offered with

What TSK-116's live run does, on the installed combined candidate:
materialize each of the 12 cases per trial (3 trials for each hard case and arm, 1 for each
negative and arm), run each in a fresh native Claude Code session typing
the plan's turns in order, keep the session JSONL outside the fixture, run
`check-session` on it, grade the probe excerpt (deterministic detectors,
then the other vendor against the fixture's grading note, a human on every
hard failure), record the trials, and run `retention-report`. Live
auto-compaction through the fixture's local settings has not been observed
yet; the first after-compaction trial shows it, and `check-session` marks a
trial without it `broken_fixture`. The smoke session before the matrix
confirms the transcript fields the checker reads (`uuid`, `parentUuid`,
`logicalParentUuid`, `stop_reason`, hook records with `stdout`); none has
been seen in a native transcript from this build.
