# TSK-451: One record per completed fact

## Description

One fact is recorded in several places and then cross-checked. Criteria and
evidence live in the task record, the acceptance block, the PR Testing
section, the verdict and an evidence ledger; the review verdict is in the PR
Reviews row, the acceptance block and the verdict text, and `codeflow ci`
blocks when the Reviews row and the acceptance block differ
(`crates/codeflow-cli/src/cmd/ci.rs:975-1090`). Release impact is judged by
`codeflow ci`, by `scripts/release.py check-pr` and by the pre-push preflight
(`pr_body.rs:1395-1495`, `push_set.rs:177-183`). A task PR cannot amend its
own task's criteria without a separate planning PR
(`crates/codeflow-core/src/workgraph/amendment.rs:385-454`). Source: the
operator approved process audit of 2026-10-23 (line numbers at `c9993bcf3`).

Scope: (1) The acceptance block is the completion record. `codeflow ci`
derives the Reviews row from it, prints it, and warns when the PR body names
something different. (2) No separate evidence ledger in any template, check
or record (the guidance text is TSK-452). (3) A task PR may amend its own
task's record (criteria, follow-ups), with a reason per removed criterion in
the PR body; any change to another task, an epic or a status that is not its
own still needs a planning PR. (4) `validate --docs` runs once per
`codeflow ci` invocation, as `work.valid_graph`; the separate pre-push step
and quick-target copy are TSK-449. (5) Release impact has one generic evaluator, the policy-controlled
reading in `ci/pr_body.rs` (`git.pr_release_impact`, enforced at the level the
project sets, including `block`), which every caller uses. This repository's
duplicate invocations are deduplicated through an explicit configuration:
`scripts/release.py check-pr` and the `release impact` job call that evaluator
(`codeflow ci --read-release-impact`) and judge nothing of their own, and the
pre-push preflight in `push_set.rs` keeps its existing call because the
evaluator's interface does not change. An adopter without `scripts/release.py`
or a release workflow keeps its enforcement from `codeflow ci`. (6) At ready,
a code PR's Testing section cites `codeflow test --mode quick` for the head
tree; a draft owes none (the Testing hunks of `ci/pr_body.rs` are this task's,
and TSK-452 owns the guidance that asks for it). (7) The PR template and the
task and PR templates shrink to match. Research and
review-only work needing no durable record is guidance (TSK-452).

Non-goals: the acceptance block's binding to the reviewed commit, the
journey criterion, the `Task:` line and the human merge do not change.
Protection to keep: weakening a criterion inside the PR that is reviewed must
stay visible, so a removal without a reason is refused (AC-3).

Effect on adopting projects: a smaller PR template and fewer `codeflow ci`
refusals over duplicated facts; adopters that wrote a Reviews row keep
passing when it agrees with the acceptance block.

Owned files: `crates/codeflow-cli/src/cmd/ci.rs` (the acceptance cross-check
and `work.valid_graph` hunks), `crates/codeflow-cli/src/cmd/ci/acceptance.rs`,
the Reviews, Testing and release-impact hunks of `ci/pr_body.rs`,
`ci/classification.rs`, `crates/codeflow-core/src/workgraph/amendment.rs`,
`acceptance.rs` and `record_text.rs`, `scripts/release.py` and
`scripts/test_release.py`, `.github/workflows/codeflow-release.yml`,
`.github/pull_request_template.md`, `assets/base/ci/pull_request_template.md`,
`assets/base/pm/`. TSK-450 owns the Summary and character hunks; TSK-449 owns
`push_set.rs`.

## Acceptance Criteria

- AC-1 When a PR has a valid acceptance block, `codeflow ci` shall derive and print the Reviews row from it, shall not block when the body's Reviews row is a pointer or is absent, and shall warn when the row names a different reviewed commit or verdict. Evidence: cases in `crates/codeflow-cli/tests/ci_cli/acceptance_fix.rs`, where the review row cases live, fail before (block on mismatch) and pass after. (serves EPC-022 AC-127)
- AC-2 When the records and templates are read, no template, check or record shall carry a separate evidence ledger, the acceptance block and the PR Testing section being the only evidence homes. Evidence: a grep of `assets/base/pm/`, both PR templates and the `codeflow ci` sources for the ledger, with the empty result in the PR, plus the template tests. (serves EPC-022 AC-127)
- AC-3 When a task PR changes its own task's criteria or follow-ups, `codeflow ci` shall accept it with the reason in the PR body, shall refuse a removed criterion without a reason, and shall still require a planning PR for any change to another task, an epic or a status that is not its own. Evidence: cases in `crates/codeflow-cli/tests/planning_amendment.rs`, one per branch. (serves EPC-022 AC-127)
- AC-4 When `codeflow ci` runs, it shall run the docs validation exactly once, as `work.valid_graph`. Evidence: a test that counts the validation runs in one invocation. (serves EPC-022 AC-127)
- AC-5 When release impact is read, `codeflow ci`, `scripts/release.py check-pr` and the pre-push preflight shall use the one evaluator, and this repository's `release impact` job shall judge nothing separately. Evidence: `scripts/test_release.py`, `crates/codeflow-cli/tests/release_contract.rs` and `release_impact_corpus.rs` over the same bodies, and a grep showing one evaluator implementation. (serves EPC-022 AC-127)
- AC-6 When a unit lands under the new rules (journey), its PR shall pass with the Reviews row derived, its own task record amended in the same PR with a reason, and one validation run. Evidence: this task's own PR checks and `codeflow ci` output. (journey) (serves EPC-022 AC-127)
- AC-7 When an adopter project has no `scripts/release.py` and no release workflow and sets `git.pr_release_impact=block`, `codeflow ci` shall pass a valid release-impact section and shall block a missing migration or an inconsistent breaking and impact. Evidence: an adopter-fixture case in `crates/codeflow-cli/tests/adopter_fit.rs` or `release_contract.rs` with both outcomes. (serves EPC-022 AC-127)
- AC-8 When a code PR is made ready, its Testing section shall cite `codeflow test --mode quick` for the head tree, `codeflow ci` shall report a missing citation at the level of the existing Testing check, and a draft shall owe none. Evidence: a `codeflow ci` classification test with a draft case and a ready case without the citation. (serves EPC-022 AC-127)
