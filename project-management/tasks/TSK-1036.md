# TSK-1036: A blocked task can be unblocked in its own pull request

## Description

Issue #365 (CodeFlow 3.1.1, `48104f48b`). A task whose record is
`blocked` on the target cannot be moved to `todo`, or on to `complete`,
by a pull request that names it. The only range that passes is a
planning amendment on a `plan/` branch whose `Task:` line names some
open epic, even one the range does not touch. The documented route says
otherwise: `cf-method` `references/project-organization.md:320` says a
status change "rides in the task's PR", and its table (`:328`) lists
"blocked to todo | `codeflow task status TSK-NNN todo`". Blocking is
asymmetric: `todo -> blocked` passes in the task's own pull request,
because the merge-base still holds `todo`.

Sites, read on the line tip `5f2fe3827` (the issue cites 3.1.1 lines):

- `crates/codeflow-core/src/workgraph/work_start.rs:1874`
  `check_task_anchor` reads the status at the merge-base and projects
  only a reopen of a complete task (`:1904-1931`); `start_gate`
  (`:2310`) then refuses the blocked base record. This holds for epic
  tasks as well as standalone ones (code reading; the issue ran the
  standalone case).
- `crates/codeflow-core/src/workgraph/lifecycle.rs:1032` refuses
  `blocked -> complete`, and `judge_range_against` (`:2026`) judges the
  range whole, so a separate unblock commit does not help.
- The refusal is raised at `crates/codeflow-cli/src/cmd/ci.rs:1715` and
  `crates/codeflow-cli/src/cmd/ci/classification.rs:986`; its remedy,
  `crates/codeflow-core/src/remedy.rs:244-248`, says to commit the
  record on this branch, which a record already on the target cannot
  satisfy.
- `crates/codeflow-core/src/workgraph/amendment.rs:10` lists a
  standalone task's change in an amendment ("listed, never refused"),
  but the planning class needs at least one `Task: EPC-NNN`.

TSK-1022 (this epic) is blocked on TSK-1002. Its unblock does not wait
on this task: it rides in the EPC-022 batched amendment that adds
`depends_on: [TSK-1002]` once PR 346 lands, a graph change that belongs
in an amendment anyway, and the issue shows that route passes.

Outcome: **a task's own pull request can move it from `blocked` to
`todo`, and on to `complete` when its work is done, with the Blocker
removal shown to the reviewer; the remedy names a route that works;
and the documented status route matches what CI accepts.**

Rules:

- The unblock is judged on what the range does: the head record has no
  Blocker and the status passes through `todo`, so the start gate judges
  `todo`, as a reopen is projected today. Every other planning input
  still comes from the merge-base.
- A head that unblocks a task whose blocker names an unfinished
  predecessor is judged by the ordinary `depends_on` rules; the unblock
  never admits work the graph does not.
- A planning amendment that changes only standalone records needs no
  epic on its `Task:` line, or the docs say why one is required; AC-1
  decides.

Non-goals: the repeated-closeout sequence (TSK-340), which this task
builds on.

## Acceptance Criteria

- AC-1 Before any change, the builder shall investigate broadly: run the issue's sequence for a standalone task and for an epic task on the line tip; list every status transition and which pull request route (own task branch, `plan/` amendment, cancellation route of TSK-414) accepts it today; compare the documented status table with that list; check adjacent paths that read the merge-base status (`work start`, `work claim`, `work next`, pre-push, the start-claim checks); and record the findings and the chosen scope in this record before any change; evidence: the record section, committed before the first code change in the PR.
- AC-2 When a task's own pull request changes its record from `blocked` to `todo` with the Blocker removed, `codeflow ci` and `codeflow work start` shall accept it for a standalone task and for an epic task, and the PR evidence shall show the removed Blocker; evidence: CLI fixtures for both, failing before the change with the issue's refusal. (serves EPC-022 AC-144)
- AC-3 When a task's own pull request moves it `blocked -> todo -> complete` across its commits, the range shall be accepted when each step passes its own rule, and a direct `blocked -> complete` in one commit shall still be refused; evidence: CLI fixtures for both. (serves EPC-022 AC-144)
- AC-4 A head that removes a Blocker while a `depends_on` predecessor is incomplete, or that changes another record's status, shall still be refused; evidence: negative fixtures.
- AC-5 The refusal's remedy shall name a route that works for a record already on the target, and the status table in `project-organization.md` shall match what CI accepts, including whether a standalone-only amendment needs an epic on its `Task:` line; evidence: a remedy test and the doc diff.
- AC-6 (journey) With the built binary in a scratch full-tier repository, the issue's steps shall pass for ranges main..A and main..B; evidence: the journey output.
