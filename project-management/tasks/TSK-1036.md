# TSK-1036: A blocked task can be unblocked in its own pull request

## Description

Issue #365 (CodeFlow 3.1.1, `48104f48b`). A task whose record is
`blocked` on the target cannot be moved to `todo`, or on to `complete`,
by a pull request that names it. The only range that passes is a
planning amendment on a `plan/` branch whose `Task:` line names some
open epic, even one the range does not touch. The documented route says
otherwise: `cf-method` `references/project-organization.md:320` says a
status change "rides in the task's PR", and its table (`:328`) lists
"blocked to todo | `codeflow task status TSK-NNN todo`". Blocking is
asymmetric: `todo -> blocked` passes in the task's own pull request,
because the merge-base still holds `todo`.

Sites, read on the line tip `5f2fe3827` (the issue cites 3.1.1 lines;
the `lifecycle.rs` lines were refreshed on `53749287c` on 2026-10-29):

- `crates/codeflow-core/src/workgraph/work_start.rs:1874`
  `check_task_anchor` reads the status at the merge-base and projects
  only a reopen of a complete task (`:1904-1931`); `start_gate`
  (`:2310`) then refuses the blocked base record. This holds for epic
  tasks as well as standalone ones (code reading; the issue ran the
  standalone case).
- `crates/codeflow-core/src/workgraph/lifecycle.rs:1148` refuses
  `blocked -> complete`, and `judge_range_against` (`:2197`) judges the
  range whole, so a separate unblock commit does not help.
- The refusal is raised at `crates/codeflow-cli/src/cmd/ci.rs:1715` and
  `crates/codeflow-cli/src/cmd/ci/classification.rs:986`; its remedy,
  `crates/codeflow-core/src/remedy.rs:244-248`, says to commit the
  record on this branch, which a record already on the target cannot
  satisfy.
- `crates/codeflow-core/src/workgraph/amendment.rs:10` lists a
  standalone task's change in an amendment ("listed, never refused"),
  but the planning class needs at least one `Task: EPC-NNN`.

Issue #400 (CodeFlow 3.1.1) is the same range judgment seen from a
sync merge. `judge_range_against` compares each changed record only
between the merge-base copy (`:2209`, one old copy at `:2260`) and the
head copy, so a merge of `main` that carries `blocked -> todo ->
complete` is read as `blocked -> complete` and refused (`:1148`). The
triage of 2026-10-29 reproduced it on the line with `codeflow ci`: the
sync merge range is refused, each of the two commits alone gave no
`work.records` finding, and the plain two-commit range is refused too.
The issue itself reports that pushing the sync in two steps passes; the
pre-push hook was not run in the triage. The endpoint rule
has a gap in the other direction: `todo -> cancelled -> todo` in one
range nets to `todo -> todo` and passes, although its second step alone
is refused because a cancelled task is terminal. Judging each step on
its own commit closes both. As an argument about status transitions
only, it accepts nothing that two separate pushes would not already
accept; it proves transition legality, not review or authorship, which
TSK-1066 owns. AC-7 carries it, because the fix is one change to the
same function as AC-3.

TSK-1022 (this epic) is blocked on TSK-1002. Its unblock does not wait
on this task: it rides in the EPC-022 batched amendment that adds
`depends_on: [TSK-1002]` once PR 346 lands, a graph change that belongs
in an amendment anyway, and the issue shows that route passes.

Widened 2026-10-30 for issue #424 (CodeFlow 3.1.1, by an adopter, the
same root as #400). On `main` a record went `blocked -> todo` and then
`todo -> complete` in two commits; a line holding it at `blocked`
merged `main` in one step, and `work.records` refused the range as
`blocked -> complete`. Merging `main` in two stages, one per step,
passed each time and ended at the identical tree. The verdict on a
status change shall not depend on how the same history was split into
merges. AC-7 already requires the one-merge sync to pass; AC-8 adds the
reporter's two shapes as fixtures and the same-tree comparison.

Outcome: **a task's own pull request can move it from `blocked` to
`todo`, and on to `complete` when its work is done, with the Blocker
removal shown to the reviewer; the remedy names a route that works;
and the documented status route matches what CI accepts; and a range
is judged step by step, so a sync merge that carries legal steps passes
and a hidden illegal step is refused.**

Rules:

- The unblock is judged on what the range does: the head record has no
  Blocker and the status passes through `todo`, so the start gate judges
  `todo`, as a reopen is projected today. Every other planning input
  still comes from the merge-base.
- A head that unblocks a task whose blocker names an unfinished
  predecessor is judged by the ordinary `depends_on` rules; the unblock
  never admits work the graph does not.
- A planning amendment that changes only standalone records needs no
  epic on its `Task:` line, or the docs say why one is required; AC-1
  decides.

Non-goals: the repeated-closeout sequence (TSK-340), which this task
builds on.

- AC-2 When a task's own pull request changes its record from `blocked` to `todo` with the Blocker removed, `codeflow ci` and `codeflow work start` shall accept it for a standalone task and for an epic task, and the PR evidence shall show the removed Blocker; evidence: CLI fixtures for both, failing before the change with the issue's refusal. (serves EPC-022 AC-144)
- AC-3 When a task's own pull request moves it `blocked -> todo -> complete` across its commits, the range shall be accepted when each step passes its own rule, and a direct `blocked -> complete` in one commit shall still be refused; evidence: CLI fixtures for both. (serves EPC-022 AC-144)
- AC-4 A head that removes a Blocker while a `depends_on` predecessor is incomplete, or that changes another record's status, shall still be refused; evidence: negative fixtures.
- AC-5 The refusal's remedy shall name a route that works for a record already on the target, and the status table in `project-organization.md` shall match what CI accepts, including whether a standalone-only amendment needs an epic on its `Task:` line; evidence: a remedy test and the doc diff.
- AC-6 (journey) With the built binary in a scratch full-tier repository, the issue's steps shall pass for ranges main..A and main..B; evidence: the journey output.
- AC-7 (issue #400) When the commits of a range move a record through legal statuses one step at a time, `codeflow ci` and the pre-push hook shall judge each step on its own commit and accept the range, for a multi-commit range and for a merge that brings those commits from the target (a sync of `main` into an integration line). An illegal step shall be refused even when the endpoints of the range look legal: a direct `blocked -> complete` in one commit, and a terminal status entered and then left inside one range (`todo -> cancelled -> todo`). A merge shall be judged against every parent, whether or not its record matches one of them: each parent-to-merge change shall be a legal step or the chain of legal steps recorded in the commits the merge brings in from the other side (so the sync of issue #400 passes), and a merge that revives a task cancelled on the other side by taking the other side's `todo` shall be refused. History that cannot be read shall refuse, and shall never fall back to the endpoints, which let `todo -> cancelled -> todo` through; the remedy shall name the cause: for shallow history, fetch the full history (`git fetch --unshallow`, or a checkout with full depth); for a missing object, fetch or repair the object store; for an unparsable record, fix that record (a fetch does not repair it). A record absent at a readable parent is a creation, not unreadable history. No remote-tracking ref or default-branch tip shall exempt a step from judgment, and the guarantee covers the history supplied and verified, since a rebase or squash that erased a step cannot be recovered. Evidence: CLI fixtures through `codeflow ci` and the pre-push hook, each failing before the change and passing after: (a) the shape of issue #400 (`blocked` on the line, `blocked -> todo -> complete` on `main`, merged into the line), failing before with `status blocked -> complete is refused`; (b) `todo -> cancelled -> todo` in one range, accepted before and refused after with the terminal-status message. Negative fixtures, each refused after the change: a direct `blocked -> complete` in one commit, a hand-edited merge record with an illegal step from some parent (with a legal resolution as the control), a task cancelled on one side with a merge taking the other side's `todo`, and, one fixture per cause, a shallow history, a missing object and an unparsable record, each with its cause-specific remedy and none accepted. (serves EPC-022 AC-144)
- AC-8 (issue #424) Under AC-7's rules (each merge judged against every parent, unreadable history refused, no ref exempting a step), a transition brought in through a merge parent shall be accepted when each step on that parent's first-parent chain is legal, and the one-merge and two-merge syncs of the same `main` history, which end at the same tree, shall get the same verdict through `codeflow ci` and the pre-push hook; a direct illegal edit in the range shall stay refused; evidence: fixtures of the reporter's shapes (the line at `blocked`; `main` moving the record `blocked -> todo` then `todo -> complete` in two commits; the line merging `main` once, and in two stages), the one-merge shape refused before the change and both accepted after, and a direct `blocked -> complete` edit in the range, refused. Added 2026-10-30 for issue #424. (serves EPC-022 AC-144)

## Findings (AC-1)

Investigated 2026-11-01 on the line tip `bee344658`, before any code change.

The issue's sequence, run as the journey fixtures in
`crates/codeflow-cli/tests/acceptance_journey/unblock.rs` against the
unchanged tree: for an epic task (TSK-002 on its line) and a standalone task
(TSK-003 on the default branch), the range main..A (the unblock commit) is
refused with `work.stable_planning_anchor: task TSK-00N is blocked: waits on
the host`, and the remedy says to merge the epic's planning change or commit
a standalone record on the branch, which a record already on the target
cannot do. Range main..B is refused the same way and also by `work.records`
(`status blocked -> complete is refused`), as the issue reports.

Each task transition and the pull request route that accepts it today
("run" means a fixture ran it; "code" means read from `start_gate` in
`work_start.rs`, which judges the merge-base status, and
`task_transition_allowed` in `lifecycle.rs`):

| Transition | Own task PR | `plan/` amendment | TSK-414 cancellation route |
|---|---|---|---|
| todo to blocked | accepted (base is todo; code) | listed, never refused (code) | not applicable |
| blocked to todo | refused by the start gate (run) | accepted only with an open epic on the `Task:` line (issue) | not applicable |
| blocked to todo to complete | refused by the start gate and by the endpoint rule (run) | not a route: completion binds the task PR | not applicable |
| todo to complete | accepted (code) | not a route | not applicable |
| todo to cancelled | accepted (code) | listed (code) | an unlanded standalone record only (code) |
| blocked to cancelled | refused by the start gate (code) | listed (code) | an unlanded standalone record only (code) |
| complete to todo (reopen) | accepted, projected by TSK-140 (code) | not a route | not applicable |
| cancelled to anything | refused: terminal (code) | refused (code) | not applicable |

The documented table in `cf-method` `references/project-organization.md`
says every status change rides in the task's pull request. Two rows did
not hold for a record already blocked on the target: blocked to todo, and
blocked to cancelled.

Adjacent paths that read the merge-base status:

- `codeflow work start` runs the same `check_task_anchor` on the checkout,
  so it refused the unblocked branch too.
- The pre-push hook and pre-commit call the same admission and the same
  `work.records` judgment, so they follow whatever this task changes there.
- `codeflow work claim` and `codeflow work next` read the target tip, where
  the task is still blocked; they keep reporting it blocked, which is
  correct. The unblocking pull request starts from a branch cut from the
  target, not from a claim.
- The range rule (`judge_range_against`) compares only the merge-base and
  head copies, so a sync merge carrying `blocked -> todo -> complete` is
  refused (issue #400), and `todo -> cancelled -> todo` nets to no change
  and passes; a record whose endpoints match was skipped entirely.

Chosen scope:

- `check_task_anchor` projects an unblock the way it projects a reopen:
  with the base record blocked and the head (or checkout) record `todo` or
  `complete` with no Blocker, or `cancelled`, and every status step from the
  merge-base read and legal, the start gate judges `todo`. Dependencies,
  specs and every other planning input still come from the merge-base.
- A new step judgment (`workgraph/status_steps.rs`) judges each commit
  against each parent. A merge that takes another parent's status is
  accepted when that parent's first-parent chain, back to the first commit
  the other parent contains, is legal step by step and the other parent
  still holds that commit's status. Unreadable history refuses with its
  cause. `judge_range_against` lifts the endpoint refusal only when every
  step is proven, and also judges records touched inside the range whose
  endpoints match.
- The blocked refusal gets its own remedy (`WORK_START_UNBLOCK`), and
  `codeflow ci` prints the removed Blocker as a notice (`RECORD_UNBLOCKED`).
- A standalone-only planning amendment keeps needing an epic on its
  `Task:` line: the `plan/` class names the epics whose plan it changes, a
  standalone task's status now rides in its own task pull request, and an
  unlanded standalone cancellation keeps the TSK-414 route. The status
  table says so.
- Not in scope: `work claim` of a blocked task, and the carried
  cancellation of another task (TSK-1152 narrows AC-4 for that).
