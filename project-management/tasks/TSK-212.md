# TSK-212: local ci matches the hosted verdict

## Description

Two consumer reports show the local checks disagreeing with the hosted
job or printing a step the guard refuses. Report sathyassn/codeflow#22:
`codeflow ci` and the pre-push hook judge the commit, branch and PR-body
standards with the branch's own `.codeflow/policy.json`
(`crates/codeflow-cli/src/cmd/ci.rs`, `Policy::load_effective`), while
the hosted `codeflow-policy.yml` job reads the policy of the base commit
it checks out, so a branch that loosens its own policy passes locally
and fails after the push. Report sathyassn/codeflow#27: when a local
target branch is strictly behind its upstream, `work start` and `ci`
already anchor on the upstream, yet print a note whose step
(`git fetch . <upstream>:<local>`, or `git merge --ff-only` on the
branch) git-guard refuses. In the same file family, `ci` reports "could
not resolve a base ref" without the cause when git itself refuses the
base, as git 2.55 does for a `GIT_REPLACE_REF_BASE` without a trailing
slash. Non-goals: the commit-msg and other git hook stages keep reading
the working copy's policy, and the guard's rules do not change.

## Acceptance Criteria

- AC-1 When `codeflow ci` resolves its policy authority (the commit
  `--policy-from` names, else the base), it judges the commit, branch,
  PR-body and work standards with the `.codeflow/policy.json` recorded
  there, read as git data, and its banner names that commit and claims
  the hosted verdict only for a target tip; evidence: ci tests where the
  head raises the commit-body limits and adds a commit with 4 bullets,
  passing before the change and blocked after, and where `--policy-from`
  judges a fork-point range with the target tip's policy. (journey)
- AC-2 When the pre-push hook judges a pushed branch, its one candidate
  authority is the destination default branch's advertised tip, never
  another branch, protected or not; the strictly validated policy there
  sets the rules and whether and at what level the check gates the push,
  and the hook names it a candidate destination authority, not the known
  pull request target, with hosted CI as the enforcement; for a head that
  shares history with that tip, its commit checks cover everything the
  head adds to the tip, whatever history the destination already holds or
  target a task record declares, so an integration line's inherited
  commits are judged too; a branch the destination already has whose
  history shares nothing with the tip, such as a deployment branch, keeps
  its own new commits under that policy and is named not default-target
  parity, while a shallow or unreadable history keeps the tip; a policy
  there that cannot be read or validated refuses the push whether or not
  its range resolves; with no candidate authority the hook says so and
  still checks at block level where a range resolves; a failed fetch of
  the default tip is tried once per push; evidence: pushes through the
  scaffolded hook to a local destination for a first push, a second push,
  a target that tightened after the fork, a head gate of `warn` or `off`,
  a declared unprotected target, a branch that protects itself, a new
  `integration/` branch, a protected wildcard line pushed twice, a
  protected symbolic alias, an unknown declared target with the gate off,
  a fork, a malformed default policy with and without a range, a default
  policy that is not UTF-8, a commit already published as a tag, an
  earlier push the default's policy has since come to forbid, and a task
  branch declaring a line that carries a commit the default now forbids,
  each let through before the change and refused after; an existing
  unrelated deployment branch whose new commits pass, refused before and
  let through after, with its own bad new commit still refused; an
  unrelated history joined into a related branch, refused with its
  inherited commit; and a refused fetch counted once with durable work
  tracking off and on.
- AC-3 When a local target branch is strictly behind its upstream,
  `work start` and `ci` anchor on the upstream and print no step that
  git-guard refuses, and `work start`'s success line still names the
  anchored ref; evidence: the work-start unit tests, the cli flow test
  and a journey with the stale branch checked out in the root checkout
  and the task in a linked worktree, which printed the note before the
  change, plus a git-guard probe refusing both steps the note printed.
- AC-4 When git refuses to resolve the base, `codeflow ci` names git's
  own refusal and a remedy for it instead of the fetch advice; evidence:
  a ci test with a replace ref git cannot follow, generic before the
  change, and a remedy-clearing proof for the new catalog row.
- AC-5 The pending 3.1.0 CHANGELOG entry, under its release-impact
  marker, states the stricter local verdict, the dropped note and the
  named git refusal; evidence: the diff and the release-impact check.
