# TSK-1421: A project can require extra sections in its task, epic and spec records

## Description

`codeflow validate --docs`, `work start`, the task-branch pre-commit hook and task-branch CI share one check for the sections a work record must carry (`validate_workgraph`, `crates/codeflow-core/src/validate/mod.rs:116-119`). The lists are fixed in code: a task needs Description and Acceptance Criteria, an epic Summary and Acceptance Criteria, a spec Summary, Behavior and Open questions. The options type already holds the lists, but no project setting reaches it. A project that wants every task to carry, for example, a Risks or a Rollback section can only ask for it in review.

This task lets a project declare extra required sections per record kind. CodeFlow's own sections stay required whatever the project writes, because other checks parse them (acceptance criteria, Closeout). `codeflow task new`, `epic new` and `spec new` write the declared sections into new records, so a new record passes the check it will meet.

The setting is read from the same trusted source as other project enforcement, so a change cannot drop a requirement it is judged by. Records that predate the setting are judged as other new rules are on existing records (AC-1 settles whether that is a warning until the record next changes, or a baseline).

Non-goals: PR body sections (`git.pr_required_sections`, already configurable); section order or content rules; removing or renaming CodeFlow's own sections.

## Outcome

After this merges, a project maintainer can require extra sections in its task, epic and spec records, and every check that validates records enforces them, while CodeFlow's own required sections stay required.

## Deliverables

- the setting, its schema entry and docs: in the project configuration CodeFlow reads for records (provisional: a key beside `git.pr_required_sections` in `.codeflow/policy.json`, or `.codeflow/project.toml`; AC-1 decides), with `docs/policy-reference.md` or the configuration reference
- the validation change: `crates/codeflow-core/src/validate/mod.rs` (`validate_workgraph` reads the project's lists)
- the record templates and allocation: where `task new`, `epic new` and `spec new` write new records (`crates/codeflow-core/src/workgraph/allocate.rs`, provisional)
- tests named in the criteria, and a release note: `changelog.d/TSK-1421.md`

## Acceptance Criteria

- AC-1 Before any change, the builder shall record in `## Findings` the home for the setting (policy or project configuration) and why, the trusted source it is read from, how records that predate a newly required section are judged, and every caller of `validate_workgraph` that must see the project's lists; evidence: the Findings section committed before the first code change.
- AC-2 When a project declares extra required sections for a record kind, `validate --docs`, `work start`, the task-branch pre-commit hook and task-branch CI shall each refuse a record of that kind that lacks one, naming the section; evidence: one test per caller with a record missing a declared section.
- AC-3 CodeFlow's own required sections shall stay required whatever the project declares, and a setting that omits or lists them changes nothing about them; evidence: a test where the project's list leaves out Acceptance Criteria and a task without it is still refused.
- AC-4 `codeflow task new`, `epic new` and `spec new` shall write each declared section into the new record, and the new record shall pass `validate --docs`; evidence: one allocation test per kind.
- AC-5 The setting shall be read from the trusted source AC-1 names, so a change that removes a declared section from the setting is still judged by the setting it replaces; evidence: a test where the head drops a section the base requires and a record missing it is refused.
- AC-6 With no setting, every record shall be judged exactly as today; evidence: the existing validate tests passing unchanged.
- AC-7 (journey) In a scratch adopter at the standard tier, declaring one extra task section, allocating a task, removing the section and running `validate --docs` shall refuse the record, and restoring the section shall pass; evidence: the journey output in the pull request body.
