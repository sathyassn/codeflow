# TSK-349: Desktop work stays in its own session worktree

## Description

Issue 219 reports that a Claude Code desktop session can create another
worktree but its native isolation hook refuses edits there. CodeFlow's
rules allow harness-managed folders, yet do not explain that a second
unit needs a separate desktop session. The shared recovery command can
also create a nested worktree when followed from a linked checkout.

Source evidence at `cdfb4964829976bf87a61e544af196801c6eff94`:

- `assets/base/rules/worktrees.md:8` permits a harness-managed folder but does not name the desktop session boundary or anchor `.worktrees/<slug>` to the canonical root.
- `crates/codeflow-core/src/root_checkout.rs:41` supplies the relative `git worktree add .worktrees/<slug> -b <branch>` recovery command. Its default locations already include `.claude/worktrees` at line 72; the defect is not a missing allowed location.
- `assets/base/claude/skills/cf-delegate/SKILL.md:123` scopes delegate edits to a worktree but does not explain desktop session cards.
- `assets/base/settings/default.json:14` begins the permission preset; all three shipped presets omit `permissions.additionalDirectories`. `crates/codeflow-core/src/scaffold/settings_merge.rs:567` already merges incoming permission entries, so any qualified addition should use that existing ownership mechanism.
- `.agents/skills/cf-ship/references/pr-evidence.md:123` already puts gate evidence in the CodeFlow home's `gate-runs` directory. The issue's general local notes need a documented desktop-access route; they do not justify moving that established evidence store.

The native desktop refusals and repeated symlink prompts are reported by
the issue and have not been reproduced in this planning session. The task
qualifies a usable desktop route before shipping permission advice. It
preserves the app's isolation hook, root-checkout protection and existing
evidence stores. A broad grant to sibling worktrees is not an isolation
repair. The proposed universal `.dev/` layout and automatic grants are
not accepted defaults merely because the issue suggests them.

## Deliverables

- worktree placement, parallel-session and cleanup guidance: `assets/base/rules/worktrees.md`, its installed copy, and the relevant `cf-method` and `cf-delegate` resources under `assets/base/claude/skills/`, mirrored into `.claude/skills/` and `.agents/skills/`
- context-correct recovery messages and location diagnostics: `crates/codeflow-core/src/root_checkout.rs`, its callers and existing worktree/doctor tests
- durable local-evidence setup: an existing adoption guide under `docs/` and managed setup guidance, exact page provisional until the native desktop experiment identifies the supported setup route
- qualified permission settings, only where needed and supported: `assets/base/settings/`, `crates/codeflow-core/src/scaffold/settings_merge.rs` and their scaffold tests, preserving project-owned entries
- native desktop evidence: the task PR and Closeout, with app version, actual session worktrees, effective grants and negative controls
- managed wiring and release note: `assets/base/scaffold-manifest.toml`, managed mirrors and baseline, `changelog.d/TSK-349.md`

## Acceptance Criteria

- AC-1 The worktree rule and recovery messages shall distinguish CLI worktrees under the canonical repository root from desktop app-managed worktrees. A desktop session edits only its own worktree; a parallel unit gets a separate app session. Existing CodeFlow, Claude, Codex and Grok location support remains. Evidence: message/fixture checks from the root and a linked worktree, plus the revised managed guidance.
- AC-2 Instructions shall prohibit creating a worktree inside another linked worktree, and inspection shall identify that layout without removing it. Desktop cleanup shall require merge proof, an inactive native session owner and a clean worktree, preserving dirty or active sessions. Evidence: nested, ordinary, active and dirty fixtures; coordination with TSK-319 preserves its deletion contract.
- AC-3 The setup shall name one durable local-only evidence home for the project and the exact supported desktop access step, with canonical and symlink paths considered. Existing gate-run and ledger homes stay authoritative. Any required operator grant shall be scoped and reviewable; project permission choices and credential denies remain intact. Evidence: repeated note writes after the supported setup without per-edit prompts, and negative controls for root product files, sibling worktrees and denied credential paths. If the native app cannot support that access, the task records the limitation and an explicit issue disposition rather than claiming a settings key bypasses isolation.
- AC-4 Fresh init and update shall deliver the qualified instructions and any supported managed settings consistently, preserving project-owned grants and removals. Evidence: scaffold round trips, permission-merge controls, byte-identical skill mirrors, manifest wiring and baseline synchronization. No automatic broad permission expansion is authorized by this criterion.
- AC-5 (journey) On the supported Claude Code desktop version, two session cards shall perform independent work in their own app-managed worktrees and retain local evidence after one proven-landed, inactive worktree is cleaned up. Writes to the other session and root product checkout shall remain refused. Evidence: native session results for fresh and updated projects, with exact app version and any unsupported behavior stated. (serves EPC-022 AC-46)
