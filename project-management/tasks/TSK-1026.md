# TSK-1026: The managed CI cancels superseded runs and skips a proven repeat

## Description

Issue #352, items 1 and 2 (CodeFlow 3.1.1). The managed workflow
`assets/base/ci/codeflow-ci.yml` has no `concurrency` group, so a new
push to a pull request leaves the superseded run going to its end, and a
push whose tree an earlier hosted run already passed runs the whole gate
again. An adopter edited the managed file to add both and recorded it as a
workaround. The issue's item 3, sharded gates, is TSK-384 AC-5 and AC-6.

Read on the line tip `7172229aa`:

- the template has no `concurrency` key (none in its 1,079 lines); this
  repository's own `.github/workflows/codeflow-ci.yml:30-32` already uses
  a group per workflow and ref with `cancel-in-progress` only for
  `pull_request` events;
- the template runs on `pull_request`, on pushes to `main` and `master`,
  weekly and on dispatch (`codeflow-ci.yml:26-35`), and since TSK-449 a
  pull request runs the essential mode and a push the full mode
  (`:170-198`);
- this repository skips a repeated push run through
  `scripts/ci-reuse.py`; TSK-359 is hardening that lookup's binding (the
  exact merged pull request, base, tested merge tree, workflow blob and
  required jobs) and states "changing the shipped template" as its
  non-goal.

Outcome: **the managed workflow cancels a superseded pull request run, and
a push to the protected branch whose tree a bound pull request run already
passed reuses that verdict under TSK-359's binding, with the secret scan
and every security job still running.**

Design and tradeoffs:

- Concurrency: a pull request run is superseded only when a run for a
  newer head of the same pull request starts. Proposed, for AC-6 to
  confirm: a group per workflow and pull request, `cancel-in-progress`
  true only for a `synchronize` event (the one `pull_request` event that
  brings a new head), and the queue mode TSK-1040 adopts (`queue: max`),
  so a same-head event (`opened`, `reopened`, a re-run, a repeated
  arrival) neither cancels a running run nor replaces a pending one; it
  waits and completes. If AC-6 finds that expression unsound, each run
  first checks whether its head is still the pull request's head and
  stops when it is not, and same-head runs share no cancelling group.
  Runs on `main`, schedule and dispatch runs are never cancelled in
  progress, so a protected-branch verdict is always completed; GitHub may
  still replace a pending run in the same group. A push to an integration
  line is cancelled by a newer push to the same line: that is TSK-1313,
  by the operator's request of 2026-11-03, and it lands before this task. Cost: a cancelled run
  shows as cancelled on the superseded commit, which only matters for a
  commit nobody merges; a queued same-head run costs one more run.
- Reuse: the managed workflow gets the same binding TSK-359 proves here,
  read from the run's recorded provenance and executed from the trusted
  base's copy of the helper, never from the pushed tree. A full-mode push
  that reuses an essential-mode pull request verdict would weaken the
  full gate, so reuse is allowed only when the reused run's effective
  mode equals the push's effective mode. A project may opt in to running
  essential on push, which changes the push's effective mode; it never
  waives the equality. Unproven reuse runs the jobs.
- Never reused: the secret scan, the gitleaks canary, the security review
  and CodeQL, as in TSK-359.
