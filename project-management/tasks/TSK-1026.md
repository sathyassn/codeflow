# TSK-1026: The managed CI cancels superseded runs and skips a proven repeat

## Description

Issue #352, items 1 and 2 (CodeFlow 3.1.1). The managed workflow
`assets/base/ci/codeflow-ci.yml` has no `concurrency` group, so a new
push to a pull request leaves the superseded run going to its end, and a
push whose tree an earlier hosted run already passed runs the whole gate
again. An adopter edited the managed file to add both and recorded it as a
workaround. The issue's item 3, sharded gates, is TSK-384 AC-5 and AC-6.

Read on the line tip `7172229aa`:

- the template has no `concurrency` key (none in its 1,079 lines); this
  repository's own `.github/workflows/codeflow-ci.yml:30-32` already uses
  a group per workflow and ref with `cancel-in-progress` only for
  `pull_request` events;
- the template runs on `pull_request`, on pushes to `main` and `master`,
  weekly and on dispatch (`codeflow-ci.yml:26-35`), and since TSK-449 a
  pull request runs the essential mode and a push the full mode
  (`:170-198`);
- this repository skips a repeated push run through
  `scripts/ci-reuse.py`; TSK-359 is hardening that lookup's binding (the
  exact merged pull request, base, tested merge tree, workflow blob and
  required jobs) and states "changing the shipped template" as its
  non-goal.

Outcome: **the managed workflow cancels a superseded pull request run, and
a push to the protected branch whose tree a bound pull request run already
passed reuses that verdict under TSK-359's binding, with the secret scan
and every security job still running.**

Design and tradeoffs:

- Concurrency: a pull request run is superseded only when a run for a
  newer head of the same pull request starts. Proposed, for AC-6 to
  confirm: a group per workflow and pull request, `cancel-in-progress`
  true only for a `synchronize` event (the one `pull_request` event that
  brings a new head), and the queue mode TSK-1040 adopts (`queue: max`),
  so a same-head event (`opened`, `reopened`, a re-run, a repeated
  arrival) neither cancels a running run nor replaces a pending one; it
  waits and completes. If AC-6 finds that expression unsound, each run
  first checks whether its head is still the pull request's head and
  stops when it is not, and same-head runs share no cancelling group.
  Push, schedule and dispatch runs are never cancelled, so a
  protected-branch verdict is always completed. Cost: a cancelled run
  shows as cancelled on the superseded commit, which only matters for a
  commit nobody merges; a queued same-head run costs one more run.
- Reuse: the managed workflow gets the same binding TSK-359 proves here,
  read from the run's recorded provenance and executed from the trusted
  base's copy of the helper, never from the pushed tree. A full-mode push
  that reuses an essential-mode pull request verdict would weaken the
  full gate, so reuse is allowed only when the reused run's effective
  mode equals the push's effective mode. A project may opt in to running
  essential on push, which changes the push's effective mode; it never
  waives the equality. Unproven reuse runs the jobs.
- Never reused: the secret scan, the gitleaks canary, the security review
  and CodeQL, as in TSK-359.

## Acceptance Criteria

- AC-6 Before any change, the builder shall research run cancellation broadly: GitHub's current `concurrency` semantics for `pull_request` events (which actions bring a new head, `cancel-in-progress` expressions, the queue modes and whether a newer run replaces or cancels pending runs), TSK-1040's recorded findings, TSK-359's landed reuse binding and TSK-384's shard set, the Bitbucket and generic templates, and adjacent concerns (fork pull requests, re-runs, merge queues, the protected-branch push run); and shall record the findings and the chosen design before any change; evidence: the record section, committed before the first change in the PR. Added 2026-10-28 with AC-5, by the operator's rule of 2026-10-27 that an amended task starts with an investigation.
- AC-1 The managed workflow shall cancel an in-progress `pull_request` run only when it is superseded, meaning a run for a newer head of the same pull request has started; a run for the same head (an `opened` or `reopened` event, a re-run or a repeated same-head arrival) shall neither cancel another run nor be cancelled, and pending same-head runs shall be kept, never replaced; a push, schedule or dispatch run shall never be cancelled; evidence: a scaffold test over the rendered `on` and `concurrency` blocks, failing before the change, and hosted runs on a scratch adopter for a newer-head cancel, a same-head event during a run, two same-head arrivals in a row, and a push run. Amended 2026-10-28 after the PR 374 review: "superseded" requires a newer head, as AC-5 states. (serves EPC-022 AC-134)
- AC-2 A push to the protected branch shall reuse a pull request run's gate verdict only under every condition TSK-359 AC-2 sets and only when that run's effective gate mode equals the push's effective mode, with sharded runs (TSK-384 AC-5) compared per mode across the whole shard set; an essential-on-push opt-in changes the push's mode and never waives the equality; the reused verdict shall name the reused run and its mode; evidence: helper tests per condition and one hosted push run in a scratch adopter. (serves EPC-022 AC-134)
- AC-3 Every refusal case of TSK-359 AC-3, plus a mode mismatch (an essential pull request run against a full push, with and without the opt-in's change of push mode considered) and a helper read from the pushed tree, shall run every job; the secret scan, gitleaks canary and security review shall run on every push; evidence: one test per case and the hosted job list.
- AC-5 The managed workflow's concurrency shall let a run for a pushed head be cancelled only by a run for a newer head, never by another event on the same head (a body edit, a label, a ready-for-review change, a reopen), following TSK-1040's rule for `codeflow-policy.yml`; evidence: the scaffold test and hosted runs of AC-1. Added 2026-10-28 for issue #373, the sibling defect in the policy workflow.
- AC-4 (journey) With the installed build, a scratch adopter shall show one cancelled superseded pull request run, then a landing push that reuses the pull request verdict with the run named and the secret scan executed; evidence: the run links.
