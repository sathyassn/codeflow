# TSK-430: One local command gives the hosted secret-scan and dependency-audit verdicts

## Description

Issue #252. The managed `secret scan` (pinned gitleaks over the full
history, with `.gitleaksignore` and `.gitattributes` from the trusted
base) and `security review` (pinned osv-scanner over every lockfile)
jobs have no local command that gives the same verdict before a push;
`codeflow test`, `codeflow validate --docs` and `codeflow ci` already
have local counterparts. The reporting monorepo holds about 30
permanent `.gitleaksignore` fingerprints found in CI after the commit,
and a hand-rolled local scan reported 7 findings against 0 when it read
`main`'s ignore file. The same 1,003-commit range took 24 s locally;
a task range took under 0.1 s. TSK-412 (4.0.0) adds the commit-time
gitleaks engine and its pin check; this task reuses that runner for a
range.

Outcome: **one local command (provisional `codeflow scan --base <ref>`)
gives the verdict the managed `secret scan` and `security review` jobs
give for the same base and head: the pinned tool versions and
checksums, the ignore and configuration files read from the base
commit, the range `base..HEAD`, and the levels `git.secret_scan`,
`git.security_review` and `git.dep_audit` set; and a project can opt
in to running it at pre-push under its own policy key.**

Research the task settles first, recorded in its PR: whether
osv-scanner's advisory download is acceptable at pre-push or is cached
with a stated maximum age; how the pinned binaries are located on
macOS, Linux and Windows without a network fetch on every run (the
TSK-412 lookup, extended to osv-scanner); and the one engine shared
with TSK-412 (staged content at commit, the range at push).

Non-goals: the commit-time scan (TSK-412); changing the hosted jobs.

## Deliverables

- the command: `crates/codeflow-cli/src/cmd/scan.rs` (new) wired in `crates/codeflow-cli/src/main.rs`, reusing the TSK-412 runner and adding the osv-scanner runner beside it
- the pre-push opt-in: a policy key in `crates/codeflow-core/src/hooks/policy_schema.rs` read by `crates/codeflow-core/src/hooks/git_hook.rs`
- doctor: both binaries' lookup and pin report in `crates/codeflow-cli/src/cmd/doctor.rs`
- tests: `crates/codeflow-cli/tests/scan_cli.rs` (new) with fake pinned binaries and `hooks_cli.rs` for the pre-push key
- docs: `docs/cli.md`, `docs/policy-reference.md` and the research note under `docs/research/`
- release note: `changelog.d/TSK-430.md`

## Acceptance Criteria

- AC-1 `codeflow scan --base <ref>` shall run the pinned gitleaks over `base..HEAD` with `.gitleaksignore` and `.gitattributes` read from the base commit, and the pinned osv-scanner over every lockfile with `osv-scanner.toml` from the base, and shall give the verdict the managed jobs give for the same base and head; evidence: a fixture where the working tree's ignore file differs from the base's, with the verdict matching the hosted job's on a draft pull request. (serves EPC-024 AC-7)
- AC-2 The command shall follow `git.secret_scan`, `git.security_review` and `git.dep_audit` for block, warn and off, and shall fail closed at `block` when a pinned binary is missing or mismatched; evidence: tests per level and per binary state. (serves EPC-024 AC-7)
- AC-3 With the pre-push key enabled, the hook shall run the scan on the push set and refuse a push the hosted job would fail, within a stated time bound for a task-sized range; evidence: a hook test and the measured time.
- AC-4 The research questions (advisory download at pre-push, binary location per platform, the shared engine) shall be answered in the research note with the choice each AC implements; evidence: the note.
- AC-5 (journey) With the installed build in a scratch adopter project, `codeflow scan` shall report the same findings as the hosted `secret scan` job on a draft pull request planted with a `generic-api-key` match, and the same clean verdict after the base's ignore file covers it; evidence: the journey output beside the hosted run.
