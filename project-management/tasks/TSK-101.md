# TSK-101: shared id registry with uid binding and the merge rule

## Description

Build the registry of design v4 section 2 so that ids stay unique across
checkouts, worktrees and lines. Every record gains a hidden UUIDv4 `uid`;
numbers are issued by a compare-and-swap push to `codeflow/registry` and
chosen from the registry's whole history and every visible ref; every record
added in a pull request must be bound to its number before merge; and the
registry only grows, enforced by pre-push, git-guard and `ids check` run
from the code branch's CI, with typed restore as the only repair (R-108,
R-109). It includes `codeflow ids seed`, `backfill`, `sync`, `admit`,
`retarget`, `restore` and `check`, `task new --resume`, the `doctor` report,
the target-side binary pin of the scaffolded workflow (R-113), and the
`codeflow remote protect` data profile as product code (SPC-013 planning
resolution 12). Its pull request accepts ADR-0072, writes the dated Note on
ADR-0046 and updates `docs/architecture.md`. Seeding gives every existing
record a `uid`, legacy `TSK-NNN-NNN` included, with no legacy exemption.
CodeFlow's registry continues at EPC-020, SPC-013, TSK-100 and the next ADR
number. Non-goal: exclusive claims (EPC-021) and the per-line backfill
(TSK-109 for `main`'s records, TSK-124 to TSK-126 for the other lines).

## Affected surfaces and interfaces

- `crates/codeflow-core/src/workgraph/` (allocation, store, record schema)
  and the `epic new`, `spec new` and `task new` commands (CAP-010).
- New `codeflow ids` commands; `doctor` (CAP-008).
- Pre-push and git-guard rules for `codeflow/registry`; the scaffolded CI
  workflow (merge rule, `ids check` jobs and the binary pin); `codeflow remote protect` data
  profile (CAP-003, CAP-008).
- Shared files this task edits: the CI workflow, the hooks, the policy
  schema and the record templates (`uid`). Ownership follows SPC-013 R-118.

## Acceptance Criteria

- [x] AC-1 When `epic new`, `spec new` or `task new` creates a record, the CLI
      shall fetch `codeflow/registry` without force, take one more than the
      highest id ever added in the registry history and on every local and
      remote-tracking ref, push the reservation without force, and write the
      record with exclusive create and the reservation's `uid`; evidence:
      concurrent issue journeys from two worktrees and two clones.
      Spec: R-1, R-5, R-7, R-11, R-12.
- [x] AC-2 When the push is rejected because the tip moved, the CLI shall
      fetch, recompute and retry a bounded number of times, then stop with
      the reason; permission, unsupported and transport errors shall be
      reported as such and never as "taken"; evidence: one fault test per
      outcome.
      Spec: R-13.
- [x] AC-3 When the push result is unclear, the CLI shall treat the number as
      reserved only if the fetched tip binds it to its own `uid`; evidence:
      the lost acknowledgement journey.
      Spec: R-13.
- [x] AC-4 When offline, the CLI shall commit the reservation on the local
      `codeflow/registry` under a lock and report "pending, not unique yet";
      `ids sync` shall publish it, treat the same `uid` as already reserved,
      and stop on a different `uid` with a direction to run `ids retarget`,
      which renumbers the unmerged record and its in-tree links and records
      `former_ids`; evidence: the offline, sync and retarget journey.
      Spec: R-13, R-15, R-16.
- [x] AC-5 `ids admit` shall reserve a number for a fork or hand-written
      record's `uid`, or the next free number with a retarget direction;
      `task new --resume TSK-N` shall write the record only when the
      reservation's issuer and `uid` match; no number is ever reissued;
      evidence: the admission and crash-between-reserve-and-write journeys.
      Spec: R-17, R-18.
- [x] AC-6 When a pull request adds a record not bound in the authority's
      registry to its `uid`, or edits the `uid` of an existing record, CI
      shall block; CI shall fetch `codeflow/registry` explicitly with enough
      history in shallow and single-branch checkouts; evidence: CI fixtures,
      including the registry moving between the check and the merge.
      Spec: R-2, R-14, R-20.
- [x] AC-7 When a pushed range on `codeflow/registry` removes or modifies a
      file outside a typed restore, or adds one outside `ids/`, pre-push and
      git-guard shall refuse it; `ids check` shall report such a commit as
      current damage while the tip fails the damage rule and as history
      once a restore has repaired it; allocation shall refuse to issue only
      while current damage exists; evidence: refused-push tests and `ids
      check` fixtures for current and historical damage.
      Spec: R-8, R-9.
- [x] AC-8 On a host without branch rules, the CLI shall refuse to issue when
      the fetched tip does not descend from the last verified tip, and
      `doctor` shall report reduced assurance; evidence: the rewrite
      detection journey.
      Spec: R-10.
- [x] AC-9 `ids seed` shall write one file per id found on every ref and in
      retained history with its `introduced` and `landed` provenance, give
      each record one `uid`, decide replicas only from a nonempty matching
      `introduced` or `landed` commit sha (the ref is metadata and `none`
      matches nothing), register a legacy `TSK-NNN-MMM` id at
      `ids/TSK/NNN-MMM.toml` without raising the canonical high-water mark,
      stop and name the ids when provenance cannot decide, and accept an
      explicit `--map` whose mapped shas it writes into the registry entry's
      `mapped` list with `mapped_by`, the verification record citing the
      map; `ids backfill` shall copy the registered `uid` into records on
      the current line and never generate one; before a line's backfill,
      CI shall judge a record without a `uid` against the registry entry
      alone (introduced, mapped or nonempty landed sha); evidence: a
      fixture with a replica, a squash, a cherry-pick and a legacy id
      seeded, checked, backfilled and admitted, two unrelated unlanded
      records with the same id stopped and named, never taken as replicas,
      and a mapped squash
      admitted by CI in a fresh checkout before backfill.
      Spec: R-3, R-24, R-25, R-111, R-104.
- [x] AC-10 `ids seed` shall create `codeflow/registry` as an orphan whose
      root commit adds only `ids/` files, idempotently; the branch shall
      stay out of `protected_branches`, branch naming and the product test
      gate, hold no workflow or code, and never trigger `ids sync`
      recursively; `remote protect` shall apply its data profile without
      changing `main`'s rules; evidence: seed, policy and remote-protect
      tests.
      Spec: R-6, R-22, R-109.
- [x] AC-11 (journey) On a fresh `codeflow init` project with a remote and on
      a no-remote project, using the installed CLI, issue, sync, admission
      and the two-integration-lines case shall produce unique numbers, and a
      deleted top reservation shall not be reissued; evidence: the design v4
      section 10 registry journeys, each with a passing control and a fault.
      Spec: R-19, R-104.
- [x] AC-12 `ids check` shall validate the registry's growth and damage
      rules and reconcile it with the record inventory on every ref; the
      code branch's CI shall run it in every PR job and every push job of a
      tracked target and on a daily schedule from the default branch, with
      no registry write scope; `doctor` shall report the result and any id
      it cannot place; evidence: `ids check` tests on a damaged and a clean
      fixture, and the workflow jobs.
      Spec: R-21, R-109.
- [x] AC-13 `ids restore <id>...` shall write one commit that returns each
      named file to the bytes of its first addition, and pre-push, git-guard
      and the registry check shall accept it; a restore that would bind a
      number to any other `uid` shall be refused; issue and CI shall be
      healthy again as soon as the tip passes the damage rule; evidence:
      deletion, modification, valid restore and rebinding restore controls
      through the pre-push, guard and CI paths.
      Spec: R-8, R-108, R-104.

      Spec: R-113.

  runs on `pull_request_target` and reads the PR head only as git data.
- The registry and uniqueness rows are appended to the `codeflow ci` record

  killed; the last one only after adding the impostor fault to the seed test.

Review round 1 (Codex, changes requested on d7b3e33ee), fixed in one
commit per finding, each regression shown to fail with its fix reverted:

- F1: every first addition is recorded before its commit is judged, merge
  trees included, so an invalid commit's number is never issued again
  (`a_number_an_invalid_commit_introduced_is_never_issued_again`).
- F2: one checkpoint writer refuses a tip that does not descend from the
  saved one; seed and restore verify descent before any push

  (`a_first_uid_backfill_must_be_the_registry_binding`).
- F4: diff, tree, history and file listings are read NUL-delimited
  (`quoted_record_paths_are_still_judged`: non-ASCII, quote and tab).
- F5: permission, unsupported and transport refusals win over lock
  wording, in issue and seed alike
  (`overlapping_refusals_are_never_retried_as_a_race`,
  `seed_reports_a_permission_refusal_once_even_beside_a_lock_message`).

- Doctor `id-registry` warns "not applicable" when project state cannot
  be read, instead of failing; the enforcing surfaces still refuse
  (found by TSK-107's builder in the CLI doctor test).
- Rebased onto `integration/EPC-020-delivery-system` after TSK-102 landed
