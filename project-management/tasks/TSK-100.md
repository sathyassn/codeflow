# TSK-100: prove the shared id registry on a real host

## Description

Plan v4 rests the id registry on a protected data branch,
`codeflow/registry`, and on the host refusing deletion and force push of
that branch without a pull-request requirement. That was verified only with
local bare remotes (Plan v4 section 2.3). This task proves the protocol end
to end on a real host before TSK-101 builds it: the data-branch profile
applied by `codeflow remote protect`, seeding, issue, a lost
acknowledgement, a reservation file deleted by a plain commit and caught by
history-based allocation and by the registry CI job, admission of a
fork-style record, and whether the host offers a file-path push rule that
would add prevention for free. It is a gate: if the proof fails, EPC-020
stops and decision 1 returns to the operator, with option (b) (a scan of all
refs plus a CI check) as the known, weaker fallback for 3.0.0.

Needs from the operator: one disposable repository on a host with branch
rules (a free public repository works). It also serves the
`remote protect --apply` test approved earlier and never run. Agents never
create or delete repositories.

## Affected surfaces and interfaces

- The disposable repository only; no change to this repository's remote.
- `codeflow remote protect` (CAP-008): the data-branch profile.
- Evidence: a verification record under `docs/verification/`.

## Acceptance Criteria

- [ ] AC-1 When `codeflow remote protect` applies the data-branch profile to
      `codeflow/registry` on the disposable repository, the host shall refuse
      deletion and force push of that branch, shall not require a pull
      request for it, and `main`'s rules shall be unchanged; evidence: the
      host rule listing before and after, and the refused push transcripts.
- [ ] AC-2 When one id is issued after seeding, a plain push of the
      reservation shall be accepted, and a second plain push onto the moved
      tip shall be rejected; evidence: transcript.
- [ ] AC-3 When the acknowledgement of an accepted issue push is lost, a
      fetch shall show the number bound to the issuer's `uid`, and the issuer
      shall treat it as reserved; evidence: transcript with the
      acknowledgement dropped.
- [ ] AC-4 When a plain commit deleting the top reservation file is pushed,
      history-based allocation shall not reissue that number and the
      registry CI job shall report the deletion; evidence: transcript and the
      job run.
- [ ] AC-5 When a fork-style record with no reservation is proposed, its pull
      request check shall stay red until a maintainer admission binds its
      `uid`; evidence: the check runs before and after admission.
- [ ] AC-6 The verification record shall state whether the host offers a
      file-path push rule that refuses a change under `ids/`, citing the
      setting or documentation checked.
- [ ] AC-7 If AC-1 to AC-5 do not all pass, the task shall record the
      failure and its evidence, no later EPC-020 task shall start, and
      decision 1 shall be returned to the operator; evidence: the
      verification record and the hand-off.
