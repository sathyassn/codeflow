# TSK-1244: An agent can create a disposable sample repository through a sanctioned path

## Description

Source: the CI throughput study of 2026-11-02 (`coordination/coordinators/parallel/throughput/`: RECOMMENDATIONS.md, FINDINGS.md, CHECK-codex.md, CHECK-fable.md), cross-checked by Codex GPT-6 Astra and Claude Fable 5.1, and the operator's priority on CI throughput.

Today the git guard refuses `git init` of a new, empty folder with the rule `git.policy_authority` ("no readable repository ... unborn HEAD"), so no agent session can create a disposable sample repository. That blocked step 4 of TSK-431's AC-4 journey and would block the beta binary trial the operator wants before adopting a beta on this machine.

Two designs are open and the task chooses one with the threat model stated first: (a) a guard allowance for `git init` into a new, empty folder outside any repository, or (b) a `codeflow` command that creates the sample. Either way the guard keeps failing closed for everything else. The task changes a guard, so it is a security task: the threat each rule closes and why the design is the standard one go in the pull request.

The plan's text, with `git_guard.rs` lines read again at line tip `1107c5974` (`token_integrity_path` is still at `:2347`; `eval_kit.py` `RUN_MARKER` `:53`, `cleanup_run` `:7578`):

Issue #500 (CodeFlow 3.1.1, `48104f48b`, filed 2026-11-02 00:51Z). The
git guard's `git.hook_integrity` rule refuses `mv` and `rm` on any path
with a component named `.git` (`token_integrity_path`,
`crates/codeflow-core/src/hooks/git_guard.rs:2347`). The rule cannot tell
the project's own git directory from a throwaway repository, so an agent
cannot run a task that tests worktree protection on a scratch clone
(renaming or rewriting `.git/worktrees/<name>`, `commondir`, `gitdir` or
`config`), and cannot delete a scratch clone it made. The issue's repro:

```text
git init "$TMPDIR/probe"; add a linked worktree inside it
mv "$TMPDIR/probe/.git/worktrees/w" "$TMPDIR/probe/.git/worktrees/w2"   refused
rm -rf "$TMPDIR/probe"                                                   refused
```

The task has two possible outcomes, and AC-6 picks one:

- **Branch F (fixture route):** an agent can rename, rewrite and remove
  git state inside a fixture repository through a sanctioned mechanism
  that is proven to act only on that fixture; every other `.git` path,
  raw shell writes into fixtures included, stays refused.
- **Branch R (refusal only):** no sound mechanism exists; the rule stays
  as it is, and its refusal names a route that really exists for this
  work.

This is a guard change, so it is secure by default (workspace AGENTS.md
"Security decisions are secure by default"):

- **Fail closed.** An operation leaves the rule's scope only when it is
  proven to act on a disposable repository that is not the project
  repository, not a linked worktree of it, and shares no git directory
  with it. The proof uses resolved real paths, follows a `.git` file's
  `gitdir` and the git directory's `commondir`, and considers symlinks
  and hard links. Anything not proven keeps today's refusal.
- **Unforgeable binding.** The requester cannot make a repository its own
  scratch by a name, a path, an environment variable (`$TMPDIR`
  included), a marker file, or a record it can write or replace by any
  route: a direct write, another program or binary, or a replaced parent
  directory.
- **No check-then-use gap.** A guard decision on a command line is made
  before the command runs, and a concurrent process can swap a directory
  inside the fixture for a link into the project afterwards. So the
  guard never exempts an ordinary shell `mv`, `rm` or write into a
  `.git` path. In branch F the sanctioned mechanism performs each
  operation itself, against the directory it validated (held open,
  operations relative to it, links never followed), so validation and
  use act on the same object.

Threat: an agent turns the exemption against the project's git state (its
hooks, config, `commondir`, worktree records or the policy authority) by
pointing a "scratch" path at it, forging the fixture binding, swapping a
path between check and use, or writing a new redirect and then using it,
so it can disable a hook, rewrite a worktree link or delete the
repository.

Options for the binding (AC-6 settles them, with the threat each leaves
open):

| Option | Binds to | Open question |
|---|---|---|
| A. `$TMPDIR` or a path prefix | a value the requester sets | forgeable; rejected unless AC-6 shows otherwise |
| B. The host's session scratch directory | the harness's own value | the guard must read it from state the agent cannot change; not every harness provides it; it still binds a directory, not who made a repository |
| C. A marker file in the fixture root, as cf-evaluate-model does | a file the agent can write | forgeable as it stands (below) |
| D. A sanctioned `codeflow` command that creates fixtures, keeps a record, and performs the fixture operations itself | a record and a writer the agent cannot forge, plus the fixture git directory's device and inode | a guard rule on command lines alone does not make a record unforgeable: another program, another binary or a replaced parent directory can write it; AC-6 must find a writer boundary enforced outside the guard (for example a location the sandbox denies to agent sessions, or an identity the agent does not hold), or branch R follows |

cf-evaluate-model's marked fixture roots (`eval_kit.py`, `RUN_MARKER` at
`:53`, `cleanup_run` at `:7578`) are not sound as a guard exemption as
they stand:

- the marker `.codeflow-eval-run.json` sits in the run root, which the
  agent can write, so an agent can mark any directory;
- the confirmation string is the marker's own `run_id`, read from that
  same file, so it proves nothing about who made the root;
- `cleanup_run` refuses a symlinked root, the file-system root, home, a
  root that is itself a repository and an overlapping subjects root, but
  trusts the marker's `subjects_root` and does not check that it is not
  the project repository, a parent of it, or a repository sharing its
  git directory;
- its deletion runs inside Python, where the guard never sees the paths.

Its safety for model evaluation comes from trusted orchestration and
confinement of the evaluation run, not from the marker. It is scoped to
model evaluation (its skill excludes ordinary repository work and
generic cleanup), so it is not a fixture route for this task.

## Outcome

After this merges, an agent session can create a disposable sample repository in a new empty folder by a documented path, and every other repository creation or read the guard refuses today is still refused. It can also rename, rewrite and remove git state inside a fixture repository through the route AC-6 chooses, or, in branch R, the refusal names a route that exists; the project's own git state stays refused either way.
