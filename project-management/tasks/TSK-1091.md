# TSK-1091: The anchor refusal names the branch shape a new standalone record needs

## Description

Source: issue #430 (CodeFlow 3.1.1, filed 2026-10-30 by an adopter),
triaged the same day. No open task covers it; TSK-414 (complete) covers
only a cancelled standalone record landing through a `plan/` branch.

A pull request adds a standalone task record on a branch whose name
does not carry the task (`chore/close-tsk-nnn-record`), with `Task:
TSK-NNN` in its body. `codeflow ci` refuses it with
`work.stable_planning_anchor`: "task TSK-NNN is not present at the
merge-base; land its epic planning record, or carry its own standalone
record on this task branch", and the remedy says to run `codeflow work
start`. The record is on the branch, and `work start` only checks the
anchor, so neither tells the author what to change. The same range
passes on a branch named `chore/TSK-NNN-<slug>`.

The cause, read on the line tip `b7ae7c6a6`: `standalone_at_head`
(`crates/codeflow-core/src/workgraph/work_start.rs:2232`) accepts a
record that is not at the merge-base only when the branch's work suffix
starts with `TSK-NNN-`, and otherwise returns `TaskNotAnchored`, whose
text (`work_start.rs:69`) does not mention the branch. Its remedy,
`WORK_START_MERGE_PLANNING` (`crates/codeflow-core/src/remedy.rs:340`),
names `codeflow work start`. `TaskNotAnchored` also covers a record
missing from both the merge-base and the head, and an epic task whose
planning has not landed.

The verdicts stay as they are: the rule is right, and only its text and
remedy change. Non-goals: accepting a record on a branch that does not
carry the task.

## Outcome

After this merges, an author whose standalone record is refused for its branch name is told the branch shape the record needs and how to get there, from `codeflow ci`, `codeflow work start` and the pre-push hook alike.

## Deliverables

- the refusal text and its causes: `crates/codeflow-core/src/workgraph/work_start.rs` (`TaskNotAnchored` and `standalone_at_head`)
- the remedies: `crates/codeflow-core/src/remedy.rs`
- tests: `crates/codeflow-cli/tests/ci_cli/` (the issue's reproduction), unit tests beside the changed code, and a `remedy_clearing` entry in `crates/codeflow-cli/tests/remedy_clearing/`
- docs: the anchor refusal in `docs/troubleshooting.md`, where it is described
- release note: `changelog.d/TSK-1091.md`

## Acceptance Criteria

- AC-1 When a standalone record that is not at the merge-base is refused because the branch name does not carry the task, the refusal shall name the branch and the shape `<prefix>/TSK-NNN-<slug>`; a record missing from the head and an epic task whose planning has not landed shall each keep a distinct text; evidence: a `ci_cli` fixture of the issue's reproduction, whose output lacks the branch and the shape before the change and has them after, and one test per other cause. (serves EPC-022 AC-173)
- AC-2 That refusal's remedy shall name renaming the branch or cutting a new one in that shape, and for a cancelled record also the `plan/` route TSK-414 opened, and shall never point at `codeflow work start`; evidence: a `remedy_clearing` entry that follows the printed step and sees the refusal clear. (serves EPC-022 AC-173)
- AC-3 The verdicts shall be unchanged, and `codeflow ci`, `codeflow work start` and the pre-push hook shall print the same text for the same cause; evidence: the existing anchor tests passing unchanged, and one fixture run through each of the three entry points.
