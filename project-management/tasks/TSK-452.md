# TSK-452: Review cadence and guidance state each rule once

## Description

Guidance repeats work and repeats itself. Every review round rereads the whole
unit "not only the delta" (`findings.md:64-66`), a security change can get five
or six passes over one diff (`cf-security-reviewer.md:12-34`), cf-reviewer is
mandatory in one file and optional in another (`cf-develop` step 4b,
`workflow-discipline.md:265`, `cf-model-orchestrator` SKILL.md:381-383,
`cf-reviewer.md:138-139`), rounds 6 and 7 found sibling cases one at a time,
the routed required reading is about 150 KB, batch landing is stated in four
files and the plain-writing rule in eight. Source: the operator approved
process audit of 2026-10-23, including the operator's decision of that day on
the security review stack (line numbers at `c9993bcf3`).

Scope: (1) Review cadence at four stages: plan settlement (epics only), PR
ready, landing candidate (hand-resolved hunks only), epic close. Between
stages the finder confirms a fix on the delta plus the affected tests; one
final holistic pass on the final substantive revision precedes approval. (2)
The builder's sibling sweep, with file:line per site, precedes the first
review on a class fix; a reviewer who finds a sibling returns the unit to the
sweep. (3) Security: the one other-lineage whole-unit review runs with the
security checklist as the attacker lens; the Claude side triages scanner
output inside its integrated judgment; cf-reviewer runs only when no
other-lineage seat exists, stated once; the "high complexity" and "material
depth" triggers for an extra family are dropped from `routing-policy.json`,
the security and irreversible triggers stay. (4) Only material findings
block; nits get a disposition. (5) Estimates come from planned throughput
(`cf-estimate`, "Durations"). (6) Lane and queue rules: lanes sized from host
memory and CPU, cheap targeted checks run freely while heavy work takes TSK-331's
admission, and only the primary runs the full gate. (7) Research, review and consult work gets no
durable record unless it produces a durable artifact; the evidence ledger text
goes; one findings record linked from the PR (resolving the conflict between
`completion.md` and `pr-evidence.md`). (8) Dedupe: batch landing in one home
(cf-method "Managing a body of work"), the plain-writing rule once in
`.codeflow/rules/writing.md`, the delivery flow once, one editorial-review
trigger, cf-present loads specimens on demand, and the orchestrator preflight
is printed by `codeflow doctor` (configured versus observed values, with
unavailable evidence reported) and read, with the live observation still made.

(9) Planned work is delivered at speed (operator direction of 2026-10-23).
Exploration, research and planning stay deliberate; once work is planned into
an epic and tasks with criteria, builders execute without re-planning,
re-litigating settled decisions or confirmation work for its own sake.
Throughput expectation, set by the operator as an explicit decision of
2026-10-23 (which satisfies "Only the operator adds process"): each build
lane delivers at least one planned task to ready-for-review per hour,
preferably two. Quality is not traded: criteria, the tests that prove them
and real security stay. Speed practices: targeted tests in the worktree, the
quick gate once before ready, no local full gate, one push at ready, no
reruns on an unchanged tree, lean PR bodies carrying criteria with file:line
and test evidence, any stop over 15 minutes reported at once, reversible
choices decided by the builder. Coordinator duties: start every task whose
edges allow, up to host capacity; measure each lane's time on its task at
every sweep; act on any lane past an hour. One canonical home: cf-method's workflow lifecycle reference holds the full
rule; cf-develop, cf-model-orchestrator, the managed map's build row and
cf-estimate (estimates from planned throughput, never extrapolated from a
slow pace) point to it. The durability-push rule in the git rules
changes to match "one push at ready" for the pre-push cost TSK-449 removes.

Non-goals: no hook, guard, CI or policy change, and no change to what the
protections are; the deterministic scanners, the secret scan and trusted CI
are untouched. Protection lost by (3): one fewer independent security pass
per security-sensitive unit; both lineages still read the diff with the
security checklist.

Effect on adopting projects: a smaller managed block and about 150 KB less
required reading per routed session; `codeflow update` rewrites the managed
files (AGENTS.md block, rules, skills, agents) and the baseline; adopters
keep their own rules outside the managed markers.

Owned files: the managed block of `AGENTS.md` and `assets/base/AGENTS*.tmpl`,
`CLAUDE.md` and its templates, `.codeflow/rules/*` with `assets/base/rules/*`,
the skills cf-method, cf-develop, cf-ship, cf-plan, cf-estimate,
cf-model-orchestrator, cf-present and cf-editorial-review in
`.claude/skills`, `.agents/skills`, `assets/base/claude/skills` and
`assets/base/agents/skills` (byte-identical mirrors), the agents
`cf-reviewer` and `cf-security-reviewer` in `.claude/agents` and their asset
copies, `routing-policy.json`, `crates/codeflow-cli/src/cmd/doctor.rs` (the
preflight output), and the resynced `.codeflow/.baseline` for those files.
TSK-452 depends on TSK-331 (the lane and queue guidance names the admission lock and `codeflow reserve` as built). Other open tasks edit some of these files (TSK-419, TSK-423, TSK-435,
TSK-441, TSK-387); dispatch keeps one writer at a time.
