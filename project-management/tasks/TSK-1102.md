# TSK-1102: The qualification runner accepts a peer in a registered fixture worktree

## Description

The native qualification runner (`evals/qualification/runner.py`) refuses
every peer seat a subject opens outside the fixture repository root:
`check_peer_state` compares the peer's working directory with the fixture
path and raises "peers start in the fixture repository" (runner.py:1302-1303
at TSK-1094's reviewed head `addf25865`). The method puts a review seat in
the subject's task worktree (`cf-herdr` "Naming": the intended worktree
`cwd` identifies the seat; `.codeflow/rules/worktrees.md`: work happens in
`.worktrees/<slug>`), so a subject that follows the method gets
`peer_launch_refused` and its trial is invalid. Evidence: TSK-1032 trial
round 7 (`.worktrees/tsk-1032/target/qualification/typed-code-r7/builder-adds-type-checker-and-config-model-7/peers.json`):
the Codex start requested for `<repository>/.worktrees/tsk-031` was refused
with that message, and `observation.json` carries `peer_launch_refused`;
round 5 shows the same for `.worktrees/tsk-032`. Both trials ran under the
default `--codex-hook-trust=review` option (`launch.json`,
`hook_trust.option`). The sibling tasks TSK-1030, TSK-1031 and TSK-1033
open peers the same way when their subjects follow the method; only
TSK-1032's refusal is demonstrated here.

Two more checks are keyed to the root path. `trust_choice`
(runner.py:306-357) accepts a folder-trust dialog only when it names the
fixture path, and `observe_peer` passes `Path(run["repository"])` to
`handle_startup` (runner.py:1529). Codex keys hook trust by the absolute
path of `.codex/hooks.json` (`evals/qualification/README.md:101`), so a
Codex peer in a worktree shows "Hooks need review" even after the
operator's pre-launch review of the fixture root, and the runner refuses
that screen (runner.py:308-311). The worktree does not exist before launch,
so `print-hook-review` (runner.py:1114) cannot cover it.

The subject runs as the operator's user and can write every file the
runner reads, git's worktree metadata included. The checks below are
therefore bounded evidence, not proof of ownership: each one is a concrete
predicate the runner evaluates at a stated moment, and the record names
what polling cannot see.

### Admission: the directory and its repository identity

A peer's working directory `C` is accepted when it is the fixture
repository root, as today, or passes every check below, all evaluated on
the raw path first and on realpaths second, with `lstat` so that a symlink
is seen rather than followed:

1. Fixture identity, captured once at `launch` into `launch.json`
   (`peers.fixture_identity`): the realpath of the repository `R` and the
   realpath of its common directory from `git -C R rev-parse --git-common-dir`,
   which must be `R/.git`, a real directory.
2. Placement: `C` is lexically `R/.worktrees/<name>`, one level down; `R`,
   `R/.worktrees` and `C` are real directories, none a symlink;
   `os.path.realpath(C) == C`.
3. Link file: `C/.git` is a regular file under a small size cap holding
   exactly one line `gitdir: <A>`; `A`, resolved against `C` when relative,
   is a real directory lexically `R/.git/worktrees/<id>`, one level down,
   with `R/.git`, `R/.git/worktrees` and `A` real directories and no
   symlink among them; `os.path.realpath(A) == A`.
4. Reciprocal pair: `A/gitdir` is a regular file whose content, resolved
   and realpath'd, is exactly `C/.git`; `A/commondir` is a regular file
   whose content, resolved against `A` and realpath'd, is exactly the
   fixture's common directory from step 1. A changed `commondir`, a
   backlink to another worktree, a symlink or any non-regular file in this
   chain refuses.
5. Git's own view, read in a clean subprocess environment (every `GIT_*`
   variable unset, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`,
   `HOME` set to an empty temporary directory): `git -C R worktree list --porcelain`
   lists a non-main `worktree` entry whose realpath is `C`, neither `bare`
   nor `prunable`; `git -C C rev-parse --git-common-dir` realpath'd equals
   the fixture's common directory; `git -C C rev-parse --show-toplevel`
   realpath'd equals `C`. A git error, a missing, ambiguous or prunable
   entry refuses.
6. The accepted identity is pinned to the launch at bind: `C`, `A`, the
   common directory and the SHA-256 of the contents of `C/.git`,
   `A/gitdir` and `A/commondir`. A later check that yields a different
   identity, including a re-registered `A`, is a failure, never a new
   acceptance.

Names are never matched. Other worktree locations (`.claude/worktrees`,
harness homes) and nested directories stay refused.

### Revalidation: when the checks run

The identity checks, and under `--codex-hook-trust=bypass` the hook
content checks against `C/.codex` (`codex_hook_preflight` on the worktree:
`hooks.json` equal to the shipped contract-3 definitions, no other hook
source, no symlink; the evaluator-home checks as today; `hooks_sha256` is
the hash of the file the peer's Codex reads), run at every one of these
moments:

- when a request is answered (`peer_decision`);
- at bind (`verify_peer_process` from `observe_peer`);
- inside `before_key`, immediately before every startup key
  (`accept_workspace_trust`, `decline_renderer`), in addition to the
  process identity recheck it makes today;
- at readiness, before the ready record is written;
- on every later poll of a launch whose status is `ready`: `observe_peer`
  no longer returns before verification for a ready launch
  (runner.py:1514).

A failure at any moment revokes the ready record (`set_gate(run, pane,
None)`), sets the launch to `unverified` with the failing predicate in
`error`, and the trial carries `peer_launch_unverified`; no key is sent
and nothing restores the launch. `identity_of` (runner.py:1419) stays the
process identity; the pinned worktree identity is checked beside it, not
folded into it, so a registration-only change with pid, argv, cwd and
environment unchanged is still caught.

Limitation, stated in the README: the watcher polls, and a gap longer
than `WATCH_GAP_SECONDS` between two completed polls invalidates coverage
(`peer_watch_incomplete`, read back by `watch_gaps`); the watcher does not
guarantee a poll within that interval, cannot see a change removed and
restored between two polls, and no check-then-use step is atomic against
an unrestricted same-user writer. This is the runner's existing posture
for root peers; the new paths add no stronger claim.

### Exact-path trust and the folder-trust finish allowance

The accepted directory becomes that launch's subject path. `handle_startup`
and `trust_choice` receive the launch's verified cwd instead of the fixture
root, so a folder-trust dialog (Claude "Accessing workspace:", Codex
"Folder access", Grok "Do you trust the contents of this directory?") must
name exactly that path; a dialog naming the root for a worktree peer, or a
worktree for a root peer, refuses with no key, as any other path does
today.

The folder-trust change `finish` allows (`config_drift`,
runner.py:1075-1089; `codex_trust_entry`, runner.py:1026-1038) extends to
a `trust_level = "trusted"` project entry for an accepted worktree path
after a recorded folder-trust acceptance for exactly that path. Each
recorded acceptance allows at most its own entry, with no other key in it;
two accepted worktrees, or the root and a worktree, are each matched to
their own acceptance; the rest of the file keeps its baseline (the whole
`projects` table is not stripped); any other folder-trust change stays
`evaluator_config_drift`. This rule covers folder trust only; no
hook-trust change is allowed at finish.

The decision and launch records carry the accepted path, its kind
(`repository` or `worktree`) and the pinned identity, and the refusal text
names both accepted forms.

### Hook review in a worktree created during the trial: decided, route B

Under the default `review` option a Codex peer in a worktree meets "Hooks
need review" because Codex keys hook trust by the absolute path of
`hooks.json`; the worktree does not exist before launch, so the pre-launch
review cannot cover it; and the runner never answers that screen or waits
for an answer it cannot attribute to a human (runner.py:308-311). The
admission work above does not change that, so under `review` a worktree
Codex peer moves from `peer_launch_refused` to `peer_startup_refused` and
the trial stays invalid.

Operator decision, 2026-10-31 12:52, saved on the status page and
relayed by the coordinator: route B. TSK-1032's trials run with the
runner's existing per-trial `--codex-hook-trust=bypass`, the choice the
README already assigns to the person running the evaluation
(`evals/qualification/README.md:105`). Under it the runner's hook content
check runs against the worktree's own `hooks.json` at every moment listed
above, and under `review` a worktree Codex peer stays refused at its hook
screen with no key. The runner's never-answer-hook-screens contract is
unchanged, and the finish allowance stays folder trust only. TSK-1032's
prerequisite: its AC-4 native trials are launched with
`--codex-hook-trust=bypass` once this task lands.

Not chosen, recorded for later tracking if wanted: route A, an
operator-authorized, digest-bound review of the shipped hooks for a
worktree created mid-trial, which would change the never-answer contract
and would first need Codex's supported native trust mechanism
investigated. No record owns it; it can be filed as its own task if the
default option is ever required for worktree peers.

Alternatives rejected on evidence: pre-creating the review worktree at
launch changes a trial that asks the subject to create its own worktree,
so its fidelity, although a pre-created path could be verified
structurally; waiting at "Hooks need review" in the peer pane cannot tell
the operator from the subject typing through the real Herdr binary, and
the hook-trust record Codex would write is config drift.

Non-goals: Herdr's own `worktree create|open` stays refused in
`peer_shim.py`; the subject seat's checks, the peer flag allowlist, the
plugin checks and every other refusal are unchanged; the runner never
answers a hook screen; no hook-review bypass is added beyond the existing
per-trial option.

## Outcome

After this merges, the qualification operator can run trials under the
per-trial `--codex-hook-trust=bypass` option whose subject opens a Codex
review seat in its task worktree, as the method prescribes: the peer
reaches ready, receives its delivery and the trial finishes with no
validity flag from it; under the default `review` option such a peer is
still refused at its hook screen; and the runner still refuses any peer
whose working directory fails the stated identity checks at any moment it
looks.

## Acceptance Criteria

AC-1 to AC-5, AC-7 and AC-8 are the admission work; AC-7 covers
folder-trust entries only. AC-6, AC-9 and AC-10 follow the operator's
route B decision of 2026-10-31 (the per-trial bypass option). Baselines:
AC-1 and AC-8 are new regressions that fail on `addf25865`; AC-2 to AC-4
are rejection controls that already refuse there (every non-root cwd is
refused today) and must stay green; AC-8's tests establish their setup
first so an unrelated admission failure cannot pass as the regression.

- AC-1 When a peer start names a working directory that passes every admission check (a registered linked worktree of the fixture at `<repository>/.worktrees/<name>` with the reciprocal `.git` and `gitdir` pair and the fixture's common directory), `peer_decision` shall allow it and `verify_peer_process` shall verify a live process in that directory, recording the accepted path, kind and pinned identity. Evidence: new tests in `evals/model-artifacts/test_eval_kit.py` on a `git init` fixture with `git worktree add .worktrees/review`, failing on `addf25865` with "peers start in the fixture repository" and passing after. (serves EPC-022 AC-175)
- AC-2 When the working directory is under `.worktrees/` but is not a registered worktree of the fixture (a plain directory, an unregistered copy, a subdirectory of a registered worktree, or a worktree removed or pruned since the request was answered), the runner shall refuse the start and fail live verification, sending no key. Evidence: tests for each case; the existing "wrong path" negative control still refuses.
- AC-3 When the working directory reaches a worktree through a symlink, or its realpath lies outside the fixture repository (a symlink under `.worktrees/` to another directory, a registered worktree whose path resolves elsewhere, or a symlink or non-regular file anywhere in the `.git`, `gitdir` and `commondir` chain), the runner shall refuse. Evidence: tests for each case, evaluated on the raw path before any resolution.
- AC-4 When the working directory is a worktree registered to another repository, including one placed at `<fixture>/.worktrees/<name>` by that repository's `git worktree add`; when a registered fixture worktree's admin `commondir` is rewritten to another repository's `.git`; or when the admin entry's `gitdir` backlink names a different worktree than the one requesting, the runner shall refuse. Evidence: tests for each case, with a second `git init` repository.
- AC-5 When an accepted worktree peer shows a folder-trust dialog naming exactly the worktree path, the runner shall accept it as it does for the root; when the dialog names any other path, the root included, or a root peer's dialog names a worktree, the runner shall refuse with no key. Evidence: `trust_choice` and `handle_startup` tests for the Claude, Codex and Grok screens with the path substituted; the existing trust tests pass unchanged.
- AC-6 Under `--codex-hook-trust=bypass`, when the worktree's `.codex/hooks.json` differs from the shipped contract-3 hooks or its `.codex` holds another hook source or a symlink, the start, the bind, the pre-key check, the readiness check and a later ready-peer poll shall each refuse even while the root's hooks are intact; when they match, the decision's `hooks_sha256` shall be the hash of the worktree's file. Under the default `review` option a Codex worktree peer's "Hooks need review" screen shall still refuse with `peer_startup_refused` and no key. Evidence: tests under both options at each boundary.
- AC-7 Folder trust only: when the only Codex config change at finish is a `trust_level = "trusted"` entry for an accepted worktree path with a recorded folder-trust acceptance for that path, `finish` shall list it under `config_allowances` and not flag `evaluator_config_drift`; an entry for any other path, an extra key on an accepted entry, two accepted paths where only one acceptance was recorded, an unrelated change alongside, or an entry without a recorded acceptance shall still flag drift. Evidence: `config_drift` tests covering the root plus a worktree and two worktrees together.
- AC-8 When only the worktree's registration or admin files change after bind, immediately before a startup key, or after readiness, with pid, argv, cwd and environment unchanged, the runner shall revoke the ready record, mark the launch `unverified` with the failing predicate, flag `peer_launch_unverified` and send no key; the same shall hold for a hook content change under bypass at each of those moments. Evidence: tests through `observe_peer` with the scripted Herdr and process table and the gate file, not only direct validator tests; the existing peer, trust, startup, finish and delivery tests pass unchanged (`evals/model-artifacts/test_eval_kit.py`, `evals/herdr-delivery/test_delivery.py`), and `evals/qualification/README.md` states the accepted directories, the moments the checks run, the hook behaviour under each option and the polling limitation.
- AC-9 One native dry run by the primary on a fresh fixture launched with `--codex-hook-trust=bypass`: the subject opens a Codex peer through the trial launcher in a registered fixture worktree, the peer reaches `ready`, one delivery through the trial `herdr` is logged, and `finish` reports no validity flag from the peer. Evidence: `peers.json` and `observation.json` of the run. (journey)
- AC-10 A second native dry run under the default `review` option records `peer_startup_refused` at the hook screen with no key sent. Evidence: `peers.json` of that run.
