# TSK-1102: The qualification runner accepts a peer in a registered fixture worktree

## Description

The native qualification runner (`evals/qualification/runner.py`) refuses
every peer seat a subject opens outside the fixture repository root:
`check_peer_state` compares the peer's working directory with the fixture
path and raises "peers start in the fixture repository" (runner.py:1302-1303
at TSK-1094's reviewed head `addf25865`). The method puts a review seat in
the subject's task worktree (`cf-herdr` "Naming": the intended worktree
`cwd` identifies the seat; `.codeflow/rules/worktrees.md`: work happens in
`.worktrees/<slug>`), so a subject that follows the method gets
`peer_launch_refused` and its trial is invalid. Evidence: TSK-1032 trial
round 7 (`.worktrees/tsk-1032/target/qualification/typed-code-r7/builder-adds-type-checker-and-config-model-7/peers.json`):
the Codex start requested for `<repository>/.worktrees/tsk-031` was refused
with that message, and `observation.json` carries `peer_launch_refused`;
round 5 shows the same for `.worktrees/tsk-032`.

Two more checks are keyed to the root path. `trust_choice`
(runner.py:306-357) accepts a folder-trust dialog only when it names the
fixture path, and `observe_peer` passes `Path(run["repository"])` to
`handle_startup` (runner.py:1521). Codex keys hook trust by the absolute
path of `.codex/hooks.json` (`evals/qualification/README.md:101`), so a
Codex peer in a worktree shows "Hooks need review" even after the
operator's pre-launch review of the fixture root, and the runner refuses
that screen (runner.py:308-311). The worktree does not exist before launch,
so `print-hook-review` cannot cover it.

The change, in the runner:

- A peer's working directory is accepted when it is the fixture repository
  root, as today, or a registered linked worktree of that repository:
  `os.path.realpath(cwd)` is exactly `<realpath(repository)>/.worktrees/<name>`
  (the worktree root, one level down); no path component between the
  repository and the cwd is a symlink (`kit.refuse_symlink_components`);
  `git -C <repository> worktree list --porcelain`, run by the runner with a
  clean environment, lists a `worktree` entry other than the main one whose
  realpath equals the cwd's; and `<cwd>/.git` is a regular file whose
  `gitdir:` resolves inside `<repository>/.git/worktrees/`. A git error, a
  missing or ambiguous entry, a bare or prunable entry refuses. Names are
  never matched; only realpaths and git's own registration count. The check
  runs wherever `check_peer_state` runs: when a request is answered
  (`peer_decision`) and at every live verification (`verify_peer_process`
  at bind and at readiness), so a worktree removed or re-registered between
  polls fails verification and loses its ready record.
- The accepted directory becomes that launch's subject path. `handle_startup`
  and `trust_choice` receive the launch's verified cwd instead of the fixture
  root, so a folder-trust dialog (Claude "Accessing workspace:", Codex
  "Folder access", Grok "Do you trust the contents of this directory?") must
  name exactly that path; a dialog naming the root for a worktree peer, or a
  worktree for a root peer, refuses with no key, as any other path does
  today.
- Hook checks follow the path. Under `--codex-hook-trust=bypass`,
  `codex_hook_preflight` runs against the accepted worktree (`<worktree>/.codex`):
  its `hooks.json` must equal the shipped contract-3 definitions, it may hold
  no other hook source or symlink, and the evaluator-home checks run as
  today; the recorded `hooks_sha256` is the hash of the file the peer's
  Codex reads. Under the default `review` option nothing changes: a Codex
  peer at its "Hooks need review" screen gets no key and its launch is
  `startup_refused`, for a worktree as for the root. The README states that
  a trial whose subject may open a Codex peer in a worktree runs under the
  per-trial bypass option, and why: Codex's hook trust is a per-path human
  acceptance in the evaluator home, a path created during the trial cannot
  be reviewed before launch, and the runner never answers that screen or
  waits for an answer it cannot attribute to a human.
- The one Codex config change `finish` allows (`config_drift`,
  runner.py:1075-1089; `codex_trust_entry`, runner.py:1026-1038) extends to
  a `trust_level = "trusted"` project entry for an accepted worktree path
  after a recorded folder-trust acceptance for exactly that path. Each
  recorded acceptance allows at most its own entry; any other change stays
  `evaluator_config_drift`.
- The decision and launch records carry the accepted path and its kind
  (`repository` or `worktree`), and the refusal text names both accepted
  forms.

Non-goals: other worktree locations (`.claude/worktrees`, harness homes)
stay refused; Herdr's own `worktree create|open` stays refused in
`peer_shim.py`; the subject seat's checks, the peer flag allowlist, the
plugin checks and every other refusal are unchanged; no hook-review bypass
is added and no key is ever sent at a hook screen.

Alternatives rejected: pre-creating a review worktree at launch (the
subject names its own worktree, so this is a name match, and it changes
the subject's starting state from what adopters see); the runner answering
or waiting at "Hooks need review" for an accepted worktree (it cannot tell
the operator from the subject typing through the real Herdr binary, and the
hook-trust record Codex would write is config drift).

## Outcome

After this merges, the qualification operator can run trials whose subject
opens a review seat in its task worktree, as the method prescribes, and the
runner still refuses any peer whose working directory it cannot tie to the
fixture repository through git's own registration.

## Acceptance Criteria

- AC-1 When a peer start names a working directory that is a registered linked worktree of the fixture repository at `<repository>/.worktrees/<name>`, `peer_decision` shall allow it and `verify_peer_process` shall verify a live process in that directory, recording the accepted path and kind. Evidence: new tests in `evals/model-artifacts/test_eval_kit.py` on a `git init` fixture with `git worktree add .worktrees/review`, failing on `addf25865` with "peers start in the fixture repository" and passing after. (serves EPC-022 AC-173)
- AC-2 When the working directory is under `.worktrees/` but is not a registered worktree of the fixture (a plain directory, an unregistered copy, a subdirectory of a registered worktree, or a worktree removed or pruned since the request was answered), the runner shall refuse the start and fail live verification, sending no key. Evidence: tests for each case; the existing "wrong path" negative control still refuses.
- AC-3 When the working directory reaches a worktree through a symlink, or its realpath lies outside the fixture repository (a symlink under `.worktrees/` to another directory, or a registered worktree whose path resolves elsewhere), the runner shall refuse. Evidence: tests for each case.
- AC-4 When the working directory is a worktree registered to another repository, including one placed at `<fixture>/.worktrees/<name>` by that repository's `git worktree add`, the runner shall refuse. Evidence: a test with a second `git init` repository.
- AC-5 When an accepted worktree peer shows a folder-trust dialog naming exactly the worktree path, the runner shall accept it as it does for the root; when the dialog names any other path, the root included, or a root peer's dialog names a worktree, the runner shall refuse with no key. Evidence: `trust_choice` and `handle_startup` tests for the Claude, Codex and Grok screens with the path substituted; the existing trust tests pass unchanged.
- AC-6 Under `--codex-hook-trust=bypass`, when the worktree's `.codex/hooks.json` differs from the shipped contract-3 hooks or its `.codex` holds another hook source or a symlink, the start and the readiness check shall refuse even while the root's hooks are intact; when they match, the decision's `hooks_sha256` shall be the hash of the worktree's file. Under `review`, a Codex worktree peer's "Hooks need review" screen shall still refuse with `peer_startup_refused` and no key. Evidence: tests under both options.
- AC-7 When the only Codex config change at finish is a `trust_level = "trusted"` entry for an accepted worktree path with a recorded folder-trust acceptance for that path, `finish` shall list it under `config_allowances` and not flag `evaluator_config_drift`; an entry for any other path, or one without a recorded acceptance, shall still flag drift. Evidence: `config_drift` tests.
- AC-8 The existing peer, trust, startup, finish and delivery tests shall pass unchanged (`evals/model-artifacts/test_eval_kit.py`, `evals/herdr-delivery/test_delivery.py`), and `evals/qualification/README.md` shall state the accepted working directories, the hook behaviour under each option and the reason. Evidence: the test counts in the PR body and the README diff.
- AC-9 One native dry run by the primary on a fresh fixture: the subject opens a Codex peer through the trial launcher in a registered fixture worktree; under `--codex-hook-trust=bypass` the peer reaches `ready` and one delivery through the trial `herdr` is logged; a second run under the default `review` option records `peer_startup_refused` at the hook screen with no key sent. Evidence: `peers.json` and `observation.json` of both runs. (journey)
