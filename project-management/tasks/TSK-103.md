# TSK-103: one readiness predicate with work next and work claim

## Description

Derive what is ready, waiting, active and landed from the recorded facts and
from Git, once, and use the same answer everywhere (design v4 sections 2.4, 3
and 4). One readiness predicate serves `work next`, `work start`, `status`
and CI; `work next` includes standalone tasks and names the snapshot it
read; `work claim` pushes a visible task branch as an advisory claim
(decision 2a); cross-line dependencies follow the rules of section 3; a join
awaiting a guarded selection stays blocked; `status` stops calling a live
integration branch removable; `orient` shows a task summary. Per section
3.1, this task also states the spec and epic relationship (many to many)
and the one standalone test. Non-goal: exclusive leases (EPC-021).

## Affected surfaces and interfaces

- `crates/codeflow-core/src/workgraph/work_start.rs`, `status.rs`, `orient`
  and new `work next` and `work claim` commands (CAP-010).
- The CI readiness check. Guidance for the task-graph contract is TSK-108's.
- Shared files this task edits: the CI workflow (readiness check).
  Ownership follows SPC-013 R-118.

## Acceptance Criteria

- [ ] AC-1 The core readiness predicate shall hold only when the task is
      `todo`, has no Blocker and no `awaiting_selection`, its specs are
      approved or implemented, its epic is open or it is standalone, every
      code dependency is accepted and present in the execution base, and
      every research or decision dependency is accepted at its pinned ref;
      `work next`, `work claim`, `work start`, `status` and CI shall call
      this one core; evidence: predicate tests and one test per caller.
      Spec: R-40.
- [ ] AC-2 `work next [--epic] [--json]` shall list ready tasks, then waiting
      and blocked ones with reasons, include standalone tasks, exclude tasks
      with a visible branch carrying their id on any sanctioned prefix, name
      the snapshot it read, and make no network call; evidence: backlog
      fixture tests.
      Spec: R-41, R-103.
- [ ] AC-3 `work claim TSK-NNN` shall run the predicate in its new-claim
      context and the preflight on the fetched target tip, refuse when a
      branch carrying the task id is already visible on any sanctioned
      prefix, and create and push `task/TSK-NNN-<slug>` from that tip;
      `status` shall report two branches carrying one task's id as a
      conflict; no command or document calls the claim a lock; evidence:
      claim tests and a text check.
      Spec: R-23, R-27, R-110.
- [ ] AC-4 When a code dependency is complete only on another line,
      `work start` shall refuse until the accepted change is in the task's
      base (merged or an explicit reviewed port); a research or decision
      dependency may be met at a pinned ref; an unfetched line is reported as
      unknown; evidence: cross-line journey.
      Spec: R-42.
- [ ] AC-5 A join awaiting selection shall carry `awaiting_selection` with a
      path that exists on the target, be blocked with the reason "awaiting
      selection" and that path as its revisit event, and may have an empty
      `depends_on`; it shall validate as a record and no caller context
      shall start it; a selection shall land only by a planning PR that
      removes `awaiting_selection` and writes the dependencies, never on a
      task branch; an empty `depends_on` without `awaiting_selection` is a
      root; a cancelled unselected alternative never blocks a join;
      evidence: a join that validates and cannot start, a refused selection
      on a task branch, and a cancelled alternative.
      Spec: R-26, R-43, R-104.
- [ ] AC-6 `status` shall show derived active, ready, waiting, landed (tip an
      ancestor of the target, or patch-equivalent) and epic progress, and
      shall not call a live integration branch removable; `orient` shall show
      a task summary; evidence: status and orient tests.
      Spec: R-27, R-44, R-75.
- [ ] AC-7 (journey) With the installed CLI on a fresh full-tier project
      holding blocked, waiting, cross-line and already-claimed tasks,
      `work next` then `work claim` shall pick a ready task and `status` shall
      agree; evidence: the section 10 backlog journey.
      Spec: R-104.
- [ ] AC-8 A spec shall keep no consumer list: its consumers are derived
      from the epics' and tasks' `specs` lists, and `spec new --for
      <id>...` shall write the new spec id into each consumer's `specs` list
      in the same planning change; an epic with no spec is valid,
      capabilities may list standalone tasks, and a standalone task
      completed by more than one pull request is a validator warning at
      closeout; evidence: command and validator tests.
      Spec: R-65, R-66, R-67.
- [ ] AC-9 (journey) With the installed CLI on a fresh full-tier project,
      the three caller contexts shall judge one task consistently: `work
      claim` in the new-claim context; `work start` and pre-commit in the
      own-branch context, keyed on the task id the checked-out branch
      carries on any sanctioned prefix, with status read at the merge-base
      and a staged transition judged by the transition and acceptance
      rules (the caller's branch is not a competing claim; any other
      visible branch is reported, not refused); and CI in the PR-transition
      context, keyed on the PR's `Task:` line and blocking a head branch
      that carries another task id; a complete or cancelled task fails
      every context; evidence: the full positive journey claim, start,
      build, complete and CI green, the own-branch journey on `fix/`,
      `feat/` and `spike/` branches carrying the id, a competing-branch
      negative control and a mismatched-association negative control.
      Spec: R-72, R-110, R-104.
- [ ] AC-10 A `depends_on` entry shall be a bare task id (a code
      dependency) or `{id, kind: research | decision, pin}`; a research or
      decision dependency is met when the predecessor is complete and the
      pin names a commit on the predecessor's target that holds its record
      as complete; an entry without a pin is unmet; the kind is never
      inferred from `work_type`; one predecessor may be a code dependency of
      one task and a research dependency of another; evidence: validator
      and predicate tests per case.
      Spec: R-26, R-112.

## Execution contract

- Plan: Plan v6, from design v4 section 12 (decision 2a). Size: medium.
- Seats: responsible primary, executor and cross-lineage reviewer are
  assigned at dispatch under
  `cf-model-orchestrator/resources/capability-routing.md`; Plan v6 does not
  name them.
- Integration: `task/TSK-103-<slug>` from
  `integration/EPC-020-delivery-system` after `codeflow work start` passes,
  which needs SPC-013 approved and every predecessor complete.
- Verification selection: a targeted mutation run on the readiness
  predicate (decision logic shared by four callers, where a wrong verdict
  starts work too early). Property tests: none selected; the dependency
  cases are a small finite set better enumerated directly.
- Recovery: read-only except `work claim`, whose pushed branch can be
  deleted by its owner.
- Closeout contract: capture bounded in-node discoveries only when they are
  review-relevant. A material graph, scope, interface, ownership, acceptance
  or safety change stops work and returns to both primary seats as Plan v7
  before implementation continues. Closeout cannot approve a deviation after
  the fact.
