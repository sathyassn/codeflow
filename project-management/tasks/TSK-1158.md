# TSK-1158: An epic closes a criterion that moved to another epic, with a waiver naming the moving amendment

## Description

Source: issue #492 (CodeFlow 3.1.1, by an adopter), read on the step 4
planning branch head `e0494dcb9` after a search found no open task that
covers it. A planning-only amendment moves a criterion from epic A (AC-5) to
epic B (as its AC-1) together with the tasks that serve it. The moved tasks
keep their `(serves A AC-5)` tags, because their criteria are frozen in the
line's range (issue #488, TSK-1154). `codeflow epic status A complete`
then refuses AC-5 as unverified, although A's acceptance block waives it and
names the planning-only commit that made the move. The adopter's workaround
is to delete the criterion line from A, which leaves the moved tasks tagged
with a criterion that no longer exists and which nothing reports.

Cause: `serving_tasks` (`crates/codeflow-core/src/workgraph/lifecycle.rs:1472-1482`)
matches a task to a criterion by its `(serves ...)` tag alone and ignores the
task's `epic_id`. A's AC-5 therefore still has serving tasks, so it is not
treated as an unserved criterion (`epic_own_block`, `lifecycle.rs:1548-1560`)
and the epic's waiver, which `epic_waiver_problem`
(`crates/codeflow-core/src/workgraph/acceptance.rs:1126`) already binds to a
planning-only amendment of that criterion, is never consulted.

Why no open task covers it:

- TSK-1129 (PR 478 head `d1ba70489`, `TSK-1129.md` Description and AC-2 to
  AC-4) changes the task waiver's own-range route and the planning-only path
  test that the epic waiver also uses (AC-3). It does not change which tasks
  count as serving an epic criterion, so issue #492 fails the same way after
  it. Nothing is added there; this task relies on that planning-only test
  as it stands and does not change it.
- TSK-1154 (issue #488) lets a task's own criteria change land. The moved
  tasks' tags are not a task's own change, and the freeze is not the
  cause here. TSK-350 is the PR-range rule, TSK-1124 and TSK-1152 change
  `work.acceptance_binding` and `work.criteria_frozen` for a `main` sync and
  a carried cancellation. None touches the epic completion check.

Design. A task serves the epic criterion its tag names only while the task's
`epic_id` is that epic. A tag that names epic A on a task whose `epic_id` is
another epic B is a moved serving task and is handled by a recorded move, not
by the tag alone:

- A's criterion carries a recorded move to B's criterion (the form is the
  dated note that criteria already use, settled in AC-1 against the existing
  criteria text rules; the existing `Moved YYYY-MM-DD` sub-bullet is a
  text-correction note, `record_text.rs:40-43` and `:64`, so the move form
  must not reuse that word). The move counts only when, read at the reviewed
  commit, B exists and its status is open (`EPIC_OPEN`, `lifecycle.rs:1034`;
  a complete, cancelled or archived B never counts), the single planning
  commit that records the move also introduces B's target criterion with the
  same obligation text and the same `(journey)` and `(after release)` tags,
  and the moved task's `epic_id` is B. A forged, dangling, self-referencing
  or pre-existing-destination move grants nothing, so a note cannot aim
  finished tasks at a criterion B already had.
- For A, the moved criterion is closed only by a `waived` row in A's own
  block that `epic_waiver_problem` accepts (a planning-only amendment the
  reviewed commit contains and which amends this criterion) and whose
  commit is the one that records the move, not an earlier wording change. A
  `verified` row, a tick or silence never closes it, and an `(after release)`
  source criterion stays on today's deferral path, which a waiver does not
  close, so moving a task cannot lower the proof a criterion needed.
- For B, the moved tasks' tags resolve through the recorded move to B's
  criterion only when those tasks are its only serving tasks, so B's close
  still needs a complete serving task that verified it, and a `(journey)`
  source still needs `journey: verified` on B. The proof stays with the
  tasks; only the epic's name changes.
- `codeflow validate --docs` warns (does not block) when a task's
  `(serves X AC-n)` names a criterion that does not exist, or names an epic
  other than the task's own that records no move to the task's epic.

Fail closed: a move that cannot be read, or any doubt about it, leaves the
criterion served and unverified, as today. Non-goals: no change to the
waiver's planning-only test, to the reopen freeze, to task criteria
(frozen as the line holds them) or to the criteria-authority rules of TSK-350
and TSK-1154.

## Outcome

After this merges, a maintainer can close an epic whose criterion moved to
another epic with the serving tasks, using a waiver that names the moving
planning commit, without deleting the criterion line.

- tests: `crates/codeflow-core/src/workgraph/lifecycle_tests.rs` and `crates/codeflow-cli/tests/` (a CLI fixture per case)

## Acceptance Criteria

- AC-1 Before any change, the builder shall reproduce issue #492's steps on the line tip, record which of its parts fail (the AC-5 refusal) and which already pass (the workaround's close), settle the form of a recorded move against the existing criteria text and amendment note rules (the `Moved YYYY-MM-DD` correction note is not reusable), and name every authority the move reads; evidence: a Findings section in this record, committed before the first code change.
- AC-2 (journey) When epic A's criterion is recorded as moved to open epic B's existing criterion, its serving tasks' `epic_id` is B and A's block waives the criterion with a planning-only commit the reviewed commit contains, `codeflow epic status A complete` shall succeed; evidence: a CLI fixture of the issue's repro through the built binary in a scratch repository, refused before the change and accepted after.
- AC-3 Epic A shall still refuse the moved criterion when: (a) its row is `verified`, a tick or absent; (b) the waiver names a commit that is not a planning-only amendment of that criterion or that the reviewed commit does not contain; (c) the move names a missing, cancelled, archived or complete epic, a missing criterion, or the same epic; (d) a serving task's `epic_id` is not B; (e) the move cannot be read; (f) the waiver names a commit other than the one that records the move; (g) the source criterion is `(after release)`; (h) B's criterion existed before the move, or differs from A's in text or in its `(journey)` or `(after release)` tags; evidence: one fixture per case (eight), each refused after the change for the stated cause, naming it.
- AC-4 Epic B shall verify the moved criterion only through a complete serving task that recorded `verified` or `waived` for it (with `journey: verified` for a journey criterion), resolved through the recorded move, and only when the moved tasks are its only serving tasks; a move with no complete serving task, or with another serving task still open, shall leave B refused; evidence: fixtures for each and the existing serving-task tests unchanged.
- AC-5 A criterion with no move recorded shall keep today's verdict, including a task tagged with an epic other than its own, so the change widens nothing else; evidence: the existing `lifecycle_tests.rs` cases passing unchanged and one fixture for the unrecorded foreign tag.
- AC-6 `codeflow validate --docs` shall warn, naming the task and the tag, when a `(serves X AC-n)` tag names a criterion that does not exist or names another epic with no recorded move to the task's epic, and shall stay silent for a recorded move; evidence: warning fixtures and one silent control.
- AC-7 `docs/delivery.md` and the managed epic-close text shall say how a criterion moves with its tasks and what closes it in each epic, matching the managed copies; evidence: the doc diff and `codeflow validate --docs` green.
