# TSK-175: seat postures, operator actions, live journey and decision record

Unit 5 of 5 of the harness permissions work (TSK-171 to TSK-175). It lands the decision record
(`ADR-0075`) and closes the work (design:
`docs/verification/permission-presets-design-2026-09-28.md`).

## Description

Units 1 to 4 build the presets, guards, runtime and the one sandbox exit.
The seats still launch with the postures the skills describe, and some of
those texts contradict each other: Codex Herdr seats launched in the consult
posture cannot write Git metadata, Grok seats run with no sandbox, and the
skills name `pane run` and `pane send-text` for briefing.

This unit applies the operator's decisions of 2026-09-28 to the launch text:
D1, Codex builders move to the `cf-builder` profile only if the spike shows
fetch, worktree add, commit and builds working unattended, otherwise keep
full access with the gap recorded; D2, Codex reviewers run `never` with no
`--sandbox` flag; D3, Grok builders run `--always-approve --sandbox
cf-guard-worktree --trust`, launched in their own task worktree after a
separate trust step for that same directory. It also
applies D7 to D10 as decided the same day (workspace `RELEASE-PLAN.md:537-541`):
seats briefed only with `herdr agent prompt`, folder trust granted at launch,
Escape as the only key; guard hooks fail closed with the exact command named;
agents on their own fine-grained token with workflow pushes queued; and
fixtures under one admitted root. It sets the criteria for the one
operator-actions list that every step needing the operator goes on. It runs
the live journey in disposable fixtures, resolves every open row of the
closeout evidence matrix, and lands the decision record.

- AC-8 (operator-actions list) Every step that needs the operator shall go
  on one list, `.codeflow/operator-actions.jsonl` in the repository's main
  checkout (resolved through the common git directory, so every worktree
  shares it), listed in the managed `.gitignore` block and not an
  enforcement path, written only through TSK-172 AC-25's safe-path writer.
  It is an append-only event log (`docs/verification/evidence/permission-presets/state/operator-actions.example.jsonl`):
  an action line holds `id`,
  `key` (kind plus subject, for de-duplication), `kind` (one of
  `herdr-keys`, `folder-trust`, `binary-update`, `project-update`,
  `binary-rollback`, `workflow-push`, `enforcement-approval`,
  `codex-hook-trust`, `fixture-root`, `enrollment`, `seat-approval-prompt`),
  `subject`, `command` (the exact command, or the exact operator step where
  there is none), `why`, `blocks` (what waits on it), `recorded_by` (guard
  or agent, with session and seat) and `recorded_at`; an event line holds
  `id`, `event` (`updated`, `done`, `withdrawn`), `at` and `by`, and the
  row for an `id` is the fold of its action line with its later events,
  which carry only the fields they change, never the last line alone. A
  `workflow-push` action line carries the parsed tuple as fields
  (`source_commit`, `destination_url`, `destination_ref`) beside the
  display `command`. Guards append when they refuse with
  "queued for the operator"; an agent appends through `codeflow
  operator-actions add` when it meets an operator step no guard recorded; a
  request whose `key` is already open appends an `updated` event with its
  current destination, command and blocker, so the row never shows a stale
  one. Appends are serialized by the writer's lock. `command` is display
  text only: no CodeFlow component executes it, pastes it into a pane or
  pipes it anywhere, and status and the digest print it quoted. The list grants no authority: nothing reads an entry as
  approval, marking one `done` changes no guard decision, and each guard
  re-checks the live condition. `codeflow status` and the orient digest
  show the open entries, newest first, with the count; the orchestrator's
  status report to the operator (the hourly status, `RELEASE-PLAN.md:541`)
  leads with open entries and those added since the last report. At E20 the
  orchestrator skill has no status-report step (no match for "hourly" or
  "status report" in `assets/base/agents/skills/cf-model-orchestrator/SKILL.md`),
  so this unit adds it. Marking a row done or deleting it shall not hide
  an outstanding dependency (`docs/verification/permission-presets-design-2026-09-28.md` 9.2): kinds with repository
  evidence (binary and project contract, enforcement approval, Codex hook
  trust, enrollment and fixture root, and `workflow-push`, which status
  reconciles by running TSK-172 AC-23's classification for each local task
  branch and each live worktree's branch against its push destination) are
  shown from that evidence, a row marked done while the evidence says
  outstanding is shown outstanding with the reason, a deleted row is
  reconstructed, a completed operator push closes the row with a `done`
  event by status, and an unreadable destination shows "unknown", never
  done; kinds without repository evidence (`herdr-keys`,
  `seat-approval-prompt`, and a `folder-trust` the harness store cannot
  show) are kept by the host in its delegate record under the CodeFlow
  state root, outside the queue file, outstanding until their evidence
  clears or the operator confirms to the host, and shown with "deleting
  from the queue is not completion". The same record keeps every
  workflow-push requirement whose exact source and destination cannot be
  reconstructed, whatever its kind: A workflow push whose exact source commit and resolved destination (push URL and ref) cannot be reconstructed from the branch's configured push destination is kept, as that tuple, in the host dependency record outside the editable queue until evidence for that destination shows the source reachable from its advertised tip, or the operator explicitly withdraws it; reconciliation uses that tuple and never substitutes the branch's current default. The skill text shall tell the agent to record and continue, and
