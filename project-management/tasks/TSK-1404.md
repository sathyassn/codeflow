# TSK-1404: Both guards refuse a program word they cannot fill

## Description

When a command's program word is built from a parameter, a brace form or a
word another program supplies, the guards fill it from the line's literals
before judging the command. TSK-326's cross-lineage review (PR 718, Grok
delta 6, F1) found that when the fill fails, git-guard refuses only where it
sees signs of git in the arguments, and otherwise leaves the command to
exec-guard, whose deletion check does not report every such command as
unproven, so the deletion floor does not always refuse it. In an agent session a
program word the guards cannot fill is therefore not refused in every case.
This task makes both guards refuse a program word they cannot fill, naming
the rule and the remedy "spell the program literally", and makes the deletion
check report it as unproven. A literal assignment on the same line still
fills the word and passes. It is a security change and needs a cross-lineage
review with the security checklist. Non-goal: words in other positions,
which TSK-326 covers.

## Outcome

After this merges, an operator can rely on both guards refusing, in agent
sessions, a command whose program word they cannot fill, with a remedy that
says to spell the program literally.

## Deliverables

- the guard change and its tests: `crates/codeflow-core/src/hooks/` (git-guard) and `crates/codeflow-core/src/security/` (exec-guard and its deletion check)
- the over-refusal measurement and the sibling sweep list: the pull request body
- the refusal and its remedy in the policy reference: `docs/policy-reference.md`

## Acceptance Criteria

- AC-1 In an agent session, when the program word of a command is an unassigned parameter, a brace form or a supplied-input marker that the guard cannot fill from the line's literals, exec-guard and git-guard shall each refuse the command whatever the evidence of git in its arguments, naming the rule and the remedy "spell the program literally"; evidence: one test per guard and per kind of unfilled word, each failing before the change and passing after.
- AC-2 The deletion check shall report a command whose program word is spelled but unfilled, or whose child program word is a supplier's replacement string, as unproven, so the deletion floor refuses it; evidence: one test per form, failing before the change and passing after.
- AC-3 A program word filled by a literal assignment on the same line shall still be filled and judged as the program it names, and shall pass where that program passes; evidence: one test per guard, passing before and after the change.
- AC-4 Before the pull request goes ready, the builder shall measure how many commands in the repository's scripts, docs code blocks and test corpus the change newly refuses, and list each by its form; evidence: the count and the list in the pull request body, each new refusal either a true unfilled program word or fixed in this change.
- AC-5 Every other place in either guard or the deletion check where a failed fill returns early without a refusal shall be swept for the same class and listed, each with the test that covers it or the reason none is needed; evidence: the list in the pull request body, and a fail-before and pass-after test for each place that had the gap.
- AC-6 The policy reference shall describe the refusal and its remedy; evidence: the `docs/policy-reference.md` diff.
- AC-7 The change shall have a cross-lineage security review with the `cf-security-reviewer` checklist, with the seat's availability checked live at dispatch; evidence: the review row and its findings record.
