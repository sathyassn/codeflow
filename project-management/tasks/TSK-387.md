# TSK-387: The managed map and autonomy guidance cover multi-session coordination

## Description

Issues: #223 and #225, two field reports from one adopter that ran a coordinator, six lanes and many Codex and Grok seats on one machine for a day. In each case CodeFlow already had the guidance, or nearly, but the managed `AGENTS.md` map or `cf-method` autonomy guidance never pointed a session at it, so the operator repeated it in chat.

From #223 (the map):

- seat tabs: the cleanup row covers branches, build output and worktrees, not Herdr seat tabs (`cf-herdr` "Cleanup" has the rule);
- standing operator rules: no row says where a rule the operator gives in chat is recorded (`standing_reviews` in `.codeflow/model-selection.json`, policy or a config key, else one project line);
- standing reviews: the review and PR rows do not name the reviews `codeflow models resolve` owes for the touched areas;
- pre-handoff checks: the status row does not say to check live state (remote ref, PR, checks) before handing the operator a command.

From #225 (autonomy guidance):

- a peer seat's command prompt inside its brief's scope is the host's to answer and record; anything outside goes to the operator;
- a classifier refusal with no stated rule of an in-scope verification command is distinct from a policy guard that names the operator; the sanctioned next step is stated, including a host-run route the operator turns on once in config;
- operator delegations have a recorded home, and the autonomy rows read "the operator, or the delegate the project records";
- shared machine resources: the host orders the gate queue and can ask lanes to defer heavy runs;
- message budgets: batch one digest per lane rather than stall on a count;
- a stuck-lane sweep before each status report.

Outcome: **a session in an adopting project finds, from the managed map and the autonomy guidance, what to do in each of these multi-session cases without the operator repeating it.**

Non-goals: new commands or checks (the `doctor` seat count and `ci` standing-review comparison suggested in #223 item 3, and a queue-aware gate lock from #225 item 4, beyond what TSK-331 delivers); each stays a separate request. Adding a standing approval or setting is a proposal to the operator under "Only the operator adds process", not a rule this task grants.

Added by the EPC-022 amendment of 2026-10-18 under the operator's release decision of that day (workspace `RELEASE-PLAN.md`, 2026-10-18 operator decision).
