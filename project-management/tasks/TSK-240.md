# TSK-240: Issues are handled by cause and class, with a written critical path

## Description

This cycle's defects were fixed one site at a time (issue 60 left four
sites of its class, which became issue 79), review loops ran without a
diagnosis (PR 56 took eight rounds before its approach was withdrawn), one
rule was redesigned in parallel by PRs 42, 61 and 73, and issue 48 had no
written critical route. This task ships the issue-handling process the
operator approved: a project-neutral reference in `cf-method` that takes a
reported defect from intake to closure (reproduction and severity, cause and
defect class, sibling sweep, grouping by cause with a design first for rule
mechanisms, a fix of the whole class with a durable check where one can be
written, review of class coverage and the sweep with a re-diagnosis trigger,
release target, closure note) and the critical path; the pointer from the
lifecycle's repair bullet; CodeFlow's own release routes for a critical
issue; the reporter's side; and the reviewer's two checks. Effect on
adopting projects at the standard and full tiers: `codeflow update` installs
the new reference, a changed lifecycle reference and a changed `cf-reviewer`.
It adds no check, no PR, no approval and no review round. Non-goals: a
maintenance-release route, a `codeflow ci` rule on fix PR bodies, a severity
field in any record schema, and creating the GitHub label, which the
operator does.

Operator decisions (source: operator, chat, 2026-10-04), on the issue
handling design drafted that day:

- Adopt the design as written, all six pieces: intake with reproduction and
  severity; cause and defect class; sibling sweep; group by cause with a
  design first for guards, parsers, policy, acceptance rules, hooks and CI;
  fix the class with a durable check where one can be written; review that
  checks class coverage and the sweep, with the re-diagnosis trigger;
  release target; closure note.
- A `critical` label and a severity line in the bug report template.
- A critical fix may jump work within its epic on the primary's call;
  jumping another epic's planned work is the operator's call.
- Releases stay main-only with no maintenance branch; critical fixes land
  first so `main` stays releasable.
- The per-task reading guideline may rise by 256 bytes in this change if the
  pointer does not fit. It fits: the chain measures 131041 of 131072 bytes,
  so the guideline is unchanged.
