# TSK-165: task work in linked worktrees, the root checkout on its root branch

## Description

The operator decided on 2026-09-28 (workspace `RELEASE-PLAN.md`, "Operator
decisions, 2026-09-28": the worktree rule, option A, and the workspace
layout) that task work happens in a linked worktree on a feature branch and
the root checkout stays on its designated root branch. Today the rule lives
only in prose: CodeFlow's own `AGENTS.md` and the shipped
`.codeflow/rules/worktrees.md` ("Develop in a worktree per session ...
Protected branches stay at the repo root"). Nothing stops an agent from
switching the root checkout to a feature branch and committing there, and
`doctor` checks only for a protected branch in a linked worktree
(`doctor/mod.rs:1400-1427`, the second signal of `check_repo_integrity`).

This task adds a policy key that names the root branch, blocks agent commits
at the root checkout on any other branch in git-guard and the git hooks,
warns a human at their own terminal, and reports the root checkout in
`doctor`. It also supports "workspace mode": an umbrella repository with
CodeFlow projects inside, such as the agentic-systems workspace, whose root
checkout stays on a working branch on purpose, because sessions load their
instructions and settings from it. CodeFlow's convention name for that
branch is `integration/workspace`, held in one constant. `codeflow init
--workspace` sets an umbrella up; `doctor` recognises workspace mode by
`git.root_branch`, checks that nested repositories are ignored and
recognises the worktree folders the harnesses manage; a short guide explains
the layout. The contract every tier ships states the rule.

A project (a repository that is not an umbrella) keeps its default branch as
its root branch. Every default leaves a single-repository project that
already follows the shipped doctrine (root checkout on its default branch,
worktrees under `.worktrees/`) without a new refusal, warning or change.

Non-goals: switching the root checkout (`checkout`, `switch`) stays
unguarded and is reported by `doctor`; the rule judges commits. Settings
unit 2's effective-context resolution (its AC-13, draft v10) and nested
repository enrolment (its AC-21) are not built here. The check that an
umbrella's harness settings are at least as strict as each enrolled
project's, named in the workspace layout decision, is not in this task; the
harness permissions work owns it as its unit 3 AC-13 (settings v11), which
detects an umbrella through `git.root_branch`.
Setting the agentic-systems workspace's own policy key is the operator's
adoption step after the release.

## Affected surfaces and interfaces

- Policy: three new `git` keys in `assets/base/policy.json`, the parser
  (`hooks/policy.rs`), the schema (`hooks/policy_schema.rs`) and the key
  list in `docs/adoption.md`:
  - `git.root_branch` (string, default empty): the branch the root checkout
    holds. Empty means the repository's default branch, resolved in this
    order: the target of `refs/remotes/origin/HEAD`, then the first
    `protected_branches` entry that exists as a local branch, then `main`.
    An umbrella sets it, normally to `integration/workspace`. A value that
    is not a valid branch name is a policy error.
  - `git.root_checkout_commits` (level, default `block`): the rule's level,
    suspended in bootstrap grace like the other git rules.
  - `git.worktree_locations` (list): where linked worktrees may live. The
    default covers `.worktrees/` and the folders the harnesses manage:
    `.claude/worktrees/` (the Claude desktop app, observed in the

## How the hooks tell an agent from a human

The in-session git-guard runs only inside a harness session, so every
command it judges comes from an agent; it blocks at the policy level and
never reads the environment to decide who is acting. The git hooks run for
everyone and read the process environment, which the harnesses mark:

| Harness | Marker in the shell environment | Evidence |
|---|---|---|
| Claude Code | `CLAUDECODE=1` | observed in this session's Bash tool, Claude Code 2.1.281, 2026-09-28 |
| Codex CLI | `CODEX_SESSION_ID` and `CODEX_CI=1` on the agent's exec tool (unified exec, its only shell tool at this commit), `CODEX_SESSION_ID` in the user's shell too, `CODEX_THREAD_ID` when a thread id exists | `openai/codex` `4fd5745`: `core/src/exec_env.rs:40-50`, `core/src/unified_exec/process_manager.rs:103`, `:1451`, `core/src/tasks/user_shell.rs:170` |
| Grok Build | `GROK_SESSION_ID` in the session environment its bash tool runs with, and in the user's bash mode | `xai-grok-build` `f0e3be1`: `xai-grok-shell/src/session/agent_rebuild.rs:297-300`; the bash tool reads it through `SessionEnv` (`xai-grok-tools/src/registry/types.rs:1005`, `implementations/grok_build/bash/mod.rs:1692`); bash mode through `xai-grok-shell/src/session/acp_session_impl/tool_dispatch.rs:289-294` |

A hook that sees any marker treats the actor as an agent and applies the
rule's level. A hook that sees none cannot tell, and treats the actor as a
human: it warns and lets the commit proceed. An agent that strips its
environment still meets git-guard, which does not depend on it. A human
working in a marked shell (a harness's user shell mode) is judged as an
agent; `CODEFLOW_HUMAN_OVERRIDE`, which the git layer already honours and
git-guard never trusts (ADR-0007), makes the hook treat the actor as a
human, so the finding is a warning.

## Acceptance Criteria

- AC-1 The policy carries `git.root_branch`, `git.root_checkout_commits`
      and `git.worktree_locations` with the defaults above in
      `assets/base/policy.json`, the parser, the schema and
      `docs/adoption.md`; an invalid `root_branch` value is a policy error;
      bootstrap grace suspends the rule; evidence: policy parser and schema
      tests, including an invalid branch name refused.
- AC-2 When an agent session commits at the root checkout on a branch other
      than the resolved root branch, or on a detached HEAD, git-guard shall
      refuse it under `git.root_checkout_commits`; the same holds for
      `git -C <root>` from a linked worktree and for each commit-creating
      subcommand listed above; at `warn` it warns and at `off` it is
      silent; evidence: git-guard unit tests for each case.
- AC-3 The pre-commit and pre-merge-commit hooks shall block such a commit
      when any harness marker in the table is set, and warn and let it
      proceed when none is set or when `CODEFLOW_HUMAN_OVERRIDE` is set;
      evidence: hook tests with each marker alone, with no marker, and with
      a marker plus the override.
- AC-4 A protected root branch keeps today's protection: a commit at the
      root checkout on `main` is refused by `git.commit_to_protected`
      exactly as before, and the new rule adds no finding there; evidence:
      the existing protected-commit tests pass unchanged, plus one test with
      `root_branch` set to `main` explicitly.
- AC-5 `codeflow doctor` shall report the resolved root branch and its
      source (policy, `origin/HEAD`, protected list or fallback), and warn
      when the root checkout is on another branch or detached, naming the
      branch and whether it holds uncommitted or unpushed changes, and when
      the root checkout on a protected root branch holds uncommitted changes
      to tracked files (the root takes no task edits); a root branch the
      policy names but the repository lacks is a warning; evidence: doctor
      tests for each case.
- AC-6 Nested repositories are found by git's own marker, not by CodeFlow:
      any folder under the umbrella whose `.git` is a directory or a gitdir
      file, at any depth, excluding linked worktrees of the umbrella itself
      and the paths the umbrella's `.gitmodules` registers as submodules.
      The search skips `.worktrees/`, registered submodules and folders a
      tracked `.gitignore` already ignores, and does not descend into a
      nested repository once found. `codeflow doctor` shall warn for each
      nested repository no tracked `.gitignore` covers, naming the entry to
      add; one ignored only by a local exclude source (`.git/info/exclude`
      or a global excludes file) is a warning too; a gitlink that is not a
      registered submodule is a warning; a registered submodule is never
      flagged. Each message says whether the folder is a CodeFlow project
      (it carries `.codeflow/`) or a plain git repository; evidence: doctor
      tests for a nested plain repository, a nested CodeFlow project, a
      repository two levels deep, a registered submodule (tracked and
      unflagged), and each warning case.
- AC-7 `codeflow doctor` shall list each linked worktree with its location
      and accept one under any `git.worktree_locations` entry; it warns for a
      linked worktree outside every entry, naming its path and the route,
      and for one inside the repository's tree that no exclude source
      ignores; evidence: doctor tests with a worktree in each default
      location, a sibling folder, and an unignored folder inside the tree.
- AC-8 `codeflow doctor` shall recognise workspace mode when
      `git.root_branch` is set in a repository that contains nested
      repositories, report it, and check the root checkout is on that
      branch; a repository with nested repositories and no `root_branch`
      set gets a recommendation naming `integration/workspace` and
      `codeflow init --workspace`; evidence: doctor tests on an umbrella
      with and without the key.
- AC-9 `codeflow init --workspace`, run by the operator, shall create
      `integration/workspace` from the default branch or reuse it when it
      exists, check it out at the root, set `git.root_branch` to it, add
      each nested repository found as in AC-6 that no tracked `.gitignore`
      covers to the umbrella's `.gitignore` (never a registered submodule),
      listing each as a CodeFlow project or a plain git repository, and
      print the next steps (the nested-repository inventory once the harness
      permissions work lands, and `main` as the milestone checkpoint). It
      shall never switch branches over uncommitted changes: it refuses and
      names them. A rerun changes nothing; evidence: init tests on a fixture
      with nested repositories (branch created and checked out, key set, a
      nested plain repository and a nested CodeFlow project ignored, a
      repository two levels deep found, a registered submodule left
      tracked), a rerun with no change, and a refusal on a dirty tree.
- AC-10 Plain `codeflow init` and `codeflow update` in a folder that
      contains nested repositories shall switch nothing: they report that
      the folder looks like a workspace and name `codeflow init
      --workspace`; evidence: an init test and an update test on an umbrella
      fixture printing the hint and leaving the branch and policy unchanged.
- AC-11 The convention name lives in one constant in the new module. init,
      doctor, the refusal and warning texts and the rendered contract use
      it, and no source file repeats the string; the guide names it and a
      test checks that the guide's name equals the constant; evidence: a
      test that searches the source tree for the literal outside the
      constant, and the guide pin.
- AC-12 Positive cases pass with no finding from this task: the root
      checkout on `main` in a single repository with a linked worktree under
      `.worktrees/<slug>` on a feature branch, committing there; an umbrella
      repository with `git.root_branch: "integration/workspace"` whose root
      checkout sits on `integration/workspace` and holds uncommitted
      changes, with a nested CodeFlow project ignored by the umbrella's
      `.gitignore`, committing at the root; evidence: git-guard, hook and
      doctor tests on temporary repositories, and a doctor output
      comparison showing the single repository's report gains only the
      root-branch line.
- AC-13 Negative cases are refused or reported: a single repository whose
      root checkout is on `feat/x` with an agent commit (git-guard refuses,
      the hook blocks with a marker); a single repository whose root
      checkout on `main` holds task edits (doctor warns); the umbrella's
      root checkout switched to `feat/x` with an agent commit (refused, and
      doctor names `integration/workspace` as the root branch); the umbrella
      with a nested repository its `.gitignore` does not cover (doctor warns
      and names the entry); evidence: the same test files.
- AC-14 Every refusal, warning and doctor message from this task names the
      rule, the repository, the branch or path it found, the designated root
      branch where one applies, and the exact next step, for example: "root
      checkout of <repo> is on feat/x; its root branch is
      integration/workspace. Do task work in a worktree: git worktree add
      .worktrees/<slug> -b <branch>". Each case in AC-2, AC-3, AC-5 to
      AC-10 pins its full message text in a test.
- AC-15 (journey) On a fresh `codeflow init` project driven by the built
      binary through its installed hooks: a commit in a linked worktree
      passes, an agent-marked commit at the root on a feature branch is
      refused, an unmarked commit there proceeds with a warning, and
      `codeflow doctor` reports the root checkout; then `codeflow init
      --workspace` on an umbrella fixture with a nested project sets it up
      and doctor reports workspace mode; evidence: an end-to-end test using
      the real hooks and binary.
- AC-16 The contract every tier ships states the rule: the moment table's
      branch row in the three `AGENTS*.md.tmpl` templates, `worktrees.md`
      ("Where work happens": task work in a linked worktree under
      `.worktrees/<slug>` or a harness-managed worktree folder, on a feature
      branch; the root checkout stays on its root branch and takes no task
      edits; an umbrella's root branch is `integration/workspace` by
      convention) and `git-rules.md` (the pre-commit plane lists the rule;
      agents are blocked, humans warned). For an umbrella, `worktrees.md`
      also says in a few plain bullets how a change lands, the two rules of
      AC-17, including that at a milestone the operator moves `main`
      forward and agents never do. The policy keys' doc comments and
      the contract text each say in one or two plain sentences what the
      root branch is, its default, and when to change it. Mirrors,
      baselines and the manifest are regenerated; evidence:
      `manifest_consistency`, `init_e2e` and a text pin for each template
      and rule file.
- AC-17 `docs/workspace-mode.md` explains workspace mode, consistent with
      the agentic-systems workspace `AGENTS.md` ("Workspace branch", "Where
      sessions get their settings"): an umbrella repository with CodeFlow
      projects inside; a figure of the layout (the umbrella, the nested
      projects, where each one's worktrees go, which settings apply where);
      the root on `integration/workspace`; nested repositories ignored;
      adoption steps (`codeflow init --workspace` at the umbrella, which
      sets the root branch and ignores the nested repositories, then the
      nested-repository inventory bind once the harness permissions work
      lands); `main` as the milestone checkpoint; harness settings come
      from where a session starts; a short "when to use this, when not"
      section; and how a change lands, in the figure and a few bullets:
      - The umbrella's own files: a small edit is a commit on
        `integration/workspace` at the root checkout. Larger or parallel
        work uses a short-lived branch in the umbrella's own `.worktrees/`,
        cut from the root branch and merged back with `codeflow
        integrate`. With no remote, the root branch is the landing line
        and `main` is a protected checkpoint: at a milestone the operator
        moves it forward with `codeflow integrate integration/workspace
        --into main`; agents never do. With a remote the same holds,
        the root branch is pushed, and a change into `main` is a pull
        request a human merges.
      - A nested repository: every change goes through that repository's
        own flow, a worktree under its own `.worktrees/` and a pull request
        into its integration branch or its `main`. The umbrella never
        commits nested files, which it ignores, and agents never merge
        into any repository's `main`.
      Write the guide plainly: simple, straightforward and clear, no
      mannered prose (see `.codeflow/rules/writing.md`).
      `docs/adoption.md` links it; evidence: the guide, a
      text pin for the landing bullets in the guide and `worktrees.md`, and
      `validate --docs`.
- AC-18 A decision record states how the hooks tell an agent from a human
      (the marker table with its sources, what a hook does when it cannot
      tell, the relation to ADR-0007's override) and the workspace
      convention (`integration/workspace`, and that it is not an epic line,
      which TSK-166 carries into `codeflow ci`); the
      CHANGELOG carries a pending entry naming the new default-block rule as
      a behaviour change for adopters and the new `init --workspace`;
      evidence: the ADR and the entry.
- AC-19 Before landing, a fresh Fable editorial review of all new text (the
      contract text, the guide, the doc comments, the messages and the
      decision record) approves it, alongside a Codex code review and a
      Grok review of the change; evidence: the review records bound to the
      reviewed commit.
