# TSK-242: Guards protect shell startup files from agent writes

## Description

No guard stopped an agent from writing a shell startup file (GitHub issue 86), so an agent could plant `ls() { sudo "$@"; }` in `~/.zshrc` and every later command-text guard would judge `ls`. This task makes the startup files a protected class, generated from one list in `crates/codeflow-core/src/security/actions.json`: the home startup files of bash, zsh, sh and ksh, fish, PowerShell and readline, the shell-adjacent files (`.ssh/rc`, tmux, screen, direnv's configuration and trust store), the system files under `/etc`, and `.envrc` in any directory. Containment comes from the harness sandboxes: the Claude presets' generated `Edit(...)` denies, which Claude also applies as sandbox write denies, and explicit `sandbox.filesystem.denyWrite` entries; and the Codex `cf-guard` profile's read-only entries, which `cf-builder` inherits, with Codex builder seats moving to `cf-builder`. The guards are the backstop on every harness: edit-guard refuses a native edit of the class and exec-guard refuses the shell writes it can see, both under the always-blocking rule `security.shell_startup`, with no policy key and no relief. Git-guard also refuses setting a git configuration key not known to run nothing at global or system scope, or in a file that is not a repository's own configuration, under `git.hook_integrity`. Non-goal: proving that no program can write a startup file on a seat without a sandbox. The text guard cannot see a path built at run time, a script written in one call and run in another, or a program that writes the file on its own; the docs state this per harness. Sibling classes are tracked separately: issues 87 (programs planted in a `PATH` directory), 88 (git config include files), 89 (npm `script-shell`), 90 (session environment files) and 91 (LaunchAgents and user services).

## Decisions

- 2026-10-05, operator, relayed by the primary session: Codex builder seats move into the `cf-builder` sandbox profile, which cannot write home startup files, replacing ADR-0075 D1's full-access builder posture. Real containment is filesystem denies wherever a harness has a sandbox; the text guard is the backstop, and the PR states plainly what it cannot stop. The claim that only user-planted definitions remain is dropped.
- 2026-10-05, operator, relayed by the primary session: no relief. The rule always blocks: no `security.shell_startup_allow`, no `warn` or `off`; the user edits their own profile. As relayed: "No edit-guard wiring for Claude edit tools is needed."
- 2026-10-05, operator, relayed by the primary session: adopt the review refinements (writers that name a startup path or write into the home or a startup directory refuse; startup environment assignments on a line that launches a shell refuse; no run-time following of sourced files, doctor reports them; typed anchors; an own rule id; `.envrc`, `.inputrc` and `.ssh/rc` stay in this task) and file the sibling classes as issues 87 to 91.
- 2026-10-05, design reviews by Codex GPT-6 Astra (high, interactive Herdr seat): round 1 unsound (a text guard cannot stop a path built at run time on a seat without a sandbox), round 2 sound with changes (reader exemptions judged by operation, glob words expanded through symbolic links, effective startup locations such as `ZDOTDIR`, `.zwc` companions and the fish XDG directory, read-only git and `cp` sources stay allowed, a per-harness containment statement); all adopted.
- 2026-10-07, builder, from review rounds 3 to 5 and the design pass (Grok 4.7, Fable): the staged-run check is an allowlist of data readers, not a list of programs that run text. Rounds 3 to 5 each found an unlisted spelling that ran text the call produced (a script option in another form, a wrapper, `env -S`), and the allowed `awk` and `sed` forms could run it too. The rule now refuses a line that names a class file and produces text unless every program on it is a data reader used as one. AC-7 gains one exception clause for it; the measured cost is the set of ordinary programs that now refuse on such a line (shells, editors, `make`, wrappers), recorded in the PR. The criterion changes within the task; the outcome does not.
- 2026-10-08, builder, from review round 10 (Grok 4.7): git-guard's user- and system-scope key check moves from a list of code-running keys to the key classification the staged-run check already used, now shared in `security/git.rs`: a key not known to run nothing refuses at that scope. The round found `difftool.<tool>.path` and `gpg.ssh.defaultKeyCommand` executed after a global set and six more keys the list missed, the same long-tail shape rounds 7 and 8 found in the staged check. Measured cost on 38 ordinary global settings: `safe.directory`, `protocol.file.allow`, `diff.tool` and `merge.tool` newly refuse, by intent; the harmless keys that refused in the first cut (`commit.gpgsign`, `gpg.format`, `index.version` and the like) joined the safe list. AC-5 and AC-7 now name keys not known to run nothing instead of listed keys. The same batch shares one list of git's value-taking global options among every parser (issue 120), which also closes a protected push or tag push written behind `--attr-source` or `--shallow-file`.
- 2026-10-08, builder, from review round 11 (Grok 4.7): a `--file` write counts as user or system scope unless the file is a repository's own configuration (a `config` or `config.worktree` in a git directory, a `.gitmodules` or a `.lfsconfig`), judged through its symbolic links, instead of matching a list of user and system files. Round 11 found `--file /opt/homebrew/etc/gitconfig` allowed while Homebrew git reads it as its system file. git reads the system file under whatever prefix it was built with (a source build defaults to `~/etc/gitconfig`) and every file a configuration includes, so a path list has the same long-tail shape as the key list of round 10; the derived-prefix remedy would know only the gits the hook can see, and on the review host Homebrew's exec path implies `/opt/homebrew/opt/git/etc/gitconfig` while `git var GIT_CONFIG_SYSTEM` reports `/opt/homebrew/etc/gitconfig`. A call with no scope option is judged by the file `GIT_CONFIG` names. Measured cost: a project fixture or scratch file given a key not known to run nothing now refuses (`git config --file fixtures/.gitconfig alias.x y`); a known-safe key anywhere, a repository's own file, reads and unsets still pass. The same round matches key names exactly instead of by part of the name and takes the switches beside the tool programs (`difftool.prompt`, `mergetool.keepBackup`, `uploadpack.allowFilter`, `rebase.rescheduleFailedExec`, `pager.<command>` as a number) as booleans, and builds the refusal from the setting, its value and where it lands. The sibling sweep found the shell-write and native-edit check of the user's git files (`edit_guard.rs`) knew no system file; it now also refuses a `gitconfig` in any `etc` directory and the file `GIT_CONFIG_SYSTEM` names. AC-5 and AC-7 now name that file scope.
- 2026-10-08, builder, from review round 12 (Grok 4.7): a default, `--local` or `--worktree` write is judged by the file git opens, not by its flag. Round 12 found git following a symbolic link at `.git/modules/<name>/config`, at another repository's `config.worktree`, at a bare git directory's `config` and at an existing `.git/config`, and it ran a planted `core.fsmonitor` from the user's file in a second repository. git-guard now resolves the selected git directory (`-C`, `--git-dir`, `GIT_DIR`, the `.git` file and the payload cwd, through git2) and passes its `config`, and with `--worktree` its `config.worktree`, through the same file-scope check as `--file`; a git directory named but absent is judged by its path, and a call whose repository the guard cannot locate refuses a key not known to run nothing. The file is read only after the key is classified, so a known-safe key costs nothing; measured cost on the other writes is about 1 to 3 ms per hook call. A second layer refuses `ln`, `cp`, `mv` and `rsync` onto a git directory's `config` or `config.worktree`, which covers a link made on the same line as the write; the session repository's own `config` was already authority metadata. `core.fsmonitor` set to a boolean is safe (git starts its own monitor), and a path value still refuses. The shell refusal of a user or system git file now names that class instead of remote-tracking metadata. AC-5 names the opened file.

## Acceptance Criteria

- AC-1 When a native edit (Codex `apply_patch`, `Edit` or `Write`, Grok `write` or `search_replace`) targets a startup file in any spelling (`~/`, absolute, relative from a home working directory, another letter case, through a symbolic link, under `ZDOTDIR`), edit-guard refuses it under `security.shell_startup` with the sanctioned path, and an ordinary file passes (unit tests in `edit_guard.rs` and the real hook in `crates/codeflow-cli/tests/`); Claude's `Write` and `Edit` are held by the generated `Edit` denies for the default locations instead, since its file tools are not wired to edit-guard (the no-relief decision of 2026-10-05 above), and a relocated `ZDOTDIR` is a stated residual that `codeflow doctor` reports.
- AC-2 When a shell call writes a startup file by a visible form (a redirect, `tee`, `cp`, `mv`, `ln`, `install`, `rsync`, `dd of=`, `truncate`, `sed -i`, `perl -pi`, `awk`, `python3 -c`, `node -e`, an interpreter heredoc, `curl -o`, `wget -O`, `less -o`, `git config --file`, `patch`, a heredoc script then run, `xargs`, `find -exec`, a glob or brace word, a symbolic link), exec-guard refuses it under `security.shell_startup` through the real hook on the Claude, Codex and Grok payload contracts, and reads pass (`cat`, `grep`, `ls -la ~`, `diff`, `git diff -- .envrc`, `cp ~/.bashrc ./backup`, `source ~/.zshrc`); the forms pass on 3.0.0 and refuse after.
- AC-3 When a write target is unresolved (a variable, a substitution, `~user`, an unknown directory) and the line names a startup file or the target's directory is the home, `/etc` or a startup directory, the call refuses; the same forms in a project directory keep their verdict (unit tests).
- AC-4 When a placing program (`tar`, `unzip`, `rsync`, `cp -r`, `git` and the like) can write files it does not name into the home, `/etc` or a startup directory (an extraction or checkout there, a contents copy, or a tree landing above a class entry), the call refuses, while a named file or a new tree name in the home passes (`cp -r dir ~/`); when `ZDOTDIR`, `HOME`, `BASH_ENV`, `ENV` or `PROMPT_COMMAND` is set on a line that launches a shell which reads startup files, the call refuses; `direnv allow` refuses (unit tests and the real hook).
- AC-5 When `git config --global` or `--system`, or a write into a file that is not a repository's own configuration (named by `--file`, `--blob` or `GIT_CONFIG`, or the repository file a default, `--local` or `--worktree` write opens, judged through its symbolic links), sets a key not known to run nothing (a code-running key such as `alias.*`, `core.pager`, `core.editor`, `core.sshCommand`, `core.fsmonitor`, `credential.helper`, `include.path`, `difftool.<tool>.path` or `gpg.ssh.defaultKeyCommand`, or a key the shared classification does not know), git-guard refuses it under `git.hook_integrity`; known-safe keys such as `user.name`, repository-scope settings, unsets and reads pass (unit tests).
- AC-6 The Claude presets carry the class as `Edit(...)` denies and `sandbox.filesystem.denyWrite` entries and the Codex `cf-guard` profile carries it as read-only entries, generated or checked from the one table (`settings_presets` and `codex_config` tests); `codeflow doctor` reports whether the class is in the presets in force and lists the sourced files outside it.
- AC-7 The TSK-233 corpus and the guard corpora change no verdict except lines that write the class, write into the home or `/etc`, set the startup environment for a shell, set a git key not known to run nothing at user or system scope or in a file that is not a repository's own configuration, or run a program that is not a listed data reader on a line that names a class file and produces text (the false refusals this admits, measured in review: `grep alias ~/.zshrc > b.txt; cp b.txt docs/a.txt`, the same with `cargo test`, `grep alias ~/.zshrc | vim -`, `| awk '/a|b/ {print}'`, `| sed 's|a|b|'` and `| busybox awk '{print $1}'`) (a differential run of both binaries, attached to the PR).
- AC-8 The Codex builder posture is `cf-builder` in the transport table and an ADR-0075 amendment; the docs state the class, the refusal, the sandbox containment per harness and what the backstop cannot stop; `CHANGELOG.md` has one 3.1.0 entry annotated minor; `codeflow validate --docs` passes.
- AC-9 (journey) With the installed hooks, an agent session on the Claude, Codex and Grok contracts that asks to append an alias to `~/.zshrc`, write `~/.bashrc` or write `.envrc` is refused under `security.shell_startup` with the sanctioned path, while reading `~/.zshrc` and writing an ordinary project file pass (`crates/codeflow-cli/tests/refusal_journey/startup.rs`, and the built binary driven with real hook payloads on the PR); the same requests pass on 3.0.0.
