# TSK-1552: The present-browser test times out in Firefox after launch under the software compositor

## Description

Source: the Director's message to coord/records on 2026-11-19 (17:4x), from the candidate 1119j journey-gate probe. Filed by coord/records.

As reported by the Director, not re-run here: the `present-browser` target fails with a Firefox `TimeoutError` after the browser has launched. This happens on `main` at `17510e9bd4` and on landing candidate 1119j alike, so it is not caused by the candidate. The browser prints `GraphicsCriticalError RenderCompositorSWGL failed mapping default framebuffer`, the same line that appears in the failing test logs. Probe: `coordination/coordinators/parallel/notes/candidate-main-1119j-firefox-probe/01-probe.log` (sha256 `0e1c95c89bfb440e51d3a350eac88aa26f81d7ae2b49e5e3c7a66d29ad97b1f3`, checked by coord/records at filing). Playwright build `firefox-1538`.

The likely area is the page or context step under the software GL compositor. That is a lead, not a finding.

Premise: before any change, read the probe log and reproduce the timeout on `main` at `17510e9bd4`, and say where it stops (browser launch, context, page creation or first navigation). Also say whether the same target passes with another Playwright browser or with the compositor setting changed.

Non-goals: changing what the present runtime renders; skipping or weakening the browser test to make a gate green.

## Outcome

After this merges, the `present-browser` target runs to completion in Firefox on the machines that gate CodeFlow, or, if the fault is in the host rather than the code, the target reports that cause plainly instead of a bare timeout.

## Findings

- Diagnosis (2026-11-24): the target stops at the Firefox browser launch, before any context, page or navigation; Playwright never sees `Juggler listening to the pipe`. Playwright's build 1538 and the installed Firefox 154.0 both hang at start on this host when started directly, without Playwright or our code, so our code is not shown to cause the hang. Whether the cause is this Mac or processes started from an agent session is not settled. Detail: the coordinator's diagnosis note for TSK-1552.
- AC-1: not yet run. The target run at this head needs a cold build and `npm ci` for the web `node_modules`, which uses the network; it is left for the gate run.
- AC-2: built as the second ending, a start failure that names the host cause. `crates/codeflow-present/web/scripts/browser-start.mjs` adds `launchOrExplain`, and `browser-check.mjs` starts Firefox and WebKit through it (the appearance loop and the `CF_PRESENT_CHIP_ENGINES` loop). A start that fails or times out throws `present-browser: <engine> <version> (Playwright build <revision>) did not start on macOS <version> (<build>) within <ms> ms. Playwright's launch log: <log>. ...`, with the launch error kept as its cause. Evidence: `scripts/browser-start.test.mjs`, run by `npm run check`, asserts the text with a stub launch that fails, for Firefox and WebKit; its first test fails on the unfixed head and all pass after the change.
- AC-3: the launch is unchanged: no option, preference or variable is added, and the options pass through as given (asserted by the test). A failed start still throws, so the check and the target still exit non-zero. The Chromium checks and the target's command in `.codeflow/test-config.json` are unchanged; nothing is skipped or narrowed.
- AC-4: not yet run, for the same reason as AC-1.
