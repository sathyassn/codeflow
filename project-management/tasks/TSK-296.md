# TSK-296: The managed workflows pin every action by commit

## Description

The managed CI workflows that `codeflow init` and `codeflow update` install
reference `actions/checkout@v6` by tag: `assets/base/ci/codeflow-ci.yml` four
times and `assets/base/ci/codeflow-policy.yml` once. A tag can move, so the
action's code can change under a workflow that holds repository write and
pull request permissions, and an adopter that pins every action by commit has
to re-pin these lines after each `codeflow update` and carry them as a local
change to a managed file (issue 148). This task pins each of those
references to a full 40-character commit with the release tag as a trailing
comment, does the same for this repository's own `codeflow-ci.yml` and
`codeflow-policy.yml` (which also use `actions/setup-node@v6` and
`actions/cache@v6`), and adds a contract test so a tag reference cannot come
back. Each pin is the commit its tag resolves to today, so the action code
that runs does not change, and every pinned commit uses the node24 runtime.
The doctor check that recognises the shipped policy install keeps recognising
a 3.1.0 workflow that still uses the tag. Non-goal: the cargo-dist generated
`.github/workflows/release.yml` is already pinned by commit and is not
rewritten.

The change touches managed files, so the baseline copies and the manifest
digests are regenerated with `codeflow update`, and the release state is
staged as a 3.1.1 patch.

## Deliverables

- the pinned shipped workflows: `assets/base/ci/codeflow-ci.yml`, `assets/base/ci/codeflow-policy.yml`
- the pinned repository workflows: `.github/workflows/codeflow-ci.yml`, `.github/workflows/codeflow-policy.yml`
- the regenerated managed baseline and digests: `.codeflow/.baseline/.github/workflows/`, `.codeflow/manifest.json`
- the tests and checks that name the action lines: `scripts/test_gate_contracts.py`, `scripts/gate-parity.py`, `scripts/test_gate_parity.py`, `scripts/check-scaffold-gitleaks.sh`, `crates/codeflow-cli/tests/ci_pin.rs`, `crates/codeflow-core/tests/scaffold_test.rs`
- the contract test that fails on a workflow action referenced by tag: `scripts/test_gate_contracts.py`
- the release note and the 3.1.1 stamps: `changelog.d/TSK-296.md`, `Cargo.toml`, `Cargo.lock`, `.codeflow/project.toml`

## Acceptance Criteria

- AC-1 When a shipped managed workflow or a workflow in this repository references an action, the reference shall be a 40-character commit SHA, and a shipped reference shall carry its release tag as a comment. Evidence: the new contract test in `scripts/test_gate_contracts.py`, shown failing on the 3.1.0 tree and passing on this one.
- AC-2 Each pinned commit shall be the commit its recorded release tag resolves to, and its `action.yml` shall run on node24. Evidence: `gh api` ref and `action.yml` output for each pin, quoted in the pull request.
- AC-3 When the pinned workflows are installed, the managed baseline and manifest digests shall agree with the shipped assets, and the doctor check shall still recognise the shipped policy install, whether the adopter file uses the earlier tag or the new pin. Evidence: `cargo test -p codeflow-core --test manifest_consistency`, the `ci_pin` and `scaffold_test` suites and the doctor unit tests.
- AC-4 (journey) When a project set up with CodeFlow 3.1.0 runs `codeflow update` with this build, its managed workflows shall carry the pinned references, `codeflow doctor` shall report no managed-file drift, and a second `codeflow update` shall change nothing. Evidence: a scratch project run through the 3.1.0 binary and then the built binary, with the workflow files diffed before and after.
