# TSK-1001: Merge admission and PR checks refuse what the retro review found

## Description

A Codex GPT-6 Astra retro review of three landed units, TSK-449 (push and
CI gates), TSK-451 (PR checks) and TSK-414 (cancelled standalone records
through plan PRs), returned changes_requested on all three. This task fixes
the material defects in the product. Merge admission trusts job names a pull
request controls and ignores the base a run tested. The gate verdict accepts
a skipped release part the event owed. A ready code PR with an unfinished
task and no acceptance block passes. The completed-task correction route
skips the record-ownership check. The removal-reason check accepts ids as
reasons. A derived review still needs a Reviews section. Planning PRs skip
docs validation, and hosted runs validate the target checkout rather than
the candidate. The draft variable shares its name with the release
preflight's body path. The cancellation route has no review binding, skips
full schema validation and checks paths only in the final tree. An
adopter's quick-only targets lost their automatic run when the pre-push
quick gate was removed.

Non-goals: the integration ruleset (which checks are required) and the
`main` copy of `codeflow-policy.yml` are operator and main-checkpoint
matters; the PR body states what they need. Strict base freshness (a rerun
on every advance of the target) stays the ruleset's choice.

## Acceptance Criteria

- AC-1 When merge admission judges a pull request, it shall admit a run only when `.github/workflows/codeflow-ci.yml` and `scripts/ci-reuse.py` at the pull request head hash (SHA-256) the same as at the trusted base, and shall refuse, naming the file, when either differs or cannot be read, so job names from a workflow the pull request controls never admit it. Evidence: `scripts/test_ci_reuse.py` admission tests.
- AC-2 When merge admission judges a pull request, it shall take the head, base, body digest and draft state the policy job judged from one live read, require the live pull request to match them before and after admission, refuse a draft judgment, and admit only a run whose GitHub-signed OIDC provenance, verified with PyJWT and cryptography pinned by hash under an archival time policy (iat inside the run's window), names that run and attempt, a `pull_request` event on this pull request's merge ref and base, and a merge commit of that base and head whose trusted files equal the base's; a run for another base, a companion pull request's run, a retargeted or moved pull request, an edited body, a rerun draft event, or a missing or forged provenance shall refuse. Evidence: `scripts/test_ci_reuse.py` admission and provenance tests and the readiness contract test.
- AC-3 When a pull request's base is changed, codeflow-ci shall run again (`edited`); an edit that leaves the base unchanged shall reuse the newest green run of the same pull request, head and base, and otherwise every gate shall run. Evidence: `scripts/test_ci_reuse.py` edit-reuse tests and the gate contract tests.
- AC-4 When the event owes the release parts (a pull request into main or master, a push to main or master, the schedule or a manual run), the `codeflow gates` verdict shall refuse a `gates-release` result other than success. Evidence: a gate contract test that runs the verdict step.
- AC-5 When a pull request known to be ready (from the event, or `CODEFLOW_PR_IS_DRAFT=false`) changes code for a task that is not complete, `codeflow ci` shall refuse it as not yet landable whatever acceptance text the record holds, and an unfinished task's block shall derive no Reviews row; a draft, and a run that cannot tell (a push, a local lint), shall pass. Evidence: `ci_cli` tests, including a `todo` task with a parseable block.
- AC-6 When a pull request names a completed task, the record-ownership check shall run, and a correctable record shall change only its criteria text; an accompanying epic edit, or a description, dependency or provenance edit, shall refuse. Evidence: `ci_cli` tests.
- AC-7 When a task removes a criterion, its pull request body shall give a line `AC-n removed: <reason>`, optionally led by the task id, which must then be that task, whose reason has at least three words that are not ids or forms of remove; `AC-1 AC-2 AC-3 removed` and `Do not remove AC-1` shall refuse. Evidence: unit tests in `pr_body.rs`.
- AC-8 When a completed task's acceptance block supplies the review row, leaving out the Reviews section shall not block under a policy that lists Reviews as required at block level. Evidence: a `ci_cli` test under that policy.
- AC-9 When `codeflow ci` judges a planning pull request, docs validation shall run once, and it shall validate the candidate head, not a checkout at another commit. Evidence: a `ci_cli` test with a malformed planning record.
- AC-10 The draft state shall be read from `CODEFLOW_PR_IS_DRAFT`, so `CODEFLOW_PR_DRAFT` keeps its one meaning, the path of the PR body file for the release preflight. Evidence: a `ci_cli` test and the docs.
- AC-11 When a pull request known to be ready is a record-only cancellation, its Reviews section shall carry a row approving the exact head commit, or `codeflow ci` shall refuse it; a draft or a push shall pass. Evidence: a `cancelled_standalone` test.
- AC-12 When a cancellation adds a cancelled record that fails the task schema (no title, no standalone reason), `codeflow ci` shall refuse it. Evidence: a `cancelled_standalone` test.
- AC-13 When a planning or cancellation range is judged, every entry a commit of the range changes (a root commit's whole tree, and what a merge commit changes against all its parents) shall be held to the planning path rules, to regular entries only and to the target's managed `AGENTS.md` block, not only the final tree diff. Evidence: tests with add-and-revert product history, an unrelated root commit, a symbolic link and a managed-block change each restored later.
- AC-14 When an adopter's test config has targets that define `quick` but not the mode hosted CI runs, the shipped workflow shall run them with `codeflow test --strict --mode quick --only <targets>`. Evidence: a gate contract test on `assets/base/ci/codeflow-ci.yml`.
- AC-15 (journey) On a scratch repository with the built binary, a ready task pull request with no acceptance block is refused by `codeflow ci` while its draft and its push through the real pre-push hook pass, and a `plan/` branch whose history adds and reverts a product file before its cancelled record is refused by both `codeflow ci` and the pre-push hook. Evidence: `ci_cli acceptance_fix::an_unfinished_task_is_not_landable_once_ready` and `ci_cli cancelled_standalone::{a_ready_cancellation_needs_a_review_of_its_head, product_commits_reverted_later_still_refuse_a_planning_range}`.
- AC-16 When a pull request's release impact is judged, `release impact (trusted)`, in its own workflow `codeflow-release-trusted.yml` on `pull_request_target`, shall refuse a base other than `main`, `master` or `integration/**` before any checkout or build, build and run only the base commit's `codeflow` and `scripts/release.py`, read the candidate as git data, and pin the head, base and body it judges and recheck them before reporting; each release-impact check shall trigger only on events where its job runs, so none is reported skipped; until `main` carries it, the `pull_request` job `release impact` keeps reporting unchanged, and the follow-up TSK-1015 removes that job. Evidence: `scripts/test_gate_contracts.py` release workflow and event-matrix tests, and `scripts/test_release.py` trusted-judge and snapshot tests.
- AC-17 When `codeflow ci` or `codeflow ids check --base --head` judges a range, record and id-registry checks shall turn on when the checkout or the range's base or head commits durable tracking, so a target checkout without tracking still refuses an unregistered first record. Evidence: a `cancelled_standalone` test from both checkouts.
- AC-18 When codeflow-ci gates a pull request, the coverage shards' and Windows partitions' test filters shall be computed by a `judge` job that checks out the base revision, runs no pull request code and runs the selection scripts in isolated mode (`-I -B`), and shall reach the shard and partition jobs only as job outputs, which those jobs refuse when empty; every job that judges results (the coverage floor, the journey map, the partition and shard checks) shall unpack those judge files and their fixtures from the base revision and run them in isolated mode, so a pull request cannot narrow its own selection or floors while its code under test keeps its own copies. The targets and their commands still come from the pull request's test config (see the pull request's NEED YOUR ATTENTION). Evidence: `scripts/test_gate_contracts.py` running the judge job's script on the base checkout under a planted `PYTHONPATH`, `PYTHONSTARTUP` and working-directory module, and running the extracted self-tests and selection from the judge directory against a pull request that narrows them; `scripts/gate-parity.py` pinning the judge job, the filter outputs and the judge-path commands.
