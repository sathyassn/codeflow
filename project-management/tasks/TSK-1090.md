# TSK-1090: Every Windows test partition stays inside its margin on consecutive line runs

## Description

Source: the coordinator's reading of PR 426's dispatch run 41110375672 on
2026-10-30. TSK-1063 ("Every Windows test partition finishes well inside
its job limit") is complete on the line, and the run's head `63b9cb5be`
contains it. On that run's first attempt, "windows tests (3 of 12)" was
cancelled at the 30 minute job limit (job 124254047321, 19:00:33 to
19:30:51Z) after 294 of its 329 tests, with no failure. The other eleven
partitions passed in 9.5 to 16.6 job minutes. The planner on the line
plans every partition at about 9.2 minutes
(`python3 scripts/windows-partitions.py plan`).

The job log's slowest tests were near the end of the partition, each
running past 180 seconds while it overlapped the others:
`installed_cli_journey`
`repeated_update_changes_nothing_and_restores_a_managed_file_changed_out_of_band`
(371.6 s), `release_line_cli` `the_release_rule_table_is_a_one_time_bridge`
(264.0 s), `init_e2e` `a_fresh_standard_project_prints_steps_that_clear_each_finding`
(223.0 s) and seven `remedy_clearing` tests (185 to 230 s). Its 60 SLOW
lines name `remedy_clearing` 25 times and `hooks_cli` 9 times, besides
`codeflow-core` `hooks::exec_guard` and others. TSK-1063's run check
(`windows-partitions.py check`) runs after the partitions and reads
their reports, so it names an overrun only once it has happened; a
cancelled partition writes no report.

The cause is not established: stale timing data, a slow runner, the
overlap of long tests at the end of one partition, or tests that grew
since TSK-1063 measured them. AC-1 measures it.

Sibling: TSK-1071 (Linux coverage shard drift), which shares the
planner's approach but not its files.

Non-goals: raising the job limit alone; the shipped managed workflow
(TSK-384).

## Outcome

After this merges, a maintainer can rely on every Windows test partition of this repository's CI finishing inside its stated margin run after run, and on a partition that is drifting toward its limit being named on a green run before it overruns.

## Deliverables

- the planner and its data: `scripts/windows-partitions.py`, `scripts/windows-test-times.json`
- its tests: `scripts/test_windows_partitions.py`
- the slow tests, where AC-2 makes one faster: their files under `crates/codeflow-cli/tests/` and `crates/codeflow-core/`
- the partition jobs, only if the investigation shows they need it: `.github/workflows/codeflow-ci.yml` (`windows-tests` and the jobs that read their reports)
- investigation findings with the measured times: a `## Findings` section in this record

- AC-1 Before any change, the builder shall record in this record: the per-partition job and test minutes of run 41110375672 (both attempts) and of at least five line or pull request runs since TSK-1063 landed, run ids named; for partition 3 of that run, each test's measured time against the planner's data and how many long tests overlapped at its end; the runner factor against TSK-1063's Findings; and which cause, or mix of causes, the numbers support; evidence: the Findings section, committed before the first code change.
- AC-2 Each Windows test that takes more than a stated number of seconds in the runs AC-1 reads (at least the `remedy_clearing`, `installed_cli_journey`, `release_line_cli`, `init_e2e` and `hooks_cli` tests the Description names, and `codeflow-core` `hooks::exec_guard` tests over the bound) shall be either made faster, with the before and after times recorded, or placed by its measured weight so that no partition's planned time exceeds TSK-1063's margin and no partition holds a larger share of those long tests than the plan states; evidence: `windows-partitions.py plan` output, a unit test of the placement rule with a planted set of long tests, and the measured times.
