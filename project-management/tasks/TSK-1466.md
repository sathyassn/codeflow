# TSK-1466: Both guards read an enforcement path the same way

## Description

CodeFlow's two command guards, `git-guard` and `exec-guard`, and the native edit guard each decide whether a command writes an enforcement file, a file that holds CodeFlow's own checks, such as a shipped workflow, a hook or the policy. Today they do not always reach the same answer for the same path, so a write one guard refuses can be allowed by another. The protected set of shipped workflows also does not name every workflow CodeFlow ships. The coordinators measured both on 2026-11-12 against the installed 4.0.0 binary (source 678d3fa48); the details stay in the workspace until the fix is on `main`. The risk today is low: the most sensitive workflow judges a pull request from the default branch's copy, not the head's. The gap is still a place where the guards disagree, and it widens whenever a new workflow is shipped.

Non-goals: no guard is relaxed; the scaffold manifest stays an integrity record judged by CI's drift checks, with no guard change; code inside a script file the guard does not read stays the documented residual, backed by the operating system sandbox's write denies.

## Outcome

After this merges, an adopter's agent session meets the same verdict from every guard for a write to an enforcement file, and every workflow CodeFlow ships is protected, each with its stated reason.

## Deliverables

- the shared enforcement-path rule and its use in both command guards and the native edit guard: `crates/codeflow-core/src/hooks/` (provisional; the builder confirms the files)
- the protected set with a reason per workflow: `crates/codeflow-core/src/security/actions.json`
- tests: the hook test suites for both guards and the edit guard
- the docs residual sentence: `docs/policy-reference.md`
- the release note: `changelog.d/TSK-1466.md`

## Acceptance Criteria

- AC-1 Every writer reading in either command guard shall judge an enforcement path by one shared rule, tightening only: no path either guard refuses on `main` becomes allowed. Evidence: one test feeds the same paths to both guards and shows the same verdict and rule for each, covering a live enforcement file, each other path form the workspace draft lists, and an unrelated file, failing before and passing after.
- AC-2 The protected set shall name every live workflow CodeFlow ships, and any added later through the scaffold manifest. Each entry shall carry its reason in the source: the events it runs on, which copy of the workflow that run reads (the pull request head or the trusted base), and what an agent edit could change. The builder establishes the copy for each event rather than assuming it. Evidence: a test that fails when the manifest ships a workflow the set does not name.
- AC-3 The native edit guard, `git-guard` and `exec-guard` shall agree on AC-1 and AC-2 for each supported harness (Claude, Codex and Grok), wherever that harness routes native edits. Evidence: one test per harness route.
- AC-4 The refusal message for a copy of an enforcement file shall say that such copies are refreshed only by `codeflow update`, and name that command. Evidence: the message in AC-1's test.
- AC-5 The cost shall be stated in the docs residual sentence, the changelog entry and the pull request's release impact: a script or tool edit to a copy of an enforcement file now refuses, and an agent edit to every shipped workflow now refuses, so those changes go through `codeflow update` or the operator. The pull request counts the existing refusal-test rows whose verdict moves. Evidence: the docs diff, `changelog.d/TSK-1466.md` and the count.
- AC-6 The text-guard invariant shall pass with no move from refuse to allow, and every new row shall fail on `main` and pass at the head. Evidence: the invariant test and the before and after runs.
