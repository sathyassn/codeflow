# TSK-147: every warning names the step that clears it

## Description

A warning that no step can clear is noise that every run repeats, and
agents and people learn to read past it. Three warnings seen on this line
show the pattern (measured at `208f32565`):

- `validate --docs` reports "stale status: approved spec whose consumers
  are all accepted; its derived state is implemented" for SPC-006 and
  SPC-009, and "in_progress with no active branch" for TSK-013. The spec
  case is no fault at all: `implemented` is a derived state (R-32), and an
  approved spec whose consumers are all accepted is its healthy form, so
  that warning is false. The task case names no command or edit that
  clears it.
- The `git.breaking_watch_paths` warning (`hooks/git_hook.rs` in
  `commit_msg_with_files`) says "confirm it is not a breaking change", but
  no confirmation is ever recorded, so every commit and every ci run on the
  pull request repeats it.
- Pre-push runs `codeflow ci` through the same binary and prints the
  child's findings, rendered `BLOCKED` at the finding's own level
  (`Violation::render`, `hooks/mod.rs`), and then reports the push set as
  `git.test_gate_on_push` at the policy's level (`cmd/push_set.rs`). With
  that rule at warn, the output says blocked and the push goes through.

This task audits every warning and note printed by `codeflow ci`,
`validate --docs`, `doctor` and the git and session hooks, and makes each
one actionable: it names an existing command, or an edit to a named file,
that clears it, and states its effective level truthfully.

## Affected surfaces and interfaces

- `crates/codeflow-core/src/hooks/mod.rs` (`Violation::render`,
  `render_invariant`), `hooks/git_hook.rs`, `cmd/push_set.rs`,
  `cmd/git_hook.rs`, `cmd/ci.rs` and `cmd/ci/*`, the validator's stale
  checks, `cmd/doctor.rs`, the exec and git guards.
- The validator's stale checks: no warning for a spec whose derived
  state is `implemented`; no change to the spec status set or R-32.
- `cf-ship` `references/pr-evidence.md` (Release impact) only if its
  `Breaking` and `Rationale` wording must name the watch-path clearing.
- Shared files, per SPC-013 R-118: `codeflow ci` dispatch, pre-push, hook
  rendering and dispatch, doctor, record schema and validator, the release
  docs row (the Rust PR-body check), `cf-ship`.

## Acceptance Criteria

- AC-1 When any of `codeflow ci`, `validate --docs`, `doctor`, the git
  hooks or the session guards emits a warning or note, the message shall
  name the step that clears it: a `codeflow` command, a named `git`
  command, or an edit to a named file; a doctor note about a state doctor
  cannot read shall instead name the manual confirmation step and say
  that doctor cannot verify it; evidence: an inventory test that collects
  every warning-level message constructor and fails on one without a
  remedy naming a command that exists in `codeflow --help`, a subcommand
  that exists in `git help -a`, or a file path, and the inventory table
  in the pull request (message, source, remedy). (Amended 2026-09-28 by a
  planning pull request: git state is cleared by a git command, and some
  harness state is not readable from outside the harness.)
- AC-2 When a finding is printed by a plane whose rule for it is lower
  than the finding's own (a pre-push run of `codeflow ci` with
  `git.test_gate_on_push` at warn), and the finding's rule permits that
  downgrade, the finding shall be printed at the effective level; an
  always-blocking rule and a configured block shall keep their level and
  stop the operation (R-80); the closing line shall say whether the
  operation was stopped; evidence: `hooks_cli` tests pushing a range with
  a downgradable blocking ci finding at warn and at block (no `BLOCKED`
  and "push not stopped" at warn; `BLOCKED` and "push stopped" at block),
  plus two controls at warn, an always-blocking finding (a registry rule)
  and a never-exempt rule the project configured to block, each printed
  `BLOCKED` with the push stopped.
- AC-3 When an approved spec's consumers are all accepted, `validate
  --docs` shall not warn, since that is the healthy derived `implemented`
  state (R-32); when it reports a genuinely inconsistent status (such as
  `in_progress` with no active branch), the warning shall name the command
  or record edit that clears it; evidence: a healthy fixture (the SPC-006
  shape, no warning), and a validator test for the TSK-013 shape with the
  clearing step applied and the warning gone.
- AC-4 When a commit touches `git.breaking_watch_paths` and the pull
  request's Release impact states `Breaking: no` with a `Rationale`,
  `codeflow ci` given that body shall not report the finding; a bodyless
  local run (pre-push, commit-msg) shall keep a note that truthfully
  points at those Release impact fields, and no remote lookup or new
  commit trailer is added; evidence: `ci_cli` tests with and without the
  body, and a `hooks_cli` commit-msg test.
- AC-5 (journey) In a freshly scaffolded standard-tier project driven by
  the installed CLI: a pre-push with a ci finding at warn and a stale task
  shall each print a finding whose named step, run as printed, clears it
  on the next run; a commit on a watched path shall print the local
  pointer note, and `codeflow ci` with a pull request body declaring
  `Breaking: no` and a `Rationale` shall then report no finding; evidence:
  a journey test in `hooks_cli` or `init_e2e` that drives both surfaces.
