# TSK-147: every warning names the step that clears it

## Description

A warning that no step can clear is noise that every run repeats, and
agents and people learn to read past it. Three warnings seen on this line
show the pattern (measured at `208f32565`):

- `validate --docs` reports "stale status: approved spec whose consumers
  are all accepted; its derived state is implemented" for SPC-006 and
  SPC-009, and "in_progress with no active branch" for TSK-013. Neither
  names a command or edit that clears it; the spec case has no `implemented`
  status to move to (the gap TSK-109 found).
- The `git.breaking_watch_paths` warning (`hooks/git_hook.rs` in
  `commit_msg_with_files`) says "confirm it is not a breaking change", but
  no confirmation is ever recorded, so every commit and every ci run on the
  pull request repeats it.
- Pre-push runs `codeflow ci` through the same binary and prints the
  child's findings, rendered `BLOCKED` at the finding's own level
  (`Violation::render`, `hooks/mod.rs`), and then reports the push set as
  `git.test_gate_on_push` at the policy's level (`cmd/push_set.rs`). With
  that rule at warn, the output says blocked and the push goes through.

This task audits every warning and note printed by `codeflow ci`,
`validate --docs`, `doctor` and the git and session hooks, and makes each
one actionable: it names an existing command, or an edit to a named file,
that clears it, and states its effective level truthfully.

## Affected surfaces and interfaces

- `crates/codeflow-core/src/hooks/mod.rs` (`Violation::render`,
  `render_invariant`), `hooks/git_hook.rs`, `cmd/push_set.rs`,
  `cmd/git_hook.rs`, `cmd/ci.rs` and `cmd/ci/*`, the validator's stale
  checks, `cmd/doctor.rs`, the exec and git guards.
- The spec status set and its validator, only where the stale-spec remedy
  needs a status to move to (coordinated with TSK-109 AC-3).
- `cf-ship` `references/pr-evidence.md` (Release impact) only if its
  `Breaking` and `Rationale` wording must name the watch-path clearing.
- Shared files, per SPC-013 R-118: `codeflow ci` dispatch, pre-push, hook
  rendering and dispatch, doctor, record schema and validator, the release
  docs row (the Rust PR-body check), `cf-ship`.

## Acceptance Criteria

- AC-1 When any of `codeflow ci`, `validate --docs`, `doctor`, the git
  hooks or the session guards emits a warning or note, the message shall
  name an existing command, or an edit to a named file, that clears it;
  evidence: an inventory test that collects every warning-level message
  constructor and fails on one without a remedy naming a command that
  exists in `codeflow --help` or a file path, and the inventory table in
  the pull request (message, source, remedy).
- AC-2 When a finding is printed by a plane whose effective level for it
  is lower than the finding's own (a pre-push run of `codeflow ci` with
  `git.test_gate_on_push` at warn), the finding shall be printed at the
  effective level, and the closing line shall say whether the operation
  was stopped; evidence: a `hooks_cli` test pushing a range with a
  blocking ci finding at warn and at block, asserting no `BLOCKED` label
  and "push not stopped" at warn, and `BLOCKED` with "push stopped" at
  block.
- AC-3 When `validate --docs` reports a stale status, the warning shall
  name the command or record edit that clears it (the status transition,
  or the branch to start), and a spec whose consumers are all accepted
  shall have a status it can move to; evidence: validator tests for the
  SPC-006 and TSK-013 shapes, with the clearing step applied in the test
  and the warning gone.
- AC-4 When a commit touches `git.breaking_watch_paths` and the pull
  request's Release impact states `Breaking: no` with a `Rationale`, `codeflow
  ci` with that body shall not repeat the warning; without a body (pre-push,
  commit-msg) it shall be a note that names the Release impact fields as the
  clearing step; no new commit trailer is introduced; evidence: `ci_cli`
  tests with and without the body, and a `hooks_cli` commit-msg test.
- AC-5 (journey) In a freshly scaffolded standard-tier project driven by
  the installed CLI, a commit on a watched path, a pre-push with a ci
  finding at warn and a stale task shall each print a finding whose named
  step, run as printed, clears it on the next run; evidence: a journey test
  in `hooks_cli` or `init_e2e` that runs each printed step.
