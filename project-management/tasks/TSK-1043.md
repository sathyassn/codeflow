# TSK-1043: Each release records the tests and checks behind every managed script

## Description

Issue #372 (CodeFlow 3.1.1, opened 2026-10-28 01:16Z). CodeFlow installs
executable scripts into adopting repositories as managed files. An
adopter with strict checks (a type checker, a linter, coverage) must
decide whether those scripts are in scope, cannot fix a managed file
(the next `codeflow update` overwrites it), and cannot tell from the
repository what CodeFlow checked upstream. The adopter's repository
holds 36 tracked Python files from 9 distinct scripts (each in
`.agents/skills/`, `.claude/skills/` and twice under `.codeflow/.baseline/`);
`cf-evaluate-model/scripts` ships 5 scripts with 3 test files, and
`cf-herdr/scripts/deliver.py`, which types prompts into other agents'
terminals, ships no test. `.codeflow/manifest.json` records `src`,
`ownership`, `sha256` and `exec` per file and nothing about tests or
checks. The adopter excludes byte-identical managed copies from its
strict checks by a path and SHA-256 manifest, as a recorded workaround.

Outcome: **every executable file CodeFlow installs is covered by an
upstream test suite and passes the strict checks CodeFlow applies to its
own code, and each release ships a machine-readable assurance record per
managed executable (hash, covering tests and their result, coverage,
type checker and linter with versions, settings and results, the release
commit and CI run), which `codeflow doctor` checks against the installed
files, so an adopter can exclude a file from its own checks exactly while
it is byte-identical to what CodeFlow vouched for.**

Rules:

- Shipped tests: either every managed script ships its test with a
  documented way to run it, or none ships and the record carries the
  assurance; a partial set is not kept. AC-1 decides which.
- The record is generated by the release pipeline from the run that
  produced it, never hand-written.
- Provenance (a signed record or a build attestation) is in scope only
  if AC-1 finds the release pipeline can produce it without a new
  secret; otherwise it is a tracked follow-up.
- The shell hooks under `.codeflow/git-hooks/` and every other file
  marked `exec` are in scope, not only Python.

Non-goals: CodeFlow's managed-copy footprint (TSK-429); the adopter's
own tooling (TSK-1031, TSK-1006).

### First-pass survey (planning, 2026-10-28, line tip after PR 367)

- Vendored executables: nine Python files under `assets/` (eight in `assets/base/agents/skills/cf-evaluate-model/scripts`, one in `cf-herdr/scripts`), plus the shell hooks under `assets/base/git-hooks/`.
- `.codeflow/test-config.json` runs this repository's `scripts/test_*.py` without coverage and no target over the vendored Python; TSK-427 AC-3 (EPC-024) puts the vendored Python under pyright strict and Ruff in this repository's gate and admits the rest in the TSK-424 baseline.
- The manifest writer: `.codeflow/manifest.json` per installed file (`src`, `ownership`, `sha256`, `exec`); `codeflow doctor` already reads it for managed drift (`check_managed_drift`, `crates/codeflow-core/src/doctor/mod.rs:3239`).
- Release flow: `scripts/release.py` and `docs/releasing.md`.

## Deliverables

- research note: under `docs/research/` (provisional), or in this record when short
- the tests: a test per managed executable that has none (for example `cf-herdr/scripts/deliver.py`), run in this repository's gate, or the documented decision to ship none
- the assurance record: generated by `scripts/release.py` (or the step AC-1 names) and shipped beside `.codeflow/manifest.json`, with its schema in `docs/policy-reference.md` or the manifest reference
- the doctor check: `crates/codeflow-core/src/doctor/`
- tests: generator tests and a doctor test in `crates/codeflow-cli/tests/`
- release note: `changelog.d/TSK-1043.md`

## Acceptance Criteria

- AC-1 Before any change, the builder shall research managed-script assurance broadly: how package managers and distributors record what was verified for shipped files (SLSA provenance, in-toto attestations, Sigstore, `pip` and `npm` provenance), what CodeFlow's release pipeline can produce today, the coverage and check tools per language for Python and shell, the CodeFlow readers in the survey above, and adjacent concerns (adopters who modify a managed file, Windows line endings and hashes, record size); and shall record the findings with sources and the chosen scope, including the shipped-tests decision and whether provenance is in scope, before any change; evidence: the note or record section, committed before the first change in the PR.
- AC-2 Every managed executable shall be covered by an upstream test suite run in this repository's gate, with its coverage measured where its language allows, and shall pass the strict checks TSK-427 applies to CodeFlow's own code; evidence: the gate run naming each file's suite and the coverage report. (serves EPC-024 AC-17)
- AC-3 Each release shall ship an assurance record with, per managed executable, its hash, covering tests and their result, line coverage and branch coverage, each with tool and version or marked unsupported or not measured with the reason, the type checker and linter with versions, settings and results, and the release commit and CI run, generated by the pipeline; evidence: a generator test and the record from a release-candidate run. (serves EPC-024 AC-17)
- AC-4 `codeflow doctor` shall report each installed managed executable whose hash differs from the assurance record, and confirm the rest; evidence: doctor tests with a matching and a modified file.
- AC-5 The docs shall say how an adopter excludes managed files from its own checks only while they are byte-identical to the record, and whether to run the shipped tests; evidence: the text diff and a `cf-editorial-review` pass.
- AC-6 (journey) With the installed build in a scratch adopter, `codeflow doctor` shall confirm the record after `codeflow init` and name a managed script after it is edited; evidence: the journey output.
