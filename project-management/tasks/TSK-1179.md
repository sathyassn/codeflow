# TSK-1179: A reopened task's criterion takes an append-only waiver, with one verdict in codeflow ci and the verb

## Description

Issue 502. After a task's completion has landed and the task is reopened,
`work.criteria_frozen` refuses any edit of its criteria in its own PR, and
`work.acceptance_binding` accepts a waiver only when its commit amends that
criterion. Together they leave a planning amendment as the only route, even
for a one-line ruling. The report gives three attempts, each refused:
rewrite the criterion text, a records-only note that does not amend the
criterion, and a waiver note appended to the criterion's line.

This task opens one route inside the task's own PR, the second of the
issue's two options, tightened: an append-only waiver annotation on the
criterion's line, bound to the waiver commit's content and SHA. The
original criterion text stays byte for byte, which is what the freeze
protects, so the freeze is unchanged for every other edit. Neither a name
nor a branch decides it.

Outcome: **after this merges, a reopened task whose completion landed can
complete in its own pull request with `AC-n: waived | <40-hex sha>`, where
that commit appends a waiver annotation to criterion n, keeps its original
text unchanged, cites the superseding commit by its SHA, and changes only
planning records; any other change to a frozen criterion, and any
unprovable condition, is refused with the cause named and the planning
route.**

Rules (fail closed; authority bound to content and SHAs):

- **Content, not claims.** The waiver commit's diff for criterion n must be
  a pure append: the pre-image of the criterion block is an unchanged
  prefix of the post-image, and the added text matches the annotation form
  `Waived <date>: <reason>. Superseded by <40-hex sha>.` No other line of
  any criterion changes, and no criterion is added or removed.
- **SHA-bound.** The waiver value is a full 40-hex commit id. A branch,
  tag, abbreviated id, PR number, person or role name is refused. The
  commit must be in the head's own range, after the reopen commit and
  strictly before `reviewed` (the existing ordering rules), and must be
  the commit that adds the annotation (not a later or earlier record
  commit).
- **The superseding commit is named by SHA and resolved.** The annotation's
  SHA must resolve to a commit reachable from the head's history; it is
  recorded, and review judges whether it supports the reason. The check
  proves existence and reachability, never meaning.
- **Authority from the trusted side.** The rule runs under the policy
  authority the run pins (`--policy-from`, the pre-push hook's default
  branch tip), never the head's copy: a head that edits the policy cannot
  admit its own waiver.
- **Paths.** The waiver commit changes only the task's own record, judged
  by the planning-only test TSK-1129 gives both waiver routes (no product
  code, policy, harness instruction, hidden file, adopter-facing path,
  symbolic link or submodule).
- **Verb and CI agree.** `codeflow task status <id> complete` and
  `codeflow ci` reach the same verdict and print the same refusal.
- **Scope.** Only a task with a landed completion that was reopened is
  affected. Other tasks' criteria, a task that was never completed, and a
  criterion text rewrite keep today's refusals.

Non-goals: letting a reopened task rewrite criterion text; accepting a
waiver by role or name; changing `work.acceptance_binding` for a task that
was never reopened; the planning-amendment route, which stays.

Security task. It changes policy authority, the rule that decides who may change or waive a frozen criterion, so it carries the cross-lineage Codex security review set out in the Execution contract.

Split on 2026-11-02 after the cross-lineage review of the cut: with the waiver annotation scored as a changed persisted shape (S1 3, as TSK-1173 scores its `claimed:` line) the task graded Very Hard (9), and a Very Hard task is split before claim.
