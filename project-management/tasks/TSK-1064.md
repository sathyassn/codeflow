# TSK-1064: Update reports a malformed hook group in a person's settings instead of crashing

## Description

Source: Codex review 09 of TSK-1029 (PR 385), which found a defect older
than that task. When `codeflow update` merges the shipped Claude
settings into a person's `.claude/settings.json`, it looks for the
person's hook group whose matcher equals each shipped group's matcher
(`crates/codeflow-core/src/scaffold/settings_merge.rs:567`). `matcher_of`
returns `None` both for a group with no `matcher` key and for an entry
that is not an object at all (`:94-96`). The shipped preset has
matcher-less groups for `UserPromptSubmit` and `SessionEnd`
(`assets/base/settings/default.json`), so a malformed entry such as
`"UserPromptSubmit": [null]` is taken as the matching group and reaches
`.as_object_mut().expect("hook group is an object")` (`:571` on the line
tip `3a4522fcb`; `:663` on TSK-1029's branch). `codeflow update` then
panics instead of giving a diagnostic. The panic text is fixed, so no
user content leaks. A second malformed shape fails silently: when a
matching group's `hooks` value is not an array, the merge skips it
(`:574`), so the shipped CodeFlow hook is never added and nothing is
reported (Codex review 01 of PR 393).

The fix: a malformed hook group or hook entry gives the same kind of
diagnostic other settings problems give, naming the event and the entry,
and update never panics on, or silently skips, user-shaped settings
JSON. Found by reading the code; neither case has been reproduced yet
(AC-1).

Non-goals: changing which hooks are shipped or how valid groups merge;
repairing a malformed file automatically.

## Outcome

After this merges, a person whose settings file holds a malformed hook group can run `codeflow update` and get a message naming the event and the entry to fix, instead of a crash or a hook silently left out.

## Deliverables

- the fix: `crates/codeflow-core/src/scaffold/settings_merge.rs`
- tests: unit tests in the same file's `tests` module, and a CLI test in `crates/codeflow-cli/tests/` that runs `codeflow update` on a fixture
- investigation findings: a `## Findings` section in this record
- release note: `changelog.d/TSK-1064.md`

## Acceptance Criteria

- AC-1 Before any change, the builder shall reproduce the panic with `"UserPromptSubmit": [null]` and the silent skip with `"UserPromptSubmit": [{"hooks": "x"}]` through `codeflow update` and record the output, and shall sweep `settings_merge.rs` and the other scaffold code that reads a person's JSON for `expect`, `unwrap`, indexing or other panicking calls on user-shaped values, listing each with its line and whether user input can reach it; evidence: the Findings section, committed before the first code change.
- AC-2 When a hook event's list holds an entry that is not an object (`null`, a string, a number, an array or a boolean), or a group whose `hooks` is not an array, `codeflow update` shall exit with a diagnostic naming the settings file, the event and the entry's position, change no file, and never panic; evidence: unit tests for each shape and a CLI test with the `null` entry, each asserting the diagnostic and the unchanged file. Before the change the non-object entries matched by a shipped matcher-less group panic at `:571`, and a group whose `hooks` is not an array is skipped silently at `:574`, so the shipped hook is never added and nothing is reported; both fail the assertions before the change and pass after. Amended 2026-10-29 after Codex review 01 of PR 393, which found the silent skip. (serves EPC-022 AC-158)
- AC-3 Each panicking call AC-1 finds that user input can reach shall be replaced by a diagnostic or a proven non-panicking path, with a test for each; a call kept because user input cannot reach it shall carry the reason in the Findings; evidence: the Findings and the tests.
- AC-4 Valid settings shall merge exactly as before; evidence: the existing `settings_merge` tests and the scaffold tests unchanged and passing.
