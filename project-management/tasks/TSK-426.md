# TSK-426: Strict typing and linting are the default tooling per language

## Description

Issue #275, items 2, 3 and 4 as revised on 2026-10-22 (strict by
default, explicit opt-out). In two adopting repositories, three
TypeScript projects were never type-checked as a whole (`node --test`
strips types; no gate runs `tsc -b`), Python was 53 % and 5 %
annotated with no type checker or linter, inline workflow shell had no
ShellCheck or actionlint, OpenTofu had no tflint and Rego no Regal. No
managed gate target or template type-checks a project, and the
test-config schema has no notion of a strictness profile.

Outcome: **for each language `cf-stack` detects, it sets up the strict
tooling the issue lists at the strictest settings each tool allows,
with the checks per profile that AC-8's capability matrix marks
applicable,
the managed gate runs those targets in quick and CI modes, suppressions
without a reason and unused suppressions fail the gate, and a project
relaxes a specific setting only through a TSK-424 relaxation entry that
`codeflow ci` reports.**

The per-language set (the issue's list, confirmed at build against each
tool's current release): TypeScript `tsc -b` with `strict`,
`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`,
`noUnusedParameters` and `noPropertyAccessFromIndexSignature`, no
`allowJs` without `checkJs`, typescript-eslint `strictTypeChecked` and
`stylisticTypeChecked` with `projectService`, `no-explicit-any` as an
error and `ban-ts-comment` with descriptions; Python pyright strict or
`mypy --strict`, Ruff with a broad selection including `ANN401` and
`RUF100`, a locked tool environment; Go golangci-lint v2 with a
committed config; shell and workflows ShellCheck `--enable=all`,
actionlint and zizmor; OpenTofu tflint `preset = "all"` with validation
on every variable; Rego `opa check --strict` with schemas and Regal;
JSON and YAML config JSON Schema validation. Existing debt enters the
TSK-424 baseline, which only shrinks.

Non-goals: the instruction and review changes (TSK-1032 in EPC-022,
formerly TSK-427's); typed-model generation from schemas beyond the
recommendation `cf-stack` gives; CodeFlow's own vendored Python
(TSK-427).

Amended 2026-10-27 by the quality asks amendment (the operator's D3
ask), adding two outcomes to the tooling:

- Typed data at every boundary, per profile. AC-8's capability matrix
  records which boundary checks each profile's tools support, and
  `cf-stack` sets up the ones it marks applicable:
  - a typed profile gets a typed-model library that validates on parse
    (for example Pydantic v2 in Python, zod in TypeScript, serde in
    Rust, structs with a validator in Go; a plain dataclass or
    interface alone does not validate) and the strict rules that flag
    untyped boundary data (for example Ruff `ANN401`, typescript-eslint
    `no-unsafe-assignment` and `no-unsafe-member-access`, pyright
    `reportUnknown*`);
  - a schema-only profile gets its schema check (OpenTofu variable
    validation, Rego with `opa check --strict` and schemas, JSON Schema
    for JSON and YAML config);
  - a profile with neither (for example shell) has the boundary check
    recorded as unsupported with its treatment, and the gate reports it
    as not applicable.
  TSK-1032 states the instruction in 4.0.0.
- TypeScript is the default for new projects and new files. `cf-stack`
  sets a new JavaScript project up as TypeScript, and an existing one
  with `tsc` and `checkJs` (JSDoc types) over its JavaScript in place,
  without rewriting it (the operator's decision of 2026-10-27, stated in
  TSK-1032).

First-pass survey (planning, 2026-10-27, line tip `5f2fe3827`):
`assets/base/agents/skills/cf-stack/SKILL.md:29-35` says "Do not mandate
TypeScript, a validator library"; `assets/base/testing/templates/example-node.json`
and `example-python.json` have no type-check target; no template names a
typed-model library.

## Acceptance Criteria

- AC-8 Before any change, the builder shall research strict tooling broadly: each tool's current release and strictest settings for the languages CodeFlow serves, the typed-model libraries and boundary rules per language, routes from JavaScript to TypeScript, TSK-1032's research and instruction, the CodeFlow templates and `cf-stack` text named in this record, and adjacent concerns (install cost, locked tool environments, monorepos, tools a project cannot run); and shall produce a per-profile capability and fixture matrix (for each profile the Description lists: which typing, lint, typed-model and schema-validation checks its tools support, the planted case that proves each, and the treatment of each unsupported check), recording the findings with sources and the chosen scope before any setup or default changes; evidence: the note or record section with the matrix, committed before the first change in the PR. Added 2026-10-27; listed first because it runs first.
- AC-1 On a fixture project per profile the Description lists, `cf-stack` shall write the strict configuration and the gate targets that run it, and the quick gate shall fail on that profile's planted cases from AC-8's matrix (for a typed language: an untyped function, an escape type such as `any`, an unexplained suppression and an unused suppression; for shell, workflows, OpenTofu, Rego, and JSON or YAML config: the lint, type or schema violation the matrix names and an unexplained suppression where the tool has suppressions), with every check the matrix marks unsupported for a profile named in the gate output and the docs; evidence: one fixture run per profile. - AC-3 Existing debt on a project adopting the defaults shall enter the TSK-424 baseline through `codeflow baseline admit` inside the pull request that introduces the strict targets (no separate pull request), by stable occurrence identity with a fix task per occurrence; the gate shall pass while the head's occurrences are all in the admitted baseline at the default-branch authority (amended 2026-10-29 from "the trusted base", by the content policy amendment, since TSK-1077 makes the default branch the only authority), and shall refuse growth, replacement debt, a re-admission and an occurrence with no fix task, whether or not the head edited the baseline; evidence: a fixture with pre-existing debt, the admission in the introducing head, and the refusals including a head-edited baseline. (serves EPC-024 AC-3)
- AC-4 A project that has not opted out and lacks a tool shall be told by `codeflow doctor` which tool and version to install, and the gate shall report the target as not run at the configured level; evidence: the doctor output and a gate test.
- AC-6 For each profile AC-8's matrix marks as having typed boundary data, `cf-stack` shall set up its standard typed-model or validation library and the rules that flag untyped boundary data, and the quick gate shall fail on that profile's fixture that reads structured data into an untyped value (for example `dict[str, Any]` in Python, `any` in TypeScript) and pass once it is parsed into a validating model; for a profile where boundary data is checked by a schema instead (OpenTofu variable validation, Rego with `opa check --strict` and schemas, JSON or YAML config under JSON Schema), the fixture shall fail on a value the schema rejects and pass on a valid one; for a profile with neither, the gate output for its fixture shall name the boundary check as unsupported with the treatment the matrix records; evidence: one fixture run per profile. Added 2026-10-27. (serves EPC-024 AC-3)
