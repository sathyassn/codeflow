# TSK-401: A person's additions to enforcement files survive update and are reported

## Description

Issue: #172, its defect portion. A new adopter needs enforcement additions on day one: policy keys in `.codeflow/policy.json` and `.codeflow/project.toml`, extra deny rules in `.claude/settings.json`, and extra Codex `prefix_rule`s under `.codex/rules/`. `git.hook_integrity` rightly makes these agent-proof, so a person applies them by hand. The workaround problem is what happens next: nothing records which lines are the project's additions, `codeflow update` and `doctor` treat them as unexplained local edits, and nothing proves they survive the next update.

Human approval is intentional and stays. The person-applied overlay with digests and rendering (TSK-321, EPC-023, 4.1.0) is the later general route; it now depends on this task.

Outcome: **a person's additions to the managed enforcement files survive `codeflow update` unchanged, and `doctor` reports them as the project's additions rather than as drift to fix.**

The builder first runs the adopter route on the current build and records what update does to each kind of addition today (kept, merged, conflicted or dropped); the criteria then hold whatever the fix needs to change.

Added by the EPC-022 amendment of 2026-10-18 after the Codex review of PR 249 (`target/review-PR249-codex-01.md`), under the operator's rule that every security gap and every defect that forces an adopter workaround or blocks work belongs in 3.2.0.

- AC-2 `codeflow doctor` shall list those additions as project additions, by file and entry, and shall not report them as drift to repair; evidence: CLI tests.
- AC-3 An agent session shall still be refused a write to each of those files; evidence: the existing guard tests rerun.
- AC-4 (journey) With the installed build, the issue's case (`codeflow init --full` at 3.1.1, the four files patched by a person, then `codeflow update`) shall keep every addition and `doctor` shall name them; evidence: the journey output.
- AC-5 (moved from TSK-1064 AC-1) Before any change, the builder shall reproduce the panic with `"UserPromptSubmit": [null]` and the silent skip with `"UserPromptSubmit": [{"hooks": "x"}]` through `codeflow update` and record the output, and shall sweep `settings_merge.rs` and the other scaffold code that reads a person's JSON for `expect`, `unwrap`, indexing or other panicking calls on user-shaped values, listing each with its line and whether user input can reach it; evidence: the Findings section, committed before the first code change.
- AC-6 (moved from TSK-1064 AC-2) When a hook event's list holds an entry that is not an object (`null`, a string, a number, an array or a boolean), or a group whose `hooks` is not an array, `codeflow update` shall exit with a diagnostic naming the settings file, the event and the entry's position, change no file, and never panic; evidence: unit tests for each shape and a CLI test with the `null` entry, each asserting the diagnostic and the unchanged file. - AC-8 (moved from TSK-1064 AC-4) Valid settings shall merge exactly as before; evidence: the existing `settings_merge` tests and the scaffold tests unchanged and passing.
- AC-9 (moved from TSK-1064 AC-5) (added 2026-11-02, journey amendment: the task had no journey criterion; this one drives its own change with the built binary) When a scratch project whose `.claude/settings.json` holds `"UserPromptSubmit": [null]` is updated with the installed build, `codeflow update` shall exit with a diagnostic that names the setting and shall not panic, and a project with valid settings shall update as before; evidence: the journey output.
