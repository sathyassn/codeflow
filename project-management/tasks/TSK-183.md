# TSK-183: Fetch the Bitbucket destination when its commit variable is unset

## Description

The Bitbucket template from TSK-095 takes its target only from
`BITBUCKET_PR_DESTINATION_COMMIT`. Atlassian's current default-variable
table lists `BITBUCKET_PR_ID` and `BITBUCKET_PR_DESTINATION_BRANCH` but not
that commit variable (checked 2026-09-28 by the builder and by Fable's
review of the TSK-095 round 1 fix, `67c41f322`). When it is unset the step
exits at "no target commit": it fails closed, but the template is then
unusable on Bitbucket. This task adds the fallback GitLab now has: when the
commit variable is empty, fetch the destination branch from `origin` and
judge by that commit, and fail closed when the fetch fails. It also records
in the template that Bitbucket "merges the destination branch into your
working branch before it runs" (Atlassian, pipeline start conditions), so
`codeflow test` and `validate --docs` see the merge while `codeflow ci`
judges `BITBUCKET_COMMIT`, the source commit, against the target.

Non-goal: changing the shared pinned run, which stays byte-identical across
the three templates; the fallback lives in the Bitbucket preamble, as the
GitLab one does.

## Affected surfaces and interfaces

- `assets/base/ci/bitbucket-pipelines.yml` (copy-in template, not managed
  by `codeflow update`), `assets/base/ci/README.md`, `docs/adoption.md`,
  and `crates/codeflow-cli/tests/ci_pin_platforms.rs`.
- No binary, policy key or CLI change.

## Acceptance Criteria

- AC-1 (journey) When a Bitbucket pull-request step runs with
  `BITBUCKET_PR_DESTINATION_COMMIT` unset or empty, the template shall
  fetch `refs/heads/$BITBUCKET_PR_DESTINATION_BRANCH` from `origin` and use
  that commit as the target, so a destination that advanced after the
  source branched judges the change with its own pin and policy; evidence:
  a `ci_pin_platforms` test with the variable unset and the destination
  advanced, red at the TSK-095 landing commit, that runs the shipped
  Bitbucket script on a fixture project with an `origin` remote and
  installs the pinned local release, checksum-verified, whose `codeflow
  ci` is this build.
- AC-2 When the commit variable is unset and the destination branch is
  empty or cannot be fetched, the step shall fail with a message naming the
  branch, install no release and never fall back to the head or a merge
  base; evidence: a test whose destination branch does not exist, with an
  empty call log.
- AC-3 When `BITBUCKET_PR_DESTINATION_COMMIT` is set, full or abbreviated
  to 12 characters, the template shall keep using it as the target;
  evidence: the existing platform tests plus one with a 12-character
  abbreviation.
- AC-4 The Bitbucket template header and the CI README shall say that
  Bitbucket merges the destination branch into the working tree before the
  step, that `codeflow test` and `validate --docs` run on that merge, and
  that `codeflow ci` judges `BITBUCKET_COMMIT` against the target, citing
  Atlassian's pipeline start conditions page; evidence: review of the two
  files.
