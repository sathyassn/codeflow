# TSK-291: CodeFlow's own pushes use a configured non-personal credential

## Description

CodeFlow's own pushes (the registry reservation from `task new`, `epic new`
and `adr new`, `work claim`, `epic new --integration`, `ids sync`) use
whatever git credential is ambient (https://github.com/sathyassn/codeflow/issues/151). A project that requires agent
pushes to come from a bot or GitHub App identity had to inject a credential
helper per command through `GIT_CONFIG_COUNT` and its keys. Since 3.1.0
git-guard refuses that route under `git.hook_integrity` (the issue
comment), and repository or worktree writes of `credential.*.helper` are
refused too, so an agent's reservation goes out under the operator's
personal credential; the adopter has stopped agent CodeFlow pushes. This
task gives a first-class setting that CodeFlow applies to its own pushes
only, reports it in doctor, and can refuse an agent push when no
non-personal credential is configured. A credential helper runs a program
(`credential.helper=!cmd`), so where the setting is read from and who may
change it is a security boundary; the design settles it first. It is first
in the 3.2.0 build order because an adopter is blocked on it.

## Deliverables

- the design note: `docs/research/codeflow-push-credential.md` (provisional; the design decides whether an ADR is needed)
- the setting and its use in every CodeFlow push: `crates/codeflow-core/src/ids/issue.rs` and the other push sites the design lists, the project config reader
- the guard rule that sanctions CodeFlow's own pushes with the configured helper and keeps refusing hand-built environments: `crates/codeflow-core/src/hooks/git_guard.rs`
- doctor: a check under `crates/codeflow-core/src/doctor/`
- docs: `docs/adoption.md`, `docs/policy-reference.md` or the project config reference the design names
- release note: `changelog.d/TSK-291.md`

## Acceptance Criteria

- AC-1 Before any code, a design note reviewed by the other lineage shall
  settle where the helper setting is read from (a source a pull request
  cannot change, such as the trusted target's project file or user scope),
  which CodeFlow commands push, how the helper is applied (`-c
  credential.helper= -c credential.helper=<command>` on CodeFlow's own git
  calls only), what the guard sanctions and still refuses, and whether a
  missing non-personal credential refuses under an opt-in policy; a choice
  that changes authority over credentials goes to the operator with a
  recommendation; evidence: the note and its review row at a commit before
  the first code commit.
- AC-2 When the setting is present, every CodeFlow push shall use only the
  configured helper and never the ambient one; evidence: a test per push
  site with a recording helper and a planted ambient helper that must not
  be called. (serves EPC-022 AC-9)
- AC-3 When a branch changes the setting, the change shall not take effect
  for that branch's own pushes, and a line that sets `GIT_CONFIG_*` by hand
  shall stay refused as at 3.1.0; evidence: a planted-branch test and the
  existing guard refusal test.
- AC-4 `codeflow doctor` shall report the configured helper and which
  CodeFlow commands use it, and warn when none is set while the opt-in
  policy asks for one; evidence: doctor tests.
- AC-5 When an agent session in a fresh project with the installed build
  and a configured helper runs `codeflow task new`, the registry
  reservation shall be pushed through that helper and the guard shall
  allow the command (journey); evidence: a CLI journey with a local bare
  remote and a recording helper.
