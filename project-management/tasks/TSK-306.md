# TSK-306: A line's newer task version wins over a copy main inherited

## Description

Pre-push refuses a task branch on an integration line when `main` holds an
older version of the task record that the line itself held and later
amended (https://github.com/sathyassn/codeflow/issues/176). With `main`
and the line diverged, `judge` in
`crates/codeflow-core/src/workgraph/landing.rs` (from `:442`) finds no
judged point that is newer than every other (`:458-475`), falls to
`agreed` (`:523-559`), and refuses whenever the held criteria signatures
differ. It never asks whether one point's version was inherited and then
replaced on the other point's line. The issue states the search
backwards: `judge` looks for a point that descends from every other point,
not for their common ancestor. The current refusal is intended:
`held_versions_that_differ_still_give_no_answer` (`landing.rs:1354`)
builds this shape and expects unknown authority, so this task changes that
test and settles the inheritance rule. 3.1.1's issue 153 fix (TSK-295)
left this case unresolved; it did not cause it.

The fix adapts the inherited-supersession reasoning the recovered-record
path already has (`recovered` from `:562`, `inherited` at `:633`, and its
merge-resolution handling near `:668`, which tells choosing an old version
apart from inheriting it unchanged) to held records, and keeps refusing
competing introductions, ambiguous identities, unreadable history and
overlays. Copying the helper alone does not supply every safeguard of its
current caller. The issue's suggested rule, dropping a version whose bytes
appear somewhere in the other point's history, is not used: `main` may
revert to v1, reintroduce v1 independently or resolve a merge to v1 after
the line chose v2, and equal bytes do not make those decisions stale
(`triage-codex-02.md`, "The stale-record refusal"). This is a core
acceptance rule, never a project setting.

Recovery first. Merging current `main` into the line makes `main` an
ancestor of the line tip, so a task range based on the new tip has a newest
judged point (`landing.rs:458-475`) and takes the line's criteria without
`agreed`. That recovery is proved through the installed hooks before any
code, and the result is written in this record. If it fails through the
installed gates and no other sanctioned recovery exists, the operator
decides whether this fix moves to 3.1.2 (workspace `RELEASE-PLAN.md`, triage
of 2026-10-13). Merging `main` into the task branch alone, while the judged
line base stays old, is not the same recovery, and dropping
`--policy-from` or `--commits-from` is not a workaround.

### Design note, 2026-10-14

Written before any code, at the EPC-022 line tip 1e6e29e93 (`landing.rs`
line numbers below are at that revision). It settles the held-version
inheritance rule, the cases, the AC-1 recovery procedure and the change to
the existing test. The AC-1 result is appended to this record as a dated
"Recovery proof" note when the procedure is run, before the first code
commit; nothing below reports a run.

**The shape.** `main` planned T at v1; the line forked from that commit
and amended T to v2; `main` moved on without touching T. The pre-push
judges the task branch at two points: the line tip (the range base) and
the `main` tip (`--policy-from`).

```
main:  A(v1) -- N              N = unrelated commit, still holds v1
                \
line:            B(v2) -- ...  the task branch forks here
```

Neither point descends from the other, so `judge` finds no newest point
(`landing.rs:458-475`) and asks `agreed` (`:523-559`), which compares only
the criteria signatures the points hold now and refuses at `:550`.
`held_versions_that_differ_still_give_no_answer` (`:1354`) builds this
exact shape and expects the refusal.

**The inheritance rule for held records (decision).** When no judged point
is newest and the held points' criteria signatures differ, a held point's
version is older when some other held point holds a version with other
criteria and the first point's line inherited its version unchanged from
the other point's line: every commit in the first point's history that
introduced its version is an ancestor of the other point. The points that
are not older must hold one criteria signature; the newest point's record
is the authority. Otherwise no answer, naming the points and their
versions (AC-5). This is the rule `recovered` already applies between
lines of a history (`:590-608`), moved up to the judged points, and it
applies to any number of points, as `recovered` does.

Why one condition is enough: the record's AC-2 names two, that every
introduction of v1 is an ancestor of the v2 point and that the line later
replaced v1 with v2. The second follows from the first: the v2 point
descends from every introduction of v1 and no longer holds v1, so on its
line a later decision replaced v1. Where v2 came from (an amendment commit
or a merge the line resolved to v2) does not matter, because the version
being dropped is `main`'s, and what is being proved is that `main` made no
decision of its own about it.

An introduction is as `inherited` reads it (`:633-704`): a commit holds
the version while no parent does, and a two-parent merge that resolves the
record's path against the automatic remerge of its parents introduces the
version it keeps, however its bytes match (`:670-690`, `read_merge`). A
clean merge inherits.

**What identifies a version in the walk: blob or signature.** Two options
were open.

| Option | Introduction of a version | Effect on `main`'s copy after the fork |
|---|---|---|
| A, by blob | A commit holds the record's blob while no parent does; `inherited` as written | Any edit to T on `main`, criteria or not, is a new introduction, so `main`'s copy competes and the push is refused |
| B, by criteria signature | A commit holds a record with the signature while no parent does | A non-criteria edit on `main` (description, status) is no introduction; a revert or reintroduction of v1's criteria still is |

Recommended: A. It is the tested helper and the only reading `read_merge`
supports without new work (the merge resolution is read per path, and a
signature-level reading would have to decide what a resolution that
changes the record's text but not its criteria means). It is the
conservative side: a record `main` touched after the fork is a decision on
`main` and stays a competing version, with the recovery route open and the
refusal naming both points. B would also have to define an introduction
across renames and status changes, which the criteria freeze does not
read. Known limit of A: a records sweep on `main` that rewrites T's text
without changing its criteria makes the line's push refuse until `main` is
merged into the line; that is the existing refusal with a better message,
not a new one. B can be reconsidered with its own evidence if adopters
hit that limit.

The pre-filter stays as it is: the inheritance test runs only when the
held signatures differ, the condition that refuses today. Held versions
with equal criteria and other status or epic still agree, as `agreed`
returns today.

**Why the issue's byte-match rule is rejected.** The issue proposes
dropping a point's version when an equal version (same blob, or the same
signature) appears in the other point's history at an ancestor of that
point. In the issue's shape that gives the right answer, and it gives the
wrong one in three others, each of which the introduction rule refuses:

| `main` after the fork | Byte rule | Introduction rule |
|---|---|---|
| merges the line (takes v2 clean), then reverts T to v1 | v1's bytes are at A, an ancestor of the line tip: v1 dropped, v2 wins | the revert introduces v1 at a commit the line tip does not descend from: no answer |
| deletes T, then adds v1's bytes again | same: v1 dropped | the re-add is an introduction outside the line's history: no answer |
| merges the line and resolves T to v1 against the remerge | same: v1 dropped | the resolution introduces v1 at the merge (`read_merge` names the path): no answer |

In each, `main` made a newer decision for v1 after the line chose v2, and
equal bytes do not make that decision stale. Dropping it would let the
line's criteria win over a reviewed decision on `main`, which is the
"unreviewed criteria win" risk the triage named (triage-codex-02, "The
stale-record refusal"). The introduction rule asks where a version was
decided, never only whether its bytes occur.

**Safeguards `inherited` does not carry on its own.** In `recovered`, the
walk that finds each line's holder (`first_holder`, `:710-748`) has already
refused a shallow boundary (`:730`), a held doubt (`:736`) and a second
uid (`:740`) before `inherited` reads the same history, and `recovered`
refuses an overlay first (`:579`). `inherited` itself reads
`held_at(...).records` and ignores `doubt`, never checks `self.boundary`,
and does not collect uids (`:642-648`). Called from `agreed` without
those, it would trust an overlaid, cut or ambiguous history. The design
therefore moves the introduction walk into one helper, `introductions`,
that both callers use and that refuses on all four: overlay before any
read, the shallow boundary and a held doubt at each commit, and a second
uid across the walk (`two_uids`). `inherited` becomes "every introduction
is an ancestor of `newer`", and `recovered` keeps its behaviour because
its own guards fire first. Coordination with TSK-287: the ancestry and
parent reads in this walk and in `judge` (`:462`, which reads ancestry
without an overlay check today) go through the guarded reader when
TSK-287 lands first; when this task lands first, the new helper is one
site in TSK-287's sweep, with its overlay and boundary checks already in
place.

**Cases.** Shapes are the `diverged` fixture's (`:1255`): one base
commit on `main`, then `main`'s steps and the line's steps on their own
branches. Each row is one unit test in both point orders.

| Case | `main` after the fork | line after the fork | Expected |
|---|---|---|---|
| positive (AC-2, issue 176) | an unrelated commit | amend T to v2 | Held, v2 |
| concurrent amendments (AC-3) | amend T to v1' | amend T to v2 | no answer, naming both points |
| revert (AC-3) | merge the line, revert T to v1 | amend T to v2, then an unrelated commit (so the points stay unordered) | no answer |
| independent reintroduction (AC-4) | delete T, add v1's bytes again | amend T to v2 | no answer |
| merge resolution (AC-3) | merge the line, resolving T to v1 against the remerge | amend T to v2, then an unrelated commit | no answer |
| shallow history (AC-3) | the positive shape, judged in a clone cut before A | | no answer, "shallow" |
| grafted history (AC-3) | the positive shape with `.git/info/grafts` rewriting a parent | | no answer, overlay |
| replaced history (AC-3) | the positive shape with a replace ref on a commit in the walk | | no answer, overlay |
| duplicate identity in history (AC-3) | add a second record carrying T's id with another uid, then delete it | amend T to v2 | no answer, "another uid" |
| duplicate identity at a point (AC-3) | add a second record of T | amend T to v2 | no answer (the point's own doubt, as today) |

Controls that do not change: points ordered by ancestry keep the newest
point's version (`:476`); held versions with one signature and other
status or epic still agree; a point that no longer holds T is still judged
by `recovered` against the held signature, so a deletion on `main` after
the fork still refuses (a deletion is a decision; the absent case keeps
its test at `:1375`); the issue 153 case (`:1327`) is unchanged.

**The refusal message (AC-5).** The message keeps its first clause, which
three tests assert on ("different versions"), and names each held point
with its version: "the judged points hold different versions of this
task, and none of them is newer than the others: <point> holds <blob>,
<point> holds <blob>", with ids shortened to nine characters as the
module's other messages do. `judge` sees only ids; the `codeflow ci` range
line already says which id is the base and which `--policy-from` names,
so the adopter can tell which point is `main`'s.

**The recovery procedure (AC-1), through the installed hooks.** Run on a
scratch repository with a bare destination, as the TSK-295 journey was,
with the real `codeflow git-hook pre-push` entry. The binary is the line
tip's build (`cargo build -p codeflow-cli` in this worktree, then
`CODEFLOW_HOOK_BINARY` at its `target/debug/codeflow`), because it carries
the 3.1.1 fix the issue was reported against and the hook report prints
its revision; the host's installed binary is 3.1.0 (`codeflow 3.1.0
source=698cc878`), which predates issue 153's fix and would be the wrong
witness. The note records `codeflow --version` in full.

1. `git init --bare` the destination; `git init -b main` the scratch
   repository with the destination as `origin`; `codeflow init` there, so
   the hooks and policy are the installed ones; commit and push `main`.
2. On `main`, plan T (`project-management/tasks/TSK-001.md`) with one
   criterion, v1; commit and push. Create `integration/EPC-001-line` from
   that commit and push it.
3. On a `plan/` branch from the line, amend T's criteria to v2 as a
   planning amendment naming EPC-001; push; merge it into the line with
   `--no-ff` from a worktree on the line, and push the line.
4. On `main`, commit an unrelated file and push. `main` and the line now
   diverge and `main` holds v1.
5. Reproduce first: `task/TSK-001-x` from the line changes a non-criteria
   line of T; `git push -u origin task/TSK-001-x`. Expected:
   `work.criteria_frozen` with the issue's message. Record the exit code
   and the message; this is the fail-before for AC-6's fixture too.
6. Recovery: from the worktree on the line, `git merge --no-ff origin/main`
   with the message `Merge origin/main into integration/EPC-001-line` (this
   repository's own precedent is `4a16a43d6` on the EPC-022 line), then
   `git push origin integration/EPC-001-line`. The pre-push judges the
   line's push from its old remote tip with `main` as the candidate
   authority; a two-parent merge is not a direct commit
   (`line_adoption.rs:194`). Record whether it passed and the output.
7. On the task branch, `git merge origin/integration/EPC-001-line` (the
   task's declared target tip is the base the hook passes,
   `push_set.rs:1324-1337`, so the branch takes the new tip before it is
   judged from it), then `git push`. Expected: pass, with the range line
   naming the new line tip as the base and `main`'s tip as
   `--policy-from`, and no `work.criteria_frozen`. Record exit code, the
   range line and the judged points.
8. Also record the variant the Description rules out: the task branch
   with only `origin/main` merged in, pushed before step 6; expected still
   refused, because the judged base is the old line tip.

The note states each revision (the bare destination's `main`, the line tip
before and after the sync merge, the task head) and summarizes the output.
If step 6 or 7 fails through the installed gates, the 2026-10-14 decision
in the workspace `RELEASE-PLAN.md` (no 3.1.2) means the failure changes
this task's build order and the adopter guidance, not the release; the
operator decides the guidance.

**What changes in `held_versions_that_differ_still_give_no_answer`
(`:1354`).** Its shape is the positive case, so it cannot keep its
expectation. The test is rebuilt in two: a renamed positive test (for
example `a_version_the_line_replaced_does_not_compete`) on the same shape,
run in both point orders like `:1333`, asserting `Authority::Held` with
v2's signature; and `held_versions_that_differ_still_give_no_answer`
itself, kept under its name on the concurrent-amendment shape (`main`
amends T to another criterion, the line to v2), asserting
`Authority::Unknown` whose reason contains "different versions" and both
point ids. Its doc comment says why the first shape no longer refuses.
The `diverged` helper gains a step for a clean `--no-ff` merge of a named
branch and one for a merge that resolves the record to the current
branch's version against the remerge; the shallow, graft and replace
cases reuse `codeflow_fixture::clone(...).depth(n)` (`:1173`) and plant
`.git/info/grafts` or `git replace` on a clone of the positive shape.

**Truth written once.** The parenthetical in SPC-013's criteria-authority
requirement (near line 611, "a line's version is older only when that
line inherited it unchanged ...") is extended to say the same rule decides
between versions the judged points hold, so the spec states one rule for
both paths. The release fragment is a patch entry: a false refusal
removed; competing versions still refused.

## Acceptance Criteria

- AC-1 Before any code commit, the recovery shall be run through the
  installed hooks on a scratch repository with the issue's shape (a line
  that amended T to v2, `main` diverged and holding v1): merge current
  `main` into the line through its sanctioned route, then push a task
  branch that changes a non-criteria line of T. The record shall state
  whether the push passed, with the binary version, the revisions and the
  output summary; evidence: the dated note in this record at a commit
  before the first code commit.
- AC-2 When the judged points are not ordered by ancestry, one holds v1,
  and the other holds v2 on a line whose every introduction of v1 is an
  ancestor of its v2 and which later replaced v1 with v2, the judgement
  shall take v2 as the authority; evidence: a unit test of `judge`, in
  both point orders, and the issue 176 reproduction as a CLI fixture,
  failing before the fix and passing after. (serves EPC-022 AC-16)
- AC-3 The judgement shall still give no answer when both lines amended
  the task concurrently, when `main` reverted to v1 or reintroduced v1
  after the line's v2, when a merge resolved the record to v1 against the
  automatic remerge, when the history is replaced, grafted or shallow, and
  when two records share the task's identity; evidence: one unit test per
  case. (serves EPC-022 AC-16)
- AC-4 No decision shall rest on byte equality alone: a version whose
  bytes equal v1 but whose introduction is not an ancestor of the other
  line's v2 shall stay a competing version; evidence: a unit test with an
  independently reintroduced v1.
- AC-5 When the judgement gives no answer, the refusal shall name which
  judged point holds which version; evidence: a CLI test that reads the
  message.
- AC-6 When the installed pre-push hook pushes the issue's task branch,
  with `--policy-from` and `--commits-from` at the `main` tip as the hook
  passes them, the push shall pass and the output shall name the line's
  version as the authority and the judged candidate (journey); evidence:
  the journey output.
