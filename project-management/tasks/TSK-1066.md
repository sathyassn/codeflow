# TSK-1066: A task pull request into an epic line judges a sync that edits task files as the line push does

## Description

Source: issue #394, reported on 3.1.1, triaged on the line at
`35672e8bd` by running the issue's fixture (with one added `## Outcome`
line, which records now require) through three forms: a pull request
from the sync, a pull request with a later task commit, and the line
push.

The issue's two reported behaviours are already fixed on the line. A
clean sync passes in all three forms, and the line push blocks a sync
merge that hand-edits a task's file. Two residuals remain:

- **A. The pull request form accepts a hand-edited sync.** The check
  that catches it, `receiving_merges::findings`
  (`crates/codeflow-core/src/workgraph/acceptance/receiving_merges.rs:86`,
  called from `acceptance.rs:4006`), returns early when the judged
  branch is not an epic line (the predicate at `receiving_merges.rs:17`), so a pull
  request from a task branch carrying the sync never runs it. In the
  `edited-merge` case both pull request forms exit 0 while the line push
  exits 1.
- **B. The tampered-acceptance case blocks with the wrong cause.** The
  outcome (block) is right, but the messages name CODEOWNERS and "a
  parent other than its first" (`acceptance.rs:1521`), and the
  task-commit form calls the sync "the landing merge" (`:1682`), instead
  of naming the acceptance block edit and the merge.

Severity: A is low (the hand edit shows in the pull request diff, and
the line push still blocks the line itself), but it matters where hosted
CI is the only gate on a task branch that carries a sync. B is low: the
block is right and the text points a person at the wrong file.

TSK-339, TSK-340 and TSK-433 (all complete) fixed the main shapes; this
task builds on their checks. Placement against TSK-421: TSK-421 (open,
EPC-022) owns `codeflow line sync` and its AC-3 already requires a clean
sync to pass in the #176, #181, #217, #218 and #240 shapes. Residuals A
and B are binding and message fixes in the acceptance checks, not part
of a sync command, so this task is the smaller home; TSK-421 is left
unchanged, and this task's clean-case fixture (AC-3) is the regression
TSK-421 may reuse.

## Outcome

After this merges, a maintainer who syncs `main` into an epic line through a task branch gets a block that names the merge and the edited file when the sync hand-edits a task's deliverable or acceptance block, and no block when the sync is clean, in the pull request form as in the line push.

## Acceptance Criteria

- AC-1 Before any change, the builder shall record in this record whether skipping `receiving_merges::findings` for a pull request whose branch is not an epic line (the branch predicate at `receiving_merges.rs:17`) is deliberate, with the commit and record that introduced it, and which receiving line a task-branch pull request into the line should be judged against; if the findings show the skip should stay, the builder stops and returns them to the primary, and only a planning amendment that changes this task's outcome and EPC-022 AC-159 together can remove AC-2; evidence: the Findings section, committed before the first code change.
- AC-2 A pull request from a task branch into an epic line, whose head carries a sync merge that adds a line neither parent has to a `main` task's deliverable, shall block `codeflow ci` with a finding that names the merge and the file; evidence: the issue's `edited-merge` case through both pull request forms, exiting 0 before the change and blocking after.
- AC-3 The same pull requests with a clean sync shall pass, and so shall the line push; evidence: the issue's `clean` case through both pull request forms and the line push, passing before and after (the regression test).
- AC-4 When a sync merge edits a `main` task's acceptance block, the finding shall name the acceptance block edit and the merge, never an unrelated file changed on `main` or "a parent other than its first", and "the landing merge" shall name only the commit on the receiving line's trusted first-parent chain, never the sync; evidence: the `tampered-acceptance` case through all three forms, its messages asserted, each naming the wrong cause before the change.
- AC-5 The `bad-completion` case shall keep blocking in all three forms; evidence: the case through all three forms, before and after.
