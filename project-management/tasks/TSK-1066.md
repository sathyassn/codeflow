# TSK-1066: A task pull request into an epic line judges a sync that edits task files as the line push does

## Description

Source: issue #394, reported on 3.1.1, triaged on the line at
`35672e8bd` by running the issue's fixture (with one added `## Outcome`
line, which records now require) through three forms: a pull request
from the sync, a pull request with a later task commit, and the line
push.

The issue's two reported behaviours are already fixed on the line. A
clean sync passes in all three forms, and the line push blocks a sync
merge that hand-edits a task's file. Two residuals remain:

- **A. The pull request form accepts a hand-edited sync.** The check
  that catches it, `receiving_merges::findings`
  (`crates/codeflow-core/src/workgraph/acceptance/receiving_merges.rs:86`,
  called from `acceptance.rs:4006`), returns early when the judged
  branch is not an epic line (the predicate at `receiving_merges.rs:17`), so a pull
  request from a task branch carrying the sync never runs it. In the
  `edited-merge` case both pull request forms exit 0 while the line push
  exits 1.
- **B. The tampered-acceptance case blocks with the wrong cause.** The
  outcome (block) is right, but the messages name CODEOWNERS and "a
  parent other than its first" (`acceptance.rs:1521`), and the
  task-commit form calls the sync "the landing merge" (`:1682`), instead
  of naming the acceptance block edit and the merge.

Severity: A is low (the hand edit shows in the pull request diff, and
the line push still blocks the line itself), but it matters where hosted
CI is the only gate on a task branch that carries a sync. B is low: the
block is right and the text points a person at the wrong file.

TSK-339, TSK-340 and TSK-433 (all complete) fixed the main shapes; this
task builds on their checks. Placement against TSK-421: TSK-421 (open,
EPC-022) owns `codeflow line sync` and its AC-3 already requires a clean
sync to pass in the #176, #181, #217, #218 and #240 shapes. Residuals A
and B are binding and message fixes in the acceptance checks, not part
of a sync command, so this task is the smaller home; TSK-421 is left
unchanged, and this task's clean-case fixture (AC-3) is the regression
TSK-421 may reuse.

## Outcome

After this merges, a maintainer who syncs `main` into an epic line through a task branch gets a block that names the merge and the edited file when the sync hand-edits a task's deliverable or acceptance block, and no block when the sync is clean, in the pull request form as in the line push.

## Findings (AC-1)

Investigated 2026-11-01 at the line tip `f0b3f04f0`, before any code
change. The issue's fixture (`02-fixture.sh`, with one `## Outcome` line

| Case | pr-sync | pr-task | line push |
|---|---|---|---|
| `clean` | exit 0 | exit 0 | exit 0 |
| `bad-completion` | blocks (`work.import_authority`, `src/tool.txt`) | blocks (same) | blocks (same) |

### Is the skip for task branches deliberate?

No. It is an omission in how the check names the receiving line.

- The check came in with `fd2009012` ("fix(acceptance): require published
  import authority", TSK-339, 2026-10-23). Its intent, from the commit body
  ("Attribute unreviewed merge work to the receiving line") and TSK-339's
  changelog, is that "a receiving-line merge's product changes outside
  verified source history require a reviewed task head".
- TSK-339 AC-1 names "task branches carrying those syncs", and AC-4 says
  "a receiving line's new unreviewed product change is never hidden by
  source attribution". Neither excludes the pull request form.
- The predicate (`receiving_merges.rs:17`) tests the `line` argument,
  which `completions_in_range` passes on from the judged branch
  (`acceptance.rs:4006`, from `pull_request_findings_judged`'s `branch`).
  In the line push that branch is the line. In a pull request from a task
  branch it is `task/...`, so the check returns early. Its only tests
  (`imports.rs:730-779`) run the line form, so the gap was never exercised.

### Which receiving line a task pull request is judged against

The pull request's target (`--into`, or the host's base ref), when that
target is an epic line. The judged branch still wins when it is itself an
epic line, so the line push is unchanged. The change only adds a check
where none ran; a wrong `--into` cannot remove one. A reviewed head of a
completion in the range still hides the merge, as TSK-339 intends: a task
completed at a reviewed commit after its sync has had the sync reviewed.

### The wrong causes (residual B)

- `tampered-acceptance` edits TSK-001's acceptance block inside the sync
  merge, so the head's record is not `main`'s and is judged as a
  completion in the range. `introduced_at` (`acceptance.rs:4228`) stops at
  the sync merge, because neither parent holds the edited block.
- Line push and pr-sync (amendable or own-task line ranges) bind at that
  merge. `stacked` (`acceptance.rs:1519-1522`) stops at its first parent,
  and `later_change_finding` names the first net path change since the
  review: `main`'s CODEOWNERS edit.
- pr-task (a frozen task range) binds at the head. `task_landing`
  (`acceptance.rs:1636-1682`) takes the first first-parent commit whose
  first parent lacks the reviewed commit, the sync, as "the landing merge",
  and refuses the head's own `LINE.md` change before it checks whether
  that merge is on a trusted receiving line (`untrusted_landing`, `:1686`).

Design for B: a completion whose block a merge introduces (neither parent
holds it) is refused at that merge with a message naming the acceptance
block edit and the merge. In `task_landing`, the trusted-landing check
runs before any refusal that calls a merge "the landing merge".
`bad-completion` is judged from `main`'s history (`work.import_authority`)
and is untouched.
