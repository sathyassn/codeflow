# TSK-237: codeflow init no longer hangs on a git pipe deadlock

## Description

`codeflow init` could hang forever (GitHub issue 71). `git_stdin` in `crates/codeflow-core/src/root_checkout.rs` wrote all of a child's stdin before it read stdout. With `git check-ignore -v -n --no-index --stdin -z`, git answers each path it reads, so once the stdout pipe filled, git blocked on its write while codeflow blocked on the rest of stdin. The fix is one shared helper, `codeflow_core::git::output_with_input`, that writes stdin from its own thread while stdout and stderr are drained, closes stdin when the input is written, and joins the writer with its error. The same write-all-then-read pattern is fixed in every production place found by a search for piped stdin: `git_stdin`, `doctor::Options::do_exec_stdin`, `doctor::run_captured` (whose timeout never started while the write was blocked) and `GithubProvider::run_gh` (a request body to `gh api --input`). Call sites that already use a writer thread (`ids/git.rs`, `ci.rs`, `push_set.rs`, `hooks/conflict_markers.rs`, `validate/portal.rs`) and test fixtures are unchanged. Non-goal: no new timeout on the git call; the exchange now cannot block on pipe size.

- AC-4 Every production call site that writes a child's stdin and then reads its output either writes on its own thread or goes through the helper, and the fixed sites are listed in the PR (search of `crates` for piped stdin, recorded in the acceptance block).
- AC-5 The pending 3.1.0 CHANGELOG has a Fixed entry annotated patch, and `codeflow validate --docs` passes.
