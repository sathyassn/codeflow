# TSK-107: adopter fit for automation, brownfield templates and release backends

## Description

Adopters meet failing CI on bot and release-tool pull requests, kept
pull request templates that fail the section check, ignored project record
templates, templates carrying dashes, and a release calculator they never
chose. This task delivers Plan v4 sections 6 (adopters) and 7 for them:
trusted automation profiles with the actor passed to `codeflow ci`; the four
brownfield template mapping states; project record templates read and
validated; dash-free templates; `release.backend` (`none` by default,
`external`, `codeflow`); planning commands below full tier; minimal-tier
release guidance; the commit-msg rule for a blank line after the subject;
the upgrade order; and the adoption guide. Per SPC-013 planning resolution
14, this task writes the ownership map it shares with TSK-089 on the EPC-020
line; TSK-089 on the EPC-018 line consumes it after that line syncs from
`main`. The map gives the commit-msg item to this task.

## Affected surfaces and interfaces

- `codeflow init`, `codeflow update`, `doctor` (CAP-001, CAP-002).
- `codeflow ci`, the scaffolded CI workflow (actor input), commit-msg,
  policy keys `git.automation_profiles` and `release.backend` (CAP-003).
- `assets/base/pm/*.tmpl`, `project-management/templates/`, the adoption
  guide and release guidance.
- Shared files this task edits: the CI workflow, the hooks, the policy
  schema and the templates. Ownership follows SPC-013
  planning resolution 8.

## Acceptance Criteria

- [ ] AC-1 When CI metadata names a trusted actor and the branch pattern
      matches, an automation profile shall skip branch naming, PR sections
      and commit format, count as its own classification, and keep tests,
      secret scan, contract assessment and target-side policy; it never
      changes a policy level; locally and on fork pull requests the actor is
      "unknown" and only the pattern is reported; evidence: a real Dependabot
      and a real Changesets PR body, a spoofed branch, an unknown actor and a
      planted secret.
- [ ] AC-2 When `init` or `update` meets a kept PR template whose headings do
      not match, it shall write a proposed heading mapping and set only the
      PR-section check to warn, visibly, with `doctor` repeating it
      (Diagnosed); Accepted, Refused and Custom shall behave as Plan v4
      section 7 states; no existing explicit value is overwritten; evidence:
      the first PR after install tested in each state, on first install and
      on upgrade.
- [ ] AC-3 `new` shall read templates from `project-management/templates/`,
      validate them before use, fall back to the embedded ones, and work at
      every tier; evidence: template tests, including rendering under
      `block`.
- [ ] AC-4 Every shipped record and PR template shall be free of em and en
      dashes; evidence: a template check.
- [ ] AC-5 `release.backend` shall default to `none` at every tier (only the
      PR's Release impact declaration is checked, warn by default), accept
      `external` and `codeflow`, and keep one version authority per release
      unit; the projects `codeflow` supports are documented; evidence: policy
      tests and the guide.
- [ ] AC-6 Commit-msg shall require a blank line after the subject; planning
      commands shall work below full tier; minimal-tier release guidance and
      the adoption guide sections shall exist; evidence: hook tests and the
      guide.
- [ ] AC-7 The release note shall state the upgrade order (new binary, then
      `codeflow update`), and updated hook shims shall check the binary's
      capability before dispatch; evidence: shim tests with an older binary.
- [ ] AC-8 This task shall write the ownership map shared with TSK-089 on
      the EPC-020 line, naming for every overlapping item the single task
      that owns it, for TSK-089 to consume after the EPC-018 line syncs from
      `main` (SPC-013 planning resolution 14); evidence: the map in this
      record.
- [ ] AC-9 (journey) A fresh init and an update of a brownfield repository
      with the installed CLI shall pass a trusted bot pull request and each
      template mapping state; evidence: the section 10 adopter journeys.
