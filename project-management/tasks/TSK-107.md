# TSK-107: adopter fit for automation, brownfield templates and release backends

## Description

Adopters meet failing CI on bot and release-tool pull requests, kept
pull request templates that fail the section check, ignored project record
templates, templates carrying dashes, and a release calculator they never
chose. This task delivers design v4 sections 6 (adopters) and 7 for them:
trusted automation profiles with the actor passed to `codeflow ci`; the four
brownfield template mapping states; project record templates read and
validated; dash-free templates; `release.backend` (`none` by default,
`external`, `codeflow`); planning commands below full tier; minimal-tier
release guidance; the commit-msg rule for a blank line after the subject;
the upgrade order; and the adoption guide. The ownership of files it shares
with other tasks, and with TSK-089 on the EPC-018 line, is SPC-013 R-118
(planning resolution 14): this task carries the adopter rows on the EPC-020
line, including the commit-msg item, and TSK-089 consumes them after the
EPC-018 line syncs from `main`.

## Affected surfaces and interfaces

- `codeflow init`, `codeflow update`, `doctor` (CAP-001, CAP-002).
- `codeflow ci`, the scaffolded CI workflow (actor input), commit-msg,
  policy keys `git.automation_profiles` and `git.pr_section_mapping`
  (CAP-003); project config `release.backend`.
- `assets/base/pm/*.tmpl`, `project-management/templates/`, the adoption
  guide and release guidance.
- Shared files this task edits: the CI workflow, the hooks, the policy
  schema and the templates. Ownership follows SPC-013 R-118.

## Acceptance Criteria

- [ ] AC-1 When CI metadata names a trusted actor and the branch pattern
      matches, an automation profile shall skip only branch naming and
      commit format, count as its own classification, and keep tests,
      secret scan, contract assessment and target-side policy; PR sections
      stay evaluated at the configured level, and the profile may only name
      sections the bot omits and supply their content; it never changes a
      policy level; locally and on fork pull requests the actor is
      "unknown", only the pattern is reported, and no exemption or supplied
      content applies; evidence: a real Dependabot and a real Changesets PR
      body, one bot body missing a section judged for a trusted, a spoofed
      and an unknown actor, and a planted secret.
      Spec: R-80, R-82.
- [ ] AC-2 When `init` or `update` meets a kept PR template whose headings do
      not match, it shall record the state in `git.pr_section_mapping` and
      write a proposed heading mapping without overwriting any policy byte;
      an interactive run shall ask and record accepted, refused or custom
      before it reports setup complete, and only a non-interactive run
      leaves the diagnosed state; while diagnosed, the PR-section check
      shall run at `warn` only when this run creates the policy file and no
      decision is recorded; a `pr_sections` key present in the prior policy
      file is explicit whatever its value, including one equal to the
      shipped default, and keeps the configured level, as does unreadable
      provenance; `doctor` shall name the effective level, its origin and
      the pending decision, and `codeflow ci` shall print the effective
      level and origin of every check; evidence: the first PR after install
      in each state, on a first install and on an upgrade, including an
      upgrade whose policy sets `pr_sections` to `block` equal to the
      default, asserting the effective level and the preserved policy
      bytes.
      Spec: R-84, R-115, R-104.
- [ ] AC-3 `new` shall read templates from `project-management/templates/`,
      validate them before use, fall back to the embedded ones, and work at
      every tier; evidence: template tests, including rendering under
      `block`.
      Spec: R-37.
- [ ] AC-4 Every shipped record and PR template shall be free of em and en
      dashes; evidence: a template check.
      Spec: R-37.
- [ ] AC-5 Project config `release.backend` shall default to `none` at every
      tier (only the PR's Release impact declaration is checked, warn by
      default), accept `external` and `codeflow`, and keep one version
      authority per release unit; the projects `codeflow` supports are
      documented; evidence: config tests and the guide.
      Spec: R-97.
- [ ] AC-6 Commit-msg shall require a blank line after the subject;
      evidence: hook tests with and without the blank line.
      Spec: none in SPC-013; design v4 section 13 (commit subject without a
      blank line); ownership R-118 (commit-msg row).
- [ ] AC-7 The release note shall state the upgrade order (new binary, then
      `codeflow update`), and updated hook shims shall check the binary's
      capability before dispatch; evidence: shim tests with an older binary.
      Spec: R-85.
- [ ] AC-8 This task's edits of shared files shall stay within the rows
      SPC-013 R-118 assigns it, land after each named owner, and name every
      extension of another owner's file in the Closeout; evidence: the diff
      checked against the R-118 table.
      Spec: R-118; planning resolution 14.
- [ ] AC-9 (journey) A fresh init and an update of a brownfield repository
      with the installed CLI shall pass a trusted bot pull request and each
      template mapping state; evidence: the section 10 adopter journeys.
      Spec: R-104.
- [ ] AC-10 `epic new`, `spec new` and `task new` shall work below full
      tier; evidence: command tests at the minimal and standard tiers.
      Spec: R-37.
- [ ] AC-11 The minimal-tier release guidance and the adoption guide
