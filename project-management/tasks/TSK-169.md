# TSK-169: an approved spec amended before it ships, frozen after

## Description

The operator asked on 2026-09-28 how CodeFlow handles a spec change found
during development. The method answers it: a material discovery stops the
task, the plan goes to Plan vN+1 in a reviewed planning change, and work
resumes (cf-plan step 9, `project-organization.md` "What records carry").
That is how SPC-013 has been changed while `approved`: it carries 16 dated
amendment notes and 22 planning resolutions, with superseded ones kept as
history. What the shipped text says about an approved spec disagrees:

- the spec template (`assets/base/pm/spec.md.tmpl:15-20`) says approval
  "freezes the criteria" and "A changed contract is a new spec";
- `project-organization.md:302-306` says "Later semantic change gets a new
  spec or an explicit superseding record", which reads as any change after
  approval;
- the refusal of an approved spec moved back to `draft`
  (`workgraph/lifecycle.rs:806`) ends "a changed contract is a new spec";
- SPC-013 itself says so in R-32 ("a changed contract is a new spec") and
  R-51 ("Spec criteria freeze at approval and change only by a new spec
  revision").

This task states one rule in those places, in at most three sentences
each: while a spec is approved and not yet `implemented`, a change to it
is Plan vN+1, amended in place in a reviewed planning change, with each
change of meaning marked by a dated note naming its resolution and the
superseded decision kept visibly as history (an editorial change needs no
note); that change names each consumer bound to a
changed requirement and its disposition (unaffected, criteria amended in
the same change, or reopened); once `implemented`, the spec is frozen and
a later change gets a new spec or an explicit superseding record. The same
planning change that files this task amends SPC-013 R-32 and R-51 to say
it (planning resolution 23). Non-goals: no new status, verb or check; the
`approved` to `draft` refusal stays; `superseded` still needs a new spec.

## Acceptance Criteria

- AC-1 `project-organization.md` shall state, in at most three sentences
  in the spec paragraph, that a change to an approved spec that is not
  yet `implemented` is Plan vN+1, amended in place through a reviewed
  planning change that marks each change of meaning with a dated note
  naming its resolution (an editorial change needs none) and keeps the
  superseded decision visible as history; that the change
  names each consumer bound to a changed requirement and its disposition:
  unaffected, criteria amended in the same change, or reopened; and that an
  `implemented` spec is frozen, so a later change gets a new spec or an
  explicit superseding record; the sentence "Later semantic change gets a
  new spec or an explicit superseding record" no longer stands without
  that `implemented` condition; evidence: the diff and the AC-4 pin.
- AC-2 The spec template's lifecycle comment shall state the same rule,
  consumer dispositions included, in at most three sentences, keep the
  `supersedes` / `superseded_by` route for a new spec, and no longer say
  that approval freezes the criteria. Its opening "optional frozen work
  inputs, not living requirements" is qualified to match (for example
  "settled work inputs, frozen once implemented"), and the CF-PM-010
  marker for that file in `cf-evaluate-model/resources/requirements.json`
  and its mirrors follows the new text. The installed
  `project-management/templates/spec.md` and the baseline copy equal the
  asset; evidence: the diff, `record_template` tests
  (`shipped_templates_are_usable`), `model_eval_contract` and the AC-4
  pin.
- AC-3 When an approved or implemented spec is moved to `draft`, by
  `codeflow spec status` or by a hand edit the lifecycle judge reads, the
  refusal shall keep "approved never returns to draft" and name both
  routes: an amendment in a planning change while the spec is not
  implemented, a new spec once it is; evidence: `lifecycle_tests.rs`
  asserting both routes in the message.
- AC-4 A contract test in `orchestration_contract.rs` shall fail when
  `project-organization.md` or the spec template loses the amendment rule
  or its `implemented` boundary, or when either says approval freezes the
  criteria; evidence: the test and a negative control that removes the
  rule from each file in turn.
- AC-5 The `.claude/skills` and `.agents/skills` mirrors and the managed
  baseline match the assets and `.codeflow/manifest.json` records the new
  hashes; evidence: `manifest_consistency`, `artifact_budget_contract`,
  `catalog_craft_contract`, `model_eval_contract`, `orchestration_contract`
  and `codeflow doctor --check managed-drift` clean.
- AC-6 In a freshly scaffolded project the changed `project-organization.md`
  is installed at the standard and full tiers and the changed spec
  template at the full tier, and `codeflow update` brings both to an
  existing project without stale text; evidence: `init_e2e` and an update
  test (serves EPC-020 AC-13).
- AC-7 `CHANGELOG.md` carries one pending Fixed entry, marked
  `codeflow:release-impact patch`, that names the rule and says
  `codeflow update` brings it; `codeflow validate --docs` and `codeflow ci`
  over the task range are clean with no warning (serves EPC-020 AC-8).
