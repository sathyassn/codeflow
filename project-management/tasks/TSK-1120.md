# TSK-1120: cf-present documents open in a dashboard shell with a side menu, tabs and drill-down views

## Description

The operator's feedback of 2026-10-31 on the hand-built 4.0.0 status page:
a report page needs proper structure for how it reports different aspects,
changed by choosing a tab or the like; a proper side menu, like a proper
dashboard, with drill-downs; even tasks need proper context sometimes; and
this belongs in `cf-present`, not only for reports, neither rigid nor
random, so that each page is not a fresh design with no consistency. Today a
present document is one linear block list: the chrome lists the top-level
sections in a fixed rail (`crates/codeflow-present/web/src/chrome.tsx:1718`,
`cf-section-route`), a `tabs` block switches peer panels inside one place
(`crates/codeflow-present/src/document.rs:151`; `document-authoring.md`
"Progressive depth"), a `disclosure` nests detail, and nothing lets a
reader move from a release to an epic to a theme to a task and back, or
see a task with its own context. The 4.0.0 status page built that shell
by hand in an `html` page outside the runtime (its source
`codeflow-400-status.html`: a sections nav and eleven titled sections),
which is the inconsistency the operator named.

Outcome: **a `schema_version: 2` document may declare `views`: a tree of
titled views the runtime draws in a dashboard shell with a side menu (the
view tree, the current view marked, collapsing to a drawer at phone
width), a header carrying the document's anchor, a view body of catalog
blocks, an optional context strip per view (short labelled facts such as
an item's outcome, location, owner, state and window), tabs for peer
aspects inside a view, and drill-down links that open a child view with a
breadcrumb back; a stable layout contract names these regions and the
component set that fills them, with a registry of view kinds that has room
for a new kind; a linear document without `views` renders exactly as today.**

```text
  +------------------+---------------------------------------------------+
  | side menu        | header: title, anchor line, revision r3           |
  |                  +---------------------------------------------------+
  | > Overview       | breadcrumb: Release > Epic 22 > Theme: status     |
  |   Epics          | context strip: outcome | on line | lane 2 | window |
  |     Epic 22  *   +---------------------------------------------------+
  |       Themes     | tabs: [ Progress ] [ Order ] [ Issues ]           |
  |         status   |                                                   |
  |           TSK-x  |   view body: catalog blocks, figures, encoded     |
  |   Lanes          |   tables, decisions, code                         |
  |   Decisions      |   drill-down link -> child view (TSK-x)           |
  |   Script         |                                                   |
  +------------------+---------------------------------------------------+
```

Figure: the shell's regions; the side menu is the view tree, the
breadcrumb is the path down it, the context strip is the current view's
facts, and tabs switch aspects inside the view.

Decisions, each reversible and disclosed here:

- **The shell is declared, not drawn by the author.** The document gains
  an optional `views` array beside `blocks`; a view has `id`, `title`,
  `kind`, optional `context` (one to eight labelled facts, each `label`,
  `text` and an optional `state` or location mark from the grammar
  vocabulary), `blocks` (the existing catalog; `tabs` and `disclosure`
  included) and `children` (nested views). The root `blocks` of a document
  with `views` are the header's anchor (the first narrative and the
  orienting figure, as the bar of TSK-1097 requires) and render above
  every view. A `reference` of kind `view` (`document.rs:514`, the
  existing frame-reference shape) in any block opens that view; the
  runtime draws the breadcrumb from the tree, never from the author.
  The side menu lists the tree to the depth the document declares, with
  the current view marked and the view's `summary` mark or count when it
  carries one (TSK-1096 AC-9's summary vocabulary); at phone width it is
  a drawer behind one button. The sections rail of today lists the
  current view's sections inside the body.
- **Outcomes first is the contract's primary structure.** The operator's
  direction of 2026-10-31 (13:15): a report is organised by outcomes
  first, and every outcome opens to its detail. The contract therefore
  fixes the root view as an `overview` whose body lists the document's
  outcomes (each with its state, percent and next step where the kind has
  them), each outcome a `view` reference into its own `topic` view, and
  the tree under a topic going to `item` views and their `evidence`; the
  side menu's first group is those outcomes, and other kinds (`list`,
  `timeline`, `issues`, `decisions`, `evidence`, `commands`) are
  cross-cutting entries after it. This is the shape every registry
  document has, not an option an author picks.
- **View kinds are a registry, with room.** `kind` is one of `overview`
  (the first view, the outcomes and the decision picture), `topic` (a
  group of items with a percent, what it is, done and not done, and its
  reasoning), `item` (one thing with its context strip), `list` (an encoded table of items), `timeline` (a
  schedule figure and its windows), `issues` (blocked and owed items),
  `decisions` (operator inputs as `decision` and `form` blocks),
  `evidence` (coverage and refs), `commands` (one runnable script) or
  `custom` with a one-line `reason`. The registry fixes what a reader
  finds in each kind (the layout contract below) and `present check`
  warns on a `custom` view, naming the registry, so a new kind that
  recurs is added to the registry with a specimen once, and never
  improvised. Adding a kind is a change to this registry and its
  specimen, not to the shell.
- **The layout contract.** One reference section in
  `document-authoring.md` names the regions (side menu, header, breadcrumb,
  context strip, tabs, body, drawer), the order a view's body follows (lead
  line, the answering figure or encoded table, short acting text, then
  disclosures), the component set that fills a body (the catalog blocks,
  the figure families, the encoded table, the `schedule` family, the
  `decision` and `form` blocks, labelled `code`), and what each registry
  kind must carry; the specimen page renders every kind once. A document
  that follows the contract looks like every other document that does, and
  the contract leaves content free; it is the consistency the operator
  asked for and the `custom` kind is the flexibility.
- **Drill-down is navigation, not duplication.** A child view is declared
  once and reached from any `reference`; the same task view serves the
  release, the epic and the theme that link to it. The breadcrumb is the
  declared path to the current view; a reference from elsewhere keeps the
  tree's path, so a reader always knows where a view lives.
- **Export and comments.** The export renders the shell with the side menu
  as a static outline, every view present in tree order with its
  breadcrumb as a heading path, and the first view shown when scripts are
  off, so a capture holds everything. Comment anchors bind to blocks
  inside views as they bind today; a view id is part of the anchor's
  context so a moved block in another view is not re-anchored by mistake.
- **Capacity holds the largest report it must carry (Codex round 8,
  F1).** A status document for a scope of 300 tasks declares one `item`
  view per task (TSK-1098 AC-10), so a document-wide cap of a few dozen
  views or 512 blocks (`limits.rs:5`, `MAX_BLOCKS`; `:11`,
  `MAX_FIGURE_BLOCKS` 24) cannot hold it. The budgets are therefore
  scoped: the existing block, nesting and figure budgets of `limits.rs`
  apply per view (each view is one block tree of at most 512 blocks and
  24 figures, as a linear document is today), and the document gains a
  view budget of 1024 views, a view depth of four and a total of 16384
  blocks and the existing 8 MiB document size, each refused by name;
  the runtime renders the current view into the page and keeps the other
  views as parsed data, so a large document stays responsive, and the
  export writes every view. Every task stays reachable through the
  outcomes path; the generator never drops a drill-down to fit, and a
  document over the budget is refused, never truncated. A `custom`
  view, `title`, `label`, `text` and `reason` are text through the
  existing sanitiser; `html` stages inside a view keep their frame and
  sandbox (ADR-0049).
- **Check ownership (Codex round 8, F4).** This task owns the
  `present check` warning for an `html` stage in a view whose registry
  kind names a catalog carrier for its content (a `timeline` view with a
  stage instead of the `schedule` family, a `list` view with a stage
  instead of an encoded table); TSK-1121 owns the missing-`topic`
  warning; TSK-1097 carries the guidance for both and neither check.

Non-goals: the status report's own views (TSK-1098); topic identity and
per-view change marks across revisions (TSK-1121); new block kinds
(TSK-1113, PR 449) and the figure frame chrome (TSK-1111, PR 449); the
portal (TSK-1114, PR 449), whose pages keep their committed source and
route identity under the portal content contract and share only the
composition guidance; a page builder or a stored layout.

## Outcome

After this merges, an author of any present document can declare a tree of
views and the runtime draws it as a dashboard with a side menu, tabs, a
context strip and drill-down with a breadcrumb, under one layout contract
and view-kind registry, with a linear document rendering as before.
