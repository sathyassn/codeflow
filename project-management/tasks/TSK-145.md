# TSK-145: release lines judged where each change was introduced

## Description

The release catch-up merge that brings the EPC-020 line into the release
branch (the local `integration/release-3-0-0-rehearsal` at `cbc0b2ec8`)
was refused at pre-push with 15 `work.acceptance_binding` and 20
`work.criteria_frozen` findings, and `codeflow ci --base origin/main` on
it gives 18 `work.acceptance_binding` blocks (scratchpad
`models-stream/rehearsal/push-M3.txt`, `ci-M3-vsmain.txt`,
`ci-M3-vsL.txt`). In `cmd/ci/acceptance.rs` `criteria()`, a branch that
combines several lines is neither planning-only nor an epic line, so its
criteria are frozen and every completion is bound at the head, although
each change was already judged on the line it came from. This task judges
a release line, including its pull request into `main`, by SPC-013 R-120.
It is on the release's critical path.

R-120 in short. Recognition is by structure and provenance, never by the
branch name or a declaration (planning resolution 20 records why). A merge
qualifies when each non-first parent is reachable from the authority's
ref of a verified epic line or from the default target; otherwise the
whole merge is direct work, which covers octopus merges and lines rebased
after the merge. Within a qualifying merge, a path is brought only when
its blob equals the expected import (the clean three-way result, or the
second parent's blob for a conflicted path); any other path is a
resolution judged against that import, never against the first parent,
so a resolution that restores an older record is caught with no
first-parent diff. Brought completions bind where they
were introduced; brought criteria changes are judged again at the merge
that landed them on their line. Direct changes: a direct commit touching
only planning records is judged as planning-only, a merge resolution
never is; anything else is integration work for the one
release-integration task, completed inside the release pull request at
the head both primary seats reviewed; another task's direct completion is
judged as a task pull request.

Release-integration task: TSK-010 ("integrate and release the CodeFlow
system") owns release integration; TSK-109 AC-3 keeps TSK-010's release
ownership when it reconciles TSK-010, TSK-013 and EPC-005. TSK-010 today
targets `integration/EPC-005-presentation-system`, so it can carry the
release pull request only after that reconciliation retargets it; this
task does not retarget it.

Trust boundary: a structural check can re-judge the merge that landed a
criteria change on its line by that merge's paths, so a loosening that
arrived with code is refused. It cannot see whether a planning-only
landing merge passed the line's pull request check; that stays with the
host's review and required checks on the line, which are not armed on
CodeFlow's own host.

The 3.0.0 rehearsal as built does not satisfy R-120. On `cbc0b2ec8`'s
first-parent path it carries direct code commits (`b1f52a820`,
`c455717bf`, `23979d7d8`, `580344e2b`, `f0f7e1a12` among them), TSK-049's
direct completion `1dc0033a2` followed by code, and the merge `b1923ac60`
of `integration/release-3-0-0-list`, which is no verified line.

## Acceptance Criteria

- AC-1 When a qualifying merge brings a completion and a planning
  amendment from a verified line, the completion shall be bound at the
  commit that introduced its block on that line under R-60 and the
  amendment shall be accepted; and when a criteria loosening reaches the
  release line from a commit reachable from a line's ref but landed on
  that line by a merge whose range is not planning-only, CI and pre-push
  shall refuse it as `work.criteria_frozen` on the committed range;
  evidence: `ci_cli` fixtures with two epic lines merged into a release
  branch, and the negative twin.
- AC-2 When a completion is made directly on the release line (a
  first-parent commit, a clean merge's evil change, a conflicted merge's
  resolution, or a resolution that keeps or restores an older verified
  record where the import would change it) and its reviewed commit is not
  the head or an ancestor whose later diff touches only that record's
  status and Closeout, CI and pre-push shall refuse the committed range
  as `work.acceptance_binding`; evidence: one fixture per shape, each
  refused, including the restoration fixture of plan review round 2
  (Codex R2-1, `followups-r2-restoration.py`: the line reopens, strengthens
  a criterion, fixes code and completes with a new block; the release
  merge restores the old record with no first-parent diff).
- AC-3 When a criterion is changed directly on the release line (a
  first-parent commit, a clean merge's evil change, a conflicted merge's
  resolution, or a resolution that keeps or restores a weaker criterion
  where the import would strengthen it), CI and pre-push shall refuse the
  committed range as `work.criteria_frozen`; evidence: one fixture per
  shape, each refused, including the same Codex R2-1 restoration fixture,
  which must yield both this refusal and the AC-2 binding refusal.
- AC-4 When a merge has a parent that does not qualify (a branch that
  fails the epic-line check, an unpushed branch, a forged merge message
  naming a real line, or a line rebased after the merge), all its changes
  shall be judged as direct, and no parent shall inherit another's
  qualification; evidence: one fixture per case, judged as AC-2, AC-3 and
  AC-7, plus a clean-octopus negative (Codex R2-2, `followups-r2-probes`
  `octopus_untrusted_third`: a clean three-parent merge whose verified
  second parent comes with an unverified third carrying a completion and
  an unreviewed code change), distinct from the dirty-resolution
  fixtures of AC-2 and AC-3.
- AC-5 Pre-push and CI shall reach one shared judge with equivalent
  inputs and return the same findings for every committed range of AC-1
  to AC-4 and AC-7; and `task status complete`, given one prospective
  completion (the record before completion, the block, and the head it
  would be committed on), shall return the same acceptance finding as CI
  on that completion committed, with no new range-audit interface; its
  refusal of a task already complete shall be a status refusal, reported
  apart from any acceptance finding; evidence: each committed fixture run
  through pre-push and CI, the direct-completion fixtures of AC-2 run as
  prospective completions through `task status` and CI, and a control
  that an already-complete task gets the status refusal (Codex R2-3,
  `followups-r2-probes/status_frontdoor.log`).
- AC-6 (journey) When the EPC-020 line and one other line are merged
  into a release branch in a freshly scaffolded full-tier project driven
  by the installed CLI, the push shall pass pre-push and `codeflow ci
  --base` the default target shall be clean. A rebuilt 3.0.0 candidate
  that follows R-120 (direct code changes covered by the
  release-integration completion at its head, TSK-049's completion moved
  after the last code change or to its line, and the helper branch's
  commits carried as direct work) shall push and report no finding
  against `origin/main`; and the raw `cbc0b2ec8` replay shall report the
  expected findings: integration work without a release-integration
  completion for the direct code commits, `work.acceptance_binding` for
  `1dc0033a2`, and the merge `b1923ac60` judged as direct work; evidence:
  an `acceptance_journey` case and both replay logs beside the three
  refusal logs above.
- AC-7 When a direct commit on the release line touches only planning
  records, it shall be judged as a planning-only change; when a direct
  change touches anything else, CI shall require the release-integration
  task's completion inside the range, bound to the head under the first
  rule of R-60, and refuse the range without it; evidence: fixtures for a
  records-only commit, a code commit with that completion at the head, a
  code commit without it, and a code commit after it.
