# TSK-1060: Codex seats can be qualified under managed requirements

## Description

This is a planning draft accepted from the TSK-397 design note, revision 4.1, Part C (pull request 331), where it is unit U7 (Codex managed requirements). The note called the unit 3.3.0; the release is 4.1.0. Part C is accepted as planning drafts only: the criteria below are drafts, and this unit takes its own whole-unit review when it is built. Part C decisions (i) to (v) apply: (i) explicit non-secret enforcement-file arguments are allowed on a qualified host under attested `W-enforcement`, and the secret-read classes override, never a file name; (ii) a patch update invalidates a record, because exact executable digests bind it and a changed binary is `Unknown` until the operator re-runs the ceremony; (iii) managed settings are a design requirement for qualification, not a vendor fact; (iv) no exclusion matcher ever, so a non-empty `excludedCommands` disqualifies and route A+ is dropped; (v) the ceremony runs through the Bash tool, never the `!` prompt, and its evidence is receipts, not operator attention.

Codex seats can be qualified only when an administrator-owned requirements file fixes the profiles and modes a seat may use and the effective context of a launched seat can be shown. This unit investigates first, on named Codex versions and platforms, what the supported requirements schema, the permission profiles and the documented fallback actually do; it then defines the file and the tests that the investigation supports. A safe launch refusal is an accepted outcome. A route that cannot be shown to have trustworthy receipts and secret containment stays unqualified, or is removed from the task, and the record says which.

Edges: a root. TSK-1054 (U1) depends on this unit, because the design note requires the requirements file to have landed before any Codex record is attested.

## Outcome

after this merges, an administrator can see, per Codex version and platform, whether Codex seats can be qualified, and can install one managed requirements file that keeps every qualified seat on a sandboxed profile.

## Acceptance Criteria

- AC-1 Before any file is written, the investigation shall be recorded on named Codex CLI versions and named platforms (macOS, Linux, Windows in each mode): the supported requirements schema, how permission profiles differ from legacy sandbox modes, the effective profile of a launched seat read from the running seat, what the hook's execution context sees, and what the documented fallback does for each forbidden launch; evidence: the investigation record with the commands and observed outputs.
- AC-2 The managed requirements file (`/etc/codex/requirements.toml`, `%ProgramData%\OpenAI\Codex\requirements.toml` on Windows) shall define `cf-guard` and `cf-builder` and pin `allowed_permission_profiles` to them, `allowed_sandbox_modes` without `danger-full-access`, and `allowed_approval_policies` including `never`, using only the keys the investigation shows are supported; evidence: the file and a parse test on each tested version.
- AC-3 A `--sandbox danger-full-access` launch and a bypass-flag launch shall each end in a safe outcome: a launch refusal, or a sandboxed profile whose effective settings are shown; a launch that reaches an unsandboxed context fails the task; evidence: a launch test per flag, per version and platform, that names the outcome it observed.
- AC-4 A route shall be qualified only on a demonstrated effective context: the seat's effective profile, read from the running seat and not from the file, shall close nested secrets and `.envrc`, and the hook's receipts shall be trustworthy (written where the seat cannot write or alter them); where either cannot be shown on a version or platform, that route shall stay unqualified or be removed from this task with the reason recorded; evidence: a read-denial test from inside a seat and a receipt-integrity test, per qualified route.
- AC-5 A profile that keeps an approved name with weaker settings (a redefined `cf-guard` or `cf-builder`, a widened writable root, a restored approval bypass) shall not qualify, and a seat whose effective profile differs from the file shall read as `Unknown`; evidence: a negative test for each of these.
- AC-6 The file shall be readable by the hook; evidence: a hook test on a host with the file installed.
- AC-7 Codex on Windows shall be qualified per mode, and `unelevated` never; evidence: a native Windows run per mode.
