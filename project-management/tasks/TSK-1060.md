# TSK-1060: Codex seats can be qualified under managed requirements

## Description

This is a planning draft accepted from the TSK-397 design note, revision 4.1, Part C (pull request 331), where it is unit U7 (Codex managed requirements). The note called the unit 3.3.0; the release is 4.1.0. Part C is accepted as planning drafts only: the criteria below are drafts, and this unit takes its own whole-unit review when it is built. Part C decisions (i) to (v) apply: (i) explicit non-secret enforcement-file arguments are allowed on a qualified host under attested `W-enforcement`, and the secret-read classes override, never a file name; (ii) a patch update invalidates a record, because exact executable digests bind it and a changed binary is `Unknown` until the operator re-runs the ceremony; (iii) managed settings are a design requirement for qualification, not a vendor fact; (iv) no exclusion matcher ever, so a non-empty `excludedCommands` disqualifies and route A+ is dropped; (v) the ceremony runs through the Bash tool, never the `!` prompt, and its evidence is receipts, not operator attention.

Codex seats can be qualified only when an administrator-owned requirements file fixes the profiles and modes a seat may use. This unit defines that file, tests what a seat gets when it is launched against it, and closes nested secrets in the profile.

Edges: none structural. Criterion AC-2 (the fallback-target test) is a prerequisite for any Codex qualification under TSK-1054 (U1), which states that in its AC-5.

## Outcome

after this merges, an administrator can install one managed requirements file that keeps every Codex seat on a sandboxed profile, so that Codex seats can be qualified.

## Acceptance Criteria

- AC-1 `/etc/codex/requirements.toml` (`%ProgramData%\OpenAI\Codex\requirements.toml` on Windows) shall define `cf-guard` and `cf-builder` and pin `allowed_permission_profiles` to them, `allowed_sandbox_modes` without `danger-full-access`, and `allowed_approval_policies` including `never`; evidence: the file and a parse test.
- AC-2 A `--sandbox danger-full-access` launch and a bypass-flag launch shall land on a sandboxed profile; the documented fallback has an undocumented target, so the test shall name the target it observes; evidence: a launch test per flag on the pinned Codex version.
- AC-3 The profile shall close nested secrets and `.envrc`; evidence: a read test from inside a seat.
- AC-4 The file shall be readable by the hook; evidence: a hook test on a host with the file installed.
- AC-5 Codex on Windows shall be qualified per mode, and `unelevated` never; evidence: a native Windows run per mode.
