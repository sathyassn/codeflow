# TSK-414: A cancelled standalone task record lands through a planning pull request

## Description

Issue #257. A standalone task's record was committed only on its own
task branch, which also held a commit the project did not want on
`main`. The task was cancelled before anything landed, and the project
wanted only the cancelled record on `main` so the decision stays in the
record history. A fresh `plan/` branch with one commit adding the record
at `status: cancelled` was refused both ways by `codeflow ci` 3.1.1:
with `Task: TSK-366`, `work.stable_planning_anchor` asked to land the
record on the task branch and run `work start`, which would make a second
claim for a task being cancelled; without a `Task:` line,
`work.classification` asked for one, and `Task: EPC-NNN` does not apply
to a task with no epic. The cancel commit stays on a local branch and the
decision is recorded elsewhere.

Outcome: **a planning pull request can land a standalone task record
whose status is `cancelled` and that is not present at the merge-base,
with no start claim, and the docs name that route.**

Decisions recorded here:

- The class is the existing planning amendment on a `plan/` branch: a
  record-only range that adds a standalone task record already at
  `cancelled` (its Closeout carrying `- cancelled:` and `- scope:`), with
  `Task: TSK-NNN` naming that task. `codeflow ci` accepts it without a
  start claim, because a cancelled task never starts, and prints the
  note it prints for a planning amendment with no epic.
- The record must be a valid cancellation: a status other than
  `cancelled`, a missing reason or scope, or any path outside
  `project-management/` in the range keeps today's refusal.
- A task record that is present at the merge-base at another status is
  not this route; it changes status in its own task PR or through
  `codeflow task status` as today.

Non-goals: landing the cancelled task's product commits; a route for a
cancelled epic (TSK-418 covers wording edits to a cancelled epic's
records).

Added by the EPC-022 amendment of 2026-10-22 under the operator's
decisions of 2026-10-18 and 2026-10-22 (a defect that blocks work, and a
project-management change, belong in 3.2.0).

## Acceptance Criteria

- AC-1 A `plan/` branch whose range adds one standalone task record at `status: cancelled` with `- cancelled:` and `- scope:` lines, absent from the merge-base, with `Task: TSK-NNN` naming it, shall pass `codeflow ci` with no start claim and no `work.stable_planning_anchor` or `work.classification` refusal; evidence: a CLI fixture of the issue's shape, failing before the change. (serves EPC-022 AC-103)
- AC-2 The same range with the record at `todo` or `complete`, with a missing reason or scope, or with a product path in the range shall keep today's refusal, and the refusal for the `todo` case shall name the task-branch route; evidence: one negative fixture per case. (serves EPC-022 AC-103)
- AC-3 The pre-push check and `codeflow ci` with `--branch` shall agree on the verdict of AC-1 and AC-2; evidence: the fixtures run through both.
- AC-4 The documentation shall name the route for recording a standalone task cancelled before its record reached the target; evidence: the doc text.
- AC-5 (journey) With the installed build in a scratch adopter project, the issue's steps (a task branch with the record, a cancellation with `codeflow task status`, a one-commit `plan/` branch cut from the target) shall produce a pull request range `codeflow ci` accepts; evidence: the journey output.
