# TSK-416: Every check judges a line or a pinned predecessor by its fetched tip, never a stale local copy

## Description

Issue #262 and the 2026-10-22 comment on issue #278, the same cause in
two commands. `codeflow work claim` reports readiness "on
origin/<line>" (`crates/codeflow-core/src/workgraph/readiness.rs:1236`)
but checks a dependency's research pin against
`target_reference(repo, &line)` with the dependency's bare
`integration_target`, and `target_reference_names`
(`crates/codeflow-core/src/workgraph/work_start.rs:3039-3058`) tries
`refs/heads/<target>` before `refs/remotes/origin/<target>`, so a stale
local branch of the line decides readiness and refuses a pin that is on
origin's tip. `codeflow task status <id> complete` judges a waiver's
planning commit "on the target" the same way: with local `main` stale
at a commit before the planning pull request merged, completion refused
"waiver names <planning sha>, which is not on the target" although
`origin/main` held it. In both cases the agent cannot repair the local
branch: `git fetch origin <line>:<line>` is refused by git-guard as a
policy-authority change, and fast-forwarding a protected local `main`
is refused by `git.merge_to_protected`, so a person has to update the
checkout. TSK-398 fixed the same local-first lookup for `codeflow ci`
and pre-push anchors only (`cmd/ci.rs`).

Outcome: **every readiness and completion check that reports a
reference judges against that reference: a bare target resolves to the
remote-tracking ref when the remote has it, a local branch of the same
name never decides, and when only a local branch exists the message
says which reference was read.**

Rule: `target_reference_names` for a bare name tries
`refs/remotes/origin/<target>` first and `refs/heads/<target>` only
when the remote-tracking ref is absent, and every caller that reports a
reference prints the one it resolved. Callers found by a search of
`target_reference` and `target_reference_names` are each covered by a
test. The fetch `work claim` performs stays; it updates the
remote-tracking ref the check now reads.

Non-goals: moving a local branch for the user; the chain semantics
TSK-341 decides; the reopened-task waiver rule TSK-340 now carries (the
body of #278).

Added by the EPC-022 amendment of 2026-10-22 under the operator's release
rule of 2026-10-18 (a defect that blocks work belongs in 3.2.0).

## Findings

Read and run 2026-11-05 at `fd820f700`, before any code change. "Failed at
base" means the new fixture, run with the product code reverted, failed.

- **One cause.** `target_reference_names` listed `refs/heads/<name>`
  before `refs/remotes/origin/<name>` for a bare name, and
  `target_reference` took the first that resolved. Every reader of a bare
  name inherited it: `code_dependency` (failed at base: it reported the
  stale copy's `todo`), `task_target` for the waiver check, `coord/due.rs`,
  `lifecycle::has_active_branch` and the readiness test helper.
- **A second reader kept the local branch on purpose.**
  `resolve_work_target_checked` kept a local branch equal to or ahead of
  its upstream and returned the bare name. The claim cut from it (issue
  550, failed at base: a local line with an unpushed commit was claimed).
- **The unchecked resolver fell back to the bare name** on a diverged
  target (`resolve_work_target`), which `revparse` reads as the local
  branch; `task status complete` used it for the reopen base (issue 573).
- **The reopen judgment listed every copy.** `target_tips` returned the
  local tip beside the fetched one, so a stale copy could count as an
  outside tip.
- **Predecessor copies.** `pin_name` refused any second tip of a branch
  as "has advanced", and `stacked_pins` counted a stale copy behind the pin
  as a second stack (issue 603's wording half, failed at base).
- **Already fixed at base, so no failure to show.** The research pin check
  of issue 262 reads `tracking_reference` since TSK-381. The waiver of issue
  278 passes once pinned with `--base origin/<name> --into <name>` since
  TSK-340. Issue 573's reported refusal did not reproduce through `task
  status` on three shapes (stale before the landing, stale holding the old
  completion, ahead), unpinned or pinned, because TSK-340 moved that path.
- **Still reads the local branch.** `ci --base main` takes the revision it is
  given and says so; with a stale local copy that holds an older completion
  it still refuses the reopen. Hooks pass a commit, and the sanctioned
  spelling is `--base origin/main`.
- **Already remote-first** (no change): `git/conflict.rs`
  `find_target_ref`, `cmd/ci.rs` `branch_anchors` and `base_refs` (TSK-398),
  `ci.rs` `target_tip` (advertised heads), `default_work_target_ref`
  (the pre-push default target, `hooks/git_hook.rs` `epic_line_push`), and
  `tracking_reference` (remote-tracking only).
- **Issue 547.** `pr_review` sent the provider's stderr to null, so every
  failure read "provider failed" (failed at base).
- **AC-19.** `supersede_active_block` wrote `reason: {reason}` unquoted
  inside the YAML block.
