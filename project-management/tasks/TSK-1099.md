# TSK-1099: A cf-status skill answers every status request from codeflow status in any adopting project

## Description

The operator asked on 2026-10-30 for a command or skill that knows how to
report the status of things properly each time it is asked, in any
project that adopts CodeFlow. Today the rules say how a status reply reads
(`.codeflow/rules/writing.md` "Replies and status": outcomes first,
live-checked facts, operator items once) and the map's "report status or
hand off" row says what to check, but every session composes the report
by hand, and the hourly report of a long run has no fixed shape. TSK-1095
computes the facts and TSK-1098 renders them; this task is the managed
skill that runs them on every status request and adds the facts and
context only the session has: which lanes the coordinator runs, which
builders and seats carry them, which verdicts are in flight and which
blockers it knows that no record holds yet.

Outcome: **a session asked for status in any adopting project at the
standard or full tier runs `/cf-status`: it picks the scope from the
request (a task, an epic, the line, or the lanes it coordinates), writes
its session-only facts to a `--session` file in the shipped schema
(lane, task, builder, reviewer, seat, verdict in flight, blocker, each
with its observation time), runs `codeflow status --present <path>
--session <file>` and opens the document with `cf-present`, prepends one
context block with what is being worked on and why it matters in a few
plain lines, replies in chat with the handoff line and the anchor only,
uses the `--md` form where no browser can open (a terminal-only harness, a
PR body, a hand-off file), never computes a percent, an order or an
estimate by hand, and marks every fact the command marked unverified as
such; the orchestrator's status and hourly report guidance, the map row
and the away report point to it instead of restating a shape.**

```text
  "where are we?"  /  hourly tick  /  hand-off
        |
        v
  scope from the request (task | epic | line | my lanes)
        |
        v
  session facts -> session.json (lanes, seats, verdicts, blockers, times)
        |
        v
  codeflow status --present <tmp> --session session.json  [--md]
        |
        v
  one context block (what is being worked, why it matters)   <- the session
        |
        v
  cf-present open  ->  reply: handoff line + anchor; NEED YOUR ATTENTION
                        only for operator-owned items the report lists
```

Figure: the skill adds scope, session facts and context around one
command and one surface; the numbers never come from the session.

Decisions, each reversible and disclosed here:

- Name `cf-status`, matching the command it runs; trigger on a request
  for status, progress, where things stand, an hourly or hand-off report,
  or "report" in a coordination session; the operator confirms the name
  at plan approval (the earlier working name was `cf-report`).
- Tier: standard and full (it needs `cf-present`); the minimal tier's map
  row keeps its text and gains a pointer to the command's `--md` form.
- Session facts are observations, never state: the skill writes what it
  saw and when (a Herdr pane, a subagent id, a verdict file, a blocker
  it met), the command labels them `session` in the lanes view, and they
  never change a percent or a stage (TSK-1095 AC-4). The skill checks each
  changeable fact live before writing it, as the map row requires, or
  writes it with its last check time.
- In chat the reply is the handoff line, the anchor's lines and, once,
  NEED YOUR ATTENTION for the operator-owned items the issues view names
  (a merge into `main`, a hook trust, a decision); counts and tooling
  come last, as the writing rule orders.
- In a project with no `project-management/` tier the skill says so,
  reports what git and the forge show through the command's `unknown`
  fields and never invents tasks, lanes or percents.
- The hourly report of a long run (the coordinator's sweep, the away
  tick of TSK-1046 when it lands) is this skill with the same scope and a
  fresh session file each time, passing the previous run's facts file
  through `--since` so the since strip is filled; the skill keeps the
  last facts file per scope under the present state directory, never in
  the repository. The away report (`codeflow report away`, TSK-1045)
  stays the activation's own report and links the progress document.
- The live `cf-present` session is the handover surface; an export is a
  review capture of the session at a time and the skill says so beside
  any export it hands over (the four reviews of 2026-10-30 found the
  export clipping stages; TSK-1101 fixes it).

Non-goals: the facts and the rendering (TSK-1095, TSK-1098); scheduling
(the harness schedules, as TSK-1037 and TSK-1046 record); writing to any
record or ledger; replacing `codeflow status`'s text view, `work next` or
`orient`.

## Outcome

After this merges, anyone on an adopting project who asks a session for
status gets the same figure-led progress document with the session's
lanes, seats and context drawn in, in a few seconds, with every number
from the command and every unverified fact marked.
