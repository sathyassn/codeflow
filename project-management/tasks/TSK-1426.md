# TSK-1426: The edit guard maps drive-relative and NT namespace paths, and the line's Windows tests pass

## Description

After PR 747 landed TSK-1400, line push run 42913832921 (at 0318b9c03) failed `the_authority_directory_is_covered_under_windows_spellings_of_the_home` in Windows partition 1 of 12. The guard was right and the test was wrong. A verbatim path keeps a trailing dot, so `\\?\<home>\.codeflow\authority.\config.toml` names a different directory. `namespace_spelling` (`portable_path.rs:177-181`) refuses to map it, and `evaluate` returns an error, which the hook adapter refuses (`hook.rs:843-846`, exit 2). The test helper panicked on that error.

The spelling sweep that followed found two spellings the edit guard judged wrongly:

- A drive-relative target (`C:name`) joined onto the cwd keeps its drive and drops the cwd. Windows opens it from the writer's current directory on that drive, which the guard cannot read. When the parent did not exist, the guard allowed it.
- An NT namespace target (`\??\C:\x`) is rooted but not absolute to the standard library, so a join put the cwd's drive in front of it, while Win32 opens it as `\\?\C:\x`. The fix forward removes that exception. `absolute_target` maps every namespace and UNC spelling by its prefix class before the join (`portable_path::edit_target`), so every target must be absolute after the join, and a spelling that maps to no rooted drive or complete UNC path refuses.

Overlap: TSK-391 AC-4 asks for device-namespace spellings to map or be refused. This task covers the edit guard's `\??\` case. TSK-391's builder reads this record's spelling table before building, and TSK-391 AC-13 and AC-14 hold the shell guards' same gap (residual 5).

This is the TSK-1400 recovery as a new task (Director ruling 2026-11-10, operator option 1 of 16:22); TSK-1400 stays complete at ee4b33625. The code is on `task/TSK-1400-the-3-2-0-line-passes-its-windows-tests-after-th`: `12d1161fb` (the test), `4780fa7f0` (the guard) and the fix forward `a7469cc5d`, which removes the NT namespace exception (Codex approved at a7469cc5d, `coordination/coordinators/parallel/reviews/tsk1400-fixforward-a7469cc5d-codex.md` in the workspace repository). The builder moves those commits to this task's branch and reverts the reopen of TSK-1400 (`131f429e4`). Epic: EPC-050 holds the Windows path-spelling work (TSK-391). TSK-1400's own epic, EPC-054, is about trusting the landed policy and the real remote, which this fix does not change.

- Root cause: the test expected a refusal finding for `\\?\<home>\.codeflow\authority.\config.toml`. A verbatim path keeps the trailing dot, so it names another directory; `namespace_spelling` (`portable_path.rs:177-181`) refuses to map it (review 01, B6) and `evaluate` returns an error, which the hook adapter refuses (`codeflow-cli/src/cmd/hook.rs:843-846`, exit 2). - The spelling sweep found two spellings the guard judged wrongly, fixed in `4780fa7f0` and `a7469cc5d`, now as one rule:
  - A drive-relative target (`C:name`) joined onto the cwd keeps its drive and drops the cwd. Windows opens it from the writer's current directory on that drive, which the guard cannot read; when the parent did not exist it was allowed.
  - An NT namespace target (`\??\C:\x`) is rooted but not absolute to the standard library, so a join put the cwd's drive in front of it, while Win32 opens it as `\\?\C:\x`.
  - The rule: `absolute_target` (`edit_guard.rs:236-249`) maps every namespace and UNC spelling by its prefix class through `portable_path::edit_target` (`portable_path.rs:310`), before the join and once more after it, and `evaluate` refuses every target still not absolute (`edit_guard.rs:349`). The earlier `nt_namespace` exception is gone.
- The prefix class is read from the written text before separators are rewritten (`PrefixClass`, `prefix_class`, `class_spelling`, `portable_path.rs:215-300`), and `guard_path` uses the same reading (`portable_path.rs:123`). A namespace drive path must be rooted (`portable_path.rs:160-164`) and a UNC path complete (`edit_target_text`, `portable_path.rs:322-348`).
- Shell startup files are judged on the mapped target and its normalized and resolved spellings, whatever the hook integrity level (`edit_guard.rs:366-378`), never only on the path as written. Test `startup_files_refuse_under_namespace_spellings_with_integrity_off` (`edit_guard.rs:2368`, Windows).

Residuals:

1. Closed: a non-administrative UNC share that maps into the home now refuses outside the chosen directories, so it can no longer reach the home unjudged. A UNC home or cwd keeps working, as TSK-1002 decided, because those are chosen directories. An alias inside a chosen share is still trusted, the same assumption the interpreter guard makes.
2. A non-ASCII case variant of the home is covered only through the resolved spelling, so only while the home exists.
3. Junctions have no Windows test.
4. A hard link to an authority file is outside the edit guard; making one is a shell command the exec guard judges.
5. Unchanged, held by TSK-391 AC-13 and AC-14: the shell guards join path operands onto the cwd without mapping `\??\` or refusing `C:name`: `shell_path_with_home` (`git_guard.rs:4018`) and `path_integrity` (`git_guard.rs:2462-2466`), and `linked_paths` (`security/composed/paths.rs:444`). Interpreter literals reach the edit guard through `enforcement_path` (`security/interpreter.rs:122`, `security/arguments.rs:1335`), which this fix covers; `interpreter.rs:110` skips a word with no `/` that does not start with `.`. Git lines refuse namespace markers (`git_preflight.rs:123`, `:349`); other lines do not.
6. Accepted: administrative shares map by drive letter whatever the host (`portable_path.rs:199-206`). That inherited mapping can over-refuse a remote file and does not establish its identity with a local one; it fails closed, so no task is filed.
