# TSK-1293: A project adds its own model lines in the model selection file

## Description

Models change faster than CodeFlow releases. The operator ruled on 2026-11-03 that a consuming project can add a model line or version CodeFlow does not ship yet, without waiting for a release, and can override every catalog field. Today `.codeflow/model-selection.json` schema 1 and 2 accept only qualified-binding ids, design authority within a family and standing reviews (`references/model-overrides.md:3-28`, `crates/codeflow-core/src/model_catalog/selection.rs:18-29`); the personal overlay (`overlay.rs:4-20`) is per user and carries no routes.

This task adds the schema 3 `models` block. A project entry gives family and lineage, a selector per harness, allowed efforts, lifecycle and launch mode, and may mark a shipped version retired or excluded. A family the catalog does not know must declare its lineage, so the review-independence check can still tell lineages apart. Project entries carry no designations or qualification evidence; those stay managed.

The only refusals are the floors: no headless seats, launching the pinned id that resolve returns, and failing closed with the key named when the file is invalid. Security relevant: the file decides which model reviews whose work.

## Outcome

After this merges, a project maintainer can register a new model line or version in `.codeflow/model-selection.json` and have `codeflow models resolve` launch its pinned id.

## Deliverables

- the schema 3 `models` block, its parser and validation: `crates/codeflow-core/src/model_catalog/selection.rs` and `inputs.rs`, the shipped `assets/base/model-selection.json` and its JSON schema
- docs: `references/model-overrides.md` (mirrored)
- tests: unit tests beside the parser and a CLI test of `codeflow models resolve`
- release note: `changelog.d/TSK-1293.md`

## Acceptance Criteria

- AC-1 When `.codeflow/model-selection.json` schema 3 adds a version of a shipped line, or a new line with family, lineage, selector per harness, allowed efforts, lifecycle and launch mode, `codeflow models resolve` shall launch its pinned id for a route that names it; evidence: a CLI test for each.
- AC-2 A project entry may mark a shipped version retired or excluded, and resolve shall then skip it or refuse a route that names it, naming the entry; evidence: a test for each.
- AC-3 An entry that is unknown, lacks a lineage for a family the catalog does not know, carries a designation or evidence field, or is otherwise invalid shall refuse with the key named, and no part of the file shall be used; evidence: one test per case.
- AC-4 The floors shall hold whatever the file says: a headless launch is refused, the launched id is the pinned id resolve returned, and an invalid file fails closed naming the key; evidence: a test per floor with a file that tries to lift it.
- AC-5 Schema 1 and 2 files shall keep validating and resolving as before; evidence: the existing selection tests passing unchanged.
- AC-6 (journey) In a scratch project with the installed build, a maintainer adds a new version, resolve launches it, and an entry missing its lineage is refused naming the key; evidence: the journey output.
- AC-7 A changelog entry shall describe the block; evidence: `changelog.d/TSK-1293.md`.
