# TSK-1418: A pipeline run given a task claims and starts it, and records a blocker it cannot clear

## Description

The scaffolded develop pipeline (`assets/base/claude/workflows/pipeline.workflow.js`, installed at `.claude/workflows/pipeline.workflow.js`) takes a free-text `task` and criteria. It calls `codeflow validate`, `codeflow test` and `codeflow models resolve`, and never a work verb. A person who runs it on a planned task must run `codeflow work claim` and `codeflow work start` first and set the task's status after, by hand. A run that skips them builds on a branch no claim records and that `work start` never checked.

This task lets the caller pass a task id. With an id, the pipeline claims and starts the task before any stage builds, stops with the verb's own refusal when either refuses, and, when a stage reports a blocker outside the unit, records it on the task with `codeflow task status <id> blocked` and its reason, owner and revisit. It never sets a task complete or cancelled: completion needs an acceptance block bound to an independent review, and a pipeline run is single-vendor (ADR-0023). Its last output names the next step for the caller.

Design part settled here: the pipeline stays user-owned, so `codeflow update` never rewrites an adopter's copy. Fresh installs get the change, and the release note gives existing adopters the edit, as TSK-370 does. Design part left to AC-1: how a run moves from the claim's reported branch to a worktree the stages work in.

Non-goals: the interactive orchestrator and `cf-develop`, which already call the verbs; away sessions (EPC-049); a run with no task id, which behaves as today.

## Outcome

After this merges, an adopter who runs the pipeline on a planned task gets a claimed, started task branch before any code is written, a refusal when the task is not ready, and a recorded blocker when the run cannot finish, with no hand-run verbs.

## Acceptance Criteria

- AC-1 Before any change, the builder shall record in `## Findings` how a pipeline run goes from a task id to a started task branch (the claim's reported branch, the worktree the stages run in, and `work start` in it), which status writes a single-vendor run may make, and how TSK-1173's claim changes the steps; evidence: the Findings section committed before the first code change.
- AC-2 When the pipeline is given a task id, it shall run `codeflow work claim` and then `codeflow work start` for that id before the first stage that writes code, and every later stage shall work in the started task branch; evidence: a contract test that pins the calls and their order, and the journey in AC-6.
- AC-3 When `work claim` or `work start` refuses, the pipeline shall stop before any stage writes code and report the verb's refusal text as its result; evidence: contract tests for a claim refusal and a start refusal.
- AC-4 When a stage reports a blocker outside the unit, the pipeline shall run `codeflow task status <id> blocked` with a reason, an owner and a revisit event taken from the stage's structured output, and stop; it shall never set a task `complete` or `cancelled`; evidence: a contract test for the blocked path, and a test that no code path passes `complete` or `cancelled` to `task status`.
- AC-5 Without a task id, the pipeline shall behave as before this change; evidence: the existing pipeline contract tests passing unchanged.
- AC-6 (journey) In a scratch adopter at the full tier, scaffolded by this task's binary, a pipeline run given a planned task shall leave a claimed and started task branch with the stages' commits on it, and a second run on a task whose predecessor is open shall stop on the start refusal; evidence: the journey output in the pull request body.
- AC-7 The release note shall give existing adopters the edit that adopts the change, since `codeflow update` never rewrites the user-owned pipeline; evidence: `changelog.d/TSK-1418.md`.
