# TSK-1570: Judge refused unreadable -c and -e forms on data programs

## Description

Source: the Director, 2026-11-20, from PR 706 phase 7 (TSK-1344), which kept these forms refused so the guard fails closed. Owner: coord/catalog. The epic is EPC-029 ("Guards read command lines and inline programs as they run"), the epic that owns guard judging and holds TSK-1344. It lands on the EPC-022 line through EPC-029's `parent_line`. It depends on TSK-1344, because the refusals it narrows are added by PR 706 and are not on `main`.

The guard refuses an option value it cannot read, because a value it cannot read might hold a command. These ordinary forms are refused today, in exec-guard and in git-guard. The first six are refused only because the argument is not readable. The last five are refused by the rules PR 706 added in its last round, which read more forms as command slots (`coordination/coordinators/capabilities/notes/pr706-report.md:820-823` and `:874`):

| Form | Why the guard refuses it |
|---|---|
| `psql -c "$SQL"` | the value is a shell variable |
| `mysql -e "$SQL"` | the value is a shell variable |
| `docker run -e "FOO=$X" image` | the value is a shell variable |
| `ls -c "$D"` | `-c` is a sort flag here, and the rule cannot tell a flag from a valued option for a program it does not model |
| `ssh -o "$OPT"` | the option key cannot be read, and `ProxyCommand` runs a command |
| GNU `sed -i 's/a/b/' "$F"` | the scan reads `-i` the BSD way, where the next word is the backup suffix |
| `ls -lc "$D"` | for a program off the data list, a short option cluster ending in `c` or `e` takes the next word as its value, and that word is a shell variable |
| `cp -ec "$F" d` | the same cluster rule as `ls -lc`; the next word is a shell variable |
| `export EDITOR="$E"`, `export VISUAL="$E"`, `export PAGER="$P"`, and a bare `EDITOR="$E"` statement | the value is a shell variable, git falls back to these variables for its editor and pager, and the program the value reaches is not known, so a later git command on the line could run it (`EDITOR="$E" make` stays allowed) |
| `a=b=hc` | the word has a carrier (`hc`) after a later `=`, which the scan reads as a carrier assignment; the shell assigns the text `b=hc` to `a` |
| `tar --new "$X"` | the scan reads the abbreviated long option `--new` as `--new-volume-script`, which runs a command, and the next word is a shell variable |

Where the code is, in PR 706's head `c0c482a7b8` (worktree `codeflow/.worktrees/tsk-1344`):

- `crates/codeflow-core/src/security/outward.rs:1816-1844`, the data list `DATA_OPTION_PROGRAMS` (grep, cut, ssh `-c`, curl and others, each with its manual-page reason).
- `crates/codeflow-core/src/security/outward.rs:1854-1880`, `unread_command_values`, which refuses an unread `-c` or `-e` value for any program off that list.
- `crates/codeflow-core/src/security/outward.rs:6216`, the test `unreadable_c_and_e_values_refuse_by_default`.
- The record of the choice: `coordination/coordinators/capabilities/notes/pr706-report.md:626-640` and `:748-760` (the before and after table).

Design points the builder settles, with reasons recorded in `## Findings` or the code comment:

- psql and mysql have meta-commands that run a shell command (`\!` in psql, `\!` or `system` in mysql). PR 706's report says it did not check whether `-c` and `-e` accept them. A literal SQL value is judged only after that is read from the manuals, and a literal that holds such a command refuses.
- `docker run -e` sets a container variable; `docker run` with a readable `FOO=value` carries no command. The value's name and text are judged by the existing carrier rules.
- `ls -c` is a sort flag; the fix is a per-program option table entry, not a general rule that a flag is never valued.
- GNU `sed -i` takes an attached suffix only (`-i.bak`), so the next word is the script. BSD `sed -i ''` takes the suffix as the next word. The scan must read which one is meant, or refuse when it cannot tell.
- `ssh -o` with a readable key that is not a command key (`User=`, `Port=`, `StrictHostKeyChecking=`) is data. `ProxyCommand`, `LocalCommand` and any key the guard cannot read stay refused.
- Decide `<unknown program> --command "$CMD"` (the case `frobnicate --command "$CMD"`, a long command option on a program the guard does not model) on the guard's model: for an unknown program the guard's boundary is the program word, not the program's option names, and refusing by option name is a heuristic that cannot be made sound and would over-refuse widely. The same decision covers the option-name refusals PR 706 added for unknown programs (`frobnicate -c "$CMD"`, `frobnicate -xc "$CMD"`); for this case it takes precedence over the non-goals below, and the decision and its reason go in `## Findings`. (Added 2026-11-20 by the Director's order, in the delivery-approach planning amendment.)

Non-goals: loosening the default for a program the guard does not model, reading any value that is still unreadable (`"$SQL"` stays unreadable), and changing the carrier scan's rules for tar, ssh `-c`, scp or rsync. A form that stays unreadable stays refused; this task never allows an unreadable value.

## Outcome

After this merges, an adopter's session can run `psql`, `mysql`, `docker run -e`, `ls -c`, `ssh -o` and GNU `sed -i` with arguments the guard can read, and an argument it cannot read is still refused.

## Acceptance Criteria

- AC-1 When a `psql -c` or `mysql -e` value is a literal the guard can read and holds no shell-running meta-command, the guard shall allow the call, and when the value is an expansion it cannot read, or a literal that holds a shell-running meta-command, the guard shall refuse it; evidence: a refused and an allowed test per program, in exec-guard and git-guard.
- AC-2 When a `docker run -e` value is a literal `NAME=value`, or an expansion the guard tracks to a literal, and carries no command, the guard shall allow the call, and when the value is an expansion it cannot read, the guard shall refuse it; evidence: a refused and an allowed test, in both guards.
- AC-3 When `ls -c` is given only operands that are literals or tracked values, the guard shall allow the call, and when an operand is an expansion it cannot read, the guard shall refuse it; evidence: a refused and an allowed test, in both guards.
- AC-4 When an `ssh -o` option names a key that is not a command key and the value is readable, the guard shall allow the call, and when the key cannot be read, or names `ProxyCommand`, `LocalCommand` or another key that runs a command, the guard shall refuse it; evidence: a refused and an allowed test, in both guards.
- AC-5 When `sed -i` is written in the GNU form (an attached suffix or none) with a script that is a literal, the guard shall read the next word as the script and allow the call, and when the script is an expansion it cannot read, or the guard cannot tell the GNU form from the BSD form, it shall refuse it; evidence: a refused and an allowed test, with the BSD form `sed -i '' 's/a/b/' file` still allowed.
- AC-6 When the guard judges a form of AC-1 to AC-5, it shall give the same decision for the same command in exec-guard and in git-guard; evidence: a test that runs each form through both guards and compares the result and message.
