# TSK-435: Records state their Outcome and epics their Deliverables

## Description

Operator decision of 2026-10-22, part of the issue #280 work: an
explicit Outcome on records, and Deliverables on epics. Issue 280 asks
that an epic state one value line ("after this merges, X can do Y");
today the task template has no home for it (records put an "Outcome:"
sentence in the Description by convention), the epic template has no
Deliverables section, and `codeflow validate --docs` checks a task's
Deliverables (`crates/codeflow-core/src/workgraph/record_text.rs:581-596`)
but no Outcome anywhere.

Outcome: **after this lands, a task or epic record created with the
templates carries an `## Outcome` section with one line saying what
someone can do once it lands, an epic carries a `## Deliverables`
section like a task's, `codeflow validate --docs` requires the Outcome
section on records created after the change, and existing records stay
valid: closed records are never changed or flagged, and an open record
created before the change gets a warning, not a refusal, and gains the
section when next amended.**

Rules:

- **Templates.** `assets/base/pm/task.md.tmpl` and `epic.md.tmpl` gain
  `## Outcome` (one line, in the form "after this merges, X can do Y")
  between the Description and the Deliverables; `epic.md.tmpl` gains
  `## Deliverables` with the task template's comment. `codeflow task
  new` and `epic new` write both.
- **Validation, adoption-aware.** The compatibility boundary is the
  project's own adoption of this release, identified by record
  identity, never by a calendar date: when `codeflow update` first
  brings a release that has the section, it writes the adoption marker
  into the project's configuration (provisional
  `records.outcome_required_since` in `.codeflow/project.toml`) with
  the adoption commit (the project's HEAD at that update) and the
  `uid` of every task and epic record present in the working tree at
  that moment, committed or not. A record is "present at adoption"
  when its uid is in that list; every other record is "later". A later
  non-terminal record whose Outcome section is missing or empty is
  refused by `validate --docs`; a present-at-adoption record without it
  gets a warning naming the section and gains the section when next
  amended, whatever its `created` date, so a record made with the old
  release the morning of a same-day upgrade stays valid; a record whose
  status is terminal (complete, cancelled, archived) is never flagged.
  A fresh `codeflow init` writes the marker with an empty list, so
  every record of a new project needs the section. With no marker (a
  project updated by hand, or one that has not yet run `codeflow
  update`), every missing section warns and nothing refuses, and
  `codeflow doctor` says the marker is missing and how `update` writes
  it.
- **Compatibility.** No existing record is edited by this task; the
  "Outcome:" sentence convention in Descriptions stays valid for old
  records.
- **Guidance.** `cf-plan` and `cf-method` "Planning an epic" name the
  section as the home of the value line; TSK-419's sizing guidance
  points at it, so TSK-419 depends on this task.

Non-goals: rewording existing records (TSK-418's class covers that when
a project wants it); any new field in frontmatter.

Added by the EPC-022 amendment of 2026-10-22 at the operator's
direction of that day.

- AC-1 `codeflow task new` and `codeflow epic new` shall write an `## Outcome` section with its one-line comment, and `epic new` shall also write `## Deliverables` with the task template's comment; evidence: scaffold tests reading both records. (serves EPC-022 AC-117)
- AC-2 `codeflow validate --docs` shall refuse a non-terminal task or epic record whose uid is not in the project's adoption marker and whose Outcome section is missing or empty, naming the record and the section; evidence: a validate test, failing before the change. (serves EPC-022 AC-117)

(serves EPC-022 AC-117)
- AC-4 `cf-plan` and `cf-method` "Planning an epic" shall name the Outcome section as the home of the epic's value line and the task's outcome, and `docs/policy-reference.md` shall state the adoption-marker rule and the compatibility rule; evidence: the text diff and `codeflow validate --docs`.
