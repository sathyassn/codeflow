# TSK-1240: Main's own push builds and saves the policy cache for main-target pull requests

## Description

Source: the CI throughput study of 2026-11-02 (`coordination/coordinators/parallel/throughput/`: RECOMMENDATIONS.md, FINDINGS.md, CHECK-codex.md, CHECK-fable.md), cross-checked by Codex GPT-6 Astra and Claude Fable 5.1, and the priority on CI throughput.

The hosted "commit standards" job rebuilds `codeflow` from the target branch on every pull request event, including body edits (`.github/workflows/codeflow-policy.yml:78-89`). Each rebuild takes about 3 minutes. The policy check runs the target's binary against the pull request, so what a cache holds and who may write it decide what runs with the check's authority.

Re-scope (Director ruling, 07:16 on 2026-11-03, quoted): "Its security review found that main's run building integration code could poison main's caches, so I ruled that main's run never saves a cache from integration output. That removes the title's promise to cache verified target builds in main's scope." The earlier design, in which a main-ref dispatch built an integration SHA and saved it into main's cache scope ("Selected writer design" below), is withdrawn. The later Director ruling, after Fable design review r2 F2, drops part (a), evidence reuse. The task retains only part (b):

- (b) Main's own push run builds and saves main-scope caches from main's code. No run saves a main-scope cache from integration output.

Non-goals: new evidence reuse, changes to existing TSK-265/359 reuse, admission (TSK-1239) and the verdict jobs. TSK-1248, which carries the hosted proof of the withdrawn writer, no longer matches this scope and needs its own re-scope by coord/planning.

## Outcome

After this merges, main's own pushes warm main's policy-binary cache from main's code, pull request events targeting the same main SHA can restore that build instead of rebuilding, and no integration output can reach main's cache scope.

- the main-only cache save and the removal of the integration-output save: `.github/workflows/codeflow-policy.yml`

## Current design: attested binary cache

This section is the current design. The "Implementation notes" section after it is history from the earlier design, which this one replaces where they differ.

### What runs where

| Where | What it does |
|---|---|
| `codeflow-registry.yml`, job `cache-main-build` (the one writer) | On a push to `refs/heads/main` only: builds the pushed commit, checks the embedded revision, attests the binary with `actions/attest-build-provenance`, saves it under the exact key, and saves the dependency cache. Holds `contents: read`, `id-token: write` and `attestations: write`, and no other write permission. Checkout does not persist credentials. |
| `codeflow-policy.yml`, both verdict jobs (readers) | Restore the exact key into `$RUNNER_TEMP/codeflow-main-binary` (never on PATH), then run `gh attestation verify` pinned to the registry workflow on `refs/heads/main`, the main commit as source and signer digest, and no self-hosted runners. Only when it verifies, and the scrubbed `--version` reports the main commit and a clean tree, is the file used. On anything else the restored directory is deleted, a warning names the entry, the dependency cache is restored and the job builds. A rebuilt binary must report the main commit and a clean tree or the job stops. Readers never save (`save-if: false`). |

### The limit, stated plainly

- The attestation covers the bytes that run, and nothing else.
- Restoring an entry is not made safe by it. `actions/cache` extracts an archive with `tar -P` before any check can run, so the archive decides where files land. The reader restores into a fresh directory off PATH and deletes it unless it verifies, which limits what a bad entry reaches but does not make extraction safe by itself.
- "No fallback keys" holds for the binary only. The dependency restore has a prefix fallback inside the action: `Swatinem/rust-cache` always passes `config.restoreKey` (`config.ts:27-28`, `restore.ts:41`), so a miss may restore an older main-built dependency entry of the `codeflow-policy-main-deps-v3` namespace.
- On a miss the verdict job builds with the dependency cache restored from main's scope. Cargo links cached dependency artifacts into that build, so the trust there is the single writer of main's scope: one writer job, one trigger, tested.
- The scrubbed `--version` probe is an extra stale-entry check, not authentication.
- The verify step holds the job's read-only token (also persisted by the checkout).

Ordering: TSK-1314 is complete on main, and PR 528 now targets main (coord/ci route of 2026-11-05). The proposals were rebased onto main's workflow text at `fa9a1023e` by a three-way merge with no conflicts; main's own changes since the line (the queued concurrency group and the body read from a file) are kept unchanged.

### Why the default branch carries the authority

GitHub's [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) gives `pull_request_target` and `schedule` the default branch's last commit as `GITHUB_SHA` and the default branch as `GITHUB_REF` ("Last commit on default branch", "Default branch"). For `schedule` it adds that the event "will only trigger a workflow run if the workflow file exists on the default branch"; the `pull_request_target` section has no such sentence. The [2025-11-07 changelog](https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/) says "The `pull_request_target` event now always uses the default branch for workflow source and reference", that `GITHUB_SHA` "will point to the latest commit on that branch", and that the change takes effect on 12/8/2025. Both pages were re-read on 2026-11-03 through a fetch tool that returns excerpts, so the quoted phrases are the tool's quotations of the pages.

### Evidence, and what is estimated

Measured:

- The build step took a median of 164.5 s (range 122 to 176 s) over 14 recent `commit standards` runs.
- `gh attestation verify` took about 2 s against an attested public `cli/cli` asset, and a wrong `--source-ref` exited 1.
- The dependency-cache restore step (`Swatinem/rust-cache`) took 3 to 7 s, median 5 s, in the 8 recorded runs checked on 2026-11-03.
- The binary is about 32 MB.

Estimate for AC-9 (not a measurement): a hit costs about 5 s to restore the binary (taken as no more than the dependency restore, which moves more data), about 2 s to verify and about 1 s for the version probe, and skips the dependency restore of about 5 s. A hit job then spends about 8 s where the baseline spends about 170 s (a 5 s dependency restore plus the 165 s median build), a saving of about 150 s a job and about 300 s an event, since each event runs two verdict jobs. The cost is the writer job, which builds once per main push (about 4 minutes); main moved 6 times on 2026-11-03 against hundreds of policy runs. The estimate favours keeping the binary restore.

Not verified until a hosted run on main (TSK-1248): the restore time itself, whether attestations work for this user-owned public repository, whether the job token can read them, the runner's `gh` flags and Sigstore availability. If attestations do not work, every verdict job rebuilds as it does today and none runs an unverified binary; a test shows that (`test_only_a_verified_attestation_lets_a_restored_binary_run`, cases "attestation fails" and "attestations unavailable for the repository"). The hosted proof must show one verified pass.

### Removal recipe and what was dropped

- To drop the binary restore and keep the dependency restore: delete the steps "Restore the authority binary" and "Verify the authority binary" and the Assert steps after them in each verdict job, drop the `if:` lines on the dependency and build steps, and delete the writer's "Look for", "Attest" and "Save" steps and the job's two extra permissions. The dependency steps reference no binary key or output apart from the `verified` flag in their `if:` (test `test_removing_the_binary_restore_leaves_the_dependency_cache`).
- Dropped, F5 of the design review (a writer split into a build job and an attest-and-save job): it needs `needs:` and an artifact transfer for a small gain, because a compromised build already compromises the binary it attests. The review's cheap part is kept: the dependency save is gated to main on the writer and `save-if: false` on the readers. `Swatinem/rust-cache` has no `cache-mode` input at the pinned revision (6323deb, v2.9.2). `save-if` governs saving only; whether a run may read or write main's scope is set by the trigger's default. `cache-mode` is a job-level workflow key, not an action input, and is optional hardening here, because `pull_request_target` already defaults to read.

### Outcome and criteria

Main's own push at SHA X builds and saves its policy binary. A later PR-target
event with main base X restores that exact binary, reducing its build time.
A new main SHA misses and rebuilds. Integration builds never populate main's
cache scope. There is no integration-target speedup claim.

| Criterion | Design obligation |
|---|---|
| AC-1 | Retain historical measurements and input/scope inventory |
| AC-2 | Exact main SHA and environment/toolchain key, no fallback, main rebuild on miss |
| AC-3 | Only push on refs/heads/main saves main binary or dependency caches |
| AC-4 | Verify restored source/clean identity, rebuild wrong entries, refuse wrong rebuilt identity |
| AC-5 | Cross-lineage cache-security review, including integration poisoning |
| AC-6 | Main saves X; PR-target base X hits faster than a PR-target miss; changed main SHA misses |

AC-7/AC-8 are removed with part (a); their IDs are not reused. AC-5 no longer
asks for evidence-reuse attacks. AC-1/2/3/4/6 remain unchanged by this ruling.

### Four binding rules

1. **Remove the integration dispatch writer; preserve target judging.** Remove
   build_sha and the dispatched integration checkout/build. Main push builds
   only its immutable event SHA. Integration-target PR runs keep checking out
   and building their own base target as today and never save. Their token's
   cache access stays read-only. This task does not replace the target's binary
   or admission helper with main's, so ahead-of-main policy schemas remain
   judged by the target's own code.

2. **No main cache of any kind from integration output.** The only producer
   is push:main executing main code on its own runner. No dispatch or artifact
   publisher survives. Binary and dependency caches use fresh main-only
   namespaces with no fallback to old potentially contaminated entries.
   No integration artifact is downloaded, restored, copied into a build tree,
   executed or saved in main scope, even if that SHA later lands on main.
   After landing, build afresh as main code. This task disables integration
   cache writes in the policy workflow rather than retaining a second producer.
   Cost: each integration push rebuilds dependencies not already supplied by
   a matching main dependency cache; it cannot retain its own new build output
   for later runs. This trades integration cache performance for simpler saves.

3. **No new run-evidence trust boundary.** The API run/workflow-blob/tree/digest
   verifier required for part (a) is removed with that part. Nothing accepts
   integration run IDs, job text, manifests or artifact hashes as authority.
   Existing TSK-265/359 bindings remain unchanged. Part (b)'s source identity
   comes from the event's trusted main commit and clean checkout; cache keys
   are calculated locally before fetching any PR head, never from head input.

4. **Fail closed.** Wrong, absent or inexact main binary entries rebuild from
   their main target. Integration targets always build their own source and
   never use or save the main binary cache. A dirty source, failed build or
   wrong rebuilt identity refuses before PATH or save-enabling output.
   The PR body explains runtime-token arbitrary-key cache poisoning and why
   self-reported binary identity cannot authenticate an adversarial writer.
   Main-owned production plus read-only PR consumers is the standard boundary;
   an identity string detects stale entries, not malicious trusted producers.

### Workflow behavior

Only `.github/workflows/codeflow-policy.yml` changes. Remove workflow_dispatch
and its inputs, the warm job, actions: write and dispatched-SHA selection.
Remove master consistently from triggers/allowed in this main-only repository
copy; the shipped template is untouched. Top-level permissions stay exactly
contents: read. Preserve the existing policy job's necessary read permissions.

The binary key includes exact main source SHA, rustc/Cargo and compiler identity,
runner image and architecture, and build flags. A versioned main-only namespace
fixes release/default-feature/native-target choices. No restore-keys. Separate
binary cache storage from Cargo's build tree; roll dependency namespace too.

Use lookup-only on push:main restore. An exact existing entry avoids redundant
cache population without downloading/executing that entry; any binary needed
for the push's own policy work must still be obtained through the trusted build
path. PR-target readers restore bytes, then perform the identity check. Remove
any separate pre-check version execution; the identity predicate is the single
version probe. Require executable regular file, exact source SHA and clean
state. Recheck newly built identity before exposing the binary.

Binary save-if requires verified fresh build, cache miss, and exactly
`github.event_name == 'push' && github.ref == 'refs/heads/main'`.
Dependency save-if also requires exactly that event/ref conjunction. No other
event is allowed to save. workflow_dispatch and master never enter allowed.
Use strict shell mode. A missing cache never weakens these rules.

### Build inputs and identity

- The checkout uses the event's base SHA for a pull request; other events use
  their own commit (`.github/workflows/codeflow-policy.yml:73-89`). That SHA
  fixes Rust sources, embedded assets, Cargo manifests and lockfile, Cargo

- `rust-toolchain.toml` pins Rust 1.94.0. Include actual `rustc -vV` and

- The build selects `codeflow-cli`, release profile, default dependency
  features and the native host target. There are no extra feature flags.
  The cache namespace fixes those choices; changes must change that namespace.
- The environment is GitHub's `ubuntu-24.04` runner, with its architecture,

  Include image identity and compiler/build environment in the digest so an

### Cache authority and design

[GitHub's cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)
and [read-only trigger announcement](https://github.blog/changelog/2026-06-26-read-only-actions-cache-for-untrusted-triggers/)
were checked live. Caches are branch/ref scoped. Runs can restore current and
default-branch caches; pull-request runs can also read base-branch caches.
Head builds under `pull_request` write only their merge-ref scope, invisible
to a target run. Default-scope writes are allowed for push, dispatch,
repository_dispatch, delete, registry_package, page_build and schedule.
`pull_request_target` has read-only default-scope access unless explicitly
weakened. This change must not weaken it.

Use separate pinned `actions/cache/restore` and `actions/cache/save` actions,
with an exact target-SHA/toolchain key and no fallback keys. Accept only an
exact hit, because the cache service can also return a prefix match. Save
only after a fresh verified target build on a push to main, master or an
integration branch. (Under the re-scope, only main's own push saves a main-scope cache; see AC-3.) Disable the dependency cache's save on PR events too.
Manual dispatches on arbitrary branches must not restore or save this binary.
Only the binary is cached, outside the Cargo build tree; a mismatch discards
it and rebuilds from the target. A restored executable's reported identity
is not a signature and cannot defend against an actor who already controls
a trusted branch's workflows or cache-write authority.

The workflow is evaluated from trusted workflow content. This PR's own
`pull_request_target` run cannot execute its proposed workflow change; hosted
hit/miss and consecutive-event journey evidence remains owed until the
trusted workflow has the change. Do not change the denied CI workflow or
execute PR-head code in the trusted job to manufacture that evidence.
