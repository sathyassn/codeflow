# TSK-1240: Commit standards caches the target build by the target's SHA

## Description

Source: the CI throughput study of 2026-11-02 (`coordination/coordinators/parallel/throughput/`: RECOMMENDATIONS.md, FINDINGS.md, CHECK-codex.md, CHECK-fable.md), cross-checked by Codex GPT-6 Astra and Claude Fable 5.1, and the operator's priority on CI throughput.

The hosted "commit standards" job rebuilds `codeflow` from the target branch on every pull request event, including body edits (`.github/workflows/codeflow-policy.yml:78-89`). Each rebuild takes about 3 minutes. The build can be cached by the exact target SHA and the toolchain, because the same target gives the same binary.

The change is security-adjacent: the policy check runs the target's binary against the pull request, so what the cache holds and who may write it decide what runs with the check's authority. The head must never write the cache, and a miss must rebuild. Non-goals: admission (TSK-1239) and the verdict jobs.

## Outcome

After this merges, a pull request event whose target has not moved restores the target's codeflow build from a cache instead of rebuilding it, and the head of a pull request can never place anything in that cache.

## Deliverables

- the cache restore and save steps: `.github/workflows/codeflow-policy.yml`
- a test or workflow check that the key and the write rule hold: `scripts/` or the workflow test the repository uses for its workflows

## Acceptance Criteria

- AC-1 Before any change, the builder shall record in the Findings, with run links: the rebuild time at `codeflow-policy.yml:78-89` on recent pull request events; every input that decides the built binary (target SHA, toolchain, features, build environment); and the cache scopes the host offers and which events can write to which scope; evidence: a `## Findings` section, committed before the first code change.
- AC-2 The cache key shall be the exact target SHA plus the toolchain identity, and a cache miss shall rebuild from the target; evidence: the workflow diff and one hosted run each for a hit and a miss. (serves EPC-022 AC-230)
- AC-3 Only a step that runs on the target, in the trusted job and after building from the target, shall write the cache; the pull request's head shall never write or overwrite it, and a restore shall never use a key a head can influence; evidence: the workflow diff, a test or check over the workflow that fails a head-triggered save, and the security review.
- AC-4 A restored binary shall be the one built from the key's target SHA: the job shall verify the identity the binary embeds (source revision) against the target SHA before it runs, and rebuild when they differ; evidence: a test or hosted run with a deliberately wrong cache entry that is refused and rebuilt.
- AC-5 A cross-lineage security review carrying the `cf-security-reviewer` checklist shall cover the change before it is ready, because the cached binary judges every pull request; it shall try a head-written entry, a stale entry, a wrong-toolchain entry and a key a head can influence, with the seat probed live at dispatch; evidence: the review verdict and the pull request body naming the threat each rule closes.
- AC-6 Two consecutive pull request events on one unmoved target shall show the second restoring the build with a shorter job time, and a moved target shall miss and rebuild; evidence: the links and durations of the hosted runs. (journey)
