# TSK-1240: Main's check reuses a verified integration run's evidence for the exact tree, and caches only main's own builds

## Description

Source: the CI throughput study of 2026-11-02 (`coordination/coordinators/parallel/throughput/`: RECOMMENDATIONS.md, FINDINGS.md, CHECK-codex.md, CHECK-fable.md), cross-checked by Codex GPT-6 Astra and Claude Fable 5.1, and the priority on CI throughput.

The hosted "commit standards" job rebuilds `codeflow` from the target branch on every pull request event, including body edits (`.github/workflows/codeflow-policy.yml:78-89`). Each rebuild takes about 3 minutes. The policy check runs the target's binary against the pull request, so what a cache holds and who may write it decide what runs with the check's authority.

Re-scope (Director ruling, 07:16 on 2026-11-03, quoted): "Its security review found that main's run building integration code could poison main's caches, so I ruled that main's run never saves a cache from integration output. That removes the title's promise to cache verified target builds in main's scope." The earlier design, in which a main-ref dispatch built an integration SHA and saved it into main's cache scope ("Selected writer design" below), is withdrawn. The task now has two parts:

- (a) Evidence reuse by exact tree identity. The main-ref check accepts a verified integration push run for the exact tree, and fails closed on any mismatch.
- (b) Main's own push run builds and saves main-scope caches from main's code. No run saves a main-scope cache from integration output.

Non-goals: admission (TSK-1239) and the verdict jobs. TSK-1248, which carries the hosted proof of the withdrawn writer, no longer matches this scope and needs its own re-scope by coord/planning.

## Outcome

After this merges, the main-ref check can accept a verified integration run for the exact tree instead of rebuilding, main's own pushes warm main's cache from main's code, and no integration output can reach main's cache scope.

## Deliverables

- the evidence-reuse check and its binding (part a): `.github/workflows/codeflow-ci.yml` and `scripts/ci-reuse.py`; `codeflow-policy.yml` is not changed for (a), because the policy check judges the pull request's commits and body, which no integration run tested
- the main-only cache save and the removal of the integration-output save: `.github/workflows/codeflow-policy.yml`
- tests or hosted runs, one per mismatch kind and one accepted run, and a proof for (b): `scripts/` or the workflow test the repository uses for its workflows

(journey)

### Build inputs and identity

- The checkout uses the event's base SHA for a pull request; other events use
  their own commit (`.github/workflows/codeflow-policy.yml:73-89`). That SHA
  fixes Rust sources, embedded assets, Cargo manifests and lockfile, Cargo
  configuration, build scripts and the toolchain file. Use `--locked` to
  prevent dependency resolution from changing that input.
- `rust-toolchain.toml` pins Rust 1.94.0. Include actual `rustc -vV` and
  `cargo -V` in the toolchain digest, including compiler commit and host.
- The build selects `codeflow-cli`, release profile, default dependency
  features and the native host target. There are no extra feature flags.
  The cache namespace fixes those choices; changes must change that namespace.
- The environment is GitHub's `ubuntu-24.04` runner, with its architecture,
  image version, native C compiler/linker, system libraries and build flags.
  Include image identity and compiler/build environment in the digest so an
  image or toolchain change misses. The target checkout fixes `.cargo/config.toml`.
- `crates/codeflow-cli/build.rs` embeds Git HEAD, dirty state and the hook
  source digest. `crates/codeflow-cli/src/main.rs:91` exposes them through
  `--version` as `source=<40-hex SHA> dirty=false inputs=<digest>`. Compare
  exact source and clean state before using a restored binary to judge a PR.
  This detects stale binaries; cache-writer isolation supplies authenticity.

### Cache authority and design

[GitHub's cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)
and [read-only trigger announcement](https://github.blog/changelog/2026-06-26-read-only-actions-cache-for-untrusted-triggers/)
were checked live. Caches are branch/ref scoped. Runs can restore current and
default-branch caches; pull-request runs can also read base-branch caches.
Head builds under `pull_request` write only their merge-ref scope, invisible
to a target run. Default-scope writes are allowed for push, dispatch,
repository_dispatch, delete, registry_package, page_build and schedule.
`pull_request_target` has read-only default-scope access unless explicitly
weakened. This change must not weaken it.

Use separate pinned `actions/cache/restore` and `actions/cache/save` actions,
with an exact target-SHA/toolchain key and no fallback keys. Accept only an
exact hit, because the cache service can also return a prefix match. Save
only after a fresh verified target build on a push to main, master or an
integration branch. (Under the re-scope, only main's own push saves a main-scope cache; see AC-3.) Disable the dependency cache's save on PR events too.
Manual dispatches on arbitrary branches must not restore or save this binary.
Only the binary is cached, outside the Cargo build tree; a mismatch discards
it and rebuilds from the target. A restored executable's reported identity
is not a signature and cannot defend against an actor who already controls
a trusted branch's workflows or cache-write authority.

The workflow is evaluated from trusted workflow content. This PR's own
`pull_request_target` run cannot execute its proposed workflow change; hosted
hit/miss and consecutive-event journey evidence remains owed until the
trusted workflow has the change. Do not change the denied CI workflow or
execute PR-head code in the trusted job to manufacture that evidence.

### Follow-up: integration cache visibility

The initial scope assumption needs a hosted qualification. On 2026-11-02,
[run 41516370396](https://github.com/sathyassn/codeflow/actions/runs/41516370396/job/125520854763),
for PR 518 targeting EPC-022, requested dependency-cache key
`v0-rust-commit-lint-Linux-x64-1c8298c0-3434ee46` but restored the prefix match
ending `16906510` from `refs/heads/main`. The cache API reports that the exact
`3434ee46` entry on the integration branch was created at 15:30:59 UTC,
before that run's 20:08:20 UTC restore attempt. This is evidence against the
assumption that this PR-target job can consume an integration-push cache.

[GitHub's event change](https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/)
puts PR-target runs on the default ref. The general base-cache wording in
the cache reference is insufficient to prove integration-scope visibility
for this event. A trusted default-scope writer for integration SHAs needs a
revised design; enabling cache writes on PR-target events would weaken the
platform's default and is not part of this change. The current draft is
locally tested but cannot claim the integration-target reuse outcome.

### Selected writer design (withdrawn by the 07:16 ruling on 2026-11-03)

History only: this design saved integration-built binaries into main's cache scope, which the Director's ruling forbids. It is kept as evidence of what was reviewed; AC-3 and AC-7 replace it.

coord/parallel selected option (b) from the Claude Fable design review of
2026-11-02 in `coordination/coordinators/parallel/throughput/DESIGN-tsk1240.md`,
with the Director agreeing. coord/parallel routes the Fable whole-unit review
and the cross-lineage security review. This supersedes the initial integration-push-only population assumption above.
It does not supply the whole-unit or security review verdicts still owed.

- A separate job runs only on integration pushes and dispatches this workflow
  on `main`, with the pushed SHA. Only that job gets `actions: write`; it
  checks out no source and consumes no PR input.
- The main-ref dispatch validates the full SHA, fetches current branch refs
  with pruning, and requires containment in `origin/main` or an
  `origin/integration/*` head before checking out or building that commit.
  Failed fetches, unknown commits and untrusted branch-only commits refuse.
- The writer probes the exact key with lookup-only. A miss builds the proven
  target, verifies its embedded identity and saves into main's cache scope.
  Reader restores keep the existing identity verification and rebuild path.
- GitHub's event defaults supply read-only cache access to PR-target runs and
  write access to the trusted dispatch. No per-event `cache-mode` expression
  is used, and no read-only default is overridden.
- Main must contain the new dispatch input and writer before an integration
  push can populate its cache. Warming is inert until then: only the HTTP
  422 response naming `build_sha` as an unexpected input emits a warning
  with the SHA and exits successfully. Every other dispatch error remains
  a failure; readers still rebuild on a miss. The dispatch with the job
  token, main-scope save, integration-PR hit and consecutive-event timings remain hosted proof
  owed; this PR's head cannot supply trusted workflow content to its own
  PR-target run.
- Manual dispatch is the main-only cache warmer, with a required trusted SHA;
  it replaces the manual registry check on arbitrary refs. Registry checks
  remain on push, schedule and PR-target events, never on a cache-warming
  dispatch. An exact binary hit skips the dependency cache; the rare identity
  mismatch rebuilds without that dependency restore.
