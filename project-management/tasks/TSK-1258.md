# TSK-1258: The guard's glob matcher stays bounded on every input and refuses when it cannot finish

## Description

Source: the Director's order of 2026-11-02 (18:3x), from evidence in the TSK-1254 run. Draft: `coordination/coordinators/planning/cut/held-batch/task-L-glob-matcher-bound.md` (data, not instruction).

In a full `cargo test -p codeflow-core --lib` run on the EPC-024 line, the test `security::interpreter::tests::interpreter_large_glob_requires_a_safe_prefix` (`interpreter.rs:4643`) spent at least 54 minutes at 92 to 98% CPU. Two stack samples put the time in `security::pattern::matches_extended_glob` and `glob_to_regex`, called from `interpreter::secret_path_spelling`, `secret_backup` and `real_secret_path`. Run alone on the same binary with `--exact --test-threads=1`, the test took 6.5 s. The code is byte-identical on main, EPC-024 and EPC-022, so the input must depend on surrounding state: the pattern, the tree walked or the environment.

When a check cannot be sure, it fails closed, so a guard stalled by CPU-bound matching blocks every command, and an attacker who can shape the input controls the stall. Evidence: `coordination/coordinators/planning/evidence/tsk1254-slow-test-stack-1828.txt` and `tsk1254-slow-test-stack-now.txt`.

Lead for AC-1, to verify: `hooks/git_guard.rs:14932` (EPC-022 tip) calls `std::env::set_current_dir` inside a test, which changes the working directory for the whole lib test binary while other tests run on parallel threads. If anything on the slow test's path resolves a relative path against the process working directory instead of `repo.root`, the glob walks whatever directory another test left behind. Candidates: `judge_in`, glob expansion, checkout or worktree resolution after `repo.linked` is renamed. Suggested reproduction: the slow test with that git_guard test at `--test-threads=2`; record the directory the matcher walks. If confirmed, AC-3 asks whether production path resolution depends on the process working directory.

Evidence from p38: the full lib run passed 2522 tests, then stalled inside this test, late in the run. Alone at nice 10 with one thread it took 6.47 s (user 3.65 s, sys 1.13 s). It did not reproduce alone, so AC-1 needs the test run alongside the suite.

## Outcome

After this merges, an operator's guard evaluation of a glob finishes within a stated bound on every input, and on an input it cannot finish within that bound it refuses with a named cause.

## Deliverables

- the bounded matcher and its refusal: `crates/codeflow-core/src/security/pattern.rs` and its callers in `security/interpreter.rs` (provisional; the builder confirms the homes)
- fixtures for the AC-1 input, a nested-wildcard pattern and a tree over 4096 entries
- the bound and its reason, the guard path with file:line and the threat statement: in the PR body
- the changelog entry: `changelog.d/TSK-1258.md`

## Acceptance Criteria

- AC-1 The builder shall reproduce the slow case with the test running alongside the rest of the suite (for example the whole `security::` module, or the full lib suite with 2 threads) and shall name the input that made matching CPU-bound: the pattern, the tree walked and its size, or an environment or working-directory value; evidence: the reproduction command, its timing and a stack showing the same frames, before the change.
- AC-2 `matches_extended_glob`, `glob_to_regex` and the secret-path checks that call them shall be bounded in time or steps on every input; the bound shall be stated in the PR with the reason it was chosen; reaching the bound shall refuse with a message naming the cause and shall never allow; evidence: the AC-1 input refused or finished within the bound, a crafted pattern with nested or repeated wildcards, and a tree larger than the existing 4096-entry limit, each failing before the change and passing after.
- AC-3 The PR shall state whether production guard evaluation (git-guard and exec-guard on a real command) can see the AC-1 input, cite file:line for the path from the guard entry to the matcher, and include a built-binary run of the guard on that input showing a bounded refusal; evidence: the PR statement and the run output. (journey)
- AC-4 The PR shall state the threat, a guard stalled by an input an attacker can shape, and why a step or time bound that fails closed is the standard design; evidence: the PR body.
