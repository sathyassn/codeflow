# TSK-1258: The guard's glob matcher stays bounded on every input and refuses when it cannot finish

## Description

Source: the Director's order of 2026-11-02 (18:3x), from evidence in the TSK-1254 run. Draft: `coordination/coordinators/planning/cut/held-batch/task-L-glob-matcher-bound.md` (data, not instruction).

In a full `cargo test -p codeflow-core --lib` run on the EPC-024 line, the test `security::interpreter::tests::interpreter_large_glob_requires_a_safe_prefix` (`interpreter.rs:4643`) spent at least 54 minutes at 92 to 98% CPU. Two stack samples put the time in `security::pattern::matches_extended_glob` and `glob_to_regex`, called from `interpreter::secret_path_spelling`, `secret_backup` and `real_secret_path`. Run alone on the same binary with `--exact --test-threads=1`, the test took 6.5 s. The code is byte-identical on main, EPC-024 and EPC-022, so the input must depend on surrounding state: the pattern, the tree walked or the environment.

When a check cannot be sure, it fails closed, so a guard stalled by CPU-bound matching blocks every command, and an attacker who can shape the input controls the stall. Evidence: `coordination/coordinators/planning/evidence/tsk1254-slow-test-stack-1828.txt` and `tsk1254-slow-test-stack-now.txt`.

Amended 2026-11-02 at 20:5x, after the whole-unit review of the held batch at 20:42 (Major). The first draft led with a working-directory race, and that lead is false. `hooks/git_guard.rs:14928-14954` (read at d2752c69d) runs `std::env::set_current_dir` only inside a child process that executes the one exact test `r22_missing_working_directory_refuses`, so no other test sees the changed directory and the stack samples show no working-directory race. The cause is therefore not known, and this task names it from evidence (AC-1) before the bound is chosen.

Cause, measured (AC-1, see "Evidence" below): `security/pattern.rs:89-110` at `c585d8e23` kept a process-wide cache of compiled patterns that stopped admitting entries after 128 (`entries.len() < 128`), so every later pattern compiled again on each call through `glob_to_regex` and `Regex::new`. With that cache full, the slow test spent its time in `Regex::new` (229 of 283 stack samples) and ran past 600 s, against 6 s alone. The pattern, the tree walked and the environment are not the cause: the same test with the cache not full is fast on the same tree.

Evidence from p38: the full lib run passed 2522 tests, then stalled inside this test, late in the run. Alone at nice 10 with one thread it took 6.47 s (user 3.65 s, sys 1.13 s). It did not reproduce alone, so AC-1 needs the test run alongside the suite.

## Outcome

After this merges, an operator's guard evaluation of a glob finishes within a stated bound on every input, and on an input it cannot finish within that bound it refuses with a named cause.

## Guard callers of the secret-path check

The glob bound reaches the guard through `secret_path_spelling_checked`
(`security/interpreter.rs:1474`), which returns the bound's name as the
refusal. There is no yes/no form of it and no boolean form of the matcher
(`match_extended_glob`, `security/pattern.rs`), so a caller cannot read a
bound hit as "no match". Lines are at the review-fix head.

- Carries the name (returns `Result<bool, &str>`): `secret_path_result`
  (`:1222`, `:1229`), `physical_secret` (`:1255`), `unc_store_suffix`
  (`:1392`), `secret_glob` (`:1606`), `real_secret_path` (`:1725`, `:1737`,
  `:1748`), `search_root_matches` (`:2397`), the git pathspec check (`:636`),
  the git read `pattern` judge (`:543`, `git_reads.rs:473`, `:830`),
  `substitution_may_name_secret` (`:682`, `:704`; caller `:776`),
  `relative_may_name_secret` (`:215`, `:233`; caller `:1403`) and
  `relative_names_secret` (`:247`; callers `:538`, `:728`).
- `substitution_root_unknown` also returns `Result<bool, &str>` and its caller
  passes the cause on, so the command-substitution refusal names the bound
  (`oversize_name_after_a_substitution_names_the_bound`). No caller refuses
  without the name, except `glob_intersects` (see the sibling table).
- Negated control: `relative_names_secret` (`:274`, `:275`) returns the cause
  as an error when either spelling cannot be judged, so the negation cannot
  turn it into an allow.
- `hooks/edit_guard.rs`: `covers` (`:412`) returns an error naming the bound,
  and `evaluate` (`:284`) passes it on, so the refusal says
  `cannot check the edit path against the protected paths: a path is longer
  than the glob matcher's bound` and never `enforcement path`.
- `scaffold/state.rs`: `is_ignored` (`:214`) counts an unfinished match as
  ignored, so the opt-out never lapses and `update` never manages the file
  (consumers `scaffold/update.rs:258`, `:348`, `:402`, `:1633`).

## Evidence

AC-1, cause (host: macOS, `nice10.sh`, debug build; base code at `c585d8e23`):

- Slow case, cache not full: `cargo test -p codeflow-core --lib -- --exact
  security::interpreter::tests::interpreter_large_glob_requires_a_safe_prefix
  --test-threads=1` finished in 5.99 s.
- Same test with the cache already full: a temporary line at the start of the
  test called the matcher on 300 distinct patterns first. It ran past 600 s
  and was still running when sampled at 1 h 3 min elapsed (the host paused it
  with SIGSTOP during that time, so the elapsed time includes the pause; the
  figure is a lower bound on a run that never finished).
- Stack sample, one, from that run: 229 of 283 samples in
  `regex::Regex::new` under `pattern::matches_extended_glob`, called from
  `interpreter::secret_path_spelling` and `real_secret_path`, the frames of
  the original stall. File: `/private/tmp/claude/tsk1258-stack.txt`.
- Fail before: `full_glob_cache_does_not_recompile_a_repeated_pattern` failed
  with `recompiled 100 times in 100 calls with a full cache` at `c585d8e23`
  plus the test, and passes at the head.
- After the change, same experiment (the 300-pattern line, then the test):
  4.97 s. An interim version that cloned the compiled regex on each cache hit
  took 46.9 s with user CPU 14 times higher, because a cloned regex builds a
  new search-cache pool; the cache now holds shared `Arc<Regex>` values.
- The 54-minute original stall was not reproduced with the full lib suite;
  the cache-full condition and its frames were.

AC-2, fail before and pass after (each at the head, new tests):

| Case | Test | Before |
|---|---|---|

| oversize pattern or path | `glob_past_the_bound_refuses_with_a_cause` | no bound existed |
| nested wildcards | `nested_wildcards_stay_bounded_and_never_allow` | no bound existed |

A tree over 4096 entries keeps its existing refusal

AC-3, production reach and built-binary journey. Path to the matcher:
`hooks/exec_guard.rs:260` (`evaluate_ruled`) to `secret_path_result`
(`interpreter.rs:1116`) to `secret_path_spelling_checked` (`:1474`) to
`match_extended_glob` (`pattern.rs`); the edit guard reaches it through
`hooks/edit_guard.rs:284` to `covers` (`:412`). Run with
`target/debug/codeflow hook <name> --contract 3` on the head build:

```text
exec-guard  cat /<40000 a>   exit 2  security.secret_reads: cannot verify file operand
            `/a...`: a path is longer than the glob matcher's bound
exec-guard  cat README.md    exit 0
edit-guard  Write <repo>/notes/a/a/...(20000)/x.md   exit 2  git.hook_integrity: cannot inspect
            edit target: cannot check the edit path against the protected paths: a path is
            longer than the glob matcher's bound
edit-guard  Write <repo>/notes.md   exit 0
```

AC-3, which condition production reaches. Two conditions differ:

- The cache-full stall (AC-1) is not reachable from one production guard
  call. Each `codeflow hook exec-guard` or `edit-guard` call is a fresh
  process with an empty cache. The glob working set of one call is 35 read
  patterns plus 44 edit patterns, under the 128-entry cache
  (`one_guard_call_compiles_fewer_globs_than_the_cache_holds` prints it).
  The stall was reproduced only in a long-lived process, the test process, and
  it is the cost every test session paid. A long-lived caller of the matcher
  (a test run, `codeflow update` over many ignore globs) can reach it, so the
  refill fix applies there.
- The oversize input is reachable from a production guard call: any operand
  path or selector an attacker shapes. The production evidence is the bound
  and its named refusal in the built-binary journeys above, not the stall.

AC-5: `r22_missing_working_directory_refuses`
(`hooks/git_guard.rs:14960`) passes at the head (see the PR body for the
run).
