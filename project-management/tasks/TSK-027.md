# TSK-027 — automate release candidates and governed publication

## Description

Automate CodeFlow's complete release-candidate path around its existing
git-cliff and cargo-dist authorities: check per-PR impact, continuously maintain
one candidate PR, prepare and verify consistent release state, then require a
human-authorized exact-source publication action. Reconcile current historical
provenance without moving tags or publishing anything in this task.

## Affected surfaces and interfaces

Repository PR template/checks; `.github/workflows/` release automation;
git-cliff/cargo-dist configuration and supported generated extensions; a small
locally testable preparer/verifier; workspace, lockfile and managed scaffold
stamp agreement; `CHANGELOG.md`, `docs/releasing.md`, the next available release
ADR, release verification/history, and focused release-contract tests. Shipped
consumer skills/assets and their mirrors/manifests belong to TSK-028.

- [ ] PR validation reads the actual base-relative change, requires release
      unit, `none | patch | minor | major`, rationale and evidence, and rejects
      missing intent, conventional-marker contradictions, unassessed watched
      surfaces and missing required migration guidance without pretending to
      infer every semantic break.
- [ ] git-cliff is the sole bump calculator from reviewed landed commit markers;
      the preparer uses an explicit verified release baseline, promotes curated
      notes rather than replacing them with commit subjects, and has explicit
      outcomes for patch/minor/major/mixed/all-none, reverts, integration
      reruns, unknown tags and the staged unpublished-v3 state.
- [ ] Preparation updates the workspace, lockfile and deliberately coupled
      scaffold/version stamps through a callable supported regeneration/update
      procedure, is idempotent, preserves reviewed prose and unrelated version
      domains, and detects drift instead of blind text replacement.
- [ ] A pinned workflow automatically creates or updates one release-candidate
      PR after relevant main changes, serializes concurrent runs and invalidates
      stale review when the candidate changes; retries converge without duplicate
      bumps or release candidates.
- [ ] Publication can act only on the exact reviewed candidate source and a
      configured human approval boundary, revalidates versions, migration,
      source/tag identity and expected artifacts, and refuses stale approval,
      wrong commits, mismatched existing tags/assets, missing credentials,
      partial uploads and conflicting concurrent attempts.
- [ ] cargo-dist remains the sole artifact publisher and is extended only via
      supported configuration/generation paths; mocked hosting and disposable
      repository tests cover failure, retry and idempotency without performing a
      real tag, upload or release.
- [ ] The v2.1 published-source/tag discrepancy and v3 candidate status are
      recorded with the current reachable tag as git-cliff's calculation
      baseline and the published source/archive checksum as distinct immutable
      provenance; the expected first candidate is 3.0.0, and no historical tag
      is moved or silently equated with published source.
- [ ] Post-merge publication authorization proves the candidate-approved head
      association and tree equality before acting; a moving branch name or
      release-PR label alone is insufficient authority.
- [ ] Focused release contracts, workflow/config validation, local dry runs,
      repository gates and exact-diff native Fable review pass; documentation
      states what was not exercised and makes no publication claim.

## Execution contract

Plan v1 is grounded in the independently settled release-management proposal;
the exact records still require Codex-primary and native-Claude review before
landing. The root Codex host is responsible primary; a Sol/high worker executes
this bounded node under its inspection and acceptance; native Fable performs
independent cross-lineage source review. Actual selector/effort and available
usage evidence are recorded at execution. Target:
`integration/EPC-010-release-automation`. One writer owns this task's files and
one heavy release build/test runs at a time. Any publication, tag mutation,
credential provisioning, destructive historical repair or change to the task
graph/safety boundary stops work for explicit authority and Plan v2.

Verification uses finite edge/error fixtures, idempotent reruns, mocked hosting
responses and architecture/release-contract checks; no new generative or
mutation framework is selected. A controlled non-publishing dry run is the
highest authorized external effect.
