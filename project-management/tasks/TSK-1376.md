# TSK-1376: A project can raise the guard readers' bounds

## Description

The operator's rule is that stricter checks stay configurable and security floors stay. TSK-1299 gives each security limit a floor and a ceiling a project can raise it to, and lands the guard readers' bounds as fixed entries. This task makes twelve of those bounds settable through the policy, the same way as `limits.guard_glob_entry_limit`: nine from TSK-1299's registry and the deletion reader, and the three TSK-1374 adds to the deletion reader and the shell lexer. A project can raise them and cannot lower them. Building waits for PR 695 (TSK-1299) to land on this line and for TSK-1374 (PR 701, into main) to reach this line through a sync from main; the builder adds the TSK-1374 edge to `depends_on` in this task's own pull request once that record is on the line. Non-goal: changing any default value.

## Outcome

After this merges, a project maintainer can raise any of the guard readers' twelve bounds up to a stated ceiling through the policy, and cannot lower them below today's values.

## Deliverables

- the twelve registry entries changed from fixed to security (the launch-wrapper count enters the registry first), with policy keys named by the key placement rule: `crates/codeflow-limits/src/`
- the readers take their bounds from the judging policy at run time: `crates/codeflow-core/src/security/`
- the generated limits page and the policy schema entries: `docs/limits.md`, `docs/policy-reference.md`
- release note: `changelog.d/TSK-1376.md`

## Acceptance Criteria

- AC-1 Before any change, the builder shall size each ceiling from measured stack use, guard memory and the guard deadline with all twelve bounds raised together, and state the basis in `## Findings`; the Findings shall also list every other fixed bound in the guard readers and the shell lexer with the reason it stays fixed; evidence: the Findings table and the measurements.
- AC-2 Each of the twelve bounds (`DELETION_READER_DEPTH`, `DELETION_READER_VALUES`, `DELETION_READER_VARIANTS`, `DELETION_READER_LOOP_PASSES`, `DELETION_GLOB_LIMIT`, `GUARD_SCRIPT_READINGS`, the deletion reader's launch-wrapper count, `STARTUP_LINK_LIMIT`, `ARGUMENT_WALK_LIMIT`, and TSK-1374's `MAX_NESTING`, `MAX_EXPANSION_DEPTH` and `MAX_BRACE_GROUPS`) shall default to its value today, with a floor equal to that value and the ceiling from AC-1, and an absent key shall keep the default; evidence: the registry and a test per key, set and absent.
- AC-3 When a value is below the floor, past the ceiling or of the wrong type, the policy shall refuse naming the key and its bounds; evidence: one test per case.
- AC-4 With all twelve bounds at their ceilings together, a guard run on the worst input the builder can construct shall finish or refuse inside the guard deadline, shall not exhaust its stack, and shall stay inside a memory budget the builder states in `## Findings`; evidence: the test at the ceilings.
- AC-5 The readers shall take these values only from the judging policy, never from the command they read; evidence: a test.
- AC-6 In a scratch project with the installed build, a maintainer raises one bound to its ceiling, is refused one step past it and one step below the floor with the key named, and finds the key on the generated limits page; evidence: the journey output. (journey)
- AC-7 A changelog entry shall name the keys; evidence: `changelog.d/TSK-1376.md`.
- AC-8 When the session's working tree holds an uncommitted or staged change to the project policy file, the guards shall read these bounds from the policy on the judged commit, so a session cannot raise a bound by editing the file before a hook runs; evidence: a test where a dirty policy file sets a bound to its ceiling and the guard keeps the committed value.
