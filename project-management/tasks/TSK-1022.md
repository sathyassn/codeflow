# TSK-1022: Deleting a configured secret store is refused

## Description

Source: the Claude security review of PR 346 (TSK-1002), finding S10, saved as `target/review-TSK-1002-security-02.md` in the `guard-bypass-classes` worktree. Severity medium, CWE-284, OWASP A01, confirmed by the reviewer. The gap predates PR 346: the line base allows the same commands.

Evidence: the guards allow `rm -rf ~/.ssh`, `echo ~/.ssh | xargs rm -rf` and `unlink ~/.ssh/id_rsa`. Home secret stores are protected from reads and writes but not from deletion, so an agent session can destroy keys and credentials the operator cannot recreate.

Outcome: **a command that deletes a configured secret store, or a file inside one, gets a refusal that names the store and its remedy, in every deleting spelling the guards read, while ordinary deletions stay allowed.**

Order: build this on top of TSK-1002 (PR 346), which reshapes the same guard code. TSK-1002 landed in PR 346 on 2026-10-30 and the `depends_on` edge is recorded.

Remedy direction from the review: a deletion rule for the configured secret stores under `security.dangerous_commands` or an operator-owned level. The builder settles which of the two with evidence and records the choice.

Non-goal: a deletion built at run time that no guard can read stays a named residual, as the other guard rules state.

## Deliverables

## Acceptance Criteria

- AC-1 When a command deletes a configured secret store or a file inside one, the guards shall refuse it across a command-family matrix built on the existing deletion mechanisms (`security/deletion.rs`, `dangerous.rs`, `git_guard.rs`): plain `rm FILE` and `rm -f`; every recursive flag spelling (`-r`, `-R`, `-rf`, `--recursive`, split and reordered flags); `rmdir`; `unlink`; `shred` and `srm`; `find -delete` and `find -exec rm`; `xargs rm`; `parallel`; destructive `rsync` (`--delete`, `--remove-source-files`); and each launcher carrying any of these (`env`, `sh -c`, `bash -c`, `eval`, `command`, `nohup`, `exec`, `xargs`); for every store in the configured list; evidence: a matrix test of family by launcher by store through the real hook, each refusal failing before the change (`rm -rf ~/.ssh`, `echo ~/.ssh | xargs rm -rf` and `unlink ~/.ssh/id_rsa` among them).
- AC-2 When a command moves a configured secret store away (`mv ~/.ssh x`), truncates a file in one (`: > ~/.ssh/id_rsa`, `truncate -s 0`), or runs `git clean` over one, the guards shall refuse it, or the record shall state per form why it is excluded, with the reason in the PR body; evidence: a test per form, or the stated exclusion reviewed.
- AC-3 When the target is spelled by any equivalent path, the guards shall give the same verdict: `~`, `$HOME`, `${HOME}`, an absolute path, a relative path after `cd`, a variable the line assigned, a symbolic link to the store, a glob that can match it, and deleting a parent directory of the store; a target the guards cannot resolve shall refuse (fail closed); evidence: a test per spelling, each failing before the change, and an unresolved-target case that refuses.
- AC-4 When the guards refuse such a deletion, the message shall name the store and the remedy (the sanctioned way for the operator to delete it); evidence: a test asserting the rule name, the store and the remedy text.
- AC-5 When a command deletes an ordinary path, the guards shall keep allowing it in both outcomes where it is written without a run-time word: project temp files (`rm -rf ./target`) and harmless globs (`rm ./*.log`); the controls written with a leading `~`, a project temp file (`rm -rf ~/scratch/x`), a near-name (`rm ~/.sshx-notes`) and unprotected siblings of protected entries (`rm ~/.cargo/config.toml` next to the protected `~/.cargo/credentials*`; the builder picks each sibling control from `crates/codeflow-core/src/security/actions.json` and checks it is not listed), shall be allowed by git-guard and by exec-guard under `security.text_guard: relaxed`, and under the strict default exec-guard shall refuse them under `security.text_guard`; the SSH entries `~/.ssh/id_rsa.pub` and `~/.ssh/known_hosts` are protected (`actions.json:636`, `:638`) and stay in the AC-1 refusal matrix, never in the controls; evidence: allowed-control tests beside the refusals, the `~` controls under both outcomes.
  - Amended 2026-10-30: earlier text "the guards shall keep allowing it", for every control including the `~` forms. Reason: TSK-397 option 2 (PR 331) makes the strict text rule the default, and PR 331's binary at `c53591264` refuses `rm -rf ~/scratch/x`, `rm ~/.sshx-notes` and `rm ~/.cargo/config.toml` in exec-guard under `security.text_guard`; `rm -rf ./target` and `rm ./*.log` pass in both outcomes.
- AC-6 Boundary with TSK-395: TSK-395 AC-1 and AC-2 own writes, copies, moves and recursive deletes of the harness settings folders (`~/.claude`, `~/.codex`, `~/.grok`); this task owns the home credential and secret stores in the configured list and adds no rule for those three folders; evidence: the builder reads both lists, records any store named in both, and the matrix test names which task owns each store.
- AC-7 (journey) The installed Claude, Codex and Grok hook commands shall refuse the planted deletions without running them; evidence: a refusal journey replaying each installed hook.
- AC-8 When a deletion form could reach a configured secret store but the guard does not model it (an unsupported option, an unknown launcher, or an input transformation it cannot read, as at `security/deletion.rs:4464`), the guards shall refuse it as cannot-verify and say so; this is separate from the opaque program-internals residual (a program that deletes on its own), which stays a named residual; evidence: tests per unmodeled option, launcher and input transformation, each refusing, and a positive control with a modeled equivalent (plain `rm -rf ./target`) that still passes; a deletion is allowed only when the guard can prove every effective target is ordinary, so a form with an input it does not model (`xargs --arg-file=paths rm -rf ./target` also takes targets from `paths`) refuses even when its visible operand looks ordinary.

### Rule and verification choices

Use the existing `security.dangerous_commands` non-relaxable floor for
irrecoverable store destruction. `exec_guard.rs:59-70` and `:171-184` already
make that level unconditional; no new policy key, exception or weaker level
is needed. A refusal identifies the configured store and directs the human
to perform an intentional deletion outside the agent session, rather than
suggesting an override environment variable or disabling a hook.

The store-deletion integration must run even when the command is certified
as prose; truncation is destructive although the producer is harmless.
The reader remains bounded, and unsupported deletion options, launchers,
input transformations and unresolved targets are cannot-verify refusals.
The existing opaque-program residual is stated separately.
