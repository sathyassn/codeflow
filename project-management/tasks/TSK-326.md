# TSK-326: Guards judge git operands and environment supplied as data

## Description

Both guards can be handed a git ref, a remote, a program or an environment
assignment that comes from data they cannot read, and they allow it. The
TSK-283 security review (PR 195, `target/security-review-TSK-283-03.md` in
its worktree) confirmed these on the installed 3.1.0 build and on the
TSK-283 head, with git-guard and exec-guard both allowing:

```text
V=$(cat refs); git push origin "$V"
V=$(cat cmdfile); $V push origin HEAD:main
xargs git push origin < refs
V=$(cat envpush3); env "$V" git push origin      # a dry run reached main
xargs -I{} env {} git push origin < envpush2
```

The guards resolve a value only when its text is in the command. A variable
set from a command substitution, `read` or any other file or process data
has no text to resolve, so the push, alias, transport and release decisions
see an empty or unknown operand and pass. Severity: high. Branch protection
and the pre-push hook still stop a push to a protected ref, so this is a
missing in-session guard and not a way past the remote floor.

The remedy: a variable assigned from a command substitution, `read` or
other data, and every `xargs`, `-I` or `{}` operand, is unresolved
wherever it reaches a git ref, a remote operand, an environment assignment
or a program position. The guard refuses, naming the rule and the
sanctioned path (assign the value in the command, or run the command
without data-supplied operands), before the push, alias, transport and
release decisions. The same task closes a second, low gap found in the
TSK-283 round 4 review (`target/security-review-TSK-283-04.md`): a
bracket-arithmetic ref such as `git push origin HEAD:v$[2]` passes
git-guard on 3.1.0 and on the TSK-283 head when `v2` is protected, while
`$((2))` is refused. It has the same cause, an operand the guard does not
resolve as the shell will, and it lives in the same ref-operand resolution,
so it is one criterion here and not a task of its own (the sizing rule in
`.codeflow/rules/workflow-discipline.md` "Planning" splits only for
separate shippable value, a pinned contract, an operator decision, size or
a risk boundary, and none applies: it is digits only and cannot spell
`main`).

Non-goals: judging the content of a data file, and weakening the
deterministic floor, which stays pre-push and branch protection. The
policy reference must say that configuration or refs supplied as data
through variables or `xargs` are not judged except by this refusal (the
docs nit of the TSK-283 round 3 review).

## Acceptance Criteria

- AC-1 When a variable assigned from a command substitution, `read` or
  other data reaches a git ref, a remote operand, an environment
  assignment or the program position, git-guard and exec-guard shall
  refuse the command as unresolved; evidence: unit tests for `V=$(cat
  refs); git push origin "$V"`, `V=$(cat cmdfile); $V push origin
  HEAD:main` and `V=$(cat envpush3); env "$V" git push origin`, each
  failing before the change and passing after. (serves EPC-022 AC-23)
- AC-2 When `xargs`, `xargs -I` or a `{}` placeholder supplies a git ref,
  remote, environment assignment or program, both guards shall refuse
  it as unresolved; evidence: unit tests for `xargs git push origin <
  refs` and `xargs -I{} env {} git push origin < envpush2`. (serves
  EPC-022 AC-23)
- AC-3 The unresolved judgment shall apply before the push, alias,
  transport and release decisions, so a data-supplied operand cannot
  select a path those decisions allow; evidence: a table in the pull
  request that names, for each decision site, the file:line and the test.
  (serves EPC-022 AC-23)
- AC-4 When a ref operand uses bracket arithmetic such as `HEAD:v$[2]`,
  git-guard shall resolve it as it resolves `$((2))`, or refuse it as
  unresolved, so a protected ref `v2` is refused; evidence: a unit test
  that fails on the 3.1.0 behavior (`git push origin HEAD:v$[2]` with
  `v2` protected passes) and passes after, with `$((2))` as the control.
  (serves EPC-022 AC-23)
- AC-5 Plain commands with operands in their own text, quoted variables
  assigned from literals and data pipelines that never reach a git operand
  shall still pass; evidence: an allow-control list in the guard tests,
  and the three refusals the TSK-283 review accepted by design left
  as they are.
- AC-6 The policy reference shall say that refs, remotes and environment
  supplied as data through variables or `xargs` are refused as unresolved,
  and that pre-push and branch protection remain the floors; evidence: the
  `docs/policy-reference.md` diff.
- AC-7 When a fresh project with the installed build wires only exec-guard
  and then only git-guard, each of the five forms above shall be refused
  with the rule and the sanctioned path, and a literal `git push origin
  HEAD` shall pass (journey); evidence: a CLI journey for each wiring,
  with the output. (serves EPC-022 AC-23)
