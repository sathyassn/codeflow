# TSK-326: Guards judge git operands and environment supplied as data

## Description

Both guards can be handed a git ref, a remote, a program or an environment
assignment that comes from data they cannot read, and they allow it. The
TSK-283 security review (PR 195, `target/security-review-TSK-283-03.md` in
its worktree) confirmed these on the installed 3.1.0 build and on the
TSK-283 head, with git-guard and exec-guard both allowing:

```text
V=$(cat refs); git push origin "$V"
V=$(cat cmdfile); $V push origin HEAD:main
xargs git push origin < refs
V=$(cat envpush3); env "$V" git push origin      # a dry run reached main
xargs -I{} env {} git push origin < envpush2
```

The guards resolve a value only when its text is in the command. A variable
set from a command substitution, `read` or any other file or process data
has no text to resolve, so the push, alias, transport and release decisions
see an empty or unknown operand and pass. Severity: high. Branch protection
and the pre-push hook still stop a push to a protected ref, so this is a
missing in-session guard and not a way past the remote floor.

The remedy: a variable assigned from a command substitution, `read` or
other data, and every `xargs`, `-I` or `{}` operand, is unresolved
wherever it reaches a git ref, a remote operand, an environment assignment
or a program position. The guard refuses, naming the rule and the
sanctioned path (assign the value in the command, or run the command
without data-supplied operands), before the push, alias, transport and
release decisions. The same task closes a second, low gap found in the
TSK-283 round 4 review (`target/security-review-TSK-283-04.md`): a
bracket-arithmetic ref such as `git push origin HEAD:v$[2]` passes
git-guard on 3.1.0 and on the TSK-283 head when `v2` is protected, while
`$((2))` is refused. It has the same cause, an operand the guard does not
resolve as the shell will, and it lives in the same ref-operand resolution,
so it is one criterion here and not a task of its own (the sizing rule in
`.codeflow/rules/workflow-discipline.md` "Planning" splits only for
separate shippable value, a pinned contract, an operator decision, size or
a risk boundary, and none applies: it is digits only and cannot spell
`main`).

Non-goals: judging the content of a data file, and weakening the
deterministic floor, which stays pre-push and branch protection. The
policy reference must say that configuration or refs supplied as data
through variables or `xargs` are not judged except by this refusal (the
docs nit of the TSK-283 round 3 review).

## Acceptance Criteria

- AC-1 When a variable assigned from a command substitution, `read` or
  other data reaches a git ref, a remote operand, an environment
  assignment or the program position, git-guard and exec-guard shall
  refuse the command as unresolved; evidence: unit tests for `V=$(cat
  refs); git push origin "$V"`, `V=$(cat cmdfile); $V push origin
  HEAD:main` and `V=$(cat envpush3); env "$V" git push origin`, each
  failing before the change and passing after. (serves EPC-022 AC-23)
- AC-2 When `xargs`, `xargs -I` or a `{}` placeholder supplies a git ref,
  remote, environment assignment or program, both guards shall refuse
  it as unresolved; evidence: unit tests for `xargs git push origin <
  refs` and `xargs -I{} env {} git push origin < envpush2`. (serves
  EPC-022 AC-23)
- AC-3 The unresolved judgment shall apply before the push, alias,
  transport and release decisions, so a data-supplied operand cannot
  select a path those decisions allow; evidence: a table in the pull
  request that names, for each decision site, the file:line and the test.
  (serves EPC-022 AC-23)
- AC-4 When a ref operand uses bracket arithmetic such as `HEAD:v$[2]`,
  git-guard shall resolve it as it resolves `$((2))` and judge the
  resolved ref against policy, so a protected `v2` is refused and an
  unprotected resolved ref (`v3`) passes; if it cannot resolve the
  expression it shall refuse it as unresolved. The scope is git-guard's
  ref-operand resolution; exec-guard's data-operand refusal of AC-1 and
  AC-2 is unchanged. Evidence: a unit test that fails on the 3.1.0 behavior
  (`git push origin HEAD:v$[2]` with `v2` protected passes) and passes
  after, with `$((2))` as the refused control and the unprotected resolved
  ref as the allowed control. (serves EPC-022 AC-23)
- AC-5 Plain commands with operands in their own text, quoted variables
  assigned from literals and data pipelines that never reach a git operand
  shall still pass; evidence: an allow-control list in the guard tests,
  and the three refusals the TSK-283 review accepted by design left
  as they are.
- AC-6 The policy reference shall say that refs, remotes and environment
  supplied as data through variables or `xargs` are refused as unresolved,
  and that pre-push and branch protection remain the floors; evidence: the
  `docs/policy-reference.md` diff.
- AC-7 (journey) When a fresh project with the installed build wires only exec-guard
  and then only git-guard, each of the five forms above shall be refused
  with the rule and the sanctioned path, and a literal `git push origin
  HEAD` shall pass; evidence: a CLI journey for each wiring,
  with the output. (serves EPC-022 AC-23)
  - Amended 2026-11-02: the journey tag moved to open the criterion, where the check counts it; the wording and the serves tag are unchanged.

## Findings

Judged on the line's built binary (`c35cf003f`) before any product change,
in a scratch repository with `main` and `v2` protected, under the relaxed
text rule and then with hook integrity off. "Incidental" means a refusal
from another check (the Git runner reader under `git.hook_integrity`, or a
secret-read check of the file a substitution reads), which goes away when
that rule is relaxed.

| Form | git-guard on the line | exec-guard on the line |
|---|---|---|
| variable from a substitution as a push ref | incidental only | incidental only |
| variable from a substitution as the program | allowed | incidental only |
| `xargs` appending refs to a push | incidental only | incidental only |
| variable from a substitution as an `env` assignment | allowed | incidental only |
| `xargs -I{}` placeholder as an `env` assignment | allowed | incidental only |
| variable from `read` as a push ref | incidental only | incidental only |
| literal variable naming a protected branch | allowed | not its decision |
| literal variable naming a tag | not its decision | allowed |
| bracket arithmetic `$[2]` in a ref, `v2` protected | incidental only | incidental only |
| bracket arithmetic `$[3]`, unprotected | refused (incidental) | refused (incidental) |

Sibling sweep of the other guard readers, judged the same way:

| Sibling | On the line | In this task |
|---|---|---|
| `parallel` input (`::::`, `--arg-file`, standard input) | allowed by both | refused as unresolved by both |
| `fd -x`, `--exec`, `-X`, `--exec-batch` input | allowed by both | refused as unresolved by both |
| git child of `watch`, `flock`, `script -c` with a data variable | allowed by both | refused as unresolved by both |
| a quoted `$` in a force-deleted branch name | read as a variable by the discard check | read as the name; an unquoted `$b` stays data |
| a shell `-c` or `eval` a supplier runs, its script taking the input (`find main -exec sh -c 'git push origin {}' \;`, `fd -x`, `xargs -I{}`, `parallel`, `"$1"`) | allowed by git-guard; the `find` and `fd` forms by both | refused as unresolved by both; input spliced into the script, and a script the guard cannot read, refuse too |
| `-m` on `git branch`, a rename whose names are operands (`git branch -fm "$V"`) | skipped as a message | judged; `-m` is skipped only on `commit`, `tag`, `merge`, `notes add` and `append`, and a saving `stash` |
| an unquoted brace list or sequence in a judged git word (`git push origin {feat/x,main}`) | read as one word | refused as unresolved by both; a quoted or escaped brace stays text |
| a shell script run by a supplier with substituted input from the line, through any replacement string or input separator, one an option of `parallel` sets included | read with the input outside the script, or an option's replacement string or separator not read | refused as unresolved by both; `parallel`'s options are read as `parallel` reads them; a template with no shell is judged with the whole input as written, and a replacement string for part of the input counts as supplied |
| ref writers outside the subcommands git-guard judges | not judged | out of scope, subcommand coverage: tracked in the EPC-029 follow-up amendment |
| a further shell-wrapper class | not unwrapped | out of scope: a further shell-wrapper class is tracked for follow-up |
| one shell quoting form | over-refused as a variable | unchanged, the safe side: tracked in the EPC-029 follow-up amendment |
| `$((N))` in a ref | refused | unchanged: refused, which is the safe side |

AC-5's "three refusals the TSK-283 review accepted by design": no review
file under `coordination/coordinators/*/reviews/` names them, and the
TSK-283 record lists none by that name. PR 195's body lists the accepted
over-refusals on a line with a configuration-dependent push: non-Git data
naming a configuration variable, a parameter read with an operator, an
unresolved assignment destination and a command-local prefix on a non-Git
command. Each still refuses in both guards, as on the line
(`tsk283_accepted_over_refusals_still_refuse`).

The cross-lineage review of 42d330c2b (Grok, PR 718) found the shell
script, `git branch -m` and brace list rows; this task fixes them. Its nit
N3, a panic in `expand_word` on a `$` with no name, does not occur: the
name slice `(i+1)..=i` is an empty range, and the word refuses as
unresolved, which `a_dollar_with_no_name_is_unresolved` now pins.
Follow-ups for nits N2 and N4 are tracked in the EPC-029 follow-up amendment.

Floors for ref writers outside the judged list were checked at
b0d8fa34e's binary in a scratch project. The reference-transaction,
pre-commit and pre-push hooks stopped the writes to protected `main` tried,
apart from two ref-write classes outside this task's scope, which are
tracked in the EPC-029 follow-up amendment.
