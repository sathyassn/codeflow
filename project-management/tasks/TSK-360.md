# TSK-360: The repository contract states builder evidence and the hosted green landing rule

## Description

Source: the operator's request of 2026-10-17 to make the gates fast while
the right checks run locally and in hosted CI, the decisions taken on it
the same day, and the hosted-red diagnosis of 2026-10-17. Amended after the
Codex review of PR 226 (finding F4 and a minor on the builder rule).

Two rules this repository works by are not written where builders and the
primary read them:

- **Builder evidence.** Builders no longer run routine whole essential or
  full gates. Their evidence is targeted tests plus the quick gate (the
  pre-push quick run counts for the same tree), as the managed block of
  `AGENTS.md` already states in its "build" row; one full gate runs on each
  landing candidate. Targeted checks that exist only in a heavier mode
  (`codeflow test --mode essential --only <target>` and the like, as
  `.codeflow/rules/workflow-discipline.md` already requires) and
  measurement trials a task authorizes stay allowed. The project section of
  `AGENTS.md` still asks for `codeflow test --mode essential` on every
  `crates/**` change.
- **Hosted green before the next landing.** The line was red on hosted
  Linux and Windows from 2026-10-12 while later pull requests landed.

The hosted landing rule, as written by this task:

- Ordinary landings on an integration line wait until the line's current
  tip has green `codeflow gates` and `windows` verdicts.
- Recovery exception: while the tip is red or lacks evidence, the only
  landings allowed are the repair of the failure and work needed to
  produce the evidence (for example a workflow fix without which the jobs
  cannot run). After such a landing, ordinary landings still wait for green
  verdicts on the new tip.
- Pending (a run still in progress) is not green: wait for it.
- Cancelled, skipped (other than a reuse that names a green run, TSK-359),
  and missing (no run for the tip) are not green: start or rerun the run.
- Stale (a green verdict for an earlier tip) is not evidence for the
  current tip.
- A failure shown to come from runner infrastructure is rerun, never read
  as a pass; a failure shown to be unrelated to the next landing still
  blocks it until repaired, under the recovery exception.
- Once TSK-358 lands, a pull request into a line also needs its own green
  `codeflow gates` and `windows` verdicts at the exact head that lands;
  TSK-358 updates that sentence when it lands.

The managed block between the codeflow markers is maintained by
`codeflow update`, and the files under `.codeflow/rules/` are managed
scaffold destinations, so both rules go in the project section of
`AGENTS.md`, below the markers.

Authority: the operator decided on 2026-10-17 that hosted gates run on
ready pull requests and that a line lands only on hosted green, from the
request to make sure the right checks run locally and in CI. Protection:
no landing without Linux and Windows evidence, and no landing on top of an
unproven or failed hosted run. Cost: a check of the line's latest hosted
run before each landing, and a wait while a run is in progress (about 31
minutes from run start to finish in the failed-run sample of 2026-10-17).

Non-goals: the managed block, shipped rules, and the shipped pipeline
default (TSK-370). Product surface: this repository's contract only.
