# TSK-265: CodeFlow's own CI finishes in about half the time

## Description

CodeFlow's own CI run on a pull request took 32 minutes on PR 126 (run 38094269415). The critical path was a Windows test partition that waited 9 minutes for a runner, because the full push run on main from the previous merge was running at the same time; 18 minutes in that partition (3 compiling, 15 testing, with partitions ranging 9 to 15 minutes of tests); then 4.5 minutes in `windows journeys`, nearly all of it the release-script journey (`scripts/test_release.py EntryIdentityTests TypedRepairTests`), which needs no partition results. This task cuts that time without dropping coverage: run that journey beside the partitions, build the Windows test binaries once and run every partition from that build, balance partitions by measured duration, and let a push to main reuse the verdict of a pull request run that already tested the exact same tree (operator decision, 2026-10-11). Scope is this repository's own `.github/workflows/` and the scripts and contract tests that pin them. Non-goals: paid larger runners (not approved), removing or weakening any check, and changing the adopter CI templates in `assets/base/ci/` unless a parity check requires it.

## Deliverables

- Workflow changes: `.github/workflows/codeflow-ci.yml`
- The push-reuse decision and its tests: `scripts/` (a new script beside the existing CI scripts) and its unit tests
- Journey gate changes, if any: `scripts/journey-gate.py`, `scripts/test_journey_gate.py`
- Contract pins: `scripts/gate-parity.py`, `scripts/test_gate_contracts.py`, `crates/codeflow-cli/tests/ci_pin.rs` where they describe these jobs
- Changelog fragment: `changelog.d/TSK-265.md`

## Acceptance Criteria

- AC-1 When the Windows jobs run, the release-script journey runs in a job that starts with the test partitions, and the job that waits for the partitions only reads their results. Evidence: the workflow and its contract pin, and a hosted run where the post-partition journey job takes under one minute of gate work.
- AC-2 When the Windows tests run, the workspace test binaries are built once into a nextest archive and every partition runs from that archive without compiling, and the same set of tests runs as before. Evidence: the workflow and its pin, and a hosted run whose partitions show no compile step and whose combined test count equals the base run's.
- AC-3 When the Windows partitions run, the tests are split by measured duration so that no partition's test time exceeds the mean by more than 25 percent on a hosted run. Evidence: the split's source (the measured durations and how they are assigned) and the per-partition test times of a hosted run.
- AC-4 When a push to main carries the exact tree of a pull request head whose `codeflow-ci` pull request run concluded success in every job, the push run reuses that verdict: the gate and Windows jobs are skipped and the `codeflow gates` and `windows` verdicts pass and name the reused run. Every other push runs every job. The match is decided from git tree ids and the run's recorded head commit and workflow file, never from a branch name or text a pull request controls. Evidence: unit tests of the decision against fixtures (exact match; tree differs; run failed, cancelled, missing, from another workflow or another event; a job skipped), and the first push run on main after this lands.
- AC-5 (journey) When this pull request's final head is pushed, the `codeflow-ci` required checks pass; on a hosted run the `windows` verdict finishes within 16 minutes of the run start and the post-partition journey job does under one minute of gate work. The whole-run wall time, now bounded by the Linux coverage part this task does not change, is recorded beside the 32-minute base and is not a new bar. Evidence: the hosted run id with the `windows` verdict time, the journeys job time and the coverage time.
- AC-6 When an adopter runs `codeflow update`, nothing changes for them unless a shipped template changed, and `codeflow update` stays a no-op on this repository. Evidence: `repository_update_noop`, `manifest_consistency`, `ci_pin`, and gate-parity on the tree.
