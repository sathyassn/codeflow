# TSK-331: Essential gate runs are serialized like full runs

## Description

`codeflow test` takes the machine gate lock only in full mode:
`guard_gate` returns before the lock for any other mode
(`crates/codeflow-cli/src/cmd/test.rs:198`), and the lock itself is
`full-gate.lock` under the CodeFlow home and under the git common directory
(`crates/codeflow-core/src/testing/gate_guard.rs:54`, `:215`). Essential
runs from several worktrees on one machine therefore overlap, with each
other and with a full gate, and their targets time each other out, the
failure TSK-134 fixed for full runs. In this repository, essential runs the
workspace tests, clippy and docs (15 essential targets in
`.codeflow/test-config.json`).

The outcome is that on one machine an essential or full run never overlaps
another essential or full run: the second run refuses at once, naming the
holder, its mode and its directory. Quick runs are unaffected.

Decisions recorded here:

- **One shared lock.** Essential takes the same lock files as full; there
  is no second lock and no per-mode policy table. The protection sought is
  one heavy gate at a time, and essential beside full times out just as two
  full runs do. Keeping the files also means a 3.1 binary running a full
  gate and this build running an essential one still exclude each other,
  and the shipped sandbox presets already allow `~/.codeflow/locks`. The
  file keeps the name `full-gate.lock`; the docs say it serves both modes.
- **Refuse, do not queue.** The second run refuses as a second full gate
  does today, with the holder's mode added to the message. Waiting is not
  added here.
- **The lock follows the requested mode.** `--mode essential` and
  `--mode full` take it. `--mode quick` never takes it, including in a
  project whose test config defines no `quick` targets, where quick runs
  the essential targets (`crates/codeflow-core/src/testing/gate.rs:735`).
  The pre-push gate runs quick through `run_gate_exact`
  (`crates/codeflow-core/src/hooks/git_hook.rs:1280`) and is unchanged. The
  reason is that quick is the builder's and pre-push's fast loop and must
  never wait on a gate in another worktree.

Non-goals: queueing or waiting for the lock, changing how targets run
inside one gate, and locking quick runs.

## Deliverables

- the lock for essential runs: `crates/codeflow-cli/src/cmd/test.rs` (`guard_gate`) and `crates/codeflow-core/src/testing/gate_guard.rs` (holder record and message)
- tests: `crates/codeflow-cli/tests/test_gate_cli.rs` and the unit tests in `gate_guard.rs`
- docs: the gate lock description in `docs/troubleshooting.md` (the `permissions` row and the refusal) and the CLI help for `--mode`
- release note: `changelog.d/TSK-331.md`

## Acceptance Criteria

- AC-1 While an essential or full run holds the gate lock, a second
  `codeflow test --mode essential` or `--mode full` on the same machine,
  from another worktree or another repository, shall refuse before any
  target starts, naming the holder's process, mode and directory; evidence:
  CLI tests for each of the four mode pairs. (serves EPC-022 AC-28)
- AC-2 `codeflow test --mode quick` shall take no gate lock and run while
  an essential or full run holds it, including in a project whose test
  config defines only `essential` and `full` targets, and the pre-push
  gate shall be unchanged; evidence: a CLI test with the lock held, and the
  existing pre-push tests passing unchanged. (serves EPC-022 AC-28)
- AC-3 An essential run shall use the same lock files as a full run, and a
  holder record written by this build shall still be read by the 3.1
  holder description (one added key only); evidence: a test that a full
  run refuses while an essential run holds the lock, and a test that parses
  the new record with the old reader's rules.
- AC-4 An essential run killed while it holds the lock, or whose target
  process group is still alive, shall be handled as a killed full gate is
  today: a free lock with a dead holder is reclaimed, and a live target
  group still blocks; evidence: the existing killed-gate tests extended to
  essential mode.
- AC-5 When a lock directory cannot be written, an essential run shall
  refuse with the `gate lock unavailable` message and its doctor pointer,
  as a full run does, and `codeflow doctor --check permissions` shall say
  the directories serve both modes; evidence: a test and the doctor text.
- AC-6 (journey) With the installed build of this change, two essential
  runs started together from two worktrees of one repository shall run one
  at a time: the second refuses at once, naming the first, and passes when
  rerun after the first ends; evidence: both runs' output with timestamps.
- AC-7 The `--mode` help and `docs/troubleshooting.md` shall state what the
  lock covers and what it does not: it keeps new essential and full runs,
  and full runs of 3.1, apart, through both the CodeFlow home lock and the
  git common directory lock; a quick run, including one that runs the
  essential targets in a project with no `quick` targets, can still run
  beside a locked gate; an essential run of a 3.1 binary takes no lock and
  is not excluded; and the lock does not make the machine otherwise quiet.
  Evidence: the help text and the doc diff.
