# TSK-331: Essential gate runs are serialized like full runs

## Description

`codeflow test` takes the machine gate lock only in full mode:
`guard_gate` returns before the lock for any other mode
(`crates/codeflow-cli/src/cmd/test.rs:198`), and the lock itself is
`full-gate.lock` under the CodeFlow home and under the git common directory
(`crates/codeflow-core/src/testing/gate_guard.rs:54`, `:215`). Essential
runs from several worktrees on one machine therefore overlap, with each
other and with a full gate, and their targets time each other out, the
failure TSK-134 fixed for full runs. In this repository, essential runs the
workspace tests, clippy and docs (15 essential targets in
`.codeflow/test-config.json`).

The outcome is that on one machine an essential or full run never overlaps
another essential or full run: the second run refuses at once, naming the
holder, its mode and its directory. As amended on 2026-10-17, a quick
run's light targets are unaffected and its heavy targets follow the same
lock.

Decisions recorded here:

- **One shared lock.** Essential takes the same lock files as full; there
  is no second lock and no per-mode policy table. The protection sought is
  one heavy gate at a time, and essential beside full times out just as two
  full runs do. Keeping the files also means a 3.1 binary running a full
  gate and this build running an essential one still exclude each other,
  and the shipped sandbox presets already allow `~/.codeflow/locks`. The
  file keeps the name `full-gate.lock`; the docs say it serves both modes.
- **Refuse, do not queue.** The second run refuses as a second full gate
  does today, with the holder's mode added to the message. Waiting is not
  added here.
- **The lock follows the heavy work, not only the mode.** `--mode
  essential` and `--mode full` take it for the whole run. Amended
  2026-10-17 after the Codex review of PR 226 (finding F5): a quick run
  takes it only for its heavy targets. A target is heavy when the test
  config declares it heavy; in a project whose config defines no `quick`
  targets, where quick runs the essential targets
  (`crates/codeflow-core/src/testing/gate.rs:735`), every target counts as
  heavy unless declared light. Light quick targets run without the lock,
  beside any gate. This repository declares its heavy quick targets
  (workspace clippy at least). The pre-push gate runs quick through
  `run_gate_exact` (`crates/codeflow-core/src/hooks/git_hook.rs:1280`) and
  follows the same rule; its ref, range, authority and checked-out-tree
  checks are unchanged.
- **Waiting is bounded.** A heavy quick target that meets a held lock waits
  up to a bound the repository config sets, default zero, then refuses
  naming the holder; the run reports which light targets ran.
- **Direct heavy work.** The engine cannot see a `cargo` command run
  directly. A sanctioned wrapper runs a direct heavy command under the
  same lock and cleans up its process group (provisional name `codeflow
  reserve -- <command>`; the builder settles the shape), and this
  repository's contract says heavy direct Cargo work uses it while another
  worktree may be gating.

Non-goals: an unbounded queue, and any fixed worker cap for adopters.

Amended 2026-10-17 by the gate efficiency amendment of EPC-022, from the
gate speed discovery of that day (ranked change 5). The lock keeps a second
heavy gate off the machine, but one gate still contends with itself:
`execution.max_parallel` is 3 and counts target processes, not the workers
inside them, so Cargo builds, clippy, nextest and the shell oracle (up to
eight workers of its own, `crates/codeflow-cli/tests/prose_oracle.rs`) each
size themselves to the whole machine. `rust-build`, `codeflow-bin` and
`rust-clippy` reported Cargo lock waits in all three inspected recent
essential runs. The task therefore also gives heavy targets inside one gate
one worker budget and stops this repository's Cargo producers waiting on
each other (AC-8 and AC-9). The budget starts as a setting of this
repository (about eight workers on the 10-CPU reference host, two left for
the host); an engine change to the runner is made only if configuration
cannot express it, and the reason is stated. No fixed cap is added for
adopters. Over-serializing also costs time, so the change is adopted only
on measured elapsed time.
Widened 2026-10-22 by the EPC-022 amendment of that day for issue #276:
a project where several agent sessions push from separate worktrees saw
two quick sets overlap and fail targets that pass alone (the quick suites
run 420 to 456 s against a 600 s limit and are undeclared, so AC-2 leaves
them light), and the `pgrep` check agents used before pushing is a race.
AC-12 lets the project make undeclared quick targets heavy and bounds the
pre-push wait with the holder named; AC-13 makes the holder record
readable. The lock decision (one lock, refuse by default, bounded wait by
setting) is unchanged.

Folded in by the amendment of 2026-10-18: the unit test
`testing::gate_guard::r22_regressions::r22_invalid_group_record_cannot_be_reclaimed`
in `crates/codeflow-core/src/testing/gate_guard.rs` failed one of three
module reruns in TSK-305's essential run at `269f520bc`. This task changes
the same lock code, so it finds the cause and makes the test reliable
(AC-11) rather than a separate task.

## Acceptance Criteria

- AC-1 While an essential or full run holds the gate lock, a second
  `codeflow test --mode essential` or `--mode full` on the same machine,
  from another worktree or another repository, shall refuse before any
  target starts, naming the holder's process, mode and directory; evidence:
  CLI tests for each of the four mode pairs. (serves EPC-022 AC-28)
- AC-2 While an essential or full run holds the gate lock, a quick run
  from another worktree shall run its light targets, and shall not run a
  heavy target (a declared heavy target, or any undeclared target of the
  quick-to-essential fallback) beside it: the heavy target waits up to the
  configured bound and then refuses naming the holder; the pre-push gate
  shall follow the same rule with its other checks unchanged; evidence:
  CLI tests with the lock held for a full run plus quick workspace clippy,
  for the quick-to-essential fallback, and for a light-only quick run, and
  the existing pre-push tests passing. (serves EPC-022 AC-28)
- AC-3 An essential run shall use the same lock files as a full run, and a
  holder record written by this build shall still be read by the 3.1
  holder description (one added key only); evidence: a test that a full
  run refuses while an essential run holds the lock, and a test that parses
  the new record with the old reader's rules.
- AC-4 An essential run killed while it holds the lock, or whose target
  process group is still alive, shall be handled as a killed full gate is
  today: a free lock with a dead holder is reclaimed, and a live target
  group still blocks; evidence: the existing killed-gate tests extended to
  essential mode.
- AC-5 When a lock directory cannot be written, an essential run shall
  refuse with the `gate lock unavailable` message and its doctor pointer,
  as a full run does, and `codeflow doctor --check permissions` shall say
  the directories serve both modes; evidence: a test and the doctor text.
- AC-6 (journey) With the installed build of this change, two essential
  runs started together from two worktrees of one repository shall run one
  at a time: the second refuses at once, naming the first, and passes when
  rerun after the first ends; evidence: both runs' output with timestamps.
- AC-7 The `--mode` help and `docs/troubleshooting.md` shall state what the
  lock covers and what it does not: it keeps new essential and full runs,
  and full runs of 3.1, apart, through both the CodeFlow home lock and the
  git common directory lock; a quick run can still run its light targets
  beside a locked gate, while its heavy targets, and every undeclared
  target of the quick-to-essential fallback, follow AC-2; an essential run of a 3.1 binary takes no lock and
  is not excluded; and the lock does not make the machine otherwise quiet.
  Evidence: the help text and the doc diff.
- AC-8 Inside one gate, heavy targets that run at the same time (Cargo
  builds, clippy, nextest and the shell oracle) shall share one configured
  worker budget, each given its share as its job or thread count, while
  light targets still run beside them; evidence: the configuration, a run
  log showing each heavy target's worker count, and elapsed gate time, lock
  waits and memory pressure from one essential and one full run before and
  after on one host, with the change kept only if elapsed time does not
  rise. (serves EPC-022 AC-53)
- AC-9 This repository's Cargo producers shall not wait on each other's
  build directory lock within one gate: `rust-clippy` runs with its own
  target directory inside the worktree (for example `target/clippy`, never
  shared with another worktree), and `rust-build` and `codeflow-bin` are
  ordered or combined so that they do not compile into the same target
  directory at once, while all-target compilation and the binary each
  consumer runs are kept; clippy waited on the lock in 7 of 18 sampled runs
  (build-speed research of 2026-10-17); evidence: the extra disk the clippy
  directory uses, no `Blocking waiting for file lock`
  line in those targets' logs in one essential and one full run, the
  producer table before and after, and the consumers' `requires` unchanged
  or still satisfied. (serves EPC-022 AC-53)
- AC-10 Across worktrees on one machine, a full landing gate shall not
  share the machine with heavy work started through CodeFlow elsewhere: a
  heavy quick target, a quick-to-essential fallback, and a direct heavy
  command run through the sanctioned wrapper shall each wait or refuse
  while the lock is held, light checks shall still run, the nested worker
  counts each heavy target used shall be recorded, and no process of a
  refused or killed run shall remain; evidence: a two-worktree test per
  case with process listings after each, and the wrapper's refusal and
  pass-after runs. (serves EPC-022 AC-53)
- AC-11 The `r22_invalid_group_record_cannot_be_reclaimed` test shall pass
  in 50 consecutive module reruns under host load, with the cause of its
  2026-10-16 failure found and named, and the fix shall not weaken what
  the test asserts; evidence: the rerun log and the cause in the PR.
- AC-12 A project shall be able to set the default class of an undeclared
  quick target (`heavy` or `light`, default `light` for a declared quick
  mode as AC-2 states) and the wait bound in its test config, and the
  pre-push gate shall follow both, waiting up to the bound and then
  refusing with a message naming the holder's process, mode and
  directory; evidence: CLI tests with the default set to `heavy` on a
  project whose quick targets are undeclared, through `codeflow test
  --mode quick` and the pre-push hook. (serves EPC-022 AC-28)
- AC-13 The lock record (pid, worktree, mode, start time) shall be
  readable through `codeflow test --lock-status` (provisional name), so
  a person or agent sees who holds the gate without `pgrep`, and the
  record shall stay readable by the 3.1 holder description; evidence: a
  CLI test and the AC-3 compatibility test. (serves EPC-022 AC-28)
