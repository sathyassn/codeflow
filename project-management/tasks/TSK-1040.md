# TSK-1040: A pull request body edit never cancels the required policy check

## Description

Issue #373 (CodeFlow 3.1.1, opened 2026-10-28 01:17Z). The generated
`.github/workflows/codeflow-policy.yml` runs on `pull_request_target`
with types `opened, synchronize, reopened, edited, ready_for_review`, in
one concurrency group per pull request with `cancel-in-progress` true for
those runs (`assets/base/ci/codeflow-policy.yml:40-53`). When the body is
edited seconds after a push, the `edited` run cancels the push's run; the
required "commit standards" check on that head then shows once cancelled
and once passed, and the adopter's PR stayed blocked until someone re-ran
it (runs 40613620628 and 40613623003, 2026-10-28; five more cancelled
runs on three branches on 2026-10-26 and 2026-10-27). Turning
`cancel-in-progress` off alone does not fix it: with the default
single-slot queue GitHub keeps one pending run per group and cancels it
when a newer one arrives. The shipped comment (`:29-36`) states the
cancellation as intended, reasoning that the surviving run reads the
current body from the API; the required check on the pushed head is what
it loses. This repository's own `.github/workflows/codeflow-policy.yml`
carries the same block.

Outcome: **no pull request event cancels or replaces the run that judges
a pushed head's required "commit standards" check; every queued run
completes; a run that judged a body, head or base that changed while it
ran fails with its own message so the run queued by that change decides;
and the body is logged by digest, never as text.**

Rules (the issue's proposal, to be confirmed by AC-1):

- Concurrency keeps the per-PR group and the per-run group for push,
  schedule and dispatch, with `cancel-in-progress: false` and the queue
  mode that keeps every pending run (`queue: max`, GitHub changelog of
  2026-05-07), if AC-1 confirms the key and its limits.
- A last step reads the pull request again and fails if the head SHA,
  the base branch or the body changed while the run judged them, and
  fails closed when the read fails. The base commit is not compared,
  since a push to the base fires no pull request event.
- The body is logged as a sha256 digest.
- Limits are documented: the queue's 100-run cap (past it a newest push
  fails closed), the window after a run's last read, two API calls per
  run on the shared token's rate limit, and linter support for the new
  key.

Non-goals: `codeflow-ci.yml`'s cancellation of superseded runs
(TSK-1026, which builds on this task's rule).

## Research and design (AC-1)

Researched 2026-11-01 before any change. Sources: the GitHub changelog of
2026-05-07, "GitHub Actions concurrency groups now allow larger queues"
(https://github.blog/changelog/2026-05-07-github-actions-concurrency-groups-now-allow-larger-queues);
this repository's workflows; issue #373; web search results for actionlint
and zizmor.

Findings:

- Concurrency semantics. By default a group allows one running and one
  pending run, and a newly arriving run replaces the pending one.
  `cancel-in-progress: true` also cancels the running one. The changelog adds
  `queue: max` under `concurrency:`: many pending runs wait and run in
  sequence, up to 100 per group, and it applies when `cancel-in-progress` is
  false or unset. The changelog does not say what happens past 100 or in what
  order; a secondary source says a run arriving at a full queue is cancelled
  and first-in-first-out is not promised. The design treats a cancelled run as
  a failed check (fail closed) and does not rely on order.
- Why `cancel-in-progress: false` alone is not enough. The single pending
  slot is still replaced by a newer run, so a push's run waiting behind a
  running one is cancelled by a later body edit. `queue: max` keeps every
  pending run.
- Check attachment. A `pull_request_target` run reports its check on the
  event's head SHA, so an `edited` run and a `synchronize` run for one head
  both report "commit standards" on that head. One cancelled and one passed
  on a head is the state issue #373 reports, and a cancelled run does not
  satisfy a required check. A re-run reuses its original event.
- Cost of queueing. Every event runs to completion, so an edit-heavy PR
  queues runs; each is a short job (20 minute timeout). A run judges the
  body as read when it runs, so a queued run can judge a newer body than its
  event. The final recheck fails a run whose judged head, base branch or body
  changed, and the run queued by that change decides.
- Other uses. `codeflow-ci.yml` cancels superseded `pull_request` runs
  (TSK-1026 owns it and follows this rule). The GitLab, Bitbucket and generic
  templates carry no concurrency key. The policy workflow's push, schedule
  and dispatch runs use a per-run group, so they never queue behind each
  other.
- Linters. actionlint releases up to 1.7.12 are reported to reject the
  `queue` key as unexpected (rhysd/actionlint#654; adopters ignore the
  message in `.github/actionlint.yml`). Search found nothing on zizmor and
  `queue`; its `concurrency-limits` audit checks that a key exists. Neither
  linter is installed or run in this repository's gates.
- Adjacent. Fork pull requests: `pull_request_target` runs from the base
  branch with a read-only token, unchanged. Rate limits: the recheck adds one
  API read per run (two per run in total) on the job's shared token. A re-run
  of an old run fails the recheck once the pull request has changed; the
  newest run decides.

Design:

1. `concurrency` keeps its group expression, sets `cancel-in-progress: false`
   and adds `queue: max`.
2. The body step also writes the body's sha256 digest to its output and logs
   the digest, never the text.
3. A last step for pull request events reads the pull request again and fails
   when the head SHA, the base branch name or the body digest differs from
   what the run judged, and fails closed when the read or parse fails. The
   base commit is not compared, since a push to the base fires no pull
   request event. The step is a shell block in the workflow, because the
   workflow is the only file an adopter receives.
4. Documented limits: the 100-run queue cap (a run past it is cancelled, so
   the newest push fails closed), the window after the last read, two API
   reads per run, and actionlint support for `queue`.

Not exercised here: AC-2 and AC-6 need a hosted scratch adopter repository
(see the pull request for what it needs).
