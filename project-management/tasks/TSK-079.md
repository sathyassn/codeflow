# TSK-079: model catalog with latest eligible resolution

## Description

Build the catalog engine: the schema 5 types, the validator, the
eligibility predicate and the duty resolver described in EPC-018 "Model
routing, as config". This task changes no managed file: every test runs on
fictional catalogs (fictional families, lines, versions and ids), so it runs
beside the autonomy chain. TSK-085 later switches
the managed catalog to the roster.

Schema 5, keeping the file name `current-ensemble.json`:

- families (`claude`, `codex`, `grok`) with provider, harness ids, probe ids
  and usage bucket; harness and probe ids must already exist in
  `harnesses.json` and the code allowlist (ADR-0054 item 8);
- product lines with ordered versions; a version carries alias, pinned
  id, selector per harness, supported efforts, lifecycle (`active`,
  `fallback-only`, `retired`), seat designations (seat, date, record) and
  scoped evidence entries (exact harness, selector, effort, duty, evidence
  paths);
- one primary seat per family, mapped to its standing or catalog role, with
  ordered eligible lines; the Claude seat is the design owner;
- duties with required participants, triggered participants (trigger ids
  from `routing-policy.json` or a named policy), each participant an ordered
  list of alternatives (seat or line) with a lineage relation to the author,
  an entry effort per duty, and the `xhigh-reasoning` obligation added on an
  xhigh trigger (ADR-0056); the `design` duty is served by the design owner
  seat's first line only;
- the existing high and xhigh triggers; rules text names no model; an
  adoption policy per line (`manual` or `workers`) for Q1.

The validator rejects: an unknown field, a duplicate key, an unsupported
harness or probe, standing families that are not two distinct lineages, a
non-Claude design owner, more than one primary seat per family, a seat line
with no version that could be eligible for it, a seat designation on a
retired version or on a version in a line that no seat lists, a duty
default below its floor, and a designation or evidence entry without its record.

The eligibility predicate and the resolver follow EPC-018 "Eligibility and
resolution" exactly. `resolve(duty, task id, host harness, author lineage,
exclusions, observed ids, trigger facts, operator override)` returns every owed participant with
the chosen version, pinned id to launch, effort and remaining alternatives,
plus any `xhigh-reasoning` obligation and any labeled second opinion, or names
the participant it cannot fill and why. It is a pure function: no launch, no
probe, no clock.

Operator override. The only override input is an `OPERATOR_OVERRIDE` record
already parsed from the approved Plan vN task record (TSK-080 sources and
anchors it); a caller-supplied string is never one. Following
`capability-routing.md` (near line 247) and ADR-0060, the record names the
exact task, duty, route (seat or line, and harness) and effort, the plan
version, and where the operator gave the instruction. A matching record
replaces the `design` duty's ordinary first-line restriction for that exact
task only: its route may be any line that a catalog seat lists (for example
the Claude seat's second line, or another family's seat line). That
restriction is the only rule it replaces. The resolver applies it only when
its task equals the task being resolved and its duty is `design`, and the
named route still passes these checks: the chosen version is not `retired`;
its efforts include the named effort, which is at or above the `design`
floor (high); no fresh native exclusion applies to it; and the drift rule
holds (launch by pinned id; an observed mismatch inherits nothing and the
duty stays open). Any mismatch, failed check or missing record leaves
`design` open with the reason. An override grants nothing for another task
or another duty, and never grants direction or fidelity approval to a
worker.

Overrides: the personal overlay `~/.codeflow/model-catalog.local.json` may
add a version to an existing line (always a candidate, no designation) or
exclude a version; anything else fails the whole overlay. The project file
`.codeflow/model-selection.json` stays at schema 1 (ADR-0041): a binding
reference still applies only to its exact role and harness, and is tested
against schema 5.

Until TSK-085 lands, the engine also accepts the schema 4 managed file so
the current tree stays green; TSK-085 removes that path.

Rename this module's own fixture ids that use a current model name (for
example `claude-fable-high` near `model_qualification.rs:1214`) to fictional
ids.

Write ADR-0069, "model catalog with product lines, seats and duties", as
`proposed`: the catalog model, eligibility (designation apart from scoped
evidence), duties as participant sets, effort floors (ADR-0056 unchanged),
the `xhigh-reasoning` obligation, the launch identity rule (seats launch by
the pinned id of the designated version the catalog resolved; aliases are
used only by the identity canary to discover a newer version; drift inherits
nothing), the design owner seat and the rule that design stays open when its
first line is ineligible unless an `OPERATOR_OVERRIDE` record in the
approved Plan vN names the exact task, duty, route and effort (Fable may
hold the seat for orchestration, planning and review as a recorded
fallback; without such an override it never authors design or gives design
or fidelity approval, and with one the named line serves `design` for that
task only), the Codex transport (a stale
plugin login is a native exclusion and the Herdr interactive Codex seat is
the qualified fallback, as ADR-0059 already allows), designation and
qualification as separate fields with qualification empty at first, the
overlay limits, deferred project schema 2 with its "may" and "never" lists,
and one sentence naming `grok-4.7-build-fast` as known and not routed.
TSK-085 accepts it with the roster.

Non-goal: the command and doctor output (TSK-080), any managed file, prose,
Agent OS.

## Acceptance Criteria

- [x] When a fictional schema 5 catalog is loaded, the validator shall accept a valid one and reject each invalid shape named above; evidence: unit tests with one failing fixture per rule.
- [x] When `unit-review` is resolved, a Claude-authored unit shall owe the Codex seat, a Codex-authored unit the Claude seat, and a Grok-authored unit the Codex seat, else the Claude seat; the Grok seat shall be added only when its trigger fires and Grok is not the author; a missing required reviewer shall leave the duty open, never substituted by a same-lineage model; evidence: unit tests for all three authors and the missing-reviewer case.
- [x] When `independent-plan` or `body-review` is resolved, both standing seats shall be returned; with one seat excluded the duty shall be open; evidence: unit tests.
- [x] Eligibility negatives: a version with scoped test-authoring evidence offered a primary seat is ineligible; a scoped tuple reused at another effort or harness is ineligible; a design-implementation worker offered direction or fidelity approval is refused; a candidate added by the overlay never fills a seat; evidence: unit tests.
- [x] Effort: a catalog with a seat duty default of medium is rejected; a medium default for `bounded-execution` is valid; a worker version that lacks its participant's effort is excluded, not clamped; evidence: unit tests.
- [x] xhigh (ADR-0056): with an xhigh trigger the seat resolves at high and an `xhigh-reasoning` obligation resolves to a same-family worker at xhigh while the seat keeps approval; a seat version without xhigh stays eligible; with no same-family xhigh worker the obligation is open, the seat stays at high and the result says the trigger is not met; evidence: unit tests for all three.
- [x] Launch identity: every resolved participant carries a pinned id, never an alias; an observed id that differs from the pinned id inherits no designation or evidence; a seat falls to its next eligible alternative, a candidate-eligible worker duty may use the drifted model only as a candidate, and with no alternative the duty is open; evidence: unit tests including a drift control where design work must not proceed.
- [x] Design: with the design owner seat's first line eligible, `design` resolves to it; with that line excluded, the seat resolves to its fallback line for `orchestrate` and `independent-plan` with reduced assurance while `design` stays open; the positive control is a concrete alternate route with the first line excluded: an `OPERATOR_OVERRIDE` for task T naming the Claude seat's second line at high fills `design` for T with that line's pinned id at high and records the override; evidence: unit tests.
- [x] Override negatives: no record, and a record whose task, duty, route or effort differs from the resolution (one test per field), each leave `design` open with the reason; the same record applied to another task, or to a non-design duty such as `orchestrate` or `unit-review`, grants nothing; a record naming a retired version, an effort the version lacks, an effort below high, an excluded version, or a version whose observed id drifted leaves `design` open; evidence: unit tests.
- [x] The validator rejects a designation on a retired version and on a version in a line no seat lists; evidence: unit tests.
- [x] Other rows: `general-review` of Claude work with Grok excluded returns a labeled second opinion and leaves the independent reviewer open; `reasoning-support` never resolves to the version serving the seat; `computer-use-qa` for Grok-authored UI resolves to the Codex seat on `codex-app`; `test-authoring` is not resolved separately; evidence: unit tests.
- [x] Latest eligible: a newer active version is chosen for a worker duty when adoption is `workers` and ignored under `manual`; a usage-bucket exclusion removes every line in it; `fallback-only` serves only as a listed seat fallback; evidence: unit tests.
- [x] A schema 1 project binding reference resolves only for its exact role and harness under schema 5, and a reference for another harness or effort fails; evidence: tests.
- [x] The targeted crate tests pass and no fixture in this module uses a current model name; evidence: test output and a search in the closeout.
