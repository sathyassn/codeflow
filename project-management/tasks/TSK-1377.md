# TSK-1377: Coordinating sessions message on events, batch under the harness ceiling and fan out one level

## Description

Issue #225 and the token-use coordination brief of 2026-11-07 (`token-use-coordination-proposal.md`, outside the repository; the operator approved its three decisions the same day). Coordinating sessions spend tokens on routine messages and the replies they start ("sweep done, nothing changed", "Worker resumed"), on sessions that wait by polling, and on delegates that start delegates. The consuming project also found that Claude Desktop pauses session-to-session messages after 10 sends since the user last typed (#225, the correction to its item 5), so a coordinator that sends one message per update stalls its Workers. Batching is required to keep working, not only to save tokens.

This task puts one set of coordination rules in the shipped guidance. A session messages a peer only on an event that peer must act on. It sends at most one batched message per peer per turn. It waits through watchers that cost no model tokens, including a seat prompt waiting past its bound. A delegate starts no delegates. A coordinator starts a fresh session at a phase boundary, so most turns stay well below the compaction point. Until it lands, the workspace's `coordination/sweep-checklist.md` carries the same rules for the workspace.

Non-goals: the sweep command, its 120-minute default and its findings (TSK-1037); the report shape, delta-only reports and the pointer in `writing.md` (TSK-1099 AC-4); the read-only route itself (TSK-1292 AC-11); the ledger vocabulary, tier names and tier effort (TSK-423); the compaction point (TSK-1029, TSK-1049).

## Outcome

After this merges, a coordinating session in any adopting project messages a peer only when that peer must act, sends at most one batched message per peer per turn (under the Desktop ceiling of 10 sends), waits through watchers that cost no model tokens, has delegates that start no delegates, and starts a fresh session per phase.
