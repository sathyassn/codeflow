# TSK-1422: The present review page allows no inline style the renderer did not write

## Description

The cf-present review page sends a Content-Security-Policy that keeps scripts strict but allows any inline style: `style-src-elem 'self' 'unsafe-inline'` and `style-src-attr 'unsafe-inline'` (`crates/codeflow-present/src/service.rs:658`). Two things need inline styles: the project utility token style element (`render.rs:84`) and the interactive `html` block, which is inlined with scoped style elements and validated style attributes (`safe_html.rs`, `scoped_css.rs`). The renderer drops raw HTML and scopes those styles, so the allowance is narrow in practice, but the header itself would let any injected style run.

EPC-016 deferred this when TSK-087 removed Mermaid, with the trigger "after TSK-060 and TSK-087 have both landed"; both landed before 3.0.0. This task replaces `'unsafe-inline'` with a nonce the service generates per response. The design is settled: no `'unsafe-hashes'`, since a hash allows the same style attribute on any element, so a copied attribute would apply. The renderer writes no inline style attributes. Styling comes from classes or from style elements that carry the per-response nonce: the token style element, each scoped `html` block style element, and the block's validated style attributes rewritten at render time into the block's scoped sheet as classes. `style-src-attr` allows nothing.

Non-goals: the script policy, which is already strict; the docs portal; exported files, which carry their own policy (TSK-1101).

## Outcome

After this merges, a reader of a cf-present review page is served a policy under which only the styles the renderer wrote can apply, and every block and chrome control still renders with no policy violation in every skin and mode.

## Deliverables

- the per-render style sources and the header: `crates/codeflow-present/src/service.rs`, `render.rs`, and the `html` block style code in `safe_html.rs` or `scoped_css.rs`
- the browser fixture and violation check: `crates/codeflow-present/web/scripts/csp-violations.mjs` and `csp-violations-browser-check.mjs`, extended
- the impact assessment EPC-016's Deferred item asks for: in the pull request body
- a release note: `changelog.d/TSK-1422.md`

## Estimate

- Grade: Hard; band: Hard (4 to 6 h); moved: none
- Split: not needed; one policy change with its render-time sources and one browser proof

## Acceptance Criteria

- AC-1 Before any change, the builder shall record in `## Findings` every inline style the review page renders (elements and attributes, by producer), how each style attribute becomes a class in a nonced style element, and the impact on adopters' existing `html` blocks; evidence: the Findings section committed before the first code change.
- AC-2 The review page's policy shall carry no `'unsafe-inline'` and no `'unsafe-hashes'` in any style directive, shall allow style elements only through a nonce generated fresh for each response from a cryptographically secure random source with at least 128 bits before encoding, never reused across responses (CSP Level 3, Security Considerations, "Nonce Reuse"), and shall allow no style attribute (`style-src-attr 'none'`); the rendered page shall contain no inline style attribute, and the token style element and each scoped `html` block style element shall carry that response's nonce; evidence: a service test that reads the header of two responses, checks the nonces differ, decode to at least 16 bytes and match the rendered elements, and finds no `style=` attribute in the rendered page; and the reviewer's check of the generator (the random source it calls and the byte count it draws) read together with that service test and the AC-3 browser test, since a test of two values alone cannot show the source is unpredictable.
- AC-3 A style element or style attribute the renderer did not write shall not apply under the new policy, including a style attribute copied from one element onto another; evidence: a browser fixture that injects a style element and a style attribute after render, and one that copies a style attribute onto another element, each recording a CSP violation and no style change.
- AC-4 A fixture with an `html` stage whose source uses both a style element and a style attribute shall render with zero policy violations and its styles applied (the attribute's through its rewritten class), in every skin and mode, in Chromium, Firefox and WebKit where the host runs them; evidence: the extended `csp-violations` browser check output.
- AC-5 The present chrome and every block type shall pass the same browser check under the new policy; evidence: the same run covering every block in the catalog fixture.
- AC-6 (journey) An agent opens a cf-present session with an `html` stage through the installed candidate binary, and the page renders as before with no console policy violation; evidence: the session's browser check output in the pull request body.
