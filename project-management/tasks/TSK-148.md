# TSK-148: release branch integrates each line as it lands

## Description

The 3.0.0 release branch met the EPC-020 line once, late, and the catch-up
merge failed on everything that had accumulated: 15 binding and 20 frozen
findings at pre-push, and a reading chain of 175,166 bytes against the
151,552 cap (scratchpad `models-stream/rehearsal/push-M3.txt` and
`chain-fit-design.md`). Each of those would have been one small finding
had the lines been combined as they landed. This task makes release
integration continuous: the release branch takes each epic line's
landings as they happen (per landing, with a daily run as a backstop),
and the binding, reading and conflict checks run on the combined result,
so a conflict or finding surfaces on the landing that caused it.

Scope: `cf-ship` guidance for what a landing does next, CodeFlow's own
release workflow automation, and TSK-010's release-integration duty.
Merges into the release branch are judged by SPC-013 R-120 (TSK-145); a
conflict resolution is integration work that TSK-010 owns, so the
automation never resolves one.

## Affected surfaces and interfaces

- The CodeFlow-only release workflow that TSK-106 creates (outside the
  managed CI file adopters receive).
- `assets/base/agents/skills/cf-ship` (the step after a landing on an
  epic line) and its installed copies and mirrors.
- TSK-010's record: the release-integration duty, after TSK-109 AC-3
  retargets TSK-010 to this line.
- Shared files, per SPC-013 R-118: the release workflow row and the
  `cf-ship` row.

## Acceptance Criteria

- AC-1 When a pull request lands on a verified epic line, the release
  workflow shall merge the line's new tip into the release branch when the
  merge is clean and `codeflow ci` judges the combined result clean under
  R-120, and push that merge; evidence: a workflow test on a fixture
  repository with two lines landing in turn, showing one integration merge
  per landing.
- AC-2 When the merge conflicts, or the combined result has a binding,
  frozen-criteria or reading-check finding, the workflow shall push
  nothing, fail visibly with the finding, name the open
  release-integration task as its owner, or report "no
  release-integration task to own it" when no open task carries the role,
  and print the local commands that reproduce it; evidence: the fixture
  run with a conflicting landing, one with a binding finding and one with
  no holder, each leaving the release branch unchanged.
- AC-3 When no landing ran the job for a day, a scheduled run shall do the
  same integration for every verified epic line; evidence: the workflow's
  schedule trigger and the fixture run of the scheduled entry.
- AC-4 TSK-010's record shall carry the duty of resolving a reported
  release-integration conflict or finding within the release pull request,
  per R-120's direct-change rules, and of accepting the disposition of the
  nine other-line byte-cut losses in TSK-150's audit table (restored or
  justified as superseded) before the combined release is ready;
  evidence: the TSK-010 record diff in this task's pull request.
- AC-5 (journey) In a freshly scaffolded full-tier project, the installed
  `cf-ship` shall tell the agent, after a landing on an epic line and only
  when the project has a release branch (a name matching the release
  pattern, R-120), to read the release integration result and route a
  failure to the release-integration task, or report that no task owns it
  when none carries the role; a project without a release branch gets no
  such step; evidence: an `init_e2e` check of the installed text, a run of
  the named command on a fixture with a failed integration, one with no
  holder, and one with no release branch.
- AC-6 A task pull request that lands on an epic line shall never wait on
  the release integration; it is reported after the landing, not gated
  before it; evidence: the workflow's triggers (push to the line, schedule)
  and no required check added to task pull requests.
