# TSK-184: One delivery process with the waste removed

## Description

The operator approved one delivery process on 2026-09-29 and directed that
every wasteful step in CodeFlow be removed in one round, with quality never
lowered. Today the method plans per task (55 planning PRs against 42 task
PRs on this line), caps and repeats reviews, runs a 43-minute sequential
gate that executes the Rust tests up to three times, and asks for per-task
paperwork no check reads. This task lands the whole change in one PR: the
process (plan once when a brief or spec is broken down, one PR per task
with its record, one holistic review, one gate per batch, continuous
landing), the scenario map in AGENTS.md and CLAUDE.md at every tier, the
rules, skills, agents, templates, spec sections and the superseding ADR
that state it, the checker changes that let it run, and the gate, CI and
eval changes that remove repeated work. The change list with one row per
file is the work breakdown inside this task.

Non-goal: changing any quality floor. AC-7 lists the floors that keep
their strength.

## Affected surfaces and interfaces

- Managed instructions: `assets/base/rule-map.toml`, the AGENTS and CLAUDE
  templates at every tier, the rendered `AGENTS.md` and `CLAUDE.md`.
- `.codeflow/rules/`, the skills and agents under `assets/base/` with their
  mirrors and baselines, `project-management/templates/`, SPC-013's method
  sections, a new ADR superseding the per-task and round-cap clauses.
- Checker: `crates/codeflow-cli/src/cmd/ci/` (classification, acceptance),
  `crates/codeflow-core/src/workgraph/` (acceptance binding, work start,
  allocation), hooks and policy schema where the `Task:` grammar lives.
- Gate and CI: `.codeflow/test-config.json`, `crates/codeflow-core/src/testing/`,
  `scripts/journey-gate.py`, `scripts/check-present-binary-delta.mjs`,
  `.github/workflows/`, `.release/config.json`.
- Evals: `evals/` requirement anchors and qualification triggers.
- Public behaviour for adopters changes: a PR must carry a `Task:` line,
  a standalone task may land with its code, start verbs take `--on`, and a
  release-impact note is required only on a protected base or a breaking
  commit. The release impact of this change is assessed in its PR.

## Acceptance Criteria

- AC-1 When an agent reads the managed AGENTS.md and CLAUDE.md at any
  tier, each of the 26 moments in the rule map's contract list shall
  resolve to an inline action or a named skill or file, with the reads
  that must happen before acting marked; evidence: the rule-map
  contract test over the rendered templates at each tier.
- AC-2 When `codeflow ci` judges a pull request, it shall refuse one whose
  `Task:` line is missing or empty, require a `TSK-NNN` or `EPC-NNN` value
  where durable tracking is active and accept any non-empty unit name where
  it is not, and accept a standalone task whose record and implementation
  arrive in the same reviewed PR while still refusing any other record in
  that PR; evidence: CLI tests at each tier, red before the change and
  green after.
- AC-3 When a task PR changes its own acceptance criteria, `codeflow ci`
  shall print the change for the reviewer instead of refusing it, and still
  refuse a change to another task's criteria; evidence: CLI tests.
- AC-4 When reviewed task heads land together, or a task branch merges the
  line after review and its tree equals the clean re-merge, each completion
  shall stay bound to its reviewed commit, and a hand-resolved product hunk
  shall still unbind it; evidence: CLI tests, including the batch landing
  that the current check refuses.
- AC-5 When the full gate runs, target groups with no producer and consumer
  relation shall run in parallel, the instrumented Rust suite shall run
  once with coverage and the journey check shall read that run, the
  doctest target shall still run, and a target shall be skipped only when
  its declared inputs are unchanged against a known base, with an
  undeclared input, an unknown base or an epic close running every target;
  evidence: gate tests and a recorded before and after timing on this
  machine.
- AC-6 When a skill, rule, agent or template states the delivery method,
  it shall state the approved process once, in its one home, with no
  review-round cap, no per-task planning PR and no per-task closeout
  narrative; evidence: the eval kit and skill-trigger checks green, and a
  holistic review of the rewritten text.
- AC-7 When the change lands, these floors shall hold at their current
  strength: the secret scan, protected branches, commit rules, security
  review on its trigger, other-lineage review of every task, criteria with
  evidence per criterion, the acceptance block bound to the reviewed
  commit, `work.stable_planning_anchor` at block, completed predecessors at
  the merge base on landing, the coverage floor, the doctest and journey
  checks, the Windows raw run as referee, binary size, SBOM and licence
  checks, the full-gate lock, the read benchmark, `validate --docs`, one
  full gate on the exact candidate before the line moves, the headless
  prohibition and other delegate protections, `current-ensemble.json` and
  `routing-policy.json` unedited, the 32 KiB instruction limit, the
  `cf-reviewer` read-only verdict, the security reviewer's axes, schema
  and block, three trials per eval case, self-written approval never
  authorizing, the epic close rule, exclusive allocation, the tested tip
  in `integrate`, hook integrity, accepted ADR text never edited, spec
  approval only with no open questions, and human-only merges into main;
  evidence: the policy file
  diff, a green test per floor (rewritten tests keep their assertion), and
  the review verdict.
- AC-8 When a new project is initialized at each tier and a first task PR
  is checked, the rendered instructions shall carry the new map and the
  task-naming rule shall apply; evidence: the init journey test. (journey)
- AC-9 When a start verb runs on a task whose predecessor is reviewed but
  not complete, it shall accept `--on <task>@<reviewed commit>` and build
  on that commit, and `codeflow ci` shall still require the predecessor
  complete at the merge base when the task lands; evidence: CLI tests.
- AC-10 When `codeflow ci` judges a pull request, it shall require a
  release-impact note only for a protected base or a breaking commit;
  evidence: CLI tests for each case.
