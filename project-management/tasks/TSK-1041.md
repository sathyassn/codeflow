# TSK-1041: Open pull requests are reported by state in one read-only command

## Description

Issue #369 (opened 2026-10-28 00:50Z, the same adopter as #366 and
#370). CodeFlow's PR guidance covers one PR at the moment its author asks
for a merge: `cf-ship` `references/pr-evidence.md` ("After opening")
reads hosted results once, and `references/pr-checks.md` gives a bounded
`gh pr checks --watch` and the redness classes. Nothing covers the other
open PRs while one waits, or after something else lands. In one
adopting repository on 2026-10-27 and 2026-10-28, a coordinator with
about fifteen open PRs found three kinds of problem late: a conflict
that appeared after another PR landed on the same target (found by the
operator's merge script), reviewed heads that went stale through
legitimate record or line-merge commits (tracked by hand), and a
non-required check that failed closed on every PR touching an image row
and was classified only when a reviewer asked. Each session writes its
own loop of `gh pr list`, `gh pr view` and `gh pr checks`; those loops
differ, use the write token where a read token belongs, and miss the
base-moved case.

Outcome: **a read-only `codeflow pr status` reports every open PR in
scope with one line and a state class, worst first (`conflict`, `red`,
`stale-review`, `base-moved`, `unreviewed`, `pending`, `ready`,
`advisory-red`), from
one host query per call, with `--json` and an opt-in `--fail-on`; it
uses the project's read profile where one exists; and `cf-ship` says to
run it after each landing on a target and before sending the operator a
merge command.**

Rules:

- Facts per PR: head SHA, the reviewed SHA, draft or ready, mergeable
  and merge state, required checks by state, failed non-required
  checks, review decision, and commits the target gained since the
  reviewed SHA's merge base. `stale-review` says whether the commits
  since review touch only records and merge commits, or product files.
- The reviewed SHA uses `codeflow ci`'s acceptance binding (TSK-451,
  EPC-022 AC-127; `tracked_review` in `crates/codeflow-cli/src/cmd/ci.rs`
  `:1066-1160`), never a second reader. For a task PR whose record at
  the head carries an active acceptance block, the block's reviewed
  commit binds; a Reviews row that is left out or only points at the
  record defers to it, and a row naming another commit or verdict is
  shown as a disagreement note, never used. For a PR with no active
  block (a task still in progress, a planning PR), the Reviews row read
  by the strict `review_names_revision` rule gives the reviewed SHA.
  When neither gives one, or the record cannot be read, the class is
  `unreviewed` with the reason, and such a PR is never `ready`.
- Redness classes come from `pr-checks.md`, read from a failed step's
  log only when that is cheap and cached by run id; otherwise
  "unclassified".
- Scope: `--mine`, `--into <target>` or `--all`; the default is the PRs
  whose head branches have local worktrees.
- No watch mode and no background process; `pr-checks.md`'s bounded
  watch stays the only wait. Exit 0 unless `--fail-on` is given.
- No gate, no record and no required step. The `cf-ship` method lines
  (rerun after a landing, confirm `ready` before a merge command, name
  `advisory-red` checks, list PRs that touch the same files in a merge
  script) are guidance.
- The session sweep (TSK-1037) reads this command's classes rather than
  reimplementing them.
- One forge reader for pull-request facts (amended 2026-10-28). The
  host query runs through the coordination ledger's bounded observer,
  `coord/observe.rs`'s `command` with its freshness `Cache`, so one
  bound and one cache answer "has this PR's base or head moved" for
  every caller. Once this command lands, `codeflow report away`
  (TSK-1045) takes `conflict`, `base-moved` and `stale-review` from
  this classifier for the pull requests its items name, instead of
  computing them a second way.

Non-goals: merging, rebasing or rerunning anything; a watch loop; any
change to which checks are required.

### First-pass survey (planning, 2026-10-28, line tip after PR 367)

## Acceptance Criteria

- AC-1 Before any change, the builder shall research multi-PR status broadly: what each forge CodeFlow serves exposes in one query (GitHub GraphQL `mergeable`, `mergeStateStatus`, `statusCheckRollup`, `reviewDecision`, `headRefOid`; the GitLab and other equivalents where CodeFlow runs), its rate limits and the cost per call, how comparable tools classify PR state, how a read-only token is configured per host, the CodeFlow guidance and readers in the survey above, and adjacent concerns (merge queues, required checks by ruleset, fork PRs, `pull_request_target` jobs, offline sessions); and shall record the findings with sources and the chosen scope before any change; evidence: the note or record section, committed before the first code change in the PR.
- AC-2 `codeflow pr status` shall report each PR in scope with its facts and one class, worst first, and shall classify `conflict`, `red` (with its redness class or "unclassified"), `stale-review` (records-only or product commits since review), `base-moved`, `unreviewed` (no reviewed commit found, or the record unreadable, with the reason), `pending`, `ready` and `advisory-red` (each failed non-required check named), taking the reviewed SHA from the acceptance binding as the Rules state; evidence: classifier tests over recorded responses for each class, including a target that moved after another PR landed, a head pushed after its reviewed SHA with only a record commit, a failed non-required check, and for the review source: a bound acceptance block with the Reviews row left out, with a row that only points at the record, and with a row naming another commit (the block binds and the note is shown), a valid bound block at the head, a product commit after the block's reviewed commit (`stale-review`), and a PR with no block and no row (`unreviewed`). Amended 2026-10-28 after the PR 374 review: the acceptance block binds. (serves EPC-023 AC-35)
- AC-3 One call shall make one host query for every PR in scope, plus one log read per newly red required check, cached by run id; the query shall run through `coord/observe.rs`'s bounded `command` and `Cache`, and a query past its bound shall report each PR's forge facts as unknown; where TSK-1045 has landed, `report away` shall show this classifier's class for each pull request an owed item names; evidence: a test counting requests over a recorded fixture, a hung-host test that finishes within the bound, and a `report away` test over the same fixture showing the class. Amended 2026-10-28 so one bounded reader serves both commands.
- AC-4 Where the project defines a read-only token, the command shall use it and never the write token; evidence: a test with both configured.
- AC-5 The command shall exit 0 and change no file, ref or remote state; `--fail-on conflict,red` shall exit non-zero only on those classes; `--json` shall carry the same content; evidence: CLI tests.
- AC-6 `cf-ship` shall say to run `codeflow pr status --into <target>` after any landing and handle `conflict` and `base-moved` before the next merge command, to confirm each PR is `ready` at its reviewed head before sending a merge command, to list PRs in one merge script that touch the same files, and to name `advisory-red` checks in readiness reports; evidence: the text diff and a `cf-editorial-review` pass. (serves EPC-023 AC-35)
- AC-7 (journey) With the installed build against a scratch repository on the forge with three open PRs (one made conflicting by landing another, one pushed after review, one ready), the command shall print `conflict`, `stale-review` and `ready`; evidence: the journey output.
