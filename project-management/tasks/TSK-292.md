# TSK-292: A project can refuse inline gitleaks:allow on trusted commits

## Description

The managed secret scan accepts an inline `gitleaks:allow` on any commit
the trusted commit already holds (`assets/base/ci/codeflow-ci.yml:739-773`
at v3.1.0). A project that refuses every inline allow, so that a finding is
exempted only through the reviewed ignore file on the base, must delete the
`held` filter from the managed step and carry that edit through every
update (https://github.com/sathyassn/codeflow/issues/152). The same step passes `HEAD` or `<sha>..HEAD` to
`--log-opts` without resolving `HEAD` or ending with `--` (`:458-466`,
`:722`); a path named `HEAD` would make git's argument ambiguous, which
fails closed today. This task adds a policy key for the inline allow and
hardens the log options. It is split from TSK-294 (the same workflow file)
because the secret scan is a security boundary with its own review.

## Deliverables

- the step and the hardening: `assets/base/ci/codeflow-ci.yml`, its installed copy `.github/workflows/codeflow-ci.yml` and baseline
- the key: `crates/codeflow-core/src/hooks/policy_schema.rs`, placed by TSK-280's rule
- tests: the managed workflow tests in `crates/codeflow-core/tests/`
- docs: `docs/policy-reference.md`, `assets/base/ci/README.md`
- release note: `changelog.d/TSK-292.md`

## Acceptance Criteria

- AC-1 When the trusted commit's policy sets the inline allow key to
  `never`, the secret scan shall report a finding marked `gitleaks:allow`
  on a commit the trusted commit holds, and with the default (`trusted`)
  it shall allow it as at v3.1.0; evidence: workflow tests for both values.
  (serves EPC-022 AC-10)
- AC-2 The key shall be read from the trusted commit, so a pull request
  that changes it does not change its own scan; evidence: a test with the
  key changed only on the head.
- AC-3 The scan shall pass resolved commit ids to `--log-opts` and end the
  revision list with `--`, so a tracked path named `HEAD` changes nothing;
  evidence: a test with a file named `HEAD` in the tree.
- AC-4 The new key shall be placed by the rule TSK-280 writes and pass its
  check, and the policy reference and the CI README shall document it;
  evidence: TSK-280's check on this branch and the doc diff.
- AC-5 When a fresh project updated with the installed build sets the key
  to `never`, a pull request carrying a held commit with an inline allow
  shall fail the secret scan with no local edit to the managed workflow
  (journey); evidence: a run of the managed step on a scratch repository.
