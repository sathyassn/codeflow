# TSK-1116: New files meet the strict profile at once against a recorded boundary

## Description

Issue #275's comment of 2026-10-29, lesson 7: new files can be strict at
once, before the old code is fixed. Repository A checks every new file
against a recorded boundary revision per line; a copy, a rename, a new
folder or a missing pragma never makes a file count as existing; lines with
no recorded boundary are reported as "unproved" rather than silently passed.
TSK-424's ratchet admits existing debt by stable occurrence identity and
only shrinks it; TSK-426 configures the strict profile; neither makes a new
file strict while the baseline is being paid down, so a long migration can
grow its debt in new code.

This task adds the mode: a recorded boundary revision per target branch and
line, held in the register's configuration at the default-branch authority;
every file absent from the tree at the boundary is checked at the full
strict profile with no debt admitted; a line with no recorded boundary is
reported unproved and fails at `block`; moving a boundary is a register
event with the ratchet's semantics (authority-only, and a later boundary
only widens the strict set). Non-goal: the per-diagnostic ratchet itself
(TSK-424) and the merge rules (TSK-1117).

## Outcome

After this merges, an adopter migrating a large codebase to the strict profile has every new file held strict from its first commit, while the old code pays down its recorded debt.

## Deliverables

- the boundary configuration and the new-file decision: `crates/codeflow-core/src/exemptions/boundary.rs` (new; the parent `exemptions/` module is itself new in TSK-424 and does not exist today), the register schema fields
- the gate wiring: the strict targets of TSK-426 read the boundary and apply no debt to files absent from it; the report line per file (`strict`, `existing`, `unproved`)
- docs: `docs/test-gate.md`, `docs/policy-reference.md`, `assets/base/agents/skills/cf-stack/SKILL.md` and `assets/base/agents/skills/cf-develop/SKILL.md` (one paragraph each), the `.claude/skills` and `.agents/skills` mirrors byte-identical
- tests: boundary tests (new file, copy, rename, new folder, missing pragma, unproved line), authority tests (a head that moves the boundary is refused), a `cf-stack` fixture

## Acceptance Criteria

- AC-1 Before any change, the builder shall research new-file strictness during a migration broadly: how type checkers and linters support per-file strictness and boundaries (pyright `strict` paths, TypeScript project references, ESLint overrides, Ruff per-file settings), how a file is proven new against a revision under renames, copies and history rewrites, Repository A's boundary check as the reference, TSK-424's register fields and authority rules, and adjacent concerns (generated files, a file moved out of a frozen tree, squash merges, a boundary on a line cut before the register existed); and shall record the findings with sources and the chosen scope before anything else changes; evidence: the Findings section, committed before the first code change in the PR. Listed first because it runs first (the operator's rule of 2026-10-27).
- AC-2 The register configuration at the default-branch authority shall hold a boundary revision per target branch and per line, and the strict targets shall check every file absent from the tree at the boundary at the full profile with no debt admitted, naming each new file in the report; evidence: fixtures for a new file (strict), an existing file (debt applies), a copy, a rename, a new folder and a file with a missing pragma (each strict). (serves EPC-024 AC-20)
- AC-3 A line or branch with no recorded boundary shall be reported `unproved`, never silently passed, and shall fail at `block`; evidence: a fixture per level. (serves EPC-024 AC-20)
- AC-4 Moving a boundary shall be a register event read only from the authority (a head-introduced move is refused for a blocking class, as TSK-424 AC-4 requires), and a later boundary shall only widen the strict set; evidence: the authority tests and a ratchet test. (serves EPC-024 AC-20)
- AC-5 `docs/test-gate.md`, `docs/policy-reference.md`, `cf-stack` and `cf-develop` shall state the mode and the boundary route; evidence: the text diff, both mirrors byte-identical.
- AC-6 (journey) With the installed build in a scratch adopter with admitted debt, a new module with one untyped function shall fail the quick gate while an existing module with the same debt passes, and the same new module copied from an existing one shall still fail; evidence: the journey output.
