# TSK-1047: New work starts from the live tip of the branch that holds the work it needs

## Description

The operator's rule of 2026-10-28, given for the away capability and
general by its wording: new work starts from the live tip of the branch
that already holds the work it needs. That is `main` when `main` has
it; when the needed work has landed on an epic or integration line that
`main` has not received yet, it is that line's tip; never a stale copy
of either. The target's current tip is merged in before review.

What enforces it today, by code reading on the line tip `654935d52`
(not reproduced in planning; AC-1 reproduces it):

- `codeflow work claim` fetches the target's remote and `origin`
  (`crates/codeflow-core/src/workgraph/readiness.rs:1652-1695`,
  `refresh_claim`), judges readiness on the target's live tip and
  creates the task branch there (`claim_on`, `:1734-1810`); with `--on`
  it stacks on a reviewed predecessor's pull request head, checked live
  (`crates/codeflow-cli/src/cmd/work.rs:445-473`). A standalone claim
  must contain its current target (`readiness.rs:1717-1722`). So the
  claim route starts from a live tip.
- `codeflow work start` checks planning and anchoring
  (`work.rs:314-361`, `plan_check`) but, as far as reading shows, not
  that HEAD contains the target's current tip, so a branch made by hand
  from `main` or from a stale copy of the line passes it.
- When the needed work landed on another line (for example an EPC-025
  task the EPC-022 task builds on, before that line is merged into
  EPC-022), readiness is judged on the task's own target, where the
  predecessor is not complete, so `work claim` refuses; whether `--on`
  accepts a predecessor whose pull request already merged into another
  line is not known.
- "Merge the current line in before review" is an instruction
  (`.codeflow/rules/worktrees.md:160-162`, the map's build row); no
  check reads it before review. TSK-1041 (EPC-023, 4.1.0) will report
  `base-moved` pull requests.

Outcome: **`work claim` chooses and records one base by the rule below,
`work start` refuses a branch that does not contain it, the route for a
predecessor on another line is one documented command that works, and
before review `codeflow ci` warns when the head does not contain its
target's current tip.**

The base rule (one rule, settled in planning after the Codex review of
PR 379):

```text
  for each predecessor of the task, at claim time, after a fetch:
    landed on the task's target       -> the target's live tip
    landed on another line that the   -> that line's live tip
      target has not received
    not landed, reviewed              -> its exact reviewed head, named
                                         with --on TSK@SHA (the existing
                                         pin rule, worktrees.md:60-64,
                                         task-graph.md:22-28)
  no predecessor needs another source -> the target's live tip
  predecessors on two different       -> refuse; name the line-sync route
    unmerged sources                     (issue #280)
```

Figure: how `work claim` picks the base. `main` is a valid base when it
is the target and holds the work; no rule prefers a line for its own
sake.

Rules:

- The base is fixed at claim. `work claim` records the base commit and
  its source in durable Git or claim metadata that does not depend on
  the coordination ledger (AC-1 decides which: the claimed branch's
  creation point as pushed, a note or ref beside it), because no gate
  reads the ledger (`docs/coordination-ledger.md:386-392`, TSK-422
  AC-8). A copy in the ledger for reporting is allowed. `work start`
  checks that HEAD contains that recorded base, and, for an unclaimed
  branch made by hand, the base the rule picks at start.
- A source that advances after the claim does not invalidate the start;
  `codeflow ci` warns until the target's current tip is merged in, which
  the contract already requires before review (`worktrees.md:160-162`).
- A reviewed pin stays valid while the predecessor's pull request head
  still equals the pinned SHA; when it moves, the old pin is refused
  naming the new head. After rebasing, an explicit replacement pin renews
  only the reviewed claim after current review, ancestry and planning checks
  pass and the new base is durably recorded, as the operator clarified.
- Fail closed: when the remote cannot be fetched, `work claim` and
  `work start` refuse admission, naming the remote and the last fetch
  time, because the live tip cannot be proven. `codeflow ci` cannot see
  the target's current tip in that case and reports it as unverified
  with a warning.
- A wrong base is a refusal at `work start` at the `git.work_planning`
  level the project sets, and a warning in `codeflow ci`, since an
  author merging the target in is the fix.

Non-goals: merging lines into each other (the epic's line-sync route,
issue #280); the full open-PR report (TSK-1041).

## Outcome

After this merges, builders start tasks from a verified prerequisite base, and
reviewers see a warning when the target has advanced beyond the task head.

  evidence: the record section, committed before the first code change in the PR.
- AC-2 `codeflow work start` shall refuse, at the project's `git.work_planning` level, a HEAD that does not contain the base the rule picks, naming the source, its tip and `codeflow work claim` as the route:
  (a) a branch made by hand from `main` while the needed work is only on the line: refused;
  (b) an unclaimed branch made from a stale copy of the line, older than the line's tip at the check: refused (a claimed branch keeps its recorded base, AC-4);
  (c) `main` as the target holding all the needed work: accepted from its tip;
  (d) the line's tip at claim: accepted;
  evidence: one CLI fixture per case, (a) and (b) failing before the change. (serves EPC-022 AC-151)
- AC-3 When a predecessor has landed on another line that the task's target has not received, `work claim` shall start the task from that line's live tip in one documented command and record that base, and `work start` shall accept it; predecessors on two different unmerged sources shall be refused with the line-sync route named; evidence: CLI fixtures for the cross-line case (failing before the change) and the two-source case. (serves EPC-022 AC-151)
- AC-4 The base shall stay valid in these cases:
  (a) the source line advances after the predecessor landed and after the claim: `work start` accepts the recorded base and reports the advance;
  (b) a reviewed stack with `--on TSK@SHA` at a reviewed head older than the line's tip: accepted while the predecessor's pull request head equals the pin, refused naming the new head once it moves; after rebasing, an explicit replacement pin renews only the reviewed claim after current review, ancestry and planning checks and a durable write;
  evidence: one CLI fixture per case.
- AC-5 When a pull request's head does not contain its target's current tip, `codeflow ci` shall warn, naming the target tip and the merge that clears it, and shall report the tip as unverified when it cannot read it; evidence: a CI fixture failing before the change, one passing after the merge, and one with the target ref unreadable.
- AC-6 When the remote cannot be fetched, `work claim` and `work start` shall refuse admission, naming the remote and the last fetch time; evidence: tests with the remote unreachable at claim and at start.
- AC-7 (journey) With the built binary in a scratch adopter repository with `main` and two lines, and a predecessor landed on line B that neither `main` nor line A has received:
  (a) `work claim` and `work start` for a dependent task on line A start it from line B's tip;
  (b) a hand-made branch from `main` is refused at `work start`;
  (c) after line A moves, `codeflow ci` warns until line A's tip is merged in;
  evidence: the journey output.
- AC-8 `work claim` and `work start` shall give the same verdict, and `work start` shall find the same recorded base, with the coordination ledger present, absent and damaged; evidence: fixture runs of each AC-2 to AC-4 case in all three ledger states. (serves EPC-022 AC-151)

## Investigation before implementation

Investigated on `cf9a0c9eaa208534c869e87d2d4f9520d910a79d`.
The worker is the operator-assigned Codex seat. The coordinator owns review.
Design intent: N/A, command admission and diagnostics only.

- Reproduced with the installed beta binary through `nice10.sh`, in a fresh
  scratch repository with `main`, `integration/a` and `integration/b`.
  A hand-made task branch at their common planning commit passed `work start`
  with exit 0 after line A advanced with the needed file. This is also the
  stale-copy case: its HEAD remained at A's previous tip. Expected refusal.
  A dependent task on A whose predecessor was complete only on B failed
  `work claim` with exit 1: `complete on 'integration/b' but not in this base`.
  These fixtures will become separate CLI regression cases before the fix.
- `readiness.rs:1931` selects a reviewed stack or the resolved target tip,
  reads that tree and validates readiness before creating the claim branch.
  It records no fixed base or source beside the branch. `refresh_claim`
  fetches the target remote and origin, but does not discover and fetch a
  predecessor's other remote. Its fetch error lacks the last-fetch time.
- `work.rs:385` resolves the target without fetching. `check_work_start_on`
  (`work_start.rs:1765`) checks pin ancestry and the planning anchor, not
  containment of the required base. Start must fetch before resolving pins
  and apply the new containment rule at `git.work_planning`.
- `code_dependency` (`work_start.rs:2810`) already finds a predecessor's
  declared line and checks its committed record there. Reuse that discovery,
  with the remote-owned tracking-ref reader, rather than guessing from branch
  names or asking the ledger. Two required unmerged sources refuse and name
  the line-sync route. Only code dependencies select a source; research and
  decision dependencies keep their existing pinned-input rules.
- `ci.rs:1841` runs the shared planning admission, including on pushes.
  Add a separate warning for target containment; do not put the new start
  refusal in shared admission. Target lookup failures report unverified.
  Pre-push invokes CI, so it inherits that warning without a hook change.
  Orient (`hooks/orient.rs:31`, `workgraph/line_drift.rs:49`) intentionally
  uses refs as last fetched and reports line-to-default drift. It needs no
  network call or new task-base admission duty.
- Record a claim in `refs/codeflow/claims/<task branch>` as an annotated Git
  object targeting the exact base, with versioned source, task, target,
  branch and reviewed pins in its message. It is shared by linked worktrees,
  survives ledger loss and keeps the task branch exactly at the selected
  base. Malformed metadata refuses; absence uses the fresh selection rule.
  Metadata is local claim evidence, never authority for a task plan or review.
  A fresh clone without it uses the unclaimed-start rule. No shared Git config
  write is needed, preserving the TSK-262 claim contract.
- Preserve the target's anchored task, epic and spec checks. For cross-line
  code dependencies, admit only committed completion at history shared by
  HEAD and the verified predecessor line. A source's advancing tip must not
  revoke a recorded base; reviewed pins still need live exact-head evidence.
  Use the guarded history reader so replace refs, grafts and shallow history
  cannot manufacture containment.
- The base rule refines worktrees.md item 3 to include already-landed work on
  another line. It does not merge lines, permit unreviewed stacks, change the
  target or change the task graph. This agrees with git-rules.md Bodies of
  work and task-graph.md's exact reviewed-head rule for unlanded predecessors.
  The managed rule, shipped asset, baseline and command docs change together.
- Verification will cover wrong and stale bases, main and line tips,
  cross-line and two-source selection, source advancement, moved reviewed
  pins, unreachable fetches, CI warnings before and after a merge, and missing
  target refs. Admission cases run with the ledger present, absent and damaged.
  The scratch adopter journey will drive the built binary with both lines.

## Reviewed-claim renewal clarification

The operator confirmed that `work start --on TSK@NEW_SHA` may renew only a
reviewed claim after current review, ancestry and planning checks. This keeps
the existing rebase route working when the predecessor rewrites its reviewed
head. Ordinary landed-source claims keep their fixed bases. A failed metadata
write blocks renewal even when planning findings are advisory.
