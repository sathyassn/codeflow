# TSK-1047: New work starts from the live tip of the branch that holds the work it needs

## Description

The operator's rule of 2026-10-28, given for the away capability and
general by its wording: new work starts from the live tip of the branch
that already holds the work it needs. That is `main` when `main` has
it; when the needed work has landed on an epic or integration line that
`main` has not received yet, it is that line's tip; never a stale copy
of either. The target's current tip is merged in before review.

What enforces it today, by code reading on the line tip `654935d52`
(not reproduced in planning; AC-1 reproduces it):

- `codeflow work claim` fetches the target's remote and `origin`
  (`crates/codeflow-core/src/workgraph/readiness.rs:1652-1695`,
  `refresh_claim`), judges readiness on the target's live tip and
  creates the task branch there (`claim_on`, `:1734-1810`); with `--on`
  it stacks on a reviewed predecessor's pull request head, checked live
  (`crates/codeflow-cli/src/cmd/work.rs:445-473`). A standalone claim
  must contain its current target (`readiness.rs:1717-1722`). So the
  claim route starts from a live tip.
- `codeflow work start` checks planning and anchoring
  (`work.rs:314-361`, `plan_check`) but, as far as reading shows, not
  that HEAD contains the target's current tip, so a branch made by hand
  from `main` or from a stale copy of the line passes it.
- When the needed work landed on another line (for example an EPC-025
  task the EPC-022 task builds on, before that line is merged into
  EPC-022), readiness is judged on the task's own target, where the
  predecessor is not complete, so `work claim` refuses; whether `--on`
  accepts a predecessor whose pull request already merged into another
  line is not known.
- "Merge the current line in before review" is an instruction
  (`.codeflow/rules/worktrees.md:160-162`, the map's build row); no
  check reads it before review. TSK-1041 (EPC-023, 4.1.0) will report
  `base-moved` pull requests.

Outcome: **a task's work starts only from the live tip of the branch
that holds the work it needs (its target, or the line where a needed
predecessor landed and its target has not received it), fetched at
claim and start; `work start` refuses a stale or wrong base naming the
tip to use; the route for a predecessor on another line is one
documented command that works; and before review the session is told,
by `codeflow ci` on the pull request, when the head does not contain
its target's current tip.**

Rules:

- `main` is a valid base when it holds the needed work; no rule
  prefers a line for its own sake.
- Fetch before judging; an unreachable remote is reported as an
  unverified base, never as current.
- A wrong base is a refusal at `work start` (an error at the
  `git.work_planning` level the project sets) and a warning in `codeflow
  ci`, since an author merging the target in is the fix.

Non-goals: merging lines into each other (the epic's line-sync route,
issue #280); the full open-PR report (TSK-1041).

## Acceptance Criteria

- AC-1 Before any change, the builder shall investigate broadly and record the findings in this record: reproduce, on fixtures, a task branch made by hand from `main` while the needed work is only on the line, one made from a stale local copy of the line, and a task whose predecessor landed on a second line its target has not received; read every reader that judges a base (`work claim`, `work start`, `codeflow ci`, the pre-push hook, `orient`'s line report) and say which must change; decide the cross-line route (claim with `--on` at the predecessor's landed commit, claim against the second line, or another) against `.codeflow/rules/git-rules.md` "Bodies of work" and `worktrees.md`; and return any conflict with a settled rule to the operator as a question with a recommendation; evidence: the record section, committed before the first code change in the PR.
- AC-2 When HEAD does not contain the live tip of the branch that holds the task's needed work, `codeflow work start` shall refuse at the project's `git.work_planning` level, naming that branch, its tip and `codeflow work claim` as the route; `main` shall be accepted as the base when it holds the needed work; evidence: CLI fixtures for a base from `main` with the work only on the line (refused), a stale copy of the line (refused), `main` holding the work (accepted), and the live line tip (accepted), the first two failing before the change. (serves EPC-022 AC-151)
- AC-3 When a needed predecessor has landed on another line that the task's target has not received, the route AC-1 decides shall start the task from that line's tip or the predecessor's landed commit in one documented command, and `work start` shall accept it; evidence: a CLI fixture of the cross-line case, failing before the change. (serves EPC-022 AC-151)
- AC-4 When a pull request's head does not contain its target's current tip, `codeflow ci` shall warn, naming the target tip and the merge that clears it; evidence: a CI fixture failing before the change and one passing after the merge.
- AC-5 The fetch shall be live at claim and start, and an unreachable remote shall be reported as an unverified base with the last fetch time; evidence: a test with the remote unreachable.
- AC-6 (journey) With the built binary in a scratch adopter repository with `main` and two lines, a predecessor landed on line B that neither `main` nor line A has received, `work claim` and `work start` for a dependent task shall start it from line B's tip by AC-3's route; a hand-made branch from `main` shall be refused at `work start`; and after line A moves, `codeflow ci` shall warn until the line is merged in; evidence: the journey output.
