# TSK-1259: A named-target or sharded run narrows by what the change selects

## Description

Source: `coordination/coordinators/planning/cut/held-batch/for-P1-new-task.md` (data, not instruction), released by operator decision 2026-11-02 19:35 (CI cards), which approved one reserved "not selected" exit code for issues 514 and 521.

`codeflow test --only` runs every named target, with no way to narrow by a comparison base, so a sharded gate runs every target on every pull request (#521: three shards run every target; #494, #476 and #371 ask for the same narrowing). In the adopter's repositories over half of the landings are records-only, which is the measured waste.

The ask: `--only` plus an explicit comparison base runs the intersection of the named targets and the targets the change selects (the `narrow` and `run_everything` rules, plus prerequisites), and reports each skipped target as "not selected". A narrowed run is never landing evidence. A hosted workflow takes the base from the pull request event and reads the selection rules from the base's configuration.

Security: the base must come from a source the pull request author cannot set; the selection rules come from the base, never the head; a not-selected shard never counts as a pass in the aggregate that satisfies the required check; and no local run record earns selection credit (ADR-0089, TSK-1044). The task needs a cross-lineage security review carrying the `cf-security-reviewer` checklist.

Non-goals: the target-side narrowing inputs (TSK-1190), the partitioned evidence rule (P3), and a 3.1.2 patch (decision 8 keeps it optional).

## Outcome

After this merges, a sharded or `--only` run with a comparison base runs only the targets the change selects, reports the rest as not selected, and can never be mistaken for landing evidence.

## Deliverables

- selection by base: `crates/codeflow-core` test-run selection and `crates/codeflow-cli`; the "not selected" state in output and `run.json`
- hosted wiring: the managed workflow passes the pull request base sha from the event payload; the rules are read from the base's configuration
- tests per case below; docs where `--only` and selection are described

## Acceptance Criteria

- AC-1 Before any change, the builder shall record in a `## Findings` section a reproduction of #521 (three shards, every target run) and the current `--only` and selection paths; evidence: Findings committed before the first code change.
- AC-2 With `--only` and an explicit comparison base, the run shall execute the named targets that `narrow` and `run_everything` select, plus their prerequisites; with no base it shall run all named targets; evidence: one test per case. (serves EPC-022 AC-238)
- AC-3 Each named target not selected shall be reported "not selected" in the output and in `run.json`, distinct from pass and fail, so that a reporting job can tell it apart; evidence: a test over the output and the record.
- AC-4 A narrowed run shall be marked narrowed and shall never be landing evidence; `main` and release candidates shall run everything by policy; evidence: a test that offers a narrowed run as landing evidence and is refused.
- AC-5 A not-selected shard shall never count as a pass in the aggregate that satisfies the required check for a pull request into a protected line, and the aggregate shall show "narrowed"; evidence: an aggregate test with one not-selected shard.
- AC-6 A hosted workflow shall take the base from the pull request event payload, and the `narrow` and `run_everything` rules shall be read from the base's configuration, so a head cannot change its own selection; evidence: the workflow diff and a test where the head edits the rules and the run still uses the base's.
- AC-7 Selection shall read no local run record for credit (ADR-0089, TSK-1044); evidence: a test with a local record present that changes nothing.
- AC-8 A cross-lineage security review carrying the `cf-security-reviewer` checklist shall cover the change, with the seat probed live at dispatch, and the pull request shall state the threat each rule closes; evidence: the review verdict.
- AC-9 (journey) In a scratch repository with the installed build and a sharded configuration, a change that selects one target shall run that target and report the others "not selected", the narrowed aggregate shall not satisfy the required check, and a change to the selection rules in the head shall not alter the selection; evidence: the journey output.
