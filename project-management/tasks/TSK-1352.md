# TSK-1352: The shipped CI places each suite by event as CodeFlow does, and a project can change it

## Description

Source: the CI suite placement records brief of 2026-11-05 (coord/records), item 4, after the operator's decision of 2026-11-05 15:57 ("A plus Linux off line PRs"), recorded in ADR-0097.

CodeFlow's own CI now places each suite by event (ADR-0097): pull requests into an integration line run only the short checks, and line pushes, pull requests into `main` and the scheduled runs run the full suites. The GitHub template CodeFlow scaffolds for adopters does not follow that placement (`assets/base/ci/codeflow-ci.yml` at `1107c5974`):

- It runs on every pull request, whatever its base, and on pushes to `main` and `master` only (`:26-35`). A push to an integration line runs no gate, so a project landing batches on a line has no hosted proof of the batch.
- It chooses the gate mode by event alone (`:45-47`, `:171-178`): every pull request runs `essential` when the test config has an essential target, so a pull request into `main` runs the same reduced gate as one into a line, where CodeFlow runs its full suites.
- It has no draft handling, so a draft pull request runs the whole gate.
- No adopter doc says which event runs which gate, or how a project changes it.

The other shipped templates are the GitLab template (`assets/base/ci/.gitlab-ci.yml`, which runs on merge requests and on the default branch only, `:53-55`), the Bitbucket template (`assets/base/ci/bitbucket-pipelines.yml`) and `ci-generic.sh` (`assets/base/ci/README.md:28-30`). AC-1 inventories them, and AC-8 brings them to the same placement where their host exposes the event and the target branch.

TSK-1026 edits the same trigger and mode block of the template (`:26-35`, `:170-198`) and adds an opt-in to run `essential` on push, so this task builds after it, and one placement setting shall serve both. A batch lands on a line as one push (ADR-0098), and an adopter uses lines only when no human merges task pull requests as they become ready, so the line-push trigger and its cancellation (AC-9) serve that case. Changing the adopter default is public behaviour, so the task is blocked on the operator's decision on that default (see `## Blocker`); AC-2, AC-8 and AC-9 state the default only as that decision sets it.

Non-goals: CodeFlow's own Windows and coverage suites, which adopters do not have; this repository's workflows (TSK-1321); any change that drops the secret scan or the policy check from an event that runs them today.

## Outcome

After this merges, and on the operator's decision on the default, a project that adopts CodeFlow's CI templates gets the same placement by default (short checks on pull requests into a line, the full gate on line pushes, pull requests into `main` and the scheduled run), sees it documented, and can change it in one declared place.

## Acceptance Criteria

- AC-1 Before any change, the builder shall list, for each shipped CI template (`codeflow-ci.yml`, `.gitlab-ci.yml`, `bitbucket-pipelines.yml`, `ci-generic.sh`), which gate each event runs today; evidence: the table in `## Findings`, with file:line for each row.
- AC-2 Only after the operator has decided the adopter default (`## Blocker`), the GitHub template's default shall be the placement that decision sets. The proposal put to the operator: only the short checks (the essential gate, or the full gate when the test config has no essential target, plus the policy check and the secret scan) on a ready pull request into an integration line; the full gate on a pull request into `main` or `master`, a push to `main`, `master` or an integration line, the weekly run and a manual run; and on a draft pull request the secret scan and the policy check only, with the gate starting when it is marked ready. Evidence: the decision's record, and workflow tests for each event, base and draft state.
- AC-3 When the event or the pull request's base cannot be read, the template shall run the full gate (fail closed), and a required check whose gate is not selected for the event shall pass with a "not selected" result that is never shown as gate evidence; evidence: tests for an unreadable base and for a not-selected gate.
- AC-4 A project shall be able to change which gate each event runs in one declared setting, read from the base side (the target branch's committed copy, as `codeflow-policy.yml` reads policy from the default branch) and never from the pull request head; `codeflow-ci.yml:177` reads `.codeflow/test-config.json` from the checkout, which is head-side, so that read cannot supply the setting; the setting shall refuse a placement that removes the secret scan or the policy check from an event; an absent setting gives the AC-2 default; evidence: tests for the default, an override, a refused override and a head-side edit that is ignored.
- AC-5 The adopter CI guide shall show the placement as a table by event, name the setting and its default, and point to ADR-0097 for CodeFlow's own choice; evidence: the text.
- AC-6 A hosted run on a sample repository scaffolded from this change shall show the short checks on a pull request into an integration line and the full gate on the push that lands it; evidence: both run ids. (journey)
- AC-7 The change shall have a cross-lineage review with the `cf-security-reviewer` checklist, since it changes which events run the trusted checks: Grok or Codex when a live probe at dispatch shows usage, else a fresh Claude Opus medium subagent with reduced assurance recorded; evidence: the review row and its findings record.
- AC-8 After the same decision, the GitLab and Bitbucket templates and `ci-generic.sh` shall apply the same placement and setting where their host exposes the event and the target branch; where it does not, they shall run the full gate and the guide shall say so for that host; evidence: per template, a test for a merge request or pull request into a line and for a push, a head-side edit of the setting that is ignored, and, for a host without the event or target branch, a run of the full gate.
- AC-9 After the same decision, a batch lands on a line as one push (ADR-0098), and that push's run is the batch's hosted proof; in each template whose host supports it, a newer push to a line shall cancel the older push run on that line, and pushes to `main` or `master`, scheduled runs and manual runs shall never be cancelled (the rule TSK-1313 sets for CodeFlow's own CI); where the host cannot cancel, every line push run finishes and the guide says so; evidence: a test of the cancellation group for each event, and a hosted pair of line pushes on the AC-6 sample repository showing the older run cancelled.
