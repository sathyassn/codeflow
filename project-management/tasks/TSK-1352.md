# TSK-1352: The shipped CI places each suite by event as CodeFlow does, and a project can change it

## Description

Source: the CI suite placement records brief of 2026-11-05 (coord/records), item 4, after the operator's decision of 2026-11-05 15:57 ("A plus Linux off line PRs"), recorded in ADR-0097. The adopter default is the operator's decision on this task of 2026-11-05 19:0x ("as you recommend - confirm it", relayed by the Director; workspace `RELEASE-PLAN.md`): the shipped CI template places suites by event as CodeFlow does.

CodeFlow's own CI now places each suite by event (ADR-0097): pull requests into an integration line run only the short checks, and line pushes, pull requests into `main` and the scheduled runs run the full suites. The GitHub template CodeFlow scaffolds for adopters does not follow that placement (`assets/base/ci/codeflow-ci.yml` at `1107c5974`):

- It runs on every pull request, whatever its base, and on pushes to `main` and `master` only (`:26-35`). A push to an integration line runs no gate, so a project landing batches on a line has no hosted proof of the batch.
- It chooses the gate mode by event alone (`:45-47`, `:171-178`): every pull request runs `essential` when the test config has an essential target, so a pull request into `main` runs the same reduced gate as one into a line, where CodeFlow runs its full suites.
- It has no draft handling, so a draft pull request runs the whole gate.
- It has no `concurrency` block, so a superseded push run is never cancelled.
- No adopter doc says which event runs which gate, or how a project changes it.

This task owns the gate mode: it chooses each event's gate mode by placement, read from the pull request's base (AC-6). It absorbs issue [#676](https://github.com/sathyassn/codeflow/issues/676) ("Managed gate mode ignores base kind and landing candidates"). TSK-384 consumes the mode this task sets and does not choose it. Added 2026-11-06 from the CI/CD coherence result of 2026-11-06 (workspace `coordination/briefs/cicd-coherence-result-2026-11-06.md`, "Where the reviews differed", rows on the gate mode and #676).

The other shipped templates are the GitLab template (`assets/base/ci/.gitlab-ci.yml`, which runs on merge requests and on the default branch only, `:53-55`), the Bitbucket template (`assets/base/ci/bitbucket-pipelines.yml`) and `ci-generic.sh` (`assets/base/ci/README.md:28-30`). AC-8 inventories them. Each criterion below applies to every shipped template where its host exposes the event and the target branch; where a host does not, that template runs the full gate and the guide says so for that host.

TSK-1026 edits the same trigger and mode block of the template (`:26-35`, `:170-198`) and adds an opt-in to run `essential` on push, so one placement setting shall serve both. Once TSK-1351 and the landing-rule ADR land, a batch lands on a line as one push, and an adopter uses lines only when no human merges task pull requests as they become ready; the line-push trigger and its cancellation (AC-3) serve that case.

Non-goals: CodeFlow's own Windows and coverage suites, which adopters do not have; this repository's workflows (TSK-1321); any change that drops the secret scan or the policy check from an event that runs them today.

## Outcome

After this merges, a project that adopts CodeFlow's CI templates gets the same placement by default (short checks on pull requests into a line and on drafts, the full gate on line pushes, pull requests into `main` and the scheduled run), sees it documented and in the release note, and can change it in one declared place.

## Acceptance Criteria

- AC-1 A ready pull request into an integration line, and a draft pull request into any base, shall run only the short checks: the essential gate (or the full gate when the test config has no essential target), the policy check and the secret scan. Short checks on an adopter's drafts are a deliberate difference from CodeFlow's own drafts, which run only the secret scan and the security review (ADR-0097), because the operator's decision names drafts with line pull requests; evidence: a workflow test per template for a ready line pull request and a draft pull request, and a hosted run of each on a sample repository scaffolded from this change. (journey)
  - Set 2026-11-05 from the operator's decision; it replaces the draft AC-2 proposal, which differed by running only the secret scan and the policy check on a draft.
- AC-2 A push to an integration line, `main` or `master`, a pull request into `main` or `master`, the scheduled run and a manual run shall run the full gate; evidence: a workflow test per template for each of these events, and the hosted run of the push that lands the AC-1 pull request on the sample repository. (journey)
  - Set 2026-11-05 from the operator's decision; with AC-1 it replaces the draft AC-2 proposal, and its hosted run replaces the draft AC-6 journey.
- AC-3 A newer push to an integration line shall cancel the older push run on that line; a run in progress for a push to `main` or `master`, a scheduled run or a manual run shall never be cancelled, though a host may still replace a pending run in the same group (the rule TSK-1313 set for CodeFlow's own CI); where a host cannot cancel, the guide says so for that host; evidence: a test that pins the cancellation group and cancel setting for each event, and a hosted pair of line pushes on the sample repository showing the older run cancelled and the newer one finished.
  - Set 2026-11-05 from the operator's decision; it replaces the draft AC-9 cancellation clause.
- AC-4 A batch shall land on a line as one push, and that push's full-gate run shall be the batch's hosted proof; a line pull request's short-check verdicts shall never be shown as the batch's proof. If TSK-1351 has not landed when this task is claimed, the builder adds TSK-1351 to `depends_on` and waits for its mechanism; evidence: the guide text that states it, and a hosted run on the sample repository where two pull requests land on the line in one push with one full-gate run for both.
  - Set 2026-11-05 from the operator's decision; it replaces the draft AC-9 batch clause, which cited the landing-rule ADR by number before that ADR existed.
- AC-5 When the event or the pull request's base cannot be read, the template shall run the full gate (fail closed). A gate that is not selected for the event shall never count as a pass of a required check; a "not selected" result, where TSK-1259 and TSK-1190 define it, is reported as an outcome that is not evidence and never as a pass (TSK-1259 AC-9); evidence: per template, tests for an unreadable event, an unreadable base and a not-selected gate that does not report a pass, and, for a host that cannot report the event or the target branch, a run of the full gate.
  - Amended 2026-11-06 from the CI/CD coherence result of 2026-11-06 (finding 3; Grok's finding 9): GitHub treats a skipped required check as a success, so a not-selected gate can never stand in for a pass. Earlier text of the second clause: "a required check whose gate is not selected for the event shall pass with a "not selected" result that is never shown as gate evidence". The fail-closed clause is unchanged.
- AC-6 A project shall be able to change which gate each event runs in one declared setting, read from the base side (the target branch's committed copy, as `codeflow-policy.yml` reads policy from the default branch) and never from the pull request head; `codeflow-ci.yml:177` reads `.codeflow/test-config.json` from the checkout, which is head-side, so that read cannot supply the setting. The setting shall refuse a placement that removes the secret scan or the policy check from an event. A reduced gate on pull requests into `main` or `master` shall run only when the setting names it explicitly, never by default or by inference. An absent setting gives the AC-1 and AC-2 placement. TSK-1026's essential-on-push opt-in shall read the same setting. The gate mode for each event shall be chosen by this placement, read from the pull request's base, or, for a push, a scheduled run or a manual run, from the target branch's committed copy; TSK-384 consumes that mode and does not choose it (issue #676). Evidence: per template, tests for the default, an override, a refused override, an explicit reduced gate on pull requests into `main`, and a head-side edit that is ignored.
  - Amended 2026-11-05 from the operator's decision; it adds the explicit opt-in for a reduced gate on pull requests into `main` and takes the per-template evidence of the draft AC-8, whose own text this criterion set replaces.
  - Amended 2026-11-06 from the CI/CD coherence result of 2026-11-06 ("Where the reviews differed", gate mode and #676): this task owns the gate mode by placement, read from the base, and absorbs issue #676; TSK-384 only consumes the mode. Added sentence: "The gate mode for each event shall be chosen by this placement, read from the pull request's base; TSK-384 consumes that mode and does not choose it (issue #676)."
  - Amended 2026-11-06 from the PR 631 review (Grok, nit 1): a push, a scheduled run and a manual run have no pull request, so the mode sentence adds that those events read the mode from the target branch's committed copy. Earlier text: "read from the pull request's base; TSK-384 consumes".
- AC-7 The release note shall state the behaviour change for adopters: pull requests into `main` and pushes to a line gain the full gate, pull requests into a line and drafts run only the short checks, a newer line push cancels the older run, and the setting that changes it, including how to opt back into a reduced gate on pull requests into `main`; evidence: `changelog.d/TSK-1352.md` and a passing release preflight.
  - Set 2026-11-05 from the operator's decision.
- AC-8 Before any change, the builder shall list, for each shipped CI template (`codeflow-ci.yml`, `.gitlab-ci.yml`, `bitbucket-pipelines.yml`, `ci-generic.sh`), which gate each event runs today; evidence: the table in `## Findings`, with file:line for each row.
- AC-9 The adopter CI guide shall show the placement as a table by event, name the setting and its default, say for each host what it cannot do, and point to ADR-0097 for CodeFlow's own choice; evidence: the text.
- AC-10 The change shall have a cross-lineage review with the `cf-security-reviewer` checklist, since it changes which events run the trusted checks: Grok or Codex when a live probe at dispatch shows usage, else a fresh Claude Opus medium subagent with reduced assurance recorded; evidence: the review row and its findings record.
