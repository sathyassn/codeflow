# TSK-1052: Runs after a same-line write fail closed on an unsandboxed host

## Description

Source: the operator's TSK-1002 scope decision of 2026-10-28 (the option
D scope in Fable's note `target/tsk1002-option-d-scope.md` in the
`guard-bypass-classes` worktree, recorded in `RELEASE-PLAN.md`). Four
review rounds on TSK-1002 (PR 346) reopened the same class: a file the
line wrote, or a tree it copied or extracted, runs through a route the
text guard did not list. Text cannot list every run route, so TSK-1002
withdraws "files run after a write" from the text guard's promise and
keeps its written-file checks as a filter. On a host where TSK-397's
`sandbox_state` shows the sandbox, the kernel contains the run; this task
supplies the fail-closed rule for every other host.

This is a follow-up of TSK-1002. TSK-1002 is a standalone task whose
record is not on this line yet (PR 346, open at `399594818`), so the
`depends_on` edge to it is added by the epic amendment that follows PR
346's landing, and PR 346 names this task in TSK-1002's `follow_ups`;
until PR 346 lands this task is blocked.

Outcome: **when TSK-397's `sandbox_state` selects the tightened outcome
(any readable trigger, a recognized unsandboxed retry, or
`security.text_guard = strict`), a line that writes a file whose contents
the guard did not read exactly refuses, as cannot-verify, every later
command on the same line that can run code: an interpreter, a shell,
Make, a launcher or runner, and any program the guard does not model. In
the baseline outcome the verdicts stay those of the line before this
task. No line the base refuses becomes allowed in either outcome.**

The rule generalises the checks the TSK-1002 builder reached for
recursive copies (`security/composed/paths.rs:1764`, `runs_after_tree`)
and for inline code with an unknown directory
(`security/interpreter.rs:134`), both at `399594818`.

Run routes the rule covers, each a fixture. Both guards allowed each one
at `399594818` and on the line base (the reviews' replays; nothing was
executed):

| Source | Route | Example |
|---|---|---|
| Codex review 04, finding 1 | child execution after a tree copy | `cp -r fixture/src fixture/out; xargs python3 <<< fixture/out/src/helper.py`; the `find -exec`, `uv run`, `poetry run`, `bundle exec` and `npm exec` siblings |
| Codex review 04, finding 2 | tree-producing operations | `tar xf fixture/archive.tar -C fixture/out; python3 fixture/out/helper.py`; the `unzip` and `ditto` siblings; new and overwritten destinations |
| Codex review 04, finding 4 | a command-hash binding | `cp fixture/source fixture/run; hash -p ./fixture/run fixture_tool; fixture_tool` |
| Fable review 06, Major 2 | bare names through launchers and runners after a `PATH` change | `printf x > run; chmod +x run; PATH=.:$PATH xargs run <<< a`, `xargs -I{} run {}`, `setsid run`, `npx run`, `npm exec -- run`, `uv run run` |
| Fable review 06, Major 2 | text tools that run commands | `PATH=.:$PATH awk 'BEGIN{system("run")}'`, `gawk`, `sed -e '1e run' notes.md` |

Controls that stay allowed in both outcomes, from the same reviews:
`printf x > notes.txt; cat notes.txt`, `cp -r src out; ls out`,
`cat out/notes.rs`, `git add out`, `PATH=.:$PATH ls`, and `cargo run` or
`npm test` on a line with no write before them.

Non-goals: containing what a program does once it runs (the sandbox's
job on a proven-sandboxed host; residual A6 of TSK-397's design D);
changing the baseline outcome's filter; modelling runner directories
(TSK-1053).
