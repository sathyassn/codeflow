# TSK-1052: Runs after a same-line write fail closed on an unsandboxed host

## Description

Source: the operator's TSK-1002 scope decision of 2026-10-28 (the option
D scope in Fable's note `target/tsk1002-option-d-scope.md` in the
`guard-bypass-classes` worktree, recorded in `RELEASE-PLAN.md`). Four
review rounds on TSK-1002 (PR 346) reopened the same class: a file the
line wrote, or a tree it copied or extracted, runs through a route the
text guard did not list. Text cannot list every run route, so TSK-1002
withdraws "files run after a write" from the text guard's promise and
keeps its written-file checks as a filter. Where the sandbox contains
the run, the kernel is the boundary; this task supplies the fail-closed
rule everywhere else.

This is a follow-up of TSK-1002. TSK-1002 landed in PR 346 on 2026-10-30
and the `depends_on` edge to it is recorded. Both prerequisites were
verified before this task was unblocked: PR 346 has landed, and
TSK-1002's landed record names this task in `follow_ups`.

### Where the rule applies

The rule applies to every command whose containment cannot be
established, decided by the coordinator on 2026-10-28 under the
operator's secure-by-default rule. TSK-397's design D (revision 4.1,
A6) leaves a command whose sandbox is ineffective but not readable as
such on the baseline rule: invisible overrides (a `--settings` file,
server-managed settings, MDM policy, a Codex launch with
`--sandbox danger-full-access` or the bypass flag) and unrecognized
unsandboxed retries (a Codex seat, which has no retry field, or a
Claude Code version not verified to deliver it). For this class those
unknown-containment cases move from TSK-397's baseline to this task's
fail-closed rule. TSK-397's Part A stays as approved; this task reads its
`sandbox_state` and adds the stricter condition for this class only.

Containment counts as established only from evidence the requester
cannot forge, hide or substitute. AC-1 records what TSK-397's
`sandbox_state` can establish in 4.0.0; design D ships no "observed
active" signal (its H-6), so where nothing establishes containment the
rule applies on every host, and AC-7 measures that cost.

### The rule

A same-line write is any write the guard models, known bytes included
(`printf x > run`, a literal heredoc, a copy, an extraction). Knowing a
file's bytes does not show that a later run of them was inspected.
After such a write, a later command on the same line that can run code
refuses as cannot-verify unless the guard verified that execution: the
program's execution identity is established (below) and the code it
runs is text the guard read and judged under that interpreter's grammar
in a known directory. Launchers and runners whose child the guard does
not read (`xargs`, `find -exec`, `setsid`, `npx`, `uv run`), text tools
that run commands (`awk system()`, GNU `sed e`), Make and every
program outside the guard's model are never verified.

Execution identity: a command name stands for a program only when it
resolves, at judgment time, to an executable the requester cannot
substitute. The guard checks the lookup state it can see, same-line and
inherited (`PATH`, including relative and project entries, hash
bindings, aliases, shell functions, exported functions and local
package directories such as `node_modules/.bin` or a virtual
environment), and the resolved file after links must lie outside every
location the session can write: the sandbox's write set where
containment is established, and every location the session user can
modify elsewhere. A name that does not resolve that way is an
unmodelled program. No allowance rests on a name alone.

It generalises the checks the TSK-1002 builder reached for recursive
copies (`security/composed/paths.rs:1764`, `runs_after_tree`) and for
inline code with an unknown directory (`security/interpreter.rs:134`),
both at `399594818`. Codex review 01 of PR 390 notes that
`composed/paths.rs:1565-1588` already keeps exact `printf` output and
literal heredoc bodies; this rule does not treat them as verified runs.

### Routes and controls

Each route is a fixture. Both guards allowed each one at `399594818`
and on the line base (the reviews' replays; nothing was executed):

| Source | Route | Example |
|---|---|---|
| Codex review 04, finding 1 | child execution after a tree copy | `cp -r fixture/src fixture/out; xargs python3 <<< fixture/out/src/helper.py`; the `find -exec`, `uv run`, `poetry run`, `bundle exec` and `npm exec` siblings |
| Codex review 04, finding 2 | tree-producing operations | `tar xf fixture/archive.tar -C fixture/out; python3 fixture/out/helper.py`; the `unzip` and `ditto` siblings; new and overwritten destinations |
| Codex review 04, finding 4 | a command-hash binding | `cp fixture/source fixture/run; hash -p ./fixture/run fixture_tool; fixture_tool` |
| Fable review 06, Major 2 | bare names through launchers and runners after a `PATH` change, from literal bytes | `printf x > run; chmod +x run; PATH=.:$PATH xargs run <<< a`, `xargs -I{} run {}`, `setsid run`, `npx run`, `npm exec -- run`, `uv run run`; the same with a literal heredoc as the writer |
| Fable review 06, Major 2 | text tools that run commands | `PATH=.:$PATH awk 'BEGIN{system("run")}'`, `gawk`, `sed -e '1e run' notes.md` |

Unknown-containment fixtures (Codex review 01 of PR 390, finding 1):
each route above judged with a Codex payload under a readable `cf-guard`
profile, a Claude Code payload without the retry field from a version
not verified to deliver it, and a host whose readable Claude settings
show the sandbox but whose containment `sandbox_state` cannot establish
(the case of a `--settings` file, server-managed settings or MDM
policy the guard cannot read).

Controls after a write, allowed in every case only while their
execution identity is established: `printf x > notes.txt; cat notes.txt`,
`cp -r src out; ls out`, `cat out/notes.rs`, `git add out` and
`PATH=.:$PATH ls`. Such a control whose name resolves into a location
the session can write, or through an alias, function or hash binding,
refuses like an unmodelled program. `cargo run` and `npm test` on a line
with no write before them are outside this rule and keep the base's
verdict.

Non-goals: containing what a program does once it runs (the sandbox's
job where containment is established); modelling runner directories
(TSK-1053); editing TSK-397's record or its decision rule.

## Outcome

After this merges, an adopter on any host where the guard cannot establish that the sandbox contains a command can rely on the guard to refuse any command that runs code after the same line wrote a file, unless the guard verified that run.

## Findings

### Investigation before implementation

The inspected line is `d2752c69d3bd077e693a28daceed38cc7f391911`.
`codeflow work start TSK-1052` confirms that TSK-397 and TSK-1002
are satisfied there. This section records source inspection only. No
cargo, test or CI command has run under the host pause. The sample counts
and runtime verdicts required by AC-7 remain unmeasured.

**Writers (AC-1a).** Shell output redirects, appends and heredoc-fed
redirects count, including exact output from `printf`, `echo` and `print`.
The command-position reader retains a plain `cat` heredoc body and exact
printed bytes, and marks other bodies unknown. It tracks copies, copy
children and recursive destinations, and operands of `tee`, `touch`,
`truncate`, `ed`, `ex`, `vi`, `vim` and `nvim`.
Sources: `crates/codeflow-core/src/security/composed/paths.rs:1510`,
`:1553`, `:1571` and `:1599`.

The shared writer table lists `cp`, `mv`, `ln`, `install`, `ditto`,
`tee`, `dd`, `truncate`, `touch`, `mkdir`, `mktemp`, `rm`, `rmdir`,
`unlink`, `chmod`, `chown`, `chgrp`, `shred`, `rsync`, `scp`, `tar`,
`bsdtar`, `gtar`, `unzip`, `zip`, `curl`, `wget`, `patch`, `trash`
and `trash-put`. GNU spellings and executable suffixes are normalized.
Its effects include named outputs, option-selected outputs, copy targets
and unnamed placement. Archive extraction, download remote names and
option-environment outputs must count even when the command-position
reader has no exact destination or bytes. Sources:
`crates/codeflow-core/src/security/unresolved.rs:39`, `:1078`,
`:1089` and `:1258`.

A program outside the model remains a possible writer. A spelling that
looks like a data reader is also a possible writer when its execution
identity is unknown. The existing reader predicate establishes spelling
and operation only; its system-directory test does not resolve PATH,
check ownership or permissions, or establish shell bindings. Sources:
`crates/codeflow-core/src/security/startup.rs:2213`, `:2223` and `:2234`.

**Runs and readable code (AC-1b).** Every unmodelled program is a possible
code runner. This includes Make, package runners, launcher children the
guard does not read, and command-executing text-tool options. Existing
code inspection covers shell inline bodies and stdin, literal written
shell bodies, and the interpreter families and file operands read by
`outward.rs`. Exact bytes alone never establish execution identity or
complete verification. Unknown directories, unread bodies, imports,
configuration and unmodelled options retain their uncertainty. Sources:
`crates/codeflow-core/src/security/composed/paths.rs:1633`, `:1657`,
`:1745`, `:1787` and `:1820`;
`crates/codeflow-core/src/security/interpreter.rs:27` and `:154`.
The new rule must retain all existing findings rather than replace their
checks with an allowance for an interpreter name.

**Execution lookup (AC-1c).** The composed evaluator tracks same-line
variables, aliases and functions. Its command-position reader starts
from an empty shell state; its writer variant imports selected variables
from the hook process. Neither path obtains the executing shell's hash
table, aliases or non-exported functions. An exported function in the
hook environment is evidence of uncertainty; its absence does not prove
that the executing shell has no function. Sources:
`crates/codeflow-core/src/security/composed.rs:1327`, `:2394`, `:3548`
and `:3661`;
`crates/codeflow-core/src/security/composed/paths.rs:92` and `:1476`.

Same-line PATH assignments and launcher assignments must invalidate
uncleared lookup state. Inherited PATH, relative or project entries,
`node_modules/.bin` and virtual-environment bins may select a substitute.
A resolved executable also needs its symlink chain and replaceable parent
directories checked against the session user's write authority. A list
of directory names or a non-writable file alone does not establish that
identity. The existing PATH heuristic compares written names and trees;
it does not establish lookup identity. Source:
`crates/codeflow-core/src/security/composed/paths.rs:1762`.

The hook payload supplies command text, working directory and a retry
marker. It supplies no authenticated snapshot of the execution shell's
bindings. Source: `crates/codeflow-core/src/hooks/git_guard.rs:285`.
Thus a clean hook-process environment or a requester-supplied identity
field cannot justify an allowance for a bare command name. How to obtain
trusted identity evidence for allowed controls remains unresolved; no
allowance should claim that evidence exists on this line.

**Containment (AC-1d).** The landed TSK-397 implementation selects strict
or relaxed text checks from policy. Its module explicitly says that the
previous sandbox-configuration attestation was removed. Neither outcome
establishes active containment. A recognized retry and native Windows
force strict checks; readable settings are used by doctor to inspect write
grants and do not attest a call's sandbox. Sources:
`crates/codeflow-core/src/hooks/sandbox_state.rs:1`, `:121`, `:185`
and `:205`. The task must therefore treat containment as unestablished
under both outcomes. Codex bypass launches, hidden settings, managed
policy and unrecognized retries gain no established-containment status.
A relaxed policy choice must not become a containment claim.
