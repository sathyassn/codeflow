# TSK-095: carry the target-side CI pin to every scaffolded platform

## Description

SPC-013 R-113 (recorded in TSK-101, built with TSK-107) owns
target-selected enforcement for 3.0.0:
the scaffolded GitHub workflow (`assets/base/ci/codeflow-ci.yml`) installs
the `codeflow` version pinned in the target-side scaffold state, never the
head's, and an upgrade takes two pull requests in order. The first raises
only the pin; the target's binary enforces it and the candidate is tested in
a separate job. The second carries `codeflow update` and is judged by the new
binary once the pin is on the target. That order matches the 3.0.0
CHANGELOG's upgrade note (upgrade the binaries first, then commit the policy
change from `codeflow update`). This task does not change the installer,
the enforcement selection, or the upgrade protocol.

This task carries the rest. The other scaffolded CI files still suggest
the `releases/latest` installer in a comment: `ci-generic.sh` (line 34) and
`bitbucket-pipelines.yml` (line 40) at `52c723c1f`. An adopter who follows
that comment gets whatever CodeFlow is newest, not the version that wrote
their scaffold, so checks drift from the files they judge. These platforms
get the same target-side pin, checksum verification and two-step order as
the GitHub workflow.
`doctor` detects the two-step state and explains it, the adoption guide
documents it, and a hosted run proves the pinned install.

Limit: on a GitHub `pull_request` event the workflow file itself runs from the
head, so a pull request that edits the workflow can change the install step.
The pin does not defend that edit; required review of `.github/workflows/`
and `.codeflow/` in the remote plane does. This task documents that
requirement in the adoption guide and does not configure repository settings.

TSK-089 (EPC-018, 4.0.0 line) kept the placeholder and recorded this
replacement as a follow-up whose trigger is the 3.0.0 publication; this task
is that follow-up. When TSK-089 lands later, its setup summary line about an
unarmed CI must be reconciled with this change.

Target release: 3.0.0 (delivery plan of 2026-09-26 evening), landing after
the GitHub workflow pin. Non-goal: CodeFlow's own
`.github/workflows/codeflow-ci.yml`, which builds from source, and the
GitHub scaffold workflow's install step, which is R-113's.

## Affected surfaces and interfaces

- `assets/base/ci/ci-generic.sh` and `assets/base/ci/bitbucket-pipelines.yml`,
  and their baseline copies. Each platform reads the target from its own
  pull request base; `ci-generic.sh` takes the target commit as a required
  input and refuses to guess it.
- `doctor`'s CI perimeter check (`crates/codeflow-core/src/doctor/`).
- `docs/adoption.md`.
- Adopters: `codeflow update` replaces an unmodified CI file and 3-way
  merges an edited one; the CHANGELOG says what an adopter who wired their
  own install should do.

## Acceptance Criteria

- [ ] When `ci-generic.sh` or the Bitbucket pipeline runs, it shall install
      the `codeflow` version pinned in the target-side scaffold state, never
      the head's, as the R-113 GitHub workflow does, and fail with a named
      error when the version is missing or unpublished; it shall carry the
      same checksum verification as the R-113 install: verify the release
      asset against the published checksum for that exact version and fail
      closed on a missing or mismatched checksum, with no fallback to an
      unverified download; `ci-generic.sh` shall refuse to run without the
      target commit; evidence: a shell test of each file against a fixture
      release layout, including a tampered asset and a missing checksum
      file.
- [ ] Given base and head fixture pairs on each platform whose pins are
      equal, raised with no other change, and lowered, the job shall install
      the target's pin, test the raised candidate in a separate step while
      the target's binary enforces, and fail a lowered pin while the
      target's binary still judges the change; an update pull request whose
      raised pin has not landed shall fail with the message naming the
      two-step order; evidence: a shell test over the pairs.
- [ ] No shipped CI file installs from or suggests `releases/latest`;
      evidence: a test that fails if any file under `assets/base/ci/`
      contains `releases/latest`.
- [ ] `doctor` shall detect a project whose head carries policy keys or
      schema its pinned binary cannot read while the raised pin has not
      landed, and explain the two-step order; its CI perimeter check shall
      describe the target-side pin instead of the placeholder; evidence:
      the doctor test for a pinned project, a pending two-step upgrade, and
      an unpinned one.
- [ ] The adoption guide shall document the target-side pin on every
      platform, the two-step upgrade order, and the remote review the
      workflow file itself needs; evidence: the diff.
- [ ] On a disposable sample repository scaffolded by the released binary,
      the pushed workflow's gates job installs the pinned version and runs
      green; evidence: the hosted run URL, or the step's output from a local
      runner if hosted Actions are unavailable, stated as such.
