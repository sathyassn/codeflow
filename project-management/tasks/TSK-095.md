# TSK-095: pin the scaffolded CI install to the target branch version

## Description

The CI workflow CodeFlow scaffolds into adopters
(`assets/base/ci/codeflow-ci.yml`) has an "Install codeflow" step in two jobs
(lines 39 to 44 and 156 to 161 at `e49726807`) that is a placeholder: it
fails red on purpose, and its comment suggests the `releases/latest`
installer. An adopter who follows that comment gets whatever CodeFlow is
newest, not the version that wrote their scaffold. Checks then drift from the
files they judge: for example, a newer binary may not know that an
unmodified managed file is exempt from the dash scan, or may apply a default
the project never saw. This task replaces the placeholder with an install of
the version recorded in `.codeflow/project.toml` (`scaffold_version`),
verified by checksum, so CI runs the same rules as the scaffold it checks.

The version that selects the enforcement binary comes from trusted target
side state, never from the pull request head alone. A checksum proves the
bytes of a genuine release, not that the release is allowed to enforce the
target's current gates; if the workflow read the head's value, a pull request
could lower it and be judged by an older release that lacks a check. So:

- On a pull request, the floor version is `scaffold_version` at the pull
  request's base commit. On a push to a protected branch, the pushed commit
  is the target state and supplies it.
- A head value equal to the floor installs the floor.
- A head value below the floor fails the job with a named downgrade error,
  and the floor release still runs every gate against the head, so the
  target's checks judge the change.
- Upgrade path: a head value above the floor, as `codeflow update` writes, is
  honored only for a published release with a matching checksum. That
  candidate runs every gate the floor would run, with no job skipped. The
  candidate judges an upgrade rather than the floor because an older release
  refuses policy keys a newer update adds (the 3.0.0 CHANGELOG records this
  for `git.pr_release_impact`), so the floor cannot read the head it would
  judge. The raise is a visible `.codeflow/project.toml` change reviewed under the
  target's rules, and it becomes the floor only after it merges.

Limit: on a GitHub `pull_request` event the workflow file itself runs from the
head, so a pull request that edits the workflow can change the install step.
The pin does not defend that edit; required review of `.github/workflows/`
and `.codeflow/` in the remote plane does. This task documents that
requirement in the adoption guide and does not configure repository settings.

TSK-089 (EPC-018, 4.0.0 line) kept the placeholder and recorded this
replacement as a follow-up whose trigger is the 3.0.0 publication; this task
is that follow-up. When TSK-089 lands later, its setup summary line about an
unarmed CI must be reconciled with this change.

Target release: the first release after 3.0.0 is published (3.0.1 if it is
ready, else 3.1). Trigger: the v3.0.0 release assets exist publicly.
Non-goal: CodeFlow's own `.github/workflows/codeflow-ci.yml`, which builds
from source.

## Affected surfaces and interfaces

- `assets/base/ci/codeflow-ci.yml` (both jobs), `ci-generic.sh` (line 34)
  and `bitbucket-pipelines.yml` (line 40), which carry the same `latest`
  suggestion, and their baseline copies.
- `.codeflow/project.toml` `scaffold_version`, read at the target side, becomes
  an input to CI; `init` and `update` already write it. Each platform reads
  the target from its own pull request base; `ci-generic.sh` takes the target
  commit as a required input and refuses to guess it.
- Adopters: `codeflow update` replaces an unmodified workflow and 3-way
  merges an edited one; the CHANGELOG says what an adopter who wired their
  own install should do.

## Acceptance Criteria

- [ ] When the scaffolded workflow runs, each job shall resolve the floor
      version from `.codeflow/project.toml` at the target side (the pull
      request base commit, or the pushed commit on a protected branch),
      install that release, verify the archive against the release's
      published checksum, and fail with a named error when the version is
      missing, unpublished, or the checksum differs; evidence: a workflow
      YAML test for the steps and a shell test of the install script against
      a fixture release layout.
- [ ] Given base and head fixture pairs whose versions are equal, raised and
      lowered, the resolver shall install the floor, the checksum-verified
      candidate, and the floor with a named downgrade failure respectively,
      and every gate job shall run in all three; evidence: a shell test over
      the three pairs.
- [ ] Given a pull request that lowers `scaffold_version` while changing a
      protected surface that the floor release blocks and the lowered
      release would pass, CI shall fail, and the report shall show both the
      downgrade error and the floor release's block of that change; evidence:
      a test on a fixture repository with two fixture releases.
- [ ] When `codeflow update` raises the version on a pull request, that pull
      request's gates run the candidate release, and after it merges the
      next run's floor is the new version with no edit to the workflow;
      evidence: a test that resolves the version before, during and after an
      update of a fixture project.
- [ ] No shipped CI file installs from or suggests `releases/latest`;
      evidence: a test that fails if any file under `assets/base/ci/`
      contains `releases/latest`.
- [ ] On a disposable sample repository scaffolded by the released binary,
      the pushed workflow's gates job installs the pinned version and runs
      green; evidence: the hosted run URL, or the step's output from a local
      runner if hosted Actions are unavailable, stated as such.
- [ ] `doctor`'s CI perimeter check and the adoption guide describe the
      target side pin, the upgrade path, and the remote review the workflow
      file itself needs, instead of the placeholder; evidence: the diff and
      the doctor test.
