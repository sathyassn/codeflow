# TSK-370: The shipped pipeline verifies each change with targeted checks and quick

## Description

Source: the operator's decision of 2026-10-17, during the gate efficiency
amendment, to change the shipped adopter pipeline default to targeted
checks plus the quick gate for each change, with one full gate per
landing.

The shipped develop pipeline (`assets/base/claude/workflows/pipeline.workflow.js`,
installed at `.claude/workflows/pipeline.workflow.js`) ends its final
verification stage with `codeflow test --mode essential --strict` whenever
a target defines an essential mode, else `codeflow test --mode quick
--strict` (near line 252). `cf-develop` and the managed `AGENTS.md` "build"
row already say a builder cites targeted tests and the quick gate and the
full gate runs once on the landing candidate, so the shipped pipeline
contradicts the shipped method. This repository's own copy is user-owned
and `codeflow update` never rewrites it.

Outcome: the shipped pipeline's verification stage runs the affected
targeted checks (including a heavy-mode check through `--only` where a
check exists only in that mode) and `codeflow test --mode quick --strict`,
and states that the primary runs one full gate on the landing candidate;
this repository's copy matches.

Kept as it is: `--strict` (a NoTargets run is not verification) and the
rule that any nonzero exit is `changes_requested`. Product surface:
adopter-facing scaffold (CAP-010 duo orchestration and the managed
workflow).

## Deliverables

- the shipped pipeline: `assets/base/claude/workflows/pipeline.workflow.js` (the final verification stage prompt) with its manifest entry and managed baseline updated as the repository's wiring rule requires
- this repository's copy: `.claude/workflows/pipeline.workflow.js`
- docs that describe the pipeline's verification stage (the builder finds them; at least the pipeline section of the `cf-develop` or orchestrator references where they mention it)
- release note: `changelog.d/TSK-370.md`, stating the changed default and that a project wanting essential runs per change can say so in its own copy

## Acceptance Criteria

- AC-1 The shipped pipeline's final verification stage shall run the
  affected targeted checks and `codeflow test --mode quick --strict`, shall
  not run a whole essential gate, and shall state that the primary runs one
  full gate on the landing candidate; evidence: the diff and a test of the
  stage prompt text. (serves EPC-022 AC-57)
- AC-2 A NoTargets quick run and any nonzero exit shall still give
  `changes_requested`; evidence: the unchanged strictness text and its
  test.
- AC-3 `codeflow update` shall deliver the new default to a project whose
  installed copy is unmodified and keep a project's edited copy, with a
  release note that names the change; evidence: update tests for both
  copies and the fragment.
- AC-4 (journey) A fresh `codeflow init --standard` project shall get the
  new stage, and a project updated from 3.1.0 with an unmodified copy shall
  get it too; evidence: the two installed files.
