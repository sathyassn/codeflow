# TSK-370: The shipped pipeline verifies each change with targeted checks and quick

## Description

Source: the operator's decision of 2026-10-17, during the gate efficiency
amendment, to change the shipped adopter pipeline default to targeted
checks plus the quick gate for each change, with one full gate per
landing.

The shipped develop pipeline (`assets/base/claude/workflows/pipeline.workflow.js`,
installed at `.claude/workflows/pipeline.workflow.js`) ends its final
verification stage with `codeflow test --mode essential --strict` whenever
a target defines an essential mode, else `codeflow test --mode quick
--strict` (near line 252). `cf-develop` and the managed `AGENTS.md` "build"
row already say a builder cites targeted tests and the quick gate and the
full gate runs once on the landing candidate, so the shipped pipeline
contradicts the shipped method.

Ownership stays as it is (the primary's decision of 2026-10-17, after the
Codex confirmation review of PR 226, finding F7): the pipeline is
user-owned (`assets/base/scaffold-manifest.toml`, `ownership =
"user-owned"`), seeded once and never rewritten by `codeflow update`
(`crates/codeflow-core/src/scaffold/update.rs`, the user-owned branch).
Fresh installs get the new default. Existing copies, this repository's
included, are never rewritten; the release note and the `codeflow update`
output tell adopters the exact one-line edit that adopts the new default,
and `codeflow doctor` reports when an installed pipeline still runs
essential per change. There is no ownership migration.

Outcome: a freshly installed pipeline's verification stage runs the
affected targeted checks (including a heavy-mode check through `--only`
where a check exists only in that mode) and `codeflow test --mode quick
--strict`, and states that the primary runs one full gate on the landing
candidate; an adopter with an existing copy is told the one-line edit and
`codeflow doctor` reports the old default; this repository's own copy gets
that edit by hand in this task.

Kept as it is: `--strict` (a NoTargets run is not verification) and the
rule that any nonzero exit is `changes_requested`. Product surface:
adopter-facing scaffold (CAP-010 duo orchestration and the user-owned
workflow) and engine (the update notice and the doctor check).

## Deliverables

- the shipped pipeline: `assets/base/claude/workflows/pipeline.workflow.js` (the final verification stage prompt); its manifest entry stays `user-owned`
- the update notice: the `codeflow update` output for a project whose pipeline still holds the old stage, naming the one-line edit (`crates/codeflow-core/src/scaffold/update.rs` or its report)
- the doctor check: a `codeflow doctor` finding when an installed pipeline still runs essential per change (`crates/codeflow-core/src/doctor/`)
- this repository's copy: `.claude/workflows/pipeline.workflow.js`, edited by hand with the same line
- docs that describe the pipeline's verification stage (the builder finds them; at least the pipeline section of the `cf-develop` or orchestrator references where they mention it)
- release note: `changelog.d/TSK-370.md`, stating the new default for fresh installs, that existing copies are not changed, the exact one-line edit, and that a project wanting essential runs per change keeps its copy as it is

## Acceptance Criteria

- AC-1 The shipped pipeline's final verification stage shall run the
  affected targeted checks and `codeflow test --mode quick --strict`, shall
  not run a whole essential gate, and shall state that the primary runs one
  full gate on the landing candidate; evidence: the diff and a test of the
  stage prompt text. (serves EPC-022 AC-57)
- AC-2 A NoTargets quick run and any nonzero exit shall still give
  `changes_requested`; evidence: the unchanged strictness text and its
  test.
- AC-3 `codeflow update` shall never rewrite an existing pipeline copy,
  unmodified or edited, and when the copy still runs essential per change
  its output shall name the exact one-line edit; the release note shall
  state the same edit; evidence: update tests asserting unchanged bytes for
  an unmodified 3.1.0 copy and an edited copy, the printed edit, and the
  fragment.
- AC-4 `codeflow doctor` shall report an installed pipeline that still runs
  essential per change, naming the edit, and shall report nothing for one
  that runs targeted checks and quick; evidence: doctor tests for both.
- AC-5 (journey) A fresh `codeflow init --standard` project shall get the
  new stage; a project updated from 3.1.0 shall keep its pipeline bytes,
  see the edit in the update output and in `codeflow doctor`, and pass
  `codeflow doctor` after applying that edit; evidence: the installed
  files, the update output and the doctor runs.
