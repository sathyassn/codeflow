# TSK-096: highlight edge clicks and browser coverage for the comment chip

## Description

The 3.0.0 readiness fix for the `cf-present` comment chip (`7086763ea` and
`0ec6ffb7b` on `chore/release-assembly`, reviewed as
`fix/present-chip-linux`) stops a click on a captured text highlight from
opening an Element chip. It decides "on the highlight" from the range's
glyph boxes (`capturedSelectionCovers` in
`crates/codeflow-present/web/src/chrome.tsx`), while Blink's caret hit test
covers a wider area, so a click in blank space at the edge of a highlight can
still pin an element. Both reviewers accepted this as a stated boundary, not
a regression, and both recorded that the fix was proven only in Chromium on
macOS, with a 200 ms held press standing in for the 0 ms drag delay on Linux
and Windows. This task settles the edge behaviour and proves the chip in the
browsers and systems the utility claims.

Planning amendment (2026-09-27, operator direction): the proof is local
tests only, with no hosted CI run. AC-3 therefore asks for Chromium,
Firefox and WebKit on the local macOS host and names native Linux and
native Windows as not run: no such host exists locally, and the Docker
daemon is not running and is not started for this task. That is a gap in
coverage, recorded as one.

Target release: 3.1. Non-goal: any other chip or composer behaviour, and the
full platform qualification TSK-007 owns (state, process, launch and cleanup
adapters per operating system).

## Affected surfaces and interfaces

## Acceptance Criteria

- AC-1 Given a captured text highlight, when the operator clicks in blank
      space inside the highlight's line box but outside its glyph boxes, the
      chip shall behave as the settled rule says (either no Element pin, or
      an Element pin that is documented as intended); evidence: a
      browser-check case that clicks at a computed point just past the last
      glyph of the highlight and asserts the settled result.
- AC-2 A drag that starts on the highlight or at its edge still makes a new
      text selection, and a press elsewhere still pins an element; evidence:
      the existing glyph and padding cases pass unchanged.
- AC-3 The chip cases pass in Chromium, Firefox and WebKit on the local
      macOS host, where Chromium takes the 200 ms held press that stands in
      for the 0 ms drag delay of Linux and Windows. Native Linux and native
      Windows are not run, because no such host is available locally, and
      the Closeout says so; evidence: the run log per browser on macOS, and
      the not-run line with its reason.
- AC-4 Browser runs use task-owned profiles and never the operator's browser;
      evidence: the teardown lines of each run.

## Closeout

The comment chip now follows one edge rule in Chromium, Firefox and WebKit:
the painted highlight decides. Evidence is at `283bf64d5` on
`task/TSK-096-chip-edge-clicks`.

- Edge rule (AC-1): a click just past the last glyph of a captured
  highlight, in the same line box, is a click on the paragraph. It drops the
  text pin, releases the highlight and pins the element, as any other click
  does. A click on the glyphs only dismisses the Text chip. The check clicks
  2 px past the computed end of "Review" and asserts an Element chip with no
  highlight left (`browser-check.mjs`, "TSK-096 edge rule").
- Drags (AC-2): a held press on the highlight while its chip shows starts a
  new selection ("eview me"), as it does after Escape. Escape, composer
  Cancel and the chip's esc button each release the highlight. The existing
  glyph and padding drag cases pass unchanged.
- Engines (AC-3): `npm run check:browser` runs the chip cases in Chromium,
  and with `CF_PRESENT_CHIP_ENGINES=firefox,webkit` also in Firefox and
  WebKit, on the local macOS host. The run logs print "firefox: interactive
  surface and comment chip cases passed" and the same for WebKit. The 200 ms
  held press stands in for the 0 ms drag delay of Linux and Windows.
- Not run: native Linux and native Windows, because no such host is
  available locally.
- Profiles (AC-4): every browser the check launches keeps its Playwright
  profile in a directory the check creates, and each close must leave its
  engine's profile gone. Each run prints "<engine>: teardown passed". The
  Chromium binary is the installed Chrome app, run headless as its own
  instance with that profile, never the operator's browser session.
- Flake fixed: the element-excerpt save in `check:browser` failed about
  once in 15 runs, in WebKit and in Firefox; the composer held an empty
  note ("Write a note before saving."). Cause: leaving element pick mode
  handed focus back to the Pick element tool for one frame before the
  composer took it, so text typed in that frame went to the button. Leaving
  the mode after a pick no longer refocuses the tool, and the check asserts
  that focus never returns to it (it fails on the old code). 10 paired
  three-engine runs at load 10 to 16 then passed. The save click is
  unforced and a stuck save names the composer state.
- Also fixed (Fable's P3): a pin dropped by Escape, the chip's esc or a
  click on its own highlight no longer leaves the rail status reading
  "Pinned: ..."; the check asserts it after each.
- Gates at `283bf64d5`: `npm run check`, `check:browser` in both
  configurations, `check:matrix`, `check:entities` pass;
  `cargo test -p codeflow-present` 155 passed; `present_cli` 12 passed and
  1 ignored; clippy and fmt clean.
