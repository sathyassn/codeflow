# TSK-1073: The guards read command lines through a qualified shell parser

## Description

Source: issue #404 (CodeFlow 3.1.1). git-guard and exec-guard read a
Bash call as text and with their own word readers, so quoted data can
be read as code or as a path. The issue asks for a real shell parser
whose tree the existing rules judge.

What the line already does, rechecked on 2026-10-29 with the line's
binary at `bd721f39b` through `codeflow hook git-guard` and `exec-guard`
(the issue gives descriptions, not exact lines, so each row was rebuilt
from its description):

- A literal assignment earlier on the same line resolves (TSK-406): the
  issue's `git -C "$W" show`, `git -C "$R" ...`, `sed -i` under `$D` and
  `tar -xf $D/... -C $D/...` all pass when the line assigns the
  variable, in `;`, `&&`, newline, `export` and pipe shapes. A variable
  the line does not assign, or one filled by a substitution
  (`D=$(mktemp -d)`), stays refused, as the issue's own proposal keeps.
- Quoted patterns and prose given to `grep`, `rg`, `echo`, `printf`
  and `cat` pass. A peer's headless form as data passes too: in a `cat`
  or `tee` heredoc and in `gh pr comment --body "codex exec ..."`.
- Still refused by exec-guard: a chained launcher (`; su`) in quoted
  data given to any program outside the certified-prose grammar
  (`gh pr comment 1 --body "the text ; su in prose"`, a `tee` heredoc
  holding `; su`), and the cases TSK-415, TSK-417, TSK-1024 and TSK-1072
  own. A peer's headless form in interpreter code (a Python heredoc) is
  refused on purpose (below).

Outcome: **an agent can pass quoted data to a program whose identity
and argument grammar the guard establishes, without a false refusal,
while every line the guards refuse without the parser, where its text
can run, stays refused.**

The base verdict below is the verdict both guards give on the revision
at which this task starts, after TSK-1072 has landed, with the parser
out of the path; a parse error or a disagreement uses that column.

Rules this task follows:

- Fail closed. The parser reading may only relieve the classes AC-5
  lists. A parse error, an unsupported construct, a dialect difference
  between the shells the harnesses run, or any disagreement between the
  parser and TSK-397's lexer (`security/shell_lex.rs`, from PR 331) on
  command or word boundaries leaves the line with the base verdict, and
  so does a line the lexer marks `opaque` (a construct it does not model
  in full) or `current_shell` (a `${ cmd; }` substitution).
- Build on TSK-397's lexer, never replace it here. It is the directory
  lexer of TSK-397's checks, which treat an opaque line's directory as
  unknown; it stays that, and becomes the divergence check. Retiring
  either reader is a later decision that needs this task's
  qualification evidence.
- Execution identity (EPC-022, Guard scope follow-ups amendment): no
  allowance rests on a command name alone. Data relief needs the
  program to resolve to an executable the requester cannot substitute,
  through the resolution TSK-1053 builds.
- Directories: the operator decided on 2026-10-25 that narrowing after
  `cd` cannot be made sound, so the parser does not narrow a directory.
  The issue's request to track `cd`, `pushd` and `popd` is not taken
  unless the operator revisits that decision.
- Classes with their own owners, which this task does not re-enter: a
  file run after a same-line write (TSK-1052) and an unmodelled
  runner's child directory (TSK-1053), the two classes option D takes
  out of the text guard's promise (TSK-1002, PR 346); content already in
  committed history, outside the promise by the operator's direction of
  2026-10-29 on TSK-1002 AC-15 (PR 346); a Git program variable before a
  program that runs Git (TSK-1053 AC-17, expected to close in PR 346);
  and a program-valued Git setting on a visible `git` call (TSK-1065).

Deliberate text scans that stay (the issue's trade-offs):

- content written to an executable file, a `.sh` path, a startup file
  or an enforcement path, and a file run later on the line or in a
  later call (TSK-1052's class);
- interpreter code: a heredoc or `-c` text given to a shell or an
  interpreter is code, so a launcher word or a peer's headless form in
  it stays refused (the issue's session rows 5 and 8). Relieving a
  string literal there needs a language reader, as TSK-413 does for
  git calls; that is not planned here;
- shell `-c` strings, `eval`, `trap`, `ssh` remote commands, and the
  templates of `xargs`, `find -exec` and `parallel` are code.

Placement: EPC-022, 4.0.0 by the operator's decision of 2026-10-29.
The planning pull request for issue #404 first recommended 4.1.0
(EPC-023), because the task needs a new parser dependency, execution
identity and a qualification corpus run under real shells; the
operator chose the current release. Its qualification (AC-3) is part
of this task and ships with it.

## Outcome

After this merges, an agent can pass quoted prose, patterns and message text to an identified program without a guard refusal, and every line the guards refuse without the parser, where its text can run, is still refused.
