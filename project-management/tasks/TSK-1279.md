# TSK-1279: Heavy runs keep the caller's job cap and each target's declared workers and exclusivity

## Description

Reported by coord/parallel on 2026-11-03 at about 02:05, from the TSK-450 lane (evidence: `coordination/coordinators/planning/evidence/reserve-jobs/finding.md`, kept outside the repository). The command `sh coordination/scripts/nice10.sh codeflow reserve -- cargo test -p codeflow-cli --test ci_pin --test policy_cli`, run with the binary built at c2 head `8a32a233b`, exports `CARGO_BUILD_JOBS=2` (`coordination/scripts/nice10.sh:16`) at nice 10. It printed "codeflow reserve: 3 heavy runs share this host's 10 jobs; this command uses 3" and "[codeflow reserve] workers: jobs=3, nextest=3, rust-tests=1, oracle=3" (pid 13748, exit 101). The caller's cap of 2 jobs was raised to 3 under contention.

Related, from c2's gate log (`evidence/coverage-timeout/c2-gate.txt:1419`): `read-benchmark` ran with `jobs=3, nextest=3`, although its entry in `.codeflow/test-config.json` declares `"workers": 9` and `"exclusive": true`. TSK-1145 AC-4's key is `host_exclusive: true`, so `exclusive` may not be the key the admission reads, and the declared exclusivity was not honoured.

Follow-up of TSK-1145 (complete), which added capacity admission. Related: TSK-1278 supplies the typed result that marks termination unconfirmed after incomplete cleanup. This task owns retaining the allocation and exclusive host lease for that result, as well as the cap, declared workers and exclusivity. Duplicate check (coord/planning): TSK-1128 (complete) covers reserve's lock hand-over, not job counts; TSK-1010 (EPC-023, todo) covers named shared resources; TSK-1189 covers wait records; no unpushed record in this pull request covers it.

Owner: coord/planning (builder to be staffed). Adopter-facing: the shipped test-config templates and reference carry the same key.

### Caller cap contract

`CARGO_BUILD_JOBS` accepts an optional ASCII sign followed by decimal digits
within the signed 32-bit integer range, or the exact lowercase word `default`.
Leading zeros and a leading plus are accepted; whitespace is not trimmed.
Positive integers mean that many jobs. Negative integers normalize to the
logical CPU count plus that value, with a minimum of one. `default` normalizes
to the logical CPU count. Resolve that count once per invocation, using one
if the platform cannot report it. An absent variable adds no cap. Zero,
including signed zero, empty text, whitespace, malformed text, overflow and
non-Unicode values refuse before any target starts, naming the variable and
whether it came from the caller or target configuration. Normalize to a
positive decimal count for child processes, then limit by the host, configured
budget and any smaller caller or target cap. A target's `default` never clears
a smaller inherited caller cap. Tests inject the CPU count and check the
normalization independently of host load.

### Exclusive queue contract

This queue gives exclusive requests priority over later shared arrivals among
queue-aware binaries. Already admitted work finishes normally. Older binaries
take shared admission without checking tickets and may delay an exclusive
request until its bounded wait expires; FIFO fairness cannot be promised
against those arrivals. Keep the real host-lock, legacy-slot and live-orphan
checks and disclose this limitation in `changelog.d/TSK-1279.md`.

- Ownership and publication: after releasing its shared lease and slot, the
  requester takes the queue mutex, creates a uniquely named stable ownership
  file such as `owners/<ticket-id>.lock`, and locks it. This file stays at the
  same name and remains locked through the entire wait and run. Under the
  mutex, allocate and record the next monotonic sequence, write a complete
  queue record under a temporary name, then close every record handle before
  atomically renaming it to `queue/<seq>-<ticket-id>`. No process holds a queue
  record open across mutation or waiting. The visible rename is publication
  and defines arrival order. Release the mutex only afterwards. No live record
  is published before ownership is locked. Counter gaps are valid; ownership
  identifiers and live sequence numbers are never reused.
- Shared admission: under that same mutex, reclaim only provably unowned
  tickets and inspect the queue. An earlier exclusive ticket defers the
  arrival; it waits outside the mutex without a shared lease or slot. If the
  queue permits it, take all required shared leases and slots non-blockingly
  before releasing the mutex. On contention or an error, release partial
  admissions before waiting or refusing. No blocking host wait holds the
  queue mutex. The same rule applies when ordinary successors reacquire.
- Exclusive admission: only the first owned visible record may attempt the
  real exclusive host lock and all legacy-slot/orphan checks. After the
  exclusive lease and holder record are established, remove its queue record
  under the mutex to complete the handoff. Keep its separate ownership file
  locked for the run, including any termination-unconfirmed retention. The
  exclusive lease protects the handoff while the ownership file remains stable.
- Cancellation and normal exit: under the mutex, close any queue-record
  inspection handles and remove the requester's queue record first (already
  absent after successful admission is valid). Only then unlock and close the
  ownership handle and remove the ownership file. Keep the mutex through this
  sequence. A record-removal error retains ownership and refuses further work;
  an ownership-removal error leaves an unowned file for later checked cleanup.
  Timeout uses the same cancellation rule. Unconfirmed termination is not
  normal exit and retains ownership, allocation and the exclusive lease.
- Reclamation: under the mutex, read a queue record and close its handle, then
  open its existing ownership file and try its lock non-blockingly. Only lock
  success permits reclamation: remove the queue record first, then unlock and
  close the ownership handle, then remove its file, all under the mutex. A
  contended ownership lock preserves the live requester's order. A missing,
  unreadable or invalid ownership file referenced by a visible record refuses
  admission; never recreate it as proof that the request is dead. No PID or
  timestamp alone permits removal. Inspectors close their ownership handles
  before releasing the mutex, so none prevents a later Windows deletion.
- Crash recovery: before publication, temporary records are never arrivals;
  incomplete creation, owner locking and publication are serialized by the
  mutex. A counter advance may leave a harmless gap. After publication, process
  exit releases the stable ownership lock, allowing the next mutex holder to
  reclaim the queue record in the order above. A crash before cancellation or
  reclamation removes the record leaves this same reclaimable pair; a crash
  after record removal leaves only an ownership file and possibly a temporary
  record. Clean these leftovers under the mutex only after obtaining that
  ownership lock, proving no live owner. Never rename or remove an ownership
  file while any inspection or ownership handle remains open. If a reclaimer
  dies after unlocking but before deletion, a later mutex holder can lock and
  clean the leftover ownership file. A crash during exclusive handoff never
  bypasses actual host leases, legacy slots or live-group checks. Existing
  process/watcher protections still apply. All handles use the existing
  contained openers and sharing flags; do not add broad delete sharing.

All queue-mutex acquisition and admission waits have deadlines. Waiting never
holds the queue mutex or partial host admissions; refusal identifies the
holder or queue failure. These are process-crash rules, not a claim of durable
recovery from a machine or storage failure.
