# TSK-1420: A squash-merging repository's pull request title meets the commit subject rules

## Description

When a repository merges pull requests by squash, the host writes one commit on the target whose subject is, by default, the pull request title. The commit-msg hook and `codeflow ci` judge the commits on the branch, but that squash commit is made by the host after both have run, so its subject is never judged. A title such as "Update stuff" lands on the protected branch in a project whose policy requires conventional commits.

This task adds a check that a project turns on when it squash-merges. With it on, `codeflow ci` judges the pull request title by the same subject rules the commit-msg hook applies (type, scope form, length, emoji, AI attribution), at the same severity TSK-450 sets for each rule. The trusted policy workflow, which runs from the base branch's definition, passes the title to `codeflow ci`, so a head-controlled workflow cannot omit the check, and it runs again when only the title is edited.

The title is untrusted input written by the requester. The workflow passes it only through an environment variable, never by expanding it inside a script, so a crafted title cannot change what the job runs. The setting that turns the check on is read from the trusted base policy, so a pull request cannot turn its own check off.

Non-goals: merge-commit and rebase repositories, where every commit is already judged; rewriting titles; reading the host's merge settings live (AC-1 decides whether doctor reports a mismatch).

## Outcome

After this merges, a maintainer of a squash-merging repository who turns the check on gets a failed or warned `codeflow ci` run when a pull request title would land on the target as a non-conforming commit subject, before anyone merges it.

## Deliverables

- the check: beside the PR body checks in `crates/codeflow-cli/src/cmd/ci.rs` (provisional; the builder places it next to the section checks)
- the policy key and its schema entry: `crates/codeflow-core/src/hooks/policy.rs` and `policy_schema.rs`, with `docs/policy-reference.md`

## Acceptance Criteria

- AC-1 Before any change, the builder shall record in `## Findings` where the subject rules live and how the check reuses them without a copy, how the managed CI gets the title, how other projects lint squash titles (for example the common conventional-commit title actions), and whether `doctor` should report a repository that allows squash merges with the check off; evidence: the Findings section committed before the first code change.
- AC-2 With the check on, `codeflow ci` given a pull request title shall judge it by every subject rule the commit-msg hook applies, at the severity TSK-450 sets for that rule, and name the rule in its message; evidence: one test per rule with a conforming and a non-conforming title.
- AC-3 With the check off, which is the default, `codeflow ci` shall not judge the title, and a project that merges by merge commit sees no change; evidence: a test with the default policy and a non-conforming title.
- AC-4 The title lint shall run in the trusted policy workflow (`codeflow-policy.yml`, which runs from the base branch's definition on `pull_request_target`), never in a workflow the head controls, so a pull request cannot omit it by editing its own workflow files; that workflow shall pass the title to `codeflow ci` through an environment variable and never expand it inside a `run` script; evidence: a workflow contract test that the lint step is in the trusted policy workflow and in no head-run workflow, a contract test that fails on any `pull_request.title` expression inside a `run` block, and a title holding shell metacharacters judged as text in a fixture run.
- AC-5 The setting shall be read from the trusted base policy, as the other managed CI policy keys are, so a pull request that turns the check off in its own head is still judged; evidence: a test where the head's policy turns the check off and the base's turns it on.
- AC-6 (journey) In a scratch adopter with the check on, a pull request with a non-conforming title shall fail the `codeflow ci` step and pass once the title is fixed; evidence: the two runs' output in the pull request body.
- AC-7 When the trusted base policy enables the title lint, the title judged shall be the pull request's current title, never the one the event carries, and a title edited after the checks ran shall be judged again on the same head. The title reads, the title comparison and the failures below apply only when the base policy enables the lint; with the lint off, which is the default, the workflow neither compares the title nor fails on it, so a project that leaves it off sees no change. The trusted policy workflow shall read the title from the pull request API when the job runs, as it already reads the body ("Read the pull request's current body", `assets/base/ci/codeflow-policy.yml:265`), and its last read ("the pull request is unchanged since it was judged", `:372`) shall compare the current title with the judged one and fail closed when it changed or cannot be read. When a conforming title is edited to a non-conforming one with the head SHA unchanged, the workflow shall run on the `edited` event, judge that same SHA, and fail; evidence: a workflow contract test that the trusted workflow triggers on `edited` and takes the title from the API read, not from `github.event.pull_request.title`; a stale-event fixture whose event payload carries an older conforming title while the API returns a non-conforming one, which fails; a fixture where the title changes between the first read and the last read, which fails; a fixture or scratch-adopter run showing the failed verdict on the unchanged head SHA; and a workflow fixture with the lint off by the base policy, where the title changes between the reads and where the API response carries no title, each leaving the verdict the same as without the change.
