# TSK-080: model bindings check and catalog derived tests

## Description

Give the catalog one supported read-only interface, a diagnostic view, and
the scan functions the derived tests use. All tests here run on fictional
catalogs and fixture trees; TSK-085 turns the scans on for the real tree
after it migrates the managed catalog.

`codeflow models resolve` is the one supported resolution interface. It
reads the managed catalog, the personal overlay and the schema 1 project
selection, takes `--duty`, `--host`, `--author` (`claude`, `codex`, `grok` or
`none`), repeated `--exclude selector:<id>` or `--exclude bucket:<id>`,
repeated `--observed <pinned-id>=<observed-id>`, `--trigger <id>`,
`--task <TSK-id>` and `--override <TSK-id>`, and prints the resolved
participant set (text, or `--json` for the launchers): for each participant
the seat or line, version, pinned id to launch, effort, remaining
alternatives and any label (`second-opinion`, reduced assurance), plus any
`xhigh-reasoning` obligation, or the open participant or obligation with its
reason. It exits non-zero when a required participant is open. It launches
nothing and writes nothing.

`--override` takes only a task id, which must equal `--task`; a path or any
other string is rejected. The command reads that task record as committed on
its `integration_target`, anchored from the merge-base the way
`codeflow work start` reads it, never from the working tree, and requires
exactly one block of this form in its Execution contract:

```text
OPERATOR_OVERRIDE
task: TSK-NNN
duty: design
route: <seat or line id>@<harness id>
effort: <effort>
plan: Plan vN
instruction: <date and where the operator gave it>
```

A missing task, a record present only in the working tree, zero or several
blocks, a missing field, or a task, duty, route or effort that differs from
the invocation is rejected with its reason: no override is passed to the
resolver, `design` stays open and the command exits non-zero. What this
proves is that the override sits in the reviewed, approved Plan vN record
(`capability-routing.md` near line 247, ADR-0060); the command does not
authenticate the operator beyond that approval.

`codeflow doctor --check model-bindings` (existing, `doctor/mod.rs:529`)
validates the catalog, the overlay and the project file, and prints one row
per supported host and duty with no author and no exclusions, labeled
"illustrative: context-free, not a task's resolution". It warns, without
failing, on: a newer version in a line not yet designated or adopted, a
designated version with no full-suite record, and a drifted id recorded by a
canary. It never launches a model and says so. While the managed file is
still schema 4 (before TSK-085), `--check model-bindings` keeps today's
output unchanged, so the integration branch stays green before the switch.

Scan functions, each tested here on fixture trees. A match is exact,
case-sensitive and token-bounded on the catalog strings (for example `opus`
or `gpt-6-astra` as a whole token), so a capitalized family or line word in
prose that TSK-081 permits cannot trip it:

- no selector, alias or pinned id of any catalog version appears in the
  operative instruction surfaces: `SKILL.md` files, skill resources,
  `AGENTS.md.tmpl`, `AGENTS.minimal.md.tmpl`, `CLAUDE.md.tmpl`, reviewer
  agents and workflow examples; excluded exactly: the catalog file and its
  four mirrors, and the evaluation kit fixture files, which use fictional
  names;
- no `retired` selector appears outside the catalog and its mirrors,
  `docs/decisions/`, `docs/verification/`, `project-management/`,
  `CHANGELOG.md` and `docs/plan/`.

Preservation fixtures that are not routing (the `Claude Fable 5` attribution
trailers in `standards.rs`, `git_hook.rs` and `ci.rs`, and `"model": "opus"`
in the settings tests) are outside the scans and named in ADR-0069.

Rename the doctor fixtures that use a current model name
(`claude-fable-high`, `fable-5` near `doctor/mod.rs:1746-1759`) to fictional
ids.

Update `docs/capabilities.md` `verified_by` for CAP-010 and CAP-013 with the
new tests.

Non-goal: the managed catalog, `orchestration_contract.rs` and the real-tree
scans (TSK-085), prose (TSK-081), launching models.

## Affected surfaces and interfaces

and their fixture tests; `docs/capabilities.md`. CAP-010, CAP-013.

## Acceptance Criteria

- [ ] When `codeflow models resolve` runs on a fictional catalog, it shall print the participant set for each duty and author, exit non-zero on an open required participant, and change its output when only the catalog changes (a newer designated version changes the selector; a changed floor changes the effort); evidence: CLI tests.
- [ ] When `--exclude bucket:<id>` or `--observed <pinned-id>=<observed-id>` is passed, the output shall follow the exclusion and drift rules; evidence: CLI tests.
- [ ] When `--override` is passed with the fictional catalog's design first line excluded, a matching block committed on the fixture integration target for task T, naming that catalog's second Claude seat line at high, fills `design` for `--task T` with that line's pinned id; each of these is rejected with `design` open and a non-zero exit: a path or free string, a task id that differs from `--task`, a task with no block, a block only in the working tree, two blocks, a missing field, and a block whose duty, route or effort differs from the invocation; the same block used with `--task U` or with `--duty orchestrate` grants nothing; evidence: CLI tests over a fixture repository.
- [ ] Doctor prints the illustrative rows with their label and the warnings above, and fails on a catalog, overlay or project violation; evidence: doctor tests and one sample run in the closeout.
- [ ] Each scan fails its fixture: a catalog selector placed in a skill, a retired selector placed outside the allowed paths; and passes when the same names sit in the catalog, its mirrors or a fixture file; evidence: fixture tests.
- [ ] No doctor fixture uses a current model name; evidence: a search in the closeout.
