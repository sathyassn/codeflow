# TSK-350: Own-task criteria use the judged head in every checkout

## Description

The same judged task head shall receive the same own-task criteria verdict
from main, detached and task checkouts. Issue 221 is a small follow-up to
TSK-275, whose reviewed completion in PR 206 must retain its verified
criteria. This task builds on that landed range context.

Criteria classification still resolves the branch's task from checkout
records. At `cdfb4964829976bf87a61e544af196801c6eff94`,
`crates/codeflow-cli/src/cmd/ci/acceptance.rs:257`, `:269` and `:286`
call `task_id_from_branch`; `crates/codeflow-core/src/workgraph/work_start.rs:899` uses
`visible_task_ids`, whose directory walk starts at line 907. A checkout
without the task record therefore loses own-task authority for the same
judged head. The existing `task_id_from_branch_at` at line 1132 reads the
named commit's records; reuse the head-based mechanism with the judging
context's policy and guarded history rules. PR 206 at
`8aa0748c3230f7eb44caa88ba5fcf5a0d7561c97` still has the checkout-based
calls at lines 267, 279 and 296. This is a remaining invocation-context
gap, distinct from TSK-339's imported completion origin.
Native reproduction remains implementation evidence.

The task stays separate from TSK-339 because it fixes branch-to-task
identity during criteria classification; TSK-339 preserves accepted
completion origins across merged lines. Each has an independently
verifiable outcome and a different regression matrix.

Widened 2026-10-26 for issue #304 (CodeFlow 3.1.1). Pre-push
`codeflow ci` refused a lease-guarded force push of a task branch with
`work.criteria_frozen`, because `refs/remotes/origin/<branch>`, the old
head the push replaces, records a completion of the task outside the
range (`Landing::Elsewhere`, `crates/codeflow-core/src/workgraph/landing.rs`).
That completion never landed; it is the state the push removes. A
remote-tracking ref is checkout state, so under this task's outcome
(the verdict depends on the judged head and explicit authorities) it
must not make the landing unknowable. The ref is identified by the
pre-push input for the destination, never by a branch name.

Widened 2026-10-27 for issue #354, item 4 (CodeFlow 3.1.1). After a
task branch was rebuilt with identical content, both a local
`codeflow ci` and the pre-push hook refused with `work.criteria_frozen`:
"`origin/task/...` records a completion of this task outside this
range". That completion existed only on the task's own remote branch,
never on the target; the adopter had to delete the remote branch, which
closed the pull request. The pre-push half is AC-4's case. The local
`codeflow ci` half has no push input to name the replaced ref, so AC-5
covers it with the same rule: the ref is the remote-tracking ref of the
branch the run judges, never a ref found by name pattern.

Widened 2026-10-28 for issue #380 (CodeFlow 3.1.1). A task on an
integration line changes its own criteria in its own PR, which `cf-plan`
step 5 allows. `codeflow ci --into <line>` reports a note; the pre-push
hook blocks the same range with `work.criteria_frozen` ("the judged
points hold different versions of this task, and none of them is newer
than the others"), because it adds `--policy-from <tip> --commits-from
<from>` for the default target (`crates/codeflow-cli/src/cmd/push_set.rs:307-314`)
and main's copy of the task then joins the judged points
(`RecordStore::agreed`, `crates/codeflow-core/src/workgraph/landing.rs:522-545`):
`--policy-from` becomes `names.candidate` (`crates/codeflow-cli/src/cmd/ci.rs:611`)
and joins `RunBases` (`crates/codeflow-core/src/workgraph/acceptance.rs:4144`);
`--commits-from` selects the commit checks and adds no criteria point.
Planning reproduced it on the line tip `654935d52` with a scratch CLI
fixture (not committed): main and the line hold versions of the task
that neither history contains (the line cut before main amended its
copy, or the task planned separately on each), the branch is cut from
the line and changes its own AC-1. Plain `codeflow ci --base <line>
--into=<line>` gives the note; the same call with the hook's
`--policy-from <main> --commits-from <main>`, with or without
`--baseline-from` and `--into`, blocks; with the line's tip as
`--policy-from` and `--commits-from` it gives the note. When main is an
ancestor of the line, or only moves on with unrelated commits, both give
the note. The adopter's workaround is a separate planning PR per
affected task.

This conflicts with landed rules. EPC-022 AC-16 and SPC-013 R-52 make
concurrent amendments at unordered judged points give no answer, and
TSK-306's test `competing_held_versions_name_the_points_and_blobs`
(`crates/codeflow-cli/tests/acceptance_cli.rs:4742`) checks that refusal
with main as the hook's authority. So #380 needs a bounded exception to
those rules, not a reading of them.

Proposed rule (the bounded exception), which AC-7 tests before any code:

- Scope: only a range whose head carries the task's own criteria change,
  whose `--into` target is an integration line the destination confirms,
  where that line is the `integration_target` the task's record declares
  both at the line's tip and at the judged head, and where the line
  passes the existing trusted-line binding (`epic_line_binding`,
  `crates/codeflow-core/src/workgraph/work_start.rs:883`): the epic exists
  in the trusted anchor records, is not cancelled or archived, and a task
  of that epic there names this exact line. Both entry points apply the
  same binding: an explicit CLI `--into`, which today skips declared-target
  eligibility (`crates/codeflow-cli/src/cmd/ci/context.rs:41`), earns the
  exception only after that check. Any other range, including one with
  no `--into`, keeps today's rule.
- Criteria points (the proposed selection): for that task's own change,
  the criteria points are the line's tip and the range base. Today
  acceptance derives its points from the range anchor and the run bases,
  and an explicit `--into` adds no point of its own; plain `codeflow ci
  --into <line>` gives a note only because it passes no `--policy-from`.
  The default branch's tip passed as `--policy-from` would no longer be a
  criteria point for that task. Concurrent amendments among the points
  that remain still give no answer (R-52 unchanged there).
- Kept from main: `--policy-from` stays the policy authority and
  `--commits-from` the commit-history authority, so main's stricter
  policy still judges every commit `commits_from` selects
  (`push_set.rs:433`), including history already on the line. A fix that
  passes the line tip for both flags is out of bounds.
- Completion history: every point, main and the line's history
  included, still counts for whether the task's completion landed
  elsewhere (R-52's completion test, R-60, R-119, the reopen freeze, and
  AC-4 and AC-5's replaced-ref rule).
- Where main's copy meets the line's today: when the line merges main
  before its landing pull request, Git merges the two copies of the
  record. Overlapping edits conflict and a person resolves them; edits on
  different lines merge without notice. The line-to-main pull request is
  an epic line range (`Criteria::Amendable`,
  `crates/codeflow-cli/src/cmd/ci/acceptance.rs:318`), which skips the
  frozen-criteria comparison (`crates/codeflow-core/src/workgraph/acceptance.rs:4171`),
  so no automatic check surfaces competing copies there; only that pull
  request's reviewer and the operator's merge do. AC-16 and R-52 give no
  automatic guarantee at that landing.
- Added enforcement at the line landing (AC-9), in the scope the operator
  decides: a line-to-main range that merges a task record whose criteria
  main and the line each amended since their common version reports the
  two versions and the one the merge kept. Proposed level: a note, since
  the line carries legitimate amendments; the alternative is a block
  until a planning amendment reconciles them.

Decision owner: this moves a criteria-authority boundary, which
`cf-method/references/autonomy.md` reserves to the operator. The
operator decides the whole: the exception (AC-6 with its binding), the
added enforcement at the line landing (AC-9) and its level (note or
block). The builder writes no AC-6 or AC-9 code until that approval is
recorded in this task's Closeout notes or a planning amendment. If

a criteria point, or a protection the rule would weaken), the builder
records them and the rule, AC-6, AC-8, AC-9, EPC-022 AC-16 and the R-52
deliverable change through a planning amendment before any code.

a record whose criteria signature (`CriteriaList::signature`,
`record_text.rs:280`, amendment notes and tags included) is the same at
the head as at the range base is not judged against the points; any
other record is judged as today. Equality with one judged point alone,
such as main's tip, never skips the check.
