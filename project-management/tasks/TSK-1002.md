# TSK-1002: The guards refuse every spelling of a checkout or secret write and read

## Description

Source: the Codex GPT-6.1 Sol retro-review of 2026-10-24 of the two landed guard units TSK-406 (PR 291, shell expansions and checkouts) and TSK-335 (PR 314, secret path spellings), each `changes_requested`, with every sampled payload rechecked by the Claude worker on the same binary. Both guards were bypassable by spellings the units meant to cover. Reproduced on this line at `e7299d699`: 47 of 66 probe payloads got the wrong verdict (judged through the hook protocol, never executed).

Operator direction for security work: durable, industry best practice, secure, never convenient. A guard that cannot resolve what a command touches near a protected path or a secret store refuses with a remedy; each class is closed, not single spellings; a heuristic that cannot be made sound is removed rather than patched.

Outcome: **a shell spelling that names a checkout or enforcement file as a write target, or a secret store or hard-secret file as a read, gets the verdict of the path it names, through every option, selector, redirection, link, namespace and directory-change grammar the guard reads; a spelling the guard cannot resolve in one of those grammars refuses as cannot-verify; ordinary data and search text stay allowed. What a program does once it runs, a file the line wrote, a copied or extracted tree, a runner's own directory, is outside this promise: the sandbox contains it where one is proven (TSK-397 option D), TSK-1052 (planned, 3.2.0) will fail it closed where containment cannot be established, and the guard's written-file checks are a filter, not a boundary.**

The classes, each owned by the guard that owns its route (git-guard for shell writers, exec-guard for interpreters and secret reads):

- TSK-406: a command substitution as a writer operand (`rm -rf "$(git rev-parse --show-toplevel)"`), a write through a same-line symlink followed by `..`, attached target-directory options (`cp f -tlink`, `--target-directory=link`), an alias defined earlier on the line, a worktree added earlier on the line and then removed by an interpreter, and credential reads through a variable or a program outside the old reader list.
- TSK-335: search-tool glob options naming a secret (`rg -g`, `--glob`, `--iglob`, `grep --include`), brace and bracket expansion, input redirection with no space and `exec {fd}<`, attached and long-option file operands (`--input=`, `-f$HOME/...`), archive and interpreter readers with a secret operand, and a newline inside a path hiding `id_rsa`.
- False refusals: ordinary writes through a resolved variable, quoted heredoc data, a search pattern that names a secret (`rg 'id_rsa' README.md`), a quoted named-user tilde and a quoted wildcard redirection source.

Glob decision: strict pattern intersection alone refuses ordinary source globs because a secret prefix can also carry a source extension. The guard therefore judges successful filesystem expansions by their actual matches, refuses secret-store directories even when empty, and refuses as cannot-verify any pattern it cannot expand completely, whatever its name, since an unseen entry may be a link into a store (corrected 2026-10-28 after Codex review 05: a name check cannot clear an incomplete expansion). A relative glob after a directory change the guard cannot establish is such a pattern and refuses whatever it names (2026-10-28, Codex review 06). Search-tool file globs use the same rules against their search roots. A secret-named file created between classification and execution remains a time-of-check gap; the native sandbox is the backstop.

Non-goal: a full shell evaluator. Paths a program assembles at run time stay the stated residual (TSK-302 scope decision of 2026-10-15) with the native sandbox as backstop. What a program does once it runs, a file the line wrote, a copied or extracted tree, a runner's own directory, is outside this promise: the sandbox contains it where one is proven (TSK-397 option D), TSK-1052 (planned, 3.2.0) will fail it closed where containment cannot be established, and the guard's written-file checks are a filter, not a boundary. Follow-ups: TSK-1052 (runs after a same-line write fail closed on an unsandboxed host) and TSK-1053 (runner directory grammars); the completion's acceptance block names both in `follow_ups`.

## Outcome

After this merges, an operator running agents under CodeFlow can rely on the git-guard and exec-guard to refuse any shell spelling that names a checkout or enforcement file as a write target, or a secret file as a read, through every grammar the guards read, while what a program does once it runs is contained by the sandbox where one is proven, and on an unsandboxed host waits for TSK-1052 (planned) to fail it closed.

## Acceptance Criteria

- AC-1 When a shell writer operand holds a command substitution the guard does not resolve (`rm -rf "$(git rev-parse --show-toplevel)"`, backticks, `printf x > "$(git rev-parse --git-path config)"`) and a checkout is reachable, git-guard shall refuse it as cannot-verify; the deletion reader's "known residual" carve-out is removed; evidence: hooks_cli refusal tests failing before the change.
- AC-2 A write through a same-line symbolic link followed by `..` (`ln -s .codeflow/rules l; printf x > l/../policy.json`, the `dd of=` form) shall get the verdict of the path the kernel resolves; evidence: hooks_cli tests failing before the change.
- AC-3 Attached and long target-directory options (`cp f -tlink`, `cp -vtlink f`, `--target-directory=link` for `cp`, `mv`, `install`, `gcp`) shall be judged like the separated `-t link`; so shall the file a program writes through an output option or in place (`sort -o`, `--output=`, `awk -i inplace`, `sponge`, `dos2unix`, a compressor, the `split` prefix) and Git's own overwrites (`git checkout REV -- PATH`, `git restore PATH`, `git checkout-index`, `git apply --directory`), while `git worktree remove` without `--force` stays the sanctioned cleanup of a clean worktree. Reason (2026-10-29, Fable review 15): these writers were not judged. Evidence: hooks_cli tests failing before the change.
- AC-4 A command whose name an alias defined earlier on the line may replace shall be refused as cannot-verify when the alias body is not read; evidence: hooks_cli tests for the newline and `;` forms failing before the change.
- AC-5 A path a `git worktree add` earlier on the line creates shall be protected from interpreter arguments and inline interpreter code as a registered checkout; evidence: exec-guard tests for `node -e` and `python3` forms failing before the change.
- AC-6 A secret store or hard-secret file named as an operand of any program, including through a variable assigned earlier on the line, shall be refused by exec-guard (`wc`, `git diff --no-index`, `od`, `xxd`, `tar cf - ~/.ssh`, `zip -r`, `python3 -c '...' id_rsa`); the reader allowlist is removed; a `find` that hands what it visits to a command is a recursive reader of its starting points, and `find` piped into `xargs` refuses as cannot-verify like any unread producer (Reason, 2026-10-29, Fable review 15: `find ~/.codex -exec cat {} +` was allowed); evidence: exec-guard tests failing before the change.
- AC-7 Search-tool glob options (`rg -g`, `--glob`, `--iglob`, `grep --include`, including brace forms) shall follow AC-8's expansion and store-directory rules against the actual search roots, refusing when a match names a secret or when the pattern cannot be expanded completely, whatever it names; evidence: tests failing before the change and search-root fixtures with and without a secret-named match.
- AC-8 A reader word whose brace or bracket expansion may name a secret (`cat {id_rsa,README.md}`, `cat [i]d_rsa`, `cat ~/{.codex/auth.json,notes}`, `cat *.{pem,key}`) shall be judged by its real filesystem expansion. Any secret-named match refuses. A glob whose directory is a configured secret store refuses even if it currently matches nothing. A glob the guard cannot expand completely (unreadable, over the entry budget, or relative to a directory the guard cannot establish) refuses as cannot-verify whatever its pattern names. Reason: strict intersection alone refuses ordinary source globs; actual expansion plus store-directory refusal retains protection. Reason (2026-10-28, Codex review 05): an incomplete expansion may hold a public-named link into a store, so a name check cannot clear it. Reason (2026-10-28, Codex review 06): a glob in an unknown directory is the same incomplete selection. Evidence: temporary-directory fixtures for each rule, including an unreadable glob and an over-budget directory holding a public-named link into a store.
- AC-9 Input redirection with no space (`cat<~/.codex/auth.json`), descriptor forms (`exec {fd}<`, `exec 3<`) and redirection on a compound command shall be judged like the spaced form; evidence: tests failing before the change.
- AC-10 Attached and long-option file operands (`base64 --input=...`, `grep -f$HOME/...`, `rg --file=...`, `sort --files0-from=...`) shall be judged like separated operands; evidence: tests failing before the change.
- AC-11 A path whose directory name holds a newline shall not hide a hard-secret leaf; evidence: a test failing before the change.
- AC-12 A hard-secret file name in the workspace (`id_rsa`) is a secret wherever it is, consistent with the file-tool rule `Read(**/id_rsa*)`, including when a Git call stages it without naming it (`git add .`, `-A`, a directory, `git commit -a`, `git stash -u`), judged by the files Git lists for that call (Reason, 2026-10-29, Fable review 15); evidence: the refusal_journey fixture proves the guard refusal and the file-tool deny while the native store-only profile leaves the workspace file readable. Reason: native store-root denies do not implement file-tool name rules.
- AC-13 Ordinary forms shall keep passing: `D=src; printf x > "$D/settings.json"`, quoted heredoc data naming a protected path, `rg 'id_rsa' README.md`, `grep -n id_rsa docs/x.md`, `cat '~somebody/.codex/auth.json'`, `cat < 'id_rs?'`, and the existing ordinary sweeps. Source globs such as `cat src/*.rs` and `rg -g '*.rs' foo src` pass when their real expansion is readable and has no secret-named match; the same globs refuse after a secret-named match is planted. Reason: strict intersection alone rejects ordinary source files. Evidence: tests failing before the change and paired filesystem fixtures.
- AC-14 (journey) With the installed build in a scratch adopter, the planted payloads of AC-1 to AC-11 shall be refused through the real hook protocol for every harness and the ordinary forms of AC-13 allowed; evidence: the refusal_journey run.
- AC-15 A shell construct or input the guards do not fully model yields cannot-verify, and cannot-verify refuses whatever the construct could make secret: a directory change inside a command substitution, a glob after a substitution the guard cannot establish, physical mode set through `SHELLOPTS`, a physical `cd` with no operand whose HOME or OLDPWD the guard cannot read (a command-local `HOME=` is in effect), a shell running a file the line wrote without an exact body, a command word the shell fills in at run time that the guard does not resolve or that holds blanks the shell splits at run time, a `cd` or `pushd` whose relative operand a `CDPATH` in effect (command-local included) or `cdable_vars` may send elsewhere, and a word joining a substitution the guard does not resolve to a spelled directory, judged whole with that part standing for any text. For Git, a reading the guard cannot make sound refuses: pathspec magic in an operand, a separate option value, a long option's `=value` or a short option's attached value, whatever its role; on a line that runs Git, a share, verbatim or device spelling in any word or `=` value, a `-c` setting and an environment assignment included, before either guard discovers a repository, reads configuration or looks up an alias (proved on macOS and Linux, Windows execution unverified); a `GIT_*` variable the line sets in an assignment position that the guard has not classified, and `--exec-path=DIR`; a program-valued variable (its `GIT_*` name, or `VISUAL`, `EDITOR`, `PAGER`, `SSH_ASKPASS`, `LESSOPEN` and `LESSCLOSE`, which Git and its pager fall back to) judged instead as a command, before every program the line runs and from each directory that program runs in (a Git call's `-C` directory and its repository's top included), when its value resolves to literal text and refused otherwise; every command a Git call runs itself (an operand, an option value, a `-c` setting or configured command the subcommand uses, an inherited program variable) and a `git config` write of a key not known to run nothing, judged the same way in the directory Git runs it in (operator decision 2026-10-29: Git operand commands are judged as commands), and refused when the guard cannot read it (`ext::`, an unread `--config-env` value) or when an earlier command on the line may change the checkouts a `submodule foreach` or `for-each-repo` runs in; a relative operand of a Git call read from its `-C` directory; a `--git-dir`, `--work-tree` or `GIT_DIR` that is not provably the repository Git would use without it; a NUL-separated stdin list; a stdin list for a names-reading form that is not literal input on the line; a pathspec pattern a secret name could match, for commands that may print what they select; `--icase-pathspecs`; an alias the guard cannot read, and an alias expansion that meets any of these. Every operand not proven to be text is read as an object name; the options that select what `cat-file`, `hash-object`, `update-index` and `--pathspec-from-file` read resolve by Git's unique-prefix rule or refuse; every `status` operand is judged; stdin lists are read one record per line in Git's C quoting, pathspecs from stdin meeting the pathspec rules; other Git commands are judged by their operands whatever their stdin holds. `git log` operands are file operands. Content already committed to Git's object store (an object named by id, tag or peel, a batch record, an archive, and what `show` or `log -p` prints from a commit) is outside this criterion; the paths a command names, writing working-tree files into the store, and a Git directory that is not the repository's own stay in it. Reason (2026-10-28, Codex review 06 and Fable review 08): rounds 05 to 08 found new classes of one kind, constructs the evaluator reads partly; one rule closes the kind. Reason (2026-10-28, Codex review 07 and Fable review 09): a denylist of Git readers left abbreviations, quoting, unlisted consumers and pathspec patterns open, so Git is judged by the forms it parses instead; the ordinary cost is measured on a 120-command Git corpus (1 refusal before, 2 after). Reason (2026-10-29, Codex reviews 08 and 09, Fable reviews 10 and 11): three rounds found operand roles, option ownership and record boundaries modelled by example; under the operator's rule to remove what cannot be made sound, pathspec magic, NUL lists and namespace spellings now refuse outright instead of being modelled, and `ls-files` patterns are not judged because it prints names only. Reason (2026-10-29, Codex review 10 and Fable review 12): `status -v` prints changes, so `status` patterns are judged again; the namespace refusal moved ahead of every walker and configuration read and covers `-c` and environment values; unlisted `GIT_*` variables refuse; magic in attached short option values refuses; the role-free magic and `GIT_*` rules then refused a search text such as `git grep '://'` or `git grep GIT_WORK_TREE`, an accepted over-refusal whose workaround was `rg`, until review 13 limited the `GIT_*` scan to assignments; a two-step read by object id (a blob id from `ls-tree`, then `cat-file -p`) named content without a path, so such names refused unless proven commits, until the operator's direction below removed that rule. Reason (2026-10-29, Codex review 11 and Fable review 13): a work tree moved onto a store by `--work-tree` or `--git-dir` staged it for printing, so those values must be the repository's own; program-valued `GIT_*` values were unjudged commands, so they are judged as commands; `status` kept a filename exemption; `--ca` is Git's `--cacheinfo`; the `GIT_*` scan is limited to assignments, so text naming a variable no longer refuses; a write to the alternate object lists refuses like hooks and config. Reason (2026-10-29, Codex review 12 and Fable review 14): a command or program value held in a variable was judged as its spelling, so a value the line assigns is resolved and one it cannot resolve refuses, one rule for both; Git falls back to `EDITOR`, `VISUAL` and `PAGER`; `--exec-path=DIR` moves helpers as `GIT_EXEC_PATH` does; a resolved substitution after a spelled store directory was judged by its tail; and only assignment positions assign, so `git commit -m 'GIT_WORK_TREE=/x'` passes. Reason (2026-10-29, operator direction): secrets already in committed history are handled once, by a one-time full-history secret scan whose findings are rotated or removed with the operator's approval, and the commit-time and hosted secret scans stop new commits, so the text guard does not chase object-store reads; the round 10 object-id rule is removed and Codex review 11 B1 to B3 and Fable review 13 M1 close as out of scope. Reason (2026-10-29, Codex review 13, Fable review 15, Grok on PR 405 and the operator's decision on Fable 15 B4): a program value was judged from the shell's directory without the Git call's `-C`, `cd` or links, and only on lines that run Git, so it is judged before every program in each directory it runs in, and a line that declares a link first refuses; a relative operand after `git -C` was read from the shell's directory; a command-local `CDPATH` was not modelled; a word naming a program variable refused as a possible setter in any program's operands, so only builtins, keywords and aliases that may set it count (`echo EDITOR; git status` passes); Git operand commands are judged as commands by the operator's decision, read by git-guard's existing runner reader so each runs where Git runs it, and a `submodule foreach` after a command that may add or check out submodules ran where the guard did not look, so that order refuses.
