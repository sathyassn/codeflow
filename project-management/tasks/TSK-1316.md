# TSK-1316: Import authority finds a completed task's real landing when a planning merge carried its record

## Description

The real EPC-022 into EPC-026 sync is refused for records whose task landed correctly. `matching_landing` (`crates/codeflow-core/src/workgraph/acceptance/imports.rs:522`) finds where a record's exact bytes first reached the home's first-parent chain, and `prove_task_completion` (`imports.rs:618`) treats that merge's second parent as the task's whole head. When a later planning merge edited the record (TSK-1145, TSK-1062), or a completion on a planning PR was followed by planning commits (TSK-1246), the planning head is judged as the task's landing. The line-into-main check has the same cause in `holder_outside` (`crates/codeflow-core/src/workgraph/landing.rs:1004`): a planning edit that keeps a completion unchanged reads as a completion recorded elsewhere (AC-6, AC-7).

Source: coord/catalog's proof at `coordination/coordinators/capabilities/builders/import-span-refusals.md`. Non-goals: the ordering refusals on TSK-1135, TSK-350 and the frozen criteria on TSK-1115, which are record repairs in a planning amendment and do not change the rule.

## Outcome

After this merges, a maintainer can sync one line into another without a correctly landed task being refused because a planning merge later carried its record, and every real change to what a completion attests stays refused.

## Deliverables

- the import authority change and its fixtures: `crates/codeflow-core/src/workgraph/acceptance/`
- the line-check change and its fixtures: `crates/codeflow-core/src/workgraph/landing.rs` and `crates/codeflow-core/src/workgraph/acceptance.rs`

## Acceptance Criteria

- AC-1 A record whose task landed with its acceptance block, then edited by a later planning merge with the same block bytes, criteria signature, status and declared home (or a proved planning move), shall be proved at the landing that first brought the block; evidence: a fixture refused before and proved after, for the TSK-1145 and TSK-1062 shapes.
- AC-2 A completion on a planning PR followed by non-merge commits that change only planning records and leave this record's reviewed part unchanged shall be proved; evidence: a fixture for the TSK-1246 shape.
- AC-3 Each of these shall stay refused: a planning step that changes the block bytes, the reviewed commit or evidence, the criteria, the status or the declared home; product work on a branch whose name starts `plan/`; a source task edit hidden at its introduction; and any step that cannot be read; evidence: a test for each.
- AC-4 The decision shall read only the home's fetched first-parent chain and block bytes, never a branch name, PR title or date; evidence: the code and a test that varies those names.
- AC-5 (journey) With the record repairs for TSK-1135, TSK-350 and TSK-1115 in place, the real EPC-022 into EPC-026 sync shall exit 0 on both the pinned form and the hook's form; evidence: both commands and their exit codes. Cross-lineage security review, or the review rule's fallback recorded as reduced assurance, because this is merge authority.
- AC-6 A commit outside the judged range that changes a task's record, while a parent's version holds the same completion (the same active block and archive bytes, criteria signature, status and declared home), compared by content with the same comparison AC-1 uses, never by a ref name, path or date, shall not count as a completion recorded elsewhere; evidence: a fixture of the TSK-1062 line shape (a merge whose one parent holds the completion and whose record adds a note outside the block) refused before and bound after with no finding for TSK-1062, and tests that a change to the block, the archive, the criteria, the status or the home still refuses.
- AC-7 When a ref that records a completion elsewhere reaches the judged range, the refusal shall not call it a stale copy to delete; it shall name the commit and what differs (block, archive, criteria, status or home) and tell the reader to repair the record on that line through a planning pull request; evidence: a test on the message.
  - AC-6 and AC-7 added 2026-11-04 by a planning pull request; reason: a clean-clone check of the EPC-022 line into main (main 879a7a7fc, line 9c5f665cf) refuses TSK-1062. Its record holds an archived block, and merge c677596d6 on PR 434's branch added one "Reassigned 2026-10-30" note outside the block after landing merge b361b7cd9 (PR 426). `holder_outside` (`landing.rs:1004`) reads that as a completion elsewhere, and the refusal at `acceptance.rs:2195` tells the reader to delete the judged line. That check is outside AC-1 to AC-4, which cover the import path.
- AC-8 A completion shall count as reopened only when a commit that descends from the commit that made it, read from commit ancestry alone, holds the record not complete, under the same history overlay check the walk runs (`history::judgment`, `acceptance.rs:953`), so a graft or replace ref cannot fake the descent; a commit of the receiving line's own parallel history that does not descend from the completion shall not reopen it, whatever order the walk visits it in; evidence: a fixture of the TSK-350 shape (a record its own PR completed twice, synced into another line whose history holds it as todo) refused before and bound after, a test that a real reopen on the completion's own chain still refuses, and a test that reordering the parallel history does not change the result. This narrows a security check, so the build PR carries a `cf-security-reviewer` checklist review.
  - AC-8 added 2026-11-04 by a planning pull request; reason: the narrow EPC-022 into EPC-026 resync refuses TSK-350 with "the archive must hold every completion this range made, in order: the completion reviewed at 23e84cab6 (made at ea99582a8) is missing". `completions_made` (`crates/codeflow-core/src/workgraph/acceptance.rs:947-1001`) walks the range in reverse topological order and marks the last completion reopened at any later-walked commit where the record is not complete (`:975-978`), even one that does not descend from it; the receiving line's parallel commits hold TSK-350 as todo, so the current completion is not set aside (`:873-882`) and reads as missing (`:909-913`). A planning repair that copies the record cannot clear it (coord/catalog's probe 20453658f refuses with `work.acceptance_binding`, rightly).
