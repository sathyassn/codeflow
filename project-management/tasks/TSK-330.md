# TSK-330: Hooks stay usable while a CodeFlow settings file has merge conflicts

## Description

When `.codeflow/project.toml` holds merge conflict markers, every CodeFlow
hook refuses every command, so an adopter's agent cannot take part in
resolving the conflict. Reproduced on 2026-10-16 with the installed 3.1.0
build in a scratch repository: after a merge left `tier` conflicted in
`project.toml`, `codeflow hook git-guard`, `exec-guard` and `edit-guard`
each exited 2 with `cannot parse project settings: invalid key` for
`git status`, `git checkout --theirs .codeflow/project.toml`,
`git merge --abort`, plain `ls` and an Edit of an unrelated `README.md`.
After `git merge --abort`, run outside the session, the same `ls` passed.
A conflicted `.codeflow/policy.json` locks the session out the same way
(`cannot parse policy ... key must be a string`, reproduced the same day),
so this task covers both settings files the hooks parse.

The refusal comes from `read_project_toml`
(`crates/codeflow-core/src/hooks/policy.rs:955`), reached through
`policy_armed` and `effective_armed` (`policy.rs:866`, `:931`) on every
`Policy::load_effective` call, and from the landed policy path
(`hooks/landed_policy.rs:164`, `:180`) and `project_tier`
(`hooks/guidance.rs:342`). Failing closed on an unreadable settings file is
right in general. The defect is that a conflict the adopter is resolving
leaves no sanctioned path inside the session.

The outcome is that a conflict in either settings file can be resolved or
abandoned from the session, while every guard gives the verdict the
ordinary effective policy gives.

Conflict recovery only replaces a local settings read that would otherwise
fail. It never changes which policy is the authority:

- The authority stays what `landed_policy.rs` selects today: the fetched
  default branch and any declared integration line, combined by
  `stricter` (`landed_policy.rs:74` to `:110`), and HEAD only where the
  existing no-tracking rule already uses it (`landed_policy.rs:58` to
  `:72`). Protected refs, root-branch selection and every level are
  chosen the same way, as is any enrolled baseline that TSK-320 composes
  later.
- Where a hook reads the local file (the `policy_armed` read,
  `policy.rs:931`; the local comparison in `finish`,
  `landed_policy.rs:178` to `:180`; `project_tier`,
  `guidance.rs:342`), the unreadable working copy is replaced by the copy
  committed at `HEAD`, read as git data, for that input only, with one note
  naming the file. Where a read can be dropped instead (for example,
  `policy_armed` is ignored once a commit exists, `policy.rs:856`), the
  builder may drop it and record why.
- Recovery starts only on unmerged index entries for the path (stages 1
  to 3). Conflict marker text alone is not evidence: a file that does not
  parse with no unmerged entry refuses as today.
- An authority that cannot be read is never replaced by defaults: the hook
  refuses, naming the source.

Hook integrity is unchanged: a Bash write to a settings file is refused as
today.

Non-goals: accepting a settings file that is unreadable for any reason other
than an unresolved conflict (that still refuses, naming the file), and
changing what any guard refuses once the file parses.

## Deliverables

- the conflict-aware settings read: `crates/codeflow-core/src/hooks/policy.rs` and `crates/codeflow-core/src/hooks/landed_policy.rs` (provisional; the builder confirms where the fallback lives and whether `hooks/guidance.rs` shares it)
- tests: unit tests for each criterion, and a CLI test that drives `codeflow hook git-guard`, `exec-guard` and `edit-guard` against a conflicted scratch repository
- docs: the conflict note in `docs/policy-reference.md` and the matching entry in `docs/troubleshooting.md`
- release note: `changelog.d/TSK-330.md`

## Acceptance Criteria

- AC-1 When the index holds unmerged entries for `.codeflow/project.toml`
  or `.codeflow/policy.json` and a hook's local read of that file would
  otherwise fail, git-guard, exec-guard and edit-guard shall replace only
  that local read with the copy committed at `HEAD` and print one note
  naming the file. Authority selection, the stricter composition with
  fetched lines, protected refs, root-branch selection and levels shall be
  the same as with a parsed file; evidence: unit tests per guard and per
  file. (serves EPC-022 AC-27)
- AC-2 While a settings file is unmerged, the commands that resolve or
  abandon the conflict (`git status`, `git diff`, `git checkout --ours`
  and `--theirs` on the file, `git add`, the concluding `git commit`,
  `git merge --abort`, `git rebase --abort`) and an edit of an unrelated
  file shall get from every hook the verdict the ordinary effective policy
  gives them when the settings parse; evidence: the CLI test, including the scaffolded git
  hooks (pre-commit, commit-msg, reference-transaction) where a command
  runs them. (serves EPC-022 AC-27)
- AC-3 No guard shall be weaker while a settings file is unmerged than the
  ordinary effective policy: a planted `git push origin HEAD:main`, a
  commit on a protected branch and a Bash write to
  `.codeflow/policy.json` shall each get the verdict they get with parsed
  settings. The regressions shall cover a local `HEAD` weaker than the
  fetched authority (a lower push level, `policy_armed = false` or a
  changed `root_branch` at `HEAD`, with `origin/main` or the declared
  integration line stricter), where the verdict follows the stricter
  fetched authority; both settings files unmerged at once; and the
  no-remote case, where `HEAD` is already the authority. Evidence: a test
  per case that fails on a recovery that reads the working copy or makes
  `HEAD` the authority. (serves EPC-022 AC-27)
- AC-4 When a settings file does not parse and the index holds no unmerged
  entry for it (conflict marker text alone included), every hook shall
  refuse as today, naming the file; and an attempted recovery from
  unreadable settings in a repository with an unborn `HEAD` shall refuse.
  A valid unborn bootstrap control (parseable settings with
  `policy_armed = false` before the first commit) shall still let the
  first scaffold commit through as today. Evidence: tests for the plain
  parse error, the marker text without an unmerged entry, the unborn
  recovery and the bootstrap control. (serves EPC-022 AC-27)
  - Amended 2026-10-31 by the batched amendment after Codex review 03 of PR 448 (finding F2): the `reference-transaction` stage judges a transaction that writes only Git's own state refs (`AUTO_MERGE`, `ORIG_HEAD`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `REBASE_HEAD`, named exactly, none a branch) at the shipped levels when the settings cannot be read, instead of cancelling the merge, because a merge writes `AUTO_MERGE` before its index records the conflict; every other unreadable-settings case refuses as this criterion states. Evidence: the state-ref tests and `docs/policy-reference.md`'s settings-conflict section.
- AC-5 When the file is unmerged but `HEAD` holds no copy of it or its copy
  does not parse, or a required authority source (a fetched line the
  ordinary selection needs) cannot be read, the hooks shall refuse with a
  message that names the conflict or the source and the operator's
  recovery (`git merge --abort`, `git fetch`, or resolving the file outside
  the session), never fall back to defaults; evidence: a test per case.
- AC-6 (journey) With the installed build of this change in a scratch
  adopter made by `codeflow init --standard`, a merge that conflicts in
  `project.toml` shall be resolved through hook payloads for
  `git status`, `git checkout --theirs`, `git add` and `git commit`, and a
  second one abandoned with `git merge --abort`, while a planted protected
  push during the conflict is refused, including when the conflicted
  side would lower the push level; evidence: the journey output with
  each hook's exit code.
  - Amended 2026-10-31 by the same amendment (F2): `git checkout --theirs` on a settings file is refused by `git.hook_integrity` with or without a conflict, so the journey shows that refusal and the operator resolving the file's content outside the session, then `git add` and `git commit` through the hooks; hook integrity is unchanged.
