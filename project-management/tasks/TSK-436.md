# TSK-436: A task criterion can record a deferred result proved after merge

## Description

Issue #287. A task's acceptance block accepts only `verified` or
`waived` per criterion; `deferred` exists only for an epic's
after-release criteria (`cf-method/references/project-organization.md`,
the `deferred | owner; window; follow-up` form, read by
`crates/codeflow-core/src/workgraph/record_text.rs:1533-1546`), and a
`waived` result needs a planning amendment of that criterion inside the
reviewed commit. Some criteria can only be proved after the merge: an
adopter's dependency-admission check runs as `pull_request_target`, so
the base's checker judges the head's data and a pull request that adds
a new exception kind cannot go green until it is merged; the first push
scan of `main` after the merge is the real proof. The author must
reword the criterion to match local evidence, or the maintainer merges
on known reds with no record that a check is owed.

Outcome: **a task's acceptance block can record a criterion as
`deferred`, naming the event that will prove it, who checks it and a
follow-up, with no planning amendment because the criterion does not
change; `codeflow ci` and `orient` show the owed follow-up until
someone records the result as verified, or as failed with a linked
task.**

Rules:

- **Form.** The task result reuses the epic form: `AC-n: deferred |
  event: <the proving event>; owner: <who checks>; follow-up: <TSK-NNN
  or another permitted durable record, an epic criterion or a feedback
  item>`. The event is free text, the owner a role or seat, the
  follow-up a tracked record that exists in the repository. A tracked
  record never cites a coordination ledger id (`FU-NNN`, `LN-NNN`,
  `WS-NNN`): the ledger is clone-local and absent in CI (ADR-0086), so
  a ledger item may link outward to the task's deferred criterion, and
  the durable reference stays in the record.
- **Binding.** A deferred result binds like a verified one: the task
  can complete and land, and the block names the reviewed commit. The
  task stays `complete`; the deferred criteria are listed in the task's
  Closeout as owed.
- **Resolution.** `codeflow task status <id> defer-resolve AC-n
  --verified <evidence>` or `--failed --task TSK-NNN` (provisional
  verb) appends the result under the block as a dated line, a
  records-only change `codeflow ci` accepts in a planning amendment or a
  task PR, judged like the amendment note of SPC-013 R-50. A failed
  result must link an open task.
- **Surfacing.** `codeflow ci` prints each owed deferred result of the
  tasks in its range as a note, and `orient` lists every owed deferred
  result of the project with its event and owner, from the records
  alone; neither blocks and neither reads the ledger.
- An epic closes only when every deferred task result is resolved, or
  the epic's own block defers the criterion as today.

Non-goals: changing `waived`; deferring a journey criterion; a hosted
check that records the result by itself.

Added by the EPC-022 amendment of 2026-10-22 under the operator's
decision of that day (project-management changes go in 3.2.0).

## Acceptance Criteria

- AC-1 A task acceptance block with `AC-n: deferred | event: ...; owner: ...; follow-up: TSK-NNN` shall be accepted by `task status complete` and bind in `codeflow ci` without a planning amendment; a deferred result missing the event, the owner or an existing tracked follow-up shall be refused naming the part, and a follow-up naming a coordination ledger id (`FU-NNN`, `LN-NNN`, `WS-NNN`) shall be refused as not durable; evidence: tests, the first failing before the change, plus the ledger-id negative test. (serves EPC-022 AC-118)
- AC-2 `codeflow ci` shall print each owed deferred result of the tasks in its range, and `codeflow orient` every owed deferred result of the project, with event and owner, without blocking; evidence: CLI tests reading the output. (serves EPC-022 AC-118)
- AC-3 The resolution verb shall append a dated verified or failed line under the block, a failed line shall require a linked open task, and the resulting records-only change shall pass `codeflow ci` in a planning amendment and in the task's own pull request without rebinding the completion; evidence: fixtures for both routes and a negative fixture with no linked task. (serves EPC-022 AC-118)
- AC-4 An epic with a task whose deferred result is unresolved shall not close, and shall close once it is resolved; evidence: lifecycle tests.
- AC-5 SPC-013 shall be amended in place with a dated note naming the bound consumers, and the guidance shall state the form, when to use it instead of rewording a criterion, and that a journey criterion cannot be deferred; evidence: the spec diff, the doc text and `codeflow validate --docs`.
- AC-6 (journey) With the installed build in a scratch adopter project, a task shall complete with one deferred criterion, land, show the owed result in `orient`, and be resolved as verified with the record passing `codeflow ci`; evidence: the journey output.
