# TSK-363: Policy keys with no reader are refused or warned, never documented as controls

## Description

Source: the Claude Fable 5.1 test integrity audit of 2026-10-17, finding
F1, at `eaf2ed04e932186cdd26dc4a7e5740cc553acee3`.

Two shipped security policy keys are parsed, defaulted, shipped and
documented as controls, and no code reads them:

- `security.script_bypass` (default `warn`, `assets/base/policy.json:56`),
  described at `docs/policy-reference.md:82` as refusing actions found in a
  script a command runs. `crates/codeflow-core/src/security/privilege.rs:11`
  says TSK-172 reads it; TSK-172 is cancelled. The docs do not say it is
  unread.
- `security.sandbox_retry` (default `allowlist`) and
  `security.sandbox_retry_allow` (`assets/base/policy.json:62`), described
  at `docs/policy-reference.md:88` and `:89`. The shipped entry carries
  literal placeholder digests (`"<sha256 at qualification>"`). The schema
  validates only `program` (`crates/codeflow-core/src/hooks/policy_schema.rs`
  near line 1333). TSK-174 is cancelled. `docs/policy-reference.md:598`
  discloses that these keys are not read yet.

An adopter who sets `block` gets nothing, on a security surface.

Decision (the primary's default, 2026-10-17): remove the claimed behaviour.
The keys stop being documented as controls, a policy that still sets them
gets a clear "not supported, has no effect" message naming the key, the
shipped template and default policy drop them, and `codeflow update`
migrates an adopter's managed copy. Implementing either control remains a
separate future decision. A key that a project still carries must not
break its hooks: the message warns, and `codeflow doctor` reports it; it
never silently passes as a control.

A reader contract test makes this class of defect fail the build: every
policy key the schema accepts and the reference documents has a module
that reads it, or is listed as refused or unsupported.

Product surface: adopter-facing engine (policy load, schema, doctor),
scaffold (`assets/base/policy.json`) and docs.

## Acceptance Criteria

- AC-1 A reader contract test shall derive from the code, not from a
  hand-maintained list, which policy keys the schema accepts and which are
  consumed by enforcement code, and shall fail when a documented key is
  not consumed and not marked unsupported; a fixture that keeps a key's
  claimed reader module but disconnects the consumer shall be refused;
  evidence: the test failing on the current tree for `script_bypass`,
  `sandbox_retry` and `sandbox_retry_allow`, the disconnected-consumer
  fixture refused, and the test passing after the change. (serves EPC-022 AC-61)
- AC-2 When a policy sets `security.script_bypass`, `security.sandbox_retry`
  or `security.sandbox_retry_allow`, the hooks shall keep working and shall
  print a "not supported, has no effect" message naming the key, and
  `codeflow doctor` shall report it; evidence: CLI tests with representative
  valid and invalid values by key type: each level of `script_bypass`
  including `block`, each value of `sandbox_retry`, and for the structured
  `sandbox_retry_allow` array an empty list, the shipped entry and a
  malformed entry (a scalar such as `block` is invalid for it, not
  accepted).
- AC-3 `assets/base/policy.json` shall no longer ship the keys or the
  placeholder digests, and `codeflow update` on a project whose managed
  policy carries the shipped defaults shall remove them, while a project's
  own edited value is kept and warned about; evidence: update tests for an
  unmodified and an edited copy.
- AC-4 `docs/policy-reference.md` shall no longer describe either control
  as working and shall state that the keys are unsupported; evidence: the
  diff.
- AC-5 (journey) With the installed build, a fresh project and a project
  updated from 3.1.0 with `script_bypass: block` shall each commit and push
  normally while the warning names the key; evidence: the two journeys'
  output.
