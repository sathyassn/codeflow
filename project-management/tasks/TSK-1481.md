# TSK-1481: Test files the Claude sandbox hides get readable names

## Description

Three test files on `main` have "secret" in their names: `crates/codeflow-cli/tests/ci_cli/secret_scan_exemption.rs`, `crates/codeflow-cli/tests/refusal_journey/secret_paths.rs` and `crates/codeflow-core/tests/managed_secret_scan.rs`. A Claude session's Bash sandbox in this project cannot read them ("Operation not permitted"). So `git status` in any worktree on `main` reports them as unreadable, and every verb that reads a worktree's changes counts them as changed. On 2026-11-12 this refused `codeflow spec status` in a records worktree and made merges of `main` and worktree cleanups operator steps. This task renames the three files to names the sandbox's patterns do not match and adds a test that fails when a tracked path gets such a name again.

When this task was filed, the configured pattern that hides the three files was not yet identified; `## Findings` now names it (the machine's managed settings). This project's workspace root has no broad read deny for `*secret*`. The shipped presets deny `Read(**/*secret*)` and try to exempt source files with `!` entries, which TSK-1106 records as not taking effect as permission rules. So AC-5 reads its patterns from the shipped presets, with their `!` exceptions ignored.

Scope and non-goals:

- Only the three test files are renamed, with the references that follow them. A sandboxed `git status` on `main` at eb4d74418 reported these three and no other path, and a name listing of `git ls-files` found no other tracked source or test file whose name matches.
- No guard changes. The hooks' secret-path rules (TSK-335, TSK-1002) and the shipped preset denies are unchanged. TSK-1106 owns the presets.
- `crates/codeflow-cli/tests/ci_cli/scan_exemption_admission.rs` is a different file and is not touched.

The rename itself is made by the operator, because an agent cannot read or write those paths in the sandbox. The builder writes an operator script whose `--check` shows the plan, and which runs `git mv` for exactly the three paths, pinned by their blob ids at the base.

Moved from TSK-1105 (2026-11-12, the Director's ruling on draft 18): TSK-1105's AC-7 to AC-10 become this task's AC-1 to AC-4, text unchanged, because the cost is paid on `main` now and TSK-1105 is a larger task on the EPC-022 line. TSK-1105 gets a dated note on each moved criterion naming this task, in the next records change on that line.

## Outcome

After this merges, a Claude session can run `git status` and the record verbs in a worktree on `main` inside its sandbox, and merge a `main` that writes no path Claude Code itself protects (such as `.claude/agents/` and its baseline copies); a newly tracked path whose name the shipped presets deny fails a test.

## Findings

- Denied paths and the commands that hit them (AC-1):
  - A sandboxed `git status --short` in this task's worktree, at `main` `eb4d74418` plus this record's commit, on 2026-11-12 at 14:36 (coord/ci) printed only these three lines:
    - `crates/codeflow-cli/tests/ci_cli/secret_scan_exemption.rs: Operation not permitted`
    - `crates/codeflow-cli/tests/refusal_journey/secret_paths.rs: Operation not permitted`
    - `crates/codeflow-core/tests/managed_secret_scan.rs: Operation not permitted`
  - `codeflow spec status` was refused in a records worktree on 2026-11-12, because it counted the three paths as changed (coord/records).
  - A sandboxed `git worktree add` of `.worktrees/tsk-1461-reword` at about 14:15 on 2026-11-12 was refused on the three paths and left a partial folder (coord/catalog).
  - `du -sh` of that partial folder at 14:22 printed "Operation not permitted" on all three paths (coord/ci).
  - For the same reason, merges of `main` into task branches and worktree cleanups became operator steps on 2026-11-12.
- Other protected writes, which this task does not fix:
  - The same `git worktree add` was also refused writing `.claude/agents/cf-reviewer.md` and `.claude/agents/cf-security-reviewer.md`.
  - Sandboxed merges of `main` into TSK-1275 (13:16) and TSK-1433 were refused on `.claude/agents/cf-security-reviewer.md` and its `.codeflow/.baseline/` copy.
  - These are Claude Code's own protected write paths, not a CodeFlow preset rule. A sandboxed add or merge that writes a `.claude/agents` file still fails after this task.
- The pattern that hides the three files is `Read(/**/*secret*)` in the machine's Claude Code managed settings (`/Library/Application Support/ClaudeCode/managed-settings.json:151`). That file is machine configuration, not this project's, and this task does not change it. The description's statement that the pattern was not identified predates this finding. AC-5 still uses the `Read` deny patterns of the shipped presets (`crates/codeflow-core/src/security/actions.json`) with every `!` exception ignored.
- The same pattern stops an in-tree `cargo doc` rerun (AC-3):
  - Inside the project tree, the sandbox lets a session write a file whose name contains "secret" (any case, any extension), but not read or remove it. A probe on 2026-11-12 at 18:40 (coord/ci) wrote `probe.SECRET_X.html`, `probe.SecretHit.html` and `probe.secret_shaped.html` in the tree: write ok, read and remove denied. The same names in the session scratchpad could be written, read and removed.
  - rustdoc writes 12 such pages for public `codeflow_core` items: `remedy::SECRET_STAGED`, `SECRET_SCAN_INCOMPLETE`, `SECRET_ENGINE_UNAVAILABLE` and `SECRET_SELECTION`; `hooks::scan::SecretHit`; `hooks::git_hook::commit_msg_secret_scan`; `coord::text::secret_shaped`; `hooks::policy::SecretScanEngine` and `SecretScanInlineAllow`; `work_start::check_secret_scan_exemption_admission`; `classify::validate_secret_scan_exemption_entry` and `is_secret_scan_exemption`.
  - So every in-tree rerun exits 101 with `failed to remove file .../target/doc/codeflow_core/remedy/static.SECRET_STAGED.html: Operation not permitted`. AC-3's doc run therefore uses a target folder outside the tree. The 12 items keep their names (the Director's ruling of 18:47).
  - The managed rule's effect on build output and on future secret-named paths is filed for the operator's sandbox decision, outside this task.
- AC-2's route is the rename: the three files get names that no shipped `Read` deny pattern matches.
- AC-6's reading, settled with coord/records: "old names" means the old file paths.
  - The Rust module names `secret_scan_exemption` and `secret_paths` stay, with new `#[path]` values. Every test name stays the same, so both test-times files (`scripts/windows-test-times.json`, `scripts/coverage-test-times.json`) stay valid.
