# TSK-1347: The policy check keeps running when GitHub blocks pull_request_target by default

## Description

Source: the TSK-1040 security review at `35aa2174a` (`coordination/coordinators/parallel/reviews/tsk1040-security-opus-35aa2174a.md`, F1), filed at coord/ci's request on 2026-11-05.

GitHub announced on 2026-11-02 (https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2, read 2026-11-05) that workflow runs triggered by `pull_request_target` are blocked by default in public repositories on GitHub Free, Team and Enterprise Cloud, "unless an applicable Actions event policy explicitly allows them". Private and internal repositories and GitHub Enterprise Server are not affected. Brownouts run on 2026-11-09 and 2026-11-16, 16:00 to 18:00 UTC, when blocked runs fail with an error annotation and the workflow does not execute. Between them the rule runs in evaluate mode with warnings. Enforcement starts on 2026-12-02. The page does not say whether same-repository pull requests are exempt, or name the setting's location beyond the docs it links.

The verdict job `trusted: commit standards` runs only on `pull_request_target` (`.github/workflows/codeflow-policy.yml:4`, `:46`, `:79`), and so does its shipped copy (`assets/base/ci/codeflow-policy.yml`). `codeflow-ci.yml` and `codeflow-registry.yml` describe the same split. Under the block, this public repository's required check stops running, so every pull request fails closed and cannot merge, and so does every public adopter's.

The event is a security property here, not a convenience: the check runs from the default branch and never runs head code, so a pull request cannot edit the job that judges it. TSK-1343 and TSK-1103 rely on that.

Non-goals: the repository setting itself, which is the operator's, and private repositories.

## Outcome

After this merges, a maintainer of a public repository keeps a working required policy check after GitHub's default block, either through a documented Actions event policy that allows only the managed workflow or through a design that no longer needs the event. `codeflow doctor` tells an adopter whose policy would block it, and how to fix it.

### AC-2: the decision and the threat each option leaves

Decision: an Actions event policy that allows `pull_request_target` for `.github/workflows/codeflow-policy.yml` alone. The trust design does not change, so no ADR.

| Option | Keeps "default branch, never head code" | Threat it leaves |
|---|---|---|
| A. Event policy targeting the policy workflow alone (chosen) | yes: the event still runs the default branch's file at `github.sha`; the head is fetched as git data (ADR-0091) | an administrator can widen or delete the policy. Deleting it fails closed: no check, no merge. Widening it to every workflow lets any later `pull_request_target` workflow that checks out head code run with the default branch's token and secrets, which is the risk GitHub's default closes. Doctor warns on a wide policy. A pull request cannot use the path target, because the event never runs a head copy of the file |
| B. No `pull_request_target`: a `workflow_run` job after a `pull_request` workflow, posting a status or check run to the head | partly: the trusted job runs from the default branch | the trigger is head-controlled, so the pull request decides when and whether the trusted job runs and can add a same-named trigger. The payload's head and pull request fields need re-deriving and binding (the pull request list is empty for forks). The result is posted by API, so the required name needs a pin that a pull request's own workflow cannot satisfy; a check pinned to GitHub Actions (Mode B) can be produced by any workflow, including one the pull request adds. It also needs `pull_request` `edited` runs for body checks. TSK-1343 and TSK-1103 rely on the event, so both would need rework |
| C. Plain `pull_request` | no | the pull request edits the job that judges it, the reason the job moved to `pull_request_target` (`docs/verification/tsk-100-registry-proof.md`) |

A is GitHub's documented remedy ("Explicitly allow `pull_request_target` in an applicable Actions event policy", "Use workflow file targeting", changelog of 2026-11-02) and keeps the reviewed design. What adopters must configure changes: a public repository needs one administrator step. The Director took the block to the operator at 13:53 on 2026-11-05, and the operator applied option A on this repository at 14:21 EST (`coordination/HANDOFF-2026-10-27.md` entries of 13:53 and 14:21 in the workspace). The builder reads that as the operator's AC-2 decision; coord/ci confirms.

Not verified until a brownout: the `workflow_path` pattern form that GitHub matches, and whether same-repository pull requests are exempt. The first pull request event after the policy (19:42Z) started every workflow, which shows the policy blocks nothing else, but the default block was in evaluate mode then.
