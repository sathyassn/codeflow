# TSK-364: A substituted hook binary cannot pass a hook silently

## Description

Source: both test integrity audits of 2026-10-17 at
`eaf2ed04e932186cdd26dc4a7e5740cc553acee3` (Codex medium finding on hook
dispatch; Fable finding F2 and probes 1 and 3; Fable minor M6). Amended
after the Codex review of PR 228 (finding R1) with the primary's decision
of 2026-10-17.

Every installed git hook shim (`assets/base/git-hooks/*`, installed under
`.codeflow/git-hooks/`) runs `CODEFLOW_HOOK_BINARY` when it names an
executable file, checks only that it prints `hooks 3` to `git-hook
capabilities`, and then takes its verdict (`pre-commit:7` to `:24`). An
executable that prints that line and exits 0 disables the commit-time
secret scan, the commit format check and the pre-push gate. The code calls
the variable "a dispatch hint, not authentication"
(`crates/codeflow-core/src/git/mod.rs:21`); tests cover only a missing or
non-executable path (`crates/codeflow-cli/tests/hooks_cli.rs:7256`). No
test presents an impostor that answers the handshake. The secret scan is
the gate that is never relaxed (`.codeflow/rules/git-rules.md`).

Two related local overrides are honoured without a record:
`CODEFLOW_INTEGRATE_TOKEN` is accepted when non-empty
(`crates/codeflow-cli/src/cmd/mod.rs:37`), and no test sets it empty, so
weakening that check to "set" survives; and `CODEFLOW_HUMAN_OVERRIDE=1`.
Neither use is written to the ledger.

Split with TSK-324 (EPC-022 since 2026-10-18): TSK-324 AC-5 makes the guard
refuse an in-session assignment of `CODEFLOW_HOOK_BINARY` and a `PATH` that
changes which `codeflow` resolves, and TSK-324 records the verified
binary's digest under `~/.codeflow/versions/`. This task depends on
TSK-324 and covers what happens when the variable is set anyway, from the
launching environment.

Decision (the primary's, 2026-10-17): an impostor is refused, never
admitted with reduced assurance. The shim dispatches only to a binary
whose identity CodeFlow has established, for example the binary CodeFlow
installed and recorded with its digest; a substituted binary that answers
the handshake is refused through every entry point. A legitimate
development binary (this repository's hook and policy tasks run the
worktree's own build) is admitted only through an explicit trusted route
that records its digest outside an agent session; the ADR names that
route. No choice that relaxes the secret floor is left to the builder.

Outcome: the trust contract of a designated hook binary is written down,
an impostor is refused at every entry point with the repository unchanged,
a legitimate designated binary still works through the trusted route, and
override and integrate-token use is visible.

Product surface: adopter-facing scaffold (the shims) and engine (hooks,
ledger).

## Deliverables

- the contract: an ADR draft allocated with `codeflow adr new` (home `docs/decisions/`) stating how a hook binary's identity is established and the trusted route for a development binary, and the hook binary sections of `docs/adoption.md` and `docs/policy-reference.md`
- the shims: `assets/base/git-hooks/*` and the harness wrappers in `assets/base/settings/default.json`, with installed copies and baseline resynchronised
- override recording: the ledger write for integrate-token and human-override use (`crates/codeflow-cli/src/cmd/git_hook.rs` and `crates/codeflow-core/src/hooks/`), never recording the token's value
- tests: impostor tests in `crates/codeflow-cli/tests/hooks_cli.rs`, and an empty-token test for `cmd/mod.rs`
- release note: `changelog.d/TSK-364.md`

## Acceptance Criteria

- AC-1 With `CODEFLOW_HOOK_BINARY` naming an executable that prints `hooks
  3` and approves everything, a commit with a staged synthetic secret, a
  badly formatted commit message, a push to a protected ref and a
  protected reference update shall each be refused through `pre-commit`,
  `commit-msg`, `pre-push`, `reference-transaction` and each harness
  wrapper, with HEAD, the index and every ref unchanged; a warning alone
  never counts as handling the case; evidence: one test per entry point,
  failing before the change, with before and after ref and HEAD ids.
  (serves EPC-022 AC-62)
- AC-2 A designated binary admitted through the ADR's trusted route shall
  work through every entry point, and the same binary bytes not admitted
  through that route shall be refused; evidence: the control and negative
  case of each test above.
- AC-3 An empty `CODEFLOW_INTEGRATE_TOKEN` shall not count as present, and
  each use of the integrate token or the human override in a hook shall
  write a ledger event naming the variable, the rule it skipped and the
  ref, without the token's value; evidence: an empty-token test that fails
  when the check is weakened to presence, and ledger assertions.
  (serves EPC-022 AC-62)
- AC-4 No doc, message or comment shall state that the capability
  handshake authenticates a binary; evidence: the diff and a search of
  `docs/`, `assets/` and `crates/`.
- AC-5 (journey) With the installed build, an agent session that sets the
  variable is refused by the guard (TSK-324), and a hook run under an
  impostor set from the launching environment is refused with the
  repository unchanged, while the trusted development route passes;
  evidence: the three journeys' output.
