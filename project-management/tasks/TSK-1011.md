# TSK-1011: A child epic line inherits the line adoptions of the line it starts from

## Description

Issue #288. `work.epic_line` refuses a push that creates a new epic line
from another line's tip when the parent line carries direct commits its
epic adopted through `line_adoptions`: the child epic's record has no
adoptions, so each inherited commit is reported as "a commit made
directly on the line" (`crates/codeflow-core/src/workgraph/line_adoption.rs`).
The sanctioned route today is to copy every adoption entry (commit,
reason, review) into each child epic; the adopter split one line into
four and made sixteen hand copies of the same evidence. The manual route
works, so this is a feature generalization for 4.1.0, not a 4.0.0
defect.

Outcome: **an epic record may declare the line it starts from
(provisional `parent_line: EPC-NNN`), and the child line's check then
reads the parent epic's landed `line_adoptions` for the commits it
inherited, printing them on the class line as inherited.**

Rules:

- Inheritance is declared, never inferred from a tip: the issue's first
  option (treat a line whose first commit is another line's tip as
  inheriting) binds trust to branch shape, which a requester controls;
  the declared field is read from the trusted base like the rest of the
  epic record.
- Only commits reachable from the parent line's tip at the child line's
  start are covered, and only by adoptions landed on the parent's epic
  record at that point; a later parent adoption does not reach back.
- An unreadable parent record, a parent that is not an epic, or a cycle
  refuses, naming the cause.

Non-goals: carrying task completions between lines (TSK-318 and
TSK-402); line sync and close routes (TSK-421).

## Deliverables

- the field, its reader and the inherited check: `crates/codeflow-core/src/workgraph/line_adoption.rs`, the epic schema in `crates/codeflow-core/src/validate/`
- the class-line print: `crates/codeflow-cli/src/cmd/ci/classification.rs`
- the epic template: `assets/base/` project-management templates
- tests: unit tests and `crates/codeflow-cli/tests/ci_cli/` with a parent line, a child line and negative controls
- docs: `cf-method` "Managing a body of work" (mirrored), `docs/policy-reference.md`
- release note: `changelog.d/TSK-1011.md`

## Acceptance Criteria

- AC-1 When a child epic declares `parent_line` and its line starts at the parent line's tip, a push and `codeflow ci` of the child line shall accept the parent's adopted direct commits and print them as inherited on the class line; evidence: a CLI fixture, failing before the change. (serves EPC-023 AC-31)
- AC-2 A direct commit the parent did not adopt, a parent adoption landed after the child line started, an undeclared parent, an unreadable or non-epic parent, and a cycle shall each keep a refusal naming the cause; evidence: one negative fixture per case. (serves EPC-023 AC-31)
- AC-3 `codeflow validate --docs` shall check that `parent_line` names an existing epic; evidence: a validation test.
- AC-4 (journey) With the installed build in a scratch adopter, splitting one line into two child epics with `parent_line` and pushing both shall pass with no copied adoptions; evidence: the journey output.
