# TSK-1476: Guards hold the operator-only path for project install files

## Description

CodeFlow's init and update verbs write the files the guards and hooks enforce from: harness settings and presets, hooks, policy, workflows, the managed baseline and the manifest. Only the operator should run them in a way that writes those files. Today that rule rests on instructions: no guard refuses an agent's run of either verb, and a linked worktree's copies of the enforcement files are not protected the way the root checkout's are. This task makes the guards hold the rule.

Decision: option (A), by the operator on 2026-11-12 at about 10:36. The init and update verbs stay operator-only for any binary: the guards refuse an agent's run of either verb that can write an enforcement path, whichever binary runs it, and name the operator's path; a form that writes nothing stays allowed, and guard messages say the operator runs update. Considered and not chosen: refusing only a binary other than the installed one, because an agent's run of the installed binary would still write enforcement files; and instructions alone, because they do not fail closed. Option (A) changes public behaviour for adopters whose agents run update today.

Decision, by the operator on 2026-11-12 at about 14:25, after the first review: AC-1 is narrowed to every spelling of a run of the binary that the guards can read, and a renamed or copied binary, with the verbs' words written to a file and run later, is a named residual that the separate operator task on unsandboxed retries closes. The worktree denies in the shipped presets are dropped, because a deny on a worktree's copy also stops Git's own writes there in a sandboxed session; the guards hold those copies against shell writes, and against a harness's native write and edit tools where its shipped hooks bind edit-guard to them. Refusals that stopping an agent's run of the verbs does not need come out: text that only names the verbs stays allowed.

Non-goals: changing what the verbs write, and adding the read-only plan form, which TSK-247 adds.

Limits, by the Director's rulings of 2026-11-12:

- An agent's run of init or update in a scratch project refuses like any other, including a scratch project under the temp folder; there is no exemption by location. The earlier allowance for an agent to trial a branch build of these verbs in such a scratch project is replaced by the operator's decision above. The compiled scaffold test suites, which the guards do not judge, cover the verbs' behaviour, and the operator runs any live trial. The pull request lists this as an accepted over-refusal (AC-6).
- The guards judge command text. A program an agent builds, renames or copies, and the verbs' words written to a file and run later, are a named residual; a separate operator task on unsandboxed retries closes it.
- Codex seats keep a worktree's copies of the enforcement files protected by the guards only: the Codex sandbox cannot deny them without also blocking worktree removal in the seat. The docs name this.

Boundary with other work:

- TSK-247 AC-9 makes the update plan list the files only a person may change. That list and the guards' set of enforcement paths shall be one definition; whichever of the two tasks lands second aligns them and says so in its pull request.
- TSK-1461 changes the shipped presets and the exec guard. This task builds on main as it is; its pull request lists every file both tasks touch, so the second to land reconciles them.
- Conflict note, not a dependency: TSK-1461 binds edit-guard to Claude's native write and edit tools (Edit, MultiEdit, Write and NotebookEdit) in the shipped presets, and it lands on main first. This task ships no such binding and does not need TSK-1461's code to pass its own tests. Until TSK-1461 lands, the docs state that in a Claude session those tools can still change a worktree's copies (`docs/harness-posture.md`).

## Outcome

After this merges, an adopter's operator can rely on the guards, not on instructions, to keep agents from installing or refreshing the project's enforcement files, in the root checkout and in every worktree. In a worktree the guards hold the copies against shell writes, and against a harness's native write and edit tools where its shipped hooks bind edit-guard to them; Claude's tools reach edit-guard once TSK-1461's preset binding lands.

## Acceptance Criteria

- AC-1 When an agent command runs a build of the CodeFlow binary other than the installed hook binary as init or update, in any spelling of that run the guards can read, the guards shall refuse it and name the operator's path. A binary an agent renames or copies, and the verbs' words written to a file and run later, are a named residual, closed by the separate operator task on unsandboxed retries. Evidence: fail-before tests fed as hook payload strings for each form, refused after; nothing under test is executed.
- AC-2 When an agent command runs the installed binary as init or update and the run can write an enforcement path, the guards shall refuse it; a form that writes nothing stays allowed; evidence: fail-before payload tests, refused after, and the write-nothing form allowed.
- AC-3 The guards shall protect each worktree's harness settings, hooks and policy files against shell writes as they protect the root checkout's, so a write to a worktree's copy by redirect, copy, move, link, an interpreter or a verb is refused as the root's is; edit-guard, when a harness calls it for a native write or edit tool, shall refuse that tool's write to a worktree's copy, and the shipped Codex and Grok hooks call it for their file tools. The shipped presets name no worktree path, so Git's own writes in a sandboxed session are not stopped. This task binds no guard to Claude's native write and edit tools: they reach edit-guard through TSK-1461's preset binding, and until that lands the docs state the gap. Evidence: a test per shell route with a worktree target, refused; edit-guard tests per native tool form, called directly, refused; and the preset test that no shipped preset names a worktree path.
- AC-4 Every guard and hook message that names init or update as a sanctioned path shall name the operator as the one who runs it; evidence: a test over the messages, and the list with file and line in the pull request.
- AC-5 The install docs and managed instructions shall state that only the operator runs init and update in a way that writes project install files, whichever build of the binary, and that an agent may run only a form that writes nothing; evidence: the doc diff and a clean docs validation run.
- AC-6 Every accepted over-refusal shall be listed in the pull request with how the operator clears it, including an agent's run of init or update in a scratch project under the temp folder, which the operator clears by running the trial; evidence: the PR body's table.
- AC-7 The change shall get a cross-lineage security review with the cf-security-reviewer checklist, and the pull request shall state the threat closed and why its design is the fail-closed one; evidence: the review row.
- AC-8 No concrete path, payload or command form shall appear in the pull request title, its body summary, any commit subject, the changelog fragment or a test name until the fix is on main; evidence: the pull request as opened, checked by the reviewer.
- AC-9 When a harness calls the built binary's guard hooks before an agent's shell or file tool runs, as a session does, an agent's run of either install verb shall be refused with the blocking exit code and the operator's path, in the project, in a linked worktree and in a scratch folder, and a write to a worktree's copies of the enforcement files shall be refused, while a form that writes nothing and ordinary commands beside them pass the install check; evidence: the built-binary hook tests that feed each call as a hook payload and read its exit code and message, run at the head (journey)
