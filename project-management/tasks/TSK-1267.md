# TSK-1267: codeflow ci learns the default branch without a network credential, and says when it needs one

## Description

Source: adopter issue 527 (opened 2026-11-02 21:11Z); the Director's order of 20:15 to file it in the CI unblock planning pull request. Release: 4.0.0.

On codeflow 3.1.1, `codeflow ci` asks the destination for its default branch on every range, with `git ls-remote --symref`. On a private repository that needs a credential. A workflow that checks out with `persist-credentials: false`, the hardened setting, therefore fails every pull request policy check (`work.records`, `work.criteria_frozen`). Nothing in `codeflow ci --help` or the managed `codeflow-policy.yml` says so.

Where the code does it, read at the line tip 349d0f176:

- `crates/codeflow-cli/src/cmd/ci.rs:589-600`: with no `--destination`, the destination is the origin URL, so every run asks the network. The destination flags are hidden (`ci.rs:162-170`).
- `crates/codeflow-cli/src/cmd/ci/acceptance.rs:226-236` (`release_scope`): without a handed-over advertisement it calls `release_line::ask_destination`.
- `crates/codeflow-core/src/workgraph/release_line.rs:194-198` (`advertisement`): the `git ls-remote --symref` call; `release_line.rs:623-632` (`ensure_objects`): fetches objects the range needs from the destination.
- `assets/base/ci/codeflow-policy.yml:221-229`: the managed step runs `codeflow ci --base ... --head ... --branch ... --actor ...` and passes no default branch.

The 3.1.1 workaround stops working in 4.0.0 (coord/planning, 20:2x). An adopter passes a masked header to the lookup through the environment (`GIT_CONFIG_COUNT` with its key and value variables). On the line tip, `judging_command()` (`crates/codeflow-core/src/git/mod.rs:65-92`) removes `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n` and `GIT_CONFIG_VALUE_n`, and `remote_query::run` builds its git command with it (`crates/codeflow-core/src/git/remote_query.rs:240` and `:287`). So the header never reaches `ls-remote`, and private repositories that use the hardened checkout fail under 4.0.0. Without this task, 4.0.0 breaks them, so it is a 4.0.0 must-have (listed in EPC-022's CI unblock amendment).

Security relevance: the default branch decides whether a range is judged under the release rules (SPC-013 R-120). A value the pull request author can set would let a change pick the rules it is judged under, so only a source the author cannot set is trusted: the event of a `pull_request_target` run, or a flag in the base branch's workflow. This needs a cross-lineage review carrying the `cf-security-reviewer` checklist.

Non-goals: a new credential flow, and changing what the pre-push hook hands over.

## Outcome

After this merges, an adopter on a private repository can run the managed policy workflow with `persist-credentials: false` and pass the policy check, and a run that does need the network says so and names the fix.

## Deliverables

- the default branch from a trusted CI source, with the destination asked only when needed: `crates/codeflow-cli/src/cmd/ci.rs`, `crates/codeflow-cli/src/cmd/ci/acceptance.rs`, `crates/codeflow-core/src/workgraph/release_line.rs`
- the error text and `--help` text: the same files
- the managed workflow change: `assets/base/ci/codeflow-policy.yml` and its baseline and manifest entries

## Acceptance Criteria

- AC-1 Hosted CI shall be able to give `codeflow ci` the default branch without network access, by a flag or from the CI event (GitHub `repository.default_branch` in `GITHUB_EVENT_PATH`), and only a source the pull request author cannot set shall be trusted: the event of a `pull_request_target` run, or a flag in the base branch's workflow; evidence: a test showing a value controlled by the head is not trusted.
- AC-2 The destination shall be asked only when the answer needs its branch tips, and when it is asked and fails for want of a credential, the error shall say so and name the fix; evidence: a test for each of the two cases and the error text.
- AC-3 `codeflow ci --help` and the managed `codeflow-policy.yml` shall document the need, and the managed workflow shall pass the default branch to its `codeflow ci` step from the trusted flag or event input of AC-1, with no header option; evidence: the help text, the workflow diff and the managed-asset consistency test.
- AC-4 (journey) On the 4.0.0 path, with the `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n` and `GIT_CONFIG_VALUE_n` environment scrubbed as `judging_command()` scrubs it, a private-repository fixture, plus a real line run on the 4.0.0 path where one exists, shall pass the policy check with no credential reaching the `codeflow ci` step; evidence: the fixture output and, where a real line run exists, its run link (no scratch GitHub repository; operator direction 2026-11-02, relayed by coord/parallel).
