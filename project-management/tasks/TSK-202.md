# TSK-202: Keep the release dispatch within GitHub's limits

## Description

The first v3.0.0 dispatch (run 37000508223) stopped in the release source
authority job before any check ran: "An error occurred trying to start process
'/usr/bin/bash' ... Argument list too long". The job passed the whole
cargo-dist plan, which carries the full release notes, through one environment
variable, and 3.0.0's plan exceeds Linux's 128 KiB limit on a single variable.
The post-announce verification had the same pattern. Both now take only the
fields they read (the announcement tag and the pull request run mode). No tag,
draft or release was created by the failed run.

Two read-only reviews of every later step on the public repository then found
the next stop: the 3.0.0 notes render to 167,352 characters, and GitHub
refuses a release body above 125,000, so the draft could never be created.
Nothing checked the size before dispatch. The notes now stay whole when they
fit; otherwise each entry is cut to its bold label, every note and quoted
block stays, and a link points to the full section at the source commit. The
renderer fails closed when even that is too long. The pull request check, the
main-push state check and `codeflow integrate` render the notes and refuse a
section that would push the plan job output past GitHub's 1 MB, counted in
UTF-16 with the section carried twice (3.0.0's plan is 714,658 UTF-16 bytes),
so an oversized section fails on the pull request that grows it.
The release guide adds the dry-run dispatch before the real one and the
recovery steps for a stopped draft.

The dry-run dispatch (run 37003474977) built every artifact on the public
repository and showed a 91 MB `source.tar.gz`, almost all of it retained
evidence under `docs/verification/`. The operator ruled that consuming
projects should not receive it: `.gitattributes` marks that folder
`export-ignore`, and `git archive` builds a 10 MB source archive that still
builds the release binary. Non-goal: any change to what the guards check.

## Acceptance Criteria

- AC-1 The release source authority and post-announce workflows pass only the
  plan fields they read, and still compare the plan's tag with the requested
  tag and refuse an empty one; evidence: the workflow diff and
  `cargo test -p codeflow-cli --test release_contract`.
- AC-2 No release workflow passes the whole plan into the environment;
  evidence: the release contract test fails on the previous post-announce
  workflow and passes on the fixed ones.
- AC-3 Release notes over 125,000 bytes render as the section with each
  entry cut to its label, keeping headings, notes, quoted blocks and the
  source marker, with a link to the full section at the source commit;
  notes within the limit stay whole; the renderer refuses notes that do not
  fit either way; evidence: `scripts/test_release.py` notes tests, and the
  real 3.0.0 notes rendering under the limit.
- AC-4 The pull request check, the main-push state check and the structural
  check refuse a pending section whose notes GitHub would refuse or whose
  plan job output would exceed 1 MB in UTF-16; evidence: the check-pr and
  check-state tests, which fail on the previous script, and the bound
  covering the 3.0.0 dry-run plan.
- AC-5 `docs/releasing.md` names the dry-run dispatch before the real one,
  the renderer's repository argument and the recovery for a stopped draft;
  evidence: the guide diff and the guide budget test.
- AC-6 `source.tar.gz` leaves out exactly `docs/verification/` and still
  builds the release binary; evidence: the release contract test, which
  compares the real `git archive` with the tracked files (negative controls:
  a parent-folder exclusion and evidence put back), and a release build from
  the extracted archive.
- AC-7 When the operator dispatches v3.0.0 again on the merged main, the
  authority job creates the draft and the release publishes; evidence: the
  dispatch run and the published release. (journey)
