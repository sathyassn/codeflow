# TSK-1150: Generated workflow jobs declare a timeout

## Description

Bound generated CI jobs so a hung setup or gate releases its runner. This
standalone fix contributes to EPC-022 and addresses issue 472.

## Outcome

After this merges, adopters receive bounded workflow jobs and can retain
project timeout values through updates.

## Deliverables

- Job defaults: `assets/base/ci/codeflow-ci.yml` and its managed baseline.
- Contract and update tests: `crates/codeflow-core/tests/`.
- Timeout guidance: `docs/capabilities.md`.
- Release note: `changelog.d/TSK-1150.md`.

## Acceptance Criteria

- AC-1 The generated gates and candidate jobs declare timeout-minutes above the measured hosted gate time and the adopter maximum of 1335 seconds; the record states the basis.
- AC-2 A contract test fails when any job in a shipped GitHub workflow template lacks timeout-minutes.
- AC-3 A three-way update test proves a project's own timeout survives codeflow update. (journey)
- AC-4 CodeFlow's own workflow passes the same contract check, and one documentation line explains the timeout and how to change it.

## Implementation notes

- Band: Easy (1 to 2 h). Basis: two job keys, two tests and one docs line.
- Timeout: 45 minutes, matching this repository's existing gate job limit.
- Hosted basis: run 41337769821 at line tip 92149edc8, coverage partition 2 ran from 18:40:10 to 18:59:29 UTC on 2026-11-01 (1159 seconds). The adopter reported a maximum of 1335 seconds in issue 472. A 2700-second default leaves 1365 seconds over that maximum for setup, installation and variation.
- TSK-384 and TSK-1026 were todo with no open PR on 2026-11-01. Both share the shipped workflow; later changes must retain timeout keys on existing and newly added jobs. No dependency prevents this fix.
- Design intent: N/A, workflow configuration only.
- Execution: assigned Codex builder seat; coord/parallel owns review routing.
