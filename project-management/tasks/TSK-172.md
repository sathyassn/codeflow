# TSK-172: guard families, the enforcement baseline and repository binding

Unit 2 of 5 of the harness permissions work, TSK-171 to TSK-175 (decision record:
`ADR-0075`; design: `docs/verification/permission-presets-design-2026-09-28.md` section 2).
It reads TSK-171's policy keys and merges after TSK-171; the two can be
drafted and reviewed in parallel and ship in the same release as separate
pull requests.

## Description

TSK-171 refuses the canonical spellings of every rung-4 action through native
deny rules. Those rules match command text as a prefix or glob, so they miss
the forms the reviews found: `env sudo`, `bash -lc 'sudo -n id'`, `cargo
+stable publish`, `gh -R o/r release create`, `git push origin v1.2.3`,
`git stash drop`, a traversal write to `.codeflow/policy.json`, and a
headless peer started from a Python one-liner. This unit adds the guard checks
that parse the unwrapped argv and interpreter one-liners, and moves the
guards' authority from the repository's mutable files to an enforcement
baseline that only the operator advances.

The baseline is found through a binding that only the operator writes. A
repository whose routing changed, or whose baseline disappeared, is refused
and needs the operator; it never falls back to reading its own files. Only a
project whose hooks predate this release keeps the old narrow form until its
next `codeflow update`.

Operator decisions this unit applies (2026-09-28): D4, headless peer runs are
refused in consumers too, with a config opt-in; D5, privilege escalation is
blocked, including wrapped forms and `osascript ... with administrator
privileges`.

The text checks are command-level rules. A script file or binary that starts
a child process, and a path or command name assembled at run time, are not
seen; the sandbox, the baseline and the token's scope sit below them. The
closeout states this and does not claim a complete boundary.

Non-goals: hook wiring, fail-closed commands, the guard-readiness preflight and readiness
(TSK-173); the retry check (TSK-174).

## Acceptance Criteria

- AC-1 When a command reaches `sudo`, `su`, `doas`, `pkexec`, `gsudo`,
  `runas`, `Start-Process -Verb RunAs` or `osascript ... with administrator
  privileges` through a path, `env` with options, `command`, `nohup`,
  `timeout`, `xargs`, `find -exec`, `npx`, `bunx`, a shell `-c`, `-lc` or
  `-ic` string, or a control structure, exec-guard shall refuse it under
  `security.privilege_escalation`; `bash -c 'printf ok'`, `bash -lc 'cargo
  test --workspace'`, `source .venv/bin/activate`, `LD_LIBRARY_PATH=/opt/lib
  cargo test`, `sudoku --help` and `grep -rn sudo docs/` shall pass, with
  script findings under `security.script_bypass` (warn); evidence: paired
  tests.
- AC-2 When a command publishes, releases, pushes a tag, creates or edits a
  gist, or deletes, archives, renames or changes the visibility of a
  repository, exec-guard shall refuse it under `security.outward_actions`
  with a message that the operator performs it and names `cargo package` and
  `npm pack --dry-run`; this includes `cargo +stable publish`, `npm
  --ignore-scripts publish`, `uv --directory . publish`, `gh -R o/r release
  create v1`, `git push origin v1.2.3` against a fixture tag, `git push origin
  refs/tags/v1`, `git push --follow-tags`, `git push origin --mirror`, `gh
  repo edit o/r --visibility public`, `gh api -X PATCH repos/o/r -f
  visibility=public` and `gh api -X DELETE repos/o/r`; `git push origin
  task/x`, `gh release view v1`, `cargo package` and `npm pack --dry-run`
  shall pass; evidence: tests with a fixture repository.
- AC-3 When a command would discard work that exists only locally, git-guard
  shall refuse it under `git.discard_uncommitted` and name the recoverable
  route: `reset --hard` with tracked changes; `checkout` or `restore` whose
  pathspec is absent, `.`, `:/` or a directory; `stash drop` and `stash
  clear` of an existing entry; `clean` whose dry run lists an untracked
  non-ignored path; `clean -x` or `-X` listing a path outside
  `git.clean_regenerable`; any `clean -ff`; `branch -D` of commits reachable
  from no other ref; `worktree remove --force` of a dirty tree. `git restore
  <file>` beside unrelated dirty paths, `clean -fdX` over `target/` only,
  `rm -rf ./target` and `stash pop` shall pass; evidence: tests pairing dirty
  and clean fixtures.
- AC-4 When a command writes an enforcement path by a recognized write form,
  including after `.` and `..` normalization and through a symlinked parent,
  the guards shall refuse it under `git.hook_integrity`; the write-refused
  list shall also hold the git routing files, which are not part of an
  identity: a worktree's `.git` pointer file, and the `commondir` and
  `gitdir` files under the common dir's `worktrees/`
  (`gitrepository-layout(5)`); the path list shall have one source,
  replacing `SecurityPolicy.protected_paths`; evidence: tests per form.
- AC-5 exec-guard shall scan the code of `python`/`python3 -c`, `node -e` and
  `-p`, `perl -e`, `ruby -e` one-liners and heredocs under one key,
  `security.interpreter_scan`, reporting under the family matched: a
  privilege launcher, a headless peer launcher (`codex exec`, `codex e`,
  `claude -p`, `claude --print`, `grok -p`), an enforcement path, or a
  recursive delete of `/`, `~` or `$HOME`. A launcher counts only as a
  command word or a subprocess argument. `grep -rn "codex exec" docs/`, `rg
  'claude -p' assets/` and `python3 -c "print(os.environ.get('SUDO_USER'))"`
  shall pass; evidence: paired tests.
- AC-6 When a command's argv or interpreter code names a secret store from
  the sandbox deny list, exec-guard shall refuse it under
  `security.secret_reads`; `cat README.md` and reading `.env.example` shall
  pass; evidence: tests.
- AC-7 When a headless peer run is attempted directly, through the
  unwrapper, or in interpreter code (AC-5), exec-guard shall refuse it with a
  message naming an interactive seat and the route for the project's tier,
  and `security.headless_opt_in` in `.codeflow/policy.json`; with an opt-in
  whose `families` names the peer's catalog family (`claude`, `codex` or
  `grok`) and a non-empty reason it shall pass with a logged note, and doctor
  shall name the matching catalog harnesses (`claude-code`, `codex-cli`,
  `codex-app`, `grok-cli`); config decides, and a detected interactive
  harness only shapes the message; an unknown family id shall be a policy
  error;
  an opt-in without a reason shall be a policy error; help and version
  probes, a payload piped to the guard, and qualification rows run from the
  operator's terminal shall need no opt-in; `warn` shall be accepted as a
  legacy value; evidence: tests.
- AC-8 `codeflow hook edit-guard` shall refuse a file-edit tool call that
  targets an enforcement path: Codex `apply_patch` by every `*** Add File:`,
  `*** Update File:`, `*** Delete File:` and `*** Move to:` header; Grok
  `search_replace` and `write` by `file_path`; Claude `Edit`, `Write`,
  `NotebookEdit`; it shall allow other paths and refuse a payload it cannot
  read; evidence: tests with payloads captured from each harness.
- AC-9 (baseline and registry) For a bound path (AC-13), git-guard and
  exec-guard shall evaluate the policy stored in the current identity of the
  bound repository's baseline (keyed by the real path of the common git dir,
  under the CodeFlow state root) and never the policy in `HEAD`, the index or
  the working copy. Each identity shall record the contract it was approved
  under. `codeflow init` and `codeflow update` shall record the identity they
  write and bind the root they run in (`bindings.json`), in the same
  operation; `codeflow baseline approve` shall record the index's identity
  (or `--tree <ref>`'s) after showing its diff from the current one, **and
  the first approve in a root shall also create that root's binding in the
  same operation**; when the identity equals one already approved on this
  machine under the current contract, approve shall show a binding-only
  confirmation naming the exact destination root and the earlier approval,
  with no full policy review, and a content match shall never choose the
  path; approve shall refuse an identity whose harness hook config lacks a
  required guard entry in the fail-closed form with the current
  `--contract`; `codeflow baseline bind [<path>]` shall record a binding
  after showing the old and new common dir. exec-guard shall refuse all
  four commands from agent sessions, through wrappers and CLI-global flags
  alike. `codeflow init` is described in the command help
  and docs as an operator bootstrap: on a fresh repository with an unborn
  `HEAD` it enrolls the scaffolded identity before the first agent commit;
  evidence: tests, including init on an unborn `HEAD` followed by an agent
  commit that passes, a first approve in a fresh clone that leaves the root
  bound, and a binding-only confirmation for an identical identity.
- AC-10 (commits and transitions) Before a command that creates a commit,
  git-guard shall refuse it unless the enforcement entries of every tree it
  will commit equal an approved, contract-compatible identity by path, mode
  and blob, additions and deletions included (the trees per AC-14 and
  AC-17). `pull` shall be refused in agent sessions with a message naming
  the replacement, `git fetch <remote>` then `git merge --ff-only
  <remote>/<branch>` or `git rebase <remote>/<branch>`, and stating that a
  human terminal is unaffected.
  Before `checkout`, `switch`, `restore --source`, `reset`, `worktree add`,
  `stash apply` and `stash pop`, it shall refuse a target tree whose
  enforcement entries equal no approved, contract-compatible identity,
  naming `codeflow baseline approve --tree <ref>`; an identity approved under
  an older contract shall be refused until requalified. A working-copy
  difference shall be reported, not refused. Paired evidence:
  `update-index --cacheinfo` of a weaker policy refused, and an index
  changed by a library then plain `commit` refused on state; a staged mode
  change, a staged deletion and a staged addition refused; a checkout of an
  unapproved older commit refused, of an approved compatible one allowed,
  and of an approved older-contract one refused; a merge bringing an
  enforcement change refused; ordinary commits, branch switches, rebases onto
  the integration tip and `worktree add` passing; an operator edit approved
  then committed with agent calls in between passing.
- AC-11 (the states) The guards shall distinguish, and doctor and the
  orient digest shall report: **bound**; **binding lost**, meaning a
  registered root whose effective common dir is not its recorded key, a
  read failure of the store per AC-20, a missing or unparsable baseline for
  a registered root, a void exclusion boundary (AC-21), or an admission pin
  the store does not satisfy, where git commands that create commits, move
  refs or change routing and `codeflow guard-probe` shall be refused naming
  `codeflow baseline bind`, and other calls judged under the binary's
  built-in policy; **excluded**, on the built-in policy with seats
  unavailable (AC-21); **not enrolled**, only when no entry covers the path,
  its common dir has no baseline, no pin is held, and the store is readable
  and empty or absent. Bindings, exclusions and the pin shall be checked
  before the `--contract` flag: in a bound root a hook without `--contract`
  shall get the baseline, not the narrow form. Outside every entry, a hook
  without `--contract` shall keep the narrow form (policy from `HEAD`, or the
  working copy on an unborn `HEAD`, with "no enforcement baseline"
  reported), and the docs and doctor shall describe the missing flag as a
  compatibility selector, not proof that the repository predates this
  release; a hook with `--contract` shall use the binary's built-in policy.
  A lost binding shall never be treated as not enrolled while the store or a
  pin remains; total erasure of the store, seen by a new process without a
  pin, is the declared residual on routes where the seat can write the
  store, and the tests record it as such; evidence: tests of each state and
  each transition between them.
- AC-12 The checks of AC-1 to AC-11, AC-13 to AC-17 and AC-19 shall each finish
  within the guard time budget on a repository the size of CodeFlow's;
  evidence: a timing test.
- AC-13 (repository binding and effective context) On every call the guards
  shall resolve the command's effective worktree top level, git dir, common
  dir, index and config with git itself, applying the command's `cd`, `-C`,
  `--git-dir`, `--work-tree`, `GIT_DIR`, `GIT_COMMON_DIR`, `GIT_WORK_TREE`
  and `GIT_INDEX_FILE` (`git(1)`, "ENVIRONMENT"); a path is bound when the
  longest registered root containing its top level has a matching common
  dir; from a bound path, a git-dir, common-dir or work-tree override that
  resolves outside the bound repository shall be refused; a statement that
  exports any of those variables or `GIT_CONFIG_*` for later calls shall be
  refused; an override the guard cannot resolve shall be refused. Paired
  evidence: a seat worktree's `commondir` edited to point at a copy, refused
  as binding lost; `git init --separate-git-dir` at a bound root refused,
  and an operator-made relocation refused until `codeflow baseline bind`;
  `GIT_DIR=<copy> git commit`, `GIT_COMMON_DIR=<copy> git commit` and `git
  --git-dir=<copy> commit` from a bound path refused, and `git -C <other
  enrolled repo> status` passing under that repository's binding; the
  baseline deleted, and the registry corrupted, each refused as binding lost;
  a genuine legacy install (pre-release hooks, no state root) on the narrow
  form, then bound after `codeflow update`; contract-3 hooks with no state
  (a fresh clone on a new machine) on the built-in policy until `codeflow
  baseline approve`; two ordinary linked worktrees under one root bound to
  one baseline, and a linked worktree outside the root whose common dir is
  enrolled using that baseline; a nested repository under a bound root
  refused until the operator adopts or excludes it (AC-21).
- AC-14 (alternate and target index) The commit check shall read the index
  git will commit: the target worktree's own index, not the root checkout's,
  or the file `GIT_INDEX_FILE` names. Paired evidence: an approved default
  index with an unapproved alternate index, `GIT_INDEX_FILE=<alt> git
  commit`, refused; an alternate index with approved entries passing;
  worktree B's index unapproved while the root's is approved, a commit in B
  refused, and the converse passing.
- AC-15 (effective config) Every call shall resolve the effective
  `core.hooksPath` for the target worktree by asking git with the command's
  `-c` and `--config-env` flags and `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>`,
  `GIT_CONFIG_VALUE_<n>` and `GIT_CONFIG_PARAMETERS` environment
  (`git-config(1)`, "ENVIRONMENT"), so that case folding, includes and
  worktree config apply, and refuse a value that is not the shipped hooks
  path. Paired evidence: `git -c core.hookspath=/x commit`, `git
  --config-env=core.hooksPath=V commit`, `GIT_CONFIG_COUNT=1
  GIT_CONFIG_KEY_0=core.hooksPath GIT_CONFIG_VALUE_0=/x git commit`, an
  `include.path` file setting it, and a `config.worktree` setting it in the
  target worktree, each refused; the same forms setting `user.name` or
  `user.email` passing.
- AC-16 (plumbing and routing by effect) `codeflow integrate <branch>
  <target>` shall be classified as a replay plus a ref move: before it runs,
  git-guard shall apply AC-19's pre-check to the branch's commits and require
  every replayed tree and the target's resulting tree to equal an approved
  identity, as for `git rebase`, since its rebase and `update-ref` run in
  child processes the hooks never see (E20
  `crates/codeflow-core/src/integrate.rs:1-13`, `:245-262`); `gh pr merge`
  is AC-24's; a local landing that changes an enforcement path shall be
  refused naming "the operator approves this landing with `codeflow
  baseline approve --merge <source> --into <target>`", queued for the
  operator, an operator command that computes every tree the landing will
  create with AC-19's pre-check and query, shows each enforcement diff and
  records those identities in an approval bound to the repository's
  baseline key, the source ref and commit, the target ref and commit and
  the method (`merge --no-ff`, `merge --ff-only`, `integrate`, `rebase`);
  at the landing git-guard shall re-read all four and refuse, queued for a
  fresh approval, when any differs, and the push of the landed target shall
  be checked against the approved result. From agent sessions git-guard shall also
  refuse a git command whose effect is to write live enforcement files
  (`checkout-index`, `read-tree -u`, `apply` or `apply --index` of a patch
  touching an enforcement path), to write the index or refs directly
  (`update-index`, `read-tree`, `update-ref`, `symbolic-ref`, `commit-tree`,
  `write-tree`, `replace`, `filter-branch`, `fast-import`, `apply --cached`
  touching an enforcement path, `fetch` whose resolved destinations include
  `refs/heads/` or `HEAD`, or with `--update-head-ok`, where destinations
  are resolved in git's precedence (`git-fetch(1)`, "Configured
  remote-tracking branches", `--refmap`): with no source on the command,
  the effective `remote.<name>.fetch` values and `remote.<name>.mirror`;
  with sources on the command, the union of the explicit destinations and
  the destinations the mapping gives the selected sources, the mapping
  being `remote.<name>.fetch` unless `--refmap` replaces it, and an empty
  `--refmap=` leaving only the explicit destinations), or
  to change the route
  to the baseline (`init` inside a bound root, `--separate-git-dir`,
  `worktree move`, `worktree repair`, `config` writes of `core.worktree`,
  `core.bare`, `core.hooksPath`, `extensions.worktreeConfig`, `include.*` or
  `includeIf.*`); a git subcommand or alias it does not classify shall be
  refused in a bound repository, naming the operator. This check owns the
  classification and does not rely on the existing path for commands the
  guard cannot judge. Paired evidence: each refused form; `git fetch`, `git
  fetch origin`, `git fetch origin main`, `git fetch --tags`, `git status`,
  `git log`, `git diff`, `git show`, `git add` of a non-enforcement path and
  `git init` in a scratch directory outside every root passing;
  `remote.origin.fetch = +refs/heads/*:refs/heads/*` configured, then a
  plain `git fetch`, refused, and `remote.origin.mirror = true` then `git
  fetch`, refused, while the default `+refs/heads/*:refs/remotes/origin/*`
  passes; with the heads mapping configured, `git fetch origin topic` (an
  explicit source, no destination on the command, `topic` not checked out)
  refused, `git fetch --refmap= origin topic` passing, and `git fetch
  --refmap= origin topic:topic` refused on its explicit destination; with
  the default mapping, `git fetch origin topic` passing; `codeflow integrate task/x integration/y` with a replayed commit
  that changes `.codeflow/policy.json`, refused naming the operator command,
  and passing after `codeflow baseline approve --merge task/x --into
  integration/y`; the same approval after the source moved, after the
  target moved, and used by `git merge --no-ff` instead of `integrate`,
  each refused; an unchanged-enforcement `codeflow integrate`, passing.
- AC-17 (replayed trees) For `merge`, the check shall use the result tree
  from `git merge-tree --write-tree` (`git-merge-tree(1)`) before the merge,
  run only after AC-19's pre-check and in AC-19's sanitized query context;
  for `rebase`, and `cherry-pick`, `revert` or `am` over a range, every
  replayed commit, allowed when no commit in the range changes an
  enforcement path and the base tree's entries are approved, or when each
  intermediate result equals an approved identity; `--continue` after a
  conflict shall be checked on the index at that moment. Paired evidence: a
  rebase whose middle commit weakens the policy and whose last commit
  restores it, refused; a cherry-pick range with the same shape, refused; a
  conflict resolved with an unapproved staged policy then `rebase
  --continue`, refused; an unchanged-enforcement rebase and cherry-pick
  range as the positive controls, passing.
- AC-18 (operator guidance and the guard's own queries) When a commit is
  refused because the index mixes enforcement entries from two approved
  identities, the message shall list, per enforcement path, which identity
  its staged entry matches, and name both ways out: stage every enforcement
  path from the working copy, or unstage them all, then commit. **Host-side
  inspection shall run no program the repository selected.** The guards'
  queries shall change no index, ref or working tree; `rev-parse`, `ls-files
  -s`, `ls-tree`, `config --get` and `check-attr` shall write nothing, and
  `merge-tree --write-tree`, which writes tree and blob objects, shall run
  only as AC-19 states, so that the repository's object store is unchanged.
  All queries shall run with `core.fsmonitor` off and with no pager,
  textconv or external diff. Evidence: a message test after an operator
  update with half the new identity staged; a test that a fixture
  `core.fsmonitor` command in the repository's config is not run by a guard
  call; AC-19's controls.
- AC-19 (merge pre-check and sanitized query) Before any candidate merge
  query, for `merge`, `rebase`, `cherry-pick`, `revert`, `am`, `stash
  apply`, `stash pop`, `checkout -m`, `switch -m` and each `--continue`,
  git-guard shall read, running no program, the effective config for the
  command's context (all scopes, includes, the command's `-c` and
  environment) and the attributes of every path the merge changes on either
  side (`check-attr` from the worktree, the index and each tree involved;
  `gitattributes(5)` lists the sources), and shall **refuse the command
  itself** when a changed path selects a merge driver other than a
  built-in, resolved by effective definition and never by name: a set
  `merge` (the text driver), an unset `-merge`, and a string `text`,
  `binary` or `union` only when the effective config defines no
  `merge.<name>.driver` of that name, since git looks up user-defined
  drivers first; unspecified `merge` (`!merge` or none) selects
  `merge.default`, which must resolve to a built-in in the same way; or
  when a changed path has a `filter` that the config defines
  (`clean`, `smudge` or `process`), or renormalization is on
  (`merge.renormalize`, `-X renormalize`, `--renormalize`); the refusal
  shall name the operator's route (a human terminal, or removing the driver
  or filter). Drivers shall never be disabled only for inspection. The
  query shall then run in a guard-private temporary repository that borrows
  the repository's objects through `objects/info/alternates`, with
  `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, a config of only
  the validated keys that affect the result and name no program,
  `GIT_ATTR_SOURCE` set to the empty tree plus an `info/attributes` of the
  validated built-in `merge` selections, `core.fsmonitor` off, a fixed
  system `PATH`, a private `HOME` and no other `GIT_*` variable; it shall be
  discarded afterwards. Paired evidence, each with an inert canary program
  that only writes a marker: `.gitattributes` selecting the canary driver
  for a path both sides changed, then `git merge`, `git rebase`, a
  `cherry-pick` range and `git stash pop`, each refused before any query
  with the marker absent; `merge.default` naming the canary with no
  attribute, refused, marker absent; a defined canary filter on a changed
  path with `merge.renormalize=true`, and with `-X renormalize`, refused,
  marker absent; the canary driver defined in the trusted home's global
  config, refused, marker absent; same-name custom drivers (the canary
