# TSK-321: A person applies an agent's proposed enforcement change

## Description

An agent cannot change enforcement files in session (ADR-0075:227-229), and
there is no reviewed route for it to draft a project enforcement addition
that a person then applies (https://github.com/sathyassn/codeflow/issues/172).
This task gives that route and keeps the native rule files in step with the
policy, under decisions 6, 8 and 15:

- One authority: project enforcement additions are policy keys in
  `.codeflow/policy.json`. No overlay, approval store, ownership record or
  journal.
- Rendering targets: Claude `permissions.deny` in `.claude/settings.json`
  and a generated `.codex/rules/codeflow-project.rules`; Grok reads Claude's
  rules; if a canary shows Codex loads one rules file only, a marked region
  of `.codex/rules/codeflow.rules` instead.
- Render only adds: the render of a policy is a deterministic set of
  entries. `init`, `update`, `apply` and `codeflow policy render` add every
  missing rendered entry in the existing exception-safe order, and never
  remove, reorder or rewrite an entry (the Claude array, the Codex file and
  the Codex region alike; the region is a union, never replaced). A stale
  entry is reported by `doctor` as `unexplained` and removed by a person.
  The shipped-preset retirement on `update`
  (`crates/codeflow-core/src/scaffold/settings_merge.rs:93-96`) is
  unchanged and is not this rendering.
- Rendering boundary: `program` and `commands` declarations render to
  prefix rules; `verbs` and interleaved-option forms cannot be represented
  fully as native prefixes, so their native coverage is `partial`; a
  whole-program declaration gives `full` native coverage. A narrower
  declaration is never widened into a whole-program deny. Native rules are
  defense in depth; exec-guard's judgment stays the enforcement.
- Proposal and apply: `codeflow policy propose <name>` (name
  `[A-Za-z0-9][A-Za-z0-9_-]{0,63}`) writes `.codeflow/proposals/<name>.json`,
  confined by lexical normalization and symlink resolution, holding a merge
  patch, a reason, the schema version and the SHA-256 of the policy text it
  was computed against, and prints the file's SHA-256; the folder is
  gitignored, inert, and not an integrity path.
  `codeflow policy apply <name> --digest <sha256>`, run by a person,
  requires the file digest to match, re-reads the policy under the writer
  lock and requires its SHA-256 to equal the proposal's base, validates the
  candidate strictly, publishes it, adds the native entries and prints them.
- Writer lock: `.codeflow/.writer.lock`, a payload-free regular file that
  only orders the cooperating writers (`apply`, `render`, `init`, `update`),
  taken once at each command's public boundary and passed into the render
  step. The existing `lock_path_exclusive` and `atomic_write` helpers
  (`crates/codeflow-core/src/file_lock.rs:291-333`) are not reused
  unchanged.
- Publication: every policy or native file goes through one routine whose
  temporary lives in `.codeflow/.publish/`. The lock path and the
  publication directory are integrity paths (decision 8).
- Head-versus-head presence check and the `enforcement` floor family
  (decision 6), and `doctor enforcement-render`.

Windows: the lock and publication routine state their Windows behaviour or
refuse there (design section 10).

## Deliverables

- the commands: `crates/codeflow-cli/src/cmd/policy.rs` (`propose`, `apply`, `render`)
- the renderer, lock and publication routine: `crates/codeflow-core/src/scaffold/settings_merge.rs` and a new module beside `crates/codeflow-core/src/file_lock.rs` (provisional name)
- the integrity additions: `crates/codeflow-core/src/security/actions.json`, git-guard's integrity set in `crates/codeflow-core/src/hooks/git_guard.rs`, the managed block of `assets/base/gitignore`, the regenerated presets

- docs: `docs/policy-reference.md`, `docs/adoption.md`; release note: `changelog.d/TSK-321.md`

## Acceptance Criteria

- AC-1 A canary shall settle whether Codex loads more than one rules
  file, and rendering shall add to the generated file or the marked region
  accordingly; `init`, `update`, `apply` and `render` shall add every
  missing rendered entry and never remove, reorder or rewrite one in the
  Claude array, the Codex file or the region; a handwritten deny equal to a
  rendered one shall survive the removal of its declaration; evidence:
  the canary record and renderer tests. (serves EPC-023 AC-7)
- AC-2 `propose` shall enforce the name grammar and confinement and write
  the stated fields; `apply` shall refuse a wrong digest, a stale base, a
  path outside the folder and a candidate the strict validator rejects;
  of two proposals computed against one base, the second shall refuse once
  the first is installed; evidence: CLI tests. (serves EPC-023 AC-7)
- AC-3 The writer lock shall be acquired as specified: `lstat` refuses at
  once, without blocking, a symlink, FIFO, socket, device or directory;
  open with `O_CREAT | O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC`, never
  `O_TRUNC`, within a bounded time; `fstat` requires a regular file; the
  kernel lock is tried without blocking up to a bounded wait, then refuses;
  after locking, the path's device and inode must still be the locked one,
  else release and retry a bounded number of times; release never unlinks.
  The two protections are tested apart: an in-session unlink or recreate
  of the lock path is refused by the integrity guard (AC-5), and an entry
  replaced during acquisition is detected by the inode check, which makes
  the writer retry and never enter. The inode check is not claimed as
  protection against an outside process replacing the path after a writer
  is inside the critical section; that is the same-host residual. On
  Windows the routine uses exact equivalents of `O_NOFOLLOW`, the
  non-blocking lock and the identity check, or refuses with an explicit
  unsupported message; evidence: tests for a FIFO and a symlink at the
  path (no block), an entry replaced between open and lock (retry, never
  both inside), contention that times out and refuses, a child process
  that does not inherit the descriptor, and the Windows equivalent or
  refusal.
- AC-4 Every policy and native file shall be published through the one
  routine: an `O_CREAT | O_EXCL | O_NOFOLLOW | O_CLOEXEC` temporary in
  `.codeflow/.publish/` (created when absent, refused when not a directory
  owned by the current user), written, synced, read back and compared on
  its descriptor, then the temporary's identity and the destination's
  digest rechecked immediately before one rename. An absent destination
  (first `init`, or a newly generated rules file) is an explicit case: it
  must still be absent immediately before the rename, and a destination
  that appears or changes unexpectedly refuses. The rename is atomic on
  one filesystem; a cross-filesystem rename refuses, with no copy
  fallback; file modes and permissions are set as stated; a failure
  removes the temporary. On Windows the routine uses exact equivalents or
  refuses with an explicit unsupported message; evidence: tests where a
  temporary replaced at its path publishes nothing forged, an outside edit
  of the policy or a native file is refused with "edited concurrently; run
  `codeflow policy render` again", a render racing an `update` keeps a
  handwritten entry, an absent destination is published once and an
  unexpectedly appearing one refuses, a cross-filesystem case refuses,
  an error leaves no temporary behind, and the Windows equivalent or
  refusal. (serves EPC-023 AC-7)
- AC-5 `.codeflow/.writer.lock` and `.codeflow/.publish/**` shall be in
  `claude_edit_denies`, git-guard's integrity set and the managed
  `.gitignore` block, with the presets regenerated, and the publication
  directory itself and its ancestor rename paths shall be protected as
  well as its children, consistently for Claude, Codex and git-guard; the
  routine validates the directory's type and ownership without following
  an unintended symlink; evidence: guard tests that refuse an in-session
  write, unlink and rename of each, a rename of `.codeflow/.publish` and of
  `.codeflow`, and a symlinked publication directory refused by the
  routine. (serves EPC-023 AC-11)
- AC-6 `ci` shall render the head's policy and block, whatever
  `git.hook_integrity` says, when a rendered entry is missing from the
  head's native files or the shipped slice is not intact, and pass extra
  entries; an interrupted apply that leaves a newly required entry missing
  shall be named by `doctor` and blocked by `ci`, while a relaxation or an
  already-covered addition passes; evidence: CLI tests.
- AC-7 The `enforcement` family shall refuse at the floor, whatever any
  level says, `codeflow policy apply` and `policy render` after unwrapping,
  and the same words in a direct script operand of `sh`, `bash`, `zsh`,
  `dash`, `ksh`, `ash` or `pwsh` or in a file read by `source`, `.` or
  pwsh dot-source, tokenized one level; an unreadable or non-UTF-8 operand
  refuses; git-guard treats a match as a write of the policy and native
  files; the Claude preset gains `Bash(codeflow policy apply*)` and
  `Bash(codeflow policy render*)` in `deny`, with a canary that a deny beats
  `Bash(codeflow *)`, else the allow is split; evidence: guard tests and
  the canary. (serves EPC-023 AC-11)
- AC-8 `doctor enforcement-render` shall list each native entry's origin
  (`shipped: <family>`, `policy: security.project_actions[<id>]`,
  `preset: <name>`, `unexplained`), rendered entries the checkout lacks
  with the command to add them, allows that contradict a deny, the
  checkout-versus-landed render difference, and `full` or `partial` native
  coverage per project action by the rendering boundary above (a
  whole-program entry `full`, a verb or interleaved-option entry
  `partial`, no narrower entry widened); and in Claude, Codex and Grok sessions with
  the installed build a person's `apply` shall make each harness refuse the
  new command while an agent's `apply` is refused (journey); evidence:
  doctor tests and the harness canaries.
