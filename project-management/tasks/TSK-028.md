# TSK-028 — guide consumer-owned releases and qualify impact reasoning

## Description

Teach CodeFlow to discover and respect a consuming project's release authority,
offer an opt-in starter only when no compatible process exists, and test
evidence-linked impact reasoning. Keep repository publication separate from
deployment and never make CodeFlow's own scaffold/version metadata the
consumer application's version authority.

## Affected surfaces and interfaces

CAP-012; canonical release-method guidance and thin cf-ship/review/customize and
AGENTS/CLAUDE pointers; managed asset mirrors, baselines and manifest; semantic
model-evaluation requirements/cases/fixtures and their distribution contracts.
TSK-027 alone owns CodeFlow repository release workflows, preparer and history.

## Acceptance Criteria — Plan v2

- [x] Offer same-work-PR impact/notes/version preparation as a practical
      starting point, without imposing it on an existing project release policy
      or installing CodeFlow's repository-specific release helpers in consumers.
- [x] Entry points route to one canonical release reference; PR review assesses
      meaning, warranted coupled versions and current target state. Publication
      stays separate, with no implied automatic second PR or CI LLM judgment.
- [x] Behavioral fixtures cover repeated pending fixes, a feature followed by
      a stale fix, withdrawal, explicit publication and an existing external
      release authority. Native results and deterministic registration tests are
      distinguished; useful earlier cases remain intact with historical evidence.
- [x] Managed assets, mirrors, baselines and manifest agree after supported
      synchronization; repository-specific workflows/versions remain unowned.
- [x] Local distribution/evaluation gates and exact native source review pass
      before integration; final combined validation follows TSK-027 landing.
