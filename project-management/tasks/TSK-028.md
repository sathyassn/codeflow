# TSK-028 — guide consumer-owned releases and qualify impact reasoning

## Description

Teach CodeFlow to discover and respect a consuming project's release authority,
offer an opt-in starter only when no compatible process exists, and test
evidence-linked impact reasoning. Keep repository publication separate from
deployment and never make CodeFlow's own scaffold/version metadata the
consumer application's version authority.

## Affected surfaces and interfaces

CAP-012; canonical release-method guidance and thin cf-ship/review/customize and
AGENTS/CLAUDE pointers; managed asset mirrors, baselines and manifest; semantic
model-evaluation requirements/cases/fixtures and their distribution contracts.
TSK-027 alone owns CodeFlow repository release workflows, preparer and history.

- [ ] Canonical guidance records each project's version source, release units,
      impact/changelog policy, prerelease/backport rules, publication authority
      and verification command, reusing a compatible native process before
      offering an opt-in starter.
- [ ] Guidance explicitly preserves independent package groups, calendar or
      deployment identifiers and non-Cargo tooling; CodeFlow scaffold manifests
      never become consuming-product version authority.
- [ ] Repository publication and runtime deployment remain separate, and stable
      Agent OS consumption pins an exact released bundle/digest rather than
      silently following main or deploying to a personal runtime.
- [ ] Managed canonical assets, thin entry pointers, mirrors, baselines and
      manifest hashes are synchronized once, without duplicating a release
      ledger or introducing package orchestration.
- [ ] Positive and adversarial evaluation cases cover misleading commit types,
      breaking managed defaults, harmless internal changes, doctrine guarantee
      reversal, existing release tools, new single-product repositories and
      independent monorepo version domains.
- [ ] Evaluation rubrics require evidence-linked classification and respect the
      project's authority, distinguish syntax checks from semantic judgment,
      and make no universal model-accuracy, qualification or publication claim.
- [ ] Focused doctrine, manifest, artifact-budget and evaluation-contract tests
      plus independent native review pass before integration; exact runtime
      trials and limitations are retained honestly.

## Execution contract

Plan v1 is grounded in the independently settled release-management proposal;
the exact records still require Codex-primary and native-Claude review before
landing. The root Codex host is responsible primary and owns this task's
shipped assets, source skills, mirrors/baselines, manifest and evaluations;
native Fable independently reviews the exact unit. Target:
`integration/EPC-010-release-automation`. This root node is independent of
TSK-027; any shared manifest synchronization is serialized at integration.
Changes that impose a consumer version topology, automate deployment, add a
second release ledger or alter the graph/authority boundary require Plan v2.

Verification uses finite semantic cases and distribution/contract checks; no
new property or mutation framework is selected. Native cases measure only the
declared fixtures and cannot promote a route or prove all future release-impact
decisions.
