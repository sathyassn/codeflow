# TSK-339: Completed work keeps its verified origin when lines merge

## Description

Issues: #181, #197 and #218. These share loss of the completion's home authority during import. They have distinct manifestations which need one composed regression set.

- `workgraph/acceptance.rs:2992` adds own-line stacking authority only when the task target matches the currently judged line (`:3004`). That explains #197 and #181's target-history form.
- `acceptance.rs:2940` assigns a task range all its changes. Its `origin` becomes the range head at `:2953` unless the amendable-line path applies. `task_landing` at `:1058` and the refusal at `:1152` can therefore treat a sync merge as the landing of imported main completions and blame later product work on them. This covers #181's 2026-10-17 comment as well as its earlier differing-shared-file comment.
- `recovered_completion` at `:1427` handles `Landed::Unjudged` at `:1475` by retaining earlier criteria. This explains #218 after a valid pre-landing reopen on the task's home.
- TSK-275 explicitly excludes attribution after a merge (`project-management/tasks/TSK-275.md:31`). Its AC-5 (`:72`) overlaps the simple sync case, but PR 206 at `1b2c9664e` still has the core routines and decisions above unchanged. TSK-306 settles inherited held-version conflict (`TSK-306.md:36`); it does not authorize a previously unjudged home. TSK-308 AC-1 covers a landed direct adoption (`TSK-308.md:52`). TSK-318 explicitly excludes merges (`TSK-318.md:53`) and its AC-1 rejects them (`:67`). None closes this group as written.

Folded in by the amendment of 2026-10-18: issue #240. A task branch on an integration line merges the protected target twice (the task must land with that merge). `codeflow ci` over the task's range then reports 42 blocks, none naming the task: 29 `work.acceptance_binding` blocks attribute a later target commit (one that edits `.codeflow/policy.json`) to every target task whose completion arrived with the first merge; 7 blame files that differ between line and target; 5 `work.criteria_frozen` blocks report the target's own criteria changes as the branch's; 2 concern a task the target reopened. Any non-merge commit on the branch that edits a file a target task's reviewed commit touched is refused as "changes <file> after the landing merge", even an unrelated runbook (34 more blocks). With a PR body, `work.classification` adds "a task PR may add only its own standalone task record" for records that arrived from the target. The pre-push hook gives the same blocks with different wording. Same family as #181: the importing range is judged as if it landed the imported completions.

Outcome: **A completion imported unchanged from its proven home is judged at its accepted home landing, while changes introduced by the receiving line remain accountable to that line.**

Source inspection is from the accepted triage at `c5c6f6f671d2bf67a77113c656b3be446fb0bea1`; runtime reproductions remain implementation evidence.

## Acceptance Criteria

- AC-1 Main -> integration, integration A -> B and task branches carrying those syncs preserve valid source completions, including a task that merged its home after review and one that reopened before its first landing.
- AC-2 The #181 fixtures include a receiving line's already-reviewed differing shared file and product commits following the task branch's sync. No imported task is told to reopen for the receiver's work.
- AC-3 #218 retains the criteria actually accepted on the home, with ref-name and SHA range spellings giving the same result. Source equality alone is insufficient: verify source identity, target relationship, ancestry and landing through the guarded reader.
- AC-4 A forged home, changed record/acceptance, unreviewed merge resolution, unavailable home, competing criteria introduction or overlaid history still refuses. A receiving line's new unreviewed product change is never hidden by source attribution.
- AC-5 (journey) The full CLI/pre-push matrix imports valid source work and then lands receiving-line work without waivers, while the negative controls stay blocked.
- AC-6 For the #240 shape (a task range that merges the protected target twice, with a later target commit that edits `.codeflow/policy.json` and a task commit that edits a file earlier target tasks touched), `codeflow ci` with and without `--branch <line>`, with a PR body, and pre-push shall report no block for a task or epic whose completion is reachable from the protected target ref; later target commits shall not be attributed to earlier target completions. Evidence: the issue's reproduction as a CLI fixture, failing before the change.
- AC-7 Criteria changes, reopenings and task records that arrive from the protected target by merge shall not be reported as the branch's own criteria changes or as records the task PR adds, and when a range cannot be judged this way the output shall say the blocks come from the target's history and name the sanctioned route. Evidence: fixtures per case, including the PR-body classification block.
