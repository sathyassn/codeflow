# TSK-1109: The display scale is a root scale and nothing renders under the floor

## Description

The operator said on 2026-10-31 11:10 that `cf-present` and `cf-docs-portal`
pages are hard to read and have no aesthetics, and asked for both to reach
the standard of a well-designed website (type, palette, spacing, hierarchy,
charts, chips), with the artifact-design guidance as reference and the 4.0.0
status report page as the reference look (queue item 36). The design audit
of 2026-10-31 (Source, below) found the first cause: Size is a token multiplier on a fixed 16px root
(`styles.css:50-58`, `:113-115`, `:344`). Compact 0.94, Default 1 and Large
1.12 scale only the `--cf-fs-*` tokens, so every rem or px an author writes
in an html stage ignores the setting; the status report's stages stayed at
11.5 to 13px at every Size (10 rules at 0.82rem, 9 at 0.78rem, 7 at 0.72rem,
4 at 12px in `export-light.html`), and the runtime's own kickers sit at
0.7rem (`styles.css:421`, `:436`, `:449`, `:479`), under its declared 12.5px
floor (`:58`). `document-authoring.md` gives authors no type guidance.

This task makes the root the scale: `html { font-size }` per Size step
(Compact 15px, Default 17px, Large 19px), every runtime token in rem, the
stage host inheriting the `ui` size, nothing under the floor, and the type
scale the audit sets (display 2.35rem, section 1.65, subsection 1.25, lede
1.18, body 1, ui 0.88, caption 0.82, micro 0.76; labels that name structure
leave mono for the body face). The Display panel gains a Headings choice
(body face or a bundled display face) and a live preview that shows a figure
label and a stage line, so Size is seen to scale them. It is first in the
redesign because every later mockup and screenshot depends on it. Non-goal:
palette (TSK-1110), frame chrome (TSK-1111), stage at-rules (TSK-1112).

## Outcome

After this merges, a reader who sets Size in cf-present sees every line on the page scale, stage content included, and nothing on the page renders under the readable floor.

### Browser behavior and comparable systems

- [CSS Values and Units, font-relative lengths](https://www.w3.org/TR/css-values-4/#font-relative-lengths)
  defines rem relative to the root. A rem on the root itself uses the initial
  font metrics. Prefer root percentages 93.75%, 106.25% and 118.75% to obtain
  15px, 17px and 19px at the conventional baseline while retaining the
  browser's user-selected default size. Literal px roots override that
  default. Page zoom still scales CSS pixels. Browser minimum-font-size
  settings need a real browser check; they are not equivalent to page zoom.
- [WCAG resize text](https://w3c.github.io/wcag/understanding/resize-text.html)
  requires text enlargement without lost content or functionality. It does
  not prescribe this task's chosen numerical floor. Inspect wrapping,
  popover scrolling, comment rail and controls at enlarged sizes.
- [GOV.UK type scale](https://design-system.service.gov.uk/styles/type-scale/)
  uses relative output units, with 19px body and 16px small-body equivalents.
  Its small-screen body also stays at 19px. This supports retaining readable
  roles on phones rather than restoring fixed 12px overrides.
- [Carbon type sets](https://www.carbondesignsystem.com/building-blocks/foundations/typography/type-sets)
  distinguishes productive and expressive typography, with 14px and 16px
  bases. Its supporting styles are separate from body styles. These are
  useful comparisons, not a replacement for this task's approved scale.
- [Bricolage metadata](https://raw.githubusercontent.com/google/fonts/main/ofl/bricolagegrotesque/METADATA.pb)
  declares a variable weight range of 200 to 800 and optical sizes 12 to 96.
  Bundle only the needed face data and measure the binary delta. The
  [font license](https://raw.githubusercontent.com/google/fonts/main/ofl/bricolagegrotesque/OFL.txt)
  is OFL 1.1. Carry its full notice with the asset and in the existing offline
  license footer. Current bundling and disclosure are in
  `crates/codeflow-present/web/src/fonts.ts:1` and `:31`.
