# TSK-1385: The read benchmark tells a load-skewed latency miss from a regression

## Description

The read benchmark (`crates/codeflow-cli/tests/read_benchmark.rs`, `read_commands_on_ten_thousand_records_stay_within_their_budgets`, assertion at `:562`) holds each read command to a latency ratio: the command's wall time over one calibration of short git reads on the same 10,000-record fixture, at most twice the baseline ratio (`over_budget`, `:697-701`). The calibration runs once, before any command (`:516`), and is a few short processes, while each command runs for tens of seconds. Under host load the two scale differently, so the ratio drifts with no code change. On EPC-022 candidate `addc0cd01` the `validate --docs` ratio was 14.33 in the full gate and 13.37 in a probe (load about 18), against a 12.76 budget; at line tip `c35cf003f` it was 15.43 (load 21 to 23); a targeted run on the same candidate passed at 20:35 (load about 20, falling). The fixture is generated and identical on both sides, so the miss came from host load. A full gate went red with no code cause.

This task makes the benchmark tell a load-skewed miss from a regression, so a red latency result means the command got slower. It keeps the two-times budget and the check itself: the budget is not widened, the check is not skipped or made advisory, and when the benchmark cannot tell, it fails.

Sibling note, checked 2026-11-08: TSK-1357 covers this benchmark's memory budget, not latency; TSK-1013, TSK-184 and TSK-110 are complete; TSK-361 covers tests that report a pass for a scenario they did not run. None covers latency under load.

Non-goals: the memory and git-process budgets (TSK-1357 owns memory); the commands' own speed; the baselines' recorded values, except where AC-3 needs a recorded field.

## Outcome

After this merges, the primary landing a candidate can treat a red read-benchmark latency result as a slower command, and a busy host no longer turns a full gate red by itself.

## Acceptance Criteria

- AC-1 When a command's latency ratio is over budget, the benchmark shall measure again before failing: a fresh calibration taken next to a fresh run of that command, compared with the same two-times budget. A command over budget on the remeasure fails; one within it passes, and the report keeps both measurements. Evidence: fixture tests over the decision function with a skewed first measurement and a clean remeasure (pass), and a slow command on both (fail), each failing before the change where it applies.
- AC-2 The calibration shall bracket the commands, not only precede them: it is taken before and after the measured commands, or next to each one, so a load change during the run shows in the calibration the ratio uses. The ratio's denominator is the faster of the bracketing calibrations, or the calibration taken next to that command; no choice of denominator may make a ratio smaller than that rule gives. Evidence: the measurement code, a fixture test where a slower second calibration would pull a slowed command under budget and the rule keeps it over, and the run report naming the calibration used for each command.
- AC-3 When the benchmark cannot tell load from a regression, it shall fail with a message that says so and names the measurements, never pass. This covers at least: the bracketing calibrations differ by more than a stated spread, or a remeasure is itself skewed by that rule. The spread and its reason are stated in the module docs. Evidence: fixture tests for each case, each failing closed.
- AC-4 The two-times latency budget, the memory budget and the git-process budget shall be unchanged, and the check shall still run in every gate that runs it today. Evidence: `over_budget` budgets unchanged in the diff, `the_budget_check_flags_a_run_over_its_baseline` still passing, a fixture where a command 2.5 times its baseline on both measurements still fails, and the diff leaving the ignored benchmark in the gate that runs it today (`scripts/journey-gate.py`, named in the module header).
- AC-5 (journey) The release benchmark shall pass on a loaded host where today's version fails on load alone, and shall still fail on a real slowdown. Evidence: one session on one macOS host through `coordination/scripts/nice10.sh`, the ignored benchmark run at this task's base and then at its head, with the load average recorded for each. The criterion is met only when that session's base fails on latency and that session's head passes; an earlier red gate does not count, and a session whose base passes does not meet it. Also the head run with one command slowed on purpose (a test-only delay) failing, its log kept with the pull request, which states that the delay is absent from the reviewed commit; AC-4's 2.5 times fixture stays the durable failing case.
