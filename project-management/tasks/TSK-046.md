# TSK-046: compose decisions, records and landings from the doc graph

## Description

Cancelled on 2026-09-20 by Plan v7: the portal explains the project as it
stands and points to records as folders, so composed record views are not
built. The defect fixes and the layer figure from its branch move to TSK-051.

The decisions landing, the records landing, the epic, task and ADR pages and
the layer landings are re-rendered Markdown under the portal shell, which is
exactly what the shared doctrine says must fail: the portal is presenting a
copy of the source instead of composing it. This task makes the adapter derive
each of those views from frontmatter and the doc graph it already builds, under
the data contract and the altitude grammar pinned in SPC-010, so meaning sits
in geometry, time, edges and node state and text is labels. Every composed page
uses the same Concept, Architecture and Technical tablist the adapter already
emits, so the reader navigates one way everywhere. Non-goals: no second ADR map
is emitted, since the area oriented map stays in TSK-039's `architecture.md`;
the Rust workgraph is not imported; the ADR body text is not rewritten or
reinterpreted onto the altitude headings; and no new ADR is written, because
ADR-0048 and ADR-0058 already cover adapter-derived views in the managed
starter and ADR-0053 stays untouched.

## Affected surfaces and interfaces

`docs-portal/scripts/adapter.mjs` and its starter mirror under
`assets/docs-portal/starter`. The new test file
`docs-portal/tests/composed-views.test.mjs` and nothing else under
`docs-portal/tests`. `docs-portal/src/styles/portal.css` and its starter
mirror. The page-class and visual-craft landing sentences in the
cf-docs-portal doctrine and its resources. The carrier table in
`docs/architecture/utility-presentation.md`, which gains adapter-generated
figures as a supported carrier once they ship. CAP-015. The extract helpers
stay inside `adapter.mjs`. This task does not edit
`docs-portal/scripts/browser-verify.mjs`, the token sheets, or any file owned
by TSK-045.

## Acceptance Criteria

- [ ] The decisions landing shall compose the trio: a Concept timeline of
      decisions with supersession edges, an Architecture view grouping
      decisions by status with their supersession chains and impact edges, and
      a Technical sortable table of id, title, date, status, superseded by and
      impact with links; evidence: the ADR fixture with a supersession renders
      all three panels and the tablist, asserted in
      `docs-portal/tests/composed-views.test.mjs`.
- [ ] The records landing and each epic page shall compose the trio: a Concept
      task dependency graph with status carried in node style, an Architecture
      view of the same graph expanded per task with its in edges, out edges and
      integration target, and Technical criteria and evidence tables; evidence:
      the epic and tasks board fixture asserts all three panels.
- [ ] When a dependency graph exceeds six stages or five nodes per stage, the
      view shall render the table fallback with identical rows and state which
      form it is showing; evidence: the EPC-014 fixture, which exceeds both
      limits, renders the table, and a trimmed fixture renders the graph.
- [ ] A task page shall open with its own node and edges at Concept, its
      execution contract as a small flow of responsible primary, executor and
      reviewer at Architecture, and its criteria checklist table with closeout
      evidence at Technical; evidence: the task fixture asserts the three
      panels and the checklist rows against the source checkboxes.
- [ ] An ADR page shall open with derived header panels holding the first
      sentences of Context, Decision and Consequences at Concept, the
      supersession and impact edges as a small figure at Architecture, and the
      unchanged append-only text at Technical; evidence: the ADR fixture
      asserts the panels and a byte comparison of the rendered body against the
      source body.
- [ ] Each layer landing and the home page shall carry the layer description
      and its reading-order figure at Concept, the pages of the layer as a
      structure with counts at Architecture, and the searchable index at
      Technical; home stays the four-layer stage and adds a start-here section
      only by restaging the existing layer descriptions; evidence: the layer
      fixture asserts the three panels, and a home assertion shows the
      start-here text equals the declared layer descriptions.
- [ ] The capabilities registry table shall be generated from the
      `capabilities` YAML fences and from `docs/capabilities/CAP-*.md`;
      evidence: two fixtures, one per source form, produce the same table, and
      TSK-039's hand written table is the recorded fallback until this lands.
- [ ] Every rendered field shall be frontmatter or one of the two named
      extracts, neutralized before rendering; evidence: a test that injects
      markup into a first sentence and a criterion and asserts it is escaped,
      plus a field-provenance assertion over the fixture set.
- [ ] Markdown twins shall remain the rendered page with the source body
      preserved and no new claims, and `llms.txt` shall list only non-stale
      source routes; evidence: the twin comparison test and the `llms.txt`
      assertion over a fixture set containing one stale source.
- [ ] Stale behaviour shall follow `content-contract.md` unchanged, so a stale
      record contributes no node, no edge and no table row while its siblings
      continue; evidence: the stale fixture asserts the error stub, the cleared
      ids and relationships, and the exclusions.
- [ ] The evidence schema shall stay at version 1 with no new field; evidence:
      the schema test passes unchanged.
- [ ] `npm run browser:verify` shall pass for home, the four landings and one
      page of each record class, and `codeflow validate --portal` shall pass;
      evidence: recorded output with the exact head SHA.
- [ ] The starter mirror of the adapter shall be byte-identical to the live
      copy; evidence: the mirror equality check passes and fails when one copy
      is perturbed.
- [ ] A record page shipped as raw Markdown under the portal shell shall fail
      and be named; evidence: the negative fixture fails the TSK-042 gate with
      the offending source named.
- [ ] The shared doctrine page-class table and the visual-craft landing
      sentences shall state that these record and decision classes are composed
      rather than exempt, and `docs/architecture/utility-presentation.md` shall
      list adapter-generated figures as a supported carrier; evidence:
      `codeflow validate --docs` passes and the rendered review of both pages
      confirms the new rows.
- [ ] Fable's rendered review checks each view at each altitude against the
      question SPC-010 states for it, not against richness; a figure that
      renders well but does not answer its stated question fails; evidence: the
      review record lists every view and altitude with its question and a pass
      or fail verdict.
- [ ] Rendered defect 1, stage flow width: a five-node stage at 1280 pixels
      shall keep each node at or above its minimum width and wrap label text at
      word boundaries rather than breaking a token; evidence: rendered review of
      a five-node stage at 1280 and 390, plus a style assertion that the node
      rule carries a minimum width and word-level wrapping.
- [ ] Rendered defect 2, heading anchors: heading ids and the "On this page"
      list shall exclude the provenance line; evidence: a test asserting the
      generated ids for a page that carries a provenance line, and the same
      page's "On this page" entries matching its real headings.
- [ ] Rendered defect 3, capabilities registry width: the generated
      capabilities table shall read without horizontal cramping at 1280 by
      moving the epic and ADR columns into the row detail; evidence: rendered
      review at 1280 and 390, plus a test asserting the generated table emits
      five columns with epic and ADR in the detail.
- [ ] Rendered defect 4, layer landing order: landing order shall follow the
      layer configuration rather than the sorted source scan, so a configured
      first page is first; evidence: a fixture whose configured first page
      sorts last renders first, and the assertion fails when the sort is
      restored.
