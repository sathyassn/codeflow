# TSK-340: Status changes and repeated closeout have one valid acceptance sequence

## Description

Issues: #198 and #217. Both arise from a mismatch between the record lifecycle the CLI produces and the completion content/span that binding accepts. They require different repairs inside that shared contract.

- #198: `acceptance.rs:208` excludes only frontmatter status and Closeout; `:219` retains Blocker. `later_change` compares that projection at `:1388`. The status writer adds/removes Blocker at `workgraph/status_verb.rs:533` and `:544`.
- #217: `workgraph/lifecycle.rs:1084` requires the last superseded block to match the particular before-record's active block. Different CLI/range bases therefore impose different last-block requirements. `acceptance.rs:502` explicitly disallows normal stacking for a reopening range and forces direct transport at `:544`. `later_change` refuses every other changed path at `:1380`, including a later epic record.
- TSK-278's ACs concern a redaction-only change preserving results (`TSK-278.md:42`), not new acceptance after a reopen. Proposal F may remove the unnecessary rebinding trigger for imported changes, but the normal repeated-reopen and blocked-status sequence still needs proof.

Outcome: **A task can become blocked, complete, reopen and complete again, followed by epic Closeout, using ordinary commands that local and range validation both accept.**

Source inspection is from the accepted triage at `c5c6f6f671d2bf67a77113c656b3be446fb0bea1`; runtime reproductions remain implementation evidence.
