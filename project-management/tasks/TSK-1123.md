# TSK-1123: A completion that reaches a task range unchanged through a merge is not bound at the range head

## Description

Source: issue #455 (CodeFlow 3.1.1, `48104f48b`, by an adopter), read
on the line tip `79eec1783` after a diagnosis found no open task that
covers it. TSK-1083 binds a landed task's own completion and TSK-1066
judges a sync; neither changes which commit a foreign completion is
bound at in a task range.

A task branch can merge in another integration line that carries a
completed task X. `codeflow ci` then binds X's completion at the task
range's head and refuses every non-merge, non-planning commit on the
head's first-parent chain after the merge that brought X in. Those
commits belong to the task under review, not to X, so any line that
takes another line and then builds on it gets a `work.acceptance_binding`
block against a task nobody changed. No waiver clears it (a waiver is
checked for validity only), no planning amendment clears it, and
rebuilding the branch moves the block to another commit. The only route
the message offers is to reopen X and complete it again at the new head,
which attributes the later unit's work to a task that did not do it.

Sites, read on the line tip (the issue cites `48104f48b` lines; the
code has moved):

- `crates/codeflow-core/src/workgraph/acceptance.rs:3857`
  `completions_in_range`. For a range that cannot be amended (a task
  range), `origin` is `head_oid` at `:3956-3961` for any completion that
  is new against the anchor, including one that arrives unchanged
  through a merge. A planning or line range binds at `introduced`
  (`introduced_at`, `:3945-3954`).
- `acceptance.rs:1594` `task_landing` walks the first-parent chain from
  that origin back to the merge that brought the reviewed commit and
  records the first non-merge commit with a non-planning change
  (`after_merge`, `:1632-1697`). It refuses that commit at `:1753`
  ("only merges, planning records and landed line adoptions may follow
  it").

The issue's reproduction, in a pnpm/Nx monorepo: line A holds task X
(complete, reviewed commit R, landing merge on A); line B's tip is a
commit; task Y's branch on B merges A's tip, adds 13 of its own product
commits and records. `codeflow ci --base <B tip> --head <Y head>
--branch task/Y --into integration/B` blocks X at Y's first product
commit. The same tree rebuilt as one merge with A as second parent
blocks X on a record file; with A as first parent it blocks X on A's own
later commits; with `main` merged into B first (ci run with `--base` at
that merge) it blocks X on a `main` commit.

Design (Fable reviews it before the build): a completion that reaches
the range through a merge, with its record unchanged since the merge
parent that holds it, belongs to the line it came from. In a task range
it binds where it was introduced, as a planning or line range already
does, and is judged there:

- `introduced_at` (`:4228-4259`) walks back through the first parent and
  then the second while the parent holds the same complete record and
  block, so line A may be either parent of the bringing merge. The
  shape with A as first parent is in scope; it is refused today because
  `stacked` stops when the reviewed commit is not on the first parent
  (`:1519-1522`), and a head merge that changes non-planning paths is
  refused as the completing commit (`:1680-1684`).
- The completion is bound at that point by the binding the range
  already runs (`bind_completion_with_amendment`, `:3969-3987`), as its
  own line binds it. It is never skipped unjudged: a record whose bytes
  match the bringing parent but whose block would not bind on that
  parent is still refused (AC-4).
- Commits after the bringing merge on the task's chain belong to the
  task under review and are judged against its own record, not X's.

What still binds at the head and is refused as today:

- a record or acceptance block of X that the merge, or any later commit
  of the range, changes against the parent that holds X's completion;
- a completion the range itself adds, changes or reopens.

A squashed shape (one merge whose tree also holds the task branch's own
product changes) is not a change to X when X's record is byte for byte
the copy on the parent that holds it; the merge's other changes are the
task's own work under review, judged by the task's own binding and
review, and raise no finding for X. Rejected: skipping a completion
whose record equals the second parent's copy, because it accepts bytes
without judging them and misses the first-parent shape.

This binds trust: the choice decides which completions a task range
accepts without re-binding at its head.

Two completions in one range (the reporter's comment of 2026-10-31,
https://github.com/sathyassn/codeflow/issues/455#issuecomment-6550610794).
The route the refusal offers, reopening X on Y's branch and completing it
again at Y's head, cannot pass when Y also completes in that range.
`reviewed_span_problem` (`acceptance.rs:1366`; the comment cites
`:816-821` at `48104f48b`) lets only the task's own record change after
its reviewed commit (SPC-013 R-60), so X's completion refuses Y's record
and Y's refuses X's, in any order or commit split. The reporter's
workaround is a second, records-only landing for X whose reviewed commit
is Y's completion commit.

Decision on the reporter's fallback (allow any planning path after the
reviewed commit, as after a landing merge): rejected as stated, taken in
a narrow form, in this task's scope because the route this task's
refusal prints must be passable.

- Threat the broad form opens: a commit after the review could change
  another task's criteria or body, an epic, a spec or a decision record,
  and the completion would still bind, so a reviewed verdict would cover
  planning content no reviewer saw. Other rules judge some of those
  changes, but the binding would stop naming them.
- Narrow form: after T's reviewed commit, another task U's record may
  change only when the change is U's status and Closeout (U's
  `reviewed_part`, `acceptance.rs:245`, is unchanged) and U's completion
  is itself made in this range and binds by its own rules, its own
  reviewed commit and review included. Any other change after the
  reviewed commit (U's criteria or body, a status step with no bound
  completion, an epic or spec) stays refused.
- Why the narrow form is safe: nothing reaches a verdict unreviewed. U's
  status and Closeout are the part R-60 already lets a completion write
  after its review, and U's own binding judges them; the reviewed
  content of every record is unchanged.

Non-goals: the sync-merge check (TSK-1066), the landed-task binding
(TSK-1083), a waiver that suppresses `binding_problem`.

## Outcome

After this merges, a maintainer whose task branch takes another integration line's tip and then builds on it passes `codeflow ci` without reopening a task that line completed, and a completion the range itself changes is still bound and refused as before.

(serves EPC-022 AC-197)
- AC-3 The same history rebuilt as the issue's other shapes shall also raise no finding for X: one squashed merge with the same tree as Y's head and parents (B tip, A tip), whose X record is byte for byte A's copy; the same tree with A as the first parent; and `main` merged into B first with ci run with `--base` at that merge; evidence: one fixture per shape, each blocking before and passing after. (serves EPC-022 AC-197)
- AC-4 A foreign completion shall still be refused, naming X, when: the merge that brought it, or a later commit of the range, changes X's record or acceptance block against the parent that holds X's completion (one fixture with A as second parent and one with A as first); or X's record is byte for byte the bringing parent's copy but its block would not bind on that parent (its reviewed commit is not on A, or a non-planning commit follows its landing merge on A); evidence: one negative fixture per case, refused before and after.
- AC-5 A completion the range itself adds, changes or reopens (a task completing its own record, or reopening and recompleting X in the range) shall bind at the head as today, and its later non-planning commits shall still be refused; evidence: the existing task-landing tests plus a fixture of each, passing before and after.
- AC-6 (journey) With the built binary in a scratch repository holding two integration lines, the AC-2 range, the AC-3 first-parent shape and the AC-7 two-completion range shall pass through `codeflow ci`, and the AC-4 hand-edited merge shall block naming X and the merge; evidence: the journey output.
- AC-7 Given the reporter's reproduction in the comment cited above (Y's branch on line B with Y's product commits, a merge of `main`-into-B, X reopened, then X and Y both completed in the range, in one commit or two, with each reviewed commit set to either completion head), `codeflow ci --base <the main-into-B merge> --head <Y head> --branch task/Y --into <B>` shall raise no `work.acceptance_binding` finding for X or Y; and after Y's reviewed commit, another task's record changed outside its status and Closeout, a status change with no completion bound in the range, another completion whose own binding fails, a third task whose status and Closeout change while X and Y both bind, and an epic or spec change shall each still be refused; evidence: a fixture of the reproduction, blocking before the change with the line's "1 path changed between the reviewed commit … and …, first: …" finding (`acceptance.rs:2044-2046`) for each, X's naming Y's record and Y's naming X's (the issue comment quotes the 3.1.1 wording), and passing after, and one negative fixture per refused case, refused before and after. (serves EPC-022 AC-197)
