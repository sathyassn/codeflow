# TSK-1013: An opt-in time-box profile compares each task with its frozen band

## Description

Issue #334, items A, C, E, G and H. An adopter runs an estimation method
from a feature specification to delivered tasks: a feature estimate (an
expected task mix and a budget envelope, never a date) and a task
estimate (a class, a driver grade and a time band whose top is a stop
rule), compared at epic close. CodeFlow supplies the rubric, grades,
outcome clock, blocked spans and three-scenario forecast; the adopter
asks for an **optional, opt-in** profile that compares each task with its
frozen band, and for the templates to carry its fields. The adopter runs
it locally today, so this is a 4.1.0 feature.

Outcome: **a project that turns on a versioned time-box profile gets
each task compared with the band and profile revision frozen at its
breakdown (hits, misses, breaches), grouped by the project's declared
class beside `work_type`, with the template fields and their warnings;
a project that does not turn it on sees no change, and nothing in the
profile is a gate or a forecast.**

Rules:

- **A, the profile.** A versioned file in the estimate root holds the
  grade-to-band map, band tops, the split rule and the hit rule.
  `outcomes` reports hits, misses and breaches apart from forecasts.
  Tasks created before the profile's effective date are reported as "no
  band", never back-filled.
- **C, the clock's end.** A review-approved event bound to the reviewed
  SHA ends the clock only when it binds the final reviewed SHA; the end
  is the later of that approval and the completion of verification; a
  later in-scope commit falls back to the completion. A deferred result
  (TSK-436) is reported outstanding against the task and links its
  later result. The PR settles whether the event reuses the structured
  evidence of TSK-1008 (EPC-024) or the ledger, with the reason.
- **E, class grouping.** Outcomes group by the project-declared `class`
  of TSK-313, added beside the `work_type` grouping, not instead of it.
- **G, templates.** Under the profile only: `class:` and an Estimate
  block in the task template, the specification pin, value line and
  Estimate section in the epic template, the epic-close outcome step in
  `cf-ship` before a line is deleted, and `validate --docs` checks of
  band names and block shape, as warnings, never failures; breaches are
  reported apart from structural warnings and never block delivery.
- **H, references.** `cf-estimate` describes the profile beside the
  three-scenario forecast: how a feature mix becomes forecast
  activities, and why band tops are not forecasts.
- **Consistency first.** Before building, the PR states how the design
  relates to issues #164 (class), #166 (program view), #168 (scope
  drift), #280 (short epics), #287 (deferred proof), #301 and #302
  (structured evidence), and to `operating-model.md` (assumed bands are
  not defaults), `records.md` (forecast validity) and the
  orientation-only criteria counts of the workflow rules, as the issue
  asks.

Non-goals: any default band set; a band-only forecast; the measurement
fixes (TSK-1012).

## Deliverables

- the profile reader and the band comparison: `crates/codeflow-core/src/estimate/` (`outcomes/`, a provisional `profile.rs`)

- references: `cf-estimate` `references/operating-model.md` and `records.md` (mirrored)
- tests: `crates/codeflow-cli/tests/estimate_outcomes_cli.rs`, validation tests
- release note: `changelog.d/TSK-1013.md`

## Acceptance Criteria

- AC-1 With no profile, `estimate outcomes`, the templates and `validate --docs` shall behave as before this task; evidence: the existing tests passing and a fixture with no profile. (serves EPC-023 AC-33)
- AC-2 With a profile on, `outcomes` shall compare each task with the band and profile revision frozen at its breakdown and report hits, misses and breaches separately from forecasts, with pre-profile tasks as "no band" and re-planned or split tasks keeping their original band and breach; evidence: a fixture with a profile change between two tasks. (serves EPC-023 AC-33)
- AC-3 A review-approved event bound to the final reviewed SHA shall end the clock at the later of approval and verification completion, and a later in-scope commit shall fall back to the completion; a deferred result shall show as outstanding; evidence: fixtures for each case.
- AC-4 Outcomes shall group by declared `class` beside `work_type`, and a task with no class shall stay valid; evidence: a fixture with mixed classes.
- AC-5 Under the profile, a missing or malformed Estimate block or class shall give a warning in `validate --docs`, never a failure, and a breach shall be reported, never block a push or `codeflow ci`; evidence: validation and CI tests.
- AC-6 The PR shall carry the consistency statement against #164, #166, #168, #280, #287, #301, #302 and the `cf-estimate` references, and `cf-estimate` shall describe the profile beside the forecast; evidence: the PR body and the reference diff.
- AC-7 (journey) With the installed build in a scratch adopter with the profile on, one task finished under its band top and one over shall be reported as a hit and a breach, and turning the profile off shall remove both lines; evidence: the journey output.
