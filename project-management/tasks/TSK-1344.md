# TSK-1344: Guards judge commands run through the Herdr app the same as bare commands

## Description

Source: the research for moving seats to the new Herdr app, finding S1, with the scope widened by the Director on 2026-11-05. It ranks with TSK-1343 at the top of the guards order. It is separate from TSK-1345 so that a gap open today does not wait on that migration.

Guards judged these strings on installed CodeFlow 3.1.0 on 2026-11-05; nothing ran:

| Command | exec-guard | git-guard |
|---|---|---|
| `claude -p hello` | blocked | passed |
| `hc run -- claude -p hello` | **passed** | passed |
| `hc run -- codex exec hello` | **passed** | passed |
| `herdr pane run w1:p1 'claude -p hello'` | **passed** | passed |
| `git push --force origin main` | passed | blocked |
| `hc run -- git push --force origin main` | passed | **passed** |

The gap reaches past peers and git, and it is uneven, so fixing one reader does not fix the rest:

| Command | exec-guard | git-guard |
|---|---|---|
| `rm -rf /` | blocked | blocked |
| `hc run -- rm -rf /` | **passed** | **passed** |
| `sudo rm -rf /var` | blocked | passed |
| `hc run -- sudo rm -rf /var` | **passed** | passed |
| `hc run -- rm -rf ~` | blocked | passed |
| `git branch -D main` | passed | blocked |
| `hc run -- git branch -D main` | passed | **passed** |

`hc run --cwd <path> -- git ...` also changes which repository the git command targets, and git-guard judges by target repository.

`crates/codeflow-core/src/security/headless.rs:154` returns `Found::Nothing` for a program it does not know. `hc` is not in `COMMAND_CARRIERS` (`crates/codeflow-core/src/hooks/git_guard.rs:14131`). A sandboxed Bash call cannot reach the `hc` socket, so this route needs an unsandboxed retry first.

Untested forms the manual lists, which AC-1 tests first:

- `hc exec [--on m] <argv>`: runs a program directly, with no terminal.
- `hc file write|edit`: changes files from the core, outside the Bash sandbox and the Edit rules.
- `hc send` and `hc keys` to a plain shell terminal: run whatever is typed.
- `hc run --bg <template>`: the command lives in a template file.

The floor under the guard is weaker than the first report said:

- The pre-push hook should stop a wrapped force push to a protected branch, but that was not run. `--no-verify` skips that hook, and git-guard does not refuse `--no-verify` even bare (issue #619). Judged as payloads on beta 4.0.0 (source 678d3fa48) on 2026-11-05, nothing run: `commit --no-verify`, `commit -n` and `merge --no-verify` pass both guards; `push --no-verify` passes git-guard and is refused by exec-guard only under `security.outward_actions`; `-c core.hooksPath=/dev/null` is refused under `git.hook_integrity`. So a wrapped `git push --no-verify` is reasoned to pass both guards once the wrapper hides it from exec-guard. Not run. TSK-1349, filed by PR 625, closes the bare-flag gap; this task's AC-7 still records what stops the wrapped push.

Corrected 2026-11-05 by the records follow-up after PR 617: the bullet above said "git-guard is what refuses `--no-verify`", which is false (issue #619); the payload results replace it.
- `main` here has classic protection with `allow_force_pushes: false` and `allow_deletions: false`, but `enforce_admins: false`, and the `main required checks` ruleset holds only `required_status_checks` (read 2026-11-05 through the API). Whether that stops a push made with an admin credential is not established, and it must not be tested on a real branch. Any change to that setting is the operator's; the Director took it to the operator on 2026-11-05.

Non-goals: moving CodeFlow's seats and skills to `hc` (TSK-1345), and the worktree cleanup rule (TSK-1345).

## Outcome

After this merges, a command run through the Herdr app is judged as if it were run bare, and an `hc` form a guard cannot parse is refused. A reader of the rules can see which `hc` routes a guard can stop and which floor holds for those it cannot.

### AC-1: the forms on three builds

190 carried forms: 17 carrier families (`hc run` with each option form,
`hc exec` with and without `--on` and its options, `herdr pane run`, a
nested `sh -c`, `hc` by path and after `env`), each with eleven inner
commands (three headless peers, a protected force push, a protected branch
delete, a `--no-verify` push, two destructive deletes, a privileged delete
and two outward actions), plus the `--cwd`, template, `herdr agent start`,
file, typing, read-only, unknown-form and seat-line cases.

| Build | Carried forms weaker than the same command bare | Notes |
|---|---|---|
| installed 3.1.0 | 163 of 189 | every family except the file, typing and `--cwd` rows lets most classes through |
| line tip c35cf003f | 164 of 190 | the same; a few destructive forms refuse only through the outer read of the whole line |
| this branch | 0 of 190 | every carried form refuses where its bare form refuses, under the same rule |

Other rows on the branch:

- `--cwd`: a carried Git commit with `hc run --cwd` or `hc exec --cwd` on the
  protected branch of another repository refuses under
  `git.commit_to_protected`, as `git -C` does bare. It passed on 3.1.0 and the
  tip.
- Templates: `hc run --bg <template>` whose `command` is a headless peer refuses;
  a template whose command cannot be read refuses and names the form.
- `herdr agent start`: refuses, headless or interactive, because the pane's
  directory is unknown (review F1); a headless peer also refuses under its own rule.
- Files: `hc file write` and `hc file edit` to a hook or protected path refuse
  under the Edit tool's rules; to an ordinary path they pass. `hc file read`,
  `hc put <t> <file>` and `hc update --from <file>` are judged as a read of
  the file, so a protected secret path refuses under `security.secret_reads`.
  No other `hc` 0.1.18 or `herdr` subcommand reads, copies or uploads a path
  it is given: the rest are `run`, `exec`, `machine`, `send`, `keys`, `ls`,
  `get`, `read` (terminal output), `wait`, `kill`, `rm`, `attach`,
  `interrupt`, `label`, `keep`, `templates`, `events`, `schema`, `server`,
  `connect`, `--skill`, and the `herdr` pane and agent forms.
- Read-only and control forms pass: `hc ls`, `get`, `read`, `--skill`, `wait`,
  `kill`, `rm`, `attach`, `send --if idle`, `keys`.
- Unknown forms refuse and name the form: an unknown subcommand, an unknown
  `run` or `exec` option, a word the guard cannot fill in, a word supplied by
  `xargs` or `find`, a `$` in `--cwd`, and any carried command or file read
  whose directory the guard cannot establish (`--on` another machine with
  or without `--cwd`, a `herdr` pane, `herdr pane split` with `--cwd` or
  `--env`).
- Review F1 (PR 706, cross-lineage): the first review head refused only a
  Git command in an unknown directory, so a relative delete or read on
  another machine or in a pane was judged against the session tree. On
  that head such forms passed both guards; they now refuse in both, with
  tests per trigger.
- Tracked, not changed here (review nit): `hc update` and `herdr update`
  pass because they run no carried command, but they download and replace
  their own binary; `hc update --from` is judged only as a read of its file.
- Seat lines (AC-2): the Codex and Grok launch lines, each with and without

  reader has fully read; this removes a second read of the outer words, and
  the carried command is still judged in full. An unknown form keeps the walk.

### AC-5: text typed into a terminal

A guard cannot soundly judge text sent by `hc send`, `hc keys` or the `herdr`
send forms. What the text does depends on the program reading the terminal
(a shell, an editor, a peer's prompt), its mode and state at delivery, and
key sequences that can rewrite the line before Enter. A filter on the text
would refuse some strings and pass equivalent ones, so it is not offered as
protection. These forms pass when their own options parse. The floor that
holds is the receiving program: an agent session runs its own guards before
it runs a command, and a plain shell has none. Then the Git hooks, CI and
the remote branch protection hold, as for a command a person types. Stated in `docs/policy-reference.md`
"Terminal carriers the guards model". Nothing here refuses `hc send --if idle`
or `hc keys`, so no operator decision was needed.

### AC-6: running outside the Bash sandbox

`assets/base/rules/workflow-discipline.md` "Match the gate" now states that
a command an `hc` terminal runs is started by the Herdr core, outside the
harness's Bash sandbox, so the sandbox's file and network limits do not
apply to it; the guards are the only check before it runs. The live
scratch-core write check was not run: this build was told to run no real
`hc` or `herdr` command. The opt-in test
`crates/codeflow-cli/tests/hc_scratch_floor.rs` makes that write and is owed
to the operator. Its AC-6 row counts only when the operator runs it from a
plain terminal: inside the Claude sandbox the sandbox can block the write,
while the table would still call the path outside the sandbox.

### AC-7: not verified at build

Not run. Agents do not run Git through `hc`, and this build was told to run
no real `hc` or `herdr` command, so no scratch core was started. The
guard-level proof stands in its place: the carried force push to a
protected branch, with and without `--no-verify`, refuses through the guard
binary under `git.force_push_protected`, `git.no_verify_bypass` and
`security.outward_actions` (AC-1, every carrier family). Which floor stops
the push once a guard is not in the path (pre-push hook or remote) stays
unverified.

### AC-8: what stops a force push on the hosted repository

Read live through the API on 2026-11-07 at 13:33; no push was made.

- Classic protection on `main`: force pushes and deletion off;
  `enforce_admins` false.
- Ruleset "main required checks": `required_status_checks`,
  `non_fast_forward`, `deletion` and `pull_request`, with the admin role as a
  bypass actor in `always` mode.
- Ruleset for `integration/**`: `required_status_checks`, `non_fast_forward`
  and `deletion`, with no bypass actor.

A non-admin force push or delete on `main` or an integration line is
refused by the remote. An admin credential can bypass the `main` ruleset,
and the classic protection does not bind admins, so on `main` the remote
does not stop an admin force push. This gap goes to the Director for the
operator; the setting is the operator's.

### Sibling sweep

launchers: `tmux` (`new-session`, `new-window`, `send-keys`), `screen -dm`,
`zellij run`, `wezterm cli spawn`, `kitty @ launch`, `ssh <host>`, `at`,
`launchctl submit`, `systemd-run`, `docker exec`, `dtach`, `abduco`,
`open -a` and `expect`. They are outside the launcher list the policy
reference promises, and none is in this task's scope; the class goes to the
owning coordinator for one tracked item.
