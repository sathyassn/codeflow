# TSK-1344: Guards judge commands run through the Herdr app the same as bare commands

## Description

Source: the research for moving seats to the new Herdr app, finding S1, with the scope widened by the Director on 2026-11-05. It ranks with TSK-1343 at the top of the guards order. It is separate from TSK-1345 so that a gap open today does not wait on that migration.

Guards judged these strings on installed CodeFlow 3.1.0 on 2026-11-05; nothing ran:

| Command | exec-guard | git-guard |
|---|---|---|
| `claude -p hello` | blocked | passed |
| `hc run -- claude -p hello` | **passed** | passed |
| `hc run -- codex exec hello` | **passed** | passed |
| `herdr pane run w1:p1 'claude -p hello'` | **passed** | passed |
| `git push --force origin main` | passed | blocked |
| `hc run -- git push --force origin main` | passed | **passed** |

`crates/codeflow-core/src/security/headless.rs:154` returns `Found::Nothing` for a program it does not know. `hc` is not in `COMMAND_CARRIERS` (`crates/codeflow-core/src/hooks/git_guard.rs:14131`). A sandboxed Bash call cannot reach the `hc` socket, so this route needs an unsandboxed retry first.

Untested forms the manual lists, which AC-1 tests first:

- `hc exec [--on m] <argv>`: runs a program directly, with no terminal.
- `hc file write|edit`: changes files from the core, outside the Bash sandbox and the Edit rules.
- `hc send` and `hc keys` to a plain shell terminal: run whatever is typed.
- `hc run --bg <template>`: the command lives in a template file.

The floor under the guard is weaker than the first report said:

- The pre-push hook should stop a wrapped force push to a protected branch, but that was not run. `--no-verify` skips that hook, and git-guard is what refuses `--no-verify`, so a wrapped `git push --no-verify` is reasoned to pass both. Not run.
- `main` here has classic protection with `allow_force_pushes: false` and `allow_deletions: false`, but `enforce_admins: false`, and the `main required checks` ruleset holds only `required_status_checks` (read 2026-11-05 through the API). Whether that stops a push made with an admin credential is not established, and it must not be tested on a real branch. Any change to that setting is the operator's.

Non-goals: moving CodeFlow's seats and skills to `hc` (TSK-1345), and the worktree cleanup rule (TSK-1345).

## Outcome

After this merges, a command run through the Herdr app is judged as if it were run bare, and an `hc` form a guard cannot read is refused. A reader of the rules can see which `hc` routes a guard can stop and which floor holds for those it cannot.

## Acceptance Criteria

- AC-1 Before any product change, the builder shall test each of `hc run` with every option form, `hc run --bg <template>`, `hc exec` with and without `--on`, `hc file write`, `hc file edit`, `hc send`, `hc keys` and `herdr pane run` against exec-guard and git-guard, and shall record the result of each; evidence: the table in `## Findings`, with the build it ran on.
- AC-2 When a command runs through `hc run`, `hc exec` or `herdr pane run`, each guard shall judge the inner command by the same rules as the bare command, so `claude -p`, `codex exec`, `grok -p` and every git rule refuse as they do bare; evidence: tests that fail before the change and pass after it, for each carrier and option form. `hc run --bg --name x -- codex --no-daemon` shall still pass; evidence: a test.
- AC-3 When a guard cannot parse an `hc` form, including an unknown subcommand or option and a template whose command it cannot read, it shall refuse and name the form; read-only forms such as `hc ls`, `hc get`, `hc read` and `hc --skill` shall still pass; evidence: tests for each.
- AC-4 `hc file write` and `hc file edit` shall either meet the same path rules as the Edit tool or be refused; evidence: tests with a protected path and an ordinary path.
- AC-5 The builder shall decide whether a guard can soundly judge text sent to a terminal by `hc send` and `hc keys`. If it cannot, the task shall say so plainly and name the floor that holds instead; a partial filter shall not be presented as protection; evidence: the decision with its reasons in `## Findings`, the rule or skill text, and a test of whatever the decision enforces.
- AC-6 The rule or skill text shall state what running in an `hc` terminal without the Bash sandbox means for a command started there; evidence: the text, and a live check in a scratch core of one path write the Bash sandbox would refuse.
- AC-7 In a scratch repository with a hook-managed protected branch and a local bare remote, never a real one, a force push to that branch shall be attempted through the `hc run` route with and without `--no-verify`, and each result recorded, including which floor stopped it or that none did; evidence: the output and `git show-ref` on the remote before and after, from a test harness that uses a scratch `hc` core.
- AC-8 The findings shall name what stops such a push on a real hosted repository for a non-admin and for an admin credential, from the provider's documentation and the live protection settings, with no push against a real branch; if the floor has a gap, it goes to the Director for the operator; evidence: the entry in `## Findings`.
- AC-9 The change shall have a cross-lineage security review with the `cf-security-reviewer` checklist: Grok or Codex when a live probe at dispatch shows usage, else a fresh Claude Opus medium subagent with reduced assurance recorded; evidence: the review row and its findings record.
- AC-10 The pull request shall state the threat this closes and why judging the inner command and failing closed is the standard design; evidence: the PR body.
