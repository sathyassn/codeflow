# TSK-1369: Core lib tests pass with or without CARGO_TARGET_DIR

## Description

Two codeflow-core lib tests fail 5 of 5 when `CARGO_TARGET_DIR` is set to an absolute path in the test process, and pass 5 of 5 when it is unset (coord/catalog, at main `c5e9366fe` and at `bc257a48e`):

- `testing::gate::evidence_root_link_tests::a_link_at_the_build_output_folder_is_refused_before_any_write` (`crates/codeflow-core/src/testing/gate.rs:1745`);
- `testing::runner::tests::timeout_cause_survives_dependent_skips_and_saved_report` (`crates/codeflow-core/src/testing/runner/mod.rs:1814`).

The gate's evidence root reads the variable from the process (`crates/codeflow-core/src/testing/delivery.rs:146` in `target_dir` and `:162` in `target_anchor`, at line tip `d9bf657be`). With it set, a test gate in a temporary project writes its evidence into the folder cargo builds CodeFlow into, outside that project. Every Worker exports `CARGO_TARGET_DIR`, so this makes builder lib-test evidence depend on the shell and breaks the rule in EPC-022 AC-6 that tests write only inside their own temporary folders.

Scope: the tests' isolation. TSK-1044's evidence-anchor rule for adopters, where the gate honours `CARGO_TARGET_DIR`, stays unchanged. Near misses that do not cover this: TSK-1044 built the rule; TSK-1278 records the runner test failing on macOS as not verified; TSK-1253 is about wall-clock waits; TSK-1280 is about network lookups.

This is CI/CD and foundations work, so it gets a cross-family review (Grok), per the operator's order of 2026-11-06.

## Outcome

After this merges, a builder can run the codeflow-core lib tests with `CARGO_TARGET_DIR` set or unset and get the same results, with no gate evidence written outside the test's temporary project.

## Findings

Recorded before the code change, by reading the line tip `d9bf657be` (AC-1).

### Why the two tests fail with the variable set

- `delivery::target_anchor` (`delivery.rs:161-180`) anchors the evidence walk at the parent of an absolute `CARGO_TARGET_DIR`, outside the temporary project.
- The gate test plants a link at `<project>/target` and expects the gate to refuse it. With the variable set, the gate never looks at `<project>/target`, so it writes its run under the outside folder and returns no error.
- The runner test makes its run folder at `<project>/target/codeflow-gate/run`. With the variable set, the anchor and output (`runner/mod.rs:797`, `:896`) no longer contain that folder, so saving the result fails.

### Reads of build-environment variables (AC-1)

| Read | file:line | Class |
|---|---|---|
| `target_dir`, `CARGO_TARGET_DIR` | `codeflow-core/src/testing/delivery.rs:146` | product (TSK-1044); adopters rely on it |
| `target_anchor`, `CARGO_TARGET_DIR` | `codeflow-core/src/testing/delivery.rs:162` | product (TSK-1044); adopters rely on it |

The core lib tests that reach the first two reads through the gate or runner, all reading the variable from the process before this change: the 18 `run_gate` tests in `testing/gate.rs` from `:1053` to `:1745`, among them `config_evidence_digest_includes_defaults` (`:1421`), which lists `target_dir(...)/codeflow-gate` and so would see other tests' runs in a shared outside folder; and `timeout_cause_survives_dependent_skips_and_saved_report` (`runner/mod.rs:1814`). These are test-only uses of the product read.

### The change (AC-2)

- `delivery.rs` reads `CARGO_TARGET_DIR` once, in `build_output_setting`, defaulting to `target`. `target_dir` and `target_anchor` keep their signatures and behaviour; `target_dir_for` and `target_anchor_for` take the value as a parameter.
- In this library's unit tests (`cfg(test)`), `build_output_setting` returns `target`: in a test process the variable names CodeFlow's own build folder, never the temporary project's. Nothing writes the process environment, so parallel test threads are unaffected.
- Set values stay tested: `build_output_tests` checks relative, absolute and default values through the `_for` forms, and the CLI journeys check the real binary with the variable set (`a_link_at_the_build_output_folder_or_the_home_is_refused` in `test_gate_cli/containment.rs`, `a_cargo_target_dir_outside_the_worktree_warns_and_runs` in `test_gate_cli.rs`).
- The name-decode scan entry moves from `target_anchor` and `target_dir` to `build_output_setting`, count 1.

`CARGO_TARGET_DIR` cannot join the `.cargo/config.toml` `[env]` table: cargo has no way to unset a variable there, and an empty value makes `root.join("")` the project root.

`isolate_git` writes the process environment, once, behind a `Once` that every test in those two suites reaches before its first spawn. That is the two suites' existing pattern. Integration tests link the library without `cfg(test)`, so the unit-test route does not reach them. The two tests AC-2 names use no environment write.

Direct runs of a binary lack the `[env]` table, so `adopter_fit`, `ci_pin_platforms` and `git_maintenance_contract` failed in the first pass with 0 entries; they pass with the table applied. Two other failures needed a rerun with the failure text kept. The core lib's `a_composed_deletion_is_refused_as_its_rm_equivalent` failed once in the first pass, with its text not captured; the rerun passed 3821 with 1 ignored and 0 entries, so it did not repeat and its cause is not established. `refusal_journey`'s `installed_minimal_hooks_refuse_each_family_and_allow_real_ordinary_work` fails under a direct run at `refusal_journey.rs:228` with `unknown command: cargo. Perhaps you have to reshim?`, an asdf shim message that does not involve the build folder; under `cargo test` from the worktree it passes 68 of 68 with the variable set and unset.
