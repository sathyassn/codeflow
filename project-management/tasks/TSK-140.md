# TSK-140: one structural acceptance rule, with the one-PR fix

## Description

On 2026-09-27 a one-line test fixture fix for TSK-105, a complete task,
took three pull requests: a planning PR to reopen the record (628), the fix
(629) and a planning PR to complete it again (630). The fix itself needed
one review. The anchored preflight refuses a complete task, so the reopen
had to land on the target before the fix PR could name the task, and the
re-completion followed as its own PR. This task lets one fix PR carry the
reopen, the fix and the re-completion, with the new acceptance block bound
to a reviewed commit inside the fix PR and every rejection deterministic
(SPC-013 R-119). Plan review round 1 (Codex, with probes) showed two ways
today's judge would accept a stale review in this shape: a new active
block copied from the old one skips binding, and a fix merged into a task
completed late passes the landing-merge rule with the old reviewed commit.
Non-goals: criteria stay frozen, so a criterion change such as PR 637's
journey marking stays a planning PR (R-52); the separate reopen path stays
valid.

Reshaped 2026-09-27 (planning resolution 21). Binding today is several
cases: rule 1 of R-60, R-60's landing-merge rule (added in code by PR 636,
stated with its bounded ancestor form in plan review rounds 3 and 4),
waivers, R-119 and R-120. This task states and implements one rule: a
completion names a reviewed head, and after it only that record's status
and Closeout change. Merges are judged by structure and R-120's release
branch, named by `git.release_branch_pattern` under the default target's
policy, never by inferring a line's parent from topology. A task landing,
the merge of the judged task's own branch into its line, carries the
landed task's review through R-60's landing-merge rule, so a completion
made on the line after the landing keeps its verdict although unrelated
line commits came before the merge. Only on a release range is a merge a
brought import, when each non-first parent lies on a verified epic line's
or the default target's first-parent chain, however it arrives, judged by
TSK-145's per-path attribution (the full tree entry against the expected
import, never the range's own refs as qualifiers); any other merge there,
the release task's own fix pull requests included, is direct work. Every
other range, epic lines, stacked lines, shared history and line-to-line
syncs included, keeps R-52 and R-60. Criteria stay frozen wherever R-52
and R-120 freeze them: a release range's direct changes never amend one,
and an amendment reaches it only brought from a line's planning pull
request. The one-PR fix and the release-line case become results of that
rule. It reshapes this task rather than adding one: the task is unstarted,
already follows TSK-145 in the same file, and building R-119 as a separate
case first would be removed again by the consolidation. Clear semantics
come first; the spec text size is reported, not a target.

## Acceptance Criteria

- AC-1 When a pull request names a complete task and its range reopens the
  record (the active acceptance block kept under `acceptance_superseded:`
  with a reason) and completes it again with a new block, `work start`,
  `task status` and CI shall accept the reopen, the fix and the
  re-completion in that one pull request; evidence: lifecycle tests and a
  `ci_cli` fixture of a one-PR fix of a complete task.
- AC-2 When a range reopens and completes a task again, `task status` and
  CI shall judge it as a reopen plus a completion and bind it explicitly,
  even when the new active block equals the old one; the new block's
  reviewed commit shall lie inside the range at or after its last change
  outside the record's status and Closeout; the superseded block shall be
  compared with the anchored target's; and the late binding to a landing
  merge shall not apply; evidence: lifecycle and `ci_cli` tests.
- AC-3 When a one-PR fix is judged, each of these shall block for its
  stated reason in both `task status` and CI: a direct code fix whose new
  block copies the old one; a fix merged into a task completed late whose
  new block keeps the old reviewed commit; a code commit after the
  reviewed commit; a dropped or edited old block; a missing reason; a
  missing or unverified criterion; a changed criterion, including a
  records-only range that loosens a criterion and completes again; and a
  waiver without an amendment on the target; evidence: one fixture per
  fault, seeded from the Codex plan review probes
  (`followups-acceptance-probe.py`, its `merged_fix` and `direct_fix`
  cases and the copied-block CI run), each failing before the change.
- AC-4 When a planning PR reopens a complete task as today, and later
  PRs fix and complete it, the checks shall pass as before; evidence: the
  existing reopen tests pass unmodified.
- AC-5 cf-ship shall gain the one-PR fix of a complete task in its step 1
  completion text (reopen with a reason, fix, complete again against the
  fix PR's head), where it has no reopen text today; the mirrors shall
  stay byte identical and the text shall be reachable from cf-ship's
  index; evidence: the skill diff, `manifest_consistency`,
  `artifact_budget_contract`, and the chain total reported before and
  after (a measure, not a gate; TSK-150).
- AC-6 (journey) On a freshly scaffolded full-tier project with the
  installed CLI, a task completed in one pull request is then fixed by a
  second single pull request that carries its reopen and re-completion,
  CI passes it, and the copied-block and missing-reason faults fail for
  their stated reasons; evidence: a case in `acceptance_journey`.
- AC-7 SPC-013 shall state binding once, as the rule and the two merge
  provenances in the Description, with R-119, R-120 and the landing-merge
  rule's clauses restated as its results; evidence: the spec diff in this
  task's pull request, with the size of R-54, R-60, R-119 and R-120
  reported before and after (7,231 bytes at `8df3cac42`) as information,
  not a target.
- AC-8 When the unified judge replaces rule 1, the landing-merge case and
  the head-or-introduced split, every existing binding fixture shall give
  the same verdict (`acceptance_cli`, `acceptance_journey`, the `ci_cli`
  acceptance and change-class probes, the lifecycle tests, and TSK-145's
  fixtures, among them the round 3 and 4 ones: the
  `records_only_criterion` matrix with its `base=M` slice,
  `mode_only_resolution` and the file-type change with their exact-entry
  positive, the side branch pushed only to the release branch, the
  synthetic landing-merge ancestor positive, TSK-037's real history as its
  negative, and TSK-145 AC-9's scope fixtures); evidence: a verdict
  table of every fixture before and after, with no difference.
- AC-9 When a range contains a merge, the judge shall treat it as a task
  landing, as a brought import only on a release range (R-120, a branch
  named by the default target's policy), or as direct work, without
  inferring a line's parent from topology, so lines that share history,
  stacked lines and line-to-line syncs keep their own landings and
  planning amendments; a late completion after a clean task landing
  (reviewed R, then a status and Closeout commit C, an unrelated product
  commit P on the line, the clean merge M of C, and the completion D)
  shall bind, and a fix merged into a task completed late whose new block
  keeps the old reviewed commit shall stay refused; evidence: both
  fixtures in `ci_cli` and `acceptance_cli`, and the AC-8 table.
