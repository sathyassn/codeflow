# TSK-168: explanatory pages carry their page class marker

## Description

TSK-063's rendered design review of the Agent OS guide found that the one
explanatory page, `repository-surfaces`, carries no `data-cf-page-class`
attribute in its built markup, while every illustrated, pass-through and
derived-lookup page carries one. A consumer of the markup, such as a test,
the verifier or a reader's tool, cannot tell the explanatory page from an
unmarked generated page. This task makes every built route carry its page
class, the explanatory one included, from the same class record the
adapter already computes. Changing what the classes mean is a non-goal.

## Affected surfaces and interfaces

- The adapter's rendering of an explanatory page in
  `docs-portal/scripts/adapter.mjs`, the class vocabulary in
  `docs-portal/scripts/page-classes.mjs`, the browser verifier's page-class
  coverage, their byte copies under `assets/docs-portal/starter/`, and the
  starter pins in the scaffold manifest.

## Acceptance Criteria

- AC-1 When the adapter builds an explanatory page, its source region
      carries `data-cf-page-class="explanatory"`, like every other class;
      evidence: an adapter test over a fixture with one page of each class,
      failing before the fix.
- AC-2 The browser verifier's page-class coverage fails a built route with
      no class marker; evidence: a verifier test with a marker removed.
- AC-3 The starter copies and pins are updated and the portal checks pass;
      evidence: `npm run check` and `browser:verify` in `docs-portal`,
      `codeflow validate --portal` on a scaffolded guide and the scaffold
      manifest tests, recorded with the head SHA.
