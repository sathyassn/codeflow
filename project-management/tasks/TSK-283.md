# TSK-283: Guards read the git configuration a command will use

## Description

Exec-guard's outward-release check reads a git alias from configuration
files and `-c` and refuses `--config-env`, but it ignores configuration
given through `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n`, `GIT_CONFIG_VALUE_n`,
`GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` or
`GIT_CONFIG_NOSYSTEM` (https://github.com/sathyassn/codeflow/issues/98; `crates/codeflow-core/src/security/outward.rs:725-790`
at v3.1.0). Only git-guard covers that case today. Files that an existing
`include.path` or `includeIf.*.path` names are not protected, so a planted
alias or pager there runs under a later git command (https://github.com/sathyassn/codeflow/issues/88; an open residual
in `docs/policy-reference.md:476-477`). Both need the configuration git will
actually use, and one shared reader serves both, so they are one task.

## Deliverables

- the shared reader: a module under `crates/codeflow-core/src/security/` (provisional name)
- its users: `crates/codeflow-core/src/security/outward.rs`, `crates/codeflow-core/src/security/git.rs`, `crates/codeflow-core/src/hooks/git_guard.rs`, `crates/codeflow-core/src/hooks/edit_guard.rs`, and the doctor report in `crates/codeflow-core/src/doctor/`
- tests: guard unit tests and an exec-guard CLI test
- docs: `docs/policy-reference.md` residual list
- release note: `changelog.d/TSK-283.md`

## Acceptance Criteria

- AC-1 One shared reader shall build a command's effective git
  configuration from its files, includes and conditional includes
  (bounded, with no loops), `-c`, `--config-env` and the `GIT_CONFIG_*`
  variables above, and report "cannot verify" when it cannot reproduce
  them; evidence: reader tests, an include loop and a missing include
  among them. (serves EPC-022 AC-5)
- AC-2 When exec-guard runs alone, `GIT_CONFIG_COUNT=1
  GIT_CONFIG_KEY_0=alias.ship GIT_CONFIG_VALUE_0='push origin v9.9.9' git
  ship` shall be refused as an outward release, as shall the same alias
  through `GIT_CONFIG_PARAMETERS` and through a `GIT_CONFIG_GLOBAL` file;
  evidence: exec-guard tests with git-guard not wired. (serves EPC-022 AC-5)
- AC-3 Every other guard that decides from `alias.*`, `core.*`, `push.*`,
  `remote.*` or `branch.*` shall use the reader or refuse when the
  command's environment names one of these variables; evidence: a sweep
  table in the pull request with file:line per reader.
- AC-4 A native edit or shell write to a file that the global, system or
  repository configuration includes shall be refused, naming the rule and
  the sanctioned path, or `codeflow doctor` shall report includes that
  point at writable files; the policy reference shall update its residual
  list; evidence: planted include tests and the doc diff.
- AC-5 (journey) When a fresh project with the installed build wires only exec-guard,
  the AC-2 command shall be refused, and a session edit to a file named by
  `include.path` shall be refused or reported by doctor;
  evidence: a CLI journey.

## Follow-ups

- Track once: Git program variables such as `GIT_SSH_COMMAND` and `GIT_PAGER`
  refuse when exported in a non-Git segment but are allowed as a command-local
  prefix on Git. Revisit when the guards decide whether program variables are
  decision inputs.
- Track once (security F3): libgit2 project-root discovery can block on a
  non-regular include before the shared reader's deadline. Revisit at the
  EPC-022 closeout review; add a FIFO include journey that proves both hooks
  refuse within a bounded discovery path. Check how Claude, Codex and Grok
  handle a hook timeout: allowing the call to proceed would fail open.
  A bounded reader call cannot interrupt in-process libgit2, and changing
  all hook discovery is disproportionate to the alias/parser repair.
- Track once: the include diagnostic lists present and missing files but does
  not check file permissions. Revisit when include-file writes are guarded
  (issue 88), and report writability for the current user and others then.
- Track once: exec-guard alone does not discover configuration variables set
  by `source` or `.` before a Git alias or push. Revisit when the guards model
  sourced files; cover a sourced environment file followed by a release alias.
- Track once: exec-guard alone does not follow a same-line configuration write
  before an alias (`git config alias.st ...; git st`, or `cp`, `mv` and `sed`
  into `.git/config`). Revisit when exec-guard takes git-guard's ordered
  config_changed and config_write facts. Shipped wiring installs both guards.

## Security repair evidence

- F1: configuration lookup follows Git's section/variable case rules and
  preserves subsection case; both guards lowercase alias names. Regressions
  cover mixed-case command-local and repository aliases.
- F2: destinations must be literal variable names after quote removal;
  unreadable brace words and other unresolved shapes refuse. A closing rule
  on configuration-dependent lines refuses configuration-variable mentions
  in non-Git segments except plain `$NAME` and `${NAME}` reads. Both guards
  cover brace/glob destinations, indirect zsh assignments, `getln`, variable
  redirections and unquoted heredocs. Git operands and commit messages remain
  excluded; data mentions in non-Git segments may conservatively refuse.
  Assignment-prefix inspection retains executable paths containing `=`;
  regression tests cover Git, launchers and interpreter paths.
  Arithmetic writes in `$[...]` are inspected in Git segments and unquoted
  heredocs as well as `$((...))`; array diagnostics name the assignment.
- F3 is tracked above; F4 remains the accepted include-write diagnostic
  residual. Independent Fable and security confirmation follow this repair.
