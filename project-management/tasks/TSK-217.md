# TSK-217: Fix split warnings, the present message, reopened criteria and a Node 20 action

## Description

Four small defects that 3.1.0 removes in one pull request.

- `codeflow validate --docs` warns that most completed standalone tasks
  were "completed by N pull requests". It counted every merge commit whose
  subject names the task branch, which includes the catch-up merges of the
  target into the task branch that the rules require: TSK-197 landed through
  one pull request (merge `9d72d3625`) but is reported as 5. The count now
  takes only merges in the history of `HEAD` whose merged-in branch, the
  part of the subject before ` into `, names the task. It reads all
  reachable history, not only the first-parent line: a standalone task
  whose target is an integration line lands there, and that line reaches
  `main` in one merge, so a first-parent count on `main` would hide a real
  double landing (TSK-196 landed twice on its integration line, PRs #785
  and #786). A plain `git merge --no-ff`, GitLab's merge subject and
  GitHub's merge subject all name the merged-in branch first;
  `codeflow integrate` fast-forwards and writes no merge, so it was never
  counted and still is not.
  Known limits, which predate this change and stay: a custom subject such
  as "Merge main to task/TSK-217-x" still counts; a merged-in source named
  by a repository URL that contains `/TSK-217-` can count; squash and
  rebase landings write no merge and are not counted.
- `codeflow present show` on a session whose browser is still running exits
  4 with "presentation browser launch is not qualified: this presentation
  already has an owned browser window". The message now says the session's
  browser is already open and what to do: switch to that window, or quit
  that browser and run `show` again, with `--no-launch` printing the
  address. The exit code stays 4.
- CodeFlow's own CI still runs `actions/cache@v4`, which uses the
  deprecated Node 20 runtime, so every gates run on the public repository
  carries the deprecation annotation. It moves to `actions/cache@v6`
  (v6.1.0, Node 24). That workflow is an enforcement file agents cannot
  edit (ADR-0009; the guard refuses the write), so a human makes this
  one-line edit on the task branch before the merge. The shipped CI
  templates and their baselines already use only Node 24 actions
  (`actions/checkout@v6`), so adopters' workflows do not change.

- A task whose record exists only on its own branch cannot change its
  criteria after a reopen: `codeflow task status <id> complete` refuses
  with "a reopened task keeps its criteria as the anchored target has
  them" (seen on TSK-213, PR 37). The binding recovers the earlier
  completion inside the branch and, when the anchored target has no record
  of the task, kept that completion's criteria as the ones to preserve.
  Now a task new in its range takes its criteria from the range; a task
  the target records keeps today's rule. Whether the target records it is
  decided by identity, the `id` and `uid` as the frontmatter parser reads
  them, in the task directories of every supported layout, at every
  reference point either path could judge against: the range base, the
  tips of every target the record has named (its configured upstream on
  any remote, its `origin` ref and the local branch), the pull request's
  base in CI, and the default target's tips. The targets the record has
  named are the declared one, the recovered completion's, and the one in
  each version of the record in the range, the range base's version
  included, so a branch cut from an integration line still names that
  line after it retargets the record. So a moved record, a stale local
  branch, an upstream on another remote, an older comparison base, a
  record retargeted away from `main` or from an integration line, and a
  re-quoted uid cannot make a recorded task look new, and the verb and
  `codeflow ci` reach the same answer. Because the range's own history is
  the branch's to rewrite, a task no point holds is new only when no
  branch or remote-tracking ref outside the range records it: a commit
  that such a ref reaches and the head does not, and that adds the task's
  record or changes it from every parent's version, makes the task
  recorded, and the refusal names that ref. Copies inherited from the
  range's own commits do not count, so a branch stacked on this one or
  the task branch's remote copy with unrelated commits on top leaves a
  new task new. The default target is the branch
  `origin/HEAD` names, else `main` or `master`; a clone with another
  default branch and no `origin/HEAD` cannot find it. It fails closed:
  when a target the record names or the default target does not resolve
  in the clone, the history of the range cannot be read, or the record at
  the task's own file name does not parse, the earlier criteria stay and a
  change is refused with a reason that names the ref to fetch, or, when
  no default target is found, how discovery works and how to record
  `origin/HEAD`.
  Limits: a branch that replaces both the id and the uid of a record under
  a new file name is judged a new task, and editing the uid of a kept
  record is refused by the registry check; a stale or abandoned branch
  that adds or edits the record blocks a criteria change until a human
  deletes it (or merges it, when it is newer work on the task); a record
  deleted from the target before the range began is not found again
  through a branch cut before the deletion; the check reads only the refs
  the clone has, which hosted CI fetches in full.

Non-goals: the other "launch is not qualified" messages, which report real
launch failures, and the evaluation fixtures under `cf-evaluate-model`,
whose `actions/checkout@v4` lines are scenario data, not workflows.

## Acceptance Criteria

- AC-1 When a completed standalone task's branch took catch-up merges of
  its target and landed once, `codeflow validate --docs` shall not warn
  that it was completed by more than one pull request; evidence: a new
  `remedy_clearing` test with two catch-up merges (one in git's default
  subject, one in GitHub's remote-tracking subject) that fails on the
  previous count and passes after the fix.
- AC-2 When a standalone task really landed through two pull requests, the
  warning shall still name 2, even with catch-up merges on the line;
  evidence: the existing `clears_standalone_split` test and a new test that
  lands two branches of the task, with catch-up merges, through GitHub's
  merge subject.

  browser is still running, it shall exit 4 with a message that says the
  session's browser is already open and names `codeflow present show <id>`
  and `--no-launch`, without "not qualified"; evidence: a `present_cli`
  test that fails on the previous message and passes after the fix, and the
  `present show` row of `docs/present-guide.md` updated to match.
- AC-4 No workflow under `.github/workflows/` and no shipped CI template
  shall use an action whose `action.yml` runs on Node 20; evidence: each
  `uses:` reference listed with its `runs.using` read through `gh api` at

  this branch, and `scripts/gate-parity.py` passing.

  validate and present fixes; evidence: the CHANGELOG diff and
  `codeflow validate --docs`.

  `a_task_new_in_its_range_may_change_criteria_on_reopen`, which fails on
  the previous binding and passes after the fix, and

  comparison base predates it, and when the range retargets it to a
  branch that predates it; evidence:
  `a_moved_record_keeps_the_target_criteria_on_reopen` and
  `every_anchor_sees_the_target_record_on_reopen`, which fail on the
  previous binding, and the unit test
  `presence_finds_a_task_by_identity_in_any_layout`. The same holds when
  the target's tip is a configured upstream on another remote and when
  the uid is kept in another YAML form (plain, single or double quoted),
  and a clone without the default target refuses the change and names
  the ref to fetch; evidence:
  `a_configured_upstream_on_another_remote_holds_the_task`,
  `a_kept_uid_matches_in_every_yaml_form` and
  `a_clone_without_the_default_target_fails_closed`, which fail on the
  previous binding. A task planned on an integration line that `main`

  `a_task_planned_on_an_integration_line_keeps_its_criteria_on_retarget`
  and `a_custom_default_branch_is_found_through_origin_head`, which fail
  on the previous binding. A branch that rewrites the task's planning
