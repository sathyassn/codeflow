# TSK-1105: A builder creates its task worktree and claims under its harness sandbox

## Description

Two harness sandboxes stop a builder before its first commit. Codex builder
seats (the `cf-builder` posture) cannot finish a build here: the Codex
sandbox denies the `.git/config` write `git worktree add` makes, denies
`ps`, which `coordination/scripts/gate-turn.sh` uses to prove a ticket
holder is alive, and denies the gate lock holder record under
`~/.codeflow/locks/` (`full-gate.lock: Operation not permitted`), so a Codex
builder cannot claim, run `codeflow reserve` or push (queue items 29 and
29b, 2026-10-31; TSK-1077, TSK-323 and TSK-330 were reassigned to Claude
builders for this reason). In a scaffolded project, Claude's sandbox
write-deny on `.claude/` (an enforcement path) makes the required
`git worktree add` fail on `.claude/agents/*.md`, so a subject cannot start a
task worktree without the auto-mode unsandboxed retry; in the TSK-1032
trials one subject stopped to ask the user and the other retried with the
sandbox off (queue item 30, 2026-10-31 01:15). Every Claude builder and
every adopter on the sandboxed preset meets this.

This task gives both a sanctioned route that works inside the sandbox
without weakening any deny: `codeflow work start` (or `work claim`) creates
the worktree through a route the presets allow, with the enforcement-path
denies judged on the worktree's own copies after checkout as TSK-399
requires; the Codex builder posture gets a lock home its profile allows and a
liveness proof that does not need `ps`. Non-goals: no deny is relaxed, no
preset gains a broad allow, and the coordination scripts are the workspace's
(`coordination/` is not in this repository); this task changes the shipped
posture and the `codeflow` commands they call.

## Outcome

After this merges, a Claude or Codex builder can create its task worktree, claim, reserve and push from inside its harness sandbox with no unsandboxed retry and every enforcement-path deny still in force.

## Deliverables

- the sanctioned worktree route: `crates/codeflow-cli/src/cmd/work.rs` (`work start` and `work claim` creating the worktree) and `crates/codeflow-core/src/workgraph/readiness.rs`
- the lock home and liveness proof: `crates/codeflow-core/src/gate/reserve.rs` (or where `codeflow reserve` keeps `full-gate.lock`), with the Codex profile's allowed home
- the Codex builder posture: `assets/base/skills/cf-model-orchestrator/resources/routing/transport.md`, `cf-herdr/SKILL.md`, both mirrors byte-identical; the Codex profile under `.codex/`
- the Claude preset: `assets/base/settings/default.json` and siblings only if AC-2 proves a change is needed, each change listed with its deny before and after
- docs: `.codeflow/rules/worktrees.md` (the work-start check), `docs/harness-posture.md`, `docs/troubleshooting.md`
- tests: `crates/codeflow-cli/tests/work_cli/` for the worktree route under a simulated deny, the reserve lock tests, the preset mirror tests

## Acceptance Criteria

- AC-1 Before any change, the builder shall research worktree creation and locking under harness sandboxes broadly: reproduce each denial on the current presets (Codex: the `.git/config` write, `ps`, the lock directory; Claude: the `.claude/` write during `git worktree add`), read the Claude Code and Codex sandbox documentation for what each profile can allow per path, how other tools create worktrees without writing enforcement paths (sparse checkout, a two-step checkout, creating the worktree from the primary), TSK-349's and TSK-399's rules and tests, and adjacent concerns (worktrees on another volume, a repository whose `.claude/` is a symbolic link, the auto-mode retry classifier); and shall record the findings with sources and the chosen scope before anything else changes; evidence: the Findings section, committed before the first code change in the PR. Listed first because it runs first (the operator's rule of 2026-10-27).
- AC-2 Under the shipped Claude presets with the sandbox on, `codeflow work start` (and `work claim` where it creates the branch) shall create the task worktree without an unsandboxed retry, and after checkout every TSK-399 deny shall hold on the worktree's own `.claude/` and `.codex/` copies; evidence: a test that runs the route under a simulated enforcement-path deny and fails on the current `git worktree add` route, and the TSK-399 tests unchanged and green. (serves EPC-022 AC-183)
- AC-3 A Codex builder seat in the `cf-builder` posture shall create its worktree, claim, run `codeflow reserve` and push: the gate lock shall live in a home the Codex profile allows, holder liveness shall be proven without `ps` (a heartbeat or lock lease the holder renews), and a stale holder shall be reported, never silently taken over; evidence: the reserve tests for a live, a dead and a stale holder, and the profile diff. (serves EPC-022 AC-183)
- AC-4 No deny shall be weaker after this change: every preset and profile deny shall be listed before and after in the PR body, byte-identical where unchanged, and a change shall name the path it opens and why no enforcement file is reachable through it; evidence: the preset mirror tests and the list. (serves EPC-022 AC-183)
- AC-5 `transport.md`, `cf-herdr` and `.codeflow/rules/worktrees.md` shall state the route per harness, and the Codex builder posture shall no longer be recorded as unable to build here; evidence: the text diff, both mirrors byte-identical.
- AC-6 (journey) With the installed build in a scratch adopter made by `codeflow init --standard`, a Claude session under the shipped preset and a Codex seat in the builder posture shall each start a task, make one commit and push it, with the hooks' exit codes shown and no unsandboxed retry; evidence: the journey output per harness.
