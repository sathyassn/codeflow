# TSK-1105: A builder creates its task worktree and claims under its harness sandbox

## Description

Two harness sandboxes stop a builder before its first commit. Codex builder
seats (the `cf-builder` posture) cannot finish a build here: the Codex
sandbox denies the `.git/config` write `git worktree add` makes, denies
`ps`, which `coordination/scripts/gate-turn.sh` uses to prove a ticket
holder is alive, and denies the gate lock holder record under
`~/.codeflow/locks/` (`full-gate.lock: Operation not permitted`), so a Codex
builder cannot claim, run `codeflow reserve` or push (queue items 29 and
29b, 2026-10-31; TSK-1077, TSK-323 and TSK-330 were reassigned to Claude
builders for this reason). In a scaffolded project, Claude's sandbox
write-deny on `.claude/` (an enforcement path) makes the required
`git worktree add` fail on `.claude/agents/*.md`, so a subject cannot start a
task worktree without the auto-mode unsandboxed retry; in the TSK-1032
trials one subject stopped to ask the user and the other retried with the
sandbox off (queue item 30, 2026-10-31 01:15). Every Claude builder and
every adopter on the sandboxed preset meets this.

This task gives both a sanctioned route that works inside the sandbox
without weakening any deny: `codeflow work claim` (one step with the claim
commit and preflight, operator decision D4 of 2026-11-01) creates
the worktree through a route the presets allow, with the enforcement-path
denies judged on the worktree's own copies after checkout as TSK-399
requires; the Codex builder posture gets a lock home its profile allows and a
liveness proof that does not need `ps`. Non-goals: no deny is relaxed, no
preset gains a broad allow, and the coordination scripts are the workspace's
(`coordination/` is not in this repository); this task changes the shipped
posture and the `codeflow` commands they call.

## Outcome

After this merges, a Claude or Codex builder can create its task worktree, claim, reserve and push from inside its harness sandbox with no unsandboxed retry and every enforcement-path deny still in force.

### Harness boundary and candidate routes

The [Claude sandbox documentation](https://code.claude.com/docs/en/sandboxing#protected-paths)
says protected settings and code paths remain denied despite `allowWrite`.
Its retry section says auto mode classifies an unsandboxed retry; classifier
approval does not make that retry sandboxed. The
[Codex permission documentation](https://learn.chatgpt.com/docs/permissions)
defines `read` as forbidding creation, modification, rename and deletion;
more specific filesystem entries override covering entries. Neither source
establishes an executable-specific filesystem exception for `codeflow`.

| Candidate | Assessment before native reproduction |
|---|---|
| Direct checkout through Git or libgit2 | A process still cannot create a destination that its OS sandbox denies; changing libraries does not establish a sanctioned exception |
| Sparse checkout | Git documents `--no-checkout` for sparse setup, but omitting enforcement files cannot prove protection of the worktree's own installed copies |
| Two-step checkout | Deferring checkout moves the protected-file write to a later step; that step still needs an authorized creation route |
| Create from the primary before launching the builder | Can separate checkout creation from the builder's later denies, but changes the specified builder-owned creation journey and needs coordinator settlement |
| Harness-native worktree creation | Claude documents `claude --worktree`; it is a candidate for creation before shell sandbox execution, not evidence that `codeflow work claim` can invoke it inside that sandbox |

Sources for those routes are the
[Git worktree manual](https://git-scm.com/docs/git-worktree#Documentation/git-worktree.txt---no-checkout)
and [Claude's worktree workflow](https://code.claude.com/docs/en/common-workflows#run-parallel-sessions-with-worktrees).
TSK-349 also requires a separate desktop session for a separate unit and
forbids a broad sibling-worktree grant as an isolation repair.

Adjacent cases remain part of qualification:

- A worktree on another volume needs an allowed destination and shared Git
  metadata access. A staging-and-rename route is not portable across volumes.
- A symlinked `.claude` must retain target-path protection. Claude documents
  resolved symlink protection; replacing a denied file through an alias is
  not an acceptable creation route.
- A simulated deny must refuse the actual protected-file write. A Git shim
  that merely refuses the words `worktree add` cannot establish OS sandbox
  compatibility.
- The final deny comparison must use TSK-399's landed set. All preset and
  profile bytes remain unchanged in this reading pass.
