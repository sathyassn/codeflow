# TSK-393: A re-push judges project paths from the target's policy

## Description

Source: PR 237 (TSK-276) reviews, 2026-10-17. Pre-push judges an already-pushed branch's range under its own earlier tip's policy (`crates/codeflow-cli/src/cmd/push_set.rs:1390-1391`, `:1531-1548`; `crates/codeflow-core/src/workgraph/amendment.rs:397-405`). So `product_paths`, watched paths and `git.document_indexes` can be granted by the branch itself across two pushes. The hosted check reads the PR base and is the enforcement. Security, low.

Outcome: **pre-push reads project paths from the target's authority tip on every push, so a branch cannot grant itself paths across two pushes.**

Added to EPC-023 (4.1.0) by the amendment of 2026-10-18: the operator's release decision of that day puts lower-severity review follow-ups in 4.1.0 (workspace `RELEASE-PLAN.md`, 2026-10-18 operator decision).

## Deliverables

- the authority read: `crates/codeflow-cli/src/cmd/push_set.rs` and `crates/codeflow-core/src/workgraph/amendment.rs` (`--policy-from`)
- tests: CLI tests with a two-push fixture
- release note: `changelog.d/TSK-393.md`

## Acceptance Criteria

- AC-1 When a branch's first push adds a path to `product_paths`, `git.document_indexes` or the watched paths, and its second push relies on it, pre-push shall judge the second push with the target's policy and refuse; evidence: a two-push fixture, failing before the change. (serves EPC-023 AC-28)
- AC-2 A re-push of a `plan/` branch with an advertised work target shall still judge from the merge base with that target; evidence: tests.
- AC-3 (journey) With the installed build, the two-push sequence in a scratch adopter project shall be refused at the second push; evidence: the journey output.
