# TSK-048: close the validator and cleanliness holes under the portal gate

## Description

Two holes that the per-source composition gate rests on do not depend on the
composed views and were waiting behind them for no reason: the portal
validator accepts an empty or malformed Pagefind entry file, and the adapter's
HEAD-cleanliness check refuses harness litter such as `.claude/.cc-writes` and
`__pycache__` while it must never excuse a tracked or source-file change. This
task closes both now so the composition gate task carries only the page-class
rules. Non-goals: no page-class rule, no browser-verify change, no page content.

## Affected surfaces and interfaces

The portal validator under `crates/codeflow-core/src/validate/` and its tests;
the dirty-check in `docs-portal/scripts/lib.mjs` and `git-snapshot.mjs` with
their starter mirrors under `assets/docs-portal/starter`; the adapter test
fixtures in `docs-portal/tests/adapter.test.mjs` and its mirror, only for the
three cleanliness cases. Does not touch `adapter.mjs`, `portal.css`,
`browser-verify.mjs` or `composed-views.test.mjs`. CAP-015.

### What landed

`crates/codeflow-core/src/validate/portal.rs` gained `verify_pagefind_entry`,
called from `validate_portal` once the built artifact inventory is collected.
When `dist/pagefind/pagefind-entry.json` is present in that inventory the
validator reads it under a 1 MiB bound and refuses four shapes: unreadable,
empty or whitespace only, not valid JSON, and structurally wrong (not an
object, no non-empty `version` string, or no non-empty `languages` object).
Every message names `dist/pagefind/pagefind-entry.json`. A portal that never
built a search index is unchanged: the claimed-versus-actual artifact
cross-check already reports a missing or unclaimed entry, so the new function
returns early rather than duplicating that refusal.

`docs-portal/scripts/git-snapshot.mjs` changed `assertClean` and replaced
`parsePorcelainPaths` with `parsePorcelainRecords`, which carries each
porcelain status code alongside its path. A dirty path inside a watched root is
now exempted only by `#exemptLitter`, and only when all of the following hold:

- the status code is `!!`, which Git reports for a path that is untracked and
  matched by the repository's ignore rules;
- the path is not one of the configured snapshot paths the adapter passed in;
- the path is not a file committed at HEAD in the loaded inventory;
- no configured snapshot path lies underneath it.

The last two conditions fail closed: with no inventory loaded, nothing is
exempt, so a caller that skips `loadInventory` keeps the old strictness. A
tracked modification carries a code of ` M`, so a file that is tracked and also
matched by an ignore pattern stays dirty. An untracked file the repository does
not ignore carries `??`, so it stays dirty too.

The adapter runs Git with `GIT_CONFIG_GLOBAL` pointed at `/dev/null` and
`GIT_CONFIG_NOSYSTEM=1`, so `!!` reflects the repository's own ignore rules and
`.git/info/exclude`, not a developer's global ignore file. That is the intended
reading of the criterion.

`docs-portal/scripts/adapter.mjs` was not edited. The exemption sits entirely
behind the unchanged `assertClean(paths)` signature.
