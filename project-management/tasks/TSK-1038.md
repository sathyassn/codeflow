# TSK-1038: Work next never offers a task whose work has landed as ready

## Description

Issue #370, its `work next` part. `codeflow work next` trusts each task
record's status, so a task whose work has landed but whose record was
never completed is offered as ready, and a session may start finished
work again. The backlog already holds the fact that would stop it:
`crates/codeflow-core/src/workgraph/readiness.rs` `backlog` (`:774`)
splits each record's claim branches into open and landed (`split_landed`,
`:638`, proving a landing with `git cherry` in `landed`, `:446`), then
marks the task `Ready` when no open branch remains (`:846-847`), so a
task whose only branch has landed shows as ready. The landed names reach
`Backlog::landed` but `work next` (`crates/codeflow-cli/src/cmd/work.rs:100`)
never prints them.

Planning found no live instance on this line: no ready EPC-022 task
had a remote `task/` branch merged into the line (checked on 2026-10-28
with `work next --json` and `git branch -r --merged`), so the defect
is shown by code reading and AC-1 reproduces it on a fixture.

This is a defect in an existing command, reporting finished work as
ready from facts it already computes, so it is placed in 4.0.0. The full
audit of every drift class is TSK-1042 in EPC-023 (4.1.0).

Outcome: **`codeflow work next` never offers as ready a task whose branch
has landed in its target while its record is still open; it lists such a
task as landed with the suggested `codeflow task status` command, and
`work claim` refuses it with the same reason.**

Rules:

- A record-only branch (one that only filed or amended the record) does
  not count as landed work; AC-1 settles how that is told apart.
- Nothing changes a status; the command reports and refuses.

Non-goals: the other drift classes (blocker cleared, idle claims,
abandoned, owed completion, epic out of step), which are TSK-1042 in
EPC-023.

## Investigation

Recorded before the first code change (AC-1), on the line tip 461827479.

**Reproduction.** On a fixture, `work next` lists a todo task as `ready`
after its `task/<id>-...` branch is merged into the target with a merge
commit and the record stays `todo`: `backlog` (`readiness.rs`) splits the
claim branches with `split_landed` and sets `Ready` when no open branch
remains, and the landed names go only to `Backlog::landed`, which `work
next` never prints. `work claim` (`claim_on`) ignores the landed names the
same way. On this repository `work next` lists 84 ready tasks across every
target; none of them has a remote `task/` branch merged into the line
(`git branch -r --merged`, compared by task id, 2026-10-30), so no live
instance exists, as planning found.

**Readers of the backlog states.**

| Reader | Uses | Must treat landed work differently |
|---|---|---|
| `work next` (`cmd/work.rs`) | all states, text and `--json` | Yes: list a `landed` state with the command, never `ready` |
| `work claim` (`claim_on`) | its own check of open branches | Yes: refuse, name the branch and the command |
| `orient` (`hooks/orient.rs` `tasks_line`) | `counts_line` and the first `Ready` entry | Follows from the state: a landed task is no longer the suggested next task; the count line shows `landed N` when non-zero |
| `status` (`status.rs` `render_derived`) | `counts_line`, active, ready, held lists | Follows from the state; adds a `landed:` line with the command |
| `estimate outcomes` | does not read the backlog | No |
| `work start` | own-branch context (`other_branches`) | No: it starts a claimed branch; `landed` there already means open claims only |

**How `landed` judges the cases.**

- Merge commit landing: the tip is an ancestor of the target and off its
  first-parent line, so landed.
- Squash or rebase landing: every commit is patch-equivalent on the target
  (`git cherry`), so landed; a range holding a merge commit is never proven
  this way.
- Fast-forward landing or a fresh claim: the tip is on the first-parent
  line, so it is not landed (indistinguishable from a claim not started).
  This stays as it is; a fast-forward landing is not detected.
- A branch carried to another line: judged only against the task's own
  target; a branch merged into a different line is not landed for this task.
- Unproven (an unreadable range): not landed, so the task stays ready, as
  before.

**Record-only branch.** `landed` cannot tell a branch that only filed or
amended the record. The chosen test: the branch's own commits (the
first-parent chain from its tip down to the commit where it left the
target's first-parent line, skipping merge commits) change no path other
than the task's own record file. Such a branch does not make the task
`landed`. A branch whose commits cannot be read to the end is not counted
as landed work, the same unproven rule.

**Scope.** `State::Landed` in `readiness.rs` (only a task that would be
`Ready` becomes `Landed`; a claim, hold or dependency keeps its state),
`Entry::landed_branches` and `landed_branch_names`, `landed_status_command`;
`work next` text and `--json`; `claim_on` refusal; `status` line; `orient`
and `counts_line` follow the new state. Nothing changes a status. The other
drift classes stay with TSK-1042. Limits: a fast-forward landing is not
detected; a stacked branch's predecessor commits count as its work.
