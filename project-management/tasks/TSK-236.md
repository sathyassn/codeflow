# TSK-236: A project can configure design authority

## Description

Issue 43: a project cannot say who holds design authority. Only the first
line of the catalog's design owner seat designs; a later line is a
"fallback with reduced assurance" and designs only through a per-task
`OPERATOR_OVERRIDE`; no duty holds a same-family design approval; and an
extra family cannot be a standing reviewer for an area. This task builds
recommendation B of the design (Fable, 2026-10-03) with the operator's
decisions of 2026-10-04 (D1 same family only, D2 a separate opt-in
`design-approval` duty, D3 standing reviews in schema 2, D4 the fallback
label dropped only for a designated line, D5 CodeFlow's own file later).
`.codeflow/model-selection.json` schema 2 gains `design_authority` and
`standing_reviews`; `codeflow models resolve` gains the engine-owned
`design-approval` duty and `--area`; doctor prints both blocks.

Interfaces: the schema 2 file format, `models resolve --duty
design-approval`, `--area`, and `ResolveRequest.area` in the core crate.
The design-authority block confers authority only as committed at the
merge-base of `HEAD` and the task's integration target, read on the
task's own branch after the planning anchor rule `codeflow work start`
applies: a task already on the anchor must declare the same target there,
and a standalone record arriving with its own pull request is judged at
the head. The five protections hold: one accountable designated
line with fallbacks labelled; authority from a committed record, never the
working tree or a caller string; a same-family approval never counts as
the independent review; an extra family never votes silently; repository
content cannot add a selector, command, family or designation. Non-goals:
another family as a standing designer (still the task override), any
change to `routing-policy.json`, and CodeFlow's own selection file (D5).

## Acceptance Criteria

- AC-1 When a fresh project commits a schema 2 block naming the design owner seat's second line `co-owner` on the task's integration target, `codeflow models resolve --duty design --task <id> --host claude-code` with the first line excluded returns the co-owner with no override, `reduced_assurance` false and a limitation naming the project designation and where it was committed; a working-tree or task-branch-only block confers nothing and the result says why, as does a block reached by rewriting the task's declared target, while a standalone task reads the block its own target carries (`a_fresh_project_resolves_design_to_its_committed_co_owner` in `init_e2e.rs`; `a_committed_co_owner_designs_without_an_override`, `a_block_off_the_integration_target_confers_nothing`, `a_rewritten_task_target_cannot_borrow_another_lines_authority` and `a_standalone_task_reads_only_its_targets_committed_block` in `models_design_authority.rs`) (journey)
- AC-2 `--duty design-approval` returns the committed co-owner as a required participant labelled "same-family design approval; not the independent review", a consultant as advisory; with no block it returns one optional open `design-approval` gap, `is_open()` false and exit 0 (`design_approval_is_its_own_duty_and_optional_when_unconfigured`; `design_approval_is_a_separate_same_family_duty_never_the_independent_review`).
- AC-3 `--duty unit-review --author claude --area design` with a `standing_reviews` entry returns the catalog's extra-family participant as a required participant with the "standing assignment" disposition; without `--area`, or with another area, the output equals the output with no project file (`a_standing_review_applies_to_its_area_only`; `a_standing_review_adds_the_catalog_participant_only_for_its_area`).
- AC-4 Each invalid block (a line the seat does not list, another family, owner not the first line, a line without an active designated or fully qualified version, an unknown field, a duplicate key, an invalid standing review) rejects the whole file: `models resolve` exits 2 for every duty and `codeflow doctor --check model-bindings` fails, which blocks preflight (`an_invalid_block_rejects_the_whole_file`; `each_invalid_block_rejects_the_whole_file`; `a_line_without_an_active_designated_version_cannot_hold_design_authority`; `doctor_prints_design_authority_and_fails_an_invalid_block`).
- AC-5 With no project file, and with a schema 1 file, every managed-catalog duty resolution for every host, author and trigger set is byte-identical to the engine before this change (`managed_resolutions_without_a_schema_two_block_match_the_prior_engine` against the baseline recorded from main 447455ca5).
- AC-6 An `OPERATOR_OVERRIDE` naming another family still fills design with a schema 2 block present, and the same route without the anchored record is refused (`another_family_still_needs_the_task_override`).
- AC-7 Contract tests pin "A same-family design approval and a cross-family review are separate duties; when both are configured, both are required." in the design routing section and cf-design's revision reference, and no catalog rule or designation calls the later line a design fallback without "otherwise" (`design_approval_and_cross_family_review_stay_separate_duties`).
