# TSK-250: Work start accepts a reviewed unlanded predecessor

## Description

<!-- One paragraph: the outcome/change, why it is needed, and its bounded scope.
     Name a non-goal when omission would otherwise be ambiguous.
     Review-relevant scope, interfaces and recovery notes go here: the
     public contracts or boundaries this task changes, and how to recover
     from an irreversible step, when a reviewer needs them. -->

`codeflow work start <task> --on TSK-NNN@<sha>` is the sanctioned way to build on a reviewed predecessor that has not landed, and it always refuses on a real repository. `crates/codeflow-cli/src/cmd/work.rs` asks `gh pr view --json headRepository`, which returns only `id` and `name`, then reads `headRepository.nameWithOwner` (line 335) and compares it with the repository's short name, so the identity check fails for every pull request; the tests in `work_cli.rs` (lines 80 and 619) fake a `nameWithOwner` field gh never sends. Second, the review check needs the pull request's tip to equal the pin and its Reviews section to name that exact revision, but a task's acceptance completion is its last commit, made after the reviewed head, so a completed predecessor's tip is never named reviewed (PR 57: reviewed 316c7e8f7, tip af9fec717 adds only the TSK-225 acceptance block). Found while starting TSK-247 on PR 57. This task makes the identity check read fields gh returns (owner login and name) and compare both, and accepts a pin at the tip when the Reviews section approves a revision R that is an ancestor of the tip and every commit from R to the tip changes only the predecessor task's own record. Non-goal: accepting any other post-review change.

- AC-1 When the fake `gh pr view` returns the fields gh really returns (`headRepository` with `id` and `name`, `headRepositoryOwner` with `login`) for a same-repository pull request whose tip equals the pin and whose Reviews section approves the pin, `work start --on` accepts it; a different owner, a different name or a cross-repository pull request is refused (`work_cli`). Fails on main.
- AC-2 When the Reviews section approves revision R, R is an ancestor of the pinned tip, and every commit from R to the tip changes only the predecessor task's own record file, `work start --on` accepts the pin; when any commit in that span changes another file, or R is not an ancestor, it is refused naming the revision (`work_cli`). Fails on main for the accepted case.
- AC-3 A sweep of every `gh ... --json` field the CLI reads finds no other field gh does not return; the result is recorded in the PR (review evidence).
