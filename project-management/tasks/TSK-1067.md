# TSK-1067: The exec guard refuses an awk program that writes an enforcement path

## Description

Source: the TSK-397 builder (PR 331), 2026-10-29, outside that task's
outcome. An `awk` program can write a file or run a command itself, so
the shell sees no redirection: `print > "path"`, `print >> "path"`,
`print | "cmd"`, `system("cmd")` and `"cmd" | getline`. exec-guard
judges inline code only for the interpreter families `python`, `node`,
`nodejs`, `perl` and `ruby`
(`crates/codeflow-core/src/security/outward.rs:1391-1406`), and treats
`awk` only as a reader of files for secret reads
(`crates/codeflow-core/src/security/interpreter.rs:31`). The builder
reported that git-guard refuses such a program when the path is an
enforcement path; that paired result is not reproduced yet, and AC-1
establishes it.

Scope: the bounded class of inline program sources that can hide an
enforcement-path write from the guards, with awk as the demonstrated
case. The task reads what program text visible on the command line
spells literally (output targets, `system()` commands, command pipes).
It does not read program files, and it does not model every effect of
arbitrary interpreter code, and it keeps the residual boundary the
guard documents (`crates/codeflow-core/src/security/arguments.rs:66-72`,
operator decision 2026-10-15): code in a file the guard does not read,
and a path the program builds at run time, stay past the guard, with
the OS sandbox as the backstop. Changing that boundary is an operator
decision. Program text the shell fills in at run time is a separate
case: exec-guard already refuses it for the other interpreters wherever
a checkout is reachable (`security/arguments.rs:700-720`), and awk takes
the same rule; it is never weakened to a residual.

Overlap, checked at line tip `35672e8bd`:

- TSK-1002 (PR 346; its record is not on the line yet) owns interpreter
  arguments, inline-code path handling for the five families and secret
  reads. It does not read awk's output grammar.
- TSK-1052 owns a run of a file written earlier on the same line
  (`TSK-1052.md:62`), such as `awk 'BEGIN{system("run")}'` after a
  modelled write of `run`. A direct `system()` call or command pipe that
  runs a writer on an enforcement path needs no earlier write, so it is
  this task's.
- TSK-1053 owns runner directories.
- TSK-378 owns the launchers outside the family list (`TSK-378.md:22`)
  and Perl embedded in `parallel` replacement strings (`:104`). This
  task adds no launcher and no `parallel` form. Both tasks change
  `interpreter_family` in `outward.rs`, so whichever lands second builds
  on the other's family list.
- TSK-342 owns writing programs' output options and the nested `sed`
  script reading, which covers `sed`'s own `w` command.
- TSK-413 owns inline Python git-call expressions.

None covers an awk program that writes or runs a writer, so this is its
own task.

## Outcome

After this merges, an agent cannot write an enforcement path through a literal output target, `system()` command or command pipe in `awk` program text visible on the command line, on a route where exec-guard judges the line; awk program text the shell fills in is refused wherever a checkout is reachable, as it is for the other interpreters; and the guards' stated residual boundary is unchanged.

- tests: exec-guard tests beside the TSK-1002 refusal tests, and one table run through both guards

## Acceptance Criteria

- AC-1 Before any change, the builder shall record, on this line's built binary, the actual exec-guard and git-guard verdict and rule for `awk 'BEGIN { print "x" > ".claude/settings.json" }'` and for every row of AC-2 to AC-4, and shall record: the dialects (`awk`, `gawk`, `mawk`, `nawk`, `busybox awk`, the macOS one-true-awk) with their versions; the program sources each dialect accepts (inline, `-f file`, `-e` or `--source` text, `--include` or `@include`), confirmed against each dialect's manual; the in-place extension mode `gawk -i inplace`, which rewrites its operand files; the write and run forms (`>`, `>>`, `print | "cmd"`, `system("cmd")`, `"cmd" | getline`); which harness routes run exec-guard without git-guard; and any other tool with an inline program that can write a file or run a command and that neither guard reads today; evidence: the Findings section, committed before the first code change.
- AC-2 exec-guard shall refuse, under `git.hook_integrity`, an awk program whose text is visible on the command line (the inline program argument, and `-e` or `--source` text in the dialects AC-1 finds accept it) when that text has a string-literal output target (`>`, `>>`) naming an enforcement path, or a string-literal `system()`, `print |` or `| getline` command that is a command line exec-guard refuses when run directly (such as `tee` or `sed -i` onto an enforcement path); and shall refuse `gawk -i inplace` with an enforcement path as an operand, whatever the program's source; for each dialect AC-1 finds valid; evidence: one exec-guard test per dialect, visible source and form, each marked from AC-1's baseline as newly refused (allowed before the change, so failing before) or already refused (passing before and after).
- AC-3 The existing rule for unresolved program text and the residual boundary shall hold, each case with one expected verdict stated in its test: (a) program text the shell fills in at run time (`awk "$P"`, `awk "$UNSET"`, `awk "$(cat p)"`) takes the rule exec-guard already applies to an interpreter call with an unresolved expansion (`security/outward.rs:383`, `security/arguments.rs:700-720`): refuse under `git.hook_integrity` with the cannot-verify finding ("cannot verify interpreter expansion ... where a checkout or enforcement path is reachable") whenever a checkout root is in the protected-name set, the protected-name set is unknown, or a directory the call runs in opens a git repository, whether or not the command line spells a protected path;
