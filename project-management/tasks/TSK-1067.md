# TSK-1067: The exec guard refuses an awk program that writes an enforcement path

## Description

Source: the TSK-397 builder (PR 331), 2026-10-29, outside that task's
outcome. An `awk` program can write a file itself, with `print > "path"`,
`print >> "path"` or `printf ... | "tee path"`, so the shell sees no
redirection. git-guard refuses such a program when the path is an
enforcement path, but exec-guard allows it: the exec guard judges inline
code only for the interpreter families `python`, `node`, `nodejs`,
`perl` and `ruby` (`crates/codeflow-core/src/security/outward.rs:1391-1406`),
and treats `awk` only as a reader of files for secret reads
(`crates/codeflow-core/src/security/interpreter.rs:31`). The two guards
therefore disagree on the same line, and a route that runs exec-guard
without git-guard would let the write through.

Coverage checked before filing (line tip `35672e8bd`): TSK-1002 (PR 346)
covers interpreter arguments, inline code and secret reads, not awk
program writes. TSK-1052 covers a run of a file written earlier on the
line, including `awk 'BEGIN{system("run")}'` (its Fable review 06 row),
which is a program run, not a write. TSK-1053 covers runner directories.
None covers an awk program that writes, so this is its own task.

Non-goals: `awk system()` and pipes into a program that runs a written
file (TSK-1052); runner directories (TSK-1053).

## Outcome

After this merges, an agent cannot write an enforcement path through an `awk` program's own output, whichever guard judges the line.

## Deliverables

- investigation findings: a `## Findings` section in this record
- the exec guard's reading of awk programs: `crates/codeflow-core/src/security/outward.rs` and `crates/codeflow-core/src/security/interpreter.rs`, reusing git-guard's awk reading where it exists (`crates/codeflow-core/src/hooks/git_guard.rs`)
- tests: exec-guard tests beside the TSK-1002 refusal tests, and a shared table run through both guards
- release note: `changelog.d/TSK-1067.md`

## Acceptance Criteria

- AC-1 Before any change, the builder shall reproduce, on this line's built binary, git-guard refusing and exec-guard allowing `awk 'BEGIN { print "x" > ".claude/settings.json" }'`, and shall record: the awk spellings (`awk`, `gawk`, `mawk`, `nawk`, `busybox awk`, a `g`-prefixed GNU name), the program sources (inline, `-f`, `--source`, `-i inplace`), the write forms (`>`, `>>`, `|` into a writer, `-i inplace` on an operand), how git-guard reads each today, and which harness routes run exec-guard without git-guard; evidence: the Findings section, committed before the first code change.
- AC-2 exec-guard shall refuse an awk program whose own output writes an enforcement path, for each spelling and write form AC-1 lists; evidence: exec-guard tests for each, allowed at `35672e8bd` (failing before) and refused after.
- AC-3 An awk program exec-guard cannot read (a `-f` file it cannot judge, a program from a variable, an output target that is not a string literal) shall get the unknown-target rule the exec guard already applies to other interpreters' inline code; evidence: exec-guard tests for each form.
- AC-4 Ordinary awk lines shall keep their verdict: `awk '{print $1}' data.txt`, `awk 'BEGIN { print "x" > "out.txt" }'` in a public tree and `gawk -F, '{print $2}' notes.csv` allow; evidence: control tests passing before and after.
- AC-5 git-guard and exec-guard shall give the same verdict class on every row of AC-2 to AC-4; evidence: one test table run through both guards.
