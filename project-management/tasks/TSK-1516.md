# TSK-1516: validate --docs on ten thousand records is back within its read budget

## Description

Main's full gate is red on the read benchmark (`read_commands_on_ten_thousand_records_stay_within_their_budgets`, `crates/codeflow-cli/tests/read_benchmark.rs:551`). Its `validate --docs` latency ratio is over budget: the budget is twice the macOS baseline ratio (`read_benchmark.rs:829`), and that baseline is 6.38 (`read_benchmark_baseline-macos.json:24`), so the budget is 12.76. The two red gates measured 14.11 and 14.14. Filed by coord/records on 2026-11-16 on the Director's ruling, from coord/ci's diagnosis of the same day (workspace `coordination/coordinators/parallel/notes/read-benchmark-diagnosis-2026-11-16.md`, commit `e433a1b1c`).

The slowdown is real and does not come from host load. Measured as CPU time, which load barely changes, `validate --docs` on `main` at `ec8d5c1ab3` cost 4.10 to 4.45 s against 0.30 to 0.35 s for the calibration, on a 10,000-task fixture of 48,541,777 record bytes. That is a CPU ratio of about 13.9 (4.3 s over 0.31 s). Host load decides only whether a given wall-clock run goes red: on 2026-11-11 the same command passed when run alone, at 11.85. Two code costs added since the baseline account for most of the excess:

- The ledger-citation pass, `lint_ledger_citations` (`crates/codeflow-core/src/validate/docs.rs:181-204`), added by TSK-422 AC-8 in `de8e4102d7`. It lists every task, epic and ADR record again, adds another read of each one, and runs the `ledger_citation` regex line by line until the first citation in that file (`docs.rs:190-201`). On the measured fixture this makes five reads of each task record. It takes about 21 to 28% of the run (0.9 to 1.2 s CPU). The check is intended; this way of running it is the costly part.
- The full-path sort, from TSK-1023 in `9071530b71`. `task_record_files` (`crates/codeflow-core/src/workgraph/layout.rs:239`), `direct_markdown_files` (`layout.rs:263`) and `collect_record_files` (`crates/codeflow-cli/src/cmd/validate.rs:291`) sort with `compare_id_paths` (`crates/codeflow-core/src/ids/order.rs:61`), which walks every component of the absolute path on each comparison. It takes about 10 to 14% of the sampled run. The id order is intended; its cost is not.

Without the ledger pass the CPU ratio would be about 10.0 to 10.9, and without the sort cost as well about 8.5 to 9.5. The proposed fixes, which keep every check:

1. Fold the ledger-citation scan into a read that already happens: the per-task read in `parse_task_graph_record` (`docs.rs:744-761`, under `lint_tasks` at `docs.rs:726`), the epic read under `lint_epics` (`docs.rs:597`), and the ADR read under `lint_adrs` (`docs.rs:535`), so the separate listing, open and read go away. The regex may run once over the whole text, with the line number found only on a hit. The fold must keep the check's present behaviour: it scans a record whose front matter does not parse, although those readers return early on a parse failure (`docs.rs:550-556`, `:616-620`, `:761-766`); it skips a record that cannot be read as UTF-8 text without a finding (`docs.rs:188-189`); it reports only the first citation in a file; and its findings come last in the report, tasks then epics then ADRs (`docs.rs:133-138`, `:184-186`), so findings collected during the earlier reads are held and emitted in that place.
2. Sort by a precomputed key that gives exactly the order `compare_id_paths` gives today (`ids/order.rs:61-78`), including its byte-order tie-break and lists that mix flat and epic-local task paths with different parents (`layout.rs:230-239`); a key of the record id alone is not equivalent there. Comparing file names only is valid where every path in the list shares its parent. The second sort in `task_record_files` is redundant when there are no epic-local task folders.

A further option, if those two are not enough: `validate_workgraph` reads each record for its identity (`crates/codeflow-core/src/validate/mod.rs:157-159`) and again inside the validator.

Related work:

- TSK-1279 AC-18 (todo, on the local branch `task/TSK-1279-heavy-runs-keep-the-caller-s-job-cap-and-each-ta`, commit `fd5a28db16`) changes how the benchmark measures latency (CPU time over a reference of the same kinds of work). It is related but does not cover this: it changes the unit and keeps the allowed slowdown, so the cost stays over.
- TSK-1385 ("The read benchmark tells a load-skewed latency miss from a regression") covers load skew, not a real slowdown.

Non-goals: no change to either read benchmark baseline file (`read_benchmark_baseline-macos.json`, `read_benchmark_baseline-linux.json`) or to the budgets they set; no change to how the benchmark measures (TSK-1279 AC-18) or treats load (TSK-1385); no check dropped, narrowed or weakened.

- AC-2 When the release read benchmark (`read_benchmark.rs:551`, run in release mode) runs on macOS against the unchanged baseline, the `validate --docs` latency ratio shall be under 12.76. Evidence: the measured ratio, wall time, calibration and host load (1, 5 and 15 minute) in the pull request, and the benchmark's passing result for `validate --docs`. Evidence: the commands, at least three runs each for base and head with each run's command and calibration CPU times and the host load, the medians and ratios, and the fixture's task count and record bytes, in the pull request.
