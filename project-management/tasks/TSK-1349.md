# TSK-1349: The guards refuse the flags that skip git hooks

## Description

Issue #619. git-guard lets `--no-verify` through on `git commit`, `git merge` and `git push`, and the short form `git commit -n`, so an agent can skip the commit-msg, pre-commit (with its secret scan), pre-merge-commit and pre-push hooks with no refusal and no warning. The managed rules forbid it (`.codeflow/rules/git-rules.md`: "never bypass (`--no-verify`, editing hooks, exporting gate tokens)"), and `git.hook_integrity` already refuses the configuration override with the same effect (`-c core.hooksPath=/dev/null`).

Reproduced on the beta 4.0.0 (source 678d3fa48) on 2026-11-05 by feeding PreToolUse payloads to `codeflow hook git-guard --contract 3` and `codeflow hook exec-guard --contract 3`, with nothing executed: `commit --no-verify`, `commit -n` and `merge --no-verify` exit 0 under both guards; `push --no-verify` exits 0 under git-guard and is refused by exec-guard only under `security.outward_actions`; `-c core.hooksPath=/dev/null commit` is refused by git-guard under `git.hook_integrity` (the control).

This is a security floor gap and goes first in the guards order (EPC-029 and EPC-051). Non-goals: the general shell parser (TSK-1073), which this task uses as it stands; checks after the fact at pre-push or in CI, which a skipped pre-push cannot provide.

## Outcome

After this merges, an agent cannot skip a git hook through a git flag: the guards refuse every skip-hooks form on every branch and name the sanctioned path, which is to fix the cause the hook reports.

## Deliverables

- the refusal: `crates/codeflow-core/src/hooks/git_guard.rs` (or the module that owns `git.hook_integrity`)
- the tests: the git-guard payload tests in `crates/codeflow-core/tests/` and a CLI test
- the rule text: `.codeflow/rules/git-rules.md` "Enforcement" names the flags the guard refuses, if it does not already
- release note: `changelog.d/TSK-1349.md`

## Acceptance Criteria

- AC-1 Before any change, the builder shall list every git subcommand option that skips a hook, from git's own documentation for the git version the tests run (at least `commit --no-verify` and `-n`, `merge --no-verify`, `pull --no-verify`, `push --no-verify`, `rebase --no-verify`, `am --no-verify`), with the hook each one skips, and reproduce the issue's payloads on the line tip; evidence: the list and the payload output in `## Findings`.
- AC-2 git-guard shall refuse each option of AC-1 under `git.hook_integrity`, on a protected and an unprotected branch, in a linked worktree and with `git -C`, including the forms git itself accepts: an abbreviated long option (`--no-verif`), `-n` inside a cluster of short options (`commit -qn`, `commit -anm msg`), and the option after `--` only where git still reads it as an option; `-n` on a subcommand where it means something else (`push -n` is a dry run, `merge -n` is no-stat) shall not be refused for that reason; evidence: one payload test per form, each failing before the change and passing after. (serves EPC-022 AC-5)
- AC-3 When the guard cannot tell whether an option is effective, for example `--no-verify` followed by `--verify`, it shall refuse, failing closed; evidence: payload tests for the mixed forms.
- AC-4 The same refusal shall hold when the git command is wrapped in a form the guards already unwrap (`sh -c`, `bash -c`, `env`, `hc run --`, a `;` or `&&` list), and exec-guard shall not admit a form git-guard refuses; evidence: payload tests through each wrapper the guards unwrap today, run against both hooks.
- AC-5 The refusal message shall name the rule, the flag and the sanctioned path (fix the cause the hook reports; never skip it), and shall carry no project value; evidence: a CLI test of the message text.
- AC-6 (journey) With the installed build, a Claude Code session's Bash call of `git commit --no-verify` in a scratch adopter project shall be refused before git runs, and the same call without the flag shall run its hooks; evidence: the journey output.
- AC-7 git-guard and exec-guard shall refuse, under `git.hook_integrity`, a shell write to any path under `.github/workflows/` or `.github/actions/` (a local action runs as workflow code with the workflow's token), new or edited, with any name or extension, and edit-guard shall refuse the same through the file tools, matched after normalising letter case, separators, `..`, symbolic links and hard links (making one to a workflow, or writing through one); a path the guard cannot resolve shall refuse; reading a workflow and writing elsewhere (a file in the project, `$TMPDIR`, build output) shall stay admitted on both hooks; each sibling the sweep in `## Findings` names as changed shall get the same; evidence: payload tests per form on both hooks, failing before the change and passing after. (added 2026-11-05 by Director approval, relayed by coord/ci: TSK-1239's `codeflow-admission.yml` was written past a guard that protected one workflow file)

### Options that skip a hook (git 2.53.0)

Read from the man pages of the git the tests run (`git version 2.53.0`, Homebrew): every `git-*.1` page was searched for `--no-verify`, `bypass`, `skip` or `suppress` near `hook`, and `--no-post-rewrite`. git-config(1) names one configuration that disables hooks, `core.hooksPath`.

|---|---|---|---|
| `commit` | `--no-verify` | `-n` | pre-commit, commit-msg |

### Security review at `40ac016a2` (Grok, CHANGES)

The review found three high findings, fixed in this pull request, and two medium ones, tracked once.

| Finding | Before | Fix |
|---|---|---|
| 1. A separate `export GIT_CONFIG_GLOBAL=<file>`, or `GIT_CONFIG_COUNT` with `GIT_CONFIG_KEY_0=include.path`, admitted by both guards, then a plain `git commit` runs no hook | git-guard refused only a `GIT_CONFIG_KEY_*` or `GIT_CONFIG_PARAMETERS` value spelling `core.hooksPath`; exec-guard had no check | both guards refuse, under `git.hook_integrity`, any setting of `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_PARAMETERS` or `GIT_CONFIG_KEY_<n>`, whatever the value, on the line that sets it: an assignment prefix, `env`, `export`, the declare family, `command`, or a bare `export NAME` |
| 2. `git -c include.path=<file> commit` admitted by exec-guard | git-guard refused it under `git.policy_authority`; exec-guard admitted it | exec-guard refuses `-c` and `--config-env` for `include.path` and `includeIf.<condition>.path` under `git.hook_integrity`, without reading the file |
| 3. `export GIT_CONFIG_KEY_0=core.hooksPath` admitted by exec-guard | git-guard alone refused it | the fix of finding 1, in exec-guard too |

Why this design: the guard judges one tool call's text and cannot see the shell environment an earlier call left, nor the contents of a file git will read later. A check that reads the value or the file decides on input the attacker controls after the check. Refusing the setting itself, whatever its value, is the fail-closed form: it binds the decision to the text the guard sees. The one cost is that a session can no longer set these variables in-session for an ordinary purpose; exec-guard already refused the same-line forms (unclassified `GIT_CONFIG_COUNT`), and a host or test harness that sets them in a process environment is not affected.

Payloads, debug build of this branch on the merged line tip `d9bf657be`, judged only: `crates/codeflow-cli/tests/hooks_cli/hook_skip.rs` `both_guards_refuse_configuration_sources_and_includes` failed before the guard change, with 45 of its 48 cases (24 lines, each judged by both guards) admitted or refused under another rule, and passes after. `a_configuration_source_skips_the_hooks_of_a_later_plain_commit` drives git 2.53: a plain commit runs the pre-commit hook; the same commit with `GIT_CONFIG_GLOBAL`, or with an include through `GIT_CONFIG_COUNT`, naming a file that sets `core.hooksPath` to an empty directory, runs none. `neither_guard_refuses_a_configuration_variable_it_does_not_set` shows naming or reading the variables, and `-c user.email=…`, stay admitted. The unit test `test_b4_git_config_env_injection` asserted that `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=user.email … git status` was admitted by git-guard; it now asserts the refusal, since exec-guard already refused that line.

Tracked once, not fixed here:

- Finding 4 (medium): `hc run -- git commit --no-verify` is admitted by both guards. Owner: TSK-1344 AC-7, which covers `hc run` with and without `--no-verify`. Revisit: when TSK-1344 lands.
- Finding 5 (medium): an alias from a configuration file that expands to a hook skip is resolved only by git-guard; exec-guard reads aliases only from `-c alias.<name>=…` on the line. The installed pair still refuses it, because git-guard reads the alias. Revisit: when exec-guard gets a reader for aliases stored in configuration, or when exec-guard is installed without git-guard.
- Finding 6 (medium, track once, found in the AC-7 sweep): the Codex `cf-guard` profile (`assets/base/codex/config.toml`) makes only `.github/workflows/codeflow-ci.yml` read-only, so Codex's sandbox alone would let another workflow or action file be written. The guards refuse those writes in a Codex session, through `.codex/hooks.json`, so the gap is defence in depth. The fix sets `.github/workflows` and `.github/actions` to `"read"` in the asset, the reference sample and this repository's `.codex/config.toml` together; that last file is an enforcement path an agent session cannot write. Revisit: an operator-applied patch, or the next change that moves this repository's `.codex/config.toml`.

### Security delta at `ed8387095` (Grok, CHANGES)

| Finding | Before | Fix |
|---|---|---|
| A. `builtin export GIT_CONFIG_GLOBAL=…` and `builtin declare -x GIT_CONFIG_KEY_0=core.hooksPath` admitted by both guards | the configuration-source scan looked for `export` or the declare family as the first word, so `builtin`, and an `exec`, `nohup` or `env` in front of `env`, hid it | `git_config_source_assignment` finds the program through `strip_launchers`, as every other check does, and reads every assignment in front of it; a command whose program cannot be found (`env -S`, assignments only) is read for any such assignment, so it fails closed |
| B. `git -ccore.hooksPath=/dev/null commit` and `git -cinclude.path=<file> commit`, the entry attached to `-c` | the scanners matched only a word that is exactly `-c`; most attached forms were refused only because the hook-skip reader took the `n` in `/dev/null` or `include` for a clustered `-n` | one reader, `git_config_global`, reads `-c <entry>`, `-c<entry>`, `--config-env <entry>` and `--config-env=<entry>` for the hooks-path scan, the include scan, the `-c alias.<name>` lookup and the alias configuration list; the startup-setting check in `security/startup.rs` reads the attached form too |

Git 2.53 rejects an attached `-c<entry>` as an unknown option (a scratch-repository probe printed `unknown option: -cuser.name=…`), so finding B does not take effect with the git the tests run; the guards refuse it so a git that accepts it cannot set a key past them. Keys are matched without regard to case, as git reads them: `-c CORE.hookspath=…` sets the hooks path (the probe read `-c USER.Name=…` as `user.name`).

Payloads, debug build, judged only: `both_guards_refuse_configuration_sources_and_includes` gained 63 lines (126 cases): the `builtin`, `command`, `exec`, `nohup`, `env`, `env -S`, `eval` and `sh -c` wrappers around an export and around a git call with a spaced or attached `-c`, attached `--config-env=`, `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_COUNT`/`KEY_<n>`, and mixed-case keys. The test now also requires the refusal to name the configuration it reads, so a refusal for a clustered `-n` does not count. On `ed8387095` 70 of the 126 cases failed; after the fix all pass. git-guard refuses `eval 'git -cinclude.path=… commit'` before and after because git rejects the configuration it is asked to verify, a fail-closed refusal the test accepts for includes on git-guard.

exec-guard's shell-write check now runs git-guard's two passes in git-guard's order (`line_integrity_write`): the pass that resolves filled-in operands (`expanded_integrity`) for a line that has them, then each segment as written. It runs after exec-guard's own checks and only on a line none of them refuses, so a refused line keeps its own finding (an interpreter call names the paths it is given). The whole `hooks_cli` suite showed that the earlier per-segment reading refused a line git-guard admits (`D=src; printf x > "$D/settings.json"`), and that two interpreter calls (`xargs python3 edit.py`, `find … -execdir python3`) were refused with the write finding in place of the interpreter's; all three now pass. Two expectations change because exec-guard now gives git-guard's refusal, which the installed pair already gave: `EDITOR='rm -rf .claude' git config --get user.name` (`repair3_runner_configuration_and_environment_sources`), and the run-time deletions git-guard refuses for a word it cannot verify in a writer (`run_time_project_deletions_refuse_only_when_tightened`, which still requires the strict rule's own finding when tightened).

Findings 4 and 5 stay tracked as above.

Where git-guard already refused a line, exec-guard now refuses it too, which is AC-4. Besides the enforcement writes above, one such line found by the unit suite is `cd build && rm -rf *` where `build` does not exist: git-guard refused it at the line tip because the glob's directory cannot be resolved, and exec-guard now refuses it too. `a_composed_deletion_is_refused_as_its_rm_equivalent` now judges the project deletions in a project that holds `build/`, `dist/` and `target/`: each is admitted, or refused only with git-guard's own write finding (a `cd` inside a loop, such as `for i in 1; do cd build && rm -rf *; done`, after which `*` could name `.codeflow/policy.json`); none is a dangerous deletion. A command the catastrophic floor already refuses (`rm -rf /`) keeps that one finding. The write check runs inside one repository snapshot (`RepoFactsScope`), as git-guard's own evaluation does. On a deletion line in this repository's debug build, with 108 registered worktrees, exec-guard took 1.9 s against 1.0 s for the line's binary; git-guard takes 1.6 s on the same line.

The change:

- The action table protects `Edit(/.github/workflows/**)` and `Edit(/.github/actions/**)`, so the resolved check (links, `..`, case) and edit-guard cover every file there; the design reference copy in `docs/verification/evidence/permission-presets/actions.json` and the shipped presets in `assets/base/settings/` follow it.
- git-guard's text floor, its whole-directory list and its integrity prefixes name `.github/workflows` and `.github/actions` as directories.
- A hard link is judged on both sides: `ln` without `-s`, and `cp -l` or `--link`, judge their sources as written, and a write to an existing file with more than one link refuses when its inode is a protected file's (`hard_link_to_protected` in `crates/codeflow-core/src/hooks/edit_guard.rs`). A protected directory too large to walk, or unreadable, counts as holding the file.
- exec-guard runs git-guard's writer checks on every segment (`line_integrity_write`), so it refuses the shell writes git-guard refuses. Before, it read no shell writes of its own.
- `codeflow ci`'s workflow-change warning lists every path the range changes under `.github/workflows/` and `.github/actions/`, not only the managed workflows, and warns when it cannot list them. `ci_warns_on_a_new_unmanaged_workflow` in `crates/codeflow-cli/tests/ci_cli.rs` failed before and passes after.
- Tests: `crates/codeflow-cli/tests/hooks_cli/workflow_paths.rs`. Its refusal tests (shell writes on both hooks; tool writes through edit-guard) failed before, with 41 of 42 shell cases admitted or refused under another rule at the line's guard sources, and pass after; its admission test passes before and after.
