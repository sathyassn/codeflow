# TSK-359: An integration push reuses the hosted verdict of an identical pull request tree

## Description

Source: the gate speed discovery of 2026-10-17, ranked change 7, and
`scripts/ci-reuse.py`.

A push to `main` already reuses a pull request run's verdict when the
pushed merge commit has exactly the tree of the pull request head and every
condition in `scripts/ci-reuse.py` holds (exact tree, one merged pull
request, ancestry, unchanged cache inputs, the present part's apt cache,
and a fully successful pull request run). The operator approved that reuse
on 2026-10-11, for `main` only; condition 1 makes every other push run
every job. Once TSK-358 runs the gate jobs on ready pull requests into
integration lines, the push that lands such a pull request runs the same
jobs a second time on the same tree, about 157 runner minutes and 31
minutes of wall time per landing.

Outcome: when evidence shows such a pair, an integration line push reuses
the verdict of the pull request run that tested its exact tree, through the
existing mechanism and never from local evidence.

The task starts with evidence: it first finds at least one real pair after
TSK-358 lands (a ready pull request run and the landing push run on one
tree) and records both runs and their timings. If no pair exists, because
landings change the tree (for example a merge of a moved line), the task
records that and closes without a change.

Decisions recorded here:

- Extend `scripts/ci-reuse.py`; do not add a second mechanism.
- Every existing condition stays, with condition 1 extended to
  `refs/heads/integration/**` and condition 4 using the line's previous tip.
- The secret scan, gitleaks canary, security review and CodeQL never reuse.
- Extending reuse beyond `main` is a scope change the operator approved for
  `main` only; this plan carries the operator's 2026-10-17 request for
  faster gates, and the pull request states the extension for the
  operator's confirmation.

Non-goals: reusing local results as hosted evidence, changing the shipped
template, and the cache-priming design. Product surface: this
repository's CI only.

## Deliverables

- the evidence: the first observed pair of runs with links, trees and timings, in the pull request body
- reuse for integration pushes: `scripts/ci-reuse.py` and `scripts/test_ci_reuse.py`
- wiring: `.github/workflows/codeflow-ci.yml` (the `reuse` job and the comment block that lists its scope)

## Acceptance Criteria

- AC-1 The pull request shall cite at least one real pair of a ready pull
  request run and its landing push run on one integration line with equal
  trees, with both runs' durations; with none, the task closes with that
  finding and no change; evidence: run links and `git rev-parse` of both
  trees. (serves EPC-022 AC-56)
- AC-2 A push to an integration line whose commit has the exact tree of a
  merged pull request's head, whose ready pull request run passed every job,
  and which meets every other existing condition shall skip the gate and
  Windows jobs, and its `codeflow gates` and `windows` verdicts shall pass
  and name the reused run; evidence: `scripts/test_ci_reuse.py` cases and
  one hosted push run after landing. (serves EPC-022 AC-56)
- AC-3 Each existing refusal shall still refuse for integration pushes: a
  different tree, no or several merged pull requests, broken ancestry, a
  changed cache input, a missing apt cache, a failed, cancelled or partial
  pull request run, a draft-only run, a different workflow file, and any
  API or git error; evidence: one test per case.
- AC-4 The secret scan, gitleaks canary and security review shall run on
  every integration push as before; evidence: the workflow diff and the
  hosted push run's job list.
- AC-5 (journey) The first landing after this change shall show a ready
  pull request run, then a line push run that reuses it with its verdicts
  naming the reused run; evidence: both run links.
