# TSK-359: An integration push reuses the hosted verdict of an identical pull request tree

## Description

Source: the gate speed discovery of 2026-10-17, ranked change 7, and
`scripts/ci-reuse.py`. Amended after the Codex review of PR 226 (finding
F2).

A push to `main` already reuses a pull request run's verdict when the
pushed merge commit has exactly the tree of the pull request head and the
conditions in `scripts/ci-reuse.py` hold (one merged pull request,
ancestry, unchanged cache inputs, the present part's apt cache, and a fully
successful pull request run). The operator approved that reuse on
2026-10-11 for `main`, and on 2026-10-17 extended it to integration lines.

The existing lookup has a provenance gap that matters once several lines
reuse: it picks the newest successful run by head SHA, event and workflow
path (`scripts/ci-reuse.py` near lines 116 to 144). It does not bind that
run to the merged pull request's number, its base line and base commit, or
the merge tree the run actually tested. Counterexample: head H contains
line A's tip; a pull request for H into A lands with tree H; a newer
successful run for the same H into line B tested merge(H, B), which holds
changes absent from H; the lookup can pick that run and certify A's push.
A retargeted pull request creates the same ambiguity, and a workflow file
changed at the same path is not distinguished.

Once TSK-358 runs the gate jobs on ready pull requests into integration
lines, the push that lands such a pull request runs the same jobs a second
time on the same tree.

Outcome: a line push, and a `main` push, reuse a hosted verdict only from
the run that tested exactly the merged pull request into exactly that
destination, on the exact pushed tree, under the same workflow content and
job contract; anything unproven runs the jobs.

The task starts with evidence: it first finds at least one real pair after
TSK-358 lands (a ready pull request run and the landing push run on one
tree) and records both runs and their timings. If no pair exists, because
landings change the tree (for example a merge of a moved line), the task
records that and closes without a change.

Decisions recorded here:

- Extend `scripts/ci-reuse.py`; do not add a second mechanism. The
  stronger binding applies to `main` pushes as well as line pushes.
- The pull request run records, in its own job output or artifact, the Git
  tree id of the merge it tested and the base commit it merged with. Reuse
  reads those from the run itself, never from text the pull request
  controls.
- The secret scan, gitleaks canary, security review and CodeQL never reuse.
- The required job set is read from the pushed workflow's verdict jobs, so
  jobs added later (for example by PR 224's hosted policy and native
  platform tasks) join the contract instead of being frozen out.

Non-goals: reusing local results as hosted evidence, changing the shipped
template, and the cache-priming design. Product surface: this
repository's CI only.

## Deliverables

- the evidence: the first observed pair of runs with links, trees and timings, in the pull request body
- provenance recording: a step in the pull request jobs of `.github/workflows/codeflow-ci.yml` that records the tested merge tree and base commit
- reuse binding: `scripts/ci-reuse.py` and `scripts/test_ci_reuse.py`
- wiring: the `reuse` job and the comment block that lists its scope in `.github/workflows/codeflow-ci.yml`

## Acceptance Criteria

- AC-1 The pull request shall cite at least one real pair of a ready pull
  request run and its landing push run on one integration line with equal
  trees, with both runs' durations; with none, the task closes with that
  finding and no change; evidence: run links and `git rev-parse` of both
  trees. (serves EPC-022 AC-56)
- AC-2 A push shall reuse a run only when that run is associated with the
  exact merged pull request (by number), its recorded base ref equals the
  pushed line, its recorded tested merge tree equals the pushed commit's
  tree, the workflow file's blob at the run equals the pushed commit's,
  every required verdict job of the pushed workflow concluded success with
  a matching runner image identity, and every existing condition holds;
  then its `codeflow gates` and `windows` verdicts shall pass and name the
  reused run; evidence: `scripts/test_ci_reuse.py` cases and one hosted
  push run after landing. (serves EPC-022 AC-56)
- AC-3 Reuse shall be refused, and every job shall run, for two pull
  requests with the same head and different bases, a retargeted pull
  request, a changed workflow at the same path, a run without recorded
  provenance, a different tree, no or several merged pull requests, broken
  ancestry, a changed cache input, a missing apt cache, a failed,
  cancelled or partial run, a draft-only run, and any API or git error;
  evidence: one test per case.
- AC-4 The secret scan, gitleaks canary and security review shall run on
  every push as before; evidence: the workflow diff and the hosted push
  run's job list.
- AC-5 (journey) The first landing after this change shall show a ready
  pull request run that recorded its tested merge tree, then a line push
  run that reuses it with its verdicts naming the reused run; evidence:
  both run links.
