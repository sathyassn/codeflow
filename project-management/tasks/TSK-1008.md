# TSK-1008: Acceptance evidence names its test or command, and a fix proves it failed before

## Description

Issue #301, filed against CodeFlow 3.1.1 (`48104f48b`). The method asks
that every criterion is evidenced with file:line or a command, and that
every defect fix adds a regression test that fails before the fix and
passes after. The acceptance checker accepts any non-empty text as
evidence (`crates/codeflow-core/src/workgraph/record_text.rs`, the
`<outcome> | <evidence>` parse) and has no notion of a test or a fix;
`acceptance.rs` states it proves structure and binding only. The issue
proposes a deliberate tightening, so it is a feature of this epic.

Outcome: **a `verified` criterion's evidence names a test path that
exists at the reviewed commit, a command with a gate-run id, or a
`manual:` entry that states what was inspected and why no automated test
fits; and a fix carries its regression test with a failing run before
the fix and a passing run at the reviewed commit, or a recorded
`regression: none: <reason>`. Where the default branch's policy turns it
on, a `run:` command is also rerun at the reviewed commit inside an
operating-system sandbox, and the binding fails when its exit status
differs from the one recorded; every other token stays a structure and
existence check.**

Rules:

- New evidence tokens: `test: <repo path>[::<name>]`, `cmd: <command>`
  with a gate-run id, and `manual: <what, where, result; why no test>`.
  A bare `manual: <reason>` is refused.
- A range holding a `fix:` commit, or a task whose `work_type` is `fix`
  or `hotfix`, needs a `regression` field in the acceptance block:
  the test reference, `fails-at: <sha> <run id>` (an ancestor of the
  fix, inside or outside the PR range) and `passes-at: <reviewed sha>
  <run id>`, or `none: <reason>`, which `codeflow ci` prints.
- `codeflow test --only <target>` can record a run at a named sha in the
  gate-runs home so the failing result is attributable. Where that home
  is not readable (hosted CI), `ci` checks the structure only and the
  local completion step checks the results.
- Rules apply only to acceptance blocks first written after the
  activation commit, recorded as `work_records_baseline` is; a
  report-only pass lists active tasks that would fail; `block` comes
  through a reviewed policy change, and new scaffolds write it on.
- Issue #450 adds a rerun. A criterion's evidence may hold a fourth token,
  `run: <command> => exit <code>`, where `<code>` is the exit status the
  command must return at the reviewed sha (`exit 0` for a pass, a nonzero
  code for a planted failure; a journey that needs setup names a committed
  script that plants, runs and cleans up). A `run:` token satisfies AC-1's
  token rule. With the rerun on, `codeflow ci` and `codeflow task status
  <id> complete` run each `run:` command against the reviewed sha and fail
  the binding when the exit status differs from `<code>` or the command
  times out. With it off, or for evidence without a `run:` token, today's
  behaviour holds. Hosted `ci` runs nothing: it checks the token's
  structure only and reports that no result was verified. The security
  contract below governs every run. AC-6 holds the contract. If the
  builder finds the rerun too large for one pull request, it is split out
  as one tracked EPC-024 task that takes AC-6, through the batched epic
  amendment, and is never dropped.

Security contract for the rerun (Codex review 06 of PR 449, F7). The
command comes from a record a contributor writes, so it is untrusted code,
and the rerun is a command-execution feature. Each rule names the threat
it closes and why its design is the standard one.

- Activation from the trusted authority. `work.evidence_rerun` (off by
  default) and its limits (`timeout_secs`, `network`, default `false`) are
  read only from the policy at the default branch resolved to one SHA, the
  authority TSK-1077 defines (ADR-0091), before any candidate input is read.
  The candidate branch's policy, the working copy's and the exported tree's
  are never read for these keys. A missing or unreadable authority means
  off, with a note; it never means on. `ci` and `task status complete` use
  the same resolver. Threat closed: a contributor turning on execution of
  their own command, or loosening its limits, from the change under review.
  Standard design: authorization comes from the protected base, never from
  the change (the trust rule GitHub applies to fork pull requests, and
  CodeFlow's own ADR-0091).
- Containment by a named provider, fail closed. The runner launches the
  command itself inside an operating-system sandbox: Seatbelt
  (`sandbox-exec`) on macOS and bubblewrap (`bwrap`) on Linux, the same
  mechanisms the harness sandboxes use, with a deny-by-default profile.
  The existing `crates/codeflow-core/src/security/actions.json` supplies
  the action and read-rule catalogue the profile draws on; translating it
  into Seatbelt and bubblewrap profiles is new work in this task, since no
  profile generator exists today. The profile allows reads of the exported tree and the
  system toolchain paths, writes only to the exported tree and one fresh
  temporary directory, and no network unless the trusted policy's
  `network` is `true`. The command starts with an empty environment plus a
  fixed allowlist (`PATH` set to fixed system directories, `HOME` and
  `TMPDIR` set to the temporary directory, `LANG`); nothing is inherited,
  so tokens, `GIT_*`, `SSH_AUTH_SOCK` and cloud credentials are absent, and
  the profile denies the home credential paths. If the provider is
  missing (Windows, no `bwrap`), cannot start, or any check below fails,
  the runner refuses before running any command and says why. A
  timeout and a temporary directory are not described as containment.
  `codeflow test`'s runner is not the boundary: it inherits the
  environment and applies no sandbox. The required properties follow; the
  mechanism is the builder's, settled with the task's security review.
  - Provider floor. The provider executable is resolved independently of
    the candidate (a fixed trusted path or the trusted policy, never the
    exported tree, the candidate's `PATH` or its configuration), and its
    version is checked against a stated minimum secure version before use;
    an older or unverifiable provider is refused. For bubblewrap the floor
    is 0.12.0 or later: earlier versions have a setup-time symlink escape
    when creating files on attacker-controlled content
    ([GHSA-pxhw-h44j-8pfx](https://github.com/containers/bubblewrap/security/advisories/GHSA-pxhw-h44j-8pfx)).
    The Seatbelt floor is the macOS version the builder qualifies and
    records.
  - Tree fidelity. The exported tree's tracked paths, file bytes, modes
    and link targets equal the pinned commit's tree exactly, with no
    attribute processing: `export-ignore`, `export-subst`, filters and any
    candidate, working-copy or local (`info/attributes`) attributes change
    nothing. A tree entry the export cannot reproduce faithfully (a
    submodule, for example) is refused, never skipped. The export keeps no
    `.git` link to the repository's object store. A plain `git archive`
    does not meet this (it applies export attributes; this repository's
    `.gitattributes:18` drops a tracked file from it), so it is not the
    named mechanism.
  - Setup never follows candidate links. Exporting the tree and creating
    every sandbox path (mounts, bind targets, the temporary directory and
    any file written during setup) never follows a symlink from the
    candidate tree to a location outside it; a link that would require
    that is refused before execution. In-tree links are reproduced as links
    and resolved only inside the sandbox.
  - Trusted probe. The containment probe is trusted launcher code, not the
    candidate's, run under the same provider and profile as the command.
    It uses synthetic controls the launcher creates outside the sandbox (a
    file holding a fresh secret token, a writable file and, when the
    trusted policy's `network` is off, a reachable local endpoint), and
    attempts a read, a write and a connection from inside the sandbox. The
    probe establishes the outcome of each attempted operation
    independently and reports it through a channel the candidate cannot
    write. A read counts as denied only when trustworthy evidence shows the
    attempt did not obtain the file's content (for example, the launcher
    checks that the probe's reported read result does not contain the
    token it wrote); an unchanged file, no output or a generic command
    failure does not count. A write counts as denied only when the control
    file is unchanged, and a connection only when the endpoint received
    nothing. The read and write denials are always required; the
    connection denial is required only when `network` is off. A missing
    control, an unreachable endpoint, a probe error or any required
    outcome not established refuses the run. The mechanism is the
    builder's.
  Threat closed: a command that reads
  credentials, changes files outside its tree or sends data out, then
  returns the expected code. Standard design: an OS sandbox with deny by
  default, an emptied environment and a pre-run probe, as Bazel's
  sandboxed execution and the harness sandboxes do; refusing when the
  boundary cannot be shown is the fail-closed rule of 2026-10-24.
- Parsing as untrusted input. One `run:` token per evidence field; the
  token takes the rest of the field. It splits at the last occurrence of
  ` => exit ` (one space either side) that is followed by a decimal code
  from 0 to 255 and then the end of the field; the text before it is the
  command. CodeFlow applies no unquoting, escape processing or expansion of
  its own: quotes and backslashes in the command pass byte for byte to
  `/bin/sh -c` inside the sandbox, so a `=> exit` inside quotes is command
  text unless it is the final delimiter. Refused before any execution: no
  delimiter, a code outside 0 to 255 or with a sign or leading zeros, an
  empty command, a newline, NUL or other control character, and a command
  over 4096 bytes. The reviewed sha, export path, sandbox profile and
  policy are computed before the command is read, and the command reaches
  only the sandboxed shell's argument, never a path, a git argument or
  the policy lookup. Threat closed: delimiter or quoting tricks that change
  the expected code, or that leak command text into runner setup, export
  or policy selection. Standard design: a fixed grammar with a single
  defined split point, and untrusted text passed as one argument, never
  re-parsed by the host.
- Distinct failure classes. A provider, probe, export or launch failure is
  reported out of band by the launcher, never through the command's exit
  code, and refuses the binding as "rerun could not run"; only a command
  that ran to completion is compared with `<code>`. A timeout kills the
  process group and refuses. Threat closed: a runner or sandbox failure
  that happens to return the expected nonzero code being read as a
  reproduced failure.
- The acceptance block format is shared with TSK-436 (deferred results,
  4.0.0), which lands first; this task extends that format, not a copy.

Non-goals: proving evidence honest beyond the structural and existence
checks above and the opted-in `run:` rerun; rerunning `test:` or `cmd:`
evidence; re-judging completed records.

## Acceptance Criteria

- AC-1 After activation, `codeflow task status <id> complete` and `codeflow ci` shall refuse a `verified` criterion whose evidence holds no `test:`, `cmd:`, `manual:` or `run:` token, a `test:` path missing at the reviewed commit, and a bare `manual: <reason>`; evidence: one test per case. (serves EPC-024 AC-15)
- AC-2 On a range with a `fix:` commit, or for a `fix` or `hotfix` task, the acceptance block shall need a `regression` field whose `fails-at` sha is an ancestor of the fix and whose `passes-at` sha is the reviewed commit, or `none: <reason>`, which `codeflow ci` prints; evidence: tests for a valid field, a wrong `fails-at`, a missing field and `none:`. (serves EPC-024 AC-15)
- AC-3 `codeflow test --only <target>` shall record a run at a named sha in the gate-runs home, and the local completion step shall check that the named runs failed and passed; hosted `codeflow ci` shall check the structure only and say so; evidence: a test that records both runs and a hosted-mode test.
- AC-4 Acceptance blocks written before the activation commit shall stay valid, and the report-only pass shall list active tasks whose blocks would fail; evidence: a fixture with an old and a new block.
- AC-5 (journey) With the installed build in a scratch adopter at `block`, completing a `fix` task without a regression field shall be refused, and recording the failing and passing runs then completing shall pass; evidence: the journey output. (serves EPC-024 AC-15)
- AC-6 With `work.evidence_rerun` on at the default-branch policy authority, `codeflow ci` and `codeflow task status <id> complete` shall rerun each `run: <command> => exit <code>` token in an export equal to the reviewed sha's tree inside the named operating-system sandbox, after the provider floor, tree fidelity, setup and probe checks of the security contract pass, and shall pass the binding only when every exit status equals its `<code>`; a mismatched status, a timeout and a `run:` token without `=> exit <code>` shall be refused, naming the criterion, the command and the actual result; with the key off, and for evidence without a `run:` token, the verdict shall equal today's; hosted `ci` shall check the token's structure only and say so; evidence: tests for a matching pass, a matching expected failure (`exit 1`), a mismatch, a timeout, a malformed token, the key off, unmarked evidence and hosted mode, plus a journey in a scratch adopter where a `run:` command that passes only in an uncommitted worktree is refused at the reviewed sha (issue #450's case). The security contract in the Description shall hold, each part shown by a synthetic adversarial fixture that fails before the rule exists: the key turned on only in the candidate branch's or working copy's policy runs nothing; an unreadable authority runs nothing; a command that reads an environment token, `HOME` credential paths or `SSH_AUTH_SOCK` finds none, and a command that writes outside the tree is denied; a network connection is denied with `network` off; delimiter injection (a quoted ` => exit 0` before the real delimiter, two delimiters, a trailing space, a signed or out-of-range code, a newline, a NUL) parses by the stated rule or is refused before execution; with the provider absent or the probe not denied the runner refuses before running any command; a launch failure that would exit with the expected code is reported as "rerun could not run"; a provider older than its stated floor (bubblewrap before 0.12.0) or resolved from the candidate's `PATH` is refused; tree fidelity holds against an `export-ignore` path, an `export-subst` file and a local attributes override, with the exported bytes and modes equal to the pinned tree or the run refused before execution; setup refuses, with no write outside the tree observed during setup, an absolute symlink, a parent-relative (`../`) symlink and a symlink placed at a path setup creates or binds; the probe establishes each required read, write and connection outcome independently through the protected channel, and qualification fails for a sandbox where the outside token file is readable from inside while writes and network stay blocked (the file unchanged), and a probe whose control is missing, whose endpoint is unreachable or whose printed result is forged by the candidate does not count as established; and hosted mode executes no command or setup and reports that no result was verified. (serves EPC-024 AC-15)
