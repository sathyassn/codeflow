# TSK-044 — qualify the CLI on sample projects

## Description

Every other task in this epic verifies the repository against itself, so no
evidence exists that a reader who installs the binary and points it at their
own project gets the behaviour the documentation now promises. This task
exercises the installed `codeflow` binary from the candidate tree against
generated sample repositories, greenfield and brownfield, at each of the three
tiers, running every subcommand against its documented contract and recording
passed, failed or unavailable with expected versus observed. Non-goal: this
task fixes nothing. A material failure blocks qualification rather than being
filed and passed; a non-material defect is fixed in its owning task or filed
with an id, and the native-platform and hosted-publication gates stay with
their existing owners and are reported unavailable, never inferred.

## Affected surfaces and interfaces

A new `tests/release-qualification/` fixture and script area. The sample
greenfield and brownfield repositories it generates live under `$TMPDIR` and
are never committed. `docs/verification/releases/v3.0.0.md` receives appended
CLI qualification evidence only. `docs/release-checklist.md` stays owned by
TSK-040; if a checklist row is needed, this task hands TSK-040 one line rather
than editing that file. The qualification exercises the public CLI contract of
every subcommand but changes no CLI source.

### What the qualification is

`tests/release-qualification/qualify.sh` builds the named commit in a detached
worktree, records the binary's SHA-256, generates the samples in a disposable
root under `$TMPDIR`, exercises the documented contract of every subcommand,
and writes the matrix and the delimited block inside the release record.
Nothing in the repository under qualification is touched, and the run deletes
its root. The candidate commit and the work directory are parameters, so the
same script re-runs unchanged against a later head.

Each row carries expected, taken from `docs/cli.md`, against observed, which is
the exit status and the output line that decided it. The renderer refuses a
blank expected or observed and refuses an unavailable row with no owner, so a
gap cannot be written as a pass.

### A concurrent gate failure, reproduced and explained

While this harness was running in this worktree, the coordinator's full gate
failed twice in `cf-present-qualification`, at `6d6b0a5a2` and `d801bd982`.
`real-browser-check.mjs` reported `presentation service did not become ready:
service exited before readiness with exit status: 5` on `codeflow present open
... --no-launch`. The question put to this task was whether its present rows
share session state or a port with a concurrently running service. They do
not, and the real cause is worse and simpler: this harness replaced the
binary the gate was running.

First, what is not the cause. State is per `$HOME`: on macOS the store root is
`$HOME/Library/Application Support/codeflow/present`
(`crates/codeflow-present/src/state.rs:2658`), and every present call here runs
under `HOME="$PRESENT_HOME"`, inside the run's own work root, through one
helper (`tests/release-qualification/qualify.sh:1103`). There is no fixed port:
the service binds `127.0.0.1:0` (`crates/codeflow-present/src/service.rs:223`).
The sessions live in disposable sample repositories, not in this worktree.

The actual mechanism, reproduced directly after the run:

    $ HOME=<fresh> codeflow present serve-internal <id>
    present: presentation state is corrupt: embedded renderer manifest is missing
    serve-internal EXIT 5

Exit 5 is `CorruptState` (`crates/codeflow-cli/src/cmd/present.rs:680`), raised
at `crates/codeflow-present/src/service.rs:950`. The renderer assets are
`rust-embed` (`crates/codeflow-present/src/service.rs:47`) declared without the
`debug-embed` feature (`Cargo.toml:38`), so a debug binary does not carry them:
it reads them at run time from the source folder recorded at compile time.

This run was given `--target-dir` pointing at this worktree's `target/`, so its
build of the candidate overwrote `target/debug/codeflow` with a binary whose
asset folder is the disposable checkout `$WORK/candidate`. Every later use of
`target/debug/codeflow`, including the coordinator's gate, then looked for the
renderer inside a temporary tree that was removed at teardown, and the service
child exited 5 before readiness. That is why the same target passes when it
runs alone on another branch: there, `target/debug/codeflow` is rooted in its
own worktree.

Two consequences worth stating plainly:

- The gate failure is collateral from sharing one Cargo target directory
  between a build and a gate, which is already a recorded quirk of this
  development environment. It is not a defect in the presentation surface and
  not a concurrency bug in it. Nothing needs to change in TSK-007 for it; the
  note routed there is that the observation was explained, with this mechanism,
  so it is not carried as an open shared-state suspicion.
- The matrix's present rows are honest for this run: they ran while
  `$WORK/candidate` still existed, and `present open` recorded exit 0. But a
  debug binary resolves those assets differently from a release binary, so the
  presentation rows qualify the debug build in place. A release binary embeds
  them, which this run did not build and therefore did not check. That is
  stated in "What was not verified".

### What the candidate binding finding changed

The git hook shims are `command -v codeflow >/dev/null 2>&1 || exit 0` followed
by `exec codeflow git-hook <stage>`, so every real commit, ref move and push in
a sample resolves the binary through PATH. The earlier run never put the
candidate on PATH, so those probes were enforced by the codeflow installed on
the machine, which this task was told is stale. The rows were green and did not
describe the candidate.

Two rows now hold that closed. `candidate binding` asserts that
`command -v codeflow` is the built candidate and that its digest equals the
recorded one. A decoy `codeflow` sits immediately behind the candidate on PATH
and appends to a sentinel if it is ever reached; after every sample, tier and
probe in the run, the second row asserts the sentinel is absent.

### A documentation finding, routed

`docs/cli.md` states that `hook delegate-turn` exits 2 when a schema-v2 payload
cannot be read. The binary returns 2 only when the failing payload is a prompt
submission, and 1 for any other failure, which is the deliberate behaviour:
blocking a turn matters where a prompt would otherwise run blind. Measured on
the candidate: no run id 1, unreadable run on a `SessionStart` payload 1,
unreadable run on a `UserPromptSubmit` payload 2. The matrix records all three.
This is a wording imprecision, not a product defect, and it belongs to TSK-052,
which owns `docs/cli.md`.

### What the new coverage found

Adding rows found something the old matrix could not see. `present close`
returns 0 once the session is marked closed, but its service process is still
running for a moment afterwards, and `present clear` deliberately retains a
session whose service is alive. Run against the candidate, an immediate
`present clear --dry-run` exited 1 with `cleanup was partial; removed [];
retained [... session service is still running]`, and the same session was
removed cleanly by teardown seconds later.

The documented contract for `close` promises that repeating it is safe and says
nothing about when the service exits, so the first form of these rows asserted
more than `docs/cli.md` promises. They now wait a bounded thirty seconds for the
service to exit, record how long that took in the `present close` row, and fail
if it never does. Retaining a live session is the safe behaviour, not a defect.

One asymmetry is worth the owning task's attention rather than a silent pass:
on the same partial outcome, `present clear --dry-run` exited 1 while
`present clear` exited 0 and left the session listed. `docs/cli.md` does not
state an exit for a partial clear, so this is not measured as a failure here.
It belongs to TSK-007, which owns the presentation surface.

### The round two cleanup failure, explained

Round two reported `presentation sessions could not be listed`, and the
closeout said the cause could not be determined. It can. Round three's review
found it by reading the code: the discovery helper set its success flag inside
a command substitution, so the assignment happened in a subshell and the parent
always saw zero. Teardown therefore rejected every listing, including
successful ones, and never closed a session. The failure was the harness
mis-reading its own result, not anything wrong with `present list`, which is
why running `present list` by hand afterwards never reproduced it.

The fix removes the flag and uses the function's exit status, which is what
crosses a subshell boundary. Stderr from both the command and the parser now
flows into the teardown log, so a future failure can be read rather than
guessed at.

### A process error, recorded

Round three's run was started, and then the harness script was edited while
that run was executing it. `sh` reads a script as it goes, so changing its
length under a running interpreter can shift byte offsets and make it execute
something the file never said. This is the second time in this task, and it is
recorded rather than quietly corrected.

The run was stopped with `SIGTERM` rather than allowed to finish, because its
result could not be trusted. The edit was folded into the harness commit and
the whole matrix was re-run from the committed script, which is the state the
record is generated from. The stop was not wasted: the signal path is one
teardown case that had never been exercised, and it removed the run's work
directory and left only the Cargo target directory it was given, which is the
behaviour round two claimed and could not show.
