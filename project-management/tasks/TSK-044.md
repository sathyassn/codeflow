# TSK-044 — qualify the CLI on sample projects

## Description

Every other task in this epic verifies the repository against itself, so no
evidence exists that a reader who installs the binary and points it at their
own project gets the behaviour the documentation now promises. This task
exercises the installed `codeflow` binary from the candidate tree against
generated sample repositories — greenfield and brownfield, at each of the three
tiers — running every subcommand against its documented contract and recording
passed, failed or unavailable with expected versus observed. Non-goal: this
task fixes nothing. A material failure blocks qualification rather than being
filed and passed; a non-material defect is fixed in its owning task or filed
with an id, and the native-platform and hosted-publication gates stay with
their existing owners and are reported unavailable, never inferred.

## Affected surfaces and interfaces

A new `tests/release-qualification/` fixture and script area. The sample
greenfield and brownfield repositories it generates live under `$TMPDIR` and
are never committed. `docs/verification/releases/v3.0.0.md` receives appended
CLI qualification evidence only. `docs/release-checklist.md` stays owned by
TSK-040; if a checklist row is needed, this task hands TSK-040 one line rather
than editing that file. The qualification exercises the public CLI contract of
every subcommand but changes no CLI source.

### What the qualification is

`tests/release-qualification/qualify.sh` builds the named commit in a detached
worktree, records the binary's SHA-256, generates the samples in a disposable
root under `$TMPDIR`, exercises the documented contract of every subcommand,
and writes the matrix and the delimited block inside the release record.

its root. The candidate commit and the work directory are parameters, so the
same script re-runs unchanged against a later head.

Each row carries expected, taken from `docs/cli.md`, against observed, which is
the exit status and the output line that decided it. The renderer refuses a
blank expected or observed and refuses an unavailable row with no owner, so a

### What the candidate binding finding changed

The git hook shims are `command -v codeflow >/dev/null 2>&1 || exit 0` followed
by `exec codeflow git-hook <stage>`, so every real commit, ref move and push in
a sample resolves the binary through PATH. The earlier run never put the
candidate on PATH, so those probes were enforced by the codeflow installed on
the machine, which this task was told is stale. The rows were green and did not
describe the candidate.

Two rows now hold that closed. `candidate binding` asserts that
`command -v codeflow` is the built candidate and that its digest equals the
recorded one. A decoy `codeflow` sits immediately behind the candidate on PATH
and appends to a sentinel if it is ever reached; after every sample, tier and
probe in the run, the second row asserts the sentinel is absent.

### A documentation finding, routed

`docs/cli.md` states that `hook delegate-turn` exits 2 when a schema-v2 payload
cannot be read. The binary returns 2 only when the failing payload is a prompt
submission, and 1 for any other failure, which is the deliberate behaviour:
blocking a turn matters where a prompt would otherwise run blind. Measured on
the candidate: no run id 1, unreadable run on a `SessionStart` payload 1,
unreadable run on a `UserPromptSubmit` payload 2. The matrix records all three.
This is a wording imprecision, not a product defect, and it belongs to TSK-052,
which owns `docs/cli.md`.

### What the new coverage found

Adding rows found something the old matrix could not see. `present close`
returns 0 once the session is marked closed, but its service process is still
running for a moment afterwards, and `present clear` deliberately retains a
session whose service is alive. Run against the candidate, an immediate
`present clear --dry-run` exited 1 with `cleanup was partial; removed [];
retained [... session service is still running]`, and the same session was
removed cleanly by teardown seconds later.

The documented contract for `close` promises that repeating it is safe and says
nothing about when the service exits, so the first form of these rows asserted
more than `docs/cli.md` promises. They now wait a bounded thirty seconds for the
service to exit, record how long that took in the `present close` row, and fail
if it never does. Retaining a live session is the safe behaviour, not a defect.

One asymmetry is worth the owning task's attention rather than a silent pass:
on the same partial outcome, `present clear --dry-run` exited 1 while
`present clear` exited 0 and left the session listed. `docs/cli.md` does not
state an exit for a partial clear, so this is not measured as a failure here.
It belongs to TSK-007, which owns the presentation surface.
