# TSK-044 — qualify the CLI on sample projects

## Description

Every other task in this epic verifies the repository against itself, so no
evidence exists that a reader who installs the binary and points it at their
own project gets the behaviour the documentation now promises. This task
exercises the installed `codeflow` binary from the candidate tree against
generated sample repositories — greenfield and brownfield, at each of the three
tiers — running every subcommand against its documented contract and recording
passed, failed or unavailable with expected versus observed. Non-goal: this
task fixes nothing. A material failure blocks qualification rather than being
filed and passed; a non-material defect is fixed in its owning task or filed
with an id, and the native-platform and hosted-publication gates stay with
their existing owners and are reported unavailable, never inferred.

## Affected surfaces and interfaces

A new `tests/release-qualification/` fixture and script area. The sample
greenfield and brownfield repositories it generates live under `$TMPDIR` and
are never committed. `docs/verification/releases/v3.0.0.md` receives appended
CLI qualification evidence only. `docs/release-checklist.md` stays owned by
TSK-040; if a checklist row is needed, this task hands TSK-040 one line rather
than editing that file. The qualification exercises the public CLI contract of
every subcommand but changes no CLI source.

## Acceptance Criteria

- [ ] The qualification runs against the integrated candidate, not a task
      branch; evidence: the candidate commit SHA and the SHA-256 of the
      installed binary are recorded in the appended v3.0.0 evidence, and both
      match the integration head used.
- [ ] Greenfield samples — an empty git repository in a Rust stack and in a Node
      stack — are qualified at the minimal, standard and full tiers; evidence:
      one recorded result matrix per stack and tier.
- [ ] A brownfield sample carrying its own README, CI workflow and git hooks is
      qualified at the same three tiers, with the existing files preserved;
      evidence: the sample's pre-existing files are unchanged or 3-way merged as
      documented, shown by a before/after diff.
- [ ] `init` and `update` are idempotent and the `update` 3-way merge never
      clobbers user edits; evidence: a second consecutive run produces no diff,
      and a deliberately edited managed file survives `update`.
- [ ] `hook` and `git-hook` enforce commit format, attribution, secrets and the
      protected-branch rule; evidence: a positive and a rejecting case recorded
      per rule, with the observed exit status and message.
- [ ] Each remaining subcommand runs against its documented contract with
      expected versus observed recorded: `orient`, `test` (setup and run),
      `validate --docs` and `validate --portal`, `ci` range check, `status`,
      `integrate` including the flock path, `doctor` across all checks named by
      `doctor --list`, `policy explain` and `policy show`, `recall`, `remote` in
      dry mode, the `epic`/`spec`/`task`/`work` lifecycle including both a
      `work start` refusal and a success, `estimate` check, `portal setup`,
      `portal build` and portal validation, and `present` open, feedback and
      resolve; evidence: one matrix row per subcommand, none skipped silently.
- [ ] The `delegate` lifecycle — init, arm, wait — is proved by a canary against
      a real Claude session in a Herdr tab this run created; evidence: the
      recorded session and tab identifiers plus the observed lifecycle
      transitions.
- [ ] The pipeline workflow runs once end to end on a sample; evidence: the
      recorded run output and its terminal state.
- [ ] Every check records exactly one of passed, failed or unavailable with
      expected versus observed; evidence: the matrix has no blank or inferred
      cell, and each `unavailable` names the owner it belongs to (native
      platform gates, hosted publication).
- [ ] A material failure blocks qualification; evidence: the record states the
      qualification verdict, and any non-material defect carries either its
      owning task id or a filed id — never a bare note.
- [ ] All canaries ran only in disposable repositories under `$TMPDIR` and in
      sessions and Herdr tabs this run created, and all were torn down;
      evidence: teardown output showing the temporary paths and the owned
      sessions are gone.

## Execution contract

Plan v4, EPC-014. Responsible primary: claude-primary at high effort (Fable),
who directs the matrix and personally judges every failure — a worker may not
classify a failure as non-material. Execution: a same-family opus worker at
high effort runs the qualification matrix and the canaries. Cross-lineage
reviewer: codex-primary at high effort. Integration target
`integration/EPC-014-public-docs`. Sequencing: the fixtures and scripts may be
prepared from the start of the epic, but the qualification run executes only
against the integrated candidate after TSK-037 through TSK-042 have landed on
the integration branch. Risk: the canaries create real sessions and real
repositories, so they are confined to `$TMPDIR` and to sessions this run owns,
and teardown evidence is part of acceptance rather than a courtesy. Recovery is
deletion of the temporary trees; nothing in the repository is mutated except
the appended v3.0.0 evidence.
