# TSK-1453: A push from a partial clone names its missing file contents and how to fetch them

## Description

In a `blob:none` partial clone, file contents that were never checked out are not in the local object store. The pre-push `git.path_policy` check reads the pushed files through libgit2 (`hooks/path_policy.rs:395`, `:734` `find_blob`; `:958-959` `odb().read_header`; `:1023` `find_blob`), which never fetches a missing object. So a push whose range holds such contents is refused: commits fetched but never checked out, or a merge whose other side's contents are absent. This repository is a `blob:none` clone (`remote.origin.partialclonefilter`).

It fails closed, so it is not a security hole. It is a usability defect: the refusal does not say the cause is a partial clone, and an adopter on a partial clone cannot tell what to do.

The hooks never fetch from the network while judging. `git/mod.rs:48-57` (`local_objects_only`) forces `GIT_NO_LAZY_FETCH=1` so a missing object is an error, never a fetch from the promisor remote, and TSK-412 AC-5 holds the secret scan to the same rule. A fetch here would contact a remote named in repository configuration, which an agent can write. So this task keeps the no-fetch rule and makes the refusal say what is missing and how the person pushing fills it. Non-goal: fetching objects from inside a hook.

Search (coord/records, 2026-11-11 04:12 EST): open records on `main`, the EPC-022, EPC-024, EPC-025 and EPC-026 lines and plan/records-2026-11-10 hold no criterion for `path_policy` over missing contents. TSK-110 (a treeless clone in a benchmark), TSK-412 AC-5 (the secret scan never fetches), TSK-1193 AC-2 (cancelled; the tree reader's missing-blob refusal) and TSK-1423 AC-5 (an unreadable object in a line-merge range keeps its refusal) are related, and none covers this.

Source: coord/catalog's report of 2026-11-11 at about 04:10 EST, from the PR 699 (TSK-327) build, whose first version of its stall test hit this (Worker report 09:07 UTC). Facts checked by coord/records at 2026-11-11 04:12 EST against the EPC-022 line tip 0318b9c03.

## Outcome

After this merges, a person pushing from a partial clone whose range holds file contents that are not local gets a refusal that names the partial-clone cause, the paths, and a command that fetches them, and the push passes once they run it; no check fetches anything itself.

## Acceptance Criteria

- AC-1 When a pushed range holds file contents that are missing from a partial clone's object store, the `git.path_policy` pre-push check shall refuse with a message that names a partial clone as the cause, lists the affected paths (shown as the path display rules require), and gives a command that fetches those contents without naming any remote whose name codeflow withholds. It shall never fetch, and never pass, while any content is missing. Evidence: a `blob:none` fixture pushing a commit that was fetched but never checked out, and one pushing a merge whose other side's contents are absent: each refused with the new message, and the push judged as in a full clone after the stated command runs.
- AC-2 A missing object in a repository that is not a partial clone, or one that the stated command cannot fetch, shall still refuse, naming the object as unreadable, as today. Evidence: a full-clone fixture with a removed blob, and an offline partial-clone fixture, each refused with its message.
- AC-3 Every other pre-push or `codeflow ci` check that reads pushed file contents through libgit2 shall be listed with its verdict (gives the same message, or why it cannot meet a missing object), and each one that can meet one shall give the AC-1 message. Evidence: the list in the pull request body, with file:line for each check, and one fixture per check that changes.
- AC-4 The checks shall make no network request while judging, in the partial-clone fixtures as elsewhere. Evidence: the fixtures run with `GIT_NO_LAZY_FETCH` unset in the caller's environment and an unreachable promisor URL, and still refuse without a fetch attempt.
