# TSK-226: Records match what landed on main

## Description

CodeFlow 3.0.0 is published, and the records on `main` still describe the
time before it. Seven merged tasks (TSK-198 to TSK-202, TSK-090, TSK-187) are
`todo` or carry template closeouts; several tasks name integration lines that
exist only in the archive, so `codeflow work next` shows cancelled tasks as
waiting and finished work as ready. This task makes each record say what
happened, from the merged pull requests and the release evidence, and records
the decision on the release baselines. The test that keeps the baseline ids
honest is TSK-227's: a completion after a landing may change planning
records only, so `codeflow ci` refuses a range that completes landed tasks
and also adds code, and the two changes cannot share a pull request. This
task also replaces the plan's reuse of TSK-195: that record targets a retired
release branch, and a pull request that names it is refused by
`work.stable_planning_anchor` until a planning change retargets it, so the
reconciliation runs here and TSK-195 is only retargeted and noted (it
completes after this pull request's review).

Nothing is invented. Five of the seven close on the evidence (TSK-198,
TSK-200, TSK-201, TSK-202 and TSK-187). TSK-090 and TSK-199 stay open,
because a criterion of each cannot be verified as written (TSK-090 AC-8 asks
for a qualification on a release-assembly head that never ran; TSK-199 AC-3
fails on macOS, found here by running its five checks), and a completion with
a "narrower than written" result does not satisfy SPC-013 R-60. Where
evidence was never recorded or is not in this repository (the archive review
files), the acceptance block says so. Non-goals: moving the release baseline
tables (decided below), closing the epics, changing what any task delivered,
and TSK-091's and TSK-099's open criteria, which need a release qualification
run and a download that this task does not run.

Decision on the release baselines: `release_records_baseline` and
`release_rule_baseline` keep their archive ids, for three reasons. SPC-013
R-120 makes them a write-once bridge, so any later edit makes every release
check refuse and name the editing commit. `.codeflow/project.toml` is an
enforcement path that agents cannot edit, so a move is the operator's. And
the work records baseline, which every pull request reads, already names
public ids that resolve in a public-only clone (TSK-198), so ordinary pull
requests are not affected. The cost is recorded here, not hidden: the
release judge checks every cutoff in both tables, whether or not an import
uses it (`crates/codeflow-core/src/workgraph/release_line.rs:2308`), and a
public-only clone does not hold the five archive cutoff objects. A release
range judged in a public-only clone is therefore refused until the operator
resolves the bridge (a specification change to the one-time bridge, or a
reviewed edit of the tables that the release judge accepts). The public
repository has no `integration/EPC-*` branch, but it does have
`integration/release-3-0-0-r3` (`git ls-remote --heads origin`, 2026-10-03),
so a release range can be judged there. TSK-227's test lists the
ten entries by table, line and id, so a rewritten id anywhere else fails and
a table entry missing from that list fails too.
