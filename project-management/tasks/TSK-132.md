# TSK-132: a pre-push gate under a minute that blocks

## Description

The pre-push quick gate runs the whole test suite in 5.5 to 7.6 minutes,
only warns, was pushed through while failing, and competes with full gates
for CPU. This task makes pre-push a set that finishes in under a minute and
blocks, for CodeFlow and, as the operator settled, as the shipped default
for adopters: format, lint, `validate --docs` and `codeflow ci` on the
pushed range, with the test suite left to the full gate. Changing the
adopter default from warn to block is public behaviour and is marked so in
the changelog. Source: guardrails strand row 9 and top five item 2.

## Affected surfaces and interfaces

- `crates/codeflow-cli/src/cmd/git_hook.rs` (pre-push), the push set in
  `.codeflow/test-config.json` and the scaffolded test config.
- `test_gate_on_push` default in `assets/base/policy.json` and
  `.codeflow/policy.json`; `codeflow update` policy migration.
- `CHANGELOG.md` with a release-impact marker.

## Acceptance Criteria

- [x] AC-1 Pre-push shall run only the push set and block on its failure; on
      CodeFlow's own repository the set shall finish in under 60 seconds on
      a warm target; evidence: a hook test for the block path and a timed
      push log.
- [x] AC-2 When the push set's measured time exceeds 60 seconds, the hook
      shall name the slowest target and the config key that moves it out of
      the push set; evidence: a hook test with a slow fixture target.
- [x] AC-3 In a freshly scaffolded project at every tier (minimal, standard,
      full) `test_gate_on_push` shall default to block with the fast set;
      evidence: `init_e2e` and `tier_floor_e2e`.
- [x] AC-4 `codeflow update` shall keep an existing `test_gate_on_push`
      value and print one line recommending `block` and how to set it
      (amended in review round 1: equality with the old baseline cannot show
      the adopter did not choose `warn`); evidence: update tests for the
      default-equal `warn`, other explicit values and an existing `block`.
- [x] AC-5 The changelog shall state the new default as a public behaviour
      change with the way to restore warn; evidence: the `CHANGELOG.md`
      entry and its release-impact marker.

Push set for this repository: `rust-format`, `rust-clippy`, `gate-parity`,
`skill-triggers`, `herdr-delivery`. Kept out on measured cost:
`release-automation` (129 s), `model-eval-kit` (54 s), the suite, `rustdoc`
and `docs-validation` (the built-in `validate --docs` covers it).

Review round 1 (Codex): T132-3, T132-4 and T132-5 fixed; T132-1 and T132-2
were only partly fixed and are completed in round 2.

Review round 2 (Codex), principle: the hook blocks on what it can see and
never claims more than it checked; CI is the authority.
- R2-1: tree checks do not run on a sparse checkout or with a submodule that
  is uninitialized, at another commit or conflicted; the pass line says it
  checked the working checkout, where untracked files can influence a quick
  target. Tests: `hooks_cli::push_set_does_not_run_tree_checks_on_a_sparse_checkout`,
  `push_set_does_not_run_tree_checks_with_an_uninitialized_submodule`,
  `push_set_untracked_input_is_named_in_the_pass_line`, each with its
  complete-checkout control that blocks.
- R2-2: no local branch is ever substituted for destination history; without
  the destination's sha or tracking refs the range is reported unresolved.
  Tests: `push_set_uses_the_destination_base_not_local_main` (a `stable`
  destination blocks the bad commit while local `main` points at it),
  `push_set_ignores_a_stale_local_main` (a legacy commit already on the
  destination is not rechecked), and
  `push_set_by_path_reports_an_unresolved_range_without_borrowing_history`.

Found while force-pushing the rebase over the landed EPC-020 work: from the
destination's old sha, a rebased branch's range held every upstream commit
the rebase brought in, so the hook blocked on landed records. A destination
sha that the pushed sha does not extend, but shares history with, now falls
to the tracking-ref base; an unrelated one still goes to `codeflow ci`,
which blocks it. Test:
`hooks_cli::push_set_checks_only_the_rebased_commits_of_a_rewrite` (fails
without the change on the upstream legacy commit). Superseded by the rule
below, which trades that narrower range for never trusting a cached ref.

Review round 4 (R4-1) and its follow-up review: any cached tracking ref,
the pushed branch's own or an `integration/*` sibling, can be stale and hold
a commit the destination dropped, so a push restoring it went unchecked.
Rule (operator, 2026-09-27): no cached tracking ref shrinks the range. An
existing destination branch is checked from the sha the destination
advertises; after a rebase that includes the commits it brought in, and the
hook says so. A new branch is bounded only by the tracking refs of the
destination's protected branches, which policy keeps from being rewritten;
with none, the range is reported unresolved. Tests:
`hooks_cli::push_set_checks_a_commit_only_a_stale_tracking_ref_holds` (own
feature ref, own integration ref, stale sibling integration ref; fails
before the change) and
`push_set_checks_a_rewrite_from_the_destination_sha_and_says_so`.
`tier_floor_e2e::push_set_blocks_a_bad_push_at_every_tier` seeds the
destination's protected default branch so new-branch ranges resolve.

Timing, pushes of this branch from a clean checkout with the branch binary
on `PATH` and a warm target: round 0, push set 2.4 s and 2.5 s (whole
`git push` 4.15 s and 4.22 s); after review round 1, with `codeflow ci`,
`validate --docs` and the five quick targets bound to the pushed commit,
push set 3.2 s (whole `git push` 5.07 s).

Not verified: a push on Windows; a push whose clippy must rebuild every crate
(cold clippy measured 31 s); the Go template's `go vet` target against a Go
project; a hosted remote with a fetch refspec that is not a glob (treated as
no destination history).
