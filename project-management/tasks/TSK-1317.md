# TSK-1317: A killed gate's fence outlasts its process tree on Windows

## Description

On Windows only the gate process holds `full-gate.lock`, as a shared `LockFileEx` lock. Its targets do not inherit it (`runner/mod.rs:1246`; the open at `bounded_file/confined/windows.rs:93` sets no `OBJ_INHERIT`). The tree ends through a kill-on-close job whose only handle the gate holds (`runner/target_job.rs:80-106`). When the gate dies the OS closes both handles, Microsoft documents no order between them, and it documents `TerminateProcess` as asynchronous. So the fence can free before the tree has ended, and an older binary can start beside it. The test `a_killed_gates_target_tree_ends_before_older_binaries_get_in` failed once on this at line tip `fe66d4c62` (codeflow-ci run 41763959485, job 126359726029). There is no evidence of target code running after the fence freed; the run cannot show either way.

A green rerun of that job does not close this task, because the gap comes from the design and the failure depends on timing.

The default fix is a Windows watcher like the Unix `runner/group_watch.rs`: it runs outside the job, holds the fence and a job handle, ends the job when the gate dies, waits until the job is empty, then exits. Older binaries read only the OS lock, so the hold itself has to outlast the tree. Measure first from the timing TSK-1318 reports. If the measured window or the build cost argues for restating the guarantee instead, the numbers go to coord/ci and the Director rules. The test's assertion is not loosened without that ruling; if the Director so rules, this record's criteria change with the ruling named.

Restated on 2026-11-08, after TSK-1318. TSK-1318 (complete on `main`) built the Windows watcher this task proposed (`crates/codeflow-core/src/testing/runner/job_watch.rs`) and the test's timing report. The watcher frees the fences once the job reports no active process (`JOB_OBJECT_MSG_ACTIVE_PROCESS_ZERO`, with `ActiveProcesses` as a backstop). Windows removes a process from the job's count as it starts to exit, before its handle is signalled, so the fence can still free before the tree has ended. Hosted job 127813575450 (run 42181083859, PR 655 head `bb64e3114`, which carries the watcher) failed the test with a kill-to-take time of 26 ms, a target kill-to-end of 54 ms and a grandchild kill-to-end of 41 ms. The fix is in the watcher: it keeps a waitable handle to every process in the job and frees the fences only after each one is signalled. The `main` line has the watcher and the EPC-022 line does not, so this task now targets `main`.

Non-goals: processes started outside the job, such as through a service; slot-count policy.

## Outcome

After this merges, an operator who kills a 4.0.0 gate on Windows finds that an older CodeFlow gate cannot start until that gate's whole process tree has ended.
