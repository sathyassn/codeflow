# TSK-412: The commit-time secret scan can run the pinned gitleaks rules

## Description

Issue #251. The pre-commit hook scans the added lines of the staged diff
with a fixed set of high-signal credential shapes
(`crates/codeflow-core/src/hooks/git_hook.rs:110-152` calls
`scan_staged`, which runs `crates/codeflow-core/src/hooks/scan.rs`
`scan_line`). The managed CI secret scan runs gitleaks 8.30.1 with its
default rules, which include the entropy-based `generic-api-key`. A match
that only the CI rule sees is found after the commit exists and other
work is built on it; the adopter's only fixes are a history rewrite or a
permanent `.gitleaksignore` fingerprint, each needing a person's reviewed
commit. In the reporting monorepo, 7 of 23 exemptions are one spec line
that passes the hook on every edit, and a file's SHA-256 recorded under
its path name cost two permanent exemptions. The adopter measured
`gitleaks git --staged` at 0.03 s for an empty stage and 0.06 s for a
merge commit's range, so a staged scan fits the pre-commit budget.

Outcome: **a project can opt in to running the pinned gitleaks binary on
the staged content at commit time, with the same rules and ignore files
the managed CI scan reads, so a match is caught while it can still be
reworded; the built-in patterns stay the floor, and at `block` a missing
or mismatched binary fails closed.**

Decisions recorded here:

- **Opt-in, not default.** A new policy key (provisional name
  `git.secret_scan_engine`, values `builtin` and `gitleaks`, default
  `builtin`), placed by TSK-280's placement rule and read by the hook
  (TSK-363 refuses a key with no reader). The built-in scan runs in both
  settings; `gitleaks` adds the binary's verdict.
- **Same pins as CI.** The hook runs the gitleaks version the managed
  workflow pins (`assets/base/ci/codeflow-ci.yml`) and checks its
  checksum; at `block`, a binary that is missing, unpinned or mismatched
  refuses the commit and names `codeflow doctor` and the install route.
  At `warn` it warns once and runs the built-in scan.
- **Ignore files.** The working tree's `.gitleaksignore` and
  `.gitleaks.toml` are read, as the only copies available before a
  commit exists; a commit cannot weaken CI, which reads them from the
  trusted base. The pull request records what a staged fingerprint looks
  like (the issue's open question) and documents that an existing
  commit-bound fingerprint never covers a staged finding, so a known
  false-positive file is allowlisted by path in `.gitleaks.toml`.
- **No network at commit time.** The hook never downloads the binary;
  `codeflow doctor` reports where it looked and the pinned version.

Non-goals: a local run of the full managed scan over a range (TSK-430 in
EPC-024), the dependency audit, and making gitleaks the default.

Added by the EPC-022 amendment of 2026-10-22 under the operator's release
rule of 2026-10-18 (a defect that forces an adopter workaround belongs in
3.2.0).

Widened 2026-10-26 for issue #296 (CodeFlow 3.1.1; unchanged at this
line's `0f08dd7f8`). The staged secret scan never runs for an automatic
merge commit: Git runs `pre-merge-commit` on that path and not
`pre-commit`, and `pre_merge_commit`
(`crates/codeflow-core/src/hooks/git_hook.rs`) checks protected
branches and the root checkout only, so a merge driver that writes a
key neither parent holds commits it. Git writes `MERGE_HEAD` after
`pre-merge-commit` runs (git v2.54.0, `builtin/merge.c:930` and `:963`),
so the scan runs in `commit-msg`, which Git calls with `MERGE_MSG` for
an automatic merge and with `COMMIT_EDITMSG` for plain and
hand-concluded commits that already ran `pre-commit`. The built-in floor
and, when chosen, the gitleaks engine both run there. This is a
security gap in the default, so it rides with this task's scan work in
3.2.0 rather than waiting for the opt-in engine's users.

- the engine key and its reader: `crates/codeflow-core/src/hooks/policy_schema.rs`, `crates/codeflow-core/src/hooks/policy.rs` and the pre-commit path in `crates/codeflow-core/src/hooks/git_hook.rs` (`scan_staged`)
- the gitleaks runner, its pin and checksum check: a new module under `crates/codeflow-core/src/hooks/` (provisional `secret_engine.rs`), reading the pinned version from the same source the managed workflow uses

- tests: `crates/codeflow-cli/tests/hooks_cli.rs` with a fake pinned binary, a mismatched one and a missing one, and `git_hook.rs` unit tests
- docs: `docs/policy-reference.md` (the key, its levels, the fail-closed rule and the fingerprint note) and `docs/troubleshooting.md`
- release note: `changelog.d/TSK-412.md`
- the automatic-merge scan: `commit_msg` in `crates/codeflow-core/src/hooks/git_hook.rs` and the managed hook shim, if it must pass the message path through

## Acceptance Criteria

- AC-1 With `git.secret_scan_engine: gitleaks` and `git.secret_scan: block`, a staged line that gitleaks' default `generic-api-key` rule matches and the built-in patterns miss (the issue's `"<path>": "<64 hex>"` shape) shall be refused at commit time naming the rule and the line; evidence: a hook test with a pinned test binary, failing before the change. (serves EPC-022 AC-101)
- AC-2 With the default `builtin`, the hook shall behave as today, and with `gitleaks` the built-in patterns shall still run first, so no refusal the floor gives today is lost; evidence: the existing pre-commit secret tests passing under both settings. (serves EPC-022 AC-101)
- AC-3 At `block`, a gitleaks binary that is missing, not the pinned version or not the pinned checksum shall refuse the commit naming the pin and the doctor check; at `warn` the hook shall warn and run the built-in scan; evidence: one test per case and level. (serves EPC-022 AC-101)
- AC-4 The hook shall read `.gitleaksignore` and `.gitleaks.toml` from the working tree, and the documentation shall state that a commit-bound fingerprint cannot cover a staged finding and name the path allowlist route; evidence: a test with an allowlisted path and the doc text.
- AC-5 `codeflow doctor` shall report, for the gitleaks engine, the paths searched, the version and checksum found and the pin expected, and the hook shall make no network request; evidence: the doctor output and a test run with the network unreachable.
- AC-6 (journey) With the installed hooks in a scratch adopter project with the engine enabled and the pinned binary present, the issue's SHA-256 line shall be refused at commit and the same commit shall pass after the line is reworded; evidence: the journey output with timings under 1 s for the scan.
- AC-7 When Git concludes an automatic merge, the staged scan (the built-in patterns, and the gitleaks engine when chosen) shall run in `commit-msg` after the message checks and refuse a planted key naming the rule, path and line; each commit path shall be scanned once, the automatic merge identified by Git's `MERGE_MSG` argument checked against the repository's actual `MERGE_MSG` path (linked worktrees included), and a message path matching neither `MERGE_MSG` nor `COMMIT_EDITMSG` shall refuse the commit with a diagnostic, never skip the scan; evidence: hook tests with two clean parents and a custom merge driver that writes a fixture key (failing before the change), unchanged main content, a plain commit, a hand-concluded merge, a linked worktree and a mismatched path. (serves EPC-022 AC-101)
