# TSK-1533: The docs portal audit accepts the picomatch advisory until 2026-12-17

## Description

Source: the Director's live check of advisory GHSA-fc5q-39xc-vjpf against `picomatch`, found while triaging TSK-1528 on 2026-11-17. Filed by coord/records. The advisory falls outside TSK-1528's outcome, which adds no suppression, so it is a task of its own.

Checked here, at origin/main `ec8d5c1ab3`:

- `docs-portal/package-lock.json` resolves `picomatch` 4.0.7 (`:6512-6514`) and 2.3.2 under `anymatch` (`:2712-2714`). `assets/docs-portal/starter/package-lock.json` is the same blob.
- `docs-portal/osv-scanner.toml` and `assets/docs-portal/starter/osv-scanner.toml` hold a header and no entry. With no `--config`, osv-scanner reads only the `osv-scanner.toml` beside each lockfile (`.github/workflows/codeflow-ci.yml:1849-1853`).
- The security review job replaces every `osv-scanner.toml` in the checkout with the base commit's copies, so a new suppression takes effect once its own pull request lands (`.github/workflows/codeflow-ci.yml:1860-1862`). This task's own pull request therefore runs the audit with no entry, and its audit is red by construction. The operator lands it by admin merge.
- For the portal and the starter as shipped, every glob pattern picomatch receives is fixed text in their own config or in the pinned dependencies; none comes from a network request, a URL, page content or Markdown. The executable config (`astro.config.mjs`) is trusted owner-controlled code. Each `portal.config.json` layer id reaches Starlight's sidebar autogenerate directory (`astro.config.mjs:43`), which Starlight compares by equality and a directory-prefix test, not as a glob. A change to the config, plugins, content loaders or dependencies needs reassessment. The full triage is coord/records' findings note of 2026-11-17, with a Codex review that approved the two entries.

As the Director reported, not checked here (this session has no network):

- GHSA-fc5q-39xc-vjpf is a high ReDoS through extglob patterns, published 2026-10-19, affecting `picomatch` up to 4.0.7, with no fixed release.

This task adds one dated entry for GHSA-fc5q-39xc-vjpf to each of the two `osv-scanner.toml` files, with a reason and `ignoreUntil = 2026-12-17`. Non-goals: dependency upgrades, other suppressions, and changes to the audit step or its policy.

Accepted risk: the OSV ignore entries for GHSA-fc5q-39xc-vjpf (picomatch) in `docs-portal/osv-scanner.toml` and `assets/docs-portal/starter/osv-scanner.toml` are ID-only. OSV-Scanner 2.4.0 ignore entries carry only an ID, an expiry and a reason, so the scanner cannot bind the exception to a package or version. A lockfile change to another affected picomatch version keeps the suppression until it expires.

The operator accepted this risk until 2026-12-17 (Codex review finding F1, CWE-693, medium). On 2026-12-17 the entries are removed, or a new operator decision extends them. Still checked: CI reads suppressions from the base commit, so a PR cannot add its own, and each entry names one advisory with an expiry date and a reason. Not checked: nothing enforces reassessment when a lockfile or consumer changes before that date.
