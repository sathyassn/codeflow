# TSK-1299: One limits registry, declared once

## Description

The config audit of 2026-11-03 found 49 limits spread across the test runner, CI, hooks and guards, and coordination, most of them literal constants (for example `LS_REMOTE_DEADLINE` at `crates/codeflow-core/src/git/remote_query.rs:15`, the guard deadlines at `crates/codeflow-core/src/hooks/guard_deadline.rs:27-32`, `CHECK_INTERVAL_SECS` and `HEARTBEAT_TIMEOUT_SECS` at `crates/codeflow-core/src/coord/mod.rs:96-99`); 18 are configurable today, each in its own way. This task applies the operator's rule of 2026-11-03: "things that are operationally relevant should be made configurable - even if there is slightest hint that it may be needed ... Only on things that are security/safety related we need to have reasonably well considered and where needed ones with buffer - and even them should be internally done - meaning configurable within codeflow - and not hardcoded ... declare/define once policy".

It declares every operational limit once, in one registry: timeouts, retries, counts, sizes, waits, shard and parallel numbers, and word limits. Each entry has a key, a default, bounds, a class (operational or security) and a reason. Code reads each value only from the registry, never from a literal constant; the adopter limits page and the policy schema are generated from it; and a check fails on any new literal limit outside it.

- Operational class: the project sets the value, and the bounds are only what correctness needs (for example a timeout of at least 1 second).
- Security class: the floor and its buffer live in the registry, not in code. The project can always tighten the value, and can raise it up to the buffered ceiling where that is safe; the ceiling is sized from real scenarios (slow hosts, large repositories, cold starts). The guard deadline stays inside the guard hook timeout.
- Default to configurable: any operational value is configurable unless its registry entry states why not, as a protocol constraint.

Consumers it absorbs, without editing their records here: TSK-1301 (standalone, coord/ci: the pre-push destination probe's timeout and attempt count; integers of at least 1, defaults 30 s and 3 attempts) may land first with its own keys and is the first consumer to migrate; TSK-1278 (PR 557) adds `stall_timeout_seconds` and the heavy limits, which migrate the same way; TSK-1258 (PR 552) adds the glob matcher bound; TSK-1297, TSK-1300 and TSK-1073 AC-12 declare their values here. TSK-1279 brings back `execution.heavy_wait_seconds`, default 0, by the Director's ruling of 2026-11-03, and it migrates the same way. The model choice page of TSK-1296 is linked from the limits page. The id sync's registry fetch (`fetch` in `crates/codeflow-core/src/ids/issue.rs`) does not use TSK-1301's configured waits (`git.remote_query_timeout_seconds`, `git.remote_query_attempts`, `git.remote_fetch_timeout_seconds`): it runs under git's own waits, so no CodeFlow limit bounds it. TSK-1301 discloses it and leaves it to this task.

## Outcome

After this merges, a project maintainer can find every CodeFlow limit in one generated page, with its key, default, bounds and class, and set each one through the same route; a maintainer adding a limit declares it once.

## Deliverables

- the registry and its reader: a new module under `crates/codeflow-core/src/` (the builder names it), with the policy key placement rule applied
- the generated outputs: the policy schema entries and the adopter page `docs/limits.md` (provisional; the builder checks the docs map), covering `.codeflow/ci-wait.json` and the test-config timeout keys
- the check against new literal limits: a contract test beside the existing source scans
- the migrations: each limit of the config audit moved to read from the registry
- release note: `changelog.d/TSK-1299.md`

## Acceptance Criteria

- AC-1 Before any change, the builder shall list every limit in the config audit of 2026-11-03 and any other the source scan finds, with file:line, current value, class and reason, and for a security limit the scenarios that size its ceiling, in a `## Findings` section; evidence: the Findings table.
- AC-2 Every operational limit shall be declared once in the registry with key, default, bounds, class and reason, and code shall read it only from the registry; evidence: the registry, and the source scan of AC-5 passing.
- AC-3 Any operational value shall be configurable by the project, with bounds only where correctness needs them, unless its registry entry states why not; a value outside its bounds or of the wrong type shall refuse naming the key and the bounds, never wrapping or panicking; evidence: a test per key, set, absent and out of bounds.
- AC-4 Each security limit's floor and buffered ceiling shall live in the registry; the project can tighten it at any time and raise it up to the ceiling, the guard deadline shall stay inside the guard hook timeout, and a value past the ceiling or below the floor shall refuse naming the key and the limit; evidence: a test per security key, and a guard test at the ceiling that still refuses on time.
- AC-5 A check shall fail on a literal limit (a timeout, retry, count, size, wait, shard or parallel number, or word limit) in product code outside the registry, naming the file and line; evidence: the check failing on a planted literal and passing on the migrated tree.
- AC-6 The adopter limits page and the policy schema entries shall be generated from the registry, and a drift test shall fail when either differs from it; the page shall link TSK-1296's model page; evidence: the generator, the drift test and `codeflow validate --docs`.
- AC-7 The keys of TSK-1301, TSK-1278 and TSK-1279, and the glob matcher bound of TSK-1258, shall be migrated into the registry with their defaults and bounds unchanged, once each has landed; evidence: their tests passing unchanged against the registry.

- AC-8 (journey) In a scratch project with the installed build, a maintainer raises an operational limit, raises a security limit to its ceiling and is refused one step past it with the key named, and finds all three on the generated page; evidence: the journey output.
- AC-9 A changelog entry shall describe the registry and the page; evidence: `changelog.d/TSK-1299.md`.
