# TSK-1177: The App authority names the verdict identity and Mode B fails closed

## Description

Issue #279. Split from TSK-336 on 2026-11-01. The whole-PR review of PR 479 graded TSK-336 Very Hard (9: S2 2, S6 1, S7 1, C 2, X 1, R 2), and a Very Hard task is split before claim. TSK-336 keeps the foundation (the default branch's code judges every pull request); this task takes one outcome with the criteria that prove it, moved and not copied, each marked with its old number. The five pieces are TSK-336, TSK-1175, TSK-1176, TSK-1177 and TSK-1178.

A check bound to a job name under the Actions app id (15368) can be produced by any workflow in the repository. One authority job, only for `pull_request_target` into the default branch, is the only job that references `environment: codeflow-authority`; it mints a dedicated GitHub App's installation token inside the one step that creates the `authority:` check runs on the head SHA, and ruleset B (TSK-1080) pins those names to the App's id. Without the App (Mode B, a lower tier), the final step lists check runs and statuses of the trusted names and fails on any other producer present when it runs; it does not close forgery by a later producer, which only Mode A does (review of fc1a9acb1, F1). The hosted report prints the content verdict and the authority line separately. AC-12 (the report line) is here and not with TSK-336 as the review proposed: it names "check identity: App `<id>` or Actions" and the host rules, which this task establishes, so TSK-336 would otherwise print an identity it does not yet produce.

Files shared by the five pieces (`codeflow-ci.yml`, `codeflow-policy.yml`, their installed copies and baselines, `ci.rs`): one writer at a time, as TSK-336's contract says; the Coordinator orders the writers. File sharing adds no scheduling dependency.

Outcome: **only the default branch's authority job, holding an App token confined to one step, creates the `authority:` check runs on the head SHA; without the App the final step fails on any other producer of a trusted name present when it runs, a lower tier that does not close forgery by a later producer; and the hosted report prints the content verdict and the authority line separately.**

Non-goals: the verdict jobs themselves (TSK-336); ruleset writing (TSK-1080, complete).

## Outcome

after this merges, with the App configured (Mode A) a verdict check on a pull request can be produced only by an identity the agent cannot hold; without the App (Mode B) the check fails on another producer present when each verdict job ends, and a later producer can still satisfy it.

## Findings

### The pinned token action and why the job mints its own token (AC-5), 2026-11-05

Read from the action's source at tag `v3.3.0`, the newest release
(published 2026-10-12), commit `64ab729a6294000f5aa4a4bc0b73d1f32bc45510`
(`gh api repos/actions/create-github-app-token/git/ref/tags/v3.3.0`).

- **Inputs** (`action.yml` at that commit): `client-id` (preferred),
  `app-id` (deprecated in favour of `client-id`), `private-key` (required),
  `owner`, `repositories`, `enterprise`, `skip-token-revoke` (default
  `false`), `github-api-url`, and one `permission-<name>` input per App
  permission, `permission-checks` among them. Outputs: `token`,
  `installation-id`, `app-slug`. It runs on `node24` with a `post` step.
- **Masking:** `lib/main.js:48` registers the token with the runner
  (`core.setSecret`) before `lib/main.js:50` sets it as the step output
  `token`, so the value is masked in every later log line of the job.
- **Revocation:** `lib/main.js:54-58` saves the token to the action's
  state unless `skip-token-revoke` is set, and `lib/post.js` revokes it
  (`DELETE /installation/token`) in the post step at the end of the job,
  warning but not failing when revocation fails.
- **Consequence for AC-1.** The action's token is a step output, readable
  by every later step of the job through `steps.<id>.outputs.token` until
  the post step runs. AC-1 requires the token confined to the one step that
  creates the check runs and never an output. So the authority job uses the
  equivalent JWT step AC-1 allows, following GitHub's documented Bash
  example ("Generating a JSON Web Token (JWT) for a GitHub App", section
  "Example: Using Bash to generate a JWT": `openssl dgst -sha256 -sign`,
  `iat` 60 seconds in the past, `exp` at most 10 minutes ahead). In that one
  step it signs the JWT, masks it, exchanges it for an installation token
  scoped to this repository and `checks: write`, masks that, creates and
  concludes the check runs, and revokes the token on exit (REST "Revoke an
  installation access token"). Credentials reach `curl` through a header
  file in a mode-0700 temporary folder, never its argument list. The job
  runs no third-party action, so no code outside the workflow file sees the
  key.
- **Not yet confirmed on the scratch repository.** The hosted half of this
  check (the masked output in a real log, and which steps can read the
  token) waits for hosted runners, which this task may not use until the
  EPC-022 candidate and PR 616 land. The source reading above is the
  evidence so far, and the difference from AC-1's first option (the token
  is a step output) went to the Coordinator with this build.
- Sources: https://github.com/actions/create-github-app-token/tree/v3.3.0,
  https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app,
  https://docs.github.com/en/rest/apps/installations, all read on
  2026-11-05.

### How a genuine verdict check is told from another producer, 2026-11-05

Read live on `sathyassn/codeflow` pull request 622 (head `7dbe69c8`):

- A `pull_request_target` run of `codeflow-policy.yml` reports its check
  runs on the pull request's head SHA; its workflow run has
  `event: pull_request_target`, `path: .github/workflows/codeflow-policy.yml`
  and its own `check_suite_id` (`gh api
  repos/sathyassn/codeflow/actions/workflows/codeflow-policy.yml/runs?event=pull_request_target`).
- Every check run on that SHA carries `app.id` 15368 (GitHub Actions) and
  its `check_suite.id`; `actions/runs?check_suite_id=<id>` returns the one
  workflow run with its `event` and `path`. A cancelled older run of the
  same workflow left its own check of the same name on the head.

So the final step accepts a check run of a trusted name only when GitHub
Actions created it in a `pull_request_target` run of this workflow's own
path, which only the default branch's file can produce, and accepts no
commit status of a trusted or authority name. Older runs of the same
workflow for the same head (a body edit, a re-run) stay genuine.

### What Mode B does not close, 2026-11-05

The review of fc1a9acb1 (F1) showed that the refusal is one read, when
each verdict job ends, and GitHub's required check takes the newest
check run of a name. A producer that runs later is never seen: for
example a head-branch workflow on `pull_request: labeled`, an event the
policy workflow does not run on, with a job named `trusted: commit
standards` that succeeds. So Mode B is a lower tier that does not close
forgery by a later producer; only Mode A, where ruleset B pins the
`authority:` names to the App, closes it. The workflow comments, the
changelog, `remote protect`, `doctor --check remote-perimeter` and the
report line say so, and the AC-3 fixture script records the host's
behaviour (`later-producer`). The authority job's own refusal now runs
before it creates any check, so in Mode A a refusal leaves the
`authority:` checks uncreated and the merge blocked.
