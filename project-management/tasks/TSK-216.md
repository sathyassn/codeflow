# TSK-216: CodeFlow guards and gate work inside its own Claude sandbox

## Description

Three defects make CodeFlow fight its own Claude sandbox or let a
protected branch move. Issue 23: on macOS the git guard refuses
`sed -i '' ...`, and an empty `rm ''` operand, as an edit of the
enforcement files whenever the cwd is a worktree under
`<root>/.claude/worktrees/`. Issue 24: the full gate refuses with
`gate lock unavailable` inside the sandbox the shipped presets install,
because they do not allow writes to `~/.codeflow/locks` or
`~/.codeflow/gate-runs`; `codeflow doctor` misses that and, in the
sandbox, reports offline and signed out of Codex when neither is true. A
gap found on 2026-10-03: the guard allows `git branch -f main HEAD~3`, a
local rewind of a protected branch. The review of PR 36 found more ways
past the same guards, which this task also closes: BSD `sed -l`, the
`sed` `w` command, branch expressions such as `@{-1}`, `find -exec` and
`xargs`, and recursive deletion of live worktrees.

Scope: the guards' reading of these commands, the presets' sandbox write
roots, the gate's refusal text and the doctor checks. Two full gates must
still never run at once on one machine. Non-goal: the Claude and Grok hook
command strings in the presets, which another task changes (issue 29).

The guard is a fail-closed floor, not a sandbox (orchestrator decision,
review round 2). Its text floor is new hardening over 3.0.0's
command-specific checks and must keep every refusal they made: a command
that can change files and names an enforcement path anywhere in its text,
in any spelling the file system reads as one, is refused; precise parsing
may only clear a false positive. Each command, pipeline members and
shell bodies included, is judged from every directory a literal `cd`,
`pushd`, `env -C` or `env --chdir` on its line can move it to; globs are
expanded from there, symbolic links and registered worktrees included.
With a directory filled in at run time, a writing command whose words
could name an enforcement path by their names alone is refused. An
expansion reads at most 4,096 directory
entries, and past that the directory it starts from decides. A
differential test compares the guard
with one built from `origin/main`. Known limits, left to the OS sandbox's
write denies in Claude sessions:

- a path built from parts at run time, which no argument and no other
  text on the command line spells;
- an `xargs` or `sed -f -` fed from a source the line does not show;
- moving a worktree folder (`mv .worktrees elsewhere`), which is
  recoverable but breaks its registration;
- an unresolved delete target run from a checkout that holds no
  registered worktree, such as `rm -rf "$d"` inside a linked worktree;
- a glob that only reaches an enforcement path through a symbolic link
  inside a directory of more than 4,096 entries that holds no
  enforcement files;
- a symbolic link with an unrelated name, used from a directory filled
  in at run time, which the guard can judge only by its name;
- `env -S` and `--split-string`, which pack the command into one word.

A complete model of shell commands is a design question for a later
task.

## Acceptance Criteria

- AC-1 When git-guard judges, with the cwd in a linked worktree under
  `<root>/.claude/worktrees/<name>`, `sed -i '' 's/a/b/'` on a scratch
  file or `README.md`, `rm -f ''`, `rm -f .`, `sed -i` and `sed -i.bak`,
  it allows them, and it still refuses `sed -i ''` on the worktree's
  policy file, `sed -i '' -e` on its Claude settings and `rm -rf` of its
  `.claude` or `.codeflow` directory. It reads GNU and BSD sed by their
  own grammars (BSD `-l` is a flag, `sed -li ''` a cluster) and refuses a
  `sed` whose script, options, `-f` script file or backup name names an
  enforcement path, while a plain read of one passes; evidence: `hooks_cli`
  `git_guard_allows_empty_operands_in_a_claude_worktree` and
  `git_guard_refuses_sed_writes_through_bsd_options_and_the_w_command`
  fail before the change and pass after, the `git_guard` unit tests for
  BSD `sed` forms, and `test_native_sed_writes_only_paths_the_guard_judges`
  against the platform `sed`. (journey)
- AC-2 When a full gate runs in a session using a shipped Claude preset,
  the sandbox lets it write `~/.codeflow/locks` and `~/.codeflow/gate-runs`,
  the presets add no other write root under the CodeFlow home, `codeflow
  update` carries the roots into this repository's settings, an unopenable
  lock still refuses, and the refusal names `codeflow doctor --check
  permissions`; evidence: `settings_presets`
  `sandbox_allows_writes_only_to_present_state_and_the_gate_directories`,
  the gate lock unit tests, `test_gate_cli`
  `unavailable_gate_lock_refuses_before_start`, and
  `repository_update_noop`.
- AC-3 When `codeflow doctor` runs, the permissions check names each gate
  lock or evidence directory this process cannot write, with the remedy to
  allow it, and with `SANDBOX_RUNTIME` set doctor notes the marker as
  context, probes the network over HTTPS and passes only on an HTTP 2xx
  or 3xx answer, and reports a failed `codex login status` as unconfirmed
  with its error quoted, unless it says signed out; evidence: the doctor
  unit tests for permissions, network (200, 403, no answer, transport
  error) and delegates (access denied, signed out), and a doctor run in a
  sandboxed session.
- AC-4 When git-guard judges `git branch -f main HEAD~3`, `git branch -M`
  or `-C` onto a protected branch, `git checkout -B main` or `git switch -C
  main`, `git worktree add -B main`, including flag clusters (`-fv`),
  abbreviations (`--force-c`) and `@{-1}` or `@{upstream}` resolved in the
  target repository, it refuses under `git.local_ref_protection`, refuses
  a forced move it cannot resolve or whose expression an earlier git
  command on the line may change, and the same moves of a feature branch
  stay allowed; evidence:
  `hooks_cli` `git_guard_refuses_a_forced_move_of_a_protected_branch` and
  `git_guard_resolves_forced_moves_of_a_protected_branch` fail before the
  change and pass after, and the `git_guard` unit test
  `test_forced_branch_move_of_protected_blocked`.
- AC-6 When git-guard judges a `find`, `xargs` or `parallel` that can
  change files and whose command line names an enforcement path or
  worktree folder (in a `sh -c` string, a producer in the pipeline or a
  shell variable's value, in any spelling the file system reads as one,
  including a glob that reaches one through a symbolic link or from the
  directory a `cd`, `env -C` or `env --chdir` moves to, in a pipeline
  member or a `sh -c` body (`env -C`, `xargs` and `find -exec` bodies
  alike), a word that could name one by name after a directory filled in
  at run time, behind a launcher
  such as `nice` or `timeout`, or behind a launcher option it cannot
  read), a recursive `rm` or a
  `chmod` or `chown` of a directory holding enforcement files from any
  checkout, a `find` action that reaches an enforcement file in expression
  order or from a match's own directory, or a recursive `rm`, `trash`,
  `find -delete` or `git clean -ff` of a registered worktree, a directory
  holding one (`.worktrees`, `.claude/worktrees`, `..` from a worktree, a
  symlinked spelling) or an unresolved target in a checkout that holds
  worktrees, it refuses under `git.hook_integrity`; read-only and
  unrelated forms, including `find build -print0 | xargs -0 rm`,
  `find build -delete` and a glob over a build directory of more than
  4,096 files, stay allowed; evidence: `hooks_cli`
  `git_guard_refuses_enforcement_writes_through_xargs_and_find`,
  `git_guard_refuses_recursive_deletion_of_registered_worktrees` and
  `git_guard_holds_the_text_floor_for_wrapped_writes`,
  `git_guard_refuses_the_reviewers_commands` and
  `git_guard_judges_recursive_changes_by_the_files_they_reach` fail before
  the change and pass after, the `git_guard` unit tests for glob
  expansion (including a file name that is not UTF-8, on Linux), the
  directories a script can run in and words read by name alone,
  `remedy_clearing` `clears_worktree_delete`,
  and `git_guard_keeps_every_baseline_refusal` run against a guard built
  from `origin/main`.
- AC-5 The pending 3.1.0 CHANGELOG entries, under their release-impact
  markers, state each fix and who it affects; evidence: the diff and the
  release-impact check.
