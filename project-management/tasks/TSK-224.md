# TSK-224: Plain product page, README tiers, progressive docs order and Pages hosting

## Description

CodeFlow's public documentation does not yet say plainly what the product is.
The README opens with traits, the product page mixes the thesis with
non-goal tables, the docs have no reading order, and many pages carry
mannered prose and walls of text. This task rewrites them from one source and
hosts the guide, in the operator's order (RELEASE-PLAN.md, "After 3.0.0:
documentation and README", operator review of 2026-10-01).

- `docs/product.md` is rewritten in plain language: what CodeFlow is, who it
  is for, what it does, what it is not, with one ASCII figure of the four
  enforcement planes. Every later page takes its wording from it.
- The README opens with what CodeFlow is and the problem it solves, links
  the product page near the top and carries the init tiers as a table of what
  each installs and when to pick it.
- The docs are listed in one reading order by reader need: understand,
  start, use, configure, reference, maintain. The README Docs section and
  the portal navigation use the same order.
- Every user-facing document is swept against `.codeflow/rules/writing.md`
  and the editorial smells list; each claim touched is checked against the
  code or the CLI help.
- The portal draws the same flows as figures, and a GitHub Pages workflow
  builds and deploys it to `https://sathyassn.github.io/codeflow/`. The
  address is not live until the operator enables Pages.
- Links from files the source archive keeps into `docs/verification/`, which
  the archive leaves out (`.gitattributes` `export-ignore`, TSK-202), point
  at the published copy on `main`.

Non-goals: no change to product behaviour, policy, hooks, guards or CI
gates; no change to ADR decisions (a link target is not a decision); no
change to the reading-chain files (AGENTS.md managed block and skills); the
portal runtime scripts stay as shipped (only the project-owned
`portal.config.json` and figure declarations change). Enabling Pages in the
repository settings is the operator's step.

## Deliverables

- Product page: `docs/product.md`
- README: `README.md`
- Docs reading order: `README.md` (Docs section) and `docs-portal/portal.config.json` (layers)
- Prose sweep of the user-facing docs: `docs/*.md`, `docs/architecture/`, `docs/capabilities/`, `docs/capabilities.md`
- Portal figures: `docs-portal/figures/`
- Pages workflow: `.github/workflows/portal-pages.yml`
- Archive-safe links: `docs/decisions/`, `CHANGELOG.md`, `project-management/tasks/`
- Release note: `CHANGELOG.md`
- Archive link test: `crates/codeflow-cli/tests/release_contract.rs`

## Acceptance Criteria

- AC-1 When a reader opens `docs/product.md`, it shall state in short
  sections what CodeFlow is, who it is for, what it does and what it is
  not, with one fenced ASCII figure of the four enforcement planes (git
  hooks, in-session guards, scaffolded CI, remote branch protection) and no
  Mermaid; evidence: the page itself, every behavioural claim checked
  against `codeflow --help`, `codeflow init --help`, the scaffold manifest
  and `docs/architecture/enforcement-planes.md`, and a grep for em and en
  dashes and the editorial smells in the new text.
- AC-2 When a reader opens the README, its first screen shall say what
  CodeFlow is and the problem it solves and link `docs/product.md`, and it
  shall carry a table of the three init tiers with what each installs and
  when to pick it; evidence: the README, with each tier row checked against
  `codeflow init --help` and `assets/base/scaffold-manifest.toml`.
- AC-3 The docs shall be listed in the order understand, start, use,
  configure, reference, maintain, identically in the README Docs section
  and in the portal navigation; evidence: the README, the layers in
  `docs-portal/portal.config.json`, and the built portal's sidebar order read
  from the build output.
- AC-4 Every user-facing document under `docs/` (outside `docs/decisions/`,
  `docs/verification/` and `docs/plan/`) shall be free of the mannered-prose
  patterns, break long prose into short paragraphs, bullets or tables, and
  carry an ASCII flow where a flow carries the point, with no changed fact;
  evidence: the per-file change list in the PR, a scan of the changed files
  for dash characters and the smells list, and the portal's pinned figure
  facts, which re-derive from the swept text during the build.
- AC-5 The portal shall draw the new product-page flows as figures on its
  pages, keep every figure fact bound to its source, and stay green;
  evidence: `npm run check`, `npm run build`, `codeflow validate --portal
  docs-portal` and `npm run browser:verify` with the Node version pinned in
  `docs-portal/.node-version`.
- AC-6 The repository shall carry a workflow that builds the portal and
  deploys it to GitHub Pages at the address `https://sathyassn.github.io/codeflow/` on a push to `main` that changes the portal or its sources, with
  the portal `base` set to the repository path; evidence: the workflow file,
  the portal built with that base, and the operator steps listed in the PR.
  The address is not live until the operator enables Pages.
- AC-7 When the source archive is extracted, no Markdown link in a kept file
  other than the frozen CHANGELOG shall point into `docs/verification/`;
  evidence: the new `release_contract` test
  `kept_markdown_does_not_link_into_the_evidence_the_archive_leaves_out`,
  which fails with a relative link put back and passes on the change. The
  CHANGELOG's one link sits in the published 3.0.0 section, which the release
  tree check keeps byte-identical, and waits for a dated erratum.
- AC-8 When a reader follows the journey from the README to the product
  page, the docs index and a portal page, every link shall resolve; evidence:
  `codeflow validate --docs`, the portal link check in the build, and the
  built portal opened in a browser at desktop and phone widths. (journey)
