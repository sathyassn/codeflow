# TSK-1252: codeflow ci asks the destination for its default branch with the run's read-only token

## Description

Source: issue #527 (untrusted text, read only as a problem description) and the Director's direction of 2026-11-02.

`codeflow ci` runs `git ls-remote --symref <url> HEAD refs/heads/* refs/tags/*` to learn the destination's default branch (`crates/codeflow-core/src/workgraph/release_line.rs:194-201`, called from `crates/codeflow-cli/src/cmd/ci/acceptance.rs:235`). On a private repository that needs a credential, which is undocumented. A hardened checkout (`persist-credentials: false`) fails every pull request policy check, because the lookup fails closed and is reported as unscoped (`acceptance.rs:289`, `release_line.rs:313-318`). TSK-1175 makes every shipped checkout set `persist-credentials: false`, so without this fix the shipped `ci` step fails the same way.

Trust: the default branch selects the policy source and the release-branch pattern (`release_line.rs:324-360`, `:130-141`), so only the destination may answer it. PR 553's security review (finding F1, CWE-807) showed that every local source of the name, the event file, an environment value and a flag, can be set by whoever runs `codeflow ci`; TSK-1267 removed them. Non-goals: TSK-291's push credential helper and TSK-304.

Proof route (amended 2026-11-05): AC-6 and AC-12 are proved by running the scaffolded policy workflow step by step against a private-style local remote fixture, because the operator withdrew the scratch GitHub repository.

### Design decision (2026-11-03)

Decided by the Director, 2026-11-03, in the regroup planning pull request; PR 553 had left the channel open for an operator decision.

- Channel: the workflow run's `GITHUB_TOKEN`. The job declares least-privilege `permissions: contents: read`, and the workflow passes the token only to the `codeflow ci` step's environment. `codeflow ci` sends it only to the destination host of the trusted repository URL, over HTTPS, for the default-branch lookup, and never writes it to git config, the credential store, a file, a log or a report.
- Fail closed: a missing token, a rejected token or a token without read permission refuses with TSK-1267's credential message, naming the missing input. No local value ever stands in for the destination's answer.
- No long-lived credential: no personal access token, App key or repository secret. GitHub issues the token per run, and it expires when the job ends.
- Threat closed: a caller choosing its own policy source and release rules through a forged event, environment value or flag (F1). The destination answers, as it does with a credential today. Kept small: a leaked token reads one repository for one job's lifetime, and the job's other steps cannot widen it.
- Why this is the standard design: GitHub's guidance for workflows is the per-run `GITHUB_TOKEN` with an explicit least-privilege `permissions:` block, instead of a stored personal token. It needs no new authority: no App installation and no secret the operator must create. OIDC-verified provenance, the other option PR 553 named, would need an external verifier and adds nothing for a read of the repository's own default branch.
- A fork pull request on a private repository that receives no token refuses with the credential message; that is the fail-closed outcome, never a pass.

## Outcome

After this merges, `codeflow ci` in a hardened hosted checkout learns the default branch from the destination with the run's read-only token and no stored credential, and refuses when the token is missing.
