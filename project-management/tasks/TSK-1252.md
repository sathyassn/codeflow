# TSK-1252: codeflow ci asks the destination for its default branch with the run's read-only token

## Description

Source: issue #527 (untrusted text, read only as a problem description) and the Director's direction of 2026-11-02.

`codeflow ci` runs `git ls-remote --symref <url> HEAD refs/heads/* refs/tags/*` to learn the destination's default branch (`crates/codeflow-core/src/workgraph/release_line.rs:194-201`, called from `crates/codeflow-cli/src/cmd/ci/acceptance.rs:235`). On a private repository that needs a credential, which is undocumented. A hardened checkout (`persist-credentials: false`) fails every pull request policy check, because the lookup fails closed and is reported as unscoped (`acceptance.rs:289`, `release_line.rs:313-318`). TSK-1175 makes every shipped checkout set `persist-credentials: false`, so without this fix the shipped `ci` step fails the same way.

Trust: the default branch selects the policy source and the release-branch pattern (`release_line.rs:324-360`, `:130-141`), so only the destination may answer it. PR 553's security review (finding F1, CWE-807) showed that every local source of the name, the event file, an environment value and a flag, can be set by whoever runs `codeflow ci`; TSK-1267 removed them. Non-goals: TSK-291's push credential helper and TSK-304.

### Design decision (2026-11-03)

Decided by the Director, 2026-11-03, in the regroup planning pull request; PR 553 had left the channel open for an operator decision.

- Channel: the workflow run's `GITHUB_TOKEN`. The job declares least-privilege `permissions: contents: read`, and the workflow passes the token only to the `codeflow ci` step's environment. `codeflow ci` sends it only to the destination host of the trusted repository URL, over HTTPS, for the default-branch lookup, and never writes it to git config, the credential store, a file, a log or a report.
- Fail closed: a missing token, a rejected token or a token without read permission refuses with TSK-1267's credential message, naming the missing input. No local value ever stands in for the destination's answer.
- No long-lived credential: no personal access token, App key or repository secret. GitHub issues the token per run, and it expires when the job ends.
- Threat closed: a caller choosing its own policy source and release rules through a forged event, environment value or flag (F1). The destination answers, as it does with a credential today. Kept small: a leaked token reads one repository for one job's lifetime, and the job's other steps cannot widen it.
- Why this is the standard design: GitHub's guidance for workflows is the per-run `GITHUB_TOKEN` with an explicit least-privilege `permissions:` block, instead of a stored personal token. It needs no new authority: no App installation and no secret the operator must create. OIDC-verified provenance, the other option PR 553 named, would need an external verifier and adds nothing for a read of the repository's own default branch.
- A fork pull request on a private repository that receives no token refuses with the credential message; that is the fail-closed outcome, never a pass.

## Outcome

After this merges, `codeflow ci` in a hardened hosted checkout learns the default branch from the destination with the run's read-only token and no stored credential, and refuses when the token is missing.

## Acceptance Criteria

- AC-1 With `persist-credentials: false` and no stored credential, `codeflow ci` in the hosted policy workflow shall resolve the destination's default branch by asking the destination with the run's `GITHUB_TOKEN`, passed only to the `codeflow ci` step, with the job's `permissions:` limited to `contents: read`, and pass; evidence: a fixture remote that requires the token, failing before and passing after.
- AC-2 When the token is missing, rejected or lacks read permission, `codeflow ci` shall fail closed with TSK-1267's credential message naming the missing input, and no local value (event file, environment value or flag) shall select the default branch or release scope; evidence: one fixture per case, and PR 553's forged-event fixture still refusing.
- AC-3 The token shall go only to the destination host of the trusted repository URL, over HTTPS, only for the lookup, and never to another host on a redirect; it shall never be written to git config, the credential store, a file, a log or a report; evidence: a fixture that records each request's headers, a redirect fixture, and a scan of the run's output and files for the token value.
- AC-4 The docs shall name the lookup, the token channel, the required `permissions:` and the hardened-checkout route, and the shipped workflows shall set those permissions and pass the token only to the `ci` step; evidence: the docs diff, the workflow diff and the help output.
- AC-5 A cross-lineage security review shall cover the change, with the seat checked live, and the pull request shall state the threat it closes and why the run-scoped, least-privilege token is the standard design; evidence: the review verdict and the pull request body.
- AC-6 A scaffolded adopter workflow with `persist-credentials: false` shall pass its pull request policy check on a private-style remote with only the run's token, and refuse with the credential message when the step receives no token; evidence: the run output. (journey)
- AC-7 The managed workflow shall carry no long-lived credential: the `ci` step reads no personal access token, App key or repository secret; evidence: a scaffold test that asserts the step's environment and the job's `permissions:`.
- AC-8 (was TSK-1267 AC-2) The destination shall be asked only when the answer needs its branch tips, and when it is asked and fails for want of a credential, the error shall say so and name the fix; evidence: a test for each of the two cases and the error text.
- AC-9 (was TSK-1267 AC-3) `codeflow ci --help` shall document that the destination lookup on a private repository needs read access, and the managed workflow shall be unchanged; evidence: the help text and the managed-asset consistency test.
- AC-10 (was TSK-1267 AC-4) (journey) On the 4.0.0 path, with an `Authorization` header injected through `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n` and `GIT_CONFIG_VALUE_n` and scrubbed as `judging_command()` scrubs it, a private-repository fixture shall refuse with the AC-2 message, and no `Authorization` header shall reach the destination; evidence: the fixture output with the captured request headers (no scratch GitHub repository; operator direction 2026-11-02, relayed by coord/parallel).
- AC-11 (moved from TSK-1175 AC-1) Every shipped checkout disables credential persistence. Later private-repository fetches still work through an explicitly scoped authentication mechanism that is not left available to repository code.
  - Moved from TSK-336 AC-4: one mechanism, separable from verdict identity.
- AC-12 (moved from TSK-1175 AC-2) (journey) Template tests shall cover every checkout and event class this task changes, and hosted evidence shall prove a valid integration pull request and the negative case in which later repository code reads no checkout token; evidence: the template tests and the hosted run URLs.
  - Moved from TSK-336 AC-5, the per-surface part; the update-route run over the whole resulting set is TSK-1178 AC-3. (serves EPC-022 AC-33)
