# TSK-083: qualify harness answers its own trust prompt

## Description

The release qualification harness waits for a human on a trust prompt the
workspace rule of 2026-09-22 says the agent answers. At commit `814cbebeb`
(branch `fix/qualify-trust-prompt`, carried by
`integration/EPC-014-public-docs` and `integration/EPC-016-visual-guide`),
`tests/release-qualification/qualify.sh` builds a human-only reason, sets the
owner to a human, prints "ACTION NEEDED: a human must answer" and polls for
an answer. Changing its comment would not change that behaviour.

Change the behaviour: when the pane's trust prompt names the path of the
sample this run created (path identity against the run's own `$DIR`,
resolved to a real path), the harness answers it and continues, recording
that it did; any other path keeps today's bounded wait for the operator with
an accurate reason and owner. Diagnostics and the evidence owner say which
case applied. Point the comment at `cf-method/references/autonomy.md`.

Guard (EPC-018 `harness:present-at-merge-forward`): the harness is absent
from this epic's base (`e6121491e`) and from `origin/main` (`93b7b222c`). The
guard is observed once, by TSK-086 when it merges `main` forward, and this
task depends on TSK-086, so `codeflow work start` refuses it before then.
Present: this task runs and lands before TSK-078 prepares the pull request.
Absent: its status becomes `cancelled` with the evidence, and one tracked
item carrying this description and these criteria goes to the harness's
owning line; TSK-078's pull request names it. This task is in no other
task's `depends_on`, so a cancelled outcome blocks nothing.

## Affected surfaces and interfaces
