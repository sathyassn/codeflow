# TSK-1057: The policy authority cannot be weakened by a direct ref write

## Description

This is a planning draft accepted from the TSK-397 design note, revision 4.1, Part C (pull request 331), where it is unit U4 (authenticated policy authority). The note called the unit 3.3.0; the release is 4.1.0. Part C is accepted as planning drafts only: the criteria below are drafts, and this unit takes its own whole-unit review when it is built. Part C decisions (i) to (v) apply: (i) explicit non-secret enforcement-file arguments are allowed on a qualified host under attested `W-enforcement`, and the secret-read classes override, never a file name; (ii) a patch update invalidates a record, because exact executable digests bind it and a changed binary is `Unknown` until the operator re-runs the ceremony; (iii) managed settings are a design requirement for qualification, not a vendor fact; (iv) no exclusion matcher ever, so a non-empty `excludedCommands` disqualifies and route A+ is dropped; (v) the ceremony runs through the Bash tool, never the `!` prompt, and its evidence is receipts, not operator attention.

`landed_policy` reads the landed policy from a remote-tracking ref, and a direct write to `refs/remotes/*` or `packed-refs` can weaken it. This unit keeps a baseline copy of the landed policy and enforces the stricter of the two. A copy is only as sound as its source, so the baseline is bound to an independently authorized repository, authority and exact commit, and only a command behind an enforced boundary, not a name or a flag, creates or replaces it.

Edges: depends on TSK-397, whose H-5 change denies `~/.codeflow/authority/` in 3.2.0 and so protects the baseline written there, as it protects TSK-1054's receipts. TSK-1055 (U2) depends on this unit, because the general run-time rule relaxes only after it has landed.

Non-goal: a sandbox deny on `refs/remotes` (AC-4).

Amended 2026-10-29 by the content policy amendment (issue #279, design
revision 5; EPC-022 section of that date). TSK-1077 (EPC-022) makes the
default branch at one SHA the only local policy authority, removes the
line-sourced exceptions and the `origin/main` guess, and refuses the
empty-namespace and unset-HEAD states. This task now builds on that
resolution and depends on TSK-1077, which owns `landed_policy.rs` and
`push_set.rs` until it lands. The design raised the empty-namespace
fallback to medium (D-9): the condition also follows deleting the
tracking refs or removing the remote, and in session git-guard does not
refuse `git remote remove`, `rm`, `set-url` or `set-head`, nor `git
symbolic-ref refs/remotes/<remote>/HEAD <other>` (`check_symbolic_ref` at
`crates/codeflow-core/src/hooks/git_guard.rs:11032-11058` strips only
`refs/heads/`, at `:11046`).

Placement, decided 2026-10-29: this task stays in EPC-023. It is the
baseline half of the 4.1.0 qualification (TSK-1055 depends on it), and
its integration target is already the EPC-022 line, so moving it into
EPC-022 would only let an unfinished baseline hold the 4.0.0 close. Its
link to the content policy is the edge from TSK-1077.

## Outcome

after this merges, an operator can rely on the landed policy even if an agent rewrites a remote-tracking ref to a weaker one.

## Findings (AC-7)

Recorded 2026-11-15 on base `5405cdb1b8` (the EPC-022 line, TSK-1077 and TSK-397 complete), before any code change.

How `landed_policy` resolves the authority (`crates/codeflow-core/src/hooks/landed_policy.rs`):

- The remote is `origin` when configured, else the only remote; several remotes without `origin` refuse as ambiguous, and no remote is the labelled local-only state (`:111-130`).
- The tracking namespace `refs/remotes/<remote>/*` must hold a ref. When it is empty, the session guards ask the remote once (`advertises_refs`, `:195-235`, after `remote_identity::verify`); `load_local` refuses without asking (`:138-142`).
- The authority is `refs/remotes/<remote>/HEAD`, which must be symbolic and name a non-`HEAD` branch under `refs/remotes/<remote>/`; its commit is read once and the policy and project settings come from that commit's tree (`default_branch`, `:239-297`, and `at_commit`, `:545-562`).
- A loose ref file that is a symbolic link, or passes through one, or is not a regular file, marks the read as doubted (`ref_file_doubt`, `:299-347`): `text_guard: relaxed` and `trusted_client_configs` are then not honoured (`:95-105`). A packed ref is read as it is. The read does not authenticate the refs: whoever can write `.git` can set them, which this task addresses.

Refusal and labelled states it reports:

| State | Result | Where |
|---|---|---|
| unborn `HEAD`, no repository commit | working copy, labelled local only | `:108-110` |
| no remote | `HEAD`, labelled local only | `:122` |
| several remotes, none `origin` | refused: ambiguous | `:124-128` |
| empty namespace, not asked (`load_local`) | refused | `:138-142` |
| empty namespace, remote advertises no refs | `HEAD`, labelled initialization | `:149-153` |
| empty namespace, remote has refs | refused: run `git fetch <remote>` | `:154-156` |
| empty namespace, remote identity not verified or not reachable | refused | `:157-162` |
| `refs/remotes/<remote>/HEAD` missing | refused: authority unset, operator runs `git remote set-head <remote> -a` | `:244-250` |
| remote `HEAD` direct, outside the remote, `HEAD` itself, not UTF-8, or names a symbolic ref | refused | `:257-289` |
| branch or commit unreadable, invalid policy | refused | `:282-292`, `:554-556` |

Routes that can remove, re-point or empty the authority remote's tracking refs and `refs/remotes/<remote>/HEAD`:

| Route | Judged today by |
|---|---|
| `git remote remove`, `rm`, `rename`, `set-url`, `set-head`, `add` | in session: git-guard `git.policy_authority` through `ref_authority::check` (`ref_authority.rs:74-84`, called at `git_guard.rs:9596`); the record's earlier `git_guard.rs:11032-11058` citation predates TSK-1077 |
| `git symbolic-ref refs/remotes/<remote>/HEAD <other>`, `git symbolic-ref -d refs/remotes/<remote>/HEAD` | in session: `ref_plumbing_tampers` (`git_guard.rs:12680-12689`, via `ref_authority.rs:60-63`), which refuses any write or delete naming `refs/remotes/` |
| `git update-ref` and `git update-ref -d` of `refs/remotes/<remote>/*` | in session: the same `ref_plumbing_tampers`; also `git.local_ref_protection` for a protected branch (`git_guard.rs:11764-11777`) |
| `git branch -d -r <remote>/<branch>` | in session: `ref_authority.rs:64-73` |
| `git config` writes to `remote.*`, `url.*.insteadOf`, `include*`, `fetch.followRemoteHEAD`, and the same as `-c` or `--config-env` | in session: `ref_authority.rs:4-53` |
| `git fetch` with a destination ref or `--refmap` | in session: `ref_authority.rs:357-363` |
| shell writes to `.git/refs/remotes/**` or `.git/packed-refs` | in session: `git.hook_integrity` integrity prefixes (`git_guard.rs:2046`, `:4540`); edit-guard for Write and Edit |
| `git fetch --prune`, `git remote prune` | allowed: they delete only refs the remote no longer has, through the remote's own mapping |
| any of the above out of session (a terminal, a script, a harness without these guards, an unsandboxed retry) | none: the reference-transaction hook does not refuse remote-tracking updates (`git_hook.rs:999`); this task's baseline is the check that holds there |

So in-session git-guard already refuses every command AC-6 names. The gap this task closes is out of session and direct file writes: there a weaker policy can still reach `refs/remotes/<remote>/<branch>` or `packed-refs`, and the guards read it as the authority.
