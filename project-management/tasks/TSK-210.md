# TSK-210: the secret scan reads its exemptions from the trusted commit

## Description

A consuming project reported (sathyassn/codeflow#20) that the required
`secret scan` check can be passed by the pull request it scans. The
adopter CI template's gitleaks step (`assets/base/ci/codeflow-ci.yml`)
and this repository's own (`.github/workflows/codeflow-ci.yml`) run
gitleaks on the pull request's checkout, so gitleaks reads
`.gitleaksignore`, `.gitleaks.toml` (and `.gitleaks.json` beside it) and
inline `gitleaks:allow` comments that the same pull request can add for
the secret it leaks. Both steps also download and unpack the gitleaks
archive inside the checkout, so a file or link the pull request commits at
that name is written through. This task reads every exemption from the
trusted commit instead (the pull request's base SHA, or the pushed SHA on
a push), as CodeFlow already does for work records (TSK-102: a change
cannot exempt its own commit), keeps the adopter's own configuration and
TSK-206's behaviour, and moves the download under `$RUNNER_TEMP`. An
adopter's new exemption takes effect once its own pull request merges.
Non-goal: changing which rules the scan runs.

## Acceptance Criteria

- AC-1 When a pull request adds a secret together with an exemption for
  it, by a `.gitleaksignore` entry, a `.gitleaks.toml` allowlist, a
  `.gitleaks.json` beside a `.gitleaks.toml`, or an inline
  `gitleaks:allow` comment, the template's secret-scan step fails; when
  the same exemption is already on the trusted commit, the scan passes;
  evidence: a fixture test running the template step with the pinned
  gitleaks 8.30.1 over each case, failing on the old step and passing
  after the fix. (journey)
- AC-2 When the trusted commit cannot be read, the step fails before it
  scans; evidence: the same fixture.
- AC-3 The gitleaks archive is downloaded and unpacked under
  `$RUNNER_TEMP`, and a `.gitleaksignore` or `.gitleaks.toml` that the
  pull request commits as a symbolic link is removed without its target
  being touched; evidence: the fixture, with a planted link.
- AC-4 A trusted `.gitleaks.toml` whose `[extend]` names a path is never
  resolved against the pull request's checkout: the extended file is read
  from the trusted commit, or the step refuses with a message naming the
  fix; evidence: the fixture and the template comment.
- AC-5 TSK-206 still holds: the 3.0.0 pipeline-prose allowance, failure on
  a scan that logs an error or reads no commit, and the adopter's own
  trusted configuration; evidence: `scripts/check-scaffold-gitleaks.sh`
  passing.
- AC-6 This repository's own `secret scan` job reads its exemptions the
  same way; evidence: the workflow diff and that job passing on this
  pull request.
- AC-7 The CI README and the pending 3.1.0 CHANGELOG entry (with its
  release-impact marker) say that exemptions come from the trusted commit
  and take effect after their own pull request merges; evidence: the diff.
