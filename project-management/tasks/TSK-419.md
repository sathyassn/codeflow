# TSK-419: Epics are sized to one value line and built one at a time per stream

## Description

Issue #280, items 1 and 4 and the comment of 2026-10-22. A full-tier
project on 3.1.1 runs 17 integration lines; several epics hold 22 to 69
tasks, and after three weeks almost no product work has reached `main`,
because an epic finishes only when all of its tasks finish and each work
stream held several open epics at once. `cf-method` "Planning an epic"
warrants an epic by the standalone test and names no size; `cf-plan`
step 5 partitions tasks by outcome and dependency. Nothing says how small
an epic should be, when to open the pull request to `main`, or how many
epics a stream builds at once.

Outcome: **the managed guidance says an epic is the smallest set of
tasks that gives a reviewer something usable on `main`, stated as one
value line ("after this merges, X can do Y"); an epic that will not fit
that line is planned as two or more epics with their merge order; the
pull request to `main` opens when a usable set of finished tasks is
ready, with unfinished user-facing work switched off; and a work stream
builds one epic at a time to completion.**

Rules the guidance states, each in plain words with an example:

- **The value line.** `cf-plan` and the epic template ask for one value
  line in the epic Summary; `cf-method` "Planning an epic" adds it to the
  clarity checklist. Size numbers, where given, are an orientation range,
  never a cap ("Only the operator adds process").
- **Split, with merge order.** A brief whose outcome needs more than one
  value line becomes two or more epics; the plan names which merges
  first and the edge between them.
- **Early pull request to `main`.** Open it when a usable set of finished
  tasks is ready, not only when the epic is done; unfinished user-facing
  work stays off on `main` behind a flag, a disabled default or an
  unwired entry point, named in the PR, so a partial merge never shows
  half-built work. The epic's remaining tasks continue on the line. The
  precondition is TSK-433: until it lands, `codeflow ci` judges a line's
  own reopened and amended completions as foreign in a pull request
  into `main` (18 blocking findings on the 3.2.0 line head
  `29a217556`), so the guidance names TSK-433's class and this task is
  dispatched after it lands.
- **One epic at a time per stream.** A stream builds one epic to
  completion (all tasks landed, closed, PR to `main`); the next epic's
  planning and reviews may run alongside, and the next build starts only
  while the current epic waits on something outside the stream. The
  managed map's "shape a request" and "land a batch" rows carry the rule.

Non-goals: a cap on epic size; a status view of streams (TSK-420 shows
line drift; the per-stream view is TSK-311's in 4.1.0); changing how
epics close.

Added by the EPC-022 amendment of 2026-10-22 under the operator's
decision of that day (project-management changes go in 3.2.0). This
amendment applies the rule to EPC-024.
