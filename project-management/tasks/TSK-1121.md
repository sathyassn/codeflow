# TSK-1121: A present document on a topic is revised in place with its version history and per-view change marks

## Description

The operator's feedback of 2026-10-31: things must be reused where it
makes sense, each time a report on a topic is presented, so tokens and
effort are not wasted redoing them, with proper revision or versions; and
it cannot be random, with too much change and no consistency from one
report to the next. The runtime already keeps immutable revisions per
session with a block digest per block (`crates/codeflow-present/src/state.rs:137`,
`RevisionRecord`; `revision.rs:141`, `diff` marks a block `unchanged` or
`changed` by digest) and `codeflow present update <session> <file>
--expected-revision N` adds a revision (`cf-present/SKILL.md` section 4).
What is missing is the topic: nothing ties a new document to the sessions
that presented the same subject before, so a session asked for the same
report opens a new session and redraws everything; nothing shows a reader
which views changed since the previous revision; and an author who wants
to carry a prior revision's blocks forward has no command for it, so the
blocks are rewritten and drift.

Outcome: **a document may declare a `topic` (a stable key such as
`status:epc-022` or `design:present-shell`; a generator derives it by
lower-casing its scope key, so one scope always yields one topic); `present list --topic <key>`
finds its sessions and `present open` on a document whose topic has an
open session says so and offers `update`; a revision's shell marks each
view and each block `changed`, `unchanged`, `new` or `removed` against the
previous revision from the stored digests, in the side menu and on the
view, with a "since revision N" line in the header; `present show
<session> --revision N --blocks <ids>` and `--view <id>` print a prior
revision's blocks as document JSON so an author reuses them unchanged;
and `present diff` groups its result by view.**

```text
  report on topic T, time 1          report on topic T, time 2
  present open  -> session S, r1     present update S  -> r2
  blocks a b c d                     blocks a b' c e      (d removed)
                                     menu:  a unchanged, b changed,
                                            c unchanged, e new, d removed
                                     header: since r1: 1 changed, 1 new,
                                             1 removed
```

Figure: the second report updates the first report's session; the
runtime, not the author, works out what changed, from digests it already
stores.

Decisions, each reversible and disclosed here:

- **A topic is a key in the envelope**, `topic`, optional, lower-case
  words, digits, `:`, `.`, `_` and `-`, at most 80 characters; it names a
  subject, never a revision. The session store indexes sessions by topic
  under the present state directory; `present list --topic` lists them
  newest first with revision count and last update; `present open` of a
  document with a topic that has an open session prints the session id and
  the `update` command and opens a new session only with `--new-session`,
  so reuse is the default and a fresh start is a stated choice. A closed
  session on the topic is listed and never reopened (SKILL.md section 4).
- **Change marks come from digests, never from the author.** On a
  revision after the first, the renderer compares each block's digest with
  the previous revision's by block id (`block_digest`, `state.rs`, which
  serialises one block) and each view's digest by view id, where a view's
  digest covers its title, kind, context strip, the ordered ids of its
  blocks and children, and its place in the tree (Codex round 8, F2): a
  view is `changed` when any of those changed or any block in it changed,
  was added or removed, `unchanged` otherwise, `new` when its id is only
  in the new revision and `removed` when only in the old, listed in the
  header line and shown struck in the menu; a block id present only in the
  new revision is `new`, only in the old is `removed` and listed in the
  header line. A changed context strip with identical blocks is therefore
  `changed`, and a view moved under another parent is `changed` with
  "moved" as its word. The
  marks draw with the grammar vocabulary (two non-hue channels, the word
  in the accessible tree), on the side menu beside each view and as a
  small chip on the view's header; the header carries "since revision N:
  so many changed, new, removed"; the first revision carries no marks. A
  block whose id changed is `new` plus `removed`, which is the cost of
  breaking the id and is said in the authoring reference, so authors keep
  ids stable for conceptually unchanged blocks (the rule SKILL.md already
  states). The marks are a reading aid; they never change comment anchors
  or the feedback lifecycle.
- **Reuse is a read, not a copy inside the runtime.** `present show
  <session> --revision N --blocks <id,...>` and `--view <id>` print the
  named blocks of that revision as document JSON an author pastes or a
  generator reads, so a repeat report carries unchanged sections forward
  byte for byte and only revises what the facts changed; a generator that
  writes the whole document (TSK-1098) gets the same effect by writing
  stable ids and stable content, and the marks then show only real
  change. No runtime-side merge, template or partial update: the document
  stays one file an author owns, and the revision history is the version
  history.
- **`present diff` groups by view** when either revision has `views`:
  per view, the block changes as today; a linear document diffs as today.
- Boundaries: `topic` is text through the existing validation; the topic
  index is a file under the session store, never in the repository; no
  network, no write to any record.

Non-goals: the shell itself (TSK-1120); the status facts and their
`--since` delta (TSK-1095); the status document's ids and revision flow
(TSK-1098); the skill's topic register and reply (TSK-1099); a stored
template or a partial-update API; reopening a closed session.

## Outcome

After this merges, a session that presents a topic again updates the
topic's existing document instead of opening a new one, the reader sees
which views and blocks changed since the previous revision, and an author
or generator carries prior blocks forward unchanged by their ids.
