# TSK-433: The epic line's pull request into main judges the line's own completions as its own

## Description

Found by the primary on 2026-10-22 while rehearsing the 3.2.0 release
pull request. `codeflow ci --base origin/main --head 29a217556 --branch
integration/EPC-022-the-3-2-0-milestone-fixes --into main`, run with the
binary built at the line's tree, gives 18 blocking findings, all
`work.acceptance_binding`, two for each of nine tasks that were reopened
and amended on the line (TSK-275, TSK-276, TSK-278, TSK-280, TSK-304,
TSK-305, TSK-306, TSK-307 and TSK-352):

- "`refs/remotes/origin/integration/EPC-022-the-3-2-0-milestone-fixes`
  (commit 29a217556) records a completion of this task, but it is not
  the target this run is judged against, so its criteria stay as they
  were" (`crates/codeflow-core/src/workgraph/landing.rs:129`);
- "a reopened task keeps its criteria as the anchored target has them;
  change them in the epic's batched amendment, a planning pull request
  on the target" (`crates/codeflow-core/src/workgraph/acceptance.rs:2795`,
  `REOPENED_CRITERIA`).

When the epic line itself is the head of a pull request into `main`,
the anchored target is `main`, so the line's own landed completions and
the planning amendments that changed those tasks' criteria on the line
are judged as foreign: the line is the home that TSK-339 says a
completion is judged at, but here it is also the head. Every epic pull
request to `main`, and every early checkpoint pull request (issue #280
item 4, TSK-419), fails the same way, so the release pull request
itself is blocked. No open task owns this direction: TSK-339 judges a
completion imported into a receiving line at its proven home, TSK-306
settles competing record versions at unordered judged points, TSK-340
settles the reopened completion sequence, and TSK-308 counts adopted
direct commits; none of their criteria names the line-into-target pull
request.

Outcome: **when a pull request's head is an integration line and its
target is the protected branch, `codeflow ci` judges each task whose
`integration_target` is that line against the line's own history: a
completion landed on the line is bound at its line landing, criteria
amended by a planning amendment on the line are the task's criteria,
and a reopen and re-completion on the line is one valid sequence; and
`codeflow ci` for the EPC-022 line's pull request into `main` is clean
on the line head.**

Rules:

- The pull request class is the epic PR (`Task: EPC-NNN`, head an
  `integration/` line, target the protected branch). For it, the
  anchored target for a task whose `integration_target` is the line is
  the line head, with `main` as the base of the range; a task whose
  target is `main` keeps today's judgment.
- The line's authority is proven the way TSK-339 proves a home: the
  completion's landing merge on the line, the reviewed commit on the
  line, and the planning amendments on the line, each through the
  guarded history reader. A task whose line history cannot be read, or
  whose record on the line differs from the record at the head, stays
  refused.
- A checkpoint pull request from the line to `main` before the epic
  closes (TSK-419) is the same class and gets the same judgment.
- An epic line that joined the judged line, whose tip the range head
  contains and which passes the epic-line proof itself, is judged the
  same way for the tasks that declare it (amended 2026-10-28: route A
  joined the EPC-025 line into this line through TSK-1000). A joined
  line that fails the proof keeps today's refusal.

Non-goals: changing how a task pull request into the line is judged;
waiving any task's binding; closing the epic.

Added by the EPC-022 amendment of 2026-10-22 under the operator's
release rule of 2026-10-18 (a defect that blocks work belongs in
4.0.0). It must land before the epic's pull request to `main` is
opened.

Widened 2026-10-26 for issues #320 and #341, both from one adopter's
`codeflow ci --into main` runs on an integration line (CodeFlow 3.1.1).
When `check_epic_line` fails, `criteria` in
`crates/codeflow-cli/src/cmd/ci/acceptance.rs` judges the line as a
frozen task range and drops the reason (`check_epic_line(...).is_ok()`),
so every completion binds at the range head. `task_landing` then names
the head commit's own change as "the completion also changes <path>"
(#341, 16 tasks in one run), and `later_change` diffs the whole tree
from the reviewed commit to the head and names the first path in byte
order, which was a file `main` brought in through a sync merge and that
equals `main` (#320, 1,592 changed paths for one task). On a verified
line, AC-1 binds a line completion at its line landing, which removes
#320's blame for a reopened and re-completed task. AC-7 and AC-8 make
the downgrade and the comparison visible, and pin #320's shape.

(serves EPC-022 AC-113)
- AC-9 In the same class, a task whose `integration_target` is another epic line that joined the judged line, whose tip the range head contains and which passes the epic-line proof, shall bind at its landing as a task of the judged line does; a joined line that fails the proof, a joined tip beyond the range head, a joined line's task that targets `main`, and a completion forged on the joined line shall keep today's refusal; evidence: a CLI fixture failing before the change and one negative fixture per case.
