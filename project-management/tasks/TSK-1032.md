# TSK-1032: The shipped instructions require typed code and typed data at every boundary

## Description

Issue #275 (items 1 and 6 and its comments of 2026-10-22) and the
operator's quality asks of 2026-10-27, strict typing (D3). Three shipped
texts steer agents away from strictness:
`cf-model-orchestrator/resources/quality/design-implementation.md:24-33`
(types "where they prevent material errors"; no "stricter-compiler or
language migrations merely to satisfy this rule"),
`cf-develop/SKILL.md:41-44` ("never force a stricter compiler") and
`cf-stack/SKILL.md:32-35` ("Do not mandate TypeScript, a validator
library"). Under them, reviews passed Python at 5% annotated, hundreds
of `dict[str, Any]` and hand-written validators, and TypeScript never
type-checked as a whole.

This task takes TSK-427's former AC-1, AC-2, AC-4 and AC-5 (the texts,
the review check, qualification and the journey), which are instruction
and review-question changes small enough to ship in 4.0.0. The tooling
per language (TSK-426), CodeFlow's own code passing the defaults and
relaxations through the register (TSK-427) stay in EPC-024, because they
need TSK-424's register and baseline.

Outcome: **by default the shipped instructions require new and changed
code to be fully typed, every escape type and suppression to carry an
inline reason, and data crossing any boundary (files, network, process,
environment, database, user input, another module's untyped output) to
be parsed into a typed model that also validates it, with the
language's standard library for it (for example Pydantic models in
Python, zod schemas in TypeScript, serde types in Rust, structs with a
validator in Go); a typed representation alone (a plain Python
dataclass or a TypeScript interface) does not validate its input, so
the instructions name both parts; TypeScript is the
default for new projects and new files, and an existing JavaScript
codebase type-checks its JavaScript in place; adding the project's type checker,
linter and typed-model library is in scope for `cf-develop`; and
`cf-reviewer` checks it.**

Rules:

- A project opts out of the default only by stating its reason in the
  project-owned part of `AGENTS.md` (its Stack standards) until
  TSK-424's register ships in 4.2.0, when TSK-427 moves the route to a
  register entry (the operator's decision of 2026-10-27).
- TypeScript is the default for new projects and new files. An existing
  JavaScript codebase type-checks its JavaScript (for example `checkJs`
  with JSDoc types) instead of being rewritten (the operator's decision
  of 2026-10-27); AC-1 confirms the mechanism per toolchain.
- The proportionality wording that remains applies to how much a
  boundary model holds, never to whether code is typed.

Non-goals: per-language tool setup and gate targets (TSK-426);
CodeFlow's own code passing the defaults and the register route
(TSK-427); rewriting adopters' existing code.

### Research findings (AC-1, builder, 2026-10-30, line tip `461827479`)

Sources were read on 2026-10-30; each link resolved then.

**What a type checker gives and what it does not.** A static type
describes data the program already holds; it does not check data arriving
at run time. Node runs `.ts` files by replacing type syntax with
whitespace and "no type checking is performed"
(https://nodejs.org/api/typescript.html), which is how issue #275's
TypeScript projects were never checked. A Python standard-library
dataclass accepts `name=['not', 'a', 'string']` without error; Pydantic
adds validation on construction
(https://pydantic.dev/docs/validation/latest/concepts/dataclasses/). A
TypeScript `interface` is erased at run time. So the instruction has to
name two parts at a boundary: a typed model, and a parse that validates
input into it ("parse, don't validate",
https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/).

**Standard library per served language** (the model that also validates):

| Language | Type checker, strict setting | Validating typed model at a boundary | Typed representation only |
|---|---|---|---|
| TypeScript | `tsc` with `strict` over the whole project (`tsc -b`, `--noEmit`) | zod schema, type from `z.infer`; `.parse` returns typed data or throws (https://zod.dev/basics); Ajv where JSON Schema is the source | `interface`, `type`, `as` cast |
| JavaScript, existing | `tsc` with `allowJs` and `checkJs` (or `// @ts-check` per file, `jsconfig.json`), types in JSDoc (https://www.typescriptlang.org/docs/handbook/intro-to-js-ts.html) | the same zod schema, its type named in JSDoc | JSDoc `@typedef` alone |
| Python | pyright `strict` (https://github.com/microsoft/pyright/blob/main/docs/configuration.md) or `mypy --strict` (https://mypy.readthedocs.io/en/stable/command_line.html) | Pydantic v2 `BaseModel` or Pydantic dataclass; `TypeAdapter` for a bare type | stdlib `dataclass`, `TypedDict`, `NamedTuple`, `cast()` |
| Rust | the compiler; clippy | serde `Deserialize` into structs, `#[serde(deny_unknown_fields)]` where an unknown key is an error, `#[serde(try_from = ...)]` or a newtype for invariants (https://serde.rs/container-attrs.html) | `serde_json::Value` |
| Go | the compiler, `go vet` | typed structs decoded with `json.Decoder.DisallowUnknownFields` (https://pkg.go.dev/encoding/json#Decoder.DisallowUnknownFields) plus a `Validate` method or go-playground/validator tags (https://github.com/go-playground/validator) | `map[string]any`, `interface{}` |
| Shell | no type system; ShellCheck | parse arguments explicitly and refuse unknown ones; hand structured data to a typed language or check it against its JSON Schema | unquoted strings |
| OpenTofu | `tofu validate`; a `type` on every variable | `type` constraint plus a `validation` block (https://opentofu.org/docs/language/values/variables/) | an untyped variable accepts any value |
| Rego | `opa check --strict` | JSON Schema for `input` and `data` through `--schema` or METADATA schema annotations; the checker then reports an undefined reference such as a misspelled path (https://www.openpolicyagent.org/docs/policy-language/#schema-annotations) | rules with no schema, typed as `any` |
| JSON and YAML config | a JSON Schema validator | JSON Schema as the one source; types generated from it (datamodel-code-generator for Pydantic, https://github.com/koxudaxi/datamodel-code-generator; json-schema-to-typescript, https://github.com/bcherny/json-schema-to-typescript; typify for Rust, https://github.com/oxidecomputer/typify), and a validator for what a generated type cannot express | a hand-written type beside the schema |

**Type-checking existing JavaScript in place.** `tsc` with `allowJs` and
`checkJs` reports type errors in `.js` files; `// @ts-check` turns this on
per file and `// @ts-nocheck` turns it off
(https://www.typescriptlang.org/docs/handbook/intro-to-js-ts.html). JSDoc
supplies the types. JavaScript checking is looser than `.ts` checking: a
parameter without JSDoc is optional, a value initialised to `null` or
`undefined` becomes `any` even under strict null checks, and object
literals are open-ended
(https://www.typescriptlang.org/docs/handbook/type-checking-javascript-files.html).
So the rule asks for JSDoc types on every new or changed function and
data shape in a checked JavaScript file. A file-by-file `// @ts-check`
start is the incremental route; the whole-project setting and its gate are
TSK-426's.

**What "every boundary" covers.** Data that enters code from outside the
code's own type checker: files and config; network requests and
responses; process input (arguments, standard input, a subprocess's
output, exit codes); environment variables; database rows; user input;
inter-process and queue messages; caches read back from disk; generated
code's inputs; and another module's untyped output (a third-party call
returning `Any`, `any` or a JSON value). A value already parsed into a
model and passed between typed modules is trusted; it is not validated
again. That keeps the existing "Trusted internal values do not need
redundant runtime validation" sentence, with "trusted" now meaning
"already parsed".

**Escape types and suppressions.** Each language has a standard way to
scope a suppression and to report unused ones: typescript-eslint
`ban-ts-comment` with `allow-with-description`
(https://typescript-eslint.io/rules/ban-ts-comment/) and `no-explicit-any`,
which recommends `unknown` and narrowing
(https://typescript-eslint.io/rules/no-explicit-any/); pyright
`# pyright: ignore[rule]` and `reportUnnecessaryTypeIgnoreComment`
(https://github.com/microsoft/pyright/blob/main/docs/comments.md); mypy
`--warn-unused-ignores`; Ruff `ANN401` for `Any`
(https://docs.astral.sh/ruff/rules/any-type/), `PGH003` for a blanket
`type: ignore` (https://docs.astral.sh/ruff/rules/blanket-type-ignore/) and
`RUF100` for an unused `noqa` (https://docs.astral.sh/ruff/rules/unused-noqa/);
ShellCheck accepts a comment at the end of the directive line
(https://github.com/koalaman/shellcheck/wiki/Directive). The instruction
therefore asks for a reason on the same line or the line above, and the
narrowest scope the tool offers (one rule, one line). Turning on the
unused-suppression checks is TSK-426's tooling.

**Adjacent concerns.**
- Runtime cost: parse once at the boundary; internal values are not
  revalidated. A hot path may use a faster validator of the same standard
  (compiled Ajv, msgspec); the remaining proportionality wording covers
  how much a boundary model holds, never whether code is typed.
- Tests: tests are code and are typed. A test of invalid input passes raw
  data (a string, bytes, a dict literal) through the boundary parser,
  which needs no escape type; a cast that bypasses a type to reach
  internal code carries a reason like any other.
- Generated types: generated from the schema and never hand-edited; the
  regenerate-and-compare gate is TSK-426's.
- Issue #274's single home for a shared shape belongs to TSK-1033. This
  task says one model per shape, reused wherever that shape is read, and
  leaves the cross-language rule to TSK-1033.

**CodeFlow guidance survey, confirmed at the tip.** A sweep of
`assets/base` for typing and validation wording finds exactly the four
places in the first-pass survey: `design-implementation.md:24-33`,
`cf-develop/SKILL.md:41-44`, `cf-stack/SKILL.md:29-35` and
`cf-reviewer.md:40-48`. No `requirements.json` entry covers typing, so
qualification needs a new requirement. `cf-security-reviewer.md` covers
untrusted-source-to-sink flows and needs no change. This repository's own
state, for TSK-427: 197 tracked `.js` and `.mjs` files with no `checkJs`;
2,665 of 3,281 Python functions fully annotated; the present web
`tsconfig.json` already sets `strict`, `noUncheckedIndexedAccess` and
`exactOptionalPropertyTypes`.

**Chosen scope.**
- `design-implementation.md` stays the one home of the rule: fully typed
  new and changed code; an inline reason for every escape type and
  suppression; every boundary parsed into a validating typed model with
  the standard library named per language, and the difference between a
  typed representation and a validating parse; TypeScript for new
  projects and files, existing JavaScript checked in place; adding the
  tools is in scope; the opt-out stated in the project's own `AGENTS.md`
  until the 4.2.0 register. The "merely to satisfy this rule" sentence is
  removed for typing, and proportionality is kept for how much a boundary
  model holds.
- `cf-develop` points to that rule and says adding the type checker,
  linter and typed-model library is in scope.
- `cf-stack` replaces "Do not mandate TypeScript, a validator library"
  with the default: set up the type checker and the typed-model library,
  TypeScript for a new project, `checkJs` for existing JavaScript, the
  opt-out in Stack standards. Strictest settings per tool and gate targets
  stay with TSK-426.
- `cf-reviewer` extends its type-contract check to return
  `changes_requested` for the four finding kinds, each with file:line.
- Qualification: one requirement, four review cases (one per finding
  kind) and two builder cases (adds a checker and parses JSON into a
  model; adds no unexplained `Any`), in their own pack.
