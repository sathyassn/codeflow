# TSK-1156: Codex builder seats can claim, push and run their own gates

## Description

A Codex builder seat, launched with the builder posture in
`.agents/skills/cf-model-orchestrator/resources/routing/transport.md`, is
refused when it runs `codeflow work claim`, renames a branch, pushes, or runs
`codeflow test --mode essential`. Known so far: `codeflow work claim` writes
the repository's shared git config file, which the seat cannot write. Whether
writes under `~/.codeflow/gate-runs` still block a gate run is unconfirmed
(PR 419 dropped that grant from the Claude presets; ADR-0089 gives local run
records no credit). Issue 254's lock grant has landed; its `gate-runs` grant
stays withdrawn (the epic's gate-evidence amendment of 2026-10-30), so this
task does not take it. Only a full run copies its record to
`~/.codeflow/gate-runs`; this task's gates are quick and essential, which
record under the worktree. This task finds each refusal with its exact message,
fixes each one by a code change where that avoids widening the seat's
sandbox, and makes `codeflow doctor --preflight` and `--check permissions`
name what a Codex builder seat can and cannot do. Non-goals: authenticating
local run records (ADR-0089); any sandbox grant, which is written up as an
operator decision instead.

## Outcome

After this merges, a Codex builder seat can claim a task, push, and run its
quick and essential gates under its own profile, and doctor tells it what it
cannot do.

## Deliverables

- Investigation record of each refusal with its exact message: this task's PR body
- Fixes with tests (claim, rename, doctor): `crates/codeflow-core`, provisional until the investigation names the code
- Operator decision write-up for any remaining sandbox grant: this task's PR body

## Investigation

Draft design before the canary results; confirmed or changed by them. Code
read at the line tip `bee344658`.

### Where `work claim` writes the shared git config file

`claim_on` (`crates/codeflow-core/src/workgraph/readiness.rs:1934`) runs two
git commands that rewrite it:

- `git push --quiet -u ...` (`readiness.rs:2024`): `-u` writes
  `branch.<name>.remote` and `branch.<name>.merge`.
- `git branch -m <new>` (`readiness.rs:2014`, only for a standalone claim that
  renames the checked-out branch): git renames the `branch.<old>` section in
  the config file, which takes the config lock in the common git directory.

The other git calls in claim (`fetch --prune`, `branch <name> <sha>`) write
refs and `FETCH_HEAD`, which the existing builder probe already covers
(`testing/gate_guard.rs:371`, `objects` and `refs`). The probe does not cover
a write of the shared config file itself, which the `.git` write grant does
not imply.

### Does anything need the upstream setting `-u` writes

No. Every reader falls back to `refs/remotes/origin/<branch>` when no
upstream is configured, and a claim pushes to `origin` under the same name:
`hooks/git_hook.rs:1111` (pre-push sync check), `workgraph/work_start.rs:403`
and `:2719` (`configured_upstream` returns none, so the authority remote's
tracking ref is read), `workgraph/acceptance.rs:2531`. So the push can drop
`-u` and the recorded behaviour does not change. The branch is still pushed,
which is the visible mark of the claim. Later pushes already name the remote
(`git push origin HEAD:refs/heads/<branch>` is the documented form).

### Design (smallest change)

1. **Claim push without `-u`.** Remove `-u` from the push at `readiness.rs:2024`.
   No upstream is recorded, so the push touches no config. Trade-off: plain
   `git push` and `git status` ahead/behind on the task branch need an
   explicit remote until the operator sets one. Test: a claim in a fixture
   repo leaves the config file byte-identical (fail before: it gains a
   `branch.<name>` section; pass after: it does not), and the claim still
   pushes and the ref exists on origin.
2. **Standalone rename without a config write when none is needed.** In the
   rename path, if the old branch has no `branch.<old>.*` keys, create the new
   branch at HEAD (`git branch <new> HEAD`), point HEAD at it
   (`git symbolic-ref HEAD refs/heads/<new>`, which writes only this
   worktree's HEAD) and remove the old ref (`git update-ref -d`, which does
   not edit config). If the old branch does have config keys, keep
   `git branch -m` so that tracking moves with the branch; under a profile
   that cannot write the config file it fails closed with git's message,
   which the claim error then names. `libgit2`'s `Branch::delete` is not
   used: it also rewrites the config section. Test: rename a branch with and
   without tracking; assert the config file is unchanged in the first case and
   the tracking keys moved in the second.
3. **Doctor names the seat's limits.** Add the common git directory root to
   the builder write probe: a non-truncating write of the shared git config
   file itself (open it for append and write nothing, or create and rename a
   `config.lock` as git does), not a dot file in the common directory, which
   the `.git` write grant allows while `git config` still fails. Doctor
   reports that path. Say in `--preflight` and `--check permissions` what a
   builder seat can do (claim, commit, push, quick and essential gates) and
   cannot (write the shared git config file or `~/.codeflow/gate-runs`; only
   a full run copies its record to the second path).

### What each change does for security

The seat's sandbox is not widened. No grant on the git config file or the
common directory root is proposed: the shared config file carries
`core.hooksPath`, aliases and remotes that govern every worktree, so an
agent-writable seat there could disable the hook plane (`git.hook_integrity`
guards it). Removing the need for the write is the standard fix; granting it
would be the weakening.

What this settles and what it leaves open:

- **Confirmed blockers:** claim (the config write by `push -u`) and the
  standalone rename. Rename is worse than a refusal: it half-completes, so a
  claim that renamed the branch and then failed leaves the ref moved and the
  config stale. The design below makes the rename avoid the write, and makes
  the claim check before it moves anything.
- **Push:** not blocked by the sandbox. The seat's hook ran the installed
  3.1.0 binary because the seat PATH lacked the worktree binary; a seat on a
  line that needs 4.0.0 policy must put its worktree `target/debug` first.
- **Gate record write: still unconfirmed.** The essential run stopped at the
  heavy-gate lock before it could try `~/.codeflow/gate-runs`, so whether a
  gate run fails, or only its evidence record, is not shown. The `mkdir`
  refusal shows the folder is unwritable, nothing more. The amended AC-3 no
  longer asks for the essential run, so this stays unconfirmed; the code read
  (only a full run copies its record there) stands in for it.
- **Observed dependency, not in this task:** the heavy-gate lock refusal is the
  single-gate barrier that TSK-1145 (PR 483) replaces. TSK-1156 does not
  change the lock. The original AC-3 (a seat running `codeflow test --mode
  essential` end to end) depended on TSK-1145 landing or on a free lock; the
  amended AC-3 asks for the quick gate instead (see Criteria changes).

### Doctor wording change

`codeflow doctor --check permissions` says the gate-runs folder "is not
writable in a Codex seat, by design: full gates and their evidence stay with
the primary, run outside the sandbox" (`doctor/mod.rs:2416`, and the profile
sentence ending "full gates and their evidence stay with the primary" near
`doctor/mod.rs:2604`; tests assert it at `mod.rs:6819`). That is an
instruction, and it conflicts with the operator's direction that gate runs
have no artificial barriers and with TSK-1147. The new wording states only
what the check measured, and says what is refused rather than who must do it:

- Can: write the worktree, commit, create and push branches, take the gate
  lock folders, run quick-mode heavy targets under `codeflow reserve`.
- Cannot (under the shipped cf-builder profile): write the shared git config
  file (so no tracking config, no `git branch -m` of a branch that has any),
  and write `~/.codeflow/gate-runs`. Only a full run copies its record there;
  quick and essential runs keep theirs under the worktree, so an unwritable
  `gate-runs` does not stop them.
- No "by design" and no routing instruction. If an operator wants a seat to
  run gates with local evidence, that is a grant to decide (AC-4), and doctor
  names which folder it is.

The doctor probe also gains a non-truncating write of the shared git config
file (not a dot file in the common directory) so the refusal the canary hit
is reported by doctor before a claim hits it. Tests: update the assertions at
`mod.rs:6718`, `:6737`, `:6750` and `:6819` to the new sentences and add one
for the config-file probe result, fail-before with a read-only config file.
No grant is added.

### Revised design

1. Claim push without `-u` (no config write). Fail before: config gains
   `branch.<name>` keys; pass after: byte-identical.
2. Rename without a config write when the old branch has no `branch.<old>.*`
   keys (create new, `symbolic-ref HEAD`, `update-ref -d` old). When it does,
   the claim first checks that the config file is writable and refuses before
   moving the ref, so no half-done rename. Test the half-done case with a
   read-only config file.
3. Doctor wording and the config-file probe as above.
4. A claim that fails at the push after creating the local branch already says
   "created <branch> locally; push to origin failed"; unchanged.

Whether work may start on the task branch before PR 490 lands: the record
allows it only at the reviewed record SHA (AGENTS.md: on an unlanded
predecessor only at its reviewed SHA); no review exists yet, so no code until
PR 490 lands or its record SHA is reviewed.
