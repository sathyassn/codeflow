# TSK-1156: Codex builder seats can claim, push and run their own gates

## Description

A Codex builder seat, launched with the builder posture in
`.agents/skills/cf-model-orchestrator/resources/routing/transport.md`, is
refused when it runs `codeflow work claim`, renames a branch, pushes, or runs
`codeflow test --mode essential`. Known so far: `codeflow work claim` writes
the repository's shared git config file, which the seat cannot write. Whether
writes under `~/.codeflow/gate-runs` still block a gate run is unconfirmed
(PR 419 dropped that grant from the Claude presets; ADR-0089 gives local run
records no credit). This task finds each refusal with its exact message,
fixes each one by a code change where that avoids widening the seat's
sandbox, and makes `codeflow doctor --preflight` and `--check permissions`
name what a Codex builder seat can and cannot do. Non-goals: authenticating
local run records (ADR-0089); any sandbox grant, which is written up as an
operator decision instead.

## Outcome

After this merges, a Codex builder seat can claim a task, push, and run its
quick and essential gates under its own profile, and doctor tells it what it
cannot do.

## Deliverables

- Investigation record of each refusal with its exact message: this task's PR body
- Fixes with tests (claim, rename, doctor): `crates/codeflow-core`, provisional until the investigation names the code
- Operator decision write-up for any remaining sandbox grant: this task's PR body

## Acceptance Criteria

- AC-1 Investigation first: a live check of what refuses a Codex seat launched with the builder posture in `.agents/skills/cf-model-orchestrator/resources/routing/transport.md:60` when it runs `codeflow work claim`, a branch rename, a push and `codeflow test --mode essential` at the line tip; each refusal is recorded with its exact message.
- AC-2 Each refusal found is fixed without widening the seat's sandbox where a code change can avoid it (for example, claim not needing a shared git config write from the seat, or a gate run that does not need a shared write); a fix shows fail-before and pass-after; `codeflow doctor --preflight` and `--check permissions` name what a Codex builder seat can and cannot do.

- AC-4 Any grant that would still widen the sandbox is not made in this task; it is written up as an operator decision (protection, cost, alternative). Local run records stay uncredited.

## Investigation

Draft design before the canary results; confirmed or changed by them. Code
read at the line tip `bee344658`.

### Where `work claim` writes the shared git config file

`claim_on` (`crates/codeflow-core/src/workgraph/readiness.rs:1934`) runs two
git commands that rewrite it:

- `git push --quiet -u ...` (`readiness.rs:2024`): `-u` writes
  `branch.<name>.remote` and `branch.<name>.merge`.
- `git branch -m <new>` (`readiness.rs:2014`, only for a standalone claim that
  renames the checked-out branch): git renames the `branch.<old>` section in
  the config file, which takes the config lock in the common git directory.

The other git calls in claim (`fetch --prune`, `branch <name> <sha>`) write
refs and `FETCH_HEAD`, which the existing builder probe already covers
(`testing/gate_guard.rs:371`, `objects` and `refs`). The probe does not cover
a write to the common directory root, where `config.lock` is created.

### Does anything need the upstream setting `-u` writes

No. Every reader falls back to `refs/remotes/origin/<branch>` when no
upstream is configured, and a claim pushes to `origin` under the same name:
`hooks/git_hook.rs:1111` (pre-push sync check), `workgraph/work_start.rs:403`
and `:2719` (`configured_upstream` returns none, so the authority remote's
tracking ref is read), `workgraph/acceptance.rs:2531`. So the push can drop
`-u` and the recorded behaviour does not change. The branch is still pushed,
which is the visible mark of the claim. Later pushes already name the remote
(`git push origin HEAD:refs/heads/<branch>` is the documented form).

### Design (smallest change)

1. **Claim push without `-u`.** Remove `-u` from the push at `readiness.rs:2024`.
   No upstream is recorded, so the push touches no config. Trade-off: plain
   `git push` and `git status` ahead/behind on the task branch need an
   explicit remote until the operator sets one. Test: a claim in a fixture
   repo leaves the config file byte-identical (fail before: it gains a
   `branch.<name>` section; pass after: it does not), and the claim still
   pushes and the ref exists on origin.
2. **Standalone rename without a config write when none is needed.** In the
   rename path, if the old branch has no `branch.<old>.*` keys, create the new
   branch at HEAD (`git branch <new> HEAD`), point HEAD at it
   (`git symbolic-ref HEAD refs/heads/<new>`, which writes only this
   worktree's HEAD) and remove the old ref (`git update-ref -d`, which does
   not edit config). If the old branch does have config keys, keep
   `git branch -m` so that tracking moves with the branch; under a profile
   that cannot write the config file it fails closed with git's message,
   which the claim error then names. `libgit2`'s `Branch::delete` is not
   used: it also rewrites the config section. Test: rename a branch with and
   without tracking; assert the config file is unchanged in the first case and
   the tracking keys moved in the second.
3. **Doctor names the seat's limits.** Add the common git directory root to
   the builder write probe (create and remove a dot-named file there, the
   directory in which git creates `config.lock`), and say in `--preflight` and
   `--check permissions` what a builder seat can do (claim, commit, push,
   quick-mode gates) and cannot (edit tracking config, full gates and their
   `~/.codeflow/gate-runs` evidence, which `doctor/mod.rs:2604` already
   states by design). The wording follows what the canary shows is actually
   refused.

### What each change does for security

The seat's sandbox is not widened. No grant on the git config file or the
common directory root is proposed: the shared config file carries
`core.hooksPath`, aliases and remotes that govern every worktree, so an
agent-writable seat there could disable the hook plane (`git.hook_integrity`
guards it). Removing the need for the write is the standard fix; granting it
would be the weakening.

### Open until the canary returns

- Whether a gate run under the builder posture fails or only its record write
  fails on `~/.codeflow/gate-runs` (step 5 and 6 of `CANARY-COMMANDS.md`).
- Whether `fetch`, branch creation and push are refused for reasons other than
  the config file (refs, `FETCH_HEAD`, credentials, the pre-push check).
- Whether the worktree itself is writable to the seat (step 1).
