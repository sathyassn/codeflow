# TSK-1042: Task records whose status no longer matches git are reported

## Description

Issue #370 (opened 2026-10-28 00:53Z, the same adopter as #366 and
#369). CodeFlow judges a task's status when a range changes it
(`work.records`, `work.acceptance_binding`, `work.criteria_frozen`, the
transition table), but nothing reports a status the facts have moved
past. In one adopting repository on 2026-10-28 (CodeFlow 3.1.1), 54
`task/TSK-*` branches were fully merged into `main`, and for 11 of them
`main` still recorded the task `todo` or `blocked`: some legitimately (a
record-only filing PR, a task blocked by design), others drift (a
settings task merged in its own PR but still `todo`; an operator-confirmed
change still `todo`; a standalone task whose work landed but stayed
`blocked`, which #365 then refused to unblock; a completion owed to a
later PR that nobody tracked). Nobody noticed until a hand audit.

The narrow defect, `codeflow work next` offering a task whose branch has
landed as ready, is TSK-1038 in EPC-022 (3.2.0). This task is the
feature: a read-only audit of every class.

Outcome: **a read-only `codeflow work audit` lists each task record whose
status no longer matches the facts in git, by class (merged but not
closed, blocker cleared, claimed but idle, abandoned, owed completion,
epic out of step, and a Closeout follow-up whose record is missing or
was cancelled without a reason), each with its reason and
the suggested `codeflow task status` command, from local refs and records
by default and with one host query under `--remote`; `codeflow ci` warns
when a task PR leaves its own task `todo` and names no PR that completes
it; and `cf-ship`'s cleanup step and the session sweep run the audit.**

Rules:

- "Merged but not closed" says whether the merged work was record-only,
  so a filing PR is not flagged.
- "Claimed, idle" uses a configurable number of days with no commit and
  no open PR.
- Exit 0 with pointers and counts, `--json`, and `--fail-on <class>` for
  a project that wants it in CI. The `ci` warning stays a warning by
  default; a project may raise it to a block through policy.
- Local refs as last fetched by default; `--remote` adds one query for PR
  states, so it can see branches already deleted.
- The session sweep (TSK-1037) and `work next` (TSK-1038) read the same
  classes; there is one reader.

Non-goals: changing any status automatically; the unblock route itself
(TSK-1036); the ledger's follow-ups (EPC-025).

### First-pass survey (planning, 2026-10-28, line tip after PR 367)

- `crates/codeflow-core/src/workgraph/readiness.rs`: `backlog` (`:774`) already splits each record's claim branches into open and landed (`split_landed`, `:638`; `landed`, `:446`, which proves landing with `git cherry`) and reports the landed names in `Backlog::landed`; it does not compare them with the record's status.
- `crates/codeflow-cli/src/cmd/work.rs:100` (`work next`) prints ready, waiting, blocked and invalid entries and an active count; it prints nothing about landed branches.
- `codeflow validate --docs` checks frontmatter and the doc graph; `codeflow ci` judges only records a range changes.
- Related records: TSK-1036 (unblock in the task's own PR, #365), TSK-1037 (the session sweep, #366), TSK-1041 (open PR state, #369), EPC-025 (the ledger, #272), and TSK-340 (#217, reopen and Closeout).

## Acceptance Criteria

- AC-1 Before any change, the builder shall research status drift broadly: how each class can be proven from local refs and records alone and which need the forge, how comparable trackers detect stale items, the cost on a repository with hundreds of records and branches, the CodeFlow readers in the survey above, and adjacent concerns (squash and rebase merges, deleted branches, record-only PRs, line merges that carry a task to another line, tasks blocked by design); and shall record the findings with sources and the chosen scope before any change; evidence: the note or record section, committed before the first code change in the PR.
- AC-2 `codeflow work audit` shall list each class with its reason and suggested command: merged but not closed (with record-only filings told apart), blocker cleared, claimed but idle (configurable days, no open PR), abandoned, owed completion, epic out of step, and a Closeout follow-up whose record is missing or whose record was cancelled without a reason; evidence: one fixture per class, with separate fixtures for a missing follow-up record and a follow-up cancelled without a reason (both reported), a follow-up cancelled with a valid reason (not reported), and a record-only filing (not flagged). Amended 2026-10-28 after the PR 374 review: issue #370 names both follow-up conditions. (serves EPC-023 AC-36)
- AC-3 The audit shall read local refs and records only by default and finish within a stated budget on this repository; `--remote` shall add one host query that finds a merged PR whose branch was deleted; evidence: a timing run and a test with a deleted branch.
- AC-4 The command shall exit 0 and change no file or ref; `--fail-on <class>` shall exit non-zero only on that class; `--json` shall carry the same content; evidence: CLI tests.
- AC-5 `codeflow ci` shall warn, not block, when a task PR into its target leaves its own task `todo` and its body names no PR that completes it, and a project policy key shall raise it to a block; evidence: CI tests at both levels.
- AC-6 `cf-ship`'s cleanup step shall run the audit and close a "merged but not closed" item in the same step; evidence: the text diff and a `cf-editorial-review` pass.
- AC-7 (journey) With the installed build in a scratch adopter project holding a merged-but-`todo` task, a blocked task whose blocker completed and a filing PR, the audit shall list the first two and not the third; evidence: the journey output.
