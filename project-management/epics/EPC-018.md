# EPC-018: autonomy with judgment and a config-driven model catalog

## Summary

The operator asked for two things on 2026-09-23. First, CodeFlow should get
work done without being watched and stop only where a human really has to
decide, clarify or supply an input. Second, model routing should become
configuration: agents take the latest eligible version in a family, each
family says which models may be primary, and adding or removing a model
changes a catalog entry, not an instruction. Plan v3 lands both on two
independent chains that join at the end: the autonomy chain (reference,
skill corrections, blind cases) and the catalog chain (engine, check and
resolution command, then the switch of the managed catalog and the
instruction rewrite).

## Model routing, as config

```text
catalog (managed current-ensemble.json, schema 5)
  family -> product lines -> ordered versions
            (alias, expected id, selectors, efforts, lifecycle,
             seat designations, scoped evidence)
  family -> one primary seat -> ordered eligible lines
  duties -> required participants (each an ordered list of alternatives)
         -> triggered participants (with the trigger)
         -> effort floor and escalation obligation
        |
        +-- personal overlay ~/.codeflow/model-catalog.local.json
        |   (add a candidate version, exclude a version; nothing else)
        +-- project selection .codeflow/model-selection.json schema 1
        v
codeflow models resolve --duty D --host H --author A
                        [--exclude ...] [--observed alias=id ...]
        -> one resolved participant set, or the open duty and its reason
        v
orchestrator, cf-delegate, cf-herdr and grok-host launch what it returned;
skills, contracts and templates name only seats, roles and duties
```

personal overlay carry versions or selectors; only one read-only command

### Eligibility and resolution

A version is eligible for one participant, at one harness and effort, when
all of these hold:

1. lifecycle is `active`, or `fallback-only` where the participant lists it
   as a seat fallback; `retired` never;
2. a seat participant needs a designation for that seat in the managed
   catalog, or a full-suite binding record for that role, harness, selector
   and effort (ADR-0039); scoped worker evidence never satisfies a seat;
3. a worker participant may be a candidate where ADR-0060 lets candidates
   work (bounded, light, evidence, advisory reasoning, consultation); a
   design-implementation worker needs scoped evidence for the exact harness,
   selector, effort and duty, and never holds direction or fidelity
   approval;
4. the required effort (the floor, or xhigh on a trigger) is in the
   version's efforts; otherwise the version is excluded for that
   participant, not clamped;
5. no fresh native exclusion applies (a harness or rate-limit error, a
   failed canary, a stale login); an exhausted usage bucket excludes every
   line in it; unknown usage excludes nothing;
6. identity: an observed id that differs from the version's expected id
   inherits no designation and no evidence (below).

Resolution takes the participant's alternatives in order, and within a line
the newest eligible version. The command records requested selector and
effort; the launcher records the observed id and effort. An unfilled
required participant leaves the duty open: the existing reduced-assurance
and solo rules apply and nothing is simulated.

Identity drift. Seats pass the alias and record the expected full id; the
alias keeps the family current without an edit, and the recorded id keeps
the designation honest. At preflight the launcher compares the observed id.
A match proceeds. A mismatch is drift: the observed model is an uncatalogued
candidate. Then, in order: the same designated version by its pinned id if
the harness accepts it; else the participant's next eligible alternative;
else, for a worker duty that admits candidates, candidate-only use with the
drift recorded; else the duty is open. Doctor and the command name the
drifted id as "newer version observed, not designated". An unobservable id
is a named limitation, as ADR-0041 already says.

## Decisions settled here

- Design owner. Seat `claude-primary` owns design direction, real design and
  fidelity approval; with this roster it resolves to Opus 5.5 at high. Fable
  serves `reasoning-support`, `design-and-editorial-review`,
  `general-review` as a second opinion, and `consultation`; it never authors
  design. Fallbacks come from seat order: Opus unavailable after preflight,
  Fable at high carries the seat with reduced assurance.
- Eligibility, not ranks. A seat needs a designation or a full-suite record
  for that exact role and tuple; scoped worker evidence stays scoped to its
  exact tuple. `qualified` still means a full native suite plus an approved
  binding record (ADR-0039 unchanged); a designation is labeled
  "designated, full suite not run" in every closeout and never reported as
  qualified.
- Effort floors follow ADR-0056 unchanged: seat duties at high with xhigh
  reasoning on a trigger, workers at medium. The validator rejects a catalog
  default below a floor; an unsupported required effort excludes the
  version. Nothing lowers a floor in this epic.
- Q3, settled: seats pass the alias and record the expected full id; on
  drift they fall back to the same designated version by pinned id before
  any other alternative. This keeps the family current without edits and
  keeps the primary stable when a vendor moves an alias. The routing audit
  preferred pinned ids for seats; the pinned-id fallback answers its reason.
- Q5, settled from `capability-routing.md` and `harnesses.json`: computer-use
  QA runs on `codex-app` for Claude-authored UI and on `claude-code` for
  Codex-authored UI. A Claude desktop app harness enters only when a harness
  record with native computer-use evidence exists.
- The minimal contract cap: charter section 4.4 settles it; the duplicated
  tier paragraph pays for the compact clause; no ratchet move.
- `cf-plan` keeps its clarity gate but its operator-owned list becomes the
  pointer alone; the per-file test asserts the pointer and the absence of a
  list.
- Project override schema 2 is deferred: no consuming project needs it now.
  Schema 1 binding references keep working and are tested against schema 5.
- The personal overlay may add a candidate version or exclude a version; it
  cannot designate a seat, add a family, harness or probe, or claim
