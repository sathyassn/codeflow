# EPC-018: autonomy with judgment and a config-driven model catalog

## Summary

The operator asked for two things on 2026-09-23. First, CodeFlow should get
work done without being watched and stop only where a human really has to
decide, clarify or supply an input. Second, model routing should become
configuration: agents take the latest eligible version in a family, each
family says which models may be primary, and adding or removing a model
changes a catalog entry, not an instruction. Plan v3.1 lands both on two
independent chains that join at the end: the autonomy chain (reference,
skill corrections, blind cases) and the catalog chain (engine, check and
resolution command, then the switch of the managed catalog and the
instruction rewrite), followed by one merge-forward of `main`.

| Gap | Where it shows today |

| No positive finish-line statement | only the pull request loop from EPC-017 covers one stage |

Done is: `codeflow models resolve` returns the duties owed for a unit from

## Model routing, as config

```text
catalog (managed current-ensemble.json, schema 5)
  family -> product lines -> ordered versions
            (alias, pinned id, selectors, efforts, lifecycle,
             seat designations, scoped evidence)
  family -> one primary seat -> ordered eligible lines
  duties -> required participants (each an ordered list of alternatives)
         -> triggered participants (with the trigger)
         -> effort floor and escalation obligation
        |
        +-- personal overlay ~/.codeflow/model-catalog.local.json
        |   (add a candidate version, exclude a version; nothing else)
        +-- project selection .codeflow/model-selection.json schema 1
        v
codeflow models resolve --duty D --host H --author A
                        [--exclude ...] [--observed pinned=observed ...]
                        [--trigger ...] [--override record]
        -> pinned ids, efforts, labels and obligations, or the open duty
        v
orchestrator, cf-delegate, cf-herdr and grok-host launch what it returned;
skills, contracts and templates name only seats, roles and duties
```

personal overlay carry versions or selectors; only one read-only command

### Duties, and who owes them

A duty lists required participants, triggered participants and
obligations. Each participant is an ordered list of alternatives; the first
eligible one serves. The resolver returns every participant and obligation
owed, or names the one it cannot fill.

"xhigh worker" in the table is the ADR-0056 obligation, unchanged: the seat
enters at high; when an xhigh trigger fires, the resolver adds an
`xhigh-reasoning` obligation served by a worker session in the seat's own
family on a version whose efforts include xhigh (the seat's own version in a
separate worker session qualifies), and the seat keeps approval. A seat
version without xhigh stays eligible. With no such worker the obligation is
open: the seat continues at high, the gap is recorded, and the trigger is
never reported as met.

### Eligibility and resolution

A version is eligible for one participant, at one harness and effort, when
all of these hold:

1. lifecycle is `active`, or `fallback-only` where the participant lists it
   as a seat fallback; `retired` never;
2. a seat participant needs a designation for that seat in the managed
   catalog, or a full-suite binding record for that role, harness, selector
   and effort (ADR-0039); scoped worker evidence never satisfies a seat;
3. a worker participant may be a candidate where ADR-0060 lets candidates
   work (bounded, light, evidence, advisory reasoning, consultation); a
   design-implementation worker needs scoped evidence for the exact harness,
   selector, effort and duty, and never holds direction or fidelity
   approval;
4. the participant's effort (the duty's entry effort, or xhigh for an
   `xhigh-reasoning` obligation) is in the version's efforts; otherwise the
   version is excluded for that participant, not clamped; an xhigh trigger
   never raises a seat's entry effort;
5. no fresh native exclusion applies (a harness or rate-limit error, a
   failed canary, a stale login, including a stale Codex plugin login, after
   which the Herdr interactive Codex seat is the qualified transport per
   ADR-0059); an exhausted usage bucket excludes every line in it; unknown
   usage excludes nothing;
6. identity: an observed id that differs from the version's pinned id
   inherits no designation and no evidence (below).

Resolution takes the participant's alternatives in order, and within a line
the newest eligible version. The command records requested selector and
effort; the launcher records the observed id and effort. An unfilled
required participant leaves the duty open: the existing reduced-assurance
and solo rules apply and nothing is simulated.

Launch identity. Every launch passes the pinned id of the version the
catalog resolved; an alias is never used to launch a seat. Aliases are data
used only by the identity canary (TSK-078 and later canaries) to discover
that a vendor now serves a newer version; a discovered version enters the
catalog as a candidate by a data edit, and takes a seat only after a
designation. At preflight the launcher compares the observed id with the
pinned id. A match proceeds. A mismatch is drift: the observed model
inherits no designation and no evidence. Then, in order: the participant's
next eligible alternative; else, for a worker duty that admits candidates,
candidate-only use with the drift recorded; else the duty is open. An
unobservable id is a named limitation, as ADR-0041 already says.

## Decisions settled here

- Design owner. Seat `claude-primary` on its first line owns design
  direction, real design and fidelity approval; with this roster that is
  Opus 5.5 at high. Fable serves `reasoning-support`,
  `design-and-editorial-review`, `general-review` as a second opinion, and
  `consultation`. When Opus is unavailable after preflight, Fable may hold
  `claude-primary` as the recorded fallback for orchestration, planning and
  review with reduced assurance; it never authors design or gives design or
  fidelity approval, and the `design` duty stays open until Opus is back
  unless a recorded task-specific operator override names the route. The
  seed, TSK-079, TSK-081 and the TSK-085 cases say the same.
- Eligibility, not ranks. A seat needs a designation or a full-suite record
  for that exact role and tuple; scoped worker evidence stays scoped to its
