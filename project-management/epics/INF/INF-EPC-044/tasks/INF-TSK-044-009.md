# INF-TSK-044-009: PathFlow Dynamic Gates, ProtectionGuard Bypass Fix, and Cleanup

## Description

PR #286 closed the ProtectionGuard `./` prefix bypass (SEC-INFO-001) and cleaned up Go/SQLite remnants. This follow-up task addresses architectural debt surfaced during that work:

1. **Hardcoded PathFlow sentinel names across hook code** — `pre_tool_use.rs`, `post_tool_use.rs`, `task_completed.rs`, `tui/data.rs`, and `cli/src/cmd/autorun.rs` all carry string literals (`"pf-3"`, `"pf-6"`, `"pathflow-pf-6"`, `["ws-dev","ws-sec","ws-rev","ws-qa"]`) that encode the PathFlow gate topology in code instead of config.
2. **Stray commits after PR merge** — `rescue_uncommitted_work` creates `wip: auto-save` commits whenever the worktree has dirty files, including AFTER the PR has been pushed.
3. **Missing `WsSec` enum variant** — `WorkStage` lacks the WS-SEC variant (added in commit 7eab5202 by cf-development-2).

- **validate_stage_ordering behavioral change (REV F5)** — Part B's refactor in 3ca7718c extracted `check_stage_ordering` as a pure free function driven by pipeline config. When the session status, config, or pipeline cannot resolve at check time, the new code returns `None` (no block) whereas the prior inline code had a hardcoded `"ws-rev requires prior primary stage"` fallback branch. **Why the trade-off is acceptable:** the stage-ordering check here only runs at stage-sentinel-write time (cf-development signaling STAGE-COMPLETE: WS-REV after work stages). At that moment, a silent bypass allows one wrongly-created sentinel into the state directory — but that sentinel cannot cause work to be pushed or merged. The SAME pipeline check runs again at `Bash(git push)` / `Bash(gh pr create)` time via `check_cumulative_push_pr_gate` in pre_tool_use.rs, which verifies ALL pipeline stage sentinels exist for the declared work_type. A session that bypassed stage ordering at sentinel-write time will still be blocked at push time if any prior stage is actually missing — the user cannot ship unreviewed/untested code. The push/PR gate is universally config-driven with fallback=5 phases, so degradation is bounded. **Rework iter 1 upgrade:** F5 was promoted from doc-only to actual code change — each of the 4 None-return paths now emits `diagnostics::warn` with a specific reason (session-dir unresolved, work_type missing, config load error, no pipeline entry). Auditable via hook logs; a real misconfiguration produces visible diagnostics rather than silently degrading.

- **is_pr_push_command(command)**: `command` comes from `tool_input["command"]` (the Bash command string sent by the LLM agent). - **bash_command_succeeded(tool_response)**: reads JSON from tool response. Unknown shapes default to `true` (tolerant default). This cannot escalate privileges — a false true only means pr_pushed=true gets set when it shouldn't, which is a minor UX concern (potential extra WIP commit), not a security breach.

The caller at cleanup.rs:215 uses the `name` field from a WorktreeEntry which was registered by the CLI, not from an external trust boundary. No trust boundary crossing found.

#### Concurrency Security

- `update_session_status` uses `locked_rmw` for atomic read-modify-write — prevents concurrent writes corrupting the status file
- TOCTOU between pr_pushed write and rescue_uncommitted_work read: benign race. If rescue reads before hook writes, it performs an unnecessary rescue (extra WIP commit, not a security issue). The reverse (rescue skips but hook hasn't written yet) is not possible — rescue runs during cleanup AFTER the session, not concurrently.
- GateConfig is loaded once at handler construction and stored as `Option<GateConfig>` — no concurrent mutation
