# INF-TSK-021-023: Integration testing -- full PathFlow lifecycle with Go hooks

## Description

The critical pre-cutover verification task (required prerequisite for Phase E cutover). After all Go subcommands are built, this task runs a complete PathFlow lifecycle test by calling Go subcommands directly (not via settings.json wiring). This tests the Go implementations in isolation: session start, phase progression, sentinel creation, gate enforcement, security checks, and session end. Any failure here means a Go subcommand has a bug that must be fixed before the cutover task (INF-TSK-021-022) can proceed. Note: this tests Go subcommands directly; the separate shadow testing task (INF-TSK-021-030, if created) would test Go-vs-shell comparison.

## Approach

1. Create `codeflow-cli/internal/integration/` package:
   - `lifecycle_test.go`:
     - `func TestFullPathFlowLifecycle(t *testing.T)` -- end-to-end test:
       1. Create temp project dir with required config files (enforcement-policy.json, pathflow-config.json) using `testutil.TempProject(t)`
       2. Call `init_.StartInit(stdin, projectDir)` using test Initializer (mock SessionStarter, mock ProcessChecker) -- verify session dir created, pathflow-active flag set, checkpoint initialized for 7 phases; StartInit() also calls StartSession() → session_start event appears in sessions.jsonl
       3. Simulate PF1-PF3 phase tasks: call `cp.RegisterTask(checkpointPath, sentinelDir, taskID)` + `cp.CompleteTask(checkpointPath, sentinelDir, taskID)` for each, verify pf-1, pf-2, pf-3 sentinels created. Note: checkpoint.Checkpoint is a struct with Now field, not an interface.
       4. Call `(&gate.GateChecker{SentinelDir: sentinelDir}).Check(toolName, toolInput)` with Edit tool input -- verify ALLOWED (pf-3 exists)
       5. Call gate checker with Edit tool input WITHOUT pf-3 sentinel -- verify BLOCKED
       6. Simulate WS-DEV stage: call `sentinel.CheckAndCreateStageSentinel(stdin, sentinelDir)` with STAGE-COMPLETE pattern -- verify `pathflow-ws-dev` sentinel created
       7. Call `security.NewChecker().Check(checkCtx)` with dangerous command input -- verify BLOCKED
       8. Call `security.NewChecker().Check(checkCtx)` with safe command input -- verify ALLOWED
       9. Call `team.CheckTeamDelete(stdin, sessionDir, sentinelDir)` with pathflow-active flag -- verify BLOCKED
       10. Call `team.CheckTeamDelete` with pf-6 sentinel -- verify ALLOWED
       11. Simulate WS-REV, WS-QA stages, PF5-PF7 phases
       12. Call `cleaner.EndCleanup(stdin, projectDir)` using test Cleaner (mock ProcessChecker) -- verify pathflow-active removed, state archived, session_end event in sessions.jsonl; note: EndCleanup writes session_end event via ledger.NewWriter to sessions.jsonl (NEW behavior vs shell hook which did NOT write JSONL events)
       13. Verify all 7 phase sentinels exist (pf-1 through pf-7)
       14. Verify JSONL ledger has session_end events with correct Go canonical schema (event/timestamp fields, NOT type/ts)
     - `func TestGateEnforcementIndependent(t *testing.T)` -- table-driven:
       - Edit before pf-3 (block), Edit after pf-3 (allow), git push before pf-5+ws-rev (block), git push after pf-5+ws-rev (allow), role spawn before pf-3 (block), no pathflow-active (allow all)
     - `func TestSecurityEnforcementIndependent(t *testing.T)` -- table-driven:
       - `rm -rf /` (block), `sudo` (block), `git push --force` (block), `ls` (allow), `cat file.txt` (allow)
     - `func TestSentinelPipelineIndependent(t *testing.T)` -- table-driven:
       - STAGE-COMPLETE pattern creates sentinel, no pattern no sentinel, checkpoint register/complete lifecycle, phase sentinel created when all tasks done
   - `testdata/`:
     - `enforcement-policy.json` -- test enforcement policy
     - `pathflow-config.json` -- test pathflow config
     - `hook-stdin-samples/` -- sample stdin JSON for each hook event type
   - `runbook.md`:
     - Step-by-step manual verification procedure
     - How to run integration tests: `cd codeflow-cli && go test -v -timeout 300s ./internal/integration/...`
     - Expected output for each test
2. Run `./codeflow test` to verify existing test suite not regressed
3. Run `go test -race ./internal/integration/...` to verify no race conditions

## Notes

- This is a TEST pipeline task. Route to cf-quality-assurance.
- The integration test must be able to run without an active Claude Code session (mock the stdin JSON).
- Consider testing with `go test -timeout 300s` as lifecycle tests may be slow.
- The runbook should document how to manually verify the Go hook migration.
- See `.codeflow/docs/analysis/go-cli-migration-comprehensive.md` Section 13 (Recommendation) for detailed mapping.
- **Go test conventions:** Go tests must achieve >= 85% coverage on new business packages per test-config.json. Top-level test functions MUST use `t.Parallel()`; subtests sharing temp state MUST NOT. Do not use `context.Background()` (use `context.TODO()` or test-specific context). New packages registered in test-config.json business_packages (or noted in INF-TSK-021-028 for batch registration).
- **Integration package is test-only:** `internal/integration/` contains only `_test.go` files. It must NOT be added to `business_packages` in test-config.json — integration packages are excluded from per-file coverage enforcement.
- **Schema Divergence:** Shell scripts use `type`/`ts` field names and `session_metadata` event type for session registration. Go uses `event`/`timestamp` field names and `session_register` event type. Integration tests MUST verify Go canonical schema (`event`/`timestamp` fields, `session_register` event type), NOT shell schema. See INF-TSK-021-026 for JSONL normalization of historical events. Tests use isolated testdata fixtures — they do not depend on TSK-026 completing first.
- **EndCleanup new behavior:** Go `EndCleanup()` writes `session_end` event to `sessions.jsonl` via `ledger.Writer`. This is new behavior vs the shell hook which did NOT write JSONL events. Integration tests verify no duplicate `session_end` events in `sessions.jsonl`.
- **Teammate mode:** When lead PID is alive, `StartInit()` returns `IsTeammate=true` and skips checkpoint init and pathflow flag creation. Integration tests verify this path.
- **Compact/resume path:** `StartInit()` with `source=compact` and dead PID updates `lead_pid` without full cleanup. Integration tests verify source=compact path updates lead_pid.
- **Isolated testdata:** Integration tests create isolated temp directories via `testutil.TempProject(t)` — they do not read from or write to live project state.
