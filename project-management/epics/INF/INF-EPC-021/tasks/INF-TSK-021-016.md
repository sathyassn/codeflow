# INF-TSK-021-016: Build Go CLI for settings validation and protection guard

## Description

This task builds three Go components that together replace the settings management and protected-resource shell scripts:

**Component 1 — setup-managed-settings (KEPT):** Migrates `setup-managed-settings.sh` (417 lines) to Go as `codeflow settings setup-managed`. Go handles sudo via `os/exec` calling `sudo`. Creates or updates `/Library/Application Support/ClaudeCode/managed-settings.json` on macOS. Creates `internal/settings/` package.

**Component 2 — Settings validation (NEW):** Consolidates the PostToolUse `cf-post-tool-use-settings-templates.sh` hook into Go with a shared core function `ValidateSettingsTemplates(projectDir)` used by both entry points:

- Hook entry: `codeflow hooks post-tool-use settings-validate` — reads stdin, filters for Edit/Write to `settings-templates/*.json`, always exits 0 (advisory), outputs `hookSpecificOutput` JSON.
- CLI entry: `codeflow settings validate` — no stdin, runs unconditionally, human-readable output, non-zero exit on failure.
- Validations: (a) hooks section SHA256 consistency across all 4 templates, (b) `_version` consistency, (c) hook wiring audit (orphaned or broken scripts), (d) full file SHA256 checksum of `settings.json` vs `autonomous.json` template source, (e) full file SHA256 checksum of `settings.local.json` vs `autonomous.json` template source.
- Requires adding `SettingsTemplates` struct to `EnforcementPolicy` in `security/readers.go` to expose `copy_mappings` from `enforcement-policy.json`.
- Both `settings.json` and `settings.local.json` map to `autonomous.json` per `enforcement-policy.json` `copy_mappings`.

**Component 3 — Protection guard (NEW):** Replaces 5 dormant staging scripts and consolidates the protection-resource tier check into a single command `codeflow hooks pre-tool-use protection-guard`:

- Checks if a file path is in a protected tier (critical/high/moderate) per `enforcement-policy.json`.
- If protected: auto-copies to staging area, provides structured LLM feedback with tier info and next steps.
- If not protected: allows through (exit 0).
- Consolidates: `cf-pre-tool-use-protected-resource.sh` (tier check) + `cf-post-tool-use-tmp-workflow.sh` (staging guidance) + 5 dormant staging scripts (`cf-stage-edit.sh`, `cf-apply-staged-edit.sh`, `cf-reject-staged-edit.sh`, `cf-rollback-edit.sh`, `cf-cleanup-expired.sh`).

**NOTE:** This is DIFFERENT from `edit-write-guard` (INF-TSK-021-018), which enforces Edit/Write file path scope permissions. `protection-guard` checks protection TIER and handles the staging workflow. These are complementary commands, not overlapping.

**DROPPED from original scope:**

- `codeflow settings approval-mode` — the shell script `cf-change-approval-mode.sh` is dropped; the `/cf-approval-mode` slash command remains as-is (AI-handled, no Go binary needed).
- `codeflow staging stage/apply/reject/rollback/cleanup` — replaced by `protection-guard` (integrated staging).

## Approach

1. Create `codeflow-cli/internal/settings/` package:
   - `managed.go`:
     - `func SetupManagedSettings(projectDir string) error` — creates or updates `/Library/Application Support/ClaudeCode/managed-settings.json` on macOS; invokes `sudo` via `os/exec` to write to the system path.
     - Go equivalent of: `setup-managed-settings.sh` (417 lines)
   - `validate.go`:
     - `func ValidateSettingsTemplates(projectDir string) ([]ValidationResult, error)` — shared core function used by both hook and CLI entry points. Runs 5 validations: (a) hooks SHA256 consistency across 4 templates, (b) `_version` consistency, (c) hook wiring audit, (d) full file SHA256 of `settings.json` vs `autonomous.json`, (e) full file SHA256 of `settings.local.json` vs `autonomous.json`. Reads `copy_mappings` from `EnforcementPolicy.SettingsTemplates`.
   - `settings_test.go`:
     - Managed settings setup (new install, existing install — idempotent), settings validation (all pass, SHA256 mismatch, missing template), hook entry exits 0 always (advisory), CLI entry non-zero on failure.

2. Add `SettingsTemplates` struct to `EnforcementPolicy` in `security/readers.go`:
   - `type SettingsTemplates struct { Directory string; CopyMappings []CopyMapping }` where `CopyMapping` has `Template`, `Destination`, `Purpose` fields.
   - Update `EnforcementPolicy` struct to include `SettingsTemplates SettingsTemplates \`json:"settings_templates"\``.

3. Create `codeflow-cli/internal/hooks/resource/` package:
   - `resource.go`:
     - `type ProtectionTier string` — `const TierCritical = "critical"`, `const TierHigh = "high"`, `const TierModerate = "moderate"`
     - `type ProtectionGuard struct { Resources map[string]ProtectionTier; StagingDir string }` — loaded from `enforcement-policy.json` `resource_protection` section.
     - `func (g *ProtectionGuard) Check(stdin io.Reader) (Verdict, error)` — parses stdin JSON (PreToolUse for Edit/Write/Bash), extracts target file path, checks against protection tiers:
       - Critical: auto-copies to staging area at `.state/staging/`, outputs structured LLM feedback with tier info and exact `cp` command to apply, exits 2 (block).
       - High: outputs caution message with staging recommendation, exits 2 (block, require acknowledgment).
       - Moderate: allows through with log entry, exits 0.
       - Unprotected: allows through (exit 0).
   - `resource_test.go`:
     - Table-driven: critical resource (block + auto-stage), high resource (block + caution), moderate resource (allow+log), unprotected resource (allow), Bash command targeting protected path.

4. Add CLI subcommands:
   - `codeflow settings setup-managed` — initialize managed settings.
   - `codeflow settings validate` — standalone settings template validation.
   - `codeflow hooks post-tool-use settings-validate` — hook entry point (reads stdin, advisory, always exits 0).
   - `codeflow hooks pre-tool-use protection-guard` — protection tier check with auto-staging.
