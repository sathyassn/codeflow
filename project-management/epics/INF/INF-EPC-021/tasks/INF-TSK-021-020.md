# INF-TSK-021-020: Build Go CLI workgraph commands

## Description

Build atomic CLI commands for epic and task lifecycle management under a new `codeflow workgraph` command group. Currently, cf-knowledge-layer creates epics/tasks via 4-5 fragile steps: Python ULID generation, manual format_id query via `codeflow db generate-id`, raw SQL INSERT via `codeflow db exec`, and manual JSONL append via `codeflow ledger append`. This task consolidates each operation into a single atomic CLI command that generates IDs, writes the DB, and appends the JSONL event in one call.

**Why this replaced the original scope:** The original task described absorbing `migrate-to-dual-id.sh` into `codeflow db migrate`. That shell script is a markdown file migration (rewrites YAML frontmatter in epic/task docs), NOT a SQL migration. SQL format_id columns already exist via migrations 001 and 005. The markdown migration has already been applied. The real gap is atomic workgraph commands for the LLM-to-CLI interface.

## Approach

1. Create `internal/workgraph/` package with a `Service` struct holding DB and ledger writer references
2. Implement `CreateEpic`, `CreateTask`, `UpdateEpic`, `UpdateTask`, and query functions as business logic
3. Add `ParseEpicSeq` helper to `internal/idgen/formatid.go` (extracts epic sequence from format_id for task ID generation)
4. Create `cmd/codeflow/workgraph.go` with cobra command group and 5 subcommands
5. Register `workgraph` in the root command tree (`main.go`)
6. Update `config/testing/test-config.json` to include `./internal/workgraph/...` in business_packages
7. Write comprehensive tests for all commands and business logic

## Command Design

### 1. codeflow workgraph create-epic

**Flags:** `--db` (default `.state/db/codeflow.db`), `--ledger` (default `.state/ledger`), `--data` (JSON string, alternative to stdin)

**Required input fields:** `title`, `area_type`, `work_type`, `domain`

**Optional input fields:** `status` (default `draft`), `summary`, `is_ongoing` (default `false`), `file_scope` (JSON array), `priority` (default `normal`)

**Internal operations:**

1. Parse and validate JSON input
2. Validate field values against CHECK constraints (status: draft/planning/in_progress/blocked/complete/archived; priority: low/normal/high/critical)
3. Validate area_type, work_type, domain exist in reference tables
4. Generate ULID PK: `idgen.NewPrefixedULID("epic")` → `epic-01jm...`
5. Query next seq: `idgen.NextFormatID(ctx, db, "epics", areaType)` → `idgen.FormatEpicID(areaType, seq)` → `INF-EPC-022`
6. INSERT into epics table (all columns from input + generated IDs + timestamps)
7. Append `epic_created` event to JSONL via ledger writer (includes id, format_id, title, area_type, work_type, domain, status, timestamp)
8. Print JSON result to stdout

**Output (JSON):**

```json
{
  "id": "epic-01jm...",
  "format_id": "INF-EPC-022",
  "title": "Epic title"
}
```

### 2. codeflow workgraph create-task

**Flags:** `--db`, `--ledger`, `--data`

**Required input fields:** `epic_id` (ULID PK of the parent epic), `title`, `area_type`, `work_type`, `domain`

**Optional input fields:** `description`, `status` (default `todo`), `origin` (default `planned`), `file_scope`, `scope_policy` (default `soft`), `scope_root`, `estimate`, `priority` (default `normal`), `acceptance` (JSON array of strings), `tests` (JSON array of strings), `autorun_eligible` (default `false`), `raise_pr` (default `true`), `auto_merge` (default `false`), `target_branch`

**Internal operations:**

1. Parse and validate JSON input
2. Validate field values against CHECK constraints (status: todo/blocked/in_progress/complete/cancelled; origin: planned/informal/auto; scope_policy: soft/hard/permissive; priority; estimate via FK)
3. Verify `epic_id` exists in epics table; retrieve epic's format_id to extract epic sequence number
4. Parse epic sequence: `ParseEpicSeq(epicFormatID)` → e.g., `21` from `INF-EPC-021`
5. Generate ULID PK: `idgen.NewPrefixedULID("task")` → `task-01jm...`
6. Query next task seq: `idgen.NextFormatID(ctx, db, "tasks", areaType)` → `idgen.FormatTaskID(areaType, epicSeq, taskSeq)` → `INF-TSK-021-001`
7. INSERT into tasks table
8. Append `task_created` event to JSONL (includes id, format_id, epic_id, epic_format_id, title, area_type, work_type, domain, status, timestamp)
9. Print JSON result

**Output (JSON):**

```json
{
  "id": "task-01jm...",
  "format_id": "INF-TSK-021-001",
  "epic_id": "epic-01jm...",
  "title": "Task title"
}
```

### 3. codeflow workgraph update-epic

**Flags:** `--db`, `--ledger`, `--data`

**Required input fields:** `id` (ULID) OR `format_id` (human-readable) — at least one to identify the epic

**Optional input fields (any field to update):** `title`, `summary`, `status`, `is_ongoing`, `file_scope`, `priority`, `pr_number`, `external_id`, `external_url`

**Internal operations:**

1. Parse input, resolve epic by id or format_id (query DB to get both)
2. Validate any field values against CHECK constraints
3. UPDATE specified columns in epics table + set updated_at
4. If `status` was changed: append `epic_status_changed` event to JSONL (includes epic_id, old_status, new_status, timestamp)
5. Print JSON result

**Output (JSON):**

```json
{
  "id": "epic-01jm...",
  "format_id": "INF-EPC-021",
  "updated_fields": ["status", "priority"]
}
```

### 4. codeflow workgraph update-task

**Flags:** `--db`, `--ledger`, `--data`

**Required input fields:** `id` (ULID) OR `format_id` — at least one to identify the task

**Optional input fields:** `title`, `description`, `status`, `file_scope`, `scope_policy`, `scope_root`, `estimate`, `priority`, `assignee_id`, `autorun_eligible`, `raise_pr`, `auto_merge`, `target_branch`, `acceptance`, `tests`, `branch`, `pr_number`, `external_id`, `external_url`, `stage`, `stage_status`

**Internal operations:**

1. Parse input, resolve task by id or format_id
2. Validate field values
3. UPDATE specified columns + set updated_at; if status changed to `in_progress`, set started_at; if to `complete`, set completed_at
4. If `status` was changed: append `task_status_changed` event to JSONL (includes task_id, format_id, old_status, new_status, timestamp)
5. Print JSON result

**Output (JSON):**

```json
{
  "id": "task-01jm...",
  "format_id": "INF-TSK-021-001",
  "updated_fields": ["status", "branch"]
}
```

### 5. codeflow workgraph query

**Flags:** `--db`, `--mode` (required), `--id`, `--format-id`, `--epic-id`, `--area`, `--status`, `--domain`, `--work-type`, `--limit` (default 50)

**Modes and behavior:**

| Mode | Required Flags | Optional Filters | Output |
|---|---|---|---|
| `get-epic` | `--id` or `--format-id` | (none) | Single epic JSON object |
| `get-task` | `--id` or `--format-id` | (none) | Single task JSON object |
| `list-epics` | (none) | `--area`, `--status`, `--domain`, `--work-type`, `--limit` | JSON array of epics |
| `list-tasks` | (none) | `--epic-id`, `--area`, `--status`, `--domain`, `--work-type`, `--limit` | JSON array of tasks |

**Internal operations:**

1. Parse mode and flags
2. Build parameterized SELECT query (never string interpolation — use `?` placeholders)
3. Execute query against DB
4. Marshal results to JSON
5. Print to stdout

**Output examples:**

```json
// get-epic / get-task: single object
{
  "id": "epic-01jm...",
  "format_id": "INF-EPC-021",
  "title": "Go CLI Migration",
  "status": "in_progress",
  ...
}

// list-epics / list-tasks: array
[
  {"id": "epic-01jm...", "format_id": "INF-EPC-021", "title": "...", "status": "..."},
  ...
]
```

**Why this over raw `codeflow db query`:** Parameterized queries eliminate SQL injection risk, consistent JSON output format, validated inputs, and the caller (cf-knowledge-layer) never needs to construct SQL strings.

## Notes

### Original Scope Was Incorrect

The task previously described absorbing `migrate-to-dual-id.sh` into `codeflow db migrate`. That shell script is a markdown file migration (rewrites YAML frontmatter in epic/task docs), NOT a SQL migration. SQL format_id columns already exist via migrations 001 and 005. The real gap was atomic workgraph CLI commands.

### What This Replaces

cf-knowledge-layer currently creates epics/tasks via 4-5 separate CLI commands:

1. `python3 .codeflow/scripts/codeflow_py_lib/ulid_generator.py` → ULID PK
2. `codeflow db generate-id --table epics --area INF` → format_id (or just seq for tasks)
3. `codeflow db exec "INSERT INTO epics (...) VALUES (...)"` → DB write
4. `codeflow ledger append --event '{"event":"epic_created",...}'` → JSONL write

Each step is an independent CLI call where one can fail silently, leaving DB and JSONL inconsistent. The workgraph commands replace all 4 steps with 1 atomic call.

### ParseEpicSeq Addition

`internal/idgen/formatid.go` needs a new function:

```go
// ParseEpicSeq extracts the numeric sequence from an epic format ID.
// Example: "INF-EPC-021" → 21
// Returns ErrInvalidFormatID if the format doesn't match {AREA}-EPC-{NNN}
func ParseEpicSeq(formatID string) (int, error)
```

This is needed by create-task to construct the full task format_id using `FormatTaskID(areaType, epicSeq, taskSeq)`.

### NextFormatID Requires Querier Adapter

`idgen.NextFormatID` takes a `Querier` interface, not `*sql.DB` directly. The caller must wrap the DB connection using the adapter: `idgen.QueryRowFunc(db.QueryRowContext)`. See `cmd/codeflow/internal.go:78-80` for the existing usage pattern.

### task_status_changed Event Key: Use `task_id` Not `id`

Some legacy production JSONL events use `"id"` as the key in `task_status_changed` events. The new workgraph `update-task` command MUST emit `"task_id"` per the `schema.go` validation spec and `sync.go`'s `applyTaskStatusChanged` handler (which reads `getString(raw, "task_id")`). Do NOT follow the inconsistent legacy format.

### FormatTaskID Asymmetry

The existing `codeflow db generate-id --table tasks` returns only the 3-digit sequence, not the full format_id. The workgraph create-task command internalizes this — the caller never needs to assemble the format_id manually.

### Event Schema Compatibility

The JSONL events produced by create/update commands MUST match what `sync.go` event handlers expect:

- `applyEpicCreated` looks for: `id`, `format_id`, `title`, `status`, `area_type`, `work_type`, `domain`, `is_ongoing`, `file_scope`, `priority`
- `applyTaskCreated` looks for: `id`, `format_id`, `epic_id`, `title`, `status`, `area_type`, `work_type`, `domain`, `origin`, `priority`
- `applyEpicStatusChanged` looks for: `epic_id`, `new_status`
- `applyTaskStatusChanged` looks for: `task_id`, `new_status`

Ledger schema validation (`schema.go`) requires:

- `epic_created` → `id` + `title`
- `task_created` → `id` + `epic_id` + `title`
- `epic_status_changed` → `epic_id` + `new_status`
- `task_status_changed` → `task_id` + `new_status`
