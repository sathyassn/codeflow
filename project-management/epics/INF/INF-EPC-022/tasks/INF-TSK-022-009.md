# INF-TSK-022-009: Implement DataStore trait and SurrealStore

## Description

Define the `DataStore` trait -- the primary data access abstraction for the Rust CLI. The trait encapsulates all database operations behind an async interface, enabling mock-based testing and future implementation swaps (e.g., `ws+unix://` connection for global daemon mode in Epic C).

`SurrealStore` is the sole `DataStore` implementation. It uses the `surrealdb` crate in embedded `surrealkv://` mode, connecting to `.state/db/codeflow/`. All queries use SurrealQL, not SQL. Schema initialization uses idempotent DEFINE statements that can be re-run safely.

There is NO `SqliteStore`. SurrealDB replaces SQLite entirely per Decision #17. The `DataStore` trait is retained for testability (MockStore) and future extensibility, not for multiple production implementations in this epic.

The Go CLI currently has 37 SQLite tables (per `schema-standardization.md`). All must be translated to SurrealDB DEFINE TABLE statements with appropriate DEFINE FIELD and DEFINE INDEX declarations.

## Approach

1. Define `DataStore` trait in `traits/datastore.rs` with async methods using `#[async_trait]`
2. Define method signatures matching the Go `internal/db/` package API surface
3. Implement `SurrealStore` in `store/surreal.rs` with embedded `surrealkv://` connection
4. Implement schema initialization: DEFINE TABLE, DEFINE FIELD, DEFINE INDEX for all tables
5. Implement CRUD methods using SurrealQL queries
6. Create `MockStore` in test module implementing DataStore with in-memory state
7. Write unit tests against `Surreal::new::<Mem>()` for integration tests
8. Write unit tests against `MockStore` for pure trait-based testing
9. Ensure 85% coverage on all store modules

## Notes

The Go CLI has 37 SQLite tables per the schema audit. The SurrealDB schema should consolidate where possible (SurrealDB supports nested objects natively, reducing the need for join tables). Graph relations (DEFINE TABLE TYPE RELATION) replace foreign key relationships for task-epic and session-task associations.

**SurrealDB Rationale:** SurrealDB embedded (Option E from `data-layer-protection.md` Section 5) chosen over alternatives: Option A (sidecar process), Option B (sidecar + Loro FFI), Option C (wait for Go SDK), Option D (Rust shared library + CGo). Option E provides: single language (pure Rust), maximum performance (no FFI/IPC overhead), embedded `surrealkv://` storage (no external process), and native async support via Tokio.

**Standards references:** Follow cf-surrealdb-standards (task 004) for embedded mode patterns, SurrealQL conventions, schema migration strategy, connection management, and testing patterns. Follow cf-rust-standards (task 003) for trait design patterns, error handling (`Result<T, DbError>` with thiserror), and async patterns.
