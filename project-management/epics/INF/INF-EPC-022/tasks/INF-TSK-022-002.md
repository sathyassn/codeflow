# INF-TSK-022-002: Define trait hierarchy and module map

## Description

Design the core trait hierarchy and module dependency graph for the Rust CLI. This document is the architectural blueprint that all Phase 0C-0E implementation tasks follow. The trait hierarchy must match the architecture defined in `data-layer-protection.md` Section 6, while the module map translates Go packages to Rust modules with appropriate consolidation and separation.

Key traits to define:
- `DataStore` -- CRUD operations for sessions, tasks, epics, workgraph (sole impl: `SurrealStore`)
- `LedgerWriter` -- append-only event logging (sole impl: `JsonlWriter`)
- `HookHandler` -- hook event processing with typed input/output

Traits deferred to Epic A (NOT defined here, but placeholders documented):
- `Coordinator` -- CRDT claim/merge/sync (impl: `LoroCoordinator` in Epic A)
- `Transport` -- delta exchange mechanism (impls: `FileTransport`, `GitRefTransport` in Epic A)

## Approach

1. Read the Go CLI audit from INF-TSK-022-001
2. Read `data-layer-protection.md` Section 6 for the target architecture
3. Define each trait's method signatures with Rust types (using domain enums from task 006)
4. Map each Go package to its Rust module, documenting merge/split decisions
5. Draw the module dependency graph (which modules import which)
6. Verify no circular dependencies in the proposed graph
7. Document placeholder traits (Coordinator, Transport) with Epic A cross-references

## Notes

The trait hierarchy is the architectural foundation. `DataStore` and `LedgerWriter` are implemented in Phase 0C. `HookHandler` is implemented in Phase 0D. `Coordinator` and `Transport` are placeholders here and implemented in Epic A. The key design principle: code depends on traits, not implementations. This enables mock-based unit testing and future implementation swaps.

**Standards references:** Follow cf-rust-standards for trait design patterns (trait objects vs generics decision tree), naming conventions, and module visibility rules. Refer to `data-layer-protection.md` Section 6 for the target architecture diagram.

**Go source references for trait mapping:**
- `DataStore` maps to: `codeflow-cli/internal/db/connection.go`, `codeflow-cli/internal/db/queries.go`, `codeflow-cli/internal/db/models.go`, `codeflow-cli/internal/db/transactions.go`
- `LedgerWriter` maps to: `codeflow-cli/internal/ledger/writer.go`, `codeflow-cli/internal/ledger/routing.go`
- `HookHandler` maps to: `codeflow-cli/cmd/codeflow/hooks.go` (dispatch), `codeflow-cli/internal/hooks/` (implementations per subdirectory: gate/, edit/, team/, sentinel/, session/, etc.)

**Cross-task coherence:**
- Consumes audit findings from task 001 (`go-audit.md`)
- Produces trait signatures consumed by tasks 006 (type definitions), 009 (DataStore impl), 010 (LedgerWriter impl), 015 (HookHandler impl)
- Module map consumed by task 005 (workspace structure)
