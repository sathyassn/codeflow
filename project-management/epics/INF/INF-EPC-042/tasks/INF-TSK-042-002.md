# INF-TSK-042-002: Fix worktree cleanup log residue and missing source field in registry

> **MANDATORY VALIDATION:** Files created from this template MUST be validated before committing:
> `codeflow validate task <file-path>`
> Fix all errors (exit code 1) before requesting a commit. Warnings are advisory.

## Description

Two bugs in the worktree lifecycle:

1. **Log residue bug:** `write_cleanup_log()` in `session_end.rs` writes cleanup logs to the worktree's `.state/logs/sessions/` path. Since the worktree is being destroyed, this log either gets lost or creates residue in the wrong location. It should write to the main repo's `.state/logs/sessions/` directory.

2. **Missing source field:** `interactive.rs` creates worktree registry entries (`WorktreeEntry`) without setting the `source` field, leaving it null/default. This causes downstream issues where the registry can't distinguish how the worktree was created.

### Path Traversal Analysis (focused review)

`resolve_effective_root` (session_end.rs:~L99, worktree/mod.rs:290-317) uses two resolution methods:

- **Method 1** (ancestor walk): Iterates `dir.ancestors()` looking for a component named `.git-worktrees`. Returns `ancestor.parent()`. This is pure path component comparison — no filesystem reads beyond what `ancestors()` does (path string splitting). No user-controlled input enters this path; `project_dir` is resolved internally by `detect_project_dir()` before being passed here.
- **Method 2** (`.git` file parse): Reads `dir/.git` if it exists as a file, strips prefix `"gitdir: "`, then walks the resulting path's ancestors looking for `worktrees/` → `.git/` → main repo. The gitdir path comes from the `.git` file on disk — this is a git-maintained file in the project root, not user input. No path is used for file writes; it is used only to derive an ancestor path string. No symlink following or escaping beyond the file content.

**Verdict:** No path traversal risk. The resolved `log_root` is always a parent directory of the original `project_dir` or `project_dir` itself — it cannot traverse outside the known project tree.

### Concurrency Safety Analysis

`write_cleanup_log` uses `OpenOptions::new().create(true).append(true).open(log_path)`. Append-mode opens are atomic at the OS level on POSIX systems — concurrent writers to the same file will not interleave bytes mid-line (each `writeln!` is a single write syscall). Multiple sessions writing to the same `cleanup-{date}.jsonl` file is safe: each line is a complete JSON object. This matches the existing pattern used for all JSONL logs in this codebase.

`locked_update_source` uses `locked_binary_rmw` (file-lock based read-modify-write) — the same locking mechanism as `locked_update_lead_pid` and `locked_update_session_id`. No concurrency regression introduced.
