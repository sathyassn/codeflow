# INF-TSK-033-006: Add conditional status transitions for autorun sessions

## Description

`update_autorun_session` in `surreal.rs` currently uses an unconditional MERGE — it writes the new status regardless of the current DB value. This creates a theoretical race condition: if the orchestrator marks a session `Completed` at the same moment an abort signal arrives (setting `Aborting` or `Cancelled`), one write will silently overwrite the other. There is no protection against a stale-status overwrite.

Adding compare-and-swap (CAS) semantics — `UPDATE WHERE status = $expected RETURN AFTER` — prevents stale overwrites. The caller knows what status it expects the session to be in before transitioning; if the DB disagrees, the update is a no-op and the caller can handle accordingly.

**Current call sites for `update_autorun_session` (3 locations):**

- `orchestrator.rs:185` — session status update within the run loop
- `orchestrator.rs:344` — final status write after batch completes
- `stale.rs:391` — stale session detection sets status to Failed

All three should migrate to the new CAS method where the expected status is known. The stale detection call is the most critical — it should only write `Failed` if the session is still in a non-terminal state.

## Approach

1. **Add `update_autorun_session_cas(id, expected_status, update)` method** to the `Store` trait in `store/mod.rs`. Signature: `async fn update_autorun_session_cas(&self, id: &str, expected: AutorunSessionStatus, update: AutorunSessionUpdate) -> Result<CasResult, DbError>` where `CasResult` is a new enum: `Updated(AutorunSession)` or `NoOp` (status was not what was expected).

2. **Implement in `surreal.rs`** using SurrealQL: `UPDATE type::thing('autorun_session', $id) MERGE $data WHERE status = $expected RETURN AFTER`. If the returned array is empty, the status guard prevented the update — return `CasResult::NoOp`. If non-empty, return `CasResult::Updated(session)`.

3. **Migrate call sites in `orchestrator.rs`**: at line 185 (mid-run update) use expected=Running; at line 344 (final status) use expected=Running for the Completed/Failed/Cancelled write and handle `NoOp` by logging a warning (another process beat us to it). Also update `Pending→Running` transition if it exists.

4. **Migrate call site in `stale.rs:391`**: use expected status = any non-terminal (pass a set or use a separate `update_autorun_session_if_not_terminal` helper). If NoOp, log that session was already in a terminal state and skip.

5. **Add NoopStore and FailingStore stubs** in `mod.rs` for the new trait method.

6. **Write unit tests** covering: CAS update succeeds when expected status matches, CAS returns NoOp when status has already changed, concurrent CAS scenario (two competing writes — one wins, one gets NoOp).

## Concurrency Considerations

> The CAS semantics are the safety mechanism for the race condition this task addresses.

| Shared Resource | Access Pattern | Safety Mechanism |
|----------------|---------------|-----------------|
| `autorun_session.status` in DB | Concurrent UPDATE from orchestrator + abort signal | CAS: `UPDATE WHERE status = $expected` — only one writer wins |
| Orchestrator complete vs abort race | Both attempt to set terminal status simultaneously | First write wins; second gets `NoOp` and logs warning |
| Stale detection vs active worker | Stale detector may write `Failed` while worker completes | CAS with non-terminal guard — won't overwrite Completed/Cancelled |
| SurrealDB embedded | Single-process embedded — no true concurrent transactions | SurrealDB uses optimistic locking; `UPDATE WHERE` is atomic at the query level |
