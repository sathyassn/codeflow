# INF-TSK-023-045: Fencing token validation via Loro Map

## Description

Fencing tokens prevent stale claims from being acted upon. Each claim in the LoroMap includes a monotonically increasing `u64` fencing token. When a session acquires a claim, it receives the current token value. Before proceeding with a file operation, the PreToolUse hook validates that the session's token matches the latest token stored in `state.loro` for the claimed pattern. If a newer claim has been issued (token mismatch), the operation is blocked with an advisory exit 2.

This builds on the claim wiring from INF-TSK-023-044, adding the validation layer that detects stale claims even when the claiming session believes it still holds the resource.

## Approach

1. In `claims.rs`, add `fencing_token: u64` field to claim entries stored in LoroMap
2. On `acquire()`, increment the global token counter (atomic u64) and store with the claim
3. Return the token to the caller as part of the claim result
4. In `tooluse.rs` gate-check handler, after successful claim acquisition:
   a. Read current token from LoroDoc for the claimed pattern
   b. Compare against the session's stored token
   c. If mismatch (another session acquired a newer claim): return exit 2 with advisory warning
   d. If match: proceed with the operation
5. Token comparison is a single atomic read from LoroDoc -- no read-modify-write cycle needed
6. Write concurrency tests: two threads claim same pattern, one gets newer token, other detects mismatch
