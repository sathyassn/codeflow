# INF-TSK-023-016: Autorun worker worktree integration

## Description

The autorun batch orchestrator currently runs all workers in the project root directory (`work_dir: "."`). This means concurrent workers share the same filesystem, leading to file conflicts. This task updates the worker to create a per-worker worktree before invoking Claude, pass the worktree path as `work_dir`, and clean up the worktree after completion.

The worker lifecycle becomes: create worktree -> claim files via Loro -> invoke Claude in worktree -> cleanup worktree.

## Approach

1. In `TmuxWorker.run()`, before invoking Claude:
   a. Generate worker session ID
   b. Call `Manager::setup_detached(&format!("worktree-{}", worker_sid))`
   c. Set `CODEFLOW_WORKTREE_PATH` in worker environment
   d. Set `InvokeConfig.work_dir` to the worktree absolute path
2. In batch orchestrator validation:
   a. Check batch size against `max_session_workers` (default 3, Decision #10)
   b. Reject batches exceeding the limit
3. After worker completes (any exit path):
   a. Call `Manager::cleanup(worktree_name, force=true)` in a finally/drop handler
   b. Deregister from `.state/worktrees.yaml`
4. Worker claims file patterns from task's `file_scope` via LoroCoordinator before starting
5. Write integration test: two workers run concurrently with separate worktrees

> Populated by cf-development before STAGE-COMPLETE: WS-DEV

**Implementation Summary:**

Added per-worker worktree lifecycle to the autorun worker. Key design decision: introduced a `WorktreeProvider` trait (following the existing `TmuxRunner`/`ClaudeInvoker` DI pattern) so worker tests can mock worktree operations without requiring a real git repo. The `RealWorktreeProvider` implementation delegates to `WorktreeManager`. Added `AutorunError::Worktree` variant for error propagation. Added `file_scope: Vec<String>` to `TaskSpec` and `WorkerConfig` to thread file claim data through the pipeline (Loro acquire/release deferred to task 018 which covers registry locking and coordination). Added `max_workers` validation in `validate_batch()`. Registry write race condition is a known issue documented for task 018.

**Deviations from Approach:**

- AC #7 (Loro claims): Marked PARTIAL. Added `file_scope` field threading through TaskSpec -> WorkerConfig, but actual Loro `coordinator.acquire()`/`release()` calls were deferred. The `Coordinator` trait takes `&mut self` which requires threading a mutable coordinator through the worker, and task 018 (Parallel session coordination) specifically covers registry locking and coordination. The file_scope data pipeline is ready for task 018 to consume.
- Used 16-char ULID suffix for worktree names instead of 8-char (task spec suggested `[4..12]`) to avoid collisions when workers start within the same millisecond.
- Integration test (AC #9) implemented as `test_worker_unique_worktree_names` which verifies two workers get distinct worktree names, rather than a full concurrent execution test (which would require real git repos and is better suited for WS-QA).
