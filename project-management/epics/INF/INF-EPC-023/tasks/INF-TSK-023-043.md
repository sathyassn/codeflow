# INF-TSK-023-043: Replace state.json with state.loro using Loro Map CRDT

## Description

The current claims system uses a plain JSON file (`state.json`) with a read-modify-write cycle that has a TOCTOU race condition. Two sessions calling `Acquire()` concurrently can both read the same state, both add their claim, and one write overwrites the other -- losing a claim. This is the central coordination bug blocking parallel execution.

This task replaces `state.json` with `state.loro` using Loro Map CRDT as the sole coordination mechanism (Decision #8). `LoroCoordinator` implements the `Coordinator` trait from Epic 0. Loro's Map CRDT resolves concurrent inserts deterministically via last-writer-wins on the same key, eliminating the race entirely.

Per Decision #23, the LoroDoc namespace must reserve containers for future knowledge graph sync (Epic C): `kg_entities`, `kg_relationships`, `kg_metadata`, `extraction_queue`.

## Approach

1. Define `LoroCoordinator` struct implementing `Coordinator` trait from `codeflow-core::traits::coordinator`
2. Initialize `LoroDoc` with named containers: `claims` (LoroMap), `merge_queue` (LoroList), `kg_entities` (LoroMap, reserved), `kg_relationships` (LoroMap, reserved), `kg_metadata` (LoroMap, reserved), `extraction_queue` (LoroList, reserved)
3. Implement `acquire(pattern, session_id)`: insert claim into LoroMap with `{owner, token, ttl, timestamp}` value
4. Implement `release(pattern, session_id)`: remove claim from LoroMap
5. Implement `check(pattern)`: read claim from LoroMap, check TTL expiry
6. Persist LoroDoc to `.state/coordination/state.loro` via `doc.export(Snapshot)` with atomic temp+rename
7. Load state on startup via `LoroDoc::from_snapshot(bytes)`
8. Write concurrency tests using Rust's `std::thread` with two threads acquiring the same pattern

## Acceptance Criteria

1. LoroCoordinator struct implements Coordinator trait from Epic 0
2. Claims stored in LoroMap container keyed by exact file path (relative to project root) -- no glob matching; glob patterns deferred to enforcing mode (future)
3. Claim values include owner session_id, fencing token, TTL, and timestamp
4. Define newtype wrappers: `SessionId(Ulid)`, `WorktreeId(String)`, `FencingToken(u64)`, `PeerId(String)` -- all coordination APIs use these types, not raw String/u64
5. Define `enum CoordinationError { ClaimConflict { path: String, owner: SessionId }, TokenMismatch { expected: u64, found: u64 }, ContainerNotFound(String), MergeFailure(loro::Error) }` -- no stringly-typed errors
6. Default claim TTL: 5 minutes (configurable via CODEFLOW_CLAIM_TTL_SECS env var)
7. LoroDoc persisted to .state/coordination/state.loro via atomic write (temp+rename)
8. Concurrent acquire from two sessions produces deterministic merge via Loro last-writer-wins
9. state.json is no longer read or written by any code path
10. Unit tests: single-session claim acquire/release, concurrent two-session claim, TTL expiry
11. Concurrency test: two threads acquire same pattern simultaneously -- one wins deterministically
12. Property-based test (proptest): concurrent claims are commutative -- Loro CRDT merge produces same final state regardless of operation order, at least 100 random test cases
13. LoroDoc namespace reserves kg_entities, kg_relationships, kg_metadata, extraction_queue containers for Epic C (Decision #23)
14. Code coverage >= 85% per file (measured by cargo-llvm-cov)
15. cargo clippy -- -D warnings passes
16. cargo fmt --check passes
