# INF-TSK-023-027: Implement scope policy enforcement + validation

> **MANDATORY VALIDATION:** Files created from this template MUST be validated against the task validation script before committing:

## Description

Wire `scope_policy` (`soft`/`hard`/`permissive`) enforcement into the edit-write-guard/claims system. `scope_policy` IS the enforcement mechanism — soft/hard/permissive determines behavior directly with no separate toggle or advisory layer. In soft mode, out-of-scope file edits trigger CRDT claim acquisition — allowed if claim succeeds (no other worker holds it), blocked if conflict. In hard mode, out-of-scope edits are blocked without claim attempt. In permissive mode, no restrictions.

Extend the `Claim` struct with `task_id: String` and `worktree_id: Option<WorktreeId>` fields for coordination intelligence. Add coordination event types (ClaimAcquired, ClaimConflict, ClaimReleased, ScopeExpansion, MergeConflictDetected, MergeRebaseAttempted) in `types/events.rs` and routing for `coordination-events.jsonl` in `ledger/routing.rs`. Add `coordination_event` table definition to `schema.surql`.

Add cross-field validation rules in `validate/mod.rs` (not config-driven). Fix invalid `scope_policy` values in store fixtures. Default `scope_policy` to `soft` when not specified in task definition. The `cf-planning` teammate determines `file_scope` and `scope_policy` for planned tasks at task creation time.

   - `hard` + file NOT in `file_scope`: BLOCK (exit 2, no claim attempt)
   - `permissive`: no scope checking, no claim acquisition, edit allowed

## Notes

Key references:
- `codeflow-cli/core/src/hooks/pre_tool_use.rs` — `try_acquire_claim` (enforcement dispatch point)
- `codeflow-cli/core/src/coordination/mod.rs` — `Coordinator::acquire` interface

- `codeflow-cli/core/src/validate/mod.rs` — task validation rules (add autorun cross-field checks here)
- `codeflow-cli/core/src/store/mod.rs` — scope_policy field (line 600: "append" should be "soft")
- `codeflow-cli/core/src/store/surreal.rs` — scope_policy field (lines 917, 1736: "strict" should be "soft")
- `.state/runtime/active-task.json` — runtime source of scope_policy and file_scope

**Enforcement model:** `scope_policy` IS the enforcement mechanism. There is no separate `claims.mode` toggle in `enforcement-policy.json` — that design was superseded. The valid values are `soft`, `hard`, and `permissive` and behavior is determined entirely by which value is set.

**At task creation time:** cf-planning (for planned tasks) determines `file_scope` and `scope_policy` based on the task's acceptance criteria and work scope. The default `scope_policy` is `soft` unless criteria indicate hard boundaries are needed (e.g., isolated infrastructure work).

**Claim struct extension:** `task_id` links the claim to the work item for auditability. `worktree_id` enables the sync daemon to identify which worktree holds a claim (used for dead PID detection and force-release).

**Validation rules:** All validation rules live in `validate/mod.rs`. There is no validation section in `parallel-work-config.json` — config is for runtime behavior, not validation rules.
