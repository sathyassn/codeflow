# INF-TSK-023-019: SurrealDB parallel access tuning

## Description

SurrealDB with the `surrealkv://` embedded engine (replacing SQLite from Epic 0) needs validation for multi-session access. When 3 concurrent sessions perform CRUD operations on the shared database, write contention may cause latency spikes. This task tunes the connection strategy, measures contention, and implements retry/backoff for busy errors.

## Approach

0. Investigate surrealkv:// locking behavior:
   a. Verify whether the exclusive lock is process-lifetime or per-query
   b. Test: open surrealkv:// from two async tasks in same process
   c. Test: concurrent CRUD from multiple tasks on shared SurrealStore
   d. Based on findings, choose strategy and document rationale
1. Configure SurrealDB embedded connection for shared access:
   a. Use `surrealkv://{path}` pointing to the shared `.state/db/` directory
   b. Evaluate connection pooling vs per-session connections
   c. Document the chosen strategy with rationale
2. Implement retry/backoff for contention errors:
   a. On `Db::Error` indicating busy/lock contention: retry with exponential backoff
   b. Backoff: 100ms initial, 2x multiplier, cap 1s, max 3 attempts (aligns with AC4 and AC5 values)
   c. After max retries: return error with context
3. Write performance benchmark:
   a. Spawn N tasks simulating concurrent sessions (parameterized)
   b. Each task performs CRUD operations (mix of insert, select, update)
   c. Measure p50, p95, p99 latencies
   d. Assert p99 under 100ms
4. Write unit tests for concurrent access and retry behavior
5. Remove hardcoded max-workers ceiling:
   a. Remove or replace the hard cap validation in batch.rs
   b. Ensure locked_register_with_limit receives config-driven value
   c. Benchmark with N > 3 to verify no hidden assumptions

### DEV Report

> Populated by cf-development before STAGE-COMPLETE: WS-DEV

**Implementation Summary:**

Two deliverables implemented:

1. **SurrealDB parallel access tuning**: Investigated surrealkv:// locking behavior. The `Surreal<Any>` client is internally `Arc`-based and thread-safe -- sharing a single `SurrealStore` instance across async tasks within one process works without contention. For inter-process access (autorun workers in separate tmux panes), each process opens its own `surrealkv://` connection with retry/backoff for exclusive lock contention. Added `RetryConfig` struct (100ms initial, 2x multiplier, 1s cap, 3 attempts), `with_retry_async()` for async retry with exponential backoff, `with_timeout()` for query timeouts, `QUERY_TIMEOUT` constant (5s), and `DbError::Contention` variant with `is_retryable()`/`is_schema_error()` classification methods.

2. **Remove hardcoded max-workers ceiling**: Removed the `validate_batch()` check that rejected `max_workers > DEFAULT_MAX_WORKERS`. `DEFAULT_MAX_WORKERS` (3) now serves only as the default value when `max_workers` is 0 or omitted -- it is no longer a cap. Updated 3 existing tests and added 2 new tests for large values (10, 20).

**Connection Strategy (AC2):** Shared-instance model. `SurrealStore` wraps `Surreal<Any>` which is `Arc`-based internally. Within a single process, one `SurrealStore` is created and cloned (`Clone` is cheap -- reference counting). For inter-process scenarios (autorun workers), each process opens its own connection with retry/backoff to handle the surrealkv:// exclusive directory lock. Rationale: connection pooling adds complexity without benefit since `Surreal<Any>` already handles internal connection management.
