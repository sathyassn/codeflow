## Description

Fix two related bugs in the worktree subsystem:

1. **Stale eviction safety**: Worktree stale cleanup could leave partial state if cleanup failed mid-way, leading to inconsistency between the registry and the filesystem.
2. **Config-driven limit enforcement**: The maximum concurrent worktrees limit was hardcoded (5) instead of being read from `parallel-work-config.json`, making it non-configurable without code changes.

## Approach

1. Review `codeflow-cli/core/src/worktree/` (cleanup.rs, registry.rs, setup.rs) for stale eviction logic
2. Fix cleanup to be idempotent and safe when partial failures occur
3. Load max_worktrees from `parallel-work-config.json` worktree section
4. Update tests to cover the fixed code paths

## Acceptance Criteria

1. Stale worktree eviction is safe and idempotent: if cleanup fails mid-way, re-running cleanup produces the same correct end state
2. Max concurrent worktree limit is read from `parallel-work-config.json` worktree.max_concurrent field (not hardcoded to 5)
3. Default limit of 5 applies when config is absent or field is missing
4. All existing worktree tests pass without regression
5. New tests cover: (a) partial cleanup idempotency, (b) config-driven limit loading, (c) default limit fallback
