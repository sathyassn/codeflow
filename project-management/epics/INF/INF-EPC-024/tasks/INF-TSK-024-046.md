## Description

Five-part fix for autorun reliability that must land in a single PR before INF-EPC-024 autorun batches can run reliably. PR rescue housekeeping steps (ACs 23-28) execute during the PF6-TSK-03 window via cf-git-operations after the code changes are committed.

**Part A — Network bypass:** `NetworkModule::check()` blocks git/gh network commands unless `ctx.sandbox_bypass` is set per-Bash-call. Autorun workers spawn with `--dangerously-skip-permissions` but that is separate from `ctx.sandbox_bypass`. Add 3-line `AUTORUN_SESSION_ID` bypass after the existing `sandbox_bypass` check — mirrors the pattern at `gh_pr_guard.rs:235`.

**Part B — PermissionRequest matcher expansion:** The `PermissionRequest` hook in `.claude/settings.json` currently matches only `Edit|Write`. Worktree paths (`.git-worktrees/worktree-XXX/.claude/agents/*.md`) fall outside the Claude Code `.claude/agents/**` exemption pattern. Expand the matcher to `Edit|Write|Bash|WebFetch` and bump `_version` to `1.1.1` across all 4 settings templates.

**Part C — Worktree reaper guard:** Two prior sessions (INF-TSK-024-040 at PF6, INF-TSK-024-045 at PF4-TSK-02) were killed mid-flight by the worktree cleanup mechanism. Add `is_session_alive()` with a 5-layer veto to all 3 cleanup call sites. Fail-safe-true: ambiguous evidence blocks cleanup, not permits it.

**Part D — Per-task / stage timeouts:** `TaskSpec.timeout_secs` already exists in `batch.rs`; no code change needed there. Populate it in both phase YAML files tuned by work_type. Add `autorun.stage_timeout_secs` to `parallel-work-config.json` and implement stage-transition monitoring in the orchestrator to abort hung workers with exit 125 and emit a `stage_timeout` event.

**Part E — UI parity:** `codeflow autorun status` and `codeflow interactive status` render session detail in divergent code paths. Extract a unified `SessionDetailPane` widget; extend `TaskView` with all fields needed for the autorun variant. Both views consume the same widget with no duplicated rendering code.

**PR rescue (PF6-TSK-03 window):** Merge #305, raise PR for 040, disposition 045 stale branch, clean stale interactive sessions, reset 045 DB anomaly.

#### WS-DEV-3 Partial Report — Part E (UI Parity Refactor)

**Implementation Summary:**

Unified the autorun and interactive session detail panes behind a single
`SessionDetail { autorun_extras: Option<AutorunExtras> }` widget. The autorun
detail pane previously hid PID, liveness, phase, work_type, task_id, status,
and duration — the exact fields an operator needs to debug the reaper. The
interactive pane had all of those but was a hand-rolled render path in
`interactive.rs`. Both paths now construct a `SessionDetail` and delegate
to `render_session_detail`, eliminating ~90 lines of duplication and
guaranteeing the two views stay in sync going forward.

Key design decisions:

1. **Kept `detail_pane.rs` as a thin adapter** rather than deleting it. The
   autorun call site passes a `TaskView`; the adapter's only job is to
   convert that into a `SessionDetail` with `AutorunExtras` populated and
   delegate to the unified widget. The adapter also normalizes
   `task_format_id` so the widget never double-renders the raw ULID when
   the formatted ID is absent.
2. **New `TaskView` fields (`pid`, `pid_alive`, `task_format_id`)** are
   resolved from `pathflow-session-status.json` under the worker's own
   worktree first, with a fallback to the main repo. Pending tasks (no
   worker session yet) return `(None, None)` so the UI renders a dash
   instead of a misleading `0 (DEAD)`.
3. **Dashes over fake values** — every optional field renders `--` when
   unknown rather than substituting a placeholder like `0` or `unknown`.
   This is how the interactive pane already treated the intermediate
   fields; the autorun pane now matches.

#### WS-DEV-1 Partial Report — Part C (Reaper Fix)

**Implementation Summary:**

Stopped live autorun worktrees from being physically reaped mid-run. The
race had three independent entry points (SessionEnd, session_start's
`clean_stale_worktrees`, autorun's `cleanup_stale_session`) that each
reached a `git worktree remove --force` or `mgr.cleanup` call after a
single status-file-based liveness check. None of the three entry points
defended against the case where the status file was stale (race window
between `pf-complete` write and the rest of teardown), missing entirely
(initializing session before pathflow-team.json is created), or the
caller was running INSIDE the session it was about to reap. Bug evidence:
session ses-01kq0fwt19xrmy7g3nsqkw41yj was reaped mid-PF4 with zero
commits despite an alive worker; the current session
ses-01kq0ha7gngv48v2v5sw0zhkw0 was flagged "cleaned" by interactive
cleanup today.

The fix is a single fail-safe-true predicate, `is_session_alive`, that
votes alive if ANY of five independent veto signals fires:

- **V1 grace window** — registry `created_at` within 5 minutes
- **V2 self-match** — caller's `CODEFLOW_WORKTREE_PATH` equals the target
  (canonicalized; never reap own worktree)
- **V3 tmux pane alive** — any tmux pane in a session whose name contains
  the 8-char ULID suffix is non-dead
- **V4 lead_pid** — `pathflow-team.json` lead_pid is alive (`kill(pid,0)`);
  **abstains alive** if the file is missing or malformed (init protection)
- **V5 interactive heartbeat** — `.state/interactive/heartbeat-{sid}` mtime
  within 10 minutes

The predicate is wired into all three entry points, plus `should_skip_cleanup`
in SessionEnd was reordered to run BEFORE `mark_pending_cleanup` so a
live session no longer queues its own worktree for removal by a later
session's `clean_stale_worktrees`.

Key design decisions:

1. **Fail-safe-true default.** A false positive (skip cleanup of a dead
   session) costs one cycle of leftover state; a false negative (reap a
   live session) destroys in-flight work. We cannot tolerate the latter,
   so V4 abstains alive on missing/malformed `pathflow-team.json` and V3
   votes false (not true) on tmux failure — i.e., tmux unavailability
   doesn't reap, but it doesn't keep the session alive either; other
   vetoes still apply.

2. **Predicate is pure and composable.** All five vetoes are split into
   private `veto_*` helpers that read the filesystem (or env, or tmux)
   exactly once. The aggregate `is_session_alive` short-circuits on the
   first true vote. Every helper is independently unit-tested.

3. **session_end.rs guard reorder.** The original code marked the
   worktree PendingCleanup BEFORE `should_skip_cleanup` "for crash
   recovery". That logic broke once `clean_stale_worktrees` started
   eagerly reaping PendingCleanup entries from other sessions. The fix
   moves the guard first; SessionEnd now only marks PendingCleanup when
   it has decided to proceed with its own cleanup. The reordering
   strictly improves crash recovery because (a) a real crash leaves the
   guard returning false-with-aggregate-dead, and (b) a spurious
   SessionEnd from a misrouted teammate stop now correctly defers.

4. **Tmux session matcher uses an 8-char suffix, not the full ULID.**
   Worker tmux sessions are named `cf-ar-task-{slug}-{suffix}`, lead
   sessions reuse the user's tmux. Matching the first 8 chars of the
   ULID portion of the session ID covers both naming conventions and
   tolerates session-name truncation seen in the wild.

#### WS-DEV-4 Partial Report — Part D (Timeouts)

**Implementation Summary:**

Adds stage-timeout enforcement to the autorun worker so a worker stuck on
a single PathFlow stage (e.g. cf-development hung mid-WS-DEV) is aborted
within `stage_timeout_secs` (default 3600s = 60 min) instead of waiting
out the full `worker_timeout_secs` window (default 7200s = 2h). Distinct
from worker-timeout: stage-timeout fires when there's no STAGE PROGRESS,
even if the wall-clock budget hasn't been exhausted.

The watcher polls `.state/sentinels/pathflow/{worker_session_id}/`
(local in worktree mode) every 30 seconds for the most recent `ws-*`
sentinel mtime. If `now - last_sentinel_mtime >= stage_timeout_secs`,
the watcher resolves and the parent `tokio::select!` arm wins over
`claude.invoke`. The worker synthesizes a result with `exit_code = 125`
(distinct from worker-timeout's exit 124), emits a `stage_timeout`
JSONL event to `.state/ledger/pathflow-events.jsonl`, and propagates
the failure through the existing classification path.

Until the first `ws-*` sentinel appears, the watcher uses the worker
start time as its baseline so a worker that hangs DURING setup (before
WS-DEV begins) still gets aborted on schedule.

Key design decisions:

1. **Pure decision function `stage_timeout_decision`.** The
   "is_stale_for >= timeout" comparison is split out as a pure
   synchronous fn so the seven boundary cases (within window, exact
   boundary, past window, no sentinel + baseline fresh, no sentinel
   + baseline expired, clock skew, exact-time skew) are unit-testable
   without async or filesystem fixtures. The polling loop wraps it.

2. **Polling, not inotify/fsevents.** The existing hook pipeline
   creates `.state/sentinels/...` lazily, so a notification-based
   watcher would need extra logic for the directory-doesn't-exist
   case. A 30s poll on a directory with at most ~10 entries is
   negligible vs the 1-hour timeout window.

3. **`tokio::select! { biased; }` ordering.** The watcher arm goes
   first so a stage-timeout that fires concurrently with claude.invoke
   completion is observed deterministically.

4. **Test isolation via `await_stage_timeout_with_interval`.** The
   public production wrapper uses the 30s constant; tests use 10ms
   so they don't need tokio's `test-util` mock-clock feature
   (which is gated and would require a Cargo.toml change).

5. **Worktree-aware sentinel lookup.** Sentinels are LOCAL state
   per-worktree (not symlinked). The `latest_ws_sentinel_mtime_secs`
   helper takes an explicit `worktree_path: Option<&Path>` so it can
   look in the correct location both in autorun (worktree exists)
   and in non-worktree contexts.

6. **Phase YAMLs deferred (AC-18 PARTIAL).** `inf-epc-024-phase1.yaml`
   and `inf-epc-024-phase2.yaml` do not exist on this branch (no git
   history). I cannot fabricate the task list for those batches —
   that is an architectural decision (which of the 46 tasks belongs
   in phase 1 vs phase 2). The orchestrator/worker code path for
   per-task `timeout_secs` (already in `TaskSpec`, consumed at
   `worker.rs:838`) is unchanged and ready; once the YAMLs are
   authored the per-task overrides will apply automatically.
   Alternatives considered: (a) create empty stub YAMLs with no
   tasks — meaningless and would still need a follow-up. (b) Pick
   tasks heuristically from the file list — too risky without
   ownership context. Decided to mark PARTIAL with explanation
   and let team-lead/WS-REV route the YAML authorship to the
   right owner.

#### WS-DEV-2 Partial Report — Parts A + B (Permission Prompts Fix)

**Implementation Summary:**

Stops autorun sessions from pausing on permission prompts. Autorun workers
have no human to answer a prompt, so any hook that emits a Block/Deny
decision visible to the user becomes a deadlock.

The fix introduces a single helper `crate::session::is_autorun_session()` that
checks the `AUTORUN_SESSION_ID` env var (set by `autorun/worker.rs` before
exec), and wires an early-return into every hook whose verdict could surface

1. **`NetworkModule::check()`** (`hooks/security/network.rs`) — before the
   existing `ctx.sandbox_bypass` short-circuit. Autorun workers spawn with
   `--dangerously-skip-permissions` and the orchestrator pre-bypasses the

#### WS-DEV-2 Rework — F1 Hardening (post WS-SEC review)

**Trigger:** WS-SEC F1 finding — `is_autorun_session()` was a single-env-var
trust boundary, forgeable by a local attacker exporting
`AUTORUN_SESSION_ID=ses-anything`. Zero-tolerance security policy required
defense-in-depth on this gate.

**Change:** `is_autorun_session()` now requires three conditions, all must
hold simultaneously:

1. `AUTORUN_SESSION_ID` env var is set AND non-blank.
2. `AUTORUN_BATCH_ID` env var is set AND non-blank (second var the
   orchestrator sets per `CLAUDE.md` "Environment variables" table).
3. `AUTORUN_SESSION_ID` value passes the existing
   `crate::session::is_valid_session_id` check (ULID format
   `ses-{26-char Crockford base32}` or legacy
   `ses-{13-digit timestamp}{12-char lowercase hex}`).

The body uses a `read_non_blank_env` helper that mirrors
`gh_pr_guard.rs:235-238` for consistency. Blank/whitespace values continue
to be treated as unset to prevent stale-env-var bypass.

**Rationale:** This raises the forgery bar from "guess one env var" to
"know two env var names AND produce a syntactically valid ULID." It is
not cryptographic — but it matches the orchestrator's existing invocation
pattern (both vars + valid ULID always set together) and closes the
documented F1 attack chain without adding new infrastructure (no shared
secret, no signing, no IPC). Re-uses the existing
`is_valid_session_id` validator instead of duplicating regex logic
(DRY); the validator is already well-tested in `session/mod.rs`.
