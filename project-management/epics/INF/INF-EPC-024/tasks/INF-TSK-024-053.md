## Description

Real-world test of an autorun batch (after PR #319 merge) revealed 4 independent autorun-reliability bugs. The worker session ses-01ks677d4d1yzq655f5qpth03x exited with `exit_code=125`, `DURATION=01:00:04`, `ERROR=<empty>` — the `stage_timeout` fired even though the worker was making progress. The TUI showed the failure as `status=failed` (not `timeout`), the claude subprocess leaked +10:49 after the worker_failed event, and a separate but related bug in stale.rs uses the wrong PID validator for the orchestrator. This task fixes all 4 in a single PR.

### DEV Report

> Populated by cf-development before STAGE-COMPLETE: WS-DEV

**Implementation Summary:**

Four-bug autorun reliability fix, delivered as a single PR. Each bug is independent and rooted in a different surface area, but all four trace back to the same production incident (ses-01ks677d4d1yzq655f5qpth03x exited at exit_code=125 with empty error, claude leaked +10:49, TUI showed `failed` instead of `timeout`, and a separate stale.rs PID validator bug was filed alongside).

Key design decisions:

1. **stage_timeout=7200 (AC-1):** Default constant bumped in code AND in `parallel-work-config.json`. The 60s lower-bound validation is unchanged so test stage_timeouts down to 60s still work.
2. **pf-3-done heartbeat (AC-2):** Reused the existing `pathflow-pf-3` sentinel instead of inventing a new heartbeat file. The watcher already polls `.state/sentinels/pathflow/{session_id}/`; extending the `is_stage_progress_sentinel` allow-list to include the PF3 sentinel is a one-line semantic change. Other phase sentinels (pf-1/2/4..7) are explicitly excluded — pf-1/2 fire on every session (would defeat the watcher), pf-4..7 fire after a ws-* sentinel has already reset the clock.
3. **exit_code=125 → timeout status (AC-3):** Extended `classify_invoke_outcome` with an `output: &str` parameter. The 125 branch sources its error message from `invoke_result.output` (which is the synthetic `stage_timeout: no ws-* sentinel in {n}s` message). Empty-output fallback ensures the error_msg is NEVER empty — a contract the TUI relies on.
4. **tmux kill on stage_timeout (AC-4):** Extracted `kill_tmux_on_stage_timeout(&tmux, name, log_path)` helper that wraps `kill_session` + escalation to `escalate_tmux_kill_to_sigkill`. This mirrors the post-invoke cleanup path's two-step pattern so failure semantics are consistent across normal-exit and timeout exits.
5. **stale.rs default_pid_validator (AC-5):** One-line swap from `validate_claude_pid` to `validate_orchestrator_pid`. Doc comments on the two public wrappers (`is_session_pid_alive` and the prior internal `default_pid_validator`) updated to reflect the corrected orchestrator-PID semantics. The `orchestrator.rs:189` write of `session.pid = std::process::id()` was the load-bearing fact — the bug was a documentation-vs-implementation drift where `is_session_pid_alive` documented "alive AND named claude" but its only producer wrote the codeflow PID, never a claude PID.

Lint-guard interaction: the `no_hardcoded_pathflow_names` integration test caught literal `"pathflow-pf-3"` strings in `is_stage_progress_sentinel`. Fixed by resolving the digit via `Phase::Pf3Classify.index()` — same approach used elsewhere in the codebase (`checkpoint.rs:441` uses `format!("pf-{i}")`).
