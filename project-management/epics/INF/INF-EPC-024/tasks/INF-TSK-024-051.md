# INF-TSK-024-051: Liveness-source consolidation (real fix for PR #310 regression)

## Description

PR #310 (INF-TSK-024-050) fixed the PID source bug where `interactive_session.pid` was populated from
the hook subprocess PID (`std::process::id()`) instead of the live Claude lead PID (`parent_id()`).
PR #310 also removed V5 `veto_heartbeat_fresh` from `is_session_alive`.

**However PR #310 introduced a regression by incomplete consolidation.** The fix only addressed
the SessionStart hook path for unmanaged sessions and removed V5 from `is_session_alive`. It left
three related gaps:

1. **`check_session_liveness` still has heartbeat as Signal 2** (`liveness.rs:84-90`): when PID is
   dead but a heartbeat file is fresh, the function returns `LivenessResult::Recent` instead of
   `Dead`. Since `session_start.rs:591` still writes the heartbeat file for unmanaged sessions,
   recently-ended sessions appear as alive/Recent to cleanup — exactly the "stale-but-not-reaped"
   symptom that motivated the PR.

2. **The interactive TUI reads `interactive_session.pid` from the DB** rather than from
   `pathflow-session-status.json::lead_pid`. The DB column may hold a stale value (PID 4954 =
   tmux-attach client process, not the live Claude PID 5303). The canonical PID lives in
   `pathflow-session-status.json::lead_pid` which the TUI does not consult.

3. **No single chokepoint function**: `is_session_alive` (V1-V4, for worktree reaper),
   `check_session_liveness` (general-purpose signal combiner), `is_session_pid_alive*` (autorun),
   and `default_session_pid_validator` (TUI) are four separate code paths that make independent
   liveness decisions. Any future fix to one will not propagate to the others.

This task introduces a single canonical `liveness::is_session_alive(project_dir, session_id)`
function that reads from `pathflow-session-status.json::lead_pid` (with worktree-path resolution via
`worktrees.yaml`), migrates all 8 `check_session_liveness` call sites and both TUI readers to it,
and removes the heartbeat signal and writer entirely.

**Implementation Summary (Phase 1):**

Added a single canonical liveness chokepoint and consolidated V4 of the
fail-safe-true cleanup predicate onto it.

- **`SessionLiveness` enum** (`Active` / `Dead` / `Unknown`) — three values
  cover the cases callers act on. `Unknown` is NOT alive (does not match
  the previous `LivenessResult::Recent` semantics) so callers stay
  fail-closed by default. Callers that want fail-safe-true (don't reap
  initializing sessions) use `is_session_alive_for_cleanup` instead.
- **`is_session_alive(project_dir, sid) -> SessionLiveness`** — reads the
  worktree-resolved `pathflow-session-status.json::lead_pid` and validates
  via `validate_claude_pid` (alive AND named "claude"). This is the only
  function the TUI / sync / worktree-status callers should reach for.
- **`resolve_session_state_dir(project_dir, sid) -> PathBuf`** — consults
  `worktrees.yaml`; if an entry's `session_id` matches, returns the
  worktree-rooted path; otherwise falls back to `project_dir`. Includes a
  path-traversal guard.
- **`read_canonical_lead_pid`** — companion that returns the raw PID
  without performing the alive check. Useful for TUI surfaces that need
  to display the PID number separately from the liveness verdict.
- **Renamed V1-V4 predicate** `is_session_alive(&SessionAliveInputs) ->
  bool` → `is_session_alive_for_cleanup(&SessionAliveInputs) -> bool`.
  Preserves V1 (grace window) + V2 (CODEFLOW_WORKTREE_PATH self-match) +
  V3 (tmux pane alive). V4 internally delegates to the new chokepoint
  (`Active|Unknown` → vote alive, `Dead` → vote dead). This fixes the
  latent bug at session_start.rs:1003 where the cleanup path searched
  for the status file in the main repo only — V4 now gets worktree
  resolution for free.
- **5 callers renamed**: autorun/stale.rs (1), hooks/session_end.rs (1),
  hooks/session_start.rs (2), liveness.rs internal aggregate.

Phase 2-7 (TUI migration, 8 call-site migration, lead_pid removal,
heartbeat removal, lint guards, e2e test) follow in subsequent commits.

**Unhandled paths identified and fixed (Phase 1):** 1 — `session_start.rs:1003` previously read the status file from `project_dir` only; for worktree sessions the file lives in the worktree, so V4 always saw `Unknown` and the cleanup path fell through to a separate `is_live_worktree_session` helper. #### Phase 2.5 — XDG_LOCK consolidation (test-infra cleanup)

**Implementation Summary (Phase 2.5):**

Phase 1 surfaced a long-standing parallel-test race: `worktree::cleanup`
and `autorun::rescue` each defined their OWN `Mutex<()>` to serialise
tests that mutate `HOME`/`XDG_CACHE_HOME`. The two locks raced against
each other under `cargo test --lib` (default parallel mode), causing 12
intermittent test failures across the two modules. Single-threaded runs
and isolated runs always passed — symptomatic of cross-module env-var
races, not a production bug.

- New `codeflow-cli/core/src/test_util.rs` (`#[cfg(test)]`-gated) exposes
  a single shared `xdg_env_lock()` returning a poison-tolerant
  `MutexGuard<'static, ()>`. Defined once in `core::test_util`, imported
  by every caller in the crate so all XDG-mutating tests serialise
  through ONE mutex.
- `worktree::cleanup::tests::xdg_lock` and
  `autorun::rescue::tests::env_lock` migrated to delegate to the shared
  lock. Module-local `static *_LOCK: Mutex<()>` definitions removed.
- Module doc explains the convention and points at the existing
  `serial_test::serial(env_vars)` key as a parallel safety net for tests
  that mutate other process-global env vars (CODEFLOW_*).

#### Phase 4-C — DB `pid` column drop on `interactive_session`

**Implementation Summary (Phase 4-C):**

The DB column `interactive_session.pid` was the last duplicate of the
canonical PID source (`pathflow-session-status.json::lead_pid`). It was
written pre-`exec` by the codeflow CLI wrapper and so always recorded the
wrapper PID, never the live Claude lead. With the chokepoint migration
finished (Phases 1-3) and the wrapper-context writes removed (Phase 4-B),
the column is dead weight. This phase removes it from the schema, the
serde model, the runtime CREATE statements, and runs a one-shot UNSET
migration to scrub the column from any pre-existing rows on next startup.

**Surfaces removed:**

- **Schema (`store/schema.surql`)** — the
  `DEFINE FIELD OVERWRITE pid ON TABLE interactive_session TYPE int;`
  line is gone. Replaced with a comment block referencing this task and
  pointing the reader at the chokepoint.
- **Model (`models/interactive_session.rs`)** — `pub pid: i64` field
  removed from the `InteractiveSession` struct. Comment in place
  explaining the canonical replacement and the migration strategy. With
  `serde(default)` on every other field, legacy rows that still have a
  `pid` column on disk deserialise without error (serde silently ignores
  unknown fields when reading).
- **Wrapper CREATE (`cli/cmd/interactive.rs::run_launch`)** — the
  `pid = $pid,` clause and the `.bind(("pid", ...))` call are gone from
  the `interactive_session` CREATE.
- **SessionStart unmanaged CREATE (`hooks/session_start.rs`)** — the
  `pid = $pid,` clause removed from the unmanaged-session
  `INSERT INTO interactive_session` and the
  `let pid = i64::from(validate_claude_pid(parent_id()))` binding deleted
  alongside.
- **TUI displayed_pid (`tui/data.rs::SessionView`)** — the helper
  `displayed_pid` no longer takes a `db_pid` argument; it returns
  `read_canonical_lead_pid(project_dir, sid)` directly. The DB-fallback
  branch is gone.
- **`resolve_displayed_pid` (`cli/cmd/interactive.rs`)** — collapsed for
  the same reason: only the canonical reader remains.

**Migration (`store/schema.rs`):**

Added `MIGRATION_DROP_INTERACTIVE_SESSION_PID = "UPDATE interactive_session UNSET pid;"`.
SCHEMAFULL `OVERWRITE` does NOT auto-strip columns when a `DEFINE FIELD`
disappears — existing rows keep the (now-undefined) column until
explicitly unset. The migration is idempotent (UNSET on a missing field
is a no-op) and runs on every `apply_schema` call alongside the existing
`session_kind` back-fill.

**Regression-prevention test:**

Added `schema_does_not_define_interactive_session_pid` to the schema
test suite. Asserts the SQL does NOT contain
`ON TABLE interactive_session TYPE int`, with a comment pointing at this
task and the canonical chokepoint. Also tightened the existing
`schema_contains_autorun_new_fields` assertion for the autorun_session
`pid` field to disambiguate: it now matches
`DEFINE FIELD OVERWRITE pid ... ON TABLE autorun_session` exactly so a
hypothetical re-introduction of `interactive_session.pid` cannot satisfy
the (previously substring-only) check.

#### Phase 7 — AC #13 e2e canary integration test (the merge gate)

**Implementation Summary (Phase 7):**

Added `tui::data::tests::ac13_e2e_live_session_shows_active_via_worktree_resolution`
— the canary that catches PR #310-class regressions where unit tests
pass while the user-visible TUI flow shows "live session as
Stale/DEAD". Wired automatically into `codeflow test --mode full` via
the `rust-core` target (`cargo nextest run --profile full` picks up
every workspace `#[test]` / `#[tokio::test]`). No additional CLI
plumbing required — the project's testing config already routes the
codeflow-cli workspace through the unified runner.

**What the test exercises (the FULL chain):**

1. Register a worktree in `{project_root}/.state/worktrees/worktrees.yaml`
   with `session_id == sid` and `path == worktree_root`.
2. Write `pathflow-session-status.json` INSIDE the worktree (at
   `{worktree_root}/.state/session/{sid}/pathflow/`), with `lead_pid`
   = canonical Claude lead PID. This is the critical detail PR #310
   missed: the file lives in the worktree, not the main repo.
3. Insert an `interactive_session` row in the in-memory SurrealDB
   matching the worktree, with `worktree_path` set so the TUI fetcher
   can correlate.
4. Call `fetch_session_views(&store, project_root)` — the EXACT
   production entry-point used by the `codeflow interactive status`
   TUI. No synthetic oracle — the chokepoint resolves the worktree
   from `worktrees.yaml`, reads the status file from the worktree,
   validates via `default_session_liveness_oracle` →
   `is_session_alive` → `validate_claude_pid`.
5. The test installs `override_pid_validator_for_tests(|_| true)` so
   the test runner's PID stands in for a live `claude` process
   (runners are `cargo`, not `claude`); EVERY OTHER step is the real
   production code path.

**Assertions (the canary's invariants):**

- `summary.active == 1` — the row is counted as alive.
- `summary.stale == 0` — NOT promoted to stale (PR #310 had this == 1).
- `view.status == "active"` — user-visible status string is the
  correct one (PR #310 had this == "stale").
- `view.pid == canonical_pid` — displayed PID is the canonical lead
  from the worktree-resolved status file (PR #310 had this == 4954,
  the tmux-attach client PID, instead of 5303 the canonical lead).

**How the test catches regressions (proof by construction):**

- If `resolve_session_state_dir` ever forgets `worktrees.yaml` (the
  PR #310 root cause), the chokepoint will look at
  `project_root/.state/session/{sid}/pathflow/pathflow-session-status.json`
  — which DOES NOT EXIST in this fixture. The chokepoint returns
  `Unknown`, the TUI demotes to "stale" (or refuses to promote),
  and ALL FOUR assertions fail.
- If `displayed_pid` ever falls back to the deleted DB column (the
  Phase 4-C semantic regression), the assertion `view.pid ==
