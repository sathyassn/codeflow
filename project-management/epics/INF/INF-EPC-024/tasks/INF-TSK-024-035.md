## Description

The pathflow-events.jsonl file currently resides at `.state/logs/pathflow-events.jsonl` (legacy location), while the ledger routing system (`routing.rs`) already routes pathflow event types to `files::PATHFLOW_EVENTS` which resolves to the `.state/ledger/pathflow-events/` subdirectory. This creates an inconsistency: new events route to the ledger directory, but the historical 170KB file remains in the logs directory.

This task adds a one-time, idempotent migration in `session_start.rs` to move the file from the old location to the new, following the same pattern used by `migrate_flat_to_subdirs()` in PR #221.

### DEV Report

> Populated by cf-development before STAGE-COMPLETE: WS-DEV

**Implementation Summary:**

Added a one-time, idempotent auto-migration that moves `pathflow-events.jsonl` from the legacy `.state/logs/` location to its canonical `.state/ledger/pathflow-events/` subdirectory (matching the subdir layout established in PR #221). The migration is wired into SessionStart so it runs transparently the first time a user launches a session on the new binary; subsequent sessions fast-path skip.

Key design decisions:

1. **Freestanding helper, not a method on `SessionStartInit`.** The migration has no dependency on session state (pid, home_dir, `now` fn) — only on the `.state/` path. Module-level `fn migrate_pathflow_events_from_logs(state_dir: &Path)` mirrors the shape of `crate::ledger::migrate::migrate_flat_to_subdirs` and keeps the caller sites compact. Alternatives considered: (a) add to `ledger/migrate.rs` — rejected because task scope restricts `ledger/` to read-only; (b) combine with `migrate_flat_to_subdirs` — rejected because the source directory differs (`.state/logs/` vs `.state/ledger/`) and the mapping is 1:1 for this one file, not type-driven.
2. **Move semantics with re-run preservation.** Happy path uses `fs::rename` (atomic on same filesystem) with a `fs::copy` + `fs::remove_file` fallback for cross-device edge cases. If the destination already exists on re-run (partial earlier migration, manual file creation, or double-invocation), the destination is NEVER overwritten — instead the stale source is removed so subsequent runs hit the fast-path skip. This makes the operation safe against concurrent writes to the destination by the ledger writer.
3. **Errors never block session start.** Every filesystem operation is a best-effort write; errors are logged to stderr and swallowed, matching the `migrate_flat_to_subdirs` invocation pattern already present in `create_directories`. PathFlow degrades gracefully: a failed migration just means the file stays in `.state/logs/` and tries again next session.
4. **Lock file cleanup is unconditional.** The `.state/logs/pathflow-events.jsonl.lock` is removed in every branch (happy-path move, re-run skip, orphan-lock cleanup when source is already gone). Older deployments where the data was migrated manually but the lock persisted are healed on first post-update session.
5. **Invoked in BOTH dispatch paths.** Called from `create_directories()` (non-worktree sessions) AND `create_directories_in_worktree()` (worktree sessions). In worktree mode, `.state/logs/` is symlinked to the main repo (shared), `.state/ledger/` is local — the first session (whether worktree or main) migrates the shared file to its own local ledger; subsequent sessions see no source and skip.
6. **No routing changes.** `routing.rs:57` already routes every pathflow event type (`phase_transition`, `stage_transition`, `session_register`, `session_metadata`, `pathflow_task_update`) to `files::PATHFLOW_EVENTS` (= "pathflow-events" subdir). Verified during exploration.

**Silent failure check:** No path returns "success" with wrong behavior. Every mutation path either completes fully (rename, or copy+remove, or destination preservation) or logs a specific stderr warn and returns without partial state corruption. The `let _ = fs::remove_file(lock)` swallows errors intentionally (best-effort orphan cleanup) — documented as such and cannot mask a real failure since the lock file is advisory only.

**Resource cleanup verification:** Every exit path leaves the filesystem in a recoverable state:
- Happy path: src→dst atomic rename (no intermediate state) OR copy-then-remove (dst populated before src removed; if crash between copy and remove, next run hits dst-exists branch and removes src).
- Re-run edge: dst never touched; src removed or error-logged.
- Error: src preserved, dst_dir may be created (harmless — empty dir).
- Orphan lock: best-effort remove, no state coupled to the lock.
No open file descriptors (all ops complete synchronously). No memory allocations that need Drop — all `PathBuf`s are stack-lived inside the function.

**Error path security:** All error paths maintain security controls. No error path causes a security regression: every failure leaves `src` and `dst` in a mutually consistent state (either src-only, dst-only, or both present as a recoverable re-run scenario). No partial state can corrupt session startup.

**TOCTOU check:** Structural TOCTOU exists between `dst.exists()` (line 2107) and `fs::rename(src, dst)` (line 2129). Analyzed for exploitability:
- Two concurrent sessions share the same `src` (shared symlinked `.state/logs/`) but have DIFFERENT `dst` paths (per-worktree ledger directories). No dst collision is possible between sessions.
- If two non-worktree plain-`claude` sessions race (same src AND same dst): first rename succeeds (removing src); second rename on now-absent src fails with ENOENT → falls to `copy(src)` → also fails (src gone) → logs warning → returns. First session's dst is untouched. No overwrite.
- POSIX `rename(2)` is not used as a security mechanism here — it is used for atomic move semantics on the happy path. The check-then-act pattern's TOCTOU cannot be leveraged to overwrite the destination by an attacker, because the rename on a missing src fails rather than overwriting an existing dst.
- **Verdict: TOCTOU exists structurally but is not exploitable. No data corruption or privilege escalation possible via the race.**

**Defense-in-depth:** Migration failure degrades gracefully — session start is never blocked. Destination preservation relies on two independent layers: (1) the `dst.exists()` check guards normal re-runs; (2) POSIX rename semantics on missing src return ENOENT for the concurrent case. Both layers must fail simultaneously to lose destination data, which requires `dst` to be deleted between the `dst.exists()` check returning false and the rename completing — not a plausible attack scenario in the `.state/` directory model.
