# INF-TSK-024-019: Document DB-to-JSONL rebuild mapping per table

## Description

Create a comprehensive mapping document that captures the DB-to-JSONL rebuild relationship for every table in the database. The three-tier data model requires that Tier 1 (SurrealDB via surrealkv:// embedded mode, per Decision D17) can be fully rebuilt from Tier 0 (JSONL). Currently, no formal mapping document exists, and the analysis in schema-standardization.md Section 8 reveals significant coverage gaps -- the `tasks` table is only 28% rebuildable, and two tables (`security_logs`, `network_logs`) have completely dead JSONL writers.

This document serves as the authoritative reference for: (1) understanding current rebuild capability, (2) prioritizing gap-filling work, (3) implementing the rebuild validation tooling in INF-TSK-024-020, and (4) guiding the SurrealDB schema design in INF-TSK-024-022.

The mapping uses Rust module paths (`codeflow-rs/codeflow-core/src/`) for the post-Epic 0 codebase where writers, normalizers, and schema validators reside.

## Approach

1. Read schema-standardization.md Section 8 (DB-to-JSONL Rebuild Mapping) for the complete field-by-field analysis
2. Read Rust ledger module structure at `codeflow-rs/codeflow-core/src/ledger/` for writer locations
3. Read Rust store module at `codeflow-rs/codeflow-core/src/store/` for DB sync/rebuild logic
4. Organize tables into 5 categories: (a) rebuildable from JSONL, (b) reference data, (c) derived data, (d) runtime-only, (e) gap tables
5. For each rebuildable table, document field-by-field mapping with JSONL source event, coverage status, and Rust module responsible
6. Classify all missing fields by priority (P0-P4)
7. Document rebuild strategies for non-JSONL tables
8. Reference SurrealDB migration context (Decision D17)
9. Write the mapping document
