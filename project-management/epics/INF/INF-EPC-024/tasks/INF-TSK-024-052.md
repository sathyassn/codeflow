# INF-TSK-024-052: Rescue test flake — investigate and stabilize

## Description

PR #311 (INF-TSK-024-051, merged 2026-05-03) consolidated liveness
detection into a single chokepoint and modified the rescue subsystem's
sentinel-write paths. A flaky rescue test was observed during the
PR's QA cycle but was not blocking — it passed on retry and was
filed as follow-up rather than gating the merge.

This task is two-phase:

- **Phase 1 — Investigation:** identify which test(s) flake, with
  what failure modes, and at what frequency. Determine the root
  cause from the categorical taxonomy below.
- **Phase 2 — Stabilization:** apply a deterministic fix for the
  identified root cause; prove stability with 100 consecutive
  passes; no test deletions or `#[ignore]` markers.

Phase 1's investigation OUTPUT becomes Phase 2's INPUT. The fix
plan, file_scope, and tests array in this task doc are deliberately
empty / vague until Phase 1 completes; this is correct for a
two-phase ticket and the autorun runner is expected to pause for the
operator after Phase 1 to confirm the diagnosis before Phase 2 ships.

This task lives under INF-EPC-024 (autorun reliability) and NOT
under INF-EPC-050 — the flake was surfaced by PR #311 which is part
of the EPC-024 lifecycle. Do NOT move it.

## Approach

### Phase 1: Investigate

1. **Run the rescue test target 10 times locally** with verbose
   output:
   ```bash
   for i in $(seq 1 10); do
     codeflow test --mode full --only <rescue-target> 2>&1 \
       | tee /tmp/rescue-flake-run-$i.log
   done
   ```
   Identify which run(s) failed; capture test name, panic message,
   stack trace.
2. **Categorize the failure** using the taxonomy below; record the
   evidence in `## Phase 1: Investigation`. If 10/10 runs are
   clean, escalate: the flake may have already self-healed via
   another PR; the operator decides whether to keep the ticket or
   close as cancelled.
3. **Identify the precise root cause** — file:line evidence, not
   "looks like a race".

### Phase 2: Stabilize

1. Apply the deterministic fix matching the root-cause category.
2. Run `codeflow test --mode full --only <rescue-target>` 100 times.
   If any run fails, return to Phase 1 step 3 (the diagnosis was
   wrong).
3. Run `codeflow test --mode full` end-to-end at least 2 times
   to confirm no regression elsewhere.
4. Update this task doc's QA Report with the 100-run output.

### Root Cause Categorization Taxonomy

| Category | Symptom | Common fix |
|----------|---------|-----------|
| (a) Timing race (sleep / interval) | Test passes individually, fails under load. Failure timing varies. | Fake clock (`tokio::time::pause` + `advance`); explicit barrier; remove sleep dependency |
| (b) Test ordering / shared state | Test passes alone, fails when run with others; failure correlates with test name (e.g. always the second one) | Per-test temp dir; `serial_test::serial`; reset shared singletons between tests |
| (c) FS race (atomic write + read) | Failure on `read returned None` or "file not found" on the very file just written | `sync_all` before read; explicit `tempfile::tempdir()` with `keep()`; avoid network-FS test paths |
| (d) External process timing (gh / git) | Failure references `gh` or `git` exit codes / stderr; intermittent on CI but rare locally | Mock subprocess; replace `Command::new("gh")` with injected trait; use git2 for plumbing |
| (e) Other | Doesn't match above | Document specifically before applying fix |

## Notes

This is an EPC-024 task, not EPC-050. The flake was surfaced during
PR #311 (INF-TSK-024-051) which is part of EPC-024's lifecycle. The
task lives at
`project-management/epics/INF/INF-EPC-024/tasks/INF-TSK-024-052.md`
and the EPC-024 epic markdown SHOULD list this task in its task
table — verify the EPC-024 epic and update if missing (out of scope
for this task; flag in DEV Report if needed).

The two-phase structure is intentional: a flake fix that ships
without a documented root cause is a regression-in-disguise. Phase 1
ensures the root cause is identified BEFORE Phase 2 attempts a fix.
If the autorun runner picks this task and Phase 1 yields 10/10
clean, the worker SHOULD escalate to the operator (mark task
cancelled with explanation in the DEV Report) rather than fabricating
a fix for a non-reproducible flake.

`scope_policy=soft` (not `hard`) because Phase 1 may surface a flake
in an unexpected file outside the original guess; the file_scope is
intentionally empty and the soft policy lets the implementer
acquire claims dynamically.

**`autorun_eligible: false`** because Phase 1's investigation needs
human judgment to categorize the root cause (taxonomy a-e) before
Phase 2 can apply a fix. An autorun worker that fabricates a
diagnosis without operator confirmation is a regression-in-disguise.
Operator runs this task interactively (or via `/cf-develop`), files
follow-up tickets if the investigation reveals separate issues, and
manually flips `autorun_eligible: true` for any future Phase 2-only
re-run that comes with a known root cause + file_scope. The
validator correctly rejects empty `file_scope` + autorun-eligible
because that combination would let the worker edit anywhere in the
repo with no claim discipline; the explicit `false` here is the
right answer.
