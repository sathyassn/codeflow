# INF-TSK-024-038: Fix template-to-DB alignment gaps in epic/task validation

> **MANDATORY VALIDATION:** Files created from this template MUST be validated before committing:
> `codeflow validate task <file-path>`
> Fix all errors (exit code 1) before requesting a commit. Warnings are advisory.

## Description

During review of the task template (`project-management/templates/task-template.md`) against the DB schema (`schema.surql`), Task struct (`models/task.rs`), and validation logic (`validate/mod.rs`), three alignment gaps were identified:

1. **`auto_commit` missing from `TASK_BOOLEAN_FIELDS`:** The `auto_commit` field exists in both the DB schema (line 78: `DEFINE FIELD OVERWRITE auto_commit ON TABLE task TYPE bool`) and the Task struct (line 32: `pub auto_commit: bool`), but is NOT included in `TASK_BOOLEAN_FIELDS` at `validate/mod.rs:418`. This means task markdown with `auto_commit: "yes"` or other non-boolean values would pass validation silently.

2. **`dependencies` field in template but not in DB:** The task template includes `dependencies: []` (line 31), but the Task struct has no `dependencies` field. The DB schema uses a `depends_on` graph relation (line 244) rather than an inline field. The template should clarify that `dependencies` is a markdown-only convenience field for human readability, not persisted to the DB, OR the field should be added to the Task struct for round-trip fidelity.

3. **`epic_format_id` field in template but not in DB:** The task template includes `epic_format_id` (line 5), but the Task struct only has `epic_id` (the ULID FK). The `epic_format_id` is useful for human readability (cross-referencing the epic by its readable ID). Either add it to the Task struct + DB, or document it as markdown-only in the template.

## Approach

1. **Add `auto_commit` to `TASK_BOOLEAN_FIELDS`** in `validate/mod.rs:418`:
   - Current: `const TASK_BOOLEAN_FIELDS: &[&str] = &["autorun_eligible", "raise_pr", "auto_merge"];`
   - After: `const TASK_BOOLEAN_FIELDS: &[&str] = &["autorun_eligible", "raise_pr", "auto_merge", "auto_commit"];`
   - Add test: task markdown with `auto_commit: "yes"` should produce a validation error

2. **Decide and implement `dependencies` field resolution:**
   - **Recommended approach:** Keep `dependencies` as markdown-only. The DB already has the `depends_on` graph relation for structured dependency tracking. The markdown `dependencies` field serves as a human-readable reference in the task file. Add a comment in the template clarifying this, and add validation to `validate/mod.rs` that accepts `dependencies` as an optional array field (no DB persistence check).
   - **Alternative:** Add `dependencies: Vec<String>` to the Task struct and `DEFINE FIELD OVERWRITE dependencies ON TABLE task TYPE array` to the schema. This creates DB round-trip fidelity but duplicates the graph relation.

3. **Decide and implement `epic_format_id` field resolution:**
   - **Recommended approach:** Keep `epic_format_id` as markdown-only. It's a convenience cross-reference that can be derived from `epic_id` via a DB lookup. Add a comment in the template clarifying this.
   - **Alternative:** Add `epic_format_id: Option<String>` to the Task struct and add it to the DB schema. This provides denormalized access but requires keeping it in sync with the epic table.

4. **Add test cases** for each validation change in the `#[cfg(test)]` module of `validate/mod.rs`.

## Notes

- **Gap discovery context:** These gaps were found during template review as part of INF-EPC-024 Data Layer Standardization work.
- **`auto_commit` is the simplest fix:** It's a one-line change to `TASK_BOOLEAN_FIELDS` plus test cases. The field already exists in both the DB schema and the Task struct.
- **`dependencies` recommendation:** Keep as markdown-only. The DB already has `depends_on` graph relations (schema.surql line 244) which provide structured dependency tracking with `relates_to(task_a, task_b)`. The markdown `dependencies` field is a convenience for humans reading the task file. Adding it to the Task struct would create redundancy with the graph relation.
- **`epic_format_id` recommendation:** Keep as markdown-only. It can always be derived by joining `task.epic_id` to `epic.format_id`. Adding it to the Task struct would create a denormalized field that could drift out of sync with the epic table.
- **Autorun-eligible:** This task has `scope_policy: hard` because it modifies validation logic and DB schema -- files that multiple parallel workers should not touch concurrently.
- **Standard requirements:** `cargo clippy --all-targets --all-features -- -D warnings`, `cargo fmt --check`, coverage >= 85% per file.
