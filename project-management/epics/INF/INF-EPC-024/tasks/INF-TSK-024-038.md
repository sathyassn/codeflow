# INF-TSK-024-038: Fix template-to-DB alignment gaps in epic/task validation

> **MANDATORY VALIDATION:** Files created from this template MUST be validated against the task validation command before committing:
> `codeflow validate task <file-path>`
> Fix all errors (exit code 1) before requesting a commit. Warnings are advisory.

## Description

During review of the task template (`project-management/templates/task-template.md`) against the DB schema (`schema.surql`), Task struct (`models/task.rs`), and validation logic (`validate/mod.rs`), three alignment gaps were identified:

1. **`auto_commit` missing from `TASK_BOOLEAN_FIELDS`:** The `auto_commit` field exists in both the DB schema (line 78: `DEFINE FIELD OVERWRITE auto_commit ON TABLE task TYPE bool`) and the Task struct (line 32: `pub auto_commit: bool`), but is NOT included in `TASK_BOOLEAN_FIELDS` at `validate/mod.rs:418`. This means task markdown with `auto_commit: "yes"` or other non-boolean values would pass validation silently.

2. **`dependencies` field in template but not in DB:** The task template includes `dependencies: []` (line 31), but the Task struct has no `dependencies` field. The DB schema uses a `depends_on` graph relation (line 244) rather than an inline field. The template should clarify that `dependencies` is a markdown-only convenience field for human readability, not persisted to the DB, OR the field should be added to the Task struct for round-trip fidelity.

3. **`epic_format_id` field in template but not in DB:** The task template includes `epic_format_id` (line 5), but the Task struct only has `epic_id` (the ULID FK). The `epic_format_id` is useful for human readability (cross-referencing the epic by its readable ID). Either add it to the Task struct + DB, or document it as markdown-only in the template.

### DEV Report

> Populated by cf-development before STAGE-COMPLETE: WS-DEV

**Implementation Summary:**

Closed three template-to-DB alignment gaps in the task markdown validator:

1. **`auto_commit` boolean validation (AC #1):** Added `auto_commit` to
   `TASK_BOOLEAN_FIELDS` in `validate/mod.rs:437`. The existing
   `validate_boolean_fields()` helper now enforces that `auto_commit`
   must be `true`/`false` (or the quoted-string equivalents), matching
   the DB schema (`DEFINE FIELD OVERWRITE auto_commit ON TABLE task
   TYPE bool`) and the `Task` struct (`pub auto_commit: bool`). String
   values like `"yes"` or numbers now produce a descriptive
   `ValidationError`.

2. **`dependencies` field — markdown-only (AC #2):** The DB already
   provides the `depends_on` graph relation (schema.surql:287) for
   structured dependency tracking, so `dependencies` is NOT added to
   the `Task` struct or schema. Instead, I added a new
   `TASK_MARKDOWN_ARRAY_FIELDS` constant and a `validate_array_fields()`
   helper that accepts `None`/`Null`/`Sequence(_)` and rejects other
   types with `"must be an array, got ..."`. Template comment at
   `task-template.md:31` explains the convention: human-readable
   reference only; DB graph relation is authoritative.

3. **`epic_format_id` field — markdown-only (AC #3):** Convenience
   cross-reference derivable from `epic_id` via DB lookup. No
   persistence change; template comment at `task-template.md:5`
   clarifies it is markdown-only for readability.

**Design decisions (Tier 2 — documented):**

- Chose the recommended markdown-only approach for both
  `dependencies` and `epic_format_id` per task pre-decided approach.
  Duplicating `depends_on` in the task row would create sync-drift
  risk (two sources of truth for the same semantic relation).
  `epic_format_id` denormalization would require cascade updates
  when an epic is renamed.
- Introduced `validate_array_fields()` as a generic helper (parallel
  to `validate_boolean_fields()`) so future markdown-only array
  fields can be added by extending `TASK_MARKDOWN_ARRAY_FIELDS`
  without duplicating the type-check logic (DRY).
- Preserved tolerance for YAML `Null` on markdown-only array fields
  to match existing validator permissiveness for optional fields.
