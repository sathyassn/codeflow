# INF-TSK-025-009: Cross-Project Visibility and Graph Relations

## Description

Implement the visibility enforcement layer that controls which projects can see each other's data in the global daemon. This uses SurrealDB's graph relation system: `can_access` is a typed relation table (`TYPE RELATION IN project OUT project`) that carries scopes (which data types are visible) and a grant timestamp.

Every cross-project query in the daemon MUST pass through the `scope_filter()` helper, which generates a SurrealQL WHERE clause restricting results to records from projects that the requesting project has `can_access` relations to. This is a security-critical module -- bypassing visibility is equivalent to unauthorized data access.

The visibility model follows Decision #20 (Cross-Project Visibility Model): per-project opt-in, explicit linking, scope-constrained access.

## Approach

1. Define `VisibilityScope` enum:
   - Variants: `Tasks`, `Sessions`, `Epics`, `Events`, `Memory`, `Entities`, `All`
   - Implements serde Serialize/Deserialize
   - `All` expands to all other variants (convenience)
2. Implement `VisibilityManager` struct:
   - Holds `Arc<Surreal<Client>>` reference to global DB
   - `grant(from: &ProjectId, to: &ProjectId, scopes: Vec<VisibilityScope>) -> Result<(), GraphError>`:
     - Execute `RELATE project:{from}->can_access->project:{to} SET scopes = $scopes, granted_at = time::now()`
     - By default, also create reverse relation (bidirectional) unless one_way flag
   - `revoke(from: &ProjectId, to: &ProjectId) -> Result<(), GraphError>`:
     - Execute `DELETE can_access WHERE in = project:{from} AND out = project:{to}`
   - `visible_projects(project_id: &ProjectId) -> Result<Vec<ProjectId>, GraphError>`:
     - Execute `SELECT ->can_access->project.project_id FROM project:{id}`
     - Returns list of accessible project_ids
   - `is_visible(from: &ProjectId, to: &ProjectId, scope: VisibilityScope) -> Result<bool, GraphError>`:
     - Check if can_access edge exists with matching scope
3. Implement `scope_filter()` helper:
   - Input: requesting `project_id`, target `scope` (which table is being queried)
   - Output: SurrealQL clause: `WHERE project IN (SELECT ->can_access->project FROM project:{id} WHERE scopes CONTAINS $scope) OR project = project:{id}`
   - The `OR project = project:{id}` ensures a project always sees its own data
4. Implement bidirectional linking:
   - Default: `grant(A, B, scopes)` creates edges in BOTH directions (A->B and B->A)
   - Optional `--one-way` flag creates only A->B
   - `revoke(A, B)` removes A->B only (not B->A) -- explicit per-direction
5. Write tests:
   - Grant visibility, verify visible_projects returns correct set
   - Scope filtering: grant Tasks scope, verify Memory queries are blocked
   - Bidirectional: link A<->B, verify both directions work
   - Revoke: remove one direction, verify other still works
   - Self-visibility: project always sees its own data without explicit grant

## Acceptance Criteria

1. `can_access` graph relation created via SurrealDB `RELATE project:a->can_access->project:b` with `scopes` array and `granted_at` timestamp
2. `VisibilityScope` enum with variants: `Tasks`, `Sessions`, `Epics`, `Events`, `Memory`, `Entities`, `All`
3. `scope_filter(project_id, scopes)` returns SurrealQL WHERE clause that restricts queries to visible projects only
4. Bidirectional linking: project link creates `can_access` in both directions (A sees B AND B sees A) unless `--one-way` flag
5. Scope-based filtering: `can_access` relation carries `scopes` array and queries respect scope constraints
6. `VisibilityManager::grant(from, to, scopes)` creates `can_access` edge with specified scopes
7. `VisibilityManager::revoke(from, to)` removes `can_access` edge
8. `VisibilityManager::visible_projects(project_id)` returns list of project_ids accessible from given project
9. All cross-project queries MUST use `scope_filter` -- direct table queries without visibility check are a security violation

## Notes

- Source: decisions.md D20 (Cross-Project Visibility Model) -- per-project opt-in, graph relations
- Source: global-intelligence.md Section 5 (Data Model, Visibility Enforcement in Queries)
- The SurrealQL pattern `SELECT ->can_access->project FROM project:{id}` is a native graph traversal -- no joins, no subquery overhead
- `scope_filter()` MUST be used by every module that queries cross-project data: sync engine (INF-TSK-025-010), search (INF-TSK-025-015), KG pipeline (INF-TSK-025-016)
- Consider making `scope_filter()` a required parameter in `GlobalDb` query methods to enforce usage at the API level rather than relying on caller discipline
- The `ENFORCED` keyword on can_access relation table ensures both project endpoints exist before creating an edge
