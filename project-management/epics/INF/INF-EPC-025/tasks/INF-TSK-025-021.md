# INF-TSK-025-021: Loro CRDT KG Sync Integration

## Description

Integrate Loro CRDT synchronization for knowledge graph entities and relationships across multiple developers on a team. This extends the Loro infrastructure designed in Epic A (parallel execution coordination) to handle knowledge graph data, enabling team members to share discovered entities and relationships without a centralized server.

Entities and relationships are small records (< 1KB each) that map naturally to LoroMap containers. Embeddings are explicitly excluded from sync -- they are too large for CRDT (1.5KB per 384-dim embedding) and can be deterministically regenerated locally using the same ONNX model (all-MiniLM-L6-v2). After receiving synced entities, the local machine regenerates embeddings for new/changed entities.

This task has a soft dependency on Epic A (Loro infrastructure). If Epic A is not yet complete when this task is implemented, a stub implementation is provided that disables sync gracefully and returns Ok(()) for all sync operations.

## Approach

1. Define `KgSyncEngine` struct holding references to KgStore, EmbeddingEngine, and an optional `LoroDoc` (None if Epic A not available)
2. Define Loro container layout:
   - `kg_entities`: LoroMap keyed by entity_id, values are serialized entity records (excluding embedding field)
   - `kg_relationships`: LoroMap keyed by edge_id, values are serialized relationship records
   - `kg_metadata`: LoroMap for graph statistics, ontology version, last_memify timestamp
   - `extraction_queue`: LoroList for pending extraction entries (optional sync)
3. Implement `export_entity(entity)` -- serialize entity to LoroMap entry (strip embedding, keep all other fields)
4. Implement `export_relationship(edge)` -- serialize relationship to LoroMap entry
5. Implement `import_sync(remote_loro_doc)`:
   a. Merge remote LoroDoc with local using Loro's deterministic merge
   b. Diff to find new/updated entities
   c. Upsert new/updated entities into local SurrealDB via KgStore
   d. Queue embedding regeneration for new/updated entities
6. Implement `regenerate_embeddings(entity_ids)` -- batch call EmbeddingEngine.embed_batch() for entities that need new embeddings after sync
7. Implement stub mode: if LoroDoc is None (Epic A not available), all export/import methods log "KG sync disabled: Loro infrastructure not available" and return Ok(())
8. Wire into git ref transport: sync happens on the same 30s interval as Epic A coordination sync, using refs/coordination/loro/{peer-id}
9. Write tests for export, import, merge, and stub mode

## Notes

- Decision #23 (Knowledge Graph Synchronization): Loro CRDT for teams < 15 devs, TiKV for large/enterprise
- Decision #8 (Loro CRDT as Foundation): same infrastructure handles coordination AND KG sync
- Embeddings are deterministic: same ONNX model + same text = identical vector. Regeneration cost ~5-10ms per entity (knowledge-graph-engine.md Section 8)
- Entity records are < 1KB each -- well within CRDT bandwidth limits
- Loro containers use LoroMap (not LoroTree) because entities are a flat key-value store, not hierarchical
- The extraction_queue sync is optional and may be disabled in config -- queue entries are project-specific and may not need cross-developer sync
- Reference: knowledge-graph-engine.md Section 8 (Multi-User Synchronization Architecture) for the full Loro KG sync design
