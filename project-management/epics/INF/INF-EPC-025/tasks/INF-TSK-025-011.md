# INF-TSK-025-011: Global SurrealDB Schema -- Project-Scoped Tables

## Description

Define the complete field-level SCHEMAFULL schema for the four primary data tables in the global daemon database: `task`, `session`, `epic`, and `memory`. While INF-TSK-025-005 (Global SurrealDB Instance) creates the table structures at a high level, this task fills in the detailed DEFINE FIELD statements for every column, adds comprehensive indexes for query performance, and ensures all tables use project scoping via `record<project>` foreign key references.

The schema definitions align with the canonical field names from the data layer standardization work (INF-EPC-024) and use SurrealDB's SCHEMAFULL enforcement to reject undefined fields. Each table includes an optional `embedding` field (384-dim vector) for semantic search integration.

## Approach

1. Create `schema.rs` module with all DEFINE FIELD statements organized by table
2. Define `task` table fields:
   - Core: `id` (string), `project` (record<project>), `format_id` (string), `title` (string), `description` (option<string>)
   - Status: `status` (string -- enum constraint via ASSERT), `stage` (option<string>), `stage_status` (option<string>)
   - Classification: `area_type` (string), `work_type` (string), `domain` (string), `priority` (string)
   - Estimation: `estimate` (option<string>), `origin` (string), `scope_policy` (string)
   - Dates: `created_at` (datetime), `updated_at` (datetime), `started_at` (option<datetime>), `completed_at` (option<datetime>)
   - Vector: `embedding` (option<array<float>>)
3. Define `session` table fields:
   - Core: `id` (string), `project` (record<project>), `session_id` (string), `status` (string)
   - Context: `interaction_mode` (option<string>), `source` (option<string>), `summary` (option<string>)
   - Dates: `started_at` (datetime), `ended_at` (option<datetime>)
   - Vector: `embedding` (option<array<float>>)
4. Define `epic` table fields:
   - Core: `id` (string), `project` (record<project>), `format_id` (string), `title` (string), `summary` (option<string>)
   - Classification: `status` (string), `area_type` (string), `work_type` (string), `domain` (string), `priority` (string), `is_ongoing` (bool)
   - Dates: `created_at` (datetime), `updated_at` (datetime)
5. Define `memory` table fields:
   - Core: `id` (string), `project` (record<project>), `key` (string), `value` (string)
   - Context: `category` (option<string>), `source_session` (option<string>)
   - Dates: `created_at` (datetime), `updated_at` (datetime)
   - Vector: `embedding` (option<array<float>>)
6. Define indexes:
   - Per-table project index: `DEFINE INDEX {table}_project ON {table} FIELDS project`
   - format_id unique indexes: `DEFINE INDEX task_format_id ON task FIELDS project, format_id UNIQUE`
   - Status indexes: `DEFINE INDEX task_status ON task FIELDS status`, `DEFINE INDEX session_status ON session FIELDS status`
   - Work type index: `DEFINE INDEX task_work_type ON task FIELDS work_type`
   - Date range indexes: `DEFINE INDEX task_created ON task FIELDS created_at`, `DEFINE INDEX session_started ON session FIELDS started_at`
7. Implement `apply_schema(db)` function:
   - Execute all DEFINE statements in order (tables, fields, indexes)
   - Idempotent: safe to run multiple times
8. Implement `verify_schema(db)` function:
   - Query `INFO FOR TABLE {name}` for each table
   - Compare defined fields and indexes against expected
   - Return discrepancies
9. Write tests: schema creation, field constraint validation, index verification

## Notes

- Source: global-intelligence.md Section 5 (Data Model) -- table schemas
- Source: INF-EPC-024 (Data Layer Standardization) -- canonical field names
- The `format_id` UNIQUE index is scoped to project (`FIELDS project, format_id`) because the same format_id (e.g., INF-TSK-021-001) could theoretically appear in different projects
- SCHEMAFULL mode rejects undefined fields, providing data integrity but requiring all fields to be explicitly defined
- The `embedding` field on all tables is `option<array<float>>` -- it starts null and is populated by the embedding pipeline (INF-TSK-025-013) during sync or on-demand
- Consider using `DEFINE FIELD status ON task TYPE string ASSERT $value IN ["todo", "blocked", "in_progress", "complete", "cancelled"]` for enum-like constraints at the DB level
