# INF-TSK-025-017: Entity Deduplication

## Description

Implement entity deduplication for the knowledge graph to prevent the same concept, decision, pattern, or other entity from appearing multiple times. Deduplication runs in two phases: fast hash-based matching for exact duplicates (same entity type + normalized name) and embedding similarity matching for near-duplicates (e.g., "SurrealDB" vs "SurrealDB embedded" vs "Surreal database").

When duplicates are found within the same project, entities are merged: the canonical entity retains the higher confidence score, all descriptions are unioned, and the earliest created_at timestamp is preserved. All edges from the merged entity are redirected to the canonical entity. Cross-project duplicates are NOT merged but instead linked via a `SimilarTo` relationship with `RelationSource::Sync` to preserve project-level autonomy.

## Approach

1. Define `DeduResult` enum: `New`, `ExactMatch(EntityId)`, `NearMatch(EntityId, f32)`
2. Define `Deduplicator` struct holding references to `KgStore` and `EmbeddingEngine`
3. Implement name normalization: lowercase -> trim whitespace -> remove articles (a, an, the) -> collapse multiple spaces -> compute SHA-256 hash of "{entity_type}:{normalized_name}"
4. Implement Phase 1 (hash-based): query `SELECT * FROM entity WHERE hash = $hash` -- if found, return `ExactMatch(id)`
5. Implement Phase 2 (embedding similarity): if no exact match, generate embedding for the new entity's name+description, query `vector::similarity::cosine(embedding, $vec) > 0.95` from entity table -- if found, return `NearMatch(id, score)`
6. If neither phase finds a match, return `New`
7. Implement `merge_entities(canonical_id, duplicate_id)`:
   a. Compare confidence -- keep higher value
   b. Union descriptions (append duplicate's description if not already present)
   c. Keep earliest created_at
   d. Redirect all edges: `UPDATE knows SET in = $canonical WHERE in = $duplicate` and `UPDATE knows SET out = $canonical WHERE out = $duplicate`
   e. Delete the duplicate entity
8. Implement cross-project linking: when entities from different projects match, create `RELATE entity:a->similar_to->entity:b SET source = "sync", confidence = $similarity_score` instead of merging
9. Implement `deduplicate_batch()` for processing arrays of RawEntity from COGNIFY
10. Add dedup statistics tracking and logging
11. Write tests covering exact match, near match, new entity, cross-project linking, edge redirection, and batch processing

## Acceptance Criteria

1. Two-phase dedup: Phase 1 hash-based (SHA-256 of normalized name) for exact matches, Phase 2 embedding similarity (>0.95 cosine) for near matches
2. Name normalization: lowercase, strip leading/trailing whitespace, remove articles (a, an, the), collapse multiple spaces
3. DeduResult enum with variants: New, ExactMatch(EntityId), NearMatch(EntityId, f32) -- f32 is similarity score
4. Merge strategy for matched entities: higher confidence value wins, descriptions are unioned, earliest created_at is preserved
5. Cross-project entities are linked not merged: creates RelationType::SimilarTo with RelationSource::Sync instead of merging
6. Deduplicator struct with deduplicate(raw_entity: &RawEntity) -> Result<DeduResult> method
7. Batch dedup: deduplicate_batch(entities: &[RawEntity]) -> Vec<DeduResult> for processing COGNIFY output
8. Existing edges are redirected from merged entity to canonical entity after merge
9. Dedup statistics logged: total processed, exact matches, near matches, new entities created
10. All dedup operations are idempotent -- running dedup twice produces the same result

## Notes

- The 0.95 embedding similarity threshold for near-match is intentionally high to minimize false merges; configurable via codeflow-knowledge.toml
- Hash normalization pattern: SHA-256(entity_type + ":" + normalize(name)) ensures entities of different types with the same name are not merged (e.g., "SurrealDB" as Technology vs "SurrealDB" as Component)
- Article removal handles: "a", "an", "the" (English only for v1; extend to other languages later if needed)
- Edge redirection must be atomic -- use SurrealDB transaction to update all edges and delete the duplicate in one operation
- MEMIFY (TSK-020) will also perform periodic dedup sweeps, but this module handles the synchronous dedup during COGNIFY ingestion
- Reference: knowledge-graph-engine.md Section 3.3 (COGNIFY pipeline, step d: Deduplication)
