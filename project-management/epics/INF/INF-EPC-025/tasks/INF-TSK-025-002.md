# INF-TSK-025-002: Daemon Process Manager

## Description

Implement the daemon process lifecycle manager that handles starting, stopping, restarting, and health-checking the global SurrealDB daemon. The daemon runs as a background process within the `codeflow` binary (not a separate SurrealDB installation). The manager uses a PID file at `~/.codeflow/run/daemon.pid` with a RAII `PidFileGuard` that ensures automatic cleanup on process exit.

Key design decisions from global-intelligence.md Section 4:
- The `codeflow` binary IS the SurrealDB server in daemon mode
- PID file at `~/.codeflow/run/daemon.pid` with exclusive file lock
- SIGTERM for graceful shutdown with 5-second timeout before SIGKILL
- Signal handling via `nix` crate (not libc directly)
- Stale PID detection: if PID file exists but `kill(pid, 0)` fails, the PID file is orphaned and can be safely removed

## Approach

1. Create `DaemonManager` struct holding configuration (data_dir, socket_path, pid_path, log_path)
2. Implement `PidFileGuard` struct:
   - `PidFileGuard::create(pid_path)` -- writes current PID, acquires file lock
   - `Drop` impl -- removes PID file on scope exit (graceful or panic)
   - File lock via `flock(LOCK_EX | LOCK_NB)` to prevent concurrent daemon instances
3. Implement stale PID detection in `DaemonManager::check_stale_pid()`:
   - Read PID from file
   - Call `nix::sys::signal::kill(Pid::from_raw(pid), None)` (signal 0 -- existence check)
   - If `Errno::ESRCH` (no such process), remove stale PID file
   - If `Errno::EPERM` (process exists, different user), return error
4. Implement `DaemonManager::start()`:
   - Check stale PID, fail if daemon already running
   - Create directories: `~/.codeflow/run/`, `~/.codeflow/data/`, `~/.codeflow/logs/`
   - Fork daemon process using `std::process::Command` with stdout/stderr redirected to log file
   - Wait for socket file to appear (poll up to 10 seconds)
   - Return `Ok(pid)` on success
5. Implement `DaemonManager::stop()`:
   - Read PID from file
   - Send SIGTERM via `nix::sys::signal::kill(pid, Signal::SIGTERM)`
   - Poll process existence for up to 5 seconds
   - If still running, send SIGKILL
   - Remove PID file
6. Implement `DaemonManager::restart()` -- stop() then start() with error recovery
7. Implement `DaemonManager::health_check()` -- process alive AND socket responds to IPC ping
8. Implement `DaemonManager::status()` -- returns `DaemonStatus` with metadata
9. Create daemon binary entry point at `codeflow-daemon.rs`:
   - Initialize tokio runtime
   - Create `PidFileGuard`
   - Start SurrealDB server on Unix socket
   - Install signal handlers (SIGTERM, SIGINT)
   - Enter main event loop
   - On signal, initiate graceful shutdown
10. Write tests using temp directories for PID files (no actual daemon spawn in unit tests)

## Acceptance Criteria

1. `PidFileGuard` struct implemented with RAII `Drop` that removes PID file on daemon exit
2. PID file written to `~/.codeflow/run/daemon.pid` with exclusive file lock
3. Stale PID detection: if PID file exists but process is not running (`kill -0` fails), PID file is removed and daemon can start
4. `DaemonManager::start()` launches daemon process in background, writes PID file, returns `Ok(pid)`
5. `DaemonManager::stop()` reads PID file, sends SIGTERM, waits up to 5 seconds, sends SIGKILL if still running
6. `DaemonManager::restart()` calls `stop()` then `start()` with proper error handling for already-stopped case
7. `DaemonManager::health_check()` verifies process is running AND IPC socket responds to ping
8. `DaemonManager::status()` returns `DaemonStatus` enum with pid, uptime, and connection count
9. Signal handling via `nix` crate: SIGTERM triggers graceful shutdown, SIGINT triggers graceful shutdown
10. Binary entry point at `codeflow-daemon.rs` initializes tokio runtime, starts SurrealDB server, enters main loop
11. All daemon operations log to `~/.codeflow/logs/daemon.log` with structured JSON format

## Notes

- Source: global-intelligence.md Section 4 (Daemon Architecture)
- The `nix` crate is preferred over raw libc for signal handling because it provides safe Rust wrappers with proper error types
- `PidFileGuard` follows the RAII pattern from Epic 0's resource management conventions
- The daemon binary (`codeflow-daemon`) may be a separate binary target or a subcommand of the main `codeflow` binary -- implementation can decide based on cargo workspace structure. The analysis docs describe `codeflow db daemon start` which suggests subcommand approach.
- Graceful shutdown sequence: receive SIGTERM -> stop accepting new connections -> drain in-flight queries -> flush SurrealDB -> remove PID file -> exit(0)
- Log rotation for daemon.log is out of scope (covered by retention policies in INF-EPC-024)
