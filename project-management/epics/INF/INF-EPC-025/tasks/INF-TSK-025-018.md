# INF-TSK-025-018: Cross-Project Entity Linking

## Description

Implement cross-project entity linking that discovers semantically similar entities across projects registered in the global daemon. After entity deduplication (TSK-017) processes a new entity within a project, the linker checks all visible projects (determined by `can_access` graph relations) for entities with high embedding similarity and creates `SimilarTo` relationship edges across project boundaries.

This enables cross-project knowledge graph traversal -- an agent working in a frontend project can discover that "authentication component" is similar to an entity in the backend project, enabling richer context retrieval. Visibility enforcement ensures projects only see entities they are authorized to access via the `can_access` graph relation.

## Approach

1. Define `EntityLinker` struct holding a reference to the global daemon SurrealDB connection
2. Implement `get_visible_projects(project_id)` -- query `SELECT ->can_access->project FROM project:$id` to get the list of projects the current project can see
3. Implement `find_similar_across_projects(entity_id, visible_projects, threshold)`:
   a. Get the entity's embedding from the local project
   b. Query the global daemon: `SELECT id, name, entity_type, project, vector::similarity::cosine(embedding, $vec) AS score FROM entity WHERE project IN $visible AND vector::similarity::cosine(embedding, $vec) > $threshold ORDER BY score DESC LIMIT 10`
   c. Filter out entities from the same project (intra-project dedup is handled by TSK-017)
   d. Return list of (entity_id, score) pairs
4. Implement `create_cross_project_link(from_entity, to_entity, score)`:
   a. Use SurrealDB symmetric dedup pattern: `DEFINE FIELD key ON TABLE similar_to VALUE <string>array::sort([in, out]); DEFINE INDEX only_one_similarity ON similar_to FIELDS key UNIQUE;`
   b. `RELATE entity:from->similar_to->entity:to SET confidence = $score, source = "cross_project", linked_at = time::now()`
5. Implement `link_new_entities(entity_ids)` -- batch wrapper that processes multiple entities, calling find_similar + create_link for each
6. Implement visibility check: before any cross-project query, verify the `can_access` relation exists; skip projects without access
7. Write tests with mock project setup (two projects with can_access, entities in each, verify linking)

## Acceptance Criteria

2. Trigger: runs after entity dedup completes for a new entity, checking visible projects for similar entities
3. Visibility enforcement: only compares entities in projects reachable via can_access graph relations
4. Similarity threshold of 0.85 cosine distance for cross-project SimilarTo links (lower than intra-project 0.95)
5. Creates RelationType::SimilarTo edge with confidence equal to the cosine similarity score
6. Batch processing: link_new_entities(entity_ids) processes a batch of recently created entities
7. Cross-project links are bidirectional: creates edge in both directions using SurrealDB symmetric dedup pattern
8. Linking is additive only -- never deletes existing cross-project links (MEMIFY handles stale link cleanup)

## Notes

- The 0.85 threshold for cross-project linking is lower than the 0.95 intra-project near-match threshold because cross-project entities may use different terminology for the same concept
- Symmetric dedup pattern from knowledge-graph-engine.md Section 2.1: `DEFINE FIELD key ON TABLE similar_to VALUE <string>array::sort([in, out]); DEFINE INDEX only_one_similarity ON similar_to FIELDS key UNIQUE;`
- Cross-project linking requires the global daemon to be running; if daemon is unavailable, linking is silently skipped (graceful degradation)
- The linker only creates SimilarTo relationships -- it does NOT merge entities across projects (that would violate project autonomy)
- Visibility model from decisions.md Decision #20: per-project opt-in via .codeflow/config/project.toml visible_projects config
