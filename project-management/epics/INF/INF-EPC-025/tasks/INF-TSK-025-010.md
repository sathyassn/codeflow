# INF-TSK-025-010: Sync Engine -- Ledger Replay

## Description

Implement the core sync engine that populates the global SurrealDB daemon with data from registered project repositories. The sync engine uses ledger replay: it reads JSONL event files from each project's `.state/ledger/` directory and upserts them into the global database. This is the recommended sync strategy from global-intelligence.md Section 8 (Sync Engine) because:

- Tier 0 JSONL is the rebuild authority -- replaying it is consistent by definition
- No write-path latency added to hook handlers
- The daemon can be rebuilt from scratch at any time without data loss

Each project maintains a sync cursor (byte offset) stored in the project record. On each sync cycle, only new events since the cursor are processed. Rate limiting prevents thundering herd behavior when the daemon starts with many registered projects.

## Approach

1. Create `sync` submodule with `mod.rs` and `engine.rs`
2. Implement `SyncEngine` struct:
   - Fields: `db: Arc<Surreal<Client>>`, `config: SyncConfig`, `rate_limiter: HashMap<ProjectId, Instant>`
   - `SyncEngine::new(db, config)` -- initialize with DB connection and sync settings
3. Implement background sync loop:
   - `SyncEngine::start_background()` -- spawns tokio task running sync loop
   - Loop body: for each registered project, check rate limit, if eligible run `sync_project()`
   - Sleep `sync_interval_seconds` between loop iterations
   - Graceful shutdown on cancellation token
4. Implement per-project sync:
   - `sync_project(project_id, force) -> Result<SyncResult, SyncError>`:
     - Load project record from DB (includes repo_path, sync_cursor)
     - Open `{repo_path}/.state/ledger/` directory
     - For each JSONL file (sessions.jsonl, work-graph.jsonl, memory-events.jsonl, config.jsonl):
       - Seek to sync_cursor offset
       - Read new lines
       - Parse each line as `serde_json::Value`
       - Map event_type to target table (session_start -> session, task_created -> task, etc.)
       - Execute SurrealDB UPSERT with project field set
       - Track events_processed, events_skipped, errors
     - Update sync_cursor in project record
     - Return SyncResult
5. Implement event-to-table mapping:
   - `map_event(event_type: &str, payload: Value) -> Option<(String, Value)>`:
     - Returns (table_name, record_data) for known event types
     - Returns None for unknown/unsupported events (skipped, counted in events_skipped)
6. Implement rate limiting:
   - `RateLimiter` tracks last sync time per project
   - `can_sync(project_id) -> bool` -- true if >5 seconds since last sync
   - `record_sync(project_id)` -- updates last sync time
   - `force` flag bypasses rate limiter
7. Implement conflict resolution:
   - UPSERT uses `WHERE timestamp < $new_timestamp` to ensure last-write-wins
   - If existing record has newer timestamp, skip update
8. Error handling:
   - Individual event failures (parse error, upsert failure) logged and counted
   - Cursor advances past failed events to avoid infinite retry loops
   - SyncResult.errors contains count of failed events
9. Write tests:
   - Create temp directory with sample JSONL files
   - Sync and verify records appear in test DB
   - Cursor tracking: sync twice, verify only new events processed
   - Rate limiting: verify second sync within 5s is skipped
   - Error handling: malformed JSONL line, verify sync continues past it

## Acceptance Criteria

1. `SyncEngine::new(db, config)` initializes engine with global DB connection and sync configuration
2. Background sync loop runs every `sync_interval_seconds` (default 30) from `GlobalConfig`
3. Per-project sync cursors stored in project record's `sync_cursor` field (byte offset in JSONL file)
4. Ledger replay: reads `.state/ledger/*.jsonl` files from each registered project's `repo_path`
5. JSONL parsing: each line parsed as `serde_json::Value`, mapped to target SurrealDB table based on `event_type`
6. Upsert semantics: existing records updated, new records created, using SurrealDB `UPSERT` statement
7. All synced records tagged with `project` field linking to source project record
8. Rate limiting: max 1 sync per project per 5 seconds to prevent thundering herd on daemon startup
9. Conflict resolution: last-write-wins by `timestamp` field
10. `SyncResult` returned per project: `events_processed`, `events_skipped`, `errors`, `duration_ms`
11. Error handling: individual event parse/upsert failures do not abort sync -- logged and counted in errors, cursor advances
12. `SyncEngine::sync_project(project_id, force)` triggers immediate sync for one project, bypassing rate limit if `force=true`

## Notes

- Source: global-intelligence.md Section 8 (Sync Engine) -- ledger replay strategy, cursors, rebuild
- Source: decisions.md D17 (SurrealDB-only) -- all upserts target SurrealDB, not SQLite
- Sync cursors are file-offset based (byte position in the JSONL file) for exact resumption after daemon restart
- The event-to-table mapping must handle both shell-era and Go-era field naming (from schema standardization analysis in INF-EPC-024). In the post-Epic-0 world, all JSONL entries should use canonical fields, but backward compatibility with existing entries is needed.
- Consider using `tokio::fs::File` with `seek()` for efficient cursor-based reads instead of reading from the beginning each time
- The 5-second rate limit prevents N projects from all syncing simultaneously on daemon startup, spreading the load over time
- Dual-write sync (writing to both local and daemon on each write) is explicitly deferred (global-intelligence.md Section 8) -- ledger replay is the V1 approach
- Design decision: Sync engine uses ledger replay (JSONL file tailing) exclusively in this epic. Dual-write strategy (writing to both local and daemon simultaneously) was evaluated and deferred as a future enhancement after ledger replay proves stable. Ref: global-intelligence.md Section 8.
