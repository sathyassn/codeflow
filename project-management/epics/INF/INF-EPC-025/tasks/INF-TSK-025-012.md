# INF-TSK-025-012: Rebuild Command

## Description

Implement the global database rebuild command, which is the primary recovery mechanism for the global intelligence layer. When the global database is corrupted, has schema drift, or needs to incorporate new record types, `codeflow daemon rebuild` drops all data tables (while preserving the project registry and configuration), re-initializes the schema, and replays all JSONL ledger events from every registered project from the beginning.

This is a direct implementation of the key resilience property from global-intelligence.md Section 9: "The global database is always reconstructible from Tier 0 JSONL." The rebuild command makes this property actionable with a single CLI command.

## Approach

1. Implement `RebuildManager` struct:
   - Fields: `db: Arc<Surreal<Client>>`, `sync_engine: SyncEngine`, `config: GlobalConfig`
   - `RebuildManager::new(db, sync_engine, config)` -- constructor
2. Implement rebuild sequence in `RebuildManager::rebuild(dry_run: bool)`:
   - **Step 1: Acquire rebuild lock**
     - Create `~/.codeflow/run/rebuild.lock` with exclusive flock
     - If lock already held, return `DaemonError::RebuildInProgress`
   - **Step 2: Save project registry**
     - Read all project records and can_access relations into memory
   - **Step 3: Drop data tables**
     - `REMOVE TABLE task; REMOVE TABLE session; REMOVE TABLE epic; REMOVE TABLE event; REMOVE TABLE memory; REMOVE TABLE entity; REMOVE TABLE extraction_queue;`
     - DO NOT remove: `project`, `can_access`, `_meta`
   - **Step 4: Re-initialize schema**
     - Call `apply_schema(db)` from schema module (INF-TSK-025-011)
     - Update `_meta` schema_version
   - **Step 5: Reset sync cursors**
     - `UPDATE project SET sync_cursor = NONE` for all projects
   - **Step 6: Replay all JSONL**
     - For each registered project:
       - Call `sync_engine.sync_project(project_id, force=true)`
       - Report progress: project name, events processed, errors
   - **Step 7: Regenerate embeddings** (if embedding pipeline available)
     - Query all records with null embedding field
     - Generate embeddings via ONNX pipeline
     - This step is best-effort -- if embedding model not available, skip with warning
   - **Step 8: Report summary**
     - Total events processed, total errors, duration, per-project breakdown
   - **Step 9: Release rebuild lock**
     - Remove `~/.codeflow/run/rebuild.lock`
3. Implement dry-run mode:
   - Count registered projects
   - Estimate total events by reading JSONL file sizes
   - Print plan without executing
4. Implement progress reporting:
   - Use callback pattern or channel to emit progress events
   - CLI formats as: `[2/5] Syncing codeflow: 1,234 events processed (3 errors)`
5. Write tests:
   - Pre-populate DB with records, rebuild, verify records restored
   - Verify project registry preserved across rebuild
   - Verify sync cursors reset to zero
   - Verify dry-run produces no side effects
   - Verify exclusive lock prevents concurrent rebuild

## Acceptance Criteria

1. Rebuild sequence: drop data tables (preserve project registry and `_meta`) -> re-init schema -> replay all JSONL from all projects -> regenerate embeddings
2. Project registry preserved: project records and `can_access` relations survive rebuild
3. Sync cursors reset to zero for all projects during rebuild (forces full replay)
4. Progress reporting: prints per-project progress (project name, events processed, errors) during rebuild
5. `--dry-run` flag: reports what would be done (project count, estimated event count) without executing
6. Rebuild uses `SyncEngine::sync_project(project_id, force=true)` for each project with cursor reset to 0
7. Embedding regeneration: after replay, triggers embedding pipeline for all records with null embedding field
8. Rebuild acquires exclusive lock: prevents concurrent rebuilds via PID-file-style lock at `~/.codeflow/run/rebuild.lock`
9. Rebuild completes with summary: total events, total errors, duration, per-project breakdown

## Notes

- Source: global-intelligence.md Section 8 (Sync Engine, Rebuild Capability)
- Source: global-intelligence.md Section 9 (Reliability, Key Resilience Property)
- The rebuild command is the "nuclear option" for the global database -- it should work in any state, including corrupt databases
- Preserving project registry and can_access is critical: users should not need to re-register and re-link projects after rebuild
- Embedding regeneration may be slow for large databases (each record needs ONNX inference). Consider making it optional with `--skip-embeddings` flag.
- The exclusive lock prevents data corruption from concurrent rebuilds but does NOT prevent normal sync operations during rebuild. The sync engine should be paused during rebuild steps 3-6 to avoid race conditions.
- Full rebuild is expected to be rare (corruption, schema migrations, adding new record types). Normal operation uses incremental sync.
