# INF-TSK-025-004: IPC Client Library

## Description

Implement the client-side counterpart to the IPC server (INF-TSK-025-003). The `DaemonClient` provides a typed, ergonomic Rust API for communicating with the global daemon over the Unix domain socket. It handles connection establishment, the length-prefixed JSON protocol framing, timeout management, automatic retry on transient failures, and provides typed convenience methods for each daemon operation (register, search, sync, etc.).

The client is used by all CLI subcommands and by any codeflow component that needs to query the global daemon. A key design goal is graceful degradation: `DaemonClient::try_connect()` returns `None` when the daemon is not running, enabling callers to fall back to local-only operation without error handling boilerplate.

## Approach

1. Define `ClientConfig` struct:
   - `timeout_ms: u64` (default 5000) -- per-request timeout
   - `retry_count: u32` (default 2) -- retries on transient failure
   - `retry_delay_ms: u64` (default 500) -- delay between retries
   - Implement `Default` trait with sensible defaults
2. Implement `DaemonClient` struct:
   - Fields: `stream: tokio::net::UnixStream`, `config: ClientConfig`
   - `DaemonClient::connect(socket_path) -> Result<Self, IpcError>` -- connect and verify with ping
   - `DaemonClient::with_config(socket_path, config) -> Result<Self, IpcError>` -- custom config
   - `DaemonClient::try_connect(socket_path) -> Option<Self>` -- returns None on connection failure
3. Implement core `send()` method:
   - Encode request using protocol frame codec
   - Write to socket with timeout
   - Read response with timeout
   - Decode response
   - On transient error (ConnectionReset, Timeout): retry up to `retry_count` times with `retry_delay_ms`
4. Implement typed convenience methods:
   - `register(project_id, name, repo_path, repo_url, area_prefixes) -> Result<Response, IpcError>`
   - `search(query, limit, scope, project_filter) -> Result<Vec<SearchResult>, IpcError>`
   - `sync(project_id, force) -> Result<SyncResult, IpcError>`
   - `status() -> Result<DaemonStatus, IpcError>`
   - `query(surql, params) -> Result<Response, IpcError>`
   - `rebuild(dry_run) -> Result<Response, IpcError>`
   - Each method constructs the specific Request variant and unwraps the matching Response variant
5. Implement connection reuse: the underlying `UnixStream` persists across calls
6. Write tests against a mock IPC server (spawn server in test, connect client, verify roundtrips)

## Acceptance Criteria

1. `DaemonClient::connect(socket_path)` establishes connection to Unix domain socket, returns `Result<DaemonClient, IpcError>`
2. `DaemonClient::ping()` sends Ping request, returns `Ok(())` if Pong received within timeout
3. `DaemonClient::send(request)` sends arbitrary Request and returns Response, handling frame encoding/decoding
4. `ClientConfig` struct with `timeout_ms` (default 5000), `retry_count` (default 2), `retry_delay_ms` (default 500)
5. `DaemonClient::with_config(socket_path, config)` constructor accepts custom `ClientConfig`
6. Typed convenience methods: `register()`, `search()`, `sync()`, `status()`, `query()`, `rebuild()`
7. Automatic retry on transient failures (connection reset, timeout) up to `retry_count`
8. Connection pooling: `DaemonClient` reuses the underlying socket connection across multiple requests
9. Graceful fallback: `DaemonClient::try_connect()` returns `None` instead of `Err` when daemon is not running

## Notes

- Source: global-intelligence.md Section 9 (Reliability) -- graceful degradation when daemon unavailable
- The `try_connect()` method is critical for the access pattern split (global-intelligence.md Section 2): hook handlers use local embedded SurrealDB and never block on daemon availability
- `ClientConfig` defaults match global-intelligence.md Section 6: `daemon_timeout_ms = 500` for initial connection, but per-request timeout is higher (5000ms) to allow for complex queries
- Connection reuse reduces latency for bulk operations (e.g., project list querying status for each project)
- Consider implementing `Clone` for `DaemonClient` using `Arc<Mutex<UnixStream>>` if concurrent access is needed from multiple tasks within a single process
