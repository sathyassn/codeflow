# INF-TSK-025-026: Integration Test Suite

## Description

Implement a comprehensive integration test suite that validates the complete Global Intelligence Layer from daemon startup to knowledge graph search. The suite uses a `TestDaemon` fixture that creates isolated daemon instances in temporary directories, enabling parallel test execution without interference.

The 12 test scenarios cover the full feature surface: daemon lifecycle management, project registration and sync, visibility enforcement across projects, embedding generation, COGNIFY extraction pipeline, entity deduplication, hybrid GRAPH_COMPLETION search, concurrent connection handling, graceful shutdown under load, cross-project graph traversal, and MEMIFY refinement.

All tests are designed for CI compatibility: no platform service registration (launchd/systemd), no external network access, full temp directory cleanup via scopeguard/Drop, and a total execution time target of under 120 seconds.

## Approach

1. Implement `TestDaemon` fixture:
   a. `start(temp_dir)` -- create `~/.codeflow-test-{random}/` directory, start SurrealDB daemon on a Unix socket in that directory, wait for ready
   b. `client()` -- return a connected SurrealDB client to the test daemon
   c. `stop()` -- send SIGTERM to daemon process, wait for exit, clean up temp dir
   d. Implement Drop trait to ensure cleanup even on test panic (via scopeguard)
2. Implement `TestProject` helper:
   a. Create a temp directory with `.state/ledger/*.jsonl` files
   b. Register project with test daemon
   c. Write sample JSONL events for sync testing

**Test scenarios:**

3. **Test 1 -- Daemon lifecycle**: start() -> verify `daemon.pid` exists and process is alive -> stop() -> verify PID file removed and process exited
4. **Test 2 -- Project registration**: register project with auto-generated project_id -> query `project` table -> verify record matches
5. **Test 3 -- Ledger sync**: write 10 JSONL events to test project ledger -> trigger sync -> query daemon DB -> verify all 10 records present
6. **Test 4 -- Visibility**: register project_a and project_b -> link project_a->can_access->project_b -> query tasks with project_a scope -> verify project_b tasks visible; query with project_b scope -> verify project_a tasks NOT visible
7. **Test 5 -- Embedding generation**: create entity record -> call EmbeddingEngine.embed() -> verify result is Vec<f32> with length 384 (use mock or small test model)
8. **Test 6 -- COGNIFY**: insert task "Fix authentication bug in session handler" -> run CognifyPipeline with MockExtractor -> verify entity "authentication" (Component) and relation "session handler" -> "authentication" created
9. **Test 7 -- Dedup**: create entity "SurrealDB" (Technology) -> create entity "surrealdb" (Technology) -> run Deduplicator -> verify only one entity remains with merged properties
10. **Test 8 -- Hybrid search**: create 5 entities with embeddings -> search("database technology") -> verify results ranked by combined score, top result is most relevant
11. **Test 9 -- Concurrent connections**: spawn 3 tokio tasks each running 10 queries -> join all -> verify no panics, all queries returned valid results
12. **Test 10 -- Graceful shutdown**: start query in background task -> initiate stop() -> verify query completes or returns error (not panic), daemon exits cleanly
13. **Test 11 -- Cross-project graph**: project_a has entity "API endpoint", project_b has entity "API client" -> link projects -> create SimilarTo edge -> traverse from project_a through SimilarTo to project_b entity
14. **Test 12 -- MEMIFY**: create graph with 5 entities and 8 edges -> simulate search traversals on 3 edges -> run MEMIFY -> verify traversed edges have higher confidence, create orphaned entity -> run MEMIFY -> verify it's pruned

15. Configure all tests with `#[tokio::test]` and appropriate timeouts
16. Implement test ordering: independent tests run in parallel, dependent tests use shared fixtures

## Notes

- TestDaemon uses a unique temp directory per test to avoid daemon socket conflicts
- Daemon integration tests MUST run serially (`--test-threads=1`) because each test starts/stops a daemon process
- KG integration tests CAN run in parallel because they use isolated SurrealDB embedded instances (not the daemon socket)
- MockExtractor is used for COGNIFY tests (Test 6) to avoid LLM API dependency in CI
- For embedding tests (Test 5), use a tiny test model or mock the ort::Session -- the full 50MB model should not be downloaded in CI
- scopeguard crate ensures temp directory cleanup even on test panic
- The 120-second total time target assumes ~10 seconds per test with some parallelism
- Reference: global-intelligence.md Section 9 (Reliability -- failure modes and recovery) for graceful shutdown test scenarios
