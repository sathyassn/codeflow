# INF-TSK-025-025: Daemon Logging & Observability + Doctor Extension

## Description

Implement comprehensive logging and observability for the codeflow daemon using the `tracing` ecosystem. The daemon produces two log streams: JSON-formatted logs written to `~/.codeflow/logs/daemon.log` (for machine parsing) and human-readable logs on stdout (for interactive debugging). Log rotation handles daily file rotation with 7-day retention.

In-memory metrics track key operational counters (requests, sync ops, embedding ops, extraction ops, search ops) with duration histograms. These metrics are exposed via the `codeflow kg stats` command and the daemon status endpoint.

The `codeflow doctor` command is extended with 6 new global diagnostic checks: daemon process status, socket accessibility, registered projects, sync cursor freshness, embedding model presence, and extraction queue health.

## Approach

1. Add `tracing`, `tracing-subscriber`, and `tracing-appender` crate dependencies
2. Implement `DaemonLogger::init()`:
   a. Create JSON file subscriber targeting `~/.codeflow/logs/daemon.log` with daily rotation and 7-day retention via `tracing_appender::rolling::daily()`
   b. Create human-readable stdout subscriber with colored output
   c. Compose both subscribers using `tracing_subscriber::Layer` combinators
   d. Initialize global subscriber
3. Implement CODEFLOW_LOG env var parsing: read `std::env::var("CODEFLOW_LOG")`, parse to `tracing::Level`, default to `Level::INFO`
4. Define structured log fields convention:
   - `component`: "daemon", "kg", "sync", "search", "embedding", "cognify", "memify"
   - `operation`: specific operation name (e.g., "extract_entities", "search_query")
   - `duration_ms`: elapsed time
   - `entity_count`, `relationship_count`: counts for KG operations
   - `error_type`: error classification for failures
5. Implement `DaemonMetrics` struct (in-memory, thread-safe via AtomicU64 counters):
   - requests_total, sync_ops_total, embedding_ops_total, extraction_ops_total, search_ops_total
   - Duration tracking: Vec<Duration> per operation type for histogram computation
   - `snapshot()` method returns current metrics as a serializable struct
6. Implement 6 doctor checks as functions returning `DoctorCheck { name, status, message }`:
   a. `check_daemon_running()`: read `~/.codeflow/run/daemon.pid`, verify process alive via `kill -0 $pid`
   b. `check_socket_accessible()`: check `~/.codeflow/db.sock` exists and is connectable (try connect, timeout 500ms)
   c. `check_registered_projects()`: query daemon for project count and names
   d. `check_sync_freshness()`: query last_synced per project, compute lag in minutes
   e. `check_embedding_model()`: verify `~/.codeflow/models/all-MiniLM-L6-v2.onnx` exists, check file size (~50MB)
   f. `check_extraction_queue()`: query pending and failed counts, age of oldest pending entry
7. Register doctor checks in the existing doctor command framework (extend `codeflow doctor` output)
8. Write tests for logger initialization, metrics tracking, and each doctor check

## Notes

- Doctor checks reference: global-intelligence.md Section 11 (CLI Commands, Doctor extended checks)
- The tracing crate is the de facto standard for structured logging in async Rust applications
- tracing-appender provides non-blocking file appender with rotation -- critical for daemon performance
- In-memory metrics (not Prometheus/StatsD) -- this is a local developer tool, not a distributed system
- Doctor checks should be fast (< 500ms total) -- use timeout on socket check to avoid blocking
- Log file location: `~/.codeflow/logs/daemon.log` (same as specified in global config ~/.codeflow/config.toml)
- The PID check (`kill -0 $pid`) is cross-platform on Unix but needs adaptation for non-Unix (return "unsupported" on Windows)
