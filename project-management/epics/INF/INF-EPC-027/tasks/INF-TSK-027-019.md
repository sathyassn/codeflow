# INF-TSK-027-019: Semantic Search View

## Description

Implement the Search tab providing semantic search across all CodeFlow data. The frontend features a search input with debounced query submission (300ms), filter chips for narrowing results by category (Tasks, Sessions, Memory, Code, Entities), and a results list displaying relevance scores, source IDs, project names, titles, and text snippets with keyword highlighting.

The backend sends queries to the CodeFlow daemon which performs ONNX-based embedding generation and HNSW vector search in SurrealDB. Results are filtered by `can_access` permissions for cross-project safety. Score badges are color-coded by relevance: green (>=0.8), blue (0.5-0.8), yellow (<0.5).

This task depends on Epic C (Global Intelligence Layer) Phase C3-C4 for the daemon-side embedding and vector search infrastructure.

## Approach

1. Create the SvelteKit route at `src/routes/search/+page.svelte` with the search layout
2. Create a `search` Svelte store in `src/lib/stores/search.ts` managing query state, results, loading, and active filters
3. Create the `SearchInput.svelte` component with a text input, placeholder text, and debounce logic (300ms delay before triggering search)
4. Create the `FilterChips.svelte` component with toggle chips: All Projects, Tasks, Sessions, Memory, Code, Entities
5. Create the `SearchResults.svelte` component rendering a list of result cards:
   - Score badge with color-coding: green background for >=0.8, blue for 0.5-0.8, yellow for <0.5
   - Source ID and project name in metadata line
   - Title in bold
   - Text snippet with `<mark>` tag highlighting around matched terms
6. Create the `semantic_search(query: String, filters: Vec<String>)` Tauri command in `src-tauri/src/commands/search.rs`:
   - Send query to daemon for ONNX embedding generation
   - Execute HNSW vector search in daemon SurrealDB
   - Filter results by `can_access` permission
   - Return results sorted by relevance score descending
7. Implement loading state with skeleton result placeholders (3-5 skeleton cards)
8. Implement empty state with "No results found" message and search suggestions
9. Sanitize snippet HTML to prevent XSS (only allow `<mark>` tags)
10. Write frontend component tests for filters, debounce, and result rendering; backend tests with mock search responses

## Notes

- The ONNX embedding model runs in the daemon process, not in the Tauri app -- the app sends text to the daemon and receives embeddings back
- HNSW (Hierarchical Navigable Small World) is the vector index algorithm used by SurrealDB for approximate nearest neighbor search
- Snippet highlighting should be performed server-side (daemon) for consistency, with the app only sanitizing and rendering
- The 300ms debounce prevents excessive daemon queries during typing
- `can_access` is a per-project permission flag stored in the daemon's project registry
