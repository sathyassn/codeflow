# INF-TSK-047-001: Fix codeflow status TUI — TASK column, layout, stale semantics, details panel, auto-refresh

> **MANDATORY VALIDATION:** Files created from this template MUST be validated against the task validation command before committing:
> `codeflow validate task <file-path>`

## Description

The `codeflow interactive status` and autorun status TUI dashboards have multiple display
defects. This task fixes all of them in a single coherent change:

1. **TASK column** currently shows raw ULIDs or nothing. It should show the formatted task ID
   (`INF-TSK-047-001`) when available, a truncated ULID fallback when format_id is unset, and
   `--` when no task is associated with the session.

2. **Adhoc task format_id** — adhoc tasks registered by cf-knowledge-layer lack a format_id.
   The registration path should assign `{AREA}-TSK-adhoc-{seq}` when area is inferable.

3. **Stale-row PHASE** shows `Starti` (truncated `Starting`) or `--` instead of the actual
   last-completed phase sentinel. Should show `pf-1` through `pf-7` or `pre-pf1`.

4. **Details panel** does not update on Up/Down key selection changes — it only updates on
   refresh ticks. Should update immediately on selection.

5. **Column widths** misaligned: TASK column too narrow for formatted IDs, inconsistent spacing.

6. **Auto-refresh loop** can stall when data fetch blocks the render thread.

**Issue 1 — TASK column always shows `--` (or raw ULID).**

Root cause chain:
1. `post_tool_use.rs:631–639` reads `task_id` (ULID only) from `active-task.json` and writes it to `interactive_session.task_id`. It ignores `task_format_id` which is also in that file (`active_task.rs:37`).
2. `interactive_session.rs:29` has no `task_format_id` column.
3. `tui/data.rs:395–406` fallback re-reads `active-task.json` but only grabs `.task_id`, not `.task_format_id`.
4. `SessionView.task_id` (`tui/data.rs:72`) therefore carries either the ULID or `None`.
5. `interactive.rs:1248` prints `s.task_id.as_deref().unwrap_or("--")` — no formatting, no truncation.
6. For adhoc sessions where no ensure-work-registered ran yet, the row has `task_id = None` → `--` (AC #1 requires `--` here, which is correct).
7. For adhoc sessions where `ensure-work-registered` DID run, cf-knowledge-layer already writes `format_id` into the tasks table (workgraph/task.rs:83–88). But `active-task.json` may be written with only the ULID if the agent used the wrong CLI invocation — `codeflow state set-active-task` accepts both `--task-id` and `--task-format-id` flags (active_task.rs:31–37 shows both fields). So format_id is sometimes present, sometimes not.

Fix plan:
1. Extend `InteractiveSession` schema with `task_format_id: Option<String>` (new `#[serde(default)]` column).
2. `post_tool_use.rs:630–672`: read both `task_id` AND `task_format_id` from `active-task.json`; write both columns.
3. `tui/data.rs`: extend `SessionView` with `task_format_id: Option<String>`. Populate from DB column, fallback to `active-task.json`.
4. Add a new `fn format_task_id_for_display(task_format_id: Option<&str>, task_id: Option<&str>) -> String` helper in `tui/data.rs` implementing the AC #1 ruleset:
   - `Some(fmt)` → `fmt` as-is (e.g., `INF-TSK-046-008`)
   - `None, Some(ulid)` → `{first 8}…{last 5}` of ULID (e.g., `task-01K…MHH`)
   - `None, None` → `--`
5. `interactive.rs:1248` and `autorun.rs:2236` both call this helper.
6. Data-model note: this adds a SurrealDB column. Schema-less SurrealDB handles optional fields without migration; existing rows just return `NONE` for the new column, which deserializes via `#[serde(default)]`. No migration script needed.

**Issue 2 — Adhoc task format_id (AC #2).**

cf-knowledge-layer already generates format_id for adhoc tasks via `ensure-work-registered` → `generate_task_format_id` in `workgraph/format_id.rs:57–86`. The formatted ID uses the pattern `{AREA}-TSK-{epic_seq:03}-{next_seq:03}` — NOT the `{AREA}-TSK-adhoc-{seq}` pattern the AC proposes.

The existing convention ties adhoc tasks to an ad-hoc epic (area inferred from branch prefix per ensure-work-registered SOP). The formatted ID is then indistinguishable from a planned task's format_id, which is intentional and is how all existing adhoc tasks behave in the DB (there are 47+ such tasks across recent sessions).

⚠️ **Design decision needed from team lead:** The AC says "assigns a formatted ID `{AREA}-TSK-adhoc-{seq}`". But the codebase already generates `{AREA}-TSK-{NNN}-{NNN}` via `generate_task_format_id`. Three options:

- **Option A (recommended):** Update AC #2 to match reality — adhoc tasks already get format_id via the standard numbering. Task-doc change is an AC clarification: "adhoc tasks receive format_id via the standard `{AREA}-TSK-{epic_seq}-{task_seq}` pattern; verify format_id is populated in the DB after ensure-work-registered runs". This is a 1-line DB check.
- **Option B:** Introduce a new `-TSK-adhoc-NNN` pattern — requires new `adhoc_sequence` counter in DB, new format_id generator branch, backwards-compat migration for existing adhoc tasks. Significant scope creep.
- **Option C:** Treat as idempotency/migration only — "existing task records without format_id are migrated opportunistically on next touch" (last sentence of AC #2). Add a one-shot migration in `post_tool_use` that back-fills format_id via `generate_task_format_id` when it sees a task_id with no format_id.

I recommend **Option A** (no code change for the adhoc-ID pattern itself, just add the back-fill migration from Option C for robustness).

**Issue 3 — Stale-row PHASE = `Starti` or `--` instead of pf-N / pre-pf1 (AC #3).**

Root cause chain:
1. `tui/data.rs:362–378` — when raw_phase is None and status is stale → returns `None` → `PhaseBadge` renders `--`. For ACTIVE sessions in a worktree it returns `Starting...` (11 chars).
2. `interactive.rs:1277` — PHASE column constraint is `Length(6)`. `Starting...` gets truncated to `Starti`. This is the `Starti` bug.
3. On stale, `derive_phase_from_session` returns None if the worktree was destroyed (SessionEnd hook removes it at cleanup), so the sentinel chain also can't be read → None → `--`.

**Issue 4 — Details panel not populating/updating (AC #4).**

Current behavior (interactive.rs:975–980): the Details pane IS driven by the same `selected_session` computed from `table_state.selected()` on every draw. Since `terminal.draw` is called at the top of every loop iteration AND after every key event (implicitly via the next loop iteration), selection changes take ~1 tick (up to 2s by default) to reflect.

Root cause: `event::poll(tick)` blocks up to `tick` duration. When a key event arrives before the tick expires, we handle it, then fall through to `fetch_session_views_with_keep_last` (a DB round-trip — tens to hundreds of ms). Only then does the loop cycle back to `terminal.draw`. The UX perception is "details didn't update until next refresh" because the `terminal.draw` is after fetch, not before.

Secondary issue: `render_session_detail` in interactive.rs:1333–1373 is very minimal — only shows Session/PID, Worktree, Team/Branch/Type. It does NOT render Task, Status, Phase, or Duration per AC #4.

Fix plan:
1. Restructure the loop: after a key event that changes selection, redraw immediately BEFORE the next fetch. Explicitly: after match on KeyCode::Up/Down, call `terminal.draw(|f| ...)` again (or move the draw call to happen both at top of loop AND after any key handler that mutates table_state).
2. Cleaner approach: extract draw into a closure `let draw_ui = |terminal, table_state, last_data, ...| -> Result<()> { ... }` and invoke it after every key event that can change selection.
3. Expand `render_session_detail` to render ALL the AC-required fields (Session, PID+alive, Worktree, Team, Branch, Type, Task (formatted+ULID), Status, Phase, Duration). Row 1: Session+PID; Row 2: Worktree; Row 3: Team+Branch+Type; Row 4 (new): Task (both formatted and truncated ULID); Row 5 (new): Status+Phase+Duration. Widen detail Constraint::Length from 6 to 8.
4. Apply the same pattern to the autorun Details pane (autorun.rs around line 1795–1827).

**Issue 6 — Auto-refresh stalls/frozen (AC #6).**

Root cause candidates inspected:
1. `tui/data.rs:338–346` — when a session has `status = active` but PID is dead, `fetch_session_views_with_keep_last` issues an `UPDATE interactive_session SET status='stale'` query INSIDE the render-path fetch. This query is awaited inline, adding DB round-trip latency. If the DB is locked by another process (another TUI instance, post_tool_use running, sync daemon), this can block for up to the DB's retry timeout.
2. `interactive.rs:1127–1134` — every tick re-opens the store (`open_store(project_dir)`), which for SurrealDB embedded opens a new RocksDB handle. Repeated opens fragment cache and can intermittently stall. The comment says "re-open store for cross-process visibility" — this is the workaround landed by `1b1f293d`.
3. `event::poll(tick)` + fetch are sequential on the render thread. A slow fetch (e.g., DB in contention) freezes key responsiveness AND rendering.

Fix plan:
1. Move the DB fetch OFF the render thread. Use `tokio::sync::watch` channel: spawn a background task that re-opens store + fetches data + sends to watch channel on `interval_secs` cadence; render loop reads current watch value (non-blocking). Render thread's `event::poll` can use a shorter tick (e.g., 100ms) for UX responsiveness, independent of data refresh.
2. Remove the inline `UPDATE interactive_session SET status='stale'` from the render fetch. Move the PID-liveness-promotion to a separate housekeeping task or defer to the background fetcher's dedicated code path.
3. Track last render timestamp; if > 2×interval has elapsed without a redraw, log a stall diagnostic to stderr (on drop) so stalls are observable.
4. Regression test: simulate a slow DB (5s latency) and assert the render loop keeps ticking within 500ms of input events.

**This is the most invasive of the 6 fixes.** I propose implementing the simpler version first (keep current synchronous fetch, but reduce `event::poll` tick to 100ms and trigger a fetch at most once per `interval_secs`). That eliminates the "keys feel frozen for 2s" UX problem without requiring async channels. The full async-offload can be a follow-up if needed.
