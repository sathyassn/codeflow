# INF-TSK-026-002: Model Profile Registry

## Description

Implement the `ModelProfileRegistry` -- a validated, queryable collection of model profiles that serves as the single source of truth for which models are available and how they are configured. The registry loads built-in profiles (Claude Sonnet, Claude Opus, Codex CLI, Ollama) and merges them with custom profiles from `orchestration.toml`, allowing users to override built-in defaults or add entirely new model profiles.

The registry provides query methods for looking up profiles by ID, listing all profiles, validating CLI existence for external models, and filtering models configured for a specific work stage. This abstraction centralizes all model profile logic, keeping the routing engine and executors focused on their own concerns.

## Approach

1. Create `registry.rs` in `codeflow-rs/codeflow-core/src/orchestrator/`
2. Define `ValidationWarning` struct with `model_id: ModelId` and `message: String` fields
3. Define `ModelProfileRegistry` struct containing `profiles: HashMap<ModelId, ModelProfile>` and `config: OrchestrationConfig`
4. Implement `ModelProfileRegistry::new(config: OrchestrationConfig) -> Self`:
   - Start with built-in profiles as the base set
   - Merge custom profiles from config, overriding built-ins with matching ModelId
   - Store the merged set
5. Implement built-in profile definitions as a `fn built_in_profiles() -> HashMap<ModelId, ModelProfile>`:
   - Claude Sonnet: `ApiType::ClaudeSubagent`, `default_tier: T1`, `max_tokens: 200_000`
   - Claude Opus: `ApiType::ClaudeSubagent`, `default_tier: T3`, `max_tokens: 200_000`
   - Codex: `ApiType::ExternalCli`, `cli_command: "codex"`, `default_tier: T1`, `max_tokens: 128_000`
   - Ollama: `ApiType::LocalCli`, `cli_command: "ollama"`, `default_tier: T1`, `max_tokens: None` (model-dependent)
6. Implement `get(&self, model_id: &ModelId) -> Option<&ModelProfile>`
7. Implement `validate(&self) -> Vec<ValidationWarning>`:
   - For each `ExternalCli` and `LocalCli` profile, check if `cli_command` exists via `which` (use `std::process::Command::new("which").arg(cmd)`)
   - Return warnings for missing CLIs (not errors -- models may be configured but not installed)
8. Implement `list(&self) -> impl Iterator<Item = &ModelProfile>`
9. Implement `models_for_stage(&self, stage: &WorkStage) -> Vec<&ModelProfile>`:
   - Look up stage in config routing
   - Return the default model and all override models for that stage
10. Add module to `orchestrator/mod.rs` re-exports
11. Write tests:
    - Built-in profiles are present in fresh registry
    - Custom profile overrides built-in with same ID
    - Custom profile adds new model not in built-ins
    - `get` returns None for unknown ID
    - `validate` returns warnings for missing CLIs
    - `models_for_stage` returns correct models
    - Insta snapshots of built-in registry
