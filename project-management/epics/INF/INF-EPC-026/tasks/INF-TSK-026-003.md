# INF-TSK-026-003: Stage Routing Engine

## Description

Implement the `StageRouter` -- the core routing engine that maps `(work_stage, work_type)` tuples to model profiles using a three-tier precedence system. The router is stateless and deterministic: given the same configuration and inputs, it always produces the same model selection. It is `Send + Sync` to allow safe concurrent access from async executor threads.

The three-tier precedence system resolves model selection as follows:
1. **Work-type override:** If the stage routing has a work_type-specific override (e.g., FEAT work on WS-DEV uses Codex), use that model.
2. **Stage-specific default:** If no work-type override matches, use the stage's default model.
3. **Global default:** If no stage routing exists, use the global default model.

The router also provides an `explain_selection()` method that returns a human-readable explanation of which precedence tier matched, useful for debugging and the CLI `config --show` command.

## Approach

1. Create `router.rs` in `codeflow-rs/codeflow-core/src/orchestrator/`
2. Define `StageRouter` struct with fields:
   - `registry: Arc<ModelProfileRegistry>` -- shared reference to profile registry
   - `config: Arc<OrchestrationConfig>` -- shared reference to config
3. Implement `StageRouter::new(registry: Arc<ModelProfileRegistry>, config: Arc<OrchestrationConfig>) -> Self`
4. Implement `select_model(&self, stage: &WorkStage, work_type: Option<&str>) -> Result<&ModelProfile, OrchestratorError>`:
   - Step 1: Look up `stage` in `config.routing` -- if found, check `work_type_overrides` for match
   - Step 2: If work_type override found, look up the model in registry -- return it
   - Step 3: If no work_type override, use stage routing's `default_model` -- look up in registry
   - Step 4: If no stage routing exists, use `config.default_model` -- look up in registry
   - Return `OrchestratorError::ModelNotFound` if any referenced model is missing from registry
5. Implement `explain_selection(&self, stage: &WorkStage, work_type: Option<&str>) -> String`:
   - Return a structured explanation: "Stage: WsDev, WorkType: FEAT -> Model: codex-cli (matched: work_type override for FEAT on WS-DEV)"
   - Or: "Stage: WsRev, WorkType: None -> Model: claude-opus (matched: stage default for WS-REV)"
   - Or: "Stage: WsTest, WorkType: TEST -> Model: claude-sonnet (matched: global default -- no stage routing for WS-TEST)"
6. Verify `StageRouter` is `Send + Sync` via compile-time assertion: `fn _assert_send_sync() { fn assert<T: Send + Sync>() {} assert::<StageRouter>(); }`
7. Add module to `orchestrator/mod.rs` re-exports
8. Write tests:
   - Work-type override takes precedence over stage default
   - Stage default takes precedence over global default
   - Global default used when no stage routing exists
   - ModelNotFound error when referenced model missing
   - Determinism: same inputs -> same output (proptest)
   - Send + Sync compile-time check
   - Insta snapshots of explain_selection outputs

## Notes

- The router uses `Arc` references to registry and config for thread-safe sharing
- `work_type` parameter is `Option<&str>` to handle cases where work type is unknown at routing time
- The `explain_selection` output is designed for both human debugging and machine parsing by the CLI `config --show` command
- Precedence system mirrors the product-strategy.md description: "task override > work_type override > stage default > global default" -- task override is handled at the CLI command level, not in the router itself
