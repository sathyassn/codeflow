# INF-TSK-026-007: Response Normalization and Completion Detection

## Description

Implement the response normalization layer that converts raw model CLI output into structured `ModelResponse` values. Different model CLIs produce different output formats: Claude Code uses `STAGE-COMPLETE` markers, Codex CLI exits when done, Ollama returns to its prompt. The normalizer provides a unified interface that abstracts these differences.

The `CompletionDetector` scans the output stream in real-time (either from T1 stdout or T3 PTY events) to detect when a model has finished its work. This enables the T3 executor's polling loop to know when to stop. Built-in completion patterns are provided for Claude, Codex, and Ollama, with a regex-based custom pattern for user-defined models.

## Approach

1. Create `response.rs` in `codeflow-rs/codeflow-core/src/orchestrator/`
2. Define `ResponseNormalizer` trait:
   ```rust
   pub trait ResponseNormalizer: Send + Sync {
       fn normalize(&self, raw_output: &str, profile: &ModelProfile) -> ModelResponse;
       fn detect_completion(&self, output_chunk: &str) -> bool;
       fn detect_error(&self, output_chunk: &str) -> Option<String>;
   }
   ```
3. Define `NormalizerError` enum:
   - `PatternCompile { pattern: String, source: regex::Error }` -- regex compilation failed
   - `UnrecognizedModel { model_id: ModelId }` -- no normalizer for model type
4. Implement `ClaudeNormalizer`:
   - Completion: looks for `STAGE-COMPLETE:` pattern in output
   - Error: detects "rate limit", "overloaded", "authentication" patterns
   - Token estimate: characters / 4 (approximate for Claude)
5. Implement `CodexNormalizer`:
   - Completion: detects CLI exit (for T1) or prompt return pattern (for T3)
   - Error: detects "Error:", "Permission denied", "API key" patterns
   - Token estimate: characters / 4
6. Implement `OllamaNormalizer`:
   - Completion: detects return to `>>>` prompt
   - Error: detects "error", "model not found" patterns
   - Token estimate: characters / 4 (varies by model)
7. Implement `CustomNormalizer`:
   - Takes a compiled `regex::Regex` from `ModelProfile.completion_pattern`
   - Completion: regex match against output
   - Error: no built-in error detection (returns None)
   - Token estimate: characters / 4
8. Define `CompletionDetector` struct:
   - `normalizer: Box<dyn ResponseNormalizer>` -- the active normalizer
   - `accumulated_output: String` -- buffer for incremental output
   - `fn feed(&mut self, chunk: &str) -> bool` -- append chunk, check completion
   - `fn has_error(&self) -> Option<String>` -- check accumulated output for errors
9. Implement `NormalizerFactory::create(profile: &ModelProfile) -> Result<Box<dyn ResponseNormalizer>, NormalizerError>`:
   - Match `profile.api_type`:
     - `ClaudeSubagent` -> `ClaudeNormalizer`
     - `ExternalCli` -> select based on `profile.cli_command`: "codex" -> `CodexNormalizer`, else `CustomNormalizer`
     - `LocalCli` -> `OllamaNormalizer` if "ollama", else `CustomNormalizer`
   - If `profile.completion_pattern` is Some, always use `CustomNormalizer` with that pattern
10. Add module to `orchestrator/mod.rs` re-exports
11. Write tests:
    - Claude normalizer detects STAGE-COMPLETE
    - Codex normalizer detects CLI exit
    - Ollama normalizer detects prompt return
    - Custom normalizer with user regex
    - CompletionDetector feed/accumulate flow
    - Error detection for rate limit patterns
    - Token count estimation
    - Insta snapshots of normalized outputs

## Notes

- Estimate differs from product-strategy.md (L -> M) because the ResponseNormalizer trait and built-in normalizers follow well-established patterns (trait + factory), and the completion detection logic is largely regex-based with known patterns. The scope is narrower than initially estimated.
- Token counting is approximate (chars/4) -- exact token counting requires model-specific tokenizers which are out of scope
- The `NormalizerFactory` pattern allows adding new model normalizers without modifying existing code
- `completion_pattern` in ModelProfile takes precedence over built-in normalizer detection
- Error detection is best-effort -- it catches common patterns but cannot detect all possible error conditions
- The `CompletionDetector.feed()` pattern supports incremental output from PTY streams without buffering the entire output in memory
