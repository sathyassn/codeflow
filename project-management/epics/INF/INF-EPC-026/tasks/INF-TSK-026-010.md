# INF-TSK-026-010: Model Session Tracking in SurrealDB

## Description

Extend the SurrealDB `active_work` table with model orchestration fields and implement a `ModelSessionStore` for tracking model session lifecycles. This enables querying which models handled which work stages, how long they took, how many tokens they consumed, and what they cost.

The `ModelSessionStore` provides CRUD operations that map directly to the session lifecycle: create when a session starts, update as it progresses, complete when it finishes. All operations go through the `SurrealStore` trait established in Epic 0, ensuring consistency with the rest of the data layer.

## Approach

1. Create `store.rs` in `codeflow-rs/codeflow-core/src/orchestrator/`
2. Define the schema extension for `active_work` table in SurrealQL:
   ```sql
   DEFINE FIELD model ON active_work TYPE option<string>;
   DEFINE FIELD model_profile ON active_work TYPE option<string>;
   DEFINE FIELD execution_tier ON active_work TYPE option<string>;
   DEFINE FIELD cost_estimate ON active_work TYPE option<float>;
   DEFINE FIELD tokens_used ON active_work TYPE option<int>;
   DEFINE FIELD completion_marker ON active_work TYPE option<string>;
   ```
3. Define `ModelSessionRecord` struct (maps to extended `active_work` rows):
   - `id: String` -- SurrealDB record ID
   - `session_id: ModelSessionId`
   - `task_id: Option<String>` -- linked task if applicable
   - `model: ModelId`
   - `model_profile: String` -- profile name for display
   - `execution_tier: ExecutionTier`
   - `stage: Option<WorkStage>` -- which work stage this session serves
   - `status: ExecutionStatus`
   - `cost_estimate: f64`
   - `tokens_used: u64`
   - `completion_marker: Option<String>`
   - `started_at: DateTime`
   - `completed_at: Option<DateTime>`
   - `duration: Option<Duration>`
4. Define `SessionFilter` struct for query filtering:
   - `model: Option<ModelId>` -- filter by model
   - `stage: Option<WorkStage>` -- filter by stage
   - `tier: Option<ExecutionTier>` -- filter by tier
   - `since: Option<DateTime>` -- filter by start date
   - `status: Option<ExecutionStatus>` -- filter by status
5. Define `ModelSessionStore` struct with a reference to the SurrealDB connection
6. Implement `ModelSessionStore::create_session`:
   - Insert a new `active_work` record with type `model_session`
   - Set `model`, `model_profile`, `execution_tier`, initial `status = Running`
   - Return the created record ID
7. Implement `ModelSessionStore::update_session`:
   - Update `status`, `tokens_used` fields on the existing record
8. Implement `ModelSessionStore::complete_session`:
   - Set `status = Completed`, `completed_at`, `duration`, `tokens_used`, `cost_estimate`
9. Implement `ModelSessionStore::get_active_sessions`:
   - SurrealQL: `SELECT * FROM active_work WHERE type = 'model_session' AND status = 'running'`
10. Implement `ModelSessionStore::get_session_history`:
    - Build SurrealQL query with optional WHERE clauses from `SessionFilter`
    - Order by `started_at DESC`
11. Add module to `orchestrator/mod.rs` re-exports
12. Write tests:
    - Create session, verify it appears in active sessions
    - Update session tokens, verify updated values
    - Complete session, verify it no longer appears in active but appears in history
    - Filter history by model, stage, date range
    - Schema validation: required fields are set on create

## Notes

- Estimate differs from product-strategy.md (S -> M) because extending the SurrealDB schema requires careful backward-compatible field additions, a full CRUD implementation with typed query builders, and comprehensive filter logic for `get_session_history`. The scope exceeds a Small task.
- The `active_work` table is defined in Epic C Task 005 (Global SurrealDB Instance); this task extends it with model-specific fields
- All new fields are `option<T>` (nullable) to maintain backward compatibility with existing active_work records
- `type = 'model_session'` distinguishes orchestrator sessions from other active_work types (e.g., autorun workers)
- Session records follow the same pattern as the archived cf-model-orchestrator skill's `active_work` table usage
- The `completion_marker` field stores the detected completion marker text for audit/debugging purposes
