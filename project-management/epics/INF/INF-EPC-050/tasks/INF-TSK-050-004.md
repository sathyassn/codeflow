# INF-TSK-050-004: Tier-B Autorun Worker Robustness Fixes

## Description

Tier-B delivery from the EPC-050 follow-up audit
(`project-management/epics/INF/INF-EPC-050/analysis/2026-05-03-autorun-interactive-comprehensive-audit.md`,
sections 3.1 through 3.5).

The autorun worker has five hidden failure modes that swallow errors
silently or report task success when the underlying operation failed.
Each is a `let _` or a fall-through path that masks a real problem from
both the operator (autorun status reports completed for a task that
never merged) and from the orchestrator (worker continues running after
a CREATE that should have failed it).

This task replaces each silent-failure path with the appropriate
escalation: SIGKILL on tmux failure, retry-with-backoff on claim release,
non-zero exit on protected-branch merge failure, hard failure on DB
CREATE failure, and a pre-`gh pr create` conflict check so we never
create a PR for a known-conflicting branch.

## Background / Context

See `project-management/epics/INF/INF-EPC-050/analysis/2026-05-03-autorun-interactive-comprehensive-audit.md`
sections 3.1 through 3.5 for per-bug root cause and citations.

This task depends on TSK-050-003 (Tier-A) merging first because:

- The chokepoint world established by TSK-050-003 is the basis for the
  worker's exit semantics (non-zero exit_code is what the chokepoint-
  driven status display uses to render Failed).
- The DB retry-with-backoff helper added by TSK-050-003 AC-12 is the
  same pattern used in AC-04 here for the pre-CREATE retry decision.
  Sequencing avoids two parallel patterns.

**Expected Outcome:** Operator never sees a worker reported as
"completed" when the underlying operation failed. tmux daemon crash no
longer leaves orphan claude processes. Claim contention no longer
leaves stale claims that block successor workers. Protected-branch hook
blocks (e.g., `gh pr merge` rejected by branch protection) cause the
task to fail visibly so the operator can intervene. DB transient errors
fail the worker fast rather than letting it run silently without a DB
row.

**Deployment:** PR merge to main on a `fix/inf-tsk-050-004-*` branch.
Validation: a manual test on a branch with intentional conflicts must
fail fast with `merge_conflict` status; a manual test killing the tmux
session out-of-band must result in the orphan claude process being
SIGKILL'd within seconds.

> Populated by cf-development before STAGE-COMPLETE: WS-DEV

**Implementation Summary:**

Tier-B autorun worker robustness — five hidden silent-failure modes hardened. Each `let _` or eprintln-and-continue path was replaced with the appropriate escalation:

- **AC-01 (tmux SIGKILL escalation):** Added `resolve_tmux_pane_pid`, `sigkill_pid`, and `escalate_tmux_kill_to_sigkill` helpers in `worker.rs`. The post-cleanup tmux kill site (worker.rs ~2050) now logs failures and falls back to SIGKILL on the orphan claude PID (validated via `session::process::is_process_named("claude")` to defeat PID-recycle).
- **AC-02 (claim release retry):** Added `release_all_with_retry` in `claims.rs` with 3 attempts and 500ms/1.5s backoff. The worker shutdown wraps the full `locked_binary_rmw` + `release_all` cycle in this retry; the inner `release_all` Result is now surfaced to the retry loop instead of being discarded.
- **AC-03 (protected-branch merge failure → task FAILED):** Introduced `serialized_merge_failure: Option<(String, String)>` tracker. When `serialized_merge` returns `MergeConflict`/`CiFailed`/`QueueTimeout`/`CiTimeout`, the worker_result (built from Claude exit_code) is overridden: status → "failed"/"timeout", exit_code → 1, error appended.
- **AC-04 (DB CREATE failures fail worker):** Replaced `if let Err(e) { eprintln; }` for `create_autorun_worker` and `create_autorun_task_run` with `return Err(WorkerFailed)`. Worktree cleanup runs before propagation so the pool isn't leaked.
- **AC-05 (`check_merge_conflicts` pre-PR-merge gate):** The existing `resolve_merge_conflicts` call already runs before `serialized_merge` (and thus before any `gh pr merge`). Strengthened the comment block to document the contract; verified via integration tests that `MergeConflictAction::MergeConflict` returns the `merge_conflict` worker status without entering `serialized_merge`.

Key design decisions:

1. **PID-name validation guard on SIGKILL** (Tier 1): chose to gate SIGKILL on `is_process_named(pid, "claude")` rather than blindly killing `pane_pid`. Without this, a tmux kill failure followed by PID-recycle would let us SIGKILL an unrelated process. Same chokepoint pattern as `validate_claude_pid` elsewhere.
2. **`release_all_with_retry` accepts a closure** (Tier 2): the helper takes `FnMut() -> Result<(), E>` so callers can encapsulate their locking strategy. Lets the worker keep `locked_binary_rmw` around the operation while the retry layer is generic. Tradeoff: callers must remember to wrap their lock; documented in the helper's rustdoc.
3. **AC-03 override applied AFTER Claude classification** (Tier 1): the worker_result first runs through `classify_invoke_outcome` (gives us proper W1 timeout-on-origin handling), then `serialized_merge_failure` overrides the result. This preserves existing W1 behavior while making merge failures visible.
4. **AC-05 already implemented** (Tier 2): verified the existing pre-`serialized_merge` `resolve_merge_conflicts` call satisfies the AC contract. Added comment block explaining the order-of-execution contract; no behavioral change beyond strengthening tests for the no-PR-merge guarantee.

**Pre-merge rework (2026-05-05):**

Two small fixes addressed pre-merge after team-lead review identified residual gaps:

1. **AC-02 schedule alignment with literal AC text.** `RELEASE_ALL_RETRY_DELAYS` extended from `[500ms, 1.5s]` (2 elements -> 3 attempts, ~2s worst case) to `[500ms, 1.5s, 4.5s]` (3 elements -> 4 attempts, ~6.5s worst case). The earlier interpretation traded literal AC adherence for staying under the 5s sync-daemon poll cadence; that was over-engineered. One missed sync poll on shutdown is acceptable, and the AC text "3 attempts, 500ms / 1.5s / 4.5s" naturally reads as 3 inter-attempt sleeps (i.e., 4 total attempts). Updated `claims.rs` schedule constant + rustdoc + test names: `release_retry_succeeds_on_third_attempt` retained as a partial-success boundary check, and a new `release_retry_succeeds_on_fourth_attempt` verifies the helper exhausts the full schedule when failures persist. `release_retry_delays_constant` and `worker.rs::test_release_all_with_retry_constants` now anchor each of the 3 schedule slots so any future shrinkage produces a deliberate diff. Worst-case wall-clock wait before surfacing the final error is now ~6.5s plus the four CRDT-write attempts themselves.

2. **AC-03 W1 relationship documented.** Expanded the `serialized_merge_failure` override comment block in `worker.rs` (around line 2411) to explicitly document the interaction with the W1 path (exit_code=124 + branch-on-origin -> "completed-with-warning") in `classify_invoke_outcome`. The override fires AFTER classification and only when `serialized_merge_failure` is `Some` -- so W1's "completed-with-warning" is preserved when no merge was attempted (e.g., `integration_auto_merge=false`), and correctly clobbered to "failed/timeout" when a merge was attempted but failed (CI flake, hook block, queue timeout). Future readers shouldn't need to worry about this clobbering an intentionally-warned successful path.

After this rework: worker.rs coverage holds at >=79.55% (no test deletions; one new test added for the 4th attempt path), claims.rs holds at >=96.45%. 20 claims tests + 135 worker tests pass. cargo fmt, clippy, build all clean.
