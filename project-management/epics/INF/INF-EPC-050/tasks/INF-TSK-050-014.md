# INF-TSK-050-014: Fix worktree session latch bug

> **MANDATORY VALIDATION:** Files created from this template MUST be validated against the task validation command before committing:
> `codeflow validate task <file-path>`
> Fix all errors (exit code 1) before requesting a commit. Warnings are advisory.

## Description

A race condition in the SessionStart / teammate-spawn handlers causes
a Claude teammate process to be misclassified as a "new lead", which
in turn creates a duplicate worktree for the same logical session.

The failure sequence (verified live in current code 2026-05-07):

1. Lead SessionStart fires; `pathflow-session-status.json` written
   with `lead_pid`. `pathflow-team.json` does NOT exist yet because
   `TeamCreate` has not been called.
2. Lead spawns first teammate (e.g. cf-security). PostToolUse hook
   calls `handle_teammate_spawn`. `team_file_path.exists()` returns
   false. Function silently returns `Ok(HookOutput::Allow)` at
   `post_tool_use.rs:802-806`. **The teammate's entry is NEVER added
   to `pathflow-team.json` because the file was never created.**
3. Some time later (minutes to hours), a second teammate (e.g.
   cf-documentation) fires its SessionStart. `handle_stale_cleanup`
   reads `pathflow-team.json`. The file does not exist;
   `locked_read_critical` returns `Err(_)`. The fallback at
   `session_start.rs:948` is `0` (no pending tmux spawns).
4. The classification logic at `session_start.rs:951-961` then takes
   the `else` branch: `(None, false, None)` — **NEW LEAD MODE**, even
   though the actual lead is still alive.
5. Downstream code in `run()` creates a second worktree. Two
   worktrees now exist for the same logical session, with diverging
   work, branch state, and (eventually) merge conflicts.

The fix has three layers, applied together to defeat the race
across both the writer (post_tool_use) and the reader
(session_start) paths.

## Approach

1. **Layer 1 (post_tool_use.rs `handle_teammate_spawn`):**
   replace the bare `return Ok(HookOutput::Allow)` at lines
   802-806 with a fall-through that builds an initial
   `PathflowTeamInfo` (matching the schema written by
   `handle_team_create`), calls `atomic_write_file`, and then
   continues into the `locked_rmw` block. The team_name comes
   from `resolve_team_name_from_session_dir` (lookup helper —
   read team config; fall back to "" if absent).
2. **Layer 2 (session_start.rs `handle_stale_cleanup`):**
   restructure the read-and-classify block at lines 928-961.
   When `locked_read_critical` returns `Err(_)`:
   a) check `pathflow-session-status.json` exists and has
      `lead_pid` matching a live claude process via
      `liveness::validate_claude_pid`;
   b) if yes → return `(Some(existing_sid), true, env_worktree_path)`
      (TEAMMATE MODE, fallback);
   c) if no → return `(None, false, None)` (NEW LEAD).
   The existing pending_tmux_count==0 path keeps its current
   behavior because that case represents a healthy team file
   with no pending spawns — a different signal from "team file
   unreadable".
3. **Layer 3 (post_tool_use.rs):** Layer 1's `atomic_write_file`
   error already returns `HookError::Io`; ensure the error message
   includes the target path and the failure reason so an operator
   can tell apart a permission failure from a disk-full failure.
4. **Tests:**
   - AC-04 / AC-05 / AC-06 — inline tests in `session_start.rs`
     using existing fixtures (see lines 3346-3450).
   - AC-01 / AC-03 — inline tests in `post_tool_use.rs` extending
     the `test_handle_teammate_spawn_no_team_file` (currently at
     line 1915) to assert the file is now CREATED, not skipped.
   - AC-07 — new integration test in
     `codeflow-cli/core/tests/worktree_session_latch.rs`.

| `pathflow-team.json` | concurrent read by SessionStart, write by PostToolUse, read-modify-write by handle_teammate_spawn | `atomic_write_file` for first write (Layer 1); `locked_rmw` for subsequent updates (existing) |

| Worktree registry | unaffected by this fix | Existing `WorktreeRegistry::locked_register_with_limit` |

The race window is between (a) the lead's first teammate spawn and
(b) any concurrent teammate's SessionStart. Layer 1 closes the gap
on the writer side (file always exists after the first spawn);
Layer 2 closes it on the reader side (alive-lead-with-no-team-file
implies TEAMMATE MODE, never NEW LEAD).

## Stage Reports

### DEV Report

> Populated by cf-development before STAGE-COMPLETE: WS-DEV

**Implementation Summary:**

Three-layer defense-in-depth fix for the worktree session latch bug:

- **Layer 1 (writer side)** — `post_tool_use.rs::handle_teammate_spawn` now creates `pathflow-team.json` when missing instead of returning `Ok(HookOutput::Allow)` silently. The file is written via the existing `atomic_write_file` (tmp + rename) with a `PathflowTeamInfo` schema-compatible with `handle_team_create`'s write. `codeflow_session_id` is derived from the session_dir parent's basename; `team_name` is read from `pathflow-session-status.json` if the lead has already written it (otherwise empty — a later `handle_team_create` overwrites it). After Layer 1 writes the file, control falls through to the existing `locked_rmw` block that adds the new teammate entry.

- **Layer 2 (reader side)** — `session_start.rs::handle_stale_cleanup` no longer falls through to `pending_tmux_count=0 → NEW LEAD` when `locked_read_critical` returns `Err(_)`. By the time the team-file read happens, the lead has already been verified alive via `liveness::is_session_alive` (line 906-913 returns NEW LEAD if dead). When the team file is unreadable AND lead alive AND a session config dir exists (implicit — we just read `pathflow-session-status.json` from the same dir), classify as TEAMMATE MODE: `(Some(existing_sid), true, env_worktree_path)`. This closes the race even if Layer 1 fails or hasn't fired yet (defense-in-depth).

- **Layer 3 (loud failure)** — Layer 1's write failure path returns `HookError::Config` with a message naming the target path and the OS error reason (wrapped via `map_err` around the existing `atomic_write_file` and `create_dir_all` calls). The previous bare `Ok(HookOutput::Allow)` swallowed write failures; the new path surfaces them so the operator can distinguish a permission failure from a disk-full failure.

Key design decisions:

1. **Schema compatibility with handle_team_create:** Layer 1 constructs the same `PathflowTeamInfo` struct fields. If TeamCreate fires later, it overwrites with the canonical team_name and resets `teammates: vec![]` — the next teammate spawn re-adds the entry on top of the empty array. This is intentional and called out in the task ACs ("idempotent semantics required").

2. **Liveness chokepoint reuse:** Layer 2 doesn't add a new helper; it consumes the existing `liveness::is_session_alive` check at line 907 (already present pre-fix) and just changes the downstream classification when the team file is unreadable.

3. **No new state files, no new sentinels:** Only `pathflow-team.json` (the existing file) is touched.

4. **Defense-in-depth:** Layer 1 alone would close the bug, but Layer 2 hardens the reader path against future regressions (e.g., a permission failure that prevents Layer 1 from writing) and against operational interventions (manual `rm pathflow-team.json` while the session is live).

### Iteration 2 — flake fix

**Trigger:** Team lead expanded `file_scope` to include `codeflow-cli/core/src/autorun/worker.rs` and directed cf-development to root-cause and fix the baseline failure so AC-09 becomes truly DONE.

**Root cause:** `resolve_tmux_pane_pid("")` was the failing call site. On macOS when `cargo test` runs inside an attached tmux session, `tmux list-panes -t ""` does NOT return a non-zero exit code — instead tmux interprets the empty target as "the current session" and returns the pane PID of the host shell (verified empirically: `tmux list-panes -t "" -F '#{pane_pid}'` returned `24809` with exit 0 in the test environment). Pre-fix the function then returned `Some(24809)` and the test's `assert!(pid.is_none())` panicked. Outside a tmux session (and inside the sandbox where tmux can't connect to its socket) the function returned `None` and the test passed — explaining why this only failed inside attached tmux on macOS.

**Risk this represented for production:** The single production caller at `worker.rs:2206` passes `tmux_name` (the autorun session's tmux name) into `escalate_tmux_kill_to_sigkill`, which calls `resolve_tmux_pane_pid` and then `sigkill_pid` if it returns a non-zero PID. If `tmux_name` is ever an empty string at runtime (e.g., a future upstream bug), the SIGKILL would target the host's current tmux pane PID — killing the user's session. The defensive boundary fix forecloses that class of incident even if the upstream bug appears later.

**Fix:** Add `if session_name.is_empty() { return None; }` as the first statement of `resolve_tmux_pane_pid` (`worker.rs:146`). Update the test comment to document why the boundary check is the correct fix rather than a test patch.
