# INF-TSK-050-014: Fix worktree session latch bug

> **MANDATORY VALIDATION:** Files created from this template MUST be validated against the task validation command before committing:
> `codeflow validate task <file-path>`
> Fix all errors (exit code 1) before requesting a commit. Warnings are advisory.

## Description

A race condition in the SessionStart / teammate-spawn handlers causes
a Claude teammate process to be misclassified as a "new lead", which
in turn creates a duplicate worktree for the same logical session.

The failure sequence (verified live in current code 2026-05-07):

1. Lead SessionStart fires; `pathflow-session-status.json` written
   with `lead_pid`. `pathflow-team.json` does NOT exist yet because
   `TeamCreate` has not been called.
2. Lead spawns first teammate (e.g. cf-security). PostToolUse hook
   calls `handle_teammate_spawn`. `team_file_path.exists()` returns
   false. Function silently returns `Ok(HookOutput::Allow)` at
   `post_tool_use.rs:802-806`. **The teammate's entry is NEVER added
   to `pathflow-team.json` because the file was never created.**
3. Some time later (minutes to hours), a second teammate (e.g.
   cf-documentation) fires its SessionStart. `handle_stale_cleanup`
   reads `pathflow-team.json`. The file does not exist;
   `locked_read_critical` returns `Err(_)`. The fallback at
   `session_start.rs:948` is `0` (no pending tmux spawns).
4. The classification logic at `session_start.rs:951-961` then takes
   the `else` branch: `(None, false, None)` — **NEW LEAD MODE**, even
   though the actual lead is still alive.
5. Downstream code in `run()` creates a second worktree. Two
   worktrees now exist for the same logical session, with diverging
   work, branch state, and (eventually) merge conflicts.

The fix has three layers, applied together to defeat the race
across both the writer (post_tool_use) and the reader
(session_start) paths.

## Approach

1. **Layer 1 (post_tool_use.rs `handle_teammate_spawn`):**
   replace the bare `return Ok(HookOutput::Allow)` at lines
   802-806 with a fall-through that builds an initial
   `PathflowTeamInfo` (matching the schema written by
   `handle_team_create`), calls `atomic_write_file`, and then
   continues into the `locked_rmw` block. The team_name comes
   from `resolve_team_name_from_session_dir` (lookup helper —
   read team config; fall back to "" if absent).
2. **Layer 2 (session_start.rs `handle_stale_cleanup`):**
   restructure the read-and-classify block at lines 928-961.
   When `locked_read_critical` returns `Err(_)`:
   a) check `pathflow-session-status.json` exists and has
      `lead_pid` matching a live claude process via
      `liveness::validate_claude_pid`;
   b) if yes → return `(Some(existing_sid), true, env_worktree_path)`
      (TEAMMATE MODE, fallback);
   c) if no → return `(None, false, None)` (NEW LEAD).
   The existing pending_tmux_count==0 path keeps its current
   behavior because that case represents a healthy team file
   with no pending spawns — a different signal from "team file
   unreadable".
3. **Layer 3 (post_tool_use.rs):** Layer 1's `atomic_write_file`
   error already returns `HookError::Io`; ensure the error message
   includes the target path and the failure reason so an operator
   can tell apart a permission failure from a disk-full failure.
4. **Tests:**
   - AC-04 / AC-05 / AC-06 — inline tests in `session_start.rs`
     using existing fixtures (see lines 3346-3450).
   - AC-01 / AC-03 — inline tests in `post_tool_use.rs` extending
     the `test_handle_teammate_spawn_no_team_file` (currently at
     line 1915) to assert the file is now CREATED, not skipped.
   - AC-07 — new integration test in
     `codeflow-cli/core/tests/worktree_session_latch.rs`.

## Concurrency Considerations

| Shared Resource | Access Pattern | Safety Mechanism |
|----------------|---------------|-----------------|
| `pathflow-team.json` | concurrent read by SessionStart, write by PostToolUse, read-modify-write by handle_teammate_spawn | `atomic_write_file` for first write (Layer 1); `locked_rmw` for subsequent updates (existing) |
| `pathflow-session-status.json` | read-only in Layer 2 fallback | None needed (read-after-write semantics on the file system; status file is written by lead's SessionStart before any teammate fires) |
| Worktree registry | unaffected by this fix | Existing `WorktreeRegistry::locked_register_with_limit` |

The race window is between (a) the lead's first teammate spawn and
(b) any concurrent teammate's SessionStart. Layer 1 closes the gap
on the writer side (file always exists after the first spawn);
Layer 2 closes it on the reader side (alive-lead-with-no-team-file
implies TEAMMATE MODE, never NEW LEAD).

## Notes

This is a HIGH-priority fix because it directly causes data loss (work
diverging into a duplicate worktree, requiring manual cleanup).
The bug is currently live as of 2026-05-07; the 3-layer fix
documented in `project_pid_detection_audit.md` is the verified design.

The implementer should NOT consolidate Layer 1 and Layer 2 into a
single layer — defense-in-depth is the design choice. If a future
edit re-introduces the silent-return at the writer side, Layer 2
catches it on the reader side, and vice versa.

`scope_policy=hard` is set because both modified files are critical
infrastructure shared with every session lifecycle; an out-of-scope
edit (e.g. accidentally touching `worktree/registry.rs`) could
introduce a subtle ordering bug that is invisible in single-session
testing.
