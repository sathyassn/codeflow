### PLAN Report

> Populated by cf-planning before STAGE-COMPLETE: WS-PLAN

**Design Decisions:**

1. **Tiered task decomposition (A/B/C)** -- The 28 follow-up findings split naturally into three tiers: Tier-A (user-blocking correctness, 15 items, FIX work_type), Tier-B (robustness / hidden failure modes, 5+1 items, FIX), Tier-C (open design questions requiring discussion, 7 items, SPKE). Splitting by remediation type rather than by subsystem keeps each task's pipeline (FIX vs. SPKE) consistent and scopes Tier-A to a single PR-sized effort even though it touches many files. Alternative considered: split by subsystem (autorun vs. interactive). Rejected because the chokepoint discipline migration spans both subsystems and would create coordination friction across subsystem-boundary tasks.

2. **Tier-A scope_policy = `hard`** -- 12 of the 15 Tier-A items share a single root cause (chokepoint bypassed by `cli/cmd/autorun.rs` and `cli/cmd/interactive.rs`). Strict scope_policy prevents the implementer from drifting into adjacent files and ensures the migration stays focused. The file_scope list is exhaustive for the AC set; no out-of-scope edits should be needed.

3. **Tier-A approach = 6 staged commits** -- Each stage (infrastructure → migration → heartbeat removal → worker hardening → doctor+gate → TUI tests) ships one commit. cf-review verifies per-stage. This avoids a single mega-commit that is hard to review or roll back, and ensures the lint guard from Stage 0 is in place BEFORE the chokepoint migration in Stage 1, so any regression is caught.

4. **Audit doc as the single source of truth** -- All three follow-up tasks reference the analysis doc rather than duplicating the per-bug root cause. This avoids drift between task definitions and the audit, and lets the implementer fix audit inaccuracies in one place.

5. **Tier-C design-only scope** -- Tier-C explicitly produces NO code. Each ADR/note reserves a placeholder follow-up ticket ID (INF-TSK-050-006 through INF-TSK-050-012) so future work has a clear handoff. Alternative considered: combine ADR + implementation in single tickets. Rejected because the design questions are non-obvious and require discussion -- merging design and implementation incentivizes premature commitment.

6. **Co-locate decisions in epic directory** -- ADRs and design notes live at `project-management/epics/INF/INF-EPC-050/decisions/` rather than the project-wide `.codeflow/docs/`. Reasoning: these decisions are scoped to EPC-050 follow-up; they may not have global impact. If any of them turns out to be project-wide, it can be promoted to `.codeflow/docs/` later.

**Alternatives considered:**

- **Single FIX task for all 21 fix items** (Tier-A + Tier-B combined): rejected. ~2200 LOC is too large for one PR; reviewer fatigue. Splitting at the chokepoint-discipline boundary (A vs. B) keeps each PR digestible.
- **Skip the audit doc; embed root cause inline in each task**: rejected. Tasks repeat the same 28 root-causes 3+ times. Audit doc is the single source of truth.
- **Defer Tier-C to a future planning session**: rejected. The design questions surfaced now are forgotten in a month. Capturing them while context is fresh prevents re-investigation later.
