# EPC-026: the capabilities catalog

## Summary

CodeFlow's capability catalog is one Markdown file with YAML fences that agents update by habit, not by rule. The operator asked on 2026-11-01 for a catalog that covers user-facing, internal and technical capabilities, classifies each by facets, stays current because every pull request must say which capability it adds, changes or improves, and works with versioning and the changelog. This epic builds it for CodeFlow and for adopters. It also offers every adopting project a bootstrap epic that builds a comprehensive initial catalog, with step-by-step docs, and CodeFlow runs that same flow on itself. It is done when CodeFlow's own catalog is migrated, comprehensive, reviewed and complete, and the check blocks on CodeFlow's own pull requests.

Decisions of 2026-11-01 (operator, relayed by the Director): the per-pull-request capability impact check is approved as proposed, and the tier scope is option B: standard and full get the catalog with the check at `warn`, minimal is `off` by default and opts in with one key. CodeFlow's own policy uses `block`. The design is revision 5 of the capabilities design note with its acceptance tests (workspace repository, `coordination/coordinators/capabilities/`), approved by a Codex review; this epic does not copy it.

## Outcome

After this merges, an agent in any CodeFlow project can read a capability catalog of one record per capability, and every product pull request there must state which capabilities it adds, changes or improves, each with its name and a line on what changed for its users, checked by `codeflow ci`; a project that adopts CodeFlow is offered a bootstrap epic that builds its comprehensive initial catalog.

Its tasks carry rubric grades (`codeflow-agentic-2`); only tasks created on or after profile v1's effective date (2026-11-04) carry a band, and older tasks are never back-filled (second consolidation amendment, 2026-11-04).

## Acceptance Criteria

- AC-1 A capability catalog shall be one record per capability with five closed generic facets, two project facets from a vocabulary file and `area` from the project, read equally from a checkout or a tree, with unknown keys refused and the legacy file read beside it; evidence: TSK-1132.
- AC-2 Capability ids shall come from the shared registry, and `init`, `update`, `orient` and `doctor` shall show catalog coverage apart from evidence; evidence: TSK-1133.
- AC-3 `codeflow ci` shall judge each pull request's `## Capability impact` declaration against the catalog delta between the merge base and the head, under the target's policy, in both directions, refusing a missing section, an unknown or duplicate id, a `none` without a reason, an `improved` without a clause, and any entry without its capability name and one line of context on what changed for its users; evidence: TSK-1135.
- AC-4 The check shall ship at `warn` at standard and full, `off` at minimal with a one-key opt-in, preserve an explicit `block` across updates, and be explained by a harness-neutral guide with a bootstrap procedure for an existing codebase; evidence: TSK-1136.
- AC-5 `capability migrate` shall convert a legacy catalog with registration first and a verified, interruptible resume; evidence: TSK-1137, TSK-1159.
- AC-6 CodeFlow's own 17 capabilities shall be migrated with facets, `validate --docs` shall be green, an ADR shall record the change to a checked catalog, and CodeFlow's policy shall set the check to `block` once its catalog is complete, with the verdict running and required as a hosted check on `main` and the epic's line (any protection change is the operator's); evidence: TSK-1138, TSK-1148.
- AC-7 A CodeFlow changelog entry shall name the capabilities it serves and `check-pr` shall check them against the declaration, with other release backends reported as unchecked; evidence: TSK-1139.
- AC-8 The docs portal shall read the folder, the legacy file and a mixed tree, and show the catalog in the views the Visual and docs direction sets; evidence: TSK-1134 and TSK-1141 (blocked on that direction).
- AC-9 Every `verified_by` entry shall be typed and resolve to a test identity, a verification record or a declared gap; evidence: TSK-362.
- AC-10 (journey) On the final candidate: `init` at each tier; `update` of a 3.x repository with fences; `migrate`; a product pull request through scaffolded CI on GitHub, GitLab and the generic wrapper; the portal; and one non-Rust project running the bootstrap epic from the guide; evidence: the final integration run.
- AC-11 Every adopting project shall be offered a bootstrap epic with inventory, classification, evidence and review tasks that ends in a comprehensive reviewed catalog with `inventory: complete`, and a step-by-step guide shall cover each stage, what comprehensive means (user-facing, internal, technical; functional and non-functional) and when to move to `block`; evidence: TSK-1143, TSK-1144.
- AC-12 CodeFlow's own catalog shall be built through that flow into a comprehensive, evidenced, independently reviewed catalog with `inventory: complete`; evidence: TSK-1146, TSK-1148.

## Capability impact enforcement amendment (2026-11-02)

TSK-1135 (T4 of the throughput findings, approved by the Director) places the
authoritative capability impact check in the hosted `pull_request_target`
"commit standards" job, inside its existing `codeflow ci` call, and defines a
local pre-push preflight separately. AC-10 is amended (a push with no pull
request body is not refused by the local hook, since an ordinary first push
has none), and AC-12 to AC-16 add the check's constraints: immutable target,
merge-base and head identities, blob-only parsing with symlinks and
submodules refused, bounded work with duplicate identities refused, body, head
and target consistency, and the first-push, multi-ref and retarget cases. The
journey criterion AC-11 keeps its number. The graph is unchanged (v5). Each
criterion serves AC-3 as before.

Graph v5 (2026-11-02, coord/capabilities via coord/planning) adds `TSK-1133 -> TSK-1135`: the identity join from legacy entries to records reads the `Kind::Cap` registry bindings (`ids/CAP/<N>.toml`), and TSK-1133 adds `Kind::Cap` (design note D3, lines 167 to 173, `coordination/coordinators/capabilities/design-note.md`).
