# CodeFlow v3.1.0 CodeQL triage

This record holds the alert-by-alert disposition of the first CodeQL scan of
`sathyassn/codeflow` and the independent review of that disposition. It is a
companion to the [3.1.0 release record](v3.1.0.md).

The scan ran on `main` at `c941877ba96353cc64266cd7ea11700d01bb5169`, which
is not the release candidate. Code under `crates/`, `assets/` and `scripts/`
changed after it, so this triage does not qualify the candidate. The
candidate's own analysis is the pull request's CodeQL run on its final head.
This scan used the `default` query suite. The operator switched the setup to
the extended suite on 2026-10-11 (setup run 38182246438 on `main` at
`1105e53c1`); that run opened alerts 104 to 126, which this record does not
cover.

## Result

- Exploitable: 0.
- Defense in depth: 2, alerts 1 and 2 (the design kit `chrome.js`, both
  copies). The kit renders only its page author's data.
- False positive: 52.
- False positive, test-only: 49.
- The 103 alerts are still open on the host. Dismissing them is a repository
  action that has not been taken.

Each flow was read from source to sink in the scan's SARIF and judged against
CodeFlow's threat model: a local CLI; `codeflow-present`, a loopback-only
service that renders untrusted repository content (ADR-0049); and the docs
portal, whose repository content is untrusted. The triage was written by a
Claude Opus worker of the release session on 2026-10-11.

### Defense in depth: kit chrome.js (alerts 1, 2)

At `c941877ba`, both kit copies interpolate `n.kind` into HTML. Alert 1 is `assets/base/agents/skills/cf-docs-portal/resources/design-system/chrome.js:1260`. That flow is real for whoever authors the HTML page. Repository content does not reach it in the shipped product.

- `git grep chrome.js c941877ba -- crates/codeflow-present` is empty. The present service renders repository text through `escape_html_to` (`crates/codeflow-present/src/render.rs:1288`, call sites including :71, :155, :201, :211, :415). Its page CSP is `script-src 'self'` plus the prepaint hash (`service.rs:584-585`).
- The docs portal loads `portal-chrome.js`, a different file. It parses `#cf-data` only when that element exists (`docs-portal/public/portal-chrome.js:584`). Product portal pages do not emit it. `view.recent = data.recent || []` (`portal-chrome.js:340`) stays empty without that element.
- Inside an as-is region, a raw HTML node is replaced with a text node (`docs-portal/scripts/as-is-markdown.mjs:64-65`). On the repository rewrite path, an HTML node is passed through `escapeGeneratedHtml` (`docs-portal/scripts/lib.mjs:126-128`). A Markdown file cannot plant `#cf-data` or a script.
- Local kit notes assign `kind` only as the literals `'text'`, `'element'`, and `'area'` (chrome.js:935, :946, :958). The unescaped local kicker at chrome.js:1132 therefore carries one of those three words. The heading-id interpolation at chrome.js:694 is the same pattern as the portal TOC and is covered by the fix below.

An attacker who can already replace the kit HTML can write a `<script>` tag directly. The unescaped `n.kind` does not add a path from repository content, from another origin, or from the present service. Defense-in-depth is the right class.

#### Request checks against a hostile page or a local process

Mutations require the session cookie by constant-time compare (`service.rs:1026-1032`), `Origin` equal to `http://{authority}` (`service.rs:1041-1051`), header `x-cf-present: 1` (`service.rs:1053-1061`), and `Content-Type: application/json` (`service.rs:1063-1071`). A process on the same machine can open the loopback port and set Host, Origin, and the custom header. ### Docs portal

#### URL scheme (alerts 27, 28)

`pageScriptFailures` treats a URL as a script URL only when, after a whitespace strip, it starts with `javascript:` (`browser-verify.mjs:643`). The checked attributes are `href`, `src`, `action`, `formaction`, `xlink:href`, `data`, `poster`, and `background` (`:644`). The same function refuses `script` (except the expressive-code module), `iframe`, `frame`, `frameset`, `object`, `embed` (`:650-651`), declarative shadow roots (`:652`), `on*` handlers (`:654`), and `srcdoc` (`:655`).

The gate itself does not name `data:` or `vbscript:`. The renderer does. `unsafeUrl` (`lib.mjs:421-423`) strips colon entities (`&#58;`, `&#x3a;`, `&colon;`) and C0, space, and DEL characters, then rejects `javascript:`, `data:`, `file:`, and `vbscript:`. Any other scheme fails the resolver because it is not one of those four and is not a relative repository URL (the function returns true only for those four; callers throw on true at `lib.mjs:139` and `:427`). A `data:` or `vbscript:` document also has no embedding element left: those tags are refused at `browser-verify.mjs:651`. `vbscript:` has no engine in the gated Chromium, Firefox, and WebKit browsers. The incomplete attribute check is a weaker second gate. It is not an exploit path. False positive.

`javascript&#58;` becomes `javascript:` inside `unsafeUrl` and is rejected. `&#106;avascript:` does not match a scheme after the colon-entity decode, so it stays a relative path.
