# CodeFlow v3.0.0 harness parity

Status: **partly verified, not complete**. Claude Code parity is verified
against the installed harness. Codex parity is verified only from its shipped
schema and configuration loader, because the Codex sign-in on this machine had
expired and no live Codex session could run a tool. The CLI qualification on
the final head passes everywhere except the live delegate lane, which the
harness could not yet drive on this machine.

[`docs/releasing.md`](../../releasing.md) requires this re-verification before
tagging. Everything below was run on 2026-09-26 on macOS 26.6.2 arm64.

### Claude Code payload

The sample was created with `codeflow init --yes --full`. A capture hook in
`.claude/settings.local.json` recorded the raw PreToolUse stdin next to the
scaffolded `git-guard` and `exec-guard` hooks. The session ran
`echo parity-probe-allowed` in `bypassPermissions` mode.

- The payload carried `hook_event_name: PreToolUse`, `tool_name: Bash`,
  `tool_input.command`, `session_id`, `cwd` and a string `transcript_path`.
- It also carried fields the guards ignore: `effort`, `permission_mode`,
  `prompt_id`, `scratchpad_dir`, `tool_use_id` and `tool_input.description`.
- The model declined to run a force push to `main`, citing the sample's
  AGENTS.md, so the block path was proven by replay instead.

Replay of each captured payload with only `tool_input.command` changed gave
the same results with the `984519d6a` binary and with the final head binary.
A second real payload, from a read-only listing in the settings check session,
replayed identically.

| Guard | Command | Exit | Rule |
|---|---|---|---|
| git-guard | the captured `echo` | 0 | none |
| exec-guard | the captured `echo` | 0 | none |
| git-guard | `git push --force origin main` | 2 | `git.force_push_protected` |
| git-guard | `git config core.hooksPath /dev/null` | 2 | `git.hook_integrity` |

### Codex payload, events and configuration

- The Codex 0.157.1 binary embeds the `pre-tool-use.command.input` schema. It
  requires `hook_event_name` (const `PreToolUse`), `tool_name`, `tool_input`,
  `cwd`, `session_id` and a nullable `transcript_path`, the fields the guards
  read. It adds `model`, `permission_mode`, `tool_use_id`, `turn_id` and
  optional `agent_id`/`agent_type`. The binary still contains
  `Tool call blocked by PreToolUse hook`.
- A payload built to that schema, with `transcript_path: null`, `tool_name:
  Bash` and every extra field, gave the same eight replay results as the
  Claude payload.
- An interactive Codex session in the sample asked for folder trust and then
  for review of four new hooks: three PreToolUse (the two guards and the
  capture hook) and one SessionStart (`session-orient`). After trust, the
  hook view showed PreToolUse 3 of 3 and SessionStart 2 of 2 active; one
  SessionStart hook is user-level.
- The first prompt failed with "Your access token could not be refreshed".
  No tool ran, so the live payload, the hook firing and the shell tool's
  hook-facing name are not observed for 0.157.1. Signing in is the operator's
  step; CodeFlow never automates it.
- Strict loading: with the shipped `config.toml` as the only config of a
  throwaway `CODEX_HOME`, `codex --strict-config exec` started normally, and
  `codex doctor` showed approval `Never`, 16 denied-read rules and scan depth 6.
  The same file with one unknown top-level key failed with
  "unknown configuration field".

## CLI qualification

All runs below used `tests/release-qualification/qualify.sh` on macOS arm64
against the final head `e49726807`. The binary is the debug build with SHA-256
`de98f57f90ca8d7a6d564ca752fbe90adc8452095782024eee0235165e37138a`.

| Run | Harness | Passed | Failed | Unavailable |
|---|---|---|---|---|
| Interim, earlier head | `4896ec72b`, binary of `984519d6a` | 664 | 15 | 11 |
| Final head, run 1 | `a0f859b48` (`4896ec72b` plus the PR body fixture) | 683 | 1 | 6 |
| Final head, rerun C | `ccea716ca` (`cc680d50b` plus the PR body fixture) | 681 | 2 | 7 |
| Final head, run D | `8712cc3de` (`63a0cc775` plus the PR body fixture) | 681 | 2 | 7 |

The interim run found two causes. Six rows were a product defect: `codeflow
ci` blocked a fresh standard or full scaffold on dashes in the managed skill
files it had just added. That is fixed on the final head, and the rows pass.
Nine rows came from a stale harness fixture: the conforming PR body lacked
the Reviews and Release impact sections. The fixture fix is `a0f859b48` on
`fix/qualify-pr-body`, and the rows pass.

Run 1 on the final head:

- The live canary's first turn passed all four rows: ready, the live pane
  resolving `codeflow` to the candidate, accepted and terminal.
- The pipeline row failed. `codeflow delegate-turn` blocked the second turn
  with "submitted prompt does not match the armed prompt digest". That
  harness delivered a bare paste and pressed Enter. The final head's contract
  accepts a folded paste only when "Carry out the pasted instructions." is
  typed after it, so the product behaved as specified. The turn then timed
  out (exit 124), and the independent subtract test found no new code.
- Unavailable: the positive `present resolve` row, which only the browser
  review surface can produce, and the five release-boundary rows.

Rerun C used the harness that types the directive after a folded paste.
Every row before the canary passed, and so did canary startup and the live
pane binding. After sending the first canary prompt, the harness's editor check
found no current editor: the transcript reads "no current editor is visible
after the paste; no further text or keys sent". It sent no Enter, and the
prompt stayed unsent in the input box. The accepted and terminal rows failed
on their timeouts (exit 124), and the pipeline row was unavailable. The product
was not reached. The harness does not log the refused frame.

The live pane on this machine draws a status line (`main`) above the
permission footer. With a stubbed pane reader, `current_editor` at
`cc680d50b` accepts that frame, and at `63a0cc775` it refuses it, because
that harness allows exactly one footer line.

Run D used the harness Codex approved in its fourth review round of
`63a0cc775` (verdict approved, DPD-1 and DPD-2 resolved). It ended the same way. Its transcript line 17189 reads "no
current editor is visible after the paste; no further text or keys sent", and
the pane then showed the prompt unsent above the `main` status line and the
bypass-permissions footer. The accepted and terminal rows failed on their
timeouts, and the pipeline row was unavailable. Teardown closed the Herdr tab
and released every resource. In rerun C and run D the seven unavailable rows
are the positive `present resolve`, the five release-boundary rows and the
pipeline row.

The live lane is therefore not qualified on the final head. The planned fix
makes the canary's status line a fixed marker through the harness's own
settings, allows exactly that marker above the known footer, and logs every
refused frame. After Codex reviews it, the live lane runs once more.

Reduced assurance for rerun C's harness: Codex's review of its current-editor
check had an open finding, DPD-2. The check could accept history
or a trust dialog framed by two rule lines as the editor. `cc680d50b`
partly resolves it by recognising the footer through a list of known
screens. It affected ambiguous screens, not the normal path. `63a0cc775`
resolves it, but that harness has not yet passed the live lane on this
machine, so the harness stays reduced assurance until a live run passes.
