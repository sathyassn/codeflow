Status: **partly verified, not complete**. Claude Code parity is verified
against the installed harness. Codex parity is verified only from its shipped
schema and configuration loader, because the Codex sign-in on this machine had
expired and no live Codex session could run a tool. The CLI qualification on
the task-notice fix head, run G, has no failed row. It stays blocked only on
the positive `present resolve` row, which needs the browser review surface.

[`docs/releasing.md`](../../releasing.md) requires this re-verification before
tagging. Everything below was run on 2026-09-26 on macOS 26.6.2 arm64.

### Claude Code payload

The sample was created with `codeflow init --yes --full`. A capture hook in
`.claude/settings.local.json` recorded the raw PreToolUse stdin next to the
scaffolded `git-guard` and `exec-guard` hooks. The session ran
`echo parity-probe-allowed` in `bypassPermissions` mode.

- The payload carried `hook_event_name: PreToolUse`, `tool_name: Bash`,
  `tool_input.command`, `session_id`, `cwd` and a string `transcript_path`.
- It also carried fields the guards ignore: `effort`, `permission_mode`,
  `prompt_id`, `scratchpad_dir`, `tool_use_id` and `tool_input.description`.
- The model declined to run a force push to `main`, citing the sample's
  AGENTS.md, so the block path was proven by replay instead.

Replay of each captured payload with only `tool_input.command` changed gave
the same results with the `984519d6a` binary and with the final head binary.
A second real payload, from a read-only listing in the settings check session,
replayed identically.

### Codex payload, events and configuration

- The Codex 0.157.1 binary embeds the `pre-tool-use.command.input` schema. It
  requires `hook_event_name` (const `PreToolUse`), `tool_name`, `tool_input`,
  `cwd`, `session_id` and a nullable `transcript_path`, the fields the guards
  read. It adds `model`, `permission_mode`, `tool_use_id`, `turn_id` and
  optional `agent_id`/`agent_type`. The binary still contains
  `Tool call blocked by PreToolUse hook`.
- A payload built to that schema, with `transcript_path: null`, `tool_name:
  Bash` and every extra field, gave the same eight replay results as the
  Claude payload.
- An interactive Codex session in the sample asked for folder trust and then
  for review of four new hooks: three PreToolUse (the two guards and the
  capture hook) and one SessionStart (`session-orient`). After trust, the
  hook view showed PreToolUse 3 of 3 and SessionStart 2 of 2 active; one
  SessionStart hook is user-level.
- The first prompt failed with "Your access token could not be refreshed".
  No tool ran, so the live payload, the hook firing and the shell tool's
  hook-facing name are not observed for 0.157.1. Signing in is the operator's
  step; CodeFlow never automates it.
- Strict loading: with the shipped `config.toml` as the only config of a
  throwaway `CODEX_HOME`, `codex --strict-config exec` started normally, and
  `codex doctor` showed approval `Never`, 16 denied-read rules and scan depth 6.
  The same file with one unknown top-level key failed with
  "unknown configuration field".

## Where the harness lives

The qualification harness, `tests/release-qualification/`, is not part of the
3.0.0 tree. `main` and the 3.0.0 line have never carried it. It belongs to
the public docs line (EPC-014), which ships as 3.1.

- Every run above is pinned to the harness commit it used, cited by SHA. The
  latest is `37001567c` on `qualify/release-3.0.0-r7`.
- `qualify/release-3.0.0-r7` is kept, not deleted, until the 3.1 line takes
  in its harness-only commits.
- That branch also carries an earlier, unreviewed task-notice fix
  (`a56551dad`, `aa74edd83`). In 3.0.0 it is superseded by the reviewed fix
  from `fix/delegate-task-notice-3.0.0` (`588bbda67`).
