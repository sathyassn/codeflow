### Fixed

<!-- codeflow:release-impact patch -->
- **Policy authority checks that the remote it asks is the one git uses.**
  When a repository has no fetched copy of its remote yet, CodeFlow asks the
  remote whether it holds anything, and reads policy from `HEAD` only when
  the answer is "nothing yet". It now first checks that the configured
  `remote.<name>.url` is the URL git itself fetches from and pushes to,
  after `insteadOf`, `pushInsteadOf`, `pushurl` and included configuration
  files are applied. If they differ, or git cannot say which URL it uses,
  the guards, the commit hooks and doctor refuse and name both URLs; they
  never read policy from `HEAD` in that state. A remote whose transport is
  outside the hermetic allow-list (`file`, `http`, `https`, `ssh`), such as
  `ext::` or `git://`, is now refused by name with the list shown, where it
  used to get the generic "run git fetch" hint. The same state also refuses
  when the remote's own settings replace or redirect its transport
  (`vcs`, `uploadpack`, `receivepack`), naming the setting, and when a
  configuration file that git includes only for some paths to the
  repository changes URL rewrites, remote settings, includes or the SSH
  client. For an SSH remote it also refuses when git would run a chosen SSH
  program (`GIT_SSH_COMMAND`, `core.sshCommand`, `GIT_SSH`), or when your
  SSH configuration sends the host to a different host name, port, user or
  proxy than plain `ssh` would. Because `ssh` can run a command while it
  reads its configuration, it first reads every SSH configuration file
  `ssh` could read as text: the system files, `~/.ssh/config` under both
  `HOME` and your account's home, and every file their includes can name.
  It refuses, without asking `ssh` to read them, when any line has a word
  containing `exec`, any `Match` block, `ProxyCommand`,
  `KnownHostsCommand`, `LocalCommand`, `PermitLocalCommand` other than
  `no`, or a quote that does not close, or when a file or include cannot
  be read. This refuses more than `ssh` would run, on purpose.
  - A fresh adopter whose empty remote is configured as git uses it is
    unchanged: initialization still reads `HEAD`, and the first push works.
  - A repository that has fetched its remote is unchanged: policy is read
    from the fetched default branch and the remote is not asked.
  - If you meet the new refusal on an empty remote because of a rewrite,
    such as a global `url.<base>.pushInsteadOf`, either set
    `remote.<name>.url` to the URL git really uses, or remove or narrow the
    rewrite so it does not match that remote, then retry. Run
    `git config --show-origin --get-regexp '^(url|include|includeif|remote\.<name>)\.'`
    to find where the rewrite is set. Fetching the remote once it holds
    its default branch also ends the question.
  - If the refusal names a remote transport setting, or a path-conditional
    include, remove that setting from the remote (or move it out of the
    conditional file) until the first push has landed and been fetched.
  - If the refusal names the SSH program or SSH endpoint, compare
    `ssh -G <host>` with `ssh -G -F none <host>`, and leave the program or
    `Host` entry out for that remote until the first push has landed and
    been fetched.
  - If the refusal names a line of an SSH configuration file, remove that
    line or move it out of the files ssh reads by default, or fetch the
    remote once it holds its default branch. To let `ssh` read your own
    SSH configuration as it is, set `accept_ssh_configuration = true`
    under `[policy_authority]` in `~/.codeflow/authority/config.toml`.
    It is off by default. It is read from the account's home in the
    password database, never through `HOME` or `CODEFLOW_HOME`, and the
    shipped agent presets and guards refuse an agent's write to that
    directory, so neither a branch nor an agent can turn it on.
