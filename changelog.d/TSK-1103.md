### Added

<!-- codeflow:release-impact minor -->
- **Project checks run from the default branch before any candidate
  code.** A project declares checks in `.codeflow/base-checks.json` (schema
  `.codeflow/schemas/base-checks.schema.json`); `codeflow update` never
  writes that file. The policy verdict job runs `codeflow ci base-checks`,
  which takes each declared script and its inputs from the default branch's
  commit, so a pull request cannot change the check that judges it, its
  boundary file or the declaration. The script gets the base, head and merge
  commits as git data, a cleared environment with no token, and a timeout.
  A missing, linked or unreadable script or input, a missing interpreter, a
  bad declaration or a timeout fails the check. GitLab, Bitbucket and the
  generic script run the same step from the target commit before the
  candidate's code. `codeflow ci` notes each changed check input and the
  dependency-audit exception check, and `codeflow doctor --check
  ci-perimeter` reports a declaration no managed workflow runs.

### Fixed

<!-- codeflow:release-impact minor -->
- **A pull request is judged against its base branch's current tip.**
  Every managed workflow job now resolves the base branch's tip once and
  judges the range from the merge base with that tip, instead of the base
  commit recorded when the pull request opened, so a run after the base
  moved no longer judges with the old base's policy, pin or audit
  exceptions (issue 602). A base that moves after the verdict is still
  possible; only strict up-to-date checks or a merge queue close it.

<!-- codeflow:release-impact minor -->
- **The gate reads its test config and policy from the base.** On a pull
  request the gates job uses the base tip's `.codeflow/test-config.json` and
  `.codeflow/policy.json`, so a pull request cannot drop a target or lower a
  floor in its own change. A change to either file takes effect after it
  merges, and a base copy that cannot be read fails the job.
