### Changed

<!-- codeflow:release-impact minor -->
- **The shipped instructions require typed code and typed data at every
  boundary (issue 275).** By default, new and changed code is fully typed,
  and every escape type or suppression (`any`, `Any`, an unchecked cast,
  `# type: ignore`, `@ts-expect-error` and the like) carries its reason
  inline. Data crossing a boundary (files, network, process input,
  environment, database rows, user input, another module's untyped output)
  is parsed into a typed model that also validates it, with the typed-model
  library that is standard for the language: Pydantic in Python, zod in
  TypeScript, serde in Rust, structs with a validator in Go. A plain
  dataclass, `TypedDict`, `interface` or cast describes a shape without
  validating it. Shell
  code runs ShellCheck, parses its arguments explicitly and passes
  structured data to a typed language or checks it against its JSON
  Schema. Rego checks its input at run time with `json.match_schema`; a
  Rego schema annotation is a static check only. A new project or file
  that would otherwise be JavaScript is TypeScript, and an existing
  JavaScript codebase is type-checked in place with `checkJs` and JSDoc
  types. The build row of the `AGENTS.md` map makes opening these code
  defaults a required step before writing code. `cf-develop` and
  `cf-stack` add a missing type checker, linter and typed-model library as
  part of the work, and `cf-reviewer` returns `changes_requested` for
  untyped new code, an unexplained escape type, unvalidated boundary data,
  or a hand-written validator where a standard or schema-generated model
  fits. A project that needs to opt out states its reason in the Stack
  standards of its own `AGENTS.md`. Six qualification cases in a new
  `typed-code` pack check the builder and reviewer behavior. Gates do not
  change.

<!-- codeflow:release-impact minor -->
- **The instructions say what belongs in a repository.** A file joins the
  repository only when the project needs it long term, in the smallest
  form that serves its use. Run output, per-run logs, review records,
  superseded drafts, build and cache output, copies kept for reference,
  scratch files, duplicate copies no tool manages and per-task evidence
  folders stay out; an admitted use outranks those exclusions, so a bundle
  the project ships, such as a GitHub action's `dist/index.js`, is not
  refused as build output. Required evidence goes in the PR body or the task
  record; an evidence file lands only when a live record cites it and the
  body cannot carry it, as a summary. A vendored copy a
  runtime needs joins through the project's dependency rule, and a copy
  kept for reference stays out. Git history keeps removed evidence. The
  rule's home is `workflow-discipline.md` "Write only what earns its
  keep"; `cf-develop`, `cf-ship`, `pr-evidence.md` and the evidence
  resource point to it. The `cf-method` row that sent comparison evidence
  to `docs/verification/<task>/` on protected branches now points to the
  PR body. `cf-reviewer` asks of every added file whether it is needed long
  term and in the smallest form that serves its use, its verdict reports
  the added files it checked, and an unneeded or oversized addition is a
  material finding.
  Shipped examples and the docs-portal starter's `exclude` default no
  longer name `docs/verification/`; a project's own portal config is not
  changed. `codeflow update` rewrites the managed rules, skills and agent.

<!-- codeflow:release-impact minor -->
- **Builders declare each value once, and the reviewer flags a new
  unchecked copy (issue 274).** The workflow discipline rules gain
  "Declare each value once" in "Write only what earns its keep":
  - A name, id, path, setting, limit or closed set of strings is declared
    once, as a constant, enum or type, and every use reads it, is generated
    from it or is checked against it. A value used in one place needs no
    constant.
  - A file in another language, such as a workflow, policy or config file,
    holds a generated or checked copy.
  - A shared shape or helper has one home that callers import.
  - Four deliberate copies are allowed with a reason at the site: a test's
    expected value, a stable external protocol or format constant,
    documentation and examples, and a generated or checked mirror.

  `cf-develop` and the design and implementation quality resource point
  at the rule. `cf-reviewer` returns a new unchecked copy of a value or
  code that has a home as a major finding naming the copy and the home.
  `/cf-evaluate-model` gains requirement CF-QA-019 and three cases in the
  quality-core pack. A check that finds copies automatically is planned
  separately.
