### Added

<!-- codeflow:release-impact minor -->
- **The hosted secret scan and dependency audit run locally.**
  `codeflow scan --base <ref> [--head <ref>]` runs the pinned gitleaks
  (8.30.1) over every commit in `base..head` and the pinned osv-scanner
  (2.4.0) over the head's lockfiles, and gives the verdict the managed jobs
  give. The levels, `.gitleaksignore`, the gitleaks configuration,
  `.gitattributes`, each `osv-scanner.toml` and the project exception hook
  come from the base commit, never from the working tree or the range. Each
  scan follows its level: `block` fails the command, `warn` reports, `off`
  skips. A missing or mismatched binary fails closed at `block`; the command
  never downloads one. The audit queries OSV.dev, as the hosted step does.
  With `git.scan_on_push: on` (default `off`), the pre-push hook runs the
  scan on each pushed range and refuses a push the hosted jobs would fail.
  `codeflow doctor --check scan-tools` reports both binaries against their
  pins. This folds in the TSK-430 release note, whose work moved here.

### Fixed

<!-- codeflow:release-impact major -->
- **Pull requests are scanned by the default branch.** The `secret scan`
  check now comes from a job in `codeflow-policy.yml` that GitHub runs from
  the default branch on `pull_request_target`. It runs the authority's scan
  and configuration over every introduced commit, including a finding later
  deleted. A pull request cannot replace its scan step or exempt its own
  finding. The head-run job is gone, and a job of that name in any other
  workflow fails `commit standards`. Git reads ignore replace refs, and push
  and scheduled scans include octopus-merge additions. Legacy-fingerprint
  advice now requires a remerge conflict header naming the path. Push,
  scheduled and manual scans use `history scan`, so a release check that
  read `secret scan` from a push must read `history scan`. Exemptions for
  integration-line scans must land on the default branch. Migration: a
  ruleset or protection rule that requires `secret scan` keeps working
  unchanged, with one exception. The pull request that brings this change has
  no `secret scan` check of its own, because GitHub runs the new job from the
  default branch, which does not hold it yet, and the pull request removes
  the old one. Where the check is required, an administrator merges that one
  pull request with a bypass, or lifts the requirement for that merge. Then
  merge the default branch into each
  integration line at once: until a line has the change, its pull requests
  still run the old job and fail `commit standards`.
