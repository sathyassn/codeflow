### Fixed

<!-- codeflow:release-impact patch -->
- **A landing candidate is judged member by member, so a clean batch
  passes.** `codeflow ci --line-tip integration/EPC-NNN-<slug>`, the same
  run that finds the line from its base, and the push of a `candidate/`
  branch now judge each merge on the candidate's first-parent chain from
  the line's fetched tip at its own reviewed head, against the tip it
  merged onto, as that member's own pull request into the line was judged.
  A task's own criteria change, with a dated `- Amended YYYY-MM-DD:` note
  inside each changed criterion, and its completion land through the
  candidate with no separate planning amendment (issue #488). A merge that
  differs from the clean remerge of its parents, another record's criteria
  change, an undated own change, a task that does not declare the line at
  its tip, a reopened task and an unbound completion are still refused,
  each naming the member. The member's task is read from the records at
  the exact member head; branch names and merge messages grant nothing. A
  merge of the published default target is judged as a sync, a range of its
  own with frozen criteria, as the whole candidate was before. The
  `candidate/` prefix (`git.candidate_prefix`) is now an accepted branch
  name. A landing run that names a task branch with `--branch` is still
  judged member by member, so the name grants no member the own-task rule,
  and a planning member is judged as the planning amendment its own pull
  request into the line is.
- **A batch pull request into `main` is judged member by member.** A
  `candidate/` branch cut from `main`'s fetched tip and holding only no-ff
  merges of reviewed heads passes `codeflow ci --into main`, and its push,
  when each member binds as a single-task pull request into `main` does:
  one changed task record that declares `main` (with a standalone reason,
  or an epic that is neither cancelled nor archived), whose acceptance
  block names a reviewed commit the member head is or holds with only
  clean merges of `main` after it, with an approved verdict. A member with
  no task completion may only add new record files, and its own range gets
  the checks a filing pull request into `main` gets: record rules, the id
  registry, workflow changes and path policy. A new record with an
  acceptance block binds as a task member. No existing criterion
  may change, the bound task's own included; records are matched across a
  member's two parents by id and uid, so a deleted and re-added, renamed or
  split record is still judged against its criteria. The body carries no
  `Task:` line. A direct commit, a hand-resolved merge, a forged member, an
  unreadable record and a shared id or uid are refused, each naming the
  member.
