### Fixed

<!-- codeflow:release-impact patch -->
- **The exec guard now judges the paths an interpreter is given as
  arguments.** In 3.1.1 and earlier, `exec-guard` refused a `python3 -c`
  whose code named an enforcement path, but it never read the
  interpreter's arguments, so `python3 - "<repo>/.claude/settings.json"`
  with a heredoc that wrote `sys.argv[1]` was allowed, and an agent could
  change the settings file where the guard hooks are wired
  (sathyassn/codeflow#173). The guard now reads the arguments of `python`,
  `python3`, `node`, `nodejs`, `perl` and `ruby`, a version suffix
  included: a script's arguments, arguments after inline code or stdin
  `-`, and `--name=value` options, through `env`, `env -S`, `command`, a
  shell `-c` string and `cd`, and the paths `xargs` and `find -exec`
  supply. An argument naming an enforcement path, in this checkout or a
  linked worktree, refuses under `git.hook_integrity`, and one naming
  policy authority metadata always refuses. An argument the guard cannot
  read, such as `"$W/.claude/settings.json"`, refuses when its spelled
  part could name an enforcement path or the line names one, as git-guard
  judges a writer's operands. Reading an enforcement file with an
  interpreter now needs a reader (`cat`, `jq`, `grep`) or a redirect into
  the interpreter's stdin. A path a script builds internally is still past
  the guard; the OS sandbox stays the backstop. The refusal comes from the
  local guard, so installing the 3.2.0 `codeflow` on `PATH` brings it.
