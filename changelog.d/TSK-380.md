### Fixed

<!-- codeflow:release-impact patch -->
- **Search patterns are not write targets.** exec-guard no longer refuses
  a read-only search whose pattern looks like a path, such as
  `rg --files | rg '/CHANGELOG.md$'`, as a shell startup write. The pattern
  words of `rg`, `ag`, `grep`, `egrep`, `fgrep` and `git grep` (the first
  operand when no `-e`, `--regexp`, `-f` or `--file` supplies the pattern,
  and every `-e` or `--regexp` value) are left out of the judgment, called
  directly or run by `xargs`, `parallel -q` or `find -exec`. git-guard's
  `xargs` and `find` rules no longer read such a pattern as the line
  naming an enforcement path. Only a word the shell passes as written
  counts: an unquoted glob, brace or `$` expansion such as `~/.*rc` is
  judged as before, as is any word of a `parallel` command without `-q`
  and the `rg` first operand on a line that names `RIPGREP_CONFIG_PATH`.
  A path operand, a `-f` pattern file, a redirect and any call with an
  option the guard does not know are judged as before, so
  `rg x > ~/.zshrc` is still refused (issue 242).

<!-- codeflow:release-impact patch -->
- **ripgrep preprocessors are judged by what they search.** `rg --pre` or
  `--pre-glob` runs a program on every file it searches, so both guards now
  judge each root it searches as a recursive writer's target: the home, a
  startup directory or a root holding enforcement files refuses, as does a
  `--pre` under `xargs` or `parallel`, whose files come from its input.
  `rg --pre pdftotext needle docs/` still runs where `docs/` holds no
  protected file.
