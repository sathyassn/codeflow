### Fixed

<!-- codeflow:release-impact minor -->
- **The guards judge the helper program a remote's transport starts.** To
  reach a remote, Git can start a helper program chosen by the remote's
  address or its configuration, and the guards did not judge that program
  for every way Git selects it. Both guards now resolve, through one shared
  reading, the transport Git selects for every remote a command contacts,
  after the address rewrites Git applies, and admit only the forms they can
  prove: an address the command names, a named remote with one address and
  no helper setting, the current branch's remote for a fetch or pull that
  names none, and the promisor remotes of a partial clone. New refusals,
  under hook integrity: a command whose transport starts a helper program,
  naming the program and the remote; and every form the guards cannot
  prove, such as a push or remote listing that names no remote, a fetch of
  every remote, a remote group, a remote with several addresses or a
  helper setting, and submodule recursion in a repository that may have
  submodules unless the command turns it off. Transports Git runs itself or
  ships (https, ssh, a local path) keep their verdict. A project that uses
  a helper names it in the new admitted-helpers list of its policy; the
  guards read that list only from the policy landed on the remote's default
  branch, honour it only for a command that does not select another
  repository, and judge an admitted helper as a program word. The same list
  admits a credential helper, such as the GitHub CLI's, that the account
  rule refuses when a fetch or push starts it; the account finding is then
  skipped for commands that contact a remote only, and every other finding
  stands. The list is empty by default. See the policy reference.
