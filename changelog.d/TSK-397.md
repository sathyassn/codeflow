### Changed

<!-- codeflow:release-impact major -->
- **Breaking: the exec guard adds a strict rule where the sandbox is
  absent or loosened.** Before it judges a shell call, the exec guard reads
  the harness configuration of the call's session and repository
  (ADR-0088). Where that configuration shows none of the triggers below,
  the line's rule applies unchanged; this is a reading of files, not proof
  that a sandbox contains the call. The strict rule is added on any of
  these triggers:
  - native Windows under Claude Code or Grok Build;
  - a disabled, fail-open or unset sandbox, or a settings file without a
    shipped floor entry, such as a removed `Edit(...)` deny;
  - an allow entry at a protected path, a startup file or a git
    configuration file, an `allowRead` entry beyond the shipped ones, or
    any `excludedCommands`;
  - an escape setting, including `allowAppleEvents` and
    `enableWeakerNetworkIsolation`;
  - a file that cannot be read, is not a regular file or is over 16 MiB;
  - a Codex profile that grants more than the shipped profile, drops one
    of its denies, widens its network or uses an approval policy other
    than `never`; a Grok profile missing a shipped entry or deny;
  - a Codex or Grok call with no configuration of its harness, a Claude
    call whose hook environment names no session project, or a linked
    worktree whose main checkout cannot be found;
  - a call marked `dangerouslyDisableSandbox`.

  The strict rule judges every word after a program the guard cannot read
  through, with no program exempt by name. On the 49-line everyday sample
  it refuses 42 lines where the line refuses 2, for example
  `cargo test -p "$CRATE"` and `echo "$HOME"`. Neither outcome allows a
  line the line refuses, except a line made only of bare `cd`, `pushd`
  and `popd` builtins, which writes nothing (issue 342, below); the strict
  rule still refuses that line.
  - Migration: run `codeflow doctor --check sandbox`. It prints one line
    per harness, naming each trigger. Fix each trigger (run
    `codeflow update` for a missing floor entry, remove the loosening
    setting), or accept the strict rule on that host. Native Windows
    under Claude Code has no OS sandbox, so it stays strict and has no
    remedy.
  - The new policy key `security.text_guard: strict` applies the strict
    rule on every host. No value loosens the guard.
  - What no file shows is not read, and those calls get the line's rule
    today: a `--settings` file, server-managed settings, MDM policy, a
    Codex launch flag such as `--sandbox danger-full-access`, the session
    of a call whose harness is not identified, and an unsandboxed retry
    the harness does not mark. Claude Code 2.1.312 marks its retries;
    Codex does not. Failing closed there is tracked as TSK-1052.
  - Other limits are as before: a program whose text the guard does not
    read, such as a script file, is contained only by the OS sandbox; the
    `Monitor` tool is outside the hook matcher; policy refs are writable by
    a direct file write.
<!-- codeflow:release-impact patch -->
- **The presets deny writes to the enforcement paths explicitly.** The
  shipped Claude presets list each enforcement path as a
  `sandbox.filesystem.denyWrite` entry beside its `Edit(...)` deny, and a
  new protected directory, `~/.codeflow/authority/`, is denied in the
  Claude presets, the Codex `cf-guard` profile and the Grok profiles. No
  command uses it yet. `codeflow update` delivers both.

### Fixed

<!-- codeflow:release-impact patch -->
- **A directory change is not a startup file write.** The shell's own
  `cd`, `pushd` or `popd` whose operand the guard cannot resolve is no
  longer refused under `security.shell_startup` (issue 342), on a line
  made only of bare `cd`, `pushd` and `popd` builtins with literal or
  plain `"$var"` arguments. Any other line keeps the write judgment.
<!-- codeflow:release-impact patch -->
- **Commands the shell and the guard would read differently.** A command
  holding a NUL byte is refused. The headless-run check no longer guesses
  the program after an `xargs` option it cannot place (GNU's bare
  `--replace`, `--eof` and `--max-lines`, BSD's `-J`, `-R` and `-S`), and
  reads GNU-prefixed launchers such as `gxargs`.
