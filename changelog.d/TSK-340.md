### Fixed

<!-- codeflow:release-impact minor -->
- **One acceptance sequence for blocked, reopened and closed work.** A task
  that was blocked after its review, then completed, now passes its pull
  request's `codeflow ci`: the `## Blocker` section `task status` writes and
  removes is not reviewed scope, while any other text in that section, the
  criteria and the rest of the record stay reviewed (issue #198). A task
  reopened more than once keeps one chronological archive of superseded
  acceptance blocks, which `task status` and `codeflow ci` accept against
  the line and against `main` alike. An archived block stays byte for byte
  unless a validated redaction rewords it, and the newly archived blocks
  must be every completion the range's history made, in order, counting
  each occurrence (an identical block completed again after a reopen is a
  second completion), each with a reviewed commit and waiver commits that
  exist and precede it, so a
  reordered, dropped, rewritten, invented or forged archived block is
  refused
  (issue #217). A pull request that reopens its task may merge its target
  cleanly after the review, as any task pull request may, so a later
  planning change on the line no longer forces a new review; in exchange
  it is judged commit by commit after the review, so a post-review edit to
  another path that a later commit reverts is now refused where only the
  net change was judged before. A task landing counts only when its merge
  sits on the first-parent line of a receiving line the run pins
  (`--base`, `--into`, a verified line head or a release import's
  attributed source); a local branch, a fetched unprotected branch or a
  target the record declares never adds one. Local `task status` grants landing,
  stacking and waiver authority in a clone with remotes only with the new
  `--base` and `--into` options, because any process in the clone can
  change the git settings that would otherwise decide the target; without
  them it judges only the reviewed span and a refusal names the pins.
  Hosted CI pins its own base and is the authority. With pins, a declared
  target counts only when data at the pinned tip names it (the protected
  list, or an open epic there whose task declares that line; an
  `integration/` prefix earns nothing), and a pinned ref that is not
  fetched refuses, naming the fetch; a clone with no remotes uses its
  local `main`, else `master`. A merge of the
  review into a side branch is therefore no landing, so the side branch's
  work needs the review. "On the target" for a waiver means the same
  pinned receiving lines, so an amendment made on a local or fetched
  branch is no target amendment. A waiver on the target must be an
  amendment the reviewed commit contains, so no merge after the review
  supplies one; a completion made after the task landed can no longer
  waive a planning amendment its review never saw. A waiver naming a records-only commit in the task's own pull
  request is accepted after a reopen of a completion that never landed and
  on a branch whose name carries no task id; after a reopen of a landed
  completion the refusal says the waiver must name a planning commit on
  the target that amends the criterion (issue #278). The same holds when
  the reopen came from a records-only commit after the review that
  changed another record, such as a removed follow-up record (issue #354),
  and every waiver refused as not on the target now says what that
  requires (a receiving line the run pins holds the commit) and names the
  route: a planning pull request into the target that amends the
  criterion, merged into the branch before the review.
