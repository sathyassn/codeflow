### Fixed

<!-- codeflow:release-impact minor -->
- **CodeFlow 3.1 and 4.0 gates on one machine no longer run at the same
  time.** A 3.1 gate locks only `full-gate.lock`, so a 4.0 run that held
  only a later slot let it start at full width beside heavy work. Every 4.0
  run now holds `full-gate.lock` shared for its whole life, as a fence, and
  its slots are `full-gate-1.lock` and up. A 3.1 gate started while a 4.0
  run is active refuses as it does beside another 3.1 gate. A 4.0 run
  started while a 3.1 gate, or the surviving targets of a killed one, are
  active refuses at once, naming the last recorded holder, and takes no
  slot. On Unix every target of an admitted run inherits the run's hold
  on `full-gate.lock`, so 3.1 gates stay out while any process of the
  target runs, after a killed gate too. A daemon that closes inherited descriptors escapes the
  hold, one that keeps them delays 3.1 gates until it exits, a target that
  unlocks it releases it, and on NFS the hold ends with the gate.
  `full-gate.record` names the last admitted 4.0 run, which may have ended,
  in the one-holder format older readers parse; `codeflow test
  --lock-status` shows the recorded slots and target groups. Lock files an
  earlier 4.0 line build left need no cleanup. Unreleased 4.0 line builds
  that include TSK-1145 but not this change take a later slot when
  `full-gate.lock` is busy, so they are not fenced out and can run beside
  this version at full width: let their runs end, or rebuild them, before
  running this version on the same machine.
